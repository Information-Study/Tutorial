## 檔案佈局與權限 ★★

```
/etc/ssl/
├── certs/                          ★ 644（公開，任何人可讀）
│   ├── app.example.gov.tw.crt              伺服器憑證
│   ├── app.example.gov.tw-fullchain.crt    ★ 伺服器 + 中繼（部署用）
│   └── ca-chain.crt                        中繼 + 根（驗證用）
│
└── private/                        ★★ 700（目錄本身就要鎖）
    └── app.example.gov.tw.key              ★★ 600 root:root
```

```bash
# ═══ ★★ 標準權限 ═══
$ sudo chmod 755 /etc/ssl/certs
$ sudo chmod 700 /etc/ssl/private          # ★★ 目錄就要鎖
$ sudo chown root:root /etc/ssl/private

$ sudo chmod 644 /etc/ssl/certs/*.crt
$ sudo chmod 600 /etc/ssl/private/*.key    # ★★
$ sudo chown root:root /etc/ssl/private/*.key

# ★ 驗證
$ sudo ls -la /etc/ssl/private/
drwx------ 2 root root 4096 Aug 28 12:00 .
-rw------- 1 root root 1704 Aug 28 12:00 app.example.gov.tw.key
```

> [!danger] 私鑰權限的三個要點 ★★★
> ```
> ① ★★ 私鑰【永遠 600 root:root】
>    → Nginx/Apache 的 master process 以 root 啟動並讀取私鑰，
>      之後才降權給 worker → ★ 不需要給 www-data 讀
>
> ② ★★ 目錄本身也要 700
>    → 只鎖檔案不鎖目錄，攻擊者仍能列出檔名（資訊洩漏）
>
> ③ ★★★ 【絕對不要】把私鑰放在 web root 下
>    → /var/www/html/ssl/server.key
>      → 可能被直接下載 → PKI 淪陷
>
> ★ 檢查腳本：
>   sudo find /var/www /srv -name '*.key' -o -name '*.pem' 2>/dev/null
>   → 有輸出就要立刻處理
> ```

```bash
# ★★ 私鑰外洩檢查（定期跑）
$ sudo tee /usr/local/bin/check-key-exposure >/dev/null <<'EOF'
#!/usr/bin/env bash
echo "═══ 私鑰外洩檢查 ═══"

echo -e "\n【1】★★ web root 下有沒有金鑰檔"
FOUND=$(sudo find /var/www /srv /usr/share/nginx 2>/dev/null \
    \( -name '*.key' -o -name '*.pem' -o -name '*.p12' -o -name '*.pfx' \) -print)
[ -n "$FOUND" ] && { echo "  ✗✗ 發現："; echo "$FOUND" | sed 's/^/     /'; } \
                || echo "  ✓ 沒有"

echo -e "\n【2】權限"
sudo find /etc/ssl/private /etc/nginx/ssl /etc/pki -name '*.key' 2>/dev/null | \
while read -r k; do
    P=$(stat -c '%a' "$k"); O=$(stat -c '%U:%G' "$k")
    if [ "$P" -gt 600 ] 2>/dev/null; then
        printf '  ✗ %-50s %s %s\n' "$k" "$P" "$O"
    else
        printf '  ✓ %-50s %s %s\n' "$k" "$P" "$O"
    fi
done

echo -e "\n【3】★ git repo 中有沒有金鑰"
for r in /var/www/*/; do
    [ -d "$r/.git" ] || continue
    K=$(cd "$r" && git ls-files 2>/dev/null | grep -E '\.(key|pem|p12|pfx)$')
    [ -n "$K" ] && echo "  ✗✗ $r 的 git 追蹤了：$K"
done

echo -e "\n【4】備份檔"
sudo find /etc /var/www -name '*.key.bak' -o -name '*.key~' -o -name '*.key.orig' 2>/dev/null | \
  sed 's/^/  ⚠ /'
EOF
$ sudo chmod +x /usr/local/bin/check-key-exposure && sudo check-key-exposure
```

## Nginx

```nginx
# /etc/nginx/sites-available/app.conf
server {
    listen 80;
    listen [::]:80;
    server_name app.example.gov.tw www.app.example.gov.tw;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;                                   # ★ Nginx 1.25.1+ 的新寫法
    server_name app.example.gov.tw www.app.example.gov.tw;

    # ═══ ★★ 憑證 ═══
    ssl_certificate     /etc/ssl/certs/app.example.gov.tw-fullchain.crt;  # ★ 伺服器+中繼
    ssl_certificate_key /etc/ssl/private/app.example.gov.tw.key;

    # ★ 驗證用（OCSP stapling 與 mTLS 需要）
    ssl_trusted_certificate /etc/ssl/certs/ca-chain.crt;

    # ═══ 協定與加密套件 ═══
    ssl_protocols       TLSv1.2 TLSv1.3;        # ★ 不要開 TLSv1/1.1
    ssl_ciphers         ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
    ssl_prefer_server_ciphers off;              # ★ TLS 1.3 起讓客戶端選

    # ═══ Session 快取（★ 明顯降低握手成本）═══
    ssl_session_cache   shared:SSL:10m;         # ★ 10m ≈ 40000 個 session
    ssl_session_timeout 1d;
    ssl_session_tickets off;                    # ★ 關掉以保有前向保密

    # ═══ OCSP stapling（★ 公信 CA 才開）═══
    # ssl_stapling on;
    # ssl_stapling_verify on;
    # resolver 8.8.8.8 1.1.1.1 valid=300s;
    # resolver_timeout 5s;

    # ═══ HSTS（★ 確認 HTTPS 穩定後才開）═══
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    root /var/www/app/current/dist;
    index index.html;
    location / { try_files $uri $uri/ /index.html; }
}
```

> [!danger] 內部 CA 不要開 OCSP stapling ★★
> ```
> ssl_stapling on 需要憑證裡有 authorityInfoAccess 的 OCSP URI，
> 而且那個 OCSP responder 必須真的在跑
>
> 內部 CA 通常【沒有 OCSP responder】
>   → Nginx 每次啟動會嘗試連線 → 逾時
>     → error log 大量：
>       ssl_stapling ignored, host not found in OCSP responder
>     → ★ 不影響功能，但會拖慢啟動並塞滿日誌
>
> ★★ 內部 CA 用【CRL】做撤銷檢查，不要開 stapling
> ```

### ★★ SNI 多站台

```nginx
# ★ 一個 IP 上多個 HTTPS 站台，各自的憑證
server {
    listen 443 ssl default_server;              # ★★ 一定要有 default_server
    http2 on;
    server_name _;
    ssl_certificate     /etc/ssl/certs/default-fullchain.crt;
    ssl_certificate_key /etc/ssl/private/default.key;
    return 444;                                 # ★ 未知的 Host 直接斷線
}

server {
    listen 443 ssl;
    http2 on;
    server_name app.example.gov.tw;
    ssl_certificate     /etc/ssl/certs/app-fullchain.crt;
    ssl_certificate_key /etc/ssl/private/app.key;
    # ...
}

server {
    listen 443 ssl;
    http2 on;
    server_name crm.example.gov.tw;
    ssl_certificate     /etc/ssl/certs/crm-fullchain.crt;
    ssl_certificate_key /etc/ssl/private/crm.key;
    # ...
}
```

> [!warning] `default_server` 的重要性 ★★
> ```
> 沒有 default_server 時：
>   → Nginx 用【第一個】listen 443 的 server 區塊當預設
>     → ★ 用 IP 直連或未知 Host 時會拿到那個站台的憑證
>       → 憑證名稱不符的警告，且洩漏站台資訊
>
> ★★ 一定要明確設一個 default_server 並 return 444
> ```

```bash
# ★ 測試 SNI 是否正確
$ for h in app.example.gov.tw crm.example.gov.tw; do
    printf '%-30s ' "$h"
    echo | openssl s_client -connect 10.0.20.15:443 -servername "$h" 2>/dev/null | \
      openssl x509 -noout -subject 2>/dev/null | sed 's/.*CN *= *//'
  done
app.example.gov.tw             app.example.gov.tw
crm.example.gov.tw             crm.example.gov.tw

# ★ 不帶 SNI（模擬舊客戶端或 IP 直連）
$ echo | openssl s_client -connect 10.0.20.15:443 2>/dev/null | \
    openssl x509 -noout -subject
subject=CN=default                            # ★ 應該是 default_server 的憑證
```

### ★ 多憑證（RSA + ECDSA 雙憑證）

```nginx
# ★ 同時提供 RSA 與 ECDSA 憑證，客戶端自動選
# → 現代客戶端用 ECDSA（握手更快、憑證更小）
# → 舊客戶端 fallback 到 RSA
ssl_certificate     /etc/ssl/certs/app-ecdsa-fullchain.crt;
ssl_certificate_key /etc/ssl/private/app-ecdsa.key;
ssl_certificate     /etc/ssl/certs/app-rsa-fullchain.crt;
ssl_certificate_key /etc/ssl/private/app-rsa.key;
# ★ Nginx 1.11.0+ 支援；順序無關，Nginx 依客戶端能力選
```

```bash
# ★ 簽發 ECDSA 憑證（用 08 篇的腳本）
$ sudo KEYTYPE=ec issue-cert app.example.gov.tw

# ★ 驗證雙憑證
$ echo | openssl s_client -connect app.example.gov.tw:443 \
    -servername app.example.gov.tw -cipher 'ECDSA' 2>/dev/null | \
    openssl x509 -noout -text | grep 'Public Key Algorithm'
        Public Key Algorithm: id-ecPublicKey
```

### HTTP/3（QUIC）

```nginx
server {
    listen 443 ssl;
    listen 443 quic reuseport;                  # ★ reuseport 只在一個 server 用
    http2 on;
    http3 on;

}
```

## Apache

```apache
# /etc/apache2/sites-available/app-ssl.conf
<VirtualHost *:443>
    ServerName app.example.gov.tw
    ServerAlias www.app.example.gov.tw
    DocumentRoot /var/www/app/current/public

    SSLEngine on

    # ═══ ★★ 憑證（★ Apache 分三個檔，與 Nginx 不同）═══
    SSLCertificateFile      /etc/ssl/certs/app.example.gov.tw.crt      # ★ 只有伺服器憑證
    SSLCertificateKeyFile   /etc/ssl/private/app.example.gov.tw.key
    SSLCertificateChainFile /etc/ssl/certs/intermediate.crt            # ★ 中繼

    # ★ Apache 2.4.8+ 也接受 fullchain 放在 SSLCertificateFile
    #   SSLCertificateFile /etc/ssl/certs/app-fullchain.crt
    #   （SSLCertificateChainFile 已 deprecated）

    SSLProtocol             -all +TLSv1.2 +TLSv1.3
    SSLCipherSuite          ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384
    SSLHonorCipherOrder     off
    SSLSessionTickets       off

    Header always set Strict-Transport-Security "max-age=31536000; includeSubDomains"

    <Directory /var/www/app/current/public>
        Options -Indexes +FollowSymLinks
        AllowOverride None                      # ★ 效能與安全
        Require all granted
    </Directory>
</VirtualHost>

<VirtualHost *:80>
    ServerName app.example.gov.tw
    Redirect permanent / https://app.example.gov.tw/
</VirtualHost>
```

```bash
# ★ 啟用模組
$ sudo a2enmod ssl headers http2
$ sudo a2ensite app-ssl
$ sudo apache2ctl configtest
Syntax OK
$ sudo systemctl reload apache2

# ★ Apache 的憑證檢查
$ sudo apache2ctl -t -D DUMP_VHOSTS
```

> [!warning] Apache 三個檔 vs Nginx 一個檔 ★★
> ```
> Nginx：
>   ssl_certificate  = 伺服器憑證 + 中繼憑證（★ 合併在一個檔）
>
> Apache（2.4.8 以前）：
>   SSLCertificateFile      = ★ 只有伺服器憑證
>   SSLCertificateChainFile = ★ 中繼憑證（分開）
>
> Apache 2.4.8+：
>   SSLCertificateFile = 可以放 fullchain（★ 與 Nginx 一致）
>   SSLCertificateChainFile 已 deprecated
>
> ★★ 常見錯誤：把 fullchain 給 Apache 2.4.8 以前的 SSLCertificateFile
>   → AH02561: Failed to configure certificate
> ```

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> ```bash
> # ★ 設定檔位置不同
> /etc/httpd/conf.d/ssl.conf              # ← RHEL
> /etc/apache2/sites-available/*.conf     # ← Ubuntu
>
> # ★ 服務名稱
> sudo systemctl reload httpd             # ← RHEL
> sudo systemctl reload apache2           # ← Ubuntu
>
> # ★ 語法檢查
> sudo apachectl configtest               # 兩者都可
>
> # ★ 模組（RHEL 用 dnf 裝，預設就啟用）
> sudo dnf install -y mod_ssl
>
> # ★★ SELinux！RHEL 系要注意
> sudo semanage fcontext -a -t cert_t "/etc/ssl/certs(/.*)?"
> sudo restorecon -Rv /etc/ssl/certs
> # 或直接用 RHEL 的標準位置：
> #   /etc/pki/tls/certs/  與  /etc/pki/tls/private/
> ```

### MySQL / MariaDB

```bash
# ═══ ★ MySQL 的憑證要 mysql 使用者能讀 ═══
$ sudo mkdir -p /etc/mysql/ssl
$ sudo cp /etc/ssl/certs/db.internal.example.gov.tw.crt /etc/mysql/ssl/server-cert.pem
$ sudo cp /etc/ssl/private/db.internal.example.gov.tw.key /etc/mysql/ssl/server-key.pem
$ sudo cp /etc/ssl/certs/ca-chain.crt /etc/mysql/ssl/ca.pem

$ sudo chown -R mysql:mysql /etc/mysql/ssl
$ sudo chmod 700 /etc/mysql/ssl
$ sudo chmod 600 /etc/mysql/ssl/server-key.pem
$ sudo chmod 644 /etc/mysql/ssl/server-cert.pem /etc/mysql/ssl/ca.pem
```

```ini
# /etc/mysql/mysql.conf.d/ssl.cnf
[mysqld]
ssl_ca   = /etc/mysql/ssl/ca.pem
ssl_cert = /etc/mysql/ssl/server-cert.pem
ssl_key  = /etc/mysql/ssl/server-key.pem

# ★★ 強制所有連線用 TLS
require_secure_transport = ON

# ★ 最低 TLS 版本
tls_version = TLSv1.2,TLSv1.3
```

```bash
$ sudo systemctl restart mysql          # ★★ MySQL 要 restart，不能 reload

# ★ 驗證
$ mysql -u root -p -e "SHOW VARIABLES LIKE '%ssl%';"
+---------------+---------------------------------+
| have_ssl      | YES                             |   # ★★
| ssl_ca        | /etc/mysql/ssl/ca.pem           |
| ssl_cert      | /etc/mysql/ssl/server-cert.pem  |
+---------------+---------------------------------+

$ mysql -u root -p -e "\s" | grep SSL
SSL:  Cipher in use is TLS_AES_256_GCM_SHA384      # ★

# ★ 從客戶端測試
$ mysql -h db.internal.example.gov.tw -u app -p \
    --ssl-ca=/etc/ssl/certs/ca-chain.crt \
    --ssl-mode=VERIFY_IDENTITY \
    -e "SELECT 1;"
# ★★ VERIFY_IDENTITY = 驗證憑證 + 驗證主機名（最嚴格）
```

> [!danger] MySQL 的 `--ssl-mode` 一定要用對 ★★
> ```
> DISABLED         不用 TLS
> PREFERRED        ★ 預設值 —— 有 TLS 就用，【但不驗證憑證】
> REQUIRED         必須 TLS，【但不驗證憑證】
> VERIFY_CA        驗證憑證是否由信任的 CA 簽發
> ★★ VERIFY_IDENTITY  驗證憑證【並且】驗證主機名
>
> ★★★ 只有 VERIFY_IDENTITY 能防中間人攻擊
>    PREFERRED / REQUIRED 都可以被攔截（攻擊者出示自簽憑證也會被接受）
> ```

```sql
-- ★★ 強制特定使用者必須用 TLS
CREATE USER 'app'@'%' IDENTIFIED BY '...' REQUIRE SSL;
-- ★ 更嚴：必須用特定 CA 簽發的客戶端憑證
CREATE USER 'app'@'%' IDENTIFIED BY '...'
  REQUIRE ISSUER '/C=TW/O=Example Government Agency/CN=Example Gov Issuing CA';
-- ★ 最嚴：綁定特定的客戶端憑證 Subject
CREATE USER 'app'@'%' IDENTIFIED BY '...'
  REQUIRE SUBJECT '/C=TW/O=Example Government Agency/CN=app-client';

ALTER USER 'app'@'%' REQUIRE SSL;
FLUSH PRIVILEGES;

-- 檢查
SELECT user, host, ssl_type, ssl_cipher, x509_issuer FROM mysql.user;
```

```php
// ★★ Laravel 的 config/database.php

],
```

### PostgreSQL

```bash
# ═══ ★ PostgreSQL 對權限【非常嚴格】═══
$ sudo mkdir -p /etc/postgresql/ssl
$ sudo cp /etc/ssl/certs/db-fullchain.crt /etc/postgresql/ssl/server.crt
$ sudo cp /etc/ssl/private/db.key         /etc/postgresql/ssl/server.key
$ sudo cp /etc/ssl/certs/ca-chain.crt     /etc/postgresql/ssl/root.crt

$ sudo chown postgres:postgres /etc/postgresql/ssl/*
$ sudo chmod 600 /etc/postgresql/ssl/server.key    # ★★ 必須 600 或更嚴
$ sudo chmod 644 /etc/postgresql/ssl/server.crt /etc/postgresql/ssl/root.crt
```

> [!danger] PostgreSQL 的私鑰權限檢查 ★★
> ```
> PostgreSQL 啟動時會【主動檢查】私鑰權限，不符就【拒絕啟動】：
>
>   FATAL: private key file "/etc/postgresql/ssl/server.key"
>          has group or world access
>   DETAIL: File must have permissions u=rw (0600) or less if owned by
>           the database user, or permissions u=rw,g=r (0640) or less
>           if owned by root.
>
> ★★ 兩種合法組合：
>   ① postgres:postgres  600
>   ② root:postgres      640
> ```

```ini
# /etc/postgresql/17/main/postgresql.conf
ssl = on
ssl_cert_file = '/etc/postgresql/ssl/server.crt'
ssl_key_file  = '/etc/postgresql/ssl/server.key'
ssl_ca_file   = '/etc/postgresql/ssl/root.crt'      # ★ 客戶端憑證驗證用

ssl_min_protocol_version = 'TLSv1.2'
ssl_prefer_server_ciphers = on
```

```
# /etc/postgresql/17/main/pg_hba.conf
# ★★ hostssl = 只允許 TLS 連線（host 會同時接受明文）
hostssl  appdb  appuser  10.0.20.0/24  scram-sha-256

# ★ 更嚴：要求客戶端憑證（mTLS）
hostssl  appdb  appuser  10.0.20.0/24  cert clientcert=verify-full

# ★★ 明確拒絕非 TLS 連線
hostnossl all    all      0.0.0.0/0     reject
```

> [!warning] Node 讀私鑰需要權限 ★★
> ```
> Node 應用通常以非 root 執行（★ 應該如此）
>   → 讀不到 600 root:root 的私鑰
>
> ★★ 三種解法（由好到壞）：
>   ① 【最好】不要讓 Node 處理 TLS ——
>      放在 Nginx 後面，Node 只聽 127.0.0.1 的 HTTP
>
>   ② systemd 的 LoadCredential（★ Node 22 可讀 $CREDENTIALS_DIRECTORY）
>      [Service]
>      LoadCredential=tls-key:/etc/ssl/private/app.key
>      LoadCredential=tls-crt:/etc/ssl/certs/app-fullchain.crt
>      → 程式讀 process.env.CREDENTIALS_DIRECTORY + '/tls-key'
>
>   ③ 建一個 ssl-cert 群組
>      sudo groupadd -f ssl-cert
>      sudo usermod -aG ssl-cert nodeapp
>      sudo chgrp ssl-cert /etc/ssl/private/app.key
>      sudo chmod 640 /etc/ssl/private/app.key
>      sudo chmod 750 /etc/ssl/private
>      → ★ 注意這會讓群組成員都能讀私鑰
> ```

> [!danger] 容器裡的私鑰權限 ★★
> ```
> ① ★★ 一律用 :ro 掛載（唯讀）
>    → 容器內的程序無法竄改或刪除
>
> ② ★ 容器內的 UID 與宿主機不同
>    → nginx:alpine 的 nginx 使用者是 UID 101
>      → 宿主機的 600 root:root 私鑰在容器內【讀不到】
>    → ★ 但 Nginx 的 master 以 root 啟動，可以讀 → 通常沒問題
>    → 非 root 容器就會有問題
>
> ③ ★★★ 【不要】把私鑰 COPY 進映像
>    → 映像會被推到 registry → 任何能 pull 的人都拿得到私鑰
>    → docker history <image> 也看得到
>    → ★ 一律用 volume 掛載或 secrets
>
> ④ ★ 用 Docker secrets（Swarm）或 Compose 的 secrets
> ```

## 部署後的重載 ★★

| 服務 | 憑證更換後 | 說明 |
| --- | --- | --- |
| **Nginx** | `systemctl reload nginx` ★ | **零停機**（graceful） |
| **Apache** | `systemctl reload apache2` ★ | 零停機 |
| **MySQL** | `systemctl restart mysql` ★★ | **要 restart**（8.0.16+ 可 `ALTER INSTANCE RELOAD TLS`） |
| **PostgreSQL** | `systemctl reload postgresql` | 憑證檔可 reload |
| **Redis** | `systemctl restart redis-server` | 要 restart |
| **HAProxy** | `systemctl reload haproxy` | 零停機 |
| Node.js（自帶 TLS） | 依實作 | 通常要 restart |
| Docker 容器 | `docker compose restart <svc>` | 掛載的檔案變了要重啟容器 |

```bash
# ★★ MySQL 8.0.16+ 可以不用重啟
$ mysql -u root -p -e "ALTER INSTANCE RELOAD TLS;"
# ★ 只影響【新連線】，既有連線繼續用舊憑證

# ★★ Nginx reload 前一定要 -t
$ sudo nginx -t && sudo systemctl reload nginx
# ★ 不 -t 直接 reload → 設定有錯時 Nginx 會【保持舊設定繼續跑】（不會掛）
#   但你會以為換好了

# ★ Apache
$ sudo apache2ctl configtest && sudo systemctl reload apache2
```

```bash
#!/usr/bin/env bash
# /usr/local/bin/reload-tls —— 憑證更新後統一重載
set -uo pipefail

echo "═══ 重載使用 TLS 的服務 ═══"

reload() { # reload <服務> <測試指令> <重載指令>
    systemctl is-active --quiet "$1" || { printf '  %-16s － 未執行\n' "$1"; return; }
    printf '  %-16s ' "$1"
    if [ -n "$2" ] && ! eval "$2" >/dev/null 2>&1; then
        echo "✗ 設定檔語法錯誤，跳過"
        eval "$2" 2>&1 | sed 's/^/       /'
        return 1
    fi
    if eval "$3" >/dev/null 2>&1; then echo "✓"; else echo "✗ 重載失敗"; return 1; fi
}

reload nginx     "nginx -t"            "systemctl reload nginx"
reload apache2   "apache2ctl configtest" "systemctl reload apache2"
reload httpd     "apachectl configtest"  "systemctl reload httpd"
reload postgresql ""                   "systemctl reload postgresql"
reload haproxy   "haproxy -c -f /etc/haproxy/haproxy.cfg" "systemctl reload haproxy"

# ★★ 需要 restart 的
for s in mysql mariadb redis-server; do
    systemctl is-active --quiet "$s" || continue
    printf '  %-16s ' "$s"
    if [ "$s" = mysql ] || [ "$s" = mariadb ]; then
        # ★ 先試 ALTER INSTANCE RELOAD TLS（不用停機）
        if mysql -e "ALTER INSTANCE RELOAD TLS;" 2>/dev/null; then
            echo "✓（RELOAD TLS，免重啟）"; continue
        fi
    fi
    echo -n "★ 需要 restart（會斷線）… "
    systemctl restart "$s" && echo "✓" || echo "✗"
done

echo -e "\n★ 驗證："
echo "  echo | openssl s_client -connect localhost:443 -servername <host> 2>/dev/null | \\"
echo "    openssl x509 -noout -dates"
```

## 完整實戰範例：LXMP 全套 TLS 部署

```bash
#!/usr/bin/env bash
# LXMP（Nginx + MySQL + PHP + Vue/Nuxt + Laravel）全套 TLS 部署
set -euo pipefail

FRONT=app.example.gov.tw
API=api.example.gov.tw
DB=db.internal.example.gov.tw
CA_CHAIN=/root/ca/issuing-ca/certs/ca-chain.cert.pem

echo "═══════ LXMP 全套 TLS 部署 ═══════"

# ══ ① 簽發憑證 ══
echo -e "\n【①】簽發憑證"
sudo issue-cert "$FRONT" "$API"      # ★ 前後端同機 → 一張憑證兩個 SAN
sudo issue-cert "$DB"                # ★ 資料庫另一台 → 分開簽

# ══ ② 部署到 Nginx ══
echo -e "\n【②】部署到 Nginx"
SF=$(echo "$FRONT" | tr -c 'a-zA-Z0-9.-' '_')
sudo install -m 644 "/etc/ssl/issued/$SF-fullchain.crt" /etc/ssl/certs/
sudo install -m 600 "/etc/ssl/issued/$SF.key"           /etc/ssl/private/
sudo install -m 644 "$CA_CHAIN" /etc/ssl/certs/ca-chain.crt

sudo tee /etc/nginx/sites-available/lxmp.conf >/dev/null <<EOF
# ─────────── 共用的 SSL 設定 ───────────
# （放在 /etc/nginx/snippets/ssl-common.conf 更好）

server {
    listen 80;
    listen [::]:80;
    server_name $FRONT $API;
    return 301 https://\$host\$request_uri;
}

# ─────────── 前端 Vue / Nuxt ───────────
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name $FRONT;

    ssl_certificate         /etc/ssl/certs/$SF-fullchain.crt;
    ssl_certificate_key     /etc/ssl/private/$SF.key;
    ssl_trusted_certificate /etc/ssl/certs/ca-chain.crt;
    ssl_protocols           TLSv1.2 TLSv1.3;
    ssl_ciphers             ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;
    ssl_session_cache       shared:SSL:10m;
    ssl_session_timeout     1d;
    ssl_session_tickets     off;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options nosniff always;
    add_header X-Frame-Options SAMEORIGIN always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;

    # ── Nuxt SSR（PM2 在 3000）──
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    \$http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       \$host;
        proxy_set_header X-Real-IP  \$remote_addr;
        proxy_set_header X-Forwarded-For   \$proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto \$scheme;   # ★★ 沒有這行 HTTPS 會壞
        proxy_read_timeout 60s;
    }

    # ── 靜態資源 ──
    location /_nuxt/ {
        alias /var/www/app/current/.output/public/_nuxt/;
        expires 1y;
        add_header Cache-Control "public, immutable";
        add_header X-Content-Type-Options nosniff always;   # ★ 要重複宣告
    }
}

# ─────────── 後端 Laravel ───────────
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name $API;

    ssl_certificate         /etc/ssl/certs/$SF-fullchain.crt;
    ssl_certificate_key     /etc/ssl/private/$SF.key;
    ssl_trusted_certificate /etc/ssl/certs/ca-chain.crt;
    ssl_protocols           TLSv1.2 TLSv1.3;
    ssl_session_cache       shared:SSL:10m;
    ssl_session_tickets     off;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    root /var/www/api/current/public;
    index index.php;

    location / { try_files \$uri \$uri/ /index.php?\$query_string; }

    location ~ \.php\$ {
        try_files \$uri =404;                     # ★★ 防 PathInfo 攻擊
        fastcgi_pass unix:/run/php/php8.3-fpm-api.sock;
        fastcgi_index index.php;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME \$realpath_root\$fastcgi_script_name;
        fastcgi_param DOCUMENT_ROOT   \$realpath_root;
        fastcgi_param HTTPS on;                   # ★★ 讓 Laravel 知道是 HTTPS
        fastcgi_read_timeout 60s;
    }

    location ~ /\.        { deny all; }
    location ~ composer\. { deny all; }
}
EOF

sudo ln -sfn /etc/nginx/sites-available/lxmp.conf /etc/nginx/sites-enabled/lxmp.conf
sudo nginx -t && sudo systemctl reload nginx
echo "  ✓ Nginx"

# ══ ③ MySQL TLS ══
echo -e "\n【③】MySQL TLS（在 $DB 上執行）"
cat <<'EOF'
  sudo mkdir -p /etc/mysql/ssl
  sudo cp /etc/ssl/issued/db_*-fullchain.crt /etc/mysql/ssl/server-cert.pem
  sudo cp /etc/ssl/issued/db_*.key           /etc/mysql/ssl/server-key.pem
  sudo cp /root/ca/issuing-ca/certs/ca-chain.cert.pem /etc/mysql/ssl/ca.pem
  sudo chown -R mysql:mysql /etc/mysql/ssl
  sudo chmod 700 /etc/mysql/ssl && sudo chmod 600 /etc/mysql/ssl/server-key.pem

  sudo tee /etc/mysql/mysql.conf.d/ssl.cnf <<'CNF'
[mysqld]
ssl_ca   = /etc/mysql/ssl/ca.pem
ssl_cert = /etc/mysql/ssl/server-cert.pem
ssl_key  = /etc/mysql/ssl/server-key.pem
require_secure_transport = ON
tls_version = TLSv1.2,TLSv1.3
CNF
  sudo systemctl restart mysql
  mysql -e "ALTER USER 'app'@'%' REQUIRE SSL; FLUSH PRIVILEGES;"
EOF

# ══ ④ Laravel 設定 ══
echo -e "\n【④】Laravel .env"
cat <<EOF
  APP_URL=https://$API
  ASSET_URL=https://$API

  DB_HOST=$DB
  MYSQL_ATTR_SSL_CA=/etc/ssl/certs/ca-chain.crt

  SESSION_SECURE_COOKIE=true        # ★★ 只在 HTTPS 送 cookie
  SESSION_SAME_SITE=lax
  SESSION_DOMAIN=.example.gov.tw
  SANCTUM_STATEFUL_DOMAINS=$FRONT
EOF

echo -e "\n  ★★ app/Http/Middleware/TrustProxies.php"
cat <<'EOF'
  protected $proxies = ['127.0.0.1'];      // ★ 或 '*' 但要確定只有反代能連到 PHP-FPM
  protected $headers = Request::HEADER_X_FORWARDED_FOR
                     | Request::HEADER_X_FORWARDED_HOST
                     | Request::HEADER_X_FORWARDED_PORT
                     | Request::HEADER_X_FORWARDED_PROTO;
EOF

echo -e "\n  ★ app/Providers/AppServiceProvider.php"
cat <<'EOF'
  public function boot(): void {
      if ($this->app->environment('production')) {
          URL::forceScheme('https');       // ★ 強制產生 https 連結
      }
  }
EOF

# ══ ⑤ Nuxt 設定 ══
echo -e "\n【⑤】Nuxt"
cat <<EOF
  # .env
  NUXT_PUBLIC_API_BASE=https://$API
  NODE_EXTRA_CA_CERTS=/usr/local/share/ca-certificates/internal-ca.crt   # ★★ SSR 呼叫內部 API 需要

  # ecosystem.config.cjs
  module.exports = {
    apps: [{
      name: 'app',
      script: '.output/server/index.mjs',
      exec_mode: 'cluster', instances: 2,
      env: {
        NODE_ENV: 'production',
        PORT: 3000,
        HOST: '127.0.0.1',                # ★★ 只聽本機，由 Nginx 代理
        NODE_EXTRA_CA_CERTS: '/usr/local/share/ca-certificates/internal-ca.crt',
      },
    }],
  };
EOF

# ══ ⑥ 驗證 ══
echo -e "\n【⑥】★★ 驗證"
for h in "$FRONT" "$API"; do
    printf '  %-30s ' "$h"
    if curl -sf -o /dev/null --cacert /etc/ssl/certs/ca-chain.crt "https://$h/"; then
        echo -n "✓ HTTPS  "
        D=$(echo | openssl s_client -connect "$h:443" -servername "$h" 2>/dev/null | \
            openssl x509 -noout -enddate | cut -d= -f2)
        echo "到期：$D"
    else
        echo "✗"
    fi
done

printf '  %-30s ' "MySQL TLS"
mysql -h "$DB" -u app -p"${DB_PASS:-}" \
  --ssl-ca=/etc/ssl/certs/ca-chain.crt --ssl-mode=VERIFY_IDENTITY \
  -e "SELECT 1;" >/dev/null 2>&1 && echo "✓" || echo "✗ / 未設定 DB_PASS"

printf '  %-30s ' "HTTP → HTTPS 轉址"
curl -sI "http://$FRONT/" | grep -q '301' && echo "✓" || echo "✗"

printf '  %-30s ' "HSTS 標頭"
curl -sI --cacert /etc/ssl/certs/ca-chain.crt "https://$FRONT/" | \
  grep -qi 'strict-transport-security' && echo "✓" || echo "✗"

echo -e "\n═══ 完成 ═══"
echo "  ★ 別忘了把根憑證派送到所有客戶端（見 [[09-根憑證派送與信任]]）"
echo "  ★ 設定憑證到期監控（見 [[12-憑證生命週期管理]]）"
```

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| **Nginx：`SSL_CTX_use_PrivateKey failed`** ★ | 憑證與私鑰不配對 | 比對 pubkey 的 md5 |
| **Nginx：`no "ssl_certificate" is defined`** | `listen 443 ssl` 但沒設憑證 | 補上 `ssl_certificate` |
| **`unable to get local issuer certificate`** ★★ | 沒送中繼憑證 | `ssl_certificate` 用 **fullchain** |
| **Apache：`AH02561: Failed to configure certificate`** ★ | 2.4.8 以前給了 fullchain | 拆成 `SSLCertificateFile` + `ChainFile` |
| **IP 直連拿到錯的憑證** ★★ | 沒設 `default_server` | 加一個 `default_server` + `return 444` |
| **PostgreSQL 拒絕啟動：`has group or world access`** ★★ | 私鑰權限 | `postgres:postgres 600` 或 `root:postgres 640` |
| **MySQL 換憑證沒生效** ★ | MySQL 需要 restart | `ALTER INSTANCE RELOAD TLS` 或 restart |
| MySQL 仍被中間人 ★★ | `--ssl-mode=PREFERRED` 不驗證 | 用 `VERIFY_IDENTITY` |
| PostgreSQL 仍被中間人 ★★ | `sslmode=prefer` 不驗證 | 用 `sslmode=verify-full` |
| **Node 讀不到私鑰** ★ | 非 root 執行 | 用 systemd `LoadCredential` 或放 Nginx 後面 |
| **Laravel 產生 `http://` 連結** ★★ | 沒設 `HTTPS on` / TrustProxies | `fastcgi_param HTTPS on;` + `URL::forceScheme` |
| Laravel session 一直失效 | `SESSION_SECURE_COOKIE` 但走 HTTP | 確認全站 HTTPS |
| **容器內憑證讀不到** ★ | UID 不同 / 沒掛載 | `:ro` 掛載，檢查容器內 UID |
| **映像裡含私鑰** ★★★ | `COPY` 進去了 | 改用 volume 或 secrets；重建映像 |
| `ssl_stapling ignored` 警告 | 內部 CA 沒有 OCSP | 關掉 `ssl_stapling` |
| HTTP/3 連不上 | UDP 443 沒開 | `ufw allow 443/udp` |

## 安全性注意事項

> [!danger] 私鑰的三條紅線 ★★★
> ```
> ① 【絕不】放在 web root 下
>      /var/www/html/ssl/server.key → 可能被直接下載
>
> ② 【絕不】commit 到 git
>      .gitignore：
>        *.key
>        *.pem
>        *.p12
>        *.pfx
>      ★ 若已經 commit 了 → 【那把私鑰視為已外洩】
>        → 撤銷憑證、產新私鑰、重簽
>        （★ 只 git rm 是不夠的，歷史裡還在）
>
> ③ 【絕不】COPY 進 Docker 映像
>      → 推到 registry 後任何人 pull 都拿得到
>      → docker history 也看得到
> ```

> [!warning] 憑證更換的順序 ★★
> ```
> ★ 正確順序：
>   ① 【先】把新憑證與私鑰放到位（用新檔名，不覆蓋舊的）
>   ② 修改設定檔指向新檔案
>   ③ ★★ 語法檢查（nginx -t）
>   ④ reload
>   ⑤ 驗證（openssl s_client 確認是新憑證）
>   ⑥ ★ 確認無誤後才移除舊檔
>
> ❌ 錯誤順序：直接覆蓋舊檔 → 出錯時無法快速回退
>
> ★ 更好：用符號連結
>     /etc/ssl/certs/app-current.crt -> app-20260828.crt
>     → 換憑證只要 ln -sfn 再 reload
>     → 回退也只要改連結
> ```

```bash
# ★★ 符號連結式的憑證管理
$ D=$(date +%Y%m%d)
$ sudo install -m 644 new-fullchain.crt "/etc/ssl/certs/app-$D.crt"
$ sudo install -m 600 new.key           "/etc/ssl/private/app-$D.key"

# ★ 原子式切換
$ sudo ln -sfn "app-$D.crt" /etc/ssl/certs/app-current.crt.tmp
$ sudo mv -Tf /etc/ssl/certs/app-current.crt.tmp /etc/ssl/certs/app-current.crt
$ sudo ln -sfn "app-$D.key" /etc/ssl/private/app-current.key.tmp
$ sudo mv -Tf /etc/ssl/private/app-current.key.tmp /etc/ssl/private/app-current.key

$ sudo nginx -t && sudo systemctl reload nginx

# ★ 驗證後才清舊的
$ echo | openssl s_client -connect app.example.gov.tw:443 -servername app.example.gov.tw 2>/dev/null | \
    openssl x509 -noout -dates
```

>   notify: reload nginx

>   notify: do reload nginx
> - name: do reload nginx

> [!question]- 測驗答案
> **Q1.** **私鑰：`600 root:root`**（只有 root 可讀寫）。
> **目錄 `/etc/ssl/private/`：`700 root:root`**。
> **為什麼私鑰不需要給 `www-data`**：
> Nginx / Apache 的 **master process 以 root 啟動並讀取私鑰**，
> 之後才把 worker 降權給 `www-data` —— 所以 worker 根本不需要讀私鑰。
> **為什麼目錄也要鎖**：
> 只鎖檔案不鎖目錄的話，**任何使用者仍然可以列出目錄內容**，
> 知道有哪些主機的私鑰存在（資訊洩漏），
> 也能觀察到憑證更換的時間點。
>
> **Q2.** ①**絕不放在 web root 下** ——
> `/var/www/html/ssl/server.key` 可能被直接用瀏覽器下載，等同 PKI 淪陷。
> ②**絕不 commit 到 git** ——
> `.gitignore` 要排除 `*.key` `*.pem` `*.p12` `*.pfx`；
> **若已經 commit 了，那把私鑰就視為已外洩**（只 `git rm` 不夠，歷史裡還在），
> 必須撤銷憑證、產生新私鑰、重新簽發。
> ③**絕不 `COPY` 進 Docker 映像** ——
> 映像推到 registry 後，任何能 pull 的人都拿得到；
> `docker history` 也看得到。一律用 volume 掛載或 secrets。
>
> **Q3.**
> **`ssl_certificate`** —— **伺服器憑證 + 中繼憑證**（也就是 `fullchain.pem`），
> 這是**握手時實際送給客戶端的內容**。
> **不含根憑證**（客戶端本來就有）。
> **`ssl_trusted_certificate`** —— **中繼 + 根**（也就是 `ca-chain.pem`），
> 用於 ①**OCSP stapling 的驗證**；②**mTLS 時驗證客戶端憑證**（配合 `ssl_client_certificate`）。
> **這個檔案不會送給客戶端**。
> **最常見的錯誤**：把 `ca-chain.pem` 給了 `ssl_certificate` ——
> 那裡面根本沒有伺服器憑證。
>
> **Q4.** **Apache 2.4.8 以前**：
> `SSLCertificateFile` **只能放伺服器憑證**（單張），
> 中繼憑證要另外用 **`SSLCertificateChainFile`**。
> **給了 fullchain 會報 `AH02561: Failed to configure certificate`**。
> **Apache 2.4.8 以後**：
> `SSLCertificateFile` **可以直接放 fullchain**（與 Nginx 一致），
> `SSLCertificateChainFile` 已經 deprecated。
> 這是從別的 Apache 版本或從 Nginx 搬設定時常踩的坑。
>
> **Q5.** 因為**沒有 `default_server` 時，Nginx 會用「第一個 `listen 443` 的 server 區塊」當預設**
> —— 當客戶端**用 IP 直連**、**送未知的 Host**、
> 或是**不支援 SNI 的舊客戶端**連進來時，
> **會拿到那個站台的憑證**。
> 後果：①憑證名稱不符的警告；
> ②**洩漏了那個站台的存在**（掃描者用 IP 直連就知道你上面跑什麼）。
> **正確做法**：明確設一個 `default_server`，
> 用一張無意義的憑證並 `return 444`（直接斷線不回應）。
>
> **Q6.**
> **MySQL：只有 `VERIFY_IDENTITY`**。
> `PREFERRED`（**預設值**）與 `REQUIRED` 都**只加密不驗證憑證** ——
> 攻擊者出示任何自簽憑證都會被接受，可以完整攔截與竄改。
> `VERIFY_CA` 驗證 CA 但**不驗證主機名**。
> **PostgreSQL：只有 `verify-full`**。
> `prefer`（**預設值**）與 `require` 同樣**不驗證憑證**，
> `verify-ca` 不驗證主機名。
> **兩者的預設值都是不安全的**，
> 所以連線字串必須明確寫出驗證模式與 `sslrootcert` / `--ssl-ca`。
>
> **Q7.** PostgreSQL **在啟動時會主動檢查私鑰的權限，不符就直接拒絕啟動**：
> ```
> FATAL: private key file "server.key" has group or world access
> ```
> **兩種合法的組合**：
> ①**`postgres:postgres` 且權限 `600`**（或更嚴）；
> ②**`root:postgres` 且權限 `640`**（或更嚴）。
> 也就是說「屬於資料庫使用者時只能自己讀寫」，
> 「屬於 root 時可以讓 postgres 群組唯讀」。
> 這是 PostgreSQL 特有的嚴格檢查，MySQL 與 Nginx 都不會這樣做。
>
> **Q8.**
> **可以 reload（零停機）**：
> **Nginx**（`systemctl reload nginx`，**先 `nginx -t`**）、
> **Apache**（`reload apache2`，先 `configtest`）、
> **PostgreSQL**（`reload postgresql`，憑證檔可 reload；
> 但 `ssl = on/off` 的切換要 restart）、
> **HAProxy**。
> **要 restart（會斷線）**：
> **MySQL**（★ 但 **8.0.16+ 可以用 `ALTER INSTANCE RELOAD TLS;` 免重啟**，
> 只影響新連線）、**Redis**、Node.js 自帶 TLS 的服務。
> **Docker 容器**：掛載的憑證檔換了要 `docker compose restart <svc>`。
>
> **Q9.** 因為 **`ssl_stapling on` 需要憑證裡有 `authorityInfoAccess` 的 OCSP URI，
> 而且那個 OCSP responder 必須真的在運行**。
> **內部 CA 通常沒有架設 OCSP responder** ——
> Nginx 每次啟動與定期更新時都會嘗試連線，然後逾時，
> error log 會被 `ssl_stapling ignored, host not found in OCSP responder` 塞滿，
> 並且**拖慢啟動速度**。
> 雖然不影響實際功能（stapling 失敗會靜默降級），
> 但沒有意義。
> **內部 CA 應該用 CRL 做撤銷檢查**
> （憑證裡設 `crlDistributionPoints`，
> mTLS 時用 `ssl_crl` 讓 Nginx 驗證客戶端憑證的撤銷狀態）。
>
> **Q10.** ①**Nginx 傳遞 `fastcgi_param HTTPS on;`** ——
> 讓 PHP 的 `$_SERVER['HTTPS']` 有值，Laravel 才知道原始請求是 HTTPS；
> ②**`TrustProxies` middleware** ——
> `protected $proxies = ['127.0.0.1'];` 並啟用
> `HEADER_X_FORWARDED_PROTO`（配合 Nginx 的 `proxy_set_header X-Forwarded-Proto $scheme;`）；
> ③**`URL::forceScheme('https')`**（在 `AppServiceProvider::boot()` 中，
> 通常包在 `if ($this->app->environment('production'))` 內）。
> **少了任何一個**，Laravel 產生的 `route()` / `asset()` / `url()` 連結
> 都會是 `http://`，導致**混合內容警告、無限轉址迴圈、
> 或 `SESSION_SECURE_COOKIE=true` 時 session 一直失效**。
> 另外 `.env` 也要設 `APP_URL=https://...` 與 `SESSION_SECURE_COOKIE=true`。
