# 提示工程與 AI 工作流 常見故障排除

> [!abstract] 怎麼用這份手冊
> - 依「**你剛剛看到什麼**」查，不是依「這屬於什麼理論」查
> - 找到症狀 → 看判斷分流 → 照編號步驟做 → 想懂原理再點進原文
> - ★★★★★ 本手冊**不重講原理**。每個情境結尾的「原理詳見」就是入口，
>   照著點進去看，不要在這裡找教學
> - ★★★★★ 特別是「爛回答該改哪一格」這件事，
>   [[110-06-04-guide-提示工程-迭代除錯提示與使用反模式]] 已經有一張完整的
>   **四種失敗病因診斷表**，本手冊不重寫它，只負責把你分流到對的那一格
> - ★★★★★ 動手之前先問自己一句：**現在是「AI 給的答案不好」，
>   還是「我已經照著一個沒驗證過的答案動了正式機」？**
>   兩者的第一動作完全相反 —— 前者慢慢調提示，後者立刻停手回復

## 一頁式急救卡

★★★★★ 產出不對的時候，**先問這三題再改提示**。三題裡有任何一題答不出來，
你要修的就不是提示。

```text
① 我給了脈絡與限制嗎？
   ── 我有沒有告訴它：OS 與版本、實際的錯誤訊息原文、這台機器上還有什麼、
      哪些動作絕對不可以做（重啟／刪除／改防火牆）？
   ── 沒有 → 不要調字句，先補這三行。八成的爛回答死在這裡。

② 這個回答我驗證過嗎？
   ── 裡面的每一個旗標、每一個設定指令、每一個檔案路徑，
      我有沒有用 man / --help / nginx -t / ls -l 親自確認它存在？
   ── 沒有 → 在驗證完成之前，這份回答只是「一份待審查的建議」，
      不是「可執行的答案」。★★★★★ 絕對不要貼進正式機。

③ 這件事真的該給 AI 做嗎？
   ── 這件事有沒有唯一正確答案（man 查得到）？
   ── 需不需要即時的系統狀態（只有機器自己知道）？
   ── 是不是精確計數／全量比對（grep -c、diff 就能做完）？
   ── 是不是不可逆操作（刪除、格式化、撤銷憑證）？
   ── 任一項是 → 不要用 AI。用工具或用人。
```

**三十秒分流**：先決定你現在屬於哪一類，再往下走。

```text
輸出格式對不上、腳本吃不下              → 情境一
一開始很準，聊到後面開始重複、忘記限制  → 情境二
旗標／路徑／選項看起來很像真的但不存在  → 情境三
雲端做得到，換地端 7B 就崩              → 情境四
帳單暴增、token 用量遠超預期            → 情境五
回答泛泛、答非所問、像在念教科書        → 情境六（分流到 06-04 的四格診斷）
機敏資料已經貼出去了                    → 情境七 ★★★★★ 這是資安事件，不是提示問題
半夜的自動化流程壞了、報表沒產出        → 情境八
```

> [!danger] ★★★★★ 兩件事發生之後，先停手，不要再調提示
> **一、你把 AI 給的指令直接貼進正式機了。**
> 停止繼續下指令，先確認影響範圍（`systemctl status`、`curl -o /dev/null -w "%{http_code}"`、
> 使用者有沒有在報修），能回復就先回復，然後補變更紀錄。
> AI 產出的指令在維運上等同**外部來源的未驗證腳本**，
> 出事的責任歸屬不會因為「是 AI 給的」而改變 →
> [[100-02-08-guide-維運-變更管理流程]]。
>
> **二、你把機敏資料貼進雲端模型了。**
> 這不是提示工程問題，是**資料外洩事件**。
> 私鑰、密碼、Token、個資、標案底價、內網拓撲，任一項送出就跳到**情境七**，
> 依 [[090-07-04-guide-資安實踐-資安事件應變流程]] 處理。
> ★★★★★ **「刪掉對話」不等於沒發生過** —— 資料已經離開你的網段了。

## 依情境展開

### ★★★★★ 情境一：輸出格式不穩 —— 同一個提示，每次給的形狀都不一樣

**現象**：這一類的共同點是「內容其實是對的，但**下游吃不下去**」。

```text
（第一次）
{"records":[{"ip":"203.0.113.7","action":"Ban","count":12}]}

（第二次，被 markdown 圍欄包住 —— 下面用「三個反引號」四個字代表那三個字元）
三個反引號json
{"records":[{"ip":"203.0.113.7","action":"Ban","count":12}]}
三個反引號

（第三次，多了前言）
好的，以下是根據您提供的日誌整理出的結果：
{"records":[ ... ]}

（第四次，欄位名漂了）
{"資料":[{"IP位址":"203.0.113.7","動作":"封鎖","次數":12}]}

（第五次，斷在一半）
{"records":[{"ip":"203.0.113.7","action":"Ban","cou
```

★★★★★ 這五種**根本不是同一個病**，修法完全不同。分錯就會白改半天提示。

**判斷分流**：先跑一次驗證，用**錯誤訊息**分類，不要用肉眼看。

```bash
$ jq -e . out.json > /dev/null; echo "exit=$?"
```

```text
jq 說 Invalid numeric literal / Invalid literal    → 前面有雜訊（前言或圍欄）  →【1】
jq 說 Unexpected end of input                       → ★★★★★ 被截斷，不是格式問題 →【2】
jq 過了，但欄位名不是你要的英文名                   → schema 沒寫死             →【3】
jq 過了，欄位對，但值變成中文（Ban → 封鎖）         → 值域沒鎖                 →【4】
有時是 JSON、有時整篇散文                           → 硬性限制沒寫              →【5】
最外層變成 {"result":[...]} 而不是你要的欄位名      → 沒有主動定義最外層物件    →【6】
JSON 是合法的，但筆數 0 而來源明明有資料            → ★★★★ 當作失敗處理       →【7】
```

**處置步驟**：

【1】★★★★★ 前面有雜訊 —— 這是**最便宜的一類，不要先去改提示**。
剝殼在你這邊做，一行就解決；提示端的修正當作長期改善。

```bash
# 取第一個 { 到最後一個 } —— 對「前言 + JSON」與「圍欄 + JSON」都有效
$ sed -n '/^{/,$p' out.raw | sed -e '/^```/d' > out.json
$ jq -e . out.json > /dev/null && echo 'OK'
```

比 `sed` 更穩的做法是用 Python 找配對的大括號（多層巢狀也不會出錯）：

```python
# extract_json.py：從一團文字裡撈出第一個完整的 JSON 物件
import sys, json
s = sys.stdin.read()
start = s.find('{')
if start < 0:
    sys.exit('找不到 JSON 物件起點')
depth = 0
for i in range(start, len(s)):
    if s[i] == '{':
        depth += 1
    elif s[i] == '}':
        depth -= 1
        if depth == 0:
            print(json.dumps(json.loads(s[start:i + 1]), ensure_ascii=False))
            sys.exit(0)
sys.exit('JSON 物件沒有結束，可能被截斷')
```

★★★★ 剝殼之後**還要修提示**，否則哪天它前言裡混進一個 `{` 就會踩雷：

```text
只輸出 JSON。不要 markdown 程式碼區塊，不要開場白，不要結語，不要註解，不要尾逗號。
```

【2】★★★★★ `Unexpected end of input` **不是格式問題，是長度問題**，
改提示一點用都沒有。三個方向依序查：

```bash
# ① 你的輸入有多大（粗估 token：位元組數除以 4）
$ echo $(( $(wc -c < input.txt) / 4 ))
7400

# ② 地端：模型的情境窗與輸出上限現在是多少
$ ollama show <模型名稱> --parameters

# ③ 雲端：回應裡的 usage 欄位（OpenAI 相容端點）
$ jq '.usage' resp.json
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 輸入很大、輸出斷在一半 | 輸出上限不夠（`num_predict` / `max_tokens`） | 拉大輸出上限；**或把每批輸入從 40 行改成 20 行** |
| ★★★★★ 地端貼長文後回答完全不相關 | 超出 `num_ctx` 的部分被**靜默截斷**，它只看到殘片 | 調大 `num_ctx` → [[110-02-02-guide-Ollama-模型管理與Modelfile]] |
| ★★★★ 調大 `num_ctx` 之後變超慢 | 情境變大把模型擠出 GPU | `ollama ps` 看 PROCESSOR 欄，跳**情境四**【2】 |
| ★★★ 分批處理時只有後面幾批斷 | 同一對話累積，情境越來越滿 | ★★★★ **每一批開新對話**，用完全相同的提示 |

★★★★ 分批是這一類最可靠的解法，不是調參數。切得夠小，`num_ctx` 的問題自然消失：

```bash
$ split -l 20 -d --additional-suffix=.txt input.txt chunk-
$ ls chunk-*.txt | wc -l
9
```

【3】★★★★ 欄位名漂移（`ip` 變成 `IP位址`）—— 這是**中文提示的固有副作用**，
地端小模型特別嚴重。修法有三層，由上而下做：

```text
① schema 裡的欄位名一律用英文小寫，並且明講「欄位名必須完全照抄，不得翻譯」
② 附一行「範例輸出」，範例的欄位名也用英文 —— 給範例比寫十行描述有效
③ 驗證端做必填欄位檢查，缺欄位就回饋重試（不要靜默接受）
```

```bash
# 必填欄位檢查：缺一個就非零退出
$ jq -e 'all(.records[]; has("ip") and has("action") and has("count"))' out.json > /dev/null \
    && echo '欄位齊全' || echo '★ 欄位缺漏，要回饋重試'
```

【4】★★★★ 值域被翻譯（`Ban` 變成 `封鎖`）—— 提示裡列了合法值，
但模型把「合法值」也當成需要在地化的內容。

```text
action 只能是 Ban 或 Unban 這兩個字串之一。
這兩個值必須使用英文原文，不得翻譯，不得改大小寫。
```

驗證端用正規表示式抓，不要只檢查欄位存在：

```bash
$ jq -e 'all(.records[]; .action == "Ban" or .action == "Unban")' out.json > /dev/null \
    && echo '值域正確'
```

★★★★ 同一類的還有「模型自作主張遮蔽 IP」，把 `203.0.113.7` 輸出成 `203.0.113.xxx`。
提示要明寫「**原文照抄，不得遮蔽、不得修改、不得補零**」，
並在驗證端用 IP 格式的正規表示式檢查。

【5】★★★★★ 有時 JSON 有時散文 —— 幾乎一定是**提示把限制寫成了建議語氣**。

```text
✗ 「請盡量以 JSON 格式回覆」          → 這是建議，模型可以不聽
✗ 「希望輸出是 JSON」                  → 同上
✓ 「只輸出 JSON。輸出的第一個字元必須是 {，最後一個字元必須是 }。
    不要有任何說明文字、開場白、結語、markdown 圍欄。」
```

★★★★ 再加一招：**貼一行壓縮過的範例輸出**。
模型模仿範例的傾向遠強於遵守描述，這是提示工程裡投報率最高的技巧之一。

【6】★★★ 最外層變成 `{"result":[...]}` —— 這是 JSON 模式的**已知行為**：
它只保證「輸出是一個 JSON 物件」，不保證是陣列，所以模型會自己包一層。

正解不是禁止它包，而是**你主動定義那一層要叫什麼**：

```text
最外層固定是一個物件，只有一個欄位 records，值是陣列。
沒有資料時 records 是空陣列 []，不要省略這個欄位，不要改名。
```

【7】★★★★ JSON 合法、格式全對、但**筆數是 0，而來源明明有 187 行** ——
這是最陰險的一種，因為所有驗證都會通過。

```bash
# ★★★★★ jq 的 all(...) 對空陣列回 true，光靠它會漏掉這一類
$ jq -e '(.records | length) > 0' out.json > /dev/null || echo '★ 空結果，當失敗處理'
# 與來源交叉比對
$ echo "來源 $(wc -l < raw.log) 行 / 產出 $(jq '.records | length' out.json) 筆"
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 圍欄／前言導致 `jq` 解析失敗 | 沒有明確禁止圍欄與說明文字 | 剝殼（便宜）＋提示補硬性限制（治本） |
| ★★★★★ `Unexpected end of input` | 輸出被截斷（輸出上限／`num_ctx`） | 縮小每批輸入；拉大輸出上限；分批各開新對話 |
| ★★★★ 欄位名被中文化 | 中文提示誘發中文欄位名 | schema 與範例輸出一律英文小寫；驗證端檢查必填 |
| ★★★★ 值域被翻譯 | 合法值被當成待翻譯內容 | 值域後補「必須用英文原文，不得翻譯」 |
| ★★★★ 有時 JSON 有時散文 | 限制寫成了建議語氣 | 改寫成硬性限制＋貼一行範例輸出 |
| ★★★ 出現 `// 註解` 或尾逗號 | 模型套用 JavaScript／JSONC 習慣 | 明寫「不要註解、不要尾逗號」；`jq empty` 會抓到 |
| ★★★ 必填欄位出現 `null` | 只說「必填」沒說缺漏怎麼辦 | 明寫「缺漏填空字串 `""`，不要 null、不要省欄位」 |
| ★★★ 最外層自己多包一層 | JSON 模式只保證物件 | 主動定義最外層物件與欄位名 |
| ★★★★ 驗證全過但筆數 0 | `all(...)` 對空陣列回 true | 另加 `length > 0` 並與來源行數交叉比對 |
| ★★★ 地端模型不照格式走 | 小模型對長指令的遵循度低 | 把「輸出格式」搬到提示**最後**；或拆成兩輪問 |

> [!warning] ★★★★ 不要用「重新問一次」來解決格式問題
> 格式不穩是**機率問題**：重問只是再擲一次骰子，你會花掉 token、
> 也不會知道到底哪個修正有效。
> 正解是「提示端寫死硬性限制 → 腳本端做驗證 → 不合格時**把錯誤訊息回饋回去**重試」，
> 而且重試要設上限。三段做法詳見原文。

**原理**：模型不是在「執行你的格式規定」，是在「產生最像你要的東西的文字」。
所以硬性限制、範例輸出、驗證與回饋重試三者缺一不可，
其中**驗證是唯一不靠機率的一環**。
　→ 原理詳見 [[110-06-03-guide-提示工程-結構化輸出與自動化串接]]

**預防**：
- ★★★★★ 只要輸出會進到腳本，就一定要有 `jq -e` 這一關，**不准用肉眼驗收**
- ★★★★★ 重試一定要有上限（2～4 次），超過就轉人工，不要寫成無限迴圈
- ★★★★ schema 欄位名一律英文小寫，並附一行壓縮的範例輸出
- ★★★ 產物先寫 `.tmp` 再 `mv` 原子替換，中斷時不會留下半份報表
- ★★★ 敘述型內容（事故報告內文、對外公告）不要硬塞 JSON —— 事實欄位結構化就好

### ★★★★★ 情境二：越聊越笨 —— 一開始很準，聊到後面開始重複、忘記限制

**現象**：三種長相，你**不需要任何工具**，光看它的回答就能判斷。

```text
（A）★★★★ 半小時前你已經排除的方案，它又原封不動提了一次
（B）★★★★★ 你在第 2 輪明講「營業時間不能重啟」，第 18 輪它叫你 systemctl restart
（C）★★★ 回答只剩「建議檢視效能瓶頸」「建立完善的監控機制」，
     一個指令、一個路徑、一個數字都沒有
```

> [!danger] ★★★★★ （B）的後果不是回答變爛，是你真的照做
> 排錯排到第 18 輪，人是累的、是趕的。它給一行 `systemctl restart php8.3-fpm`，
> 你手比腦快就貼上去了 —— 然後在營業時間中斷了服務，而且沒有變更單。
>
> **看到 AI 建議一個你明明禁止過的動作：先停手，不要爭辯、不要糾正、不要繼續這個對話。**
> 糾正只會再多一行文字，不會讓它真的「想起來」—— 因為它從來就沒有「想」這回事。

**判斷分流**：★★★★★ 先分清楚是**污染**、**稀釋**、**截斷**，還是**主題根本換了**，
四者的處置完全不同。

```text
重複已排除方案 / 違反已宣告限制 / 同一輪內自相矛盾  → 污染   →【1】【2】
回答變短變泛、開始複述你講過的話                     → 稀釋   →【3】
你貼了東西，它卻說「請提供您的設定檔」               → 截斷   →【4】★★★★ 地端優先查這個
你已經換了另一個題目還在同一個對話裡                 → 換題   →【5】直接重開，不必交棒
中途貼過錯的資料（貼到別台機器的日誌／舊版設定檔）   → ★★★★★ 立刻重開，不要試圖更正
```

**處置步驟**：

【1】★★★★★ 先判斷「該不該停手」。這一步比修對話重要得多。

```text
它建議的動作，屬於下列任一種嗎？
  □ 重啟／停止正式環境的服務
  □ 刪除檔案、清空表格、格式化
  □ 改動防火牆規則或 SSH 設定（有把自己鎖在門外的風險）
  □ 撤銷或重簽憑證
→ 有任一項打勾，而且你「先前明講過不可以」
  → ★★★★★ 停手。不執行、不繼續問、直接走【2】重開。
```

【2】★★★★ 重開之前**先交棒**。直接關掉重開會讓新對話比舊對話更笨 ——
它會叫你重試一遍你早就試過的東西。

```text
請把目前為止的排查整理成一段可以貼到新對話的交接說明，包含：
1. 問題現象（一句話）
2. 環境事實（OS 版本、服務版本、拓撲）
3. 已經確認的事實（附證據來源，例如哪個指令的哪一行輸出）
4. 已經排除的方向，以及各自的排除證據
5. 目前最有可能的假設
6. 下一步該驗證什麼
7. 限制與紅線 —— ★★★★★ 這一段請原文照抄，不要改寫、不要省略、不要摘要

只輸出這段交接說明本身，不要有其他文字。
```

★★★★★ 第 7 點是關鍵。不加這句，它會把「營業時間不得重啟 nginx 與 php-fpm」
壓縮成「注意服務可用性」—— 限制就在交棒的過程中被稀釋掉了。

【3】★★★★ 開新對話貼進去，並且**把限制放到最前面**：

```text
以下是前一個對話的交接說明，請先讀完再回答。

【限制與紅線】（在整個對話中一律有效，你的任何建議都不得違反）
- 這是正式環境，營業時間內不得重啟 nginx 與 php-fpm
- 這一輪只給唯讀的檢查指令，任何會改變狀態的動作都要先開變更單
- 不確定就說不知道，不要猜

【已排除】裡的方向不要再提出，除非你能指出原本的排除證據哪裡有問題。

<交接說明>
（貼上）
</交接說明>
```

【4】★★★ 只是「變泛」而還沒污染時，可以先試一次聚焦重述，不必馬上重開：

```text
把範圍縮回到單一問題：<一句話問題>。
每個建議都必須附上可執行的指令，以及「看到什麼代表什麼」。
不要給通則、不要給「建議持續監控」這類沒有動作的內容。
每次最多給我三個步驟，我做完回報結果你再給下一批。
```

★★★★ 試一次就好。**再泛一次就重開**，不要把時間花在挽救一個已經壞掉的對話。

【5】★★★★ 「它說請提供您的設定檔」但你明明貼了 —— 這是**截斷**，不是失憶。
地端模型尤其要先查這個，因為超出的部分是**無聲丟掉**的，不會有任何警告。

```bash
$ ollama show <模型名稱> --parameters      # 看 num_ctx 目前是多少
$ ollama ps                                # 確認模型還在 GPU，沒因為情境變大被擠到 CPU
$ echo $(( $(wc -c < paste.txt) / 4 ))     # 你貼的東西大概幾個 token
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 已排除的方案被重新提出第二次 | 污染：舊推論篇幅遠大於你的一行否決 | 交棒 → 重開，新對話用 `【已排除】` 附排除證據 |
| ★★★★★ 建議你做明講過禁止的動作 | 限制是一次性宣告，被後續內容淹沒 | **停手** → 交棒 → 重開，限制放最前面且要求原文照抄 |
| ★★★★ 同一輪內前後說法不一致 | 污染 | 重開，不要試圖辯論 |
| ★★★ 回答變短變泛、只剩原則 | 稀釋、失焦 | 先試聚焦重述一次；無效就重開 |
| ★★★ 大段複述你講過的話當回答 | 稀釋，輸入太長 | 縮短輸入，只留關鍵段 |
| ★★★★ 貼了東西卻說沒收到 | 情境滿被擠掉；地端 `num_ctx` 太小 | 重開重貼；地端調大 `num_ctx` |
| ★★★★★ 中途貼過錯的資料（別台機器的日誌） | 錯誤事實已經進入情境，**改不掉** | ★★★★★ 立刻重開，不要用「剛才那份請忽略」補救 |
| ★★★★ 新對話比舊對話更笨 | 沒有交棒就直接關掉 | 一律「先交棒，再重開」 |
| ★★★★ 交接說明裡的限制被改寫得很軟 | 交棒提示沒要求原文照抄 | 交棒提示明寫「限制原文照抄，不改寫不省略」 |
| ★★★ 分段處理時後面幾塊格式跑掉 | 前面幾塊的內容污染了後面 | **每一塊開新對話**，用完全相同的提示 |
| ★★★ 隔夜回來接著問 | 你自己已經忘了脈絡，它也不會提醒你 | 一律重開並重貼交接說明 |

★★★★ 什麼時候「不必等徵兆出現就該重開」——這幾個是免判斷的硬規則：

```text
□ 換題目了                → 直接重開，不必交棒
□ 中途貼過錯的資料         → 立刻重開
□ 對話超過 20～30 輪       → 準備交棒
□ 情境佔用超過 60%         → 準備交棒
□ 隔夜／隔天回來繼續       → 重開並重貼交接
```

**原理**：對話歷史每一輪都會被**完整重送**一次，所以長對話同時變貴也變笨 ——
這是同一個原因。你那句「已經排除了」只有一行，
而被排除的那段推論可能有三十行，權重比是 30:1。
　→ 原理詳見 [[110-06-02-guide-提示工程-情境工程與何時該重開對話]]

**預防**：
- ★★★★★ **一個任務一個對話**。排錯完了要寫報告，開新的
- ★★★★★ 限制寫在**最前面**，長對話中段**再重述一次**
- ★★★★ 資料先過濾聚合再貼，不要用原始日誌把情境填滿
- ★★★ 每次重開都要重放限制段 —— 它不是「上次講過了」，它是「這次沒講就等於沒有」
- ★★★ 已確認的結論存成檔案（交接說明），不要只留在聊天視窗裡

### ★★★★★ 情境三：幻覺參數 —— 旗標、選項、路徑看起來很像真的，但不存在

**現象**：四種長相，**共同點是「語氣很自信、格式很漂亮」**。

```text
（A）★★★★★ 不存在的旗標
     systemctl restart --graceful nginx
     → 執行後：unrecognized option '--graceful'

（B）★★★★★ 設定指令是別的軟體的，或根本不存在
     → nginx -t 直接說：unknown directive

（C）★★★★ 檔案路徑在你的系統上沒有
     說設定檔在 /etc/nginx/conf.d/default.conf，你的發行版放在 sites-enabled/

（D）★★★★ 引用了不存在的 man page 章節或文件節次
     「詳見 man 5 nginx.conf 第 3 節」 → man: No manual entry for nginx.conf in section 5
```

★★★★★ **這一類跟「脈絡不足」是兩回事，補脈絡沒有用。**
補脈絡治的是「它不知道你的環境」；幻覺治的是「它根本沒有那個知識，
但它沒有『不知道』這個檔位」——它永遠算得出下一個字，所以它永遠寫得出東西。

#### 辨識方法：怎麼在三十秒內判斷這個旗標是真是假 ★★★★★

由快到慢，**命中就停，不必全跑**：

```bash
# ① 最快：問指令自己（三秒）
$ nginx -h 2>&1 | grep -- '-T'
$ systemctl --help | grep -- '--graceful'      # 沒有輸出 = 高度可疑

# ② man 全文搜尋那個旗標（十秒）
$ man systemctl | grep -n -- '--graceful'
$ man 5 crontab | head -5                       # 確認這個「章節」真的存在

# ③ 反查關鍵字：如果它說某個工具叫某個名字，先確認這個工具存在
$ apropos <關鍵字>
$ man -k <關鍵字>
$ command -v <指令>

# ④ 設定檔類：讓軟體自己判卷（最可靠）
$ nginx -t
$ sshd -t
$ visudo -c -f /etc/sudoers.d/<檔名>
$ systemd-analyze verify /etc/systemd/system/<名稱>.service
$ fail2ban-client -t

# ⑤ 已經套用了才想確認：看「實際生效值」而不是檔案內容
$ nginx -T | grep -n '<關鍵字>'
$ sshd -T | grep -i '<關鍵字>'
$ systemctl show <unit> -p <屬性>
```

四個**不必動手就能起疑**的訊號 —— 看到就把警覺拉滿：

| 訊號 | 為什麼可疑 | 怎麼確認 |
| --- | --- | --- |
| ★★★★★ 旗標名稱「太好懂了」 | `--graceful`、`--safe-mode`、`--dry-run-only` 這種完全符合直覺的長旗標，常常是模型照著語意造出來的 | `<cmd> --help \| grep` |
| ★★★★★ 它把兩個同類軟體的語法混在一起 | Apache 的指令出現在 `nginx.conf`、`firewalld` 的概念用 `ufw` 的語法寫 | 該軟體的官方 directive index |
| ★★★★ 它給了一個「預設值」而且講得非常具體 | 「預設 10s」這種細節是最容易被編的部分 | 官方文件的 directive 說明 |
| ★★★★ 它引用了具體的文件節次或條號 | ★★★★★ 條號、章節號、RFC 編號是 LLM 最會編的東西之一 | 直接開那份文件查，不要相信轉述 |

★★★ 兩個**輔助**手法（有用，但不能單獨當結論）：

```text
① 交叉重問：在一個「全新的、乾淨的」對話裡重問同一件事。
   兩次答案不一致 → 高度可疑。
   ★★★★ 注意：兩次一致也不代表是真的 —— 同一個模型會穩定地編同一件事。

② 要求出處：「請說明這個選項出現在哪一份官方文件的哪一節；
   如果你不確定，直接說不知道，不要猜。」
   ★★★★★ 這句會降低編造率，但**出處本身也會被編**。
   拿到出處之後你還是得自己去開那份文件。
```

> [!tip] ★★★ 一個花三分鐘、印象會很深的實驗
> 找一個你確定**不存在**的設定指令去問它用途、預設值與合法取值範圍。
> 多數模型會認真地給你一整段說明，包含預設值與該放在哪個 context。
> **這就是幻覺的樣子：它不會抗議，它會配合。**
> 原文有一個現成的範例可以直接抄來試 →
> [[110-06-01-guide-提示工程-LLM心智模型與提示六大構件]]

#### 必做的驗證步驟（執行前，一步都不能省）★★★★★

```text
【1】逐條圈出「會改變狀態」的指令
     restart / stop / reload / rm / mv / truncate / chmod / chown /
     iptables / nft / ufw / firewall-cmd / mkfs / dd / DROP / DELETE / UPDATE
     → 圈完之後，這一輪先只跑沒被圈到的那些（唯讀的）

【2】每一個旗標、每一個設定指令，用上面的「辨識方法」核對存在性
     → 有任何一個查不到 → 整份回答的可信度歸零，重問或自己查文件
     ★★★★★ 不要只修那一行 —— 會編一個旗標的回答，通常不只編了一個

【3】每一個路徑用 ls -l 確認
     $ ls -l /etc/nginx/sites-enabled/ /etc/nginx/conf.d/ 2>&1
     → 路徑不存在就是脈絡沒給夠，把實際路徑貼回去重問

【4】有語法檢查工具的一律先跑
     nginx -t / sshd -t / visudo -c / systemd-analyze verify /
     fail2ban-client -t / bash -n / shellcheck / jq -e
     → 不通過就退回【2】

【5】有 dry-run 的一律先跑一次看清單
     rsync -n / apt -s / nft -c / logrotate -d
     → 看清楚它「打算動哪些檔案」再決定要不要真的跑

【6】會改變狀態的檔案先備份
     $ sudo cp <檔> <檔>.bak.$(date +%F)

【7】能在測試機或容器裡跑一次最好；不能的話至少想清楚回復手段是什麼
     → 想不出回復手段 → ★★★★★ 不要執行

【8】確認現在是可執行的時段，並且照變更管理流程開單
     → [[100-02-08-guide-維運-變更管理流程]]
```

> [!danger] ★★★★★ 絕對不要把 AI 產出的指令直接貼進正式機
> 語法檢查工具只檢查**語法**，不檢查**語意**。
> `nginx -t` 說 `syntax is ok` 的設定，一樣可能把整個站台導到錯的 upstream；
> `bash -n` 沒報錯的腳本，一樣可能 `rm -rf` 到錯的目錄。
>
> ★★★★★ **`-t` 過了只代表「可以載入」，不代表「行為正確」。**
> 變更後一定要有**行為驗證**：實際發一個請求、數一次日誌行數、
> 確認 socket 檔真的出現，例如：
>
> ```bash
> $ curl -s -o /dev/null -w "%{http_code}\n" https://<你的站台>/
> $ journalctl -u nginx --since "5 min ago" --no-pager | grep -c 'error'
> ```
>
> **看到預期的狀態碼之前，不要在值班紀錄上寫「已排除」。**

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ `unrecognized option` / `invalid option` | 旗標是編的 | 執行前 `<cmd> --help \| grep --` 核對；整份回答重新檢視 |
| ★★★★★ `nginx: [emerg] unknown directive` | 設定指令不存在，或是別的軟體的 | 查官方 directive index；`nginx -t` 必跑 |
| ★★★★★ 設定 `-t` 過了但行為不對 | 語法 ≠ 語意 | 一定要做行為驗證（狀態碼／日誌計數／實際檔案） |
| ★★★★ 路徑不存在 | 發行版路徑差異被幻覺填補 | 把 `ls -l` 的實際輸出貼給它，限制「只使用我提供的路徑」 |
| ★★★★ `man` 打不開它引用的章節 | 引用來源同樣會被編造 | `man -k` / `apropos` 反查；找不到就當作不存在 |
| ★★★★ 它引用了看起來很正式的法規條號 | ★★★★★ 條號與條文是最會被編的一類 | **一律不得直接引用**，回到主管機關公告查證 |
| ★★★★ 罕見錯誤訊息被配上一個很內行但對不上的成因 | 編造的錯誤訊息對應，會把排查方向整個帶歪 | 用錯誤訊息原文去官方 issue／文件搜尋，不要用轉述 |
| ★★★★ 它沿用了你範例裡的假 IP／假網域 | 範例值被照抄 | 範例用 `<SERVER_IP>` 這類佔位符，並補「範例數值僅示範格式，不要沿用」 |
| ★★★★ 它把你去識別化的佔位符還原成一個不存在的編號 | ★★★★★ 這是幻覺訊號 | 該段結論不採信，重問或人工查證 |
| ★★★ 補了脈絡幻覺還在 | ★★★★ 幻覺不是脈絡問題 | 改成「自己查文件貼給它」，並明確允許它說「不確定」 |
| ★★★ 地端小模型幻覺率明顯更高 | 參數量越小越會編，而且錯得更像真的 | ★★★★★ 小模型不要拿來問「這個指令的參數是什麼」 |

**原理**：模型的工作是「猜下一個字」，這件事**沒有「不知道」這個檔位**。
它不知道的時候產出的不是「我不知道」，而是一段語氣同樣自信、
格式同樣漂亮、但內容是編的文字。
　→ 原理詳見 [[110-06-01-guide-提示工程-LLM心智模型與提示六大構件]]
　→ 各類產出的強制驗證指令對照表 → [[110-06-05-ref-提示工程-維運提示樣板庫]]
　→ 產出物的品質控管制度 → [[110-05-10-guide-AI開發-AI產出的品質控管]]

**預防**：
- ★★★★★ 提示固定加一句「**不確定就說不知道，不要猜**」——降低編造率，但不能取代驗證
- ★★★★★ 把「查得到唯一答案」的問題留給 `man` 與官方文件，不要問 AI
- ★★★★ 讓 AI 做「答案就在你貼給它的內容裡」的任務（翻譯、摘要、格式轉換、比對），幻覺空間最小
- ★★★★ 需要具體參數時，**自己先把官方文件那一段貼給它**，再請它套用到你的情境
- ★★★ 把驗證步驟寫進提示的輸出格式：要求「每一項都附一行可直接執行的驗證指令」

### ★★★★ 情境四：地端模型接不住 —— 雲端做得到的，換成 7B 就崩

**現象**：同一份提示、同一份資料，雲端模型給出可用結果，地端模型給出殘缺、
重複、離題，或乾脆說「請提供資料」。

★★★★★ **這一節的重點是：先不要換模型。**
換模型要花錢、要重調參數、地端還要動硬體，而真正的原因常常是前兩項。

**判斷分流**：★★★★★ 三個原因**必須依序排除**，順序反了會白花錢。

```text
它說「請提供您的設定檔」／回答只涵蓋你貼的後半段  → ① 截斷      →【1】
它答得對但慢到不能用（每個字都要等）              → ② 沒進 GPU  →【2】
輸出無限重複同一段                                → ③ 取樣參數  →【3】
上面三項都排除了，內容還是明顯不如雲端            → ④ 任務類型  →【4】
四項都排除了                                      → ⑤ 真的該換  →【5】
```

**處置步驟**：

【1】★★★★★ 先排除**截斷**。這是地端最常見、也最容易被誤判成「模型太笨」的一項 ——
因為超出情境窗的部分是**靜默丟掉**的，不會有任何警告。

```bash
$ ollama show <模型名稱> --parameters       # 現在的 num_ctx 是多少
$ echo $(( $(wc -c < paste.txt) / 4 ))      # 你貼的東西大概幾個 token
```

★★★★ 判準很簡單：**貼進去的 token 數逼近或超過 `num_ctx`，就是截斷，不是笨。**

```text
估算 token 明顯小於 num_ctx  → 不是截斷，走【2】
估算 token 接近或超過        → 兩條路，優先走 (b)
   (a) 調大 num_ctx → [[110-02-02-guide-Ollama-模型管理與Modelfile]]
       ★★★★ 但調大之後一定要回頭跑【2】，情境變大很可能把模型擠出 GPU
   (b) ★★★★★ 把輸入變小 —— 這條永遠比調參數穩
```

把輸入變小的標準做法（維運人員本來就很擅長這件事）：

```bash
# 時間窗切片
$ journalctl -u nginx --since "2026-09-03 02:00" --until "2026-09-03 04:00" --no-pager > win.log
# 只留錯誤
$ grep -E '\[(error|crit|alert)\]' win.log > err.log
# ★★★★★ 聚合計次（削減幅度最大的一招，常常 90～99%）
$ sed -E 's/[0-9]+/N/g' err.log | sort | uniq -c | sort -rn | head -20
# 砍掉設定檔的註解與空行
$ grep -vE '^\s*(#|;|$)' /etc/nginx/nginx.conf
```

　→ 完整的削減指令速查表 → [[110-06-02-guide-提示工程-情境工程與何時該重開對話]]
　→ 過濾工具本身 → [[020-01-12-cmd-Linux-文字處理三劍客]]

【2】★★★★ 再排除**慢**。慢和笨是兩件事，但人在等的時候會把兩者混為一談。

```bash
$ ollama ps
```

★★★★ 看 `PROCESSOR` 欄。顯示 `100% GPU` 才是完全在 GPU 上跑；
出現 CPU 的比例就代表模型（或它的情境）沒有全部塞進顯示記憶體，
一部分退到 CPU 推論，速度會掉一個量級。

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ `PROCESSOR` 顯示有 CPU 比例 | 模型或情境放不進 VRAM | 換更小的量化版本、調小 `num_ctx`、減少同時載入的模型 |
| ★★★★ 調大 `num_ctx` 之後突然變超慢 | 情境變大，把原本裝得下的模型擠出 GPU | 回頭走【1】(b)：縮小輸入，而不是繼續加 `num_ctx` |
| ★★★ 同時開多個對話就全部變慢 | 多個模型或多個請求同時佔用 | 檢查同時載入的模型數與並行設定 |

　→ 硬體、量化與模型選型 → [[110-02-05-guide-模型服務-推論引擎與模型選型]]

【3】★★★ 排除**取樣參數**。地端最典型的失控長相是「同一段話無限重複」。

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★ 輸出同一筆記錄無限重複 | `temperature` 太高、`repeat_penalty` 太低 | 維運任務 `temperature` 設 0～0.3；縮短單批輸入 |
| ★★★ 同一提示跑兩次差很多 | 取樣隨機性 | 調低 `temperature`；做提示比較時固定 `seed` |
| ★★★ 輸出斷在一半 | `num_predict` 不夠 | 拉大輸出上限，或把每批做得更小 |

　→ 參數怎麼設 → [[110-02-02-guide-Ollama-模型管理與Modelfile]]、[[110-02-03-guide-Ollama-API使用]]

【4】★★★★★ 前三項都排除了，才輪到**任務類型**。
判斷方法只有一句話：

```text
★★★★★ 這個任務的答案，在不在我貼給它的文字裡？

在  → 翻譯、摘要、格式轉換、既有文字改寫、把日誌整理成表格、
      把錯誤訊息翻成人話、比對兩段我都貼上去的內容
      → 這類任務地端小模型的 CP 值最高，出問題多半還是【1】截斷

不在 → 「這個指令的參數是什麼」「這個版本的預設值是多少」
      「這個錯誤在這個版本上的成因」
      → ★★★★★ 這類是「知識型」任務，小模型的幻覺率最高，而且錯得很像真的
      → 不要用小模型問，直接查官方文件
```

★★★★ 所以「雲端做得到、地端做不到」的任務裡，有一大類根本不是模型不夠力，
是**你把知識型問題丟給了一個不該做知識型工作的模型**。
把它改寫成「答案在文字裡」的形態，地端往往就接得住了：

```text
✗ 「Nginx 的 proxy_read_timeout 預設值是多少？」        ← 知識型，小模型會編
✓ 「以下是我從 nginx -T 撈出來的設定片段（已附上）。
    請把裡面所有跟逾時有關的項目整理成一張表：
    指令名稱 / 目前設定值 / 出現在哪個 context。
    只根據我提供的內容回答，沒有出現的不要補。」    ← 答案在文字裡，小模型做得動
```

【5】★★★ 四項都排除了，才談換模型或拆任務。**先拆任務，拆不動才換模型。**

```text
拆任務的方向：
  □ 一次處理 40 行改成一次 20 行，每批開新對話
  □ 一次要它「分析 + 統計 + 排版」拆成三步，統計與排版用程式做（不要交給 AI）
  □ 一個提示要它同時遵守八條限制，拆成兩輪各四條

★★★★ 統計、排序、計數、比對這幾件事本來就不該給 AI，
不管是地端還是雲端 —— 它的計數是結構性弱點。
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 貼長文後回答完全不相關 | 超出 `num_ctx` 被靜默截斷，它看到的是殘片 | 縮小輸入（優先）／調大 `num_ctx`；`ollama ps` 確認仍在 GPU |
| ★★★★ 它說「請提供您的設定檔」但你貼了 | 同上 | 同上 |
| ★★★★ 答得對但慢到不能用 | 模型沒完全 offload 到 GPU | `ollama ps` 看 `PROCESSOR`；換量化版本或調小情境 |
| ★★★★ 問「這個旗標是什麼」答得又快又錯 | 知識型任務，小模型幻覺率最高 | ★★★★★ 改查官方文件；或把文件段落貼給它再問 |
| ★★★ 輸出無限重複 | `temperature` 高／`repeat_penalty` 低／輸入太長 | `temperature` 設 0～0.3；縮短單批輸入 |
| ★★★ 不照輸出格式走 | 小模型對長指令的遵循度低 | 把「輸出格式」搬到提示**最後**；或拆成兩輪 |
| ★★★ 只回應了提示的最後一段 | 情境窗或注意力分布問題 | 拆成兩個提示；最重要的限制**開頭與結尾各放一次** |
| ★★★ 上傳附檔後它算的筆數跟 `grep -c` 不一樣 | 附檔走 RAG，它只看到檢索片段不是全文 | ★★★★ 計數自己算；精確比對改成直接貼過濾後的內容 → [[110-03-04-guide-OpenWebUI-RAG與知識庫]] |

> [!warning] ★★★★ 「地端」不等於「可以隨便貼」
> 換到地端解決的是**資料落地**問題，不是**幻覺**問題，也不是**留痕**問題。
> 地端模型一樣會編旗標，而且編得更兇；
> 地端服務一樣會留對話紀錄，一樣需要存取控管與稽核 →
> [[110-03-12-guide-OpenWebUI-治理與稽核]]、
> [[110-06-06-guide-提示工程-生成式AI使用規範與資料紅線]]。

**原理**：地端模型的失效多半是**工程問題**（情境窗、顯示記憶體、取樣參數）
而不是**智力問題**，這三項排除完之後剩下的能力差距，
才是參數量真正決定的部分。
　→ 原理詳見 [[110-02-05-guide-模型服務-推論引擎與模型選型]]、
[[110-06-04-guide-提示工程-迭代除錯提示與使用反模式]] 的第 4 格

**預防**：
- ★★★★★ 地端的角色定位寫進規範：**做「答案在文字裡」的任務**，不做知識型問答
- ★★★★ 每個常用模型量一次「實際可用的情境大小」，寫在維運文件裡，不要每次現查
- ★★★★ 前處理腳本固定化：撈日誌 → 過濾 → 聚合 → 去識別化，一條龍寫成腳本
- ★★★ 地端替代方案要「夠好用」才擋得住影子 AI：回應太慢、要另記一組密碼、
  中文答得爛，同仁就會拿手機去用外部服務 → [[110-06-06-guide-提示工程-生成式AI使用規範與資料紅線]]

### ★★★★ 情境五：成本爆掉 —— token 用量遠超預期

**現象**：帳單暴增、額度提早用完，但「感覺沒有用得比較多」；
或地端 GPU 整天滿載，其他任務排不進去。

**判斷分流**：★★★★★ 先分清楚是「**單次很貴**」還是「**次數很多**」，
兩者的修法完全相反。

```bash
# 雲端（OpenAI 相容端點）：每次回應裡都有用量
$ jq '.usage' resp.json
{
  "prompt_tokens": 18420,
  "completion_tokens": 640,
  "total_tokens": 19060
}
```

```text
prompt_tokens 大得離譜（幾萬）→ 單次很貴 → ①長對話 ②整份日誌 →【1】【2】
completion_tokens 大          → 要它寫太多 →【3】
單次不大但呼叫次數暴增        → ④重試沒上限 ⑤重複問同樣的事 →【4】【5】
```

★★★★ `prompt_tokens` 遠大於 `completion_tokens` 是常態，
**但如果它一路往上爬而你的問題沒變長，那就是長對話在重送歷史。**

**處置步驟**：

【1】★★★★★ 成因一：**長對話每輪重送全部歷史**。這是最常見、也最容易被忽略的一種。

```text
第 1 輪  送出：系統提示 + 問題1                        ← 便宜
第 5 輪  送出：系統提示 + 問題1..4 + 回答1..4 + 問題5   ← 開始變貴
第 30 輪 送出：系統提示 + 前 29 輪全部 + 問題30         ← ★★★★★ 貴到不成比例
```

★★★★★ 而且**這跟「越聊越笨」是同一個原因**（情境二）——
你付更多錢，買到更差的答案。

```text
□ 一個任務一個對話。排錯完了要寫報告 → 開新的
□ 超過 20～30 輪就交棒重開（交棒提示見情境二【2】）
□ 固定不變的內容（角色、限制、樣板）放系統提示，不要每輪貼一次
□ ★★★★ 排錯時不要「一輪問一句」聊天式往返 ——
  一次把脈絡與限制給足，換三次高品質往返，比二十次低品質往返便宜也準
```

【2】★★★★★ 成因二：**把整份日誌貼進去**。
`prompt_tokens` 一次兩萬多，多半就是這一種。

```bash
# 貼之前先量：位元組數除以 4 是粗估的 token 數
$ echo $(( $(wc -c < /var/log/nginx/error.log) / 4 ))
1842000
```

★★★★★ **前處理是最划算的一件事**：它同時降低成本、提高準確度、避開截斷。

| 削減手法 | 指令 | 典型削減幅度 |
| --- | --- | --- |
| ★★★★★ 時間窗切片 | `journalctl -u <unit> --since "<t1>" --until "<t2>" --no-pager` | 90～99% |
| ★★★★ 只留錯誤層級 | `grep -E '\[(error\|crit\|alert)\]'` | 50～90% |
| ★★★★ 排除已知雜訊 | `grep -v '<雜訊樣式>'` | 10～60% |
| ★★★★★ 正規化後聚合計次 | `sed -E 's/[0-9]+/N/g' \| sort \| uniq -c \| sort -rn \| head -20` | 90～99% |
| ★★★★ 只貼 diff 不貼全文 | `diff -u <a> <b>` | 80～99% |
| ★★★ 砍設定檔註解與空行 | `grep -vE '^\s*(#\|;\|$)' <conf>` | 40～70% |
| ★★★ 只留需要的欄位 | `awk '{print $1,$2,$9}'` | 30～70% |

★★★★ 一個常犯的錯：用 `head -20` 代替 `sort | uniq -c | sort -rn | head -20`。
`head` 取的是**最早的 20 筆**，不是**最常見的 20 種** —— 省了 token，但結論會偏掉。

【3】★★★ 成因三：**要它寫太多**。`completion_tokens` 大就是這一類。

```text
□ 「列出所有可能原因」→ 改成「最多 5 項，不要為湊數擴充」
   ★★★★ 順帶治好「清單湊到十點，後面幾點明顯亂寫」的老毛病
□ 「請詳細說明」→ 改成「每項一行，不超過 30 字」
□ 「把完整設定檔寫出來」→ 改成「只給需要修改的那幾行，並標明放在哪個 context」
□ 輸出格式限制本身就在省錢：「表格之外不要有前言、結論或客套話」
```

【4】★★★★★ 成因四：**一個任務反覆重試沒設上限**。
這一類的特徵是「帳單是隔天才發現的」——因為它發生在半夜的排程裡。

> [!danger] ★★★★★ 沒有上限的重試迴圈是一顆自動化炸彈
> 「驗證不過就重試」的邏輯，配上「模型穩定地產出同一種不合格輸出」，
> 結果就是**整夜都在重試同一件做不到的事**。
> 而且失敗的那幾十次一樣要收費、一樣佔用地端 GPU、
> 一樣讓 cron 任務堆疊起來把主機拖垮。
>
> ★★★★★ **重試次數上限（2～4 次）、單次逾時、以及「超過就轉人工」的出口，
> 三者缺一不可。** 沒有出口的自動化不叫自動化，叫定時炸彈。

```bash
# 三道護欄，一道都不能少
AI_MAX_ATTEMPTS=3            # ① 重試上限
curl --max-time 120 ...      # ② 單次逾時（沒有這個，cron 任務會無限堆積）
# ③ 超過上限的出口：保留現場 + 告警 + 非零退出 + 不產出半成品
```

★★★ 系統性錯誤（端點回 4xx／5xx、金鑰失效、模型名稱錯）**不應該算進重試次數**，
更不該一直重試 —— 那不是「模型這次沒答好」，是設定壞了，重試一萬次也一樣。

【5】★★★★ 成因五：**重複問同樣的事，沒有把結論存下來**。

```text
症狀：同一份日誌問了三天，每天重新貼、重新問、重新等。
     或者三個同事各自問了同一個問題，各自付了一次錢。

修法：
□ ★★★★ 確認過的結論寫成檔案（交接說明、已知錯誤庫），不要只留在聊天視窗
□ ★★★★ 反覆用的問法固定成樣板放 git → [[110-06-05-ref-提示工程-維運提示樣板庫]]
□ ★★★ 一個案件建一個工作目錄，去識別化的對照表跨天沿用，不要每天重跑
□ ★★★ 團隊層級：把「這題已經有答案了」放進已知錯誤庫
      → [[100-02-14-guide-維運-問題管理與已知錯誤庫]]
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 帳單暴增但用量感覺沒變 | 長對話每輪重送全部歷史，成本隨輪數累積 | 一任務一對話；20～30 輪交棒重開 |
| ★★★★★ `prompt_tokens` 一次好幾萬 | 整份日誌／整份設定檔直接貼 | 先 `grep`／`awk`／`uniq -c` 前處理，再貼 |
| ★★★★★ 隔夜收到高額帳單、日誌顯示重試幾十次 | 重試迴圈沒有上限 | `AI_MAX_ATTEMPTS` 設 2～4；超過 `exit` 轉人工 |
| ★★★★ cron 任務越堆越多、主機負載升高 | `curl` 沒設 `--max-time`，端點無回應時卡住 | 一律加 `--max-time`；systemd 加 `TimeoutStartSec=` |
| ★★★★ 端點壞了卻一直重試 | 系統性錯誤被當成「模型沒答好」 | 4xx／5xx 與端點錯誤直接失敗，不計入重試次數 |
| ★★★★ `completion_tokens` 很大 | 要它「列出所有」「請詳細說明」 | 限制項數與字數；禁止前言結語 |
| ★★★★ 多代理／子任務成本翻倍 | 每個子代理都重送同一份完整脈絡 | 子代理只送必要片段；只在子任務可獨立驗收時才用 |
| ★★★ 同一份資料每天重問 | 結論沒有存下來 | 結論寫檔；常用問法做成樣板放 git |
| ★★★ 多台主機排在同一分鐘全部逾時 | 排程時間集中，端點被打爆 | timer 加 `RandomizedDelaySec=`；cron 避開整點 |
| ★★★ 地端 GPU 整天滿載 | 同樣是「重試沒上限 + 輸入沒前處理」 | 地端一樣要設上限與前處理，只是帳單換成排隊 |

★★★★ 最後一種「成本」不會出現在帳單上，但最貴：

```text
花 20 分鐘調提示，這件事自己做只要 5 分鐘。
★★★★★ 迭代三次沒有進展就停手。
能用 awk / grep / diff / jq 解決的，不要用 AI。
→ 確定性任務對照表 → [[110-06-04-guide-提示工程-迭代除錯提示與使用反模式]]
```

**原理**：計費與情境窗都以 token 計，而**對話歷史每一輪都會被完整重送**，
所以成本隨輪數累積而不是隨問題數累積。
前處理之所以是最划算的一步，是因為它同時解決成本、準確度與截斷三個問題。
　→ 原理詳見 [[110-06-02-guide-提示工程-情境工程與何時該重開對話]]
　→ 自動化的護欄與退出碼約定 → [[110-06-03-guide-提示工程-結構化輸出與自動化串接]]

**預防**：
- ★★★★★ 任何自動化的 AI 呼叫，上線前先確認三道護欄：**重試上限、單次逾時、轉人工出口**
- ★★★★★ 貼之前先量 token（`wc -c` 除以 4），養成習慣
- ★★★★ 前處理腳本化：撈 → 過濾 → 聚合 → 去識別化，不要每次手動
- ★★★★ 用量納入監控，設「單日呼叫次數」與「單日 token 數」的告警門檻
  → [[100-01-05-guide-監控-監控策略與告警設計]]
- ★★★ 結論歸檔、樣板放 git，不要讓同一個問題被付費三次

### ★★★★ 情境六：回答泛泛、答非所問 —— 三十秒分流到四格診斷

★★★★★ 這一類 [[110-06-04-guide-提示工程-迭代除錯提示與使用反模式]] 已經有一張
**四種失敗病因診斷表**，本手冊**不重寫它**，只做一件事：**把你分流到對的那一格。**

```text
問自己這四題，第一個答「是」的就是你的病因，不要往下看：

Q1 我的提示拿給同事看，他能不能一句話說出「我要的交付物是什麼」？
   不能 → 第 1 格：任務描述不清
   （典型症狀：通篇「一般來說」「建議考慮」，讀完不知道下一步做什麼）

Q2 它的回答裡，有沒有出現「我的環境中不存在的東西」？
   有 → 第 2 格：脈絡不足
   （典型症狀：用了 yum 但你是 Ubuntu、路徑不對、假設你有 Docker）
   ★★★★ 例外：如果那個東西**在任何環境都不存在**（旗標是編的）→ 那是幻覺，跳情境三

Q3 我能不能不動手就把輸出丟進腳本？
   不能 → 第 3 格：輸出格式沒指定 → 本手冊情境一

Q4 前三格都補齊了，還是在同一處崩？
   是 → 第 4 格：模型層級不對 → 本手冊情境四
```

> [!danger] ★★★★★ 最常見的誤診：把「任務不清」當成「模型不行」
> 然後跑去換更大的模型、加更多 GPU。
> 換模型是**第四層**，不是第一層。
> ★★★★★ **前三格沒補齊就談換模型，你只是在花錢逃避把問題寫清楚。**

★★★★ 分流之後，直接對照原文的兩張表施工：
四格診斷速查（快速版）與「症狀 → 病因 → 修法」15 列完整版，
以及**一次只改一個變因**的紀律 ——
同時改三處，你永遠不會知道哪一處有效。

**原理與完整修法** → [[110-06-04-guide-提示工程-迭代除錯提示與使用反模式]]

### ★★★★★ 情境七：機敏資料已經貼進雲端模型了

★★★★★ **這不是提示工程問題，是資料外洩事件。**
放下手上的提示，先做這一節。

**判斷分流**：先判定顏色，顏色決定緊急程度。

```text
貼出去的內容包含下列任一項  → 紅區 → 【1】立即處置，不可延到明天
  □ 憑證私鑰（-----BEGIN ... PRIVATE KEY-----）
  □ 任何帳號密碼、API 金鑰、Token、資料庫連線字串
  □ 個人資料（姓名 + 身分證字號／地址／電話／病歷／薪資）
  □ 未公開的標案文件、底價、評選委員名單
  □ 內網拓撲圖與 IP 對照表
  □ 資安事件細節（未修補弱點、攻擊路徑、受影響主機清單）
  □ 稽核報告原文（含尚未改善的缺失清單）

只有內部 IP、主機名、路徑、帳號名稱（沒有密碼）→ 黃區 → 【2】
公開技術問題、通用指令用法、無業務內容的寫作      → 綠區 → 沒事，繼續
```

**處置步驟**：

【1】★★★★★ 紅區：**先讓外洩的憑據失效，再談其他。**

```text
① 憑據類（密碼／金鑰／Token／連線字串）—— 立刻輪替，不要等調查結束
   □ 換掉該組密碼與 Token
   □ ★★★★ 同步更新所有用到它的地方：排程、服務設定檔、CI、備份腳本、
     其他主機上的設定 —— 這一步最容易漏，漏了會在半夜炸
   □ 檢查該憑據近期有沒有異常使用紀錄

② 憑證私鑰 —— 這是最嚴重的一種
   □ 撤銷並重簽，所有用該私鑰簽發的憑證全部處理
   □ ★★★★★ 撤銷紀錄會出現在公開的 CT log，等於對外公告出過事，
     所以這一步一定要走通報流程，不要私下處理

③ 個資／標案／資安事件細節 —— 無法「換掉」，只能走通報
   □ 依機關內部規定與主管機關要求通報
   □ → [[090-07-04-guide-資安實踐-資安事件應變流程]]
   □ → [[090-07-07-guide-資安實踐-台灣資安法規與個資法]]

④ 保存現場，不要先刪
   □ ★★★★★ 先截圖／匯出對話內容當作紀錄，再刪對話
   □ 記錄：什麼時候、用哪個服務、哪個帳號、貼了哪些內容、範圍多大
   □ 「刪掉對話」不等於沒發生過 —— 資料已經離開你的網段，
     服務端的保留政策不在你的控制範圍內

⑤ 事後
   □ 關閉該服務帳號的訓練資料使用選項（如果有這個設定）
   □ 檢討為什麼會貼出去：是不知道紅線，還是內部沒有可用的替代方案
```

> [!danger] ★★★★★ 紅區沒有「去識別化之後就可以」這個選項
> 私鑰去識別化之後就不是私鑰了，AI 也幫不了你；
> 標案底價換成 `XXX 元`，AI 就無法回答任何跟金額有關的問題；
> 未修補弱點的細節，**正是那些細節有價值**。
>
> ★★★★★ **紅區資料的正確做法是：改用地端模型，或者根本不要用 AI。**

【2】★★★ 黃區：不是事件，但要補做去識別化並檢討流程。

```bash
# ★★★★★ 送出前的最後一道：輸出必須是空的
$ grep -nE '<你的真實網域>|<你的內網網段>|<真實主機名>' payload.txt
$ grep -nE '(password|token|secret|api[_-]?key)' payload.txt
$ grep -nE '\-\-\-\-\-BEGIN [A-Z ]*PRIVATE KEY' payload.txt
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 私鑰／密碼已送出 | 沒有前處理，或前處理沒涵蓋該檔案 | 立即輪替憑據 → 保存紀錄 → 通報；**不要只刪對話了事** |
| ★★★★★ 個資已送出 | 蒐集目的不包含「送給第三方 AI 分析」 | 依內部規定與主管機關要求通報 |
| ★★★★ 去識別化跑過了，內網 IP 還是漏出去 | 正規表示式沒涵蓋所有網段，或有 IPv6 | 送出前一律跑 `grep -nE` 驗證，輸出必須為空 |
| ★★★★ 短主機名（`web01`）沒被換掉 | 純短名不帶網域，正規表示式抓不到 | 把短名加進主機清單檔後重跑 |
| ★★★★ 每次都沒問題，加起來卻是完整情報 | ★★★★★ 組合外洩：單次無害，累積成拓撲圖 | 一個案件共用一份對照表；限制送出的總量與範圍 |
| ★★★ AI 把佔位符還原成不存在的編號 | 幻覺訊號 | 該段結論不採信，重問或人工查證 |
| ★★★ 版本號被誤判成 IP 換掉 | 四段版本號與 IPv4 格式相同 | 檢查對照表，把誤判項目手動改回 |
| ★★★★ 封鎖了外部 AI 網域，同仁產出物仍有 AI 特徵 | ★★★★★ 轉移到手機了 —— 這是管控失敗訊號 | 回頭檢查內部替代方案好不好用，不要再加封鎖 |

**原理**：技術管控（網域封鎖、DLP、瀏覽器政策）擋不住手機與個人帳號，
所以真正有效的是「**規範劃清紅線 + 內部替代方案夠好用**」的組合。
　→ 原理、三色分級表與可直接跑的去識別化腳本 →
[[110-06-06-guide-提示工程-生成式AI使用規範與資料紅線]]
　→ 開發情境下的合規要求 → [[110-05-11-guide-AI開發-AI輔助開發的資安與合規]]

**預防**：
- ★★★★★ 三色分級表印出來貼在螢幕旁邊，送出前 30 秒自檢（急救卡的第三問）
- ★★★★★ 前處理腳本固定化，並在送出前跑 `grep` 複查，輸出必須為空
- ★★★★ 最好的去識別化是**一開始就不要把它放進去** ——
  大部分維運問題根本不需要真實 IP 與主機名
- ★★★ 機關層級要有《生成式 AI 使用規範》與可用的內部替代方案
  → [[090-07-10-guide-資安實踐-資安政策文件與制度]]

### ★★★★ 情境八：自動化流程壞了 —— 半夜的 AI 步驟失敗、報表沒產出

**現象**：手動跑好好的，放進 cron 或流程引擎就失敗；或流程顯示「成功」但下游拿到空資料。

**判斷分流**：★★★★★ 先確認「**是環境問題還是模型問題**」——
這一步決定了你該去看 systemd 還是去改提示。

```bash
$ journalctl -u <你的服務或 timer> --since today --no-pager | tail -30
$ grep CRON /var/log/syslog | tail -5           # RHEL：/var/log/cron
```

```text
日誌顯示指令根本沒跑起來／找不到指令       → 環境問題 →【1】
指令跑了，但端點回 401 / 404 / 連線失敗    → 設定問題 →【2】
端點回了，但驗證不過                       → 模型輸出問題 → 回情境一
流程顯示「成功」但產物是空的               → ★★★★ 驗證寫錯了 →【3】
任務越堆越多、負載升高                     → 沒有逾時 →【4】
```

**處置步驟**：

【1】★★★★★ 「手動跑正常、cron 裡失敗」幾乎一定是**環境不同**，不是腳本有問題。
cron 的 `PATH` 極短，也不讀 `~/.bashrc` —— 你 `export` 的端點位址與金鑰，
在 cron 裡一個都沒有。

```bash
# 用 cron 的空環境重現一次（★★★★★ 投報率最高的一步）
$ sudo -u <執行帳號> env -i /bin/sh -c '/opt/scripts/ai-report.sh'
/opt/scripts/ai-report.sh: 8: jq: not found
```

```bash
# 修法：腳本內用絕對路徑 + 從權限 0600 的檔案載入設定
source /etc/ai-report.env          # 內含 AI_ENDPOINT / AI_API_KEY，權限 0600
```

systemd timer 的做法是 `EnvironmentFile=`：

```ini
[Service]
EnvironmentFile=/etc/ai-report.env
TimeoutStartSec=600
```

　→ cron 與環境變數的完整排錯 → [[020-01-18-guide-Linux-排程工作]]、
[[020-01-20-guide-Linux-環境變數與設定檔]]

【2】★★★★ 端點錯誤：這是**系統性錯誤**，不要當成「模型沒答好」去重試。

```bash
# 取值之前先確認欄位存在，否則你會拿到字串 "null" 然後一路傳下去
$ jq -e '.choices[0].message.content' resp.json > /dev/null \
    || { echo '端點回應異常：'; jq '.error // .' resp.json; exit 1; }
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ `jq` 取到字串 `null` | 端點回的是錯誤物件，沒有 `choices` | 取值前先 `jq -e` 確認存在，異常直接非零退出 |
| ★★★★ 401 / 403 | 金鑰失效、或 cron 裡讀不到金鑰 | 走【1】確認環境變數有載入；再確認金鑰本身 |
| ★★★ 404 / model not found | 模型名稱打錯，或地端沒 pull 該模型 | 對照實際可用的模型清單 |
| ★★★★ 請求回 400、內容有引號或反斜線 | 手動字串拼接 JSON，跳脫沒處理 | ★★★★ 一律用 `jq -n --arg` 組請求，不要 `printf` 拼 |

【3】★★★★ 「流程成功但產物是空的」—— 驗證失敗時沒有真的讓流程失敗。

```text
✗ 驗證不過 → return []／繼續往下走     ← 下游拿到空資料，而且沒人知道
✓ 驗證不過 → 非零退出／throw new Error  ← 這樣重試與告警機制才會生效
```

★★★★★ 同一個道理的還有：`>/dev/null 2>&1` 會讓你**永遠不知道報表壞了**。
排程最危險的不是失敗，是**靜默失敗**。

```text
□ 產物先寫 .tmp，驗證通過才 mv 原子替換 → 中斷時不會留下半份報表
□ 退出碼要有約定：0 成功 / 1 系統錯誤 / 2 AI 連續失敗轉人工 / 3 交叉驗證失敗
□ ★★★★ 成功也要回報（心跳），不能只靠「失敗會告警」——
  告警管道壞掉的那一天你不會知道
```

【4】★★★ 沒有逾時 → 任務堆積。修法見情境五【4】的三道護欄。

**原理與完整實作**（含驗證腳本、回饋重試、退出碼約定、接進 cron 與流程引擎）
　→ [[110-06-03-guide-提示工程-結構化輸出與自動化串接]]
　→ 腳本本身的寫法 → [[020-01-21-cmd-Linux-Shell腳本入門]]

**預防**：
- ★★★★★ 新的 AI 排程上線後**手動觸發一次**驗證，不要等半夜
- ★★★★★ 三道護欄（重試上限、單次逾時、轉人工出口）寫進驗收清單
- ★★★★ 環境變數放 `EnvironmentFile=`（權限 0600），腳本內用絕對路徑
- ★★★ 產物一律 `.tmp` → `mv`；驗證不過一律非零退出
- ★★★ 多台主機錯開排程時間，避免同時打爆同一個端點

## 什麼時候該停手，不要再調提示了

★★★★★ 這一節可能是整份手冊最省時間的部分。

```text
□ 迭代三次，回答品質沒有可見的進展
  → 停。這件事的形態可能根本不適合 AI，或你在修錯的那一格。

□ 調提示的時間已經超過「自己做完這件事」的時間
  → 停。20 分鐘調提示 vs 5 分鐘自己做，答案很明顯。

□ 這件事有唯一正確答案（man 查得到、官方文件寫得清清楚楚）
  → 停。去查文件。AI 在這一類任務上只會用「很像對的答案」浪費你的驗證時間。

□ 這件事需要即時的系統狀態
  → 停。只有機器自己知道。先 systemctl status / journalctl / df -h，再談要不要問。

□ 這件事是精確計數、全量比對、排序統計
  → 停。grep -c / diff -u / sort | uniq -c 就做完了，而且不會錯。
    ★★★★★ LLM 的計數是結構性弱點，不是提示寫得不夠好。

□ 這件事是不可逆操作（刪除、格式化、撤銷憑證、清空資料表）
  → 停。人工逐字檢查 + dry-run + 測試機驗證。這種事不存在「AI 說可以」。

□ 我已經在「說服它」而不是在「問它」
  → 停。你在跟一個沒有意見的東西辯論。重開對話，換個問法。

□ 我已經累了、時間很趕、而它剛好給了一個很方便的 restart 指令
  → ★★★★★ 停。這是最容易出事的組合。
    停手、喝口水、走驗證流程，或者直接找人。
```

★★★★ 停手之後往哪走：

| 你原本想做的事 | 改成 |
| --- | --- |
| 問「這個旗標是什麼」 | `man <cmd>`、官方 directive index |
| 問「現在系統狀態怎樣」 | `systemctl status`、`journalctl`、`df -h`、`ss -lntp` |
| 問「這兩個檔差在哪」 | `diff -u a.conf b.conf`（★★★★ 要比**實際生效值**：`nginx -T`、`sshd -T`） |
| 問「哪個 IP 最多」 | `awk '{print $1}' access.log \| sort \| uniq -c \| sort -rn \| head` |
| 問「這個設定對不對」 | `nginx -t`、`sshd -t`、`visudo -c`、`systemd-analyze verify` |
| 問「這個腳本安全嗎」 | `bash -n`、`shellcheck`，再自己逐行看 |
| 一直調不出來的分析 | 找人。同事的十分鐘比第七版提示便宜 → [[100-02-10-guide-維運-故障排除方法論]] |
