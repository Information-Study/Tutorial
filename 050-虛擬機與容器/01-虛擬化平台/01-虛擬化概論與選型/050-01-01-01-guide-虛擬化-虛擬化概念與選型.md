# 虛擬化概念與選型

> [!abstract] 這篇你會學到
> - ★★★★★ 虛擬化真正解決的是**「一台實體機只能扮演一個角色」**這件事，不是「省錢」
> - ★★★★★ Type 1 與 Type 2 的**真正分界是誰握有 CPU 排程與記憶體配置的最終決定權**，
>   不是「有沒有裝在作業系統上面」這種表面說法
> - ★★★★★ 為什麼 **KVM 會被同時說成 Type 1 和 Type 2**，以及正確的理解方式
> - ★★★★ **VM 與容器的分界線只有一條：核心（kernel）是不是共用的**
> - ★★★★★ 六個會讓機關踩坑的迷思：**虛擬化不等於省錢**、**快照不是備份**、
>   **HA 不是零停機**、**超配不是免費的**、**VM 不會自動變安全**、**備份 VM 不等於備份服務**
> - ★★★★ 本手冊五個平台（Workstation／PVE／KVM／VirtualBox／ESXi）各自的定位與**主線權重**
> - ★★★★★ **什麼情況「不該」虛擬化** —— 這是選型會議上最少人講、但最會出事的一段
> - ★★★★ 一套可以直接照做的**實體機整併評估流程**（盤點 → 量測 → 算整併比 → 推規格）

> [!warning] 授權資訊請於採購前重新確認
> ★★★★★ 本篇提到各平台的授權模式時，**一律不寫具體金額、不寫具體版本號**。
> VMware／Broadcom 近年授權條款變動頻繁，任何「免費版可以做什麼」「幾個 CPU 起賣」
> 的說法都可能在你讀到這篇時已經失效。
> **一切以採購當時原廠報價與授權條款為準**，詳見 [[050-01-01-04-guide-虛擬化-機關選型與授權成本]]。

## 觀念說明

### ★★★★★ 虛擬化到底在解決什麼問題

在虛擬化普及之前，機關機房長這樣：

| 實體機 | 角色 | 平均 CPU 使用率 | 平均記憶體使用率 |
| --- | --- | --- | --- |
| Server-01 | 檔案伺服器 | 4% | 22% |
| Server-02 | 內部網站 | 7% | 31% |
| Server-03 | 資料庫 | 18% | 55% |
| Server-04 | 排程作業 | 2% | 12% |
| Server-05 | 測試環境 | 1% | 9% |

★★★★★ **每一台都閒到不行，但你不敢把它們裝在一起。** 為什麼？

| 不敢合併的理由 | 說明 |
| --- | --- |
| ★★★★ **相依衝突** | A 服務要 PHP 7.4、B 服務要 PHP 8.3，裝在同一台會打架 |
| ★★★★ **爆炸半徑** | 合併之後任何一個服務把機器搞掛，其他服務一起陪葬 |
| ★★★★ **權責不清** | 廠商 A 的系統和廠商 B 的系統同機，出事時互推責任 |
| ★★★★★ **升級不敢動** | 為了 A 服務要升核心，但 B 服務沒驗證過，於是永遠不升 |
| ★★★ **權限難切** | 想給廠商 root 卻不敢，因為同一台上還有別人的東西 |

**虛擬化用一句話講完：★★★★★ 讓你在一台實體機上，得到多台「彼此完全獨立、
可以各自安裝作業系統、各自重開機、各自升級、各自壞掉」的機器。**

它換來的是四件事：

| 收穫 | 說明 | 重要度 |
| --- | --- | --- |
| **硬體利用率** | 5 台閒置實體機 → 1 台實體機跑 5 台 VM | ★★★ |
| **交付速度** | 新系統上線從「採購 → 到貨 → 上架 → 裝機」的數週，變成 10 分鐘複製範本 | ★★★★★ |
| **軟硬體解耦** | VM 不再綁死在某張主機板上，硬體壞掉可以搬到別台開機 | ★★★★★ |
| **可測試性** | 快照讓你敢動生產環境的設定，因為五秒可以退回去 | ★★★★ |

> [!note] ★★★★★ 最被低估的是「軟硬體解耦」
> 機關最常見的災難不是機器爆炸，而是**十年前那台伺服器的主機板壞了，
> 而上面跑的系統原廠已經倒閉、沒有安裝光碟、沒有人知道怎麼重裝**。
> 虛擬化之後這台機器變成幾個檔案，你可以複製、可以搬到新硬體上開機。
> **這件事的價值遠大於省下的那幾台伺服器。**

### 幾個名詞先講清楚

| 名詞 | 意思 | 常見誤用 |
| --- | --- | --- |
| **Host（宿主機）** | 跑虛擬化軟體的那台**實體機** | 有人把 VM 也叫 host，會混淆 |
| **Guest（客體機）／VM** | 跑在 Host 上的虛擬機 | — |
| ★★★★ **Hypervisor／VMM** | 負責把實體資源切給多個 VM 的那一層軟體 | 有人以為 hypervisor 是一個作業系統 |
| **vCPU** | 分配給 VM 的虛擬 CPU，★★★★ **不等於實體核心** | 最常見的誤解，見下方超配段落 |
| **快照（Snapshot）** | 記錄某個時間點的磁碟（可選記憶體）狀態 | ★★★★★ **常被當成備份，這是災難的起點** |
| **樣板／範本（Template）** | 用來大量複製新 VM 的母體 | — |
| **直通（Passthrough）** | 把實體裝置（GPU／HBA／網卡）整個交給某台 VM 獨佔 | — |
| **超配（Overcommit）** | 分配給所有 VM 的資源總和超過實體擁有的量 | ★★★★ 以為記憶體和 CPU 可以一樣超配 |

### ★★★★★ Type 1 與 Type 2 的真正差別

網路上最常見的說法是：

> Type 1 直接裝在硬體上；Type 2 裝在作業系統上面。

★★★★ **這句話沒有錯，但它是「看起來像什麼」，不是「差別在哪裡」。**
照這個定義你會立刻遇到兩個講不通的地方：

1. ESXi 也有一個核心（VMkernel），也在管理程序、記憶體、檔案系統 ——
   那它不也是「裝在一個作業系統上」嗎？
2. KVM 是 Linux 的一個核心模組，Linux 明明是完整的作業系統 ——
   那 KVM 是 Type 2 嗎？可是它的效能跟 ESXi 是同一個等級。

#### ★★★★★ 正確的分界：誰握有實體資源的最終決定權

| 問題 | Type 1 | Type 2 |
| --- | --- | --- |
| ★★★★★ **誰決定哪個 vCPU 現在可以上實體核心跑？** | Hypervisor 自己 | 底下那個一般 OS 的排程器 |
| ★★★★★ **誰決定實體記憶體怎麼分？** | Hypervisor 自己 | 底下那個一般 OS 的記憶體管理 |
| **VM 在 OS 眼中是什麼？** | 就是被管理的對象本身 | ★★★★ **只是一個普通的使用者程序（process）** |
| **底層那一層還跑別的東西嗎？** | 只跑虛擬化必需的元件 | ★★★★ 瀏覽器、Office、防毒都在同一層搶資源 |
| **典型代表** | ESXi、Proxmox VE、Hyper-V（角色啟用後）、XenServer | VMware Workstation、VirtualBox、VMware Fusion |

★★★★★ **關鍵句：Type 2 的 VM 是「別人家的一個程序」，
所以它永遠拿不到超過那個 OS 願意給它的資源；
Type 1 的 hypervisor 自己就是資源的主人，它說了算。**

這帶來三個實務上摸得到的差異：

| 實務差異 | Type 1 | Type 2 |
| --- | --- | --- |
| ★★★★ **效能穩定度** | 可預期。VM 的效能不會因為你開了瀏覽器而變差 | 不可預期。你在 Host 上跑編譯，VM 就會頓 |
| ★★★★★ **即時性／低延遲** | 可以做到接近實體機 | 底層 OS 的排程延遲會直接傳到 VM 裡 |
| ★★★★ **Host 當機的影響** | Host 只做虛擬化，攻擊面與當機機率低 | ★★★★★ Host 藍屏／Windows Update 重開，**所有 VM 一起沒** |
| **可用的實體資源** | 幾乎全部 | 扣掉 Host OS 與桌面環境的消耗 |
| **上手難度** | 需要專用機器、要進 BIOS、要規劃網路 | 裝好按下一步就能用 |

> [!warning] ★★★★★ Type 2 最致命的一點不是效能，是「Windows Update」
> 把測試環境放在同事桌機的 VMware Workstation 上，
> 某天 Windows 自動更新在半夜重開機 —— **所有 VM 直接斷電關機**，
> 沒有正常關機、沒有 flush 資料庫。
> ★★★★★ **Type 2 只能放「可以隨時被強制關機」的東西。**

#### ★★★★★ 那 KVM 到底是哪一型？

★★★★★ **正確答案：這個問題本身問錯了。**

KVM（Kernel-based Virtual Machine）是 Linux 核心裡的一個模組。載入之後：

- **Linux 核心本身變成了 hypervisor** —— 它直接使用 CPU 的硬體虛擬化指令，
  自己決定 vCPU 什麼時候上實體核心
- 每台 VM 在 `ps` 裡看起來像一個 `qemu-system-x86_64` 程序，
  ★★★★ 但那個程序只是負責「模擬周邊裝置」，**CPU 與記憶體的部分是核心直接處理的**

所以：

| 從哪個角度看 | 結論 |
| --- | --- |
| 看「有沒有一個完整 OS」 | 像 Type 2 |
| ★★★★★ 看「誰決定實體資源怎麼分」 | **是 Type 1**（Linux 核心自己就是那一層） |
| 看效能表現 | 與 Type 1 同級 |

★★★★★ **實務上一律當 Type 1 看待。** Proxmox VE 就是「Debian + KVM + 管理介面」，
它的效能與 ESXi 屬於同一個量級，這一點沒有爭議。

> [!info]- ★★★ 順帶一提：Hyper-V 也是這樣
> 在 Windows 上啟用 Hyper-V 角色之後，**你原本的那個 Windows 會被降級成一個
> 特殊的 VM（叫 root partition／父分割區）**，Hyper-V 這層跑到它下面去。
> 這就是為什麼啟用 Hyper-V 之後，VMware Workstation 與 VirtualBox 的
> 傳統加速模式會出問題 —— ★★★★ **CPU 的虛擬化功能已經被 Hyper-V 佔走了**。
> 詳見 [[050-01-02-06-guide-Workstation-效能調校與疑難排解]]。

### ★★★★ VM 與容器的分界：只有一條線

這是最常被講得很複雜、其實非常簡單的一件事。

```text
      虛擬機（VM）                          容器（Container）
 ┌──────────┬──────────┐            ┌──────────┬──────────┐
 │  App A   │  App B   │            │  App A   │  App B   │
 ├──────────┼──────────┤            ├──────────┼──────────┤
 │ 函式庫    │ 函式庫    │            │ 函式庫    │ 函式庫    │
 ├──────────┼──────────┤            └──────────┴──────────┘
 │ Guest OS │ Guest OS │  ← 各自一套        ↑ 沒有 Guest OS
 │ (含核心)  │ (含核心)  │            ┌─────────────────────┐
 ├──────────┴──────────┤            │   Container Engine   │
 │     Hypervisor      │            ├─────────────────────┤
 ├─────────────────────┤            │  ★★★★★ 共用同一個核心 │
 │      實體硬體         │            ├─────────────────────┤
 └─────────────────────┘            │      實體硬體         │
                                    └─────────────────────┘
```

★★★★★ **分界線：VM 每台有自己的核心，容器共用宿主機的核心。**
其他所有差異都是從這一條線推導出來的：

| 推導出的差異 | VM | 容器 |
| --- | --- | --- |
| **啟動時間** | 數十秒（要跑完整開機流程） | ★★★ 數百毫秒（只是啟動一個程序） |
| **單體大小** | GB 級（含一整套 OS） | MB 級 |
| ★★★★★ **隔離強度** | 強。突破需要 hypervisor 層漏洞 | 較弱。共用核心，**核心漏洞就是共用的風險** |
| ★★★★ **能不能跑不同 OS** | 可以。Linux Host 上跑 Windows VM 沒問題 | ★★★★★ **不行。** Linux 容器只能在 Linux 核心上跑 |
| **能不能改核心參數** | 可以，每台 VM 自己一套 `sysctl` | ★★★★ 大部分不行，`sysctl` 是宿主機共用的 |
| **能不能載入核心模組** | 可以 | ★★★★★ **不行** |
| **適合裝什麼** | 完整系統、有狀態服務、廠商交付的整包系統 | 無狀態應用、微服務、CI 建置環境 |

> [!tip] ★★★★ 機關環境的實務建議
> - **廠商交付的系統、資料庫、AD、需要固定 IP 與長期存在的服務 → 用 VM**
> - **自己開發的 Web 應用、建置環境、短生命週期的東西 → 用容器**
> - ★★★★★ **絕大多數機關的正解是「VM 裡面再跑容器」**，不是二選一。
>   PVE 上開一台 Ubuntu VM，裡面裝 Docker，這是最常見也最好維護的組合。
>   容器相關內容見 [[050-02-01-01-svc-Docker-容器概念與Docker安裝]]。

> [!info]- ★★★ LXC 卡在中間：Proxmox VE 的第三個選項
> PVE 除了 KVM 虛擬機，還支援 **LXC 系統容器**。
> 它比 Docker 更像一台機器（有 init、有多個服務、可以 SSH 進去），
> 但**核心仍然是跟宿主機共用的**。
> - 優點：省記憶體、啟動快、備份小
> - ★★★★ 缺點：**不能跑非 Linux、不能載入核心模組、部分掛載與網路功能受限、
>   嵌套 Docker 需要額外設定**
> - ★★★★ 判斷原則：**廠商系統或有疑慮的東西一律開 KVM VM，
>   自家的輕量 Linux 服務才用 LXC**
>
> 詳見 [[050-01-03-04-guide-PVE-LXC容器管理]]。

### ★★★★★ 六個必須先破除的迷思

這一節請務必看完再去開選型會議。

#### 迷思一：★★★★★ 虛擬化 = 省錢

**不一定。** 虛擬化省的是「實體機台數」，但它同時**新增**了這些成本：

| 新增的成本 | 說明 | 重要度 |
| --- | --- | --- |
| **單機規格拉高** | 一台跑 10 台 VM 的機器，CPU／記憶體／磁碟規格遠高於原本任一台 | ★★★ |
| ★★★★★ **共用儲存** | 要做叢集與 HA 就需要共用儲存或分散式儲存，這常常是最大的一筆 | ★★★★★ |
| ★★★★ **備份方案** | VM 備份的資料量遠大於原本，備份儲存與備份軟體授權要另外編 | ★★★★ |
| ★★★★★ **授權** | 商用 hypervisor 授權、Windows Server 在虛擬化下的授權規則 | ★★★★★ |
| ★★★★ **人力** | 要有人真的懂 hypervisor、儲存與網路，不是「會按下一步」 | ★★★★ |
| **網路設備** | 整併後單台伺服器流量集中，10G 網路與交換器埠可能要升級 | ★★★ |

★★★★★ **虛擬化真正省的是「時間」與「彈性」，不是「錢」。**
用「省錢」去寫簽呈，三年後續約時會非常難看。
TCO 該怎麼算見 [[050-01-01-04-guide-虛擬化-機關選型與授權成本]]。

#### 迷思二：★★★★★ 快照就是備份

★★★★★ **快照不是備份，把快照當備份是機關最常見的資料遺失原因之一。**

| 比較項目 | 快照 | 備份 |
| --- | --- | --- |
| ★★★★★ **存放位置** | 通常**跟原始磁碟在同一份儲存上** | 在另一個儲存／另一台機器／異地 |
| ★★★★★ **儲存壞掉時** | **一起沒了** | 還在 |
| **原理** | 記錄「從某時間點之後的差異」 | 完整（或增量）複製一份資料 |
| ★★★★ **長期保留** | 不行。留越久差異檔越大，效能越差 | 可以，有保留策略 |
| ★★★★ **對效能的影響** | 有。快照鏈越長，磁碟 I/O 越慢 | 備份當下有影響，之後沒有 |
| **用途** | 「我要改設定，五分鐘後可能要退回去」 | 「這台機器沒了，我要重建」 |

> [!danger] ★★★★★ 現場真實案例的模式
> 「這台 VM 有快照，所以不用備份」→ 儲存陣列的 RAID 陣列掛掉 →
> **原始磁碟與快照在同一份儲存上，一起消失**。
> 快照的正確用法是：**動手前開，確認正常後立刻刪**。
> 保留超過數天的快照就是問題，不是保險。
> 備份請看 [[050-01-03-06-svc-PVE-備份與還原]]。

#### 迷思三：★★★★ HA（高可用）= 不會斷線

★★★★★ **不是。** 一般虛擬化平台的 HA 是這樣運作的：

```text
Host A 掛了
   ↓ 叢集偵測到（需要時間，通常數十秒到分鐘級）
   ↓ 確認不是網路分割（fencing／quorum 判斷）
   ↓ 在 Host B 上把那些 VM 開機
   ↓ VM 走完整的開機流程（等同於「被拔電源後重新開機」）
   ↓ 服務起來
```

| 你以為的 HA | 實際的 HA |
| --- | --- |
| 服務不中斷 | ★★★★★ **服務會中斷，中斷時間 = 偵測 + 重開機 + 服務啟動** |
| 資料不會壞 | ★★★★ **等同於斷電，未寫入磁碟的資料會遺失**，資料庫可能要跑復原 |
| 全自動 | ★★★★ 需要 quorum、fencing、共用儲存都設定正確才會動 |

★★★★★ **要「真的不中斷」必須靠應用層做（多節點負載平衡、資料庫複寫），
不是靠 hypervisor。** 見 [[120-01-04-svc-雲端-高可用與負載平衡架構]]
與 [[050-01-03-07-svc-PVE-叢集與高可用]]。

#### 迷思四：★★★★ 超配（Overcommit）是免費的

「我這台有 128 GB 記憶體，我開 20 台各 8 GB 的 VM，反正它們用不滿」——
★★★★★ 這句話對 CPU 大致成立，**對記憶體極度危險**。

| 資源 | 可否超配 | 超配過頭的後果 |
| --- | --- | --- |
| **vCPU** | ★★★ **可以**，這是虛擬化的常態 | 效能變慢、延遲變高，但服務還活著 |
| ★★★★★ **記憶體** | **可以，但代價完全不同** | 開始 swap → 效能崩潰 → **OOM Killer 隨機殺掉 VM** |
| **磁碟空間**（thin provision） | ★★★★ 可以 | ★★★★★ **儲存池寫滿時所有 VM 同時當掉且可能損毀** |

★★★★★ **記憶體超配失控的現場症狀不是「有點慢」，是「整台 Host 上的 VM 一起爆」。**
安全比例與計算方法見 [[050-01-01-02-guide-虛擬化-虛擬化底層技術]]。

#### 迷思五：★★★★ VM 隔離所以比較安全

VM 之間的隔離確實比容器強，但：

| 錯誤期待 | 事實 |
| --- | --- |
| VM 被入侵不會影響別台 | ★★★★ **同一個 vSwitch／橋接網段內的 VM 彼此看得到**，橫向移動照樣發生 |
| Hypervisor 不會被攻擊 | ★★★★★ **hypervisor 與管理介面本身就是最高價值的攻擊目標**，拿下等於拿下全部 VM |
| VM 不用打補丁 | ★★★★★ **每台 VM 都是完整 OS，該打的補丁一個都不能少**，而且台數變多了 |
| VM 不用防毒／不用防火牆 | ★★★★ 一樣要 |

★★★★★ **虛擬化讓你「更容易產生沒人管的機器」** ——
這才是它最大的資安風險。見 [[100-02-13-guide-維運-資產與授權管理]]。

#### 迷思六：★★★★ 備份 VM = 備份服務

備份了整台 VM，還原時你會遇到：

| 問題 | 說明 |
| --- | --- |
| ★★★★ **還原點是磁碟一致，不是應用一致** | 資料庫可能停在交易中間，還原後要跑修復 |
| ★★★★★ **還原需要時間** | 一台 500 GB 的 VM 從備份還原可能要數十分鐘到數小時，RTO 要算進去 |
| ★★★★ **IP／主機名／授權會衝突** | 還原到不同環境時，重複 IP 與 MAC 會打架 |
| ★★★★★ **從來沒演練過** | 最常見的問題。**沒還原過的備份等於沒有備份** |

★★★★ **資料庫請額外做應用層備份（`mysqldump` 或原生工具），不要只靠 VM 快照式備份。**

### ★★★★ 五個平台的定位（本手冊的主線）

> [!tip] ★★★★★ 本手冊的虛擬化主線
> **桌機端／測試環境 → VMware Workstation**
> **機房端／正式環境 → Proxmox VE**
> KVM + libvirt 為輔（理解底層、無 GUI 的伺服器環境），

| 平台 | 型別 | 本手冊定位 | 一句話 |
| --- | --- | --- | --- |
| ★★★★★ **VMware Workstation** | Type 2 | **桌機端主線** | 資訊人員自己桌機上的實驗室，功能與穩定度是 Type 2 裡最完整的 |
| ★★★★★ **Proxmox VE** | Type 1 | **機房端主線** | 開源、含叢集／HA／備份／Web 管理，機關自建機房的預設答案 |

| ★★★ **VMware ESXi** | Type 1 | 補充 | 商用市佔主流，機關接手既有環境時一定會遇到 |

#### 各平台的典型使用情境

| 情境 | 建議平台 | 理由 |
| --- | --- | --- |
| 我要在自己桌機上練 Linux | ★★★★★ **Workstation** | 快照方便、網路模式完整、與桌面整合好 |
| 我要在桌機上模擬三台機器組叢集 | ★★★★ **Workstation** | 支援多網段、Team 式的內部網路 |
| 機房裡有一台實體伺服器，要跑 8 個服務 | ★★★★★ **Proxmox VE** | 單機也能用，且日後可以擴成叢集 |
| 機房裡有三台伺服器要做 HA | ★★★★★ **Proxmox VE** | 內建叢集、Ceph、HA、備份，不用另外買 |
| 純 CLI 的 Ubuntu 伺服器要臨時開一台 VM | ★★★ **KVM + libvirt** | 不用再裝一層管理平台 |
| 我要在 macOS／Windows 上做一個丟完就刪的測試 | ★★ **VirtualBox** | 免費、跨平台、裝了就能用 |
| 接手前朝留下的 vSphere 環境 | ★★★ **ESXi** | 沒得選，先學會維護它再談遷移 |

★★★★ 完整的欄位對照請看 [[050-01-01-03-ref-虛擬化-五平台橫向對照]]。

### ★★★★★ 什麼情況「不該」虛擬化

這一節比前面所有內容都重要，因為它會決定你會不會在半夜被叫回機房。

| 不該虛擬化的情況 | 原因 | 替代做法 |
| --- | --- | --- |
| ★★★★★ **需要特殊實體介面卡** | 老舊的 ISA／PCI 卡、專用 I/O 卡、加密鎖（dongle） | 保留實體機，或確認可用 PCI 直通並先實測 |
| ★★★★★ **原廠明確不支援虛擬化** | 出事時廠商會第一句就說「你沒跑在支援環境上」 | 先取得原廠書面支援聲明再做 |
| ★★★★ **極度延遲敏感的系統** | 工業控制、即時訊號處理、部分語音系統 | 保留實體機，或用直通 + CPU pinning 並實測 |
| ★★★★ **授權綁定實體特徵** | 綁 MAC、綁主機板序號、綁實體 CPU 數的老舊軟體 | 確認授權可轉移，取得原廠同意 |
| ★★★★★ **單一 VM 就要吃掉整台實體機的資源** | 大型資料庫吃掉 90% 資源時，虛擬化只是多一層開銷 | 直接跑實體機（bare metal） |
| ★★★★ **虛擬化平台本身的依賴元件** | 例如：把管理 PVE 叢集用的 DNS／DHCP／AD 開在該叢集裡面 | ★★★★★ **必須放在叢集外**，否則會出現雞生蛋問題 |
| ★★★ **備份伺服器** | 備份主機跟被備份的東西在同一份儲存上 | 備份目的地一定要在叢集外 |
| ★★★★ **沒有人會維護的環境** | 分支單位沒有 IT 人員 | 用雲端服務，或維持單純的實體機 |

> [!danger] ★★★★★ 最經典的雞生蛋事故
> 把 **AD 網域控制站** 與 **DNS** 全部虛擬化，並且放在需要 AD 認證才能登入的
> 管理平台所管理的叢集上。
> 全機房停電復電後：hypervisor 要 DNS 解析才能組叢集 → DNS 在 VM 裡 →
> VM 要叢集起來才能開機 → **卡死**。
> ★★★★★ **至少保留一台獨立的 DNS／DC，或確保它在不依賴叢集服務的節點上可以單獨開機。**

## 安裝或基礎操作

這一節不裝任何虛擬化平台，只做三件必須先會的事：
**確認硬體支援、判斷自己在不在 VM 裡、看懂資源分配的現況。**

### ★★★★★ 步驟一：確認 CPU 支援硬體虛擬化

沒有硬體虛擬化支援，KVM 與 ESXi 根本裝不起來，Workstation 也只能跑在很慢的模式。

#### Linux 端

```bash
# 看 CPU 旗標。Intel 是 vmx，AMD 是 svm
grep -o -m1 -E 'vmx|svm' /proc/cpuinfo
```

預期輸出（Intel 機器）：

```text
vmx
```

★★★ 什麼都沒印出來代表 **CPU 不支援，或 BIOS 沒開**。

```bash
# 算有幾顆邏輯核心支援（等於邏輯核心數）
grep -c -E 'vmx|svm' /proc/cpuinfo
```

```text
16
```

```bash
# 用 lscpu 看得更清楚
lscpu | grep -i -E 'virtual|model name|^CPU\(s\)'
```

預期輸出：

```text
CPU(s):                             16
Model name:                         Intel(R) Xeon(R) Silver 4210R CPU @ 2.40GHz
Virtualization:                     VT-x
```

★★★★ 看到 `Virtualization: VT-x`（AMD 是 `AMD-V`）就代表**硬體支援且 BIOS 已開啟**。

```bash
# Ubuntu/Debian 上更直接的檢查工具
sudo apt install -y cpu-checker
sudo kvm-ok
```

預期輸出（可用）：

```text
INFO: /dev/kvm exists
KVM acceleration can be used
```

預期輸出（BIOS 沒開）：

```text
INFO: Your CPU does not support KVM extensions
KVM acceleration can NOT be used
```

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> RHEL 系沒有 `cpu-checker` 套件，用內建工具即可：
>
> ```bash
> # 檢查 CPU 旗標
> grep -E -o 'vmx|svm' /proc/cpuinfo | sort -u
>
> # 檢查 KVM 模組有沒有載入
> lsmod | grep kvm
> ```
>
> 預期輸出：
>
> ```text
> kvm_intel             380928  0
> kvm                  1146880  1 kvm_intel
> irqbypass              16384  1 kvm
> ```
>
> ★★★ 安裝虛擬化套件群組：`sudo dnf group install "Virtualization Host"`

#### Windows 端

GUI 做法：**工作管理員 → 效能 → CPU**，右下角看「虛擬化：已啟用」。

PowerShell 並陳：

```powershell
# 查 CPU 是否支援並已啟用虛擬化
Get-CimInstance Win32_Processor |
    Select-Object Name, VirtualizationFirmwareEnabled, SecondLevelAddressTranslationExtensions
```

預期輸出：

```text
Name                                      VirtualizationFirmwareEnabled SecondLevelAddressTranslationExtensions
----                                      ----------------------------- ---------------------------------------
Intel(R) Core(TM) i7-12700 CPU @ 2.10GHz                           True                                    True
```

★★★★ `VirtualizationFirmwareEnabled: True` 代表 BIOS 已開啟；
`SecondLevelAddressTranslationExtensions: True` 代表支援 EPT／NPT
（這是效能的關鍵，見 [[050-01-01-02-guide-虛擬化-虛擬化底層技術]]）。

```powershell
# 檢查 Hyper-V 是否已啟用（會影響 Workstation / VirtualBox）
Get-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All |
    Select-Object FeatureName, State
```

```text
FeatureName            State
-----------            -----
Microsoft-Hyper-V-All  Disabled
```

★★★★ 若顯示 `Enabled`，代表 Hyper-V 已接管虛擬化功能，
Workstation 需要走相容模式，效能會下降。處理方式見
[[050-01-02-06-guide-Workstation-效能調校與疑難排解]]。

### ★★★★ 步驟二：BIOS／UEFI 開啟虛擬化

若上一步顯示不支援，重開機進 BIOS：

| 廠牌 | 選項通常在 | 選項名稱 |
| --- | --- | --- |
| Intel 平台 | Advanced → CPU Configuration | `Intel (VMX) Virtualization Technology` |
| AMD 平台 | Advanced → CPU Configuration | `SVM Mode` |
| 直通用（Intel） | Advanced → Chipset / North Bridge | `VT-d` / `Intel VT for Directed I/O` |
| 直通用（AMD） | Advanced → Chipset | `IOMMU` / `AMD-Vi` |

> [!warning] ★★★ 改完 BIOS 一定要「完全斷電」再開
> 部分機型的 VT-x 設定要**完整關機再開機**（不是重開機）才會生效。
> 有些伺服器要透過 BMC 做一次 Power Cycle。

★★★★ 打算做 GPU 或網卡直通的，**VT-d／IOMMU 必須一起開**，
詳見 [[050-01-03-10-guide-PVE-硬體直通與GPU]]。

### ★★★ 步驟三：判斷這台機器是實體機還是 VM

接手不熟悉的環境時，這是第一個要問的問題。

```bash
# 最快的方式（systemd 系統都有）
systemd-detect-virt
```

可能的輸出：

```text

```

| 輸出 | 意思 |
| --- | --- |
| `none` | ★★★ **實體機**（此時指令回傳值為 1） |
| `kvm` | 跑在 KVM／Proxmox VE 上 |
| `vmware` | 跑在 VMware（ESXi 或 Workstation）上 |
| `oracle` | 跑在 VirtualBox 上 |
| `microsoft` | 跑在 Hyper-V 上 |
| `lxc` / `docker` | ★★★ 這根本不是 VM，是容器 |

```bash
# 用 DMI 資訊交叉確認
sudo dmidecode -s system-manufacturer
sudo dmidecode -s system-product-name
```

預期輸出（跑在 PVE 上的 VM）：

```text

Standard PC (i440FX + PIIX, 1996)
```

預期輸出（跑在 VMware 上的 VM）：

```text
VMware, Inc.
VMware Virtual Platform
```

預期輸出（實體伺服器）：

```text
Dell Inc.
PowerEdge R650
```

```powershell

```

```text
Manufacturer   Model
------------   -----
VMware, Inc.   VMware Virtual Platform
```

### ★★★ 步驟四：量測現有實體機的實際負載

整併評估的第一手資料，一定要自己量，不能用「感覺」。

```bash
# 安裝 sysstat（會開啟 sar 的歷史資料收集）
sudo apt install -y sysstat
sudo sed -i 's/^ENABLED="false"/ENABLED="true"/' /etc/default/sysstat
sudo systemctl enable --now sysstat
```

```bash
# 隔天之後，看昨天整天的 CPU 使用率
sar -u -f /var/log/sysstat/sa$(date -d yesterday +%d) | tail -5
```

預期輸出：

```text
23:50:01     CPU     %user     %nice   %system   %iowait    %steal     %idle
23:50:01     all      3.12      0.00      1.04      0.31      0.00     95.53
Average:     all      4.87      0.02      1.55      0.44      0.00     93.12
```

★★★★ 這台機器平均只用了約 **6.4% 的 CPU**（100 − 93.12），
是整併的標準對象。

```bash
# 看記憶體實際使用（重點是 available，不是 free）
free -h
```

```text
               total        used        free      shared  buff/cache   available
Mem:            15Gi       3.2Gi       8.1Gi       120Mi       4.4Gi        11Gi
Swap:          2.0Gi          0B       2.0Gi
```

★★★★★ **看 `available`（11 Gi 可用），不要看 `free`。**
`buff/cache` 是可回收的，把它算成「已用」會嚴重高估需求。

```bash
# 看磁碟實際用量（不是磁碟容量）
df -hT -x tmpfs -x devtmpfs
```

```text
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/sda2      ext4  196G   58G  128G  32% /
/dev/sdb1      xfs   1.8T  340G  1.5T  19% /data
```

★★★★ 整併時要遷移的是 **58G + 340G ≈ 398 GB 的實際資料**，不是 2 TB 的容量。

## 進階應用

### ★★★★ 整併比（Consolidation Ratio）怎麼算

整併比 = 幾台 VM 塞進一台實體 Host。它由**三個上限中最嚴格的那一個**決定：

```text
整併比 = MIN( CPU 允許的台數, 記憶體允許的台數, 儲存允許的台數 )
```

| 資源 | 算法 | 常見瓶頸程度 |
| --- | --- | --- |
| **CPU** | 實體邏輯核心數 × 允許超配倍率 ÷ 每台 VM 的 vCPU 數 | ★★ 通常不是瓶頸 |
| ★★★★★ **記憶體** | （實體記憶體 − Host 保留）÷ 每台 VM 記憶體 | ★★★★★ **九成以上的情況瓶頸在這裡** |
| **儲存 IOPS** | 儲存能提供的 IOPS ÷ 每台 VM 需要的 IOPS | ★★★★ 用機械硬碟時會是瓶頸 |
| **儲存容量** | 可用容量 ÷ 每台 VM 佔用 | ★★★ |

★★★★★ **記住這句話：買虛擬化主機時，記憶體永遠先買滿，CPU 核心數不必衝頂。**

### ★★★★ 從實體到虛擬（P2V）的判斷

| 這台機器的狀況 | 建議做法 | 理由 |
| --- | --- | --- |
| 有安裝程式、有設定文件、廠商還在 | ★★★★★ **重建（rebuild），不要 P2V** | 順便清掉十年的垃圾，OS 也升級 |
| 沒有安裝程式，但服務單純 | ★★★★ 重建 + 搬資料 | 一樣建議重建 |
| ★★★★★ **沒程式、沒文件、沒人懂、廠商倒了** | **P2V 整台搬過來** | 這正是 P2V 存在的理由 |
| 極舊的 OS（已停止支援） | ★★★★ P2V 後**隔離網段**、只開必要埠 | 保命用，同時排除役規劃 |
| 有硬體加密鎖或特殊介面卡 | ★★★★★ **先別動**，確認直通可行再說 | 直通失敗會整個卡住 |

> [!tip] ★★★★ P2V 之後一定要做的四件事
> 1. **移除舊硬體驅動與原廠管理代理程式**（iDRAC/iLO agent、RAID 卡工具）
> 2. **安裝 guest agent**（`qemu-guest-agent` 或 VMware Tools），否則正常關機與備份一致性都會有問題
> 3. ★★★★★ **確認網卡名稱有沒有改變** —— Linux 的網卡從 `eno1` 變成 `ens18`，
>    設定檔沒改就開不了機也連不上
> 4. **檢查授權是否需要重新啟用**

### ★★★★ 虛擬化下的授權陷阱

| 陷阱 | 說明 | 重要度 |
| --- | --- | --- |
| **Windows Server 授權綁實體核心** | 授權是按 Host 的**實體核心**買的，不是按 VM 數量 | ★★★★★ |
| **OEM 授權不可轉移** | 隨機出貨的 OEM Windows **不能** P2V 到別台機器上 | ★★★★★ |
| **VM 遷移會觸發重新啟用** | VM 在叢集節點間搬動時，某些軟體會判定為換機器 | ★★★★ |
| ★★★ **資料庫按核心授權** | 給 VM 8 vCPU 就可能要買 8 核心的授權，即使實體只用到 2 核 | ★★★★★ |
| **廠商系統的支援聲明** | 「不支援虛擬化環境」寫在合約裡卻沒人看 | ★★★★★ |

★★★★★ **採購前必問廠商：「這套系統在虛擬化環境下你們支援嗎？請提供書面說明。」**
詳見 [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 與 [[080-01-04-guide-專管-機關採購案實務]]。

### ★★★ 虛擬化的五個層次

大部分人講「虛擬化」只想到伺服器虛擬化，實際上有五層：

| 層次 | 做什麼 | 本手冊在哪裡談 |
| --- | --- | --- |
| ★★★★★ **伺服器虛擬化** | 一台實體機切成多台 VM | 本章 |
| ★★★ **儲存虛擬化** | 把多顆磁碟／多台機器的空間抽象成一個池 | [[050-01-03-02-guide-PVE-儲存設定]]、[[020-01-24-guide-進階儲存-ZFS與Btrfs]] |

### ★★★★ 第 2 步：撰寫資料收集腳本

```bash
cat > collect.sh <<'EOF'
#!/usr/bin/env bash
# 收集單台主機的整併評估資料

    sar -u 1 5 | tail -1
else

fi

echo "===== MEM ====="

df -BG -x tmpfs -x devtmpfs --output=source,size,used,target | tail -n +2

echo "===== NET ====="
ip -br -4 addr show | grep -v '^lo'

echo "===== OS ====="
. /etc/os-release && echo "$PRETTY_NAME"

echo "===== SERVICES ====="
systemctl list-units --type=service --state=running --no-legend --no-pager | awk '{print $1}'
EOF
```

### ★★★★ 第 4 步：彙整成一張表

```bash
cat > summarize.sh <<'EOF'
#!/usr/bin/env bash
# 從 raw/*.txt 產生整併彙總表
printf "%-12s %-6s %-10s %-10s %-10s %-10s\n" \
    "HOST" "CPUs" "CPU_USED%" "MEM_TOT_GB" "MEM_USED_GB" "DISK_USED_GB"

    host=$(awk '/^===== HOSTNAME/{getline; print}' "$f")
    cpus=$(awk '/^CPU\(s\):/{print $2; exit}' "$f")
    idle=$(awk '/^Average:/{print $NF; exit}' "$f")
    cpu_used=$(awk -v i="$idle" 'BEGIN{printf "%.1f", 100-i}')
    mem_tot=$(awk -F'total_MB=| used_MB=' '/total_MB=/{print $2; exit}' "$f" | awk '{print $1}')
    mem_used=$(awk -F'used_MB=' '/total_MB=/{print $2; exit}' "$f" | awk '{print $1}')
    disk_used=$(awk '/^\/dev\//{gsub(/G/,"",$3); s+=$3} END{print s}' "$f")
    printf "%-12s %-6s %-10s %-10.1f %-10.1f %-10s\n" \
        "$host" "$cpus" "$cpu_used" \
        "$(awk -v m="$mem_tot" 'BEGIN{print m/1024}')" \
        "$(awk -v m="$mem_used" 'BEGIN{print m/1024}')" \
        "$disk_used"
done
EOF
```

### ★★★★★ 第 5 步：推算整併後的規格需求

把上表換算成 VM 規格。★★★★★ **規則：vCPU 給實體核心數即可（超配靠 Host 消化），
記憶體給「實際使用 × 1.5」並向上取到 2 的次方，磁碟給「實際使用 × 1.6」。**

| VM | vCPU | 記憶體 | 磁碟 | 依據 |
| --- | --- | --- | --- | --- |
| srv-db | 8 | 32 GB | 640 GB | 17.4 × 1.5 ≈ 26 → 取 32；398 × 1.6 ≈ 637 |
| srv-file | 4 | 8 GB | 2000 GB | 檔案伺服器記憶體需求低、容量需求高 |
| srv-web | 4 | 8 GB | 120 GB | 5.6 × 1.5 ≈ 8.4 → 取 8（有 balloon 可調） |
| srv-batch | 2 | 8 GB | 80 GB | — |
| srv-test | 2 | 4 GB | 60 GB | 測試機可以壓低 |
| **合計** | **20 vCPU** | **60 GB** | **2900 GB** | — |

### ★★★★★ 第 6 步：推算 Host 規格

```bash
cat > sizing.sh <<'EOF'
#!/usr/bin/env bash
# 依 VM 資源總和推算 Host 規格
set -euo pipefail

TOTAL_VCPU=20          # 所有 VM 的 vCPU 總和
TOTAL_MEM_GB=60        # 所有 VM 的記憶體總和
TOTAL_DISK_GB=2900     # 所有 VM 的磁碟總和

CPU_OVERCOMMIT=4       # vCPU : 實體邏輯核心 的允許比例（一般負載 3~4）
HOST_RESERVE_GB=16     # 保留給 hypervisor 本身（PVE 含 ZFS 時要更多）
GROWTH=1.3             # 三年成長係數
N_PLUS_1=1             # 是否預留一台 Host 故障的餘裕（1=是）

echo "===== Host 規格推算 ====="

CORES=$(awk -v v="$TOTAL_VCPU" -v o="$CPU_OVERCOMMIT" -v g="$GROWTH" \
    'BEGIN{printf "%d", (v/o)*g + 0.999}')
echo "需要邏輯核心數（含成長）      : ${CORES}"

MEM=$(awk -v m="$TOTAL_MEM_GB" -v r="$HOST_RESERVE_GB" -v g="$GROWTH" \
    'BEGIN{printf "%d", m*g + r + 0.999}')
echo "需要記憶體 GB（含成長與保留） : ${MEM}"

DISK=$(awk -v d="$TOTAL_DISK_GB" -v g="$GROWTH" \
    'BEGIN{printf "%d", d*g*1.25 + 0.999}')
echo "需要可用儲存 GB（含快照餘裕）  : ${DISK}"

if [ "$N_PLUS_1" -eq 1 ]; then
    echo
    echo "--- N+1（任一台故障仍能承載全部 VM）---"
    echo "三台節點時，每台建議規格："
    awk -v c="$CORES" 'BEGIN{printf "  邏輯核心      : %d\n", (c/2)+0.999}'
    awk -v m="$MEM" 'BEGIN{printf "  記憶體 GB     : %d\n", (m/2)+0.999}'
    echo "  （三台中任兩台即可承載全部負載）"
fi
EOF

chmod +x sizing.sh
./sizing.sh
```

預期輸出：

```text
===== Host 規格推算 =====
需要邏輯核心數（含成長）      : 7
需要記憶體 GB（含成長與保留） : 94
需要可用儲存 GB（含快照餘裕）  : 4713

--- N+1（任一台故障仍能承載全部 VM）---
三台節點時，每台建議規格：
  邏輯核心      : 4
  記憶體 GB     : 47
  （三台中任兩台即可承載全部負載）
```

★★★★★ **實際採購時要向上取到市售規格**，例如：

| 項目 | 計算值 | 採購值 | 理由 |
| --- | --- | --- | --- |
| 邏輯核心／台 | 4 | **16**（8 核心含 HT） | 市售最小規格已經超過，且要留 Ceph／ZFS 的運算量 |
| 記憶體／台 | 47 GB | **128 GB** | ★★★★★ 記憶體是唯一的硬瓶頸，一次買到位比事後加便宜 |
| 可用儲存 | 4713 GB | **8 TB 可用** | RAID／副本會吃掉一半以上原始容量 |

### 第 7 步：決定平台

用 [[050-01-01-03-ref-虛擬化-五平台橫向對照]] 的決策樹跑一次。本例的條件是：
三台節點、要 HA、機關預算有限、有 Linux 人力 →

### ★★★★ 第 8 步：排出遷移順序

★★★★★ **順序原則：從最沒人在意的開始，最重要的最後做。**

| 順序 | VM | 方式 | 理由 |

| 1 | srv-test | 重建 | 沒人在意，用來驗證整套流程 |
| 2 | srv-batch | 重建 | 排程作業可以挑週末停 |
| 3 | srv-web | 重建 + 搬資料 | 有停機時窗可談 |
| 4 | srv-file | 資料同步（rsync）分次搬 | 資料量大，先同步再切換 |
| 5 | srv-db | ★★★★★ **最後做，且要有回退計畫** | 停機成本最高 |

## 常見錯誤與排錯

| # | 現象 | 原因 | 解法 |
| --- | --- | --- | --- |
| 1 | ★★★★ `kvm-ok` 回報 `KVM acceleration can NOT be used` | BIOS 未開啟 VT-x／SVM | 進 BIOS 開啟後**完全斷電再開機**（不是重開機） |
| 2 | ★★★★★ Windows 上裝 Workstation 後，VM 開機極慢或報告與 Hyper-V 衝突 | Hyper-V／記憶體完整性（Core Isolation）佔用了虛擬化功能 | 停用 Hyper-V 與 Device Guard，或改用 Workstation 的 Hyper-V 相容模式；見 [[050-01-02-06-guide-Workstation-效能調校與疑難排解]] |
| 3 | ★★★★ VM 遷移後 Linux 開不了機，卡在等待網路逾時 | 網卡名稱從 `eno1` 變成 `ens18`，網路設定檔對不上 | 進單人模式改 netplan／`/etc/network/interfaces` 的介面名，或用 `net.ifnames=0` 暫時繞過 |
| 4 | ★★★★★ Host 突然變得極慢，多台 VM 同時無回應 | 記憶體超配過頭，Host 開始大量 swap | 立刻關閉非必要 VM 或降低配額；長期解是加記憶體。見 [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] |
| 5 | ★★★★★ 儲存池顯示 100%，所有 VM 同時進入唯讀或當機 | thin provision 超賣，實際寫入把儲存寫滿 | 立即刪除舊快照／舊備份釋放空間；建立 80% 告警門檻 |
| 6 | ★★★★★ 想還原時發現「快照都在，但儲存壞了」 | 把快照當備份，兩者在同一份儲存 | 建立獨立的備份目的地；見 [[050-01-03-06-svc-PVE-備份與還原]] |
| 7 | ★★★★ VM 越跑越慢，磁碟 I/O 延遲飆高 | 快照鏈太長，每次讀寫都要穿過多層差異檔 | 刪除不需要的快照並整併；訂「快照存活不超過 7 天」的規則 |
| 8 | ★★★★ 停電復電後叢集起不來，管理介面連不上 | DNS／DHCP／AD 全部虛擬化在同一個叢集內 | 保留獨立的 DNS／DC；節點設定用 IP 或 `/etc/hosts` 而非依賴 DNS |
| 9 | ★★★★ VM 內部時間持續偏移 | 未安裝 guest agent／未設定時間同步 | 安裝 `qemu-guest-agent` 或 VMware Tools，並設定 chrony；見 [[020-01-28-cmd-Linux-時間同步NTP與chrony]] |
| 10 | ★★★★ 從 PVE 介面按「關機」沒反應，只能強制停止 | VM 內未安裝 guest agent，ACPI 訊號沒有被處理 | 安裝 `qemu-guest-agent` 並在 VM 選項中啟用 QEMU Guest Agent |
| 11 | ★★★★★ 廠商拒絕支援，理由是「跑在虛擬化上」 | 採購前未取得書面支援聲明 | 採購階段就要求廠商書面確認；已發生時協商或保留實體機 |
| 12 | ★★★ `systemd-detect-virt` 顯示 `none` 但明明是 VM | 該虛擬化平台隱藏了 CPUID 特徵，或是非 systemd 系統 | 用 `dmidecode -s system-manufacturer` 交叉確認 |
| 13 | ★★★★ 整併後尖峰時段所有 VM 一起變慢 | 只算了平均負載，沒算尖峰同時發生的情況 | 評估時要看 `sar` 的**尖峰值**與尖峰**時間分布**，錯開排程作業 |
| 14 | ★★★★ VM 內 `top` 顯示 `st`（steal）數值很高 | CPU 超配過頭，vCPU 排不到實體核心 | 降低 vCPU 超配比、減少 VM 數量，或增加實體核心 |
| 15 | ★★★★★ 備份都有跑，但真的要還原時失敗 | 從未做過還原演練，備份其實是壞的 | ★★★★★ **每季至少做一次還原演練並記錄耗時**，寫進維運制度 |
| 16 | ★★★ 新建的 VM 沒人知道是誰開的、跑什麼 | 缺乏命名規則與資產登錄 | 建立命名規則與 VM 資產表；見 [[100-02-13-guide-維運-資產與授權管理]] |

## 安全性注意事項

> [!danger] ★★★★★ Hypervisor 管理介面 = 整個機房的鑰匙
> 拿到 PVE 或 ESXi 的管理權限，等於拿到上面**每一台 VM 的磁碟內容**。
> 攻擊者不需要破解任何一台 VM 的密碼 —— 直接掛載它的磁碟就好。
> **管理介面的防護等級必須高於任何一台 VM。**

| 項目 | 做法 | 重要度 |
| --- | --- | --- |
| **管理網段分離** | 管理介面放在獨立 VLAN，不與 VM 服務網段共用 | ★★★★★ |
| **不開放對外** | 管理介面**絕對不要**直接對 Internet；要遠端就走 VPN 或跳板 | ★★★★★ |
| **停用 root 直接登入** | 建個人帳號，用角色授權；PVE 見 [[050-01-03-08-guide-PVE-使用者權限與API]] | ★★★★★ |
| **二階段驗證** | 管理介面帳號一律啟用 TOTP | ★★★★★ |
| **最小權限** | 廠商只給他負責那幾台 VM 的權限，不給整個資料中心 | ★★★★ |
| ★★★★ **VM 之間也要防火牆** | 同一個橋接網段內的 VM 彼此可見，該隔離的要用 VLAN 或防火牆規則隔開 | ★★★★ |
| **快照與備份也要保護** | 備份檔案含完整磁碟內容，**權限等同於原機** | ★★★★★ |
| **hypervisor 也要更新** | 虛擬化平台本身的安全更新不能只做一次 | ★★★★ |
| ★★★ **注意「殭屍 VM」** | 沒人維護、沒打補丁、還開著的 VM 是最好的跳板 | ★★★★★ |
| **稽核日誌** | 誰開了 VM、誰做了快照、誰匯出磁碟，都要留紀錄 | ★★★★ |
| **匯出磁碟的管制** | ★★★★★ 一個 `qm importdisk`／下載 vmdk 的動作就等於把整台機器帶走 | ★★★★★ |

> [!warning] ★★★★ 虛擬化最容易被忽略的資安問題
> 不是 hypervisor 有漏洞，而是 **「開 VM 太簡單，所以到處都是沒人管的 VM」**。
> 制度上必須要求：**每台 VM 都要有負責人、有用途、有退場日期。**
> 見 [[100-02-13-guide-維運-資產與授權管理]] 與 [[040-02-11-guide-機房-資訊設備盤點]]。

## 速查表

### 硬體與環境檢查

| 目的 | 指令 | 重點 |
| --- | --- | --- |
| 看 CPU 是否支援虛擬化（Linux） | `grep -o -m1 -E 'vmx\|svm' /proc/cpuinfo` | 空白 = 不支援或 BIOS 沒開 |
| 看虛擬化狀態（清楚版） | `lscpu \| grep -i virtual` | 應顯示 `VT-x` 或 `AMD-V` |
| KVM 可用性檢查（Debian 系） | `sudo kvm-ok` | 需先裝 `cpu-checker` |
| KVM 模組是否載入 | `lsmod \| grep kvm` | 應看到 `kvm_intel` 或 `kvm_amd` |
| ★★★ 判斷是否在 VM 內 | `systemd-detect-virt` | `none` = 實體機 |
| 交叉確認虛擬化廠商 | `sudo dmidecode -s system-manufacturer` | `QEMU` / `VMware, Inc.` / `Dell Inc.` |
| CPU 支援虛擬化（Windows） | `Get-CimInstance Win32_Processor \| Select VirtualizationFirmwareEnabled` | `True` = 已開啟 |
| Hyper-V 是否啟用（Windows） | `Get-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All` | 會影響 Workstation |

### 負載量測

| 目的 | 指令 | 重點 |
| --- | --- | --- |
| ★★★★ 昨日 CPU 平均使用率 | `sar -u -f /var/log/sysstat/sa$(date -d yesterday +%d)` | 看 `Average:` 那行的 `%idle` |
| 即時 CPU 取樣 | `sar -u 1 5` | 沒有歷史資料時用 |
| ★★★★★ 記憶體真實可用量 | `free -m` | **看 `available`，不是 `free`** |
| 磁碟實際用量 | `df -hT -x tmpfs -x devtmpfs` | 遷移量看 `Used` 不看 `Size` |
| 磁碟 I/O 延遲 | `iostat -xz 1 5` | 看 `await` 與 `%util` |
| ★★★★ VM 內看 CPU 被搶走多少 | `top` 的 `%st`（steal） | 持續 > 5% 代表 Host 超配過頭 |

## 練習題

1. **量測你自己的機器**：在一台你有權限的伺服器上，安裝 `sysstat`，
   啟用歷史收集，隔天用 `sar` 取出整天的 CPU 平均使用率與尖峰值。
   判斷這台機器是不是整併的候選對象。
2. **判斷身分**：找三台你管理的機器，用 `systemd-detect-virt` 與 `dmidecode`
   判斷它們分別是實體機、KVM VM、還是 VMware VM，並解釋兩個指令結果不一致時要信哪一個。
3. **算一次整併**：假設你有 6 台實體機，記憶體實際使用分別為
   3、5、12、4、18、2 GB。用本篇的係數推算：這些 VM 的記憶體總需求是多少？
   一台 Host 至少要多少實體記憶體？做 N+1 三節點時每台要多少？
4. **抓出不該虛擬化的機器**：檢視你單位的伺服器清單，找出至少一台
   「不該虛擬化」的機器，寫出理由屬於本篇表格中的哪一類。
5. **快照演練**：在測試 VM 上建立快照 → 故意刪掉一個設定檔 → 還原快照 →
   確認檔案回來了 → **刪除快照**。記錄整個流程各花多久。

> [!question]- 練習題參考解答
>
> **1.** 關鍵在於「不能只看平均」。指令流程：
> ```bash
> sudo apt install -y sysstat
> sudo sed -i 's/^ENABLED="false"/ENABLED="true"/' /etc/default/sysstat
> sudo systemctl enable --now sysstat
> # 隔天
> sar -u -f /var/log/sysstat/sa$(date -d yesterday +%d)
> ```
> ★★★★ 判斷標準：**平均使用率低於 20%、且尖峰不超過 60%** 的機器是好的整併對象。
> 若尖峰逼近 100%（例如每天凌晨的批次），整併時要注意**不要跟其他同時段的
> 尖峰負載放在同一台 Host**。
>
> **2.** `systemd-detect-virt` 靠 CPUID 與 DMI 判斷，速度快；
> `dmidecode` 直接讀 SMBIOS 的廠商字串。
> ★★★★ **兩者不一致時，以 `dmidecode` 為準** —— 有些平台會刻意隱藏 CPUID 特徵
> （例如做 GPU 直通時為了繞過驅動檢查），但 DMI 字串通常還在。
> 另外 `systemd-detect-virt` 在容器裡會回報 `lxc`／`docker`，那根本不是 VM。
>
> **3.**
> - VM 記憶體需求：(3 + 5 + 12 + 4 + 18 + 2) × 1.5 = 44 × 1.5 = **66 GB**
>   （逐台向上取 2 的次方會更多：8+8+32+8+32+4 = **92 GB**，★★★★ 以這個為準比較安全）
> - 單台 Host：92 × 1.3（成長）+ 16（保留）≈ **136 GB → 採購 192 GB**
> - N+1 三節點：任兩台要能承載 92 GB → 每台至少 46 GB + 保留 16 GB ≈ 62 GB
>   → ★★★★ **每台採購 128 GB**（市售級距，且留給 Ceph／ZFS）
>
> **4.** 常見答案：跑舊版 ERP 且原廠已倒閉、插著硬體加密鎖、
> 或是唯一一台 DNS／DC。理由要對應到「原廠不支援」「特殊實體介面」
> 「虛擬化平台自身的依賴元件」其中一類。
>
> **5.** 重點在最後一步。★★★★★ **很多人做完前四步就走了，快照留在那裡。**
> 正確流程結束時 `qm listsnapshot <VMID>`（PVE）或 Workstation 的快照管理員
> 應該是空的。快照存在的時間越長，磁碟效能越差、佔用空間越大。

## 小測驗

**Q1**（選擇）下列哪一項才是 Type 1 與 Type 2 hypervisor 的**根本**差別？
　(A) 有沒有圖形介面
　(B) 誰握有實體 CPU 排程與記憶體配置的最終決定權
　(C) 是不是免費
　(D) 能不能做快照

**Q2**（是非）KVM 因為是 Linux 核心模組，所以效能屬於 Type 2 等級。

**Q3**（簡答）用一句話說出 VM 與容器唯一的根本分界是什麼。

**Q4**（選擇）某機關把 20 台 VM 的快照當成備份，某天儲存陣列故障。
結果最可能是？
　(A) 快照還在，可以還原
　(B) 快照與原始磁碟同在該儲存上，一起遺失
　(C) 快照會自動同步到別台機器
　(D) hypervisor 會自動保護快照

**Q5**（這行指令會發生什麼）

```bash
free -m | awk '/^Mem:/ {print $2, $3, $7}'
```

**Q6**（選擇）整併評估時，最常成為瓶頸的資源是？
　(A) CPU 核心數　(B) 記憶體　(C) 網路頻寬　(D) 電源插座

**Q7**（是非）虛擬化平台的 HA 功能可以做到服務完全不中斷。

**Q8**（簡答）某機關要把唯一的 DNS 伺服器虛擬化，放進三節點 PVE 叢集。
請說出這個規劃最大的風險，以及一個可行的改法。

**Q9**（這行指令會發生什麼）在一台你不確定身分的 Ubuntu 機器上執行：

```bash
systemd-detect-virt; echo "exit=$?"
```

若輸出為 `none` 與 `exit=1`，代表什麼？

**Q10**（簡答）列出**三個**「不該虛擬化」的情況。

> [!question]- 測驗答案
>
> **Q1 → (B)** ★★★★★
> 「裝在硬體上／裝在 OS 上」只是外觀描述。真正的分界是**誰是資源的主人**：
> Type 2 的 VM 只是底層 OS 眼中的一個普通程序，永遠拿不到超過那個 OS 願意給的資源。
> 見〈Type 1 與 Type 2 的真正差別〉。
>
> **Q2 → 錯** ★★★★★
> 載入 KVM 模組後 **Linux 核心本身變成 hypervisor**，直接使用 CPU 的硬體虛擬化指令，
> 效能與 Type 1 同級。QEMU 程序只負責模擬周邊裝置。
> 實務上一律當 Type 1 看待。見〈那 KVM 到底是哪一型〉。
>
> **Q3** ★★★★★
> **核心（kernel）是不是共用的。** VM 每台有自己的核心，容器共用宿主機的核心。
> 啟動速度、隔離強度、能不能跑不同 OS，全部是從這一條線推導出來的。
> 見〈VM 與容器的分界〉。
>
> **Q4 → (B)** ★★★★★
> 快照通常與原始磁碟放在**同一份儲存**上，記錄的是差異而非完整副本。
> 儲存故障時兩者一起消失。快照的用途是「改設定前的短期後路」，不是備份。
> 見〈迷思二〉。
>
> **Q5** ★★★★
> 印出記憶體的 **total、used、available**（單位 MB）三個數值。
> 重點在第三個：★★★★★ **評估記憶體需求要看 `available`，不是 `free`**，
> 因為 `buff/cache` 是可回收的，把它算成已用會嚴重高估。
> 見〈步驟四：量測現有實體機的實際負載〉。
>
> **Q6 → (B)** ★★★★★
> CPU 可以安全超配（3～4:1），記憶體不能。九成以上的整併案例瓶頸在記憶體。
> 所以採購原則是「記憶體先買滿，核心數不必衝頂」。見〈整併比怎麼算〉。
>
> **Q7 → 錯** ★★★★★
> HA 的流程是「偵測故障 → fencing 判斷 → 在其他節點**重新開機**」，
> 對 VM 而言等同於被拔電源後重開。中斷時間 = 偵測 + 開機 + 服務啟動。
> 要真的不中斷必須靠應用層多節點。見〈迷思三〉。
>
> **Q8** ★★★★★
> 風險：**雞生蛋問題**。停電復電後，叢集節點可能需要 DNS 才能正常組成，
> 而 DNS 在需要叢集先起來的 VM 裡，導致卡死。
> 改法（任一）：(1) 保留一台獨立於叢集外的實體或雲端 DNS；
> (2) 節點間的設定全部用 IP 或 `/etc/hosts`，不依賴 DNS；
> (3) 至少讓其中一台 DNS VM 設為「不依賴共用儲存、本機磁碟即可開機」。
> 見〈什麼情況不該虛擬化〉。
>
> **Q9** ★★★
> `systemd-detect-virt` 輸出 `none` 且結束碼為 1，代表**偵測不到虛擬化環境，
> 判定為實體機**（這個指令在偵測不到時刻意回傳非 0）。
> ★★★★ 但要注意有些平台會隱藏 CPUID 特徵，
> 應再用 `sudo dmidecode -s system-manufacturer` 交叉確認。
> 見〈步驟三〉與排錯表第 12 列。
>
> **Q10** ★★★★★（任三個）
> (1) 需要特殊實體介面卡或硬體加密鎖；
> (2) 原廠明確不支援虛擬化環境；
> (3) 極度延遲敏感的即時系統；
> (4) 授權綁定實體 MAC／序號且不可轉移；
> (5) 單一系統就會吃掉整台實體機的資源；
> (6) ★★★★★ 虛擬化平台自身依賴的元件（DNS／DHCP／AD／備份主機）；
> (7) 現場沒有人會維護。
> 見〈什麼情況不該虛擬化〉。
