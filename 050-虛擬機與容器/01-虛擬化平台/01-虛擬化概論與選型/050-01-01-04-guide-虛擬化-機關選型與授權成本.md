# 機關選型與授權成本

> [!warning] 未實機驗證
> ★★★ 本篇談的是**採購方法與成本結構**，不是可以在終端機驗證的操作。
> 篇中出現的授權模式、計價單位、產品分層都是**結構性描述**，
> 各家原廠隨時可能調整。**動筆寫規格書前，一定要向原廠或經銷重新確認當期條款。**

> [!danger] ★★★★★ 本篇一律不寫金額、不寫版本號、不寫「免費版限幾顆 CPU」
> 理由有三：
> 1. **會過期。** 虛擬化的授權模式近年變動極快，任何寫死的數字都會害人。
> 2. **會誤導採購。** 機關看到手冊上的數字就當預算依據，決標時對不起來。
> 3. **會踩到底價揭露的紅線。** 手冊不該替特定廠商背書價格。
>
> ★★★★★ **一切以採購當時原廠報價與授權條款為準。**
> 本篇教你的是「**怎麼把報價填進正確的格子裡算出總帳**」，不是「答案是多少錢」。

> [!abstract] 這篇你會學到
> - ★★★★★ **採購前必問的十個問題** —— 問完這十題，選型答案通常自己浮出來
> - ★★★★★ 六種**授權模式的結構差異**：永久／訂閱／每 socket／每核心／每 VM／免費版
>   —— 以及每一種在機關預算制度下的真實痛點
> - ★★★★ **Broadcom 併購 VMware 之後**，機關會遇到什麼、有哪四個因應選項
> - ★★★★★ 規格書怎麼寫**才不綁標**：功能需求語句庫、等效品條款、可以照抄的段落
> - ★★★★★ 一份**完整的五年 TCO 試算**：3 台實體主機、30 台 VM，
>   **授權／硬體／維護／人力**四類成本全部算過一輪，三個方案並列比較
> - ★★★★ 開源方案的**隱性成本**：學習曲線、沒有原廠時誰負責、稽核時怎麼交代
> - ★★★★ 採購階段最常見的十五種踩雷，以及事前怎麼閃掉

## 觀念說明

### ★★★★★ 一、虛擬化選型不是技術題，是採購題

技術人員最常犯的錯，是把選型會議開成技術辯論會：比效能、比功能、比誰的 CLI 好寫。

★★★★★ **但決定成敗的從來不是這些。** 機關的虛擬化平台一旦上線，
會服役五到八年，中間會換人、會改組、會遇到預算刪減、會被稽核。
選型真正要回答的問題是：

| 真正的問題 | 技術辯論會通常不會談到 |
| --- | --- |
| ★★★★★ **五年後這筆錢還付得出來嗎？** | 只比首年報價 |
| ★★★★★ **現在的人力扛得動嗎？換人之後呢？** | 假設「我會就好」 |
| ★★★★ **出事的時候誰負責、幾小時到場？** | 假設「不會出事」 |
| ★★★★ **明年要多 10 台 VM，加得上去嗎？加要多少錢？** | 只算今天的量 |
| ★★★★★ **如果決定不用了，資料搬得走嗎？** | 完全不談退場 |
| ★★★★ **稽核問「為什麼選這家」，答得出來嗎？** | 「因為比較好用」 |

> [!note] ★★★★★ 一句話總結
> **選型的產出不是「選了哪一套」，而是一份「說得出理由、算得出總帳、
> 寫得出退場方案」的評估報告。** 前者是結論，後者才是機關要的東西。

### ★★★★★ 二、採購前必問的十個問題

這十題請照順序問，**而且要找使用單位一起問**，不要關在資訊室自己想。
每一題後面都標了「答案會怎麼改變選型」。

#### Q1 ★★★★★ 現有人力會什麼？下一個接手的人會什麼？

這是**第一題，也是最容易被跳過的一題**。

| 現況 | 對選型的影響 |
| --- | --- |
| 只有一位同仁懂 Linux，且是唯一維運人力 | ★★★★★ **開源自建的風險極高** —— 人一走系統就變黑盒子 |
| 團隊三人以上，都有 Linux 基礎 | ★★★★ Proxmox VE 自建可行 |
| 團隊只熟 Windows GUI | ★★★★ 需要編列教育訓練，或選 GUI 完整的方案 |
| 維運實際上外包給廠商 | ★★★★★ **要問廠商會什麼**，而不是問自己會什麼 |

> [!danger] ★★★★★ 最危險的組合：一個人 + 一套沒人懂的開源系統
> 這在機關極常見：某位很強的同仁自己架了一套，跑得很好，
> 然後他調職了。接手的人不敢動、不敢升級、不敢重開機，
> 系統就這樣「凍」在那裡，直到某天硬碟壞掉。
> ★★★★★ **選型時就要問：「這套東西，交接文件寫得出來嗎？」**
> 交接的方法見 [[100-02-12-guide-維運-交接與新人上手]]。

#### Q2 ★★★★★ 要不要 HA？可接受的停機時間是多久？

★★★★★ **這一題決定了預算級距**，因為 HA 幾乎會讓硬體數量翻倍。

問使用單位這句話：**「這個系統中午壞掉，下班前修好，可以嗎？」**

| 回答 | 需求層級 | 架構意涵 |
| --- | --- | --- |
| 「可以，隔天也行」 | ★★ 無 HA 需求 | 單節點 + 每日備份即可 |
| 「當天要好」 | ★★★ 快速復原 | 單節點 + 備份 + **備品主機**（冷備） |
| 「一小時內」 | ★★★★ 需要 HA | 至少三節點叢集 + 共用儲存 |
| 「不能停」 | ★★★★★ 需要 HA + 異地 | 叢集 + 異地備援，預算級距完全不同 |

> [!warning] ★★★★ 使用單位一定會說「不能停」
> 因為不用他們付錢。★★★★★ **正確的問法是把成本一起講**：
> 「做到一小時內復原，硬體要三台而不是一台，五年多出來的錢大概是這個量級，
> 這筆錢要從哪個科目出？」—— 通常問完，答案就變成「當天好就可以」。

#### Q3 ★★★★★ 備份怎麼做？備份放哪裡？多久驗一次還原？

★★★★★ **沒有備份方案的虛擬化選型是假的。**

要問到具體答案的四件事：

1. **備份目的地**：另一台機器？NAS？磁帶？雲端物件儲存？
2. ★★★★★ **異地副本**：備份跟 VM 在同一台機器上，等於沒備份
3. **保留策略**：日備留幾份、週備幾份、月備幾份（決定備份空間容量）
4. ★★★★★ **還原演練頻率**：**沒有還原過的備份，不能算備份**

| 平台 | 備份的採購意涵 |
| --- | --- |
| Proxmox VE | ★★★★ 內建 `vzdump` 排程備份；要去重複與增量則另建 Proxmox Backup Server（開源，但**要一台機器**） |
| VMware | ★★★★ 單機無排程備份，**幾乎一定要另外採購第三方備份軟體**，這筆錢要算進去 |
| KVM 自建 | ★★★ 要自己寫腳本或選開源備份工具，**工時要算進去** |

★★★★ 詳細做法見 [[050-01-03-06-svc-PVE-備份與還原]]。

#### Q4 ★★★★ 五年後怎麼擴？擴的時候要再花多少錢？

★★★★★ **關鍵在「擴充的邊際成本」，不是「現在的總價」。**

要向廠商問清楚的三句話：

- 「**再加一台主機**，授權要另外買嗎？怎麼算？」
- 「**VM 從 30 台變 60 台**，授權費用會變嗎？」
- 「**CPU 換成核心數更多的型號**，授權費會不會跳一級？」

> [!danger] ★★★★★ 最痛的陷阱：授權跟著核心數走
> 若授權是「每核心」計價，那麼三年後汰換硬體、換上核心數更多的新 CPU，
> **軟體授權費會自己漲**，而你什麼功能都沒多買到。
> ★★★★★ 這在編列汰換預算時極容易漏掉，一漏就是決標後才發現錢不夠。

#### Q5 ★★★★★ 出事找誰？幾小時內到場？合約怎麼寫？

要寫進契約的是**可驗收的數字**，不是形容詞：

| 該寫的 | 不該寫的 |
| --- | --- |
| ★★★★★ 「**上班日 4 小時內到場**」 | 「提供即時支援」 |
| ★★★★ 「7×24 電話支援，30 分鐘回電」 | 「全天候服務」 |
| ★★★★★ 「**未達成之罰則：每逾一小時扣履約保證金 X%**」 | 沒有罰則 |
| ★★★★ 「支援語言為**繁體中文**」 | 沒寫（結果只有英文原廠信箱） |

★★★★★ **開源方案的這一題最難答**，因為沒有原廠。三個可行答案：

1. 買**商業訂閱**（例如 Proxmox 的訂閱），有正式支援窗口
2. 找**本地系統整合商**簽維護合約，由他們負責
3. ★★★★ **自己承擔**，但要在風險評估表上寫明白，並經主管核章

#### Q6 ★★★★ 有沒有既有環境要整合或遷移？

| 既有環境 | 要多問的事 |
| --- | --- |
| 已有 ESXi + vCenter | ★★★★★ 遷移工時、Windows VM 的驅動處理、授權能不能沿用 |
| 已有 Hyper-V | ★★★★ 磁碟格式轉換（VHDX）、AD 整合方式 |
| 已有備份軟體 | ★★★★★ **新平台在該備份軟體的支援清單上嗎？** |
| 已有監控系統 | ★★★ 新平台有沒有對應的監控介面（SNMP／API／exporter） |

★★★★★ **遷移成本是選型時最常被漏算的一項**，估法見
[[050-01-01-03-ref-虛擬化-五平台橫向對照]] 的「換平台的遷移成本」。

#### Q7 ★★★★ 有沒有法規、資安或稽核上的硬性要求？

- ★★★★★ **資料落地**：能不能放雲端？決定了要不要地端自建
- ★★★★ **政府組態基準（TWGCB）**：作業系統要符合基準，平台要能配合
- ★★★★ **稽核軌跡**：誰在什麼時候開關了哪台 VM，查得到嗎？
- ★★★★ **權限分離**：可以做到「廠商只能碰自己那兩台 VM」嗎？
  → [[050-01-03-08-guide-PVE-使用者權限與API]]
- ★★★ **弱點掃描與修補**：平台本身多久更新一次？EOL 什麼時候？

#### Q8 ★★★★ 機房條件撐得住嗎？

★★★★★ **新主機不是插上去就會動。** 要先確認：

| 項目 | 要確認的事 | 對應章節 |
| --- | --- | --- |
| 電力 ★★★★ | 迴路容量、插座型式、單一迴路上的總負載 | [[040-02-04-guide-機房-電力系統與配電]] |
| UPS ★★★★★ | **加了新主機之後，UPS 還撐得住原本的備援時間嗎？** | [[040-02-05-guide-機房-UPS選型與容量計算]] |
| 空調 ★★★★ | 新增的發熱量，冷氣噸數夠嗎？ | [[040-02-02-guide-機房-空調系統與溫溼度監控]] |
| 機櫃 ★★★ | U 數、深度、承重、前後留空 | [[040-02-03-guide-機房-機櫃規劃與設備上架]] |
| 網路埠 ★★★★ | 叢集要獨立網段，交換器埠數與速率夠嗎？ | [[040-01-03-guide-網路設備-VLAN概念與規劃]] |

#### Q9 ★★★ 誰來驗收？驗收標準是什麼？

★★★★ **驗收標準要在招標文件裡就寫好**，不能等到履約才吵。
虛擬化案常見的可驗收項目：

- 建立 N 台 VM 並完成壓力測試，各項服務可正常存取
- ★★★★★ **實際做一次完整還原演練**，並記錄還原耗時
- ★★★★ 拔掉一台主機的電源，驗證 HA 是否在約定時間內把 VM 拉起來
- 交付**中文操作手冊**與**教育訓練**（幾小時、幾個人、含不含錄影）
- 帳號權限交付、密碼變更、原廠帳號移轉給機關

詳見 [[080-01-05-guide-專管-驗收與交付管理]]。

#### Q10 ★★★★★ 如果三年後想換掉，搬得走嗎？

這叫**退場策略（exit strategy）**，機關採購最不願意想、卻最該想的一題。

| 檢查點 | 好的答案 |
| --- | --- |
| 虛擬磁碟格式 ★★★★ | 開放格式（qcow2／raw），或有標準匯出（OVF／OVA） |
| 備份格式 ★★★★★ | **能不能在沒有原平台的情況下讀出來？** |
| 設定與自動化 ★★★ | 有 API／設定檔可匯出，不是只存在 GUI 裡 |
| 授權 ★★★★ | 停止付費後，既有 VM 會不會停止運作 |
| 資料清除 ★★★★★ | 退場時，舊儲存裝置怎麼銷毀或抹除（要寫進契約） |

### ★★★★★ 三、六種授權模式的結構差異

★★★★★ **看報價單之前，先搞懂它在賣什麼。** 同樣一句「一年多少錢」，
底下的計價邏輯完全不同，擴充時的行為也完全不同。

| 模式 | 怎麼算 | 對機關的優點 | ★ 痛點 |
| --- | --- | --- | --- |
| **永久授權（Perpetual）** | 一次買斷使用權 | ★★★★ 一次編列資本門預算，之後只付維護 | ★★★★ 不付維護就沒有更新與資安修補；★★★★★ **近年多家原廠已停售** |
| **訂閱制（Subscription）** | 按年（或多年）付費 | ★★★ 首年門檻低、含支援與更新 | ★★★★★ **變成每年的經常門支出，一旦某年沒編到，服務可能受影響** |
| **每 socket（每顆實體 CPU）** | 主機上有幾顆實體 CPU 就算幾份 | ★★★★ 好算、好稽核；**買核心數多的 CPU 反而划算** | ★★★ 雙路主機成本是單路的兩倍 |
| **每核心（Per-core）** | 主機實體核心總數 ÷ 授權單位，常有「每顆 CPU 最低核心數」下限 | ★★ 小機器便宜 | ★★★★★ **換高核心數 CPU 會自動漲價**；有最低核心數門檻時，小機器反而吃虧 |
| **每 VM／每使用者** | 依虛擬機數量或使用人數 | ★★★ 用多少算多少 | ★★★★ **VM 一多就失控**；「一台 VM」的定義要在合約寫清楚（關機的算不算？範本算不算？） |
| **免費版／社群版** | 不付費 | ★★★★★ 沒有授權支出 | ★★★★★ **功能被閹割的位置往往正是機關最需要的**：叢集、API、備份排程、集中管理 |

> [!danger] ★★★★★ 三個一定要在合約裡問清楚的定義
> 1. **「一顆 CPU」怎麼算？** 實體 socket？還是含 HT 的邏輯核心？
> 2. **「一台 VM」怎麼算？** 關機的算不算？範本算不算？快照算不算？
>    ★★★★★ 這一條在稽核時最容易被抓。
> 3. **授權到期會怎樣？** 停止更新？跳提示？還是 **VM 直接停機**？
>    ★★★★★ 這一條決定最壞情況下服務會不會中斷，**一定要白紙黑字**。

#### ★★★★ 免費版的閹割點通常在哪裡

★★★★★ **廠商不會把免費版做成殘廢，而是精準地拿掉「企業才需要的那幾項」**：

| 常被拿掉的功能 | 為什麼機關會痛 |
| --- | --- |
| ★★★★★ 集中管理台 | 三台主機要開三個網頁分別管，人為錯誤大增 |
| ★★★★★ 排程備份 API | 無法自動化備份，只能手動，遲早忘記 |
| ★★★★ 線上遷移 | 主機要維護就得停機，維護時窗被迫排在半夜 |
| ★★★★ 叢集與 HA | 完全無法做高可用 |
| ★★★★ 技術支援 | 出事沒人接電話 |
| ★★★ 進階儲存功能 | 無法做去重複、快照排程 |

> [!tip] ★★★★★ 判斷免費版夠不夠用的一句話
> **「把這些被拿掉的功能，用人工做一遍，要花多少工時？」**
> 把那個工時折算成人力成本，加回免費版的 TCO 裡 —— 這才是公平比較。

#### ★★★★ 機關預算制度下的特殊痛點

| 痛點 | 說明 | 因應 |
| --- | --- | --- |
| ★★★★★ **資本門 vs 經常門** | 永久授權多列資本門，訂閱多列經常門，兩者預算來源與核銷程序不同 | 選型前先跟主計確認科目，避免決標後無法核銷 |
| ★★★★★ **年度預算刪減** | 訂閱制若某年被刪，會直接影響服務 | 優先選「過期不停機」的方案；或簽多年約鎖定 |
| ★★★★ **決標延誤造成空窗** | 續約沒接上，中間空幾個月 | 契約寫明**回溯生效**條款，或提前一季啟動採購 |
| ★★★★ **匯率與報價效期** | 國外原廠報價常有效期與匯率條款 | 在招標文件要求**報價效期涵蓋預定決標日** |
| ★★★ **年度採購金額門檻** | 金額跨過門檻就要改用不同招標方式，時程差很多 | 早期就估準總額，別卡在門檻邊緣 |

### ★★★★ 四、Broadcom 併購 VMware 之後：機關會遇到什麼

> [!warning] ★★★★★ 本節只描述「結構性變化的類型」，不寫任何具體方案名稱與價格
> 授權方案的名稱與內容變動極快。**請以你手上那份當期報價單與授權條款為準。**

#### ★★★★ 機關實際會遇到的四種變化

| 變化類型 | 對機關的實際衝擊 |
| --- | --- |
| ★★★★★ **產品組合重整** | 原本單買的元件被併進套裝，**買不到「只要我需要的那一項」**，總價被迫拉高 |
| ★★★★★ **永久授權轉訂閱** | 資本門一次編列變成每年經常門，**預算科目與長期財務規劃都要改** |
| ★★★★ **計價單位調整** | 由 socket 轉向核心數計價時，同一台主機的授權數量可能改變 |
| ★★★★ **通路與續約流程改變** | 原本熟悉的經銷窗口可能改變，續約前置時間拉長 |

#### ★★★★★ 機關的四個因應選項（誠實版）

**選項 A：續留 VMware，接受新條款** ★★★

- 適合：既有環境龐大、與 vCenter 生態綁定深、遷移風險高於成本壓力
- 要做的事：★★★★ **提前一年**啟動續約評估；把新的年度費用寫進中程財務規劃；
  要求原廠或經銷提供**未來三年的費用試算**（寫進採購文件當附件）
- 風險：★★★★ 續約條件逐年變動，機關議價能力低

**選項 B：部分遷出，關鍵系統續留** ★★★★

- 適合：多數機關的**務實解**
- 做法：把**測試、開發、內部工具**類的 VM 先遷到 Proxmox VE 或 KVM，
  只留下真正需要 vSphere 進階功能的核心系統
- 好處：★★★★★ **同時降低授權數量與供應商鎖定**，而且**先在低風險系統上練兵**
- 風險：★★★ 要維護兩套平台，人力負擔增加（這筆工時要算進 TCO）

**選項 C：全面遷移到開源平台** ★★★★

- 適合：環境規模中等、有 Linux 人力、可接受一次性的遷移工時
- 做法：見 [[050-01-01-03-ref-虛擬化-五平台橫向對照]] 的遷移成本評估
- 風險：★★★★★ **一次性遷移工時被嚴重低估是常態**，
  尤其是 Windows VM 的驅動處理與備份軟體重新整合

**選項 D：部分或全面上雲** ★★★

- 適合：法規允許資料上雲、且流量／使用量可預測
- 風險：★★★★ **雲端費用是經常門且會隨用量成長**，
  ★★★★★ 出口流量費（egress）最常被漏算 → [[120-01-03-guide-雲端-雲端成本與治理]]

> [!tip] ★★★★★ 不論選哪一個，現在就該做的三件事
> 1. ★★★★★ **盤點**：確實知道自己有幾台主機、幾顆實體 CPU、幾個核心、幾台 VM。
>    ★★★★ 沒有這份清單，你連報價單對不對都看不出來。
> 2. ★★★★ **建立第二平台的基本能力**：至少讓團隊有一台 Proxmox VE 練習環境，
>    → [[050-01-03-13-guide-PVE-建立練習環境]]
> 3. ★★★★★ **確認備份能不能跨平台還原**。這是 exit strategy 的地基。

### ★★★★ 五、開源方案的隱性成本（誠實版）

★★★★★ **「開源＝免費」是選型會議上最貴的一句話。**
開源省下的是**授權費**，但把成本轉移到**人力、時間與風險**上。

| 隱性成本 | 具體長什麼樣 | 怎麼估 |
| --- | --- | --- |
| ★★★★★ **學習曲線** | 團隊要從零學會安裝、備份、叢集、故障排除 | 折算**人天**：以「每人 5～10 人天」為起點，含教育訓練與練習環境 |
| ★★★★★ **沒有原廠時誰負責** | 半夜掛掉，沒有人可以打電話 | 要嘛買商業訂閱、要嘛簽 SI 維護約、要嘛寫進風險評估自行承擔 |
| ★★★★ **稽核怎麼交代** | 稽核問「這套軟體的技術支援來源」 | ★★★★ 事前備好：訂閱合約、SI 維護合約、或**經核章的風險接受文件** |
| ★★★★ **文件與交接** | 開源的設定散在很多地方，離職就失傳 | 把「交接文件」列為**建置工作的一部分**，估工時 |
| ★★★★ **升級維護** | 大版本升級要自己讀 release note、自己排維護時窗 | 每年估固定工時 → [[050-01-03-11-svc-PVE-升級與維護]] |
| ★★★ **相容性驗證** | 備份軟體、監控、防毒是否支援該平台 | 採購前就要驗，別等上線才發現 |
| ★★★ **社群求助的時間成本** | 論壇問問題，可能沒人回 | 對關鍵系統，這個不確定性本身就是成本 |

> [!note] ★★★★★ 開源方案的正確論述方式
> 不要說「開源不用錢」。要說：
> **「這個方案把授權支出換成人力投入，五年下來總持有成本較低，
> 但前提是機關要編列 X 人天的教育訓練，並簽訂維護支援合約來承接原廠角色。」**
> ★★★★★ 這種說法在簽核與稽核時站得住腳，前一種站不住。

> [!warning] ★★★★ 反過來說，商業方案也有隱性成本
> - ★★★★ **供應商鎖定**：資料格式與管理工具綁死，離開的代價逐年變高
> - ★★★★ **續約議價能力低**：東西已經上線了，你其實不太能說不
> - ★★★ **功能綑綁**：為了要那一項，被迫買整包
> - ★★★ **硬體相容清單限制**：舊機器不能再利用，等於逼你多買硬體

## 安裝或基礎操作

### ★★★★★ 步驟一：盤點現況（沒有這一步，後面全是猜的）

★★★★★ **報價單上的授權數量對不對，取決於你的盤點準不準。**
以下指令在既有 Linux 主機（含 PVE 節點）上可直接執行。

#### 查實體 CPU 顆數（socket）與核心數 ★★★★★

```bash
lscpu | grep -E 'Socket|Core|Thread|Model name|CPU\(s\)'
```

預期輸出（範例，數字依機器而異）：

```text
CPU(s):                          32
Thread(s) per core:              2
Core(s) per socket:              8
Socket(s):                       2
Model name:                      Intel(R) Xeon(R) CPU E5-2620 v4 @ 2.10GHz
```

★★★★★ **這四個數字的關係一定要弄清楚，因為授權就是照它們算的**：

| 名詞 | 上例的值 | 授權上代表什麼 |
| --- | --- | --- |
| Socket(s) | 2 | ★★★★★ **每 socket 授權要買 2 份** |
| Core(s) per socket | 8 | 每顆 CPU 有 8 個實體核心 |
| 實體核心總數 | 2 × 8 = **16** | ★★★★★ **每核心授權的計算基礎** |
| CPU(s)（邏輯處理器） | 32 | ★★★★ 含超執行緒；**通常不是授權計算基礎，但務必跟廠商確認** |

> [!danger] ★★★★★ 最常見的算錯：把邏輯處理器當成核心數
> 上例若誤用 32 去算「每核心授權」，會**多買一倍**。
> 反過來若原廠條款真的是按邏輯處理器算，你少買一半，稽核時就是違規。
> ★★★★★ **一定要在報價單上白紙黑字寫出「以實體核心數 16 計」這種句子。**

#### 查主機型號、序號與記憶體插槽 ★★★★

```bash
sudo dmidecode -t system -t memory | grep -E 'Manufacturer|Product Name|Serial Number|Size:|Number Of Devices'
```

★★★★ 這份資料同時是**財產盤點**與**保固查詢**的依據，
做法見 [[040-02-11-guide-機房-資訊設備盤點]]。

#### 查現有 VM 數量與資源總量（Proxmox VE） ★★★★

```bash
qm list
```

預期輸出：

```text
      VMID NAME                 STATUS     MEM(MB)    BOOTDISK(GB) PID
       101 web01                running        4096          50    1234
       102 db01                 running        8192         200    1298
       103 test-template        stopped        2048          32       0
```

★★★★★ **注意 `stopped` 的那一台。** 在「每 VM 計價」的方案裡，
關機的 VM 算不算一台，是合約要寫清楚的事。

#### 把盤點結果整理成一張表 ★★★★★

★★★★★ **這張表是後面所有計算與報價比對的唯一基準**，請存成檔案並附進採購文件。

| 主機 | 型號 | 保固到期 | Socket | 每 socket 核心 | 實體核心總數 | 記憶體 | 目前 VM 數 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| host-01 | （填） | （填） | 2 | 8 | 16 | 128 GB | 12 |
| host-02 | （填） | （填） | 2 | 8 | 16 | 128 GB | 11 |
| host-03 | （填） | （填） | 2 | 8 | 16 | 96 GB | 7 |
| **合計** | — | — | **6** | — | **48** | **352 GB** | **30** |

### ★★★★ 步驟二：把需求分級，不要全部都當最高級

★★★★★ **把 30 台 VM 全部照「不能停」的標準做，預算一定爆掉。**
正確做法是分級，然後**只為最高級付高價**。

| 等級 | 定義 | 佔比（典型） | 架構 |
| --- | --- | --- | --- |
| ★★★★★ **A 級：核心** | 對外服務、全機關使用、停了會上新聞 | 10～20% | HA 叢集 + 每日備份 + 異地副本 |
| ★★★★ **B 級：重要** | 內部系統，停半天可接受 | 30～40% | 叢集內但不設 HA，或單節點 + 快速復原 |
| ★★★ **C 級：一般** | 測試、開發、工具機 | 40～60% | 單節點，備份頻率可放寬 |

> [!tip] ★★★★★ 分級表要請使用單位簽名
> 分級表上要有**使用單位主管的簽核**。
> 這樣事後系統停機時，討論的是「當初約定的等級是 C」，
> 而不是「資訊室為什麼沒做 HA」。★★★★★ 這是保護自己也保護單位的做法。

### ★★★★ 步驟三：建立 TCO 試算表的四個成本欄位

★★★★★ **TCO（Total Cost of Ownership，總持有成本）＝ 五年內所有現金與人力支出的總和。**
一定要包含這四類，少任何一類都是假的：

| 類別 | 包含什麼 | 常被漏掉的 |
| --- | --- | --- |
| **① 授權** ★★★★★ | 平台授權、管理台授權、備份軟體授權、客體 OS 授權 | ★★★★★ **客體 Windows Server 授權**、備份軟體授權 |
| **② 硬體** ★★★★ | 伺服器、儲存、網路卡、交換器埠、機櫃、UPS 擴充 | ★★★★ **備份目的地的儲存空間**、第二條網路 |
| **③ 維護** ★★★★ | 硬體保固延長、軟體訂閱續約、SI 維護合約 | ★★★★★ **第 4、5 年的保固延長費用**（通常比前三年貴） |
| **④ 人力** ★★★★★ | 建置工時、教育訓練、每年例行維運工時、遷移工時 | ★★★★★ **學習曲線**與**交接文件撰寫** |

#### ★★★★ 試算表該長什麼樣（欄位定義）

```text

┌──────────────┬────┬────┬────┬────┬────┬──────┐
│ 項目          │ Y1 │ Y2 │ Y3 │ Y4 │ Y5 │ 五年計 │
├──────────────┼────┼────┼────┼────┼────┼──────┤
│ ① 平台授權     │    │    │    │    │    │      │
│ ① 備份軟體     │    │    │    │    │    │      │
│ ① 客體 OS 授權 │    │    │    │    │    │      │
│ ② 伺服器       │    │    │    │    │    │      │
│ ② 備份儲存     │    │    │    │    │    │      │
│ ② 網路／機櫃   │    │    │    │    │    │      │
│ ③ 硬體保固     │    │    │    │    │    │      │
│ ③ 軟體訂閱     │    │    │    │    │    │      │
│ ③ SI 維護合約  │    │    │    │    │    │      │
│ ④ 建置工時     │    │    │    │    │    │      │
```

> 2. **人力欄位填「人天」，另欄折算金額。** 這樣換算基準改變時不必重算。
> 3. ★★★★★ **每一格都要註明來源**（報價單編號／估算依據）。
>    稽核問「這個數字怎麼來的」，你要答得出來。

## 進階應用

### ★★★★★ 一、規格書怎麼寫才不綁標

★★★★★ **綁標的定義很簡單：規格寫得只有一家做得到。**
最常見的三種綁標寫法，以及正確改法：

| ❌ 綁標寫法 | 為什麼綁標 | ✅ 改成 |
| --- | --- | --- |
| 「應為 VMware vSphere 8.0 以上」 | ★★★★★ **直接寫產品名與版本** | 「應提供 Type 1 型虛擬化平台，支援多節點叢集管理」 |
| 「應支援 vMotion」 | ★★★★ **vMotion 是註冊商標**，只有一家有 | 「應支援虛擬機於節點間**不中斷服務**之線上遷移」 |
| 「應支援 vSAN」 | ★★★★ 同上 | 「應支援以節點本機磁碟組成之**分散式共用儲存**，具備資料多副本保護」 |
| 「應提供 vCenter 集中管理」 | ★★★★ 同上 | 「應提供**單一集中管理介面**，可同時管理所有節點與虛擬機」 |
| 「應支援 DRS 自動負載平衡」 | ★★★★ 同上 | 「宜具備依節點負載自動調整虛擬機配置之機制」（★★★ 用「宜」不用「應」） |
| 「CPU 應為 Intel Xeon Gold 6338」 | ★★★★★ **指定型號** | 「CPU 每顆實體核心數不少於 X 核，通過 SPEC CPU 基準測試分數不低於 Y」 |
| 「應使用 Broadcom 網卡」 | ★★★★★ 指定品牌 | 「網路介面應為 10GbE 以上，並於平台之硬體相容清單內」 |

#### ★★★★★ 不綁標的三個原則

1. ★★★★★ **寫「功能」不寫「產品」。**
   問自己：「這句話換一家廠商能不能達成？」不能，就是綁標。
2. ★★★★★ **寫「可量測的門檻」不寫「品牌」。**
   例：「支援至少 3 節點叢集」「單一 VM 可配置至少 32 vCPU」「還原 100 GB 虛擬機於 60 分鐘內完成」。
3. ★★★★ **區分「應」與「宜」。**
   「應」是必要條件（不符合就不合格），「宜」是加分項目。
   ★★★★★ **把非必要的功能寫成「應」，是綁標最常見的無心之過。**

#### ★★★★ 等效品條款怎麼寫

若真的**必須**提到特定產品（例如既有環境相容性需求），要加等效條款：

> ★★★★★ 可直接引用的段落：
>
> 「本規格所列之產品名稱、型號或商標，僅為表達功能與品質水準之參考，
> 投標廠商得提出**同等品或更優之替代方案**。
> 投標時應檢附**同等品規格對照表**，逐項說明所提方案如何滿足本規格各項功能需求，
> 並由本機關就功能符合性進行審查。」

> [!warning] ★★★★ 等效品條款不是萬靈丹
> 加了等效條款，但功能需求本身仍只有一家做得到，**還是綁標**。
> ★★★★★ 等效條款解決的是「品名」問題，不是「功能設計」問題。

#### ★★★★★ 可以照抄的功能需求語句庫

```text
【平台基本】
1. 應為 Type 1（裸機型）虛擬化平台，直接安裝於實體伺服器，無須依附桌面作業系統。
2. 應提供繁體中文或英文之網頁管理介面，無須另行採購管理伺服器授權。
3. 應支援 x86-64 架構之 Windows Server 與主流 Linux 發行版作為客體作業系統。

【叢集與可用性】
4. 應支援至少 3 個節點組成之叢集，並提供單一管理介面。
5. 應支援虛擬機於節點間之線上遷移，遷移期間服務不中斷。
6. 應具備節點故障時自動於其餘節點重新啟動受影響虛擬機之機制，
   並可於契約約定之時間內完成（本案為 __ 分鐘）。

【儲存】
7. 應支援 NFS、iSCSI 等標準共用儲存協定。
8. 宜支援以節點本機磁碟組成分散式共用儲存，具資料多副本保護能力。
9. 應支援虛擬機快照，且快照建立與還原可經由管理介面操作。

【備份】
10. 應提供或可整合排程備份機制，支援全量與增量備份。
11. 備份檔案應可於**未安裝原管理平台**之環境下讀取或還原（退場保障）。
12. 應可於管理介面設定備份保留策略（日／週／月份數）。

【安全與稽核】
13. 應提供角色式存取控制（RBAC），可依使用者／群組指派不同資源之操作權限。
14. 應可介接 LDAP 或 Active Directory 進行帳號驗證。
15. 應支援管理者帳號之雙因素驗證。
16. 應保留操作稽核日誌，記錄操作者、時間、對象與動作，且可匯出。

【自動化與整合】
17. 應提供 REST API 或命令列介面，可供自動化建立、啟停與備份虛擬機。
18. 應可輸出主機與虛擬機之效能指標，供既有監控系統擷取。

【支援與交付】
19. 得標廠商應提供 __ 小時之教育訓練，並交付繁體中文操作手冊。
20. 應提供上班日 __ 小時內到場之技術支援，逾時罰則依契約第 __ 條辦理。
21. 應於驗收時實際執行一次完整還原演練，並記錄還原耗時。
22. 應交付完整之架構文件、IP 與帳號清冊，並完成管理密碼移轉。
```

> [!tip] ★★★★ 用法
> 把上面這 22 條當**檢核清單**，逐條問「本案需不需要」。
> 需要的留下並填空，不需要的刪掉 —— ★★★★★ **不要整包貼上去**，
> 用不到的條款會限制投標廠商數量，反而變成另一種綁標。

### ★★★★ 二、三個方案的結構性比較（不含金額）

### 步驟 1：走完十個問題 ★★★★★


### 步驟 3：算硬體數量（② 硬體） ★★★★

#### 先算資源總需求

```text
現有 30 台 VM 的資源加總（實際盤點值）：
  vCPU 總和  ：  92 vCPU
  記憶體總和 ： 248 GB
  磁碟總和   ： 6.4 TB

五年成長預估（30 → 45 台，約 +50%）：
  vCPU       ：  92 × 1.5 ≈ 138 vCPU
  記憶體     ： 248 × 1.5 = 372 GB
  磁碟       ： 6.4 × 1.5 ≈ 9.6 TB
```

#### 再算節點數（★★★★★ 關鍵：要留 N+1 餘裕）

```text
【記憶體】★★★★★ 記憶體幾乎不能超配，這通常是決定節點數的瓶頸
  需求 372 GB，若每節點 256 GB：
    372 ÷ 256 = 1.45 → 需 2 台
    ★★★★★ HA 要能承受「壞一台」，故 +1 → 需 3 台
    驗算：壞掉一台後剩 2 × 256 = 512 GB ≥ 372 GB ✓

【vCPU】★★★★ CPU 可超配，常見上限 4:1
  需求 138 vCPU，每節點 16 實體核（32 邏輯）：
    3 台 = 48 實體核，138 ÷ 48 ≈ 2.9:1 ✓ 在合理範圍
    壞一台：2 台 = 32 實體核，138 ÷ 32 ≈ 4.3:1
    ★★★★ 略高於建議值，但短期降級運轉可接受（要寫進報告）

【磁碟】★★★★ 分散式儲存要算副本數
  需求 9.6 TB，若採 3 副本：9.6 × 3 = 28.8 TB
    再留 30% 成長與重建空間：28.8 ÷ 0.7 ≈ 41 TB 原始容量
    3 台平均分攤：每台約 14 TB

【備份空間】★★★★★ 最常被漏算的一項
  日備 7 份 + 週備 4 份 + 月備 3 份，
  以去重複後約為來源 1.5～2.5 倍估算：9.6 × 2 ≈ 20 TB
  ★★★★★ 異地副本再一份 → 另需 20 TB（放在不同棟或不同機房）
```

#### 硬體採購清單（數量，不含金額）

| 項目 | 數量 | 備註 |
| --- | --- | --- |
| 伺服器（2 socket、256 GB RAM、14 TB 可用） | 3 | ★★★★ 三台**同型號**，避免叢集內效能不一致 |
| 10GbE 網路卡（雙埠） | 3 | ★★★★★ 叢集／儲存流量要與管理流量分離 |
| 交換器埠（10GbE） | 6 | 現有交換器餘 8 埠，足夠 |
| 備份主機（20 TB） | 1 | 放在同機房 |
| 異地備份儲存（20 TB） | 1 | ★★★★★ 放在不同棟；本案為必要項 |
| 機櫃 U 數 | 8U | 現有機櫃餘裕足夠 |

## 安全性注意事項

### ★★★★★ 一、授權合規本身就是資安與稽核議題

★★★★★ **授權不足在稽核上等同違規使用軟體。** 三個實務要點：

1. ★★★★★ **保存授權憑證與計算說明**：報價單、授權書、經銷商出具的計算說明，
   全部歸檔，並與財產清冊對應 → [[100-02-13-guide-維運-資產與授權管理]]
2. ★★★★ **建立授權盤點的例行作業**：每年至少一次，核對
   「實際 socket／核心／VM 數」是否仍在授權範圍內
3. ★★★★★ **擴充前先查授權**：新增一台主機、換一顆核心數更多的 CPU，
   都可能讓授權變不足。**先確認再動手。**

### ★★★★ 二、採購階段就要把資安需求寫進去

事後補資安永遠比較貴。這些要在規格書就寫：

| 需求 | 寫法 |
| --- | --- |
| ★★★★★ 管理介面存取控制 | 「管理介面應可限制來源 IP 網段，且不得直接對網際網路開放」 |
| ★★★★ 雙因素驗證 | 「管理者帳號應支援雙因素驗證」 |
| ★★★★ 權限分離 | 「應提供 RBAC，可指派使用者僅能操作特定虛擬機」 |
| ★★★★ 稽核日誌 | 「操作日誌應記錄操作者、時間、對象、動作，保存至少 __ 個月且可匯出」 |
| ★★★★ 漏洞修補 | 「原廠或社群應提供資安更新，並說明支援終止（EOL）時程」 |
| ★★★ 傳輸加密 | 「管理介面與遷移流量應支援加密傳輸」 |

### ★★★★★ 三、管理介面是整個環境的單一失效點

★★★★★ **拿到虛擬化管理介面的人，等於拿到裡面所有 VM。**
選型時就要確認平台具備：獨立管理網段、來源 IP 限制、雙因素驗證、
完整稽核日誌、以及**與 AD／LDAP 整合但可獨立保留一組緊急本機帳號**。

> [!danger] ★★★★★ 緊急本機帳號的兩難
> 全部帳號都接 AD，AD 掛掉時你進不去虛擬化平台 ——
> 而 AD 網域控制站很可能就是跑在這個平台上的 VM。
> ★★★★★ **一定要保留至少一組不依賴 AD 的本機管理帳號，
> 密碼封存於保險櫃或密碼保管機制，並列入交接清單。**

### ★★★★ 四、退場與汰換時的資料清除

★★★★★ 舊主機與舊儲存要退場時，上面還有 VM 的完整資料。契約要寫：

- ★★★★★ **儲存裝置的抹除或銷毀方式**（覆寫標準／實體銷毀／由機關留存）
- ★★★★ **銷毀證明**：由廠商出具，或機關人員現場監毀並拍照存證
- ★★★★ **含機敏資料的硬碟不隨機器退還租賃商**（若為租賃）
- ★★★ 備份媒體（磁帶、外接硬碟）同樣要納入清除範圍

### ★★★★ 五、供應鏈與來源可信度

- ★★★★★ **軟體只從原廠或官方套件庫取得**，不要用來路不明的映像檔
- ★★★★ **驗證下載的完整性**（checksum／GPG 簽章）
- ★★★★ **確認 EOL 時程**：買的版本什麼時候停止資安更新，
  要能撐過設備服役年限，撐不過就要編列升級工時

### ★★★ 六、報價與盤點資料本身是敏感資訊

★★★★ 盤點表含機關的主機型號、序號、IP 與 VM 清單 ——
這是攻擊者最想要的資料。**不要用個人雲端硬碟或即時通訊軟體傳給廠商**，
依機關的公文與資安規定處理。

| CPU socket／核心 ★★★★★ | `lscpu \| grep -E 'Socket\|Core\|Thread'` |
| 主機型號與序號 ★★★★ | `sudo dmidecode -t system` |
| 記憶體配置 ★★★★ | `sudo dmidecode -t memory \| grep -E 'Size\|Number Of Devices'` |
| PVE 虛擬機清單 ★★★★ | `qm list` |
| PVE 容器清單 ★★★ | `pct list` |
| PVE 儲存用量 ★★★ | `pvesm status` |
| 磁碟用量總覽 ★★★ | `df -hT` |

## 練習題

> [!question]- 練習 1：算授權數量 ★★★★★
> 某機關有 4 台主機，`lscpu` 顯示每台：
> `Socket(s): 2`、`Core(s) per socket: 12`、`Thread(s) per core: 2`、`CPU(s): 48`。
> 上面跑 52 台 VM（其中 8 台為關機狀態的範本）。
>
> 請分別算出：(a) 每 socket 計價需要幾份？(b) 每核心計價的核心數是多少？
> (c) 每 VM 計價時，你要先向廠商確認什麼？
>
> ★★★★★ 參考答案：
> **(a) 8 份。** 4 台 × 2 socket = 8。
>
> **(b) 96 核。** 4 台 × 2 socket × 12 核 = 96 個**實體核心**。
> ★★★★★ **不是 4 × 48 = 192** —— 那是含超執行緒的邏輯處理器數，
> 誤用會多買一倍。務必在報價單上寫明「以實體核心數 96 計」。
>
> **(c) 要確認「一台 VM」的定義**：
> 8 台關機的範本算不算？快照算不算？
> 52 台與 44 台的差距是 8 份授權，金額差異可觀。
> ★★★★★ 這個定義要寫進契約，不能只有口頭承諾。
> 見「六種授權模式的結構差異」。

> [!question]- 練習 2：估節點數 ★★★★
> 某案 VM 資源需求：vCPU 總和 120、記憶體總和 300 GB、磁碟 5 TB。
> 需要 HA（可承受一台節點故障）。候選機型為 2 socket × 16 核、
> 記憶體 256 GB、可用磁碟 12 TB。分散式儲存採 3 副本。
>
> 請算出：需要幾個節點？儲存夠不夠？
>
> ★★★★ 參考答案：
> **記憶體（★★★★★ 決定性條件）**：
> 300 ÷ 256 = 1.17 → 2 台；HA 要能承受壞一台 → **3 台**。
> 驗算：壞一台後 2 × 256 = 512 GB ≥ 300 GB ✓
>
> **vCPU**：3 台 = 96 實體核，120 ÷ 96 = 1.25:1，非常寬鬆 ✓
> 壞一台：120 ÷ 64 ≈ 1.9:1，仍安全 ✓
>
> **儲存**：需求 5 TB × 3 副本 = 15 TB，再留 30% 成長與重建空間：
> 15 ÷ 0.7 ≈ 21.4 TB。3 台 × 12 TB = 36 TB ✓ 足夠。
> ★★★★★ 但別忘了**另外**還要備份空間（約 5 × 2 = 10 TB）
> 與**異地副本**（再 10 TB），這兩項不能算在叢集儲存裡。

> [!question]- 練習 3：把綁標規格改寫 ★★★★★
> 以下五條規格被政風單位質疑綁標，請逐條改寫：
>
> 1. 「應為 VMware vSphere Enterprise Plus 版本」
> 2. 「應支援 Storage vMotion」
> 3. 「伺服器 CPU 應為 Intel Xeon Silver 4310 或以上」
> 4. 「應提供 Veeam 備份軟體」
> 5. 「應支援 NVIDIA vGPU」
>
> ★★★★★ 參考答案：
> 1. →「應為 Type 1 裸機型虛擬化平台，具備多節點叢集、線上遷移與高可用功能。」
> 2. →「應支援虛擬機**儲存位置**於不同儲存裝置間之線上搬移，搬移期間服務不中斷。」
> 3. →「CPU 每顆實體核心數不少於 12 核，且通過公開之 CPU 效能基準測試，
>    分數不低於 ____（填入依現有設備訂出的合理門檻）。」
>    ★★★★ 只寫核心數不寫型號，並用公開基準分數作為效能門檻。
> 4. →「應提供支援本案虛擬化平台之備份機制，具備排程、全量與增量備份、
>    保留策略設定，且備份檔案可於未安裝原管理平台之環境還原。」
> 5. →「宜支援 GPU 資源分割或直通，供多台虛擬機共用單一 GPU；
>    投標廠商應說明所提方案之授權需求。」
>    ★★★★ 注意這裡用「宜」不用「應」—— 若非必要功能，寫「應」就是不必要的限制。

> [!question]- 練習 4：回應「開源不用錢」 ★★★★★
> 會議上有人說：「用 KVM 就好啦，開源不用錢，可以省下所有授權費。」
> 你負責回應。請寫出三句話，說明為什麼這句話不完整，
> 並提出一個**建設性**的替代方向。
>
> ★★★★★ 參考答案：
> 1. ★★★★★ 「開源省下的是授權費，但把成本轉移到人力上。以本案規模估算，
>    KVM 自建的五年人力投入約 297 人天，比商業方案多出約 193 人天，
>    接近一個人整年的工作量 —— 我們資訊室只有三個人，還有其他業務。」
> 2. ★★★★★ 「另外，稽核會問技術支援來源。沒有原廠、也沒有維護合約的話，
>    我們必須提出經主管核章的風險接受文件，而且系統掛掉時真的沒有人可以打電話。」
> 3. ★★★★ 「還有，客體的 Windows Server 授權不會因為 hypervisor 免費就消失，
>    這 12 台的授權費一毛都不會少。」
>
> ★★★★★ **建設性替代方向**：
> 「建議改為 Proxmox VE + 商業訂閱 + SI 維護合約。
> 授權支出遠低於商業 hypervisor，同時保有正式支援窗口與可稽核的合約，
> 也不會有供應商鎖定 —— 這是在『省錢』與『有人負責』之間的平衡點。」

## 小測驗

Q1.（選擇）某主機 `lscpu` 顯示 `Socket(s): 2`、`Core(s) per socket: 16`、
`Thread(s) per core: 2`、`CPU(s): 64`。若授權以**實體核心數**計價，應算幾核？
(A) 32　(B) 64　(C) 16　(D) 2

Q2.（是非）訂閱制授權過期後，所有虛擬化平台都會讓 VM 停止運作。

Q3. 為什麼「每核心授權」在**硬體汰換**時特別危險？

Q4. 使用單位一律回答「系統不能停」。你該怎麼問，才能問出真實的服務等級需求？

Q5. TCO 四大類成本中，「授權」類最常被漏掉的是哪一項？為什麼會漏？

Q6. 這句規格為什麼可能被認定綁標？請改寫：
「應支援 vSAN 超融合儲存，並提供 vCenter 集中管理平台。」

Q7. 估算節點數時，為什麼**記憶體**通常是決定性條件，而不是 CPU？

Q8.（選擇）以下哪一項**不屬於**開源方案的隱性成本？
(A) 教育訓練人天　(B) 交接文件撰寫工時　(C) 客體 Windows Server 授權
(D) 大版本升級的自行排程工時

Q9. 選型報告中，為什麼「有理由地排除未採用方案」比「說明採用理由」更重要？

Q10. 全機關帳號都接 AD，虛擬化平台也接 AD 驗證。這個設計有什麼致命問題？怎麼解？

> [!question]- 測驗答案
> **Q1. (A) 32。** 2 socket × 16 核 = 32 個實體核心。
> `CPU(s): 64` 是含超執行緒的**邏輯處理器**，不是核心數。
> ★★★★★ 用 64 去算會多買一倍。見「步驟一：盤點現況」。
>
> **Q2. 否。** 各平台差異極大：有的過期只是失去更新與支援、VM 照跑；
> 有的依條款可能失去更新。★★★★★ **這一條必須逐案查合約條款，
> 不能假設**。見「六種授權模式的結構差異」的三個定義。
>
> **Q3. 因為授權費會跟著新硬體自動上漲。** 三年後汰換，
> 換上核心數更多的新 CPU，實體核心總數變多，每核心授權費就變多 ——
> ★★★★★ 但你並沒有多買到任何功能。編列汰換預算時最容易漏掉這筆。
> 見「採購前必問的十個問題」Q4。
>
> **Q4. 把成本一起講。** 問法：「做到一小時內復原，硬體要三台而不是一台，
> 五年會多出這個量級的費用，這筆錢從哪個科目出？」
> ★★★★★ 成本攤開後，答案通常會變成務實的「當天好就可以」。
> 另外要把結論做成**需求分級表請使用單位主管簽核**。見 Q2 與步驟 2。
>
> **Q5. 客體作業系統授權（尤其是 Windows Server）。**
> 因為大家的注意力都在 hypervisor 授權上，忘了 VM 裡面跑的 OS 也要授權，
> 而且虛擬化環境的 Windows Server 授權有專屬計算規則。
> ★★★★★ 要請經銷商出具書面的授權計算說明。見「步驟 4」與速查表。
>
> **Q6. 因為 vSAN 與 vCenter 都是特定廠商的產品／商標名稱**，
> 寫進規格等於只有一家能投。
> 改寫：「應支援以節點本機磁碟組成之分散式共用儲存，具備資料多副本保護；
> 並應提供單一集中管理介面，可同時管理所有節點與虛擬機。」
> ★★★★ 見「規格書怎麼寫才不綁標」。
>
> **Q7. 因為記憶體幾乎不能超配，CPU 可以。**
> vCPU 可以做 2:1 甚至 4:1 的超配，但記憶體一旦不足就會 swap 或開不起來。
> ★★★★★ 所以「記憶體總需求 ÷ 每節點記憶體」通常算出比 CPU 更多的節點數，
> 而節點數要取兩者的較大值，再 +1 做 HA 餘裕。見「步驟 3」。
>
> **Q8. (C) 客體 Windows Server 授權。**
> 它是**明帳**、不是隱性成本，而且**不論用哪個 hypervisor 都要付** ——
> 這正是「開源不用錢」說法的漏洞之一。
> (A)(B)(D) 都是開源方案特有、且最常被低估的人力成本。見「開源方案的隱性成本」。
>
> **Q9. 因為主管與稽核真正會問的是「為什麼不選那個便宜的／那個大廠的」。**
> 只寫採用理由，回答不了這個問題；
> ★★★★★ 寫成「方案 C 不符合第 Q5 項支援需求，故不採用」，
> 才是站得住腳的決策紀錄。見「三個方案的結構性比較」。
>
> **Q10. AD 網域控制站很可能就是跑在這個虛擬化平台上的 VM。**
> AD 一掛，你就登入不了平台，而要修 AD 又必須先登入平台 —— 死結。
> ★★★★★ 解法：**保留至少一組不依賴 AD 的本機管理帳號**，
> 密碼封存於保險櫃或密碼保管機制，並列入交接清單與定期稽核。
> 見「安全性注意事項」第三節。
