# 虛擬化概論與選型 常見故障排除

> [!abstract] 這份手冊和別的排除手冊不一樣
> 本子章是**概論與選型**，沒有太多可以「下一條指令就修好」的操作。
> 所以這份手冊處理的是另一種故障：
> ★★★★★ **選型與規劃階段做錯，半年到三年後會怎麼付出代價。**
>
> - 每個症狀都是**先看到後果，再回頭找當初的決定**。
>   排查步驟的終點常常不是一條指令，而是「一份要重新簽核的文件」。
> - ★★★★★ 這裡的很多問題**沒有技術解**。能做的是「先止血、再補文件、下次別再犯」，
>   排查步驟會明白寫出哪一步已經沒有回頭路。
> - ★★★★ 本手冊**不重講原理**。每個症狀結尾的「原理詳見」就是原文入口。
> - ★★★★★ 動手之前先分辨一件事：
>   **現在是「平台壞了」，還是「當初的規劃已經撐不住現在的負載」？**
>   前者修機器，後者要改配置、改預算、改文件 —— 對後者猛調參數只會把事情拖爛。

## 一頁式檢查卡

★★★★★ 出事時先照這張卡跑一遍。**大部分症狀在這 12 個問題裡就能定位。**

```text
【止血區】現在有服務在停嗎？（先做這五題，不要先查原因）
  1. host 有沒有在 swap？          free -h → Swap 的 used 欄
  2. 儲存池用了幾 %？               儲存頁面／df -h／zpool list
  3. 客體裡的 steal time 多少？      客體內 top → CPU 行的 st 欄位
  4. 有沒有快照留超過七天？          快照清單，看建立日期
  5. 有沒有 VM 正在被 OOM 殺？       dmesg -T | grep -i 'killed process'

【定位區】確定不是立即性事故之後，再問這四題
  6. 這台主機當初是用「平均負載」還是「尖峰負載」估的？
  7. 這台 VM 的磁碟／網卡是 VirtIO 還是全模擬？
  8. 這件事情屬於平台的免費版功能，還是訂閱版功能？
  9. 我們有幾台實體主機？壞一台之後剩下的撐不撐得住？

【文件區】止血完成後，這三題決定會不會再發生一次
 10. 當初的 TCO 表有沒有人力那一欄？金額那一格寫得出來源嗎？
 11. 備份的目的地跟被備份的東西，在不在同一份儲存上？
 12. 上一次真的做過還原演練是什麼時候？花了多久？
```

> [!danger] ★★★★★ 三條「立刻停手」的紅線
> 遇到下面三種狀況，**不要再往下試、不要重開機、不要調參數**，先降載或求援：
> 1. **儲存池已經 100%**，而且已經有 VM 的檔案系統轉唯讀 →
>    再寫任何東西都可能讓損毀擴大。先刪快照／舊備份釋放空間，不要先開機。
> 2. **host 正在大量 swap，多台 VM 同時無回應** →
>    這時候重開機會讓所有 VM 一起以「斷電」的方式重啟。先關掉最不重要的 VM。
> 3. **要對 AD 網域控制站做映像式還原或搬移** →
>    走錯一步會造成 USN rollback，整個網域要收拾很久。走 AD 的標準程序，不要走 VM 程序。

| 症狀（你會看到的） | 最可能的原因 | 先做這件事 | 展開在 |
| --- | --- | --- | --- |
| ★★★★★ 要做 HA／排程備份／集中管理時，介面根本沒有那個選項 | 用的是免費版／社群版，功能被拿掉的正好是這幾項 | 對照該平台的授權層級表 | 症狀一 |
| ★★★★★ 訂閱到期後跳提示、無法更新，主管問「會不會停機」 | 沒在合約裡確認「授權到期後既有 VM 的運作狀態」 | 翻合約找那一條，找不到就問經銷要書面 | 症狀二 |
| ★★★★★ 整台 host 突然變慢，多台 VM 同時無回應 | 三種超配之一失控（CPU／記憶體／I/O），**症狀一樣但解法完全不同** | `free -h`、客體內 `top` 看 `st`、看儲存用量 | 症狀三 |
| ★★★★★ 儲存池顯示滿了，多台 VM 同時變唯讀或當掉 | thin provisioning 超賣 + 快照堆積 | 立刻刪舊快照與舊備份釋放空間 | 症狀四 |
| ★★★★ 決定換平台後，遷移做到一半才發現要重來 | 只算了「搬 VM」，沒算驅動、網路、備份、監控與人 | 停下來，先把六層遷移成本列出來 | 症狀五 |
| ★★★★ 效能不如預期，以為主機不夠力想加硬體 | 磁碟／網卡用了全模擬裝置，沒裝 VirtIO | 看 VM 組態的磁碟控制器與網卡型別 | 症狀六 |
| ★★★★ 在 VM 裡再開 VM 開不起來，或慢到不能用 | VT-x 沒透傳、CPU 型別不是 host、Windows 被 Hyper-V 佔用 | L1 裡 `grep -c -E '(vmx\|svm)' /proc/cpuinfo` | 症狀七 |
| ★★★★ 規格書被質疑綁標、招標流標，或決標後要追加授權預算 | 規格寫了產品名／商標功能名；授權以錯誤單位估算 | 逐條問「換一家廠商能不能達成」 | 症狀八 |
| ★★★★ 一台主機壞掉，全部服務跟著停 —— 但我們有做虛擬化 | 虛擬化不等於高可用；單節點就是單點故障 | 數一下有幾個節點、有沒有共用儲存 | 症狀九 |
| ★★★★ 直通了 GPU／網卡的那台 VM，維護時才發現搬不走 | 直通與 SR-IOV **在設計上**就不能線上遷移 | 盤點所有直通裝置與對應 VM | 症狀十 |
| ★★★ 服務三不五時卡頓，監控圖上記憶體忽高忽低 | ballooning 抽走記憶體，或 KSM 合併頁面造成抖動 | 看 balloon 最小值、`ksmd` 的 CPU 使用率 | 症狀十一 |
| ★★★ 要還原時發現「快照都在，但儲存壞了」 | 把快照當備份，兩者在同一份儲存上 | 確認備份目的地是不是另一份儲存 | 症狀十二 |
| ★★★ 選了開源省授權費，三年後回頭算反而更貴 | TCO 沒算人力、學習曲線、交接文件與維護合約 | 把四類十三列的表補完，人力欄填人天 | 症狀十三 |
| ★★★★ 停電復電後叢集起不來，管理介面連不上 | DNS／DHCP／AD 全虛擬化在同一個叢集裡（雞生蛋） | 確認叢集依賴的服務有沒有在叢集外 | 症狀十四 |
| ★★★ 系統出事，廠商第一句話是「你們跑在虛擬化上」 | 採購前沒取得書面的虛擬化支援聲明 | 翻合約與需求書找支援範圍條款 | 症狀十五 |
| ★★★★ 平常好好的，一到月底／備份時段全部一起變慢 | 整併時只算平均負載，沒算尖峰同時發生 | 看歷史監控的尖峰值與尖峰時間分布 | 症狀十六 |

## 依症狀展開

### ★★★★★ 症狀一：要做 HA／排程備份／集中管理，介面裡根本沒有那個選項

**現象**：平台已經上線、VM 都跑起來了，接著要做「進階的那幾件事」時卡住。

```text
（A）叢集頁面是灰的，或是點下去要求輸入授權金鑰
（B）備份頁面只能「立即備份」，沒有排程欄位
（C）三台主機要開三個網頁分別管，沒有單一介面
（D）API 呼叫回 403 或「此功能需要進階授權」
（E）想做線上遷移，選單裡只有「關機後遷移」
```

★★★★★ **這五種現象是同一件事**：用的是免費版／社群版，
而**廠商拿掉的功能，剛好就是機關最需要的那幾項**。

**判斷分流**：

```text
先確認這是「功能不存在」還是「功能存在但沒設定好」：
  介面上完全找不到該選項        → 走【1】（授權層級問題）
  選項存在但點下去要求金鑰      → 走【1】
  選項存在、可設定，但執行失敗   → ★★★★ 這不是授權問題，是設定或環境問題，跳到症狀九或症狀五
  找得到選項，但只有部分主機有   → 走【2】（授權層級不一致）
```

**排查步驟**：

【1】★★★★★ 先把「本案真正需要的功能」列出來，再對照該平台的授權層級。
不要反過來做 —— 從「這個版本有什麼」開始想，永遠會漏掉需求。

```text
本案需要的功能清單（逐項打勾）：
  [ ] 多節點叢集
  [ ] 線上遷移（不中斷服務搬 VM）
  [ ] 節點故障時自動重啟 VM（HA）
  [ ] 排程備份（含保留策略）
  [ ] 增量備份與備份驗證
  [ ] 單一集中管理介面
  [ ] REST API／命令列自動化
  [ ] 角色式存取控制（RBAC）與 AD 介接
  [ ] 稽核日誌可匯出
```

★★★★ 這份清單就是 [[050-01-01-04-guide-虛擬化-機關選型與授權成本]]
〈可以照抄的功能需求語句庫〉的精簡版。**選型時就該做，不是出事後才做。**

【2】★★★★ 確認是不是「同一個叢集內授權層級不一致」。
機關常見的情況是：先買了兩套，第三台是後來用剩餘預算補的，結果版本／層級不同。
★★★★★ **叢集內混用不同授權層級，會出現「有些節點能做、有些不能」的詭異行為。**

【3】★★★★★ 計算「用人工補這些功能要花多少工時」，這是唯一公平的比較方式。

```text
免費版少了排程備份 → 改成每週手動備份
  每次 20 分鐘 × 每週 1 次 × 52 週 = 約 17 小時／年 ≈ 2.2 人天／年
  ★★★★★ 再加上「總有一週會忘記」的風險，這個風險要寫進風險評估

免費版少了線上遷移 → 主機維護要停機
  每年 2 次維護 × 每次影響 30 台 VM
  ★★★★ 維護時窗被迫排在半夜，加班費與人力疲勞也是成本
```

★★★★ 把折算出來的人天加回免費版的 TCO，才是誠實的比較。

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 叢集／HA 選項完全不存在 | 免費版把叢集與 HA 拿掉了 | 升級授權層級；或改用「叢集能力內建、不因未訂閱而消失」的平台 |
| ★★★★★ 只能手動備份，沒有排程 | 免費版拿掉排程備份與備份 API | 買訂閱；或自寫排程腳本（**這筆工時要算進 TCO**） |
| ★★★★★ 三台主機要開三個網頁管 | 免費版沒有集中管理台 | 買管理台授權；或改平台。★★★★ 分開管的人為錯誤率明顯上升 |
| ★★★★ 有些節點能做、有些不能 | 叢集內授權層級不一致 | 補齊到同一層級；★★★★ 分批採購時就要把層級寫進規格書 |
| ★★★★ API 呼叫被拒 | 自動化能力屬於進階授權 | 確認授權範圍；★★★★★ 自動化需求要在採購前就寫進功能需求 |
| ★★★★ 想做線上遷移只能關機搬 | 免費版無線上遷移 | 升級授權；或接受停機並把維護時窗寫進 SLA |
| ★★★ 進階儲存功能（去重複、快照排程）不可用 | 屬於企業版功能 | 用平台外的方案補；評估額外儲存空間成本 |

**解法**：

1. ★★★★★ **短期**：把缺掉的功能改成人工程序，並**寫成 SOP 排進行事曆**。
   最怕的不是手動，是「以為有人在做，其實沒有」。
2. ★★★★ **中期**：把折算的人天寫進下一年度的預算說明，
   用「人力成本 vs 授權成本」的對照去爭取訂閱預算。
3. ★★★★★ **長期**：把這份功能清單變成規格書的功能需求條文，
   下一次採購時**在招標階段就驗證**，不要等上線後才發現。

> [!tip] ★★★★★ 判斷免費版夠不夠用的一句話
> **「把這些被拿掉的功能，用人工做一遍，要花多少工時？」**
> 答不出這個數字，就代表還沒真的做過選型。

**原理詳見**：

- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈免費版的閹割點通常在哪裡〉
- [[050-01-01-03-ref-虛擬化-五平台橫向對照]] 的〈主對照表（三）：叢集與高可用能力〉

### ★★★★★ 症狀二：訂閱到期後跳提示、無法更新，主管問「會不會停機」

**現象**：授權或訂閱到期，管理介面開始跳提示，套件庫拿不到更新。
★★★★★ **這時候最要命的問題不是「怎麼關掉提示」，是「答不出會不會停機」。**

**判斷分流**：

```text
先分清楚你面對的是哪一種到期：
  只是跳提示、無法用企業套件庫，VM 照跑       → 走【1】（可控，補預算即可）
  無法安裝安全更新                            → 走【2】（★★★★ 這是資安問題，不只是預算問題）
  依條款可能失去授權合法性（但機器還在跑）      → 走【3】（★★★★★ 稽核問題）
  條款寫明到期後功能受限或停止運作             → 走【4】（★★★★★ 這是事故，不是提醒）
  查不到條款寫什麼                            → ★★★★★ 立刻走【4】的最壞假設，同時去要書面
```

**排查步驟**：

【1】★★★★ 先確認「跳提示」是不是唯一的影響。
有些平台的訂閱過期只會失去技術支援與企業套件庫，**VM 完全不受影響**。
★★★★★ 這一點必須拿**合約條文**證明，不能靠印象或論壇說法。

【2】★★★★★ 確認「還能不能拿到安全更新」。
這是比「會不會停機」更容易被忽略的一條。

```text
不能更新的後果，按時間軸排：
  第 1 個月：沒感覺
  第 6 個月：出現已知漏洞，稽核開始問
  第 12 個月：★★★★★ 資安事件發生時，「未更新」會成為責任歸屬的關鍵事實
```

【3】★★★★★ 準備稽核要看的三份文件之一：

| 情況 | 要準備的文件 |
| --- | --- |
| 有買訂閱／維護 | 訂閱合約與有效期證明 |
| 用開源、不買訂閱 | ★★★★★ **經主管核章的風險接受文件**，寫明無原廠支援的因應方式 |
| 有簽 SI 維護合約 | 維護合約與服務等級條文 |

★★★★ **三種都沒有，就是稽核缺失。** 這一項本身不需要花錢就能補起來，先補。

【4】★★★★★ 如果條款寫明到期會影響運作，**這是事故等級**，處理順序是：

```text
1. 立刻確認影響範圍：哪幾台主機、幾台 VM、什麼時間點生效
2. 找出「最壞情況下服務會停多久」，寫成一句話給主管
3. 同步啟動兩條線：
   （a）緊急採購／續約（含回溯生效條款）
   （b）★★★★ 準備降級方案 —— 把最關鍵的服務先搬到不受影響的環境
4. 事後補：把「授權到期後既有 VM 的運作狀態」寫進下一次的合約與風險評估
```

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 續約沒接上，中間空窗數個月 | 決標延誤，未預留採購作業時間 | 提前一季啟動；契約加**回溯生效**條款 |
| ★★★★★ 某年度預算被刪，訂閱斷掉 | 訂閱制是經常門，每年都要重新編 | 優先選「過期不停機」的方案；或簽多年約鎖定 |
| ★★★★★ 條款根本沒人看過，答不出會不會停機 | 採購時沒把這一條列為必問項 | 立刻向經銷索取書面說明，附進風險評估 |
| ★★★★ 預算科目卡住無法核銷 | 永久授權是資本門、訂閱是經常門，兩者程序不同 | ★★★★ 選型前先跟主計確認科目 |
| ★★★★ 報價過了效期，價格變了 | 國外原廠報價有效期與匯率條款 | 招標文件要求**報價效期涵蓋預定決標日** |
| ★★★★ 第 4、5 年硬體保固過期沒預算 | 只編了三年保固，設備卻要服役五年 | 採購時一次買滿服役年限；或在中程財務規劃預先編列 |
| ★★★ 使用者以為訂閱提示是故障，一直來報修 | 未事先說明 | 向使用單位說明這是正常行為，並記錄在維運文件 |

**解法**：

1. ★★★★★ **今天就做的一件事**：把手上每一份授權的
   「到期日、到期後行為、續約前置時間」列成一張表，貼在維運文件第一頁。
2. ★★★★ 下一次採購時，把這句話寫進必問清單：
   **「授權到期後，既有虛擬機的運作狀態為何？請以書面說明。」**
3. ★★★★ 把續約時程往前推一季，並在契約中加入回溯生效條款。

**原理詳見**：

- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈六種授權模式的結構差異〉
- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈機關預算制度下的特殊痛點〉

### ★★★★★ 症狀三：整台 host 突然變慢，多台 VM 同時無回應

**現象**：★★★★★ **這是虛擬化環境最常見、也最容易誤判的症狀。**
使用者的說法一律是「系統很慢」，但底下有三個完全不同的原因，
**解法方向彼此相反**。

```text
（A）client 端連得上、指令打得動，但反應延遲、忽快忽慢     → 多半是 CPU 超配
（B）host 與多台 VM 幾乎全無回應，連 SSH 都要等很久        → 多半是記憶體超配（host 已在 swap）
（C）CPU 與記憶體看起來都還好，但磁碟操作特別慢            → 多半是 I/O 瓶頸或超配
```

**判斷分流**：★★★★★ **這三題的順序不能顛倒**，因為（B）會偽裝成（A）與（C）。

```text
第 1 題（先問，最重要）：host 在 swap 嗎？
    free -h → Swap 的 used 持續 > 0 且在成長  → 記憶體超配，走【2】
    Swap 幾乎沒用                             → 往下

第 2 題：客體裡的 steal time 多少？
    客體內 top → CPU 行的 st 欄位
      st 持續 > 10%   → ★★★★★ 嚴重 CPU 超賣，走【1】
      st 持續 5~10%   → ★★★★ 已影響體感，走【1】
      st 在 0~2%      → 不是 CPU，往下

第 3 題：儲存端如何？
    儲存池用量、磁碟延遲、是否有 resync／scrub 在跑  → 走【3】

★★★★ 三題都不成立 → 這不是超配問題，回頭查單一 VM 或單一服務
```

> [!warning] ★★★★★ 最常見的誤判
> **看 host 的 CPU 使用率來判斷 CPU 夠不夠。**
> host 顯示 60% 時客體仍可能有高 steal ——
> 因為問題常常出在**排程延遲**而不是總量。
> ★★★★★ **CPU 超配的唯一正確指標是客體內的 steal time，不是 host 的使用率。**

**排查步驟**：

【1】★★★★ CPU 超配過頭。這是三者中**最溫和**的一種 —— 服務還活著，只是慢。

```text
處理順序：
  a. 先確認 host 上沒有異常吃 CPU 的程序（不是 VM 造成的）
  b. 統計目前的超配比：所有 VM 的 vCPU 總和 ÷ host 的實體執行緒數
  c. 對照建議值：
       開發／測試              4:1 ~ 8:1
       一般正式服務（網站、AP） 2:1 ~ 4:1   ← 多數機關的甜蜜點
       資料庫、即時性服務       1:1 ~ 2:1
       即時運算／VDI 高負載     不超配
  d. 超出建議值 → 降低 vCPU 配置、遷移或關閉最不重要的 VM
```

★★★★★ **反直覺但很重要的一條**：給單一 VM 太多 vCPU 反而更慢。
一台 16 vCPU 的 VM 在總共 16 執行緒的 host 上，
必須等到 16 個執行緒同時有空才跑得動，於是它比 4 vCPU 的 VM 更常卡住。
★★★★ **原則：vCPU 給到夠用就好。**

【2】★★★★★ 記憶體超配過頭，host 開始 swap。**這是三者中最危險的一種。**

```text
立即處置（順序不可顛倒）：
  a. ★★★★★ 不要重開 host —— 那等於讓所有 VM 一起斷電
  b. 立刻關閉或遷移「最不重要」的 VM，把記憶體還回來
  c. 確認有沒有 VM 已經被 OOM Killer 殺掉：
        dmesg -T | grep -i 'killed process'
  d. 等 swap 使用量開始下降、host 回應恢復，再處理根因
```

★★★★★ **不要試圖靠調參數解決記憶體超配。** 沒有參數能變出記憶體。

★★★★ 根因處理時對照這張安全比例表：

| 情境 | 建議上限（配置總量 : 實體 RAM） |
| --- | --- |
| ★★★★★ 正式環境保守做法 | **1 : 1**（不超配，實際只配置到實體的 80%） |
| ★★★★ 一般正式環境（VM 同質、有 balloon 與 KSM） | **1.2 : 1 以內** |
| ★★★ 開發／測試 | **1.5 : 1** |
| ★★★★★ 任何情況都不要超過 | **2 : 1** |

★★★★★ 另外三條不能破的規則：

1. **給 host 留下足夠記憶體**。用 ZFS 時 ARC 會吃掉可觀的記憶體，
   ★★★★★ **必須先扣掉再算 VM 額度**；一般至少留 10～15%，且不少於 8 GB。
2. **host 的 swap 使用量必須納入告警**。開始持續 swap ＝ 容量規劃失敗。
3. **資料庫與 Java 應用的 VM 不參與超配**，balloon 最小值設成等於配置值。

【3】★★★★ I/O 問題。先分清楚是「不夠快」還是「快滿了」。

```text
  儲存池用量 > 85%          → 走症狀四（這是容量問題，不是效能問題）
  有 resync／scrub／重建在跑 → 等它跑完；★★★★ 這段期間效能本來就會掉
  單一 VM 的磁碟延遲特別高   → 看它是不是全模擬 I/O，走症狀六
  所有 VM 的磁碟延遲都高     → 整體 IOPS 不足，看下面的放大因素
```

★★★★ **I/O 慢的三個最常見放大因素**（都不是「磁碟不夠快」）：

| 因素 | 說明 |
| --- | --- |
| ★★★★★ 快照鏈太長 | 每寫一個未修改過的區塊，要先把原始內容複製出去（CoW） |
| ★★★★★ RAID 5／6 承載隨機小寫入 | 一次小寫要「讀舊資料 + 讀舊校驗 + 寫新資料 + 寫新校驗」＝**四次 I/O** |
| ★★★★ 磁碟分割未對齊 | 一次邏輯寫跨到兩個實體區塊 |

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ host 極慢、多台 VM 同時無回應、swap 持續成長 | 記憶體超配過頭 | 立刻關閉／遷移非必要 VM；長期加記憶體或降低配置 |
| ★★★★★ 客體 `top` 的 `st` 持續 > 10% | CPU 超賣過頭，或 host 上有失控程序 | 先排除 host 異常程序，再降低 vCPU 超配比 |
| ★★★★ 加了 vCPU 反而更慢 | vCPU 數逼近 host 執行緒數，排程要等所有 vCPU 同時有空 | 減少 vCPU；單 VM 的 vCPU 不超過 host 執行緒數的一半 |
| ★★★★ 資料庫 VM 三不五時被 OOM killer 殺掉 | 開了 ballooning，記憶體被氣球抽走 | balloon 最小值設成等於配置記憶體（等於關閉 ballooning） |
| ★★★★ 用了 ZFS 之後 VM 開不起來，記憶體莫名不足 | ARC 預設上限太高，先吃掉了記憶體 | 設定 `zfs_arc_max`，並在算 VM 額度時先扣掉 ARC |
| ★★★★ 磁碟操作特別慢，CPU 與記憶體看起來正常 | 快照鏈太長或 RAID 5／6 的寫入放大 | 清掉舊快照；虛擬化承載改用 RAID 10 或 ZFS |
| ★★★ 開了大頁之後 host 一開機就記憶體吃緊 | 預留式大頁在開機時就從一般池扣掉且不可回收 | 降低預留量，或改回透明大頁 |

**解法**：

1. ★★★★★ **止血**：先降載（關掉最不重要的 VM），再查原因。
   ★★★★ 在 host 已經 swap 的狀態下做任何診斷都會非常慢，先讓它喘口氣。
2. ★★★★ **驗證**：把三個指標（swap 用量、客體 steal、儲存池用量）加進監控與告警，
   ★★★★★ **這三個是虛擬化平台的生命徵象**。
3. ★★★★ **根治**：重算容量規劃。記憶體是九成情況下的真正瓶頸，
   ★★★★★ **買虛擬化主機時記憶體先買滿，CPU 核心數不必衝頂。**

**原理詳見**：

- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈超配（Overcommit）的代價與安全比例〉
- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈記憶體超配的三個工具〉
- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈迷思四：超配（Overcommit）是免費的〉
- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈整併比（Consolidation Ratio）怎麼算〉

### ★★★★★ 症狀四：儲存池滿了，多台 VM 同時變唯讀或當掉

**現象**：★★★★★ **這是「一次故障打掉整個池子上所有 VM」的少數情況之一，
比單台 VM 掛掉嚴重一個等級。**

```text
儲存頁面顯示 100%
多台 VM 同時：
  - 客體檔案系統轉唯讀
  - 資料庫寫入失敗，甚至損毀
  - 快照與備份同時失敗  ← ★★★★★ 連救援的手段都沒了
```

★★★★★ **核心原因永遠是同一件事**：VM 裡的檔案系統**不知道**池子快滿了。
它以為自己還有幾百 GB 可以用，於是照常寫入。

**判斷分流**：

```text
先確認「池子滿了」是誰造成的：
  快照數量異常多，或有留很久的快照        → 走【2】（最常見，第一名原因）
  備份檔堆在同一個池子裡                  → 走【2】
  已分配總量 > 實體容量（thin 超賣）       → 走【3】
  客體刪了大檔案但空間沒回來              → 走【4】（discard/TRIM 沒開）
  單一 VM 短時間內寫了大量資料            → 走【5】
```

**排查步驟**：

【1】★★★★★ **止血優先，不要先查原因。** 順序固定：

```text
a. ★★★★★ 不要重開任何 VM —— 開機需要寫入，會讓情況更糟
b. 找出可以立刻刪除的東西，依「刪了最不痛」的順序：
     1) 過期的舊備份檔（確認異地還有一份再刪）
     2) 保留超過七天的舊快照       ← ★★★★★ 通常刪這個就夠了
     3) 已除役 VM 的殘留磁碟檔
     4) ISO 映像檔與範本
c. 空間釋放到 85% 以下之後，再處理已經受影響的 VM
d. 對已經轉唯讀的客體：先在客體內檢查檔案系統一致性，再恢復服務
e. ★★★★★ 資料庫要另外確認：可能停在交易中間，要跑資料庫自己的修復程序
```

【2】★★★★★ 快照堆積 —— **忘掉的快照是池子爆掉的第一名原因**。

```text
列出所有快照，逐一問三個問題：
  1. 這個快照是誰開的？為什麼開？
  2. 開了之後那件事做完了嗎？
  3. 還需要它嗎？

★★★★★ 正確的快照用法：動手前開，確認正常後「立刻刪」。
★★★★ 保留超過數天的快照就是問題，不是保險。
```

【3】★★★★ thin provisioning 超賣。這需要一張對照表，不是一條指令。

```text
建立這張表（每月核對一次）：
  ┌──────────────┬─────────┬─────────┬─────────┐
  │ 儲存池        │ 已分配總量 │ 實體容量  │ 實際用量  │
  ├──────────────┼─────────┼─────────┼─────────┤
  │ pool-vm       │  9.5 TB │  4.0 TB │  3.1 TB │  ← 超賣 2.4 倍
  │ pool-backup   │  ...    │  ...    │  ...    │
  └──────────────┴─────────┴─────────┴─────────┘

★★★★ 超賣本身不是錯，「超賣而沒有告警」才是錯。
```

【4】★★★★ 客體刪檔後空間沒回收 —— discard／TRIM 沒開。

```text
三個條件必須同時成立，空間才會真的還回池子：
  1. 磁碟控制器是 virtio-scsi（不是 virtio-blk）
  2. 磁碟選項有勾 discard
  3. 客體內有執行 fstrim（或掛載選項含 discard）

★★★★ 三者缺一，客體裡刪掉 500 GB，池子的用量一點都不會少。
```

【5】★★★ 單一 VM 暴衝寫入：常見來源是日誌爆量、暫存檔沒清、
或有人在 VM 裡做了大型匯出。★★★★ 這種要在客體端處理，
並把該 VM 的磁碟用量納入監控。

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 儲存池 100%，多台 VM 同時唯讀或當機 | thin 超賣 + 快照堆積 | 立刻刪舊快照／舊備份釋放空間；恢復後在客體內檢查檔案系統 |
| ★★★★★ 快照與備份也一起失敗 | 建立快照與寫備份都需要空間 | ★★★★★ 這是最壞情況：先釋放空間才有救援手段 |
| ★★★★★ 池子滿了但沒人事先知道 | 沒有設容量告警 | 設 **75% 黃燈、85% 紅燈**，紅燈必須當天處理 |
| ★★★★ 客體刪了大檔案但池子空間沒回收 | 沒開 discard／TRIM，或控制器不是 virtio-scsi | 改用 virtio-scsi、勾 discard，客體內執行 `fstrim` |
| ★★★★ 快照越留越多，VM 也越來越慢 | 快照鏈造成寫時複製放大 | 定期清理；★★★★★ 快照**不是備份** |
| ★★★★ 每個月都在刪東西騰空間 | 容量規劃時沒留成長與重建空間 | 永遠留 **10～15%** 不分配；重算容量並編列擴充預算 |
| ★★★ 備份放在同一個池子上 | 備份目的地規劃錯誤 | ★★★★★ 備份目的地一定要在被備份對象之外的儲存上 |

**解法**：

1. ★★★★★ **今天就設告警**：75% 黃燈、85% 紅燈。這一步不用花錢，但擋掉九成事故。
2. ★★★★ **快照存活期訂成規則**：例如「不超過 7 天」，寫進維運文件並排進月維護作業，
   → [[100-02-04-guide-維運-每月維護作業]]。
3. ★★★★ **每月核對一次**「已分配總量 vs 實體容量 vs 實際用量」，
   → [[100-01-03-guide-日誌-系統監控與告警]]。
4. ★★★★★ **永遠留 10～15% 不分配**，出事時才有轉圜餘地。

**原理詳見**：

- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈儲存超配（Thin Provisioning）〉
- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈寫入放大（Write Amplification）〉
- [[050-01-03-02-guide-PVE-儲存設定]] —— 儲存後端與格式的實際設定

### ★★★★ 症狀五：決定換平台後，遷移做到一半才發現要重來

**現象**：選型結論是「換平台」，但實際動手後：

```text
（A）Windows VM 搬過去藍屏：INACCESSIBLE_BOOT_DEVICE
（B）Linux VM 搬過去網路不通，console 進去才發現網卡名稱變了
（C）備份軟體不支援新平台，備份策略要整套重做
（D）自動化腳本全部失效（PowerCLI 換成別的 API）
（E）工時估了兩週，做到第六週還沒完
（F）容器（LXC）在目標平台完全沒有對應物
```

★★★★★ **共同原因只有一個：把「遷移」等同於「搬 VM 磁碟」。**
實際上遷移有六層成本，磁碟轉換是**最便宜的那一層**。

**判斷分流**：

```text
現在卡在哪一層？
  磁碟格式轉不過去              → 走【1】（層 1，通常最好解）
  VM 搬過去開不了機／網路不通    → 走【2】（層 2、3，★★★★★ 最常見）
  VM 都好了，但備份與監控沒接上  → 走【3】（層 4）
  自動化與 SOP 要重寫            → 走【4】（層 5、6）
  進度嚴重落後，說不出還要多久   → 走【5】（估算方法本身錯了）
```

**排查步驟**：

【1】★★★ 磁碟映像轉換。這一層有工具，主要成本是**停機時間**。
★★★★ 轉換前**必須先關機**，轉完要驗證映像完整性 —— 來源檔在轉換期間仍被使用中，
是產出壞映像的頭號原因。

【2】★★★★★ 客體驅動與網路 —— **這一層是災難的來源**。

> [!danger] ★★★★★ Windows VM 跨平台搬移的頭號地雷
> **先在來源平台裝好目標平台的驅動，再搬。** 正確順序是：
> 1. ★★★★★ 在**來源平台**上先開機，安裝目標平台的驅動（此時它還用得到現有磁碟）
> 2. 關機，轉換磁碟並匯入目標平台
> 3. 在目標平台先用**相容的控制器**開機確認，再改成 VirtIO
> 4. 開機正常後才移除來源平台的客體工具
>
> ★★★★★ **順序做反 —— 先搬再想裝驅動 —— 結果就是開機藍屏，
> 而你已經沒有可以開機的環境去裝驅動了。**

★★★★ Linux VM 的對應問題是**網卡名稱變動**（MAC 改變導致 `ens18` 變成 `ens19` 之類）：
從 console 進去修正網路設定；事前的做法是改用可預期的命名或以 MAC 綁定。

【3】★★★★ 備份與監控重接。★★★★★ **這一層的工時常被估成零。**

```text
逐項確認（每一項都是獨立工時）：
  [ ] 備份軟體支不支援新平台？授權要不要重買？
  [ ] 備份排程、保留策略、驗證機制要重建
  [ ] 監控代理程式要重裝，告警規則要重寫
  [ ] ★★★★★ 新平台上要做過一次完整還原演練，才算完成
```

【4】★★★ 自動化與人的成本。
★★★★★ **第 6 層（人的成本）量級最高**：維運人員重新學習、SOP 重寫、交接文件重做。
估算時**不能只算技術工時**。

【5】★★★★ 進度落後說不出還要多久 —— 這代表當初是「整批估」的。
★★★★★ 正確做法是**逐台分類估**：

```text
把 VM 分成四類，每類的單台工時完全不同：
  A 類：純 Linux、無特殊裝置、服務單純        → 最快
  B 類：Windows VM                          → ★★★★ 加驅動處理與重新啟用的時間
  C 類：有直通裝置、有特殊授權綁定             → ★★★★★ 要先確認可行性，可能根本搬不了
  D 類：容器（LXC）或平台專屬物件              → ★★★★★ 目標平台沒有對應物就得重建成 VM

再加上「與 VM 無關」的固定工時：
  平台建置、儲存規劃、網路規劃、備份重建、監控重接、SOP 與交接文件
```

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ Windows VM 搬過去藍屏 `INACCESSIBLE_BOOT_DEVICE` | 沒有先安裝目標平台的驅動就改用新控制器 | 改回相容控制器開機 → 裝驅動 → 再切換。**下次先在來源平台裝** |
| ★★★★ Linux VM 搬過去網路不通 | MAC 改變導致網卡介面名稱變動 | 從 console 修正網路設定；事前改用可預期命名或綁 MAC |
| ★★★★★ 遷移工時超支一倍以上 | 只算「搬 VM」，漏算平台建置、驗證、文件與 SOP 重寫 | 逐台分類估算並加緩衝；把六層成本全部列出來 |
| ★★★★★ 容器（LXC）搬不過去 | 目標平台沒有對應物 | ★★★★ 重建成 VM，這是重建工時不是遷移工時 |
| ★★★★ 某台 VM 直通了硬體，不能線上遷移 | 選型時沒盤點直通裝置 | 盤點時就列出所有直通裝置；見症狀十 |
| ★★★★★ 遷移做到一半發現舊備份還原不回來 | 遷移前未做還原演練 | ★★★★★ **遷移的第一步永遠是「先驗證舊環境的備份可還原」** |
| ★★★★ 同時導入新平台與新儲存架構，出問題查不出誰的錯 | 一次改太多變數 | ★★★★★ **一次只換一件事**，分階段驗收 |
| ★★★★ 舊平台太早除役，出問題無法回退 | 沒有保留回退路徑 | ★★★★★ 舊環境至少保留到新環境穩定運行數個月 |
| ★★★★★ AD 網域控制站用映像搬移後出現複寫錯誤 | USN rollback | ★★★★★ 依 AD 標準程序：新建 DC → 複寫 → 轉移 FSMO → 降級舊 DC |
| ★★★ 轉換出來的映像檔壞掉 | 來源檔在轉換期間仍被使用中 | ★★★★ 轉換前必須先關機；轉完驗證映像 |

**解法**：

1. ★★★★★ **停下來，先把六層成本列出來**，重新估一次工時再繼續。
   繼續硬做只會讓超支更難解釋。
2. ★★★★ **保留回退路徑**：舊環境不要急著除役。
3. ★★★★★ **降低未來的遷移成本**，四個設計決定：
   不要在 hypervisor 層做高可用（讓應用自己有多節點能力）、
   用標準格式與標準協定、自動化用平台無關的工具、
   把「重建一台 VM 的完整步驟」寫成文件或腳本。

- [[050-01-01-03-ref-虛擬化-五平台橫向對照]] 的〈降低未來遷移成本的四個設計決定〉

### ★★★★ 症狀六：效能不如預期，以為主機不夠力想加硬體

**現象**：新平台上線後，使用者反映「比舊的實體機還慢」。
主管的第一反應是「是不是硬體買太小」，開始討論追加預算。

★★★★★ **在買任何硬體之前，先確認這台 VM 用的是不是全模擬的 I/O。**

**判斷分流**：

```text
先看 VM 的組態，兩個欄位：
  磁碟控制器 = IDE／SATA／LSI SAS 之類  → ★★★★★ 全模擬，走【1】
  網卡型別   = Intel e1000 之類          → ★★★★★ 全模擬，走【1】
  兩者都是 VirtIO／virtio-scsi           → 不是這個問題，往下

  客體是 Windows 且裝置管理員有黃色驚嘆號 → 走【2】（驅動沒裝）
  I/O 正常但 CPU 型別怪怪的               → 走【3】
  以上都正常                              → 回到症狀三的三題分流
```

**排查步驟**：

【1】★★★★★ 確認 I/O 路徑。VM 碰磁碟與網卡只有三種走法：

| | 全模擬 | VirtIO（半虛擬化） | 直通 |
| --- | --- | --- | --- |
| 客體看到什麼 | 一張真實存在過的老硬體 | 明擺著是虛擬的裝置 | ★★★★ 真正的實體裝置 |
| 要不要裝驅動 | 不用，所有 OS 內建 | Linux 內建；**Windows 必須另外裝** | 要裝原廠驅動 |
| VM Exit 量 | ★★★★★ 極高（每個暫存器存取一次） | ★★★ 低（多筆請求合併成一次通知） | ★★ 幾乎沒有 |
| 吞吐與延遲 | 最差 | 好，一般負載綽綽有餘 | 最好 |
| 能不能線上遷移 | 可以 | **可以** | ❌ ★★★★★ 不行 |

★★★★★ **一句話的選擇原則：預設一律 VirtIO。**
用全模擬的唯一正當理由是：客體 OS 老到沒有 VirtIO 驅動。

★★★★ **為什麼 VirtIO 快**：全模擬的網卡，客體驅動要寫多個暫存器才能送出一個封包，
每一次都是一次 VM Exit。VirtIO 改成把請求寫進與 hypervisor 共用的環形佇列，
累積一批之後才敲一次門。
★★★★ **本質是「把很多次昂貴的同步呼叫，換成一次非同步批次通知」** ——
所以它在高負載下的優勢比低負載時更明顯。

【2】★★★★ Windows 客體的 VirtIO 驅動問題。

```text
兩個典型現象：
  安裝 Windows 時「找不到任何磁碟機」
      → 掛載 virtio-win 驅動 ISO，在磁碟選擇畫面按「載入驅動程式」
  Windows 網路不通、裝置管理員有黃色驚嘆號
      → 從 virtio-win ISO 安裝網卡驅動，或執行 ISO 內的完整安裝程式

★★★★ 不要為了省事改用全模擬控制器裝完就算了 —— 那台 VM 會慢一輩子。
```

【3】★★★ 其他常被誤認成「硬體不夠力」的原因：

| 誤判 | 真正的原因 |
| --- | --- |
| ★★★★ 「CPU 太慢」 | 客體 steal time 高（超配），不是主機時脈問題 → 症狀三【1】 |
| ★★★★ 「磁碟太慢」 | 快照鏈太長，或 RAID 5／6 承載隨機小寫入 → 症狀四 |
| ★★★★ 「記憶體不夠」 | ZFS ARC 吃掉了，或 balloon 抽走了 → 症狀三【2】、症狀十一 |
| ★★★ 「網路太慢」 | 整併後單台主機流量集中，實體網路才是瓶頸 |
| ★★★ 「主機規格買太小」 | 只算了平均負載，尖峰時全部一起跑 → 症狀十六 |

★★★★★ **加硬體之前，先量測。** 沒有量測就追加預算，
最好的結果是浪費錢，最壞的結果是花了錢問題還在。

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 磁碟吞吐明顯低於預期，客體 CPU 卻很忙 | 用了全模擬磁碟控制器 | 改成 virtio-scsi；Windows 需先裝驅動再切換 |
| ★★★★★ 網路吞吐上不去，`si`／`sy` 佔用高 | 用了全模擬網卡 | 改成 virtio 網卡 |
| ★★★★★ Windows 安裝時找不到磁碟 | 沒載入 VirtIO 驅動 | 掛 virtio-win ISO，安裝畫面按「載入驅動程式」 |
| ★★★★ Windows 裝置管理員有黃色驚嘆號、網路不通 | 缺 VirtIO 網卡驅動 | 從 virtio-win ISO 安裝 |
| ★★★★ 從 PVE 介面按「關機」沒反應 | VM 內未安裝 guest agent，ACPI 訊號沒被處理 | 安裝 `qemu-guest-agent` 並在 VM 選項啟用 |
| ★★★★ 備份出來的資料庫不一致 | 沒有 guest agent，無法做檔案系統凍結 | 安裝 guest agent；資料庫另做應用層備份 |
| ★★★ VM 內部時間持續偏移 | 未安裝 guest agent／未設定時間同步 | 安裝 guest agent 並設定時間同步 → [[020-01-28-cmd-Linux-時間同步NTP與chrony]] |
| ★★★ 為了效能把快取模式改成不安全的設定 | 誤以為快取模式是效能旋鈕 | ★★★★★ 忽略客體 flush 的模式只用在「壞了就重灌」的批次安裝，正式環境禁止 |

**解法**：

1. ★★★★★ **先做一次 A/B 量測再談硬體**：
   建兩台規格一模一樣的測試 VM，**差別只在 I/O 型別**，量磁碟與網路。
   ★★★★ 這個數字是說服主管「不需要追加硬體」最有力的證據。
2. ★★★★ **建立 VM 範本**：範本裡就用 virtio-scsi + virtio 網卡 + guest agent，
   從源頭杜絕全模擬 VM 被建出來。
3. ★★★★ 把「磁碟控制器型別」「網卡型別」「有無 guest agent」
   列進 VM 的建置檢核表。

**原理詳見**：

- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈I/O 虛擬化的三條路徑〉
- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈VirtIO 為什麼快〉
- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈磁碟快取模式〉

### ★★★★ 症狀七：在 VM 裡再開一台 VM，開不起來或慢到不能用

**現象**：要在筆電或既有 VM 裡練習叢集、建教學環境時：

```text
（A）L1 裡執行 grep -c -E '(vmx|svm)' /proc/cpuinfo 得到 0
（B）L1 裡的 hypervisor 說「找不到硬體虛擬化」
（C）能跑，但 L2 慢到不能用
（D）Windows 桌機上的 Type 2 平台啟動 VM 失敗或極慢
```

**判斷分流**：

```text
你是在哪一層遇到問題？
  L1（VM 裡的 hypervisor）看不到 vmx／svm     → 走【1】
  L1 看得到旗標，但 L2 效能很差                → 走【2】（這多半是正常的）
  在 Windows 桌機上，Type 2 平台起不來        → 走【3】
  實體機本身就看不到虛擬化旗標                 → 走【4】（BIOS 問題，不是巢狀問題）
```

**排查步驟**：

【1】★★★★ 巢狀虛擬化沒開，或 CPU 型別不對。★★★★★ **這兩件事都要做，缺一不可。**

```text
（a）host（L0）要開巢狀：
      Intel：模組參數 kvm_intel nested=1
      AMD  ：模組參數 kvm_amd   nested=1
      改完要重新載入模組（★★★★ 必須先關掉所有 VM）

（b）VM（L1）的 CPU 型別要能把虛擬化旗標傳下去：
      在 Proxmox VE 上把 VM 的 CPU 類型設為 host

（c）在 L1 裡驗證：
      grep -c -E '(vmx|svm)' /proc/cpuinfo   → 應該 > 0
```

★★★★★ **只做（a）不做（b），L1 裡永遠看不到 `vmx`／`svm`。**
這是最常見的錯誤 —— 因為（a）改完會顯示成功，讓人以為做完了。

> [!info]- VMware Workstation 上開巢狀虛擬化
> ★★★★ VM 設定 →「處理器（Processors）」→ 勾選
> **Virtualize Intel VT-x/EPT or AMD-V/RVI**。
> ★★★★ VM 必須先**關機**（不是暫停）才能改。
> ★★★ 這是在筆電上練習叢集的標準做法 → [[050-01-03-13-guide-PVE-建立練習環境]]。

【2】★★★★★ L2 效能差 —— **這通常不是故障，是巢狀虛擬化的本質。**

```text
CPU 只提供一層 VMX root／non-root，第二層要靠 L0 模擬：
  L0：實體機上的 hypervisor，真正握有硬體，並「假裝」提供了 VT-x 給 L1
  L1：跑在 VM 裡的 hypervisor，以為自己有硬體虛擬化
  L2：L1 開出來的 VM

★★★★★ L1 的每一次 VM Exit 都會變成 L0 的一次 VM Exit，成本相乘。
```

★★★★ 所以巢狀虛擬化的定位很明確：

| 適合 | ★★★★★ 不適合 |
| --- | --- |
| 教學、實驗、驗證叢集設定 | **任何正式服務** |
| 在桌機上練習叢集 | 效能測試（★★★★★ 數字完全不能參考） |
| CI 流程需要在 VM 裡跑 VM | 需要穩定延遲的東西 |

【3】★★★★ Windows 桌機上「誰佔走了虛擬化」。

```text
只要開啟下列任一項，Windows 自己就變成 L0 hypervisor：
  Hyper-V、WSL2、Windows 沙箱、記憶體完整性（HVCI）／Credential Guard

此時桌面型虛擬化平台必須走 Hyper-V 提供的介面來跑：
  ★★★★ 效能會下降
  ★★★★ 舊版本可能直接無法啟動 VM
```

★★★★ 解法二選一：把平台更新到支援 Hyper-V 模式的版本，
或關閉 Hyper-V 相關功能後重開機
→ [[050-01-02-06-guide-Workstation-效能調校與疑難排解]]。

【4】★★★★ 實體機本身就沒有虛擬化旗標 —— 這不是巢狀問題。

```text
（a）grep -c -E '(vmx|svm)' /proc/cpuinfo  →  0
（b）進 BIOS/UEFI 開啟 Intel VT／SVM Mode
（c）★★★★★ 儲存後「完全斷電再開機」，不是重開機
     —— 提示訊息裡的 hard poweroff/poweron 很誠實，重開機常常不夠
（d）部分機型需要清除 CMOS
```

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ L1 裡看不到 `vmx`／`svm` | host 的 nested 沒開，或 VM 的 CPU 型別不對 | ★★★★★ 兩件事都要做：開 nested + CPU 型別設為 host |
| ★★★★ 改了模組參數但沒生效 | 模組沒重新載入（重載前必須關掉所有 VM） | 關閉所有 VM 後重載模組，或重開機 |
| ★★★★★ L2 效能差得不合理 | 巢狀虛擬化的成本是相乘的 | ★★★★★ 這是設計限制，不是故障。**不要用巢狀環境做效能測試** |
| ★★★★ Windows 上 Type 2 平台啟動 VM 失敗或極慢 | Hyper-V／WSL2／HVCI 已把 Windows 變成 hypervisor | 更新平台到支援 Hyper-V 模式的版本，或關閉相關功能後重開機 |
| ★★★★★ BIOS 已開卻仍顯示未啟用 | 只做了重開機，設定未在 CPU 上電時載入 | 拔電源等一段時間再開；部分機型需清除 CMOS |
| ★★★★ `/dev/kvm` 存在但一般使用者無法用 | 使用者不在對應群組 | 把使用者加入 `kvm` 群組，重新登入 |
| ★★★ EPT／NPT 顯示為關閉 | 核心啟動參數關掉了，或 CPU 太舊 | ★★★★★ 務必查清原因 —— 沒有 EPT／NPT，記憶體效能會退回影子頁表的年代 |

**解法**：

1. ★★★★★ 巢狀環境**只用在教學與驗證**，並且在文件第一行就寫明
   「本環境效能數字不具參考價值」。
2. ★★★★ 在 Windows 桌機上，**先決定「這台機器是給 Hyper-V/WSL2 用，
   還是給桌面型虛擬化平台用」**，不要兩邊都要。
3. ★★★★ 硬體能力檢查（虛擬化旗標、模組載入、EPT／NPT、IOMMU）
   應該列進新機器的上架檢核表，不要等要用時才發現。

**原理詳見**：

- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈巢狀虛擬化（Nested Virtualization）〉
- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈第一步：確認硬體支援（Linux）〉

### ★★★★ 症狀八：規格書被質疑綁標、流標，或決標後要追加授權預算

**現象**：採購階段的四種典型事故。

```text
（A）規格書送出去，被質疑綁標
（B）招標流標 —— 沒有廠商投標，或投標廠商都不合格
（C）三家投標，規格書都符合但功能差很多
（D）★★★★★ 決標後才發現授權數量不足，要追加預算
```

**判斷分流**：

```text
（A）（B）→ 走【1】（規格寫法問題）
（C）    → 走【2】（功能需求沒有可量測門檻）
（D）    → 走【3】（授權數量估算單位錯誤）
驗收時廠商說某項測試「不能做」→ 走【4】（驗收項目沒寫進招標文件）
```

**排查步驟**：

【1】★★★★★ 綁標的定義很簡單：**規格寫得只有一家做得到。**
逐條問一句話：**「這句話換一家廠商能不能達成？」**

| ❌ 綁標寫法 | 為什麼綁標 | ✅ 改成 |
| --- | --- | --- |
| 「應為某某產品 X.0 以上」 | ★★★★★ 直接寫產品名與版本 | 「應提供 Type 1 型虛擬化平台，支援多節點叢集管理」 |
| 「應支援〈某商標功能名〉」 | ★★★★ 註冊商標，只有一家有 | 「應支援虛擬機於節點間**不中斷服務**之線上遷移」 |
| 「應提供〈某產品〉集中管理」 | ★★★★ 同上 | 「應提供**單一集中管理介面**，可同時管理所有節點與虛擬機」 |
| 「CPU 應為〈特定型號〉」 | ★★★★★ 指定型號 | 「CPU 每顆實體核心數不少於 X 核，基準測試分數不低於 Y」 |
| 「應使用〈特定品牌〉網卡」 | ★★★★★ 指定品牌 | 「網路介面應為 10GbE 以上，並於平台之硬體相容清單內」 |

★★★★ 三個原則：

1. ★★★★★ **寫「功能」不寫「產品」。**
2. ★★★★★ **寫「可量測的門檻」不寫「品牌」。**
3. ★★★★ **區分「應」與「宜」** ——
   ★★★★★ 把非必要功能寫成「應」，是綁標最常見的無心之過。

【2】★★★★ 功能需求太籠統，導致三家都「符合」但實際差很多。
★★★★★ **每一條功能需求都要加上可驗收的數字。**

```text
❌ 「應支援叢集」
✅ 「應支援至少 3 個節點組成之叢集，並提供單一管理介面」

❌ 「應支援備份」
✅ 「應提供或可整合排程備份機制，支援全量與增量備份，
     且可於管理介面設定保留策略（日／週／月份數）」

❌ 「應具備高可用」
✅ 「應具備節點故障時自動於其餘節點重新啟動受影響虛擬機之機制，
     並可於契約約定之 __ 分鐘內完成」
```

【3】★★★★★ 授權數量估算錯誤 —— 決標後才追加預算是最難看的一種。

```text
最常見的三個估算錯誤：
  1. 用「邏輯處理器（含 HT）」估，實際條款是以「實體核心」或「socket」計
  2. 用「VM 數量」估，實際是按主機資源計
  3. 漏算客體 OS 授權（★★★★★ 虛擬化環境下客體 OS 有專屬計算規則）

★★★★ 防呆做法：
  a. 招標文件內附【授權數量表】，要求投標廠商簽名確認
  b. 報價單上明列「以實體核心數 __ 計」
  c. 請經銷商出具「本案授權計算說明」書面文件，附進採購與稽核卷宗
```

★★★★★ 三個一定要在合約裡問清楚的定義：

1. **「一顆 CPU」怎麼算？** 實體 socket？還是含 HT 的邏輯核心？
2. **「一台 VM」怎麼算？** 關機的算不算？範本算不算？快照算不算？
   ★★★★★ 這一條在稽核時最容易被抓。
3. **授權到期會怎樣？** → 見症狀二。

【4】★★★★ 驗收時廠商說「這個測試會影響服務，不能做」。
★★★★★ **驗收項目沒有寫進招標文件，就沒有立場要求。**
應該在招標文件明訂：驗收含斷電測試與還原演練，並約定測試時段。

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 規格被質疑綁標，招標流標 | 規格寫了產品名、商標功能名或指定型號 | 用功能需求語句逐條改寫；必要時加等效品條款 |
| ★★★★ 加了等效品條款仍被認定綁標 | ★★★★★ 等效條款解決的是「品名」問題，不是「功能設計」問題 | 檢視功能需求本身是不是只有一家做得到 |
| ★★★★ 三家投標，規格都符合但功能差很多 | 功能需求太籠統，沒有可量測門檻 | 每條功能需求加上可驗收的數字 |
| ★★★★★ 決標後發現授權數量不足 | 以邏輯處理器或 VM 數估算，實際條款以實體核心／socket 計 | 招標文件附授權數量表並要求簽名確認 |
| ★★★★★ 客體 Windows 授權被稽核認定不足 | 客體 OS 授權在虛擬化下有專屬規則，未事先確認 | 請經銷商出具授權計算說明書面文件 |
| ★★★★★ 驗收時廠商拒絕做 HA 測試 | 驗收項目沒寫進招標文件 | 招標文件明訂驗收含斷電測試與還原演練 |
| ★★★★ 買了新伺服器，平台裝不起來 | 硬體不在該平台的相容清單（HCL）內 | 招標文件要求「所供硬體須在所供平台之硬體相容清單內，並檢附佐證」 |
| ★★★★★ 廠商代建完成後，機關拿不到管理密碼 | 交付項目未明訂帳號與密碼移轉 | 驗收項目明列「完成管理者密碼移轉並移除廠商帳號」 |
| ★★★★★ 三年後想換平台，虛擬磁碟匯不出來 | 採購時沒有寫退場條款 | 規格書列入「應支援標準格式匯出」與「備份可於未安裝原平台環境還原」 |
| ★★★★ 主管問「為什麼不選最便宜的」答不出來 | 選型報告只有結論沒有排除理由 | ★★★★★ 每個未採用方案都要寫「不符合第 X 項需求」 |
| ★★★ 整包貼上功能需求語句庫，反而限制投標廠商 | 用不到的條款會變成另一種綁標 | 逐條問「本案需不需要」，不需要的刪掉 |

**解法**：

1. ★★★★★ **把功能需求語句庫當檢核清單用**，逐條決定要不要 ——
   ★★★★★ **不要整包貼上去。**
2. ★★★★ **授權數量表 + 廠商簽名確認**，是防止追加預算最有效的一招。
3. ★★★★★ **選型報告要寫「有理由的排除」**：
   「C 授權為零但缺乏支援窗口，不符本案第 Q5 項要求，故不採用。」
   ★★★★★ 有理由的排除，比有理由的選擇更重要。

**原理詳見**：

- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈規格書怎麼寫才不綁標〉
- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈可以照抄的功能需求語句庫〉
- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈採購前必問的十個問題〉

### ★★★★ 症狀九：一台主機壞掉，全部服務跟著停 —— 但我們有做虛擬化

**現象**：★★★★★ **這是所有選型錯誤中，代價最直接的一種。**

```text
（A）只有一台實體主機，主機掛了 → 上面 15 台 VM 全停
（B）有三台主機、有做 HA，但服務仍然中斷了十幾分鐘
（C）兩節點叢集，其中一台重開機後整個叢集無法操作
（D）主機沒壞，但儲存壞了 → 全部 VM 一起停
```

**判斷分流**：

```text
（A）→ 走【1】：這不是故障，是架構本來就沒有高可用
（B）→ 走【2】：HA 有作用，但「HA ≠ 不中斷」
（C）→ 走【3】：法定人數（quorum）問題
（D）→ 走【4】：單點故障搬家了，從主機變成儲存
```

**排查步驟**：

【1】★★★★★ 單台主機就是單點故障。**虛擬化沒有讓可用度變好，反而讓它變差。**

```text
虛擬化前：5 台實體機，壞一台 → 影響 1 個服務
虛擬化後：1 台主機跑 5 台 VM，壞一台 → ★★★★★ 影響 5 個服務

★★★★★ 整併把「風險集中」了。這是整併必然的副作用，不是可以省略的細節。
```

★★★★ 這個問題**沒有事後的技術解**。能做的是：

```text
a. 誠實把現況寫成一句話給主管：
   「目前架構下，任一台實體主機故障將導致 __ 個服務中斷，
     預估恢復時間 __ 小時（取決於備品到貨與還原時間）。」
b. 提出兩個選項與各自代價：
   選項一：補到 3 節點 + 共用儲存，做 HA（要編硬體與可能的授權預算）
   選項二：接受現況，但把「還原到備援主機」的程序演練到可預期
c. ★★★★★ 讓主管簽核選哪一個。這件事不該由維運人員獨自承擔。
```

【2】★★★★★ HA 有動，但服務仍然中斷 —— **這是 HA 的正常行為。**

```text
一般虛擬化平台的 HA 是這樣運作的：
  Host A 掛了
     ↓ 叢集偵測到（需要時間，通常數十秒到分鐘級）
     ↓ 確認不是網路分割（fencing／quorum 判斷）
     ↓ 在 Host B 上把那些 VM 開機
     ↓ VM 走完整的開機流程（★★★★★ 等同於「被拔電源後重新開機」）
     ↓ 服務起來
```

| 你以為的 HA | 實際的 HA |
| --- | --- |
| 服務不中斷 | ★★★★★ **會中斷**，中斷時間 = 偵測 + 重開機 + 服務啟動 |
| 資料不會壞 | ★★★★ **等同於斷電**，未寫入磁碟的資料會遺失，資料庫可能要跑復原 |
| 全自動 | ★★★★ 需要 quorum、fencing、共用儲存都設定正確才會動 |

★★★★★ **要「真的不中斷」必須靠應用層做**（多節點負載平衡、資料庫複寫），
不是靠 hypervisor → [[120-01-04-svc-雲端-高可用與負載平衡架構]]。

【3】★★★★★ 兩節點叢集失去法定人數。

```text
兩個節點的叢集，一台下線 → 剩下的一台無法判斷
  「是對方掛了」還是「只是網路斷了、對方其實還活著」
→ 為了避免雙方都以為自己是主而造成資料損毀（split-brain），
  ★★★★★ 剩下的節點會拒絕動作

解法：
  a. 加入仲裁節點（QDevice）
  b. 或補到 3 個節點
★★★★ 「兩節點叢集」在設計上就不是可用的 HA 架構。
```

【4】★★★★ 單點故障搬家。★★★★★ **做了 HA 之後，單點故障常常從主機轉移到儲存。**

```text
檢查清單：
  [ ] 共用儲存本身有沒有冗餘？（控制器、電源、路徑）
  [ ] 儲存網路有沒有兩條路？
  [ ] 管理介面掛了會怎樣？★★★★★ 管理介面也是單一失效點
  [ ] 叢集依賴的服務（DNS 等）在不在叢集外？→ 見症狀十四
  [ ] 全部設備在同一個機櫃、同一路電源上嗎？
```

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 單台主機掛掉，全部服務停 | 整併把風險集中了；單節點無高可用 | 補到 3 節點 + 共用儲存；或簽核接受風險並演練還原程序 |
| ★★★★★ 有 HA 但服務仍中斷十幾分鐘 | ★★★★★ HA 是「自動重開」，不是「不中斷」 | 要不中斷得在應用層做多節點；把實際中斷時間寫進 SLA |
| ★★★★★ HA 觸發後資料庫需要跑復原 | HA 等同於斷電 | 資料庫另做應用層備份與複寫；不要只靠 hypervisor |
| ★★★★★ 兩節點叢集，一台重開就整個不能操作 | 失去法定人數（quorum） | 加入 QDevice 仲裁，或補到 3 個節點 |
| ★★★★ HA 設定好了卻不會觸發 | fencing 或共用儲存設定不完整 | 逐項驗證 quorum、fencing、共用儲存；**做一次真的斷電測試** |
| ★★★★ 儲存壞掉，全部 VM 一起停 | 單點故障從主機轉移到儲存 | 儲存與儲存網路都要有冗餘；重畫單點故障圖 |
| ★★★★ 管理介面掛了，什麼都不能做 | ★★★★★ 管理介面是整個環境的單一失效點 | 管理介面的防護與備援等級要高於任一台 VM |
| ★★★ 上了分散式儲存後效能差、常有告警 | 節點數不足、沒有獨立儲存網路、用了不合適的磁碟 | ★★★★★ 先退回標準協定的共用儲存，把分散式儲存當第二階段專案重新規劃 |

**解法**：

1. ★★★★★ **畫一張單點故障圖**：從電源、網路、儲存、主機到管理介面，
   逐個問「這個掛了會怎樣」。這張圖比任何規格書都有說服力。
2. ★★★★ **做一次真的斷電測試**，並記錄實際中斷時間。
   ★★★★★ 沒測過的 HA 等於沒有 HA。
3. ★★★★ 把量到的實際中斷時間寫進 SLA 與需求分級表，
   讓使用單位**事先知道**會停多久 —— 事後解釋永遠來不及。

**原理詳見**：

- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈迷思三：HA（高可用）= 不會斷線〉
- [[050-01-01-03-ref-虛擬化-五平台橫向對照]] 的〈主對照表（三）：叢集與高可用能力〉
- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈Q2 要不要 HA？可接受的停機時間是多久？〉
- [[050-01-03-07-svc-PVE-叢集與高可用]] —— 叢集與 HA 的實際設定

### ★★★★ 症狀十：直通了裝置的那台 VM，維護時才發現搬不走

**現象**：一切正常運作了一年，直到要做主機維護：

```text
按下「線上遷移」→ 灰的，或直接報錯
才發現：這台 VM 因為要跑 GPU（或高流量網卡）而直通了實體裝置
而它偏偏是不能停的系統
```

★★★★★ **這不是故障，是設計限制。**
直通與 SR-IOV **在設計上就不能線上遷移**，這個限制沒有解。

**判斷分流**：

```text
這台 VM 有直通裝置嗎？
  有，且服務可以短暫停機   → 走【1】（關機遷移，可控）
  有，且服務不能停          → 走【2】（★★★★★ 這是設計缺陷，要改架構）
  沒有，但仍不能遷移        → 走【3】（其他原因）
```

**排查步驟**：

【1】★★★★ 可以停機 → 排維護時窗，關機遷移。
★★★★ 記得目標主機上要有**同型的實體裝置**，否則搬過去也開不起來。

【2】★★★★★ 不能停機 —— 這需要改架構，不是改設定。

```text
三個方向（由好到壞）：
  a. ★★★★★ 在應用層做多節點備援
     兩台 VM 各自直通一張卡，前面放負載平衡 →
     維護時把流量切到另一台。這是唯一真正的解。
  b. ★★★★ 重新評估「真的需要直通嗎」
     ★★★★★ 直通的正當理由是「量測證明 VirtIO 撐不住」。
     很多環境的直通是「聽說比較快」就開了，實際上 VirtIO 綽綽有餘。
     → 先量測，撐得住就改回 VirtIO，問題自然消失。
  c. ★★★ 接受它，並把「此 VM 不可線上遷移」寫進維運文件與 SLA
     ★★★★ 至少讓大家事先知道維護時它會停。
```

【3】★★★ 其他不能遷移的原因：目標節點資源不足、儲存不是共用的、
CPU 型別不相容（不同世代的 CPU 之間遷移會有限制）、授權層級不含線上遷移（見症狀一）。

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 直通裝置的 VM 不能線上遷移 | ★★★★★ **這是設計限制，不是故障** | 只能關機遷移；服務不能停就在應用層做多節點備援 |
| ★★★★ SR-IOV 的 VM 也不能線上遷移 | VF 一樣是實體裝置狀態 | 同上。★★★★★ SR-IOV 解決的是「一張卡只能給一台 VM」，不是遷移問題 |
| ★★★★ 直通失敗：群組不可用 | ★★★★★ IOMMU 群組裡還有 host 正在使用的裝置 | 換插槽改變群組；或把群組內其他裝置一併直通（若可行） |
| ★★★★ 直通後 VM 開得起來但裝置沒作用 | host 端驅動仍綁著該裝置 | 用 VFIO 綁定該裝置，並把原廠驅動加入黑名單 |
| ★★★★ 直通裝置的狀態沒被快照記錄 | ★★★★ 直通裝置的狀態無法納入快照 | 依賴應用層備份，不要依賴快照 |
| ★★★★ 重開機後 SR-IOV 的 VF 全部消失 | VF 數量寫在 sysfs，重開會歸零 | 用 udev 規則或開機服務在啟動時重建 VF |
| ★★★ 為了「比較快」而直通，實際沒量測過 | 誤以為直通是免費的效能升級 | ★★★★★ 先量測；VirtIO 撐得住就不要直通 |

**解法**：

1. ★★★★★ **盤點所有直通裝置與對應 VM**，做成一張表，
   欄位包含：VM 名稱、直通了什麼、為什麼直通、**有沒有量測依據**、不能遷移的影響。
2. ★★★★★ **在設計階段就把「用直通 = 放棄線上遷移」寫進文件並簽核。**
   ★★★★ 這件事不能等到維護那天才第一次被提出來。
3. ★★★★ **原則：若服務不能停，就不要直通**；
   不然就在設計時先做應用層的多節點備援。

> [!danger] ★★★★★ 直通還有一個安全面向
> 把裝置交給 VM，等於把 DMA 權限交出去 —— VM 裡的驅動可以叫這張卡往任意實體位址寫資料。
> ★★★★★ **IOMMU 就是防這件事的**，所以直通的前提是 IOMMU 必須啟用且群組乾淨。
> 沒有 IOMMU 的直通不是「效能好」，是「整台 host 隨時可能失守」。

**原理詳見**：

- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈直通（Passthrough）與 IOMMU〉
- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈SR-IOV —— 直通的「可分享版本」〉
- [[050-01-01-03-ref-虛擬化-五平台橫向對照]] 的〈主對照表（七）：硬體直通與進階功能〉

### ★★★ 症狀十一：服務三不五時卡頓，監控圖上記憶體忽高忽低

**現象**：沒有明顯的資源不足，但服務會週期性地卡一下。
監控圖上看到 VM 的可用記憶體忽高忽低，或 host 上有個程序默默吃著 CPU。

**判斷分流**：

```text
  VM 的記憶體用量在監控圖上被「抽走又還回來」  → 走【1】（ballooning）
  host 上有背景程序持續吃 CPU，記憶體用量緩慢下降 → 走【2】（KSM）
  卡頓與備份／快照時段吻合                      → 走【3】
  卡頓與 host swap 有關                         → 回症狀三【2】
```

**排查步驟**：

【1】★★★★ Ballooning 抽走記憶體。

```text
運作方式：
  hypervisor 通知 VM 裡的 balloon 驅動「膨脹」
  → 驅動在客體內配置一大塊記憶體並「佔住」
  → 客體 OS 以為記憶體變少了，開始釋放快取、甚至 swap
  → hypervisor 把這塊實體記憶體收回去給別的 VM

★★★★★ 對「以為自己有那麼多記憶體」的應用（資料庫、Java）特別致命：
  它們啟動時就依配置值規劃了記憶體用量，被抽走之後就是 OOM 或狂 swap。
```

★★★★ 解法很單純：**資料庫與 Java 應用的 VM 不參與超配**，
把 balloon 最小值設成等於配置記憶體（等於關閉 ballooning）。

【2】★★★ KSM（Kernel Same-page Merging）造成的抖動。

```text
KSM 會掃描記憶體，把內容相同的頁面合併成一份（寫入時再分開）。
好處：同質 VM 很多時（例如十台一樣的 Ubuntu）省下可觀的記憶體
代價：
  ★★★ 掃描本身要吃 CPU
  ★★★ 被合併的頁面第一次寫入時要複製，造成延遲抖動
  ★★★★ 記憶體壓力大時 KSM 掃得更兇，於是 CPU 更忙 → 惡性循環
```

★★★ 判斷方式：看負責掃描的核心執行緒有沒有持續佔用 CPU。
★★★★ 如果環境裡的 VM 差異很大（不同 OS、不同用途），KSM 的效益很低，
**開著只是白付 CPU 成本**。

【3】★★★ 卡頓時段與備份／快照吻合 —— 這不是 ballooning 問題。
★★★★ 備份與快照建立當下會有 I/O 影響，
解法是把備份時段錯開、或降低備份的 I/O 優先權。

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ 資料庫 VM 三不五時被 OOM killer 殺掉 | ballooning 把記憶體抽走了 | balloon 最小值設成等於配置記憶體 |
| ★★★ Java 應用啟動後效能不穩 | 堆積大小依配置值設定，實際記憶體被抽走 | 同上；並確認堆積設定與 VM 實際可用記憶體一致 |
| ★★★ host 上有背景執行緒持續吃 CPU | KSM 正在掃描與合併頁面 | VM 異質性高時關閉 KSM；同質性高時保留但監控 CPU 成本 |
| ★★★ 記憶體壓力越大越卡 | ★★★★ KSM 在壓力下掃得更兇，形成惡性循環 | 根治是降低記憶體超配，不是調 KSM 參數 |
| ★★★ 卡頓時段固定，與備份時段吻合 | 備份／快照的 I/O 影響 | 錯開備份時段；降低備份 I/O 優先權 |
| ★★★ 監控圖上 VM 記憶體用量長期偏低，以為可以再塞 VM | balloon 已經在抽了，**看到的不是真實需求** | ★★★★ 用客體內的實際用量判斷，不要只看 hypervisor 端的數字 |

> [!warning] ★★★★ KSM 還有一個安全面向
> KSM 會把**不同 VM 之間**內容相同的頁面合併。
> 這在理論上構成跨 VM 的側通道 —— 透過量測寫入延遲，可以推測另一台 VM 是否持有相同內容。
> ★★★★ 在多租戶或高敏感環境中，這是關閉 KSM 的正當理由。

**解法**：

1. ★★★★ **分級**：把 VM 分成「可參與超配」與「不可參與超配」兩類，
   資料庫與 Java 應用一律放後者。
2. ★★★ **KSM 依環境決定**：VM 同質性高就開，異質性高就關。
   ★★★★ 不要因為「別人都開」而開著。
3. ★★★★ **監控要看客體內的數字**。hypervisor 端顯示的記憶體用量
   在有 ballooning 的環境裡不代表真實需求。

**原理詳見**：

- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈記憶體超配的三個工具〉
- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈Ballooning 怎麼運作〉
- [[050-01-01-02-guide-虛擬化-虛擬化底層技術]] 的〈KSM（Kernel Same-page Merging）〉

### ★★★ 症狀十二：要還原時發現「快照都在，但儲存壞了」

**現象**：★★★★★ **機關最常見的資料遺失模式，沒有之一。**

```text
「這台 VM 有快照，所以不用備份」
    ↓
儲存陣列的 RAID 陣列掛掉
    ↓
★★★★★ 原始磁碟與快照在同一份儲存上，一起消失
```

**判斷分流**：

```text
現在的狀況是？
  儲存還活著，只是 VM 壞了          → 快照可以救，走【1】
  儲存壞了，快照與原始磁碟一起沒了    → 走【2】（★★★★★ 只能靠備份）
  有備份，但從沒還原過               → 走【3】
  完全沒有異地備份                   → ★★★★★ 走【4】，並準備向上呈報
```

**排查步驟**：

【1】★★★ 儲存還在，用快照回復即可。
★★★★ 回復完之後**立刻做兩件事**：刪掉不需要的快照、確認有一份真正的備份。

【2】★★★★★ 儲存沒了。這時候唯一能救的是**在另一份儲存上的備份**。

```text
逐一確認（依可用性排序）：
  [ ] 平台的排程備份寫到哪裡？是不是同一份儲存？
  [ ] 有沒有異地副本？在不在同一棟？
  [ ] 應用層備份（例如資料庫自己的匯出）有沒有？寫到哪裡？
  [ ] 有沒有任何「不在這份儲存上」的資料副本？

★★★★★ 若答案全是「同一份儲存」，那就是沒有備份。
```

【3】★★★★ 有備份但從沒還原過 —— ★★★★★ **沒還原過的備份等於沒有備份。**

```text
還原時你會遇到的四件事（都要算進 RTO）：
  ★★★★ 還原點是磁碟一致，不是應用一致 —— 資料庫可能停在交易中間
  ★★★★★ 還原需要時間 —— 一台大 VM 可能要數十分鐘到數小時
  ★★★★ IP／主機名／授權會衝突 —— 還原到不同環境時重複 IP 與 MAC 會打架
  ★★★★★ 從來沒演練過 —— 最常見的問題
```

【4】★★★★★ 完全沒有可用備份。
這時候的工作不是技術，是**誠實地把狀況與影響寫清楚往上報**，
同時啟動「從零重建」的評估：哪些資料還有其他來源、哪些真的沒了。

★★★★ 事後一定要做的，是把這件事變成制度：

```text
  a. 備份目的地必須在被備份對象之外的儲存上（★★★★★ 這是最低要求）
  b. 每季至少做一次還原演練，並記錄耗時
  c. 資料庫額外做應用層備份，不要只靠 VM 式備份
  d. 異地副本：至少一份在不同棟或不同機房
```

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 儲存壞了，快照跟著沒了 | 快照與原始磁碟在同一份儲存上 | ★★★★★ 建立獨立的備份目的地。快照**不是**備份 |
| ★★★★★ 備份都有跑，真要還原時失敗 | 從未做過還原演練，備份其實是壞的 | ★★★★★ **每季至少一次還原演練並記錄耗時** |
| ★★★★ 還原出來的資料庫不一致 | 還原點是磁碟一致，不是應用一致 | 資料庫額外做應用層備份 |
| ★★★★ 還原花的時間遠超預期 | RTO 沒有把還原時間算進去 | 演練時記錄實際耗時，寫進 SLA |
| ★★★★ 還原到測試環境時 IP／MAC 衝突 | 沒有還原後的組態調整程序 | 把「還原後要改什麼」寫成 SOP |
| ★★★★ 備份放在同一個儲存池上 | 備份目的地規劃錯誤 | ★★★★★ 備份目的地一定要在叢集／儲存之外 |
| ★★★ 快照留了幾個月，VM 越來越慢 | 快照鏈造成寫入放大 | ★★★★ 訂「快照存活不超過 7 天」的規則並排進月維護 |

> [!danger] ★★★★★ 快照的正確用法只有一種
> **動手前開，確認正常後立刻刪。**
> 保留超過數天的快照就是問題，不是保險。

**解法**：

1. ★★★★★ **今天就確認一件事**：備份的目的地跟被備份的東西，在不在同一份儲存上。
   這一題答錯，其他都不用談。
2. ★★★★ **排一次還原演練**，記錄耗時，寫進維運文件
   → [[050-01-03-06-svc-PVE-備份與還原]]。
3. ★★★★ 把「快照存活期上限」與「每季還原演練」寫進維運制度
   → [[100-02-04-guide-維運-每月維護作業]]。

**原理詳見**：

- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈迷思二：快照就是備份〉
- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈迷思六：備份 VM = 備份服務〉
- [[050-01-01-03-ref-虛擬化-五平台橫向對照]] 的〈主對照表（六）：備份方案〉

### ★★★ 症狀十三：選了開源省授權費，三年後回頭算反而更貴

**現象**：當初的簽呈寫著「採用開源方案，可節省授權費用」。
三年後回頭看：

```text
（A）授權費確實是零，但這三年花了大量人力在學習與救火
（B）出事時沒有人可以打電話，每次都靠自己摸索
（C）稽核問「這套軟體的技術支援來源」，答不出來
（D）當初做建置的人離職，接手的人看不懂設定
（E）不敢升級 —— 沒有練習環境，也沒人有把握
```

★★★★★ **「開源＝免費」是選型會議上最貴的一句話。**
開源省下的是**授權費**，但把成本轉移到**人力、時間與風險**上。

**判斷分流**：

```text
先確認問題出在哪一類：
  人力工時遠超預期            → 走【1】（TCO 漏了第 ④ 類）
  出事沒有支援窗口            → 走【2】
  稽核交代不過去              → 走【3】
  交接／文件失傳              → 走【4】
  不敢升級                    → 走【5】
```

**排查步驟**：

【1】★★★★★ TCO 少算了人力。★★★★ 正確的 TCO 一定要有四類，少任何一類都是假的：

| 類別 | 包含什麼 | 常被漏掉的 |
| --- | --- | --- |
| **① 授權** ★★★★★ | 平台授權、管理台授權、備份軟體授權、客體 OS 授權 | ★★★★★ **客體 OS 授權**、備份軟體授權 |
| **② 硬體** ★★★★ | 伺服器、儲存、網路卡、交換器埠、機櫃、UPS 擴充 | ★★★★ **備份目的地的儲存空間**、第二條網路 |
| **③ 維護** ★★★★ | 硬體保固延長、軟體訂閱續約、SI 維護合約 | ★★★★★ **第 4、5 年的保固延長費用** |
| **④ 人力** ★★★★★ | 建置工時、教育訓練、每年例行維運工時、遷移工時 | ★★★★★ **學習曲線**與**交接文件撰寫** |

★★★★ 三條試算表鐵律：

1. **一律算五年，不要只算首年。** 首年最便宜的方案，五年常是最貴的。
2. **人力欄位填「人天」，另欄折算金額。** 換算基準改變時不必重算。
3. ★★★★★ **每一格都要註明來源**（報價單編號／估算依據）。

【2】★★★★ 沒有支援窗口 —— 三選一，**沒有第四個選項**：

```text
  a. 買該平台的商業訂閱（如果有）
  b. 簽 SI 維護合約，讓廠商承接原廠角色
  c. ★★★★★ 寫一份經主管核章的「風險接受文件」，
     明載無原廠支援、由機關自行承擔，以及最壞情況的因應方式
```

★★★★★ **三種都沒有，就是稽核缺失。** c 不用花錢，先把它補起來。

【3】★★★★ 稽核交代 —— 事前備好的三份文件之一（同上）。
★★★★ 這件事**不能等稽核來問才做**。

【4】★★★★ 文件與交接。★★★★★ **開源的設定散在很多地方，離職就失傳。**
解法是把「交接文件」列為**建置工作的一部分並估工時**，不是有空再寫。

【5】★★★★ 不敢升級。根因是「沒有練習環境」。
★★★★ 建置階段就同步建一套練習環境，升級流程寫進年度維護計畫
→ [[050-01-03-13-guide-PVE-建立練習環境]]、[[050-01-03-11-svc-PVE-升級與維護]]。

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 人力工時遠超預期 | TCO 漏了第 ④ 類（人力） | 補算人天：學習曲線以「每人 5～10 人天」為起點 |
| ★★★★★ 上線後才發現要另外買備份軟體 | 只比較平台授權，沒把備份列入成本項 | ★★★★ 備份軟體是必填列，沒有就填 0 並註明原因 |
| ★★★★ 開源方案上線後沒人敢升級 | 沒有維護合約，也沒有練習環境 | 建置階段就同步建練習環境；升級流程寫進年度維護計畫 |
| ★★★★ 稽核問技術支援來源答不出來 | 採用開源但未簽任何支援合約 | 補簽 SI 維護合約；或提出經核章的風險接受文件 |
| ★★★★ 建置的人離職，接手的看不懂 | 交接文件沒被當成工作項目 | 把交接文件列進建置工作並估工時 |
| ★★★★ 第 4、5 年硬體保固沒編到預算 | 只編三年保固，設備服役五年 | 採購時一次買滿服役年限的保固 |
| ★★★★ 商業方案續約時完全沒有議價能力 | ★★★★ 供應商鎖定 —— 東西已經上線了 | 選型時就把「退場難度」列為評估項；保持備份可跨平台還原 |
| ★★★ 選了商業方案卻被迫買整包 | 功能綑綁：為了要那一項，得買整包 | 選型時把「買不到單項」列為風險 |

> [!note] ★★★★★ 開源方案的正確論述方式
> 不要說「開源不用錢」。要說：
> **「這個方案把授權支出換成人力投入，五年下來總持有成本較低，
> 但前提是機關要編列 X 人天的教育訓練，並簽訂維護支援合約來承接原廠角色。」**
> ★★★★★ 這種說法在簽核與稽核時站得住腳，前一種站不住。

**解法**：

1. ★★★★★ **把 TCO 表補完並重算**，四類十三列一項都不能少，人力欄填人天。
2. ★★★★ **今年就補齊「支援來源」文件**：訂閱合約、SI 維護合約，
   或經核章的風險接受文件，三選一。
3. ★★★★ 下一次選型報告改用「有理由的排除」寫法，
   每個未採用方案都寫明「不符合第 X 項需求」。

- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈步驟三：建立 TCO 試算表的四個成本欄位〉

### ★★★★ 症狀十四：停電復電後叢集起不來，管理介面連不上

**現象**：機房停電、UPS 撐完、復電之後：

```text
主機都開機了，但：
  叢集組不起來
  管理介面連不上，或登入失敗
  VM 沒有自動啟動
```

★★★★★ **最經典的一種是雞生蛋問題**：

```text
hypervisor 要 DNS 解析才能組叢集
    ↓ DNS 在 VM 裡
    ↓ VM 要叢集起來才能開機
    ↓ ★★★★★ 卡死
```

**判斷分流**：

```text
  管理介面登入失敗、驗證逾時           → 走【1】（認證依賴外部服務）
  節點之間看不到彼此、叢集無法組成      → 走【2】（名稱解析或網路依賴）
  叢集起來了但 VM 沒自動開             → 走【3】（啟動順序）
  儲存沒上來                          → 走【4】
```

**排查步驟**：

【1】★★★★ 認證依賴外部服務（AD／LDAP）而該服務也在叢集裡。

```text
★★★★★ 這就是為什麼「一定要保留一組本機管理帳號」。
應急：改用本機帳號登入（從主控台／IPMI 進去）
根治：管理介面一定要保留可用的本機管理帳號，並把密碼放進密碼保管程序
```

【2】★★★★★ 節點之間靠名稱解析找彼此，而 DNS 在叢集裡。

```text
應急：直接用 IP 操作，或在各節點的本機 hosts 檔補上其他節點的對應
根治：★★★★★ 叢集節點之間的設定用 IP 或本機 hosts 檔，不要依賴外部 DNS
```

【3】★★★ VM 啟動順序沒設定。
★★★★ 復電後應該先起「基礎服務類」的 VM（DNS、認證、資料庫），
再起應用類的。★★★★ 大多數平台有開機順序與延遲設定，
**這件事應該在建置時就設好並演練過**。

【4】★★★ 儲存沒上來：外接儲存的開機順序比主機慢，
主機開機時掛不到儲存。★★★★ 解法是設定重試與延遲，
或把儲存的復電啟動順序排在主機之前。

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 復電後叢集起不來，管理介面連不上 | DNS／DHCP／AD 全虛擬化在同一個叢集內 | ★★★★★ 保留獨立的 DNS／DC；節點設定用 IP 或本機 hosts |
| ★★★★ 管理介面登入失敗 | 認證依賴的 AD／LDAP 也在叢集裡 | ★★★★★ 保留可用的本機管理帳號 |
| ★★★★ VM 復電後沒有自動啟動 | 沒設開機自動啟動或啟動順序 | 設定自動啟動與順序，並實際演練一次 |
| ★★★★ 應用起來了但連不到資料庫 | 啟動順序錯，應用比資料庫先起來 | 設定啟動延遲；應用端要能重試 |
| ★★★ 主機開機時掛不到外接儲存 | 儲存的開機比主機慢 | 設定掛載重試與延遲；調整設備的復電順序 |
| ★★★ 備份主機也在同一個叢集裡 | 備份目的地規劃錯誤 | ★★★★★ 備份目的地一定要在叢集外 |
| ★★★★ 復電後才發現 UPS 撐不到安全關機完成 | 新主機上架後沒重算 UPS 負載 | 重算 UPS 容量 → [[040-02-05-guide-機房-UPS選型與容量計算]] |

> [!danger] ★★★★★ 「不該虛擬化」的那一條清單，這裡就是它的代價
> 虛擬化平台**本身的依賴元件**（管理叢集用的 DNS／DHCP／AD）
> ★★★★★ **必須放在叢集外**，否則就會出現雞生蛋問題。
> 同理，**備份伺服器**也不該跟被備份的東西在同一份儲存上。

**解法**：

1. ★★★★★ **畫一張「開機依賴圖」**：
   哪個服務要先起來、誰依賴誰、有沒有循環依賴。有循環就要拆。
2. ★★★★ **做一次計畫性的斷電演練**（不是等真的停電），記錄實際恢復時間與卡住的地方。
3. ★★★★ 至少保留一台**不依賴叢集服務**就能單獨開機的 DNS／DC。

**原理詳見**：

- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈什麼情況「不該」虛擬化〉
- [[050-01-01-03-ref-虛擬化-五平台橫向對照]] 的〈管理介面是整個環境的單一失效點〉
- [[050-01-03-07-svc-PVE-叢集與高可用]] —— 叢集啟動與 quorum 的實際行為

### ★★★ 症狀十五：系統出事，廠商第一句話是「你們跑在虛擬化上」

**現象**：某套業務系統出問題，找廠商協助，得到的回覆是：

```text
「我們的系統不支援虛擬化環境」
「請先在實體機上重現問題」
「這個效能問題是虛擬化造成的，不在我們的保固範圍」
```

★★★★★ **這句話一旦說出口，責任就被推回來了** ——
而且很多時候合約裡真的寫了這一條，只是沒人看。

**判斷分流**：

```text
  合約／需求書裡真的寫了「不支援虛擬化」  → 走【1】（★★★★★ 這是採購缺失，要補救）
  合約沒寫，廠商只是口頭這樣說            → 走【2】
  廠商說「只在 VMware 驗證過」            → 走【3】（★★★★ 多半不是技術限制）
  廠商說是效能問題                        → 走【4】（要用數字對話）
```

**排查步驟**：

【1】★★★★★ 合約真的寫了 —— 這是既成事實，只能協商。

```text
  a. 先確認影響範圍：只有這一套系統，還是有其他系統也有同樣條款
  b. 短期：協商廠商在「盡力協助」的前提下先處理當前問題
  c. 中期：兩個選項 ——
       選項一：把這一套搬回實體機（★★★★ 這是「不該虛擬化」清單裡的正解）
       選項二：與廠商重新議定支援條款（通常要付費）
  d. ★★★★★ 長期：把「請提供虛擬化環境支援之書面說明」
     列為所有系統採購的必問項
```

【2】★★★★ 合約沒寫，只是口頭。★★★★ 這時候立場在機關這邊：
要求廠商**以書面說明技術原因**。
★★★★★ 「我們沒測過」與「技術上不支援」是完全不同的兩件事。

【3】★★★★ 「只支援某個特定虛擬化平台」——
★★★★★ 多半是「只在該平台驗證過」，不是技術限制。

```text
  a. 要求廠商書面說明技術原因（★★★★ 通常說不出來）
  b. 在合約中要求提供替代驗證：由廠商在本機關的環境上完成驗證
  c. ★★★★★ 未來的規格書要寫成能力描述，不要跟著綁一家虛擬化平台
```

【4】★★★★ 效能爭議 —— **用數字對話，不要用感覺對話。**

```text
先自己排除虛擬化端的問題（這也是對自己負責）：
  [ ] 磁碟／網卡是不是 VirtIO？          → 症狀六
  [ ] 客體 steal time 多少？              → 症狀三
  [ ] host 有沒有 swap？                  → 症狀三
  [ ] 儲存池用量與磁碟延遲正常嗎？         → 症狀四
  [ ] 有沒有長期未刪的快照？              → 症狀四

★★★★★ 這五項都清白，再把數字拿給廠商。
這時候「虛擬化造成的」就不再是一句可以隨口說的話。
```

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 廠商拒絕支援，理由是「跑在虛擬化上」 | 採購前未取得書面支援聲明 | 採購階段就要求書面確認；已發生時協商或保留實體機 |
| ★★★★ 廠商說「只支援某平台」 | 多半是「只在該平台驗證過」，不是技術限制 | 要求書面說明技術原因；合約中要求提供替代驗證 |
| ★★★★ 授權綁實體特徵（MAC、主機板序號） | 老舊軟體的授權機制 | 採購前確認授權可轉移，取得原廠同意 |
| ★★★★ VM 遷移後軟體要求重新啟用 | 某些軟體把節點間搬動判定為換機器 | 事前確認；必要時把該 VM 排除在自動遷移之外 |
| ★★★★ 資料庫按核心授權，給 8 vCPU 就要買 8 核授權 | 授權以配置的 vCPU 計 | ★★★★★ 配置 vCPU 前先確認授權規則，不要「反正沒差就多給」 |
| ★★★★ 需要特殊實體介面卡或加密鎖 | 這本來就在「不該虛擬化」清單上 | 保留實體機；或確認可用直通並**先實測** |
| ★★★ 極度延遲敏感的系統效能不符預期 | 虛擬化多一層，本來就不適合 | 保留實體機；或用直通 + CPU 綁定並實測 |

**解法**：

1. ★★★★★ **採購前必問**：「這套系統在虛擬化環境下你們支援嗎？請提供書面說明。」
   ★★★★ 這一句話能省掉未來所有的爭議。
2. ★★★★ **把「不該虛擬化」清單當成盤點項目**：
   特殊介面卡、原廠不支援、極度延遲敏感、授權綁實體特徵、
   單一 VM 就吃掉整台機器、平台自身的依賴元件、備份伺服器、沒人維護的環境。
3. ★★★★ **效能爭議先自清**，用數字對話。

**原理詳見**：

- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈什麼情況「不該」虛擬化〉
- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈虛擬化下的授權陷阱〉
- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈Q7 有沒有法規、資安或稽核上的硬性要求？〉

### ★★★★ 症狀十六：平常好好的，一到月底／備份時段全部一起變慢

**現象**：日常監控看起來很健康，平均使用率也不高，
但每逢特定時段（月底結算、每日備份、報表產製）——**全部 VM 一起變慢**。

★★★★★ **原因幾乎都一樣：整併評估時只算了平均負載，沒算尖峰同時發生。**

**判斷分流**：

```text
  變慢的時段固定且可預測（月底、每日凌晨）  → 走【1】（尖峰重疊）
  變慢的時段與備份時段吻合                  → 走【2】
  沒有規律，隨機發生                        → 回症狀三的三題分流
  只有某一台 VM 慢                          → 症狀六
```

**排查步驟**：

【1】★★★★★ 尖峰重疊。**把每台 VM 的尖峰時間畫在同一條時間軸上。**

```text
時間軸（示意）：
  00:00 ─────────────────────────────────────── 24:00
  srv-db      ████ 01:00-03:00 資料庫備份與統計
  srv-batch   ███  01:30-02:30 每日批次
  srv-file    ██   02:00-03:00 檔案同步
  srv-report        ████ 02:00-04:00 月底報表
                 ↑
        ★★★★★ 02:00-02:30 四件事全部撞在一起
```

★★★★ 解法通常不用花錢：**把排程錯開**。
這是整併後最划算的一項優化。

【2】★★★★ 備份時段的 I/O 影響。

```text
  a. 錯開備份時段（不同 VM 分批備）
  b. 降低備份的 I/O 優先權（若平台支援）
  c. ★★★★ 如果備份寫到同一份儲存上，那影響會更大 ——
     這同時也是症狀十二的問題
```

【3】★★★★ 評估方法本身要改。★★★★★ **整併比由三個上限中最嚴格的那一個決定**：

```text
整併比 = MIN( CPU 允許的台數, 記憶體允許的台數, 儲存允許的台數 )
```

| 資源 | 算法 | 常見瓶頸程度 |
| --- | --- | --- |
| **CPU** | 實體邏輯核心數 × 允許超配倍率 ÷ 每台 VM 的 vCPU 數 | ★★ 通常不是瓶頸 |
| ★★★★★ **記憶體** | （實體記憶體 − host 保留）÷ 每台 VM 記憶體 | ★★★★★ **九成以上的情況瓶頸在這裡** |
| **儲存 IOPS** | 儲存能提供的 IOPS ÷ 每台 VM 需要的 IOPS | ★★★★ 用機械硬碟時會是瓶頸 |
| **儲存容量** | 可用容量 ÷ 每台 VM 佔用 | ★★★ |

★★★★★ **評估時要看歷史監控的尖峰值與尖峰時間分布，不是月平均值。**
★★★★★ **買虛擬化主機時，記憶體永遠先買滿，CPU 核心數不必衝頂。**

**可能原因**：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ 整併後尖峰時段所有 VM 一起變慢 | 只算了平均負載，沒算尖峰同時發生 | 看歷史監控的**尖峰值**與**尖峰時間分布**；錯開排程作業 |
| ★★★★ 備份時段全體變慢 | 備份的 I/O 影響 | 錯開備份時段；降低備份 I/O 優先權 |
| ★★★★ 主機規格「照平均值」買，上線就不夠 | 用月平均使用率推算需求 | ★★★★★ 用尖峰值推算，並乘上成長係數 |
| ★★★★ 記憶體先撞牆，CPU 還很閒 | 記憶體是九成情況下的真正瓶頸 | 記憶體一次買到位；★★★★ 事後加記憶體通常比一開始買貴 |
| ★★★ 整併後網路變成瓶頸 | 整併後單台主機流量集中 | 評估網路卡與交換器埠是否要升級 |
| ★★★ 沒有留成長餘裕，兩年就滿 | 估算時沒乘成長係數 | 估算時加入三～五年成長係數與 N+1 餘裕 |
| ★★★★ 壞一台之後剩下的撐不住 | 沒有做 N+1 驗算 | ★★★★★ 節點數要驗算「壞一台後剩下的能不能承載全部負載」 |

**解法**：

1. ★★★★ **先做免費的那一件事**：把排程錯開。
   ★★★★★ 這通常能解決一半以上的「尖峰同時變慢」問題。
2. ★★★★ **重新用尖峰值算一次容量**，並補上成長係數與 N+1 驗算。
3. ★★★★ 把「尖峰時間分布圖」列進年度容量檢討的固定產出，
   → [[100-01-03-guide-日誌-系統監控與告警]]。

**原理詳見**：

- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈整併比（Consolidation Ratio）怎麼算〉
- [[050-01-01-01-guide-虛擬化-虛擬化概念與選型]] 的〈第 6 步：推算 Host 規格〉
- [[050-01-01-04-guide-虛擬化-機關選型與授權成本]] 的〈再算節點數（關鍵：要留 N+1 餘裕）〉
