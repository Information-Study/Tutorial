# 虛擬化底層技術

> [!abstract] 這篇你會學到

>   到底補上了哪一塊 —— 懂這個才知道為什麼 BIOS 那個開關沒開就什麼都跑不動
> - ★★★★ **VM Exit** 是虛擬化世界唯一真正貴的東西，所有效能調校都在減少它
> - ★★★★★ **EPT／NPT 二階分頁**解決了什麼、為什麼沒有它的年代虛擬化記憶體會慢一個數量級
> - ★★★★ 記憶體虛擬化的三個工具 —— **ballooning**、**KSM**、**swap**，

> - ★★★★★ I/O 的三條路徑：**全模擬 → 半虛擬化（VirtIO）→ 直通（passthrough／SR-IOV）**，
>   效能一路上升、彈性一路下降，**選錯就是白花錢或永遠不能線上遷移**
> - ★★★★ 磁碟格式 **raw／qcow2／VMDK** 的差別，以及 **寫入放大**是怎麼把一次 4K 寫入
>   放大成好幾次實體寫入的
> - ★★★★★ **超配（overcommit）的代價與安全比例** —— CPU 可以超配、記憶體要非常小心、
>   儲存超配（thin）是機關最常見的整機停機原因
> - ★★★★ **巢狀虛擬化**怎麼運作、什麼時候該用、為什麼不要拿它跑正式服務

## 觀念說明

### ★★★★★ 為什麼 x86 本來做不到虛擬化

要讓一台機器同時跑好幾個作業系統，必須滿足一個條件：

> **客體作業系統想做「只有作業系統才能做的事」時，必須被攔下來，
> 交給 hypervisor 去決定要怎麼假裝完成它。**

CPU 有特權等級（x86 上叫 ring 0～ring 3）。作業系統核心跑在 ring 0，
一般程式跑在 ring 3。ring 3 的程式如果執行特權指令，CPU 會丟出例外（trap），
核心接手處理 —— 這就是攔截。

虛擬化的做法很自然：**把客體作業系統降到 ring 1 或 ring 3 去跑，
它一執行特權指令就會 trap，hypervisor 就在那裡等著。** 這叫 **trap-and-emulate**。

★★★★★ **問題是 x86 有一票「敏感但不會 trap」的指令。**
最經典的例子是 `POPF`：它會嘗試修改 EFLAGS 中的中斷旗標（IF）。
在 ring 0 執行會真的改；**在 ring 3 執行不會報錯，它只是安靜地不做那件事**。

於是客體核心以為自己關掉了中斷，實際上沒有，而且沒有任何人被通知。
★★★★★ **不會 trap，就攔不到，就沒辦法正確虛擬化** —— 這是 1974 年
Popek 與 Goldberg 提出的可虛擬化條件，而 x86 在早年並不滿足它。

#### ★★★★ 三代解法

| 世代 | 做法 | 原理 | 代價 |
| --- | --- | --- | --- |
| 第一代 | **二進位轉譯**（Binary Translation） | ★★★★ 在執行前掃描客體核心的指令流，把有問題的指令**改寫**成安全的等價序列 | 轉譯有 CPU 成本、實作極複雜、除錯困難 |
| 第二代 | **半虛擬化**（Paravirtualization） | ★★★★ 改客體核心的原始碼，把特權操作換成「主動呼叫 hypervisor」（hypercall） | ★★★★★ **必須改客體 OS**，閉源系統（Windows）無解 |
| 第三代 | **硬體輔助**（VT-x／AMD-V） | ★★★★★ CPU 直接多開一個「給客體用的執行模式」，敏感指令在該模式下**一定會**交出控制權 | 幾乎沒有代價，成為今日唯一主流 |

> [!note] ★★★★ 為什麼「半虛擬化」這個詞今天還會出現？
> 因為它沒有死，只是**從 CPU 搬到了 I/O**。
> 今天沒有人再用半虛擬化處理 CPU 指令（硬體做得更好），
> 但**磁碟與網卡的半虛擬化（VirtIO）仍然是效能的關鍵**，見下方 I/O 段落。
> ★★★★ 看到「半虛擬化」，現在幾乎都是在講 VirtIO，不是在講 CPU。

### ★★★★★ CPU 硬體輔助：VT-x／AMD-V 做了什麼

Intel VT-x 與 AMD-V（早期叫 AMD-SVM）的核心想法一樣，名詞不同：

| 概念 | Intel 名稱 | AMD 名稱 |
| --- | --- | --- |
| 技術總稱 | **VT-x** | **AMD-V／SVM** |
| 進入客體模式的指令 | `VMLAUNCH` / `VMRESUME` | `VMRUN` |
| 狀態儲存結構 | **VMCS**（VM Control Structure） | **VMCB**（VM Control Block） |
| 二階分頁 | **EPT**（Extended Page Tables） | **NPT／RVI**（Nested Page Tables） |
| I/O 位址轉換 | **VT-d** | **AMD-Vi／IOMMU** |
| CPU 旗標名稱 | `vmx` | `svm` |

★★★★★ **最重要的一件事：CPU 多了一個維度。**
原本只有 ring 0～3；現在變成兩組 ring 0～3：

| 模式 | 誰在跑 | 說明 |
| --- | --- | --- |
| **VMX root**（根模式） | ★★★★ hypervisor（KVM／ESXi／Hyper-V） | 真正掌管硬體的那一層 |
| **VMX non-root**（非根模式） | ★★★★ 客體 OS 與客體上的所有程式 | ★★★★★ 客體核心可以「真的」跑在它自己的 ring 0，**不需要被降級、不需要被改寫** |

這解決了敏感指令的問題：**在 non-root 模式下，那些不會 trap 的指令現在會強制交出控制權。**

#### ★★★★★ VM Exit —— 虛擬化世界唯一真正貴的東西

客體在 non-root 模式下全速執行，直到它做了一件 hypervisor 需要介入的事，
CPU 就會發生 **VM Exit**：暫停客體、把 CPU 狀態存進 VMCS、切回 root 模式，
讓 hypervisor 處理，處理完再 **VM Entry** 回去。

★★★★★ **一次 VM Exit 的成本，大約是普通函式呼叫的好幾個數量級。**
它會弄髒快取、可能刷掉 TLB，而且是同步阻塞的。

| 會造成 VM Exit 的動作 | 頻率 | 備註 |
| --- | --- | --- |
| ★★★★★ **存取被模擬的 I/O 埠／MMIO**（模擬網卡、模擬磁碟控制器） | 極高 | **這就是全模擬裝置慢的根本原因** |
| ★★★★ **CPUID** 指令 | 中 | 必須回報「虛擬的」CPU 資訊 |
| ★★★★ 寫入某些控制暫存器（CR3 換頁表等） | 高（無 EPT 時） | ★★★★★ EPT 出現後大幅減少，見下段 |
| ★★★ 存取 APIC（中斷控制器） | 高 | 新 CPU 有 APICv／AVIC 硬體加速可省掉 |
| ★★★ `HLT`（客體閒置） | 中 | 客體閒著時把 CPU 讓出來 |
| ★★★ 外部中斷抵達 | 依負載 | 網卡收封包會產生大量中斷 |

★★★★★ **所有虛擬化效能調校，本質上都在做同一件事：減少 VM Exit 次數。**
VirtIO 減少的是 I/O 造成的 exit；EPT 減少的是換頁造成的 exit；
直通則是把整條路徑上的 exit 全部拿掉。

> [!warning] ★★★★★ BIOS／UEFI 裡沒開虛擬化，什麼都不用談
> 現代 hypervisor **完全依賴** VT-x／AMD-V，沒有它就無法啟動 VM。
> Intel 平台通常叫 `Intel Virtualization Technology` 或 `Intel VT`，
> AMD 平台通常叫 `SVM Mode` 或 `AMD-V`。
> ★★★★ 有些機器**改完要完全斷電再開**（不是重開機）才會生效，因為設定要在 CPU 重新上電時載入。

### ★★★★★ 記憶體虛擬化與二階分頁（EPT／NPT）

一般作業系統上，記憶體只需要一次轉換：

```text
程式看到的虛擬位址（VA） --[頁表]--> 實體位址（PA）
```

虛擬化之後變成兩層：

```text
客體程式的虛擬位址（GVA）
      --[客體頁表，由客體 OS 維護]-->
客體以為的實體位址（GPA）
      --[誰來轉？]-->
真正的機器實體位址（HPA）
```

★★★★★ **客體 OS 以為 GPA 是真的實體記憶體，但那是假的。**
第二層轉換必須有人負責。

#### ★★★★ 舊做法：影子頁表（Shadow Page Table）

沒有硬體支援的年代，hypervisor 自己維護一份「GVA 直接對到 HPA」的影子頁表，
把它塞給 CPU 的 MMU 用。

★★★★★ **代價非常大**：客體 OS 每次修改自己的頁表（行程切換、malloc、mmap、
寫時複製…）hypervisor 都必須攔截並同步更新影子頁表 —— 每一次都是一個 VM Exit。
記憶體壓力大、行程切換頻繁的工作負載（例如編譯、資料庫）會慢到不能接受。

#### ★★★★★ 現在的做法：EPT／NPT 二階分頁

CPU 的 MMU 直接支援兩層頁表：

| 層 | 誰維護 | 內容 |
| --- | --- | --- |
| 第一層 | ★★★ **客體 OS**（hypervisor 完全不管） | GVA → GPA |
| 第二層 | ★★★★ **hypervisor**（EPT／NPT 表） | GPA → HPA |

★★★★★ **關鍵好處：客體愛怎麼改自己的頁表就怎麼改，不會產生 VM Exit。**
記憶體密集型負載的效能因此逼近實體機。

★★★ 代價是 **page walk 變長**：TLB 沒命中時，硬體要走兩層頁表，
最壞情況的查表次數是原本的數倍。所以：

> [!tip] ★★★★ 大頁（Huge Pages）在虛擬化下的價值比在實體機上更高
> 用 2 MB 或 1 GB 大頁可以大幅減少頁表層數與 TLB 壓力，
> **在二階分頁下效果被放大**。資料庫類 VM 值得考慮，
> ★★★ 但大頁通常**不能 swap、不能 ballooning**，等於把那塊記憶體釘死，
> 要先確定你不打算超配這台機器的記憶體。

### ★★★★★ 記憶體超配的三個工具

Hypervisor 想「發出去的記憶體比實際有的多」，手上只有這幾招：

| 工具 | 原理 | 風險 | 重要度 |
| --- | --- | --- | --- |
| **Ballooning（氣球）** | 客體裡的 balloon 驅動向客體 OS 要記憶體，要到後告訴 hypervisor「這塊沒人用」，hypervisor 就收回去 | ★★★★ 客體必須裝驅動；客體會突然覺得自己記憶體變少 | ★★★★ |
| **KSM／頁面共用** | 掃描實體記憶體，把內容相同的頁合併成一份，寫入時再分開（CoW） | ★★★ 掃描吃 CPU；有側通道疑慮 | ★★★ |
| **Host swap** | 把 VM 的記憶體換到宿主機磁碟 | ★★★★★ **災難級的慢**，見下方 | ★★★★★ |

#### ★★★★ Ballooning 怎麼運作

想像 VM 裡有一顆氣球：

1. Host 記憶體吃緊 → hypervisor 叫 VM 裡的 balloon 驅動「充氣」
2. balloon 驅動向**客體 OS** 申請一大塊記憶體（就像一個普通程式在 malloc）
3. 客體 OS 為了給出這塊記憶體，會自己去回收快取、必要時把不常用的頁換出到**客體自己的 swap**
4. balloon 驅動拿到後告訴 hypervisor：「這些位址我佔住了，你可以把對應的實體頁收走」
5. hypervisor 收回實體記憶體給別的 VM 用

★★★★★ **重點：決定「犧牲什麼」的是客體 OS，不是 hypervisor。**
這比 host swap 好太多 —— 客體知道哪些頁是可丟棄的檔案快取，
而 hypervisor 從外面看只是一堆看不懂的位元組，很可能換出 VM 正在熱用的頁。

| 事實 | 說明 |
| --- | --- |
| ★★★★ 需要客體驅動 | Linux 是 `virtio_balloon` 模組；Windows 要裝 VirtIO 驅動與 guest agent |
| ★★★★ 只能「借」不能「無中生有」 | 客體本來就用滿的記憶體，氣球吹不起來 |
| ★★★★★ **反應速度慢** | 從決定收回到真正收回可能要數秒到數十秒，**擋不住突發的記憶體暴衝** |
| ★★★ 客體看到的 `free` 會變 | 客體會顯示有一大塊記憶體被某個「程式」佔用，這是正常的 |

> [!warning] ★★★★ 不要對「不能忍受記憶體變少」的 VM 開 ballooning
> 資料庫（MySQL／PostgreSQL）會在啟動時決定 buffer pool 大小，
> Java 應用會決定堆積大小。★★★★★ **氣球把記憶體抽走後，
> 這些程式不會縮小，只會開始瘋狂 swap 或被 OOM killer 殺掉。**
> 這類 VM 應該把 balloon 的最小值設成等於配置值（等於關閉 ballooning）。

#### ★★★ KSM（Kernel Same-page Merging）

Linux 核心的一個背景執行緒（`ksmd`）持續掃描標記為可合併的記憶體區域，
把內容一模一樣的頁合併成一份，並標成寫時複製。

★★★★ **什麼時候有效？** 跑很多台**相同 OS、相同版本、相同套件**的 VM 時效果最好 ——
例如 20 台一樣的 Ubuntu 22.04 範本複製出來的 VM，核心映像、共用函式庫幾乎完全相同。

★★★ **什麼時候沒用？** VM 種類雜、記憶體大多被資料庫資料佔滿、
或已經開了大頁（大頁通常不參與 KSM）。

| 觀察點 | 檔案 |
| --- | --- |
| KSM 是否啟用 | `/sys/kernel/mm/ksm/run`（1＝跑） |
| 合併後省下多少 | `/sys/kernel/mm/ksm/pages_sharing` |
| 被當成範本的頁數 | `/sys/kernel/mm/ksm/pages_shared` |
| 每次掃描的頁數 | `/sys/kernel/mm/ksm/pages_to_scan` |
| 掃描間隔（毫秒） | `/sys/kernel/mm/ksm/sleep_millisecs` |

★★★★ Proxmox VE 內建 `ksmtuned` 服務，會在記憶體吃緊時自動加大掃描力道、
寬鬆時降低，**預設就是開著的**。

#### ★★★★★ Host swap —— 唯一你絕對不想踩到的那條線

當 ballooning 來不及、KSM 省不出來，hypervisor 只剩最後一招：
把 VM 的記憶體頁寫到宿主機磁碟。

★★★★★ **這是虛擬化環境中最糟糕的狀態，沒有之一。** 原因：

1. 客體 OS **完全不知道**自己的記憶體被換出去了，它以為那是零延遲的 RAM
2. 於是它會把「其實在磁碟上」的頁當成快取來用，一碰就卡住整個 vCPU
3. 換出的可能正好是客體核心的熱區，造成 **double paging**：
   ★★★★★ hypervisor 把頁換出 → 客體自己也想把同一頁換出 →
   hypervisor 得先把它換**回來**才能讓客體換出去，白做兩趟 I/O
4. 症狀是**整台 host 上所有 VM 一起變慢**，而每台 VM 內部看起來都很正常，
   極難診斷

★★★★★ **判斷方法：在 host 上看 swap 使用量與 `si/so`。只要 hypervisor 開始持續 swap，
就是容量規劃已經失敗，要立刻遷移 VM 或關掉不重要的 VM，不是去調參數。**

### ★★★★★ I/O 虛擬化的三條路徑

這是本篇最實用的一段。VM 要碰磁碟與網卡，只有三種走法：

| | 路徑一：全模擬 | 路徑二：半虛擬化（VirtIO） | 路徑三：直通（Passthrough） |
| --- | --- | --- | --- |
| **客體看到什麼** | 一張真實存在過的老硬體（Intel e1000、IDE 控制器、LSI SAS） | 一個「明擺著是虛擬的」裝置（`virtio-net`、`virtio-blk`、`virtio-scsi`） | ★★★★ **真正的實體裝置**（就是那張卡） |
| **要不要裝驅動** | ★★★★ 不用，所有 OS 內建 | ★★★★ Linux 內建；**Windows 必須另外裝 VirtIO 驅動** | 要裝**原廠驅動**（跟實體機一樣） |
| **怎麼運作** | hypervisor 逐個暫存器模擬那張卡的行為 | 客體與 hypervisor 共用一段記憶體環形佇列（virtqueue），批次交換請求 | 由 IOMMU 直接把裝置的 DMA 對應到該 VM 的記憶體 |
| **VM Exit 量** | ★★★★★ 極高（每個暫存器存取一次） | ★★★ 低（多筆請求合併成一次通知） | ★★ 幾乎沒有 |
| **CPU 成本** | ★★★★★ 高 | ★★★ 中低 | ★★ 最低 |
| **吞吐與延遲** | 最差 | 好，一般負載綽綽有餘 | 最好，接近實體機 |
| **能不能線上遷移** | ✅ 可以 | ✅ **可以** | ❌ ★★★★★ **不行**（裝置搬不走） |
| **能不能超配該裝置** | ✅ | ✅ | ❌ 一張卡只能給一台 VM |
| **能不能快照** | ✅ | ✅ | ★★★★ 直通裝置的狀態無法納入快照 |
| **典型用途** | 安裝 OS 的過渡期、老舊系統、無驅動的環境 | ★★★★★ **99% 的 VM 都該用這個（本手冊預設）** | GPU 運算、10G/25G 高流量、儲存 HBA、加密卡 |

> [!note] ★★★★★ 一句話的選擇原則
> **預設一律 VirtIO。只有在「量測證明 VirtIO 撐不住」時才考慮直通，
> 而且要接受從此不能線上遷移、不能用一般方式做快照。**
> 用全模擬的唯一正當理由是：客體 OS 老到沒有 VirtIO 驅動。

#### ★★★★ VirtIO 為什麼快

全模擬的網卡，客體驅動要寫 5 個暫存器才能送出一個封包 —— 那是 5 次 VM Exit。
VirtIO 改成：客體把「要送的封包描述」寫進一段與 hypervisor 共用的環形佇列，
累積一批之後才敲一次門（kick）。

★★★★ **本質是「把很多次昂貴的同步呼叫，換成一次非同步批次通知」。**
這也是為什麼 VirtIO 在高負載下的效率優勢比低負載時更明顯。

| VirtIO 裝置 | 用途 | 備註 |
| --- | --- | --- |
| `virtio-net` | 網路卡 | ★★★★ 預設選它 |
| `virtio-blk` | 區塊裝置 | 簡單、快；★★★ 但一台 VM 能掛的數量有限 |
| `virtio-scsi` | SCSI 控制器 | ★★★★ **PVE 的建議值**：支援更多磁碟、支援 discard/TRIM、支援直通實體磁碟 |
| `virtio-balloon` | 記憶體氣球 | 見上一節 |
| `virtio-rng` | 亂數來源 | ★★★ VM 開機初期熵不足時很有用（憑證產生、SSH 金鑰） |
| `virtio-gpu` | 顯示 | 桌面型 VM |

> [!warning] ★★★★★ Windows VM 的第一個坑
> Windows 安裝程式**看不到 VirtIO 磁碟**，因為它沒有內建驅動。
> 結果是「安裝時找不到任何硬碟」。
> 正解是：安裝時掛第二台光碟機載入 **virtio-win 驅動 ISO**，
> 在選擇磁碟的畫面按「載入驅動程式」。
> ★★★★ 不要為了省事改用 IDE/SATA 全模擬裝完就算了 —— 那台 VM 會慢一輩子。

#### ★★★★ 直通（Passthrough）與 IOMMU

直通的前提是 **IOMMU**（Intel 叫 VT-d、AMD 叫 AMD-Vi）。

★★★★★ **為什麼一定要 IOMMU？** 因為 PCIe 裝置會做 DMA —— 直接寫記憶體。
如果把一張卡交給 VM，VM 裡的驅動可以叫這張卡「往任意實體位址寫資料」，
那它就能改寫 hypervisor 的記憶體，**整台 host 立刻失守**。
IOMMU 的作用就是在裝置與記憶體之間加一層位址轉換與權限檢查，
把裝置能碰到的範圍限制在那台 VM 的記憶體內。

★★★★ **IOMMU 群組（group）** 是直通最常卡住的地方：
硬體把互相之間可以繞過 IOMMU 直接通訊的裝置放在同一群組，
★★★★★ **直通的最小單位是一整個群組，不是一張卡**。
如果你的網卡和 SATA 控制器被分在同一組，你就得連 SATA 控制器一起交出去 ——
通常那不可行，因為 host 自己要用。

#### ★★★★ SR-IOV —— 直通的「可分享版本」

單張卡直通的致命缺點是：一張卡只能給一台 VM。
**SR-IOV**（Single Root I/O Virtualization）讓一張支援的實體卡在硬體層面
把自己切成多個獨立的 PCIe 功能：

| 名詞 | 意義 |
| --- | --- |
| **PF**（Physical Function） | ★★★ 完整的實體卡本體，host 拿著它做設定 |
| **VF**（Virtual Function） | ★★★★ 由 PF 切出來的輕量功能單元，**每個 VF 可以直通給一台 VM** |

| 特性 | 說明 |
| --- | --- |
| ★★★★ 效能 | 接近單卡直通，因為資料路徑完全不經過 hypervisor |
| ★★★★★ **仍然不能線上遷移** | VF 一樣是實體裝置狀態，**這個限制沒有解** |
| ★★★★ 需求 | 卡要支援、主機板／BIOS 要支援、要開 IOMMU、VF 數量上限由卡決定 |
| ★★★ 功能限制 | VF 的功能通常比 PF 少（VLAN、混雜模式、統計等可能受限） |
| ★★★ 適用 | 高頻交易、NFV、需要極低延遲的網路節點 |

> [!danger] ★★★★★ 決定用直通或 SR-IOV，等於決定放棄「線上遷移」
> 這件事必須在**設計階段**就講清楚並寫進文件。
> 常見的災難是：某台 VM 因為要跑 GPU 而直通了顯卡，一年後要做主機維護，
> 才發現這台 VM **不能線上遷移，只能關機搬**，而它偏偏是不能停的系統。
> ★★★★ 若服務不能停，就不要直通；不然就在設計時先做應用層的多節點備援。

### ★★★★ 儲存格式與寫入放大

#### 三種常見格式

| 格式 | 出身 | 精簡配置 | 內建快照 | 效能 | 適合 |
| --- | --- | --- | --- | --- | --- |
| **raw** | 通用 | ★★★ 靠檔案系統／LVM 的稀疏支援 | ❌（要靠下層 LVM／ZFS） | ★★★★ **最快，沒有中介層** | ★★★★ 正式環境、下層已有 ZFS／LVM-thin |
| **qcow2** | QEMU | ✅ 原生 | ✅ 原生（內部快照） | ★★★ 稍慢，有中繼資料查表 | ★★★★ 檔案式儲存（ext4/xfs 上的目錄）、要格式內快照 |
| **VMDK** | VMware | ✅（thin provisioned） | ✅（透過 delta 檔） | ★★★ | ★★★★ VMware Workstation／ESXi |
| VHD/VHDX | Microsoft | ✅ | ✅ | ★★★ | Hyper-V；★★ 本手冊只在遷移時會遇到 |

> [!tip] ★★★★ 在 Proxmox VE 上該選什麼？
> ★★★★ **儲存後端決定了格式，不是你在下拉選單裡隨便選**：
> - **ZFS** 或 **LVM-thin** 後端 → 用 **raw**（快照由下層負責，效能最好）
> - **目錄（Directory）**後端 → 用 **qcow2**（否則沒有快照可用）
> - **Ceph RBD** → 由 RBD 本身處理，格式欄位不適用
> 詳見 [[050-01-03-02-guide-PVE-儲存設定]]。

#### ★★★★ 寫入放大（Write Amplification）

客體裡的一次 4 KB 寫入，到了實體磁碟上可能變成好幾次寫入。每一層都會放大：

| 層 | 放大原因 | 重要度 |
| --- | --- | --- |
| 客體檔案系統 | 資料 + inode + journal | ★★★ |
| 客體磁碟分割未對齊 | ★★★★ 一次邏輯寫跨到兩個實體區塊 | ★★★★ |
| qcow2 | ★★★★ 首次寫入某叢集要先**配置叢集並更新 L1/L2 對照表**（多一次中繼資料寫入） | ★★★★ |
| 快照鏈 | ★★★★★ 每寫一個未修改過的區塊，要先把原始內容複製出去（CoW） | ★★★★★ |
| ZFS／LVM-thin | 寫時複製 + 中繼資料更新 | ★★★ |
| RAID 5／6 | ★★★★★ 小寫入要「讀舊資料 + 讀舊校驗 + 寫新資料 + 寫新校驗」＝**四次 I/O** | ★★★★★ |
| SSD 韌體 | 抹除區塊比寫入頁大，垃圾回收會搬移資料 | ★★★ |

★★★★★ **最實務的結論兩條：**

1. **快照留越久，寫入放大越嚴重，VM 越慢。**
   這是「快照不是備份」之外，快照必須盡快刪掉的第二個理由。
2. ★★★★★ **虛擬化平台上不要用 RAID 5／RAID 6 承載大量隨機小寫入的 VM。**
   資料庫 VM 尤其致命。要嘛用 RAID 10，要嘛用 ZFS 搭配足夠的寫入快取設計。
   詳見 [[010-01-07-guide-計概-磁碟格式化與RAID入門]]。

#### ★★★★ 磁碟快取模式

QEMU 的 `cache=` 決定資料在 host page cache 中怎麼待：

| 模式 | host 快取 | 客體寫入回報「完成」時資料在哪 | 掉電風險 | 建議 |
| --- | --- | --- | --- | --- |
| `none` | 不用（O_DIRECT） | 已交給儲存裝置 | 低 | ★★★★ **正式環境預設**，也是線上遷移的常見要求 |
| `writeback` | 用 | ★★★★ 還在 host 記憶體裡 | ★★★★ 中（host 掉電會丟） | 效能好，只用在可容忍的場合 |
| `writethrough` | 用（讀） | 已落地 | 低 | 寫入慢 |
| `directsync` | 不用 | 已落地 | 最低 | 最保守 |
| `unsafe` | 用，且**忽略客體的 flush 要求** | ★★★★★ 不保證 | ★★★★★ **極高** | ★★★★★ **只用在「壞了就重灌」的批次安裝**，正式環境絕對禁止 |

### ★★★★★ 超配（Overcommit）的代價與安全比例

這是整篇最需要背下來的一段。**三種資源的超配特性完全不同**：

| 資源 | 能不能超配 | 超配過頭的症狀 | 症狀是否可逆 |
| --- | --- | --- | --- |
| **CPU** | ★★★★ **可以，而且應該** | 變慢、延遲抖動、steal time 上升 | ✅ 可逆，關掉幾台就好 |
| **記憶體** | ★★★★ **可以，但要非常小心** | ★★★★★ host swap → 全體雪崩 → OOM killer 殺 VM | ⚠️ 部分不可逆（VM 被砍） |
| **儲存（thin）** | ★★★★ 可以，但**風險最高** | ★★★★★ **儲存池寫滿 → 所有 VM 磁碟同時變唯讀或當機** | ❌ ★★★★★ **可能造成資料損毀** |

#### ★★★★ CPU 超配

vCPU 不是實體核心的預約，它是「一個可以被排程到實體核心上的執行緒」。
只要不是所有 VM 同時全速跑，超配完全合理。

| 情境 | 建議 vCPU 總數 : 實體執行緒數 | 說明 |
| --- | --- | --- |
| 開發／測試／內部工具 | ★★★ **4:1 ～ 8:1** | 大部分時間閒置，超配效益最高 |
| 一般正式服務（網站、AP） | ★★★★ **2:1 ～ 4:1** | 常見的甜蜜點 |
| 資料庫、即時性服務 | ★★★★ **1:1 ～ 2:1** | 延遲抖動不可接受 |
| 即時運算／VDI 高負載 | ★★★★★ **不超配，甚至保留專屬核心** | — |

> [!warning] ★★★★★ 監控 CPU 超配的唯一正確指標：**steal time**
> 在**客體 Linux 裡**執行 `top` 或 `vmstat`，看 CPU 行的 `st` 欄位。
> 它的意思是「我想跑，但 hypervisor 沒給我實體核心」。
> - `st` 持續 **0～2%**：健康
> - `st` 持續 **> 5%**：★★★★ 已經開始影響體感，要檢討配置
> - `st` 持續 **> 10%**：★★★★★ 嚴重超賣，使用者一定在抱怨
> **不要只看 host 的 CPU 使用率** —— host 顯示 60% 時客體仍可能有高 steal，
> 因為問題常常出在排程延遲而不是總量。

> [!danger] ★★★★★ 給單一 VM 太多 vCPU 反而更慢
> 很多 hypervisor 傾向讓一台 VM 的所有 vCPU **同時**取得實體核心（co-scheduling／gang scheduling）。
> 一台 16 vCPU 的 VM 在一台總共 16 執行緒的 host 上，
> ★★★★★ **必須等到 16 個執行緒同時有空才跑得動**，於是它反而比 4 vCPU 的 VM 更常卡住。
> **原則：vCPU 給到夠用就好，不要「反正沒差就多給一點」。**

#### ★★★★★ 記憶體超配

★★★★★ **記憶體與 CPU 最大的不同：CPU 慢下來只是慢，記憶體不夠是會死人的。**
一個程式拿不到記憶體不會「慢慢跑」，它會直接失敗或被殺掉。

| 情境 | 建議上限（配置總量 : 實體 RAM） | 說明 |
| --- | --- | --- |
| ★★★★★ **正式環境保守做法** | **1 : 1（不超配）** | 加上 host 自己的保留，實際只配置到實體的 80% |
| ★★★★ 一般正式環境（VM 同質、有 balloon 與 KSM） | **1.2 : 1 以內** | 需要有監控與告警 |
| ★★★ 開發／測試 | **1.5 : 1** | 可以接受偶爾很慢 |
| ★★★★★ **任何情況都不要超過** | **2 : 1** | 再上去就是等著出事 |

★★★★ **無論比例多少，這三條規則不能破：**

1. ★★★★★ **給 host 留下足夠的記憶體**。Proxmox VE 上若使用 ZFS，
   ARC 快取會吃掉可觀的記憶體，**必須先扣掉再算 VM 的額度**。
   一般至少留 host 實體記憶體的 10～15%，且不少於 8 GB。
2. ★★★★★ **host 的 swap 使用量必須納入告警**。開始持續 swap ＝ 容量規劃失敗。
3. ★★★★ **資料庫與 Java 應用的 VM 不參與超配**，把 balloon 最小值設成等於配置值。

#### ★★★★★ 儲存超配（Thin Provisioning）—— 機關最常見的整機停機原因

精簡配置的意思是：VM 磁碟宣告 500 GB，但只有寫過的部分才佔實體空間。
於是你可以在 4 TB 的池子上開出 20 台 500 GB 的 VM。

★★★★★ **問題：VM 裡的檔案系統不知道池子快滿了。**
它以為自己還有 300 GB 可以用，於是照常寫入。
當實體池子真的寫滿：

| 平台行為 | 後果 |
| --- | --- |
| 有些平台把 VM 暫停（paused） | ★★★★ 服務中斷，但資料通常保得住 |
| 有些平台讓寫入失敗 | ★★★★★ 客體檔案系統轉成唯讀，資料庫直接損毀 |
| 快照與備份同時失敗 | ★★★★★ **連救援的手段都沒了** |

★★★★★ **這是「一次故障打掉整個池子上所有 VM」的少數情況之一，
比單台 VM 掛掉嚴重一個等級。**

★★★★ **安全做法：**

| 做法 | 說明 |
| --- | --- |
| ★★★★★ 池子使用率告警 | **75% 黃燈、85% 紅燈**，紅燈必須當天處理 |
| ★★★★★ 保留緊急空間 | 永遠留 **10～15%** 不分配，出事時有轉圜餘地 |
| ★★★★ 開啟 discard／TRIM | 用 `virtio-scsi` + 磁碟勾選 discard，客體刪檔後空間才會真的還回池子 |
| ★★★★ 快照納入容量計算 | ★★★★★ 快照會持續長大，**忘掉的快照是池子爆掉的第一名原因** |
| ★★★ 定期核對 | 每月比對「已分配總量 vs 實體容量 vs 實際用量」，寫進月維護作業 |

參見 [[100-02-04-guide-維運-每月維護作業]] 與 [[100-01-03-guide-日誌-系統監控與告警]]。

### ★★★★ 巢狀虛擬化（Nested Virtualization）

**在 VM 裡面再跑 VM。** 例如：實體機跑 Proxmox VE → 裡面開一台 VM 裝 Proxmox VE →
那台裡面再開 VM。本手冊的 [[050-01-03-13-guide-PVE-建立練習環境]] 就是這樣做的。

#### 怎麼運作

★★★★ CPU 只提供**一層** VMX root／non-root。第二層要靠 **L0 hypervisor 模擬**：

| 層 | 名稱 | 角色 |
| --- | --- | --- |
| L0 | 實體機上的 hypervisor | ★★★★ 真正握有硬體，並**假裝自己提供了 VT-x 給 L1** |
| L1 | 跑在 VM 裡的 hypervisor | 以為自己有硬體虛擬化，實際上每個 `VMLAUNCH` 都被 L0 攔截 |
| L2 | L1 開出來的 VM | 使用者真正在用的那一台 |

★★★★★ **L1 的每一次 VM Exit 都會變成 L0 的一次 VM Exit**，於是成本相乘。
現代 CPU 有 shadow VMCS 等最佳化，但**巢狀環境的效能仍然明顯低於單層**。

| 適合用途 | 不適合用途 |
| --- | --- |
| ★★★★ 教學、實驗、驗證叢集設定 | ★★★★★ **任何正式服務** |
| ★★★★ 在 Workstation 裡練習 PVE 叢集 | ★★★★★ 效能測試（數字完全不能參考） |
| ★★★ CI 流程需要在 VM 裡跑 VM | ★★★★ 需要穩定延遲的東西 |
| ★★★ Windows 上的 WSL2／Hyper-V 與 Workstation 並存 | — |

> [!warning] ★★★★ Windows 桌機上的「誰佔走了虛擬化」問題
> 開啟 **Hyper-V、WSL2、Windows 沙箱、記憶體完整性（HVCI）／Credential Guard**
> 任一項，Windows 就會自己變成 L0 hypervisor。
> ★★★★ 此時 VMware Workstation／VirtualBox 必須走 Hyper-V 提供的介面來跑，
> **效能會下降**，且舊版本可能直接無法啟動 VM。
> 詳見 [[050-01-02-06-guide-Workstation-效能調校與疑難排解]]。

## 安裝或基礎操作

### ★★★★★ 第一步：確認硬體支援（Linux）

#### 1. CPU 有沒有虛擬化旗標

```bash
# Intel 看 vmx，AMD 看 svm
grep -c -E '(vmx|svm)' /proc/cpuinfo
```

預期輸出（數字＝支援的邏輯核心數，只要**大於 0** 就代表 CPU 支援）：

```text
16
```

★★★★ 若輸出 `0`，兩種可能：CPU 真的不支援（很舊的機器），
或 **BIOS／UEFI 沒開**（絕大多數是這個）。

#### 2. 用 lscpu 看得更清楚

```bash
lscpu | grep -i -E 'virtual|model name'
```

預期輸出：

```text
Model name:                      Intel(R) Xeon(R) Silver 4210R CPU @ 2.40GHz
Virtualization:                  VT-x
```

AMD 機器會顯示 `AMD-V`。

#### 3. Ubuntu／Debian 上用 kvm-ok 一次判定

```bash
sudo apt install -y cpu-checker
sudo kvm-ok
```

正常時：

```text
INFO: /dev/kvm exists
KVM acceleration can be used
```

BIOS 沒開時：

```text
INFO: Your CPU supports KVM extensions
INFO: KVM is disabled by your BIOS
HINT: Enter your BIOS setup and enable Virtualization Technology (VT),
      and then hard poweroff/poweron your system
KVM acceleration can NOT be used
```

★★★★ 注意訊息裡的 **hard poweroff/poweron** —— 提示很誠實，重開機常常不夠。

#### 4. 模組是否載入、EPT／NPT 是否啟用

```bash
lsmod | grep -E '^kvm'
```

預期輸出（Intel）：

```text
kvm_intel             376832  0
kvm                  1146880  1 kvm_intel
irqbypass              12288  1 kvm
```

```bash
# Intel：檢查 EPT
cat /sys/module/kvm_intel/parameters/ept
# AMD：檢查 NPT
cat /sys/module/kvm_amd/parameters/npt
```

預期輸出：

```text
Y
```

★★★★★ 若是 `N`，記憶體效能會回到影子頁表的年代，**務必查清楚原因**
（通常是核心啟動參數把它關掉了，或 CPU 太舊）。

#### 5. 一次檢查所有先決條件

```bash
sudo apt install -y libvirt-clients
sudo virt-host-validate qemu
```

預期輸出（節錄）：

```text
  QEMU: Checking for hardware virtualization                                 : PASS
  QEMU: Checking if device /dev/kvm exists                                   : PASS
  QEMU: Checking if device /dev/kvm is accessible                            : PASS
  QEMU: Checking if device /dev/vhost-net exists                             : PASS
  QEMU: Checking for cgroup 'cpu' controller support                         : PASS
  QEMU: Checking for secure guest support                                    : WARN (Unknown if this platform has Secure Guest support)
```

★★★★ `WARN` 通常可忽略，**`FAIL` 必須處理**。

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> ★★★ 檢查指令幾乎一樣，只有套件名不同：
>
> ```bash
> sudo dnf install -y libvirt-client
> sudo virt-host-validate qemu
> lscpu | grep -i virtual
> ```
>
> ★★★ RHEL 系沒有 `kvm-ok`（那是 Debian 系 `cpu-checker` 套件的工具），
> 直接用 `virt-host-validate` 即可。
> ★★★ 若要安裝完整虛擬化環境：`sudo dnf group install "Virtualization Host"`。

### ★★★ 在 Windows 桌機上確認

在 PowerShell（不需管理員）執行：

```powershell
Get-ComputerInfo -Property "HyperV*"
```

★★★★ 重點看 `HyperVRequirementVirtualizationFirmwareEnabled`：
`True` 代表韌體層的虛擬化是開的。
若 `HyperVisorPresent` 為 `True`，代表 **Windows 自己已經是 hypervisor**
（Hyper-V／WSL2／HVCI 其中之一開著），Workstation 會以巢狀方式運作。

命令提示字元的傳統做法：

```powershell
systeminfo
```

在輸出最下方的「Hyper-V 需求」段落可以看到同樣的資訊。

### ★★★★ 在 Proxmox VE 上檢查一台 VM 的組態

```bash
qm config 100
```

典型輸出（節錄）：

```text
balloon: 2048
boot: order=scsi0;ide2;net0
cores: 4
cpu: host
memory: 8192
net0: virtio=BC:24:11:AA:BB:CC,bridge=vmbr0
numa: 0
ostype: l26
scsi0: local-lvm:vm-100-disk-0,discard=on,iothread=1,size=64G
scsihw: virtio-scsi-single
sockets: 1
```

★★★★ 四個要確認的欄位：

| 欄位 | 該長什麼樣 | 為什麼 |
| --- | --- | --- |
| `scsihw` | `virtio-scsi-single` | ★★★★ 半虛擬化控制器，搭配 `iothread` 效能最好 |
| `scsi0` 含 `discard=on` | 有 | ★★★★ 客體刪檔後空間才會還給精簡池 |
| `net0` 開頭 | `virtio=` | ★★★★ 若是 `e1000=` 就是全模擬，該換 |
| `balloon` | 資料庫 VM 設成等於 `memory` | ★★★★ 見上方 ballooning 段落 |

```bash
# 現在是否啟用

```

```text
1
```

```bash
# 省下多少頁（乘以 4096 即為位元組）
```

```text
1842301
```

換算成人看得懂的數字：


```text

```

★★★ Proxmox VE 用 `ksmtuned` 動態調整，服務狀態：

```bash

```

> [!tip] ★★★ 什麼時候該關掉 KSM
> - VM 種類差異很大（不同 OS、不同版本）→ 掃描白費 CPU
> - host CPU 已經吃緊 → `ksmd` 是額外負擔
> - ★★★★ 有嚴格資安要求、擔心跨 VM 側通道 → 見「安全性注意事項」

### ★★★★ 二、大頁（Huge Pages）

```bash
grep -i huge /proc/meminfo
```

預期輸出：

```text
AnonHugePages:   2097152 kB
ShmemHugePages:        0 kB
FileHugePages:         0 kB
HugePages_Total:       0
HugePages_Free:        0
HugePages_Rsvd:        0
HugePages_Surp:        0
Hugepagesize:       2048 kB
Hugetlb:               0 kB
```

★★★ 上面顯示的是 **THP（透明大頁）在用**（`AnonHugePages` 有值），
而**預留式大頁**（`HugePages_Total`）為 0。

檢查 THP 狀態：

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
```

```text
[always] madvise never
```

> [!warning] ★★★★ 預留式大頁會把記憶體釘死
> `vm.nr_hugepages` 設定的大頁**不能被 swap、不參與 ballooning、不參與 KSM**，
> 而且**開機時就會從一般記憶體池扣掉**。
> ★★★★★ 設太多會讓 host 一開機就記憶體不足。
> 只在「單一大型資料庫 VM 獨佔一台 host」這種明確場景才用，
> 一般機關環境**維持預設即可**。

### ★★★★ 三、開啟巢狀虛擬化（Linux／KVM）

```bash
# 先看目前狀態（Intel）
cat /sys/module/kvm_intel/parameters/nested
```

```text
N
```

啟用（Intel）：

```bash
echo 'options kvm_intel nested=1' | sudo tee /etc/modprobe.d/kvm-nested.conf
sudo modprobe -r kvm_intel     # 必須先關掉所有 VM
sudo modprobe kvm_intel
cat /sys/module/kvm_intel/parameters/nested
```

```text
Y
```

AMD 平台把 `kvm_intel` 換成 `kvm_amd`、參數同樣是 `nested=1`。

★★★★ **還要把 CPU 型別傳給 VM**：在 Proxmox VE 上把 VM 的 CPU 類型設為 `host`：

```bash
qm set 100 --cpu host
```

```text
update VM 100: -cpu host
```

★★★★★ **沒有設 `cpu: host`（或至少要有虛擬化旗標的 CPU 型別），
L1 裡面看不到 `vmx`／`svm`，巢狀虛擬化就是不會動。**
在 L1 裡驗證：

```bash
grep -c -E '(vmx|svm)' /proc/cpuinfo
```

```text
4
```

> [!info]- VMware Workstation 上開巢狀虛擬化
> ★★★★ 在 VM 設定 →「處理器（Processors）」→ 勾選
> **Virtualize Intel VT-x/EPT or AMD-V/RVI**。
> ★★★★ VM 必須先關機（不是暫停）才能改。
> ★★★ 這也是在筆電上練習 Proxmox VE 叢集的標準做法，
> 見 [[050-01-03-13-guide-PVE-建立練習環境]]。

### ★★★★ 四、確認 IOMMU 是否可用（直通前提）

Intel 平台正常時會看到類似：

```text
[    0.000000] DMAR: IOMMU enabled
[    0.187543] DMAR: Host address width 46
```

```bash
for g in /sys/kernel/iommu_groups/*; do
    echo "群組 ${g##*/}:"

```

節錄輸出：

```text
    01:00.0 VGA compatible controller [0300]: NVIDIA Corporation ... [10de:1e04] (rev a1)
```

★★★★★ **這個群組裡的兩個裝置必須一起直通**（顯卡與它的音效裝置）。

## 完整實戰範例

### 情境

某機關新採購一台雙路伺服器準備當 Proxmox VE 主機。
上線前你要做一次**完整的底層能力驗證與基準量測**，
產出一份可以歸檔的報告，證明：

1. 硬體輔助虛擬化（含 EPT／NPT）正常
2. VirtIO 相對於全模擬的效益確實存在（用數字說話）
3. 記憶體超配的護欄（告警門檻）已經設定
4. 這台機器**可以**做巢狀虛擬化（給教育訓練用）

★★★★ 這整套流程建議寫進 [[040-02-09-guide-機房-伺服器上架與初始設定]] 的驗收清單。

### 前置環境

| 項目 | 內容 |
| --- | --- |
| 硬體 | 雙路伺服器，2 × 12 核心（共 48 執行緒）、256 GB RAM |
| 儲存 | 8 顆企業級 SSD，做成 ZFS RAID10 |
| 系統 | Proxmox VE（安裝流程見 [[050-01-03-01-svc-PVE-安裝與初始設定]]） |
| 網路 | 雙 10G 網卡，做 bond 後接 `vmbr0` |

### 步驟 1：確認 BIOS 與 CPU 能力

```bash
lscpu | grep -i -E 'model name|^cpu\(s\)|virtual|thread'
```

### 步驟 2：確認記憶體與 ZFS ARC 的關係

### 步驟 3：建立兩台一模一樣的測試 VM（差別只在 I/O 型別）

```bash
# VM 9001：全模擬（e1000 網卡 + SATA 磁碟）
qm create 9001 --name test-emulated --memory 4096 --cores 4 \
    --net0 e1000,bridge=vmbr0 --sata0 local-zfs:32 --ostype l26

# VM 9002：VirtIO（virtio 網卡 + virtio-scsi 磁碟）
qm create 9002 --name test-virtio --memory 4096 --cores 4 \
    --net0 virtio,bridge=vmbr0 --scsihw virtio-scsi-single \
    --scsi0 local-zfs:32,iothread=1,discard=on --ostype l26
```

```text
  Logical volume "vm-9001-disk-0" created.
  Logical volume "vm-9002-disk-0" created.
```

兩台都裝上相同版本的 Ubuntu Server，其他設定完全一致。

確認差異只在 I/O：

```bash
qm config 9001 | grep -E 'net0|sata0|scsi'
qm config 9002 | grep -E 'net0|sata0|scsi'
```

```text
net0: e1000=BC:24:11:00:00:01,bridge=vmbr0
sata0: local-zfs:vm-9001-disk-0,size=32G
net0: virtio=BC:24:11:00:00:02,bridge=vmbr0
scsi0: local-zfs:vm-9002-disk-0,discard=on,iothread=1,size=32G
scsihw: virtio-scsi-single
```

### 步驟 4：量測磁碟 I/O 差異

在**兩台 VM 內部**分別執行同一組 `fio`：

```bash
sudo apt install -y fio
sudo fio --name=randwrite --ioengine=libaio --direct=1 \
    --rw=randwrite --bs=4k --numjobs=4 --iodepth=32 \
    --size=2G --runtime=60 --time_based --group_reporting
```

輸出的重點只有三行（實際數字依你的硬體而不同）：

```text
  write: IOPS=..., BW=...
    lat (usec): min=..., avg=..., max=...
  cpu          : usr=..., sys=..., ctx=..., majf=0, minf=0
```

★★★★ **要記錄與比較的是這三項**：

| 指標 | 意義 | 預期關係 |
| --- | --- | --- |
| `IOPS` | 每秒 I/O 次數 | ★★★★ VirtIO 明顯高於全模擬 |
| `lat avg` | 平均延遲 | ★★★★ VirtIO 明顯低 |
| `cpu sys` | ★★★★★ **客體核心花在 I/O 上的 CPU** | ★★★★★ 全模擬會高很多 —— **這才是全模擬真正的代價** |

> [!tip] ★★★★ 同時在 host 上盯著看
> 在 host 開另一個視窗跑：
>
> ```bash
> top -b -n 1 | head -15
> ```
>
> ★★★★ 觀察那台 VM 對應的 `kvm` 程序的 CPU%。
> **全模擬的那台，host 端 CPU 消耗會明顯高於 VirtIO 的那台，
> 即使兩者跑出來的 IOPS 一樣。** 這就是「同樣的工作，付了更多 CPU」。

### 步驟 5：量測網路差異

在 VM 9002 上開 iperf3 伺服器，另一台實體機當客戶端：

```bash
# VM 內
sudo apt install -y iperf3

```

```text

Server listening on 5201 (test #1)
-----------------------------------------------------------
```

```bash
# 另一台實體機
iperf3 -c 10.10.20.92 -t 30 -P 4
```

★★★★ 同樣的測試對 VM 9001（e1000）再跑一次。
**重點不只看頻寬，要同時看客體的 `%si`（軟中斷）**：

```bash
# VM 內，測試進行中

```

```text
Average:     CPU    %usr   %nice    %sys %iowait    %irq   %soft  %steal   %idle
Average:     all    2.31    0.00   11.42    0.00    0.00   18.74    0.12   67.41
```

★★★★★ **全模擬網卡在高流量時 `%soft` 會非常高，
代表大量 CPU 被拿去處理中斷與模擬，而不是跑你的應用程式。**

### 步驟 6：設定超配護欄與告警

計算本機的配置上限並寫成一份可執行的檢查腳本：

```bash
sudo tee /usr/local/bin/vm-overcommit-check.sh > /dev/null <<'EOF'
#!/bin/bash
# 檢查本機 VM 的資源超配比例
# 用法：vm-overcommit-check.sh

set -euo pipefail

PHYS_THREADS=$(nproc)
PHYS_MEM_MB=$(awk '/MemTotal/ {printf "%d", $2/1024}' /proc/meminfo)
ARC_MAX_MB=$(( $(cat /sys/module/zfs/parameters/zfs_arc_max 2>/dev/null || echo 0) / 1048576 ))
RESERVE_MB=16384          # 保留給 PVE 本身

TOTAL_VCPU=0
TOTAL_VMEM=0
for id in $(qm list | awk 'NR>1 {print $1}'); do
    cfg=$(qm config "$id")
    cores=$(echo "$cfg"   | awk -F': ' '/^cores:/   {print $2}')
    sockets=$(echo "$cfg" | awk -F': ' '/^sockets:/ {print $2}')
    mem=$(echo "$cfg"     | awk -F': ' '/^memory:/  {print $2}')
    sockets=${sockets:-1}
    TOTAL_VCPU=$(( TOTAL_VCPU + cores * sockets ))
    TOTAL_VMEM=$(( TOTAL_VMEM + mem ))
done

AVAIL_MEM=$(( PHYS_MEM_MB - ARC_MAX_MB - RESERVE_MB ))

echo "實體執行緒          : ${PHYS_THREADS}"
echo "已配置 vCPU 總數    : ${TOTAL_VCPU}"
awk -v a="$TOTAL_VCPU" -v b="$PHYS_THREADS" \
    'BEGIN {printf "CPU 超配比          : %.2f : 1\n", a/b}'
echo "---"
echo "實體記憶體 (MB)     : ${PHYS_MEM_MB}"
echo "ZFS ARC 上限 (MB)   : ${ARC_MAX_MB}"
echo "保留給 host (MB)    : ${RESERVE_MB}"
echo "VM 可用額度 (MB)    : ${AVAIL_MEM}"
echo "已配置 VM 記憶體(MB): ${TOTAL_VMEM}"
awk -v a="$TOTAL_VMEM" -v b="$AVAIL_MEM" \
    'BEGIN {printf "記憶體超配比        : %.2f : 1\n", a/b}'

SWAP_USED=$(awk '/SwapTotal/{t=$2} /SwapFree/{f=$2} END {print t-f}' /proc/meminfo)
if [ "$SWAP_USED" -gt 0 ]; then
    echo "!! 警告：host 已使用 swap ${SWAP_USED} KB —— 容量規劃可能已失敗"
fi
EOF
sudo chmod +x /usr/local/bin/vm-overcommit-check.sh
```

執行：

```bash
sudo /usr/local/bin/vm-overcommit-check.sh
```

預期輸出：

```text
實體執行緒          : 48
已配置 vCPU 總數    : 96
CPU 超配比          : 2.00 : 1
---
實體記憶體 (MB)     : 257024
ZFS ARC 上限 (MB)   : 32768
保留給 host (MB)    : 16384
VM 可用額度 (MB)    : 207872
已配置 VM 記憶體(MB): 196608
記憶體超配比        : 0.95 : 1
```

★★★★★ **驗收條件：**

| 指標 | 綠燈 | 黃燈 | 紅燈 |
| --- | --- | --- | --- |
| CPU 超配比 | ≤ 4 : 1 | 4～6 : 1 | > 6 : 1 |
| 記憶體超配比 | ≤ 1.0 : 1 | 1.0～1.2 : 1 | > 1.2 : 1 |
| host swap 使用量 | 0 | 偶發 | ★★★★★ 持續增加 |
| 儲存池使用率 | < 75% | 75～85% | > 85% |

把這支腳本掛進每月維護作業：

```bash
sudo tee /etc/cron.d/vm-overcommit > /dev/null <<'EOF'
# 每月 1 號早上 8:00 產出超配報告寄給維運信箱
0 8 1 * * root /usr/local/bin/vm-overcommit-check.sh
EOF
```

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ `KVM is disabled by your BIOS`／VM 無法啟動 | BIOS/UEFI 未啟用 VT-x／AMD-V | 進 BIOS 開啟 `Intel VT`／`SVM Mode`，★★★★ 儲存後**完全斷電再開機** |
| ★★★★ BIOS 已開卻仍顯示未啟用 | 只做了重開機，設定未在 CPU 上電時載入 | 拔電源等 30 秒再開；部分機型需清除 CMOS |
| ★★★★ `/dev/kvm` 存在但一般使用者無法用 | 使用者不在 `kvm` 群組 | `sudo usermod -aG kvm $USER`，重新登入 |
| ★★★★★ Windows 安裝時「找不到任何磁碟機」 | 用了 VirtIO 磁碟但沒載入驅動 | 掛載 virtio-win ISO，在磁碟選擇畫面按「載入驅動程式」選 `viostor`／`vioscsi` |
| ★★★★ Windows VM 網路不通、裝置管理員有黃色驚嘆號 | VirtIO 網卡缺驅動 | 從 virtio-win ISO 安裝 `NetKVM`，或直接執行 ISO 內的完整安裝程式 |
| ★★★★★ host 整體突然變超慢，所有 VM 一起卡 | host 開始 swap（記憶體超配過頭） | 立刻關掉／遷移最不重要的 VM；長期要降低配置或加記憶體。★★★★★ **不要試圖靠調參數解決** |
| ★★★★★ 客體 `top` 的 `st` 欄位持續 > 10% | CPU 超賣過頭或 host 上有失控行程 | 降低 vCPU 配置、遷移 VM；先確認 host 沒有異常吃 CPU 的程序 |
| ★★★★ 給 VM 加了 vCPU 反而更慢 | vCPU 數逼近 host 執行緒數，排程要等所有 vCPU 同時有空 | ★★★★ 減少 vCPU；單 VM 的 vCPU 不要超過 host 執行緒數的一半 |
| ★★★★★ 儲存池滿了，多台 VM 同時變唯讀 | 精簡配置超賣 + 快照堆積 | 立刻刪除舊快照／備份釋放空間；恢復後在客體內 `fsck`。★★★★★ 事前設 75%/85% 告警 |
| ★★★★ 客體刪了大檔案但池子空間沒有回收 | 沒開 discard／TRIM，或控制器不是 virtio-scsi | 改用 `virtio-scsi`、磁碟勾 `discard=on`，客體內執行 `fstrim -av` |
| ★★★★ VM 快照越留越多，磁碟效能越來越差 | 快照鏈造成寫時複製放大 | 定期清理快照；★★★★★ 快照**不是備份**，備份請用 [[050-01-03-06-svc-PVE-備份與還原]] |
| ★★★★ 直通失敗：`group is not viable` | ★★★★★ IOMMU 群組裡還有 host 正在使用的裝置 | 換 PCIe 插槽改變群組；或把群組內其他裝置也一併直通（若可行） |
| ★★★★ 直通後 VM 開得起來但裝置沒作用 | host 端驅動仍綁著該裝置 | 用 `vfio-pci` 綁定該裝置，並把原廠驅動加入黑名單 |
| ★★★★★ 直通後無法線上遷移 | ★★★★★ **這是設計限制，不是故障** | 只能關機遷移；服務不能停就要在應用層做多節點備援 |
| ★★★★ 重開機後 SR-IOV 的 VF 全部消失，VM 開不起來 | `sriov_numvfs` 寫在 sysfs，重開會歸零 | 用 udev 規則或 systemd 服務在開機時重建 VF |
| ★★★★ L1 裡看不到 `vmx`／`svm`，巢狀虛擬化不動 | host 的 `nested` 沒開，或 VM 的 CPU 型別不是 `host` | 兩件事都要做：`nested=1` + `qm set <id> --cpu host` |
| ★★★★ Windows 上 VMware Workstation 啟動 VM 失敗或極慢 | Hyper-V／WSL2／HVCI 已把 Windows 變成 hypervisor | 更新 Workstation 到支援 Hyper-V 模式的版本，或關閉 Hyper-V 相關功能後重開機 |
| ★★★ `arc_summary` 顯示 ARC 吃掉大半記憶體，VM 開不起來 | ZFS 預設 ARC 上限太高 | 設定 `zfs_arc_max` 並 `update-initramfs -u`，重開機生效 |
| ★★★ 資料庫 VM 三不五時被 OOM killer 殺掉 | 開了 ballooning，記憶體被氣球抽走 | 把 balloon 最小值設成等於配置記憶體（等於關閉 ballooning） |
| ★★★ 開了大頁之後 host 一開機就記憶體吃緊 | 預留式大頁在開機時就從一般池扣掉且不可回收 | 降低 `vm.nr_hugepages`，或改回 THP |
| ★★★ `qemu-img convert` 中途失敗或產出的映像壞掉 | 來源檔在轉換期間仍被使用中 | ★★★★ 轉換前**必須先關機**；轉完用 `qemu-img check` 驗證 |

## 安全性注意事項

### ★★★★★ 一、直通裝置＝把 DMA 權限交出去

| 風險 | 說明 | 對策 |
| --- | --- | --- |
| ★★★★★ **無 IOMMU 的直通** | 裝置可以 DMA 到任意實體記憶體，等於 VM 拿到 host 的完整記憶體讀寫權 | ★★★★★ **沒有 IOMMU 就不要直通，一次都不行** |
| ★★★★ **群組內裝置牽連** | 同群組裝置間可繞過 IOMMU 通訊 | 直通前確認整個群組都是可以交出去的 |
| ★★★★ **韌體持久化** | VM 可能改寫直通裝置的韌體，換給下一台 VM 時仍帶著後門 | 高敏感環境不要在不同信任等級的 VM 間輪替同一張卡 |

### ★★★★ 二、KSM 的跨 VM 側通道

★★★★ KSM 合併相同頁面之後，**寫入被合併的頁會觸發寫時複製，因此變慢**。
攻擊者可以量測這個時間差，推測「另一台 VM 的記憶體裡有沒有某段內容」
（記憶體去重複攻擊）。

| 環境 | 建議 |
| --- | --- |
| ★★★ 單一機關自用、所有 VM 同一信任等級 | 可以開，效益大於風險 |
| ★★★★ 多租戶、對外提供 VM 給不同單位 | ★★★★ **關閉 KSM**（`echo 0 > /sys/kernel/mm/ksm/run` 並停用 `ksmtuned`） |
| ★★★★★ 有機密資料分級要求 | ★★★★★ 關閉，並在資安文件中說明 |

### ★★★★ 三、CPU 側通道（Spectre／Meltdown 家族）

★★★★★ 這一系列漏洞的共同特徵是：**透過推測執行的副作用，跨越隔離邊界讀到不該讀的資料。**
在虛擬化環境中，這個邊界可能是 VM 對 VM，也可能是 VM 對 hypervisor。

| 對策 | 說明 | 重要度 |
| --- | --- | --- |
| **更新 CPU 微碼** | 透過 `intel-microcode`／`amd64-microcode` 套件或 BIOS 更新 | ★★★★★ |
| **更新核心與 hypervisor** | 緩解措施在核心裡 | ★★★★★ |
| ★★★★ **關閉 SMT／超執行緒** | 部分漏洞（L1TF、MDS）只有關閉 SMT 才能完全緩解 | ★★★★（高敏感環境） |
| **檢查現況** | `lscpu` 的 `Vulnerability` 欄位 | ★★★★ |

```bash
lscpu | grep -A20 -i vulnerab
```

節錄輸出：

```text
Vulnerability Meltdown:          Mitigation; PTI
Vulnerability Mds:               Mitigation; Clear CPU buffers; SMT vulnerable
Vulnerability Spectre v1:        Mitigation; usercopy/swapgs barriers and __user pointer sanitization
Vulnerability Spectre v2:        Mitigation; Retpolines, IBPB conditional, IBRS_FW, STIBP conditional, RSB filling
```

★★★★ 注意 `SMT vulnerable` 這幾個字 —— 代表**開著超執行緒時該緩解不完整**。

> [!warning] ★★★★ 關閉 SMT 的成本要先算清楚
> 關掉超執行緒等於實體執行緒數砍半，**所有超配比例都要重算**。
> ★★★★ 這是一個資安與容量的取捨，必須由業務單位與資安單位共同決定，
> 不是維運人員自己決定，且要走 [[100-02-08-guide-維運-變更管理流程]]。

### ★★★★ 四、超配本身就是一種可用性風險

★★★★★ 資安三要素的「可用性（Availability）」常被忽略。
記憶體或儲存超配過頭導致服務全停，在稽核上與被入侵造成的停機是同一類事件。

| 控制項 | 做法 |
| --- | --- |
| ★★★★★ 容量告警 | 儲存池 75%／85%、host swap > 0、客體 steal > 5% |
| ★★★★ 定期複核 | 每月產出超配報告（見實戰範例的腳本） |
| ★★★★ 變更管控 | 新增 VM 或加大配置必須先看超配比，超過紅線需簽核 |
| ★★★ 隔離重要負載 | 關鍵系統獨立 host 或不參與超配 |

### ★★★ 五、`cache=unsafe` 與資料完整性

★★★★★ `cache=unsafe` 會忽略客體發出的 flush 要求。
一旦 host 異常斷電，**客體檔案系統與資料庫的一致性完全沒有保證**。

| 場合 | 是否可用 |
| --- | --- |
| 大量安裝作業系統的自動化流程（裝壞就重來） | ★★★ 可以，但要記得改回來 |
| ★★★★★ 任何正式服務、任何有資料的 VM | ★★★★★ **絕對禁止** |

★★★★ 相對的，`cache=none` 搭配有電池／電容保護的 RAID 卡或 UPS，
是效能與安全的合理平衡點。UPS 規劃見 [[040-02-05-guide-機房-UPS選型與容量計算]]。

| ★★★★ CPU 超配比上限 | 一般正式 **2～4 : 1**；資料庫 **1～2 : 1** |
| ★★★★★ 記憶體超配比上限 | 保守 **1 : 1**；★★★★★ **絕不超過 2 : 1** |
| ★★★★★ 儲存池告警門檻 | **75% 黃燈、85% 紅燈** |
| ★★★★ 什麼時候才直通 | 量測證明 VirtIO 不夠，**且能接受不可線上遷移** |
| ★★★★ 巢狀虛擬化用在哪 | **只用於教學與實驗**，不跑正式服務 |

## 練習題

> [!question]- 練習 1：把你手上機器的底層能力寫成一份報告
> 在任何一台 Linux 機器（實體或 VM 都可以）上，依序執行：
>
> ```bash
> lscpu | grep -i -E 'model name|virtual'
> lsmod | grep -E '^kvm'
> cat /sys/module/kvm_intel/parameters/ept 2>/dev/null || \
>     cat /sys/module/kvm_amd/parameters/npt 2>/dev/null
> sudo virt-host-validate qemu 2>/dev/null | grep -v PASS
> ```
>
> **要回答的問題**：
> 1. 這台機器支不支援硬體輔助虛擬化？從哪一行看出來？
> 2. 二階分頁（EPT／NPT）有沒有啟用？
> 3. 如果你在一台 VM 裡執行，`lscpu` 會多出哪一行？那代表什麼？
>
> ★★★★ 參考答案：
> 1. 看 `Virtualization:` 那一行有沒有 `VT-x`／`AMD-V`。沒有的話再檢查
>    `/proc/cpuinfo` 有沒有 `vmx`／`svm` 旗標 —— 若旗標有但 `lscpu` 沒顯示，
>    通常是 BIOS 沒開。
> 2. 看 `ept`／`npt` 是不是 `Y`。若檔案不存在代表模組沒載入。
> 3. 會多出 `Hypervisor vendor:` 與 `Virtualization type: full`。
>    代表你正在一台 VM 裡面，且它是全虛擬化（不是容器）。

> [!question]- 練習 2：算出你的 host 到底還能開幾台 VM
> 假設一台 host：
> - 實體 2 顆 CPU × 16 核心，開啟超執行緒
> - 實體記憶體 192 GB，使用 ZFS 且 ARC 上限設為 24 GB
> - 已經跑了 12 台 VM，每台 4 vCPU / 8 GB
>
> 請計算：
> 1. 目前的 CPU 超配比是多少？
> 2. VM 可用的記憶體額度是多少（host 保留 16 GB）？目前的記憶體超配比？
> 3. 若要再開 6 台同規格的 VM，CPU 與記憶體分別會變成多少？可以嗎？
>
> ★★★★ 參考答案：
> 1. 實體執行緒 = 2 × 16 × 2 = **64**。已配置 vCPU = 12 × 4 = **48**。
>    超配比 = 48 / 64 = **0.75 : 1**（還沒超配）。
> 2. 可用額度 = 192 − 24 − 16 = **152 GB**。已配置 = 12 × 8 = **96 GB**。
>    超配比 = 96 / 152 ≈ **0.63 : 1**。
> 3. 再開 6 台：vCPU 變 72 → 72 / 64 = **1.13 : 1**（綠燈，很安全）；
>    記憶體變 144 GB → 144 / 152 ≈ **0.95 : 1**（★★★★ 綠燈但已接近滿載，
>    再多開就會進入超配）。
>    ★★★★★ **結論：CPU 完全沒問題，瓶頸在記憶體。**
>    這也是絕大多數機關虛擬化平台的真實狀況 —— **先撞到的永遠是記憶體。**

> [!question]- 練習 3：找出一台 VM 的 I/O 路徑並改成 VirtIO
> 在 Proxmox VE 上挑一台**非正式服務**的 VM：
>
> ```bash
> qm config <vmid> | grep -E 'net0|ide|sata|scsi'
> ```
>
> 1. 判斷它的網卡與磁碟走的是哪一條路徑（全模擬／VirtIO／直通）？
> 2. 如果是全模擬，寫出把網卡改成 VirtIO 的指令。
> 3. 若這是一台 Windows VM，改之前要先做什麼？
>
> ★★★★ 參考答案：
> 1. `net0: e1000=...` 是全模擬；`net0: virtio=...` 是 VirtIO。
>    磁碟用 `ide0:`／`sata0:` 是全模擬，`scsi0:` 搭配 `scsihw: virtio-scsi*` 是 VirtIO。
> 2. `qm set <vmid> --net0 virtio,bridge=vmbr0`（VM 需關機或重開才生效）。
> 3. ★★★★★ **先在 Windows 裡安裝 VirtIO 驅動**（掛 virtio-win ISO 執行安裝程式），
>    再改設定。順序反了會變成「改完開機沒有網路，也沒辦法上網去下載驅動」。
>    ★★★★ 磁碟型別更要小心：Windows 系統碟從 SATA 直接改成 VirtIO 而沒有先裝驅動，
>    **會開機藍屏**。標準做法是先掛一顆暫時的 VirtIO 磁碟讓 Windows 認到驅動，
>    再改系統碟。

> [!question]- 練習 4：模擬「儲存池快滿」的處置流程
> 不要真的把池子寫滿。請在紙上寫出：
>
> 1. 你會用什麼指令查目前池子的使用率？
> 2. 使用率到 86% 時，你按什麼順序處理？
> 3. 如果已經 99%，而且有 VM 開始出現 I/O 錯誤，第一步做什麼？
>
> ★★★★ 參考答案：
> 1. ZFS：`zpool list`、`zfs list`；LVM-thin：`lvs -a`；PVE GUI 的 Storage 頁。
> 2. ★★★★ 順序：
>    (a) 先找**最容易釋放且無風險**的：過期備份、舊 ISO、
>        ★★★★★ **忘記刪的快照**（最常見的元兇）
>    (b) 客體內執行 `fstrim -av` 把已刪檔案的空間還回去
>    (c) 把不重要的 VM 遷移到別的儲存
>    (d) 最後才考慮擴充容量
> 3. ★★★★★ **先停掉正在大量寫入的 VM**（通常是備份工作或日誌暴衝的那台），
>    爭取時間；然後立刻刪快照釋放空間。
>    ★★★★★ **不要**在這個時候嘗試「搬移 VM 到其他儲存」——
>    搬移本身可能需要暫用空間，會讓情況更糟。

> [!question]- 練習 5：判斷該不該直通
> 三個需求，各自判斷要用 VirtIO 還是直通，並說明代價：
>
> 1. 一台跑內部網站的 VM，尖峰約 200 Mbps 流量
> 2. 一台要跑本地 LLM 推論的 VM，需要 GPU
> 3. 一台防火牆 VM，要處理 8 Gbps 的南北向流量，且不能有封包遺失
>
> ★★★★ 參考答案：
> 1. ★★★★ **VirtIO**。200 Mbps 對 VirtIO 完全不成問題，
>    而且保留了線上遷移與快照能力。直通在這裡是浪費。
> 2. ★★★★ **必須直通（GPU passthrough）**。GPU 沒有實用的半虛擬化路徑。
>    代價：★★★★★ 這台 VM 不能線上遷移、快照不含 GPU 狀態、
>    host 維護時必須關機。要在設計階段就接受。
>    見 [[050-01-03-10-guide-PVE-硬體直通與GPU]]。
> 3. ★★★★ **視情況**。8 Gbps 用 VirtIO 搭配多佇列通常做得到，但延遲抖動較大；
>    若「不能有封包遺失」是硬性需求，考慮 **SR-IOV VF 直通**。
>    ★★★★★ 代價一樣是不能線上遷移 —— 而防火牆通常正是最不能停的東西，
>    所以真正的解法往往是**兩台防火牆 VM 做 HA**，而不是硬拚單台效能。

## 小測驗

Q1. x86 早年無法用單純的 trap-and-emulate 做虛擬化，根本原因是什麼？

Q2.（是非）VM Exit 越多代表 hypervisor 越努力工作，所以效能越好。

Q3. EPT／NPT 解決了什麼問題？它取代了什麼舊技術？

Q4.（選擇）下列哪一個組合**不能**線上遷移？
(A) virtio-net + virtio-scsi
(B) e1000 + SATA
(C) SR-IOV VF 直通
(D) virtio-net + qcow2 磁碟

Q5. 這行指令會發生什麼事，正常輸出應該是什麼？

```bash
cat /sys/module/kvm_intel/parameters/ept
```

Q6. Ballooning 把記憶體收回去時，「決定犧牲哪些頁」的是誰？為什麼這比 host swap 好？

Q7.（是非）記憶體超配到 3:1 只是會變慢，跟 CPU 超配一樣可以接受。

Q8. 一台 host 有 48 個實體執行緒，你打算開一台 32 vCPU 的大 VM。
這樣做有什麼隱藏的效能風險？

Q9. 為什麼「快照留很久」會讓 VM 的磁碟效能變差？

Q10. 這行指令在 Proxmox VE 上會做什麼？為什麼巢狀虛擬化需要它？

```bash
qm set 100 --cpu host
```

> [!question]- 測驗答案
> **Q1.** ★★★★★ 因為 x86 有一批**敏感但不會 trap 的指令**（例如 `POPF`）——
> 客體在低特權等級執行它們時不會產生例外，hypervisor 因此攔不到，
> 客體卻以為操作成功了。這違反了 Popek 與 Goldberg 的可虛擬化條件。
> → 見「為什麼 x86 本來做不到虛擬化」。
>
> **Q2.** ★★★★★ **錯。** VM Exit 是虛擬化中最昂貴的操作，
> 每一次都要暫停客體、儲存狀態、切換模式。
> **所有效能調校的本質都是減少 VM Exit**（VirtIO、EPT、直通都是）。
> → 見「VM Exit —— 虛擬化世界唯一真正貴的東西」。
>
> **Q3.** ★★★★★ 解決「客體實體位址（GPA）→ 機器實體位址（HPA）」這第二層轉換。
> 它取代了**影子頁表（shadow page table）**。
> 舊做法下客體每次改自己的頁表都會造成 VM Exit，記憶體密集負載慢到不能接受；
> EPT／NPT 讓 MMU 硬體直接走兩層，客體改頁表完全不需要 hypervisor 介入。
> → 見「記憶體虛擬化與二階分頁」。
>
> **Q4.** ★★★★★ **(C)**。SR-IOV VF 是實體裝置的一部分，
> 它的狀態無法在主機之間搬移，所以**不能線上遷移** —— 單卡直通也一樣。
> (B) 雖然效能差，但仍然是被模擬出來的裝置，是可以遷移的。
> → 見「I/O 虛擬化的三條路徑」對照表。
>
> **Q5.** ★★★★ 讀取 Intel KVM 模組的 EPT 參數，也就是**二階分頁是否啟用**。
> 正常輸出是 `Y`。若是 `N`，記憶體效能會退回影子頁表的年代，必須查明原因。
> AMD 平台對應的是 `/sys/module/kvm_amd/parameters/npt`。
> → 見「安裝或基礎操作」步驟 4。
>
> **Q6.** ★★★★★ 決定的是**客體作業系統自己**。
> balloon 驅動只是在客體裡「申請一大塊記憶體」，客體 OS 為了滿足這個申請，
> 會依自己的演算法回收檔案快取、換出冷頁。
> 這比 host swap 好，是因為**客體知道哪些頁是可丟棄的快取，
> 而 hypervisor 從外面看只是一堆看不懂的位元組**，很可能換掉客體正在熱用的頁，
> 甚至造成 double paging。
> → 見「記憶體超配的三個工具」。
>
> **Q7.** ★★★★★ **錯，而且是危險的錯。**
> CPU 不夠只是變慢（可逆）；記憶體不夠會導致 host swap 造成全體雪崩，
> 甚至讓 OOM killer 直接殺掉 VM（部分不可逆）。
> 記憶體超配**任何情況都不該超過 2:1，正式環境建議 1:1**。
> → 見「超配的代價與安全比例」。
>
> **Q8.** ★★★★★ 許多 hypervisor 傾向讓一台 VM 的 vCPU **同時**取得實體核心。
> 32 vCPU 在 48 執行緒的 host 上，必須等到 32 個執行緒同時有空才排得進去，
> 於是這台大 VM 反而會比小 VM **更常卡住**，而且它一旦上場就把 host 塞滿，
> 連帶影響其他 VM。原則是**vCPU 給到夠用就好**，
> 單 VM 建議不超過 host 執行緒數的一半。
> → 見「CPU 超配」的 danger callout。
>
> **Q9.** ★★★★★ 因為快照靠**寫時複製（CoW）**：
> 每次寫入一個快照之後尚未修改過的區塊，都必須先把原始內容複製出去保存，
> 一次邏輯寫入變成多次實體 I/O，這就是**寫入放大**。
> 快照鏈越長、留越久，放大越嚴重，而且快照本身還會不斷吃掉儲存空間。
> ★★★★★ 這也是「快照不是備份、用完要盡快刪」的技術理由。
> → 見「寫入放大」。
>
> **Q10.** ★★★★★ 把 VM 100 的 CPU 型別設為 `host`，
> 也就是**把宿主機 CPU 的完整指令集與旗標原樣暴露給客體**（包含 `vmx`／`svm`）。
> 巢狀虛擬化需要它，是因為 L1 裡的 hypervisor 必須「看得到」硬體虛擬化旗標
> 才會啟用 KVM；用預設的通用 CPU 型別時客體看不到 `vmx`，巢狀就不會動。
> ★★★★ 但要注意：設 `cpu: host` 之後，**這台 VM 只能遷移到 CPU 型號相容的主機**。
> → 見「進階應用」第三節。
