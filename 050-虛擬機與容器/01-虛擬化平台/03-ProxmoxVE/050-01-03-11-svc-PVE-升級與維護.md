# PVE 升級與維護

> [!abstract] 這篇你會學到
> - PVE 的**套件庫有哪幾種**（enterprise／no-subscription／test），機關該用哪一種
> - **小版本更新**的標準流程：什麼時候可以直接做、什麼時候一定要排維護窗口
> - ★★★★★ **大版本升級（7 → 8 這種）的完整前置檢查與步驟**：
>   官方的升級前檢查工具怎麼跑、怎麼判讀、套件庫怎麼換版
> - ★★★★★ **叢集節點的升級順序**，以及升級期間叢集會處在什麼狀態
> - **節點維護模式**：怎麼把工作負載乾淨地疏散出去再動手
> - ★★★★ **核心釘選（kernel pin）** —— 新核心開不起來時的保命符
> - Web 介面憑證更新：**自簽**、**自建 CA 簽發**、**ACME 自動續期**三條路
> - ★★★★★ **升級前一定要有「已驗證可還原」的備份**，沒有就不要動手
> - 一份可以直接抄走的**日／週／月維護清單**

> [!warning] 未實機驗證
> 本篇**以 Proxmox VE 8（基於 Debian 12 "bookworm"）為例**。
>
> ★★★★★ **套件庫網址、codename、升級檢查工具的名稱都會隨版本改變。**
> PVE 的升級檢查工具命名慣例是 `pve<舊版>to<新版>`（例如 7 → 8 是 `pve7to8`），
> 但**你要升的那一版叫什麼、有沒有這個工具，一律以
> Proxmox 官方 wiki 的「Upgrade from X to Y」頁面當前版本為準**。
> 不要照抄本篇的字串，先查官方文件。
>
> ★★★★★ 文中的版本號、套件數量、輸出訊息**都是示意值**。
>
> ★★★★★ **大版本升級是不可逆操作。** 沒有做過還原測試的備份，
> 就當作沒有備份，不要開始。

## 觀念說明

### PVE 的版本組成 ★★★★

PVE 不是單一軟體，它是**一疊東西的組合**：

```
┌───────────────────────────────────────────────┐
│  Proxmox VE 8.x                                │
│  ├─ Web 介面 / API（pve-manager、pveproxy）      │
│  ├─ 叢集檔案系統（pmxcfs / corosync）             │
│  ├─ QEMU/KVM（pve-qemu-kvm）                    │
│  ├─ LXC（pve-container、lxc-pve）                │
│  ├─ ZFS（zfsutils-linux）                       │
│  ├─ Ceph（可選）                                 │
│  ├─ ★★★★ Proxmox 核心（pve-kernel / proxmox-kernel）│
│  └─ Debian 12 "bookworm" 基底                    │
└───────────────────────────────────────────────┘
```

★★★★★ **「大版本升級」= 連 Debian 基底一起換**（例如 bullseye → bookworm），
所以它的風險等級跟 `apt upgrade` 完全不是同一件事。

看目前版本：

```bash
pveversion
```

```text

```

看完整組件版本（★★★★ 升級前後都要留一份）：

```bash
pveversion -v
```


### 三種套件庫 ★★★★★

| 套件庫 | 需要訂閱 | 穩定度 | 建議 |
| --- | --- | --- | --- |
| ★★★★★ **pve-enterprise** | ✅ 需要有效訂閱金鑰 | ★★★★★ 最高（經過最多測試） | ★★★★★ **機關正式環境的首選** |
| ★★★★ **pve-no-subscription** | ❌ 免費 | ★★★ 一般可用，但更新較新、測試較少 | ★★★★ 沒買訂閱時用；**能接受偶爾踩雷才用在正式環境** |
| ★★ **pvetest** | ❌ 免費 | ★ 測試中 | ★★★★★ **絕對不要用在正式環境** |

★★★★★ **沒有訂閱卻留著 enterprise 套件庫**，是新裝 PVE 最常見的狀況，
`apt update` 會直接報 401：

```text
E: Failed to fetch https://enterprise.proxmox.com/debian/pve/dists/bookworm/InRelease
   401  Unauthorized [IP: ...]
E: The repository 'https://enterprise.proxmox.com/debian/pve bookworm InRelease'
   is not signed.
```

★★★★ **這不是壞掉，是提醒你「該選一個套件庫」**。
設定方式見「安裝或基礎操作」。

> [!tip] ★★★★★ 機關採購的實務建議
> 訂閱不只是拿到 enterprise 套件庫，還包含**原廠支援**。
> 跑正式服務的 PVE 主機，把訂閱編進年度預算是划算的 ——
> 出事的時候，「有沒有人可以問」的價值遠高於授權費。
> 授權管理見 [[100-02-13-guide-維運-資產與授權管理]]。

### 更新的三個層級 ★★★★★

| 層級 | 例子 | 風險 | 需不需要重開機 | 窗口 |
| --- | --- | --- | --- | --- |
| ★★★ **一般套件更新** | 修 bug 的小版本、工具更新 | 低 | 通常不用 | ★★★ 可在低峰期做 |
| ★★★★ **核心／QEMU 更新** | `proxmox-kernel-*`、`pve-qemu-kvm` | 中 | ★★★★★ **核心要重開機**；QEMU 要**重啟 VM** 才生效 | ★★★★ 排維護窗口 |
| ★★★★★ **大版本升級** | 7.4 → 8.0（含 Debian 換版） | ★★★★★ 高 | ★★★★★ 一定要 | ★★★★★ **正式維護窗口 + 完整備份 + 回退計畫** |

> [!warning] ★★★★★ 一個常被忽略的事實
> **更新了 `pve-qemu-kvm` 之後，正在跑的 VM 還是用舊的 QEMU 程序。**
> 要讓新版生效，必須**關機再開機**（或遷移到已更新的節點）——
> 光按「Reboot」按鈕在某些情況下**不會**換掉 QEMU 程序。
>
> 這代表：**安全性修補上了，但 VM 還沒被保護到**。
> 排維護窗口時要把「重啟所有 VM」算進去。

### 大版本升級的整體流程 ★★★★★

```
【單機】
  ① 備份（★★★★★ 含 /etc/pve 與 VM 資料）
  ② 更新到「當前大版本的最新小版本」
  ③ 跑官方升級前檢查工具 → ★★★★★ 所有 FAIL 清乾淨
  ④ 換套件庫的 codename（Debian + PVE 都要換）
  ⑤ apt update && apt dist-upgrade
  ⑥ 重開機 → 驗證
  ⑦ 收尾（重啟 VM、更新文件）

【叢集】★★★★★ 一次只升一個節點
  對每個節點重複上面的 ①～⑥，
  ★★★★★ 但順序與「工作負載疏散」是關鍵，見「叢集節點的升級順序」
```

### ★★★★★ 叢集升級期間的混版狀態

升級叢集時，會有一段時間**節點跑不同大版本**。

```
   pve1 (8.x)   pve2 (7.x)   pve3 (7.x)
      ▲已升級      待升級        待升級

  ★★★★★ 這段期間可以做的事：
     - 叢集維持 Quorum、共用設定檔正常
     - ★★★★ 從舊版遷移到新版：通常可以
     - ★★★★★ 從新版遷移回舊版：★★★★★ 不保證，可能失敗

  ★★★★★ 這段期間不要做的事：
     - 建立新的 VM／CT（避免用到新版才有的功能）
     - 改叢集設定、加減節點
     - 動 Ceph 的 crush map
```

★★★★★ **混版狀態要盡量短**。規劃時就要把所有節點排在同一個維護窗口內做完，
不要「這週升一台、下週再升一台」拖上一個月。

### 節點維護模式 ★★★★

PVE 的 HA 提供「維護模式」：把節點標記為維護中，
★★★★ **HA 資源會被移走，而且不會在節點回來之前被搬回來**。

```
   ha-manager crm-command node-maintenance enable pve2
             │
             ▼
   ★★★★ HA 管理的 VM/CT 開始遷移到其他節點
             │
             ▼
   節點空了 → 可以安心重開機、升級、換硬體
             │
             ▼
   ha-manager crm-command node-maintenance disable pve2
             │
             ▼
   ★★★★ 資源依 HA 群組設定回流（或留在原地，看你的 group 設定）
```

> [!warning] ★★★★★ 維護模式只管「HA 管理的資源」
> **沒有加入 HA 的 VM 與 CT 不會被自動搬走。**
> 那些要你自己 `qm migrate` / `pct migrate`，
> 或者接受它們會跟著節點一起停機。
>
> ★★★★★ **升級前一定要用 `qm list` / `pct list` 逐一確認節點上還剩什麼。**

### 憑證：PVE 上有兩組 ★★★★★

這是很多人搞混的地方。

| 檔案 | 誰用 | 能不能換 |
| --- | --- | --- |
| ★★★★★ `/etc/pve/local/pve-ssl.pem` + `pve-ssl.key` | ★★★★★ **叢集節點之間的內部通訊**（由叢集 CA 簽發） | ❌ **不要動**，動了叢集會壞 |
| ★★★★★ `/etc/pve/local/pveproxy-ssl.pem` + `pveproxy-ssl.key` | ★★★★★ **Web 介面（8006 埠）對外的憑證** | ✅ **這個才是你要換的** |

★★★★★ **想讓瀏覽器不再跳警告，換的是 `pveproxy-ssl.*`，不是 `pve-ssl.*`。**

```
瀏覽器 ──https://pve1.example.gov.tw:8006──► pveproxy
                                              使用 pveproxy-ssl.pem
                                              （沒有這個檔就退回用 pve-ssl.pem）

pve1 ◄──叢集內部 API 呼叫──► pve2
       兩邊都用 pve-ssl.pem，由叢集 CA 互相驗證
       ★★★★★ 千萬不要用外部憑證覆蓋這一組
```

## 安裝或基礎操作

### 設定套件庫 ★★★★★

#### 看目前設定

```bash
grep -R --include='*.list' -h '^deb' /etc/apt/sources.list /etc/apt/sources.list.d/ 2>/dev/null
```

```text
deb http://ftp.tw.debian.org/debian bookworm main contrib
deb http://ftp.tw.debian.org/debian bookworm-updates main contrib
deb http://security.debian.org/debian-security bookworm-security main contrib
deb https://enterprise.proxmox.com/debian/pve bookworm pve-enterprise
```

★★★★ PVE 8 也可以在 **Web 介面 → 節點 → Updates → Repositories** 直接勾選啟用／停用，
比手改檔案安全。

#### 情況 A：有訂閱 → 用 enterprise ★★★★★

```bash
pvesubscription set 'XXXX-XXXXXXXXXX'
pvesubscription get
```

```text
checktime: 1756...
key: XXXX-XXXXXXXXXX
level: c
productname: Proxmox VE Community Subscription 1 CPU/year
serverid: XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
status: active
```

★★★★★ `status: active` 才算成功。確認 enterprise 套件庫是啟用的即可。

#### 情況 B：沒有訂閱 → 停用 enterprise，改用 no-subscription ★★★★

```bash
# 停用 enterprise（★★★★ 註解掉，不要刪檔，日後買了訂閱好還原）
sed -i 's|^deb https://enterprise|#deb https://enterprise|' \
    /etc/apt/sources.list.d/pve-enterprise.list

# 啟用 no-subscription
cat > /etc/apt/sources.list.d/pve-no-subscription.list <<'EOF'
deb http://download.proxmox.com/debian/pve bookworm pve-no-subscription
EOF

apt update
```

```text
Get:1 http://ftp.tw.debian.org/debian bookworm InRelease [151 kB]
Get:2 http://download.proxmox.com/debian/pve bookworm InRelease [2,768 B]
...
Reading package lists... Done
Building dependency tree... Done
All packages are up to date.
```

★★★★★ **`bookworm` 這個 codename 必須跟你的 PVE 大版本對應**。
升級到新大版本時，這裡也要一起改（見「完整實戰範例」）。

> [!warning] ★★★★ 用 Ceph 的話還有一個套件庫
> `/etc/apt/sources.list.d/ceph.list` 也要一起確認 enterprise／no-subscription 與 codename，
> 忘了改會造成升級中途套件相依衝突。

### 小版本更新的標準流程 ★★★★

```bash
# ① 看看有什麼要更新（★★★★ 只看不做）
apt update
apt list --upgradable
```

```text
Listing... Done
libpve-common-perl/stable 8.x.x all [upgradable from: 8.x.x]
proxmox-kernel-6.8/stable 6.8.x-x amd64 [upgradable from: 6.8.x-x]
pve-manager/stable 8.x.x amd64 [upgradable from: 8.x.x]
qemu-server/stable 8.x.x amd64 [upgradable from: 8.x.x]
```

★★★★★ **先判斷有沒有核心與 QEMU** ——
有的話就要排維護窗口，沒有的話多半可以直接做。

```bash
# ② 做更新（★★★★★ 用 dist-upgrade，不要用 upgrade）
apt dist-upgrade
```

```text
Reading package lists... Done
The following NEW packages will be installed:
  proxmox-kernel-6.8.x-x-pve-signed
The following packages will be upgraded:
  libpve-common-perl pve-manager qemu-server ...
12 upgraded, 1 newly installed, 0 to remove and 0 not upgraded.
Need to get 128 MB of archives.
After this operation, 512 MB of additional disk space will be used.
Do you want to continue? [Y/n]
```

> [!danger] ★★★★★ 為什麼一定要用 `dist-upgrade`
> `apt upgrade` **不會安裝新套件、也不會移除套件**。
> PVE 的更新常常需要引入新的相依套件（例如新核心是一個新套件名）。
> 用 `apt upgrade` 會造成**升級不完整、版本卡在半途**，
> 之後每次更新都會報一堆 held back。
>
> ★★★★★ **PVE 官方文件明確要求使用 `apt dist-upgrade`。**

```bash
# ③ 更新後確認
pveversion -v | head -5
```

```text
proxmox-ve: 8.x.x (running kernel: 6.8.x-x-pve)
pve-manager: 8.x.x (running version: 8.x.x/xxxxxxxx)
proxmox-kernel-helper: 8.x.x
```

★★★★ 注意 `running kernel` 與已安裝的新核心版本可能不同 —— **代表還沒重開機**。

```bash
# ④ 判斷要不要重開機
ls -1 /boot/vmlinuz-* | sort -V | tail -1
uname -r
```

```text
/boot/vmlinuz-6.8.x-x-pve
6.8.x-y-pve
```

★★★★ 兩者不同 → **需要重開機才會用到新核心**。

### `pveupgrade`：更新前的提醒工具 ★★★

```bash
pveupgrade
```

```text
Starting system upgrade: apt-get dist-upgrade
...
Your System is up-to-date

seems you installed a kernel update - you probably need to reboot!
```

★★★ 它就是 `apt dist-upgrade` 加上一些 PVE 專屬的提醒（例如上面那行 reboot 提醒）。
★★★★ 實務上直接用 `apt dist-upgrade` 也可以，重點是**自己要記得判斷重開機**。

### 核心釘選（kernel pin）★★★★

新核心跟你的硬體（RAID 卡、網卡、GPU 直通）不合時，這是保命符。

```bash
# 看有哪些核心
proxmox-boot-tool kernel list
```

```text
Manually selected kernels:
None.

Automatically selected kernels:
6.8.x-x-pve
6.8.x-y-pve

Pinned kernel:
None
```

```bash
# ★★★★ 釘選在已知可用的版本
proxmox-boot-tool kernel pin 6.8.x-x-pve
```

```text
Setting '6.8.x-x-pve' as grub default entry and running update-grub.
```

```bash
proxmox-boot-tool kernel list | tail -3
```

```text
Pinned kernel:
6.8.x-x-pve
```

```bash
# 問題解決後解除釘選
proxmox-boot-tool kernel unpin
```

> [!tip] ★★★★★ 釘選一次、只釘一次開機
> 想「只用某個核心開一次機」來測試，可以用：
> ```bash
> proxmox-boot-tool kernel pin 6.8.x-x-pve --next-boot
> ```
> ★★★★ 下次開機用釘選的，之後自動恢復。做遠端升級測試時很好用。

★★★★★ **釘選了核心，代表你也不會拿到之後的核心安全性修補。**
一定要在維運文件裡登記「哪台釘在哪個版本、為什麼、什麼時候要重新評估」。

## 進階應用

### ★★★★★ 大版本升級：完整前置檢查

#### 步驟 1：確認你要升到哪一版，看官方升級指引

★★★★★ **第一件事永遠是打開 Proxmox 官方 wiki 的
「Upgrade from <舊版> to <新版>」頁面**，因為每一代的注意事項都不一樣：

### 叢集節點的升級順序 ★★★★★

```
【三節點叢集，pve1 / pve2 / pve3】

  ★★★★★ 原則：一次只動一個節點，動之前先把它清空

  ┌─ 前置：三個節點都升到當前大版本的最新小版本
  │        三個節點都跑過升級前檢查工具、FAILURES = 0
  │        ★★★★★ 全叢集完整備份
  │
  ├─ 第 1 台（★★★★ 挑「工作負載最少 / 最不重要」的先做）
  │    ① ha-manager crm-command node-maintenance enable pve3
  │    ② 等 HA 資源遷走
  │    ③ ★★★★★ 手動遷走「沒進 HA」的 VM/CT
  │    ④ qm list / pct list 確認節點是空的
  │    ⑤ 換 codename → apt dist-upgrade → reboot
  │    ⑥ 驗證：pveversion / pvecm status / pvesm status
  │    ⑦ ha-manager crm-command node-maintenance disable pve3
  │    ⑧ ★★★★ 觀察一段時間（至少跑幾個工作負載上去試）
  │
  ├─ 第 2 台：同上
  │
  └─ 第 3 台：同上

  ★★★★★ 每台之間的驗證都要做完才動下一台。
     發現問題就停在這裡，不要繼續往下升。
```

> [!warning] ★★★★★ 兩節點叢集特別危險
> 兩節點叢集只要停掉一台，就**只剩 1 票，Quorum 不成立**，
> `/etc/pve` 會變成唯讀，VM 沒辦法改設定甚至沒辦法啟動。
>
> 升級兩節點叢集之前，**一定要有 QDevice（仲裁裝置）**。
> 設定方式見 [[050-01-03-07-svc-PVE-叢集與高可用]]。

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ `apt update` 報 `401 Unauthorized`（enterprise.proxmox.com） | 沒訂閱卻啟用 enterprise 套件庫 | 停用 enterprise、啟用 no-subscription；或買訂閱後 `pvesubscription set` |
| ★★★★★ 升級中途 SSH 斷線，套件停在半途 | 沒有用 screen／tmux | 重新登入後 `dpkg --configure -a` 再 `apt -f install`，然後 `apt dist-upgrade` 續做 |
| ★★★★★ `apt dist-upgrade` 報一堆套件 `held back` | 用過 `apt upgrade`，或 codename 只改了一半 | 逐行檢查所有 `.list`；`apt-mark showhold` 看有沒有被 hold 的套件 |
| ★★★★★ 升級後主機失聯 | 設定檔衝突時誤按 Y 覆蓋了 `/etc/network/interfaces` | ★★★★★ 用 IPMI／實體終端進去，從 `/etc/network/interfaces.dpkg-old` 還原 |
| ★★★★★ 重開機後進不了系統 | 新核心與硬體不合 | 在開機選單選舊核心進系統，`proxmox-boot-tool kernel pin <舊版本>` |
| ★★★★ 升級檢查工具報 `FAIL: ... storage not online` | 儲存離線 | ★★★★★ 先修好儲存再升級，備份路徑不能是壞的 |
| ★★★★ `pve7to8` 報 `WARN: N running guest(s)` | 有 VM 在跑 | 升級要重開機，先遷走或停機；這是提醒不是錯誤 |
| ★★★★★ 兩節點叢集升級時 `/etc/pve` 變唯讀 | 停掉一台後 Quorum 不成立 | ★★★★★ 先加 QDevice；緊急時 `pvecm expected 1`（★★★★★ 高風險，見下方警告） |
| ★★★★ 升級後 Web 介面連不上（8006） | pveproxy 沒起來，或憑證檔壞了 | `systemctl status pveproxy`、`journalctl -u pveproxy -n 50`；憑證問題用 `pvenode cert delete` 退回自簽 |
| ★★★★ 升級後 VM 開不起來，報 QEMU 參數不支援 | 舊版設定用了新版移除的選項 | 看 `qm start <id>` 的錯誤訊息，對照官方升級指引的「移除的功能」章節 |
| ★★★★ 安全性修補上了但 VM 仍受影響 | `pve-qemu-kvm` 更新後 VM 沒重啟 | ★★★★★ 關機再開機（不是按 Reboot），或遷移到已更新節點 |
| ★★★★ 憑證換完瀏覽器還是警告 | 換錯檔案（動到 `pve-ssl.pem`），或憑證鏈不完整、SAN 沒寫對 | 用 `pvenode cert set` 換 `pveproxy-ssl.*`；`openssl s_client` 檢查鏈與 SAN |
| ★★★★ ACME 申請失敗 `Timeout during connect` | CA 從外網連不到你的 80 埠 | 改用 DNS-01 驗證，或改用內部 CA |
| ★★★ ACME 申請失敗 `too many failed authorizations` | 在正式環境反覆重試觸發速率限制 | ★★★★★ 用 Staging 測通再切正式 |
| ★★★ 磁碟空間不足導致升級中斷 | `/` 或 `/boot` 滿了 | `apt clean`、清舊核心；★★★★ 升級前先確認 `/boot` 至少有 1 GB |
| ★★★ `pveversion -v` 顯示版本混雜 | 升級不完整 | `apt update && apt dist-upgrade` 再跑一次；仍不行看 `apt -f install` |
| ★★★ 節點解除維護模式後 HA 資源沒回來 | HA group 沒設 `nofailback` 或優先權 | 這是設定行為，見 [[050-01-03-07-svc-PVE-叢集與高可用]] |

> [!danger] ★★★★★ `pvecm expected 1` 是最後手段
> 這行指令會**強制把 Quorum 門檻降到 1**，讓單一節點可以寫 `/etc/pve`。
>
> ★★★★★ **如果另一台其實還活著（只是網路斷了），兩邊都會以為自己是唯一的節點，
> 各寫各的設定 —— 這叫 split-brain，會造成資料損毀。**
>
> 只在**你已經百分之百確認其他節點是關機狀態**時才用，
> 而且處理完要立刻恢復正常的 expected 值。

### 升級失敗時的回退決策 ★★★★★

```
       升級後驗證沒過
              │
    ┌─────────┴─────────┐
    │                    │
「系統起得來」        「系統起不來」
    │                    │
    ▼                    ▼
① 看 journalctl -p err   ① 開機選單選舊核心
② 服務層問題？           ② 進得去 → kernel pin 舊版
   → 個別修            ③ 進不去 → GRUB rescue／
③ 套件不完整？               live media 救援
   → dpkg --configure -a      （見 020-01-25）
④ 都不行 ↓                ④ 都不行 ↓
    └─────────┬─────────┘
              ▼
   ★★★★★ 最終回退：重灌該節點成新大版本，
        從 vzdump 還原 VM/CT，
        從 /root/pve-etc-*.tar.gz 還原網路與設定，
        pvecm add 重新加回叢集
```

★★★★★ **大版本升級沒有「apt downgrade 回去」這種選項。**
所謂回退，實際上就是**重建 + 還原備份**。
這也是為什麼「升級前一定要有可還原的備份」不是口號。

## 安全性注意事項

### ★★★★★ 不更新才是最大的風險

| 風險 | 說明 |
| --- | --- |
| ★★★★★ **QEMU 的虛擬機逃逸漏洞** | 一旦被利用，攻擊者從 VM 打到 hypervisor，**整台主機上所有 VM 都完蛋** |
| ★★★★★ **核心漏洞** | 本地提權、容器逃逸 |
| ★★★★ **Web 介面漏洞** | 8006 埠若對內網開放，未修補的介面是入口 |
| ★★★★ **相依函式庫** | OpenSSL、glibc 等基底套件的問題 |

★★★★★ **「怕升級出事所以不升級」是機關最常見、也最危險的決策。**
正確的作法是**建立可靠的備份與演練流程，讓升級變成低風險例行作業**。

### 更新的節奏建議 ★★★★

| 類型 | 建議節奏 |
| --- | --- |
| ★★★★★ 安全性修補（尤其 QEMU／核心） | ★★★★★ **公告後兩週內**排窗口套用 |
| ★★★★ 一般小版本 | 每月一次 |
| ★★★★ 大版本升級 | ★★★★ 新版釋出後**觀察 2～3 個月**再排，讓別人先踩雷 |
| ★★★★★ 上游停止支援前 | ★★★★★ **一定要升上去**，不要跑在 EOL 版本 |

### 升級期間的存取控制 ★★★★

- ★★★★ 維護窗口期間，把 Web 介面限制在管理網段
  （[[050-01-03-05-guide-PVE-網路設定]] 的管理網分離）
- ★★★★★ 升級用的 root 密碼與 SSH 金鑰，**窗口結束後檢查有沒有留下臨時憑證**
- ★★★ 升級腳本裡不要寫死密碼，用 SSH 金鑰

### 憑證安全 ★★★★

| 項目 | 要求 |

| ★★★★★ 私鑰不進 git | 憑證與金鑰**不要放進版本控制** |
| ★★★★ 到期監控 | 納入監控（[[100-01-04-guide-日誌-健康檢查與可用性監控]]） |

## 練習題

1. 在測試機上把 enterprise 套件庫切換成 no-subscription，
   跑完 `apt update` 並確認沒有 401 錯誤。接著把它切回去（不套用訂閱）並觀察錯誤重現。
2. 對一台測試 PVE 執行一次完整的小版本更新，**在更新前後各留一份 `pveversion -v`**，
   用 `diff` 列出哪些組件版本變了。
3. 安裝一個新核心後，用 `proxmox-boot-tool kernel pin` 釘選舊核心並重開機，
   用 `uname -r` 確認生效，再解除釘選。
4. 用自建 CA 簽一張 `pve-test.example.gov.tw` 的憑證（含正確 SAN），
   用 `pvenode cert set` 套上去，並用 `openssl s_client` 驗證憑證鏈完整。
5. 在測試叢集上把一個節點放進維護模式，記錄 HA 資源遷移的過程，
   並找出「有哪些 VM/CT 沒有被自動搬走」。
6. 寫一份你們機關的 PVE 大版本升級 SOP，
   ★★★★★ **必須包含備份驗證、回退決策點、停止判準**。

> [!question]- 練習解答
>
> **1.**
> ```bash
> sed -i 's|^deb https://enterprise|#deb https://enterprise|' \
>     /etc/apt/sources.list.d/pve-enterprise.list
> echo 'deb http://download.proxmox.com/debian/pve bookworm pve-no-subscription' \
>     > /etc/apt/sources.list.d/pve-no-subscription.list
> apt update    # 應該乾淨無錯
>
> # 切回去
> sed -i 's|^#deb https://enterprise|deb https://enterprise|' \
>     /etc/apt/sources.list.d/pve-enterprise.list
> rm /etc/apt/sources.list.d/pve-no-subscription.list
> apt update    # ★★★★ 會重現 401 Unauthorized
> ```
>
> **2.**
> ```bash
> pveversion -v > /tmp/before.txt
> apt update && apt dist-upgrade
> pveversion -v > /tmp/after.txt
> diff /tmp/before.txt /tmp/after.txt
> ```
> ★★★★ 特別注意 `pve-qemu-kvm` 與 `proxmox-kernel-*` 有沒有變 ——
> 有的話代表你需要**重啟 VM／重開機**才會真正生效。
>
> **3.**
> ```bash
> proxmox-boot-tool kernel list
> proxmox-boot-tool kernel pin 6.8.x-x-pve
> reboot
> uname -r          # 應為釘選的版本
> proxmox-boot-tool kernel unpin
> reboot
> ```
> ★★★★ 釘選期間**拿不到後續核心安全性修補**，一定要在文件裡登記原因與解除時程。
>
> **4.**
> ```bash
> # 簽發流程見 090-01-08
> cat pve-test.crt intermediate-ca.crt > fullchain.crt
> pvenode cert set fullchain.crt pve-test.key --force --restart
> openssl s_client -connect 127.0.0.1:8006 -showcerts </dev/null 2>/dev/null \
>   | grep -E 's:|i:'
> ```
> ★★★★★ 驗證重點：① `subject` 是你的主機 ② `issuer` 是你的中繼 CA
> ③ SAN 包含實際使用的 FQDN 與 IP ④ 鏈上看得到中繼 CA。
>
> **5.**
> ```bash
> ha-manager crm-command node-maintenance enable pve3
> watch -n2 'ha-manager status'
> # 遷移完成後
> ssh root@pve3 'qm list; pct list'
> ```
> ★★★★★ 剩下的就是**沒有加入 HA 的資源** —— 這正是最容易被忽略、
> 導致「以為節點清空了卻還有服務在上面」的來源。
>
> **6.** SOP 至少要有：
> - ★★★★★ **前置門檻**：備份已完成且**通過還原測試**、升級前檢查 FAILURES = 0、變更單已核准
> - ★★★★★ **停止判準**：任一節點驗證未通過即停止，維持混版並回報
> - ★★★★★ **回退方案**：重建節點 + 從備份還原（明確寫出 RTO）
> - ★★★★ **驗證清單**：版本、服務、叢集、儲存、VM、服務層 HTTP 檢查
> - ★★★★ **觀察期**與結案條件

## 小測驗

**Q1.** 為什麼 PVE 官方要求用 `apt dist-upgrade` 而不是 `apt upgrade`？

**Q2.** 是非題：更新了 `pve-qemu-kvm` 套件之後，正在執行的 VM 立刻就受到新版保護。

**Q3.** 下列哪一個檔案是「換掉之後瀏覽器就不會再跳憑證警告」的？
（A）`/etc/pve/local/pve-ssl.pem`　（B）`/etc/pve/local/pveproxy-ssl.pem`
（C）`/etc/ssl/certs/ssl-cert-snakeoil.pem`　（D）`/etc/pve/priv/pve-root-ca.pem`

**Q4.** 升級前檢查工具跑完顯示 `FAILURES: 2`，你應該？
（A）先升再說，反正只有 2 個　（B）把 2 個 FAIL 修到 0 再升
（C）改用 `--force` 跳過　（D）只要 WARNINGS 是 0 就可以升

**Q5.** 這串指令做了什麼？可能有什麼風險？

```bash
sed -i 's/bullseye/bookworm/g' /etc/apt/sources.list.d/*.list
```

**Q6.** 簡答：`ha-manager crm-command node-maintenance enable pve3` 之後，
為什麼還是要自己跑 `qm list` 和 `pct list`？

**Q7.** 兩節點叢集在升級時停掉一台，`/etc/pve` 變成唯讀。原因是什麼？
正確的預防做法是？

**Q8.** 新核心裝上去後主機開不進系統，你在開機選單選了舊核心成功進系統。
接下來最該做的一件事是什麼？

**Q9.** 是非題：大版本升級失敗時，可以用 `apt` 把套件降回舊版本回退。

**Q10.** 機關的 PVE 主機在內網，沒有對外的 80 埠。
想用 ACME 自動申請 Let's Encrypt 憑證，可行嗎？有什麼替代方案？

> [!question]- 測驗答案
>
> **Q1 →** 因為 `apt upgrade` **不會安裝新套件也不會移除套件**。 ★★★★★
> PVE 的更新常需要引入新的相依套件（例如新核心是新的套件名），
> 用 `apt upgrade` 會造成升級不完整、套件被 held back。見「小版本更新的標準流程」。
>
> **Q2 → 否** ★★★★★
> 執行中的 VM 仍由**舊的 QEMU 程序**在跑。必須**關機再開機**
> （或遷移到已更新的節點）才會換成新版。
> 光按 Reboot 在某些情況下不會換掉程序。見「更新的三個層級」下方警告。
>
> **Q3 → (B)** ★★★★★
> `pveproxy-ssl.pem` 是 Web 介面（8006）對外用的憑證。
> ★★★★★ `pve-ssl.pem` 是**叢集節點之間**用的，動它會把叢集弄壞。
> 見「憑證：PVE 上有兩組」。
>
> **Q4 → (B)** ★★★★★
> FAILURES 是明確的阻擋項，代表升級一定會出問題。
> 必須逐項修到 0。WARNINGS 也要每一條看懂再決定接不接受。
> 見「步驟 4：跑官方升級前檢查工具」。
>
> **Q5 →** 把 `/etc/apt/sources.list.d/` 底下所有 `.list` 檔的 codename
> 從 `bullseye` 換成 `bookworm`。
> ★★★★★ 風險：**它沒有動 `/etc/apt/sources.list`**（Debian 基底套件庫在那裡），
> 只改一半會造成升級失敗或套件相依衝突。
> ★★★★ 所以改完一定要用 `grep -R ... '^deb'` **逐行檢查全部**。見「步驟 5」。
>
> **Q6 →** 因為**維護模式只會疏散「HA 管理的資源」**。 ★★★★★
> 沒有加入 HA 群組的 VM 與 CT **不會被自動搬走**，
> 你必須自己 `qm migrate` / `pct migrate`。
> 兩個清單都空了才代表節點真的清乾淨。見「節點維護模式」。
>
> **Q7 →** 兩節點叢集的 Expected votes 是 2，Quorum 門檻是 2。 ★★★★★
> 停掉一台只剩 1 票，Quorum 不成立，`pmxcfs` 就把 `/etc/pve` 轉唯讀保護資料。
> ★★★★★ 預防做法：**部署 QDevice 仲裁裝置**，讓票數變成 3、門檻 2，
> 停一台仍有 2 票。見「叢集節點的升級順序」的警告與
> [[050-01-03-07-svc-PVE-叢集與高可用]]。
>
> **Q8 → 立刻 `proxmox-boot-tool kernel pin <舊核心版本>`。** ★★★★★
> 否則下次任何原因重開機（斷電、當機、遠端 reboot），
> 系統又會選新核心而再次開不起來 —— 而你可能不在現場。
> 釘選之後再從容排查，並在文件裡登記釘選原因。見「核心釘選」。
>
> **Q9 → 否** ★★★★★
> 大版本升級跨越了 Debian 基底換版，**沒有可靠的 apt 降級路徑**。
> 實務上的「回退」就是**重建節點 + 從備份還原**。
> 這正是「升級前一定要有可還原備份」的原因。見「升級失敗時的回退決策」。
>
> **Q10 → HTTP-01 驗證不可行**（CA 從外網連不到你的 80 埠）。★★★★★
> 替代方案有兩個：
> ① ★★★★ 改用 **DNS-01 驗證**（用 DNS provider plugin，不需要對外開埠）；
> ② ★★★★★ 放棄公開 CA，改用**機關內部 CA 簽發**並把根憑證派送到所有終端
> （[[090-01-09-guide-PKI-根憑證派送與信任]]）——
> 這也是機關內網主機最常見的做法。
> 另外注意 ★★★★★ **內部網域名稱本來就拿不到公開 CA 憑證**。
> 見「路線 B：ACME 自動申請與續期」。
