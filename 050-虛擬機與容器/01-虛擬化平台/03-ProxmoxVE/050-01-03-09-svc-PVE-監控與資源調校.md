# PVE 監控與資源調校

> [!abstract] 這篇你會學到
> - 內建圖表每一條線在講什麼，★★★★★ **尤其是被誤解最多的 `IO delay`**
> - RRD 資料存在哪、`pvestatd` 多久收一次、怎麼用 API 把數據撈出來
> - 外接 **InfluxDB／Graphite**（PVE 內建支援）與 **Prometheus**（走 exporter）
> - ★★★★ **超配的安全比例** —— CPU、記憶體、儲存**三者的準則完全不同**
> - **balloon** 真正的行為，以及它為什麼會造成抖動；哪些 VM 一定要關掉
> - **KSM** 省了多少、代價是什麼、什麼情況不該開
> - **CPU type** 對效能與遷移相容性的取捨（`host` vs `x86-64-v2-AES`）
> - ★★★★★ **磁碟快取模式（none／writeback／writethrough／unsafe）與資料安全的真實關係**
> - **IO thread** 與 **SCSI 控制器**怎麼選

> [!warning] 未實機驗證
> 本篇**以 Proxmox VE 8 為例**（`pvestatd`、`/etc/pve/status.cfg`、`qm set` 的磁碟參數）。
>
> ★★★★★ **超配比例、快取模式的效能數字都跟你的硬體強相關**，
> 本篇給的是**方向與上限原則**，不是可以直接套用的公式。
> ★★★★★ **任何調校都必須在你自己的環境量測前後差異**。
>
> ★★★★★ 外部 metric server 的設定鍵名會隨版本變動，
> ★★★★ **建議一律用 Web UI（`Datacenter → Metric Server`）設定**，
> 讓它幫你寫 `/etc/pve/status.cfg`，不要手打。
> 指令參數以 `man qm`、`qm set --help`、`man pvestatd` 為準。

## 觀念說明

### 一、監控在 PVE 裡是怎麼運作的 ★★★★

```
每個節點
   │
   ├── pvestatd  ★★★★★ 每 10 秒收一次
   │     ├─ 節點：CPU、記憶體、swap、IO delay、load、網路
   │     ├─ 每台 VM／CT：CPU、記憶體、磁碟 IO、網路
   │     └─ 每個儲存：總量／已用
   │
   ├──► RRD 資料庫（rrdcached）
   │      /var/lib/rrdcached/db/pve2-node/<node>
   │      /var/lib/rrdcached/db/pve2-vm/<vmid>
   │      /var/lib/rrdcached/db/pve2-storage/<node>/<storage>
   │      ★★★★★ 固定大小，越舊的資料解析度越低
   │
   ├──► Web UI 的 Summary 圖表
   │
   └──► ★★★★ 外部 metric server（若有設定）
          InfluxDB / Graphite  ← pvestatd 主動推送
```

★★★★★ **關鍵認知：PVE 內建的圖表是「RRD 輪替式」的** ——
資料庫大小固定，時間越久的資料被壓縮成越粗的平均值。

| 時間範圍 | 大約解析度 | 用途 | 重要度 |
| --- | --- | --- | --- |
| Hour | 分鐘級 | ★★★★★ **事故當下的排查** | ★★★★★ |
| Day | 十分鐘級 | 一天內的趨勢 | ★★★★ |
| Week / Month | 小時級 | 容量規劃 | ★★★★ |
| Year | 天級 | 年度成長趨勢 | ★★★ |

> [!danger] ★★★★★ RRD 不適合做事後鑑識
> 「上週三下午三點十七分那一分鐘發生什麼事」——
> ★★★★★ **RRD 已經把它平均掉了，你看不到那個尖峰。**
>
> 需要真正的歷史細節，★★★★★ **必須外接 InfluxDB／Prometheus**。
> 這是「為什麼要外接監控」最實際的理由。

### 二、內建圖表怎麼看：節點層 ★★★★★

**Node → Summary** 的四張主圖：

| 圖 / 指標 | 在講什麼 | 怎麼判讀 | 重要度 |
| --- | --- | --- | --- |
| ★★★★ **CPU usage** | 節點整體 CPU 使用率（%） | 持續 > 80% 就該擴充或減載 | ★★★★ |
| ★★★★★ **IO delay** | ★★★★★ **CPU 在「等磁碟」上浪費的時間比例** | ★★★★★ **本篇最重要的指標，見下方** | ★★★★★ |
| ★★★★ **Load average** | 1／5／15 分鐘的可執行＋不可中斷佇列長度 | ★★★★★ **要跟核心數比**，不是看絕對值 | ★★★★★ |
| ★★★★★ **RAM usage** | 已用記憶體 | ★★★★★ **超過 80% 就要警覺**（見超配一節） | ★★★★★ |
| ★★★★★ **Swap usage** | ★★★★★ **虛擬化主機上「不該有」swap 使用** | ★★★★★ 只要開始用 swap 就是超配過頭 | ★★★★★ |
| ★★★ **KSM sharing** | KSM 合併掉的記憶體量 | 數字大代表 VM 之間內容重複度高 | ★★★ |
| ★★★ **Network traffic** | 節點網路吞吐 | 跟備份／遷移時段對照 | ★★★ |

> [!danger] ★★★★★ `IO delay` 是最被誤解的指標
> 它**不是**「磁碟使用率」，也**不是**「IO 慢」。
> 它是 **CPU 處於 iowait 狀態的時間比例** ——
> 也就是「CPU 有事可做，但在等磁碟回應而閒著」。
>
> | IO delay | 意義 | 該做什麼 | 重要度 |
> | --- | --- | --- | --- |
> | **0～2%** | 正常 | 什麼都不用做 | ★ |
> | **2～10%** | ★★★★ 有壓力，可能是備份或大量寫入時段 | 對照時間點找來源 | ★★★★ |
> | ★★★★★ **> 10% 且持續** | ★★★★★ **儲存是瓶頸** | ★★★★★ 查是哪台 VM、查快取模式、查儲存本身 | ★★★★★ |
> | ★★★★★ **> 30%** | ★★★★★ **整台機器實質上被磁碟卡住** | ★★★★★ 使用者已經在抱怨了 | ★★★★★ |
>
> ★★★★★ **看到 IO delay 高，先問三件事**：
> 1. 是不是備份時段？（見 [[050-01-03-06-svc-PVE-備份與還原]]）
> 2. 是不是某台 VM 的快取模式設錯了？
> 3. 是不是 thin pool 快滿了、或 ZFS ARC 被壓縮了？

> [!note] ★★★★★ Load average 要除以核心數才有意義
> ```
> 16 核心的機器：
>   load 4.0   → 25% 忙  → ★ 很閒
>   load 16.0  → 100%    → ★★★ 滿載但還沒排隊
>   load 32.0  → 200%    → ★★★★★ 嚴重排隊，回應變慢
> ```
> ★★★★★ **但 Linux 的 load 包含「不可中斷睡眠（D state）」** ——
> 磁碟卡住時 load 會飆到很高，但 CPU 其實是閒的。
> ★★★★★ **load 高 + CPU usage 低 + IO delay 高 = 儲存問題，不是 CPU 問題。**
> 這個組合是判斷瓶頸最快的方法。

### 三、內建圖表怎麼看：VM 層 ★★★★

| 指標 | 陷阱 | 重要度 |
| --- | --- | --- |
| ★★★★ **CPU usage** | ★★★★★ 這是**相對於分配給它的 vCPU 數**的百分比，不是節點總量 | ★★★★★ |
| ★★★★★ **Memory usage** | ★★★★★ **沒裝 guest agent 時，這個數字是「QEMU 配置的量」不是 guest 真正用掉的量** | ★★★★★ |
| ★★★★ **Disk IO** | 是 QEMU 層看到的，跟 guest 內 `iostat` 可能不同 | ★★★★ |
| ★★★ **Network traffic** | 以 vNIC 為單位 | ★★★ |

> [!warning] ★★★★★ VM 記憶體圖表在沒裝 agent 時「永遠是滿的」
> 沒有 balloon driver / guest agent 時，
> PVE 只知道「我給了它 8 GB」，不知道 guest 裡面實際用了多少。
> 圖表因此看起來一直是 100%。
>
> ★★★★★ **這是「我的 VM 記憶體一直滿的」最常見的假警報。**
> 解法：★★★★★ **裝 QEMU Guest Agent**（見 [[050-01-03-03-guide-PVE-虛擬機管理]]），
> 裝了之後 PVE 才讀得到 guest 內部的真實用量。

### 四、超配（overcommit）：三種資源、三種準則 ★★★★★

★★★★★ **最重要的觀念：CPU、記憶體、儲存的超配風險完全不同，不能用同一套規則。**

```
          可以超配嗎？      超配過頭會怎樣？
CPU        ★★★★ 可以      → 變慢（可回復）
記憶體     ★★★★★ 幾乎不行 → ★★★★★ VM 被 OOM killer 殺掉（服務中斷）
儲存       ★★★★ 可以但要監控 → ★★★★★ 寫入失敗、檔案系統唯讀、可能資料損毀
```

#### CPU 超配 ★★★★

| 場景 | 建議上限（vCPU 總數 : 實體執行緒數） | 重要度 |
| --- | --- | --- |
| ★★★★★ **延遲敏感**（資料庫、即時系統、視訊） | ★★★★★ **1 : 1，不超配** | ★★★★★ |
| ★★★★ **一般伺服器**（Web、應用、檔案） | 2:1 ～ 3:1 | ★★★★ |
| ★★★ **開發測試、桌面 VDI、大多閒置** | 4:1 ～ 8:1（★★★★ 需實測） | ★★★ |

★★★★★ **判斷有沒有超配過頭的方法不是算比例，是看指標**：

| 指標 | 門檻 | 重要度 |
| --- | --- | --- |
| ★★★★★ 節點 **Load average / 核心數** | 持續 > 1.0 就代表在排隊 | ★★★★★ |
| ★★★★ 節點 CPU usage | 持續 > 80% | ★★★★ |
| ★★★★★ guest 內的 **steal time**（`top` 的 `st`） | ★★★★★ **> 5% 代表 VM 明顯被搶 CPU** | ★★★★★ |

```bash
# ★★★★★ 在 guest 裡面看 steal time（最直接的證據）
top -bn1 | head -3
```

```text
top - 14:22:31 up 12 days,  3:41,  1 user,  load average: 1.24, 1.31, 1.19
Tasks: 142 total,   1 running, 141 sleeping,   0 stopped,   0 zombie
%Cpu(s):  8.2 us,  2.1 sy,  0.0 ni, 82.4 id,  0.3 wa,  0.0 hi,  0.2 si,  6.8 st
                                                                        ^^^^^^^
                                    ★★★★★ st = 6.8% → 這台 VM 拿不到它要的 CPU
```

> [!tip] ★★★★ 單台 VM 的 vCPU 不要超過單顆 CPU 的核心數
> 給一台 VM 32 個 vCPU 而節點只有 2×16 核，
> 會讓排程器必須跨 NUMA node 安排，★★★★ **效能可能比給 16 個還差**。
> 大型 VM 要用 `--numa 1` 讓 guest 看得到 NUMA 拓撲。

#### 記憶體超配 ★★★★★

> [!danger] ★★★★★ 正式環境：記憶體不要超配
> ```
> 所有執行中 VM 的 memory 總和
>   + LXC 容器的記憶體上限總和
>   + ★★★★★ 主機保留（PVE 本身 2～4 GB）
>   + ★★★★★ ZFS ARC（如果用 ZFS，預設可能吃掉一半實體記憶體！）
>   ────────────────────────────────────────────
>   ≤  實體記憶體 × 0.8      ★★★★★ 留 20% 餘裕
> ```
> ★★★★★ **超過的後果不是「變慢」，是 Linux OOM killer 直接殺掉某個 QEMU 行程** ——
> 對使用者來說就是**一台 VM 無預警斷電**。
> ★★★★★ 而且被殺的**不一定是佔最多的那台**。

```bash
# ★★★★★ 檢查有沒有發生過 OOM（每次「VM 無故消失」都要查這個）
dmesg -T | grep -i -E "out of memory|oom-kill"
```

```text
[Tue Sep  2 03:14:22 2026] Out of memory: Killed process 3412 (kvm) total-vm:8912344kB, ...
```

```bash
journalctl -k --since "1 day ago" | grep -i oom
```

```bash
# ★★★★★ ZFS ARC 吃掉多少（用 ZFS 時必查）
arc_summary | head -20
cat /sys/module/zfs/parameters/zfs_arc_max
```

```text
0
```

★★★★★ **`0` 代表沒有限制，ZFS 預設最多可吃掉一半實體記憶體。**
在有跑 VM 的節點上，**一定要設上限**：

```bash
# 限制 ARC 最多 8 GiB（★★★★ 數字依你的環境調整）
echo "options zfs zfs_arc_max=8589934592" > /etc/modprobe.d/zfs.conf
update-initramfs -u
# ★★★★ 需要重開才生效
```

**Swap**：

```bash
free -h
```

```text
               total        used        free      shared  buff/cache   available
Mem:            62Gi        48Gi       2.1Gi       112Mi        12Gi        13Gi
Swap:          8.0Gi       1.2Gi       6.8Gi
                            ^^^^^
              ★★★★★ 虛擬化主機開始用 swap = 你已經超配了
```

★★★★ **建議把 `vm.swappiness` 調低**，讓主機盡量不要把 VM 的記憶體換出去：

```bash
sysctl vm.swappiness
```

```text
vm.swappiness = 60
```

```bash
echo "vm.swappiness = 10" > /etc/sysctl.d/99-pve-swappiness.conf
sysctl -p /etc/sysctl.d/99-pve-swappiness.conf
```

★★★★★ **但這只是緩解，真正的解法是不要超配。**

#### 儲存超配（thin provisioning） ★★★★★

| 儲存類型 | 支援薄配置 | 超配風險 | 重要度 |
| --- | --- | --- | --- |
| ★★★★★ **LVM-thin** | ✅ | ★★★★★ **thin pool 100% 滿 → VM 磁碟寫入失敗、檔案系統唯讀** | ★★★★★ |
| ★★★★★ **ZFS** | ✅ | ★★★★★ pool 滿 → 同上，而且 ZFS 在接近滿時**效能急遽下降** | ★★★★★ |
| ★★★★ **NFS（qcow2）** | ✅ | ★★★★ 底層檔案系統滿 | ★★★★ |
| ★★★ **LVM（厚配置）** | ❌ | 不會超配（配置時就佔滿） | ★★★ |

> [!danger] ★★★★★ Thin pool 滿掉是「不可逆」等級的事故
> LVM-thin pool 用到 100% 時：
> - VM 的寫入請求失敗 → guest 檔案系統**進入唯讀**或直接損毀
> - ★★★★★ **即使你事後擴充，已經寫壞的資料救不回來**
> - ★★★★★ 更糟的是**中繼資料（metadata）空間**也會滿，那個滿掉更難救
>
> ★★★★★ **鐵則**：
> | 使用率 | 動作 |
> | --- | --- |
> | 75% | ★★★★★ **告警**，開始規劃擴充 |
> | 85% | ★★★★★ **立即處理**，停止新增 VM |
> | 90% | ★★★★★ **緊急** —— 刪快照、搬 VM、擴 pool |

```bash
# ★★★★★ 每日要看的一行
lvs -o lv_name,lv_size,data_percent,metadata_percent --units g
```

```text
  LV            LSize      Data%  Meta%
  data          800.00g    68.42  31.05
  vm-101-disk-0  32.00g
  vm-102-disk-0 200.00g
```

★★★★★ **`Data%` 與 `Meta%` 兩個都要看**，中繼資料滿了一樣會出事。

```bash
# ZFS
zpool list
zfs list -o name,used,avail,refer,quota
```

```text
NAME    SIZE  ALLOC   FREE  CKPOINT  EXPANDSZ   FRAG    CAP  DEDUP    HEALTH
rpool   928G   612G   316G        -         -    18%    65%  1.00x    ONLINE
```

★★★★ ZFS 的 `CAP` **建議不要超過 80%**，超過之後寫入效能會明顯下降。

### 五、Balloon：它到底在做什麼 ★★★★★

**Balloon（記憶體氣球）= 在 guest 裡面「假裝佔用」記憶體，逼 guest 把它還給主機。**

```
VM 設定：memory=8192, balloon=4096（最小 4 GB）

主機記憶體充裕時：
  ┌──────────── guest 看到 8 GB ────────────┐
  │  guest 實際使用 3 GB │   空閒 5 GB      │
  └──────────────────────────────────────────┘
  主機實際配置：★★★★ 依 guest 觸碰過的頁面而定

主機記憶體吃緊時（★★★★★ 使用率超過門檻）：
  ┌──────────── guest 看到 8 GB ────────────┐
  │ guest 使用 3 GB │ 氣球佔住 4 GB │ 1 GB │
  └──────────────────────────────────────────┘
                     ↓ 這 4 GB 還給主機
```

| 設定 | 意義 | 重要度 |
| --- | --- | --- |
| ★★★★ `memory` | ★★★★★ **上限**，guest 看到的記憶體大小 | ★★★★★ |
| ★★★★ `balloon` | ★★★★★ **下限** —— 主機吃緊時最少會留給它這麼多 | ★★★★★ |
| ★★★★★ `balloon: 0` | ★★★★★ **關閉 balloon**，固定配置 `memory` 那麼多 | ★★★★★ |

```bash
qm set 101 --memory 8192 --balloon 4096     # 4～8 GB 動態
qm set 102 --memory 16384 --balloon 0       # ★★★★★ 固定 16 GB，不參與回收
```

> [!danger] ★★★★★ 哪些 VM 一定要 `balloon: 0`
> | VM 類型 | 理由 | 重要度 |
> | --- | --- | --- |
> | ★★★★★ **資料庫**（MySQL／PostgreSQL／Oracle） | ★★★★★ **buffer pool 被抽走 → 查詢效能崩潰、可能觸發 guest 內 OOM** | ★★★★★ |
> | ★★★★★ **Java 應用**（設了固定 heap） | JVM 已經把記憶體要走了，氣球一擠就 OOM | ★★★★★ |
> | ★★★★ **Redis／Memcached 等記憶體型服務** | 整個服務就是記憶體 | ★★★★★ |
> | ★★★★ **延遲敏感的即時服務** | 氣球膨脹時會有明顯停頓 | ★★★★ |
> | ★★★★ **Windows Server 有大量分頁的工作負載** | 抖動尤其明顯 | ★★★★ |

> [!warning] ★★★★★ Balloon 抖動（thrashing）長什麼樣
> 主機記憶體在門檻附近震盪時：
> ```
> 主機 79% → 氣球放氣 → guest 拿回記憶體 → 主機 82%
>          → 氣球充氣 → guest 記憶體被抽走 → guest 開始 swap
>          → guest 觸碰更多頁面 → 主機 79% → 放氣 → …
> ```
> ★★★★★ **症狀**：VM 週期性卡頓、guest 內 swap 忽高忽低、
> 主機 CPU 有一部分被 balloon driver 吃掉。
>
> ★★★★★ **解法不是調 balloon 參數，是「不要讓主機記憶體到那個門檻」** ——
> 回頭處理超配。

★★★★ **balloon 需要 guest 端有 driver**：

| Guest | 需要什麼 | 重要度 |
| --- | --- | --- |
| Linux | ★★★★ `virtio_balloon` 模組（現代發行版內建） | ★★★★ |
| ★★★★★ Windows | ★★★★★ **必須裝 VirtIO 驅動 + Balloon Service** | ★★★★★ |

```bash
# 在 Linux guest 裡確認
lsmod | grep balloon
```

```text

```

★★★★★ **沒有 driver 的話，balloon 設定完全無效**（但 PVE 不會報錯）。

### 六、KSM：省記憶體的代價 ★★★★

**KSM（Kernel Same-page Merging）= 主機掃描記憶體頁面，把內容相同的頁合併成一份。**

```
合併前                          合併後
VM1: [ Windows kernel 頁 ]      ┌─► [ Windows kernel 頁 ]（唯一一份）
VM2: [ Windows kernel 頁 ] ─────┤
VM3: [ Windows kernel 頁 ] ─────┘
     3 份 → 1 份，省下 2 份的空間
```

| 項目 | 說明 | 重要度 |
| --- | --- | --- |
| ★★★★ **什麼時候啟動** | `ksmtuned` 在主機記憶體使用率超過門檻時才開始積極掃描 | ★★★★ |
| ★★★★ **省多少** | ★★★★★ **同質環境（一堆相同的 Windows／Ubuntu）省很多；異質環境幾乎沒用** | ★★★★ |
| ★★★★ **代價：CPU** | 掃描與比對要吃 CPU | ★★★★ |
| ★★★★★ **代價：安全** | ★★★★★ **跨 VM 的記憶體去重是已知的側通道攻擊面** | ★★★★★ |
| ★★★ **代價：延遲** | 合併頁被寫入時要 copy-on-write，有微小延遲 | ★★★ |

> 跨 VM 的記憶體去重讓攻擊者可以**用寫入時間的差異推測其他 VM 的記憶體內容**
> （已知的側通道攻擊類別）。

### 七、CPU type：效能與遷移相容性的取捨 ★★★★★

| CPU type | 效能 | 遷移相容性 | 適用 | 重要度 |
| --- | --- | --- | --- | --- |
| ★★★★★ `host` | ★★★★★ **最好**（guest 看到主機全部指令集，AES-NI、AVX 等） | ★★★★★ **最差** —— 只能遷到 CPU 完全相同的節點 | 單節點、或全叢集 CPU 型號完全一致 | ★★★★★ |
| ★★★★★ `x86-64-v2-AES` | ★★★★ 好（含 AES-NI，涵蓋 2010 年後的主流 CPU） | ★★★★★ **好** | ★★★★★ **叢集環境的建議預設** | ★★★★★ |
| ★★★ `x86-64-v3` | 較好（含 AVX2） | 較差（需要較新的 CPU） | 確認全叢集都支援時 | ★★★ |
| ★★★ `kvm64` | ★★★★★ **差** —— ★★★★★ **沒有 AES-NI，加密流量效能很差** | 最好 | 舊環境相容 | ★★★★ |
| ★★★ 具名型號（`Skylake-Server` 等） | 依型號 | 需目標節點支援該型號的所有旗標 | 精確控制 | ★★★ |

> [!danger] ★★★★★ `host` 是「效能最好但會鎖死你」的選項
> 現場最常見的故事：
> ```
> 1. 建叢集時三台都是同型號 CPU，VM 全部設 host，效能很好
> 2. 兩年後加購一台新伺服器，CPU 是新一代
> 3. ★★★★★ 舊 VM 遷不過去 / 遷過去 guest crash
> 4. 要改 CPU type → ★★★★★ 必須把 VM 完全關機再開（重開不算）
> 5. 於是變成一次全機房的停機作業
> ```
> ★★★★★ **叢集環境一開始就用 `x86-64-v2-AES`**，
> 犧牲的效能通常在個位數百分比，換來的是「隨時可以遷移」。

> [!warning] ★★★★★ `kvm64` 沒有 AES-NI
> PVE 舊版的預設是 `kvm64`。如果你的 VM 在跑 HTTPS、VPN、資料庫加密、
> 或磁碟加密，★★★★★ **沒有 AES-NI 會讓加密效能差好幾倍**。
> ★★★★★ **從舊版升上來的 VM，記得檢查並改成 `x86-64-v2-AES`。**

### 八、磁碟快取模式：效能與資料安全 ★★★★★

★★★★★ **這是本篇最容易做錯、後果最嚴重的設定。**

```
        guest 應用程式
             │  write()
             ▼
        guest 檔案系統／page cache
             │  ★ guest 發出 flush（fsync／barrier）
             ▼
        ┌────────────────────────────┐
        │  QEMU 的 cache 設定 ← 你在這裡做選擇
        └────────────────────────────┘
             │
             ▼
        主機 page cache（有些模式會用，有些會繞過）
             │
             ▼
        實體磁碟／RAID 卡快取
```

| `cache=` | 主機 page cache | guest 看到的寫入快取 | 效能 | 資料安全 | 重要度 |
| --- | --- | --- | --- | --- | --- |
| ★★★★★ **`none`（預設，建議）** | ★★★★★ **繞過**（O_DIRECT） | 啟用（guest 的 flush 會被確實下達） | ★★★★ 好 | ★★★★★ **安全** | ★★★★★ |
| ★★★★ `writeback` | ★★★★★ **讀寫都用** | 啟用 | ★★★★★ **最快** | ★★★★ 只要 guest 正確發 flush 就一致；★★★★★ **主機突然斷電時，尚未 flush 的資料會遺失** | ★★★★★ |
| ★★★★ `writethrough` | 讀取用 | ★★★★★ **停用**（每次寫入都同步落地） | ★★ 寫入很慢 | ★★★★★ 安全 | ★★★★ |
| ★★★ `directsync` | ★★★★★ **繞過** | ★★★★★ **停用** | ★ 最慢 | ★★★★★ **最安全** | ★★★ |
| ★★★★★ **`unsafe`** | 讀寫都用 | ★★★★★ **完全忽略 guest 的 flush** | ★★★★★ 極快 | ★★★★★ **極度危險** | ★★★★★ |

> [!danger] ★★★★★ `cache=unsafe` 的真正意義
> 它**不是「快一點但風險略高」**，是
> ★★★★★ **「guest 說『請把這筆資料確實寫入磁碟』時，QEMU 直接回答『好了』但其實沒寫」**。
>
> 後果：★★★★★ **主機一斷電，guest 的檔案系統與資料庫可能直接毀掉**，
> 因為 guest 以為已經落地的東西根本不在磁碟上，日誌重放也救不回來。
>
> ★★★★★ **唯一可接受的用途**：
> - 大量安裝作業系統的當下（裝完立刻改回 `none`）
> - 完全可拋棄的測試 VM
>
> ★★★★★ **正式環境的 VM 上出現 `cache=unsafe`，就是一個必須立即修正的事故等待發生。**

> [!warning] ★★★★ `writeback` 什麼時候可以用
> `writeback` 會用主機的 page cache 做寫入快取，**但仍然尊重 guest 的 flush**。
> 所以它跟 `unsafe` 有本質差別：資料**一致性**是有保障的。
>
> ★★★★ **可以用的情況**：
> - ★★★★★ 主機有 **UPS**，且設定了正常關機
> - 儲存後端本身沒有快取（例如單純的 SATA SSD 直連）
> - 需要吃下大量小寫入的工作負載
>
> ★★★★★ **不該用的情況**：
> - 用 ZFS 或 Ceph（★★★★★ **它們自己有快取層，再疊一層主機 page cache 是浪費且可能有害**）
> - 主機沒有 UPS
> - 記憶體本來就吃緊（page cache 會跟 VM 搶記憶體）

★★★★★ **實務結論**：

```
不知道怎麼選 → ★★★★★ cache=none （PVE 預設，安全且效能夠好）
ZFS / Ceph   → ★★★★★ cache=none （不要疊快取）
需要極致寫入且有 UPS → ★★★★ cache=writeback（要能承擔風險）
資料絕對不能有一絲風險 → ★★★★ cache=directsync（接受它很慢）
★★★★★ 正式環境 → 永遠不要 unsafe
```

```bash

grep -rn "cache=unsafe" /etc/pve/nodes/*/qemu-server/*.conf
```

```

### 九、IO thread 與 SCSI 控制器 ★★★★

| SCSI 控制器 | 說明 | 重要度 |
| --- | --- | --- |
| ★★★★★ **VirtIO SCSI single**（PVE 8 建議） | ★★★★★ **每個磁碟一個控制器**，配合 `iothread=1` 才能真正每碟一條 IO 執行緒 | ★★★★★ |
| ★★★★ **VirtIO SCSI** | 所有磁碟共用一個控制器 | ★★★ |
| ★★★ **VirtIO Block**（`virtio0`） | 較舊的做法，功能較少（不支援某些 SCSI 特性） | ★★★ |
| ★★★ **LSI 53C895A** | ★★★★ **相容性選項** —— 老舊 guest 沒有 VirtIO 驅動時用 | ★★★★ |
| ★★ **VMware PVSCSI** | 從 VMware 遷移過來的暫時相容選項 | ★★ |

★★★★★ **`iothread=1` 的意義**：
把該磁碟的 IO 處理從 QEMU 主執行緒**移到獨立的執行緒**。

```
沒有 iothread：
  QEMU 主執行緒 ──► 處理 vCPU、網路、磁碟 IO ★★★★★ 全部擠在一起
                    磁碟一慢，整台 VM 都卡

有 iothread（+ virtio-scsi-single）：
  QEMU 主執行緒 ──► vCPU、網路
  IO thread 1   ──► scsi0
  IO thread 2   ──► scsi1        ★★★★ 各走各的
```

| 什麼時候一定要開 `iothread=1` | 重要度 |
| --- | --- |
| ★★★★★ **多磁碟的 VM**（尤其資料庫的資料碟與日誌碟分開） | ★★★★★ |
| ★★★★ **高 IOPS 的工作負載** | ★★★★ |
| ★★★★ **NVMe／高速 SSD 後端** | ★★★★ |

```bash
qm set 101 --scsihw virtio-scsi-single
qm set 101 --scsi0 nfs-vmdata:vm-101-disk-0,cache=none,iothread=1,discard=on,ssd=1
```

★★★★ **其他磁碟參數**：

| 參數 | 意義 | 重要度 |
| --- | --- | --- |
| ★★★★ `discard=on` | ★★★★★ **啟用 TRIM／UNMAP** —— thin 儲存要靠它才會回收空間 | ★★★★★ |
| ★★★★ `ssd=1` | 告訴 guest「這是 SSD」，影響 guest 的排程器選擇 | ★★★★ |
| ★★★ `aio=io_uring` / `native` / `threads` | 非同步 IO 後端（PVE 8 預設 `io_uring`） | ★★★ |
| ★★★★ `mbps_rd` / `mbps_wr` / `iops_rd` / `iops_wr` | ★★★★★ **IO 限流** —— 防止單一 VM 拖垮整個節點 | ★★★★★ |

```bash
# ★★★★ 對會亂寫的測試 VM 限流，保護鄰居
qm set 901 --scsi0 local-lvm:vm-901-disk-0,mbps_rd=100,mbps_wr=50,iops_rd=2000,iops_wr=1000
```

> [!danger] ★★★★★ `discard=on` 沒開的話，刪掉的空間永遠不會還回來
> guest 裡刪了 500 GB 檔案，thin pool 的用量**一點都不會下降**。
> ★★★★★ 這是 thin pool 悄悄脹滿的頭號原因。
>
> 需要三件事同時到位：
> 1. ★★★★ VM 磁碟設 `discard=on`
> 2. ★★★★ 控制器是 VirtIO SCSI（`virtio-blk` 對 discard 支援較受限）
> 3. ★★★★★ **guest 裡面要真的發出 TRIM**：
>    `fstrim -av`，或啟用 `fstrim.timer`

## 進階應用

### 一、Prometheus 路線 ★★★★

★★★★★ **PVE 沒有內建 Prometheus exporter**。兩條可行路線：

| 路線 | 做法 | 取捨 | 重要度 |
| --- | --- | --- | --- |
| ★★★★★ **A：InfluxDB（內建）** | PVE → InfluxDB → Grafana | ★★★★★ **不用裝第三方元件，最穩** | ★★★★★ |
| ★★★★ **B：prometheus-pve-exporter（第三方）** | exporter 用 API Token 讀 PVE → Prometheus 抓 exporter | ★★★★ 融入既有 Prometheus 生態；★★★ 多一個要維護的元件 | ★★★★ |
| ★★★ **C：node_exporter** | 只有主機層指標，★★★★★ **看不到 VM 層** | 補充用，不能單獨使用 | ★★★ |

> [!warning] ★★★★ 第三方 exporter 的注意事項
> `prometheus-pve-exporter` 是社群專案，**不是 Proxmox 官方元件**。
> - ★★★★★ **給它的 API Token 一定要是 `PVEAuditor` 唯讀 + `privsep=1`**
>   （見 [[050-01-03-08-guide-PVE-使用者權限與API]]）
> - ★★★★ 部署方式（套件／pip／容器）與設定檔格式請以該專案當前的說明為準
> - ★★★★ 不要把它裝在 PVE 節點的 host 上污染環境，建議跑在獨立的容器或 VM

★★★★ **不論走哪條路線，唯讀 Token 的建法都一樣**：

```bash
pveum user add monitor@pve --comment "監控系統唯讀"
pveum user token add monitor@pve metrics --privsep 1 --comment "metrics 拉取"
pveum acl modify / --users monitor@pve --roles PVEAuditor --propagate 1
pveum acl modify / --tokens 'monitor@pve!metrics' --roles PVEAuditor --propagate 1
pveum user token permissions monitor@pve metrics
```

★★★★★ **監控帳號永遠只給 `PVEAuditor`。**
監控系統被入侵時，攻擊者最多只能「看」，不能動你的 VM。

### 二、該對哪些指標設告警 ★★★★★

| 指標 | 警告門檻 | 嚴重門檻 | 為什麼 | 重要度 |
| --- | --- | --- | --- | --- |

| ★★★★★ **thin pool metadata%** | 75% | 85% | ★★★★★ 常被忽略但一樣致命 | ★★★★★ |
| ★★★★★ **IO delay** | 10%（持續 5 分鐘） | 25% | 儲存瓶頸 | ★★★★★ |

| ★★★★★ **備份任務失敗** | — | ★★★★★ **立即** | 見 [[050-01-03-06-svc-PVE-備份與還原]] | ★★★★★ |
| ★★★★ **VM 非預期停止** | — | 立即 | 可能是 OOM kill | ★★★★★ |

> 漂亮的儀表板不會在半夜叫醒你。
> ★★★★★ **每一個上面標 ★★★★★ 的門檻都必須真的會送出通知**

★★★★★ **至少要把「備份失敗」與「HA fencing」接起來。**

### 三、調校前後怎麼量測 ★★★★★

> [!danger] ★★★★★ 不要「憑感覺」調校
> ★★★★★ **調校的鐵則**：
> 1. **先量測基準**（同樣的負載、同樣的時間長度）
> 2. **一次只改一個參數**
> 3. **再量測，比較**
> 4. **記錄下來**（改了什麼、數字差多少、日期）
>
> 一次改五個參數然後說「有變快」，你不知道是哪一個有用，
> ★★★★★ **出事時也不知道要退哪一個**。

```bash
# 在 guest 內做磁碟基準測試（★★★★ 用同樣的參數跑前後兩次）
apt install -y fio
fio --name=randwrite --ioengine=libaio --direct=1 \
    --rw=randwrite --bs=4k --numjobs=4 --size=1G \
    --runtime=60 --time_based --group_reporting
```

```text
randwrite: (groupid=0, jobs=4): err= 0: pid=1234
  write: IOPS=18.2k, BW=71.1MiB/s (74.6MB/s)(4266MiB/60001msec)
    clat (usec): min=48, max=21044, avg=216.83, stdev=184.21
     lat percentiles (usec):
     |  50.00th=[  204], 95.00th=[  388], 99.00th=[  742], 99.99th=[ 3163]
```

★★★★★ **要看的是 `IOPS`、`BW`，以及 `99.00th` 的延遲百分位** ——
平均值會騙人，**尾端延遲才決定使用者的體感**。

> [!warning] ★★★★★ 不要在正式環境跑 fio
> `fio` 會把儲存打到極限，★★★★★ **同一個儲存上的其他 VM 會嚴重受影響**。
> 測試一律在維護視窗或測試環境做。

### 四、常見情境的調校配方 ★★★★

> [!example] ★★★★★ 資料庫 VM（MySQL／PostgreSQL）
> ```bash
> qm set 102 \
>   --memory 32768 --balloon 0 \
>   --cpu x86-64-v2-AES --cores 8 --sockets 1 --cpuunits 200 \
>   --scsihw virtio-scsi-single \
>   --scsi0 local-lvm:vm-102-disk-0,cache=none,iothread=1,discard=on,ssd=1 \
>   --scsi1 local-lvm:vm-102-disk-1,cache=none,iothread=1,discard=on,ssd=1 \
>   --agent enabled=1
> ```
> | 選擇 | 理由 | 重要度 |
> | --- | --- | --- |
> | ★★★★★ `balloon 0` | **buffer pool 不能被抽走** | ★★★★★ |
> | ★★★★★ `cache=none` | **不要在資料庫底下疊主機快取** | ★★★★★ |
> | ★★★★ `iothread=1` + `virtio-scsi-single` | 資料碟與日誌碟各走各的 IO 執行緒 | ★★★★ |
> | ★★★★ `cpuunits 200` | 節點忙的時候優先給它 CPU | ★★★★ |
> | ★★★★ CPU 不超配 | ★★★★★ **這台的 vCPU 要算進 1:1 的額度** | ★★★★★ |

> [!example] ★★★★ 一般 Web／應用伺服器
> ```bash
> qm set 101 \
>   --memory 8192 --balloon 4096 \
>   --cpu x86-64-v2-AES --cores 4 \
>   --scsihw virtio-scsi-single \
>   --scsi0 nfs-vmdata:vm-101-disk-0,cache=none,iothread=1,discard=on \
>   --agent enabled=1
> ```
> ★★★★ 可以適度用 balloon，CPU 允許 2～3:1 超配。

> [!example] ★★★ 開發測試 VM（要保護鄰居）
> ```bash
> qm set 901 \
>   --memory 4096 --balloon 1024 \
>   --cpu x86-64-v2-AES --cores 2 --cpuunits 50 --cpulimit 2 \
>   --scsi0 local-lvm:vm-901-disk-0,cache=none,discard=on,mbps_wr=50,iops_wr=1000
> ```
> ★★★★★ **`cpuunits 50` + `cpulimit` + IO 限流** ——
> 讓它「跑得動但吵不到別人」。

### 步驟 5：找出是哪台 VM ★★★★★

  |> range(start: 2026-09-02T06:00:00Z, stop: 2026-09-02T06:40:00Z)
  |> filter(fn: (r) => r._measurement == "qemu" and r._field == "diskwrite")
  |> aggregateWindow(every: 10m, fn: mean)

## 常見錯誤與排錯

| # | 現象 | 原因 | 解法 | 重要度 |
| --- | --- | --- | --- | --- |
| 1 | ★★★★★ **VM 半夜無故消失／被關掉** | ★★★★★ **記憶體超配 → OOM killer 殺掉 QEMU** | ★★★★★ `dmesg -T \| grep -i "out of memory"`；減少超配、限制 ZFS ARC | ★★★★★ |
| 2 | ★★★★★ **IO delay 持續 > 20%** | 儲存到極限、或某台 VM 亂寫 | ★★★★★ `iotop -boan` 找來源；檢查該 VM 的 cache／iothread 設定 | ★★★★★ |
| 3 | ★★★★★ **thin pool 滿，VM 檔案系統變唯讀** | 薄配置超配沒監控 | ★★★★★ 緊急：刪快照／搬 VM／擴 pool；事後：設 75%/85% 告警 | ★★★★★ |
| 4 | thin pool 用量只增不減 | ★★★★★ **VM 磁碟沒開 `discard=on`，或 guest 沒跑 TRIM** | ★★★★★ `qm set <id> --scsiN ...,discard=on`；guest 內 `fstrim -av` 或啟用 `fstrim.timer` | ★★★★★ |
| 5 | ★★★★★ **VM 記憶體圖表永遠 100%** | 沒裝 QEMU Guest Agent，PVE 讀不到 guest 真實用量 | ★★★★★ 裝 guest agent 並 `qm set <id> --agent enabled=1` | ★★★★★ |
| 6 | ★★★★★ **資料庫 VM 突然變超慢、guest 內狂 swap** | ★★★★★ **balloon 把記憶體抽走了** | ★★★★★ `qm set <id> --balloon 0` | ★★★★★ |
| 7 | VM 週期性卡頓，主機記憶體在 80% 附近震盪 | ★★★★★ **balloon 抖動** | ★★★★★ 解決超配（減 VM／加記憶體），不是調 balloon 參數 | ★★★★★ |
| 8 | ★★★★★ **主機開始用 swap** | 記憶體超配 | ★★★★★ 減載；`vm.swappiness=10` 只是緩解 | ★★★★★ |
| 9 | 用 ZFS 的節點記憶體莫名被吃光 | ★★★★★ **ZFS ARC 預設可用一半實體記憶體** | ★★★★★ 設 `zfs_arc_max`，`update-initramfs -u` 後重開 | ★★★★★ |

| 11 | ★★★★★ **改了 CPU type 卻沒生效** | ★★★★★ **只做了 reboot，沒有完全關機** | ★★★★★ `qm shutdown` 再 `qm start`（或 `qm stop` 再 start） | ★★★★★ |

| 14 | ★★★★★ **主機斷電後 VM 檔案系統毀損** | ★★★★★ **`cache=unsafe`** | ★★★★★ 全叢集 `grep -rn "cache=unsafe"` 清查並改 `none` | ★★★★★ |

## 安全性注意事項

> [!danger] ★★★★★ 這幾件事會直接造成資料損毀或服務中斷
> | 做法 | 後果 | 重要度 |
> | --- | --- | --- |
> | ★★★★★ 正式 VM 用 `cache=unsafe` | **主機斷電 = 檔案系統／資料庫毀損** | ★★★★★ |
> | ★★★★★ 記憶體超配 | **OOM killer 隨機殺掉 VM** | ★★★★★ |
> | ★★★★★ thin pool 沒監控 | **寫入失敗、檔案系統唯讀** | ★★★★★ |
> | ★★★★★ 資料庫 VM 開 balloon | **buffer pool 被抽走、guest 內 OOM** | ★★★★★ |
> | ★★★★ ZFS ARC 沒設上限 | 主機記憶體被吃光 | ★★★★★ |
> | ★★★★ 監控帳號給了寫入權限 | 監控系統被入侵 = PVE 被入侵 | ★★★★ |

### 一、KSM 的側通道風險 ★★★★★

- ★★★★★ **跨 VM 的記憶體去重讓攻擊者能透過寫入時間差推測其他 VM 的記憶體內容**
- ★★★★★ **多租戶、涉密環境、跨安全等級混用的節點應該關閉 KSM**
- ★★★★ 關閉前先確認記憶體有餘裕（解除合併會瞬間需要更多記憶體）

### 二、監控系統的權限 ★★★★★

- ★★★★★ **監控用的 API Token 只給 `PVEAuditor`，且 `privsep=1`**
- ★★★★★ **InfluxDB 的 token 用「只能寫入」的那種** —— PVE 被入侵時攻擊者刪不掉歷史
- ★★★★ 監控主機本身要納入資安管理（它握有整個機房的運作細節）
- ★★★★ 見 [[050-01-03-08-guide-PVE-使用者權限與API]]

### 三、指標資料本身也是敏感資訊 ★★★★

- ★★★★ VM 名稱、數量、資源配置洩漏出去，等於把機房架構圖給別人
- ★★★★ Grafana 儀表板不要對外公開，至少要有登入
- ★★★ 對外的 metric 傳輸盡量走內部網段或加密

### 四、調校變更要有紀錄 ★★★★★

★★★★★ **每一次調校都要記錄**：

| 欄位 | 範例 |
| --- | --- |
| 日期 | 2026-09-02 |
| 對象 | VM 205 |
| 改了什麼 | `cache=unsafe → none`、`scsihw lsi → virtio-scsi-single`、`balloon 512 → 0` |
| 前後數字 | 4,120 → 17,840 IOPS；p99 8,160 → 764 µs |
| ★★★★★ 風險與退回方式 | 已做快照 `pre-tune-20260902`；退回：`qm rollback 205 pre-tune-20260902` |

★★★★★ **沒有退回方式的變更不要做。**
見 [[100-02-08-guide-維運-變更管理流程]]。

### 五、量測本身會影響服務 ★★★★

- ★★★★★ **不要在正式環境跑 `fio`** —— 它會把儲存打到極限，拖垮同一儲存上的所有 VM
- ★★★★ `iotop`／`iostat` 這類觀察工具影響很小，可以在正式環境用
- ★★★★ 大範圍的 RRD／API 查詢頻率不要太高，避免給 `pvedaemon` 增加負擔

| ★★★★★ `cache=unsafe` | ★★★★★ **永遠不要用在正式環境** | flush 被忽略 | ★★★★★ |
| ★★★★ `iothread=1` | 多磁碟／高 IOPS | 獨立 IO 執行緒 | ★★★★★ |
| ★★★★ `discard=on` | ★★★★★ **thin 儲存必開** | 空間才會回收 | ★★★★★ |
| ★★★★ `ssd=1` | 後端是 SSD 時 | 影響 guest 排程器 | ★★★★ |
| ★★★★ `--cpuunits` | 正式 200／測試 50 | 相對權重 | ★★★★ |
| ★★★★ `--cpulimit` | 測試 VM | 硬上限 | ★★★★ |
| ★★★★ `mbps_wr` / `iops_wr` | 吵鄰居的 VM | IO 限流 | ★★★★ |
| ★★★★ `--agent enabled=1` | ★★★★★ **所有 VM 都該開** | 才讀得到真實記憶體用量 | ★★★★★ |

### 快取模式決策

| 情境 | 選這個 |
| --- | --- |
| ★★★★★ 不知道怎麼選 | `cache=none` |
| ★★★★★ ZFS / Ceph 後端 | `cache=none`（不要疊快取） |
| ★★★★ 需要極致寫入且有 UPS | `cache=writeback` |
| ★★★★ 資料絕不能有風險 | `cache=directsync` |
| ★★★★★ 正式環境 | ★★★★★ **永遠不要 `unsafe`** |

### 超配準則

| 資源 | 可否超配 | 準則 | 超配過頭的後果 |
| --- | --- | --- | --- |
| ★★★★ CPU | 可以 | 延遲敏感 1:1／一般 2～3:1／測試 4～8:1 | 變慢（可回復） |
| ★★★★★ 記憶體 | ★★★★★ **正式環境不要** | 總和 + 主機保留 + ARC ≤ 實體 × 0.8 | ★★★★★ **OOM 殺 VM** |
| ★★★★ 儲存 | 可以但要監控 | 75% 告警、85% 立即處理 | ★★★★★ **寫入失敗、資料損毀** |

## 練習題

> [!question]- 練習 1：判讀一組指標
> 某節點：CPU usage 15%、Load average 24（16 核）、IO delay 28%、記憶體 62%。
> 請判斷瓶頸在哪，並寫出你接下來會下的三個指令。
>
> ---
> **參考答案**
> ★★★★★ **瓶頸在儲存，不是 CPU。**
> 判斷依據：★★★★★ **CPU usage 低（15%）+ Load 高（24/16 = 1.5）+ IO delay 高（28%）**
> —— 這個組合代表大量行程卡在不可中斷的 IO 等待（D state），
> load 被撐高但 CPU 其實閒著。
>
> 接下來三個指令：
> ```bash
> vmstat 2 5              # 確認 wa 高、b 欄有排隊
> iostat -xz 2 3          # 哪個裝置 %util 接近 100
> iotop -boan -d 5 -n 2   # 哪個 kvm 行程在寫
> ```
> 找到 VM 之後檢查它的 `cache`／`iothread`／`scsihw`／`balloon`。

> [!question]- 練習 2：算出一台節點能放多少 VM
> 節點有 128 GB 實體記憶體，用 ZFS（ARC 上限設 16 GB），
> PVE 本身保留 4 GB。你要放的 VM 每台 8 GB、不開 balloon。
> 請算出安全的 VM 數量上限，並寫出你會設哪些告警。
>
> ---
> **參考答案**
> ```
> 可用給 VM = 128 × 0.8 - 16（ARC）- 4（PVE） = 102.4 - 20 = 82.4 GB
> 82.4 ÷ 8 = 10.3  →  ★★★★★ 安全上限約 10 台
> ```
> ★★★★★ **注意 `× 0.8` 的餘裕不能省** —— 它涵蓋了 QEMU 本身的額外開銷、
> 主機的 page cache、以及突發狀況。
>
> 告警：
> - ★★★★★ 節點記憶體 > 80%（警告）／> 90%（嚴重）
> - ★★★★★ swap 使用 > 0
> - ★★★★★ 出現 OOM 事件（`dmesg` 掃描）
> - ★★★★ ZFS CAP > 75%

> [!question]- 練習 3：清查危險設定
> 寫出三個一行指令，分別清查全叢集有沒有
> (a) `cache=unsafe`、(b) `cpu: kvm64`、(c) 沒開 `discard` 的 scsi 磁碟。
>
> ---
> **參考答案**
> ```bash
> # (a) ★★★★★ 最危險的那個
> grep -rn "cache=unsafe" /etc/pve/nodes/*/qemu-server/*.conf
>
> # (b) 沒有 AES-NI 的舊 CPU type
> grep -rn "^cpu: kvm64" /etc/pve/nodes/*/qemu-server/*.conf
>
> # (c) scsi 磁碟沒有 discard（thin 儲存上會脹爆）
> grep -rn "^scsi[0-9]:" /etc/pve/nodes/*/qemu-server/*.conf | grep -v "discard=on"
> ```
> ★★★★ 建議把這三行排進每月巡檢。

> [!question]- 練習 4：接一次外部監控
> 依「完整實戰範例」步驟 1～4，把一個節點接上 InfluxDB，
> 並實際查出 **IO delay 在過去 24 小時的最高值與發生時間**。
>
> ---
> **參考答案**
> 關鍵三步：
> 1. Web UI `Datacenter → Metric Server → Add → InfluxDB`
> 2. `journalctl -u pvestatd` 確認沒有連線錯誤
> 3. Flux 查詢：
>    ```
>    from(bucket: "pve") |> range(start: -24h)
>      |> filter(fn: (r) => r._measurement == "nodes" and r._field == "iowait")
>      |> aggregateWindow(every: 10m, fn: max)
>      |> sort(columns: ["_value"], desc: true) |> limit(n: 5)
>    ```
> ★★★★★ **把時間點對照 `/etc/pve/jobs.cfg` 的備份排程**，
> 十之八九尖峰就在備份時段。

> [!question]- 練習 5：調校一台 VM 並量測
> 找一台測試 VM，先用 `fio` 量基準，
> 然後**只改一個參數**（例如把 `scsihw` 從 `lsi` 改成 `virtio-scsi-single` 並加 `iothread=1`），
> 再量一次，記錄前後的 IOPS 與 p99 延遲。
>
> ---
> **參考答案**
> ```bash
> # 量基準
> fio --name=base --ioengine=libaio --direct=1 --rw=randwrite \
>     --bs=4k --numjobs=4 --size=1G --runtime=60 --time_based --group_reporting
>
> # ★★★★★ 先做快照再改
> qm snapshot 901 pre-tune
> qm shutdown 901
> qm set 901 --scsihw virtio-scsi-single
> qm set 901 --scsi0 local-lvm:vm-901-disk-0,cache=none,iothread=1,discard=on,size=32G
> qm start 901
>
> # 同樣參數再量一次
> ```
> ★★★★★ **記錄格式**：日期／對象／改了什麼／前後數字／退回方式。
> ★★★★★ **要看 p99（99.00th）而不是平均值** —— 使用者體感取決於尾端延遲。

> [!question]- 練習 6：balloon 的實際觀察
> 拿一台測試 VM 設 `--memory 8192 --balloon 1024`，
> 在 guest 內用 `free -h` 觀察，然後在主機上製造記憶體壓力，
> 再回 guest 看記憶體變化。說明你觀察到什麼、以及為什麼資料庫不能這樣設。
>
> ---
> **參考答案**
> 觀察到的現象：
> - 主機記憶體充裕時，guest `free -h` 顯示接近 8 GB
> - ★★★★★ 主機記憶體吃緊後，guest 的 `total` 會**逐步下降**趨近 1 GB
> - guest 內 `available` 變少 → 開始使用 swap → ★★★★ 應用程式變慢
>
> 資料庫不能這樣設的理由：
> ★★★★★ **InnoDB buffer pool / PostgreSQL shared_buffers 在啟動時就規劃好了**，
> 氣球把記憶體抽走時，資料庫不會自己縮小 buffer，
> 結果是 ★★★★★ **guest 內部大量 swap，甚至觸發 guest 自己的 OOM killer 殺掉資料庫行程**。
> 正解是 `--balloon 0`。

## 小測驗

Q1. 節點顯示：CPU usage 12%、Load average 30（16 核）、IO delay 26%。
瓶頸在哪？你的判斷依據是什麼？

Q2.（是非）記憶體超配跟 CPU 超配一樣，最壞情況只是變慢。

Q3.（選擇）下列哪個 `cache` 設定會讓 QEMU **忽略 guest 的 flush 請求**？
(A) `none` (B) `writeback` (C) `writethrough` (D) `unsafe`

Q4. 為什麼叢集環境建議把 CPU type 設成 `x86-64-v2-AES` 而不是 `host`？
改了之後要做什麼才會生效？

Q5.（簡答）一台資料庫 VM 設了 `--memory 16384 --balloon 2048`，
DBA 抱怨「半夜查詢突然變超慢」。最可能的原因是什麼？怎麼修？

Q6. LVM-thin pool 的 `Data%` 是 60%，`Meta%` 是 92%。
這樣安全嗎？為什麼？

Q7. 這行指令的三個參數各解決什麼問題？
`qm set 101 --scsi0 local-lvm:vm-101-disk-0,cache=none,iothread=1,discard=on`

Q8.（簡答）為什麼 PVE 內建的 RRD 圖表不適合做事後鑑識？該怎麼補足？

Q9. 什麼情況下應該關閉 KSM？關閉時要注意什麼？

Q10.（情境）你把一台 VM 的 `cache` 從 `unsafe` 改成 `none`、
`scsihw` 從 `lsi` 改成 `virtio-scsi-single`、`balloon` 從 512 改成 0，
三個一起改，結果 IOPS 提升四倍。
主管問「是哪一個改善最多？」你要怎麼回答？這個做法有什麼問題？

> [!question]- 測驗答案
> **A1.** ★★★★★ **瓶頸在儲存。**
> 判斷依據是這個組合：★★★★★ **CPU usage 低 + Load 高（30/16 ≈ 1.9）+ IO delay 高（26%）**。
> Linux 的 load 包含「不可中斷睡眠（D state）」的行程，
> 大量行程卡在等磁碟時 load 會飆高，但 CPU 其實閒著。
> ★★★★★ **load 高 + CPU 低 + IO delay 高 = 儲存問題**，這是最快的判斷法。
> 見「內建圖表怎麼看：節點層」。
>
> **A2.** ★★★★★ **否。**
> - CPU 超配過頭 → 變慢（★★★★ **可回復**）
> - ★★★★★ **記憶體超配過頭 → Linux OOM killer 直接殺掉 QEMU 行程**，
>   對使用者來說就是「一台 VM 無預警斷電」，而且被殺的不一定是佔最多的那台。
>
> 儲存超配過頭更糟：★★★★★ **寫入失敗、guest 檔案系統唯讀甚至損毀，且不可逆**。
> 見「超配：三種資源、三種準則」。
>
> **A3. (D) `unsafe`**。
> ★★★★★ 它的意思是「guest 說『請確實寫入磁碟』時，QEMU 回答『好了』但其實沒寫」。
> ★★★★★ **主機一斷電，guest 的檔案系統與資料庫可能直接毀掉**，日誌重放也救不回來。
> 注意 (B) `writeback` **會**尊重 guest 的 flush，所以跟 `unsafe` 有本質差別。
> 見「磁碟快取模式」。
>
> **A4.** ★★★★★ **`host` 讓 guest 看到主機的全部 CPU 指令集，
> 因此只能遷移到 CPU 完全相同的節點** ——
> 兩年後加購新一代 CPU 的伺服器時，舊 VM 會遷不過去或 guest crash。
> `x86-64-v2-AES` 犧牲個位數百分比的效能，換來「隨時可以遷移」。
>
> ★★★★★ **改了之後必須「完全關機再開機」（`qm shutdown` + `qm start`），
> guest 內 reboot 不算** —— 因為 CPU 型號是在 QEMU 行程啟動時決定的。
> 見「CPU type」與排錯表第 11、12 列。
>
> **A5.** ★★★★★ **balloon 把記憶體抽走了。**
> 半夜備份或其他 VM 的負載讓主機記憶體吃緊 → 氣球膨脹 →
> 這台 VM 的可用記憶體被壓到接近 2 GB →
> ★★★★★ **InnoDB buffer pool 不會自己縮小，guest 內開始狂 swap**，查詢因此暴慢。
>
> 修法：`qm set <id> --balloon 0`（固定 16 GB，不參與回收）。
> ★★★★★ **並回頭處理節點的記憶體超配** —— 否則問題只是轉移到別台 VM。
> 見「Balloon」與排錯表第 6 列。
>
> **A6.** ★★★★★ **非常不安全。**
> thin pool 有**兩個**會滿的東西：資料空間（`Data%`）與
> ★★★★★ **中繼資料空間（`Meta%`）**。
> `Meta%` 92% 已經進入危險區 —— ★★★★★ **中繼資料滿掉比資料滿掉更難救**，
> 而且一樣會造成寫入失敗與 guest 檔案系統損毀。
> ★★★★★ **兩個百分比都要監控、都要在 75%／85% 設告警。**
> 見「儲存超配」與排錯表第 3 列。
>
> **A7.**
> - ★★★★★ `cache=none` → **資料安全**（繞過主機 page cache，guest 的 flush 會確實下達）
> - ★★★★ `iothread=1` → **效能**（IO 從 QEMU 主執行緒移到獨立執行緒，
>   ★★★★★ 需搭配 `scsihw virtio-scsi-single` 才能每碟一條）
> - ★★★★ `discard=on` → ★★★★★ **空間回收**（guest 刪檔後 TRIM 才會傳到 thin 儲存，
>   否則 pool 用量只增不減）
>
> 見「IO thread 與 SCSI 控制器」。
>
> **A8.** ★★★★★ **RRD 是固定大小的輪替式資料庫，越舊的資料被壓縮成越粗的平均值** ——
> 「上週三下午三點十七分那一分鐘」的尖峰已經被平均掉，看不到了。
>
> 補足方式：★★★★★ **外接時序資料庫**（InfluxDB／Prometheus），
> 用原始解析度保留較長時間。
> ★★★★★ 這正是「為什麼要外接監控」最實際的理由。
> 見「監控在 PVE 裡是怎麼運作的」與排錯表第 19 列。
>
> **A9.** ★★★★★ **多租戶、涉密環境、跨安全等級混用的節點應該關閉** ——
> 跨 VM 的記憶體去重是已知的側通道攻擊面，
> 攻擊者可用寫入時間差推測其他 VM 的記憶體內容。
>
> ★★★★★ **關閉時要注意**：`echo 2 > /sys/kernel/mm/ksm/run`
> 會**立刻把已合併的頁還原**，如果你原本靠 KSM 才塞得下這些 VM，
> ★★★★★ **主機會瞬間記憶體不足**。先確認有餘裕再做。
> 見「KSM：省記憶體的代價」。
>
> **A10.** ★★★★★ **誠實的答案是「無法歸因」** ——
> 三個參數一起改，就沒辦法知道哪一個貢獻多少。
>
> 這個做法的問題：
> 1. ★★★★★ **無法歸因** —— 下次遇到類似情況不知道該先改哪個
> 2. ★★★★★ **出事時不知道要退哪一個** —— 只能整批退回
> 3. ★★★★ 可能其中一項其實是負面影響，被另外兩項的改善蓋過去了
>
> ★★★★★ **正確做法是「一次只改一個參數，改一次量一次」。**
> 實務上「先止血」而一起改是可以接受的，
> ★★★★★ **但必須在變更紀錄裡註明「未單獨歸因」**，不要假裝知道答案。
>
> ★★★★★ 另外要強調：本例最大的收穫不是 IOPS 提升四倍，
> 而是 ★★★★★ **把 `cache=unsafe` 這顆定時炸彈拆掉了** ——
> 那是「主機一斷電就資料損毀」等級的風險。
> 見「調校前後怎麼量測」與「完整實戰範例」步驟 9。
