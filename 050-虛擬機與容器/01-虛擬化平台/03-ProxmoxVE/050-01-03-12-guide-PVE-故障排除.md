# PVE 故障排除

> [!abstract] 這篇你會學到
> - ★★★★★ **PVE 的分層排查法**：硬體 → 作業系統 → PVE 服務 → 叢集 → 儲存 → 來賓，
>   每一層有明確的判定指令與**往下走還是停在這裡**的分支
> - PVE 有哪些**核心服務**、誰壞了會造成什麼症狀
> - ★★★★★ **`/etc/pve` 是怎麼回事** —— 它不是普通目錄，而 Quorum 掉了它就變唯讀
> - 依症狀查：**開不了機、Web 後台連不上、儲存滿了、叢集失聯、遷移失敗、
>   VM 開不起來、LXC 起不來、備份失敗、憑證過期**

> - ★★★★★ 哪些「網路上教你打的指令」其實會讓事情更糟

## 觀念說明

### ★★★★★ PVE 的分層模型：排查一律由下往上

```
┌─────────────────────────────────────────────┐
│ ⑥ 來賓層     VM (QEMU) / CT (LXC)             │  qm / pct
├─────────────────────────────────────────────┤
│ ⑤ 儲存層     local / local-lvm / NFS / Ceph   │  pvesm / lvs / zpool
├─────────────────────────────────────────────┤
│ ④ 叢集層     corosync / pmxcfs / HA           │  pvecm / ha-manager
├─────────────────────────────────────────────┤
│ ③ PVE 服務層 pveproxy / pvedaemon / pvestatd  │  systemctl
├─────────────────────────────────────────────┤
│ ② 作業系統層 Debian / 核心 / 網路 / 檔案系統    │  journalctl / ip / df
├─────────────────────────────────────────────┤
│ ① 硬體層     電源 / 硬碟 / 記憶體 / 網卡        │  IPMI / smartctl / dmesg
└─────────────────────────────────────────────┘

★★★★★ 鐵律：下層壞了，上層一定會出怪症狀。
       所以永遠**從下往上排除**，不要一看到 VM 起不來就去改 VM 設定。
```

**一個典型的誤判例子：**

```
  症狀：VM 開不起來，報「無法寫入設定檔」
    ↓
  ✗ 錯誤路徑：懷疑 VM 設定壞了 → 重建 VM → 還是不行 → 越弄越亂
    ↓
  ✓ 正確路徑：往下查
       ⑤ 儲存 OK
       ④ 叢集 → ★★★★★ pvecm status 顯示 Quorate: No
                 → /etc/pve 唯讀 → 當然寫不進去
       ↓
       真正的問題在**叢集層**，不在 VM
```

### PVE 的核心服務 ★★★★★

| 服務 | 做什麼 | 壞掉的症狀 |
| --- | --- | --- |
| ★★★★★ **`pve-cluster`**（pmxcfs） | 提供 `/etc/pve` 這個叢集檔案系統 | ★★★★★ **`/etc/pve` 空掉或消失**，幾乎所有功能都掛 |
| ★★★★★ **`corosync`** | 叢集節點之間的通訊與投票 | 節點顯示紅色、Quorum 掉、`/etc/pve` 唯讀 |
| ★★★★★ **`pveproxy`** | ★★★★★ **Web 介面與 API 的前端**（8006 埠） | ★★★★★ **後台連不上**，但 VM 仍在跑 |
| ★★★★ **`pvedaemon`** | 後端 API 工作程序（本機執行實際動作） | 後台打得開但操作都失敗 |
| ★★★★ **`pvestatd`** | 收集節點、VM、儲存的狀態數據 | ★★★★ **後台的圖表與狀態變成灰色／問號** |
| ★★★★ **`pvescheduler`** | 執行備份與複寫排程 | 備份／複寫排程不跑 |
| ★★★★ **`pve-ha-lrm` / `pve-ha-crm`** | HA 的本地與叢集資源管理 | HA 不切換、節點被 fence |
| ★★★ **`pve-firewall`** | 防火牆規則套用 | 規則沒生效或全擋 |
| ★★★ **`spiceproxy`** | SPICE 主控台代理（3128 埠） | SPICE 主控台開不起來 |
| ★★★ **`qmeventd`** | 監聽 QEMU 事件（例如 VM 關機後清理） | VM 停止後資源沒釋放 |

### ★★★★★ `/etc/pve` 不是普通目錄

這是 PVE 最容易誤解、也最常導致誤操作的地方。

```
  /etc/pve  ←── ★★★★★ 這是一個 FUSE 掛載點，由 pve-cluster (pmxcfs) 提供

                 實際資料存在：
                 /var/lib/pve-cluster/config.db   （SQLite 資料庫）

  ┌────────────────────────────────────────────────┐
  │ 特性                                            │
  ├────────────────────────────────────────────────┤
  │ ★★★★★ 內容會自動同步到叢集所有節點                 │
  │ ★★★★★ Quorum 掉了 → 立刻變成**唯讀**              │
  │ ★★★★  pve-cluster 沒起來 → /etc/pve 是空的        │
  │ ★★★★★ 有大小限制，不要往裡面丟大檔案               │
  │ ★★★★  直接改 config.db 會毀掉整個叢集設定           │
  └────────────────────────────────────────────────┘
```

```bash
mount | grep /etc/pve
```

```text
/dev/fuse on /etc/pve type fuse (rw,nosuid,nodev,relatime,user_id=0,group_id=0,default_permissions,allow_other)
```

★★★★ 這行看不到，就代表 **pmxcfs 沒有掛起來** —— 這是很多怪症狀的根源。

裡面有什麼：

```bash
ls /etc/pve/
```

```text
authkey.pub          firewall             lxc                  qemu-server
authkey.pub.old      ha                   nodes                sdn
ceph.conf            local                openvz               storage.cfg
corosync.conf        datacenter.cfg       priv                 user.cfg
```

| 路徑 | 內容 |
| --- | --- |
| ★★★★★ `/etc/pve/qemu-server/<vmid>.conf` | VM 設定 |
| ★★★★★ `/etc/pve/lxc/<ctid>.conf` | 容器設定 |
| ★★★★★ `/etc/pve/storage.cfg` | 儲存定義 |
| ★★★★★ `/etc/pve/corosync.conf` | ★★★★★ 叢集設定（**改這個要極度小心**） |
| ★★★★ `/etc/pve/user.cfg` | 使用者與權限 |
| ★★★★ `/etc/pve/local` | 指向 `/etc/pve/nodes/<本節點>` 的符號連結 |
| ★★★★★ `/etc/pve/priv/` | ★★★★★ 私鑰、叢集 CA（**只有 root 讀得到**） |
| ★★★ `/etc/pve/jobs.cfg` | 備份排程 |
| ★★★ `/etc/pve/ha/` | HA 資源與群組 |

### Quorum：叢集能不能寫設定的開關 ★★★★★

```
   總票數 = 節點數（+ QDevice 的票）
   Quorum 門檻 = floor(總票數 / 2) + 1

   3 節點：門檻 2  → 可以掛 1 台
   4 節點：門檻 3  → 可以掛 1 台（★★★ 偶數節點沒有比較好）
   5 節點：門檻 3  → 可以掛 2 台
   ★★★★★ 2 節點：門檻 2 → 掛 1 台就沒了！必須加 QDevice
```

```
   有 Quorum                       沒有 Quorum
   ─────────                       ───────────
   /etc/pve 可讀可寫                ★★★★★ /etc/pve 唯讀
   可以建立/修改/啟動 VM            ★★★★ 已在跑的 VM 繼續跑
   HA 正常運作                      ★★★★★ 不能啟動新的 VM
   可以遷移                         ★★★★★ 不能改任何設定
                                   ★★★★★ HA 可能觸發 fence（自我重開機）
```

★★★★★ **「VM 還在跑但什麼都不能改」的症狀，九成是 Quorum 掉了。**

### 日誌在哪裡 ★★★★★

| 目的 | 指令／路徑 |
| --- | --- |
| ★★★★★ 本次開機的錯誤 | `journalctl -b -p err` |
| ★★★★★ 某個服務 | `journalctl -u pveproxy -n 100 --no-pager` |
| ★★★★★ 即時追蹤 | `journalctl -f -u pvedaemon` |
| ★★★★ 上一次開機（查當機原因） | `journalctl -b -1 -p err` |
| ★★★★★ **PVE 工作日誌** | `/var/log/pve/tasks/`（★★★★ 後台每個任務都在這） |
| ★★★★ 備份日誌 | `/var/log/vzdump/` |
| ★★★★ Web 存取記錄 | `/var/log/pveproxy/access.log` |
| ★★★★ 防火牆 | `/var/log/pve-firewall.log` |
| ★★★★ 核心與硬體 | `dmesg -T`、`journalctl -k` |
| ★★★ 套件變更歷程 | `/var/log/apt/history.log` |

★★★★ **後台任務失敗時，錯誤訊息的完整版在 `/var/log/pve/tasks/`：**

```bash
ls -lt /var/log/pve/tasks/*/ 2>/dev/null | head -5
```

```text

```

```bash
# 直接看最新的失敗任務
tail -30 "$(ls -t /var/log/pve/tasks/*/* 2>/dev/null | head -1)"
```

## 安裝或基礎操作

### ★★★★★ 通用第一輪檢查（不管什麼症狀都先跑）

把這段存成 `/usr/local/bin/pve-triage.sh`，出事第一件事就跑它：

```bash
cat > /usr/local/bin/pve-triage.sh <<'EOF'
#!/usr/bin/env bash
# PVE 第一輪快速檢傷 —— 出事先跑這個，把輸出貼進工單
line() { printf '\n===== %s =====\n' "$1"; }

line "主機與版本"
hostname; uptime; pveversion 2>/dev/null

line "PVE 服務"
systemctl is-active pve-cluster corosync pveproxy pvedaemon pvestatd pvescheduler 2>&1 | paste -sd' '
systemctl list-units --state=failed --no-legend --no-pager

line "/etc/pve 掛載"
mount | grep -c '/etc/pve' | sed 's/^/fuse mounts: /'
touch /etc/pve/.rwtest 2>/dev/null && { echo "writable: YES"; rm -f /etc/pve/.rwtest; } \
                                   || echo "writable: NO  <<< 檢查 Quorum"

line "叢集"
pvecm status 2>&1 | grep -E 'Quorate|Total votes|Expected|Nodes' || echo "（單機，無叢集）"

line "儲存"
pvesm status 2>&1
df -h / /var/lib/vz /boot 2>/dev/null

line "來賓"
qm list 2>/dev/null | head -20
pct list 2>/dev/null | head -20

line "近期錯誤"
journalctl -b -p err --no-pager -n 25
EOF
chmod +x /usr/local/bin/pve-triage.sh
/usr/local/bin/pve-triage.sh
```

## 進階應用

以下每個症狀都給 **編號排查步驟**，照順序做，每一步都有判定分支。

---

### 症狀 A：主機開不了機 ★★★★★

> **前提**：你要有 **IPMI／iDRAC／iLO 或實體螢幕**。純 SSH 救不了開不了機。

#### A-1　先確定「開不了機」是哪一種

```
  ┌ 完全沒電、沒風扇 ──────────► 硬體／電力問題（見 040-02 機房章）
  │
  ├ 有畫面但停在 BIOS/POST ─────► 硬體自檢失敗，看 IPMI 的 SEL 事件記錄
  │
  ├ 到 GRUB 選單就停 ───────────► A-2
  │
  ├ 選了核心後 kernel panic ────► A-3
  │
  ├ 停在 emergency mode / 要求 root 密碼 ► A-4
  │
  └ 開起來了但沒有網路 ──────────► A-5
```

#### A-2　GRUB 進不去或找不到開機項目

```bash
# ★★★★ 在 GRUB 命令列（按 c）先看看
grub> ls
```

```text
(hd0) (hd0,gpt1) (hd0,gpt2) (hd0,gpt3) (hd1) ...
```

★★★★ 看不到磁碟 → 硬體層問題（RAID 卡、線材、磁碟死了）。
看得到 → 用 live media 開機，掛載後 `proxmox-boot-tool refresh` 重建開機項目。
詳細救援流程見 [[020-01-25-guide-Linux-開機流程與GRUB救援]]。

#### A-3　選了新核心就 panic ★★★★★

```
  在 GRUB 選 "Advanced options" → 選**舊核心**開機
              │
        ┌─────┴─────┐
      進得去        還是 panic
        │             │
        ▼             ▼
  ★★★★★ 立刻     可能是硬體（記憶體、
  proxmox-boot-tool  RAID 卡韌體）或
  kernel pin <舊版>  檔案系統損壞
```

```bash
# 進系統後第一件事
proxmox-boot-tool kernel list
proxmox-boot-tool kernel pin 6.8.x-x-pve
```

```text
Setting '6.8.x-x-pve' as grub default entry and running update-grub.
```

★★★★★ **不釘選的話，下次任何原因重開機又會選到壞核心**，
而那時你可能不在現場。詳見 [[050-01-03-11-svc-PVE-升級與維護]]。

#### A-4　停在 emergency mode ★★★★

多半是 `/etc/fstab` 裡有掛不起來的項目（NFS 掛了、磁碟 UUID 變了）。

```bash
journalctl -xb | grep -i -E 'failed|dependency' | head -20
```

```text
[FAILED] Failed to mount /mnt/pve/backup-nfs.
See 'systemctl status mnt-pve-backup\x2dnfs.mount' for details.
[DEPEND] Dependency failed for Local File Systems.
```

★★★★ 修法：暫時把那一行 `/etc/fstab` 註解掉，開機後再處理。

> [!warning] ★★★★★ NFS 儲存不要寫進 `/etc/fstab`
> PVE 的 NFS 儲存應該在 `/etc/pve/storage.cfg` 定義，由 PVE 自己掛載。
> 寫進 `/etc/fstab` 會讓 **NFS 伺服器掛掉時整台 PVE 開不了機**。
> 見 [[050-01-03-02-guide-PVE-儲存設定]]。

#### A-5　開起來了但沒網路 ★★★★

```bash
ip -br link
ip -br addr
```

```text
lo               UNKNOWN        127.0.0.1/8 ::1/128
eno1             UP
vmbr0            DOWN
```

```bash
cat /etc/network/interfaces
```

```text
auto lo
iface lo inet loopback

iface eno1 inet manual

auto vmbr0
iface vmbr0 inet static
        address 10.10.0.11/24
        gateway 10.10.0.1
        bridge-ports eno1
        bridge-stp off
        bridge-fd 0
```

```bash
# ★★★★ 檢查語法（ifupdown2 可以做 dry-run）
ifreload -a -n
```

★★★★★ 常見原因：**升級時誤覆蓋了 `/etc/network/interfaces`**。
備份在同目錄下：

```bash
ls -l /etc/network/interfaces*
```

```text
-rw-r--r-- 1 root root 412 Sep  2 13:20 /etc/network/interfaces
-rw-r--r-- 1 root root 389 Sep  1 09:14 /etc/network/interfaces.dpkg-old
```

```bash
cp /etc/network/interfaces.dpkg-old /etc/network/interfaces
ifreload -a
ip -br addr show vmbr0
```

```text
vmbr0            UP             10.10.0.11/24
```

### 症狀 B：Web 後台連不上（8006）★★★★★

★★★★★ **先確認一件事：VM 有沒有還在跑？**

#### C-3　LVM-thin pool 滿了 ★★★★★

★★★★★ **這是 PVE 最危險的儲存故障，會造成資料損毀。**

```bash
lvs -a
```

```text
  LV              VG  Attr       LSize   Pool Origin Data%  Meta%
  data            pve twi-aotzD- 780.00g              99.85  87.20
  [data_tdata]    pve Twi-ao---- 780.00g
  [data_tmeta]    pve ewi-ao----   8.00g
  root            pve -wi-ao----  94.00g
  swap            pve -wi-ao----   8.00g
  vm-101-disk-0   pve Vwi-aotz-- 100.00g data        62.11
  vm-102-disk-0   pve Vwi-aotz-- 500.00g data        88.40
```

★★★★★ **兩個數字都要看**：

| 欄位 | 意義 | 危險線 |
| --- | --- | --- |
| ★★★★★ `Data%` | thin pool 實際用掉的資料空間 | ★★★★★ **超過 90% 就要處理** |
| ★★★★★ `Meta%` | ★★★★★ **中繼資料空間**（很多人不知道有這個） | ★★★★★ **超過 80% 極度危險** |

★★★★★ **`Meta%` 滿了會讓整個 pool 進入唯讀甚至損毀**，
而且它的容量很小（幾 GB），很容易在你沒注意時就滿了。

`Attr` 欄位第 9 個字元是狀態：

| 字元 | 意義 |
| --- | --- |
| ★★★★ `D` | ★★★★ pool 已滿或有問題 |
| ★★★ `-` | 正常 |

**★★★★★ 為什麼 thin pool 會超賣**

```
   thin pool 實體容量：780 GB
   ─────────────────────────────
   VM 101 宣告 100 GB  ┐
   VM 102 宣告 500 GB  ├─ 總宣告 1000 GB  ★★★★★ 超過實體容量！
   VM 103 宣告 400 GB  ┘

   ★★★★ 一開始沒問題（沒寫的部分不佔空間）
   ★★★★★ 但 VM 持續寫入後，實際用量會逼近 780 GB
   ★★★★★ 一旦滿了 → 所有 VM 的寫入全部失敗 → 檔案系統損毀
```

**緊急處理順序 ★★★★★**

```
① ★★★★★ 立刻停止會繼續寫入的來源
     - 停掉備份任務
     - 停掉非關鍵的 VM（qm shutdown）
        ↓
② 刪掉可以刪的東西（★★★★ 依優先順序）
     - ★★★★★ 舊快照（快照是 thin pool 的空間殺手）
     - 不用的 VM 磁碟
     - 已經沒在用的 VM
        ↓
③ 擴充 pool（如果有多的實體空間）
        ↓
④ ★★★★★ 事後：設定告警，不要再讓它發生
```

```text
    `-> current                                     You are here!
```

```bash
# ① 節點還活著嗎
```


**★★★★★ 關鍵字對照：**

| 日誌 | 意思 | 往哪查 |
| --- | --- | --- |
| ★★★★★ `Token has not been received` | corosync 心跳逾時 | ★★★★★ 網路延遲／封包遺失 |
| ★★★★★ `has no active links` | 到該節點的所有連結都斷 | 網路實體層、VLAN、MTU |
| ★★★★ `Retransmit List:` 一直出現 | 封包在重傳，網路品質差 | ★★★★★ corosync 網路要獨立 |
| ★★★★ `non-primary component` | 這一半沒有 Quorum | 確認多數在哪一邊 |
| ★★★ `Sync members` 變動頻繁 | 叢集在震盪 | 網路不穩 |

```bash
# ③ corosync 走哪個網路
grep -A3 'ring0_addr\|interface' /etc/pve/corosync.conf 2>/dev/null || \

```

```text
  node {
    name: pve1
    nodeid: 1
    quorum_votes: 1
    ring0_addr: 10.10.99.11
  }
```

```bash
# ④ 測那條網路的品質（★★★★★ corosync 對延遲極度敏感）

```

```text
100 packets transmitted, 98 received, 2% packet loss, time 19845ms
rtt min/avg/max/mdev = 0.135/0.892/48.221/5.331 ms
```

★★★★★ **2% 遺失、最大 48 ms —— 這對 corosync 來說已經是災難級**。
corosync 需要**穩定的低延遲網路**，理想上要有**專用的實體網段**。
規劃見 [[050-01-03-07-svc-PVE-叢集與高可用]]。

#### D-4　修復路徑

```
  ┌ 節點真的掛了（DOWN）
  │    ↓
  │  ★★★★ 修好它並開機，Quorum 自動恢復
  │  ★★★★★ 短期內修不好 → 見 D-5「單節點緊急運作」
  │
  ├ 節點活著但 corosync 不通
  │    ↓
  │  ① 檢查該節點的 corosync 服務
  │     systemctl status corosync
  │  ② 檢查網路（VLAN、MTU、交換器埠）
  │  ③ 兩邊都重啟 corosync（★★★★ 一台一台來）
  │     systemctl restart corosync
  │  ④ 仍不行 → 檢查 /etc/pve/corosync.conf 的
  │     config_version 是否一致
  │
  └ 全部節點的 corosync 都異常
       ↓
     ★★★★★ 通常是 corosync.conf 被改壞了
     見 D-6
```

```bash
sleep 10
pvecm status | grep -E 'Quorate|Total votes'
```

#### D-5　★★★★★ 單節點緊急運作（最高風險操作）

> [!danger] ★★★★★ `pvecm expected 1` 的後果
> 這個指令把 Quorum 門檻強制降到 1，讓單一節點可以寫 `/etc/pve`。
>
> ★★★★★ **如果其他節點其實還活著（只是網路斷了），
> 兩邊都會認為自己有權寫入設定 —— 這叫 split-brain。**
> 網路恢復時兩邊的設定會衝突，可能造成：
> - VM 設定互相覆蓋
> - ★★★★★ **同一台 VM 在兩個節點同時開機 → 共享儲存上的磁碟被兩邊寫 → 資料毀了**
>
> **使用前必須百分之百確認其他節點是「關機」狀態**，
> 不是「連不上」，是**你親自確認過電源是關的**。

```bash

pvecm status | grep -E 'Quorate|Expected'
```

```text

Quorate:          Yes
```

```bash

pvecm expected 3
```

★★★★ 或者直接重啟 corosync 讓它重新協商。

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ `/etc/pve` 唯讀，什麼設定都改不了 | 失去 Quorum | `pvecm status` 確認；修 corosync 或節點；見「症狀 D」 |
| ★★★★★ `/etc/pve` 是空的 | `pve-cluster`（pmxcfs）沒起來 | `systemctl status pve-cluster`；必要時 `pmxcfs -l` 救援 |
| ★★★★★ 後台連不上但 VM 都正常 | pveproxy 掛了或防火牆擋住 | `systemctl status pveproxy`；`curl -k https://127.0.0.1:8006/` 分辨 |
| ★★★★★ 後台狀態全變灰色／問號 | pvestatd 卡在離線的儲存上 | `pvesm status` 找出離線儲存，`pvesm set <名> --disable 1` |
| ★★★★★ thin pool `Data%` 或 `Meta%` 接近 100 | 超賣 + 快照堆積 | 停止寫入 → 刪快照 → 擴充 pool；★★★★★ 設告警 |
| ★★★★★ VM 開不起來報 `no such volume` | 磁碟不見或 LVM 沒啟用 | `lvs`、`vgchange -ay`、`qm rescan`；不行就從備份還原 |
| ★★★★★ `VM is locked (backup)` | 備份異常中斷留下鎖 | ★★★★★ **先確認備份沒在跑**再 `qm unlock <id>` |
| ★★★★★ LXC `job failed with error -1` | 訊息不足 | ★★★★★ 用 `pct start <id> --debug` 看真因 |
| ★★★★ LXC 起不來，debug 顯示 `Failed to mount` | bind mount 來源不存在 | `mkdir -p` 建目錄，或從設定移除該 mp |
| ★★★★ 遷移報 `Host key verification failed` | 節點間 SSH 主機金鑰不符 | `pvecm updatecerts --force` |
| ★★★★ 遷移報 `can't migrate VM with local resources` | 有 PCIe 直通或本機專屬資源 | 直通不能線上遷移；改離線遷移 |
| ★★★★ 線上遷移 `remaining` 降不下去 | VM 寫記憶體比網路快 | 提升遷移頻寬、低峰期做、或改離線 |
| ★★★★ 備份報 `No space left on device` | 備份儲存滿 | 設 `--prune-backups` 保留政策 |
| ★★★★ 備份報 `guest-fsfreeze-freeze failed` | guest agent 沒裝／沒跑 | guest 內安裝並啟用 `qemu-guest-agent` |
| ★★★★ 節點自己重開機了 | HA watchdog fence（失去 Quorum 太久） | ★★★★ 這是設計行為；真正要修的是 Quorum |
| ★★★★ 憑證過期，瀏覽器擋住 | `pveproxy-ssl.pem` 到期 | `pvenode cert set` 換新；或 `pvenode cert delete` 退回自簽 |
| ★★★★ 節點之間 API 呼叫報憑證錯誤 | `pve-ssl.pem` 或叢集 CA 問題 | 每個節點 `pvecm updatecerts --force` |
| ★★★★ 開機停在 emergency mode | `/etc/fstab` 有掛不上的項目 | 註解該行；★★★★★ NFS 儲存不要寫進 fstab |
| ★★★★ 升級後主機沒網路 | `/etc/network/interfaces` 被覆蓋 | 從 `interfaces.dpkg-old` 還原，`ifreload -a` |
| ★★★ 根檔案系統滿 | 日誌、備份、ISO 堆積 | `apt clean`、`journalctl --vacuum-size=`、清 dump 目錄 |
| ★★★ `qm rescan` 後磁碟變成 `unused0` | 這是正常行為 | `qm set <id> --scsi0 <volid>` 接回去 |
| ★★★ 後台任務錯誤訊息看不完整 | 摘要被截斷 | 看 `/var/log/pve/tasks/` 的完整日誌 |

### ★★★★★ 千萬不要做的事

| 不要做 | 為什麼 |
| --- | --- |
| ★★★★★ 直接編輯 `/var/lib/pve-cluster/config.db` | 會毀掉整個叢集設定，且沒有還原路徑 |
| ★★★★★ 在其他節點可能還活著時 `pvecm expected 1` | ★★★★★ split-brain，共享儲存資料損毀 |
| ★★★★★ 備份還在跑時 `qm unlock` | 備份檔損毀、VM 磁碟不一致 |
| ★★★★★ 用 `lvremove` 直接刪 VM 的磁碟或快照 | 繞過 PVE，設定檔會對不上 |
| ★★★★★ 一次 `systemctl restart` 所有 PVE 服務 | 加大不確定性，反而更難判斷 |
| ★★★★★ 儲存滿了就急著刪備份檔 | 可能刪掉唯一能救回資料的那一份 |
| ★★★★ 用 `kill -9` 殺 QEMU 程序 | VM 等同拔電源，可能造成 guest 檔案系統損毀 |
| ★★★★ 沒看日誌就重開機 | ★★★★★ 重開機會沖掉現場證據，根因就查不到了 |
| ★★★ 把 `pve-firewall` 關掉就不開回來 | 主機長期暴露 |

## 安全性注意事項

### 故障排除本身的風險 ★★★★

| 風險 | 說明 | 對策 |
| --- | --- | --- |
| ★★★★★ **急救時關掉安全機制** | 為了進得去而 `pve-firewall stop`、開放全網段 | ★★★★★ **事件結束後檢查有沒有恢復**，寫進事件結案清單 |
| ★★★★★ **臨時憑證與密碼殘留** | 急救時建的臨時帳號、貼在工單裡的密碼 | 結案前逐一清除並改密碼 |
| ★★★★ **日誌被沖掉** | 重開機、`journalctl --vacuum` 清掉證據 | ★★★★★ **先蒐證再操作**（`pve-triage.sh` 的輸出留檔） |
| ★★★★ **在不安全的通道傳輸資訊** | 把設定檔、日誌用明文郵件寄出 | 走加密通道；敏感資訊遮罩 |
| ★★★ **旁人代操** | 廠商遠端進來後沒有紀錄 | 全程錄影或記錄，事後撤銷存取 |

### 蒐證優先 ★★★★★

```bash
# ★★★★★ 出事第一件事：把現場凍結成一份檔案
{
  date -Is
  /usr/local/bin/pve-triage.sh
  echo "=== journal (本次開機) ==="
  journalctl -b --no-pager | tail -500
  echo "=== journal (上次開機) ==="
  journalctl -b -1 --no-pager | tail -300
  echo "=== dmesg ==="
  dmesg -T | tail -200
} > /root/incident-$(hostname)-$(date +%F-%H%M).txt 2>&1

ls -lh /root/incident-*.txt
```

```text
-rw-r--r-- 1 root root 412K Sep  8 08:23 /root/incident-pve1-2026-09-08-0823.txt
```

★★★★ 把這份檔案**複製到別台機器**再開始動手 ——
如果接下來要重開機或重建，這是你唯一的證據。

### 存取控制 ★★★★

- ★★★★★ **`/etc/pve/priv/` 只有 root 讀得到**，裡面是叢集私鑰。
  排錯時不要把它的內容貼進工單或聊天室。
- ★★★★ 給操作員的權限應該是**唯讀 + 特定 VM 的操作**，
  不要因為「排錯方便」就發 root。權限模型見
  [[050-01-03-08-guide-PVE-使用者權限與API]]。
- ★★★ 排錯用的臨時 SSH 金鑰，結案後從 `authorized_keys` 移除。

### 事件紀錄 ★★★★★

★★★★★ 每一次故障都要留下：

```
① 什麼時候開始（★★★★★ 不是「什麼時候發現」）
② 影響範圍（哪些服務、多少使用者）
③ 怎麼判斷出根因（★★★★ 把判定分支寫下來，下次可以更快）
④ 做了什麼恢復動作
⑤ 什麼時候恢復
⑥ ★★★★★ 改善事項與負責人、期限
```

格式見 [[100-02-09-svc-維運-事件處理與升級流程]]，
知識累積見 [[100-02-11-guide-維運-維運文件與知識庫]]。

## 練習題

1. 把 `pve-triage.sh` 建到你的 PVE 上，執行一次並把輸出存檔。
   ★★★★ 說明每一段輸出「正常應該長什麼樣」。
2. 在測試環境刻意製造「Quorum 掉了」的狀況
   （★★★★★ 三節點測試叢集，關掉兩台），觀察 `/etc/pve` 變成唯讀，
   並記錄 `pvecm status` 與 corosync 日誌的變化。★★★★★ 不要在正式環境做。
3. 建一個帶 bind mount 的測試容器，故意把主機端目錄刪掉，
   用 `pct start --debug` 找出錯誤，然後修好它。
4. 對一台測試 VM 手動加上鎖（例如中斷一次備份），
   練習「確認沒有備份在跑」的三個檢查，再 `qm unlock`。
5. 用 `lvs -a` 記錄你的 thin pool 的 `Data%` 與 `Meta%`，
   算出照目前成長速度，多久會用完；然後設定一個告警。
6. 寫一份你們機關的「PVE 故障處理 SOP 第一頁」，
   ★★★★★ 內容是「接到通報後的前 10 分鐘要做什麼」，
   必須包含蒐證與影響範圍判定。

> [!question]- 練習解答
>
> **1.** 正常基準：
> - PVE 服務六個全 `active`
> - `fuse mounts: 1`、`writable: YES`
> - `Quorate: Yes`，`Total votes` = 節點數（+QDevice）
> - 儲存全部 `active`，使用率 < 80%
> - 「近期錯誤」段落最好是空的
>
> ★★★★ **把這份「正常樣貌」存檔，出事時 `diff` 一下最快。**
>
> **2.**
> ```bash
> # 在 pve2、pve3 上
> systemctl stop corosync   # ★★★★ 比關機安全，可以隨時開回來
> # 回到 pve1
> pvecm status              # Quorate: No
> touch /etc/pve/.t         # Read-only file system
> journalctl -u corosync -n 30
> # 恢復
> ssh root@pve2 'systemctl start corosync'
> ssh root@pve3 'systemctl start corosync'
> pvecm status              # Quorate: Yes
> ```
> ★★★★★ **正式環境絕對不要做這個實驗**，會讓所有 VM 無法管理。
>
> **3.**
> ```bash
> pct create 999 local:vztmpl/<模板> --rootfs local-lvm:8 \
>   --net0 name=eth0,bridge=vmbr0,ip=dhcp --hostname test999
> mkdir -p /srv/test999
> pct set 999 --mp0 /srv/test999,mp=/mnt/t
> pct start 999 && pct stop 999
> rmdir /srv/test999
> pct start 999 --debug     # ★★★★★ 會看到 Failed to mount
> mkdir -p /srv/test999
> pct start 999             # 好了
> pct destroy 999 --force
> ```
>
> **4.** 三個檢查：
> ```bash
> ps aux | grep -E '[v]zdump|[q]mrestore'          # ① 沒有程序
> pvesh get /nodes/$(hostname)/tasks --limit 10     # ② 沒有 running 任務
> ls -lt /var/log/vzdump/ | head -3                 # ③ 日誌沒有在增長
> qm unlock <id>
> ```
> ★★★★★ 三個都確認才解鎖，否則可能毀掉備份或磁碟一致性。
>
> **5.**
> ```bash
> lvs -a --units g -o lv_name,data_percent,metadata_percent pve/data
> ```
> ★★★★ 成長速度可以用**每週記錄一次**的方式估算。
> 告警設定見 [[100-01-03-guide-日誌-系統監控與告警]]，
> ★★★★★ 門檻建議 `Data% > 80` 警告、`> 90` 緊急，`Meta% > 70` 就要警告。
>
> **6.** 前 10 分鐘 SOP 至少要有：
> - ★★★★★ **0–2 分：蒐證**（`pve-triage.sh` 輸出留檔，複製到別台）
> - ★★★★★ **2–5 分：判定影響範圍**（哪些節點／VM／服務、多少人受影響）
> - ★★★★ **5–7 分：分層定位**（用 triage 輸出決定走哪個症狀分支）
> - ★★★★ **7–10 分：通報**（依嚴重度通報對象，給預估恢復時間）
> - ★★★★★ **原則：恢復優先於查根因，但蒐證優先於恢復**

## 小測驗

**Q1.** `/etc/pve` 突然變成唯讀，`touch` 失敗。最可能的原因是什麼？
第一個該跑的指令是？

**Q2.** 是非題：後台（8006）連不上，代表 VM 也停了。

**Q3.** `lvs -a` 顯示 thin pool 的 `Data% 62.00`、`Meta% 91.00`。
這個狀況危險嗎？為什麼？

**Q4.** 下列哪一個是查「後台任務為什麼失敗」最完整的地方？
（A）Web 介面的紅色錯誤提示　（B）`/var/log/pve/tasks/`
（C）`/var/log/syslog`　（D）`dmesg`

**Q5.** 這行指令會發生什麼？有什麼風險？

```bash
pvecm expected 1
```

**Q6.** LXC 容器 `pct start 201` 只回 `job failed with error -1`。
你要怎麼拿到真正的錯誤訊息？

**Q7.** 簡答：後台打得開，但所有節點與 VM 的狀態都是灰色問號。
最可能是哪個服務有問題？為什麼會這樣？

**Q8.** 節點 pve3 半夜自己重開機了，`journalctl -u pve-ha-lrm -b -1`
看到 `lost lock` 與 `watchdog expired`。這是故障還是設計行為？該修什麼？

**Q9.** 是非題：VM 顯示 `lock: backup` 但備份任務早就不見了，
可以直接 `qm unlock` 解掉。

**Q10.** 一台 PVE 主機的根檔案系統（`/`）用到 99%。
在還沒查清楚原因之前，下列哪一個動作**最不安全**？
（A）`apt clean`　（B）`journalctl --vacuum-size=500M`
（C）刪掉 `/var/lib/vz/dump/` 裡最大的備份檔　（D）`du -xh --max-depth=1 /`

> [!question]- 測驗答案
>
> **Q1 → 失去 Quorum。** ★★★★★
> `/etc/pve` 是 pmxcfs 提供的叢集檔案系統，Quorum 不成立時會轉唯讀以保護資料。
> 第一個指令：**`pvecm status`**，看 `Quorate` 是不是 `No`。
> 見「Quorum：叢集能不能寫設定的開關」與「症狀 D」。
>
> **Q2 → 否** ★★★★★
> `pveproxy` 只是管理介面。它掛掉時**執行中的 VM 與容器完全不受影響**。
> 所以後台連不上不是緊急事故，先用 SSH 進去 `qm list` 確認即可。
> 見「症狀 B」開頭。
>
> **Q3 → 非常危險。** ★★★★★
> `Meta%`（中繼資料）到 91% 比 `Data%` 62% 嚴重得多 ——
> ★★★★★ **中繼資料滿了會讓整個 thin pool 進入唯讀甚至損毀**，
> 而且它的容量很小，很容易被忽略。
> 要立刻 `lvextend --poolmetadatasize` 擴充。見「症狀 C-3」。
>
> **Q4 → (B)** ★★★★★
> Web 上的錯誤提示是**被截斷的摘要**。
> `/var/log/pve/tasks/` 存有每個任務的完整輸出，
> 包含 QEMU／LXC 吐出的真正原因。見「日誌在哪裡」與「症狀 F-2」。
>
> **Q5 →** 把 Quorum 門檻強制降到 1 票，讓單一節點可以寫 `/etc/pve`。 ★★★★★
> ★★★★★ **風險：如果其他節點其實還活著（只是網路不通），
> 兩邊都會認為自己有寫入權 → split-brain。**
> 最嚴重的後果是同一台 VM 在兩個節點同時開機，
> 共享儲存上的磁碟被兩邊寫入而毀掉。
> 只在**親自確認其他節點電源是關的**時才可以用。見「症狀 D-5」。
>
> **Q6 → `pct start 201 --debug`。** ★★★★★
> 它會印出 LXC 的完整啟動流程，**最後一行的 `Failed to ...` 才是真因**。
> 需要更詳細時用 `lxc-start -n 201 -F -l DEBUG -o /tmp/lxc.log`。
> 見「症狀 G-1」。
>
> **Q7 → `pvestatd`。** ★★★★★
> 它負責收集節點、VM、儲存的狀態。
> ★★★★★ 最典型的原因是**某個儲存（尤其 NFS）離線，
> `pvestatd` 每一輪都卡在那裡逾時**，導致所有狀態都更新不了。
> 處理方式：`pvesm status` 找出離線儲存 → `pvesm set <名> --disable 1`
> → `systemctl restart pvestatd`。見「症狀 B-5」。
>
> **Q8 → 是設計行為，不是故障。** ★★★★
> 節點失去 Quorum 超過容忍時間後，HA 的 watchdog 會主動把節點重開機，
> ★★★★★ 目的是確保它上面的 VM 真的停了，
> 避免 HA 在別的節點啟動同一台 VM 時造成雙重執行。
> **真正要修的是「為什麼會失去 Quorum」** —— 回到症狀 D 查 corosync 網路。
> 見「症狀 D-7」。
>
> **Q9 → 否（不能直接解）** ★★★★★
> 必須先做三個確認：① `ps aux | grep [v]zdump` 沒有程序、
> ② `pvesh get /nodes/<node>/tasks` 沒有 running 的備份任務、
> ③ `/var/log/vzdump/` 的日誌沒有在增長。
> ★★★★★ **在備份還在跑時解鎖，可能造成備份檔損毀或磁碟不一致。**
> 見「症狀 H-3」。
>
> **Q10 → (C)** ★★★★★
> 刪備份檔可能刪掉**唯一一份還原得回來的資料**，而且不可逆。
> (A)(B) 是安全的空間回收，(D) 只是查看不會改東西。
> ★★★★★ 正解是先用 (D) 找出原因，用 (A)(B) 爭取時間，
> 備份則要靠**保留政策**自動輪替，不是滿了才手動刪。見「症狀 C-2」。
