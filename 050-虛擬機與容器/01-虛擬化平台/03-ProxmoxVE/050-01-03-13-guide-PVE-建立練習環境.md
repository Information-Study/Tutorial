# 用 PVE 建立練習環境

> [!abstract] 這篇你會學到
> - ★★★★★ **一套可以重複建出來的實驗環境**：本手冊 Linux、Web、資料庫、
>   前後端分離、資安、監控各章要的機器，一次備齊
> - **實驗網段與 VLAN 怎麼規劃**，以及為什麼實驗環境一定要跟正式環境隔離
> - ★★★★★ **做一個 Ubuntu cloud-init 範本**，之後開一台機器只要 30 秒
> - **連結複製（linked clone）vs 完整複製**，什麼時候用哪一個
> - ★★★★ **一鍵開出 LXMP 全套所需機器**（Nginx／MySQL／PHP-FPM／Node.js）
> - ★★★★★ **快照當作實驗還原點** —— 大膽做實驗、做壞了 10 秒還原
> - ★★★★ **省資源技巧**：什麼時候用 LXC 取代 VM，可以省下多少
> - **清理與重建腳本**：讓整套環境變成「隨時可以打掉重練」

> [!warning] 未實機驗證
> 本篇**以 Proxmox VE 8 與 Ubuntu 24.04 LTS cloud image 為例**。
>
> ★★★★★ 文中的**映像檔名、版本號、VMID、IP、儲存名稱都是示意值**，
> 請換成你環境實際的值。cloud image 的檔名會隨版本改變，
> 動手前先到 Ubuntu 官方 cloud images 站台確認當前檔名。
>
> ★★★★★ 本篇的腳本會**大量刪除 VM 與容器**。
> 所有腳本都用 **900 起跳的 VMID 區段**，並在執行前有確認提示。
> ★★★★★ **絕對不要在有正式服務的 PVE 上直接跑這些腳本**，
> 也不要把 VMID 區段改到跟正式環境重疊。

## 觀念說明

### ★★★★★ 為什麼要「一套可以重建的環境」

自己手動裝機器來練習，會遇到三個問題：

| 問題 | 後果 |
| --- | --- |
| ★★★★★ **裝一台要 20 分鐘** | 想練 5 台就是 100 分鐘，人就懶了，練習變成負擔 |
| ★★★★★ **做壞了不敢還原** | 心裡想「重裝要很久」，於是不敢做危險的實驗，學不到東西 |
| ★★★★ **每次環境都不一樣** | 這次成功、下次失敗，搞不清楚是自己的問題還是環境的問題 |

★★★★★ **正確的心態：實驗環境應該是「用完就丟」的消耗品。**

```
   一次性投入                       之後每次
   ─────────────                  ──────────
   ① 規劃網段（30 分鐘）             開一台機器：★★★★★ 30 秒
   ② 做 cloud-init 範本（40 分鐘）    開一整套 6 台：★★★★★ 3 分鐘
   ③ 寫建置腳本（30 分鐘）           做壞了還原：★★★★★ 10 秒
   ④ 寫清理腳本（10 分鐘）           整套打掉重練：★★★★ 2 分鐘
   ────────────────────────
   ★★★★ 大約兩小時，換來之後無數次的省時
```

### VM vs LXC：省資源的關鍵決策 ★★★★★

```
                需要跑什麼？
                     │
    ┌────────────────┼─────────────────┐
    │                │                  │
不同的核心／OS    一般 Linux 服務      需要完整隔離
    │                │                  │
    ▼                ▼                  ▼
★★★★★ VM        ★★★★★ LXC          ★★★★ VM
（Windows、        （Nginx、PHP、        （練習核心參數、
  自訂核心、          MySQL、Node、         Docker、
  Docker）            監控、CA）             資安攻防）
```

**實際的資源差距（★★★ 示意值，看你跑什麼）：**

| 項目 | 一台 Ubuntu VM | 一個 Ubuntu LXC |
| --- | --- | --- |
| ★★★★★ 記憶體（idle） | 約 400～600 MB | ★★★★★ **約 30～80 MB** |
| ★★★★★ 磁碟（乾淨系統） | 約 2.5～4 GB | ★★★★★ **約 500 MB～1 GB** |
| ★★★★★ 開機時間 | 20～40 秒 | ★★★★★ **1～3 秒** |
| ★★★ CPU 開銷 | 有虛擬化開銷 | ★★★★ 幾乎沒有 |
| ★★★★ 隔離程度 | ★★★★★ 高（獨立核心） | ★★★ 中（共用主機核心） |

★★★★★ **同一台 32 GB 記憶體的主機：**

```
   全部用 VM：   大約可以開 8～12 台練習機
   ★★★★★ 混用： 可以開 25～40 台
```

> [!tip] ★★★★★ 練習環境的建議配比
> **八成用 LXC，兩成用 VM。**
> 只有在「必須要有自己的核心」時才用 VM：
> Windows、Docker、練習核心參數與模組、資安攻防（怕污染主機）、
> ★★★★ 以及要練習「這篇教學在真的 VM 上跑起來是什麼樣」的時候。

### 實驗網段規劃 ★★★★★

> [!danger] ★★★★★ 實驗環境一定要跟正式環境隔離
> 練習環境裡你會做的事：
> - 開一堆沒設密碼、沒更新的機器
> - 練習攻擊與弱點掃描
> - 亂設防火牆規則
> - 開 DHCP 伺服器做實驗
>
> ★★★★★ **這些任何一件跑到正式網段上都是資安事件。**
> 尤其是「自己開一台 DHCP 伺服器」—— 它會把整個辦公室的電腦搶走。

**建議的網段配置：**

| 用途 | VLAN | 網段 | 說明 |
| --- | --- | --- | --- |
| ★★★★★ PVE 管理 | 10 | `10.10.0.0/24` | ★★★★★ 正式管理網，**實驗機不要放這裡** |
| ★★★★★ **實驗 A（前端／Web）** | 30 | `192.168.30.0/24` | ★★★★ 對外服務層 |
| ★★★★★ **實驗 B（後端／資料庫）** | 31 | `192.168.31.0/24` | ★★★★ 只給 A 層連 |
| ★★★★ **實驗 C（隔離／攻防）** | 32 | `192.168.32.0/24` | ★★★★★ **完全不通外網**，練攻擊用 |
| ★★★ 實驗管理 | 33 | `192.168.33.0/24` | ★★★ 練習機的 SSH 管理介面 |

```
                    ┌──────────────┐
                    │ 辦公網／Internet │
                    └───────┬──────┘
                            │
                    ┌───────▼──────┐
                    │  防火牆／路由器  │  ★★★★★ 實驗網的出口在這裡管
                    └───────┬──────┘
                            │ trunk
                  ┌─────────▼─────────┐
                  │   交換器（VLAN）    │
                  └─────────┬─────────┘
                            │ trunk
                  ┌─────────▼─────────┐
                  │   PVE  vmbr0       │  ★★★★★ VLAN-aware bridge
                  │  （VLAN aware）     │
                  └──┬──────┬──────┬──┘
                     │      │      │
                  tag=30 tag=31 tag=32
                     │      │      │
                  ┌──▼─┐ ┌─▼──┐ ┌─▼───┐
                  │web │ │ db │ │攻防機│
                  └────┘ └────┘ └─────┘
                                  ★★★★★ VLAN 32 不給出口
```

**★★★★ 沒有可管理交換器怎麼辦？**

用 PVE 內部的 bridge 就好，不需要實體 VLAN：

```
   vmbr0  ← 有實體網卡，接到辦公網（PVE 管理用）
   vmbr30 ← ★★★★★ 沒有實體網卡的「內部 bridge」
   vmbr31 ← 同上
```

★★★★★ **`bridge-ports none` 的 bridge 是完全隔離的內部網路** ——
上面的機器只能互相溝通，碰不到外面，也不會影響辦公網。
這是**最安全也最簡單的實驗網做法**。

### cloud-init 是什麼、為什麼要用 ★★★★★

```
【傳統做法】
  掛 ISO → 開機 → 語言 → 鍵盤 → 網路 → 磁碟分割 → 使用者
  → 套件選擇 → 等 15 分鐘 → 重開機 → 設 SSH → ...
  ★★★★★ 一台 20 分鐘，開 6 台就是兩小時

【cloud-init 做法】
  做一次範本 → 之後每台：
    qm clone 9000 901 --name web01
    qm set 901 --ipconfig0 ip=192.168.30.11/24,gw=192.168.30.1
    qm start 901
  ★★★★★ 一台 30 秒，開 6 台三分鐘，而且每台都一模一樣
```

cloud-init 在**第一次開機時**讀取 PVE 餵給它的設定，自動完成：

| 項目 | PVE 的對應設定 |
| --- | --- |
| ★★★★★ 主機名稱 | `qm set <id> --name <名稱>`（★★★ cloud-init 會用它當 hostname） |
| ★★★★★ 使用者與密碼 | `--ciuser` / `--cipassword` |
| ★★★★★ SSH 公鑰 | `--sshkeys <公鑰檔>` |
| ★★★★★ IP／閘道 | `--ipconfig0 ip=...,gw=...` 或 `ip=dhcp` |
| ★★★★ DNS | `--nameserver` / `--searchdomain` |
| ★★★ 開機後執行的指令 | `--cicustom`（進階，見「進階應用」） |
| ★★★★ 磁碟自動擴充 | ★★★★ cloud image 內建，改大磁碟後自動長大 |

### 連結複製 vs 完整複製 ★★★★★

```
【完整複製 full clone】
   範本 9000 ────複製整份磁碟────► VM 901（獨立的 4 GB）
                              └► VM 902（獨立的 4 GB）
   ★★★★ 各自獨立，範本可以刪
   ★★★★★ 慢（每台都要複製）、佔空間（N 台 = N 份）

【連結複製 linked clone】
   範本 9000（唯讀基底 4 GB）
        ├── VM 901（★★★★★ 只存「跟基底的差異」，一開始幾 MB）
        └── VM 902（同上）
   ★★★★★ 快（幾秒）、超省空間
   ★★★★★ 但：範本不能刪、不能改，而且範本壞了所有子機一起完蛋
```

| 比較 | ★★★★ 完整複製 | ★★★★★ 連結複製 |
| --- | --- | --- |
| 建立速度 | 慢（分鐘級） | ★★★★★ **快（秒級）** |
| 佔空間 | N 份 | ★★★★★ **1 份 + 差異** |
| 範本可否刪除 | ✅ | ❌ **不行** |
| 效能 | ★★★★ 較好 | ★★★ 略差（要查兩層） |
| 適合 | ★★★★ 正式環境、要搬走的機器 | ★★★★★ **練習環境（就是我們要的）** |
| 儲存需求 | 任意 | ★★★★ 需要支援（LVM-thin、ZFS、qcow2 目錄） |

★★★★★ **練習環境用連結複製，這是本篇的預設做法。**

### 快照：練習環境最重要的功能 ★★★★★

```
   建好乾淨的機器
        │
        ▼
   ★★★★★ qm snapshot 901 clean   ←──── 這一步不要跳過！
        │
        ▼
   開始做實驗（★★★★★ 可以放膽亂搞）
        │
   ┌────┴────┐
做壞了      成功了
   │           │
   ▼           ▼
qm rollback   ★★★★ 再存一個快照

   │           │
   ▼           ▼
★★★★★ 10 秒   繼續下一階段
```

★★★★★ **「做壞了可以 10 秒還原」這件事會徹底改變你的學習方式** ——
你會開始敢做那些平常不敢做的實驗（刪掉 `/etc`、改壞 GRUB、
把防火牆設成全擋），而那些才是真正學得到東西的實驗。

## 安裝或基礎操作

### 第一步：建立實驗網路 ★★★★★

#### 做法 A：內部 bridge（★★★★★ 最簡單、最安全、推薦）

```bash
cp /etc/network/interfaces /etc/network/interfaces.bak.$(date +%F)
cat >> /etc/network/interfaces <<'EOF'

# ===== 實驗環境專用內部網路（★★★★★ 沒有實體網卡，完全隔離）=====
auto vmbr30
iface vmbr30 inet static
        address 192.168.30.1/24
        bridge-ports none
        bridge-stp off
        bridge-fd 0
#lab-frontend

auto vmbr31
iface vmbr31 inet static
        address 192.168.31.1/24
        bridge-ports none
        bridge-stp off
        bridge-fd 0
#lab-backend

auto vmbr32
iface vmbr32 inet manual
        bridge-ports none
        bridge-stp off
        bridge-fd 0
#lab-isolated ★★★★★ 連 PVE 自己都沒有 IP，完全孤島
EOF

# ★★★★ 先檢查語法再套用
ifreload -a -n && ifreload -a
ip -br addr show | grep vmbr
```

```text
vmbr0            UP             10.10.0.11/24
vmbr30           UP             192.168.30.1/24
vmbr31           UP             192.168.31.1/24
vmbr32           UP
```

★★★★ **PVE 主機自己在 vmbr30／31 上有 IP（`.1`）**，
所以可以從 PVE 直接 SSH 到實驗機，很方便。
`vmbr32` 沒給 IP —— 那是刻意的孤島網段。

#### 讓實驗機上得了網（★★★★ 裝套件需要）

```bash
# ① 開啟轉發
cat > /etc/sysctl.d/99-lab-forward.conf <<'EOF'
net.ipv4.ip_forward = 1
EOF
sysctl --system | grep ip_forward
```

```text
net.ipv4.ip_forward = 1
```

```bash
# ② NAT（★★★★ 把 vmbr0 換成你實際的對外介面）
cat >> /etc/network/interfaces <<'EOF'
        post-up   iptables -t nat -A POSTROUTING -s 192.168.30.0/24 -o vmbr0 -j MASQUERADE
        post-down iptables -t nat -D POSTROUTING -s 192.168.30.0/24 -o vmbr0 -j MASQUERADE
EOF
```

> [!warning] ★★★★★ 上面那段要接在 `vmbr30` 的區塊裡，不是檔尾
> `post-up` 必須縮排在對應介面的定義底下。
> ★★★★ 改完一定要用 `ifreload -a -n` 檢查語法，
> 弄壞 `/etc/network/interfaces` 會讓主機失去網路。
> 見 [[050-01-03-05-guide-PVE-網路設定]]。

★★★★ 驗證 NAT：

```bash
iptables -t nat -L POSTROUTING -n -v | grep 192.168.30
```

```text
    0     0 MASQUERADE  all  --  *  vmbr0   192.168.30.0/24  0.0.0.0/0
```

#### 做法 B：VLAN-aware bridge（有可管理交換器時）

```bash
grep -A6 'iface vmbr0' /etc/network/interfaces
```

```text
auto vmbr0
iface vmbr0 inet static
        address 10.10.0.11/24
        gateway 10.10.0.1
        bridge-ports eno1
        bridge-stp off
        bridge-fd 0
        bridge-vlan-aware yes
        bridge-vids 2-4094
```

★★★★★ 有 `bridge-vlan-aware yes` 之後，VM 的網卡加 `tag=30` 就會進 VLAN 30。
★★★★ 交換器那一側的 trunk 設定見 [[040-01-06-guide-Juniper-VLAN與Trunk設定]]。

### 第二步：★★★★★ 建立 Ubuntu cloud-init 範本

這是整篇最重要的一次性投入。

#### 2-1　下載 cloud image

```bash
cd /var/lib/vz/template/iso/
```

★★★★ 到 Ubuntu 官方 cloud images 站台確認當前檔名後下載：

```bash
wget https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img
ls -lh noble-server-cloudimg-amd64.img
```

```text
-rw-r--r-- 1 root root 588M Sep  2 10:14 noble-server-cloudimg-amd64.img
```

```bash
  --rootfs "$STORAGE:12" \

  --hostname lab-ca --cores 1 --memory 512 --swap 512 \
  --rootfs "$STORAGE:8" \
  --net0 "name=eth0,bridge=$BR_FRONT,ip=192.168.30.13/24,gw=$GW_FRONT" \

# ---- LXC：monitor ----
msg "建立 803 lab-mon (LXC)"
pct create 803 "$TEMPLATE_CT" \
  --hostname lab-mon --cores 1 --memory 1024 --swap 512 \
  --rootfs "$STORAGE:10" \
  --net0 "name=eth0,bridge=$BR_FRONT,ip=192.168.30.14/24,gw=$GW_FRONT" \

# ---- 等待開機 ----
```

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 複製出來的 VM 沒有套用 IP／使用者 | ★★★★★ 忘了加 cloud-init 磁碟（`--ide2 <儲存>:cloudinit`） | `qm set <id> --ide2 local-lvm:cloudinit` 後重開機 |
| ★★★★★ 改了 `--ipconfig0` 但機器 IP 沒變 | ★★★★★ cloud-init **只在第一次開機執行** | 重新產生 ci 磁碟並重開；或進機器 `cloud-init clean --reboot` |
| ★★★★★ 所有複製機的 SSH 主機金鑰一樣 | 範本沒清 `/etc/ssh/ssh_host_*` | ★★★★★ 重做範本並在轉範本前清乾淨 |
| ★★★★★ 多台機器拿到同一個 DHCP IP | 範本沒清 `/etc/machine-id` | 同上 |
| ★★★★ `qm clone --full 0` 報不支援連結複製 | 來源不是範本，或儲存不支援 | 先 `qm template <id>`；用 LVM-thin／ZFS |
| ★★★★★ `qm template` 之後想改範本 | ★★★★★ 範本不可逆，不能開機也不能改 | ★★★★ 從範本複製一台 → 改 → 再轉成新範本 |
| ★★★★ 刪不掉範本 | 有連結複製的子機還在用它 | ★★★★★ 先刪掉所有 linked clone |
| ★★★★ 後台 Console 一片黑（cloud image） | cloud image 輸出到序列埠 | `qm set <id> --serial0 socket --vga serial0` |
| ★★★★ SSH 進不去，密碼不對 | ★★★★ cloud image 預設**不開密碼登入** | 用 `--sshkeys` 金鑰；要密碼就 `--cipassword` 並在 yaml 裡開 `ssh_pwauth: true` |
| ★★★★ `--cicustom` 之後 `--ciuser` 失效 | ★★★★★ 自訂 user-data 整份取代預設 | yaml 裡自己寫 `users:` 與 `ssh_authorized_keys:` |
| ★★★★ 實驗機連不到網際網路 | 內部 bridge 沒設 NAT 或轉發 | `sysctl net.ipv4.ip_forward=1` + MASQUERADE 規則 |
| ★★★★ `ifreload -a` 之後主機失聯 | `/etc/network/interfaces` 語法錯 | ★★★★★ **改之前一定要先 `ifreload -a -n` 檢查** |
| ★★★★★ thin pool 用量暴增 | 快照堆積 | ★★★★★ `qm listsnapshot` 檢查並刪掉不用的；見 [[050-01-03-12-guide-PVE-故障排除]] |
| ★★★★ 主機重開後一堆練習機自動啟動、資源爆掉 | 建立時沒設 `--onboot 0` | `qm set <id> --onboot 0`、`pct set <id> --onboot 0` |
| ★★★★ LXC 裡跑不了 Docker | 非特權容器的限制 | ★★★★★ **Docker 練習請用 VM**；或加 `nesting=1` 但仍有限制 |
| ★★★ 容器裡 `systemctl` 有些服務起不來 | cgroup 或非特權限制 | 那個服務改用 VM 練習 |
| ★★★ 磁碟擴充了但 guest 裡沒變大 | ★★★★ cloud image 通常會自動長大；非 cloud image 不會 | 進 guest 手動 `growpart` + `resize2fs` |
| ★★★ `pveam download` 找不到模板 | 清單過舊 | 先 `pveam update` |
| ★★★ 清理腳本刪不掉某台 | 有鎖或快照 | `qm unlock <id>`；`--purge` 已含刪快照 |

## 安全性注意事項

### ★★★★★ 練習環境的三條紅線

| 紅線 | 為什麼 | 怎麼守 |
| --- | --- | --- |
| ★★★★★ **不要接到正式網段** | 練習機沒更新、沒密碼、還會被拿來做攻擊實驗 | ★★★★★ 用內部 bridge，或用有 ACL 的獨立 VLAN |
| ★★★★★ **不要在正式 PVE 上建練習環境** | 清理腳本手滑會刪到正式機器 | ★★★★ 用獨立主機；不得已時**嚴守 VMID 區段** |
| ★★★★★ **不要在練習機上放真實資料** | 練習機會被反覆刪掉重建，也沒在備份 | 用假資料、測試帳號 |

### 練習機自己的安全 ★★★★

★★★★ 練習環境「不用管安全」是錯的 —— 至少要做到：

| 項目 | 做法 |
| --- | --- |
| ★★★★★ **金鑰登入而不是密碼** | `--sshkeys`，養成正確習慣 |
| ★★★★ 不要開 root 直接 SSH | cloud image 預設就是關的，保持它 |
| ★★★★★ **攻防實驗一定用隔離網段** | vmbr32（完全沒有出口） |
| ★★★★ 不要下載來路不明的映像 | ★★★★ cloud image 只從官方站台拿，並核對 checksum |
| ★★★ 練習用的假密碼不要跟正式的一樣 | 避免習慣性混用 |

```bash
# ★★★★ 下載後核對 checksum（官方會提供 SHA256SUMS）
cd /var/lib/vz/template/iso/
sha256sum noble-server-cloudimg-amd64.img
```


★★★★ 跟官方站台的 `SHA256SUMS` 比對。

### 攻防實驗的隔離 ★★★★★

```
   ★★★★★ 要做弱點掃描、密碼爆破、漏洞利用練習時：

   ① 機器只接 vmbr32（沒有 IP、沒有出口的孤島）
   ② PVE 主機自己在 vmbr32 上不要有 IP
   ③ 實驗結束後 lab-clean.sh 全部刪掉
   ④ ★★★★★ 絕對不要讓這些機器有機會碰到正式網段

   ┌──────────────────────────────┐
   │  vmbr32（bridge-ports none，  │
   │         PVE 也沒 IP）          │
   │                                │
   │   攻擊機 ◄──►  靶機            │
   │                                │
   │  ★★★★★ 完全的孤島，出不去      │
   └──────────────────────────────┘
```

★★★★ 相關教學見 [[090-02-08-guide-防護-系統強化與稽核]] 與
[[090-02-01-guide-防護-伺服器初始安全設定]]。

### 資源保護 ★★★★

★★★★★ **練習環境最容易造成的實際損害是「把主機的儲存塞滿」**，
連帶影響同一台主機上的其他東西。

```bash
# ★★★★ 建議設一個檢查腳本，練習前後都跑
cat > /usr/local/bin/lab-usage.sh <<'EOF'
#!/usr/bin/env bash
echo "=== thin pool ==="
lvs -a --units g -o lv_name,lv_size,data_percent,metadata_percent pve/data 2>/dev/null
echo "=== 練習機的快照 ==="
for id in $(seq 900 949); do
  qm config "$id" >/dev/null 2>&1 || continue
  n=$(qm listsnapshot "$id" 2>/dev/null | grep -vc 'current')
  [ "$n" -gt 0 ] && echo "  VM $id: $n 個快照"
done
echo "=== 記憶體 ==="
free -h | head -2
EOF
chmod +x /usr/local/bin/lab-usage.sh
/usr/local/bin/lab-usage.sh
```

```text
=== thin pool ===
  data 780.00g  28.40  15.20
=== 練習機的快照 ===
  VM 901: 2 個快照
  VM 902: 1 個快照
=== 記憶體 ===
               total        used        free      shared  buff/cache   available
Mem:            31Gi        11Gi        18Gi       0.0Ki       2.4Gi        20Gi
```

★★★★★ **`data_percent` 超過 70% 就該清快照了。**

## 練習題

1. 依本篇建立 `vmbr30`（`192.168.30.0/24`）與 `vmbr32`（無 IP 的孤島），
   ★★★★ 用 `ifreload -a -n` 驗證語法後套用，並確認 `ip -br addr` 的結果。
2. 完整做出一個 Ubuntu cloud-init 範本（含 guest agent、清 machine-id 與 host key），
   然後用它連結複製出兩台機器，★★★★★ 確認兩台的 `machine-id` **不一樣**。
3. 對其中一台建立 `clean` 快照，故意做一件破壞性的事
   （例如 `sudo rm -rf /etc/nginx`），然後還原。★★★★ 記錄還原花了多久。
4. 用 `--cicustom` 寫一份 cloud-config，讓新機器開機後自動裝好 Nginx，
   ★★★★★ 並確認 `--ciuser` 失效後要怎麼在 yaml 裡補回使用者與金鑰。
5. 執行 `lab-build.sh` 建出整套環境，用一條指令驗證五台機器都 SSH 得進去，
   然後執行 `lab-clean.sh` 清乾淨。★★★★ 記錄整個循環花了多久。
6. 比較一台 Ubuntu VM 與一個 Ubuntu LXC 在 idle 狀態的記憶體與磁碟用量，
   ★★★★ 算出你的主機用純 VM 與混用兩種做法，各能開幾台機器。

> [!question]- 練習解答
>
> **1.**
> ```bash
> cp /etc/network/interfaces /etc/network/interfaces.bak
> # 加入 vmbr30（有 IP）與 vmbr32（inet manual，無 IP）
> ifreload -a -n     # ★★★★★ 這一步不要跳過
> ifreload -a
> ip -br addr | grep vmbr3
> ```
> ★★★★ `vmbr32` 應該顯示 `UP` 但沒有 IP —— 那就是孤島網段。
>
> **2.**
> ```bash
> ssh lab@<ip1> 'cat /etc/machine-id'
> ssh lab@<ip2> 'cat /etc/machine-id'
> ```
> ★★★★★ 兩個值必須不同。相同代表**範本沒清乾淨**，
> 要重做範本（`truncate -s0 /etc/machine-id` 後才 `qm template`）。
> 順便驗 SSH host key：
> ```bash
> ssh-keyscan <ip1> 2>/dev/null | ssh-keygen -lf -
> ssh-keyscan <ip2> 2>/dev/null | ssh-keygen -lf -
> ```
> 指紋也必須不同。
>
> **3.**
> ```bash
> qm snapshot 901 clean
> ssh lab@192.168.30.11 'sudo rm -rf /etc/nginx'
> time { qm stop 901; qm rollback 901 clean; qm start 901; }
> ```
> ★★★★ 在 LVM-thin／ZFS 上，rollback 本身通常在幾秒內完成，
> 大部分時間花在 VM 重新開機。
>
> **4.** yaml 裡要自己寫：
> ```yaml
> #cloud-config
> users:
>   - name: lab
>     sudo: ALL=(ALL) NOPASSWD:ALL
>     shell: /bin/bash
>     ssh_authorized_keys:
>       - ssh-ed25519 AAAA...
> packages: [nginx]
> runcmd:
>   - systemctl enable --now nginx
> ```
> ★★★★★ 驗證方式：`qm cloudinit dump <id> user` ——
> 輸出應該就是你的 yaml，**不再有 PVE 自動產生的 `user:` 那幾行**。
>
> **5.**
> ```bash
> time /usr/local/bin/lab-build.sh
> for t in lab@192.168.30.11 lab@192.168.31.21 root@192.168.30.12 \
>          root@192.168.30.13 root@192.168.30.14; do
>   ssh -o ConnectTimeout=5 "$t" hostname
> done
> time /usr/local/bin/lab-clean.sh
> ```
> ★★★★ 參考值：建置約 3 分鐘、清理約 1 分鐘。
> 比手動裝五台（100 分鐘以上）快非常多。
>
> **6.**
> ```bash
> qm status <vmid> --verbose | grep -E '^(mem|maxmem):'
> pct status <ctid> --verbose | grep -E '^(mem|maxmem):'
> free -h
> lvs -a --units g -o lv_name,lv_size
> ```
> ★★★★ 典型結論：32 GB 主機純 VM 約 8～12 台，
> 混用（八成 LXC）可以到 25～40 台。
> ★★★★★ 磁碟差距更大 —— 連結複製 + LXC 可以省下九成空間。

## 小測驗

**Q1.** 為什麼複製出來的 VM 一定要有 cloud-init 磁碟（`--ide2 <儲存>:cloudinit`）？

**Q2.** 是非題：`qm template 9000` 之後，還可以開機進去改範本內容。

**Q3.** 把範本轉成 template 之前，一定要在 guest 內清掉哪兩樣東西？為什麼？

**Q4.** 連結複製（`--full 0`）與完整複製（`--full 1`），練習環境該用哪一個？
它有什麼限制？

**Q5.** 這行指令會發生什麼？

```bash
qm rollback 901 clean
```

**Q6.** 簡答：你要練習 Docker 與 Windows AD，這兩個各該用 VM 還是 LXC？為什麼？

**Q7.** `bridge-ports none` 的 bridge 有什麼特性？為什麼練習環境很適合用它？

**Q8.** 你改了 `qm set 901 --ipconfig0 ip=192.168.30.99/24,gw=192.168.30.1`
但機器重開後 IP 沒變。最可能的原因是？

**Q9.** 是非題：練習環境的快照可以當備份用，反正資料不重要。

**Q10.** 清理腳本 `lab-clean.sh` 只處理 VMID 800–849 與 900–949。
為什麼要這樣限制？把範圍改成 `1-9999` 有什麼後果？

> [!question]- 測驗答案
>
> **Q1 →** 因為 cloud-init 是靠**一個掛給 VM 的虛擬光碟（NoCloud datasource）**
> 讀取設定的。★★★★★ 沒有這個磁碟，`--ciuser`、`--sshkeys`、`--ipconfig0`
> 全部都不會生效，開出來的機器會是範本的原樣。
> 見「常見錯誤與排錯」第一列。
>
> **Q2 → 否** ★★★★★
> 轉成範本是**不可逆**的：不能開機、不能改磁碟。
> 要改範本的正確做法是：★★★★ **從範本複製一台 → 改 → 再轉成新範本**。
> 見「2-5」的 danger 提醒。
>
> **Q3 → `/etc/machine-id` 與 `/etc/ssh/ssh_host_*`。** ★★★★★
> 不清的話所有複製出來的機器會有**一樣的 machine-id 與 SSH 主機金鑰**，
> 造成：DHCP 發到同一個 IP、SSH 客戶端抱怨金鑰衝突、
> 依賴 machine-id 的軟體打架。
> ★★★★ 清掉後系統會在下次開機自動重新產生。見「2-5」。
>
> **Q4 → 連結複製（`--full 0`）。** ★★★★★
> 它快（秒級）又省空間（只存差異）。
> ★★★★★ 限制：**範本不能刪、不能改**，而且範本壞了所有子機一起完蛋；
> 儲存也必須支援（LVM-thin、ZFS、qcow2 目錄）。
> 見「連結複製 vs 完整複製」。
>
> **Q5 →** 把 VM 901 的磁碟狀態**還原到名為 `clean` 的快照那一刻**，
> 之後所做的所有變更（裝的套件、改的設定、寫的檔案）**全部消失**。
> ★★★★ 通常需要先 `qm stop`，還原後 `qm start`。
> ★★★★★ 這是練習環境最重要的一個動作。見「快照：實驗還原點」。
>
> **Q6 →**
> - ★★★★★ **Docker → VM。** 在非特權 LXC 裡跑 Docker 限制很多、
>   常常卡在 cgroup 與儲存驅動；VM 裡是乾淨的環境。
> - ★★★★★ **Windows AD → 只能 VM。** LXC 共用主機的 Linux 核心，
>   ★★★★★ **根本不能跑 Windows**。
>
> 見「VM vs LXC」決策圖。
>
> **Q7 →** 它是一個**沒有連到任何實體網卡的內部橋接器**。 ★★★★★
> 特性：上面的機器只能互相溝通，**碰不到外部網路，也不會影響辦公網**。
> ★★★★★ 練習環境很適合，因為練習機常常沒更新、沒密碼、
> 甚至會被拿來做攻擊實驗 —— 隔離起來最安全。
> 見「實驗網段規劃」的做法 A。
>
> **Q8 → cloud-init 只在「第一次開機」執行。** ★★★★★
> 改了 `--ipconfig0` 之後，光重開機不會重新套用。
> 解法：進機器跑 `sudo cloud-init clean --logs --reboot`，
> 或用 `qm cloudinit update <id>` 重新產生 ci 磁碟後重開。
> 見「常見錯誤與排錯」與「cloud-init 排查三步」。
>
> **Q9 → 否** ★★★★★
> 快照存在**同一個儲存上**，儲存壞了兩個一起沒。
> ★★★★ 練習環境用快照當還原點沒問題（反正可以重建），
> ★★★★★ **但「快照 = 備份」這個觀念絕對不能帶進正式環境。**
> 另外快照會持續吃 thin pool 空間，用完要刪。
> 見「快照：實驗還原點」的兩個 warning。
>
> **Q10 →** 那是**刻意設的護欄**，避免手滑刪到正式機器。 ★★★★★
> 改成 `1-9999` 的後果：★★★★★ **在有正式服務的 PVE 上執行一次，
> 就會把所有正式 VM 與容器全部永久刪除**，
> 而且 `--purge` 會連磁碟與快照一起刪，沒有任何還原路徑。
> ★★★★★ 所以腳本才要求輸入大寫 `DELETE` —— 那三秒鐘是給你想清楚的。
> 見「清理與重建腳本」的 danger 區塊。
