## 是非題（50 題）

Q1. PVE 裝完後第一次執行 `apt update`，出現 `enterprise.proxmox.com` 的 `401 Unauthorized`，代表 ISO 下載時被竄改或安裝有問題，應該重新安裝一次。

Q2. 安裝精靈裡選 ext4 還是 ZFS，裝完之後可以用 `pvesm` 線上切換，所以不必在安裝當下想太久。

Q3. 改了 `vmbr0` 的管理 IP 卻沒有同步改 `/etc/hosts` 裡主機名那一行，後台可能還打得開，但備份與遷移會開始出怪問題。

Q4. 用 ZFS 安裝的節點，把 `zfs_arc_max` 寫進 `/etc/modprobe.d/zfs.conf` 之後直接重開機就會生效，不必重建 initramfs。

Q5. `local-lvm` 是 `lvmthin` 型儲存，所以可以拿來存放 ISO 映像檔與容器範本。

Q6. thin pool 的 `Meta%` 只是中繼資料的用量，滿了頂多效能差一點，真正要盯的只有 `Data%`。

Q7. VM 裡面 `df -h` 顯示還有 92 GB 可用，不代表底層 thin pool 還有空間；要看真正的用量必須在主機端用 `lvs`。

Q8. 在 VM 裡刪掉 10 GB 檔案之後，底層 thin pool 的 `Data%` 會自動跟著降下來。

Q9. ZFS 池與 LVM thin pool 的建議水位都是 80%，理由是相同的：配置器需要足夠的自由空間才能正常運作。

Q10. Windows guest 用 VirtIO SCSI 當磁碟時，安裝程式那一頁看不到任何磁碟是正常現象，要在安裝過程中按「載入驅動程式」掛 virtio-win.iso 才會出現。

Q11. `cpu: host` 效能最好，而且 QEMU 會自動遮罩掉對端不支援的指令集，所以線上遷移到別的節點也不會有問題。

Q12. 磁碟快取選 `Write back (unsafe)` 只是多用了主機的 page cache 加速，斷電最多丟掉最後幾秒的資料，資料庫檔案本身不會不一致。

Q13. 連結複製（Linked Clone）出來的 VM 已經是一台獨立的機器，所以範本用完就可以刪掉節省空間。

Q14. cloud-init 的參數改完之後，光是把 VM 重新開機通常不會生效，因為 cloud-init 只在「第一次開機」時完整執行。

Q15. 想把已經建好的特權容器改成非特權，只要把 `/etc/pve/lxc/<VMID>.conf` 裡的 `unprivileged: 0` 改成 `1` 再重啟容器即可。

Q16. 非特權容器在主機端 `ls -l` 看到檔案擁有者是 `100000`，這是 user namespace 的 UID 位移正常運作的結果，不是權限壞掉。

Q17. 容器的 bind mount 目錄會跟著 vzdump 一起被備份起來，所以主機上那份來源資料不必另外備份。

Q18. LXC 容器沒有自己的核心，所以在容器裡 `modprobe` 載入核心模組基本上做不到，要載模組請在主機端載。

Q19. 在 Web 介面把 `vmbr0` 的 IP 改好並按下 OK 之後設定就立刻生效了，不需要再做別的動作。

Q20. PVE 節點的管理 IP 掛在 `vmbr0` 本身、封包送出去時是 untagged，所以交換器 trunk 的 native VLAN 必須就是管理網段所在的那個 VLAN。

Q21. 主機端設了 `bond-mode 802.3ad`、交換器端兩個埠卻只是各自獨立的一般埠，典型症狀是「兩邊設定看起來都正常，但網路時通時不通、SSH 一直斷」。

Q22. 讓 corosync 跟每晚的備份流量走同一條線只是頻寬問題，最多讓備份慢一點，不會影響叢集的穩定。

Q23. vzdump 的 `stop` 模式對 VM 與對 CT 造成的停機時間是一樣的，都等於整個備份的時間。

Q24. VM 裝了 QEMU Guest Agent 之後，snapshot 模式備份會做 `fs-freeze`，所以裡面的 MySQL 就不必再另外做邏輯備份了。

Q25. 備份日誌裡出現 `excluding bind mount point mp0 ('/data') from backup`，就代表那個掛載點沒有被備份進去，這一行每次都要看。

Q26. 備份任務沒有設 `prune-backups` 保留策略時，備份會無限累積，最後把儲存塞爆，而且備份會靜靜地失敗。

Q27. 保留策略同時設了 `keep-last=3` 與 `keep-daily=7` 時，實際保留的份數是兩者取較大的那個，也就是 7 份。

Q28. 四節點叢集的 Quorum 門檻是 3，可容忍的故障節點數跟三節點叢集一樣是 1 台。

Q29. 節點在後台顯示紅色問號、SSH 也連不上時，最快的處置就是先把它重開機，讓它重新加回叢集。

Q30. 失去 Quorum 的節點上，已經在跑的 VM 會被 PVE 自動停掉，以免資料損毀。

Q31. `pvecm expected 1` 是把叢集救回來的標準做法，只要打了之後就能繼續改設定，沒有什麼副作用。

Q32. QDevice 只投票、不跑 VM，但它必須裝在那兩台 PVE 之外的第三台機器上；裝在其中一台 PVE 上是完全沒有意義的。

Q33. `/vms` 上給了某人 `PVEVMAdmin` 且 `propagate=1`，又在 `/vms/999` 給同一個人 `NoAccess`，最後的結果是兩者取聯集，他仍然管得到 999。

Q34. 建立 `privsep=1` 的 API Token 之後，只要使用者本人有權限，Token 就自動擁有同樣的權限。

Q35. API Token 的秘密值只在建立當下顯示一次，關掉視窗就再也看不到，弄丟只能刪掉重建。

Q36. 只是要讓主管「看看狀態」的話，給 `PVEVMUser` 就好，反正這個角色不能改 VM 設定。

Q37. guest 裡 `top` 看到 `st`（steal time）持續高於 5%，代表這台 VM 拿不到它要的 CPU，主機層的 CPU 超配過頭了。

Q38. 記憶體超配過頭的後果只是變慢，主機會靠 swap 撐過去，不至於讓服務中斷。

Q39. 跑資料庫或設了固定 heap 的 Java 應用的 VM 應該設 `balloon: 0`，因為氣球把記憶體抽走會直接打爛 buffer pool 或 JVM heap。

Q40. KSM 把內容相同的記憶體頁合併起來很省記憶體，只要主機 CPU 還有餘裕就應該一律開著。

Q41. VT-x（AMD-V）與 VT-d（AMD-Vi）是同一個 BIOS 選項的兩種叫法，開了一個就等於兩個都開了。

Q42. 一個 IOMMU 群組必須整組交給同一台 VM，不能只挑群組裡的其中一個裝置直通。

Q43. 核心參數 `pcie_acs_override=downstream,multifunction` 會真的把硬體上黏在一起的裝置拆開來隔離，所以是個安全的解法。

Q44. 做了 PCIe 直通的 VM 仍然可以線上遷移，只要目標節點上有同款的卡就行。

Q45. 更新了 `pve-qemu-kvm` 套件之後，正在跑的 VM 仍然使用舊版的 QEMU 程序，必須關機再開機（或遷移到已更新的節點）才會換掉。

Q46. 要讓瀏覽器不再對 PVE 後台跳憑證警告，該換掉的是 `/etc/pve/local/pve-ssl.pem`。

Q47. 啟用 HA 的節點維護模式之後，這個節點上所有的 VM 與 CT 都會被自動搬到其他節點。

Q48. SSH 進節點之後發現 `/etc/pve` 是空的，代表設定檔被誤刪了，應該先從備份還原那些設定檔。

Q49. 「VM 都還在跑，但什麼設定都改不了」這種症狀，九成是 Quorum 掉了，而不是 VM 的設定壞掉。

Q50. 練習環境用 `bridge-ports none` 的內部 bridge，是因為沒有接實體網卡的 bridge 完全隔離，上面的實驗機碰不到辦公網，也不會影響辦公網。

> **Q1. ✗**
> ★★★★★ 這是新裝 PVE 一定會撞到的第一個坑，而且**完全正常**：PVE 預設啟用的是
> 企業版套件庫，你沒有訂閱所以拿到 401。危險的是後果 ——
> **整個 `apt update` 會中止，連 Debian 官方的安全性更新都裝不到**。
> 正確處置是停用 `pve-enterprise.list`（與 `ceph.list`），改加 `pve-no-subscription`。
> → 詳見 [[050-01-03-01-svc-PVE-安裝與初始設定]] 的〈訂閱與套件庫：新手第一個坑〉
>
> **Q2. ✗**
> ★★★★★ **檔案系統是安裝精靈裡唯一無法反悔的決定**，裝完要換就是重灌。
> 判斷準則很簡單：巢狀實驗機、單顆碟、有硬體 RAID 卡 → `ext4`；
> 多顆碟走 HBA／IT mode → ZFS；不確定 → `ext4`（之後還能另外加一個 ZFS 池補上）。
> → 詳見 [[050-01-03-01-svc-PVE-安裝與初始設定]] 的〈安裝精靈裡唯一無法反悔的決定〉
>
> **Q3. ○**
> ★★★★★ `pveproxy` 與 `pve-cluster` 啟動時要把自己的主機名解析成 IP，
> 才知道「我是哪個節點、我 listen 在哪」。改 IP 的正確順序是：
> 改 `interfaces` → **同時改 `/etc/hosts`** → `ifreload -a` →
> `systemctl restart pve-cluster pveproxy pvedaemon`。漏掉第二步是最典型的自殺方式。
> → 詳見 [[050-01-03-01-svc-PVE-安裝與初始設定]] 的〈主機名稱與 `/etc/hosts` 的致命關聯〉
>
> **Q4. ✗**
> ★★★★ ZFS 在 **initramfs 階段**就會載入，只改 `/etc/modprobe.d/` 而沒有
> `update-initramfs -u -k all`，設定根本進不了開機流程。
> 另外兩個常見錯誤：數字單位是 byte（4 GB 要寫 `4294967296`，寫 `4G` 無效），
> 以及不要相信任何文章寫死的百分比，用 `arc_summary` 看你機器上的實際值。
> → 詳見 [[050-01-03-01-svc-PVE-安裝與初始設定]] 的〈ZFS 的記憶體：ARC 上限〉
>
> **Q5. ✗**
> ★★★★ `lvmthin` 是**區塊儲存**，內容類型只有 `images` 與 `rootdir`，
> 放不了 ISO 與範本這種「檔案」。ISO 與範本要放檔案型儲存（`dir`、`nfs`、`cephfs`）。
> 順帶記住另一半：`local`（`dir` 型）預設內容是 `iso,vztmpl,backup`。
> → 詳見 [[050-01-03-02-guide-PVE-儲存設定]] 的〈儲存類型能力矩陣〉
>
> **Q6. ✗**
> ★★★★★ 剛好相反 —— 快照多、VM 多的環境，**`Meta%` 有機會比 `Data%` 先爆**，
> 而 metadata 滿掉造成的損害更難修復。兩個百分比都要看，兩個都以 **80% 當警戒線**。
> 每天要看的那一行是 `lvs -o lv_name,lv_size,data_percent,metadata_percent`。
> → 詳見 [[050-01-03-02-guide-PVE-儲存設定]] 的〈Thin Provisioning：省空間，也可能毀掉一切〉
>
> **Q7. ○**
> ★★★★★ 這個「資訊落差」就是 thin provisioning 最危險的地方：
> 客體看到的是**宣告值**，底層的真實用量它完全不知情。
> thin pool 到 100% 時 VM 寫入直接失敗、檔案系統轉唯讀、資料庫可能損毀，
> 而且**即使事後擴充，已經寫壞的資料也救不回來**。
> → 詳見 [[050-01-03-02-guide-PVE-儲存設定]] 的〈Thin Provisioning：省空間，也可能毀掉一切〉
>
> **Q8. ✗**
> ★★★★ 客體刪檔案只是把檔案系統的中繼資料標成「已刪除」，
> **沒有告訴底層儲存這些區塊可以回收**。要空間真的還回去，discard/TRIM 這條鏈路必須完整：
> 磁碟勾 `Discard` → 匯流排用 `virtio-scsi-single` → 客體裡跑 `fstrim`
> （Ubuntu 有 `fstrim.timer` 每週自動跑）。
> → 詳見 [[050-01-03-02-guide-PVE-儲存設定]] 的〈Thin Provisioning：省空間，也可能毀掉一切〉
>
> **Q9. ○**
> ★★★★ 三個 80%（根分割區、thin pool、ZFS 池）的共同原因是**配置器需要自由空間才能運作**：
> ext4 需要空間避免碎裂、thin pool 需要空間放 metadata 與快照差異、
> ZFS 的 copy-on-write 更是每次寫入都需要新空間。
> 把儲存用到 95% 不是「善用資源」，是在製造故障。
> → 詳見 [[050-01-03-02-guide-PVE-儲存設定]] 的〈空間規劃：三個必須守住的水位〉
>
> **Q10. ○**
> ★★★★★ Windows 安裝程式裡沒有 VirtIO 磁碟驅動，所以它看不到那顆磁碟。
> 建 VM 時就要掛兩個光碟機（Windows ISO + virtio-win.iso），
> 在「你要將 Windows 安裝在何處」那頁按「載入驅動程式」，
> 瀏覽到 `vioscsi\<版本>\amd64\`。裝完進系統後再跑完整安裝程式把網卡、balloon、
> guest agent 一次裝齊。Linux guest 因為核心內建 VirtIO，完全沒有這個問題。
> → 詳見 [[050-01-03-03-guide-PVE-虛擬機管理]] 的〈VirtIO：這章最重要的一件事〉
>
> **Q11. ✗**
> ★★★★★ `cpu: host` 把實體 CPU 的**全部**指令集原封不動暴露給客體，客體的程式會照著
> 這些能力最佳化自己。遷到指令集較少的節點，執行中的程式碼會碰到不存在的指令，
> 結果是 `host doesn't support requested feature: ...` 或客體當場崩潰。
> 叢集裡的建議值是 **`x86-64-v2-AES`**，並以最舊那台節點的能力為準。
> → 詳見 [[050-01-03-03-guide-PVE-虛擬機管理]] 的〈CPU type：效能與遷移的取捨〉
>
> **Q12. ✗**
> ★★★★★ `unsafe` 的意思是**忽略客體發出的 flush 指令**。資料庫以為「我已經確認寫到磁碟了」，
> 其實資料還在主機記憶體裡。主機一斷電，那些資料就消失，而**資料庫完全不知道**——
> 造成的是檔案不一致，比單純丟資料更難處理。唯一合理用途是大量建置測試機時暫時加速，
> 裝完立刻改回 `Default (No cache)`。
> → 詳見 [[050-01-03-03-guide-PVE-虛擬機管理]] 的〈磁碟快取模式〉
>
> **Q13. ✗**
> ★★★★★ 連結複製只存「與範本的差異」，**共用範本那份唯讀基礎磁碟**。
> 範本磁碟損毀 = 底下所有子 VM 一起死，它是二十台機器的單點故障。
> PVE 會擋住「刪除還有連結子代的範本」，但不要依賴這個保護。

> `/var/lib/pve-cluster/config.db`。目錄空空如也代表 **`pve-cluster` 服務沒起來**，
> 設定檔並沒有不見。先查 `systemctl status pve-cluster`，
> 最常見的原因是 `/etc/hosts` 少了主機名那行或 IP 對不上。
> **絕對不要直接去編輯 `config.db`**，那會毀掉整個叢集設定且沒有還原路徑。
> → 詳見 [[050-01-03-12-guide-PVE-故障排除]] 的〈`/etc/pve` 不是普通目錄〉
>
> **Q49. ○**
> ★★★★★ 這正是「分層模型：由下往上排查」要救的誤判。
> 症狀出現在來賓層，真正的問題在叢集層 —— `pvecm status` 顯示 `Quorate: No`，
> `/etc/pve` 唯讀，所以什麼設定都寫不進去。跑去重建 VM 只會越弄越亂。
> → 詳見 [[050-01-03-12-guide-PVE-故障排除]] 的〈PVE 的分層模型：排查一律由下往上〉
>
> **Q50. ○**
> ★★★★★ 沒有可管理交換器時，`bridge-ports none` 的內部 bridge 是**最安全也最簡單**
> 的實驗網做法。這件事之所以重要，是因為練習環境裡你會開一堆沒密碼沒更新的機器、
> 練攻擊與弱點掃描、亂設防火牆、甚至自己開 DHCP 伺服器 ——
> 任何一件跑到正式網段上都是資安事件。

Q90. 一座三節點叢集要從 7.x 升到 8.x。下列哪一項是**不可省略**的前置作業？
(A) 把所有 VM 的 CPU type 改成 `host` (B) 先確認有**可還原**的完整備份（含 `/etc/pve` 與節點網路設定），更新到當前大版本的最新小版本，並把官方升級前檢查工具的 FAIL 全部清乾淨 (C) 先把叢集拆掉，升完再重建 (D) 先把所有 VM 都關機一週觀察

Q91. 叢集升級期間會有一段混版狀態（部分節點已升級、部分還沒）。這段期間下列何者最該避免？
(A) 從舊版節點遷移 VM 到新版節點 (B) 觀察服務是否正常 (C) 建立新的 VM／CT、改叢集設定、加減節點、動 Ceph 的 crush map (D) 查看 `pveversion -v` 比對版本

Q92. 使用者回報 PVE 後台的憑證過期、瀏覽器擋住。你要換上機關 CA 簽發的憑證，該動哪一組檔案？
(A) `/etc/pve/local/pve-ssl.pem` 與 `pve-ssl.key` (B) `/etc/pve/local/pveproxy-ssl.pem` 與 `pveproxy-ssl.key`（或用 `pvenode cert set`） (C) `/etc/pve/pve-root-ca.pem` (D) `/etc/ssl/certs/ssl-cert-snakeoil.pem`

Q93. 機關的一台正式 PVE 主機，套件庫該怎麼選？
(A) `pvetest`，可以最早拿到修補 (B) 同時啟用 enterprise 與 no-subscription，哪個有就用哪個 (C) 有預算就買訂閱用 `pve-enterprise`（測試最充分，且含原廠支援）；沒訂閱就用 `pve-no-subscription`，並接受它測試較少 (D) 全部停用，只用 Debian 官方套件庫

Q94. 「VM 開不起來，報無法寫入設定檔」。依 PVE 的分層排查模型，正確路徑是？
(A) 懷疑 VM 設定壞了，先重建 VM (B) 從下往上查：儲存 → 叢集（`pvecm status` 看 `Quorate`）→ 服務，先確認 `/etc/pve` 是不是唯讀 (C) 先把節點重開機，重開後再看 (D) 先重灌 `qemu-server` 套件

Q95. 備份中斷後 VM 卡在 `VM is locked (backup)`。正確處置是？
(A) 直接 `qm unlock <id>`，鎖本來就是殘留的 (B) `kill -9` 掉 QEMU 程序再開機 (C) **先確認備份真的沒有在跑**（看任務日誌與 `ps`），確認之後才 `qm unlock <id>` (D) 重開節點，鎖會自己消失

Q96. 儲存滿了導致服務停擺，現場壓力很大。下列哪一個動作最該避免？
(A) 先看 `lvs` / `zpool list` / `df -h` 確認是哪一層滿了 (B) 為了立刻空出空間，直接刪掉備份儲存上的舊備份檔 (C) 先停止會繼續寫入的服務 (D) 刪掉不再需要的快照

Q97. 事故現場什麼都還沒查，主管一直催「先重開機看看」。最正確的態度是？
(A) 照做，恢復服務最重要 (B) 重開機會沖掉現場證據、根因就查不到了；先跑檢傷腳本把輸出留檔（`pvecm status`、`journalctl -b -p err`、`/var/log/pve/tasks/` 等），再決定處置 (C) 先把 `pve-firewall` 關掉排除防火牆因素 (D) 先把所有 PVE 服務一次 `systemctl restart`

Q98. 一台 32 GB 記憶體的 PVE 要盡量多開練習機。最有效的配比是？
(A) 全部用 VM，隔離最完整 (B) 全部用 LXC，最省資源 (C) 約八成 LXC、兩成 VM；只有在必須有自己的核心時（Windows、Docker、練核心參數與模組、資安攻防）才開 VM (D) 全部用 VM 但每台只給 512 MB

Q99. 練習環境要從一個 Ubuntu cloud-init 範本快速開出六台機器。關於複製方式，下列敘述何者正確？
(A) 用完整複製，因為練習環境更需要獨立性 (B) 用連結複製：秒級建立、超省空間，**代價是範本不能刪也不能改**，而且需要底層儲存支援快照 (C) 連結複製與完整複製佔用的空間其實一樣 (D) 連結複製之後範本可以安全刪除，子機會自動轉成完整複製

Q100. 練習環境要跟正式環境隔離。下列哪一個理由最直接？
(A) 練習機的效能會拖慢正式機 (B) 練習時會開沒密碼沒更新的機器、跑弱點掃描、亂設防火牆，甚至自己開 DHCP 伺服器把整個辦公室的電腦搶走 —— 任何一件跑到正式網段都是資安事件 (C) 練習機的 IP 會跟正式機重複 (D) PVE 不支援同時管理兩種環境

>
> **Q94. (B)**
> ★★★★★ 這是分層模型的招牌例子：症狀出現在來賓層（⑥），
> 真正的原因在叢集層（④）—— `Quorate: No` → `/etc/pve` 唯讀 → 當然寫不進去。
> **下層壞了，上層一定會出怪症狀，所以永遠從下往上排除。**
> (A) 錯：重建 VM 會越弄越亂，而且根本沒碰到真因。
> (C) 錯：重開機沖掉證據，Quorum 問題重開也不會好。
> (D) 錯：套件沒壞，這是狀態問題不是安裝問題。
> → 詳見 [[050-01-03-12-guide-PVE-故障排除]] 的〈PVE 的分層模型：排查一律由下往上〉
>
> **Q95. (C)**
> ★★★★★ `qm unlock` 本身不難，難在**時機**：備份還在跑時解鎖，會造成備份檔損毀
> 與 VM 磁碟不一致 —— 這是「千萬不要做的事」清單上的一條。
> 先看 `/var/log/pve/tasks/` 的任務日誌與行程狀態確認備份真的停了，再解鎖。
> (A) 錯：少了「先確認」這個關鍵前提。
> (B) 錯：`kill -9` QEMU 等同拔電源，可能造成 guest 檔案系統損毀。
> (D) 錯：重開節點影響所有其他來賓，而且不保證鎖會乾淨消失。
> → 詳見 [[050-01-03-12-guide-PVE-故障排除]] 的〈千萬不要做的事〉
>
> **Q96. (B)**
> ★★★★★ 「儲存滿了就急著刪備份檔」是清單上明列的禁忌 ——
> **你可能刪掉的正是唯一能救回資料的那一份**。
> 空間要從快照、暫存、日誌、不再需要的磁碟去找，備份是最後才碰的。
> (A)(C)(D) 都是正確步驟：先確認是哪一層滿了、先止血（停止繼續寫入）、再刪快照。
> ★★★★ 真正的解法是事前設好 `prune-backups` 與 75%／85% 的告警。
> → 詳見 [[050-01-03-12-guide-PVE-故障排除]] 的〈症狀 C：儲存滿了〉
>
> **Q97. (B)**
> ★★★★★ 事故處理有兩個並行的目標：恢復服務與查出根因。
> 重開機常常能恢復服務，但它會**沖掉現場證據**，於是同一件事下個月會再發生一次。
> 正確做法是先把檢傷輸出留檔（成本只有幾十秒），再談處置。
> (A) 錯：不是不能重開，是不能「什麼都沒留就重開」。
> (C) 錯：急救時關掉安全機制若沒有記錄與復原，會變成長期暴露。
> (D) 錯：一次重啟所有 PVE 服務只會加大不確定性，更難判斷。
> → 詳見 [[050-01-03-12-guide-PVE-故障排除]] 的〈蒐證優先〉
>
> **Q98. (C)**
> ★★★★★ 差距很大：一台 idle 的 Ubuntu VM 約 400～600 MB、一個 LXC 約 30～80 MB；
> 開機 20～40 秒 vs 1～3 秒。同一台 32 GB 主機，全 VM 大約 8～12 台，混用可到 25～40 台。
> (A) 錯：浪費掉大部分容量。
> (B) 錯：Windows、Docker、核心參數練習、資安攻防這些一定要 VM。
> (D) 錯：把記憶體壓到 512 MB 只會讓每台都不堪用，而且記憶體超配會招來 OOM。
> → 詳見 [[050-01-03-13-guide-PVE-建立練習環境]] 的〈VM vs LXC：省資源的關鍵決策〉
>
> **Q99. (B)**
> ★★★★★ 練習環境的預設做法就是連結複製：秒級建立、只佔差異空間。
> 代價要記清楚 —— **範本不能刪、不能改，範本壞了所有子機一起完蛋**，
> 而且底層儲存必須支援快照（LVM-thin、ZFS、qcow2 目錄）。
> (A) 錯：練習機是可以重建的，用不著付出 N 份空間的代價。
> (C) 錯：空間差距正是連結複製的主要價值。
> (D) 錯：沒有「自動轉成完整複製」這回事，範本一刪子機就毀了。
> ★★★★ 正式環境則相反：用完整複製換獨立性。
> → 詳見 [[050-01-03-13-guide-PVE-建立練習環境]] 的〈連結複製 vs 完整複製〉
>
> **Q100. (B)**
> ★★★★★ 練習環境的本質就是「**故意做危險的事**」。這些行為任何一件跑到正式網段上
> 都是資安事件，尤其自己開 DHCP 伺服器會把整個辦公室的電腦搶走。
> 沒有可管理交換器時，用 `bridge-ports none` 的內部 bridge 就能達成完全隔離。
> (A) 錯：效能是次要問題，資安才是主因。
> (C) 錯：IP 衝突只是眾多後果之一，不是最根本的理由。
> (D) 錯：PVE 完全可以同時管理多種環境，問題在網路隔離不是管理能力。
> → 詳見 [[050-01-03-13-guide-PVE-建立練習環境]] 的〈實驗網段規劃〉
