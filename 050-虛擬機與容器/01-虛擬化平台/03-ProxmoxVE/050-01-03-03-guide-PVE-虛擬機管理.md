## 觀念說明

### ★★★★ 一台 VM 就是一個設定檔

PVE 的 VM 沒有什麼神秘的地方。**一台 VM = 一個設定檔 + 一個或多個磁碟**。

```bash
qm config 100
```

```text
agent: 1
boot: order=scsi0;ide2;net0
cores: 2
cpu: x86-64-v2-AES
ide2: backup-store:iso/ubuntu-24.04.1-live-server-amd64.iso,media=cdrom,size=2643756K
memory: 2048
meta: creation-qemu=8.1.5,ctime=1756789012
name: web01
net0: virtio=BC:24:11:3A:5F:82,bridge=vmbr0,firewall=1
numa: 0
ostype: l26
scsi0: vm-store:vm-100-disk-0,discard=on,iothread=1,size=32G,ssd=1
scsihw: virtio-scsi-single
smbios1: uuid=8f3c1a24-7b91-4e05-9d62-1a5c3e8f7042
sockets: 1
vmgenid: c4a91f38-2e57-4b6d-8a03-9f2e1d7c5b40
```

這個檔實際存在：

```bash
ls -l /etc/pve/qemu-server/
```

```text
-rw-r----- 1 root www-data 512 Sep  2 15:41 100.conf
```

> [!note] ★★★ 這件事的三個實用推論
> 1. **備份 VM 設定 = 複製這個檔**（磁碟另外備份）
> 2. **後台上每一個選項，都對應到這個檔裡的一行**。看不懂後台某個選項時，
>    改一下再 `qm config` 看差在哪，是最快的學習法
> 3. 這個檔在 `/etc/pve`（pmxcfs），**叢集裡會自動同步**，
>    所以遷移 VM 時設定不用手動搬

### ★★★★★ VirtIO：這章最重要的一件事

先講結論：**能用 VirtIO 的地方都要用 VirtIO**。這是效能差距最大的單一決定。

#### ★★★★ 為什麼

虛擬化裡，客體作業系統要存取硬體有兩條路：

| 方式 | 原理 | 效能 |
| --- | --- | --- |
| **模擬（Emulation）** ★★ | QEMU 假裝自己是一張真的 Intel E1000 網卡／IDE 控制器，客體用原本的驅動去操作，QEMU 一個暫存器一個暫存器地翻譯 | **很差**，每次 I/O 都要大量 VM exit |
| **半虛擬化（Paravirtual, VirtIO）** ★★★★★ | 客體裝一個「知道自己在虛擬機裡」的驅動，透過共享記憶體的環形佇列直接跟 hypervisor 溝通 | **好非常多**，一次批次處理多筆 I/O |

模擬的好處是**不用裝驅動**（任何作業系統都認得 E1000 和 IDE），
代價是效能。VirtIO 的代價是**客體要有驅動**。

原理的完整說明見 [[050-01-01-02-guide-虛擬化-虛擬化底層技術]]。

#### ★★★★★ 三種 VirtIO 裝置

| 裝置 | PVE 上的選項 | 作用 | Linux | Windows |
| --- | --- | --- | --- | --- |
| **磁碟** ★★★★★ | SCSI Controller 選 `VirtIO SCSI single` | 磁碟 I/O | 核心內建 | **要裝驅動** |
| **網卡** ★★★★★ | Network Model 選 `VirtIO (paravirtualized)` | 網路吞吐 | 核心內建 | **要裝驅動** |
| **Balloon** ★★★★ | Memory 勾 `Ballooning Device` | 動態調整記憶體 | 核心內建 | **要裝驅動** |

> [!danger] ★★★★★ Windows guest 的 VirtIO 磁碟驅動必須在**安裝過程中**載入
> 這是 Windows 安裝最經典的卡關點：
>
> 你建了一台 Windows VM，磁碟用 VirtIO SCSI，掛上 Windows ISO 開機，
> 走到「你要將 Windows 安裝在何處？」那一頁，**畫面上一顆磁碟都沒有**。
>
> 原因是 Windows 安裝程式裡沒有 VirtIO 的磁碟驅動，它看不到那顆磁碟。
>
> **解法**（在建立 VM 時就要準備好）：
> 1. 下載 **virtio-win.iso**（Fedora 專案提供的 Windows VirtIO 驅動集合）
> 2. 給 VM **掛兩個光碟機**：一個 Windows ISO，一個 virtio-win.iso
> 3. 安裝到「選擇磁碟」那一頁時，按 **`載入驅動程式 (Load driver)`**
> 4. 瀏覽到 virtio-win 光碟的 `vioscsi\<你的 Windows 版本>\amd64\` 資料夾
> 5. 載入後磁碟就會出現，繼續安裝
>
> 裝完進系統後，**再執行 virtio-win 光碟裡的完整安裝程式**，
> 把網卡、balloon、guest agent 一次裝齊。
>
> Windows guest 的完整流程見 [[030-01-01-02-svc-WinServer-WindowsServer安裝與初始設定]]。

> [!tip] ★★★ Linux guest 完全不用擔心這件事
> 主流 Linux 發行版（Ubuntu、Debian、RHEL 系）的核心**內建 VirtIO 驅動**，
> 而且 initramfs 裡也有，所以裝機時就看得到 VirtIO 磁碟，開箱即用。
> 這也是本手冊的 Linux 主線在 PVE 上特別順的原因。

#### ★★★ 磁碟匯流排怎麼選

建立磁碟時 Bus/Device 有四個選項：

| 匯流排 | 說明 | 建議 |
| --- | --- | --- |
| `IDE` ★ | 模擬的老古董，最多 4 個裝置 | **只給光碟機用** |
| `SATA` ★★ | 模擬的 AHCI | Windows 安裝時的「不用裝驅動」逃生方案 |
| `VirtIO Block` ★★★ | 舊的 VirtIO 磁碟介面（`vda`） | 可用，但功能比 SCSI 少 |
| **`SCSI` + `VirtIO SCSI single`** ★★★★★ | 現在的建議做法（`sda`） | **預設就選這個** |

> [!note] ★★★★ 為什麼是 `VirtIO SCSI single` 而不是 `VirtIO SCSI`
> `single` 代表**每一顆磁碟配一個獨立的 SCSI 控制器**。
> 好處是可以搭配 **`iothread`**——每顆磁碟有自己的 I/O 執行緒，
> 不會互相排隊。多顆磁碟的 VM 差異明顯。
>
> PVE 新版本建立 VM 時預設就是 `VirtIO SCSI single`，沿用即可。

### ★★★★★ CPU type：效能與遷移的取捨

這是另一個容易做錯、而且**做錯要關機才能改**的選項。

| CPU type | 客體看到什麼 | 效能 | 能遷移到不同世代的 CPU 嗎 |
| --- | --- | --- | --- |
| `kvm64` ★★ | 一顆功能很陽春的 x86-64 | **最差** | **可以**，相容性最好 |
| `x86-64-v2-AES` ★★★★ | 含 SSE4.2、AES-NI 等現代指令集 | 好 | **可以**（在支援 v2 的 CPU 之間） |
| `host` ★★★★★ | **實體 CPU 的全部功能** | **最好** | **不行**（除非兩端 CPU 完全相同） |

> [!danger] ★★★★★ 選了 `host` 的代價：遷移會失敗
> `cpu: host` 把實體 CPU 的所有指令集（AVX-512、特定的加密指令等）
> 原封不動地暴露給客體。客體作業系統與應用程式會**依照這些能力最佳化自己**。
>
> 現在把這台 VM 線上遷移到另一個節點——如果對端 CPU 比較舊、沒有其中某個指令集，
> 客體裡正在執行的程式碼會執行到一個**不存在的指令**，結果是：
>
> ```text
> kvm: warning: host doesn't support requested feature: CPUID.07H:EBX.avx512f
> ```
>
> 或直接讓客體**當場崩潰**。這種故障很難事後歸因。
>
> **判斷準則**：
> | 情境 | 選什麼 |
> | --- | --- |
> | 單機、不會遷移 ★★★★ | `host`（榨出最好效能） |
> | 叢集、節點 CPU 型號**完全相同** ★★★★ | `host` 可以 |
> | 叢集、節點 CPU 型號混雜 ★★★★★ | **`x86-64-v2-AES`** 或更保守的等級 |
> | 老舊硬體混用 ★★★ | `kvm64` |
>
> 叢集裡最保險的做法是：**以最舊的那台節點的 CPU 能力為準**。

> [!warning] ★★★ Windows 客體特別注意 `numa` 與 `sockets`
> 授權常以「實體插槽數」計價。給一台 VM 設 `sockets: 4, cores: 1`
> 與 `sockets: 1, cores: 4` 在效能上差不多，但**授權成本可能差四倍**。
> **一律用 1 個 socket、多個 core**，除非你真的需要 NUMA 拓撲。

### ★★★★ 磁碟快取模式

建立磁碟時有一個 `Cache` 下拉選單，五個選項。這牽涉到**斷電時資料會不會壞**。

| 模式 | 主機 page cache | 客體的 flush 有效嗎 | 斷電風險 | 效能 |
| --- | --- | --- | --- | --- |
| `Default (No cache)` ★★★★★ | 不用 | **有效** | **安全** | 好 |
| `Direct sync` ★★★ | 不用 | 每次寫都直接落碟 | **最安全** | 差 |
| `Write through` ★★★ | 用（只讀） | 每次寫都落碟 | 安全 | 讀好寫差 |
| `Write back` ★★★★ | 用（讀寫） | **有效** | 可接受 | **很好** |
| `Write back (unsafe)` ★★★★★ | 用（讀寫） | **被忽略** | **極危險** | 最好 |

> [!danger] ★★★★★ `Write back (unsafe)` 只能用在「壞掉可以重來」的機器
> 這個模式會**忽略客體發出的 flush 指令**。也就是說，資料庫以為
> 「我已經確認資料寫到磁碟了」，其實還在主機的記憶體裡。
> **主機一斷電，那些資料就消失，而資料庫完全不知道**——
> 這會造成資料庫檔案不一致，比單純丟失資料更難處理。
>
> 唯一合理的用途：**大量建置測試機時暫時開著加速安裝，裝完立刻改回來**。
> 正式環境用到它就是事故。

> [!tip] ★★★★ 不確定就用 `Default (No cache)`
> 這是 PVE 的預設值，也是絕大多數情況的正解：
> 主機不做額外快取（避免資料在主機記憶體裡「假裝已寫入」），
> 客體的 flush 語意被正確傳遞到實體磁碟。
> 效能不是最好，但**行為是可預期的**，這對正式環境更重要。

### ★★★★ 磁碟的三個核取方塊

| 選項 | 作用 | 建議 |
| --- | --- | --- |
| **`Discard`** ★★★★★ | 把客體的 TRIM/UNMAP 傳到底層儲存，**刪檔案能真的還空間** | **thin 儲存上一定要勾** |
| **`SSD emulation`** ★★★★ | 讓客體以為這是 SSD（回報 rotational=0） | 底層是 SSD 時勾；也是 `Discard` 生效的常見前提 |
| **`IO thread`** ★★★ | 這顆磁碟用獨立的 I/O 執行緒 | 搭配 `VirtIO SCSI single` 使用，多磁碟時有感 |

Discard 的完整說明與實測見 [[050-01-03-02-guide-PVE-儲存設定]]。

### ★★★★ QEMU Guest Agent：不裝就少一半功能

`qemu-guest-agent` 是**裝在客體裡面**的一個小服務，透過 virtio-serial
跟 PVE 溝通。它不是驅動，是一個「代理人」。

| 沒裝 agent | 裝了 agent |
| --- | --- |
| 後台看不到 VM 的 IP ★★★ | 摘要頁直接顯示所有網卡的 IP |
| `Shutdown` 靠 ACPI 訊號，客體可能忽略 ★★★★ | **正常呼叫客體的關機流程** |
| 備份時無法凍結檔案系統，快照可能不一致 ★★★★★ | **fsfreeze**，資料庫備份一致性大幅提升 |
| 無法從主機端執行客體指令 ★★ | `qm guest exec` 可用 |
| 無法從主機重設客體密碼 ★★ | `qm guest passwd` 可用 |

**兩邊都要做**：★★★★★

```bash
# 1) PVE 這邊打開開關
qm set 100 --agent enabled=1,fstrim_cloned_disks=1
```

```text
update VM 100: -agent enabled=1,fstrim_cloned_disks=1
```

```bash
# 2) 客體裡面安裝服務（Ubuntu/Debian）
sudo apt install -y qemu-guest-agent
sudo systemctl enable --now qemu-guest-agent
systemctl is-active qemu-guest-agent
```

```text
active
```

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> ```bash
> sudo dnf install -y qemu-guest-agent
> sudo systemctl enable --now qemu-guest-agent
> ```
> 套件名稱與服務名稱都一樣。RHEL 系的雲端映像通常已經預裝。

> [!warning] ★★★★ 只做一半的兩種症狀
> | 只做了哪一半 | 症狀 |
> | --- | --- |
> | PVE 開了 `agent: 1`，客體沒裝 ★★★★ | **關機／備份會卡住等逾時**（PVE 一直等 agent 回應），後台顯示 `QEMU guest agent is not running` |
> | 客體裝了，PVE 沒開 ★★★ | 完全沒作用，agent 在客體裡空轉 |
>
> 第一種特別討厭：**開了開關卻沒裝 agent，反而比兩邊都沒做更糟**，
> 因為關機動作會卡到逾時才 fallback。

驗證：

```bash
qm agent 100 ping
```

（成功時沒有輸出。有問題時會報 `QEMU guest agent is not running`。）

```bash
qm guest cmd 100 network-get-interfaces
```

### ★★★ BIOS、Machine Type 與開機順序

| 選項 | 值 | 說明 |
| --- | --- | --- |
| **BIOS** ★★★★ | `SeaBIOS`（傳統）／ `OVMF (UEFI)` | UEFI **需要額外一顆 EFI Disk** 存 NVRAM |
| **Machine** ★★★ | `i440fx`（預設）／ `q35` | `q35` 提供 PCIe，**PCI 直通要用它** |
| **Boot Order** ★★★★ | `order=scsi0;ide2;net0` | 由左至右嘗試 |

> [!warning] ★★★★ BIOS 型別跟 Workstation 一樣——裝完系統就不能改
> 選了 `OVMF (UEFI)` 裝好 Linux，之後改成 `SeaBIOS`，
> 會得到 `No bootable device`，因為開機載入器在 ESP 分割區裡，
> BIOS 模式根本不去讀那裡。**要改就是重灌。**

> [!tip] ★★★ 選 UEFI 時別忘了 EFI Disk
> 後台選 `OVMF (UEFI)` 時會自動提示你加一顆 EFI Disk（很小，幾 MB）。
> 用指令建立時要自己加：
> ```bash
> qm set 100 --efidisk0 vm-store:0,efitype=4m,pre-enrolled-keys=0
> ```
> `pre-enrolled-keys=0` 代表**不預載 Secure Boot 金鑰**，
> Linux 客體用這個比較省事。

開機順序的實務重點：★★★★

```bash
# 裝系統時：光碟優先
qm set 100 --boot order=ide2;scsi0

# 裝完後：改成硬碟優先，避免每次開機又進安裝程式
qm set 100 --boot order=scsi0;ide2;net0
```

> [!danger] ★★★★ 忘記把光碟從開機順序拿掉，是「重開機後系統不見了」的常見錯覺
> 使用者回報「伺服器重開機之後變成安裝畫面，資料是不是沒了」——
> 資料好好的，只是又從 ISO 開機了。
> **裝完系統的收尾動作：把 ISO 退掉（`--ide2 none,media=cdrom`）並調整開機順序。**

### ★★★★ 記憶體與 Ballooning

| 欄位 | 意義 |
| --- | --- |
| `Memory` ★★★★ | 最大記憶體 |
| `Minimum memory` ★★★★ | 啟用 balloon 後的下限 |
| `Ballooning Device` ★★★ | 是否啟用 balloon 驅動 |

**Ballooning 的原理**：客體裡的 balloon 驅動會「膨脹」佔用一塊記憶體，
然後告訴 hypervisor「這塊我不用了，你拿去給別人」。主機記憶體吃緊時，
PVE 會叫各個 VM 的 balloon 膨脹，把記憶體回收。

```bash
# max 4096 MB，最低 2048 MB
qm set 100 --memory 4096 --balloon 2048
```

> [!warning] ★★★★ Ballooning 的三個限制
> 1. **`balloon` 設成 0 表示關閉 ballooning**，VM 會固定佔用 `memory` 的量
> 2. **客體要有 balloon 驅動**。Linux 內建；**Windows 要裝 virtio-win 裡的 Balloon 驅動**，
>    而且要讓 `BLNSVR` 服務跑起來，否則後台看到的記憶體用量會是錯的
> 3. 資料庫 VM **不建議開 ballooning**——記憶體被抽走會讓 buffer pool 縮水，
>    效能斷崖式下降，而且很難察覺 ★★★★

### ★★★★ 範本、完整複製與連結複製

| 概念 | 說明 |
| --- | --- |
| **範本（Template）** ★★★★ | 一台被「凍結」的 VM，**不能開機、不能改設定**，只能拿來複製 |
| **完整複製（Full Clone）** ★★★★ | 把磁碟完整複製一份，新 VM 與來源**完全獨立** |
| **連結複製（Linked Clone）** ★★★★★ | 只記錄「與範本的差異」，共用範本的基礎磁碟 |

```text
   完整複製                        連結複製
   ┌─────────┐                    ┌─────────┐
   │ 範本磁碟 │                    │ 範本磁碟 │ ← 唯讀基礎（不能刪！）
   │  32 GB  │                    │  32 GB  │
   └─────────┘                    └────┬────┘
        │ 複製全部                      │ 共用
        ▼                          ┌────┴────┬────────┐
   ┌─────────┐                     ▼         ▼        ▼
   │ 新 VM   │                  ┌─────┐  ┌─────┐  ┌─────┐
   │  32 GB  │  ← 佔 32 GB      │差異  │  │差異  │  │差異  │
   └─────────┘                  │0.5GB│  │0.5GB│  │0.5GB│
                                └─────┘  └─────┘  └─────┘
```

| | 完整複製 | 連結複製 |
| --- | --- | --- |
| 空間 ★★★★★ | 每台佔完整容量 | **每台只佔差異** |
| 建立速度 ★★★★ | 慢（要複製 GB 級資料） | **秒級** |
| 效能 ★★★ | 正常 | 略低（讀取要走兩層） |
| 範本能不能刪 ★★★★★ | 可以 | **絕對不行**，刪了所有子 VM 全毀 |
| 儲存需求 ★★★★★ | 任何 | **底層必須支援快照**（qcow2 / lvmthin / zfs / rbd） |
| 適合 | 正式環境、長期存在的機器 | **實驗環境、大量短命的測試機** |

> [!danger] ★★★★★ 連結複製的範本是「單點故障」
> 一個範本底下掛了二十台連結複製的 VM，**那個範本的磁碟就是這二十台的命脈**。
> 範本磁碟損毀 = 二十台一起死。
>
> 所以：
> - 連結複製**只用在可以重建的實驗／測試機**
> - 正式環境用**完整複製**，多花的空間換來的是獨立性
> - PVE 會擋住「刪除還有連結複製子代的範本」，但不要依賴這個保護

> [!warning] ★★★★ LVM（thick）與 iSCSI 上做不了連結複製
> 因為那兩種儲存不支援快照。後台的 `Mode` 下拉會只剩 `Full Clone`。
> 見 [[050-01-03-02-guide-PVE-儲存設定]] 的能力矩陣。

### ★★★★★ cloud-init：範本自動化的關鍵

有了範本之後，還有一個問題沒解決：**複製出來的十台機器，主機名稱、IP、
SSH 金鑰全部一模一樣**。你還是得一台一台開主控台去改。

**cloud-init 就是解決這件事的標準機制**。

```text
   1. 你在 PVE 上設定 VM 的 cloud-init 參數
      （主機名、IP、使用者、SSH 公鑰）
                    ↓
   2. PVE 把這些參數產生成一個小的 ISO，掛給 VM
                    ↓
   3. VM 開機，客體裡的 cloud-init 服務讀取那個 ISO
                    ↓
   4. cloud-init 自動設好主機名、網路、使用者、金鑰
                    ↓
   5. 開機完成，直接 SSH 進得去。全程沒開過主控台
```

| 名詞 | 意義 |
| --- | --- |
| **cloud image** ★★★★ | 發行版官方提供的、**預裝 cloud-init 的**磁碟映像（`.img`），沒有安裝程式 |
| **CloudInit Drive** ★★★★ | PVE 產生的參數 ISO，在 VM 硬體清單裡是一個 CD-ROM |
| **`citype`** ★★★ | 參數格式。Linux 用 `nocloud`，Windows 用 `configdrive2` |

> [!warning] ★★★★★ cloud-init 只在「第一次開機」時完整執行
> cloud-init 會在客體裡留下一個 instance-id 的紀錄。
> 第二次開機時它發現 instance-id 沒變，就**跳過大部分設定**。
>
> 這造成一個常見困惑：「我改了 cloud-init 的 IP，重開機卻沒生效」。
> 原因就是這個。
>
> 正確做法有兩種：
> 1. **改完 cloud-init 參數後重建 cloud-init drive**（PVE 在你改參數時通常會處理）
> 2. 客體裡執行 `sudo cloud-init clean --logs` 再重開機（**會重跑整個流程**）
>
> 最乾淨的做法：**cloud-init 的參數在複製出新 VM 之後、第一次開機之前設定好**。

### ★★★★ 用指令建立同一台 VM

理解 `qm` 對自動化很重要。上面那一整套等同於：

```bash
  --ostype l26 \
```

## 進階應用

### ★★★★ 從 VM 做成範本

範本製作的流程有一個關鍵前置：**清理身分痕跡**。

```bash
# 在要當範本的 VM 裡執行（VM 內）
# 1) 更新到最新
sudo apt update && sudo apt full-upgrade -y

# 2) 裝好必備套件
sudo apt install -y qemu-guest-agent cloud-init
sudo systemctl enable qemu-guest-agent

# 3) 清掉 SSH host key（每台機器必須不同）★★★★★
sudo rm -f /etc/ssh/ssh_host_*

# 4) 清掉 machine-id（重複會導致 DHCP 搶 IP）★★★★★
sudo truncate -s 0 /etc/machine-id
sudo rm -f /var/lib/dbus/machine-id
sudo ln -s /etc/machine-id /var/lib/dbus/machine-id

# 5) 清 cloud-init 狀態，讓下次開機重跑
sudo cloud-init clean --logs --seed

# 6) 清掉歷史與暫存
sudo apt clean
sudo rm -f /var/log/*.log
history -c
sudo shutdown -h now
```

> [!danger] ★★★★★ 沒清 machine-id 與 SSH host key 的後果
> | 沒清什麼 | 症狀 |
> | --- | --- |
> | `machine-id` ★★★★★ | 所有複製出來的機器有相同的 DHCP client identifier，**互相搶同一個 IP**，網路時通時不通，極難查 |
> | SSH host key ★★★★★ | 所有機器的 SSH 指紋一模一樣，**中間人攻擊的偵測機制完全失效**；SSH 客戶端也會因為 `known_hosts` 衝突而拒絕連線 |
> | cloud-init 狀態 ★★★★ | 複製出來的機器認為自己「已經初始化過」，**cloud-init 不會重跑**，主機名與 IP 都不會改 |

轉成範本（PVE 端）：

```bash
qm template 900
```

轉完之後：

```bash
qm list
```

```text
      VMID NAME                 STATUS     MEM(MB)    BOOTDISK(GB) PID
       900 ubuntu-2404-tmpl     stopped    2048       32.00        0
```

在後台，這台的圖示會變成一個不同的符號，**`Start` 按鈕會消失**。

> [!danger] ★★★★★ `qm template` 是不可逆的
> 沒有 `qm untemplate` 這種指令。轉成範本之後：
> - 不能開機
> - 不能改硬體設定
> - 磁碟變成唯讀的基礎映像
>
> 想「改範本」的正確做法是：**從範本完整複製一台出來 → 改 → 再轉成新範本**。
> 所以**轉範本前一定要確認裡面該裝的都裝了**。

### ★★★★★ cloud-init 完整設定

這是本篇的重頭戲。先看有哪些參數：

| 參數 | 作用 | 範例 |
| --- | --- | --- |
| `--ciuser` ★★★★ | 建立的使用者名稱 | `sysadmin` |
| `--cipassword` ★★★ | 該使用者的密碼（**會存在設定檔裡**） | — |
| `--sshkeys` ★★★★★ | **SSH 公鑰檔案路徑** | `/root/.ssh/id_ed25519.pub` |
| `--ipconfig0` ★★★★★ | 第一張網卡的 IP 設定 | `ip=192.168.1.101/24,gw=192.168.1.1` 或 `ip=dhcp` |
| `--nameserver` ★★★ | DNS 伺服器 | `192.168.1.1` |
| `--searchdomain` ★★★ | 搜尋網域 | `lab.local` |
| `--citype` ★★★ | 參數格式 | `nocloud`（Linux）／`configdrive2`（Windows） |
| `--cicustom` ★★★★ | 用自訂的 user-data（放在 snippets 儲存） | `user=local:snippets/web.yaml` |

**主機名稱從哪裡來？** ★★★★

cloud-init 的主機名稱是**取自 VM 的 `name` 欄位**，不需要另外設。
所以 `qm clone 900 101 --name web01` 之後，開機起來主機名就是 `web01`。

> [!danger] ★★★★★ 不要用 `--cipassword`，用 SSH 金鑰
> `--cipassword` 的密碼會以**雜湊後的形式寫進 `/etc/pve/qemu-server/<id>.conf`**，
> 而這個檔案：
> - 在叢集中會同步到每個節點
> - 有 `VM.Audit` 權限的使用者就看得到
> - 會被備份帶走
>
> 而且 cloud-init 產生的 user-data 在客體裡也讀得到。
> **正確做法是只給 SSH 公鑰**，完全不設密碼。

> [!tip] ★★★★★ `qm cloudinit dump` 是排錯的第一個動作
> 「cloud-init 沒生效」時，先 dump 出來看 PVE 到底送了什麼給客體。
> 常見發現：IP 打錯、公鑰檔案是空的、`--sshkeys` 指到不存在的路徑。

### ★★★ 序列主控台（cloud image 必備）

Cloud image 通常把主控台輸出導到序列埠，而不是 VGA。
沒設定的話，開機時 novnc 主控台會**一片空白**，讓人以為開不起來。

```bash
qm set 900 --serial0 socket --vga serial0
```

之後用：

```bash
qm terminal 900
```

```text
starting serial terminal on interface serial0 (press Ctrl+O to exit)

Ubuntu 24.04.1 LTS web01 ttyS0

web01 login:
```

> [!warning] ★★★ `--vga serial0` 之後 novnc 主控台就不能用了
> 因為顯示輸出被導到序列埠。要回到圖形主控台：
> ```bash
> qm set 900 --vga std
> ```
> 實務上 cloud image 的 VM 幾乎都用 SSH 管理，序列主控台只在救援時用。

### ★★★ VM 的快照

```bash
qm snapshot 100 before-upgrade --description "升級 Nginx 前"
```

```bash
qm listsnapshot 100
```

```text
`-> before-upgrade         2026-09-02 16:12:44     升級 Nginx 前
    `-> current                                     You are here!
```

```bash
# 回復
qm rollback 100 before-upgrade
# 刪除
qm delsnapshot 100 before-upgrade
```

加上 `--vmstate 1` 會**連記憶體狀態一起存**，回復後 VM 是「執行中」的狀態：

```bash
qm snapshot 100 running-state --vmstate 1
```

> [!danger] ★★★★★ 快照不是備份，而且會拖累效能
> | 問題 | 說明 |
> | --- | --- |
> | 存在同一個儲存 ★★★★★ | 磁碟壞了，VM 跟快照一起沒 |
> | 佔用空間會成長 ★★★★ | 快照存在期間，所有變更都要額外保留一份 |
> | 拖累效能 ★★★★ | 每次寫入都要處理 COW，快照鏈越長越慢 |
> | 容易被遺忘 ★★★★★ | 「升級前打的快照」放三個月，把 thin pool 塞爆 |
>
> **紀律**：快照是「幾小時內要回復或刪除」的短期工具。
> 定期檢查有沒有老快照：
> ```bash
> for id in $(qm list | awk 'NR>1{print $1}'); do
>   echo "=== VM $id ==="; qm listsnapshot "$id"
> done
> ```

## 完整實戰範例

### 目標

接續前兩篇（PVE 裝好、`vm-store` 與 `backup-store` 配好），
**做出一個 Ubuntu 24.04 的 cloud-init 範本**，然後：


### 步驟 3：建立範本用的空 VM

```bash

  --name ubuntu-2404-cloud-tmpl \
  --ostype l26 \

  --memory 2048 --balloon 1024 \
```

> 因為磁碟要從剛下載的 cloud image 匯入，而不是建一顆空的。

3.5 GB 太小，擴到 32 GB。

> [!tip] ★★★★ 這一步在「轉成範本前」做最省事
> cloud image 的 cloud-init 會在第一次開機時**自動把根分割區長到滿**
> （`growpart` 模組是預設啟用的），所以**你只要在 PVE 這一層擴大就好**，
> 客體裡什麼都不用做。

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| Windows 安裝到「選擇磁碟」時一顆碟都沒有 ★★★★★ | 安裝程式沒有 VirtIO SCSI 驅動 | 加掛 `virtio-win.iso` 第二個光碟機，在該頁按「載入驅動程式」，選 `vioscsi\<版本>\amd64\` |
| VM 開機顯示 `No bootable device` ★★★★ | 開機順序沒有硬碟、或 BIOS 型別跟安裝時不一致 | `qm set <id> --boot order=scsi0`；BIOS 改回原本的（UEFI/SeaBIOS） |
| 重開機後又進入安裝程式 ★★★★ | ISO 還掛著且開機順序在硬碟之前 | `qm set <id> --ide2 none,media=cdrom` 並調整 `--boot order` |
| 後台看不到 VM 的 IP ★★★ | QEMU Guest Agent 沒裝或沒跑 | 客體 `apt install qemu-guest-agent && systemctl enable --now qemu-guest-agent`；PVE 端 `qm set <id> --agent enabled=1` |
| `qm shutdown` 卡很久最後逾時 ★★★★ | PVE 開了 `agent: 1` 但客體沒裝 agent | 客體裝 agent；或暫時 `qm set <id> --agent enabled=0` |
| 遷移到另一節點後 VM 崩潰或無法啟動 ★★★★★ | `cpu: host` 且兩端 CPU 指令集不同 | 改成 `x86-64-v2-AES` 之類的相容等級（**要關機才能改**） |
| `qm resize` 之後客體 `df` 沒變 ★★★★ | 只做了 PVE 那一層，分割區與檔案系統沒跟著長 | 客體裡 `growpart /dev/sda 2` 再 `resize2fs /dev/sda2`（注意是空格不是連寫） |
| `growpart` 回 `FAILED: /dev/sda2: does not exist` ★★★ | 參數格式錯 | 正確是 `growpart /dev/sda 2`（磁碟 空格 分割號） |
| cloud-init 改了 IP 重開機沒生效 ★★★★★ | cloud-init 只在第一次開機完整執行 | 客體裡 `cloud-init clean --logs` 再重開；最佳做法是**複製後、首次開機前**就設好 |
| cloud image 的 VM 開機後主控台一片空白 ★★★★ | cloud image 把輸出導到序列埠 | `qm set <id> --serial0 socket --vga serial0`，用 `qm terminal <id>` |
| 複製出來的多台機器 IP 互相搶、時通時不通 ★★★★★ | 範本沒清 `/etc/machine-id`，DHCP client identifier 重複 | 重做範本並清 machine-id；已複製的機器逐台 `truncate -s 0 /etc/machine-id` 後重開 |
| SSH 連新機器報 `HOST KEY VERIFICATION FAILED` 或多台指紋相同 ★★★★★ | 範本沒清 `/etc/ssh/ssh_host_*` | 客體 `rm -f /etc/ssh/ssh_host_* && dpkg-reconfigure openssh-server`；範本要重做 |
| VM 裡刪了大檔，thin pool 用量沒降 ★★★★ | discard 鏈路沒打通 | 磁碟加 `discard=on,ssd=1`、用 VirtIO SCSI、客體 `fstrim -av` |
| VM 網路很慢，只有幾十 Mbps ★★★★ | 網卡用了 `E1000` 模擬而非 VirtIO | `qm set <id> --net0 virtio,bridge=vmbr0`（**要關機**） |
| Windows VM 記憶體用量顯示不正常、balloon 沒作用 ★★★ | 沒裝 virtio Balloon 驅動與 `BLNSVR` 服務 | 執行 virtio-win 的完整安裝程式 |
| `qm template` 後想改範本卻改不了 ★★★★★ | 範本是唯讀的，且**沒有 untemplate 指令** | 從範本 full clone 一台出來 → 修改 → 再 `qm template` 成新範本 |
| 刪不掉範本，說有子代 ★★★★ | 底下還有連結複製的 VM | 先把那些 VM 改成完整複製（`qm move-disk` 到別的儲存）或刪掉 |
| `--boot order=ide2;scsi0` 報 `scsi0: command not found` ★★★ | shell 把分號當指令分隔 | 寫成 `ide2\;scsi0` 或 `--boot 'order=ide2;scsi0'` |
| 建 VM 時 `--name web_01` 被拒絕 ★★★ | 名稱只允許英數與 `-` | 改成 `web-01` |
| VM 開機報 `failed to initialize kvm` ★★★★★ | 巢狀虛擬化沒開 | 見 [[050-01-03-01-svc-PVE-安裝與初始設定]] 的 KVM 驗證 |

## 安全性注意事項

### ★★★★★ `--cipassword` 會把密碼留在設定檔裡

```bash
qm set 101 --cipassword 'SomePassword'
grep cipassword /etc/pve/qemu-server/101.conf
```

```text
cipassword: $5$rounds=4096$xxxxxxxx$yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy
```

這個雜湊：

- 在叢集裡會**同步到每個節點**
- 有 `VM.Audit` 權限的使用者就能讀到
- **會被備份帶走**，備份檔外流等於密碼外流
- 可以拿去離線破解

> [!danger] ★★★★★ 正確做法：只用 SSH 公鑰，不設密碼
> ```bash
> qm set 101 --sshkeys /root/.ssh/id_ed25519.pub
> qm set 101 --delete cipassword
> ```
> 需要主控台救援時，用 `qm guest passwd`（透過 agent 臨時設密碼）
> 或從 GRUB 進單使用者模式，見 [[020-01-25-guide-Linux-開機流程與GRUB救援]]。

### ★★★★★ 範本裡不可以有任何機密

範本會被複製 N 次，**範本裡的每一個秘密都會被複製 N 次**。

| 絕對不能烘進範本 | 為什麼 |
| --- | --- |
| SSH 私鑰 ★★★★★ | 每台機器都能互相登入，橫向移動零阻力 |
| API token、資料庫密碼 ★★★★★ | 一台被入侵等於全部被入侵 |
| 憑證私鑰 ★★★★★ | 無法撤銷單一台 |
| `~/.bash_history` ★★★★ | 裡面常有打錯位置的密碼 |
| 已設定好的 `authorized_keys`（個人金鑰）★★★ | 人員離職時要一台台清 |
| **SSH host key** ★★★★★ | 全部機器指紋相同，MITM 偵測失效 |
| **`/etc/machine-id`** ★★★★ | DHCP 衝突、日誌來源無法區分 |

> [!tip] ★★★★ 範本裡該有的是「共通且無害」的東西
> 更新過的套件、常用工具（vim、curl、htop）、
> 監控 agent 的**套件**（設定留給 cloud-init 帶入）、
> 時區與 NTP 設定、基本的安全強化設定。

### ★★★★ VM 之間的網路隔離

**同一個 vmbr 上的 VM 彼此是完全連通的**，就像插在同一台交換器上。
一台 VM 被入侵，攻擊者可以直接掃描並攻擊同橋接上的所有機器。

| 措施 | 說明 |
| --- | --- |
| PVE 防火牆（每個 VM 的 Firewall 分頁）★★★★ | 在虛擬網卡層級過濾 |
| 不同用途的 VM 放不同 VLAN ★★★★★ | 網路層隔離，見 [[050-01-03-05-guide-PVE-網路設定]] |
| DMZ 的 VM 用獨立 bridge ★★★★★ | 對外服務不要跟內部管理網段同橋 |

### ★★★ 主控台存取權限

PVE 的 novnc 主控台是**直接的螢幕與鍵盤存取**，繞過所有作業系統的登入稽核。
有主控台權限的人可以：從 GRUB 進單使用者模式改 root 密碼、掛救援光碟讀資料。

| 權限 | 給誰 |
| --- | --- |
| `VM.Console` ★★★★★ | **只給系統管理員**，不要給一般的 VM 操作人員 |
| `VM.PowerMgmt` ★★★ | 需要開關機的人 |
| `VM.Audit` ★★ | 只需要看狀態的人（注意它看得到設定檔內容） |

見 [[050-01-03-08-guide-PVE-使用者權限與API]]。

### ★★★★ 快照與備份的機密殘留

刪掉 VM 裡的一個機密檔案，**快照裡還有**。
備份檔裡也還有。處理外洩事件時要一併處理：

```bash
qm listsnapshot 101       # 找出所有快照
qm delsnapshot 101 <name> # 刪掉含有機密的快照
```

備份端的處理見 [[050-01-03-06-svc-PVE-備份與還原]]。

## 練習題

> [!question]- 練習 1：實測 VirtIO 網卡與 E1000 的效能差距
> 開兩台一樣的 VM，一台用 `virtio`、一台用 `e1000`，用 `iperf3` 對測。
>
> ---
> **解答**
>
> ```bash
> qm clone 900 201 --name net-virtio --full 0
> qm clone 900 202 --name net-e1000  --full 0
> qm set 201 --ipconfig0 ip=192.168.1.201/24,gw=192.168.1.1
> qm set 202 --ipconfig0 ip=192.168.1.202/24,gw=192.168.1.1 --net0 e1000,bridge=vmbr0
> qm start 201 && qm start 202
> ```
>
> 兩台都裝 iperf3：
> ```bash
> sudo apt install -y iperf3
> ```
>
> 201 當伺服器：
> ```bash
> iperf3 -s
> ```
>
> 202 當客戶端：
> ```bash
> iperf3 -c 192.168.1.201 -t 10
> ```
>
> 典型結果（實際數字受宿主機影響很大，**重點是相對差距**）：
> ```text
> # e1000 → virtio
> [ ID] Interval           Transfer     Bitrate
> [  5]   0.00-10.00  sec  1.42 GBytes  1.22 Gbits/sec
> ```
>
> 把 202 改成 virtio 再測一次：
> ```bash
> qm stop 202 && qm set 202 --net0 virtio,bridge=vmbr0 && qm start 202
> ```
> ```text
> [  5]   0.00-10.00  sec  18.7 GBytes  16.1 Gbits/sec
> ```
>
> **差距通常在一個數量級以上。** 這就是為什麼「能用 VirtIO 就用 VirtIO」
> 不是建議而是規則。★★★★★
>
> 清理：`qm stop 201 202; qm destroy 201 --purge; qm destroy 202 --purge`

> [!question]- 練習 2：故意不清 machine-id，觀察 DHCP 衝突
> 做一個**沒有清理身分**的範本，複製三台用 DHCP，觀察 IP 分配。
>
> ---
> **解答**
>
> 從乾淨範本複製一台當「壞範本」，開機後**不做任何清理**就轉範本：
> ```bash
> qm clone 900 890 --name bad-tmpl --full 1
> qm start 890
> # 進去確認 machine-id 有值
> ```
> ```bash
> cat /etc/machine-id
> ```
> ```text
> 3a7f21c8d94e4b0192fe5c8d7a361b04
> ```
> ```bash
> sudo shutdown -h now
> ```
> ```bash
> qm template 890
> for i in 1 2 3; do
>   qm clone 890 $((210+i)) --name bad0$i --full 0
>   qm set $((210+i)) --ipconfig0 ip=dhcp
>   qm start $((210+i))
> done
> ```
>
> 觀察三台的 machine-id：
> ```bash
> for id in 211 212 213; do qm guest exec $id -- cat /etc/machine-id; done
> ```
>
> **三台完全相同**。用 DHCP 時，systemd-networkd 預設會用 machine-id
> 衍生出 DHCP client identifier，於是 DHCP 伺服器認為它們是同一台機器，
> **反覆把同一個 IP 發給三台**，造成 IP 衝突、連線時通時不通。
>
> 這種故障極難診斷，因為表面症狀是「網路不穩」。★★★★★
>
> 清理：把 211～213 與 890 全部 destroy。

> [!question]- 練習 3：驗證 `qm stop` 與 `qm shutdown` 的差別
> 在 VM 裡持續寫入檔案，分別用兩種方式停機，觀察開機後的差異。
>
> ---
> **解答**
>
> VM 裡跑：
> ```bash
> while true; do date >> /home/sysadmin/heartbeat.log; sleep 1; done
> ```
>
> **A：正常關機**
> ```bash
> qm shutdown 101 --timeout 60
> qm start 101
> ```
> 開機後 `dmesg | grep -i ext4`：
> ```text
> EXT4-fs (sda1): mounted filesystem with ordered data mode.
> ```
> 乾淨掛載，`heartbeat.log` 完整。
>
> **B：強制斷電**
> ```bash
> qm stop 101
> qm start 101
> ```
> ```text
> EXT4-fs (sda1): recovery complete
> EXT4-fs (sda1): mounted filesystem with ordered data mode.
> ```
> 出現 **`recovery complete`** —— journal 重播了。
> 檔案系統救回來了（這是 journal 的功勞），但**最後幾筆寫入可能遺失**。
>
> 對資料庫而言，這種斷電更危險：InnoDB 要做 crash recovery，
> 若剛好在寫 checkpoint 就可能損毀。★★★★★

> [!question]- 練習 4：把一台跑著的 VM 從 `host` CPU 改成相容型別
> 完整走一次「需要關機的設定變更」，並確認生效。
>
> ---
> **解答**
>
> ```bash
> qm config 101 | grep cpu
> ```
> ```text
> cpu: host
> ```
>
> 直接改（VM 執行中）：
> ```bash
> qm set 101 --cpu x86-64-v2-AES
> ```
> ```text
> update VM 101: -cpu x86-64-v2-AES
> ```
> **指令成功了，但沒有生效。** 後台會顯示一個提示說有待生效的變更。
>
> 確認 VM 裡看到的仍是舊的：
> ```bash
> qm guest exec 101 -- lscpu
> ```
> 輸出裡的 Model name 還是實體 CPU 的型號。
>
> 關機再開（**不是 reboot**，reboot 不會重建 QEMU 程序）：
> ```bash
> qm shutdown 101 --timeout 60
> qm start 101
> qm guest exec 101 -- grep 'model name' /proc/cpuinfo
> ```
> 現在會看到通用的型號字串。
>
> **關鍵教訓**：`qm reboot` 是在客體裡重開機，**QEMU 程序沒有重建**，
> 所以硬體層級的變更不會生效。**必須 shutdown + start。**★★★★★

> [!question]- 練習 5：修好一個「cloud-init 不生效」的 VM
> 對已經開過機的 VM 改 IP，觀察不生效，然後用兩種方法修好。
>
> ---
> **解答**
>
> ```bash
> qm set 101 --ipconfig0 ip=192.168.1.111/24,gw=192.168.1.1
> qm shutdown 101 --timeout 60 && qm start 101
> qm guest cmd 101 network-get-interfaces | grep ip-address
> ```
> ```text
>             "ip-address" : "192.168.1.101",
> ```
> **還是舊 IP。**
>
> **方法 A：客體端重置 cloud-init 狀態**
> ```bash
> ssh -i /root/.ssh/id_ed25519 sysadmin@192.168.1.101 \
>   'sudo cloud-init clean --logs && sudo reboot'
> ```
> 等一分鐘：
> ```bash
> qm guest cmd 101 network-get-interfaces | grep ip-address
> ```
> ```text
>             "ip-address" : "192.168.1.111",
> ```
>
> **方法 B：從頭來（實務上更常用）**
> ```bash
> qm stop 101 && qm destroy 101 --purge
> qm clone 900 101 --name web01 --full 0
> qm set 101 --ipconfig0 ip=192.168.1.111/24,gw=192.168.1.1
> qm start 101
> ```
>
> **這正是「機器是牲畜不是寵物」的思路**：
> 有範本在手，重建一台只要幾秒，比修一台狀態不明的機器可靠得多。★★★★★

> [!question]- 練習 6：算出連結複製省了多少空間
> 用實際數字算出十台連結複製 vs 十台完整複製的空間差距。
>
> ---
> **解答**
>
> ```bash
> lvs vmstore -o lv_name,lv_size,data_percent
> ```
> ```text
>   LV                LSize    Data%
>   base-900-disk-0    32.00g
>   thinpool         <190.00g   1.71
>   vm-101-disk-0      32.00g   0.31
>   vm-102-disk-0      32.00g   0.29
>   vm-103-disk-0      32.00g   0.29
> ```
>
> thin pool 用了 1.71% × 190 GB ≈ **3.25 GB**，
> 其中範本基礎映像約 2.4 GB，三台差異各約 0.28 GB。
>
> 推算十台：
> ```text
> 連結複製：2.4 GB（範本） + 10 × 0.28 GB = 5.2 GB
> 完整複製：10 × 2.4 GB              = 24 GB（thin，只算實際用量）
>          10 × 32 GB               = 320 GB（若非 thin）
> ```
>
> **連結複製約省 78%（相對於 thin 的完整複製）。**★★★★
>
> 但要記得代價：**那個 `base-900-disk-0` 是十台機器的單點故障**，
> 而且十台的讀取都要經過它，I/O 熱點集中。
> 正式環境用完整複製換取獨立性，實驗環境用連結複製換取速度與空間。

Q4. 選擇題：一個三節點叢集，節點 CPU 型號不同。VM 的 CPU type 該選什麼？
（A）`host`，效能最好　（B）`kvm64`，一定不會出事
（C）`x86-64-v2-AES`，兼顧效能與相容　（D）每台 VM 設成所在節點的實際型號

Q5. 從範本複製出十台機器，三天後開始出現「網路時通時不通、IP 互搶」。範本少做了哪一步？為什麼會這樣？

Q6. 你把 cloud-init 的 IP 從 `.101` 改成 `.111`，重開機後還是舊 IP。原因是什麼？兩種解法各是什麼？

Q7. 是非題：`qm template 900` 之後如果發現範本少裝了東西，可以用 `qm untemplate` 轉回一般 VM 再修。

Q8. 磁碟的 Cache 選 `Write back (unsafe)` 會有什麼風險？唯一可以用它的場合是什麼？

Q9. 一台 VM 開了 `agent: 1`，但客體裡沒裝 `qemu-guest-agent`。這比「兩邊都沒做」更好還是更糟？為什麼？

Q10. 連結複製的十台 VM 底下共用一個 `base-900-disk-0`。列出這個架構的兩個風險。

> [!question]- 測驗答案
> **Q1.** 因為 **Windows 安裝程式裡沒有 VirtIO SCSI 的磁碟驅動**，
> 它看不到那顆磁碟。解法是給 VM 掛第二個光碟機載入 **`virtio-win.iso`**，
> 在該頁按「載入驅動程式」，瀏覽到 `vioscsi\<Windows 版本>\amd64\` 載入。
> 裝完進系統後再跑一次 virtio-win 的完整安裝程式，把網卡、balloon、
> guest agent 一併裝齊。Linux 客體沒有這個問題，因為核心內建 VirtIO 驅動。★★★★★
> （見「觀念說明 → VirtIO」）
>
> **Q2.** **錯。** `qm reboot` 是在**客體裡面**重開機，
> **底層的 QEMU 程序沒有重建**，所以硬體層級的設定變更（CPU type、記憶體上限、
> 網卡 model、BIOS）不會生效。必須 **`qm shutdown` 之後再 `qm start`**。★★★★★
> （見「進階應用」與「練習 4」）
>
> **Q3.** `qm shutdown` 是**正常關機**——透過 QEMU Guest Agent（或 ACPI 訊號）
> 請客體執行自己的關機流程，服務會被妥善停止、緩衝區會被寫入磁碟。
> `qm stop` 是**強制斷電，等同拔插頭**，檔案系統會處於不一致狀態，
> 資料庫可能損毀。
> 正確流程是先 `shutdown --timeout`，沒反應就開主控台看卡在哪，
> **真的救不了才用 `stop`，而且開機後要檢查檔案系統**。★★★★★
> （見「主控台與基本操作」）
>
> **Q4.** **（C）**。`host` 會把實體 CPU 的全部指令集暴露給客體，
> 遷移到指令集不同的節點時客體可能崩潰。`kvm64` 雖然最安全但效能明顯較差。
> `x86-64-v2-AES` 提供 SSE4.2、AES-NI 等現代指令集，
> 又能在支援 v2 的各代 CPU 之間安全遷移。
> 準則是**以叢集裡最舊的那台節點的 CPU 能力為準**。★★★★★
> （見「觀念說明 → CPU type」）
>
> **Q5.** 少清了 **`/etc/machine-id`**（以及 `/var/lib/dbus/machine-id`）。
> systemd-networkd 預設會用 machine-id 衍生出 DHCP client identifier，
> 十台機器有相同的 machine-id 就等於**十台機器對 DHCP 伺服器宣稱自己是同一台**，
> 伺服器反覆把同一個 IP 發出去，造成 IP 衝突。
> 表面症狀是「網路不穩」，極難診斷。
> 同樣該清的還有 **`/etc/ssh/ssh_host_*`**（否則所有機器 SSH 指紋相同，
> 中間人偵測失效）。★★★★★
> （見「進階應用 → 從 VM 做成範本」與「練習 2」）
>
> **Q6.** 因為 **cloud-init 只在「第一次開機」時完整執行**。
> 它在客體裡記錄了 instance-id，第二次開機發現沒變就跳過大部分設定。
> 解法 A：客體裡 `sudo cloud-init clean --logs` 再重開機，強制重跑。
> 解法 B：直接 `qm destroy` 掉重新從範本複製一台（幾秒的事，而且結果乾淨）。
> 最佳實務是**在複製之後、首次開機之前**就把 cloud-init 參數設好。★★★★★
> （見「觀念說明 → cloud-init」與「練習 5」）
>
> **Q7.** **錯。** **沒有 `qm untemplate` 這個指令**，`qm template` 是不可逆的。
> 範本轉換後不能開機、不能改硬體、磁碟變成唯讀基礎映像。
> 要「修改範本」的正確做法是：**從範本做一次完整複製 → 在複製品上修改
> → 再 `qm template` 成一個新範本**。所以轉範本前務必確認裡面該裝的都裝了。★★★★★
> （見「進階應用 → 從 VM 做成範本」）
>
> **Q8.** 它會**忽略客體發出的 flush 指令**。資料庫以為資料已經確實落碟，
> 其實還在主機的 page cache 裡；**主機一斷電，那些資料就消失，
> 而資料庫毫不知情**，造成資料檔案不一致，比單純丟失資料更難處理。
> 唯一合理的用途是**大量建置測試機時暫時開著加速安裝，裝完立刻改回來**。
> 正式環境用到它就是事故。不確定時一律用 `Default (No cache)`。★★★★★
> （見「觀念說明 → 磁碟快取模式」）
>
> **Q9.** **更糟。** PVE 開了 `agent: 1` 之後，關機與備份的流程會**先嘗試呼叫 agent
> 並等待回應**，客體沒有 agent 就一直等到逾時才 fallback 到 ACPI。
> 結果是每次關機、每次備份都要多卡一段時間。
> 兩邊都沒做的話，PVE 一開始就用 ACPI，反而比較快。
> **正確做法是兩邊都做**：PVE 端 `qm set <id> --agent enabled=1`，
> 客體端 `apt install qemu-guest-agent && systemctl enable --now qemu-guest-agent`。★★★★
> （見「觀念說明 → QEMU Guest Agent」）
>
> **Q10.** 兩個風險：
> （1）**單點故障** —— `base-900-disk-0` 是十台機器共同的基礎磁碟，
> 它損毀或被誤刪，十台一起死，而且無法個別救援。
> （2）**I/O 熱點與效能** —— 十台的讀取都要經過同一個基礎映像，
> 讀取要走兩層（基礎 + 差異），效能低於完整複製，且熱點集中。
> 另外還有管理面的風險：**刪不掉那個範本**（PVE 會擋），
> 範本會永遠佔著空間直到所有子代被處理掉。
> 因此連結複製只用在可重建的實驗／測試機，正式環境用完整複製。★★★★★
> （見「觀念說明 → 範本、完整複製與連結複製」與「練習 6」）
