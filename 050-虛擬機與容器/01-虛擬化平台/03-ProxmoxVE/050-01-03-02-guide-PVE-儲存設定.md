## 觀念說明

### ★★★★★ 兩層心智模型：類型決定能力，內容決定用途

PVE 的儲存是新手最容易搞混的部分，因為它有**兩個獨立的維度**：

```text
       ┌──────────────────────────────────────────┐
       │  儲存類型（Type）                          │
       │  dir / lvm / lvmthin / zfspool / nfs ...  │
       │  ↓ 決定「它有什麼能力」                     │
       │    能不能快照？能不能 thin？叢集共不共享？    │
       └──────────────────────────────────────────┘
                        ×
       ┌──────────────────────────────────────────┐
       │  內容類型（Content）                       │
       │  images / rootdir / iso / vztmpl /        │
       │  backup / snippets                        │
       │  ↓ 決定「它准放什麼東西」                    │
       └──────────────────────────────────────────┘
```

**一個儲存能不能放某樣東西，是這兩層一起決定的。**

- **類型**限制了「理論上可能」：block 型的儲存（LVM、iSCSI、RBD）**天生放不了檔案**，
  所以它們永遠不能放 ISO 或備份
- **內容類型**是你在設定裡**主動勾選**的：一個目錄型儲存理論上什麼都能放，
  但你可以只勾 `backup`，那它就只能放備份

> [!danger] ★★★★★ 這是新手第一個「為什麼上傳不了 ISO」的原因
> 你在後台想上傳 ISO，`Storage` 下拉選單裡**只看得到 `local`，看不到 `local-lvm`**。
> 這不是壞掉——`local-lvm` 是 LVM-Thin，它是**區塊裝置**，
> 上面沒有檔案系統，**根本無法存放一個叫做 `xxx.iso` 的檔案**。
>
> 同理，你想把備份存到 `local-lvm` 也不行。**這是物理限制，不是設定問題。**

### ★★★★ 六種內容類型

| 內容類型 | 後台顯示 | 存的是什麼 | 實際落在哪（目錄型） |
| --- | --- | --- | --- |
| `images` ★★★★★ | Disk image | **VM 的虛擬磁碟** | `images/<VMID>/vm-<VMID>-disk-N.qcow2` |
| `rootdir` ★★★★ | Container | **LXC 容器的根檔案系統** | `private/<CTID>/` 或 `images/<CTID>/` |
| `iso` ★★★★ | ISO image | 安裝用的 ISO 光碟映像 | `template/iso/` |
| `vztmpl` ★★★ | Container template | **LXC 範本**（`.tar.zst`） | `template/cache/` |
| `backup` ★★★★★ | VZDump backup file | **vzdump 產生的備份** | `dump/` |
| `snippets` ★★★ | Snippets | cloud-init 自訂片段、hook script | `snippets/` |

> [!note] ★★★ 記住這張表的用途
> 排錯時很好用：「備份跑不動，說找不到儲存」→ 檢查那個儲存有沒有勾 `backup`；
> 「上傳 ISO 沒得選」→ 檢查有沒有勾 `iso`、以及該儲存是不是檔案型的。

### ★★★★★ 儲存類型能力矩陣

這張表是整篇的核心，**選型時就看它**：

| 類型 | 底層 | 檔案/區塊 | 支援內容 | 快照 | Thin | 叢集共享 | 典型場景 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `dir` ★★★★ | 任何已掛載的目錄 | 檔案 | 全部六種 | 僅 qcow2 | 僅 qcow2 | ✘（除非底下是共享 FS） | ISO、備份、單機萬用 |
| `lvm` ★★★ | LVM 卷冊群組 | 區塊 | `images` `rootdir` | ✘ | ✘ | ✔（配 iSCSI） | 共享 SAN 上的 VM 磁碟 |
| `lvmthin` ★★★★★ | LVM Thin Pool | 區塊 | `images` `rootdir` | ✔ | ✔ | ✘ | **PVE 預設的 `local-lvm`** |
| `zfspool` ★★★★ | ZFS dataset | 區塊(zvol) | `images` `rootdir` | ✔ | ✔ | ✘（可做非同步複寫） | 單機／雙機的高階本機儲存 |
| `btrfs` ★★ | Btrfs 子卷 | 檔案 | 全部六種 | ✔ | ✔ | ✘ | 較新，生產環境較少用 |
| `nfs` ★★★★★ | NFS 掛載 | 檔案 | 全部六種 | 僅 qcow2 | 僅 qcow2 | **✔** | 備份、ISO、共享 VM 磁碟 |
| `cifs` ★★★ | SMB/CIFS 掛載 | 檔案 | 全部六種 | 僅 qcow2 | 僅 qcow2 | **✔** | 接 Windows 檔案伺服器 |
| `iscsi` ★★★ | iSCSI LUN | 區塊 | `images`（直接用） | ✘ | ✘ | ✔ | 幾乎都是拿來墊 LVM |
| `rbd`（Ceph）★★★★ | Ceph RBD | 區塊 | `images` `rootdir` | ✔ | ✔ | **✔** | 三節點以上叢集的正解 |
| `cephfs` ★★★ | CephFS | 檔案 | `iso` `vztmpl` `backup` `snippets` | ✔ | — | **✔** | 叢集裡放 ISO 與備份 |
| `pbs` ★★★★ | Proxmox Backup Server | 專用 | `backup` | — | 去重 | ✔ | **正式環境備份的最佳解** |

> [!tip] ★★★★ 三個一眼看懂這張表的重點
> 1. **「快照」這一欄決定你能不能做連結複製（Linked Clone）**。
>    `lvm`（thick）不支援快照，所以在它上面**只能做完整複製**。
> 2. **「叢集共享」決定能不能做線上遷移（Live Migration）而不搬磁碟**。
>    本機儲存（lvmthin、zfspool）也能遷移，但要把磁碟整個複製過去，很慢。
> 3. **`dir` + qcow2 幾乎什麼都能做**，只是效能不如區塊儲存。
>    不確定時用 `dir` 最不會出事。

### ★★★★ 裝完就有的兩個儲存

PVE 安裝完（選 ext4）會自動建立兩個儲存：

```bash
pvesm status
```

```text
Name             Type     Status           Total            Used       Available        %
local             dir     active        25563164         3524192        20714276    13.79%
local-lvm     lvmthin     active        64917504               0        64917504     0.00%
```

```bash
cat /etc/pve/storage.cfg
```

```ini
dir: local
	path /var/lib/vz
	content iso,vztmpl,backup

lvmthin: local-lvm
	thinpool data
	vgname pve
	content rootdir,images
```

拆開來看：

| | `local` | `local-lvm` |
| --- | --- | --- |
| 類型 ★★★★ | `dir`（目錄） | `lvmthin`（LVM Thin Pool） |
| 實體位置 ★★★★ | `/var/lib/vz`（**在根分割區裡**） | LVM VG `pve` 裡的 `data` thin pool |
| 內容 ★★★★★ | `iso` `vztmpl` `backup` | `rootdir` `images` |
| 放得下 ISO 嗎 ★★★★ | **可以** | **不行**（區塊裝置） |
| 放得下 VM 磁碟嗎 | 預設沒勾（可以加勾） | **可以，這是它的本職** |
| 支援快照 ★★★ | 用 qcow2 才有 | **有** |

> [!danger] ★★★★★ `local` 在根分割區裡，這是最常見的爆滿原因
> `/var/lib/vz` 位於 `/`，而 PVE 安裝時給 `/` 的空間通常只有二三十 GB。
> 你只要往 `local` 丟幾個 ISO、跑幾次備份，**根分割區就滿了**。
>
> 根分割區滿掉的後果是**災難級**的：
> - `/etc/pve`（pmxcfs）寫不進去 → **所有設定都改不了、VM 開不了**
> - 日誌寫不進去 → 服務開始異常
> - Web 後台可能直接掛掉
>
> **鐵律：ISO 與備份不要長期放在 `local`。** 一開始就規劃一個獨立的儲存放它們。

看清楚 LVM 的實際配置：

```bash
lvs
```

```text
  LV            VG  Attr       LSize   Pool Data%  Meta%  Move Log Cpy%Sync Convert
  data          pve twi-aotz-- <62.00g      0.00   1.58
  root          pve -wi-ao----  24.38g
  swap          pve -wi-ao----   8.00g
```

```bash
vgs
```

```text
  VG  #PV #LV #SN Attr   VSize   VFree
  pve   1   3   0 wz--n- <99.50g  4.75g
```

三個 LV 的角色：★★★★

| LV | 用途 | 對應的儲存 |
| --- | --- | --- |
| `root` | 根檔案系統 `/` | `local` 的實體位置在這裡面 |
| `swap` | 交換空間 | — |
| `data` | **Thin Pool** | `local-lvm` |

注意 `data` 的 Attr 是 `twi-aotz--`，開頭的 **`t` 代表 thin pool**。
`Data%` 那一欄就是**這個 thin pool 實際用掉多少**，**這個數字是你要盯的**。★★★★★

### ★★★★★ Thin Provisioning：省空間，也可能毀掉一切

**Thin Provisioning（精簡配置／超賣）**：宣告 100 GB 的虛擬磁碟，
但只有實際寫入的資料才佔用底層空間。

```text
     VM 裡面看到的                 底層 thin pool 實際佔用
     ┌────────────────┐            ┌────────────────┐
     │ /dev/sda 100GB │            │  已寫入 8 GB    │
     │ df 顯示：       │   ───→     │  ▓▓            │
     │  已用 8G 可用 92G│            │                │
     └────────────────┘            └────────────────┘
```

好處明顯：一個 62 GB 的 pool，可以開出五台各宣告 100 GB 的 VM——
只要它們實際用量加起來不超過 62 GB。

> [!danger] ★★★★★ Thin Pool 用完會發生什麼
> 這是 PVE 上**最嚴重、最難救的一種故障**，一定要理解。
>
> 當 thin pool 的 `Data%` 到達 100%：
>
> 1. VM 裡的**寫入操作直接失敗**，客體作業系統會看到磁碟 I/O 錯誤
> 2. Linux 客體通常會把根檔案系統**重新掛載成唯讀**，服務全部停擺
> 3. 資料庫（MySQL、PostgreSQL）在寫到一半被切斷，**很可能資料損毀** ★★★★★
> 4. 更糟的是 **metadata pool 滿掉**（`Meta%` 到 100%），
>    此時 thin pool 會進入無法寫入的狀態，救援極為困難
>
> **而且客體完全不知情**——VM 裡面 `df -h` 顯示還有 92 GB 可用，
> 因為它看到的是宣告值。**危險就在這個資訊落差。**

看真正的用量要在**主機端**：

```bash
lvs -o lv_name,lv_size,data_percent,metadata_percent pve
```

```text
  LV   LSize   Data%  Meta%
  data <62.00g  73.42  12.05
  root  24.38g
  swap   8.00g
```

> [!warning] ★★★★ 兩個必須盯的百分比
> | 欄位 | 意義 | 警戒線 |
> | --- | --- | --- |
> | `Data%` ★★★★★ | 資料實際用掉 pool 的比例 | **80% 開始處理，90% 是紅線** |
> | `Meta%` ★★★★★ | metadata 用掉的比例 | **同樣看 80%**，它會先滿 |
>
> `Meta%` 常被忽略。快照多、VM 多的環境，**metadata 有機會比 data 先爆**，
> 而 metadata 滿掉造成的損害更難修復。

> [!tip] ★★★★ 另一個容易忽略的地雷：刪檔案不會還空間
> VM 裡面刪掉 10 GB 的檔案，**底層 thin pool 的用量不會自動減少**——
> 因為客體只是把檔案系統的中繼資料標成「已刪除」，並沒有告訴底層儲存
> 「這些區塊可以回收了」。
>
> 要讓空間真的還回去，需要 **discard / TRIM** 這條鏈路完整打通：
>
> 1. VM 的磁碟要勾 **`Discard`** 選項 ★★★★
> 2. 磁碟匯流排建議用 **VirtIO SCSI**（`scsihw: virtio-scsi-single`）★★★
> 3. 客體裡要執行 `fstrim`（Ubuntu 有 `fstrim.timer` 每週自動跑）★★★★
>
> ```bash
> # 在 VM 裡面
> sudo fstrim -av
> ```
> ```text
> /boot/efi: 1 GiB (1071644672 bytes) trimmed on /dev/sda1
> /: 11.2 GiB (12025044992 bytes) trimmed on /dev/sda2
> ```
>
> 然後回到 PVE 主機看 `lvs`，`Data%` 應該降下來。
> 這件事的完整設定見 [[050-01-03-03-guide-PVE-虛擬機管理]]。

### ★★★ Ceph 概覽：什麼時候才該考慮它

Ceph 是分散式儲存系統，PVE 內建整合（`Datacenter → Ceph`）。
它把多台節點的磁碟聚合成一個叢集共享的儲存池，**每份資料複寫到多個節點**。

```text
   節點 A          節點 B          節點 C
   ┌──────┐       ┌──────┐       ┌──────┐
   │ OSD  │       │ OSD  │       │ OSD  │      ← 每顆磁碟一個 OSD
   │ OSD  │       │ OSD  │       │ OSD  │
   │ MON  │       │ MON  │       │ MON  │      ← 監控與 quorum
   └──┬───┘       └──┬───┘       └──┬───┘
      └──────────────┼──────────────┘
                     │
              Ceph RBD Pool（叢集共享）
              任一節點都能直接讀寫任一 VM 磁碟
```

| 好處 ★★★★ | 代價 ★★★★★ |
| --- | --- |
| 真正的叢集共享儲存，線上遷移**不需搬磁碟** | **至少三個節點**才有意義（quorum 與副本） |
| 節點壞掉資料還在，可做 HA 自動接手 | 需要**專用的高速網路**（10 GbE 起跳） |
| 容量與效能可以加節點橫向擴充 | 記憶體與 CPU 開銷不小 |
| 支援快照、thin | 學習曲線陡，出事排查困難 |

> [!warning] ★★★★★ 不要在兩節點或巢狀環境玩 Ceph
> 常見的錯誤決定：「反正 PVE 內建，那就用 Ceph 吧」。
> 在兩節點、單網卡、或 Workstation 巢狀環境裡跑 Ceph，
> 你會得到**又慢又不穩、而且完全不具備容錯**的儲存，
> 因為副本數湊不齊、網路頻寬不夠、latency 過高。
>
> **判斷準則**：
> - 1～2 台 PVE → **不要 Ceph**。用本機 `lvmthin` 或 `zfspool` + NFS 放備份
> - 3 台以上 + 10 GbE 專用網路 + 每台多顆 SSD → **可以考慮**
> - 只是要共享儲存放 ISO 與備份 → **NFS 就夠了**，簡單十倍
>
> Ceph 的實際部署屬於叢集主題，見 [[050-01-03-07-svc-PVE-叢集與高可用]]。

> [!note] ★★★★ Volid 的格式要看懂
> ```text
> local-lvm : vm-100-disk-0
> ─────────   ──────────────
> 儲存 ID      磁碟名稱
> ```
> 目錄型會多一層路徑：`local:iso/xxx.iso`、`local:100/vm-100-disk-0.qcow2`。

> 加了 `--sparse`，建立 VM 磁碟時 zvol 不會預留空間，

> 所有由 PVE 管理的 NFS / CIFS 儲存，都會自動掛在這個路徑底下。

> [!danger] ★★★★★ NFS 伺服器掛掉，PVE 可能整台卡住
> NFS 的預設掛載模式是 **hard mount**：伺服器沒回應時，
> 存取那個目錄的程序會**無限期卡在 D state（uninterruptible sleep）**，

> 即使其他儲存與 VM 都好好的。
>
> 應變方式：
> ```bash
> # 先讓 PVE 不要再碰它
> pvesm set nfs-backup --disable 1
> # 強制卸載
> umount -f -l /mnt/pve/nfs-backup
> systemctl restart pvestatd
> ```
> 這是**現場處置的必背動作**。

### ★★★★ 加掛儲存方式四：iSCSI + LVM

企業 SAN 的標準做法。**iSCSI 幾乎不會單獨用，都是拿來墊 LVM。**

```text
   SAN 提供一顆 LUN（就是一顆網路上的裸碟）
        ↓  iSCSI 儲存（PVE 只是把 LUN 連進來）
   PVE 看到 /dev/sdX
        ↓  在上面建立 LVM VG
   LVM 儲存（真正給 VM 磁碟用的）
```

```bash
# 1) 探索目標
apt install -y open-iscsi
iscsiadm -m discovery -t sendtargets -p 192.168.10.20
```

```text
192.168.10.20:3260,1 iqn.2003-01.org.example:storage.lun0
```

```bash
# 2) 在 PVE 註冊 iSCSI 儲存
pvesm add iscsi san-lun0 \
  --portal 192.168.10.20 \
  --target iqn.2003-01.org.example:storage.lun0 \
  --content none
```

> [!tip] ★★★★ `--content none` 是刻意的
> 這一層只是「把 LUN 接進來」，我們**不希望 PVE 直接把 LUN 當 VM 磁碟用**
> （那樣一顆 LUN 只能給一台 VM）。真正的用法是在上面建 LVM。
> 後台勾選框叫 **`Use LUNs directly`**，這裡要**取消勾選**。

```bash
# 3) 確認新的區塊裝置出現了
lsblk | grep -A1 sdb
```

```text
sdb                 8:16   0   500G  0 disk
```

```bash
# 4) 在上面建立 LVM

```

```text
  Physical volume "/dev/sdb" successfully created.
  Volume group "san-vg" successfully created
```

```bash
# 5) 註冊成 PVE 的 LVM 儲存
pvesm add lvm san-storage \
  --vgname san-vg \
  --content images,rootdir \
  --shared 1
```

> [!danger] ★★★★★ `--shared 1` 只有在儲存「真的是共享」時才能設
> 這個旗標告訴 PVE：「這個儲存在每個節點上都看得到同一份資料」，
> 於是 PVE 會允許**線上遷移不搬磁碟**。
>
> 如果你在一個**本機**儲存上亂設 `--shared 1`，PVE 會以為 B 節點也看得到 A 節點的磁碟，
> 遷移時**不複製資料就把 VM 搬過去**，結果 VM 在 B 節點找不到磁碟開不了機。
> 更糟的情況是兩個節點同時寫同一份 LVM 中繼資料，**造成資料損毀**。

> [!warning] ★★★★ LVM（thick）不支援快照
> 從能力矩陣看得出來：`lvm` 類型的儲存**沒有快照**。
> 這代表在 SAN 上跑的 VM：
> - 不能用 PVE 的快照功能（`Snapshot` 按鈕會是灰的）
> - 只能做**完整複製**，不能做連結複製
> - 備份時無法用快照模式取得一致性，要靠 QEMU Guest Agent 凍結檔案系統
>
> 有些 SAN 自己在陣列端提供快照，那是另一回事，PVE 管不到。

> 這是好事（不會誤刪），但也要知道：

## 進階應用

### ★★★★★ 空間規劃：三個必須守住的水位

| 儲存 | 建議上限 | 超過會怎樣 |
| --- | --- | --- |
| 根分割區 `/` ★★★★★ | **80%** | pmxcfs 寫不進去，設定改不了、VM 開不了、後台掛掉 |
| LVM Thin Pool（`Data%` / `Meta%`）★★★★★ | **80%** | 100% 時 VM 寫入失敗、檔案系統轉唯讀、資料庫可能損毀 |
| ZFS 池 ★★★★ | **80%** | 超過後配置演算法從「效能優先」切成「找空間優先」，**寫入效能斷崖式下降** |

> [!note] ★★★★ 為什麼三個都是 80%
> 巧合但也不巧合。三者的共同原因是：**檔案系統／配置器需要自由空間來運作**。
> ext4 需要空間避免碎裂，thin pool 需要空間放 metadata 與快照差異，
> ZFS 的 copy-on-write 更是**每次寫入都需要新空間**。
> 把儲存用到 95% 不是「善用資源」，是**在製造故障**。

#### ★★★★ 空間怎麼分配才合理

一個 500 GB 系統碟 + 2 TB 資料碟的機器，建議這樣切：

| 用途 | 位置 | 容量 | 內容類型 |
| --- | --- | --- | --- |
| PVE 系統 ★★★★ | 系統碟，`maxroot=60` | 60 GB | — |
| swap ★★ | 系統碟 | 8～16 GB | — |
| `local`（只放 ISO 與範本）★★★ | 系統碟剩餘 | 依需要 | `iso,vztmpl` |
| VM 磁碟 ★★★★★ | **資料碟**，`lvmthin` 或 `zfspool` | 1.5 TB | `images,rootdir` |
| 備份 ★★★★★ | **另一台機器**（NFS 或 PBS） | 依保留策略 | `backup` |

> [!danger] ★★★★★ 備份絕對不要跟 VM 放在同一顆磁碟
> 這是資訊安全與備份的基本原則（3-2-1 法則的一部分）：
> **磁碟壞了，VM 跟備份一起沒了，等於沒有備份。**
> 勒索軟體加密主機時也會一併加密本機備份。
> 備份至少要放在另一台機器上，最好還有一份離線副本。
> 備份策略的完整說明見 [[050-01-03-06-svc-PVE-備份與還原]]。

### ★★★★ 設定空間告警

不要等到滿了才知道。PVE 有內建的告警機制。

```bash
# 檢查 lvm thin pool 的自動延伸設定
grep -E 'thin_pool_autoextend' /etc/lvm/lvm.conf
```

```text
	thin_pool_autoextend_threshold = 100
	thin_pool_autoextend_percent = 20
```

`threshold = 100` 代表**關閉自動延伸**（100 表示不作用）。
如果 VG 裡還有未分配空間，可以打開：

```ini
	thin_pool_autoextend_threshold = 80
	thin_pool_autoextend_percent = 20
```

意思是「用到 80% 時，自動把 pool 擴大 20%」。

> [!warning] ★★★★ 自動延伸只有在 VG 有剩餘空間時才有用
> 用 `vgs` 看 `VFree`：
> ```bash
> vgs
> ```
> ```text
>   VG  #PV #LV #SN Attr   VSize   VFree
>   pve   1   3   0 wz--n- <99.50g  4.75g
> ```
> 只剩 4.75 GB，自動延伸能救的有限。**這是緩衝，不是解方。**

更實際的做法是**自己寫檢查腳本 + cron**：

```bash
cat > /usr/local/bin/check-storage.sh <<'EOF'
#!/bin/bash
# PVE 儲存水位檢查，超標寄信
THRESHOLD=80
ALERT=""

# 根分割區
ROOT_PCT=$(df --output=pcent / | tail -1 | tr -dc '0-9')
if [ "$ROOT_PCT" -ge "$THRESHOLD" ]; then
  ALERT="${ALERT}根分割區已使用 ${ROOT_PCT}%\n"
fi

# LVM thin pool
while read -r lv data meta; do
  d=${data%%.*}; m=${meta%%.*}
  [ -z "$d" ] && continue
  if [ "$d" -ge "$THRESHOLD" ]; then
    ALERT="${ALERT}Thin pool ${lv} 資料已使用 ${data}%\n"
  fi
  if [ -n "$m" ] && [ "$m" -ge "$THRESHOLD" ]; then
    ALERT="${ALERT}Thin pool ${lv} metadata 已使用 ${meta}%\n"
  fi
done < <(lvs --noheadings -o lv_name,data_percent,metadata_percent --select 'lv_attr=~^t')

# ZFS 池
if command -v zpool >/dev/null 2>&1; then
  while read -r pool cap; do
    c=${cap%\%}
    if [ -n "$c" ] && [ "$c" -ge "$THRESHOLD" ]; then
      ALERT="${ALERT}ZFS 池 ${pool} 已使用 ${cap}\n"
    fi
  done < <(zpool list -H -o name,capacity 2>/dev/null)
fi

if [ -n "$ALERT" ]; then
  echo -e "$ALERT" | mail -s "[PVE] $(hostname -s) 儲存空間告警" root
fi
EOF
chmod +x /usr/local/bin/check-storage.sh
```

測試（先手動跑一次，把門檻調低確認邏輯正確）：

### ★★★★ 磁碟格式：raw 還是 qcow2

在目錄型儲存上建立 VM 磁碟時，PVE 會問你格式。

| 格式 | 快照 | Thin | 效能 | 適用 |
| --- | --- | --- | --- | --- |
| `raw` ★★★★ | ✘（除非底層支援） | 看底層 | **最好** | 區塊儲存、追求效能 |
| `qcow2` ★★★★ | **✔** | **✔** | 略差（約 5～10%） | 目錄型儲存、需要快照 |
| `vmdk` ★★ | 有限 | 有限 | 差 | 只在從 VMware 遷移時用 |

> [!note] ★★★★ 區塊型儲存上沒有這個選項
> 在 `lvmthin`、`zfspool`、`rbd` 上建磁碟時，PVE 不會問格式——
> 因為那些儲存**自己就提供快照與 thin**，磁碟一律以 `raw` 的形式存在 zvol / LV 上。
> 「格式」這個問題只有目錄型（`dir`、`nfs`、`cifs`）才存在。

### ★★★ 在儲存之間搬移磁碟

VM 磁碟可以線上搬到另一個儲存，**VM 不用關機**。

```bash
qm move-disk 100 scsi0 zfs-vm --delete 1
```

```text
create full clone of drive scsi0 (local-lvm:vm-100-disk-0)
transferred 0.0 B of 32.0 GiB (0.00%)
transferred 328.0 MiB of 32.0 GiB (1.00%)
...
transferred 32.0 GiB of 32.0 GiB (100.00%)
Removing image: 100% complete...done.
```

| 參數 | 意義 |
| --- | --- |
| `100` | VMID |
| `scsi0` | 要搬的磁碟代號（`qm config 100` 可查）|
| `zfs-vm` | 目標儲存 |
| `--delete 1` ★★★★ | 搬完**刪掉來源**。不加的話來源會留著變成 `unused0` |

> [!warning] ★★★★ 不加 `--delete 1` 的後果
> 來源磁碟會變成 `unused0:local-lvm:vm-100-disk-0` 留在設定裡，
> **繼續佔用原本的空間**。很多人搬完發現空間沒釋放就是這個原因。
>
> ```bash
> qm config 100 | grep unused
> ```
> ```text
> unused0: local-lvm:vm-100-disk-0
> ```
> 確認不需要後刪掉：
> ```bash
> qm set 100 --delete unused0
> ```

### ★★★ 儲存與備份的關係

一個常見的規劃錯誤是把 `local` 同時勾了 `backup`，然後就這樣用下去。

**正確的備份儲存規劃**：

| 層級 | 位置 | 保留 |
| --- | --- | --- |
| 快照 ★★★ | 同一個儲存（`lvmthin` / `zfspool`） | 幾小時～幾天，**不是備份** |
| 每日備份 ★★★★ | NFS／PBS，**另一台機器** | 7～14 份 |
| 每週／每月備份 ★★★★ | 同上或更遠端 | 4～12 份 |
| 離線副本 ★★★★★ | 磁帶或離線磁碟 | 依法規 |

> [!danger] ★★★★★ 快照不是備份
> 快照存在同一個儲存池裡。**池壞了、磁碟壞了、機器被勒索加密，快照一起沒**。
> 快照的用途是「升級前留個後路，五分鐘內能回復」，
> 不是「這台機器的資料有保障」。這兩件事要分清楚。

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| 上傳 ISO 時下拉選單沒有 `local-lvm` ★★★★ | `lvmthin` 是**區塊裝置**，不能放檔案；且它沒有 `iso` 內容類型 | 這是物理限制。ISO 要放目錄型或 NFS 儲存 |
| 備份跑不動，說 `no such storage` 或找不到目標 ★★★★ | 目標儲存沒有勾 `backup` 內容類型 | `pvesm set <id> --content backup,iso,...`，或後台勾選 |
| VM 突然變唯讀，日誌全是 `I/O error` ★★★★★ | **Thin pool 用完了**（`Data%` 或 `Meta%` 到 100%） | 立刻擴充 pool（`lvextend`）或刪掉不需要的磁碟／備份；救回後在客體 `fsck`。見下方「pool 滿了的處置」 |
| VM 裡 `df` 顯示很空，主機卻說滿了 ★★★★★ | Thin Provisioning 的資訊落差；客體看宣告值，主機看實際配置 | 永遠以主機端 `lvs` / `zpool list` 為準 |
| VM 裡刪了 50 GB，`lvs` 的 `Data%` 完全沒降 ★★★★ | discard/TRIM 沒打通 | 磁碟勾 `Discard`、用 VirtIO SCSI、客體跑 `fstrim -av` |
| Web 後台超慢、一直轉圈，但 VM 都正常 ★★★★★ | 某個 NFS/CIFS 儲存的伺服器失聯，`pvestatd` 卡在 hard mount | `pvesm set <id> --disable 1`、`umount -f -l /mnt/pve/<id>`、`systemctl restart pvestatd` |
| 根分割區滿了，設定改不動、VM 開不起來 ★★★★★ | ISO／備份放在 `local`（位於 `/`） | `du -sh /var/lib/vz/*` 找兇手，刪掉或搬走；長期解是把 `local` 的 `content` 收緊 |
| 開機卡在 emergency mode ★★★★★ | fstab 裡的資料碟壞掉／不存在，且**沒加 `nofail`** | 主控台登入，把該行加上 `nofail` 或註解掉，`systemctl daemon-reload && reboot` |
| NFS 儲存 status 是 `active`，備份卻寫入失敗 ★★★★ | NFS export 是 `ro`，或 `root_squash` 把 root 降權 | 到 NFS 伺服器改 export 選項為 `rw`（必要時 `no_root_squash`），重新 `exportfs -ra` |
| 遷移 VM 到另一節點後開不了機，說找不到磁碟 ★★★★★ | 本機儲存被誤設 `--shared 1`，PVE 以為不用複製資料 | `pvesm set <id> --shared 0`，重新做一次遷移（會實際複製磁碟） |
| VM 的 Snapshot 按鈕是灰的 ★★★ | 磁碟在 `lvm`（thick）或 `iscsi` 上，這兩種不支援快照 | 把磁碟 `qm move-disk` 到 `lvmthin` / `zfspool` / qcow2 目錄儲存 |
| `qm move-disk` 之後原儲存空間沒釋放 ★★★★ | 沒加 `--delete 1`，來源變成 `unused0` 留著 | `qm config <id> \| grep unused` 確認後 `qm set <id> --delete unused0` |
| ZFS 池用到 85% 之後寫入變超慢 ★★★★ | ZFS 超過約 80% 後配置策略改變，開始「找空間」而非「找快的位置」 | 刪快照／舊資料，或加 vdev 擴充；**80% 是規劃時就要留的餘裕** |
| `zpool status` 出現 `DEGRADED` ★★★★★ | mirror 或 RAIDZ 有成員磁碟失效 | `zpool status -v` 找出壞碟，換碟後 `zpool replace`。**不要拖**，再壞一顆就全毀 |
| `pvesm remove` 之後空間沒有變多 ★★★ | `remove` 只刪儲存定義，不刪磁碟上的資料 | 手動去該路徑刪檔案 |
| `pvesm status` 某儲存顯示 `inactive` ★★★★ | 底層掛載掉了、網路儲存失聯、或被手動 disable | `mount \| grep <path>`、`ping` 儲存伺服器、`pvesm set <id> --disable 0` |
| 加了新磁碟但 `lsblk` 看不到 ★★★ | 熱插拔後核心還沒重新掃描 | `echo "- - -" > /sys/class/scsi_host/host0/scan`（逐一 host 試），或重開機 |

## 安全性注意事項

### ★★★★★ 備份儲存的存取控制

備份檔裡有**整台 VM 的完整內容**：資料庫、設定檔、私鑰、憑證。
一份 `vzdump` 備份等於一整台伺服器。

| 措施 | 說明 |
| --- | --- |
| NFS export 限制來源 IP ★★★★★ | 只允許 PVE 節點的管理 IP，不要 `*` |
| 備份儲存放獨立網段 ★★★★ | 與服務網段隔離 |
| **不要**讓 VM 掛得到備份儲存 ★★★★★ | VM 被入侵時，攻擊者就能刪光所有備份 |
| PBS 的 prune 權限與備份權限分開 ★★★★ | 避免同一組憑證既能寫又能刪 |
| 離線副本 ★★★★★ | 勒索軟體防護的最後一道 |

> [!danger] ★★★★★ 勒索軟體會專門找備份下手
> 現代勒索軟體的標準流程是：先掃描網路上所有可寫的共用資料夾與備份儲存，
> **把備份加密或刪除**，才開始加密正式資料。
> 「線上可寫的備份」在這種攻擊下等於沒有備份。

### ★★★★ iSCSI 與 NFS 的網路安全

| 協定 | 風險 | 對策 |
| --- | --- | --- |
| NFSv3 ★★★★★ | 幾乎沒有認證，**知道 IP 就能掛** | 用 NFSv4 + Kerberos，或至少嚴格限制 export 的來源網段 |
| NFSv4 ★★★ | 預設仍是明文傳輸 | 走獨立的儲存網段，不要跟使用者網段混在一起 |
| iSCSI ★★★★★ | 預設**無認證、無加密** | 開啟 CHAP 認證；**一定要放獨立的儲存 VLAN** |
| CIFS ★★★ | 舊版 SMB1 有已知漏洞 | 強制 SMB3，設定簽章 |

> [!warning] ★★★★★ 儲存流量絕對要跟一般網路分離
> 除了安全，還有效能與穩定性的理由：
> 儲存流量對延遲極度敏感，跟使用者流量搶頻寬會造成 VM 的 I/O 抖動甚至逾時。
> 正式環境的標準做法是**獨立的儲存 VLAN 或獨立實體網路**。
> VLAN 規劃見 [[040-01-03-guide-網路設備-VLAN概念與規劃]]。

### ★★★★ 磁碟報廢時的資料清除

VM 磁碟裡有機關的業務資料。磁碟報廢、退租、送修前必須清除。

| 情況 | 做法 |
| --- | --- |
| 刪 VM 磁碟 ★★★ | LVM-Thin 與 ZFS 刪除後區塊會被回收，但**不保證覆寫** |
| 整顆碟報廢（HDD）★★★★ | 多次覆寫（`shred`）或實體銷毀 |
| 整顆碟報廢（SSD）★★★★★ | 覆寫**對 SSD 不可靠**（wear leveling），用廠商的 Secure Erase 或實體銷毀 |
| 從一開始就加密 ★★★★★ | 用 LUKS 全碟加密，報廢時銷毀金鑰即可 |

設備生命週期與報廢流程見 [[040-02-12-guide-機房-設備生命週期管理]]。

### ★★★ 誰能建立與刪除儲存

PVE 的權限模型裡，儲存相關權限是分開的：

| 權限 | 能做什麼 |
| --- | --- |
| `Datastore.Allocate` ★★★★★ | **建立與刪除儲存**，等同基礎設施管理員 |
| `Datastore.AllocateSpace` ★★★★ | 在既有儲存上建立磁碟 |
| `Datastore.AllocateTemplate` ★★★ | 上傳 ISO 與範本 |
| `Datastore.Audit` ★★ | 只能看 |

一般使用者只該有 `AllocateSpace` 與 `Audit`。詳見
[[050-01-03-08-guide-PVE-使用者權限與API]]。

> [!question]- 測驗答案
> **Q1.** 因為 `local-lvm` 的類型是 **`lvmthin`，是區塊裝置**，上面沒有檔案系統，

> （`dir` / `nfs` / `cifs` / `cephfs`）上。★★★★

>
> **Q2.** **錯。** 這是 Thin Provisioning 最危險的資訊落差：
> 客體看到的是**宣告容量**，主機端看到的才是**實際配置量**。
> VM 裡顯示還有 60% 可用時，底層 thin pool 完全可能已經 100%。
> 判斷真相**永遠**要在主機端用 `lvs` / `zpool list`。★★★★★
> （見「觀念說明 → Thin Provisioning」）
>
> **Q3.** `data_percent` 是**資料**用掉 thin pool 的比例，
> `metadata_percent` 是 **metadata pool**（記錄哪個區塊屬於哪個 LV）的使用比例。
> **metadata 滿掉比較難救**——資料滿了還能刪東西擴充，
> metadata 滿掉會讓 thin pool 進入無法寫入的狀態，救援極為困難。
> 而且在快照多、VM 多的環境裡，**metadata 常常比 data 先爆**。★★★★★
> （見「觀念說明 → Thin Provisioning」與「常見錯誤」）
>
> **Q4.** **（B）**。`--shared 1` 是在告訴 PVE「每個節點都看得到同一份資料」，
> 於是遷移時 PVE **不會複製磁碟**，直接把 VM 設定搬到對端啟動，
> 結果對端根本沒有那顆磁碟，開不了機。更糟的情況是兩個節點同時寫入
> 同一份 LVM 中繼資料造成損毀。★★★★★
> （見「加掛儲存方式四」）
>
> **Q5.** 三個環節：（1）VM 磁碟要勾 **`Discard`**；
> （2）磁碟匯流排用 **VirtIO SCSI**（`virtio-scsi-single`）；
> （3）客體裡要執行 **`fstrim`**（或啟用 `fstrim.timer`）。
> 三者缺一，刪除的區塊都不會回報給底層儲存，空間就還不回去。★★★★
> （見「觀念說明 → 刪檔案不會還空間」）
>
> **Q6.** 第一個懷疑**某個網路儲存（NFS/CIFS）的伺服器失聯**。
> NFS 預設是 hard mount，`pvestatd` 定期掃描儲存狀態時會卡在 D state，
> 整個管理介面跟著卡住，即使 VM 本身完全正常。
> **現場第一步是把那個儲存 disable**：`pvesm set <id> --disable 1`，
> 接著 `umount -f -l /mnt/pve/<id>`、`systemctl restart pvestatd`。★★★★★
> （見「加掛儲存方式三」與「常見錯誤」）
>
> **Q7.** **錯。** `pvesm remove` **只刪除 `/etc/pve/storage.cfg` 裡的定義**，
> 磁碟上的檔案原封不動。這是刻意的安全設計（避免誤刪），
> 但也代表那些備份檔會**繼續佔用空間**。要釋放空間必須自己去該路徑刪檔案。★★★
> （見「修改與移除儲存」）
>
> **Q8.** 因為沒有 `nofail` 時，只要該裝置不存在或掛載失敗，
> systemd 的 `local-fs.target` 就會失敗，**整台機器停在 emergency mode 開不了機**。
> 對 hypervisor 來說，「一顆放備份的資料碟壞掉導致所有 VM 都起不來」
> 是完全不能接受的。`nofail` 讓開機在掛載失敗時繼續進行。★★★★★
> （見「加掛儲存方式一」與「練習 6」）
>
> **Q9.** ★★★★
> ```text
> 可用上限 = 190 GB × 80% = 152 GB
> 已使用   = 190 GB × 20% =  38 GB
> 剩餘     = 152 − 38     = 114 GB
> 台數     = 114 ÷ 30     = 3.8 → 3 台
> ```
> 兩個重點：分母要用 **80% 而不是 100%**（否則就是規劃到爆炸為止）；
> 算的是**實際用量**不是宣告容量（超賣是允許的，守住實際用量才是關鍵）。
> （見「進階應用 → 空間規劃」）
>
> **Q10.** 應該反對，理由是**網路頻寬不足**。Ceph 每次寫入都要同步複寫到多個節點，
> 1 GbE 的頻寬與延遲會讓 VM 的 I/O 慢到不能用，
> 而且 recovery（換碟或節點回來時的資料重建）會直接把網路塞爆。
> Ceph 的門檻是**三節點以上 + 10 GbE 以上的專用儲存網路 + 每台多顆 SSD**。
> 如果目的只是「共享儲存放 ISO 與備份」，**NFS 就夠了，簡單十倍**；
> 如果要 VM 磁碟的高可用，先評估網路升級的成本。★★★★★
> （見「觀念說明 → Ceph 概覽」）
