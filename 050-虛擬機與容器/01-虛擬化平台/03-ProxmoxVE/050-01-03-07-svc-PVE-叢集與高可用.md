# PVE 叢集與高可用

> [!abstract] 這篇你會學到
> - PVE 叢集底下的兩個引擎：**corosync**（誰還活著）與 **pmxcfs**（`/etc/pve` 這個會自己同步的檔案系統）
> - ★★★★★ **Quorum 到底在算什麼**、為什麼要奇數節點、少數方會發生什麼事

> - **線上遷移（live migration）** 與 **離線遷移** 的差別、各自的前提條件
> - **HA 群組、priority、nofailback**，以及 **fencing 是靠 watchdog 自我重開**這件事
> - ★★★★★ **節點失聯時的正確處置順序 —— 不要急著重開**
> - 叢集拆除、節點移除、以及「移除過的節點名稱不能直接重用」的原因

## 觀念說明

### 一、PVE 叢集是由兩個東西撐起來的 ★★★★★

很多人把「PVE 叢集」想成一個東西，其實是**兩層**：

```
┌──────────────────────────────────────────────────────────────┐
│  Web UI / pvesh / qm / pct / ha-manager                      │
├──────────────────────────────────────────────────────────────┤
│  pmxcfs  ——  /etc/pve                            ★★★★★      │
│    一個 FUSE 檔案系統，把叢集設定「即時同步」到每個節點       │
│    寫入時需要 Quorum；沒有 Quorum 就變成唯讀                  │
├──────────────────────────────────────────────────────────────┤
│  corosync  ——  成員關係與 Quorum                 ★★★★★      │
│    誰還活著？多數方在哪一邊？                                 │
│    走 kronosnet（corosync 3），單播，可多條 link              │
├──────────────────────────────────────────────────────────────┤
│  網路（★★★★★ 這一層的延遲決定整個叢集穩不穩）                │
└──────────────────────────────────────────────────────────────┘
```

| 元件 | 服務名 | 職責 | 重要度 |
| --- | --- | --- | --- |
| ★★★★★ **corosync** | `corosync.service` | 成員偵測、Quorum 計算、訊息排序 | ★★★★★ |
| ★★★★★ **pmxcfs** | `pve-cluster.service` | 提供 `/etc/pve`，把設定同步到全叢集 | ★★★★★ |
| ★★★★ **pve-ha-crm** | `pve-ha-crm.service` | 叢集層的 HA 決策者（只有 master 那台在做決定） | ★★★★ |
| ★★★★ **pve-ha-lrm** | `pve-ha-lrm.service` | 每個節點的 HA 執行者，負責餵 watchdog | ★★★★★ |
| ★★★ **watchdog-mux** | `watchdog-mux.service` | 把 watchdog 裝置分給 LRM 用 | ★★★★ |
| ★★★ **pveproxy / pvedaemon** | — | Web UI 與 API，跨節點請求會轉發 | ★★★ |

> [!note] ★★★★★ `/etc/pve` 不是一般目錄
> 它是 pmxcfs 掛上來的 FUSE 檔案系統，底層資料庫在 `/var/lib/pve-cluster/config.db`。
> - 你在任何一個節點寫進去，**其他節點會立刻看到**
> - ★★★★★ **失去 Quorum 時它會變成唯讀** —— 這時你連 `qm set` 都會失敗
> - ★★★★★ **不要用 `rsync` 或手動複製去「修」它**，會直接把叢集狀態弄壞
>
> 常見誤解：「我把 `/etc/pve/qemu-server/100.conf` 複製到另一台就搬好了」——
> 在叢集裡這是多餘且危險的，pmxcfs 本來就同步；在非叢集節點之間這才是手動搬遷的做法。

### 二、Quorum：叢集在算的那個多數決 ★★★★★

**Quorum（法定人數）= 允許「做決定」所需的最少票數。**

PVE 預設每個節點 1 票，Quorum 門檻是：

```
        ┌ 總票數 ┐
Quorum = │ ───── │ + 1        （整數除法，即 floor(N/2) + 1）
        └   2   ┘

  N=2  →  2/2+1 = 2   ★★★★★ 兩台都要活著才有 Quorum（掛一台就全掛）
  N=3  →  3/2+1 = 2   ★★★★★ 可以掛 1 台
  N=4  →  4/2+1 = 3   ★★★★  也只能掛 1 台（跟 3 台一樣，但風險更高）
  N=5  →  5/2+1 = 3   可以掛 2 台
  N=6  →  6/2+1 = 4   只能掛 2 台
  N=7  →  7/2+1 = 4   可以掛 3 台
```

★★★★★ **這就是「為什麼要奇數節點」的全部理由**：

| 節點數 | Quorum 門檻 | 可容忍故障 | 評語 | 重要度 |
| --- | --- | --- | --- | --- |
| 1 | 1 | 0 | 單機，不是叢集 | ★ |
| ★★★★★ **2** | **2** | **0** | ★★★★★ **最糟的組態**：可用性比單機還差，任一台維護就失去 Quorum | ★★★★★ |
| 2 + QDevice | 2（共 3 票） | 1 | ★★★★★ **兩節點的正解** | ★★★★★ |
| ★★★★★ **3** | 2 | 1 | ★★★★★ **機關環境最常見也最合理的起點** | ★★★★★ |
| 4 | 3 | 1 | ★★★★ **多花一台錢，容錯沒變好** | ★★★★ |
| 5 | 3 | 2 | 需要更高可用性時的下一階 | ★★★ |
| 6 | 4 | 2 | 同樣是「多一台但容錯沒進步」 | ★★ |

> [!danger] ★★★★★ 偶數節點的真正問題不是「數字不好看」
> 是**網路被切成兩半時，兩邊票數相同，誰都拿不到多數**。
> 4 台被交換器故障切成 2+2 → 兩邊都是 2 票 < 3 → **整個叢集全部凍結**。
> 換成 5 台切成 3+2 → 3 票那邊繼續運作，2 票那邊停下來，這才是我們要的行為。

### 三、少數方會發生什麼事 ★★★★★

失去 Quorum 的節點**不會**繼續我行我素，PVE 會刻意把它變殘廢：

| 影響 | 說明 | 重要度 |
| --- | --- | --- |
| ★★★★★ `/etc/pve` **變唯讀** | 不能改 VM 設定、不能建 VM、不能改防火牆規則 | ★★★★★ |
| ★★★★ **Web UI 上其他節點顯示灰色 `?`** | 看不到對方狀態 | ★★★★ |
| ★★★★ **不能啟動新的 VM／CT** | 因為要寫 `/etc/pve` 的鎖 | ★★★★ |
| ★★★ **已經在跑的 VM 會繼續跑** | ★★★★★ **注意：沒有 HA 的話它不會被停掉** | ★★★★★ |
| ★★★★★ **有 HA 資源時，LRM 停止餵 watchdog → 節點約 60 秒後自我重開** | 這就是 fencing | ★★★★★ |

```text
（★★★★★ 失去 Quorum 時你會看到的典型錯誤）
root@pve3:~# qm set 101 --memory 8192
cluster not ready - no quorum? (500)

root@pve3:~# touch /etc/pve/test
touch: cannot touch '/etc/pve/test': Permission denied
```

★★★★★ **看到 `cluster not ready - no quorum?` 就代表你在少數方，
不要再往下打指令，先去看網路。**

### 四、腦裂（split-brain）：現場最貴的一種故障 ★★★★★

腦裂 = **兩邊都以為自己是唯一活著的那個，同時對同一份資料寫入。**

```
      正常                                    腦裂
 ┌────────────────┐                  ┌──────────┐   ┌──────────┐
 │ pve1 pve2 pve3 │                  │pve1 pve2 │ ✂ │  pve3    │
 │  共享儲存 LUN  │                  │ 3 票     │   │  1 票    │
 └────────────────┘                  └────┬─────┘   └────┬─────┘
   VM 101 只在 pve1 跑                    │              │
                                     VM101 在這啟動   VM101「也」在這跑
                                          └──────┬───────┘
                                           同一個磁碟映像
                                      ★★★★★ 兩個 kernel 同時寫入
                                      ★★★★★ 檔案系統結構直接毀掉
```

> [!danger] ★★★★★ 腦裂造成的是「無法用 fsck 修好」的損壞
> 兩個作業系統同時掛載並寫入同一個 block device，
> 各自有各自的 journal、各自的快取，**互相覆蓋對方的 metadata**。
> 結果通常是：
> - ext4／XFS 結構性損毀，`fsck` 只能把檔案丟進 `lost+found`
> - 資料庫檔案（InnoDB／PostgreSQL）永久毀損
> - ★★★★★ **只能從備份還原** —— 見 [[050-01-03-06-svc-PVE-備份與還原]]
>
> 這也是為什麼**任何 HA 設計的第一要務不是「快速接手」，而是「確定舊的那台真的死了」**。

★★★★★ **PVE 用三道防線避免腦裂**：

| 防線 | 機制 | 重要度 |
| --- | --- | --- |
| 1. ★★★★★ **Quorum** | 少數方 `/etc/pve` 唯讀，開不了新 VM | ★★★★★ |
| 2. ★★★★★ **Watchdog fencing** | 有 HA 的節點失去 Quorum 後**自己重開** | ★★★★★ |
| 3. ★★★★ **HA CRM 的等待期** | CRM 要等到**確信**舊節點已被 fence 才在別台啟動 | ★★★★★ |

★★★★★ **而人為破壞這三道防線最常見的方式，就是「節點看起來怪怪的，先重開看看」**
與「打了 `pvecm expected 1` 讓它動起來」。詳見「節點失聯時的正確處置順序」。

### 五、corosync 網路為什麼一定要獨立 ★★★★★

corosync 靠**定時互相發訊息**判斷成員死活，預設 token timeout 是**毫秒等級**。
它怕的不是頻寬不夠，是**延遲抖動（jitter）**。

| 情境 | 會發生什麼 | 重要度 |
| --- | --- | --- |
| ★★★★★ **備份流量塞爆網卡** | corosync 封包延遲 → 節點被判定失聯 → HA fence → **節點無故重開** | ★★★★★ |
| ★★★★★ **VM 遷移走同一條線** | 遷移時瞬間吃滿頻寬，同上 | ★★★★★ |
| ★★★★ **儲存流量（NFS／iSCSI／Ceph）同線** | 儲存尖峰時整個叢集抖動 | ★★★★★ |
| ★★★★ **交換器 STP 收斂 30 秒** | 拔插線材造成短暫斷線 → fence | ★★★★ |
| ★★★ **走 WAN／跨機房** | RTT 過高，官方不建議 | ★★★★ |

> [!tip] ★★★★★ 實務建議的網段切法
> ```
> vmbr0 / 管理網段     10.0.10.0/24   Web UI、SSH
> ★★★★★ 專線 corosync  10.0.20.0/24   ← 獨立實體網卡、獨立 VLAN，不跑別的東西
> 遷移／儲存網段        10.0.30.0/24   ← 頻寬大的那條（10G）
> VM 業務網段          由 vmbr1 承載
> ```
> 沒有多餘網卡時的**最低要求**：
> ★★★★ **至少加一條備援 link（link1）走另一個網段**，
> 讓單一網段抖動不會直接拖垮 Quorum。

★★★ **corosync 3 已經不用 multicast**，改用 kronosnet 的單播，
所以「交換器要開 IGMP snooping」這個舊時代的要求已經不適用了 ——
但**交換器上不要對這個 VLAN 做限速、風暴抑制**仍然重要。

### 六、遷移（migration）的兩種模式 ★★★★★

| 模式 | 指令 | VM 狀態 | 前提 | 重要度 |
| --- | --- | --- | --- | --- |
| ★★★★★ **線上遷移（live）** | `qm migrate <id> <node> --online` | ★★★★★ **不關機**，記憶體逐步搬過去 | ★★★★★ **磁碟在共享儲存上**（或加 `--with-local-disks`）、CPU 相容 | ★★★★★ |
| ★★★★ **離線遷移** | `qm migrate <id> <node>` | ★★★★ **VM 必須是關機狀態** | 沒有共享儲存也可以（會複製磁碟） | ★★★★ |
| ★★★★ **容器遷移** | `pct migrate <id> <node>` | ★★★★★ **LXC 沒有真正的 live migration** | 用 `--restart` 讓它「關機→搬→開機」 | ★★★★★ |

> [!warning] ★★★★★ LXC 容器不能線上遷移
> 這是現場最常被誤會的一點。`pct migrate 201 pve2 --restart` 的意思是
> **停掉容器、搬過去、再開起來**，中間有停機時間（通常數秒到數十秒）。
> 需要真正不中斷的服務，**不要用 LXC，用 VM**。

**線上遷移在做什麼**（簡化）：

```
1. 目標節點開一個「空的」QEMU 行程，停在暫停狀態
2. 來源持續把記憶體頁複製過去（pre-copy）
3. 一邊複製，一邊追蹤這期間被改寫的頁（dirty page）
4. 重複 2～3，直到剩下的 dirty page 少到可以在極短時間搬完
5. ★★★★★ 短暫暫停來源（通常數十毫秒到數百毫秒）→ 搬最後一批 + CPU 狀態
6. 目標端恢復執行，來源端 QEMU 結束
```

★★★★★ **步驟 4 是失敗的主因**：
如果 VM 一直在瘋狂寫記憶體（大型資料庫、記憶體壓測），
dirty page 產生的速度超過網路搬運速度，**遷移會永遠收斂不了**。
這時要嘛加大遷移網路頻寬，要嘛選離峰時段，要嘛改成離線遷移。

**線上遷移的前提條件** ★★★★★：

| 條件 | 說明 | 沒滿足會怎樣 | 重要度 |
| --- | --- | --- | --- |
| ★★★★★ **磁碟在兩邊都存取得到** | 共享儲存（NFS／iSCSI／Ceph）；或用 `--with-local-disks` 複製 | 直接拒絕遷移 | ★★★★★ |
| ★★★★★ **目標節點 CPU 支援來源的 CPU 旗標** | `host` type 在異質 CPU 之間會失敗 | 遷移中斷或 guest crash | ★★★★★ |
| ★★★★ **兩邊 bridge 名稱一致** | `vmbr1` 在目標節點也要存在 | 遷移後網路不通 | ★★★★★ |
| ★★★★ **沒有直通硬體** | PCIe passthrough／USB 綁定的 VM 不能 live migrate | 拒絕遷移 | ★★★★★ |
| ★★★ **兩邊有相同名稱的儲存** | 或用 `--targetstorage` 指定 | 找不到儲存 | ★★★★ |
| ★★★ **SSH 互通** | 節點之間用 root SSH 建立遷移隧道 | `ERROR: migration aborted` | ★★★★ |

### 七、HA 與 fencing：接手之前要先確定舊的死了 ★★★★★

**HA（High Availability）在 PVE 的定義很窄**：
「被納管的 VM／CT，在它所在的節點掛掉之後，自動在別的節點重新啟動。」

★★★★★ **它不是零停機**。VM 是**重新開機**，不是接續執行。
對 guest 來說等同於**斷電後再開機**。

```
節點 pve3 突然斷電
   │
   ├─ 0s     corosync 在其他節點上察覺 pve3 沒回應
   ├─ ~數秒   pve3 被移出成員清單，pve1+pve2 仍有 Quorum
   ├─ ★★★★★ CRM 進入等待期，等到「確定 pve3 已被 fence」
   │          （對斷電的節點：靠 watchdog 時間上限推算）
   ├─ ~60s+  CRM 決定把 vm:101 指派給 pve2
   ├─         pve2 的 LRM 執行 qm start 101
   └─ ~1-3 分鐘後 VM 在 pve2 上開機完成
```

**fencing（隔離）在 PVE 是「自我隔離」** ★★★★★：

| 做法 | 說明 | 重要度 |
| --- | --- | --- |
| ★★★★★ **watchdog self-fencing（預設）** | 節點上的 LRM 定期餵 watchdog；失去 Quorum 就停止餵 → 硬體/軟體 watchdog 在約 60 秒後**強制重開這台機器** | ★★★★★ |
| ★★★ `softdog` | 核心模組模擬的 watchdog，PVE 預設 | ★★★★ |
| ★★★★ **IPMI / 硬體 watchdog** | 主機板提供，比 softdog 可靠（softdog 在 kernel 卡死時可能也不動） | ★★★★ |

> [!note] ★★★★★ 為什麼是「自己重開」而不是「別人把它電源切掉」
> 傳統叢集用 STONITH（遠端切電）。PVE 選擇讓**失去 Quorum 的節點自己重開**，
> 理由是：**不需要額外的電源管理設備，也不會因為 IPMI 網路也斷了而 fence 失敗**。
> 代價是：★★★★★ **CRM 必須「等夠久」才能確信對方已經重開**，
> 所以 HA 接手一定有一分鐘以上的延遲，**沒辦法更快**。

> [!danger] ★★★★★ 啟用 HA 之後，節點會「自己重開」是正常行為
> 很多人第一次看到 `pve3` 莫名其妙重開，以為硬體壞了，
> 其實是 corosync 網路抖動 → 失去 Quorum → watchdog fence。
> ★★★★★ **這是設計，不是 bug**。要解決的是網路，不是關掉 HA。

**HA 群組（HA Group）** ★★★★：

| 設定 | 意義 | 重要度 |
| --- | --- | --- |
| ★★★★ `nodes` | 這個群組允許跑在哪些節點，可加優先權 `pve1:2,pve2:1` | ★★★★ |
| ★★★★ `restricted` | ★★★★★ 開啟後**只能**在清單內的節點跑；節點全掛就停在那不啟動 | ★★★★ |
| ★★★★ `nofailback` | ★★★★★ 原節點復活後**不要自動搬回去** —— 避免二次中斷 | ★★★★★ |

★★★★★ **`nofailback` 幾乎永遠該開。**
不開的話：節點修好上線 → VM 又自動搬回去（再重開一次）→ 使用者被中斷兩次。

## 進階應用

### 一、兩節點叢集的正解：QDevice ★★★★★

**問題**：兩個節點，Quorum = 2，**掛一台就全掛**，連維護重開一台都不行。

**解法**：找第三方來當「見證者（witness）」，只投票、不跑 VM。

```
     ┌──────────┐        ┌──────────┐
     │  pve1    │        │  pve2    │
     │  1 票    │────────│  1 票    │
     └────┬─────┘        └─────┬────┘
          │                    │
          └────────┬───────────┘
                   │
          ┌────────▼─────────┐
          │  QDevice（qnetd）│  ★★★★★ 1 票
          │  一台小 Linux    │  可以是既有的 NAS／管理機
          │  不跑 VM         │  只需要能連到兩個節點
          └──────────────────┘

  總票數 3，Quorum = 2
  ★★★★★ 掛掉 pve1 → pve2 + QDevice = 2 票 → 繼續運作
  ★★★★★ 掛掉 QDevice → pve1 + pve2 = 2 票 → 繼續運作
```

> QDevice 對資源要求極低，實務上可以放在：
> - 機房裡的**管理跳板機**
> - **NAS**（如果它能跑 Debian 套件或容器）
> - 另一台跟 PVE 無關的**小型伺服器／工控機**
>
> ★★★★★ **但不要放在你要保護的那兩台 PVE 上，也不要放在同一台 UPS 之外沒有備援的地方。**

| --- | --- | --- |
| ★★★★★ `migration: network=10.0.30.0/24` | **遷移流量走這個網段** —— 讓遷移不要壓垮 corosync | ★★★★★ |
| ★★★★ `migration: type=secure` | ★★★★★ **預設，走 SSH 加密**；資料完整加密但 CPU 開銷高 | ★★★★★ |
| ★★★ `migration: type=insecure` | ★★★★★ **不加密，只能用在完全隔離的專線上**；速度快很多 | ★★★★★ |
| ★★★★ `ha: shutdown_policy=migrate` | ★★★★★ **節點正常關機時，HA VM 先遷走再關** | ★★★★★ |

> [!danger] ★★★★★ `type=insecure` 的風險
> 遷移過程中，**VM 的整份記憶體內容以明文在網路上傳輸** ——
> 包含密碼、金鑰、資料庫內容。
> 只有在**實體隔離、沒有其他設備接入的專用網段**才可以用。
> 機關環境有稽核要求時，★★★★★ **一律維持 `secure`**。

**`ha: shutdown_policy` 的四種值** ★★★★：

| 值 | 節點關機時 HA VM 的處置 | 重要度 |
| --- | --- | --- |
| ★★★★★ `migrate` | **先線上遷移到別的節點**，再讓節點關機（維護時最想要的） | ★★★★★ |
| ★★★★ `conditional`（預設） | reboot 時原地等待、shutdown 時搬走 | ★★★★ |
| ★★★ `failover` | 直接關掉 VM，讓 HA 在別台重開（會有停機） | ★★★ |
| ★★ `freeze` | 凍結 HA 狀態，什麼都不做 | ★★ |

### 三、HA 群組與資源設定 ★★★★★

```bash
# 建立 HA 群組
ha-manager groupadd prod-group --nodes "pve1:2,pve2:1,pve3:1" --nofailback 1
```

```bash
cat /etc/pve/ha/groups.cfg
```

```ini
group: prod-group
	nodes pve1:2,pve2:1,pve3:1
	nofailback 1
```

★★★★ `pve1:2` 的 `2` 是**優先權，數字大的優先**。
所以正常情況 VM 會在 pve1，pve1 掛了才到 pve2／pve3。

```bash
# 把 VM 納入 HA
ha-manager add vm:101 --group prod-group --state started --max_restart 2 --max_relocate 1
```

| 參數 | 意義 | 重要度 |
| --- | --- | --- |
| ★★★★★ `--state started` | HA 要**維持這個 VM 是開機的** | ★★★★★ |
| ★★★★ `--state stopped` | HA 納管但維持關機（維護中用） | ★★★★ |
| ★★★★★ `--state ignored` | ★★★★★ **HA 完全不管它**，但保留設定 —— 排查問題時的安全開關 | ★★★★★ |
| ★★★ `--max_restart` | 在**同一節點**上重試啟動幾次 | ★★★ |
| ★★★ `--max_relocate` | 換到**別的節點**重試幾次 | ★★★ |

```bash
ha-manager status
```

```text

master pve1 (active, Tue Sep  2 11:40:12 2026)
lrm pve1 (active, Tue Sep  2 11:40:15 2026)
lrm pve2 (active, Tue Sep  2 11:40:14 2026)
lrm pve3 (active, Tue Sep  2 11:40:13 2026)

```

★★★★★ **這五種狀態你要看得懂**：

| 顯示 | 意義 | 重要度 |
| --- | --- | --- |
| ★★★★★ `quorum OK` | 叢集有多數決；顯示其他值代表 HA 不會做任何事 | ★★★★★ |
| ★★★★ `master pveX (active, ...)` | 目前的 CRM 決策者 | ★★★★ |
| ★★★★★ `lrm pveX (active, ...)` | 該節點的執行者正常，**正在餵 watchdog** | ★★★★★ |
| ★★★★ `lrm pveX (idle, ...)` | ★★★★ 該節點上沒有 HA 資源，**沒有啟用 watchdog** | ★★★★ |
| ★★★★★ `lrm pveX (wait_for_agent_lock)` | ★★★★★ **拿不到鎖**，通常是 Quorum 有問題 | ★★★★★ |
| ★★★★ `service vm:101 (pve1, started)` | 資源目前在哪、目標狀態是什麼 | ★★★★ |

```bash
# 詳細狀態
ha-manager status --verbose
```

```bash
# 讓 HA 幫你搬（★★★★ 不要對 HA 資源直接用 qm migrate）
ha-manager migrate vm:101 pve2
```

> [!warning] ★★★★★ HA 納管的資源不要直接 `qm migrate`
> `qm migrate` 搬完之後，CRM 可能因為 HA 群組的優先權設定又把它搬回去，
> 造成 VM 被搬來搬去。★★★★★ **HA 資源一律用 `ha-manager migrate` / `ha-manager relocate`。**
>
> | 指令 | 差別 |
> | --- | --- |
> | `ha-manager migrate` | ★★★★ 嘗試**線上遷移** |
> | `ha-manager relocate` | ★★★★ **停掉再在目標節點啟動**（適用不能 live migrate 的情況） |

### 四、節點維護模式 ★★★★★

要對某個節點做韌體更新、換記憶體時，**不要直接關機**：

```bash
# 讓 HA 把這個節點上的資源都搬走，且之後不會再指派過來

```

```bash

```

lrm pve2 (maintenance mode, ...)
lrm pve3 (active, ...)

★★★★★ **標準維護流程**：

```
1. ha-manager crm-command node-maintenance enable pveX   ← HA 資源搬走

5. 關機／維護
6. 開機 → pvecm status 確認回到叢集
7. ha-manager crm-command node-maintenance disable pveX
```

### 六、`pvecm expected`：最危險的那個指令 ★★★★★

```bash
pvecm expected 1
```

> [!danger] ★★★★★ 這個指令會把 Quorum 門檻硬改成 1
> 意思是「我宣告只需要 1 票就算多數」，**等於把腦裂防護關掉**。
>
> ★★★★★ **只有在下列條件全部成立時才可以用**：
> 1. 你**親眼確認**（實體到場、或 IPMI 確認電源狀態）其他節點**真的已經斷電或關機**
> 2. 你確定其他節點**不會在你操作期間自己開機起來**（拔電源、拔網路線）
> 3. 你的目的是**緊急救援**（例如 3 台掛 2 台，要把服務先撐起來）
> 4. ★★★★★ 你已經**接受可能要從備份還原**的風險
>
> ★★★★★ **絕對不能因為「網路好像斷了但 VM 還在跑」就下這個指令** ——
> 這正是製造腦裂的標準步驟。
>
> 效果是**暫時的**（重開 corosync 就恢復），
> 但期間造成的資料損毀是**永久的**。

### 七、當 `/etc/pve` 唯讀到你連救都救不了：本機模式 ★★★★★

```bash
systemctl stop pve-cluster
pmxcfs -l
```

★★★★ `-l` 是 **local mode**，讓 pmxcfs 在**不需要 Quorum** 的情況下掛起 `/etc/pve`，
好讓你去修 `corosync.conf`。

```bash
# 修完之後
killall pmxcfs
systemctl start pve-cluster
systemctl restart corosync
```

> [!danger] ★★★★★ local mode 期間你是「脫離叢集」的
> 這時候你對 `/etc/pve` 的修改**不會同步**，
> 而且如果別的節點還活著並有 Quorum，**它們的版本才是權威的**，
> 你這邊的修改可能在重新加入時被覆蓋。
> ★★★★★ **只用來修 `corosync.conf`，修完立刻退出，不要在這個模式下做別的事。**

## 常見錯誤與排錯

### ★★★★★ 節點失聯時的正確處置順序

> [!danger] ★★★★★ 這是本篇最重要的一節
> 現場最常見的災難不是「節點掛了」，是
> **「節點失聯 → 值班人員急著重開 → 腦裂 → 資料損毀」**。
> 節點失聯本身通常不會壞資料，**錯誤的處置才會**。

★★★★★ **接到告警後，照這個順序做，不要跳步驟**：

```
【第 0 步】★★★★★ 什麼都不要重開，什麼都不要 pvecm expected
            ─────────────────────────────────────────────
【第 1 步】確認「我現在在哪一邊」
            在你手邊能連上的節點跑：
              pvecm status
            看 Quorate 是 Yes 還是 No

【第 2 步】分兩條路 ────────────────────────────────┐
                                                    │
  ┌─ Quorate: Yes（你在多數方）                     │
  │   → ★★★★ 叢集是安全的，服務多半沒事             │
  │   → 有 HA 的話，失聯節點會自我重開、VM 會接手    │
  │   → 你要做的是：查失聯節點為什麼失聯            │
  │                                                 │
  └─ Quorate: No（你在少數方或叢集全散）           │
      → ★★★★★ 這一邊什麼都不能做（/etc/pve 唯讀）  │
      → ★★★★★ 不要動 VM、不要重開、不要 expected   │
      → 先去找多數方在哪                            │
                                                    │
【第 3 步】分辨是「機器掛了」還是「網路斷了」 ◄─────┘
            ★★★★★ 這是決定後續一切的關鍵判斷
            
            從第三個位置（管理機／IPMI）測：
              ping <失聯節點的管理 IP>
              ping <失聯節點的 corosync IP>
              ipmitool -H <bmc> ... chassis power status
              
   ┌─ 機器真的掛了（IPMI 顯示 power off／完全沒回應）
   │   → ★★★★ 相對單純，等 HA 接手，或手動在別台開 VM
   │   → ★★★★★ 手動開之前一定要先確認那台真的沒在跑同一個 VM
   │
   └─ 機器活著但網路不通（★★★★★ 最危險的情況）
       → ★★★★★ 這台可能正在跑 VM，而且它自己不知道被隔離了
       → 有 HA：它會在約 60 秒後 watchdog 自我重開，安全
       → ★★★★★ 沒有 HA：它的 VM 會繼續跑！
         這時如果你在另一邊手動開同一個 VM → 立即腦裂
       → 正確動作：★★★★★ 先把那台的「儲存連線」或「電源」切掉，
         確定它不可能再寫入共享儲存，才在別台啟動 VM

【第 4 步】修網路 / 修硬體，讓節點自己回來
            corosync 會自動 rejoin，不需要人工介入
            
【第 5 步】節點回來之後
            pvecm status      → Total votes 恢復
            ha-manager status → LRM 回到 active
            檢查 VM 有沒有重複啟動（qm list 在每台都跑一次）
```

★★★★★ **一句話版本**：
**「先確認多數方在哪，再確認少數方不可能寫入，最後才動 VM。」**

## 安全性注意事項

> [!danger] ★★★★★ 不可逆或極高風險的操作清單
> | 操作 | 風險 | 重要度 |
> | --- | --- | --- |
> | `pvecm expected 1` | ★★★★★ **關掉腦裂防護**，可能造成永久資料損毀 | ★★★★★ |
> | 在少數方手動 `qm start` 已在他處運行的 VM | ★★★★★ **立即腦裂** | ★★★★★ |
> | 把已 `delnode` 的節點開機 | ★★★★★ 殘留設定造成叢集狀態混亂 | ★★★★★ |
> | 改 `corosync.conf` 沒加 `config_version` | ★★★★★ 節點設定不一致，叢集散掉 | ★★★★★ |
> | 節點失聯時直接重開機 | ★★★★★ 打斷 fence 判斷，可能兩邊同時跑 VM | ★★★★★ |
> | `pvecm delnode` 順序做錯（先刪再關機） | ★★★★ 舊節點會嘗試連回 | ★★★★ |

### 一、corosync 的通訊是加密的，但別高興太早 ★★★★

- ★★★★ corosync 用 `/etc/corosync/authkey` 做認證與加密（`secauth: on`）
- ★★★★★ **這把金鑰在 `pvecm create` 時產生，並在 `pvecm add` 時複製到新節點** ——
  誰拿到這把金鑰，誰就能假冒成叢集成員
- ★★★★★ **`/etc/corosync/authkey` 權限必須是 `0400 root:root`**

```bash
ls -l /etc/corosync/authkey
```

```text
-r-------- 1 root root 256 Sep  2 10:20 /etc/corosync/authkey
```

### 二、遷移流量的機密性 ★★★★★

- ★★★★★ **`migration: type=insecure` 會讓 VM 的整份記憶體明文過網路**
- 機關環境有個資或機敏資料時，★★★★★ **一律 `type=secure`**
- ★★★★ 就算用 `secure`，也應該把遷移網段**實體隔離**，
  不要跟辦公網段共用（見 [[050-01-03-05-guide-PVE-網路設定]]）

### 三、節點之間是 root SSH 互信 ★★★★★

```bash
cat /etc/pve/priv/authorized_keys | wc -l
```

- ★★★★★ **叢集裡任何一個節點的 root，就等於全叢集的 root**
- ★★★★★ **一台被入侵 = 全部被入侵**
- 因此：
  - ★★★★★ **管理網段一定要跟辦公網段隔離**
  - ★★★★ **關掉 root 密碼登入**，只留金鑰（見 [[020-02-01-04-svc-sshd-伺服器端設定]]）
  - ★★★★ 日常管理用**非 root 的 PVE 使用者 + 最小權限角色**
    （見 [[050-01-03-08-guide-PVE-使用者權限與API]]）
  - ★★★★ 開啟雙因素驗證

### 四、HA 不是備份，也不是災難復原 ★★★★★

| 它防得了 | 它防不了 | 重要度 |
| --- | --- | --- |
| 單一節點硬體故障 | ★★★★★ **誤刪 VM**（會在新節點上一樣不見） | ★★★★★ |
| 單一節點作業系統卡死 | ★★★★★ **共享儲存故障**（所有節點一起沒了） | ★★★★★ |
| 單一節點電源／網卡故障 | ★★★★★ **勒索軟體加密**（跟著同步） | ★★★★★ |
| — | ★★★★★ **整個機房斷電／火災** | ★★★★★ |

★★★★★ **共享儲存是叢集裡最大的單點故障。**
再多節點也救不了一顆掛掉的 LUN。
**HA 必須搭配備份（[[050-01-03-06-svc-PVE-備份與還原]]）與異地策略，缺一不可。**

### 五、變更管理 ★★★★

- ★★★★★ 建立叢集、加入節點、移除節點、改 `corosync.conf` ——
  **全部都屬於重大變更**，要走變更流程（[[100-02-08-guide-維運-變更管理流程]]）
- ★★★★ 變更前的必備動作：
  1. 全節點備份
  2. `cp /etc/pve/corosync.conf /root/corosync.conf.$(date +%F).bak`
  3. 記錄目前 `pvecm status` 的完整輸出
  4. ★★★★★ 確認**有實體或 IPMI 的存取管道**（改壞了 Web UI 進不去）

## 練習題

> [!question]- 練習 1：算 Quorum 並判斷結果
> 一個 5 節點的 PVE 叢集，交換器故障把它切成 3 台一組、2 台一組。
> 請回答：
> 1. Quorum 門檻是多少？
> 2. 哪一邊可以繼續運作？
> 3. 另一邊上面正在跑、但**沒有納入 HA** 的 VM 會怎樣？
> 4. 另一邊上面**有納入 HA** 的 VM 會怎樣？
>
> ---
> **參考答案**
> 1. `floor(5/2)+1 = 3`。
> 2. ★★★★★ **3 台那一組**（3 ≥ 3，Quorate: Yes），可以繼續運作，
>    也可以在自己這邊接手另一組的 HA VM。
> 3. ★★★★★ **會繼續跑**。少數方的 `/etc/pve` 變唯讀，不能開新 VM、不能改設定，
>    但**已經在跑的 VM 不會被停掉**。
>    ★★★★★ **這正是危險所在** —— 如果你在多數方手動啟動同一個 VM，就會腦裂。
> 4. ★★★★★ 那 2 台上的 LRM 因為失去 Quorum 而**停止餵 watchdog**，
>    約 60 秒後**兩台自我重開（fence）**，VM 隨之停止；
>    多數方的 CRM 確認 fence 完成後，把 HA VM 在自己這邊重新開機。

> [!question]- 練習 2：在測試環境建三節點叢集並做線上遷移
> 依「完整實戰範例」步驟 1～6，建出三節點叢集、掛 NFS、做一次線上遷移。
> **驗收條件**：
> - `pvecm status` 的 Membership 顯示的是 **corosync 專線 IP**
> - 遷移期間從外部 `ping` VM，掉包 **≤ 1**
> - 遷移後 `qm guest exec <id> -- uptime` 顯示的 uptime **是連續的**
>
> ---
> **參考答案（關鍵指令）**
> ```bash
> pvecm create PVE-LAB01 --link0 10.0.20.1        # pve1
> pvecm add 10.0.10.1 --link0 10.0.20.2           # pve2
> pvecm add 10.0.10.1 --link0 10.0.20.3           # pve3
> pvecm status
> pvesm add nfs nfs-vmdata --server 10.0.30.50 --export /export/pve \
>   --content images,rootdir
> qm migrate 101 pve2 --online
> qm guest exec 101 -- uptime
> ```
> ★★★★★ **如果 uptime 被重置了，那不是線上遷移，回頭檢查你是不是漏了 `--online`。**

> [!question]- 練習 3：加第二條 link 並實測
> 為練習 2 的叢集加上 `ring1_addr`（走管理網段），
> 然後把 corosync 專線的介面 `down` 掉 30 秒，觀察叢集有沒有散。
>
> ---
> **參考答案**
> 1. 編輯 `/etc/pve/corosync.conf`，每個 node 加 `ring1_addr`，
>    `totem` 加第二個 `interface { linknumber: 1 }`，
>    ★★★★★ **`config_version` 加 1**
> 2. `corosync-cfgtool -s` 確認兩條 LINK 都 `connected`
> 3. `ip link set vmbr1 down; sleep 30; pvecm status | grep Quorate; ip link set vmbr1 up`
> 4. ★★★★★ 應該仍是 `Quorate: Yes`，且 `journalctl -u corosync` 會顯示
>    `link: host: N link: 0 is down`，但成員關係沒有變動。
>
> 沒加 link1 的話，同樣的操作會讓那台被踢出叢集（有 HA 時甚至自我重開）。

> [!question]- 練習 4：兩節點叢集加 QDevice
> 用兩台 PVE + 一台 Debian，做出 2+QDevice 的組態，
> 然後關掉其中一台 PVE，驗證剩下那台仍然 `Quorate: Yes`。
>
> ---
> **參考答案**
> ```bash
> # 第三台 Debian
> apt install corosync-qnetd
> # 兩台 PVE
> apt install corosync-qdevice
> # 任一台 PVE
> pvecm qdevice setup 10.0.20.99
> pvecm status          # Flags 應有 Quorate Qdevice，Total votes: 3
> # 關掉 pve2 之後在 pve1 上
> pvecm status | grep -E "Quorate|Total"
> #   Quorate:      Yes
> #   Total votes:  2      ← pve1(1) + QDevice(1)
> ```
> ★★★★★ **對照組**：沒有 QDevice 時同樣關掉 pve2，
> pve1 會變成 `Quorate: No`，`/etc/pve` 唯讀，什麼都做不了。

> [!question]- 練習 5：模擬節點失聯，練習正確處置
> 在測試叢集裡，把 pve3 的**所有網路介面關掉**（模擬網路斷線，但機器還活著），
> 依「節點失聯時的正確處置順序」走一遍，並寫下：
> 1. 你在 pve1 上看到什麼
> 2. 你怎麼判斷 pve3 是「掛了」還是「只是網路斷了」
> 3. 如果 pve3 上有非 HA 的 VM 還在跑，你要先做什麼才敢在 pve1 上啟動它
>
> ---
> **參考答案**
> 1. `pvecm status`：`Total votes: 2`、`Quorate: Yes`；
>    Web UI 上 pve3 灰色；`journalctl -u corosync` 顯示 `Members[2]: 1 2`。
> 2. ★★★★★ 從**第三個位置**（管理機、IPMI）確認：
>    - IPMI/iDRAC 顯示 power 狀態仍是 **on** → 機器活著，只是網路斷
>    - 完全沒回應且 IPMI 也不通 → 可能真的斷電
> 3. ★★★★★ **必須先確保 pve3 不可能再寫入共享儲存**：
>    - 到現場或用 IPMI 把它**強制關機／斷電**，或
>    - 在儲存端（NFS export／iSCSI ACL）把 pve3 的存取權**拔掉**
>
>    確認之後才可以在 pve1 上 `qm start`。
>    ★★★★★ **跳過這一步就等於故意製造腦裂。**

> [!question]- 練習 6：正確移除節點
> 把測試叢集的 pve3 移除，然後嘗試把同一台機器**不重灌**直接 `pvecm add` 回來，
> 記錄你遇到的錯誤，再說明正確做法。
>
> ---
> **參考答案**
> 正確移除：
> ```bash
> # 1. 搬走 pve3 上的 VM/CT   2. 從 HA 移除   3. 關機 pve3
> pvecm nodes                 # 確認 pve3 offline
> pvecm delnode pve3
> rm -rf /etc/pve/nodes/pve3
> ```
> 直接加回來會遇到：憑證不符、SSH 互信失敗、
> 或它帶著舊的 `config.db` 造成叢集狀態不一致。
>
> ★★★★★ **正確做法：重灌 PVE，並使用不同的節點名稱再加入。**
> 官方文件明確不建議重用已移除的節點名稱與 node ID。

請寫出接下來**前三個**應該做的動作，以及**絕對不能做**的兩件事。

> [!question]- 測驗答案
> **A1.** Quorum = `floor(6/2)+1 = 4`，最多掛 **2 台**。
> ★★★★★ **跟 5 節點（Quorum 3，也是掛 2 台）相比，多的那一台在容錯上完全沒有意義**，
> 而且多一台就多一個故障來源。這就是「偶數節點不划算」的原因。
> 見「Quorum：叢集在算的那個多數決」。
>
> **A2.** ★★★★★ **否（是非題答錯的人最多）。**
> 少數方的 `/etc/pve` 變唯讀、開不了**新的** VM，
> 但**已經在跑的 VM 會繼續跑**。
> ★★★★★ 只有**納入 HA** 的節點，才會因為 LRM 停止餵 watchdog 而在約 60 秒後自我重開。
> 這個差別正是腦裂風險的來源。見「少數方會發生什麼事」。
>
> **A3.** 它把 Quorum 門檻**強制改成 1 票**，等於**關掉腦裂防護**。
> ★★★★★ **只有在你已經實體確認其他節點真的斷電、且不會自行開機**的緊急救援情境才可以用。
> ★★★★★ **絕對不能因為「網路好像斷了但 VM 還在跑」就下這個指令** ——
> 那正是製造腦裂的標準步驟。見「`pvecm expected`：最危險的那個指令」。
>
> **A4. (C)**。記憶體總量不同不影響遷移（只要目標節點放得下）。
> (A)(B)(D) 都是硬條件。
> ★★★★★ 其中 (B) 最容易踩雷 —— CPU type 設成 `host` 時，
> 異質 CPU 之間會遷移失敗或 guest crash。見「線上遷移的前提條件」。
>
> **A5.** ★★★★★ **會失敗。** LXC 容器沒有真正的 live migration，
> 執行中的容器要遷移**必須加 `--restart`**，
> 意思是「停掉 → 搬過去 → 再開起來」，中間有停機時間。
> ★★★★★ 需要真正不中斷的服務，**不要用 LXC，用 VM**。見「遷移的兩種模式」。
>
> **A6.** CRM 正在**等待，直到它能確信 pve3 已經被 fence（自我重開）**。
> ★★★★★ 它不立刻啟動，是因為**如果 pve3 其實還活著並在寫共享儲存，
> 兩邊同時跑同一個 VM 就會造成腦裂與永久資料損毀**。
> 這段等待期是安全機制，**沒辦法縮短**。
> 日誌裡的 `fencing: acknowledged - got agent lock for node 'pve3'` 就是等待結束的那一刻。
> 見「HA 與 fencing」與「一定要會看的三個日誌」。
>
> **A7.** corosync 靠毫秒等級的定時訊息判斷成員死活，怕的是**延遲抖動**而不是頻寬不足。
> ★★★★★ **典型情境**：每晚兩點的 `vzdump` 備份把網卡打滿 →
> corosync token 逾時 → 節點被判定失聯 → 有 HA 的節點 watchdog 自我重開 →
> **每天半夜固定有一台機器「無故重開」**。
> 解法是把 corosync 移到獨立網段、遷移／備份走別條線、並加第二條 link。
> 見「corosync 網路為什麼一定要獨立」與排錯表第 3、4 列。
>
> **A8.** 總票數 **3**（pve1 + pve2 + QDevice），Quorum 門檻 **2**。
> ★★★★★ **QDevice 掛了叢集仍然可以運作**（pve1+pve2 = 2 票 ≥ 2），
> 但就退回「兩台都要活著」的狀態，這時再掛任一台就會失去 Quorum。
> ★★★★★ 所以 QDevice 主機也要納入監控。見「兩節點叢集的正解：QDevice」。
>
> **A9.** ★★★★★ **其他節點會把你的新設定當成舊版本而忽略**，
> 造成節點之間 corosync 設定不一致 —— 輕則設定沒生效，重則叢集散掉。
> ★★★★★ **每次修改 `corosync.conf` 都必須把 `config_version` 加 1**，
> 而且改之前一定要備份。改壞了用 `systemctl stop pve-cluster; pmxcfs -l` 進本機模式還原。
> 見「改 `corosync.conf` 的鐵則」與排錯表第 13 列。
>
> **A10.**
> **前三個動作**：
> 1. ★★★★★ **在另一個節點（pve1／pve3）跑 `pvecm status`**，
>    確認多數方在哪一邊、`Total votes` 少了幾票
> 2. ★★★★★ **`corosync-cfgtool -s` 與 `journalctl -u corosync`**，
>    看是哪條 link 斷了、有沒有 `Token has not been received`
> 3. ★★★★ **從第三個位置測 pve2 的網路**（管理 IP、corosync IP、IPMI），
>    判斷是「機器掛了」還是「只是網路斷了」
>
> **絕對不能做的兩件事**：
> 1. ★★★★★ **不要重開 pve2**（也不要重開任何節點）——
>    重開會打斷 fence 判斷，而且問題出在網路，重開解決不了
> 2. ★★★★★ **不要在 pve2 上（或任何地方）執行 `pvecm expected 1`**，
>    也不要在其他節點手動啟動 pve2 上還在跑的 VM ——
