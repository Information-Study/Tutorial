# PVE 備份與還原

> [!abstract] 這篇你會學到
> - ★★★★★ **`vzdump` 三種模式（stop／suspend／snapshot）到底差在哪**，
>   以及「檔案系統一致 ≠ 應用程式一致」這件事對資料庫的意義
> - 備份排程怎麼設、**GFS 世代保留（keep-last／daily／weekly／monthly／yearly）** 怎麼算
> - 壓縮怎麼選（zstd／gzip／lzo）、★★★★ **加密只有 PBS 做得到**（vzdump 檔案本身沒有加密）
> - 備份到 **NFS** 與備份到 **Proxmox Backup Server**，兩者的取捨
> - ★★★★★ **完整的還原演練**：還原到新 VMID、改 IP、開機、驗證服務真的可用
> - **單檔還原**：只想救一個檔案時的三條路
> - PBS 的**去重與增量**是怎麼運作的，為什麼它的空間效率跟 vzdump 差一個量級
> - ★★★★★ **備份沒做過還原測試，等於沒有備份**

> [!warning] 未實機驗證
> 本篇**以 Proxmox VE 8 為例**（`vzdump`、`qmrestore`、`pct restore`、`/etc/pve/jobs.cfg`）。
>
> ★★★★★ **不同版本的參數會增減**（例如較新版本新增的備份選項）。
> 動手前請以你節點上的 `man vzdump`、`vzdump --help`、`qmrestore --help` 為準，
> 不要照抄本篇的參數字串就往正式環境送。
>
> ★★★★★ 文中的**備份檔名、大小、耗時、去重率都是示意值**，
> 你的環境一定不同。Proxmox Backup Server 的部分以官方文件的機制描述為準，
> 實際去重率取決於你的資料型態。

## 觀念說明

### ★★★★★ 先講最重要的一句話

> **備份沒有做過還原測試，就不是備份，只是一堆佔空間的檔案。**

機關實際發生過的情況，每一種本篇都會教你怎麼避開：

| 現場慘案 | 根因 | 本篇哪一節處理 |
| --- | --- | --- |
| ★★★★★ 備份跑了三年，要用時才發現還原不了 | 從來沒演練過 | 「完整實戰範例」 |
| ★★★★★ 容器還原後資料是空的 | 資料在 **bind mount** 上，從來沒被備份 | 「哪些東西不會被備份」 |
| ★★★★ 資料庫還原後要跑 recovery，資料掉了幾筆 | 用 snapshot 模式但沒做應用層 quiesce | 「三種模式」 |
| ★★★★ 備份儲存被勒索軟體一起加密 | 備份掛在同一台、同一組帳號、可寫 | 「安全性注意事項」 |
| ★★★★ 硬碟滿了，備份靜靜失敗三個月沒人知道 | 沒設通知、沒看報表 | 「備份排程與通知」 |
| ★★★ 要救一個檔案，卻得還原整台 500 GB 的 VM | 不知道有單檔還原 | 「單檔還原」 |

### 備份的三種一致性層級 ★★★★★

這是理解三種模式的前提。

```
【層級一】崩潰一致（crash-consistent）
   等同「直接拔電源後的磁碟狀態」
   ★★★ 檔案系統有 journal 的話開得起來，但會跑 recovery
   應用程式的記憶體內容（尚未 flush 的資料）★★★★★ 全部遺失

【層級二】檔案系統一致（filesystem-consistent）
   備份前先讓檔案系統把 cache 寫下去並凍結
   ★★★★ 開機不用跑 fsck，檔案結構完整
   但應用程式自己的交易狀態仍可能停在半途

【層級三】應用程式一致（application-consistent）★★★★★
   應用程式自己知道「要被備份了」，
   把交易做完、把 buffer flush、進入一致狀態才讓你拍
   ★★★★★ 這才是資料庫真正需要的等級
```

★★★★★ **PVE 的備份本身最多做到層級二。層級三要靠應用層自己配合**
（例如資料庫另外做 `mysqldump`／`pg_dump`／binlog）。
這一點必須寫進你的備份政策，不能假裝 `vzdump` 什麼都罩得住。

### ★★★★★ vzdump 三種模式

| 模式 | 停機時間 | 一致性 | 對儲存的要求 | 什麼時候用 |
| --- | --- | --- | --- | --- |
| ★★★★ **stop** | ★★★★★ **最長**（整個備份期間，或至少關機＋開機） | ★★★★★ **最高** | 無 | 可接受停機、要求最高一致性 |
| ★★ **suspend** | 中 | 中 | 無（VM）／需暫存空間（CT） | ★★★ 相容性理由保留，**一般不推薦** |
| ★★★★★ **snapshot** | ★★★★★ **最短**（幾乎不中斷） | ★★★ 崩潰一致（可用 Guest Agent 提升） | ★★★★ **儲存要支援快照** | ★★★★★ **正式環境預設用這個** |

#### stop 模式 ★★★★

```
VM ─── 正常關機（orderly shutdown）───► 停機 ───► 開始備份
                                                    │
                                      ★★★★ VM 在背景備份開始後就恢復運作
                                                    ▼
                                                 備份完成
```

```
CT ─── 停止容器 ───► 整個備份期間都停著 ───► 備份完成 ───► 啟動容器
                     ★★★★★ 容器的停機時間 = 整個備份時間
```

★★★★★ **VM 與 CT 的行為不一樣，這點很多人不知道**：

- **VM（QEMU）**：關機 → 啟動背景備份程序 → **VM 立刻恢復運作**，備份在背景跑完。
  停機時間 ≈ 關機 + 開機的時間。
- **CT（LXC）**：★★★★★ **容器在整個備份期間都是停止的**。
  一個 50 GB 的容器可能停 10 分鐘以上。

#### suspend 模式 ★★

- **VM**：官方說明是「**為相容性保留**」—— 它會先暫停 VM 再走 snapshot 流程，
  ★★★★ **停機時間更長，一致性卻不見得更好**。官方建議直接用 snapshot。
- **CT**：作法是 **rsync 兩趟** ——
  ```
  第一趟 rsync（容器仍在跑，複製到暫存目錄）
        ↓
  ★★★ 凍結（freeze）容器
        ↓
  第二趟 rsync（只補差異，很快）
        ↓
  解凍容器，開始把暫存目錄打包
  ```
  ★★★★ 停機時間只有第二趟 rsync 的時間，**但需要一塊夠大的暫存空間**（`--tmpdir`）。

> [!tip] ★★★★ suspend 模式什麼時候還有用
> 儲存**不支援快照**（例如某些 NFS 上的 qcow2 以外的組合、或目錄型儲存放 raw），
> 又不能接受 stop 模式的長停機時 —— 容器可以用 suspend 模式當折衷。
> ★★★ 但前提是暫存空間夠大且夠快。

#### snapshot 模式 ★★★★★

- **VM**：走 Proxmox 的 **live backup** ——
  ```
  ★★★★ VM 完全不停機
        │
        ├─ 備份程序開始逐塊讀取磁碟
        │
        └─ VM 同時繼續寫入
              │
              ▼
        ★★★★★ 寫入「還沒備份到的區塊」時，
              先把舊內容送去備份，再讓 VM 寫新的
              （copy-before-write）
  ```
  結果是**一個時間點的崩潰一致快照**。

- **CT**：★★★★ **先短暫凍結容器**確保資料一致 → 用底層儲存做快照 →
  解凍容器 → 從快照打包 → 刪掉臨時快照。
  ★★★★★ **所以 CT 的 snapshot 模式需要底層儲存支援快照**（ZFS、LVM-thin、Ceph、Btrfs）。

| 儲存後端 | CT snapshot 模式可用？ | 備註 |
| --- | --- | --- |
| ★★★★ ZFS | ✅ | dataset 快照，很快 |
| ★★★★ LVM-thin | ✅ | ★★★ 注意 thin pool 空間 |
| ★★★★ Ceph RBD | ✅ | |
| Btrfs | ✅ | |
| ★★★★★ **目錄型（dir）／NFS 存 raw** | ❌ | ★★★★ 會退回或報錯，改用 suspend／stop |

```text
（★★★★ 儲存不支援快照時會看到）
INFO: mode failure - some volumes do not support snapshots
INFO: trying 'suspend' mode instead
```

★★★★ PVE 會自動退回 suspend 模式並在日誌講清楚 —— **這行字要看到**，
否則你以為在用 snapshot，實際上每晚都在凍結容器。

### ★★★★★ QEMU Guest Agent 能把 VM 的一致性拉高一級

```bash
qm set 101 --agent enabled=1,fstrim_cloned_disks=1
```

VM 內要裝 agent：

```bash
# Debian/Ubuntu guest
apt-get install -y qemu-guest-agent
systemctl enable --now qemu-guest-agent
```

★★★★ 裝了之後，snapshot 模式備份時 PVE 會呼叫 `guest-fsfreeze-freeze`，
**讓 guest 的檔案系統先 flush 並凍結**，備份完再 thaw。
一致性從「崩潰一致」提升到「**檔案系統一致**」。

```text
（★★★★ 備份日誌會出現這兩行，代表 agent 有作用）
INFO: issuing guest-agent 'fs-freeze' command
INFO: issuing guest-agent 'fs-thaw' command
```

> [!warning] ★★★★★ Guest Agent 也救不了資料庫的交易一致性
> `fs-freeze` 只保證**檔案系統**層級一致，
> MySQL 的 InnoDB buffer pool、尚未 commit 的交易還是會遺失。
> ★★★★★ **資料庫一定要另外做邏輯備份**（`mysqldump`／`pg_dump`／binlog／WAL 歸檔），
> `vzdump` 只是「機器整台的保險」，不是資料庫備份方案。

### ★★★★★ 哪些東西不會被備份

| 項目 | 會被備份嗎 | 怎麼辦 |
| --- | --- | --- |
| VM／CT 的 rootfs 與一般磁碟 | ✅ | — |
| ★★★★★ **容器的 bind mount** | ❌ **永遠不會** | 對主機來源目錄另做備份 |
| 標記 `backup=0` 的掛載點／磁碟 | ❌ | 刻意排除的要記錄下來 |
| VM 的 `media=cdrom`（ISO） | ❌ | ISO 本來就在 `local` 上 |
| ★★★★ 直通的 PCIe 裝置／USB 裝置上的資料 | ❌ | 那些資料不在 PVE 管理範圍 |
| ★★★★ **PVE 節點自己的設定**（`/etc/pve`、`/etc/network/interfaces`） | ❌ | ★★★★★ 要另外備份，見「安全性注意事項」 |
| 快照 | ❌ | vzdump 備份的是當前狀態，不含快照樹 |

```text
（★★★★★ 備份日誌裡看到這行就代表有東西被跳過）
INFO: excluding bind mount point mp0 ('/data') from backup
```

★★★★★ **每次看備份日誌都要找這一行。**

### GFS 世代保留是什麼 ★★★★

GFS = Grandfather-Father-Son（祖父─父─子），
用「不同粒度各留幾份」的方式，用最少空間換最長的時間覆蓋。

```
今天是 2026-09-02，設定 keep-daily=7, keep-weekly=4, keep-monthly=6

  日  ████████ 最近 7 天，每天一份        → 09-02, 09-01, 08-31 ... 08-27
  週  ██       每週保留一份，共 4 週      → 08-24, 08-17, 08-10, 08-03
  月  █        每月保留一份，共 6 個月    → 07-01, 06-01, 05-01, 04-01, 03-01, 02-01
       ────────────────────────────────────────────────────────────────►
       ★★★★ 總共只留 17 份，卻涵蓋了半年
```

| 參數 | 意義 | 典型值 | 重要度 |
| --- | --- | --- | --- |
| `keep-last` | ★★★ 不管時間，就是留最近 N 份 | `3` | ★★★★ |
| `keep-hourly` | 每小時保留一份，共 N 小時 | 少用 | ★★ |
| ★★★★ `keep-daily` | 每天一份，共 N 天 | `7` | ★★★★★ |
| ★★★★ `keep-weekly` | 每週一份，共 N 週 | `4` | ★★★★ |
| ★★★★ `keep-monthly` | 每月一份，共 N 月 | `6` | ★★★★ |
| `keep-yearly` | 每年一份，共 N 年 | `2` | ★★★ |

> [!note] ★★★★★ 保留規則是「聯集」不是「取代」
> 一份備份**只要被任何一條規則選中就會留下**。
> 所以 `keep-last=3,keep-daily=7` 不是 3 或 7，而是「這 7 天每天一份，
> 加上最近 3 份（可能同一天跑了多次）」的**聯集**。
>
> ★★★★★ **設定完一定要用 `--dry-run` 看它實際會刪哪些**，見「進階應用」。

> [!danger] ★★★★★ 保留策略沒設 = 硬碟遲早爆
> 沒有 `prune-backups` 的備份任務會**無限累積**。
> 硬碟滿了之後，備份靜靜失敗，而且**同一顆碟上的 VM 磁碟也可能受影響**。
> 這是最常見的「備份把生產環境搞掛」的方式。

### 備份存哪裡：三種選擇 ★★★★

| 位置 | 優點 | 缺點 | 重要度 |
| --- | --- | --- | --- |
| ★★ **本機磁碟**（`local`／`/var/lib/vz/dump`） | 快、簡單 | ★★★★★ **主機掛了備份一起沒了**，只能當第一層 | ★★ |
| ★★★★ **NFS／CIFS 網路儲存** | 離開主機、成本低、好懂 | ★★★ 沒有去重、佔空間大；權限沒設好就可能被勒索軟體一起加密 | ★★★★ |
| ★★★★★ **Proxmox Backup Server（PBS）** | ★★★★★ **去重＋增量＋驗證＋加密**，空間效率差一個量級 | 需要另一台機器、多一套系統要維護 | ★★★★★ |

★★★★★ **3-2-1 原則**（機關稽核常見要求）：

```
3 份資料副本（1 份正式 + 2 份備份）
2 種不同媒體／位置
1 份離線或異地
```

| 實作範例 | 對應 |
| --- | --- |
| 正式 VM 在 PVE 節點上 | 第 1 份 |
| 每晚 vzdump 到 NFS（或 PBS） | 第 2 份，不同媒體 |
| ★★★★ 每週把 PBS 資料同步到異地 PBS，或每月拷到離線硬碟／磁帶 | 第 3 份，離線／異地 |

### 5. 壓縮方式怎麼選 ★★★★

| `--compress` | 速度 | 壓縮率 | CPU | 建議 |
| --- | --- | --- | --- | --- |
| ★★★★★ `zstd` | ★★★★ 快 | ★★★★ 好 | 中（可多執行緒） | ★★★★★ **預設選它** |
| `gzip` | 慢 | 中 | 高（單執行緒，除非用 `pigz`） | 相容性需求才用 |
| `lzo` | ★★★ 很快 | 差 | 低 | CPU 很弱的老機器 |
| `0`（不壓縮） | 最快 | 無 | 無 | ★★★ 後端已有壓縮／去重（如 ZFS 開了 compression、或 PBS） |

```bash
# zstd 多執行緒（0 = 依 CPU 核心數自動）
vzdump 101 --storage local --compress zstd --zstd 0
```

```bash
# gzip 用 pigz 多執行緒
vzdump 101 --storage local --compress gzip --pigz 4
```

> [!tip] ★★★★ 實測比較的做法
> 拿一台代表性的 VM，各壓一次記錄「耗時 vs 檔案大小」：
> ```bash
> for c in zstd gzip lzo; do
>   echo "=== $c"
>   /usr/bin/time -f '%e sec' vzdump 101 --storage local --compress $c 2>&1 | tail -3
> done
> ls -lh /var/lib/vz/dump/vzdump-qemu-101-*
> ```
> ★★★ 用自己的資料測出來的數字，比任何網路上的 benchmark 有意義。

### ★★★★ 備份排程（Backup Job）

PVE 8 的備份任務定義在 `/etc/pve/jobs.cfg`。

```bash
cat /etc/pve/jobs.cfg
```

```ini
vzdump: backup-nightly
	schedule 02:30
	all 1
	compress zstd
	enabled 1
	mailnotification failure
	mailto ops@example.gov.tw
	mode snapshot
	notes-template {{guestname}} @ {{node}}
	prune-backups keep-daily=7,keep-weekly=4,keep-monthly=6
	storage nfs-backup

vzdump: backup-weekly-full
	schedule sat 04:00
	enabled 1
	mode stop
	compress zstd
	prune-backups keep-weekly=8
	storage nfs-backup
	vmid 101,102
```

| 欄位 | 意義 | 重要度 |
| --- | --- | --- |
| `schedule` | ★★★★ systemd calendar 語法（`02:30`、`sat 04:00`、`mon..fri 01:00`） | ★★★★ |
| `all 1` | 本節點全部 | ★★★ |
| `vmid 101,102` | 指定 VMID（與 `all` 擇一） | ★★★ |
| `mode` | `snapshot` / `suspend` / `stop` | ★★★★★ |
| ★★★★ `prune-backups` | 保留策略 | ★★★★★ |
| `mailnotification` | `always` / `failure` | ★★★★ |
| `notes-template` | ★★★ 支援 `{{guestname}}`、`{{node}}`、`{{vmid}}`、`{{cluster}}` | ★★★ |

> [!tip] ★★★★ 建議在 Web 介面建立備份任務
> 「資料中心 → 備份 → 新增」，它會把語法寫對，你再用 `cat /etc/pve/jobs.cfg` 看結果。
> ★★★ 手寫 `jobs.cfg` 要注意**縮排是 TAB**，用空白會被忽略。

**排程規劃建議** ★★★★：

| 時段 | 做什麼 | 理由 |
| --- | --- | --- |
| ★★★★ 02:00～05:00 | 主要備份視窗 | 使用者最少 |
| ★★★★★ **不要跟其他重任務重疊** | 錯開 `apt` 更新、ZFS scrub、Ceph deep-scrub | ★★★★★ 同時跑會互相拖垮 |
| ★★★★ 分批啟動 | 大 VM 與小 CT 分成兩個任務、錯開 30 分鐘 | 避免 I-O 尖峰 |
| ★★★ 週末做 stop 模式全備 | 一週一次最高一致性 | 平日 snapshot、週末 stop |

### ★★★★★ 加密：只有 PBS 做得到

> [!danger] ★★★★★ vzdump 產生的檔案是「沒有加密」的
> `.vma.zst` 與 `.tar.zst` **只是壓縮，不是加密**。
> 任何拿到檔案的人都可以解開來看到你 VM 裡的所有東西 ——
> 包含 `/etc/shadow`、資料庫、憑證私鑰。
>
> ★★★★★ **把 vzdump 檔放在共用 NFS 上、權限又沒收緊，等於把整台伺服器的內容公開。**

三條路：

| 做法 | 說明 | 重要度 |
| --- | --- | --- |
| ★★★★★ **用 PBS** | ★★★★★ 客戶端加密（AES-256-GCM），**金鑰在 PVE 這端，PBS 存的是密文** | ★★★★★ |
| ★★★★ 儲存層加密 | NFS 後端的檔案系統加密（如 ZFS native encryption、LUKS） | ★★★★ |
| ★★★ 事後加密 | 備份完再用 `gpg`／`age` 加密（★★★ 多一道工序，容易漏掉） | ★★★ |

★★★ 最務實的組合是：**PBS 客戶端加密**（有 PBS 的話）
或 **收緊 NFS 權限 + 後端 ZFS 加密**（沒有 PBS 的話）。

### ★★★★★ Proxmox Backup Server 概覽

#### 它為什麼省空間 ★★★★★

```
【vzdump 到 NFS】
  週一 完整備份 4.5 GB
  週二 完整備份 4.5 GB   ← ★★★★ 就算只改了 100 MB，還是存一份完整的
  週三 完整備份 4.5 GB
  ...
  7 天 = 31.5 GB

【PBS】
  週一 4.5 GB 的資料被切成一堆「區塊（chunk）」，各自算 SHA-256
       ↓ 存進 chunk store，以雜湊值命名
  週二 再切一次 → ★★★★★ 雜湊值相同的區塊「已經存在了，不用再存」
       只有真正變動的區塊會寫入（約 100～300 MB）
  ...
  7 天 ≈ 5～7 GB
```

| 機制 | 說明 | 重要度 |
| --- | --- | --- |
| ★★★★★ **去重（deduplication）** | 內容相同的區塊全域只存一份，**跨 VM、跨時間都會去重** | ★★★★★ |
| ★★★★★ **增量備份** | 執行中的 VM 用 **dirty bitmap** 只讀變動過的區塊，備份時間大幅縮短 | ★★★★★ |
| ★★★★ **客戶端加密** | AES-256-GCM，★★★★★ **金鑰在 PVE 端**，PBS 看不到明文 | ★★★★★ |
| ★★★★ **驗證（verify）** | 定期重算雜湊，★★★★★ **主動發現壞掉的備份** | ★★★★★ |
| ★★★★ **垃圾回收（GC）** | 清掉沒有任何備份引用的 chunk | ★★★★ |
| ★★★ **同步（sync job）** | PBS ↔ PBS 之間複製，做異地 | ★★★★ |
| ★★★★ **單檔還原** | Web 介面直接瀏覽備份內容、下載單一檔案／資料夾 | ★★★★★ |

> [!danger] ★★★★★ dirty bitmap 只在 VM 持續執行時有效
> VM 重開機（或 PVE 節點重開）之後，bitmap 就沒了，
> **下一次備份會重新完整讀取整顆磁碟**（但去重之後**實際寫入量還是很小**）。
> 日誌會顯示：
> ```text
> INFO: enabling encryption
> INFO: skipping guest-agent 'fs-freeze', agent configured but not running?
> INFO: creating Proxmox Backup Server archive 'vm/101/2026-09-02T02:00:00Z'
> INFO: started backup task ...
> INFO: scsi0: dirty-bitmap status: created new
> ```
> ★★★★ `dirty-bitmap status: created new` = 這次是完整讀取；
> `dirty-bitmap status: OK (2.1 GiB of 32.0 GiB dirty)` = 增量。

### ★★★★ 頻寬與 I-O 節流

```bash

| --- | --- | --- |

| `--ionice 7` | ★★★★ I-O 優先權（0～8，**數字越大優先權越低**），預設 7 | ★★★★ |

mkdir -p /root/restore-tmp && cd /root/restore-tmp

```

```

```text

```

**路線三：還原到暫時的 VMID（★★★★★ 最通用，VM 與 CT 都適用）**

```bash
# 還原到一個不會撞到的 VMID

# ...取檔...
qm stop 999 && qm destroy 999

★★★★ 這條路最笨但**一定會成功**，而且順便驗證了備份可用。

> [!tip] ★★★★ 選哪一條
> | 情況 | 建議 |
> | --- | --- |
> | 有 PBS | ★★★★★ 路線一，幾秒鐘的事 |
> | 容器備份，只要幾個設定檔 | ★★★★ 路線二 |
> | VM 備份、沒有 PBS | ★★★★ 路線三 |
> | ★★★★ 順便想做還原演練 | ★★★★★ 路線三（一舉兩得） |

## 完整實戰範例

**目標**：為一台正式的 Web VM 建立完整的備份機制，
**然後實際還原到新 VMID、啟動、驗證服務真的可用**，最後產出一份演練紀錄。

★★★★★ **這個範例的重點不在備份成功，而在還原之後服務真的跑起來。**

### 情境

| 項目 | 值 |
| --- | --- |
| 節點 | `pve01` |
| 來源 VM | `101` / `web01` / `192.168.10.101` / Debian 12 + Nginx + MariaDB |

## 常見錯誤與排錯

| 現象（原文訊息） | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ `INFO: excluding bind mount point mp0 ('/data') from backup` 而你以為有備到 | bind mount 永遠不進 vzdump | 對主機來源目錄另做備份；見 [[050-01-03-04-guide-PVE-LXC容器管理]] |
| ★★★★ `INFO: mode failure - some volumes do not support snapshots` → `trying 'suspend' mode instead` | 儲存後端不支援快照（目錄型／NFS 上的 raw） | 換到 ZFS／LVM-thin／Ceph，或接受 suspend／stop 模式 |
| ★★★★★ `ERROR: Backup of VM 101 failed - no space left on device` | 備份目的地滿了 | 檢查保留策略；`df -h`；★★★★ 加監控告警 |
| ★★★★ `ERROR: VM 101 qmp command 'guest-fsfreeze-freeze' failed - got timeout` | Guest Agent 沒回應（沒裝、沒啟動、或 guest 卡住） | guest 內 `systemctl status qemu-guest-agent`；暫時 `qm set 101 --agent enabled=0` 讓備份先跑完 |
| ★★★ `INFO: skipping guest-agent 'fs-freeze', agent configured but not running?` | 設定開了但 guest 內沒裝 | guest 安裝並啟用 `qemu-guest-agent`；★★★★ 加了 agent 選項要**關機再開機**才生效 |
| ★★★★ `ERROR: Backup of VM 201 failed - command 'lxc-freeze -n 201' failed` | 容器狀態異常，凍結失敗 | 先 `pct status`、看容器內有沒有卡住的 D 狀態程序；必要時改用 stop 模式 |
| ★★★★ `ERROR: CT is locked (backup)` | 上次備份中斷留下鎖 | 確認確實沒有備份在跑，再 `pct unlock <VMID>` |
| ★★★★ `ERROR: VM is locked (backup)` | 同上（VM） | `qm unlock <VMID>` |
| ★★★★★ `unable to restore - VM 101 already exists` | 還原目標 VMID 已存在 | ★★★★★ **換一個空的 VMID**；真的要覆蓋才加 `--force`（會刪掉現有的） |
| ★★★★ 還原後兩台 VM 撞 IP、網路大亂 | 還原時沒改網路，開機就跟正式機同 IP 同 MAC | ★★★★★ **還原時加 `--unique`，開機前先改 `tag=` 或 bridge** |
| ★★★★ 還原後 VM 開機停在 `Waiting for network configuration` | guest 內綁定的網卡名稱／MAC 變了 | 進 console 改網路設定；Debian 系檢查 `/etc/network/interfaces` 與 `/etc/systemd/network/` |
| ★★★★ LVM-thin 上備份到一半失敗，之後儲存變唯讀 | ★★★★★ 臨時快照撐爆 thin pool | `lvs` 看 `Data%`；擴大 pool 或減少同時備份的數量 |
| ★★★★ 備份跑很久、其他 VM 變超慢 | I-O 被吃光 | `--bwlimit`、`--ionice`、錯開排程 |
| ★★★★★ 半夜備份時節點被 HA fence 重開 | corosync 與備份共用網段被塞爆 | 備份走專用網段；`--bwlimit` 留頻寬 |
| ★★★★ 備份靜靜失敗好幾週沒人發現 | 沒設 `mailto`／`mailnotification`，或郵件被擋 | 設定通知並**實際測試收得到**；另外接監控（見 [[100-01-03-guide-日誌-系統監控與告警]]） |
| ★★★ NFS 備份時 hang 住不動 | NFS server 沒回應（hard mount） | `findmnt`、`showmount -e` 檢查；監控 NFS 可用性 |
| ★★★★ PBS 備份出現 `fingerprint mismatch` | PBS 換憑證，或指紋抄錯 | 從 PBS 主機 `proxmox-backup-manager cert info` 重新取得並更新儲存設定 |
| ★★★ PBS 空間沒有隨著刪備份而釋放 | ★★★★ 需要跑 **garbage collection** 才會真的回收 chunk | PBS 上執行 GC，並設定定期 GC 任務 |
| ★★★★ `vma extract` 失敗 `unable to open file '...vma.zst'` | ★★★ `.vma.zst` 要先解壓縮才能 `vma extract` | `zstd -d file.vma.zst -o file.vma` 之後再 extract |
| ★★★ `jobs.cfg` 改了但排程沒生效 | 縮排用了空白而不是 TAB | `cat -A /etc/pve/jobs.cfg` 確認是 `^I`；★★★★ 建議用 Web 介面編輯 |
| ★★★★★ 需要救援時才發現三年份備份全部還原不了 | ★★★★★ **從來沒做過還原演練** | ★★★★★ 每季一次還原演練並留紀錄 |

> [!tip] ★★★★ 排錯第一步永遠是看 `.log`
> 每一份備份旁邊都有同名的 `.log`：
> ```bash
> ls /mnt/pve/nfs-backup/dump/*.log | tail -3
> grep -E 'ERROR|WARN|excluding|mode' /mnt/pve/nfs-backup/dump/vzdump-qemu-101-*.log
> ```
> Web 介面在「資料中心 → 備份 → Job Detail」與節點的「Task History」也看得到。

## 安全性注意事項

### ★★★★★ 備份是勒索軟體的第一目標

```
❌ 危險做法
   PVE 節點 ──(root 可讀寫)──► NFS 共用資料夾 ──(同一台 NAS 也給 Windows 用)
                                    ▲
                    ★★★★★ 使用者電腦中毒 → 連 NAS → 備份一起被加密

✅ 建議做法
   PVE 節點 ──(專用帳號、限來源 IP)──► 備份儲存（★★★★ 只給 PVE 用）
                    │
                    └──(定期同步/離線)──► ★★★★★ 異地或離線副本（勒索軟體碰不到）
```

| 措施 | 說明 | 重要度 |
| --- | --- | --- |
| ★★★★★ **備份儲存專用** | 不跟一般檔案分享共用同一個 export／share | ★★★★★ |
| ★★★★★ **限制來源 IP** | NFS export 只允許 PVE 節點的 IP | ★★★★★ |
| ★★★★ **專用帳號** | PBS 用獨立使用者，只給該 datastore 的權限 | ★★★★ |
| ★★★★★ **離線／異地副本** | ★★★★★ 3-2-1 的那個「1」，勒索軟體最怕這個 | ★★★★★ |
| ★★★★ **PBS 的 verify job** | 定期驗證備份完整性，壞掉能提早發現 | ★★★★ |
| ★★★ 備份儲存做 WORM／不可變快照 | NAS 支援的話開啟 | ★★★★ |

### ★★★★★ vzdump 檔案內含全部機密

★★★★★ 一份 VM 備份 = 那台機器的**完整內容**：

- `/etc/shadow` 的密碼雜湊
- SSH 私鑰、TLS 憑證私鑰
- 資料庫裡的個資
- 應用程式的 `.env`、API token

| 措施 | 重要度 |
| --- | --- |
| ★★★★★ 備份儲存的**檔案權限**收到最緊（`chmod 700`、只有 root 可讀） | ★★★★★ |
| ★★★★★ 用 **PBS 客戶端加密**，或後端檔案系統加密 | ★★★★★ |
| ★★★★ **不要**把備份放在有 Web 介面對外的 NAS 共用資料夾 | ★★★★ |
| ★★★★ 備份檔在傳輸中要走**內部網段**，不要跨不受信任的網路 | ★★★★ |
| ★★★ 淘汰硬碟前**確實抹除**（含備份碟） | ★★★★ |

> [!danger] ★★★★★ 加密金鑰弄丟 = 備份等於沒有
> PBS 的客戶端加密金鑰**存在 PVE 端**（`/etc/pve/priv/storage/<儲存名>.enc`）。
> ★★★★★ **PVE 節點整台掛掉、金鑰又沒有離線副本 → 你的加密備份永遠解不開。**
>
> 必做：
> 1. 把金鑰匯出並**印出來／存在保險櫃／存在另一套密碼管理系統**；
> 2. 在**還原演練時實際驗證**用那份離線金鑰解得開；
> 3. 交接時把金鑰保管方式寫進文件。

### ★★★★★ PVE 節點自己的設定也要備份

`vzdump` 只備份 VM 與 CT，**不備份節點本身**。節點整台掛掉時你需要：

```bash
# ★★★★ 最小可行的節點設定備份
BK=/mnt/pve/nfs-backup/nodeconf/$(hostname)-$(date +%F)
mkdir -p "$BK"
cp -a /etc/pve/                    "$BK/etc-pve"          2>/dev/null
cp -a /etc/network/interfaces      "$BK/"
cp -a /etc/hosts /etc/hostname     "$BK/"
cp -a /etc/apt/sources.list*       "$BK/"
pvesm status                     > "$BK/pvesm-status.txt"
pvecm status                     > "$BK/pvecm-status.txt" 2>/dev/null
ls -R "$BK" | head -12
```

```text
/mnt/pve/nfs-backup/nodeconf/pve01-2026-09-02:
etc-pve
hosts
hostname
interfaces
pvecm-status.txt
pvesm-status.txt
sources.list
```

> [!warning] ★★★★★ `/etc/pve/priv/` 裡有金鑰
> 上面的備份包含叢集金鑰與儲存密碼。
> ★★★★★ **這份備份的權限要比 VM 備份更嚴格**（`chmod 700`，只有 root），
> 而且**不要放在跟 VM 備份同一個開放的目錄裡**。

### ★★★★ 還原演練本身的安全

| 風險 | 防範 | 重要度 |
| --- | --- | --- |
| ★★★★★ 還原覆蓋正式 VM | ★★★★★ **一律還原到空的 VMID**，操作前唸一次目標數字 | ★★★★★ |
| ★★★★★ 測試機撞 IP／撞 MAC | ★★★★ `--unique` + 開機前改到**測試 VLAN** | ★★★★★ |
| ★★★★ 測試機忘了刪，長期消耗資源 | 演練清單最後一項就是刪除；`description` 註明用途與日期 | ★★★★ |
| ★★★★ 測試機連到正式資料庫寫入髒資料 | ★★★★★ 放在**隔離網段**，不要接得到正式服務 | ★★★★★ |
| ★★★ 演練時把備份檔弄壞 | 還原是唯讀操作，但★★★ 不要在演練中對備份儲存做刪除操作 | ★★★ |

### ★★★★ 制度面

- ★★★★★ **每季至少一次還原演練**，排進 [[100-02-05-guide-維運-每季維護作業]]，並留紀錄。
- ★★★★ 備份政策要寫明：**備哪些、多久一次、留多久、放哪裡、誰負責、多久驗一次**。
- ★★★★ 定義 **RPO／RTO**：
  - **RPO**（可容忍遺失多少資料）→ 決定備份頻率
  - **RTO**（多久要恢復服務）→ 決定備份放哪裡（本機還原快、異地慢）
- ★★★ 備份的存取要有紀錄，誰下載過備份檔要查得到。

## 練習題

1. **★★★★ 讀日誌**：找出你環境裡最近一次備份的 `.log`，
   用 `grep -E 'backup mode|excluding|fs-freeze|finished'` 抓出四個關鍵字，
   說明這次備份的模式、一致性層級、有沒有東西被排除。

2. **模式比較實作**：對同一台測試 CT 分別用 `--mode stop` 與 `--mode snapshot` 各備一次，
   記錄「備份耗時」與「容器實際停機時間」（用另一個視窗持續 `ping` 觀察）。
   寫出兩者的差距。

3. **★★★★ 保留策略試算**：假設從 2026-03-01 開始每天備份一次，今天是 2026-09-02，
   設定 `keep-daily=7,keep-weekly=4,keep-monthly=6`。
   用 `--dry-run` 實際跑一次，把 `would remove` 與 `keeping` 的數量記下來，
   並手算驗證是不是 17 份左右。

4. **★★★★ 單檔還原**：從一份容器備份中，只把 `/etc/nginx/nginx.conf` 抽出來，
   不還原整台容器。寫出你用的指令。

5. **★★★★★ 完整還原演練**：挑一台非正式的 VM 或 CT，
   照本篇「完整實戰範例」做一次：記基準值 → 備份 → 還原到新 VMID →
   改網路 → 開機 → 逐項驗收 → 寫紀錄 → 清理。
   **紀錄裡至少要有三個可量化的比對值。**

6. **★★★★ 失敗通知測試**：故意讓備份失敗（例如把備份儲存改成一個不存在的路徑，
   或把目的地填滿），確認你真的收得到通知信。
   收不到的話找出是哪一段斷掉（PVE 沒送？郵件被擋？地址錯？）。

> [!question]- 練習解答
>
> **1.** 範例輸出與解讀：
> ```bash
> grep -E 'backup mode|excluding|fs-freeze|finished' /var/lib/vz/dump/vzdump-lxc-201-*.log
> ```
> ```text
> INFO: excluding bind mount point mp0 ('/data') from backup
> INFO: backup mode: snapshot
> INFO: Backup job finished successfully
> ```
> 解讀：模式是 snapshot；★★★★★ **`/data` 這個 bind mount 沒有被備份**；
> CT 沒有 `fs-freeze`（那是 VM 的 Guest Agent 才有的）；備份成功。
>
> **2.** 典型結果（1.5 GB 的小容器）：
> | 模式 | 備份耗時 | 容器停機 |
> | stop | 約 20 秒 | ★★★★★ 約 20 秒（整段） |
> | snapshot | 約 17 秒 | 不到 1 秒（只有凍結那一下） |
> ★★★★ 容器越大，兩者的差距越懸殊 —— 50 GB 的容器 stop 模式可能停 10 分鐘以上。
>
> **3.**
> ```bash
> vzdump 201 --storage local --prune-backups keep-daily=7,keep-weekly=4,keep-monthly=6 --dry-run
> ```
> 手算：7（日）+ 4（週）+ 6（月）= 17 份上限。
> ★★★★ 實際可能少幾份，因為**週規則選中的那天可能剛好也在日規則裡**（聯集不重複計算）。
>
> **4.**
> ```bash
> mkdir -p /root/restore-tmp && cd /root/restore-tmp
> tar --zstd -xf /var/lib/vz/dump/vzdump-lxc-201-2026_09_02-10_30_01.tar.zst ./etc/nginx/nginx.conf
> pct push 201 /root/restore-tmp/etc/nginx/nginx.conf /etc/nginx/nginx.conf
> pct exec 201 -- nginx -t
> ```
> ★★★★ 容器備份是標準 tar，這是最快的路。VM 的話用「還原到暫時 VMID」。
>
> **5.** 三個可量化的比對值範例：
> - 資料庫某張表的筆數（`SELECT COUNT(*)`）
> - 某個目錄的檔案數（`find ... | wc -l`）
> - 關鍵檔案的 `md5sum`
> ★★★★★ **沒有可量化的比對值，「還原成功」就只是感覺**。
>
> **6.** 檢查順序：
> ```bash
> grep -i vzdump /var/log/syslog | tail          # PVE 有沒有嘗試送
> journalctl -u postfix -n 30                    # 本機 MTA 有沒有送出去
> grep -A3 'mailto' /etc/pve/jobs.cfg            # 地址對不對
> ```
> ★★★★ 常見原因：節點沒設定 relay、機關郵件伺服器擋掉沒有認證的來源、
> `mailnotification` 設成 `failure` 但你測的是成功的備份。

**Q10.**（簡答）「備份沒做還原測試等於沒有備份」——
請列出還原演練至少要驗證的三件事，並說明為什麼「備份成功」四個字不夠。

> [!question]- 測驗答案
>
> **A1.** ★★★★★ **(C) snapshot**。停機時間最短，配合 Guest Agent 一致性也夠用。
> `stop` 留給週末全備或特別要求最高一致性的場合；
> `suspend` 官方說是**為相容性保留**，一般不推薦。見「vzdump 三種模式」。
>
> **A2.** ★★★★ **否（VM 不是）。**
> VM 是「正常關機 → 啟動背景備份 → **VM 立刻恢復運作**」，停機時間 ≈ 關機＋開機。
> ★★★★★ **容器（CT）才是整個備份期間都停著**。這是 VM 與 CT 行為不同的重點。
>
> **A3.** ★★★★ 需要**底層儲存支援快照**（ZFS、LVM-thin、Ceph、Btrfs）。
> 目錄型儲存與 NFS 上的 raw 不支援。不支援時日誌會出現：
> ```text
> INFO: mode failure - some volumes do not support snapshots
> INFO: trying 'suspend' mode instead
> ```
> ★★★★★ **這行字一定要注意** —— 你以為在用 snapshot，實際上每晚都在凍結容器。
>
> **A4.** 提升到 ★★★★ **檔案系統一致（filesystem-consistent）**，
> 因為 PVE 會呼叫 `guest-fsfreeze-freeze` 讓 guest 先 flush 並凍結檔案系統。
> ★★★★★ **但資料庫的交易一致性沒有被保證** ——
> InnoDB buffer pool、未 commit 的交易仍會遺失。
> 資料庫必須另外做邏輯備份（`mysqldump`／`pg_dump`／binlog）。
>
> **A5.** ★★★★★ **否。** `.vma.zst` 與 `.tar.zst` **只是壓縮，沒有加密**。
> 任何拿到檔案的人都能解開看到 `/etc/shadow`、私鑰、資料庫內容。
> 加密要靠 **PBS 的客戶端加密**或後端檔案系統加密。見「加密：只有 PBS 做得到」。
>
> **A6.** **(C) 約 17 份**（7+4+6 = 17 為上限）。
> ★★★★ 實際可能略少，因為保留規則是**聯集**，
> 同一份備份可能同時被日規則與週規則選中，不重複計算。
>
> **A7.** ★★★★★ **它把備份還原到來源 VMID 101，會覆蓋正在跑的正式 VM。**
> （PVE 會擋下來要求 `--force`，但★★★★★ **不要依賴防呆**。）
> 演練一律還原到**空的 VMID**，例如 `999`，並加 `--unique`。
>
> **A8.** 兩件事：
> 1. ★★★★★ **加 `--unique`（還原時）或手動改 MAC** —— 否則跟正式機 MAC 相同，
>    交換器 MAC table 會抖動、DHCP 可能發同一個 IP；
> 2. ★★★★★ **把網路改到隔離／測試網段**（改 `tag=` 或換 bridge）並關掉 `onboot` ——
>    否則一開機就跟正式機**撞 IP**，正式服務會受影響。
> 見「完整實戰範例」步驟 6。
>
> **A9.** 兩個機制：
> 1. ★★★★★ **去重（deduplication）** —— 資料切成 chunk 依內容雜湊儲存，
>    相同內容全域只存一份，**跨 VM、跨時間都會去重**；
> 2. ★★★★★ **增量備份（dirty bitmap）** —— 執行中的 VM 只讀取變動過的區塊，
>    備份時間與寫入量都大幅減少。
> 另外還有 verify（主動發現壞掉的備份）與客戶端加密。
>
> **A10.** 至少要驗證：
> 1. ★★★★ **還原程序本身能完成**（`qmrestore`／`pct restore` 無錯誤）；
> 2. ★★★★ **guest 開得起來、服務起得來**（`systemctl is-active`、`nginx -t`）；
> 3. ★★★★★ **資料真的在且數量對得上**（表筆數、檔案數、md5 等**可量化**的比對值）。
>
> 為什麼「備份成功」不夠：★★★★★ 備份日誌顯示 `finished successfully`
> 只代表**檔案寫出去了**，不代表內容完整、不代表還原得回來、
> 更不代表 bind mount 或資料庫的資料有被涵蓋。
> 真正能證明備份有效的，只有**一次成功的還原**。
