# 設備生命週期管理

> [!abstract] 這篇你會學到
> - 把設備的一生拆成**七個階段**，每階段的產出物與負責人
> - 寫出**不綁標、又擋得住劣質品**的採購規格 —— 這兩件事其實不衝突
> - ★★★★ 建立**保固到期預警**，不要等機器壞了才發現三個月前過保
> - ★★★★★ 用**評分表**做汰換判定，把「感覺該換了」變成講得出理由的決策
> - 汰換預算的編列時程：★★★★ 為什麼決定汰換的時間點，要比實際汰換早**一年半**
> - ★★★★★ **報廢前的資料銷毀** —— NIST SP 800-88 的 Clear／Purge／Destroy 三級怎麼選
> - ★★★★★ **為什麼 HDD 的做法直接套到 SSD 上是無效的**，SSD 必須用 Secure Erase／加密抹除／實體破壞
> - 機關報廢應留存的**銷毀證明**要寫哪些欄位、留多久

> [!danger] ★★★★★ 這篇有兩段是不可逆操作
> 「資料銷毀」與「實體破壞」段落中的每一條指令，執行後**資料都救不回來**。
> 在正式環境操作前，務必：
> ① 三重確認裝置代號（`/dev/sda` 打成 `/dev/sdb` 就是災難）
> ② 確認該設備已完成資料轉移與備份驗證
> ③ 有第二人在場覆核（雙人作業）
>
> 本篇的所有銷毀指令都以「**這顆碟已確定要報廢**」為前提撰寫。

> [!warning] 未實機驗證
> `hdparm --security-erase`、`nvme sanitize`、`sg_sanitize` 的行為**高度依賴韌體實作**。
> 部分廠商韌體宣稱支援卻執行失敗，或執行後仍可讀出殘留資料。
> ★★★★ **每一種新型號第一次採用前，都應該先在一顆退役碟上實測並驗證結果**，
> 不要直接把本篇指令套用在大批報廢作業上。
> 台灣法規面的具體要求（保存年限、銷毀方式、核准層級）各機關不同，
> 本篇一律寫「依機關內部規定與主管機關要求辦理」，**請以貴機關的規定為準**。

## 觀念說明

### 設備的七個階段

```
【1】需求評估          ── 為什麼要買？現有的為什麼不夠？
      ↓                   產出：需求說明、現況數據
【2】規格撰寫與採購    ── ★★★★ 不綁標，但要擋得住劣質品
      ↓                   產出：規格書、預算
【3】驗收與入帳        ── 到貨核對、功能測試、財產編號
      ↓                   產出：驗收紀錄、資產編號、標籤
【4】服役與保固期      ── 監控、維護、故障報修
      ↓                   產出：保固紀錄、維護紀錄
【5】保固到期後        ── ★★★★ 風險升高期：壞了要自己想辦法
      ↓                   產出：延保決策、備品準備
【6】汰換判定與下架    ── 評分表決定、資料轉移、下架
      ↓                   產出：汰換簽核、下架紀錄
【7】資料銷毀與報廢    ── ★★★★★ 最容易出事、也最常被跳過的一步
                          產出：銷毀證明、財產註銷
```

★★★★★ **這七階段裡，機關最常做壞的是【1】和【7】。**
【1】沒做好，買回來的東西規格不對或用不上；
【7】沒做好，硬碟被當廢鐵賣出去，五年前的個資跟著一起出門。

### ★★★★ 「服役年限」不是一個數字，是三條互不相同的線

很多人把「幾年該換」當成一個固定數字，這是錯的。同一台機器身上有三條線：

| 線 | 定義 | 典型長度 | 誰在乎 |
| --- | --- | --- | --- |
| ★★★★ **保固期** | 原廠承諾修的期間 | 3 年（可延購至 5 年） | 維運（壞了誰修） |
| ★★★ **折舊年限（耐用年數）** | 財產帳上攤提到零的期間 | 依機關財產管理規定 | 財產／會計 |
| ★★★★★ **實際堪用年限** | 效能與可靠度還能滿足需求的期間 | 5～8 年（視角色而定） | ★ 維運與使用單位 |

> [!warning] 三條線幾乎不會重合，而衝突就發生在這裡 ★★★★
> 最常見的兩種衝突：
>
> - **保固到期但折舊未完** → 財產帳上還有價值，不能報廢，但壞了沒人修。
>   ★★★★ 處理方式：**延保**、或**準備備品**、或**降級使用**（移到非關鍵角色）。
> - **折舊完畢但機器還很好用** → 帳面 0 元，但效能還夠。
>   ★★★ 可以繼續用，但要在清冊上標明「已逾耐用年數，續用中」，
>   並提高監控與備份頻率。**不要因為帳面 0 元就以為可以隨便丟。**

### 汰換的四個觸發條件

不是只有「年限到了」才汰換。實務上有四種觸發：

| 觸發 | 說明 | 急迫性 |
| --- | --- | --- |
| ★★★ **年限到期** | 逾實際堪用年限 | 可規劃，走年度預算 |
| ★★★★ **效能不足** | 應用成長超過機器能力（CPU 長期 >80%、記憶體吃滿、IO 排隊） | 可規劃，但要有數據佐證 |
| ★★★★★ **失去支援** | 原廠停產、韌體不再更新、OS 不再支援該硬體 | ★★★★★ **資安風險，最優先** |
| ★★★★ **故障率上升** | 同一台機器半年內故障 2 次以上，或硬碟接連壞 | 急，可能要動用預備金 |

> [!danger] ★★★★★ 「失去支援」是四個裡最危險、也最容易被輕忽的
> 一台跑得好好的機器，只要原廠停止提供韌體與安全更新，它就變成一顆定時炸彈：
> - BMC／iDRAC／iLO 韌體漏洞無法修補，而管理介面往往接在管理網段上
> - RAID 卡韌體不再更新，新硬碟型號可能不相容
> - 新版 OS 不再提供該世代硬體的驅動 → 你被鎖死在舊 OS，跟著鎖死在舊核心的漏洞上
>
> **「還能跑」不等於「可以留」。** 這一條要寫進汰換準則，而且權重要高。

### 保固期結束那天，風險曲線會跳一階

```
故障造成的損失
    │
    │                                        ┌──── 過保後：
    │                                        │     壞了要自己找料
    │                                        │     停機時間不可控
    │                    ┌───────────────────┘
    │                    │  ★★★★ 這一階就是「過保跳升」
    │   ────────────────┘
    │   保固內：打電話、原廠 NBD 到府
    └────────────────────────────────────────────► 時間
                    保固到期日
```

★★★★ **過保設備的管理原則**（三選一，必須明確選一個，不能什麼都不做）：

1. **延保** —— 適合關鍵設備且原廠仍提供延保
2. **備品策略** —— 買一台同型號放著，或關鍵零件（電源、硬碟、風扇）先備料
3. **降級使用** —— 移到「壞了也不會馬上出事」的角色（例如從正式機改成測試機）

> [!tip] 過保清單要每季看一次 ★★★★
> 排進 [[100-02-05-guide-維運-每季維護作業]]：列出「未來 12 個月內保固到期」的設備，
> 逐台決定走延保／備品／降級／汰換哪一條路，並寫進紀錄。
> **沒有決定，就是預設選了「什麼都不做」，而那是最貴的選項。**

### 資料銷毀為什麼是這篇的最高優先 ★★★★★

因為它是整個生命週期裡**唯一一個「錯了就無法補救」**的環節：

- 機器買錯 → 還能換、能退、能改用途
- 驗收漏檢 → 還能補檢
- 保固忘了追 → 還能延保或自備料
- ★★★★★ **硬碟沒清就流出去 → 資料已經在外面了，做什麼都沒用**

而且它有一個非常險惡的特性：**你不會知道自己做錯了。**
一顆沒清乾淨的硬碟被賣掉，通常要等到資料出現在外面才會知道，
而那時已經是資安事件、可能還涉及個資通報。

## 環境準備與安裝

### 一、建立生命週期追蹤欄位

在 [[040-02-11-guide-機房-資訊設備盤點]] 定義的清冊欄位上，生命週期管理需要額外這幾欄：

| 欄位 | 必要性 | 說明 |
| --- | --- | --- |
| ★★★★★ 購入（驗收）日期 | ✔ | 算役齡的起點，用驗收日不是下單日 |
| ★★★★★ 保固到期日 | ✔ | 預警的依據 |
| ★★★★ 保固等級 | ✔ | 例如「NBD 到府」「5×8 送修」「僅零件保固」 |
| ★★★★ 預計汰換年度 | ✔ | 編預算的依據，購入時就先填 |
| ★★★ 原廠支援終止日（EOSL） | | 原廠公告的 End of Service Life |
| ★★★ 延保紀錄 | | 延保到哪一天、合約編號 |
| ★★★★ 故障次數 | | 累計，汰換評分用 |
| ★★★★★ 硬碟數量與序號 | ✔ | ★ 報廢時要逐顆核對，缺一顆就是資安事件 |
| ★★★★★ 資料敏感度分級 | ✔ | 決定銷毀方式（一般／內部／機敏） |
| ★★★★★ 銷毀完成日期與證明編號 | | 報廢後回填 |

### 二、抓機器的實際役齡與健康度

★★★★ 別只看購入日期，機器自己知道它跑了多久。

安裝工具：

```bash
sudo apt install -y smartmontools
```

查硬碟通電時數（最能代表真實役齡）：

```bash
sudo smartctl -A /dev/sda | grep -E 'Power_On_Hours|Power_Cycle_Count|Reallocated'
```

預期輸出（SATA HDD）：

```text
  4 Start_Stop_Count        0x0032   100   100   020    Old_age   Always       -       142
  5 Reallocated_Sector_Ct   0x0033   100   100   010    Pre-fail  Always       -       0
  9 Power_On_Hours          0x0032   079   079   000    Old_age   Always       -       18942
 12 Power_Cycle_Count       0x0032   100   100   000    Old_age   Always       -       143
```

★★★ `Power_On_Hours` 18942 小時 ≈ 2.16 年連續運轉。
★★★★ `Reallocated_Sector_Ct` 不為 0 就是壞軌重新配置過，**數字持續增加代表這顆碟正在死**。

NVMe SSD 看不同欄位：

```bash
sudo smartctl -A /dev/nvme0
```

預期輸出（節錄）：

```text
Percentage Used:                    12%
Data Units Written:                 41,238,109 [21.1 TB]
Power On Hours:                     19,204
Media and Data Integrity Errors:    0
```

★★★★ **`Percentage Used` 是 SSD 的壽命指標**：100% 代表寫入量已達原廠標稱耐久度。
超過 80% 就該排進汰換，超過 100% 不代表立刻壞，但保固通常已不涵蓋。

整機健康快掃腳本：

```bash
#!/usr/bin/env bash
# disk-age-report — 列出本機所有實體碟的役齡與健康摘要
set -euo pipefail
[ "$(id -u)" -eq 0 ] || { echo "請用 root 執行" >&2; exit 1; }

printf '%-14s %-22s %-10s %-8s %s\n' DEVICE MODEL POWER_ON HEALTH NOTE
for dev in $(lsblk -dn -o NAME,TYPE | awk '$2=="disk"{print "/dev/"$1}'); do
  info=$(smartctl -i -H -A "$dev" 2>/dev/null) || continue
  model=$(echo "$info" | awk -F': *' '/Device Model|Model Number/{print $2; exit}')
  poh=$(echo "$info"   | awk '/Power_On_Hours|Power On Hours/{print $NF; exit}')
  health=$(echo "$info"| awk -F': *' '/overall-health|SMART Health Status/{print $2; exit}')
  realloc=$(echo "$info" | awk '/Reallocated_Sector_Ct/{print $NF; exit}')
  used=$(echo "$info"  | awk -F': *' '/Percentage Used/{print $2; exit}')
  note="realloc=${realloc:-n/a} used=${used:-n/a}"
  printf '%-14s %-22s %-10s %-8s %s\n' "$dev" "${model:0:22}" "${poh:-?}" "${health:-?}" "$note"
done
```

執行與預期輸出：

```bash
sudo chmod 750 /usr/local/sbin/disk-age-report
sudo /usr/local/sbin/disk-age-report
```

```text
DEVICE         MODEL                  POWER_ON   HEALTH   NOTE
/dev/sda       ST4000NM0035           18942      PASSED   realloc=0 used=n/a
/dev/sdb       ST4000NM0035           18940      PASSED   realloc=24 used=n/a
/dev/nvme0n1   SAMSUNG MZQL2960       19204      PASSED   realloc=n/a used=12%
```

★★★★ `/dev/sdb` 有 24 個重新配置磁區 —— 這顆要列入觀察，並確認備份正常。

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> ```bash
> sudo dnf install -y smartmontools nvme-cli hdparm
> ```
> `smartctl`、`nvme`、`hdparm`、`lsblk` 的參數與輸出在 RHEL 系完全相同。
> ★★ 差別只在 RAID 卡後面的實體碟，兩系都需要加 `-d` 指定裝置類型，例如：
> `smartctl -A -d megaraid,0 /dev/sda`（LSI/PERC）或 `-d cciss,0`（HP Smart Array）。

> [!info]- Windows Server 對照
> GUI 沒有內建看通電時數的工具，用 PowerShell 取得健康狀態：
>
> ```powershell
> Get-PhysicalDisk | Select-Object DeviceId, FriendlyName, MediaType, HealthStatus, Size
> Get-StorageReliabilityCounter -PhysicalDisk (Get-PhysicalDisk) |
>     Select-Object DeviceId, PowerOnHours, Wear, ReadErrorsTotal, WriteErrorsTotal
> ```
>
> 預期輸出：
>
> ```text
> DeviceId PowerOnHours Wear ReadErrorsTotal WriteErrorsTotal
> -------- ------------ ---- --------------- ----------------
> 0               18942    0               0                0
> 1               19204   12               0                0
> ```
>
> ★★★ `Wear` 欄對 SSD 而言就是 `Percentage Used`。
> 部分 RAID 卡後面的實體碟不會出現在這裡，需用廠商工具（如 PERC 的 `perccli`）。

### 三、保固查詢與預警

多數伺服器廠商提供以序號查保固的網頁或 API。**不要依賴人工上網查**，
要把保固到期日寫進清冊，然後用腳本預警。

保固預警腳本（讀清冊 CSV，第 1 欄資產編號、第 15 欄保固到期日）：

```bash
#!/usr/bin/env bash
# warranty-alert — 列出未來 N 天內保固到期，以及已過保的設備
set -euo pipefail
CSV=${1:?用法: warranty-alert <清冊.csv> [提前天數]}
DAYS=${2:-180}

today=$(date +%s)
limit=$(( today + DAYS * 86400 ))

echo "=== 已過保（立即處理）==="
awk -F, -v t="$today" 'NR>1 && $15 != "" {
  cmd = "date -d \"" $15 "\" +%s 2>/dev/null"; cmd | getline e; close(cmd)
  if (e != "" && e+0 < t) printf "  %-14s 保固已於 %s 到期\n", $1, $15
}' "$CSV" | sort

echo
echo "=== 未來 ${DAYS} 天內到期（請決定延保/備品/降級/汰換）==="
awk -F, -v t="$today" -v l="$limit" 'NR>1 && $15 != "" {
  cmd = "date -d \"" $15 "\" +%s 2>/dev/null"; cmd | getline e; close(cmd)
  if (e != "" && e+0 >= t && e+0 <= l) printf "  %-14s %s\n", $1, $15
}' "$CSV" | sort -k2
```

執行與預期輸出：

```bash
sudo /usr/local/sbin/warranty-alert /srv/inventory/資產清冊.csv 180
```

```text
=== 已過保（立即處理）===
  SRV-A01-03     保固已於 2025-11-30 到期
  SWT-A02-01     保固已於 2026-03-14 到期

=== 未來 180 天內到期（請決定延保/備品/降級/汰換）===
  SRV-A02-05     2026-10-20
  STG-A04-01     2027-01-08
```

排進每月自動執行：

```bash
sudo tee /etc/cron.d/warranty-alert >/dev/null <<'EOF'
# 每月 1 日 08:00 寄保固預警給資訊室
0 8 1 * * root /usr/local/sbin/warranty-alert /srv/inventory/資產清冊.csv 180 | mail -s "[資產] 保固到期預警" it@example.gov.tw
EOF
```

## 基礎設定

### 一、需求評估：先講清楚「為什麼不能不買」★★★

寫規格書之前，要先能回答三題。答不出來就代表需求還沒想清楚：

| 題目 | 要拿出什麼 |
| --- | --- |
| ★★★★ 現有設備為什麼不夠？ | **數據**，不是感覺。CPU 使用率趨勢圖、記憶體用量、磁碟空間成長曲線、回應時間 |
| ★★★ 買了之後解決什麼？ | 具體指標：「批次作業從 4 小時降到 40 分鐘」而不是「效能會變好」 |
| ★★★★ 三年後還夠用嗎？ | 依成長率推估，並保留餘裕（見下方） |

★★★★ **容量規劃的簡單算法**：

```
目標規格 = 現況尖峰用量 × (1 + 年成長率)^服役年數 × 安全係數

例：現況尖峰 CPU 用量相當於 12 核，年成長 15%，服役 5 年，安全係數 1.3
    12 × 1.15^5 × 1.3 = 12 × 2.011 × 1.3 ≈ 31.4 → 採購 32 核
```

> [!warning] 安全係數不要無限放大 ★★★
> 常見的錯誤是「反正買大一點不會錯」，結果買了用不到 20% 的機器。
> ★★★ **建議安全係數 1.2～1.5**。超過 1.5 通常代表需求推估本身有問題，
> 而且在機關採購裡，**規格過度膨脹容易被質疑不符實際需要**。

### 二、規格撰寫：不綁標，但要擋得住劣質品 ★★★★★

這是機關資訊人員最痛的一環：**寫太細會被說綁標，寫太鬆會收到爛貨。**
解法是理解一個原則：

> [!note] ★★★★★ 綁標的判準是「有沒有排除實質競爭」，不是「規格細不細」
> 規格寫得細**不等於**綁標。真正的問題在於規格條件的組合是否只有一家能符合。
>
> 具體的認定與程序請洽機關採購單位，**依政府採購相關法令與機關內部規定辦理**；
> 本篇只提供技術面的寫法建議。

★★★★ **技術面的四個安全寫法**：

| 該避免的寫法 | 改寫成 | 為什麼 |
| --- | --- | --- |
| 「須為 ○○ 廠牌 R650 型」 | 「2U 機架式，支援雙路 CPU，至少 24 條記憶體插槽」 | ★★★★★ 直接指名廠牌型號是最典型的問題寫法 |
| 「CPU 須為 ○○ 型號」 | 「CPU 單顆實體核心數 ≥ 16、基礎時脈 ≥ 2.0GHz，且於公開效能基準測試達 ○○ 分以上」 | 用**可量測的能力**取代型號 |
| 「須支援 ○○ 專屬管理軟體」 | 「須具備獨立於作業系統的遠端管理控制器，支援 IPMI 2.0 或 Redfish，可遠端開關機與掛載虛擬光碟」 | 用**開放標準**取代專屬名稱 |
| 「機箱尺寸須為 xxx × yyy × zzz mm」 | 「機箱深度 ≤ 780mm，可安裝於 800mm 深機櫃」 | ★★★★ 給**上下限與理由**，不要給唯一值 |

★★★★ **擋劣質品的四個有效條款**（這些不會被視為綁標，因為它們不指向特定廠商）：

1. **保固與服務水準**：「保固 5 年，故障須於次一工作日到府維修（NBD On-site）」
   → 這一條就能自然排除沒有台灣維修體系的白牌
2. **原廠授權證明**：「須檢附原廠或原廠台灣代理商出具之授權經銷與保固證明」
3. ★★★★★ **韌體與安全更新承諾**：「原廠須於保固期間內持續提供 BIOS／BMC 韌體安全更新」
   → 這一條是資安面最重要的，卻最常被漏掉
4. **驗收測試條款**：「驗收時須通過連續 72 小時燒機測試，期間無非預期重啟或錯誤紀錄」

> [!tip] 規格書一定要寫的三個「軟」條款 ★★★★
> ① **交貨時的韌體版本要求**：「交貨時 BIOS／BMC 韌體須為原廠當時最新穩定版」
>    —— 否則會收到出廠三年的舊韌體，一上架就要先花半天升級
> ② **管理帳號交付**：「須提供 BMC 預設帳號密碼，且支援變更」
>    —— 有些整機商設了自己的密碼卻不給
> ③ **文件交付**：「須提供機架安裝指引、序號清單、保固起訖日期一覽表」
>    —— 序號清單是你入清冊的原始資料

### 一、汰換判定評分表 ★★★★★

把「感覺該換了」變成講得出理由、寫得進簽呈的決策。

| 構面 | 評分項目 | 0 分 | 2 分 | 4 分 | 權重 |
| --- | --- | --- | --- | --- | --- |
| **役齡** | 服役年數 | < 4 年 | 4～6 年 | > 6 年 | ×1 |
| **保固** | 保固狀態 | 保固內 | 已過保但可延保 | ★★★★ 已過保且**無法延保** | ×2 |
| **支援** | 原廠支援 | 支援中 | 已公告 EOSL 日期 | ★★★★★ **已停止韌體與安全更新** | ×3 |
| **效能** | 尖峰資源使用率 | < 60% | 60～80% | > 80% 或已影響服務 | ×2 |
| **可靠度** | 近 12 個月硬體故障次數 | 0 | 1 | ★★★★ ≥ 2 | ×3 |
| **健康** | 硬碟 SMART 異常 | 無 | 有重配磁區但穩定 | ★★★★ 重配磁區持續增加／SSD 壽命 >80% | ×2 |
| **相容性** | 是否卡住 OS 升級 | 否 | 需特殊處理 | ★★★★★ **無法升級到受支援的 OS** | ×3 |
| **能耗** | 相較同級新機的耗電 | 相當 | 高 20～50% | 高 > 50% | ×1 |
| **角色** | 服務關鍵性 | 測試／非關鍵 | 一般業務 | ★★★★ 關鍵業務、停機影響大 | ×2 |

**判定門檻**（總分上限 76）：

| 總分 | 判定 | 動作 |
| --- | --- | --- |
| ≤ 20 | 繼續服役 | 例行維護即可 |
| 21～38 | ★★★ 列入觀察 | 明年度預算先列，季度複評 |

| ≥ 56 | ★★★★★ **應立即汰換** | 若無預算，須簽報降級使用或加強備援，不可放著不管 |

> [!danger] ★★★★★ 有兩個項目只要中了就直接跳到「應立即汰換」
> 不用算總分：
> 1. **原廠已停止韌體與安全更新**，且該設備管理介面或服務暴露在網路上
> 2. **無法升級到受支援的 OS**，導致必須停留在已終止支援的作業系統版本
>

> 若確實無法立即汰換，必須有書面的補償措施（隔離網段、加嚴存取控制、
> 縮短稽核週期）並經權責主管核准。

### 二、汰換預算的時程 ★★★★

★★★★★ **這是最常被低估的一點：決定汰換的時間點，必須比實際汰換早一年半。**

以「2028 年要換掉一台伺服器」為例，往回推：

```
2026 Q2  ── ★★★★ 汰換評估與評分（此時就要決定 2028 要不要換）
   │        產出：評分表、初步規格構想
   ▼
2026 Q3  ── 需求提報，進入 2027 年度預算編列作業
   │        ★★★ 錯過這一季，就要等下一輪，實際汰換自動延後一年
   ▼
2026 Q4  ── 預算審議
   ▼
2027 年   ── 預算執行年度：規格書定稿 → 招標 → 決標 → 到貨
   │        ★★★ 招標到到貨通常 2～4 個月，供應鏈吃緊時可能更久
   ▼
2027 Q4 ~ 2028 Q1 ── 驗收、上架、資料遷移、平行運轉
   ▼
2028 Q1  ── 舊機下架 → ★★★★★ 資料銷毀 → 報廢
```

| 時間點 | 事情 | 誤了會怎樣 |
| --- | --- | --- |
| ★★★★ 汰換前 18～24 個月 | 評估與提報預算 | ★★★★★ 錯過預算編列時程，整批延後一年 |
| 汰換前 12 個月 | 規格書定稿 | 來不及招標 |
| 汰換前 6 個月 | 決標、到貨 | 平行運轉時間被壓縮 |
| ★★★★ 汰換前 1～3 個月 | 平行運轉與資料遷移 | 沒有回頭路，出問題只能硬上 |
| 汰換後 1 個月內 | 資料銷毀與報廢 | ★★★★★ 舊機堆在角落，硬碟沒清 |

> [!warning] 平行運轉期間，舊機不能拆 ★★★★
> 新機上線後，舊機至少保留：
> - ★★★★ **一個完整業務週期**（有月結／季結的系統就是一個月／一季）
> - 且至少確認過**一次完整備份與還原演練**
>
> 這段期間舊機**維持通電但可以斷網或停服務**。
> 太早拆機是機關系統轉換失敗最常見的後悔來源。

### 四、★★★★★ 資料銷毀

#### NIST SP 800-88 的三級

美國 NIST 的《Guidelines for Media Sanitization》（SP 800-88 Revision 1）
把媒體清理分成三級，這是國際上最常被引用的分類：

| 等級 | 英文 | 意義 | 能擋住誰 | 媒體還能不能用 |
| --- | --- | --- | --- | --- |
| ★★★ **清除** | **Clear** | 用一般讀寫介面覆寫或重設，資料無法用**一般作業系統與檔案救援工具**復原 | 一般使用者、簡單的救援軟體 | ✔ 可繼續使用 |
| ★★★★ **清除（強化）** | **Purge** | 用韌體層指令（Secure Erase／Sanitize／Crypto Erase）或消磁，使資料無法用**實驗室技術**復原 | 具備進階實驗室能力的對手 | ✔ 可繼續使用（消磁除外） |
| ★★★★★ **銷毀** | **Destroy** | 實體破壞：切碎、粉碎、焚化、崩解 | 所有已知技術 | ✖ 媒體報廢 |

> [!note] 怎麼選？看兩件事 ★★★★
> **① 這顆碟上的資料有多敏感？ ② 這顆碟接下來要去哪裡？**
>
> | 資料敏感度 \ 去向 | 機關內部再利用 | 移轉給其他機關／單位 | 對外處分（變賣／回收／報廢） |
> | --- | --- | --- | --- |
> | 一般（無個資、無機敏） | Clear | Purge | ★★★ Purge |
> | 內部（含業務資料） | Purge | Purge | ★★★★ Purge + 驗證，或 Destroy |
> | ★★★★★ 機敏（個資、人事、財務、憑證私鑰） | Purge | ★★★★ Purge + 驗證 | ★★★★★ **Destroy** |
>
> ★★★★★ **只要碟上曾經存過個資或私鑰，而且要離開機關的控制範圍，
> 一律做實體破壞（Destroy）。** 這是唯一沒有爭議的答案。

#### ★★★★★ 為什麼 HDD 的做法不能直接套到 SSD

這是本篇最重要的一段。

**HDD（機械硬碟）的儲存模型**：

```
邏輯位址 LBA 100  ──直接對應──►  某個實體磁區
覆寫 LBA 100 → 那個實體磁區的磁性真的被改寫了
```

★★★ 所以對 HDD 而言，**單次全碟覆寫就足以達到 Purge 等級**
（SP 800-88 對現代 HDD 已不再要求多次覆寫）。

**SSD（快閃記憶體）的儲存模型完全不同**：

```
邏輯位址 LBA 100 ──經過 FTL 對應表──► 實體區塊 #4821
覆寫 LBA 100 時：
   ① 控制器不會去改寫 #4821（NAND 必須先抹除整個 block 才能寫）
   ② 它把新資料寫到另一個空區塊 #9034，然後改對應表
   ③ ★★★★★ #4821 上的舊資料原封不動地留在那裡
```

造成這個現象的三個機制：

| 機制 | 作用 | 對銷毀的影響 |
| --- | --- | --- |
| ★★★★★ **Wear Leveling（磨損平均）** | 平均分散寫入，避免特定區塊先壞 | 覆寫寫不到原本那塊，舊資料殘留 |
| ★★★★ **Over-provisioning（超額配置）** | 保留 7～28% 容量供控制器內部使用，**主機看不到** | ★ 這塊空間你的覆寫指令永遠碰不到 |
| ★★★★ **Bad Block Retirement（壞塊退役）** | 有問題的區塊被標記退役、不再使用 | 退役區塊上的舊資料仍在，且無法透過一般介面存取 |

> [!danger] ★★★★★ 三句話總結
> 1. **對 SSD 執行 `shred`、`dd if=/dev/zero`、多次覆寫，都是無效的**
>    —— 它會磨損顆粒、浪費時間，卻無法保證資料被清除。
> 2. **消磁機（degausser）對 SSD 完全無效** —— NAND 快閃是電荷儲存，不是磁性儲存。
>    消磁機只能處理 HDD 與磁帶。
> 3. **SSD 的正確做法只有三種**：韌體層 Sanitize／Secure Erase、加密抹除、實體破壞。

#### HDD 的銷毀做法

| 等級 | 方法 | 指令／作法 |
| --- | --- | --- |
| Clear | 單次全碟覆寫 | `shred -v -n 1 -z /dev/sdX` 或 `dd if=/dev/zero of=/dev/sdX bs=4M status=progress` |
| ★★★★ Purge | ATA Secure Erase | `hdparm --security-erase`（見下） |
| ★★★★ Purge | 消磁（degauss） | ★★★ 使用符合規格的消磁機；**消磁後硬碟即報廢，無法再使用** |
| ★★★★★ Destroy | 實體破壞 | 切碎、鑽孔穿透碟片、粉碎 |

單次覆寫（Clear）：

```bash
# ★★★★★ 執行前務必確認裝置代號！
lsblk -d -o NAME,SIZE,MODEL,SERIAL
sudo shred -v -n 1 -z /dev/sdb
```

預期輸出：

```text
shred: /dev/sdb: pass 1/2 (random)...
shred: /dev/sdb: pass 1/2 (random)...1.1GiB/3.6TiB 0%
...
shred: /dev/sdb: pass 2/2 (000000)...
shred: /dev/sdb: pass 2/2 (000000)...3.6TiB/3.6TiB 100%
```

★★★ `-n 1` 一次隨機覆寫，`-z` 最後補一次寫 0（讓碟看起來是乾淨的）。
4TB HDD 全碟覆寫約需 6～10 小時，**要留足時間**。

#### ★★★★★ ATA Secure Erase（HDD 與 SATA SSD 皆適用）

這是韌體層的抹除，由硬碟控制器自己執行，**能觸及主機看不到的區域**。

第一步，確認支援且未被凍結：

```bash
sudo hdparm -I /dev/sdb | sed -n '/Security:/,/^$/p'
```

預期輸出：

```text
Security: 
	Master password revision code = 65534
		supported
	not	enabled
	not	locked
	not	frozen
	not	expired: security count
		supported: enhanced erase
	2min for SECURITY ERASE UNIT. 2min for ENHANCED SECURITY ERASE UNIT.
```

★★★★★ **必須是 `not frozen`。** 若顯示 `frozen`，代表 BIOS 在開機時鎖住了安全指令，
Secure Erase 會直接失敗。

> [!warning] 解除 frozen 的兩個方法 ★★★★
> ① **暫停到記憶體再喚醒**（最常用）：
> ```bash
> sudo systemctl suspend
> # 喚醒後再查一次
> sudo hdparm -I /dev/sdb | grep -i frozen
> ```
> ② **熱插拔**：在機器開著的狀態下拔掉 SATA 電源／資料線再插回（僅限支援熱插拔的機種）。
>
> ★★★ 部分主機板 BIOS 有「HDD Security Freeze Lock」選項可關閉。
> ★★★★★ 若三種方法都不行，改用其他銷毀方式，**不要因為做不到就跳過銷毀**。

第二步，設定使用者密碼（Secure Erase 的前置要求）：

```bash
sudo hdparm --user-master u --security-set-pass Eras3Me /dev/sdb
```

```text
security_password: "Eras3Me"

/dev/sdb:
 Issuing SECURITY_SET_PASS command, password="Eras3Me", user=user, mode=high
```

第三步，執行抹除：

```bash
# ★★★★★ 不可逆！執行前確認 /dev/sdb 就是要銷毀的那顆
time sudo hdparm --user-master u --security-erase Eras3Me /dev/sdb
```

```text
security_password: "Eras3Me"

/dev/sdb:
 Issuing SECURITY_ERASE command, password="Eras3Me", user=user
real	118m42.331s
```

★★★★ 若硬碟支援 `enhanced erase`，優先用它（它會連同重配磁區一起處理）：

```bash
sudo hdparm --user-master u --security-erase-enhanced Eras3Me /dev/sdb
```

第四步，★★★★ **驗證**：

```bash
# 確認安全狀態已回到 not enabled（密碼已隨抹除清掉）
sudo hdparm -I /dev/sdb | grep -A2 'Security:' 
# 抽樣讀取確認全為 0（抽頭、中、尾三處）
sudo dd if=/dev/sdb bs=1M count=16 2>/dev/null | od -An -tx1 | uniq -c | head
sudo dd if=/dev/sdb bs=1M count=16 skip=1000000 2>/dev/null | od -An -tx1 | uniq -c | head
```

預期輸出（表示全為 0）：

```text
 65536  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

> [!danger] ★★★★★ 驗證是必要步驟，不是加分項
> 有實際案例是 Secure Erase 指令回報成功，但實際上韌體沒有真正執行。
> **每一顆都要抽樣驗證**，而且要驗至少三個位置（開頭、中段、結尾）。
> 驗證結果要記進銷毀紀錄。

#### ★★★★★ NVMe SSD 的做法

NVMe 有自己的指令集，**不能用 hdparm**。

```bash
sudo apt install -y nvme-cli
```

查看支援哪些抹除能力：

```bash
sudo nvme id-ctrl /dev/nvme0 | grep -E '^sanicap|^oacs|^fna'
```

```text
oacs      : 0x17
fna       : 0x4
sanicap   : 0x3
```

★★★ `sanicap` 的位元表示支援的 Sanitize 動作（bit0 = Crypto Erase、bit1 = Block Erase、
bit2 = Overwrite）。`0x3` 代表同時支援 Crypto Erase 與 Block Erase。

**方法一：Format NVM（較快，相當於 Clear～Purge）**

```bash
# --ses=1 使用者資料抹除；--ses=2 密碼學抹除（換金鑰）
sudo nvme format /dev/nvme0n1 --ses=1 --force
```

```text
Success formatting namespace:1
```

**方法二：★★★★★ Sanitize（最徹底，達 Purge 等級）**

```bash
# --sanact=2 Block Erase（抹除整顆 NAND）
sudo nvme sanitize /dev/nvme0 --sanact=2
# --sanact=4 Crypto Erase（銷毀內部加密金鑰，瞬間完成）
sudo nvme sanitize /dev/nvme0 --sanact=4
```

Sanitize 是背景執行的，要查進度：

```bash
sudo nvme sanitize-log /dev/nvme0
```

```text
Sanitize Progress                      (SPROG) :  38234
Sanitize Status                        (SSTAT) :  0x102
Sanitize Command Dword 10 Information  (SCDW10):  0x2
```

★★★ `SPROG` 是 0～65535 的進度值（38234 ≈ 58%）。
`SSTAT` 的低 3 位為 `0b010` 表示「最近一次 sanitize 已成功完成」，`0b001` 表示進行中。

> [!warning] Sanitize 期間不可斷電 ★★★★
> Sanitize 執行中斷電，SSD 可能進入 Sanitize Failed 狀態而**整顆無法使用**。
> 若在筆電或無 UPS 保護的環境操作，先確認電源穩定。

**方法三：`blkdiscard`（TRIM 全碟）**

```bash
sudo blkdiscard -f /dev/nvme0n1
```

> [!danger] ★★★★ blkdiscard 不能單獨當成合格的銷毀方法
> `blkdiscard` 只是告訴 SSD「這些區塊我不要了」。
> **控制器什麼時候真正抹除、有沒有抹除，取決於韌體實作**，
> 而且不涵蓋超額配置與退役區塊。
> ★★★ 它適合當成「重新部署前的效能回復」，不適合當成報廢前的資料銷毀。

#### ★★★★ 加密抹除（Cryptographic Erase）—— 最省時的正解

原理：**如果整顆碟從第一天就是加密的，那麼銷毀金鑰就等於銷毀資料。**

| 前提 | 做法 | 耗時 |
| --- | --- | --- |
| ★★★★★ 用 LUKS 全碟加密 | 覆寫 LUKS header（金鑰槽） | 秒級 |
| 自我加密硬碟（SED / TCG Opal） | PSID Revert 或 Crypto Erase | 秒級 |
| Windows BitLocker | 移除保護者後重新加密／格式化 | 分鐘級 |

LUKS 的加密抹除：

```bash
# ★★★★★ 不可逆：清掉金鑰槽後，碟上的密文永遠解不開
sudo cryptsetup luksErase /dev/sdb1
```

```text
WARNING!
========
This operation will erase all keyslots on device /dev/sdb1.
Device will become unusable after this operation.

Are you sure? (Type 'yes' in capital letters): YES
```

★★★★ 保險做法是**再覆寫 header 區**（LUKS2 header 預設 16MiB）：

```bash
sudo dd if=/dev/urandom of=/dev/sdb1 bs=1M count=32 status=progress
sync
```

> [!tip] ★★★★★ 這是最值得推廣的一個做法
> **從一開始就把所有資料碟做全碟加密**，報廢時的資料銷毀就從「8 小時覆寫」
> 變成「30 秒清金鑰」。這個決定要在**建置階段**做，見
> [[020-02-03-01-svc-標準化-新機建置標準流程]]。
>
> 但前提是：★★★★ **金鑰真的有被妥善保管與備份**，否則你會在還沒報廢的時候
> 就先把自己鎖在門外。見 [[090-03-03-guide-應用安全-機密管理與金鑰保護]]。

#### 實體破壞（Destroy）

| 方式 | 適用 | 注意 |
| --- | --- | --- |
| ★★★★ **切碎（shredding）** | HDD、SSD | ★★★★★ **SSD 需要更細的顆粒**：HDD 只要碟片破碎即可，但 SSD 的資料集中在幾顆 NAND 晶片上，切得不夠細可能整顆晶片完好無損。委外時要在合約中明訂顆粒尺寸規格 |
| ★★★ **鑽孔／穿刺** | HDD | ★★★ 只穿一個孔不夠，碟片其他區域仍可讀取；且對 SSD 幾乎無效 |
| ★★★ **消磁（degauss）** | HDD、磁帶 | ★★★★★ **對 SSD 完全無效**；消磁後 HDD 報廢 |
| ★★★ **粉碎／崩解** | 全部 | 委外處理居多 |
| ★★ **焚化** | 全部 | 需符合環保法規，一般機關不自行處理 |

> [!danger] ★★★★★ 委外銷毀的四個必要條件
> 把硬碟交給廠商處理時，**在硬碟離開機關那一刻起，責任還在你身上**：
> 1. **簽訂保密協定與委外合約**，明訂銷毀方式、顆粒規格與責任
> 2. ★★★★★ **要求機關人員全程在場監毀**，或要求全程錄影並提供影片
> 3. **逐顆核對序號**：交付清單上的序號 = 實際交付顆數 = 銷毀證明上的顆數
> 4. **取得銷毀證明**（見下節）
>
> ★★★★★ **最保險的做法：在硬碟離開機房前，先自己做過一次 Purge。**
> 這樣就算委外環節出問題，資料也已經清掉了。
> 這是「深度防禦」在資料銷毀上的體現。

#### ★★★★★ 銷毀證明要寫什麼

機關報廢時應留存的紀錄。**這份文件的作用是：三年後有人問起，你拿得出來。**

必要欄位：

| # | 欄位 | 說明 |
| --- | --- | --- |
| 1 | ★★★★★ 資產編號與財產編號 | 對應到哪一台設備 |
| 2 | ★★★★★ 媒體種類與序號 | 逐顆列出：HDD/SSD/NVMe、廠牌型號、序號、容量 |
| 3 | ★★★★★ 顆數 | 與拆機清點數一致 |
| 4 | ★★★★★ 資料敏感度分級 | 一般／內部／機敏 |
| 5 | ★★★★★ 銷毀方式 | 明確寫：Clear／Purge（何種指令）／Destroy（何種破壞） |
| 6 | ★★★★ 依據 | 例如「依 NIST SP 800-88 Rev.1 Purge 等級辦理」 |
| 7 | ★★★★ 執行日期與地點 | |
| 8 | ★★★★★ 執行人與覆核人簽章 | ★ 雙人簽章，不可同一人 |
| 9 | ★★★★ 驗證方式與結果 | 例如「三處抽樣讀取，皆為 0x00」 |
| 10 | ★★★ 委外廠商資訊 | 委外時填：公司、統編、承辦人、監毀人 |
| 11 | ★★★ 影像紀錄編號 | 照片／錄影檔案編號 |
| 12 | ★★★ 保存年限 | ★★★ **依機關檔案管理規定辦理** |

範本內容（可放進 `_表單範本/`）：

```text

一、設備資訊

    廠牌型號：Dell PowerEdge R640

    #1  HDD   Seagate ST4000NM0035   S/N ZC1A9K3P   4TB
    #2  HDD   Seagate ST4000NM0035   S/N ZC1A9K4T   4TB
    #3  NVMe  Samsung MZQL2960       S/N S64GNE0T512345  960GB

    #1、#2 ── ATA Enhanced Secure Erase（hdparm --security-erase-enhanced）

    三顆完成後另委外切碎（廠商：○○環保，監毀人：王小明）

```

> [!warning] ★★★★ 三個常被漏掉的欄位
> ① **顆數** —— 沒有顆數，就沒有辦法證明「沒有一顆流出去」
> ② **驗證結果** —— 沒驗證，銷毀證明只證明了「有人執行了指令」
> ③ **覆核人** —— 單人作業的紀錄在稽核上證據力弱很多

**④ ★★★★ 驗證（三處抽樣）**

```bash
verify_zero() {
  local dev=$1
  local size_mb
  size_mb=$(( $(blockdev --getsize64 "$dev") / 1048576 ))
  for skip in 0 $(( size_mb / 2 )) $(( size_mb - 32 )); do
    local nz
    nz=$(dd if="$dev" bs=1M count=16 skip="$skip" 2>/dev/null | tr -d '\0' | wc -c)
    printf '%s offset=%sMiB 非零位元組數=%s\n' "$dev" "$skip" "$nz"
  done
}
sudo bash -c "$(declare -f verify_zero); verify_zero /dev/sdb"
```

```text
/dev/sdb offset=1907729MiB 非零位元組數=0
/dev/sdb offset=3815415MiB 非零位元組數=0
```

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| `hdparm --security-erase` 回 `SECURITY_ERASE: Input/output error` | ★★★★ 硬碟處於 `frozen` 狀態，BIOS 開機時鎖住了安全指令 | `systemctl suspend` 喚醒後重試；或熱插拔；或在 BIOS 關閉 HDD Security Freeze |
| `hdparm -I` 顯示 `not supported: enhanced erase` | 該型號韌體不支援強化抹除 | 改用一般 `--security-erase`；若也不支援，改用 `shred`（HDD）或實體破壞 |
| `hdparm --security-set-pass` 後忘記密碼 | 密碼設了但沒記下 | ★★★★ 硬碟會維持 locked 狀態；部分機種可用 master password 解，否則整顆報廢。**密碼一律用固定的作業用密碼並寫進 SOP** |
| `nvme: command not found` | 未安裝 nvme-cli | `sudo apt install nvme-cli` / `sudo dnf install nvme-cli` |
| `nvme sanitize` 回 `INVALID_FIELD: A reserved coded value...` | ★★★ 該裝置不支援指定的 sanitize 動作（`sanicap` 對應位元為 0） | `nvme id-ctrl /dev/nvmeX \| grep sanicap` 確認支援哪一種；改用 `nvme format --ses=1` |
| Sanitize 進行到一半斷電，之後裝置無法存取 | ★★★★ SSD 進入 Sanitize Failed 狀態 | 嘗試 `nvme sanitize --sanact=1`（Exit Failure Mode）；救不回就直接實體破壞 |
| 對 SSD 跑完 `shred -n 3`，用救援工具仍讀出檔案片段 | ★★★★★ Wear leveling 使覆寫寫不到原實體區塊 | **SSD 一律用 Sanitize／Secure Erase／加密抹除／實體破壞**，不要用覆寫 |
| 消磁機處理過的 SSD 仍能讀出資料 | ★★★★★ NAND 是電荷儲存，不受磁場影響 | 消磁只適用 HDD 與磁帶；SSD 改用韌體抹除或實體破壞 |
| `dd if=/dev/zero of=/dev/sda` 誤刪了工作站系統碟 | ★★★★★ 只看裝置代號沒看序號，代號因插拔順序改變 | ★ 動手前一律 `smartctl -i /dev/sdX \| grep -i serial` 核對序號，且雙人覆核 |
| `smartctl` 回 `Unknown USB bridge` | 透過 USB 外接盒連接，SMART 指令無法穿透 | 加 `-d sat`（`smartctl -d sat -A /dev/sdb`）；仍不行就直接接 SATA |
| RAID 卡後面的實體碟看不到 SMART | ★★★ 硬碟被 RAID 卡包起來 | `smartctl -d megaraid,N /dev/sda`（LSI/PERC）或 `-d cciss,N`（HP） |
| 驗收時 `lscpu` 顯示核心數是規格的兩倍 | ★★★ 把超執行緒數當成實體核心數 | 實體核心 = `Core(s) per socket` × `Socket(s)`；`CPU(s)` 是邏輯處理器數 |
| 驗收記憶體只認到標稱的 75% | 記憶體條沒插滿／插錯槽位／有壞條 | `dmidecode -t memory` 逐條看；對照主機板的記憶體插槽配置表重插 |
| 保固查詢網頁查不到序號 | ★★★ 抄到的是主機板序號或機殼貼紙上的其他號碼 | 用 `dmidecode -s system-serial-number` 取得原廠認的 Service Tag |
| 保固明明還在，原廠說已過期 | ★★★★ 保固起算日是**出貨日**不是驗收日，機器在倉庫躺了半年 | 採購時就要求「保固自驗收日起算」並寫進契約；已發生的話拿驗收紀錄向原廠申請調整 |
| 汰換預算年年沒編到 | ★★★★★ 評估時間點太晚，錯過預算編列時程 | 汰換前 18～24 個月就要完成評估與提報 |
| 新機上線後舊機馬上拆掉，結果月結出錯無法回復 | ★★★★ 平行運轉期不足一個業務週期 | 舊機保留至少一個完整業務週期並完成一次還原演練後才下架 |
| 報廢設備堆在倉庫三年，硬碟沒清 | ★★★★★ 下架與銷毀之間沒有期限與負責人 | 下架檢查表第 12 項必須填「銷毀負責人 + 期限」，並列入每季追蹤 |
| 委外銷毀後才發現少一顆硬碟 | ★★★★★ 交付前未逐顆核對序號 | 拆機清點、裝箱封條、交付清單、銷毀證明四處顆數必須一致 |

## 安全性注意事項

> [!danger] ★★★★★ 報廢設備的「三個最危險的角落」
> 1. **倉庫裡等待報廢的機器** —— 沒人管、沒上鎖、硬碟還在裡面。
>    ★★★★★ **正確做法：下架時就把硬碟拆出來單獨列管上鎖**，機殼可以隨便放，硬碟不行。
> 2. **RAID 陣列裡換下來的壞碟** —— 「反正它壞了」是最危險的想法。
>    ★★★★ 壞碟往往只是部分磁區壞，**其餘資料完好可讀**。壞碟一樣要走完整銷毀流程。
> 3. **備份磁帶與外接備份碟** —— 常常不在資產清冊上，報廢時整批被忽略。

> [!danger] ★★★★★ 不要用「已格式化」當成資料已清除
> `mkfs`、Windows 的快速格式化、刪除分割表 —— 這些**都只是改寫了檔案系統的目錄結構**，
> 資料本體原封不動，任何一套救援軟體都讀得回來。
>
> 同理，以下這些也**不算**資料銷毀：
> - 刪除檔案、清空資源回收筒
> - 重灌作業系統
> - 刪除／重建 RAID 陣列
> - 恢復原廠設定（部分設備會，部分不會，不能假設）

> [!warning] 網路設備與非硬碟媒體也存有資料 ★★★★
> 報廢時容易忘記的儲存位置：
>
> | 設備 | 存了什麼 | 處理 |
> | --- | --- | --- |
> | ★★★★ 交換器／路由器／防火牆 | 設定檔（含 SNMP community、管理密碼雜湊、VPN 預先共享金鑰） | 恢復原廠設定 + 清除 flash 上的設定檔備份 |
> | ★★★★ 伺服器 BMC（iDRAC／iLO） | 管理帳號、憑證、事件日誌 | ★★★ 執行 BMC 的 reset to default，並確認帳號已清 |
> | ★★★ RAID 卡 | 快取中的資料、陣列設定 | 清除 foreign config 與 NVRAM 設定 |
> | ★★★★ UPS 網管卡 | 網路設定、SNMP 設定、通知信箱 | 恢復原廠設定 |
> | ★★★★ 多功能事務機 | ★★★★★ **內建硬碟裡有列印／掃描過的文件影像** | 依原廠程序執行硬碟抹除，或拆出硬碟自行銷毀 |
> | ★★★ 影像監控主機（NVR） | 錄影檔 | 依 [[040-02-13-guide-機房-機房實體安全]] 的保存規定處理後銷毀 |
>
> ★★★★★ **多功能事務機是機關最常忽略的一個** —— 它是一台有硬碟的電腦，
> 而它硬碟裡有全單位印過、掃描過的公文影像。

> [!warning] Secure Erase 密碼的管理 ★★★★
> `hdparm --security-set-pass` 設下的密碼若忘記，硬碟會維持在 locked 狀態而無法使用。
> 建議：
> - ★★★ SOP 中**固定使用同一組作業用密碼**（例如 `Eras3Me`），並寫在銷毀作業程序書裡
> - 這組密碼**不是機密**（它的用途就是立刻被抹除掉），但要能被下一個執行的人查到
> - ★★★★ 抹除完成後密碼會自動清除，`hdparm -I` 應顯示 `not enabled`

> [!tip] 建置時就決定報廢時的難易度 ★★★★★
> 三個在建置階段就該做的決定，會讓五年後的報廢輕鬆十倍：
> 1. ★★★★★ **全碟加密（LUKS / BitLocker / SED）** → 報廢時 30 秒完成加密抹除
> 2. ★★★★ **清冊記錄每顆硬碟序號與 ROTA（HDD/SSD）** → 報廢時不用現場才來查
> 3. ★★★ **資料敏感度分級寫進清冊** → 報廢時直接查得到該用哪一級銷毀

### ★★★★★ 資料銷毀速查

| 媒體 | Clear | Purge | Destroy |
| --- | --- | --- | --- |
| **HDD** | `shred -v -n 1 -z /dev/sdX` | `hdparm --security-erase-enhanced` 或消磁 | 切碎 / 鑽孔 / 粉碎 |
| **SATA SSD** | ★★★★ 覆寫不可靠 | `hdparm --security-erase-enhanced` 或 SED Crypto Erase | ★★★★★ 切碎（顆粒要更細） |
| **NVMe SSD** | ★★★★ 覆寫不可靠 | `nvme sanitize --sanact=2`（Block）或 `--sanact=4`（Crypto） | ★★★★★ 切碎（顆粒要更細） |
| **LUKS 加密碟** | — | `cryptsetup luksErase` + 覆寫 header | 視需要 |
| **磁帶** | 覆寫 | 消磁 | 切碎 / 焚化 |
| **光碟** | — | — | 切碎 |

| 關鍵指令 | 說明 |
| --- | --- |
| ★★★★★ `sudo hdparm -I /dev/sdX \| grep frozen` | **執行 Secure Erase 前必查**，必須 `not frozen` |
| ★★★★ `sudo hdparm --user-master u --security-set-pass PASS /dev/sdX` | 設密碼（前置步驟） |
| ★★★★★ `sudo hdparm --user-master u --security-erase-enhanced PASS /dev/sdX` | 強化抹除（不可逆） |
| ★★★★ `sudo nvme id-ctrl /dev/nvmeX \| grep sanicap` | 查支援哪種 sanitize |
| ★★★★★ `sudo nvme sanitize /dev/nvmeX --sanact=2` | Block Erase（不可逆） |
| ★★★★ `sudo nvme sanitize-log /dev/nvmeX` | 查進度；SSTAT 低 3 位 `010` = 成功 |
| ★★★★★ `sudo cryptsetup luksErase /dev/sdX1` | 加密抹除（不可逆） |
| ★★★ `sudo blkdiscard -f /dev/nvmeXnY` | TRIM 全碟，**不可單獨當銷毀方法** |
| ★★★★★ `sudo smartctl -i /dev/sdX \| grep -i serial` | **動手前用序號確認裝置** |
| ★★★★ `sudo dd if=/dev/sdX bs=1M count=16 skip=N \| tr -d '\0' \| wc -c` | 驗證：輸出 0 表示該段全為零 |

### 三個絕對不要 ★★★★★

| 不要 | 為什麼 |
| --- | --- |
| 不要用覆寫（shred / dd）當成 SSD 的銷毀方法 | Wear leveling 使覆寫寫不到原實體區塊，且碰不到超額配置區 |
| 不要用消磁機處理 SSD | NAND 是電荷儲存，不受磁場影響 |
| 不要把「格式化 / 重灌 / 刪 RAID」當成資料已清除 | 只改了目錄結構，資料本體完好，救援軟體讀得回來 |

## 練習題

> [!question]- 練習 1：跑一次汰換評分
> 一台 2021 年驗收的伺服器，保固 2026-06 到期（原廠仍提供延保），
> 尖峰 CPU 使用率 55%，近 12 個月零故障，SMART 全正常，
> 可升級至最新 LTS，能耗與新機相當，跑的是內部知識庫（非關鍵）。
> 請計算總分並判定。
>
> **參考答案**
>
> ```
> 役齡     5 年（4～6）          → 2 × 1 = 2
> 保固     已過保但可延保        → 2 × 2 = 4
> 支援     原廠支援中            → 0 × 3 = 0
> 效能     55%（< 60%）          → 0 × 2 = 0
> 可靠度   0 次故障              → 0 × 3 = 0
> 健康     SMART 正常            → 0 × 2 = 0
> 相容性   可升級                → 0 × 3 = 0
> 能耗     相當                  → 0 × 1 = 0
> 角色     非關鍵                → 0 × 2 = 0
> ─────────────────────────────
> 總分     6 / 76  → ≤ 20 → 繼續服役
> ```
>
> ★★★★ 但保固 2026-06 到期，必須依「過保三選一」做決定：
> 這台是非關鍵角色且原廠可延保 → 建議**不延保、走備品策略或直接降級**，
> 並在清冊上標明「已過保、續用中」。

> [!question]- 練習 2：判斷該用哪一級銷毀
> 以下四個情境，各要用哪一級（Clear／Purge／Destroy）？為什麼？
> ① 測試機的 SATA SSD，要移到另一台測試機用
> ② 存過人事資料庫備份的 HDD，要當廢鐵回收
> ③ 一般檔案伺服器的 HDD，要移轉給另一個機關使用
> ④ RAID 陣列中換下來的壞掉 HDD
>
> **參考答案**
>
> | # | 等級 | 理由 |
> | --- | --- | --- |
> | ① | ★★★ **Clear**（或 Purge 更保險） | 資料非敏感、去向仍在機關控制範圍內。但因為是 SSD，Clear 也不能用覆寫，建議直接 `hdparm --security-erase` |
> | ② | ★★★★★ **Destroy** | 存過個資 + 離開機關控制範圍 = 一定實體破壞。★ 建議破壞前先自己做一次 Purge |
> | ③ | ★★★★ **Purge + 驗證** | 資料屬內部但去向是另一個機關（仍屬公務體系）；Purge 後三處抽樣驗證 |
> | ④ | ★★★★★ **Destroy** | 壞碟往往只是部分磁區壞，其餘資料完好可讀，且通常無法執行 Secure Erase → 直接實體破壞 |

> [!question]- 練習 3：寫一支報廢前檢查腳本
> 寫一支腳本，接受一個裝置代號與一個預期序號，只有序號相符才印出「確認相符，可以進行銷毀」，
> 並附上這顆碟是 HDD 還是 SSD 的判斷。
>
> **參考答案**
>
> ```bash
> #!/usr/bin/env bash
> # pre-destroy-check <裝置> <預期序號>
> set -euo pipefail
> DEV=${1:?用法: pre-destroy-check /dev/sdX SERIAL}
> WANT=${2:?請提供預期序號}
>
> [ -b "$DEV" ] || { echo "錯誤：$DEV 不是區塊裝置" >&2; exit 1; }
>
> GOT=$(smartctl -i "$DEV" | awk -F': *' '/Serial [Nn]umber/{print $2; exit}' | tr -d ' ')
> ROTA=$(lsblk -dn -o ROTA "$DEV")
> TYPE=$([ "$ROTA" = "1" ] && echo "HDD（可用覆寫/消磁/Secure Erase）" || echo "SSD（★★★★★ 不可用覆寫或消磁）")
> SIZE=$(lsblk -dn -o SIZE "$DEV")
>
> echo "裝置：$DEV  容量：$SIZE"
> echo "型態：$TYPE"
> echo "實際序號：$GOT"
> echo "預期序號：$WANT"
>
> if [ "$GOT" = "$WANT" ]; then
>   echo "✔ 確認相符，可以進行銷毀"
> else
>   echo "✘ 序號不符！停止作業" >&2
>   exit 2
> fi
> ```
>
> ★★★★ 重點：**用序號而非裝置代號做判斷**，並自動提示 HDD/SSD 該用哪類方法。

> [!question]- 練習 4：寫三條不綁標又擋得住劣質品的規格
> 你要採購一台 2U 伺服器給資料庫用。請各寫一條關於
> ①「遠端管理能力」②「保固服務水準」③「韌體安全更新」的規格條文。
>
> **參考答案**
>
> ① **遠端管理**：
> 「須內建獨立於作業系統之遠端管理控制器，具專屬管理網路埠，
>  支援 IPMI 2.0 或 Redfish 標準介面，並可遠端執行開關機、監看主控台、
>  掛載虛擬光碟／映像檔，及讀取硬體事件日誌。」
> ★★★★ 用開放標準（IPMI／Redfish）取代專屬產品名稱。
>
> ② **保固服務水準**：
> 「保固期 5 年，自機關驗收合格之日起算；故障時須於次一工作日到府維修
>  （Next Business Day On-site），並須檢附原廠或原廠台灣代理商出具之保固證明。」

>

> [!question]- 練習 5：規劃一次 SSD 銷毀
> 你有 10 顆從資料庫伺服器拆下的 NVMe SSD，存過個資，要對外報廢。
> 請寫出完整作業計畫（含人力、步驟、驗證、文件）。
>
> **參考答案**
>
> **前置**
> - 雙人作業（執行人 + 覆核人），準備獨立的銷毀工作站（不連正式網路）
> - 從清冊列印 10 顆的序號清單
>
> **步驟**
> 1. 逐顆用 `smartctl -i` 核對序號，兩人各唸一次
> 2. `nvme id-ctrl /dev/nvmeX | grep sanicap` 確認支援的 sanitize 動作
> 3. `nvme sanitize /dev/nvmeX --sanact=2`（Block Erase）
> 4. `nvme sanitize-log` 輪詢至 SSTAT 低 3 位為 `010`
> 5. ★★★★ 三處抽樣驗證（起始／中段／末段各 16MiB，非零位元組數須為 0）
> 6. 通過的貼「已 Purge」標籤，未通過的另行標記
> 7. 全部裝箱、貼封條、封條簽名並註記顆數 = 10
> 8. ★★★★★ 委外切碎，**機關人員全程監毀並錄影**，合約明訂顆粒尺寸規格
> 9. 核對廠商銷毀證明的顆數與序號
>
> **文件**
> - 儲存媒體銷毀紀錄（12 欄位齊全，含每顆的驗證結果）
> - 交付清單、封條照片、監毀影像
> - 財產報廢申請（附銷毀證明影本）
>
> ★★★★★ **關鍵**：因為存過個資且對外處分，必須做到 Destroy；
> 而在硬碟離開機關前先自己做 Purge，是委外環節出問題時的最後保險。

## 小測驗

Q1. 一台機器身上有「保固期」「折舊年限」「實際堪用年限」三條線。請說明當「保固到期但折舊未完」時，維運人員有哪三個選項。

Q2. （是非）機器如果還跑得順、效能也夠，就沒有汰換的必要。

Q3. （選擇）以下哪一個規格條文最不容易被認為有排除競爭的問題？
　　(A) 須為 ○○ 廠牌 R650 型或同等品
　　(B) 須支援 ○○ 廠牌專屬遠端管理軟體
　　(C) 須具備獨立於作業系統之管理控制器，支援 IPMI 2.0 或 Redfish
　　(D) 機箱尺寸須為 482×780×87 mm

Q4. 驗收時 `lscpu` 顯示 `CPU(s): 64`、`Core(s) per socket: 16`、`Socket(s): 2`。規格書要求「實體核心數至少 32」，這台符合嗎？為什麼？

Q5. 請說明 NIST SP 800-88 的 Clear、Purge、Destroy 三級差在哪裡，以及各自之後媒體還能不能繼續使用。

Q6. ★★★★★ 為什麼對 SSD 執行 `shred -n 3 /dev/sdX` 無法保證資料被清除？請列出至少兩個機制。

Q7. （是非）消磁機（degausser）可以用來銷毀 SSD 上的資料。

Q8. 這行指令會發生什麼，以及執行前必須先確認什麼？
```bash
sudo hdparm --user-master u --security-erase-enhanced Eras3Me /dev/sdb
```

Q9. 你的機關要在 2029 年 Q1 汰換一批伺服器。請說明「最晚什麼時候必須完成汰換評估」，以及錯過的後果。

Q10. 一顆硬碟做完 Secure Erase，指令回報成功。請說明為什麼還必須做驗證，以及驗證怎麼做、驗到什麼算通過。

> [!question]- 測驗答案
> **Q1.** ★★★★ 三個選項：① **延保**（適合關鍵設備且原廠仍提供）
> ② **備品策略**（買同型號備機或先備關鍵零件）
> ③ **降級使用**（移到壞了也不會馬上出事的角色）。
> ★★★★★ 關鍵是**必須明確選一個**；什麼都不做等於預設選了最貴的選項。
> （見「保固期結束那天，風險曲線會跳一階」）
>
> **Q2.** ★★★★★ **錯。** 汰換有四個觸發條件，「效能不足」只是其中之一。
> 最危險的是「失去支援」—— 原廠停止韌體與安全更新後，BMC 漏洞無法修補、
> 新版 OS 無驅動，這是**資安問題不是效能問題**，「還能跑」不是留下它的理由。
> （見「汰換的四個觸發條件」與「直接汰換條款」）
>
> **Q3.** ★★★★ **(C)**。它用**開放標準**（IPMI 2.0／Redfish）描述能力，多家廠商都能符合。
> (A) 直接指名廠牌型號；(B) 指向專屬軟體形同指定廠牌；
> (D) 給了唯一尺寸值而非上下限與理由。
> （見「規格撰寫：不綁標，但要擋得住劣質品」）
>
> **Q4.** ★★★★ **符合。** 實體核心數 = `Core(s) per socket × Socket(s)` = 16 × 2 = **32**。
> `CPU(s): 64` 是**邏輯處理器數**（含超執行緒），不是實體核心。
> ★★★ 這是驗收最常見的誤判點，兩個方向都會錯：把 64 當實體核心（誤判合格）
> 或把 16 當總核心數（誤判不合格）。（見「驗收：三層檢查」）
>
> **Q5.**
> - ★★★ **Clear**：用一般讀寫介面覆寫／重設，擋得住一般作業系統與救援軟體 → 媒體**可繼續使用**
> - ★★★★ **Purge**：用韌體層指令（Secure Erase／Sanitize／Crypto Erase）或消磁，
>   擋得住實驗室技術 → 媒體**可繼續使用**（消磁除外，消磁後 HDD 報廢）
> - ★★★★★ **Destroy**：實體破壞（切碎／粉碎／崩解／焚化）→ 媒體**報廢**
> （見「NIST SP 800-88 的三級」）
>
> **Q6.** ★★★★★ 至少三個機制：
> ① **Wear Leveling（磨損平均）**：覆寫 LBA 時控制器把新資料寫到別的實體區塊，
>    只改 FTL 對應表，**原區塊上的舊資料原封不動留著**
> ② **Over-provisioning（超額配置）**：7～28% 的容量主機根本看不到，覆寫指令碰不到
> ③ **Bad Block Retirement（壞塊退役）**：退役區塊上的舊資料仍在，一般介面存取不到
> 所以 SSD 必須用韌體層 Sanitize／Secure Erase、加密抹除，或實體破壞。
> （見「為什麼 HDD 的做法不能直接套到 SSD」）
>
> **Q7.** ★★★★★ **錯。** 消磁機靠強磁場破壞磁性儲存，
> 而 NAND 快閃是**電荷儲存**，不受磁場影響。消磁只適用 HDD 與磁帶。
> （見「實體破壞」與「三個絕對不要」）
>
> **Q8.** ★★★★★ 它會對 `/dev/sdb` 執行 **ATA 強化安全抹除**，
> 由硬碟韌體自己抹除全碟（含重新配置的磁區），**不可逆**。
> 執行前必須確認四件事：
> ① `hdparm -I /dev/sdb` 顯示 **`not frozen`**（frozen 會直接失敗）
> ② 該碟支援 `enhanced erase`
> ③ ★★★★★ **用 `smartctl -i /dev/sdb` 核對序號**，確認 `/dev/sdb` 真的是要銷毀那顆
> ④ 已先用 `--security-set-pass` 設好同一組密碼
> （見「ATA Secure Erase」）
>
> **Q9.** ★★★★★ 最晚 **2027 年 Q2** 完成評估（汰換前 18～24 個月），
> 因為 Q3 就要提報進入 2028 年度預算編列作業。
> 錯過的後果：**預算編不到，整批汰換自動延後一年**，
> 而這一年裡設備仍在過保、失去支援的狀態下服役。
> （見「汰換預算的時程」與練習 6）
>
> **Q10.** ★★★★★ 必須驗證的原因：**有實際案例是韌體回報成功但實際沒有執行抹除**，
> 指令的回傳值只證明「指令被接受」，不證明「資料被清掉」。
>
> 驗證方式：在碟的**起始、中段、末段三處**各讀取一段（例如 16MiB），確認內容全為 `0x00`：
> ```bash
> sudo dd if=/dev/sdb bs=1M count=16 skip=N 2>/dev/null | tr -d '\0' | wc -c
> ```
> 輸出為 **0**（非零位元組數為 0）即該段通過；三處都通過才算合格，
> 並把驗證結果寫進銷毀紀錄的「驗證方式與結果」欄。
> 任一處未通過，就換方法重做，或直接改走實體破壞。
> （見「驗證是必要步驟，不是加分項」）
