# 機房與硬體管理 常見故障排除

> [!abstract] 怎麼用這份手冊
> - 依「你在現場看到什麼」查，不是依「這屬於哪個系統」查
> - 找到症狀 → 看判斷分流 → 照編號步驟做 → 想懂原理再點進原文
> - ★★★★★ 緊急時直接看下一節的「一頁式急救卡」，不要從頭讀
> - ★★★★★ 本手冊**不重講原理**。每個情境結尾的「原理詳見」就是原文入口
> - ★★★★★ **停電、空調全停、漏水、火警**這四類重大異常有專屬的決策樹與行動時序，
>   已經寫在 [[040-02-14-guide-機房-機房異常應變]]，本手冊**不重複**，直接跳過去看。
>   本手冊處理的是那四類之外的**日常故障**。

> [!warning] 未實機驗證
> 本篇的指令輸出、面板讀值與現場數字都是**示意**，用來說明「該看哪個欄位、
> 該用什麼門檻判斷」。實際的欄位名稱、單位縮放與門檻值會因廠牌、機型、韌體版本
> 而不同，動手前務必以你自己機房的實測基線與設備手冊為準。
> 涉及配電盤、UPS 內部、電池組的作業一律由**合格電氣技術人員**執行。

## 先確認這不是四大重大異常

★★★★★ 動手排查之前先花 10 秒判斷：**這是日常故障，還是已經構成重大異常？**
只要落在下面四格任一格，立刻離開本手冊，走 [[040-02-14-guide-機房-機房異常應變]]。

| 你看到的 | 這是 | 去哪 |
| --- | --- | --- |
| ★★★★★ 市電中斷、UPS 已轉電池、發電機起動或沒起動 | 停電事件 | [[040-02-14-guide-機房-機房異常應變]]「一、停電應變」 |
| ★★★★★ 空調**全部**停止運轉，機房溫度正在快速上升 | 空調故障事件 | [[040-02-14-guide-機房-機房異常應變]]「二、空調故障應變」 |
| ★★★★★ 地面有積水、天花板滴水、漏水偵測告警 | 漏水事件 | [[040-02-14-guide-機房-機房異常應變]]「三、漏水應變」 |
| ★★★★★ 有煙、有焦味、火警受信總機動作、氣體滅火即將放射 | 火警事件 | [[040-02-14-guide-機房-機房異常應變]]「四、火警應變」 |

★★★★ 分不出來時，用這個界線：**「還有時間查原因」＝日常故障（本手冊）；
「必須先保人、先保設備，原因等一下再查」＝重大異常（應變篇）**。

## 一頁式急救卡

★★★★★ 到現場先跑這一輪，**由上而下，看到異常就停下來往對應情境走**。
沒有電腦時，前六項用眼睛和耳朵就做得完。

```text
─── 進門前 30 秒：不用開電腦就能做的四件事 ───────────────────
①【聽】 空調有沒有在吹？聲音跟平常一樣嗎？        異常 → 情境一 / 應變篇
②【聞】 有沒有焦味、塑膠味、酸味？                 ★★★★★ 有 → 立刻停手，走應變篇
③【看】 一進門的體感溫度、地面有沒有水漬            熱 → 情境一；有水 → 應變篇
④【摸】 摸一下最近的金屬機櫃門                      會電到 → 情境十四（乾燥靜電）

─── 環境面板與 UPS 面板：抄下這六個數字 ─────────────────────
⑤ 冷通道溫度（不是牆上溫度計，是機櫃進風口）      > 27 °C → 情境一 / 二
⑥ 相對溼度 RH                                      < 30% → 情境十四【1】
                                                    > 60% 或有結露 → 情境十四【2】
⑦ UPS 模式（Online / On Battery / Bypass）         Bypass → ★★★★★ 沒有保護，情境四
⑧ UPS 負載率 %                                     > 70% → 情境四【2】
⑨ 電池狀態燈／告警燈                                亮 → 情境三
⑩ PDU 每路電流 A（A 路、B 路各記）                  兩路差很多 → 情境五【3】
```

```bash
# ─── 有電腦時：從管理網段一輪掃過去 ────────────────────────────
# 【1】機櫃裡的機器還在不在（先確認災情範圍，再查原因）
for ip in 10.20.40.11 10.20.40.12 10.20.40.13; do
  printf '%-14s ' "$ip"; ping -c1 -W1 "$ip" >/dev/null 2>&1 && echo OK || echo FAIL
done
#   全 FAIL 但 BMC 通 → OS 層問題；BMC 也不通 → 供電或網路，走情境五 / 六

# 【2】伺服器自己回報的入風溫度（★★★★★ 環境感測器與它對不上時，以它為準）
ipmitool -I lanplus -H <BMC_IP> -U <帳號> -E sdr type Temperature
#   Inlet 明顯高於環境感測器 → 熱氣回流，情境一 / 二

# 【3】硬體事件日誌：機器自己記下的第一手證據
sudo ipmitool sel list | tail -20
#   Power Supply / Memory / Drive Slot / Temperature 事件 → 情境六 / 八

# 【4】UPS 現況（有裝 NUT 時）
upsc <ups名稱>@localhost 2>/dev/null | grep -E 'ups.status|battery.charge|battery.runtime|ups.load'
#   ups.status 有 RB → 情境三；有 OVER → 情境四；有 BYPASS → ★★★★★ 情境四【4】

# 【5】RAID 與磁碟冗餘有沒有掉
cat /proc/mdstat 2>/dev/null | grep -E '^\s*\['
sudo storcli64 /c0/vall show 2>/dev/null || sudo perccli64 /c0/vall show 2>/dev/null
#   Degraded / [U_] → ★★★★★ 情境八，當天處理，不要拖過夜

# 【6】網路埠實體層
sudo ethtool <介面> | grep -iE 'Speed|Duplex|Link detected'
#   Link 不亮或 Speed 100Mb/s（該是 1000）→ 情境十

# 【7】時間有沒有對（門禁、錄影、日誌對帳全靠它）
timedatectl | grep -E 'Local time|synchronized'
#   synchronized: no → 情境十三【3】與 [[020-01-28-cmd-Linux-時間同步NTP與chrony]]
```

> [!tip] ★★★★★ 三句話版本
> ① **量對地方**：溫度看機櫃進風口、電流看 PDU 讀值、溫度爭議以 IPMI Inlet 為準。
> ② **先確認冗餘還在不在**：雙電源掉一路、RAID 降級、UPS 轉旁路 ——
> 這些都「還沒出事」，但已經沒有下一次機會了，當天就要處理。
> ③ **動手之前先確認你動的是哪一台**：核對序號、核對 U 位、核對兩端標籤，
> 三者一致才動手。機房裡最貴的錯誤全部都是「拔錯／拆錯／插錯」。

## 依症狀展開

### ★★★★★ 情境一：機房溫度慢慢爬高，但空調面板顯示一切正常

**現象**：牆上溫度計或空調回風溫度看起來正常（22～24 °C），空調也在吹冷風，
但伺服器陸續回報高溫、風扇全速、甚至降頻。而且是**「慢慢變差」**，
不是某天突然壞掉 —— 上個月還好好的，這個月就常常告警。

★★★★★ 這一類問題的共同特徵：**空調沒壞，壞的是氣流**。
冷氣做出來的冷量沒有進到設備裡，或者熱氣繞回去被設備再吸一次。

**判斷分流**：★★★★★ 第一步永遠是「量對地方」——
空調面板量的是**回風**，牆上溫度計量的是**房間平均**，
但設備真正吃到的是**機櫃前門進風口**，三者可以差非常多。

```text
拿手持溫溼度計，貼近機櫃前門網孔外約 5 公分，量上／中／下三點：

 上點與下點溫差 > 5 °C          → 熱氣回流    走【1】（最常見，占大半）
 三點都高但溫差小（< 3 °C）      → 冷量不足    走【2】
 只有部分機櫃高，其他櫃正常      → 局部問題    跳情境二
 手持量到的與環境感測器差 > 3 °C → 感測器問題  走【3】
 三點都正常，但 IPMI Inlet 很高  → 機器內部    走【4】
```

★★★★ 記錄格式（直接抄在巡檢表上，之後要拿來比對趨勢）：

```text
時間     機櫃  上點   中點   下點   上下溫差  室外溫度  備註
14:30   A01   31.2   27.8   24.1    7.1      34 °C    上方三台在告警
14:35   A02   26.4   25.9   24.3    2.1      34 °C    正常
14:40   A03   30.8   28.1   24.6    6.2      34 °C
```

**處置步驟**：

【1】★★★★★ 上下溫差大 ＝ 熱氣回流。**不用花錢的四件事先做完再談買設備。**

依序檢查，每做完一項就重新量一次上點溫度，看有沒有降下來：

```text
① 空 U 位有沒有裝盲板？          ← ★★★★★ 投報率最高，成本數千元
   走一遍每個機櫃，把所有沒有設備的 U 位補滿盲板。
   ★★★★ 最常被漏掉的三個位置：機櫃最上緣、最下緣、設備之間的 1U 縫。

② 機櫃側面與底部有沒有開口？
   進線孔、地板出線孔、機櫃側板與立柱之間的縫 —— 用毛刷式進線板或封堵材封起來。
   ★★★★ 底部開口特別要命，冷風會直接從機櫃底部漏掉。

③ 前後門網孔通透率夠不夠？被東西擋住了嗎？
   後門前面堆紙箱、機櫃後緊靠牆、理線槽把整片後門擋住 —— 都會讓熱氣排不出去。

④ 冷熱通道有沒有排反？
   ★★★★★ 走一圈看每台設備的「進風面」是不是都朝向同一條通道。
   有一台裝反（後進前出），它就會把熱風吐進冷通道，污染整排。
```

★★★★ 每做完一項量一次，就能知道**哪一項貢獻了多少度**，
這個數字比任何理論都有說服力，也是下次要預算時的依據。

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 上點比下點高 5～8 °C，機櫃有很多空 U | 熱氣從機櫃後方繞回前門上緣 | ★★★★★ 補滿盲板；把發熱最大的設備移到中下段 |
| ★★★★ 冷風從機櫃底部漏走，設備吸不到 | 地板出線孔沒封、機櫃底部有開口 | 用毛刷式進線板封堵；穿孔地板移到冷通道 |
| ★★★★ 某一台設備把熱風吐進冷通道 | 該機型是後進前出（部分交換器、電源設備） | 加裝導風套件或反向風扇模組；不行就移到獨立位置 |
| ★★★★ 通道封閉做了，但門常開著 | 進出頻繁圖方便 | 加自閉門弓器；封閉門開啟時間納入監控 |

【2】★★★★ 三點都高但溫差小 ＝ **冷量真的不夠**，或者送不出來。這時要查空調本體。

```text
逐項確認（一項不通就停在那裡處理）：
 a. 幾台空調在跑？跟平常一樣嗎？          少一台在跑 → 該台故障或被關掉
 b. 出風口摸起來冷不冷？進出風溫差多少？   溫差太小 → 冷媒不足或壓縮機沒作用
 c. 濾網髒不髒？                          ★★★ 台灣環境粉塵多，1～2 個月就該檢查
 d. 室外機周圍有沒有堆雜物？鰭片乾淨嗎？   ★★★★ 這是最常見卻最常被忽略的一項
 e. 冷凝水排水口有沒有在滴水？            ★★★★★ 完全不滴 → 排水堵塞，即將漏水
 f. 室外溫度是不是異常高？                極端天氣時冷卻能力本來就會下降
```

★★★★ 判定門檻：**送風與回風的溫差**是最直接的指標。
溫差明顯小於平常的基線值，代表這台空調沒有在有效移熱 —— 即使它「看起來在運轉」。
沒有基線值就從今天開始記，這正是 [[040-02-10-guide-機房-機房巡檢與紀錄]] 存在的理由。

> [!danger] ★★★★★ 不要自己拆空調、不要自己補冷媒
> 冷媒是高壓系統，室外機內有高速旋轉風扇與高壓管路。
> 「出風不冷」的原因判定與冷媒作業一律由**合格冷凍空調技術人員**執行。
> 你能做而且該做的是：清濾網、淨空室外機周邊、記錄讀值、確認排水有在滴。

【3】★★★★ 手持儀器與環境感測器對不上 —— 先確認**誰是對的**，再決定要修哪一邊。

```bash
# 用伺服器自己的入風溫度當第三方裁判
ipmitool -I lanplus -H 10.20.40.14 -U admin -E sdr type Temperature | grep -i inlet
```

```text
判讀：
  手持 31 °C，IPMI 32 °C，感測器 24 °C   → ★★★★ 感測器壞了或裝錯位置，環境是真的熱
  手持 24 °C，IPMI 24 °C，感測器 31 °C   → ★★★ 感測器誤報，但也要人到現場確認一次
  手持 31 °C，IPMI 24 °C                 → ★★★ 量測位置不同（你量的位置沒有設備在吸風）
  監控畫面顯示「264 度」之類的怪值        → ★★★★ 單位縮放問題，設備回傳放大 10 倍的整數
```

★★★★ 感測器該裝在**機櫃前門網孔外約 5 公分**、上中下三點，
不是牆上、不是空調出風口、不是機櫃後面。裝錯位置的感測器比沒有更危險 ——
它會給你一個「一切正常」的假象。

【4】★★★ 環境正常但 IPMI Inlet 很高 ＝ 問題在**機器內部或它前面 5 公分**。

```text
 前面板擋住了嗎？              有些機型前門加了防塵蓋會讓進風量掉一半
 空的硬碟槽有沒有裝擋板？      ★★★★ 缺擋板等於機殼內部短路，風不走 CPU
 PCIe 空槽有沒有裝擋片？       同上
 內部風扇有沒有故障？          ipmitool sdr type Fan，看有沒有轉速掉到 0 或遠低於同型
 散熱膏／散熱片有沒有問題？    ★★★ 這要停機開殼，排在最後
```

**原理**：機房的熱幾乎全是顯熱，空調做的事是「把熱從房間搬出去」；
但冷量能不能真的進到晶片，取決於**氣流路徑**。
熱氣回流讓同一份熱被反覆吸入，於是「空調正常、房間平均溫度正常、設備照樣過熱」。
　→ 原理詳見 [[040-02-02-guide-機房-空調系統與溫溼度監控]]、[[040-02-01-guide-機房-機房環境需求]]

**預防**：
- ★★★★★ 盲板列入**下架流程的必做項目**：拆掉設備的同一趟就把盲板補上，
  不要說「下個月要裝新的」——那個下個月通常是三年
- ★★★★★ 每月巡檢固定量三個機櫃的上／中／下三點並記錄，**沒有基線就沒有趨勢**
- ★★★★ 室外機周邊淨空與濾網檢查列入每月目視項目（[[100-02-04-guide-維運-每月維護作業]]）
- ★★★★ 溫度告警一定要設「持續時間」條件，避免抖動誤報把大家訓練成無視告警

### ★★★★ 情境二：單一機櫃過熱，其他機櫃都正常

**現象**：整個機房的環境讀值都正常，但就是某一櫃（或某一櫃的上半段）持續高溫，
裡面的機器風扇全速、偶爾降頻或自動關機。

★★★★★ 「一櫃熱、其他櫃正常」是**好消息** —— 它排除了空調系統本身的問題，
把範圍縮到一個機櫃，通常一兩個小時內就能解決。

**判斷分流**：先確定「熱的是整櫃，還是櫃裡的某幾台」。

```bash
# 把該櫃與鄰櫃的所有機器 Inlet 溫度一次列出來比較
for h in 10.20.40.11 10.20.40.12 10.20.40.13 10.20.40.14 10.20.41.11; do
  printf '%-14s ' "$h"
  ipmitool -I lanplus -H "$h" -U admin -E sdr type Temperature 2>/dev/null \
    | grep -i inlet || echo '(unreachable)'
done
```

```text
整櫃每一台 Inlet 都偏高               → 該櫃的氣流或功率密度問題   走【1】
只有上半段幾台高，下半段正常          → 典型的櫃內熱氣回流         走【2】
只有一台高，同櫃其他台正常            → 那一台自己的問題           走【3】
該櫃 Inlet 正常但 CPU/Exhaust 很高    → 機器內部散熱問題           走【3】【4】
連不上 BMC                            → 先確認供電，跳情境五 / 七
```

**處置步驟**：

【1】★★★★ 整櫃偏高：先算這一櫃到底塞了多少瓦，再看它拿得到多少風。

```bash
# 從 PDU 讀該櫃的實際用電（★★★★ 用實測值，不要用銘牌加總）
snmpwalk -v2c -c <community> <PDU_IP> <電流 OID>
# 或直接看 PDU 面板讀值，A 路與 B 路都要記
```

```text
判定門檻（依你機房實際設計值調整，沒有設計值就以歷史最高為基準）：
  該櫃實際功率 明顯高於同型機櫃        → ★★★★ 功率密度過高，需要分散設備或加強送風
  該櫃功率與別櫃差不多但溫度高          → 氣流問題，回情境一【1】逐項檢查這一櫃
  該櫃位在冷通道末端／離空調最遠        → ★★★ 送風不足，調整穿孔地板或加導風
  該櫃後方緊貼牆面或被理線槽擋住        → 熱氣排不出去，調整位置或改理線方式
```

【2】★★★★★ 上半段熱、下半段正常 ＝ **這一櫃的熱氣正在從後方繞回前門上緣**。
處理順序（做一項量一次）：

```text
① 補滿這一櫃所有空 U 位的盲板             ← 先做這個，通常就解決了
② 封堵機櫃側板縫、底部進線孔
③ 把發熱最大的機器往下移（★★★★ 重的也本來就該放下面）
④ 確認前後門網孔沒有被擋住
⑤ 以上都做了還是熱 → 這一櫃需要局部加強送風，找空調廠商評估
```

【3】★★★★ 只有一台熱：看那一台自己的感測器與風扇。

```bash
sudo ipmitool sdr type Fan          # 有沒有風扇轉速異常低或 0
sudo ipmitool sdr type Temperature  # Inlet / Exhaust / CPU 各自多少
sudo ipmitool sel list | tail -20   # 有沒有記錄過溫度或風扇事件
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ 某一顆風扇轉速 0 或遠低於同組 | 風扇故障 | 熱插拔更換（★★★★ 確認是熱插拔機型再拔）；報修 |
| ★★★★ 全部風扇都全速但溫度不降 | 進風被擋、內部風道破壞、散熱片積灰 | 檢查前面板／硬碟槽擋板／PCIe 擋片；停機清灰 |
| ★★★★ Inlet 正常但 CPU 高 | 散熱器鬆脫、散熱膏乾涸、風道被線材擋住 | 停機開殼檢查（★★★★ 要走變更流程） |
| ★★★★ 加了一張 PCIe 卡之後風扇就一直全速 | BIOS 偵測到未知卡，套用保守的風扇策略 | 查該機型的風扇策略設定；用原廠認證的卡 |

【4】★★★ 該櫃溫度正常但機器一直告警 —— 先確認**告警門檻本身是否合理**。
有些機型出廠門檻設得很保守，或上一任管理者調過。
★★★★ 但**不要為了消除告警而調高門檻**，那是把警報器拆掉，不是修好問題。

> [!danger] ★★★★ 熱插拔更換風扇或 PSU 前，先確認冗餘還在
> 拔掉一顆風扇之前，先確認其他風扇都是好的；拔掉一顆 PSU 之前，
> 先確認另一顆真的有電（★★★★★ 不是「有插線」，是 PDU 讀值確認那一路有電流）。
> 在只剩單一冗餘的狀態下拔掉唯一還好的那一顆，就是自己造成停機。

**原理**：機櫃是一個獨立的氣流單元 —— 冷風從前門進、熱風從後門出。
只要這個單向路徑被破壞（空 U、側縫、底孔、後方阻擋），熱氣就會在櫃內循環，
造成「房間正常、單櫃過熱」的局部現象。
　→ 原理詳見 [[040-02-03-guide-機房-機櫃規劃與設備上架]]、[[040-02-02-guide-機房-空調系統與溫溼度監控]]

**預防**：
- ★★★★★ 上架前先算該櫃剩餘的**電力餘裕與散熱餘裕**，兩者任一不足就換一櫃
- ★★★★ 重的、熱的往下放；冗餘的一對設備分散到不同機櫃
- ★★★★ 每月巡檢時用熱像儀對同一角度拍一張，**只看變化不看絕對值**

### ★★★★★ 情境三：UPS 一直在充電、電池告警、切換時負載掉電

**現象**：三種不同嚴重度的狀況，判斷方式與急迫性完全不同：

```text
（A）電池告警燈亮／管理介面出現「Replace Battery」／ups.status 有 RB
     ★★★★ 還有市電，服務沒中斷 —— 但下一次停電可能撐不住

（B）電池一直顯示在充電，充不到 100%，或剩餘時間逐月下降
     ★★★★ 電池正在衰退，或充電器有問題

（C）★★★★★ 市電一中斷，負載就整批掉電（UPS 根本沒撐住）
     這是最嚴重的一種 —— UPS 等於不存在
```

**判斷分流**：先把 UPS 自己回報的四個欄位讀出來，這比看面板燈快也準。

```bash
upsc <ups名稱>@localhost | grep -E \
  'ups.status|battery.charge|battery.voltage|battery.runtime|battery.date|ups.load'
```

```text
判讀（★★★★ 欄位名稱依 driver 與機型而異，沒有的欄位就從面板讀）：
  ups.status 含 RB                      → 電池需更換        走【1】
  battery.charge 長期停在 100 以下       → 充不飽            走【2】
  battery.runtime 逐月下降（負載沒變）    → 容量衰退          走【2】
  battery.voltage 明顯低於標稱           → 有電池串失效      走【1】【3】
  切換時直接掉電                         → ★★★★★ 走【4】
  完全讀不到（Connection refused 等）     → 通訊層問題，見 [[040-02-06-svc-機房-UPS安裝與監控設定]]
```

**處置步驟**：

【1】★★★★★ `RB`（Replace Battery）亮了 —— 先確認是**真的該換**還是**狀態沒重設**。

```text
① 這組電池上次更換是什麼時候？（查 battery.date 或維護紀錄）
   → 已接近或超過廠商建議年限 → 就是該換了，走採購流程
   → 才剛換不久 → 走 ②

② 剛換完就亮 RB？部分機型換完電池要手動執行「電池更換確認」或跑一次自我測試
   才會重新判定。依機型在面板或管理軟體上執行電池重設，或跑一次快速自我測試。

③ 重設後 RB 還在 → 真的有電池失效，走 ③【量測】
```

```text
③ 量測（★★★★ 內阻量測與放電測試建議委外或由受訓人員執行）：
   a. 逐顆量電池端電壓 → 找出明顯低於其他顆的那一顆
   b. 逐顆量內阻       → 與出廠基準或同批其他顆比較，明顯偏高者判定劣化
   c. 目視             → 外殼鼓脹、端子腐蝕、漏液
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 電池外殼鼓脹 | 過充、溫度過高，熱失控前兆 | ★★★★★ **立刻停用該電池組**，不要繼續使用，通知廠商 |
| ★★★★ 端子有白色／綠色粉狀腐蝕物 | 電解液微量滲漏、環境潮濕 | 依安全程序斷電後清潔；腐蝕嚴重就整串更換 |
| ★★★★★ 換了電池 `RB` 還在 | 部分機型需手動執行電池更換確認 | 依機型執行電池重設，或跑一次快速自我測試後再看 |
| ★★★★★ 只換壞掉的那一顆 | 為了省錢混用新舊電池 | ★★★★★ 整串換掉；已混用的話把新的那顆一起換掉重來 |
| ★★★★ 電池才用兩年就嚴重衰退 | 電池區長期高溫（緊鄰發熱設備） | ★★★★★ VRLA 溫度每高 10 °C 壽命減半；移到通風處，提前編列預算 |
| ★★★★ 平常自我測試都「通過」，停電只撐幾分鐘 | ★★★★★ 快速自我測試**不驗證容量** | 必須做放電測試才知道真實續航；排進年度行事曆 |

【2】★★★★ 充不飽、續航逐月下降 —— 先排除「不是電池的問題」。

```text
① 負載有沒有變？   ★★★★ battery.runtime 會隨負載變動，比較趨勢要看「相同負載下」的值
② 環境溫度多少？   電池區溫度偏高會同時造成充電異常與加速老化
③ 最近有沒有連續跳電？ ★★★★★ 電池還沒充飽又放電，會看到續航暴跌
                        —— 這是暫時現象，等充飽再測
④ 排除以上還是充不飽 → 電池老化或充電器故障，安排容量測試與廠商檢修
```

★★★★ 判定門檻：**同樣負載率下的實測續航時間，低於設計值的某個比例就該換**。
這個比例要在採購時就與廠商約定並寫進契約，不要等出事才吵。
沒有實測值可比的話，這正是為什麼要每年做一次放電測試。

【3】★★★★ 決定要換的時候，換電池本身是一次**有服務中斷風險的變更**：

> [!danger] ★★★★★ 電池組是帶電的，而且是低電壓大電流
> - 電池組即使 UPS 關機也**依然帶電**，不會因為關掉 UPS 就變安全
> - 工具短路電池端子會產生大量火花與高溫，可能造成灼傷與火災
> - ★★★★★ 一律使用**絕緣工具**、脫掉金屬飾品與手錶、戴護目鏡與絕緣手套
> - ★★★★★ 拆線前先拍照存證，接線時嚴格核對極性 —— 接反會立刻造成事故
> - 電池更換一律走變更流程並排在維護時段，詳細 SOP 見
>   [[040-02-07-guide-機房-UPS電池維護與更換]]

【4】★★★★★ 切換瞬間負載整批掉電 —— 這代表 UPS 在最關鍵的時刻沒有發揮作用。
按可能性排序：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 一轉電池，伺服器全部關機 | UPS 輸出為階梯波，主動 PFC 電源保護動作 | ★★★★★ 更換為純正弦波輸出的在線式 UPS；規格書必須明訂「純正弦波」 |
| ★★★★★ 電池完全沒有容量 | 電池已失效，切換瞬間電壓崩潰 | 立即安排更換；★★★★ 在換好之前把 UPS 當成沒有 |
| ★★★★ 負載率過高，切換瞬間扛不住 | 負載已逼近或超過 UPS 額定 | 立即降載；跳情境四 |
| ★★★★ 切換時間過長，設備撐不過去 | 離線式／線上互動式的轉換時間 | ★★★★★ 改用在線式雙轉換（無轉換時間） |
| ★★★★ 只有部分設備掉電 | 那幾台接在 UPS 涵蓋範圍外，或雙電源只接一路 | 查配電路徑；補接；跳情境五【3】 |

★★★★★ 無論哪一種，**驗證方式只有一個：做一次拔電演練**。
面板讀值、自我測試、廠商保證都無法取代實際拔掉市電看會發生什麼事。
演練程序見 [[040-02-06-svc-機房-UPS安裝與監控設定]]。

**原理**：UPS 的價值不在「不斷電」，而在「爭取到足夠的有序關機時間」。
電池是消耗品，容量隨時間與溫度單向衰退；而快速自我測試只驗證電池沒有完全失效，
不驗證容量 —— 這就是「測試都通過、停電還是撐不住」的原因。
　→ 原理詳見 [[040-02-07-guide-機房-UPS電池維護與更換]]、[[040-02-05-guide-機房-UPS選型與容量計算]]

**預防**：
- ★★★★★ 每年做一次**放電（容量）測試**並留下比較表，不能只靠快速自我測試
- ★★★★★ 換完電池**必做驗收放電測試**，否則買到瑕疵品或裝錯你不會知道
- ★★★★ 電池區溫度要監控並納入告警，溫度是壽命的頭號殺手
- ★★★★ 每月記錄「相同負載率下的剩餘時間」，趨勢比單次讀值有價值

### ★★★★ 情境四：UPS 負載率超標，或市電正常卻頻繁切到電池

**現象**：兩種容易混在一起、但原因完全不同的狀況：

```text
（A）UPS 面板顯示過載告警，或負載率長期在 70～80% 以上
     ★★★★ 服務還正常，但已經沒有餘裕，而且電池後備時間會大幅縮短

（B）市電看起來正常（沒有停電），UPS 卻一天切到電池好幾次
     ★★★★ 每一次切換都在消耗電池壽命，而且總有一次會切不回來
```

**判斷分流**：

```bash
upsc <ups名稱>@localhost | grep -E 'ups.load|ups.status|input.voltage|input.frequency'
```

```text
ups.load 持續 > 70%                      → 容量問題          走【1】【2】
ups.status 反覆出現 OB（On Battery）      → 頻繁切換          走【3】
ups.status 含 BYPASS                     → ★★★★★ 沒有保護    走【4】
ups.status 含 OVER                       → 已經過載          走【1】立即降載
負載率沒變但告警是新出現的                → 可能是電池衰退造成的餘裕縮水，回情境三
```

**處置步驟**：

【1】★★★★★ 過載告警是**現在進行式**，先降載，再檢討。

```text
降載順序（由影響最小的開始關）：
① 測試機、開發機、暫時性的工作負載
② 非關鍵的內部服務
③ 可以延後的批次作業
★★★★★ 絕不要為了降載去關核心交換器、防火牆、環境監控主機 ——
        那幾台一關，你就失去了「知道機房發生什麼事」的能力
```

★★★★ 降載完成後量一次負載率，確認回到安全範圍再收工。

【2】★★★★ 負載率長期偏高：這是**容量規劃**問題，要用數字談，不是憑感覺。

```text
把三個數字放在一起看：
  a. UPS 額定的 kVA 與 kW（★★★★★ 兩個數字都要，只看 kVA 會踩坑）
  b. 目前實測負載（從 UPS 面板或 PDU 讀值，不要用銘牌加總）
  c. 未來 12 個月已知會增加的設備

判定：
  目前負載率 > 70%                     → ★★★★★ 停止新增設備，開始規劃擴充或汰換
  加上未來 12 個月的量會超過 70%        → 現在就要開始編預算
  負載率 < 30% 且電費異常高              → ★★★★ 過度保守選型，UPS 低負載效率差
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 買了標稱 kVA 夠的 UPS，實際帶不動 | 只看 kVA 沒看 kW（輸出功率因數陷阱） | ★★★★★ 規格書同時載明 kVA 與 kW，負載率兩邊都算取高者 |
| ★★★★ 加了一台伺服器之後開始過載告警 | 上架前沒重算 UPS 負載率 | 把「UPS 負載率」加進上架前檢查表 |
| ★★★★ 某台設備開機瞬間 UPS 轉旁路 | 負載率已高，扛不住開機突波 | ★★★★★ 降到 60% 以下；★★★ 錯開多台設備的開機時間 |
| ★★★★ 負載沒增加，但剩餘時間逐月變短 | 電池容量衰退，不是負載問題 | 回情境三；安排容量測試 |

【3】★★★★ 市電正常卻頻繁切到電池 —— 關鍵是**找出切換的時間點與什麼事重合**。

```bash
# 把 UPS 的事件時間抓出來（依實作而異：NUT 通知腳本寫的日誌、管理卡事件、監控系統）
sudo journalctl -t upsmon --since '-7 days' | grep -iE 'on battery|on line'
```

```text
把切換時間與這幾件事對照：
 ① 空調壓縮機起動時間           → ★★★★★ 空調與 IT 共用迴路，起動電流造成電壓瞬降
 ② 大型設備（電梯、幫浦）起停    → 同棟大樓的其他負載造成的電壓擾動
 ③ 雷雨、颱風時段               → 市電本身品質問題，向台電反映並保留紀錄
 ④ 沒有規律，隨機發生            → 走【3-b】

【3-a】對得上時間 → 那個負載就是元凶
   ★★★★★ 空調必須用獨立專用迴路，絕不與 IT 混接。
   已經混接的：排維護時段請電氣技術人員分開。

【3-b】對不上任何事件 → 兩種可能
   ① UPS 的輸入電壓／頻率容忍門檻設得太嚴 → 查手冊，在合理範圍內放寬
   ② 市電本身真的在抖 → 請電力公司或電氣技師量測記錄，用數據談
   ★★★★ 兩者都要先記錄「切換當下的 input.voltage 與 input.frequency」才有辦法判斷
```

【4】★★★★★ UPS 顯示 Bypass（旁路）—— 這是**最容易被忽略的高風險狀態**。

```text
★★★★★ Bypass = 市電直接供給負載，UPS 完全沒有在保護。
        這時候停電就是直接掉電，而且面板上「一切正常、沒有紅燈」。

處理：
① 先確認是哪一種旁路
   靜態旁路（自動）→ UPS 判斷自己有問題或過載時自動轉入 → 查為什麼，走【1】或找廠商
   維護旁路（手動）→ 有人切過去做維護 → 確認維護是否結束，結束就切回來
② 切回線上模式一律由原廠或受訓人員依手冊順序執行
③ ★★★★★ 把「旁路狀態」設為嚴重等級告警（簡訊等級），並納入每日巡檢必看項目
```

> [!danger] ★★★★★ 維護旁路的切換順序不可自己發明
> 切換順序錯誤會造成整機房瞬間斷電。旁路切換一律由原廠或受過訓練的人員
> 依該機型手冊執行，並在切換前確認：有多少設備其實接在旁路涵蓋範圍之外。
> 切換後用逐台的開機時間驗證有沒有人被斷過電。

**原理**：UPS 的負載率同時決定三件事 —— 能不能扛住突波、電池能撐多久、
以及設備本身的效率。負載率過高時後備時間會非線性地大幅縮短；
而旁路模式雖然維持了供電，卻把 UPS 的保護整個拿掉。
　→ 原理詳見 [[040-02-05-guide-機房-UPS選型與容量計算]]、[[040-02-04-guide-機房-電力系統與配電]]

**預防**：
- ★★★★★ 「UPS 負載率」列入上架前檢查表，超過 70% 就停止新增
- ★★★★★ 旁路狀態、通訊中斷兩項各設一個獨立告警 ——
  ★★★★ 通訊斷了就看不到其他所有告警，所以它必須有自己的心跳監控
- ★★★★ 空調用獨立專用迴路，這件事沒有例外
- ★★★★ 每月記錄負載率並看趨勢，容量問題都是慢慢長出來的

### ★★★★★ 情境五：PDU 迴路跳脫、單迴路過載、雙路變單路

**現象**：三種相關但嚴重度不同的狀況：

```text
（A）★★★★★ 斷路器跳脫，該迴路上的設備全部斷電
（B）★★★★  PDU 顯示某一路電流接近或超過額定，但還沒跳
（C）★★★★  PDU 顯示 A 路與 B 路電流嚴重不平衡（例如一路 8 A、一路 2 A）
```

> [!danger] ★★★★★ 斷路器跳脫時，不要一直重推
> 斷路器跳脫是**保護動作**，代表電流真的超過了它該保護的值。
> 反覆重推的後果是：導線持續過熱、接點劣化、最終演變成配電盤內部起火。
> ★★★★★ 正確順序是：**先降載 → 找出原因 → 才復歸**，而且復歸由合格電氣技術人員執行。

**判斷分流**：

```text
跳的是哪一級？
  設備端 PDU 上的小型斷路器跳          → 該 PDU 這一段過載或有設備故障   走【1】
  配電盤的分路斷路器跳                  → 整條迴路過載或短路             走【1】【2】
  漏電斷路器（ELCB/RCD）跳              → ★★★★★ 有漏電，走【4】
  什麼都沒跳，但電流很高                → 走【2】預防性處理
  A/B 兩路電流差很多                    → 走【3】
```

**處置步驟**：

【1】★★★★★ 跳脫後的標準處理順序 —— **一步都不要跳過**：

```text
① 確認災情範圍
   哪些設備斷電了？服務有沒有中斷？雙電源的機器是不是還活著？

   for ip in <該迴路上的設備 IP...>; do
     printf '%-14s ' "$ip"; ping -c1 -W1 "$ip" >/dev/null 2>&1 && echo OK || echo FAIL
   done

   全部 OK  → ★★★★ 雙電源發揮作用了，服務沒中斷，但現在是單點狀態，很緊急
   部分 FAIL → 那幾台是單電源或雙電源只接了一路，先記下來，之後要補
   全部 FAIL → 走服務復原流程，同時往下查原因

② 判斷是「過載」還是「故障」
   ★★★★★ 這一步決定接下來能不能復歸。
   看跳脫前的 PDU 電流紀錄（有監控型 PDU 才有；沒有的話問「最近有沒有加設備」）：
     跳脫前電流本來就接近額定       → 過載，走 ③
     跳脫前電流正常，突然跳          → 有設備故障造成過電流或短路，走 ④

③ 過載的處理：先降載到安全值，再復歸
   ★★★★★ 連續負載不應超過斷路器額定的 80%。
   把非必要設備移到其他有餘裕的迴路，或先關掉。
   降載完成 → 請電氣技術人員復歸 → 復歸後持續觀察電流讀值。

④ 疑似設備故障：不要整條復歸，逐一排除
   把該迴路上的設備全部拔離 → 復歸 → 一次插回一台，每插一台看電流
   插到某一台就跳 → 那台就是元凶，送修，不要再插回去

⑤ ★★★★★ 事後一定要做的兩件事
   a. 重新計算這條迴路的容量與現有負載，把數字寫進文件
   b. 檢討為什麼會走到跳脫 —— 是新增設備沒重算，還是本來就規劃不足
```

【2】★★★★ 還沒跳但電流很高 —— 這是你**唯一能從容處理**的時機，不要浪費它。

```text
判定門檻：
  連續負載 / 斷路器額定 > 80%      → ★★★★★ 已經超過設計上限，立刻規劃分流
  介於 60~80%                      → ★★★★ 可以運作，但不要再往這條加東西
  < 60%                            → 有餘裕
★★★★ 注意「連續負載」的意思：機房設備幾乎都是 24 小時運轉，全部都算連續負載。
```

分流的做法（由簡單到複雜）：

```text
① 把設備的 B 路電源改插到另一條有餘裕的迴路（★★★★ 前提是真的雙電源）
② 把整台設備移到別的機櫃／別的 PDU
③ 增設新迴路（要動配電盤，需排維護時段與電氣技術人員）
```

【3】★★★★ A／B 兩路電流嚴重不平衡 —— 幾乎一定是**有設備只接了一路**。

```bash
# 逐台確認兩顆 PSU 是不是都有電
sudo ipmitool sdr type 'Power Supply'
sudo ipmitool sel list | grep -i 'power supply'
```

```text
判讀：
  某台只有一顆 PSU 顯示有電        → ★★★★★ 這台等於單電源，隨時會因單路故障而掉電
  該台兩顆都有電，但整櫃仍不平衡    → 有其他設備本來就是單電源機種（交換器常見）

處理：
  a. 只接一路的 → 補接另一路（★★★★ 確認要插的那一路有餘裕）
  b. 單電源機種 → 接 ATS PDU（自動切換），或換成雙電源機種
  c. ★★★★★ 核心交換器、防火牆這種「一掛全機房失聯」的設備，
     必須雙電源或 ATS PDU，沒有例外
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 雙電源伺服器，某一路斷電還是整台掛 | ★★★★★ 假雙路：兩支 PDU 其實接在同一條迴路 | 查配電單線圖確認 A／B 分屬不同斷路器；★★★★★ 做單路斷電測試驗證 |
| ★★★★ 上架時只有一顆 PSU 顯示有電 | B 路線沒插到底／插座沒電／該迴路跳脫 | 檢查插到底、用 PDU 面板確認該插座有電、檢查斷路器 |
| ★★★★★ 電源線莫名鬆脫造成斷電 | C13／C14 沒有卡榫，震動或拉扯就滑出 | 改用帶鎖定機構的電源線或 PDU 的線材固定夾 |
| ★★★★★ 單電源核心交換器那一路跳脫，整機房失聯 | 核心設備沒有雙電源也沒接 ATS | 改雙電源機種或接 ATS PDU；兩台堆疊時分接 A／B |

【4】★★★★★ 漏電斷路器跳 —— 這與過載是**完全不同的事**，不要當成過載處理。

> [!danger] ★★★★★ 漏電跳脫代表有電流流到了不該去的地方
> 可能是設備絕緣劣化、進水受潮、或接地系統有問題。
> - ★★★★★ **不要直接復歸**。復歸等於把可能造成觸電或起火的路徑重新接通。
> - 立即通知合格電氣技術人員到場，用適當儀器逐段量測找出漏電點。
> - 如果同時看到水漬或潮濕，直接走 [[040-02-14-guide-機房-機房異常應變]] 漏水應變。
> - ★★★★★ 反過來說：**漏電時漏電斷路器卻沒跳**同樣危險 ——
>   通常是接地不良或接地開路，讓漏電電流找不到回路。這要當成緊急項目處理。

【5】★★★★★ 看到這些現象時，**停手並立刻找電氣技術人員**：

```text
 端子發燙、變色、有焦味               → ★★★★★ 火災前兆，不要自己打開檢查
 配電盤內有異音（滋滋聲）              → 同上
 設備輸入電壓明顯低於標稱              → 電壓降過大，線徑或路徑要檢討
 插座測出「接地開路」                  → 立即停用該插座並標示
 摸到機殼會被電到（不是靜電那種一下）   → ★★★★★ 立刻停用該設備並斷電
```

**原理**：斷路器保護的是**導線**不是設備 —— 它在電流超過導線安全載流量之前切斷電路。
連續負載的 80% 法則正是為了留出這個安全邊際。
而雙路供電的價值完全建立在「兩路真的獨立」這個前提上，
只要上游有任何一點共用，它就只是看起來像雙路。
　→ 原理詳見 [[040-02-04-guide-機房-電力系統與配電]]、[[010-01-15-guide-計概-電力基礎與用電安全]]

**預防**：
- ★★★★★ 每次上架都要重算該迴路負載，並把數字寫回配置文件
- ★★★★★ 雙路供電每年做一次**單路斷電測試**驗證，沒測過的雙路不算雙路
- ★★★★ 換成監控型 PDU 並把每路電流納入監控與告警（門檻設在 80% 之前）
- ★★★★ 配電單線圖與迴路標示要維護，這是驗收與稽核必查項目

### ★★★★★ 情境六：伺服器無法開機、POST 停住、指示燈與嗶聲判讀

**現象**：按了電源鍵沒反應、風扇轉一下就停、開機停在某個畫面不動、
或面板亮橘燈／紅燈、機殼內傳出規律的嗶聲。

★★★★★ 這一類問題最重要的觀念：**機器自己已經告訴你原因了**，
在 SEL（系統事件日誌）、面板燈號、嗶聲碼三個地方 —— 只是要知道去哪裡讀。

**判斷分流**：先分清楚它「有沒有通電」與「走到哪一步」。

```text
按電源鍵完全沒反應、風扇不轉、面板無燈           → 沒有電        走【1】
風扇轉一下就停，反覆嘗試                          → 供電或硬體保護 走【1】【2】
風扇全速狂轉但畫面沒輸出                          → POST 前失敗   走【2】
畫面有廠商 logo 但停住不動                        → POST 中失敗   走【3】
POST 過了，停在「找不到開機裝置」                  → 開機設定或磁碟 走【4】
面板橘燈／紅燈亮，但系統其實有起來                → 硬體異常但非致命 走【2】讀 SEL
```

**處置步驟**：

【1】★★★★ 完全沒反應：先確認電真的有到機器。

```text
① 該插座有沒有電？        用 PDU 面板／管理介面看該孔的電流，或用其他設備測試該插座
② 電源線有沒有插到底？    ★★★★ C13/C14 沒有卡榫，看起來插著其實鬆了
③ 該迴路有沒有跳脫？      跳情境五
④ PSU 指示燈是什麼顏色？  綠燈＝正常；橘／紅燈＝該顆有問題；不亮＝沒電
⑤ BMC 有沒有活著？        ★★★★★ 這是關鍵分界：
     BMC 通得到（能 ping、能開網頁） → 待機電源正常，是主機板／PSU 給主電源的問題
     BMC 也不通                      → 整台沒有待機電源，回到 ①～③
```

★★★★ BMC 通得到時，你甚至可以遠端下電源指令，不必到現場：

```bash
ipmitool -I lanplus -H <BMC_IP> -U <帳號> -E power status
ipmitool -I lanplus -H <BMC_IP> -U <帳號> power on
```

【2】★★★★★ 讀 SEL —— 這是整個情境六投報率最高的一步。

```bash
sudo ipmitool sel list | tail -30
# 或從 BMC 網頁介面的 System Event Log 讀（機器完全開不了機時只能走這條）
```

```text
SEL 常見事件與對應處置（★★★★ 事件名稱依廠商略有不同）：
  Power Supply ... Failure / AC lost   → 該顆 PSU 或該路供電有問題，回【1】
  Memory ... Correctable / Uncorrectable ECC → 記憶體條有問題，走【3】
  Processor ... 相關事件               → CPU 或其座相關，通常要原廠處理
  Drive Slot ... Fault                 → 磁碟故障，跳情境八
  Temperature ... Upper Critical       → 過熱保護，跳情境一 / 二
  Fan ... Failure                      → 風扇故障，跳情境二【3】
```

```bash
# 處理完之後才清 SEL（★★★★ 先確認已經記進工單，清了就沒了）
sudo ipmitool sel clear
```

★★★★ 面板燈號與嗶聲碼**每個廠牌、每個世代都不一樣**，
不要憑記憶或網路上隨便一篇文章判斷。正確做法是：

```text
① 記下燈號的顏色、位置、閃爍方式（幾長幾短）
② 記下嗶聲的節奏（幾聲一組、長短組合）
③ 查該機型的**原廠手冊**對照表 —— ★★★★★ 這份手冊應該在上架時就存進知識庫
④ 同時讀 SEL 交叉驗證
```

【3】★★★★ POST 停住：用**減法**找出是哪個元件。

```text
順序（每動一次就開機測試一次，一次只改一個變因）：
① 拔掉所有非必要的 PCIe 卡、USB 裝置、外接儲存
   → 能開機了 → 逐一插回，找出是哪一張卡
② 只留一條記憶體（插在主機板手冊指定的第一個必插槽位）
   → 能開機了 → 逐條測試，找出壞的那一條
   → 還是不行 → 換另一條記憶體試同一個槽位，區分是「條壞」還是「槽壞」
③ 清 CMOS／載入 BIOS 預設值
   ★★★★ 這會清掉所有 BIOS 設定（含開機模式、虛擬化、RAID 模式），
   清之前先確認你知道原本的設定是什麼
④ 以上都不行 → 主機板或 CPU 層級，走保固報修
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ 記憶體容量比訂單少 | 有一條沒插好、插槽順序錯、或該條故障 | `sudo dmidecode -t memory` 逐槽對照；重插；仍缺就報修 |
| ★★★★ 開機一直有嗶聲／面板橘燈 | 硬體異常（記憶體、電源、風扇、溫度） | ★★★★★ 從 BMC 讀 SEL，依事件內容處理，不要猜 |
| ★★★★ 加了一張卡之後就開不了機 | 卡不相容、供電不足、插槽不支援 | 拔掉該卡確認；查該機型支援清單 |
| ★★★★ 開機找不到磁碟 | RAID 尚未建立虛擬磁碟；或 RAID 卡在 HBA 模式而 OS 無驅動 | 進 RAID 設定確認有 VD；HBA 模式確認 OS 驅動支援 |
| ★★★★★ 裝完 OS 開不了機，直接跳 BIOS | Boot Mode 與安裝時不一致／開機順序錯／UEFI 開機項目沒建立 | 確認 Boot Mode；把本機磁碟拉到第一順位；★★★★★ 模式不一致要重裝 |
| ★★★★★ 系統突然變很慢，找不到原因 | RAID 卡電池／超級電容故障，快取退回 Write Through | 用 RAID 卡工具檢查電池狀態，更換電池模組 |

【4】★★★ POST 過了但找不到開機裝置：這已經離開硬體，進入開機鏈範圍。

```text
 RAID 有沒有虛擬磁碟？          沒有 → 跳情境八
 開機順序對不對？               本機磁碟有沒有在第一順位
 Boot Mode 是 UEFI 還是 Legacy？ ★★★★★ 跟安裝時不一致就開不起來
 磁碟本身有沒有掛？             跳情境八
 到這裡都正常但還是進不去       → 這是 OS 層問題，走 [[020-01-98-trouble-Linux-常見故障排除]]
```

> [!danger] ★★★★ 熱插拔元件的更換前提
> PSU、風扇、磁碟這些可熱插拔的元件，前提是**其他同類元件都是好的**。
> ★★★★★ 拔之前先確認：另一顆 PSU 真的有電（PDU 讀值確認）、
> 其他風扇轉速正常、RAID 沒有已經降級。
> 在冗餘已經失效的狀態下拔掉唯一還好的那一個，就是自己造成停機。

**原理**：伺服器開機分成「待機電源 → 主電源 → POST → 開機裝置 → OS」數個階段，
BMC 在待機電源階段就已經活著，所以它能記錄並回報後面每一階段的失敗。
這就是為什麼「BMC 通不通」是最重要的第一個分界點。
　→ 原理詳見 [[040-02-09-guide-機房-伺服器上架與初始設定]]、[[010-01-02-guide-計概-主機裡面有什麼]]

**預防**：
- ★★★★★ 上架時就把該機型的**原廠手冊、燈號對照表、預設密碼**存進知識庫
- ★★★★★ 上架時就建立「機櫃 U 位 ↔ 序號 ↔ BMC IP ↔ 磁碟槽位」對照表，
  出事時你不會有時間現場摸索（[[040-02-09-guide-機房-伺服器上架與初始設定]]）
- ★★★★ BMC 的 SEL 要納入監控，不要等到出事才第一次去讀
- ★★★★ BIOS 設定在上架驗收時就要記錄下來（開機模式、虛擬化、電源回復行為）

### ★★★★ 情境七：iDRAC／iLO 連不上，或忘記管理密碼

**現象**：需要遠端處理機器時，才發現 BMC ping 不到、網頁打不開、
或是有 IP 卻不知道密碼。★★★★★ 這通常在**最需要它的時候**才被發現。

**判斷分流**：

```text
ping 不到 BMC IP                      → 網路層或設定錯誤   走【1】
ping 得到但網頁打不開                  → BMC 服務層問題     走【2】
網頁開得了但密碼不對                    → 認證問題           走【3】
連得上但功能受限（沒有虛擬 KVM）        → 授權等級問題       走【4】
完全不知道 IP 是多少                    → 走【5】
```

**處置步驟**：

【1】★★★★★ ping 不到：三個最常見的原因，依序排除。

```text
① NIC Selection 選錯（★★★★★ 這是第一名）
   BMC 通常有兩種網路模式：
     Dedicated  → 走機身上獨立的管理埠（機身有小扳手或 MGMT 圖示）
     Shared/LOM → 與作業系統共用某一個網路埠
   ★★★★★ 設定選 Dedicated 但線接在一般網路埠 → 永遠 ping 不到。
   到現場看線接在哪個孔，跟 BIOS/BMC 裡的設定對照。

② 交換器埠的 VLAN 設錯
   BMC 應該接在**獨立的管理 VLAN**。埠設成別的 VLAN 就通不了。
   查交換器該埠設定，見 [[040-01-08-guide-Juniper-埠設定與安全]]。

③ BMC 還在開機
   ★★★ 剛通電或剛 reset 的 BMC 需要時間起來，等 60 秒再試。

排除以上還是不通：
④ 從同網段的另一台機器測，排除路由與防火牆問題
⑤ 用 OS 內的工具直接看 BMC 網路設定（前提是 OS 還活著）：
     sudo ipmitool lan print 1
   ★★★★ 回 `Invalid channel` 時，換 channel 試（1／2／3／8）
```

```bash
# OS 內看不到 /dev/ipmi0 時，核心模組沒載入
sudo modprobe ipmi_si ipmi_devintf
# 要持久化就寫進 /etc/modules-load.d/
```

【2】★★★★ ping 得到但網頁打不開：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ 瀏覽器直接拒絕連線 | BMC 用自簽憑證，或 TLS 版本太舊被現代瀏覽器擋掉 | 換一個瀏覽器或調整例外；★★★★ 長期做法是換掉 BMC 的自簽憑證（見 [[090-01-08-guide-PKI-用自建CA簽發伺服器憑證]]） |
| ★★★★ 網頁載入到一半就停 | BMC Web 服務當掉（BMC 是嵌入式系統，會當） | `ipmitool mc reset cold` 重啟 BMC（★★★ 主機不會關機，但會斷所有 BMC 連線） |
| ★★★★ 虛擬 KVM 開不起來 | 瀏覽器外掛／Java／HTML5 版本問題，或授權不足 | 確認該機型的 KVM 實作方式；確認授權等級，走【4】 |

★★★★ `ipmitool` 通但網頁不通時，很多事情其實可以直接用指令做完 ——
開關機、讀 SEL、讀感測器、開 SOL（序列主控台），不一定非要網頁。

【3】★★★★★ 密碼問題 —— 分成三種，難度差很多：

```text
（a）密碼有記錄，只是登入失敗
     確認帳號沒有被鎖定（多次失敗會鎖）；等鎖定時間過或請其他管理員解鎖。

（b）出廠隨機密碼，標籤已被撕掉
     ★★★★ 先找：機身可能有第二張備份標籤（機殼側面、抽拉式資產標籤片）。
     找不到 → 走（c）。

（c）★★★★★ 完全沒有可用憑證
     唯一的正規路徑是**在 BIOS/UEFI 設定介面中重設 BMC 帳號密碼** ——
     這需要實體接觸與**停機重開**。
     還是不行就聯絡原廠（可能需要提供購買證明與序號）。
```

> [!danger] ★★★★★ 不要為了「省一次停機」去嘗試來路不明的密碼繞過方法
> 網路上流傳的 BMC 密碼繞過手法，輕則讓 BMC 變磚，重則留下無法稽核的後門。
> ★★★★★ 而且能繞過 BMC 密碼 = 能完全控制這台伺服器（掛載虛擬光碟、改 BIOS、開關機），
> 這條路你走得通，攻擊者也走得通。正規做法是排一次停機重設。

★★★★ 另一件同樣重要的事：**BMC 絕對不可以接對外網路**。
它是一個權限極高、更新頻率極低的嵌入式系統。
一律放獨立管理網段，並限制來源 IP。詳見 [[040-02-09-guide-機房-伺服器上架與初始設定]]
與 [[090-02-06-guide-防護-遠端存取安全]]。

【4】★★★ 連得上但沒有虛擬 KVM／虛擬媒體 —— 這通常不是故障，是**授權等級**。

```text
BMC 的進階功能（虛擬 KVM、虛擬媒體、進階監控）多半需要額外授權。
① 查該機的授權狀態（BMC 網頁的 Licenses 頁面，或廠商工具）
② 沒有授權 → 採購時就該一併買；補買通常也可以，走採購流程
③ ★★★★★ 新機採購規格書就要寫明「含虛擬 KVM 與虛擬媒體授權」——
   這是遠端救援的前提，事後補買常常更貴
```

【5】★★★ 不知道 BMC IP 是多少：

```bash
# OS 還活著時，直接問
sudo ipmitool lan print 1 | grep -E 'IP Address|MAC Address|802.1q'
```

```text
OS 已經進不去時：
① 查上架紀錄／資產清冊（★★★★★ 這就是為什麼上架時要建對照表）
② 查 DHCP 伺服器的租約紀錄（BMC 若設為 DHCP）
③ 查交換器的 MAC 位址表，用 BMC 的 MAC 反查它接在哪一埠、學到什麼 IP
④ 到現場從 BIOS/UEFI 設定介面看（要重開機）
⑤ 部分機型前面板的小螢幕可以直接顯示 BMC IP
```

**原理**：BMC 是一個與主機作業系統完全獨立的嵌入式管理系統，
靠待機電源運作 —— 這是它的價值（主機掛了它還在），也是它的風險
（它是一台你不常維護、卻擁有完全控制權的獨立電腦）。
　→ 原理詳見 [[040-02-09-guide-機房-伺服器上架與初始設定]]

**預防**：
- ★★★★★ 上架時就完成：設定管理 IP、**改掉出廠密碼**、建立正式帳號、記錄進知識庫
- ★★★★★ BMC 一律放獨立管理網段，**絕不接對外網路**
- ★★★★ BMC 的 NTP 一定要設對 —— ★★★★★ 時間錯誤的日誌在資安事件調查時形同無效
- ★★★★ 每季確認一次「BMC 連得上、密碼是對的」，不要等到出事才第一次用

### ★★★★★ 情境八：RAID 降級、換上新碟不重建、多碟同時故障

**現象**：管理工具顯示 Degraded、某個磁碟槽位亮橘燈、
或是換了新碟上去卻一直不開始重建。

★★★★★ RAID 降級的本質是：**系統還活著，但已經沒有下一次機會了**。
再掉一顆（RAID 5）或掉錯一顆（RAID 1）就是整組資料消失。
所以它的優先度是「當天處理」，不是「排進下週維護」。

> [!danger] ★★★★★ 拔錯磁碟 = 整組陣列全毀
> 在降級狀態下拔掉**還好的那一顆**，資料就沒了，而且沒有回頭路。
> ★★★★★ 動手之前必須用**三方交叉確認**鎖定到序號那一層：
> ① 管理工具回報的故障碟序號　② 磁碟托架上的實體標籤　③ 槽位定位燈
> 三者對不上就**不要拔**，先查清楚。這一條沒有任何例外。

**判斷分流**：先確認是硬體 RAID 卡還是軟體 RAID，工具完全不同。

```bash
# 硬體 RAID（依廠牌選一個；工具名稱與路徑依安裝方式而異）
sudo storcli64 /c0 show                 # LSI / Broadcom
sudo perccli64 /c0 show                 # Dell PERC
sudo ssacli ctrl all show config        # HPE Smart Array

# 軟體 RAID（Linux mdadm）
cat /proc/mdstat
sudo mdadm --detail /dev/md0

# 磁碟本身的健康度（★★★★ 硬體 RAID 後面的碟要加 -d 參數才看得到）
sudo smartctl -a /dev/sda
sudo smartctl -d megaraid,0 -a /dev/sda      # LSI/PERC 後面的第 0 顆
```

```text
一顆 Failed，陣列 Degraded                 → 正常換碟流程     走【1】
換上新碟但不重建                            → 新碟狀態不對     走【2】
兩顆以上同時 Failed（RAID 5）               → ★★★★★ 走【3】停手
重建做到一半失敗                            → 另一顆也有問題   走【3】
沒有碟 Failed 但效能突然很差                 → 快取退回 WT      走【4】
系統正常但 SMART 一直報警                    → 預警，走【5】
```

**處置步驟**：

【1】★★★★★ 標準換碟流程 —— 五步，一步都不能跳。

```text
① 確認要換的是哪一顆（★★★★★ 三方交叉確認）
   a. 管理工具讀出故障碟的**序號**：
        sudo storcli64 /c0/eall/sall show all | grep -iE 'SN|State'
        sudo smartctl -i /dev/sdX | grep -i serial
   b. 到機櫃前對照磁碟托架上的標籤與槽位編號
   c. 點亮該槽位的定位燈：
        sudo storcli64 /c0/e<enc>/s<slot> start locate
        sudo ledctl locate=/dev/sdX          # 軟體 RAID 環境
   ★★★★★ 三者一致才動手。對不上就停下來查。

② 確認手上的新碟符合規格
   容量 ≥ 原碟、介面相同、轉速／型號盡量一致
   ★★★★ 容量「差一點點」也不行 —— 有些卡要求嚴格相等或更大

③ 拔舊碟、插新碟
   ★★★★ 熱插拔前確認該機型支援；插入後等 30 秒讓卡辨識

④ 確認重建開始
   sudo storcli64 /c0/vall show           # 看 State 是否為 Rebuilding / Optimal
   cat /proc/mdstat                        # 軟體 RAID 會顯示 recovery 進度與百分比
   沒有自動開始 → 走【2】

⑤ ★★★★★ 重建期間不要做任何多餘的事
   不要重開機、不要拔其他碟、不要跑大量 I/O 的批次作業。
   重建期間是整組陣列**最脆弱**的時候。
   重建完成後再確認一次狀態是 Optimal，並把這次更換記進資產與維護紀錄。
```

【2】★★★★ 換上新碟卻不重建 —— 幾乎都是**新碟的狀態不對**，不是卡壞了。

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 新碟顯示 Foreign / Foreign Configuration | 這顆碟以前在別的陣列用過，帶著舊的設定 | 在 RAID 設定介面清除 foreign config（★★★★★ 確認這顆碟上沒有你要的資料再清） |
| ★★★★ 新碟顯示 Unconfigured Bad / Failed | 卡把它標記成壞碟（可能是插入時的暫時錯誤） | 用工具把狀態改回 Unconfigured Good，再看是否開始重建 |
| ★★★★ 新碟容量比原碟小 | 不同批次的「同容量」硬碟實際區塊數可能略有差異 | 換一顆容量相同或更大的 |
| ★★★★ 卡沒有設定自動重建 | Auto Rebuild 選項是關的 | 手動指定該碟為 hot spare 或直接下重建指令；並把 Auto Rebuild 打開 |
| ★★★★ 軟體 RAID：新碟沒有被加進陣列 | mdadm 不會自動加，要手動 | `sudo mdadm --manage /dev/md0 --add /dev/sdX` |

【3】★★★★★ 多碟同時故障、或重建中又掉一顆 —— **立刻停手**。

> [!danger] ★★★★★ 這時候你的每一個動作都可能是最後一個機會
> - ★★★★★ **不要重開機**。重開之後陣列可能連降級狀態都回不去。
> - ★★★★★ **不要強制上線（force online）**，除非你已經接受可能的資料損毀，
>   而且沒有其他選項。
> - ★★★★★ **不要格式化、不要初始化、不要重建陣列**。
> - 第一件該做的事是：**確認備份還在，而且能還原**。
>   備份可用 → 就用備份還原，不要冒險搶救陣列。
>   備份不可用 → 停手，找資料救援專業廠商評估，不要自己試。
> - 現場拍照、把管理工具的完整輸出存下來，這些是後續判斷與究責的依據。

★★★★ 為什麼會多碟同時故障？三個常見原因，都指向同一個教訓：

```text
① 同批次採購、同時上線、承受相同工作負載 → 壽命曲線幾乎一樣，會接近同時劣化
② 重建期間的高強度讀取把「原本就快壞的第二顆」壓垮
   ★★★★★ 這是 RAID 5 大容量磁碟最危險的情境
③ 背板、線材、RAID 卡本身故障 → 看起來是多顆碟同時掛，其實是共同上游壞了
   ★★★★ 判斷方式：故障的碟是不是集中在同一組槽位／同一條線？
```

【4】★★★★ 沒有碟故障但效能突然變很差：查 RAID 卡的**快取狀態**。

```bash
sudo storcli64 /c0/bbu show         # 或 perccli64 / ssacli 對應指令
sudo storcli64 /c0/vall show all | grep -i cache
```

```text
判讀：
  快取策略顯示 Write Through（原本應該是 Write Back）
    → ★★★★★ RAID 卡電池／超級電容故障或正在學習週期，卡自動退回保守策略
    → 學習週期（learn cycle）是正常的，會自己恢復；電池故障就要更換模組
  ★★★★ 不要為了效能手動強制開回 Write Back —— 沒有電池保護時斷電會掉資料
```

【5】★★★ SMART 預警：陣列還是 Optimal，但某顆碟的 SMART 數值在惡化。

```bash
sudo smartctl -a /dev/sdX | grep -iE 'Reallocated|Pending|Uncorrectable|Media_Wearout|Percentage Used'
```

```text
★★★★ 判定原則（具體門檻依廠牌與型號而異，以廠商定義為準）：
  重新配置磁區數從 0 開始增加        → 開始劣化，列入觀察並排更換
  待處理磁區數 > 0                   → ★★★★ 比重新配置數更值得緊張
  SSD 的耗損指標接近上限              → 依剩餘壽命排更換
  smartctl 整體判定 FAILED            → ★★★★★ 立刻排更換，不要等它真的掛

★★★★★ 最重要的一句：**在陣列還是 Optimal 的時候換碟，是計畫性維護；
        等到 Degraded 才換，是搶救。**
```

**原理**：RAID 提供的是**可用性**（掉一顆還能跑），不是備份。
降級狀態下冗餘已經歸零，而重建過程本身又是對其餘磁碟最嚴苛的一次讀取考驗 ——
這就是為什麼「降級要當天處理」，也是為什麼「RAID 不能取代備份」。
　→ 原理詳見 [[010-01-07-guide-計概-磁碟格式化與RAID入門]]、
[[020-01-29-guide-Linux-網路儲存與軟體RAID]]

**預防**：
- ★★★★★ RAID 狀態必須納入監控與告警，不要靠人去看面板燈
  （[[100-01-03-guide-日誌-系統監控與告警]]）
- ★★★★★ **備份要能還原**才算備份，每年至少做一次還原演練
  （[[090-03-04-guide-應用安全-備份災難復原與入侵應變]]）
- ★★★★ 上架時建立「磁碟槽位 ↔ 序號」對照表並貼在機櫃上，出事時省下最危險的十分鐘
- ★★★★ 常備至少一顆同規格熱備碟；大型陣列直接設 hot spare

### ★★★★ 情境九：韌體更新失敗，設備變磚

**現象**：更新 BIOS／BMC／RAID 卡／網卡／交換器韌體的過程中斷電、卡住、
或更新完成後開機黑畫面、設備完全沒有反應。

★★★★★ 這一類問題的殘酷之處：**發生的時候，通常已經沒有太多選項了**。
所以這個情境的重點有一半在「怎麼不要走到這裡」。

**判斷分流**：

```text
更新過程中就顯示失敗，但設備還能開機          → 還有救       走【1】
更新後開機黑畫面、風扇轉但無輸出               → 走【2】
BMC 更新失敗，BMC 連不上但主機還能開           → 走【3】
交換器更新失敗，停在 loader / rommon 提示      → 走【4】
完全沒有任何反應（連風扇都不轉）                → 走【5】
```

> [!danger] ★★★★★ 第一原則：不要反覆斷電重試
> 韌體更新失敗後，設備可能正在執行自動復原程序（部分機型有雙 BIOS 或 recovery image），
> 這個過程可能長達數分鐘且**畫面上什麼都不會顯示**。
> 這時候反覆斷電重開，會把「有機會自己救回來」變成「真的變磚」。
> ★★★★★ 先等 —— 依機型手冊建議的時間等完（通常至少 10～15 分鐘），再做下一步。

**處置步驟**：

【1】★★★★ 更新失敗但設備還活著：這是最好的狀況。

```text
① 先確認目前實際運行的是哪一版
     sudo dmidecode -s bios-version
     sudo ipmitool mc info | grep -i 'firmware revision'
   ★★★★ 有可能失敗的只是「寫入」，設備仍在跑舊版 —— 那就是虛驚一場。

② 確認失敗原因再重試，不要盲目重來
   常見原因：檔案下載不完整、版本不相容、更新順序錯、電源不穩、更新期間有其他作業

③ 重試前的準備（★★★★★ 一項都不能少）
   a. 從原廠官網重新下載，並核對檔案雜湊值
   b. 確認這個版本適用於**你這台的確切機型與現有版本**（有些版本必須逐階升級）
   c. 確認雙路供電都正常、UPS 電池狀態正常
   d. 排在維護時段，不要在上班時間做
   e. 確認你有帶外管理可用（BMC），以及萬一失敗時的原廠支援管道
```

【2】★★★★★ 更新後黑畫面：依序嘗試，每一步之間要有耐心。

```text
① 等 → 至少 10～15 分鐘（見上面的 danger），期間不要斷電
② 斷電後長按電源鍵放電，再接電開機（部分機型能藉此重新初始化）
③ 找該機型的**復原模式**
   - 部分機型有雙 BIOS：可切換到備份 BIOS 開機
   - 部分機型有 recovery image：依手冊按特定按鍵組合或放特定檔名到 USB
   - ★★★★★ 這些步驟每個機型都不一樣，一定要查該機型手冊，不要憑經驗
④ BMC 還活著的話，從 BMC 網頁介面重新刷 BIOS（★★★★ 這是最常見的救回路徑）
⑤ 以上都不行 → 聯絡原廠。保固內通常能換板；保固外要評估修或報廢
```

【3】★★★★ BMC 更新失敗、BMC 連不上但主機正常：

```text
① 從 OS 內用 ipmitool 試試看還通不通
     sudo ipmitool mc info
② 通得到 → 用 OS 內的原廠工具重刷 BMC 韌體
③ 完全不通 → 部分機型可以從 BIOS 設定介面重設或重刷 BMC（需重開機）
④ 都不行 → 聯絡原廠
★★★★ 好消息是：BMC 掛了主機還是能跑。
       ★★★★★ 壞消息是：你失去了帶外管理，接下來任何問題都必須到現場處理 ——
       所以這件事不能拖。
```

【4】★★★★ 網路設備韌體更新失敗，停在 loader 提示 —— 這是**設計好的救援路徑**。

```text
交換器／路由器類設備多半有一個開機載入器（loader / rommon / U-Boot 之類），
可以從 USB、TFTP 或本機 flash 重新載入映像檔。

前提（★★★★★ 全部都要在更新前就準備好）：
 a. 主控台（console）線與轉接頭 —— 網路設備救援永遠靠 console，不靠網路
 b. 舊版與新版映像檔各一份，放在隨身碟與 TFTP 伺服器上
 c. 完整的設定檔備份
 d. 該機型的救援程序文件

★★★★ 沒有 console 線的話，這條路直接走不通 ——
      這就是為什麼機房必須常備 console 線與 USB 轉序列埠轉接器。
      交換器層面的排錯見 [[040-01-17-guide-網路設備-交換器故障排除]]。
```

【5】★★★ 完全沒有反應：先排除「其實是電源問題」，不要一開始就認定是變磚。

```text
① 換一條電源線、換一個插座（回情境五【1】）
② 兩顆 PSU 都試（只留一顆、換另一顆）
③ 拔掉所有外接裝置後再試
④ 都不行 → 走保固報修
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 韌體更新後開機黑畫面 | 更新失敗或版本不相容 | ★★★★★ **不要反覆斷電重試**；用 BMC 或機型的復原模式；不行就聯絡原廠 |
| ★★★★ 更新工具說「不支援此機型」 | 下載到別的機型或別的世代的檔案 | 用序號到原廠支援網站查對應的下載頁面 |
| ★★★★ 更新完成但版本沒變 | 需要冷重啟才會生效，或更新其實沒寫入 | 完全斷電再開；重新確認版本 |
| ★★★★ 更新後某個功能不見了或行為改變 | 新版變更了預設值 | ★★★★★ 更新前一定要讀 release note；必要時退回舊版 |
| ★★★★ 更新後 RAID 卡看不到磁碟 | 更新順序錯，或需要一併更新的元件沒更新 | 依原廠建議的更新順序重做；必要時退回 |

**原理**：韌體更新是把新的程式碼寫進非揮發性記憶體的過程，
寫入期間如果被中斷，設備就會停在一個「舊的已經被抹掉、新的還沒寫完」的狀態。
現代伺服器多半設計了備援映像或復原模式來處理這件事，
但這些機制的觸發方式因機型而異 —— 這就是為什麼手冊比經驗重要。
　→ 原理詳見 [[040-02-09-guide-機房-伺服器上架與初始設定]]

**預防**：
- ★★★★★ 韌體更新一律走**變更管理流程**：排維護時段、有回退方案、有人覆核
  （[[100-02-08-guide-維運-變更管理流程]]）
- ★★★★★ 更新前確認：雙路供電正常、UPS 正常、檔案雜湊值正確、read release note
- ★★★★ 沒有「非更新不可的理由」就不要更新 ——
  修補已知資安漏洞、解決正在發生的問題、原廠明確建議，這三個才是理由
- ★★★★ 先在測試機或同型備援機上更新，確認沒問題再更新正式機
- ★★★★ 更新順序依原廠建議（通常 BMC 先、BIOS 後、周邊卡再依序）

### ★★★★ 情境十：網路線接了沒燈，或速度只跑到 100M

**現象**：兩種不同的實體層問題：

```text
（A）線插上去了，兩端指示燈都不亮，完全不通
（B）通是通了，但協商出來的速度只有 100Mb/s（應該要 1000Mb/s），
     或 10G 埠一直重連、封包錯誤率高
```

★★★★★ 這兩種都屬於**實體層**問題。在花時間查 IP、路由、防火牆之前，
先把實體層排除掉 —— 這是分層排查最基本的紀律。

**判斷分流**：

```bash
sudo ethtool <介面> | grep -iE 'Speed|Duplex|Link detected|Auto-negotiation'
sudo ethtool -S <介面> | grep -iE 'error|crc|drop'      # 錯誤計數
sudo journalctl -k --since '-7 days' | grep -iE 'link is (down|up)|NIC Link'
```

```text
Link detected: no                        → 完全不通       走【1】
Speed 100Mb/s（應該 1000）                → 線對問題       走【2】
Speed 對但錯誤計數持續增加                 → 品質問題       走【3】
歷史紀錄顯示反覆 up/down                   → 間歇性斷線     走【3】
Duplex: Half（應該 Full）                  → 協商問題       走【4】
以上都正常但還是不通                       → 不是實體層，走 [[040-01-98-trouble-網路設備-常見故障排除]]
```

**處置步驟**：

【1】★★★★ 完全沒燈：用**替換法**，一次只換一個變因。

```text
① 換一條**已知良好**的跳線（★★★★★ 機房必須常備幾條測試用跳線）
   → 通了 → 原本那條線有問題，剪掉丟掉，不要放回線材箱
   → 還是不通 → 走 ②

② 換對側交換器的另一個埠
   → 通了 → 原本那個埠有問題（可能是 shutdown、故障、或設定錯）
   → 還是不通 → 走 ③

③ 換本機的另一個網路埠 / 換一張網卡
   → 通了 → 原本的埠或網卡有問題
   → 還是不通 → 走 ④

④ 到這裡還不通，問題在牆內線路（永久鏈路）
   → 用測線儀測該條永久鏈路
   → 沒有測線儀就用「兩端都改插跳線直連」的方式繞過牆內線路驗證
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 完全不通，測線儀顯示 Wire Map 開路 | 端接不良、線芯沒壓到底、模組故障 | 重新端接兩端；換模組後複測 |
| ★★★★★ 光纖兩端都亮但沒連線 | ★★★★★ 極性接反（Tx/Rx 顛倒） | 對調一端的收發位置，或改用正確極性的跳線 |
| ★★★★ 光纖損耗偏高但線本身沒問題 | ★★★★★ 端面髒污 | 用專用清潔工具清潔兩端；用顯微鏡確認；未使用時蓋防塵蓋 |
| ★★★★ 對側交換器埠燈不亮 | 該埠被 shutdown、VLAN 未指派、埠故障 | 查交換器該埠設定與狀態 |
| ★★★★ 剛插上時通，過一下就斷 | RJ45 卡榫斷裂，跳線靠重力垂著 | 換跳線；加裝水平理線架讓跳線有支撐 |

【2】★★★★ 只協商到 100M —— 這幾乎一定是**線對問題**。

```text
★★★★★ 關鍵知識：1000BASE-T 需要四對線全部可用；
        100BASE-TX 只需要兩對（1-2 與 3-6）。
        所以「掉到 100M」的典型原因是 4-5 或 7-8 這兩對其中一對不通。

依序檢查：
① 換一條已知良好的跳線 → 通到 1000M 就是跳線的問題
② 還是 100M → 用測線儀測該條永久鏈路的 Wire Map，看哪一對開路
③ 常見成因：
   a. 端接時只壓了兩對（用了「只接四芯」的舊做法或省事的施工）
   b. 水晶頭壓接不良，某一對沒壓到底
   c. 線材被尼龍束帶勒過、被踩過、被門夾過，內部線芯斷了
   d. 線材等級不符或距離超標
④ 修法：重新端接兩端並複測；線材本身受損就整條更換
```

★★★★ 同時檢查對側交換器的協商結果 —— 兩邊看到的速度應該一致。
不一致代表有一邊被寫死（強制速率）而不是自動協商。

【3】★★★★ 通得了但不穩、錯誤計數一直增加：這是**品質問題**，最難查也最常被忽略。

```bash
sudo ethtool -S <介面> | grep -iE 'crc|error|discard|drop'
# 記錄一次數字，等 10 分鐘再記一次 —— ★★★★ 看的是「增加速率」不是絕對值
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ ping 正常、測線儀顯示「通」，但吞吐量只有一半 | ★★★★★ 尼龍束帶勒緊，內部絞對幾何被破壞 | 剪掉所有尼龍束帶改用魔鬼氈；★★★★★ 更換受損線材（受損不可逆） |
| ★★★★ 1G 正常但 10G 一直重連 | Cat6 距離過長、施工品質不佳、測試 Margin 太小 | 查該條的測試 Margin；距離超標就改 Cat6A 或光纖 |
| ★★★★ 測線儀顯示 split pair（分岔對） | 端接時線序看似對但實際配對錯 | ★★★★★ 重新端接，嚴格照 T568A/B 的**配對**而非只看顏色順序 |
| ★★★★ 錯誤率上升，且該線與電力線平行貼合 | 電磁干擾 | 分槽敷設；必須交叉時盡量垂直交叉 |
| ★★★★ 測試 PASS 但 Margin 極小 | 束帶壓迫、彎折過度、解絞過長 | 找出該條的物理路徑逐段檢查；重新端接後複測 |
| ★★★★ 間歇性斷線，重插跳線就好一陣子 | 跳線懸空受重量拉扯、卡榫斷裂 | 加裝水平理線架；換跳線 |

【4】★★★ 協商成 Half Duplex：現代設備上很少見，出現就代表**有一邊被寫死了**。

```text
自動協商的規則：兩邊都自動協商 → 正常
                一邊自動、一邊寫死 → ★★★★ 自動那邊會退回半雙工，效能極差
處理：把兩邊都改成自動協商（現代設備的建議做法），
      或兩邊都寫死成相同的速率與雙工模式。
      ★★★★ 不要只改一邊。
```

**原理**：實體層問題有一個共同特徵 —— **「看起來是通的」**。
線插著、燈亮著、ping 得到，但線對受損、絞對幾何被破壞、端面髒污這些問題
只有在需要用到全部頻寬或全部線對時才會現形。
這就是為什麼施工驗收要用測線儀出報告，而不是「插上去能上網就好」。
　→ 原理詳見 [[040-02-08-guide-機房-結構化佈線與標籤規範]]、[[010-02-04-guide-網概-線材與實體層]]

**預防**：
- ★★★★★ 束線一律用魔鬼氈，**永遠不要用尼龍束帶綁網路線與光纖**
- ★★★★★ 新佈線驗收要求**永久鏈路模式**的測線儀報告，出現 `PASS*` 一律要求重做
- ★★★★ 跳線長度標準化（0.5／1／2／3／5 m）並建立庫存，不要都用手邊有的長線
- ★★★★ 機房常備幾條「已知良好」的測試跳線，專門用來做替換法排除

### ★★★★★ 情境十一：標籤與實際不符，差點拔錯線

**現象**：要動某一台設備時發現 —— 標籤寫 U31 但設備在 U30、
線材兩端標籤編號不一樣、配置圖上的設備現場找不到、
或者機櫃後方有一堆完全沒有標籤的線。

★★★★★ 這個情境的重點不是「怎麼修」，而是 **「發現不一致時，你應該停手」**。
機房裡最貴的錯誤全部都是拔錯、拆錯、插錯造成的。

> [!danger] ★★★★★ 三重核對對不上，就不要動手
> 拔任何一條線、拆任何一台設備之前，這三項必須全部一致：
> ① **機櫃編號 + U 位標籤**　② **線材兩端的標籤**　③ **對側設備（PDU／交換器）的埠標籤**
> 只要有一項對不上，就代表「你以為的那一台」和「實際的那一台」可能不是同一台。
> ★★★★★ 這時候正確的動作是**停下來查清楚**，不是「應該是這條吧」。
> 拔錯一條線造成的服務中斷，遠比多花二十分鐘查證昂貴。

**判斷分流**：

```text
標籤與實際位置不符                     → 走【1】重新核對並修正
線材兩端標籤不一致                      → 走【2】
線完全沒有標籤，不知道通到哪              → 走【3】追線
配置圖與現場不符                        → 走【4】
機櫃後方有一堆「殭屍線」（兩端都查不到用途） → 走【5】
```

**處置步驟**：

【1】★★★★★ 標籤與實際不符時的核對順序 —— **從最不會騙人的那一端開始**：

```text
最可信 → 最不可信：
 ① 設備自己回報的序號        sudo dmidecode -s system-serial-number
 ② 設備自己回報的主機名與 IP  hostname; ip -br addr
 ③ 交換器學到的 MAC 與埠      （從交換器端查，見 [[040-01-18-guide-網路設備-網路設備盤點與文件化]]）
 ④ 機身上的實體標籤
 ⑤ 機櫃 U 位標籤
 ⑥ 配置圖 / 清冊

★★★★★ 原則：以「機器自己說的」為準，然後把後面幾項修正到與它一致。
```

```bash
# 在機器上點亮它的定位燈，讓現場的人確認是哪一台（★★★★ 這招省下大量時間）
sudo ipmitool chassis identify 60        # 亮 60 秒
```

★★★★ 核對出差異之後，**當場就改標籤、當場就更新配置圖**。
「等一下再改」的結果一定是永遠不會改。

【2】★★★★ 線材兩端標籤不一致：代表有人只改了一端，或當初就貼錯。

```text
① 用追線的方法確認這條線真正的兩端（走【3】）
② 確認之後，兩端都重貼，並更新線路紀錄表
③ ★★★★★ 標籤格式要含 FROM 與 TO 兩端資訊，這樣任何一端脫落都還救得回來
   （編號規則見 [[040-02-08-guide-機房-結構化佈線與標籤規範]]）
```

【3】★★★★ 追一條沒有標籤的線 —— 由「不用碰線」到「必須碰線」排序：

```text
方法 A：LLDP（最快，但兩端都要支援）
   sudo lldpctl | grep -E 'Interface|SysName|PortID'
   → 直接告訴你對側是哪一台設備的哪一個埠

方法 B：MAC 位址表反查
   從交換器查該埠學到的 MAC，比對清冊或設備自己的 MAC
   → 適用於對側是伺服器、AP、IP 話機的情況

方法 C：流量比對（★★★★ 不用碰線，適合正式環境）
   在懷疑的埠上看流量圖形，跟已知設備的流量特徵比對

方法 D：線路追蹤器（tone generator）
   一端送訊號，另一端用探棒找 —— ★★★★ 適合牆內線路與線槽內的線

方法 E：★★★★ 最後手段 —— 短暫 shutdown 該埠，看誰掉線
   ★★★★★ 這會造成服務中斷，必須走變更流程、事先通知、選在維護時段
```

> [!warning] ★★★★★ 需要用到追線，代表標籤制度已經失效
> 追完之後**一定要補上標籤與紀錄**，否則下次還要再追一次，而且下次可能沒時間追。

【4】★★★ 配置圖與現場不符：

```text
① 以現場為準做一次完整校正（一個機櫃一個機櫃走）
② 校正時同時記錄：U 位、設備名稱、序號、BMC IP、電源接到哪一路、網路接到哪個埠
③ 改用純文字／Markdown 管理並放進 vault 用 git 版控
   ★★★★ 這樣就不會再出現「配置圖_最新_v3_真的最新.xlsx」
④ ★★★★★ 把「更新配置圖」寫進上架與下架流程的**最後一步**，並列為驗收條件
```

【5】★★★ 殭屍線的處理 —— 不要憑「應該沒在用」就剪掉：

```text
① 兩端都查：查標籤、查交換器埠狀態與流量、查清冊
② 兩端都查不到用途 → **掛牌標記日期**，寫上「疑似廢線，OO 年 OO 月 OO 日起觀察」
③ 觀察一個月（或一個完整業務週期），期間沒有任何人反映異常
④ 移除，並記錄在維護紀錄裡
★★★★ 每年做一次線路盤點，把這件事變成例行作業，不要等到線槽塞爆才處理
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 要拔某個 U 位的線，結果拔到旁邊那台正式服務 | 標籤缺失或與實際不符 | ★★★★★ 拔線前三重核對；對不上就停手 |
| ★★★★★ 找不到某條線接到哪 | 標籤只貼一端／脫落／紀錄未更新 | 短期用 LLDP 或追蹤器找；★★★★★ 長期補標籤並修正流程 |
| ★★★★ 同一棟樓有兩條線編號相同 | 編號規則沒有含棟別／樓層 | 改用含棟別 + 樓層 + 電信間的完整編號；★★★★★ 全域唯一 |
| ★★★★ 三年後接手的人找不到某台設備在哪一櫃 | 沒有編號規範，配置圖也沒維護 | 建立編號規範並貼標籤；把更新配置圖寫進上下架流程 |

**原理**：標籤與文件不是行政要求，而是**降低誤操作機率的工程手段**。
機房裡的每一次拔插都是一次賭注，標籤制度、色碼、三重核對這三層防護
的作用就是把「拔錯」從「可能發生」變成「很難發生」。
　→ 原理詳見 [[040-02-08-guide-機房-結構化佈線與標籤規範]]、
[[040-02-03-guide-機房-機櫃規劃與設備上架]]

**預防**：
- ★★★★★ 上架流程的最後一步、下架流程的最後一步都是「更新標籤與配置圖」，
  監工不簽不算完工
- ★★★★★ 拔線前三重核對，這條規則要寫成書面規定並教育所有人
- ★★★★ 色碼規範（用途／等級用不同顏色的跳線）讓錯誤在視覺上就看得出來
- ★★★★ 配置圖用純文字放進版控，不要用 Excel 在信箱裡傳來傳去

### ★★★ 情境十二：盤點對不起來（帳存實無／實有帳無／位置不符）

**現象**：年度盤點跑完，清冊與現場對不上 —— 清冊上有的機器找不到、
現場有的機器清冊上沒有、或設備位置與紀錄不符。

★★★★★ 這個情境的核心觀念：**症狀在盤點，病因在異動流程**。
差異率年年偏高的單位，加強盤點力度是沒有用的，
要把「更新清冊」綁進上架／變更／報修流程。

**判斷分流**：★★★★★ 先把差異**分成四類**，四類的處理方式完全不同。

```text
① 帳存實無：清冊有、現場找不到          → 走【1】
② 實有帳無：現場有、清冊沒有             → 走【2】
③ 位置不符：兩邊都有，但位置對不上        → 走【3】
④ 資料不符：位置對，但規格／IP／狀態不符   → 走【4】
```

**處置步驟**：

【1】★★★ 帳存實無 —— 不要急著報遺失，多數是「移動了但沒記錄」。

```text
逐項排除（依可能性排序）：
 a. 借出／外送維修中？        查維修紀錄與借出登記
 b. 移到別的機房／別的樓層？   查變更紀錄
 c. 已報廢但財產帳未註銷？     查報廢紀錄
 d. 換過機殼或抽取盒，標籤跟著跑掉？（★★★★ 標籤貼在可拆元件上的典型後果）
 e. 用序號、MAC、IP 三種方式再找一次：
      MAC 反查交換器埠 → 找出它實際接在哪一台交換器的哪一個埠
      → 這個方法能找出「機器還活著、只是不在你以為的位置」的情況
 f. 以上全部排除 → 才走財產遺失程序，並做資安評估
    ★★★★★ 如果那台機器上曾經有敏感資料，這同時是一個資安事件
```

【2】★★★ 實有帳無 —— 現場有東西但帳上沒有，這比帳存實無更值得緊張。

```text
 a. 是不是新到貨還沒登帳？          查採購與驗收紀錄
 b. 是不是別單位寄放的？            找出負責人並要求書面化
 c. 是不是廠商留在現場的測試機？     ★★★★★ 這是資安風險，必須確認來源與用途
 d. 是不是財產帳門檻以下的設備？     確認納管規則，該補登的補登
 e. 完全查不出來源 → ★★★★★ 當成資安事件處理，
    先斷網、保留現場、依 [[090-07-04-guide-資安實踐-資安事件應變流程]] 通報
```

【3】★★★ 位置不符：直接以現場為準修正清冊，但要留下修正紀錄。

```text
① 現場拍照存證（含機櫃編號與 U 位標籤入鏡）
② 更新清冊，並在備註欄註明「OO 年 OO 月盤點修正，原記錄為 XXX」
③ ★★★★ 追查為什麼會移動而沒有紀錄 —— 這才是要修的東西
```

【4】★★★ 資料不符（規格、IP、狀態）：讓機器自己回報，不要用手抄。

```bash
sudo dmidecode -s system-serial-number
sudo dmidecode -s system-product-name
sudo dmidecode -t memory | grep -E 'Size|Locator'
ip -br addr
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 差異率年年偏高 | ★★★★★ 病因在異動流程沒有強制更新清冊 | 不要加強盤點力度，把清冊更新綁進上架／變更／報修流程並列為驗收條件 |
| ★★★★ 標籤半年就脫落 | 用了一般紙貼紙，或貼在出風口／未清潔的表面 | 改用 PET 材質；貼前用異丙醇擦拭；避開出風口 |
| ★★★★ 換過抽取盒後資產編號跟著跑掉 | 標籤貼在可拆元件上 | 標籤只貼機殼本體或 rack ear；抽取盒上另貼硬碟編號 |

**原理**：清冊的準確度不是靠盤點維持的，是靠**每一次異動都同步更新**維持的。
盤點只是一次驗證，如果驗證出來差異率高，該修的是產生差異的那個流程。
　→ 原理詳見 [[040-02-11-guide-機房-資訊設備盤點]]、[[100-02-13-guide-維運-資產與授權管理]]

**預防**：
- ★★★★★ 上架、變更、報修、報廢四個流程的檢查表裡都要有「已更新清冊」這一項
- ★★★★ 讓機器自己回報硬體資訊（腳本定期收集），人只負責填機器說不出來的欄位
- ★★★★ 標籤用 PET 材質、貼在機殼本體、貼前清潔表面

### ★★★ 情境十三：門禁刷不進去、監視錄影沒錄到

**現象**：要進機房時刷卡沒反應；或事後要調錄影卻發現沒錄到、
畫面看不清楚、時間對不上。

**判斷分流**：

```text
【門禁】
  自己刷不進去，別人可以              → 個人授權問題   走【1】
  所有人都刷不進去                    → 系統或供電問題 走【2】
  門一直關不上／門開著沒告警           → 走【3】

【錄影】
  調不出指定時段的影像                → 走【4】
  調得出來但畫面全黑或糊到看不清       → 走【5】
  錄影時間與門禁時間對不上             → 走【6】
```

**處置步驟**：

【1】★★★ 個人刷不進去 —— 依序排除，通常很快就找到。

```text
 a. 卡片本身：換一張已知可用的卡試 → 通了就是卡片問題（消磁、破損、電池沒電）
 b. 授權有效期：查門禁主機的該卡授權，是不是過期或被停用
 c. 授權範圍：這張卡有沒有這一區的權限？（★★★★ 機房應該是獨立授權群組）
 d. 時段限制：有些設定會限制可進入的時段
 e. anti-passback：★★★★ 上一次沒有正常刷出，系統認為你「還在裡面」
    → 請門禁管理者重設該卡狀態
 f. 讀卡機本身：換另一個門的讀卡機試同一張卡
```

【2】★★★★ 所有人都進不去 —— 這是**緊急狀況**，因為你被鎖在機房外面。

```text
① 先確認門禁主機還活著嗎？（能不能連上管理介面）
② 門禁系統的電源正常嗎？★★★★★ 門禁主機與電鎖有沒有接 UPS？
   → 沒接 UPS 的話，停電時的行為取決於電鎖型式：
     斷電開啟型（fail-safe）  → 停電時門會開（消防要求，但資安上要有人看著）
     斷電鎖住型（fail-secure）→ 停電時進不去，★★★★★ 必須有機械鑰匙備援
③ ★★★★★ 找出備援進入方式（這件事必須事先準備好）：
     機械鑰匙在哪裡？誰保管？備份鑰匙在哪？
     ★★★★★ 「機房鑰匙鎖在機房裡的鑰匙櫃」是真的會發生的事，事先檢查一次
④ 進去之後：查門禁主機的事件紀錄找根因，並檢討備援機制
```

【3】★★★ 門關不上或門開著沒告警：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 機房門長期被門檔／滅火器卡住 | 進出頻繁圖方便，或門弓器太緊 | 調整門弓器；啟用「門長時間未關」告警並納入監控 |
| ★★★★ 門關上了但系統顯示未關 | 磁簧感應器鬆脫或錯位 | 調整感應器位置；更換感應器 |
| ★★★★ 門禁刷卡有紀錄，登記表上沒有 | 同仁圖方便不填表 | ★★★ 每月對帳並回饋；登記表放門外方便填寫 |
| ★★★★★ 登記表上有人，門禁沒有刷卡紀錄 | 借卡、尾隨、有人代開門 | ★★★★★ 逐案調閱錄影調查；實施 anti-passback；宣導「一人一刷」 |
| ★★★★ 離職後門禁還有效 | ★★★★★ 離職流程沒有納入門禁註銷 | 把「機房門禁註銷」列入離職交接清單必要項 |

【4】★★★★ 調不出指定時段的影像 —— 先確認「當時到底有沒有在錄」。

```text
 a. NVR 磁碟滿了沒有循環覆蓋，或磁碟故障 → 查 NVR 的磁碟狀態與錄影狀態
 b. 實際保存期限比規定短 → ★★★★ 增加鏡頭或提高解析度後沒有重算容量
    → 依實際鏡頭數、解析度、影格率重算所需容量，擴充儲存或調整規格
    ★★ 規定寫了 90 天但實際只有 40 天，比誠實寫 40 天更危險
 c. 該鏡頭當時就是故障的 → 查該鏡頭的離線紀錄
 d. 該時段的錄影被刪除 → ★★★★★ 這是資安事件，走事件應變流程
```

【5】★★★ 調得出來但看不清楚：

```text
 畫面全黑            → ★★★★ 機房關燈且鏡頭無紅外線夜視
                        → 換有夜視功能的鏡頭，或維持機房最低照明
 糊到看不出人臉      → 解析度不足或焦段不對
                        → 出入口用較高解析度；走道用廣角、機櫃區用中焦段
 逆光只看得到剪影     → 鏡頭正對門口強光
                        → 調整角度或啟用寬動態
 涵蓋不到關鍵位置     → 鏡頭配置沒有涵蓋所有出入口與機櫃區
                        → 依涵蓋範圍清單重新配置（[[040-02-13-guide-機房-機房實體安全]]）
```

【6】★★★★★ 錄影時間與門禁時間對不上 —— 這會讓證據**無法使用**。

```text
① 三個系統（門禁主機、NVR、伺服器）必須指向**同一組 NTP 來源**
② 每季檢查一次偏差
③ ★★★★★ 已經發生偏差時，調閱證據要同時說明偏差量，不要假裝沒事
   → 時間同步的做法見 [[020-01-28-cmd-Linux-時間同步NTP與chrony]]
```

> [!warning] ★★★★ 影像調閱要有程序，不是想調就調
> 監視影像涉及個人資料。調閱必須有申請、核准與紀錄，
> 並限制 NVR 帳號權限。「被隨意調閱查同仁行蹤」是稽核常見缺失，
> 程序見 [[040-02-13-guide-機房-機房實體安全]]。

**原理**：實體安全的四層同心圓（園區、建築、機房、機櫃）每一層都需要
「控制 + 紀錄 + 稽核」三件事同時到位。門禁提供控制與紀錄，
監視提供事後稽核 —— 兩者的時間必須對得起來，證據才成立。
　→ 原理詳見 [[040-02-13-guide-機房-機房實體安全]]、
[[090-05-15-guide-資安設備-實體與OT-IoT安全設備]]

**預防**：
- ★★★★★ 機械鑰匙的位置、保管人、備份位置要書面化，並且**每年實際測試一次**
- ★★★★★ 門禁主機、NVR 都要接 UPS，並與伺服器指向同一組 NTP
- ★★★★ 門禁授權每季覆核一次；離職流程強制包含門禁註銷
- ★★★★ NVR 納入監控（磁碟空間、錄影狀態、鏡頭離線）

### ★★★★ 情境十四：濕度過低造成靜電、過高造成凝露

**現象**：兩個方向相反、但同樣傷設備的問題：

```text
（A）★★★★ 太乾：拔線會啪一聲被電到、SFP 模組與記憶體陸續不明故障
（B）★★★★ 太濕：金屬件出現水珠、地板出風口周圍潮濕、設備內部發現水痕
```

★★★★★ 溼度是最容易被忽略的環境參數 —— 因為它不像溫度那樣會立刻造成當機，
它造成的是**慢性的、找不出原因的、零星的硬體故障**。

**判斷分流**：

```bash
# 先確認讀值本身可信：手持儀器 vs 環境感測器至少比對一次
```

```text
RH 低於 30%（依 ASHRAE 建議範圍的下限判斷）  → 靜電風險   走【1】
RH 高於 60%，或看到結露                       → 凝露風險   走【2】
RH 讀值劇烈跳動                               → 感測器或外氣灌入 走【3】
RH 正常但仍有靜電                             → 接地問題   走【4】
```

★★★★ 判定門檻請以 [[040-02-01-guide-機房-機房環境需求]] 裡的建議範圍為準，
並依你機房的實測基線調整。★★★★★ 更重要的是看**變化速率** ——
溼度短時間內大幅變動，比穩定的偏高或偏低更容易造成結露。

**處置步驟**：

【1】★★★★ 太乾：先止血（保護人與設備），再治本（處理溼度來源）。

```text
立即（今天就能做）：
 a. ★★★★ 進機房前先觸摸接地金屬洩掉身上的靜電
 b. ★★★★★ 拆機、換卡、換記憶體一律使用**防靜電腕帶**並確實接地
 c. 靜電敏感元件（記憶體、SFP、擴充卡）放在防靜電袋內，不要隨手放在桌上
 d. 避免在機房內穿容易產生靜電的衣物與鞋子

治本：
 e. 找出為什麼會這麼乾 → ★★★★★ 多半是一般冷氣顯熱比低，
    為了降溫而過度除濕（精密空調的顯熱比高，就是為了避免這件事）
 f. 短中期：加裝獨立加濕器，並把 RH 納入監控與告警
 g. 中長期：改用精密空調（詳見 [[040-02-02-guide-機房-空調系統與溫溼度監控]]）
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 冬天靜電嚴重，拔線就啪一聲，SFP 陸續故障 | 一般冷氣為了降溫過度除濕，RH 掉到極低 | 加裝加濕器或改用精密空調；★★★★ 短期強制使用防靜電腕帶 |
| ★★★★ 換記憶體之後那條就壞了 | 作業時靜電打壞元件（★★★ 常常當下看不出來，過幾天才出問題） | ★★★★★ 一律用防靜電腕帶；元件用防靜電袋盛裝 |

【2】★★★★ 太濕或結露：★★★★★ 結露就是機房裡在下雨，要當成緊急項目處理。

```text
① 先確認水從哪裡來
   a. 送風溫度低於露點 → 金屬表面凝結           → 走 ②
   b. 冷凝水排水堵塞    → ★★★★★ 即將漏水，跳應變篇
   c. 外氣直接灌入      → 門長時間開著、隔間有洞  → 封堵並改善進出習慣
   d. 天花板滴水        → ★★★★★ 這是漏水，跳 [[040-02-14-guide-機房-機房異常應變]]

② 送風溫度低於露點的處理
   ★★★★ 把送風溫度往上調（一次調一點，每次觀察一段時間），並降低機房溼度。
   ★★★★★ 調溫時同步監測機櫃進風溫度，不要為了解決結露反而造成過熱 ——
          任一機櫃進風超過建議上限就要回退。

③ 已經出現水珠的設備
   ★★★★★ 立刻用防水布遮蓋該機櫃頂部，避免水滴進設備。
   設備已經受潮的處理見 [[040-02-14-guide-機房-機房異常應變]]。
```

> [!danger] ★★★★★ 看到水就先想到電
> 只要機房裡有積水、滴水或明顯凝露，**水和電在一起就是致命的**。
> 不要踩進積水區去看情況，不要在潮濕環境下操作帶電設備。
> 這時候就不是本手冊的範圍了 —— 走 [[040-02-14-guide-機房-機房異常應變]] 的漏水應變。

【3】★★★ 讀值劇烈跳動：先確認是**環境真的在變**，還是**感測器在騙你**。

```text
 a. 用手持儀器在同一位置量，與感測器比對
 b. 感測器裝在門邊或出風口正前方 → 位置不對，移到機櫃進風處
 c. 門開關頻繁造成外氣灌入 → 這是真的在變，改善進出管理與門的自閉
 d. 感測器老化漂移 → 定期校正或更換（★★★ 溼度感測器的漂移比溫度明顯）
```

【4】★★★ RH 正常但還是有靜電：這時候要查**接地**。

```text
 a. 機櫃有沒有確實接地？（★★★★★ 機櫃、線槽、架高地板都要接地）
 b. 接地電阻有沒有量測報告？
 c. 防靜電地板的導電層有沒有接到接地系統？
 ★★★★ 這些屬於電氣作業，由合格電氣技術人員量測與改善。
 ★★★★★ 接地不良同時會造成漏電斷路器失效（回情境五【4】），
        兩件事要一起處理。
```

**原理**：溼度太低時空氣的導電性下降，靜電荷無法自然洩放，累積到一定程度就會
以放電形式擊穿半導體 —— 這種損傷常常不會立刻發作，而是造成後續的不明故障。
溼度太高時，只要有任何表面的溫度低於當下的露點，水就會凝結出來。
兩者的共同解法都是「把溼度控制在建議範圍內，並且不要劇烈變動」。
　→ 原理詳見 [[040-02-01-guide-機房-機房環境需求]]、
[[040-02-02-guide-機房-空調系統與溫溼度監控]]

**預防**：
- ★★★★★ RH 與溫度一樣要納入監控與告警，上下限都要設
- ★★★★★ 任何開殼作業一律使用防靜電腕帶，這是硬規定不是建議
- ★★★★ 溼度感測器定期校正，並每月做一次手持儀器比對
- ★★★★ 冷凝水排水口「運轉中確認有在滴水」列入每月巡檢

## 什麼時候該停手求援

> [!danger] ★★★★★ 以下情況請立刻停止操作 —— 繼續動手會讓災情擴大或造成人身危險

**【1】★★★★★ 任何與「電」有關而你不確定的事**：配電盤內部、UPS 內部、
電池組、接地系統、漏電斷路器跳脫、端子發燙變色有焦味。
★★★★★ 這些一律由**合格電氣技術人員**處理。
你能做的是：記錄現象、拍照、降載、確保人員遠離、通報。
帶電作業造成的傷害是不可逆的，而且通常不只傷到自己。

**【2】★★★★★ 看到水，或聞到焦味、看到煙**：
立刻停止本手冊的排查，走 [[040-02-14-guide-機房-機房異常應變]]。
★★★★★ 這兩類的第一動作是「保人、斷電、通報」，不是「查原因」。

**【3】★★★★★ RAID 已經降級，而你不確定該拔哪一顆**：
拔錯一顆就是整組陣列全毀。序號、實體標籤、定位燈三方交叉確認到序號那一層，
確認不了就**不要拔**。多碟同時故障時更要停手 —— 先確認備份能不能還原。

**【4】★★★★★ 冗餘已經失效，而下一步會動到僅存的那一路**：
UPS 在旁路模式時做電力作業、只剩一顆好 PSU 時去拔 PSU、
只剩一台空調在跑時去保養那一台、RAID 降級時去動另一顆碟。
★★★★★ 在單點狀態下的每一個動作都沒有安全網，先把冗餘救回來再說。

**【5】★★★★ 拔線、拆設備前三重核對對不上**：機櫃 U 位標籤、線材兩端標籤、
對側埠標籤，三者不一致就代表你可能認錯了設備。
★★★★★ 停下來查清楚，不要用「應該是這條」動手。

**【6】★★★★ 韌體更新失敗後想「再刷一次看看」**：
在不知道失敗原因的情況下重刷，很可能把還有救的狀態變成真的變磚。
先確認原因、確認檔案正確、確認供電穩定，必要時直接聯絡原廠。

**【7】★★★★ 災情比你以為的大**：多個機櫃同時異常、多台設備同時失聯、
或者你發現原因可能在電力、空調、網路的共用上游。
★★★★★ 這時候繼續在單一設備上找答案只會浪費時間 ——
升級成事件處理流程（[[100-02-09-svc-維運-事件處理與升級流程]]）。

**【8】★★★ 同一個問題試了超過三十分鐘就開始「隨便試試看」，
或要在正式環境做不可逆的變更卻沒走變更流程**：★★★★★ 隨機嘗試會讓單一故障變成
多重故障，而且沒人知道你動過什麼。機房裡的不可逆操作特別多 ——
拔線、拆機、清 foreign config、刷韌體、按 EPO，每一個都沒有 Ctrl+Z。
停下來，把做過的動作寫下來，找第二個人一起看，並走變更流程取得核准與備援計畫
（[[100-02-08-guide-維運-變更管理流程]]）。

> [!danger] ★★★★★ 關於 EPO（緊急電源關斷）按鈕
> EPO 會**瞬間切斷機房全部電力**，包含 UPS 輸出。
> 按下去之後所有設備立即斷電，沒有任何有序關機，資料庫與檔案系統可能損毀，
> 復電後的復原可能要花上數小時到數天。
> ★★★★★ EPO 只在**危及人身安全**時使用（例如需要立即消除電擊或助燃風險），
> 絕不用來處理「設備故障」或「想快點斷電」。
> 誰有權按、什麼情況按、按了之後怎麼辦，寫在
> [[040-02-14-guide-機房-機房異常應變]] —— 那是唯一該讀的地方。
