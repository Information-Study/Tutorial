# 委外系統上線前資安檢測

> [!abstract] 這篇你會學到
> - ★★★★★ 為什麼上線前這一關是**維運人員擋得住問題的最後機會**，錯過就是你在扛
> - 把檢測拆成**四大類**：組態部署面、傳輸憑證面、弱點掃描面、帳號權限面
> - 每一類**實際能跑的指令**，以及**看到什麼結果算通過、看到什麼算不通過**
> - ★★★★★ 一份可以直接印出來用的**上線前檢測清單**，分「必過項」與「建議項」兩級
> - ★★★★ **哪些缺失可以擋驗收** —— 給得出理由的明確判準，不是「我覺得不安全」
> - 交付物該檢查什麼：原始碼、建置文件、帳號清冊
> - ★★★★★ **不可以做的事**：授權邊界在哪裡，越線的法律風險
> - 缺失報告要**怎麼寫廠商才改得動**

## 觀念說明

### ★★★★★ 定位：你是最後一關

一個委外案的時間軸大概長這樣：

```text
需求書 ──► 招標 ──► 得標 ──► 開發 ──► 廠商說「做好了」 ──► ？？？ ──► 上線
                                                          ▲
                                                          │
                                            ★★★★★ 這裡就是你
```

在「？？？」之前，資安由廠商負責；在「？？？」之後，
**系統掛在你機關的網段上、用你機關的網域名稱、出事上新聞掛的是你機關的名字**。

> [!danger] ★★★★★ 一句話講清楚為什麼這關不能省
> **上線那一刻起，責任就從廠商轉移到你身上了。**
>
> 資安事件發生的時候，「這是廠商做的」不是一個能用的答案 ——
> 上級會問的是「**你們驗收的時候檢查了什麼**」。
>
> 如果答案是「廠商說做好了我們就收了」，那缺失就記在你頭上。
> 如果答案是「我們跑了 23 項檢測，有 4 項不通過已要求廠商改正並複測通過，紀錄在這裡」，
> 那你就站得住。
>
> **檢測紀錄本身就是你的保護傘**，就算檢測沒抓到那個漏洞也一樣。

> [!note] ★★★ 這不是滲透測試，也不是取代滲透測試
> 本篇談的是**維運端在上線前自己該做的基本檢查** ——
> 用的都是非破壞性的、公開可查的、不需要特殊授權的方法。
>
> 它抓得到的是「**顯而易見、不該犯、一查就知道**」的問題：
> 預設密碼、除錯模式沒關、`.git` 可下載、HTTPS 沒設好、預設帳號還在。
>
> 它抓不到的是深層的邏輯漏洞 —— 那要靠專業的滲透測試或原始碼檢測，
> 通常是契約另外要求廠商提供第三方報告。見 [[090-07-11-guide-資安實踐-委外與供應鏈資安]]。
>
> ★★★★ 但實務上，**機關被打進去的原因八成都是本篇這種等級的問題**，
> 不是什麼精妙的邏輯漏洞。

### ★★★★★ 先講授權邊界：什麼可以做，什麼不可以

在你打開任何工具之前，先把這件事弄清楚。

> [!danger] ★★★★★ 絕對不可以做的四件事
> **一、不可以對「不是你要驗收的那套系統」做任何掃描或測試。**
> 廠商公司的官網、廠商的其他客戶、你在掃描時「順便發現」的其他主機 —— 一律不碰。
> 這已經不是資安檢測，是未經授權的入侵行為。
>
> **二、不可以在正式（生產）環境做破壞性測試。**
> 破壞性測試包含：SQL injection 的 `DROP` / `UPDATE` 測試、大量請求的壓力測試、
> 檔案上傳測試留下的檔案、任何會寫入或刪除資料的動作。
> 這些一律在**測試環境**做。
>
> **三、不可以在沒有書面依據的情況下做主動攻擊型測試。**
> 「書面依據」指的是：契約裡的資安檢測條款、機關核准的檢測計畫、
> 或至少一封說明範圍與時間的通知信並取得回覆。
>
> **四、不可以把檢測結果外流。**
> 缺失報告等同於一份攻擊指南。它是機密文件，只給該給的人。
>
> ★★★★ 法律面：未經授權存取或干擾他人電腦系統，
> 在我國涉及**刑法妨害電腦使用罪章（第 358 條以下）**，
> 公務機關委外的資安監督義務則見**資通安全管理法**相關規定。
> **實際適用請洽機關法制或政風單位**，本篇不作法律意見。

★★★ 那什麼可以做？下面這張表是實務上的分界：

| 動作 | 在**測試環境** | 在**正式環境** | 說明 |
| --- | --- | --- | --- |
| `curl` 讀取回應標頭 | ✅ | ✅ | 跟一般瀏覽沒有兩樣 |
| 檢查 `.git`、備份檔是否可下載 | ✅ | ✅ | 只是發 GET 請求 |
| TLS 設定檢查（`openssl`、`testssl.sh`） | ✅ | ✅ | 唯讀 |
| 埠掃描（`nmap -sV`） | ✅ | ★★★ 要通知 | 會被 IDS 告警，先講一聲 |
| 弱點掃描器（Nikto、ZAP baseline） | ✅ | ★★★★ 要書面同意 | 會產生大量請求與日誌 |
| 用**自己的測試帳號**測越權 | ✅ | ★★★ 可以，但只能碰測試資料 | 見「帳號與權限面」 |
| ★★★★ 主動注入測試（SQLi / XSS payload） | ★★★ 要同意 | ❌ **不可以** | 有寫入風險 |
| 壓力測試、DoS 測試 | ★★★ 要排時段 | ❌ **不可以** | |
| ★★★★★ 密碼暴力破解 | ❌ | ❌ | **任何情況都不做**，會鎖住真實帳號 |

> [!tip] ★★★★ 最務實的做法：把檢測寫進契約與時程
> 在需求書階段就寫進去：
>
> - 「廠商應於**測試環境**提供一份與正式環境**組態一致**的系統，供機關進行上線前資安檢測。」
> - 「機關得於驗收前進行資安組態檢測，檢測項目包含但不限於……」
> - 「檢測發現之**必過項缺失**，廠商應於 X 個工作天內改正並提供複測。」
>
> 這樣你做檢測就有依據，廠商也有預期，不會變成上線前一天才吵架。
> 條款寫法見 [[090-07-11-guide-資安實踐-委外與供應鏈資安]]。

### 檢測分四類

```text
┌─────────────────────────────────────────────────────────┐
│ 一、組態與部署面   ★★★★★  最容易抓到、最該擋              │
│    預設密碼 / 除錯模式 / 目錄列表 / .git / 備份檔 / 版本外洩 │
├─────────────────────────────────────────────────────────┤
│ 二、傳輸與憑證面   ★★★★   使用者看得見、稽核一定看          │
│    HTTPS / 憑證鏈 / 協定版本 / 安全標頭 / Cookie 屬性       │
├─────────────────────────────────────────────────────────┤
│ 三、弱點掃描面     ★★★    元件版本比對、已知 CVE            │
│    框架版本 / 相依套件 / OS 套件                            │
├─────────────────────────────────────────────────────────┤
│ 四、帳號與權限面   ★★★★★  最容易外洩資料、最難自動化        │
│    預設帳號 / 權限分級 / 越權（A 帳號看得到 B 的資料嗎）      │
└─────────────────────────────────────────────────────────┘
```

★★★★ **順序有意義**：由外而內、由淺入深、由自動化到人工。
一二類跑得快、抓得到最多問題，先做。第四類最花時間但最重要。

### ★★★★★ 兩級制：必過項 vs 建議項

檢測清單一定要分兩級，否則你會陷入「這也不行那也不行」的僵局，
最後廠商全部推說做不到，你也不敢擋。

| | **必過項（P0）** | **建議項（P1／P2）** |
| --- | --- | --- |
| **定義** | 不過就**擋驗收**、不上線 | 列為缺失追蹤，但**不擋上線** |
| **判準** | ①法規或契約明文要求 ②會直接導致資料外洩或系統被接管 ③預設密碼未改 | 深度防禦、最佳實務、體驗優化 |
| **處理** | 廠商限期改正 → **複測通過**才驗收 | 記入缺失清單，約定改善期程或列入下期需求 |
| **例子** | 預設密碼還在、`.git` 可下載、資料庫直接暴露在網際網路、無 HTTPS、個資頁面無存取控制 | 缺 `Permissions-Policy` 標頭、Cookie 少了 `SameSite`、版本號外洩 |

> [!warning] ★★★★ 必過項要「少而硬」
> 必過項如果列了 40 條，等於沒有必過項 —— 廠商會逐條談判，最後你一條都擋不住。
>
> **必過項控制在 10～15 條以內，每一條都要能講出「不改會發生什麼具體後果」。**
> 講不出後果的，就放到建議項。
>
> 這也是為什麼要有兩級：建議項讓你**該記的都記下來**（稽核時證明你有看），
> 必過項讓你**該擋的擋得住**（因為理由夠硬）。

### 先把受測目標定義清楚

★★★★ 動手之前，把這張表填完並**請廠商與機關窗口簽名確認**：

| 欄位 | 填什麼 | 範例 |
| --- | --- | --- |
| 系統名稱 | | 線上報名系統 |
| ★★★★ 受測 URL／IP | **只有這些在範圍內** | `https://signup-test.example.gov.tw`（10.20.30.40） |
| 環境 | 測試 / 正式 | 測試環境 |
| ★★★★ 檢測時段 | 起訖時間 | 2026-09-08 09:00 ～ 2026-09-09 18:00 |
| 檢測方式 | 非破壞性 / 含主動測試 | 非破壞性為主，主動注入測試需另行同意 |
| 提供的測試帳號 | ★★★★ **至少要兩個不同權限的帳號** | `test_user01`（一般）、`test_user02`（一般）、`test_admin`（管理） |
| 廠商聯絡人 | 姓名、電話、信箱 | |
| 機關窗口 | 姓名、分機 | |
| 停止條件 | 什麼情況立刻停止並通知 | 系統無回應超過 1 分鐘、發現實際個資 |

> [!tip] ★★★★★ 為什麼一定要「兩個同權限等級的不同帳號」
> 越權測試（IDOR）的核心就是：**用 A 帳號的登入狀態，去存取 B 帳號的資料**。
>
> 只有一個帳號，你根本測不了這一項 ——
> 而這一項是**機關資料外洩最常見的原因**（改一下網址的 `id=` 就看到別人的資料）。
>
> 跟廠商要帳號的時候一定要講清楚：「兩個一般權限帳號，各自有自己的測試資料。」

### 第一類：組態與部署面（★★★★★ 先做這個）

這一類最容易抓、命中率最高、也最該擋驗收。

#### 1-1 ★★★★ 版本資訊外洩

```bash
TARGET="https://signup-test.example.gov.tw"

curl -sSI "$TARGET/" | grep -Ei '^(server|x-powered-by|x-aspnet-version|x-generator):'
```

**不通過**的樣子：

```text
Server: Apache/2.4.41 (Ubuntu)
X-Powered-By: PHP/7.4.3
```

**通過**的樣子：

```text
Server: Apache
```

或完全沒有這幾行。

| 判讀 | 說明 |
| --- | --- |
| ★★★ **為什麼是問題** | `PHP/7.4.3` 直接告訴攻擊者要找哪些 CVE。而且 PHP 7.4 早已終止支援 |
| **等級** | 版本號外洩本身是 **P1（建議項）**；但如果洩出來的版本是**已終止支援**的，升級為 **P0** |
| **怎麼改** | Nginx：`server_tokens off;`；Apache：`ServerTokens Prod` + `ServerSignature Off`；PHP：`expose_php = Off` |

Nginx 與 PHP 的安全設定見 [[060-02-02-09-guide-Nginx-安全設定]] 與 [[060-03-01-06-guide-PHP-安全設定]]。

#### 1-2 ★★★★★ 除錯模式沒關

這是委外系統**最常見也最嚴重**的組態缺失。

```bash
# 故意觸發一個錯誤，看回傳的是什麼
curl -sS "$TARGET/index.php?id=%27" | head -40
```

**不通過**的樣子（Laravel 的 `APP_DEBUG=true`）：

```text
<title>SQLSTATE[42000]: Syntax error or access violation ...</title>
...
/var/www/signup/app/Http/Controllers/RegisterController.php:87
    $rows = DB::select("SELECT * FROM registrations WHERE id = '".$id."'");
...
Environment & details:
  APP_KEY  base64:xxxxxxxxxxxxxxxxxxxxxxxxxxxx
  DB_HOST  10.20.30.50
  DB_USERNAME  signup_app
```

★★★★★ 這一頁同時洩漏了：**完整檔案路徑、原始碼片段、SQL 語句、應用程式金鑰、
資料庫主機與帳號**，而且那行 SQL 直接證明了系統有 **SQL injection**。

**通過**的樣子：

```text
<h1>系統發生錯誤</h1>
<p>請稍後再試，或聯絡系統管理員（錯誤代碼：E-20260908-0037）</p>
```

★★★ 錯誤畫面上只有一個**錯誤代碼**，詳細內容寫在伺服器端日誌。

檢查各種框架的除錯開關（★★★★ 請廠商在測試環境上示範）：

| 框架／語言 | 設定 | 通過標準 |
| --- | --- | --- |
| **Laravel** | `.env` 的 `APP_DEBUG` | `APP_DEBUG=false`、`APP_ENV=production` |
| **PHP（通用）** | `php.ini` | `display_errors = Off`、`display_startup_errors = Off`、`log_errors = On` |
| **Django** | `settings.py` | `DEBUG = False` |
| **Node.js／Express** | 環境變數 | `NODE_ENV=production` |
| **ASP.NET** | `web.config` | `<customErrors mode="On">` |

命令列驗證 PHP：

```bash
# 在伺服器上（若你有主機權限）
php -i | grep -E '^(display_errors|log_errors|expose_php|error_reporting)'
```

```text
display_errors => Off => Off
log_errors => On => On
expose_php => Off => Off
```

#### 1-3 ★★★★★ `.git` 與版本控制目錄可下載

```bash
for p in .git/HEAD .git/config .svn/entries .hg/store; do
  code=$(curl -sS -o /dev/null -w '%{http_code}' "$TARGET/$p")
  echo "$code  $TARGET/$p"
done
```

**不通過**：

```text
200  https://signup-test.example.gov.tw/.git/HEAD
200  https://signup-test.example.gov.tw/.git/config
404  https://signup-test.example.gov.tw/.svn/entries
404  https://signup-test.example.gov.tw/.hg/store
```

**通過**：全部是 `404` 或 `403`。

> [!danger] ★★★★★ 為什麼 `.git` 可下載是必過項（P0）
> `.git` 目錄裡有**整個專案的完整原始碼與所有歷史版本**。
> 攻擊者可以把它整包拉下來，然後：
>
> - 讀原始碼找漏洞（白箱等級的優勢）
> - ★★★★★ **翻歷史 commit 找出被刪掉的密碼**
>   —— 開發初期把資料庫密碼寫死在程式裡、後來才拿掉，這種事非常常見。
>   拿掉了但**歷史紀錄還在**。
>
> 這一項沒有討論空間，**發現就是 P0，不改不上線**。
>
> 順帶檢查：`.env`、`.env.bak`、`composer.json`、`package.json`、
> `docker-compose.yml` 是不是也拿得到。

```bash
for p in .env .env.bak .env.example config.php.bak composer.json package.json docker-compose.yml; do
  code=$(curl -sS -o /dev/null -w '%{http_code}' "$TARGET/$p")
  [ "$code" = "200" ] && echo "★★★★★ 可下載：$TARGET/$p"
done
```

**通過**：沒有任何輸出。

#### 1-4 ★★★★ 備份檔與暫存檔可下載

開發或部署時留下的檔案，是另一個高命中率的地方。

```bash
# 針對已知的主要檔案，試常見的備份副檔名
BASE="index.php"
for ext in .bak .old .orig .save "~" .swp .txt .zip .tar.gz; do
  url="$TARGET/${BASE}${ext}"
  code=$(curl -sS -o /dev/null -w '%{http_code}' "$url")
  [ "$code" = "200" ] && echo "★★★★ 可下載：$url"
done
```

```bash
# 資料庫傾印檔
for f in backup.sql dump.sql db.sql database.sql backup.zip www.zip site.tar.gz; do
  code=$(curl -sS -o /dev/null -w '%{http_code}' "$TARGET/$f")
  [ "$code" = "200" ] && echo "★★★★★ 可下載資料庫傾印：$TARGET/$f"
done
```

**通過**：兩段都沒有輸出。

★★★★ 特別注意 `.php~`（編輯器的備份檔）：
`index.php` 是被 PHP 執行的，但 `index.php~` **不會被執行，會直接當純文字送給你** ——
等於原始碼外洩。

#### 1-5 ★★★★ 目錄列表（Directory Listing）

```bash
for d in / /uploads/ /files/ /images/ /backup/ /logs/ /tmp/ /public/ /storage/; do
  body=$(curl -sS "$TARGET$d" | head -20)
  if echo "$body" | grep -qiE '<title>Index of|Directory listing for'; then
    echo "★★★★ 目錄列表開著：$TARGET$d"
  fi
done
```

**不通過**時你會在瀏覽器看到：

```text
Index of /uploads

  Name                        Last modified      Size
  ../
  身分證影本_王小明.jpg       2026-08-30 14:22   1.2M
  報名表_20260830.xlsx        2026-08-30 15:01   88K
```

★★★★★ 上面這個例子直接就是**個資外洩**。
目錄列表本身是 P1，但**如果列出來的內容含個資或敏感檔案，立刻升級成 P0**。

**怎麼改**：Nginx 預設就是關的（`autoindex off;`）；
Apache 要移除 `Options Indexes`（改成 `Options -Indexes`）。

#### 1-6 ★★★ 危險路徑與管理介面暴露

```bash
for p in phpinfo.php info.php test.php adminer.php phpmyadmin/ pma/ \
         .well-known/security.txt server-status server-info \
         actuator/health api/docs swagger-ui.html; do
  code=$(curl -sS -o /dev/null -w '%{http_code}' "$TARGET/$p")
  [ "$code" = "200" ] && echo "$code  $TARGET/$p"
done
```

判讀：

| 路徑 | 若回 200 的等級 | 說明 |
| --- | --- | --- |
| ★★★★★ `phpinfo.php` / `info.php` | **P0** | 洩漏完整環境資訊、路徑、擴充清單、有時含環境變數 |
| ★★★★★ `adminer.php` / `phpmyadmin/` | **P0** | 資料庫管理介面暴露在網際網路上 |
| ★★★★ `server-status` | **P0**（若含請求內容） | Apache 狀態頁會列出目前的請求 URL，可能含 token |
| ★★★ `swagger-ui.html` / `api/docs` | P1（內網）／**P0**（對外且未鎖） | API 文件外洩，等於給攻擊者地圖 |
| `.well-known/security.txt` | — | 這是好東西，不是問題 |

#### 1-7 ★★★ 對外開放的埠

```bash
# 只掃「你被授權的那一台」，而且是常見埠
sudo nmap -Pn -sV --top-ports 200 10.20.30.40
```

```text
PORT     STATE SERVICE  VERSION
22/tcp   open  ssh      OpenSSH 8.9p1 Ubuntu 3ubuntu0.10
80/tcp   open  http     nginx
443/tcp  open  ssl/http nginx
3306/tcp open  mysql    MySQL 8.0.36-0ubuntu0.22.04.1
```

★★★★★ `3306` 從外面連得到 = **P0，資料庫直接暴露**。

驗證它真的可以從外面連：

```bash
timeout 3 bash -c 'cat < /dev/null > /dev/tcp/10.20.30.40/3306' && echo "3306 對外開放（P0）" || echo "3306 不通"
```

★★★ 通過標準：**只有服務真正需要的埠對外開放**。
一般的 Web 系統應該只有 `443`（`80` 只做轉址），管理埠（22、3306、6379…）
應該只從管理網段或 VPN 進得來。防火牆設定見 [[090-02-02-guide-防火牆-ufw基礎與實務]]。

nmap 的完整用法見 [[060-01-04-04-guide-nmap-埠掃描與盤點]]。

### 第二類：傳輸與憑證面

#### 2-1 ★★★★★ 有沒有 HTTPS、HTTP 有沒有轉址

```bash
curl -sSI "http://signup-test.example.gov.tw/" | head -5
```

**通過**：

```text
HTTP/1.1 301 Moved Permanently
Location: https://signup-test.example.gov.tw/
```

**不通過**：回 `200` 且真的送出網頁內容 —— 代表**可以用純 HTTP 使用系統**。

★★★★★ 只要系統會處理帳號密碼或個資，**無 HTTPS 就是 P0**。

#### 2-2 ★★★★ 憑證本身

```bash
echo | openssl s_client -connect signup-test.example.gov.tw:443 \
  -servername signup-test.example.gov.tw 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

```text
subject=CN = signup-test.example.gov.tw
issuer=C = TW, O = Government Certification Authority, CN = GCA
notBefore=Aug 20 00:00:00 2026 GMT
notAfter=Nov 18 23:59:59 2026 GMT
X509v3 Subject Alternative Name:
    DNS:signup-test.example.gov.tw
```

★★★★ 四個檢查點：

| 檢查 | 通過標準 | 不通過的後果 |
| --- | --- | --- |
| **SAN 包含實際使用的網域** | 有 | 瀏覽器顯示憑證錯誤 |
| ★★★★ **簽發者是受信任的 CA** | 不是自簽 | 對外系統用自簽憑證 = **P0**（使用者被訓練成忽略警告） |
| **有效期** | `notAfter` 距今 > 30 天 | 上線後很快過期 |
| ★★★ **中繼憑證鏈完整** | 見下方 | 桌機瀏覽器可能沒事，**手機 App 與 API 呼叫會失敗** |

檢查憑證鏈完整性：

```bash
echo | openssl s_client -connect signup-test.example.gov.tw:443 \
  -servername signup-test.example.gov.tw 2>/dev/null | grep -E 'Verify return code|verify error'
```

**通過**：

```text
Verify return code: 0 (ok)
```

★★★★ 看到 `20 (unable to get local issuer certificate)` 代表**中繼憑證沒裝**。
這是機關最常見的憑證問題 —— 用 Chrome 測起來正常（Chrome 會自己補），
但 `curl`、Java 客戶端、手機 App 全部失敗。

憑證與憑證鏈的完整說明見 [[090-03-01-guide-應用安全-TLS憑證與HTTPS實務]]
與 [[090-01-07-guide-PKI-自建中繼CA與憑證鏈]]。

#### 2-3 ★★★★ 協定版本與加密套件

```bash
# 舊協定應該全部連不上
for v in ssl3 tls1 tls1_1; do
  printf '%-8s ' "$v"
  echo | openssl s_client -connect signup-test.example.gov.tw:443 -$v 2>&1 \
    | grep -qE 'Cipher.*:.*[A-Z]' && echo "★★★★ 仍支援（不通過）" || echo "已停用（通過）"
done
```

```text
ssl3     已停用（通過）
tls1     已停用（通過）
tls1_1   已停用（通過）
```

```bash
# TLS 1.2 / 1.3 應該要支援
for v in tls1_2 tls1_3; do
  printf '%-8s ' "$v"
  echo | openssl s_client -connect signup-test.example.gov.tw:443 -$v 2>&1 \
    | grep -q 'Verify return code: 0' && echo "支援（通過）" || echo "不支援"
done
```

```text
tls1_2   支援（通過）
tls1_3   支援（通過）
```

★★★ 更完整的檢查（含加密套件強度、憑證問題、已知漏洞）用 `testssl.sh`：

```bash
docker run --rm -ti drwetter/testssl.sh --quiet --color 0 \
  signup-test.example.gov.tw:443
```

> [!warning] ★★★ 未實機驗證
> `openssl s_client` 是否還支援 `-ssl3`／`-tls1` 旗標，取決於**你這台的 OpenSSL 編譯選項**。
> 新版 OpenSSL 3.x 預設可能已移除舊協定支援 —— 這時候旗標本身會報錯，
> 那**不代表對方停用了**，只代表你測不了。
> 遇到這種情形請改用 `testssl.sh` 或 `nmap --script ssl-enum-ciphers`。

#### 2-4 ★★★★ 安全標頭

```bash
curl -sSI "$TARGET/" | grep -Ei \
 '^(strict-transport-security|content-security-policy|x-frame-options|x-content-type-options|referrer-policy|permissions-policy):'
```

**通過**的樣子：

```text
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'
X-Frame-Options: SAMEORIGIN
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
```

分級（★★★★ 這是實務上守得住的分法）：

| 標頭 | 等級 | 沒有的後果 |
| --- | --- | --- |
| ★★★★ `Strict-Transport-Security` | **P0**（有登入功能時） | 使用者第一次用 HTTP 連進來就可能被降級攻擊 |
| ★★★★ `X-Frame-Options` 或 CSP 的 `frame-ancestors` | **P0**（有登入功能時） | 點擊劫持：把你的系統嵌在假網頁裡騙使用者點 |
| ★★★ `X-Content-Type-Options: nosniff` | P1 | MIME 嗅探造成的 XSS |
| ★★★ `Content-Security-Policy` | P1（新系統可要求 P0） | XSS 的第二道防線失守 |
| ★★ `Referrer-Policy` | P1 | 網址中的參數外洩給第三方 |
| ★ `Permissions-Policy` | P2 | — |

各標頭的意義與正確設定見 [[090-03-02-guide-應用安全-應用層安全]]。

#### 2-5 ★★★★ Cookie 屬性

```bash
curl -sSI "$TARGET/" | grep -i '^set-cookie:'
```

**不通過**：

```text
Set-Cookie: PHPSESSID=a1b2c3d4e5f6; path=/
```

**通過**：

```text
Set-Cookie: PHPSESSID=a1b2c3d4e5f6; path=/; secure; HttpOnly; SameSite=Lax
```

| 屬性 | 等級 | 沒有的後果 |
| --- | --- | --- |
| ★★★★★ `Secure` | **P0** | session cookie 會在 HTTP 連線上被明文送出 = **帳號被劫持** |
| ★★★★★ `HttpOnly` | **P0** | JavaScript 讀得到 session，一個 XSS 就能偷走登入狀態 |
| ★★★ `SameSite` | P1（`Lax` 以上） | CSRF 的第一道防線 |

> [!tip] ★★★ 登入之後再測一次
> 首頁的 cookie 常常不是 session cookie。**真正的 session cookie 在登入之後才發**。
>
> ```bash
> curl -sS -c /tmp/cookie.txt -o /dev/null \
>   -d 'username=test_user01&password=***' "$TARGET/login" -D /tmp/hdr.txt
> grep -i '^set-cookie:' /tmp/hdr.txt
> ```
>
> ★★★★ 用完記得 `shred -u /tmp/cookie.txt`，那裡面是有效的登入憑證。

### 第三類：弱點掃描面

★★★ 這一類的重點是**元件版本比對**：系統用了哪些框架與套件、版本多舊、有沒有已知 CVE。

工具本身（Nessus、OpenVAS、Trivy、Nuclei 的操作）見
[[090-05-10-guide-資安設備-弱點管理與滲透測試工具]]，本篇不重複。
這裡只講**驗收情境下怎麼用**。

#### 3-1 ★★★★ 跟廠商要「軟體物料清單」

與其自己猜系統用了什麼，不如直接要。

```text
交付項目：軟體物料清單（SBOM）或相依套件清單
內容應包含：套件名稱、版本、授權條款、來源
格式：CycloneDX / SPDX 或至少是 composer.lock / package-lock.json
```

拿到之後自己核對：

```bash
# PHP 專案（Composer 2.4 以上內建）
composer audit --format=table
```

```text
Found 2 security vulnerability advisories affecting 2 packages:
+-------------------+----------------------------------------------------------+
| Package           | guzzlehttp/guzzle                                        |
| CVE               | CVE-2022-31090                                           |
| Title             | Cookie headers on redirect                               |
| Affected versions | >=7.0.0,<7.4.5                                           |
+-------------------+----------------------------------------------------------+
```

```bash
# Node.js 專案
npm audit --audit-level=high
```

```text
# npm audit report

axios  <1.6.0
Severity: high
Server-Side Request Forgery in axios - https://github.com/advisories/GHSA-xxxx
fix available via `npm audit fix --force`
```

★★★★ 判讀原則：

| 情況 | 等級 |
| --- | --- |
| ★★★★★ 有 **Critical／High** 且該套件**在對外路徑上**（處理使用者輸入） | **P0** |
| ★★★★ 使用**已終止支援（EOL）**的主要元件（PHP 7.x、Node 14、CentOS 7…） | **P0** |
| ★★★ Medium／Low，或該套件只在建置階段用到（devDependencies） | P1 |
| 有 CVE 但廠商已提出**具體的緩解措施**與升級時程 | P1 + 追蹤 |

> [!warning] ★★★★ 「不能升級因為會壞掉」不是免責理由
> 廠商常說「升級這個套件會影響功能，我們用了替代方案」。
> 這句話可以接受，但**必須要有書面的替代方案說明**：
>
> - 具體的緩解措施是什麼（例如 WAF 規則、輸入過濾、關閉該功能）
> - 什麼時候會真正升級
> - 誰負責追蹤
>
> 只有口頭說「沒事啦」，就照 P0 處理。

#### 3-2 ★★★ 從外部指認元件版本

如果拿不到清單（或要驗證清單是不是真的）：

```bash
# 從回應標頭與常見指紋檔案推測
curl -sSI "$TARGET/" | grep -Ei 'server|x-powered-by|x-drupal|x-generator'
curl -sS "$TARGET/" | grep -oiE '<meta name="generator" content="[^"]*"'
```

```bash
# 常見框架的版本指紋檔
for p in /CHANGELOG.txt /readme.html /wp-includes/version.php /package.json; do
  code=$(curl -sS -o /dev/null -w '%{http_code}' "$TARGET$p")
  [ "$code" = "200" ] && echo "$code  $TARGET$p"
done
```

★★★ 這些檔案本身回 200 就已經是一個缺失（版本外洩），順便也告訴你版本號。

#### 3-3 ★★★ 被動掃描

★★★★ 在**測試環境**、且取得同意之後，可以跑一次 ZAP 的 baseline 掃描。
它是**被動**掃描 —— 只分析正常瀏覽的流量，不送攻擊 payload。

```bash
docker run --rm -t -v "$(pwd)":/zap/wrk:rw \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t "$TARGET" -r zap-baseline-report.html
```

```text
PASS: Vulnerable JS Library [10003]
WARN-NEW: Missing Anti-clickjacking Header [10020] x 3
WARN-NEW: Cookie No HttpOnly Flag [10010] x 1
FAIL-NEW: 0  FAIL-INPROG: 0  WARN-NEW: 2  WARN-INPROG: 0  INFO: 4  IGNORE: 0  PASS: 51
```

> [!danger] ★★★★★ 不要在正式環境跑 `zap-full-scan.py` 或 `-a`（主動掃描）
> `zap-baseline.py` 是被動的、安全的。
> `zap-full-scan.py` 會送出**主動攻擊 payload**（SQLi、XSS、指令注入…），
> 可能**寫入資料、觸發寄信、刪除記錄、癱瘓服務**。
>
> 主動掃描：**只在測試環境、只在取得書面同意、只在約定時段**。

### 第四類：帳號與權限面（★★★★★ 最重要）

#### 4-1 ★★★★★ 預設帳號與預設密碼

這是**擋驗收最沒有爭議**的一項。

```text
檢查方式：請廠商提供「系統上所有存在的帳號清冊」，逐一確認：
  □ 沒有 admin / administrator / root / test / demo / guest 這類帳號
  □ 如果有，密碼不是 admin / 123456 / password / 空白 / 與帳號相同
  □ 開發時期的測試帳號已刪除
  □ 資料庫的 root 帳號有密碼，且應用程式不是用 root 連資料庫
```

實際測試（★★★ 只試少數幾組，**不要做暴力破解**）：

```bash
# 手動在登入頁試 3～5 組最常見的組合就好
# admin/admin, admin/123456, admin/password, test/test
```

> [!danger] ★★★★★ 這裡的紅線
> **試 3～5 組公認的預設組合是「組態檢查」；用字典檔跑幾千次是「暴力破解」。**
>
> 後者會：①觸發帳號鎖定，可能鎖住真實使用者
> ②在日誌裡留下大量失敗紀錄，被當成攻擊事件
> ③超出「非破壞性檢測」的範圍
>
> **任何情況下都不要做暴力破解。**
> 密碼強度要驗證的話，改成檢查「系統有沒有強制密碼複雜度與鎖定機制」。

順帶檢查密碼政策：

```text
□ 註冊／改密碼時，能不能設一個 6 位數字的密碼？（應該被擋）
□ 連續輸入錯誤密碼 5 次以上，會不會鎖定或延遲？
□ 密碼是不是雜湊儲存？（請廠商在測試環境 SELECT 一筆給你看）
```

★★★★ 最後一項很重要：

```sql
-- 請廠商在測試環境示範（正式環境不要動）
SELECT username, password FROM users LIMIT 3;
```

**不通過**：

```text
+------------+--------------+
| username   | password     |
+------------+--------------+
| test_user01| Abcd1234     |   ← ★★★★★ 明文，P0
+------------+--------------+
```

**通過**：

```text
+------------+--------------------------------------------------------------+
| username   | password                                                     |
+------------+--------------------------------------------------------------+
| test_user01| $2y$12$LQv3c1yqBWVHxkd0LHAkCOYz6TtxMQJqhN8/LewdBPj6Ea.aQe7Aq |
+------------+--------------------------------------------------------------+
```

★★★ `$2y$` 開頭是 bcrypt，`$argon2id$` 是 Argon2 —— 兩者都可以。
看到 32 位十六進位（MD5）或 40 位（SHA-1）就是**不通過**。

#### 4-2 ★★★★★ 越權測試：用 A 帳號能不能看到 B 的資料

**這一項是機關資料外洩最常見的原因，也是自動化工具最不容易抓到的。**

準備兩個一般權限帳號，各自建立一筆自己的資料。

```bash
# 用 test_user01 登入並保存 cookie
curl -sS -c /tmp/u1.txt -o /dev/null \
  -d 'username=test_user01&password=***' "$TARGET/login"

# 用 test_user02 登入並保存 cookie
curl -sS -c /tmp/u2.txt -o /dev/null \
  -d 'username=test_user02&password=***' "$TARGET/login"
```

先用 user01 看自己的資料，記下網址裡的識別碼：

```bash
curl -sS -b /tmp/u1.txt "$TARGET/registration/view?id=1001" | grep -o '<h2>.*</h2>'
```

```text
<h2>報名資料：王小明</h2>
```

★★★★★ 關鍵一步 —— **改成別人的 id，但帶自己的 cookie**：

```bash
curl -sS -b /tmp/u1.txt -w '\nHTTP %{http_code}\n' \
  "$TARGET/registration/view?id=1002" | tail -5
```

**不通過**（越權成功）：

```text
<h2>報名資料：李大華</h2>
<p>身分證字號：A12345****</p>
HTTP 200
```

**通過**：

```text
HTTP 403
```

或

```text
HTTP 404
```

> [!danger] ★★★★★ 為什麼這是 P0，沒有例外
> 這代表**任何一個註冊使用者，只要改一下網址的數字，就能看到全部人的資料**。
>
> 不需要任何駭客技巧，不需要工具，改個數字就好。
> 如果系統裡有個資，這就是**確定會發生的個資外洩**，
> 涉及個人資料保護法的通報義務。見 [[090-07-07-guide-資安實踐-台灣資安法規與個資法]]。
>
> **發現這個，直接擋驗收。**

★★★★ 要測的不只是查看，還有**修改與刪除**：

```bash
# 用 user01 的身分嘗試修改 user02 的資料（★★★ 只在測試環境做）
curl -sS -b /tmp/u1.txt -X POST -w '\nHTTP %{http_code}\n' \
  -d 'id=1002&note=越權測試' "$TARGET/registration/update"
```

通過標準：回 `403`，而且**回去用 user02 確認資料真的沒被改到**。

還有**垂直越權**（一般使用者能不能做管理員的事）：

```bash
# 用一般使用者的 cookie 直接打管理路徑
for p in /admin /admin/users /admin/export /api/admin/users; do
  code=$(curl -sS -o /dev/null -w '%{http_code}' -b /tmp/u1.txt "$TARGET$p")
  echo "$code  $p"
done
```

```text
403  /admin
403  /admin/users
403  /admin/export
403  /api/admin/users
```

★★★★ 全部 `403` 或 `302`（轉回登入頁）才算通過。
只要有一個回 `200` 就是 P0。

> [!warning] ★★★★ 常見的假通過：前端藏起來不算存取控制
> 有些系統的做法是「一般使用者的畫面上不顯示管理選單」，
> 但後端 API **根本沒檢查權限**。
>
> 所以測試**一定要用 `curl` 直接打 API**，不能只看畫面上有沒有那個按鈕。
> 「看不到」跟「不能存取」是兩件完全不同的事。

#### 4-3 ★★★ 登出與 session

```bash
# 登出後，原本的 cookie 應該失效
curl -sS -b /tmp/u1.txt -o /dev/null "$TARGET/logout"
curl -sS -b /tmp/u1.txt -o /dev/null -w '%{http_code}\n' "$TARGET/registration/view?id=1001"
```

**通過**：`302`（轉回登入頁）或 `401` / `403`。
**不通過**：`200` —— 代表**登出只是清了瀏覽器的 cookie，伺服器端 session 還活著**。

其他要確認的：

| 檢查 | 通過標準 |
| --- | --- |
| ★★★ 登入成功後 session ID 有沒有更換 | 有換（防 session fixation） |
| ★★★ 閒置多久自動登出 | 有設定，且合理（30 分鐘～8 小時） |
| ★★ 同一帳號可否多處同時登入 | 依需求，但要有一致的行為 |
| ★★★★ 系統是否接上機關的集中認證 | 見下方 |

> [!tip] ★★★★ 順便看一下帳號的來源
> 如果這套系統自己有一份帳號密碼資料庫，那它就是**又一套需要人工停權的系統**。
>
> 在驗收階段就問廠商：「能不能接機關的 AD？」
> 這件事在**開發完成前**提出，成本遠低於上線後才回頭要求。
>
> 做法見 [[090-03-05-svc-應用安全-自建服務接上AD與LDAP認證]]。

### ★★★★★ 哪些缺失可以擋驗收：給得出理由的判準

你需要的不是「我覺得不安全」，而是一句**上級與廠商都反駁不了的話**。

| 判準 | 為什麼站得住 | 講法範例 |
| --- | --- | --- |
| ★★★★★ **一、契約或需求書明文要求** | 這是履約標準，不是你的個人意見 | 「需求書第 X 章第 Y 條要求系統應以 HTTPS 提供服務，現況為 HTTP 可直接存取，未達履約標準。」 |
| ★★★★★ **二、法規要求** | 法遵是機關的義務，沒有裁量空間 | 「本系統處理個人資料，依個人資料保護法及本機關資安規定應採適當安全措施，現況存在越權存取，任一使用者可讀取全部民眾個資。」 |
| ★★★★★ **三、會直接導致資料外洩或系統被接管** | 後果具體、可示範 | 「以測試帳號 A 將網址參數由 1001 改為 1002，即可讀取他人身分證字號，附證據截圖。」 |
| ★★★★★ **四、預設密碼未變更** | 業界共識、零爭議 | 「管理員帳號 admin 密碼仍為 admin，任何人可取得系統最高權限。」 |
| ★★★★ **五、使用已終止支援的元件** | 客觀事實，有官方 EOL 日期可查 | 「系統使用 PHP 7.4，官方已於 2022-11-28 終止安全支援，後續無安全性更新。」 |

> [!warning] ★★★★ 反過來說，這幾種理由**擋不住**
> | 講法 | 為什麼擋不住 |
> | --- | --- |
> | 「這樣寫不夠安全」 | 主觀，沒有具體後果 |
> | 「別家都用 XX 框架」 | 契約沒要求 |
> | 「我覺得效能不好」 | 那是效能問題不是資安問題，而且要有量測數據 |
> | 「缺 `Permissions-Policy` 標頭」 | 深度防禦項目，沒有立即後果，屬 P1 |
> | 「原始碼寫得很亂」 | ★★★ 除非契約有品質條款，否則列建議 |
>
> ★★★★★ **判準是「不改會發生什麼具體後果」，能講出來的就擋得住，講不出來的就列建議項。**

法定的驗收程序、不符時的處理（限期改正、罰則、保證金）

### 交付物的檢查

★★★ 資安檢測不只看跑起來的系統，也要看**交出來的東西**。

| 交付物 | 檢查什麼 | 常見缺失 |
| --- | --- | --- |
| ★★★★ **原始碼** | 完整、可建置、含建置說明 | 交了一包 zip 但缺相依套件、缺建置步驟、根本編不起來 |
| ★★★★★ **原始碼裡的機密** | **不可以有寫死的密碼、金鑰、Token** | 見下方檢查方式 |
| ★★★★ **建置與部署文件** | 照著做能重建一套系統 | 只有「安裝 PHP」四個字 |
| ★★★★★ **帳號清冊** | 所有預設／內建／服務帳號的完整列表 | 沒交，或漏掉開發時建的測試帳號 |
| ★★★ **系統架構圖與資料流圖** | 資料存在哪、走什麼路徑、誰能存取 | 沒有，導致你不知道個資存在哪 |
| ★★★★ **相依套件清單（SBOM）** | 套件名、版本、授權 | 沒有，無法做弱點比對 |
| ★★★ **第三方檢測報告** | 若契約有要求 | 報告日期比交付日早半年，中間改了很多 |
| ★★★ **智財與授權聲明** | 使用的開源元件授權是否相容 | 用了 GPL 元件但機關要閉源散布 |

原始碼與智財歸屬的完整要求見 [[080-05-06-guide-採購-交付物原始碼與智財歸屬]]。

#### ★★★★★ 檢查原始碼裡有沒有寫死的機密

```bash
cd /path/to/交付的原始碼

# 用 grep 快速掃一遍
grep -rniE '(password|passwd|pwd|secret|api[_-]?key|token|private[_-]?key)[[:space:]]*[:=]' \
  --include='*.php' --include='*.js' --include='*.py' --include='*.env*' \
  --include='*.yml' --include='*.yaml' --include='*.json' --include='*.ini' . \
  | grep -vE '(example|sample|placeholder|your[_-]|xxx|\*\*\*)' \
  | head -40
```

**不通過**的樣子：

```text
./config/database.php:12:    'password' => 'P@ssw0rd2024',
./app/Services/SmsService.php:8:    private $apiKey = 'sk_live_9a8b7c6d5e4f3g2h';
./.env:15:MAIL_PASSWORD=Abc123456
```

★★★★★ 特別要看 **git 歷史**：

```bash
# 如果交付的是 git repo，歷史裡的祕密比現在的更危險
git log --all --oneline | wc -l
git log -p --all -S 'password' -- . | grep -iE '^\+.*password.*=' | head -20
```

★★★★ 更完整的做法是用專門的工具（例如 `gitleaks`），
不過即使只用上面兩段 `grep`，命中率也已經很高。

> [!danger] ★★★★★ 在原始碼裡找到正式環境的密碼＝立刻處理
> 這不是「請廠商下次注意」，而是：
>
> 1. ★★★★★ **立刻輪替那組密碼／金鑰**。它已經在原始碼裡，
>    可能也在廠商的 git、廠商員工的筆電、外包給誰的硬碟裡。
> 2. 要求廠商說明**這份原始碼流通到哪些地方**。
> 3. 檢查該憑據有沒有被使用過的異常紀錄。
> 4. 才是要求修改程式改用環境變數或機密管理。
>
> 正確的做法見 [[090-03-03-guide-應用安全-機密管理與金鑰保護]]。

### ★★★★★ 缺失報告怎麼寫，廠商才改得動

同樣一個問題，寫法不同，結果差很多。

> [!example] ★★★★★ 廠商當天就能動工的寫法
> ```text

> 【等級】P0（必過項，不改正不予驗收）

> 【使用帳號】test_user01（一般使用者，其本人資料 id=1001）
>
> 【重現步驟】

>   2. 開啟 /registration/view?id=1001 —— 正常顯示本人資料。
>   3. 將網址參數改為 id=1002（此為 test_user02 之資料）。
>   4. 頁面回應 HTTP 200，並顯示 test_user02 之姓名與身分證字號。
>
> 【證據】
>   附件 A：步驟 3 之瀏覽器截圖（已遮蔽個資）
>   附件 B：curl 完整請求與回應（screenshots/SEC-2026-004-curl.txt）
>
> 【影響】
>   任一已註冊使用者僅需修改網址數字，即可讀取系統內全部報名者之
>   姓名、身分證字號、聯絡電話與地址。屬個人資料外洩風險。
>
> 【依據】
>   需求書第四章 4.3「系統應確保使用者僅能存取其本人資料」
>   個人資料保護法之安全維護義務
>
> 【建議修正方向】
>   於 /registration/view 之後端邏輯，加入「該筆資料之 owner_id
>   是否等於目前登入者 id」之檢查；管理員角色另以角色判斷放行。
>   建議一併檢視所有以 id 參數查詢的端點（至少包含 view / edit /
>   update / delete / export）。
>
> 【要求改正期限】2026-09-15
> 【複測方式】依上述重現步驟複測，步驟 3 應回應 HTTP 403。
> ```

★★★★ 一份好的缺失單有這八個欄位：

| 欄位 | 為什麼不能少 |
| --- | --- |
| ★★★★ **編號與等級** | 讓雙方能精準指涉，也讓「哪些擋驗收」一目瞭然 |
| **環境與時間** | 避免「我在別的環境測沒問題」的爭執 |
| ★★★★★ **重現步驟** | **廠商最需要的就是這個**。沒有它，廠商第一件事就是問你怎麼重現 |
| ★★★★ **證據** | 截圖或 request/response。避免變成各說各話 |
| ★★★★★ **影響** | 這是「為什麼要改」的說服力來源 |
| ★★★★★ **依據** | 這是「為什麼你有權要求」的來源（契約條款／法規） |
| ★★★ **建議修正方向** | 不是幫他寫程式，是**縮短來回**。也順便暗示不要只改那一個端點 |
| ★★★★ **期限與複測方式** | ★★★★★ **「複測方式」寫清楚，廠商就知道改到什麼程度算完成** |

> 在「建議修正方向」裡加上一句「**建議一併檢視所有類似端點**」。
>
> 否則廠商只會修你舉例的那一個 URL，剩下十幾個一樣的問題還在，
> 你複測時再開一張單，來回沒完沒了。

### 步驟 2：★★★★ 寫一支自動化的組態與傳輸檢查腳本

```bash
cat > check-baseline.sh <<'SCRIPT'
#!/usr/bin/env bash
# 上線前資安檢測 — 組態與傳輸面自動檢查
# 用法：./check-baseline.sh https://target.example.gov.tw
set -uo pipefail

TARGET="${1:?用法: $0 https://target}"
HOST="$(echo "$TARGET" | sed -E 's#https?://##; s#/.*##')"
PASS=0; FAIL=0; WARN=0

ok()   { echo "  [通過] $*"; PASS=$((PASS+1)); }
bad()  { echo "  [不通過][P0] $*"; FAIL=$((FAIL+1)); }
warn() { echo "  [建議][P1] $*"; WARN=$((WARN+1)); }

code() { curl -sS -o /dev/null -w '%{http_code}' --max-time 10 "$1" 2>/dev/null; }

echo "=== 受測目標：$TARGET  ($(date '+%F %T')) ==="

echo
echo "── 一、組態與部署面 ──"

# 1-1 版本外洩
hdrs="$(curl -sSI --max-time 10 "$TARGET/" 2>/dev/null)"
if echo "$hdrs" | grep -qiE '^x-powered-by:'; then
  warn "X-Powered-By 外洩：$(echo "$hdrs" | grep -i '^x-powered-by:' | tr -d '\r')"
else
  ok "無 X-Powered-By 標頭"
fi
if echo "$hdrs" | grep -qiE '^server:.*[0-9]+\.[0-9]+'; then
  warn "Server 標頭含版本號：$(echo "$hdrs" | grep -i '^server:' | tr -d '\r')"
else
  ok "Server 標頭未含版本號"
fi

# 1-3 版本控制目錄
for p in .git/HEAD .git/config .svn/entries; do
  if [ "$(code "$TARGET/$p")" = "200" ]; then
    bad "可下載版本控制檔案：/$p"
  else
    ok "/$p 不可下載"
  fi
done

# 敏感設定檔
for p in .env .env.bak config.php.bak docker-compose.yml; do
  [ "$(code "$TARGET/$p")" = "200" ] && bad "可下載敏感檔案：/$p" || ok "/$p 不可下載"
done

# 1-4 備份與傾印檔
for f in backup.sql dump.sql db.sql backup.zip www.zip index.php.bak "index.php~"; do
  [ "$(code "$TARGET/$f")" = "200" ] && bad "可下載備份檔：/$f"
done

# 1-5 目錄列表
for d in / /uploads/ /files/ /storage/ /logs/ /backup/; do
  if curl -sS --max-time 10 "$TARGET$d" 2>/dev/null | grep -qiE '<title>Index of|Directory listing for'; then
    bad "目錄列表開啟：$d"
  fi
done

# 1-6 危險路徑
for p in phpinfo.php info.php adminer.php phpmyadmin/ server-status; do
  [ "$(code "$TARGET/$p")" = "200" ] && bad "危險路徑可存取：/$p"
done

echo
echo "── 二、傳輸與憑證面 ──"

# 2-1 HTTP 轉址
hcode="$(code "http://$HOST/")"
case "$hcode" in
  301|302|307|308) ok "HTTP 已轉址（$hcode）" ;;
  200)             bad "HTTP 可直接使用（未強制 HTTPS）" ;;
  *)               ok "HTTP 未提供服務（$hcode）" ;;
esac

# 2-2 憑證
certout="$(echo | openssl s_client -connect "$HOST:443" -servername "$HOST" 2>/dev/null)"
if echo "$certout" | grep -q 'Verify return code: 0'; then
  ok "憑證鏈驗證通過"
else
  bad "憑證鏈驗證失敗：$(echo "$certout" | grep 'Verify return code' | head -1)"
fi
notafter="$(echo "$certout" | openssl x509 -noout -enddate 2>/dev/null | cut -d= -f2)"
if [ -n "$notafter" ]; then
  left=$(( ( $(date -d "$notafter" +%s) - $(date +%s) ) / 86400 ))
  if [ "$left" -lt 30 ]; then bad "憑證 $left 天後到期（$notafter）"
  else ok "憑證有效天數 $left 天（$notafter）"; fi
fi

# 2-4 安全標頭
declare -A HDR_LEVEL=(
  [strict-transport-security]=P0
  [x-frame-options]=P0
  [x-content-type-options]=P1
  [content-security-policy]=P1
  [referrer-policy]=P2
)
for h in "${!HDR_LEVEL[@]}"; do
  if echo "$hdrs" | grep -qi "^$h:"; then
    ok "標頭存在：$h"
  elif [ "${HDR_LEVEL[$h]}" = "P0" ]; then
    bad "缺少標頭：$h"
  else
    warn "缺少標頭：$h（${HDR_LEVEL[$h]}）"
  fi
done

# 2-5 Cookie
setck="$(echo "$hdrs" | grep -i '^set-cookie:' || true)"
if [ -n "$setck" ]; then
  echo "$setck" | grep -qi 'secure'   && ok "Cookie 有 Secure"   || bad "Cookie 缺 Secure"
  echo "$setck" | grep -qi 'httponly' && ok "Cookie 有 HttpOnly" || bad "Cookie 缺 HttpOnly"
  echo "$setck" | grep -qi 'samesite' && ok "Cookie 有 SameSite" || warn "Cookie 缺 SameSite"
else
  echo "  [略過] 首頁未設定 cookie，請登入後手動檢查"
fi

echo
echo "=== 結果：通過 $PASS／不通過(P0) $FAIL／建議(P1-P2) $WARN ==="
[ "$FAIL" -eq 0 ]
SCRIPT

chmod +x check-baseline.sh
```

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 廠商說「不能測，會影響系統」 | 沒有事先在契約或需求書約定檢測 | 短期：改在測試環境測、書面約定時段與方式。長期：★★★★ **下次採購把資安檢測條款寫進需求書** |
| ★★★★ 廠商只給一個測試帳號 | 沒說清楚用途 | 明確要求「**兩個一般權限帳號，各有獨立測試資料**」，並說明是為了驗證存取控制。沒有兩個帳號就測不了越權 |
| ★★★★ 測試環境跟正式環境設定不一樣，測了等於白測 | 廠商在測試環境刻意調鬆或調緊 | 要求「測試環境組態應與正式環境一致」寫進需求書；上線後對正式環境**只做非破壞性的組態複查** |
| ★★★ `curl` 回 `000` 或連線逾時 | DNS 解不到、防火牆擋、目標只允許特定來源 | `dig +short <host>`、`timeout 3 bash -c 'cat < /dev/null > /dev/tcp/<ip>/443'`。若是白名單，請廠商加入你的來源 IP |
| ★★★ `curl` 回 `403` 但瀏覽器正常 | 有 WAF 擋掉了 `curl` 的 User-Agent，或需要 cookie | 加 `-A "Mozilla/5.0 ..."` 與 `-b cookie`。★★★ 這也代表 WAF 有在運作，是好事 |
| ★★★★ 掃描跑到一半系統掛了 | 請求太密集，或誤觸了破壞性功能 | **立即停止**、通知廠商與窗口、記錄時間點。之後降低併發（`--max-rate`）、避開會寫入的端點 |
| ★★★★★ 掃描時觸發大量告警，被資安單位當成攻擊 | 沒有事先通知 | 事前把**檢測時段與來源 IP** 通知資安／網管單位。這是流程問題不是技術問題 |
| ★★★ `openssl s_client -tls1` 報 `unknown option` | 你這台的 OpenSSL 已移除舊協定支援 | 這**不代表對方停用了**。改用 `testssl.sh` 或 `nmap --script ssl-enum-ciphers` |
| ★★★★ 憑證在 Chrome 正常、`curl` 卻失敗 | **中繼憑證沒裝**（Chrome 會自己補，其他客戶端不會） | `openssl s_client ... 2>&1 \| grep 'Verify return code'`，若是 `20` 就是缺鏈。要求廠商補完整鏈 |
| ★★★ 安全標頭在首頁有、在 API 路徑沒有 | 標頭只加在某個 `server` / `location` 區塊 | 檢測要**涵蓋多個路徑**：首頁、登入頁、API、靜態資源 |
| ★★★★ 廠商只修了你舉例的那一個 URL | 缺失單沒寫「一併檢視類似端點」 | 複測時**額外測 3～5 個同類型端點**（edit／delete／export／API）。缺失單寫法見「進階應用」 |
| ★★★★★ 複測時發現又冒出新問題 | 廠商為了修 A 改壞了 B，或部署了新版本 | ★★★★ **複測要跑完整清單，不是只測改過的那幾項**。用同一支腳本可以確保這件事 |
| ★★★ 抓到的都是 P1，找不到 P0，覺得白做了 | 這是**好事**，不是白做 | 出具「必過項全數通過」的結論一樣有價值 —— 這正是你證明有做檢測的紀錄 |
| ★★★★ 上級問「為什麼要擋上線」，你講不清楚 | 缺失單缺「影響」與「依據」兩欄 | 每一條 P0 都要能講出「不改會發生什麼具體後果」與「哪一條契約或法規要求」 |
| ★★★★★ 檢測發現真實個資，不小心存到自己電腦 | 蒐證時下載了整個檔案 | **只用 `curl -I` 取標頭證明可下載**。已下載的立刻 `shred -u` 並記錄處置過程 |
| ★★★ 測試帳號的 cookie 檔留在共用主機上 | 疏忽 | `shred -u` 刪除。檢測期間的暫存檔要跟證據分開存放並定期清理 |
| ★★★ 缺失報告寄出後石沉大海 | 沒有期限與複測方式 | 每張缺失單都要有**改正期限**與**複測方式**；追蹤表定期在會議上過 |

### ★★★★ 檢測遇到障礙時的處理順序

```text
1. 停下來 —— 不確定是否在授權範圍內時，一律先停
2. 記錄 —— 時間、指令、觀察到的現象
3. 通知 —— 廠商聯絡人 + 機關窗口
4. 確認 —— 是否需要調整範圍或方式，取得書面回覆
5. 再繼續
```

★★★★★ **絕對不要「先做了再說」。** 授權邊界一旦越線，
你原本是在保護機關，變成是你自己有問題。

## 安全性注意事項

> [!danger] ★★★★★ 一、授權邊界是紅線，不是建議
> 重申「觀念說明」裡那四條：
>
> 1. **只測你被授權的那個標的**。掃描時「順便發現」的其他主機一律不碰。
> 2. **正式環境不做破壞性測試**。
> 3. **沒有書面依據不做主動攻擊型測試**。
> 4. **檢測結果不外流**。
>
> ★★★★ 額外兩條實務規則：
>
> - **不要用自己的個人設備或個人網路做檢測。** 用機關的設備，
>   從機關的網段出去，這樣紀錄才是機關的紀錄。
> - **不要在下班時間偷偷測。** 有正式時段、有通知、有紀錄，才是檢測；
>   沒有這些，同樣的行為在紀錄上就是入侵。

> [!danger] ★★★★★ 二、檢測資料本身是機密
> 你的檢測產出包含：
>
> | 產物 | 為什麼敏感 |
> | --- | --- |
> | **缺失報告** | ★★★★★ 這是一份**針對這套系統的攻擊指南** |
> | **證據截圖** | 可能含真實個資 |
> | **cookie 檔** | ★★★★ 是**有效的登入憑證** |
> | **nmap 結果** | 內部網路拓撲 |
> | **原始碼與 SBOM** | 智財，且含結構資訊 |
>
> 處置規則：
>
> - 存在機關指定的位置，**不放個人雲端硬碟**。
> - 缺失報告加密或密件處理，收件人限本案相關人員。
> - ★★★★ 檢測結束後 `shred -u` 掉所有 cookie 檔與暫存檔。
> - 證據中的個資要**遮蔽**（身分證只留頭尾）。
> - 保存期限依機關檔案規定，到期依規定銷毀。

> [!warning] ★★★★ 三、蒐證要「證明可存取」而不是「取得資料」
> 要證明「未授權者可以下載全部報名資料」，
> **`curl -I` 拿到 `HTTP 200` 與 `Content-Length: 1842301` 就已經夠了。**
>
> 真的把 1.8MB 的 CSV 下載下來，你就從「檢測人員」變成「持有大量個資的人」，
> 而你的筆電不一定符合個資的儲存要求。
>
> ★★★ 需要確認內容確實是個資時：請廠商或機關窗口在場，
> 共同開啟確認一筆，做成書面紀錄，不留存檔案。

> [!warning] ★★★★ 四、發現正在被攻擊或已經被入侵怎麼辦
> 檢測時偶爾會發現這套系統**已經被種了東西**（webshell、異常排程、後門帳號）。
>
> 這時候**停止檢測，改走資安事件流程**：
>
> 1. ★★★★★ **不要自己動手清理** —— 會破壞跡證。
> 2. 立刻通報機關資安主管與資安事件應變窗口。
> 3. 保全現況（記憶體、磁碟、日誌）。
> 4. 依機關規定進行通報（時限依資安事件等級而定）。
>
> 流程見 [[090-07-04-guide-資安實踐-資安事件應變流程]]
> 與 [[090-07-15-guide-資安實踐-被入侵主機的跡證檢查]]。

> [!warning] ★★★★★ 五、憑據外洩不等驗收流程
> 如果你在原始碼、git 歷史、設定檔、或錯誤畫面上看到**正式環境的**
> 資料庫密碼、API 金鑰、憑證私鑰：
>
> **當天就要求輪替，不要等驗收會議。**
>
> 理由：這些憑據已經流通到廠商的 git、廠商員工的筆電、可能還有其他協力廠商。
> 你不知道它已經散到哪裡了。等兩週再處理，那兩週都是曝險期。
>
> 處理順序：**先輪替 → 再查有沒有異常使用紀錄 → 最後才是要求改程式。**
> 見 [[090-03-03-guide-應用安全-機密管理與金鑰保護]]。

> [!tip] ★★★★ 六、把「上線前檢測」變成制度，不要每次重新發明
> 一次性的努力價值有限。真正有效的是：
>
> | 做法 | 效果 |
> | --- | --- |
> | ★★★★★ **把檢測項目寫進需求書** | 廠商從一開始就知道要過這些，成本從驗收階段前移到開發階段 |
> | ★★★★ **把檢測清單標準化** | 每個案子用同一份，不會這次記得那次忘記 |
> | ★★★★ **把腳本納入維運工具** | 五分鐘跑完，沒有理由不做 |
> | ★★★ **檢測紀錄歸檔** | 稽核與資安健診時直接拿得出來 |
> | ★★★ **對既有系統定期複查** | 上線時通過不代表現在還通過（改版會退步） |
>
> ★★★★ 特別是最後一項：把 `check-baseline.sh` 排進月維護作業，
> 對所有對外系統跑一次。見 [[100-02-04-guide-維運-每月維護作業]]。

> [!warning] ★★★ 七、通過檢測不等於安全
> 這份清單抓的是**組態層級**的問題。它抓不到：
>
> - 業務邏輯漏洞（例如訂單金額可以改成負數）
> - 需要深入互動才觸發的注入
> - 供應鏈植入的後門
> - 未公開的 0-day
>
> ★★★★ 所以結論要寫「**所有必過項均已改正並經複測通過**」，
> **不要寫「本系統安全無虞」**。前者是事實陳述，後者是你扛不起的背書。
>
> 更深的檢測要靠契約要求的第三方滲透測試與原始碼掃描，
> 見 [[090-05-10-guide-資安設備-弱點管理與滲透測試工具]]。

> [!tip] ★★★ 八、上線之後的第一週
> 檢測通過只是起點。上線後第一週要做：
>
> - ★★★★ 確認**正式環境**的組態跟測試環境一致（跑一次腳本）
> - 確認日誌真的有在寫、有被集中收走
> - 確認監控與告警有涵蓋這套新系統
> - 確認備份真的有跑，而且**還原演練過**
>
> 見 [[090-03-04-guide-應用安全-備份災難復原與入侵應變]] 與 [[100-01-05-guide-監控-監控策略與告警設計]]。

### HTTP 狀態碼判讀

| 回應 | 對敏感路徑而言 |
| --- | --- |
| ★★★★★ `200` | **不通過** —— 拿得到 |
| `301` / `302` | 通常是轉回登入頁，★★★ 要確認轉去哪裡 |
| ★★★★ `403` | 通過 —— 明確拒絕 |
| ★★★★ `404` | 通過 —— 不存在（或刻意偽裝成不存在） |
| `401` | 通過 —— 要求認證 |
| `500` | ★★★ 不算通過。代表有東西壞了，而且可能洩漏資訊 |
| `000` | 連不上，不是結果。先排查網路 |

### 必過項一覽（P0）

| 面向 | 必過項 |
| --- | --- |
| 組態 | 除錯模式關閉、`.git`／`.env` 不可下載、無備份檔可下載、無 `phpinfo`／DB 管理介面 |
| 傳輸 | HTTPS 啟用且轉址、憑證受信任且鏈完整、cookie `Secure` + `HttpOnly` |
| 弱點 | 無 EOL 主要元件、對外元件無 Critical／High CVE |
| 帳號 | 預設密碼已改、密碼安全雜湊、無水平越權、無垂直越權 |
| 網路 | 資料庫等管理埠未對外開放 |

### 擋驗收的五個判準

| # | 判準 |
| --- | --- |
| 1 | ★★★★★ 契約或需求書明文要求 |
| 2 | ★★★★★ 法規要求（個資法、資通安全管理法等） |
| 3 | ★★★★★ 會直接導致資料外洩或系統被接管 |
| 4 | ★★★★★ 預設密碼未變更 |
| 5 | ★★★★ 使用已終止支援（EOL）的元件 |

### 缺失單必備欄位

| # | 欄位 |
| --- | --- |
| 1 | 編號與等級（P0／P1／P2） |
| 2 | 環境與檢測時間 |
| 3 | ★★★★★ 重現步驟 |
| 4 | 證據（截圖／request-response） |
| 5 | ★★★★★ 影響 |
| 6 | ★★★★★ 依據（契約條款／法規） |
| 7 | 建議修正方向（含「一併檢視類似端點」） |
| 8 | ★★★★ 改正期限與**複測方式** |

### ★★★★★ 不可以做的事

| # | 禁止事項 |
| --- | --- |
| 1 | 測試授權範圍外的任何標的 |
| 2 | 在正式環境做破壞性測試 |
| 3 | 密碼暴力破解（任何環境） |
| 4 | 無書面依據的主動注入／攻擊測試 |
| 5 | 下載真實個資到自己的設備 |
| 6 | 檢測結果外流 |
| 7 | 發現入侵跡象時自行清理 |

## 練習題

> [!question]- 練習 1：寫出你自己的授權範圍確認函
> 挑一套你手上（或即將驗收）的委外系統，寫一封範圍確認函，必須包含：
>
> 1. 受測標的（URL／IP，並明示不含哪些）
> 2. 檢測時段
> 3. 檢測方式（明列「會做」與「不會做」）
> 4. 要廠商提供的東西（★★★★ 記得要**兩個**一般權限帳號）
> 5. 緊急停止條件與聯絡方式
>
> **通過標準**：把它拿給你的主管看，主管看完知道你要做什麼、不會做什麼。

> [!question]- 練習 2：跑一次基線檢查
> 對一套**你有權限的**測試系統，跑「完整實戰範例」步驟 2 的腳本。
>
> 1. 記錄輸出。
> 2. 把每一個「不通過」項目分類成 P0 或 P1，並寫出理由。
> 3. 針對其中一個 P0，寫出完整的八欄位缺失單。
>
> **通過標準**：缺失單交給別人，對方照著「重現步驟」能重現出同樣結果。

> [!question]- 練習 3：★★★★★ 越權測試
> 用兩個一般權限的測試帳號，對一套系統做完整的越權測試：
>
> | 測試 | 指令 | 結果 |
> | --- | --- | --- |
> | 水平越權（查看） | | |
> | 水平越權（修改） | | |
> | 垂直越權（管理頁面） | | |
> | 垂直越權（管理 API） | | |
> | 登出後 session 失效 | | |
>
> **通過標準**：五項都測過並記錄狀態碼。
>
> ★★★★ **注意**：修改類的測試只能在測試環境做，而且測完要確認資料真的沒被改到。

> [!question]- 練習 4：判斷該不該擋
> 對下列每一項，判斷是 **P0（擋驗收）** 還是 **P1（列追蹤）**，並寫出理由：
>
> 1. `Server: nginx/1.18.0` 洩漏版本號
> 2. 一般使用者可以呼叫 `/api/admin/users` 並取得全部帳號清單
> 3. 缺少 `Permissions-Policy` 標頭
> 4. 系統使用 PHP 7.4
> 5. `/uploads/` 目錄列表開啟，裡面是網站的裝飾圖片
> 6. `/uploads/` 目錄列表開啟，裡面是民眾上傳的證明文件掃描檔
> 7. 管理員帳號 `admin` 密碼是 `Admin@2026#Gov`
> 8. 資料庫密碼出現在 git 歷史裡
>
> **通過標準**：每一項的理由都能對應到「五個判準」之一。

> [!question]- 練習 5：把清單變成需求書條文
> 從「必過項」清單裡挑五項，改寫成可以直接放進**需求書**的條文。
>
> 提示：需求書的寫法要**可驗證**。
> 「系統應具備良好資安防護」不可驗證；
> 「系統應停用除錯模式，錯誤畫面不得顯示程式路徑、堆疊資訊或 SQL 語句」可驗證。
>
> **通過標準**：每一條都寫得出「怎麼驗證通過」。

> [!question]- 練習 6：★★★★ 複測的完整性
> 假設廠商回報「SEC-002 水平越權已修正」。設計一份複測計畫，回答：
>
> 1. 你會測哪些 URL？（不只是缺失單裡舉例的那一個）
> 2. 你會不會重跑整份清單？為什麼？
> 3. 如果複測時發現一個**新的**問題，怎麼處理？
>
> **通過標準**：第 1 題至少列出 5 個相關端點；第 2 題答案是「會」並說得出理由。

## 小測驗

Q1. 為什麼說「上線前檢測」是維運人員擋得住問題的最後一關？
上線之後責任歸屬有什麼改變？

Q2. 檢測分成哪四類？為什麼建議按照「組態部署 → 傳輸憑證 → 弱點掃描 → 帳號權限」的順序做？

Q3. 為什麼檢測清單一定要分「必過項」與「建議項」兩級？
如果把必過項列了 40 條會發生什麼事？

Q4. 這兩行指令分別在檢查什麼？看到什麼輸出算不通過？

```bash
curl -sS -o /dev/null -w '%{http_code}\n' "$TARGET/.git/HEAD"
curl -sSI "$TARGET/" | grep -i '^set-cookie:'
```

Q5. 為什麼 `.git` 目錄可下載是沒有討論空間的 P0？
「歷史 commit」為什麼比現在的原始碼更危險？

Q6. 越權測試（IDOR）為什麼**一定要兩個同權限等級的帳號**？
測試的具體做法是什麼？

Q7. 是非題並說明理由：
「一般使用者的畫面上看不到管理選單，所以權限控制沒問題。」

Q8. 擋驗收的五個判準是什麼？請用其中一個，把「系統可以用 HTTP 直接存取」
寫成一句廠商反駁不了的話。

Q9. 你在廠商交付的原始碼 git 歷史裡發現了正式環境的資料庫密碼。
正確的處理順序是什麼？為什麼不能等驗收會議再談？

Q10. 檢測時你發現 `/storage/` 目錄列表開著，裡面有一個 `registrations.xlsx`。
為了蒐證，你應該做什麼、不應該做什麼？為什麼？

> [!question]- 測驗答案
> **Q1.** 因為**上線那一刻起，責任就從廠商轉移到機關**：
> 系統掛在機關網段、用機關的網域、出事上新聞掛的是機關的名字。
> 事後上級問的不是「廠商做了什麼」，而是「**你們驗收時檢查了什麼**」。
> 「廠商說做好了我們就收了」站不住；
> 「跑了 N 項檢測、X 項不通過、已改正並複測通過、紀錄在此」站得住。
> ★★★★ **檢測紀錄本身就是保護傘**，就算沒抓到那個漏洞也一樣。
> → 見「觀念說明 / 定位」。
>
> **Q2.** 四類是：①**組態與部署面** ②**傳輸與憑證面**
> ③**弱點掃描面** ④**帳號與權限面**。
> 順序的理由是**由外而內、由淺入深、由自動化到人工**：
> 一二類跑得最快、命中率最高（幾分鐘就能抓到多個 P0），
> 第四類最花時間、最難自動化，但**最容易造成資料外洩**，所以放最後但不能省。
> → 見「檢測分四類」。
>
> **Q3.** 因為不分級的話會陷入「這也不行那也不行」的僵局，
> 廠商會逐條談判，最後你**一條都擋不住**。
> 必過項列 40 條**等於沒有必過項** —— 必須控制在 10～15 條，
> 而且每一條都要能講出「不改會發生什麼具體後果」。
> 兩級制的價值是：**建議項讓你該記的都記下來**（稽核時證明你有看），
> **必過項讓你該擋的擋得住**（因為理由夠硬）。
> → 見「兩級制」。
>
> **Q4.** 第一行檢查 **`.git/HEAD` 是否可下載** ——
> 回 `200` 就是**不通過（P0）**，通過應該是 `403` 或 `404`。
> 第二行檢查 **`Set-Cookie` 的屬性** ——
> 少了 `secure` 或 `HttpOnly` 就是不通過（P0），少了 `SameSite` 是 P1。
> ★★★ 注意首頁的 cookie 常常不是 session cookie，**要登入後再測一次**。
> → 見「1-3」與「2-5」。
>
> **Q5.** 因為 `.git` 目錄裡是**整個專案的完整原始碼與所有歷史版本**，
> 攻擊者可以整包拉下來，取得白箱等級的優勢。
> ★★★★★ **歷史 commit 更危險**是因為：
> 開發初期常把資料庫密碼、API 金鑰寫死在程式裡，後來才拿掉 ——
> **拿掉了，但歷史紀錄還在**。所以歷史裡藏的往往是「已經被認為刪掉了」的正式憑據。
> → 見「1-3」的 danger 區塊與實戰「步驟 6」。
>
> **Q6.** 因為 IDOR 的本質是「**用 A 帳號的登入狀態去存取 B 帳號的資料**」——
> 只有一個帳號**根本測不了**。
> 做法：兩個帳號各自登入並保存 cookie（`curl -c`），
> 先用 user01 看自己的資料記下 id，
> 然後**帶著 user01 的 cookie 去請求 user02 的 id**。
> 回 `200` 且顯示對方資料 = 越權成立（P0）；回 `403`／`404` = 通過。
> ★★★★ 除了查看，還要測**修改、刪除**與**垂直越權**（打 `/admin` 與管理 API）。
> → 見「4-2」。
>
> **Q7.** **非。** 「看不到」跟「不能存取」是兩件完全不同的事。
> 很多系統只是**前端不顯示管理選單**，後端 API 根本沒檢查權限 ——
> 用 `curl` 直接打 `/admin/export` 就拿得到。
> ★★★★ 所以測試**一定要用 `curl` 直接打 API**，不能只看畫面上有沒有那個按鈕。
> 實戰「步驟 5」裡 `/admin/export` 回 `200`（可匯出全部個資）就是這種情況。
> → 見「4-2」的 warning 區塊。
>
> **Q8.** 五個判準：①**契約或需求書明文要求** ②**法規要求**
> ③**會直接導致資料外洩或系統被接管** ④**預設密碼未變更**
> ⑤**使用已終止支援（EOL）的元件**。
> 用判準①的寫法範例：
> 「需求書第 X 章第 Y 條要求系統應以 HTTPS 提供服務，
> 現況為 HTTP 可直接存取並傳輸帳號密碼，未達履約標準。」
> ★★★★★ 關鍵是「**不改會發生什麼具體後果**」——
> 講得出來就擋得住，講不出來就列建議項。
> → 見「哪些缺失可以擋驗收」。
>
> **Q9.** 順序是：①★★★★★ **立刻輪替該密碼與金鑰（當天）**
> ②要求廠商說明這份原始碼流通到哪些地方
> ③檢查該憑據有沒有異常使用紀錄
> ④**最後**才是要求改程式改用環境變數或機密管理。
> 不能等驗收會議的理由：這些憑據**已經散布到廠商的 git、員工筆電、
> 可能還有其他協力廠商**，你不知道它流到哪去了。
> 等兩週再處理，那兩週全是曝險期。
> → 見「安全性注意事項」第五條與實戰「步驟 6」。
>
> **Q10.** **應該做**：用 `curl -sSI` 只取回應標頭，
> 以 `HTTP 200` + `Content-Type` + `Content-Length` 證明「任何人可下載」，
> 這就足以構成證據。
> **不應該做**：把那個 `.xlsx` **真的下載到自己的設備上**。
> 理由是★★★★★ 那會讓你自己變成**大量個資的持有者**，
> 而你的筆電不一定符合個資的儲存要求 —— 你原本在保護機關，反而變成新的風險點。
> 若必須確認內容確實是個資，請廠商或機關窗口在場共同確認一筆並做成紀錄，不留存檔案。
> → 見實戰「步驟 4」的 warning 與「安全性注意事項」第三條。
