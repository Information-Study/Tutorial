# 應用層安全

## 這篇你會學到

> [!abstract] 學習目標
> - ★★★★★ 用**維運視角**看 OWASP Top 10：程式碼不是我寫的，那我到底能做什麼
> - ★★★★★ 五個必設的**安全標頭**：各擋什麼、怎麼設、以及**設錯會把網站弄壞在哪裡**
> - ★★★★★ CSP 的正確導入姿勢：**先 Report-Only 觀察，再切強制**，絕不一步到位
> - ★★★★ Cookie 的 `Secure`／`HttpOnly`／`SameSite` 各擋什麼，廠商程式不肯改時維運端怎麼補
> - ★★★★ 堵住資訊洩漏：版本橫幅、目錄列表、錯誤頁路徑、**`.git` 與備份檔被下載**
> - ★★★★ 上傳目錄的三道防線：副檔名、路徑穿越、**儲存位置不可執行**
> - ★★★ 用 `limit_req`／`limit_conn` 做速率限制，而且不誤擋 NAT 後面的正常使用者
> - 理解**這篇與 WAF 的分工**：這篇是應用與伺服器自己的設定，WAF 是外加的一層

### 這篇的立場：你是維運，不是開發 ★★★★★

機關的現實是這樣的：系統是三年前某家廠商做的，程式碼你沒有、有也不敢改，
維護合約可能已經到期。資安稽核送來一份掃描報告，上面十幾條紅字。
你能做的是什麼？

> **這篇教的全部是「不動應用程式一行程式碼」就能做的防護。**

所以每一項防護都會分成兩欄：

| 欄位 | 意思 |
| --- | --- |
| **開發者該修什麼** | 你要寫進「廠商改善需求單」的內容 —— 治本，但要等 |
| **維運能擋什麼** | 你今天下午就能在 Nginx／PHP 設定裡做掉的 —— 治標，但立刻生效 |

> [!warning] ★★★★ 治標不是藉口，但治標很重要
> 「這要廠商改」和「所以我什麼都不做」是兩回事。維運端的設定通常能把
> 一份掃描報告的紅字砍掉一半以上，剩下的才是真的要發文請廠商處理的。
> 而且維運端的設定**你自己說了算**、當天可以上線、出問題也是你自己回滾。

### 與 WAF 的分工 ★★★★

| 層次 | 做什麼 | 在哪一篇 |
| --- | --- | --- |
| **應用程式自己** | 輸入驗證、參數化查詢、輸出編碼、權限檢查 | 廠商的責任 |
| **應用執行環境** | PHP 的 `open_basedir`、`disable_functions`、session 設定 | [[060-03-01-06-guide-PHP-安全設定]] |
| **Web 伺服器** ← **這篇** | 安全標頭、Cookie 屬性補強、資訊隱藏、路徑封鎖、上傳目錄限制、速率限制 | ★ **本篇** |
| **WAF（外加一層）** | 用規則比對攔截攻擊 payload（SQLi、XSS、掃描器） | [[090-04-00-idx-ModSecurity]]、[[090-05-04-guide-資安設備-Web應用防火牆WAF]] |
| **網路層** | 防火牆、IPS、DDoS 防護 | [[090-05-02-guide-資安設備-防火牆與次世代防火牆]]、[[090-05-11-guide-資安設備-DDoS防護與CDN]] |

> [!tip] ★★★★ 順序建議
> **先把這篇做完，再上 WAF。** 原因是：這篇的設定是確定性的（設了就是設了、不會誤判），
> WAF 是機率性的（會誤擋、要調校）。基本功沒做好就上 WAF，等於用一層要不斷調校的東西，
> 去補一個改一行設定就能解決的洞。

## 觀念說明

### OWASP Top 10 的維運視角 ★★★★★

OWASP Top 10（2021 版）是業界最常被引用的 Web 風險清單，資安稽核報告幾乎都會對應到它。
下表把每一項拆成「開發者該修什麼」與「維運能擋什麼」。

| 編號 | 風險 | 開發者該修什麼 | ★ 維運能擋什麼（不改程式碼） |
| --- | --- | --- | --- |
| **A01** | Broken Access Control（權限控管失效） | 每個端點都做伺服器端授權檢查；不要靠隱藏 URL | ★★★ 用 Nginx 把管理後台路徑（`/admin`、`/manager`）限制來源 IP；加第二層 HTTP Basic 認證；封鎖目錄列表 |
| **A02** | Cryptographic Failures（加密失效） | 敏感資料不明文存、密碼用適當的雜湊 | ★★★★ 全站 HTTPS + HSTS（見 [[090-03-01-guide-應用安全-TLS憑證與HTTPS實務]]）；Cookie 加 `Secure`；資料庫連線加密 |
| **A03** | Injection（注入，含 SQLi、XSS、命令注入） | 參數化查詢、輸出編碼、不要拼字串 | ★★★★ **CSP** 大幅降低 XSS 的可利用性；★★★★ **WAF** 攔常見 payload；PHP `disable_functions` 擋命令執行 |
| **A04** | Insecure Design（不安全的設計） | 威脅建模、設計階段就考慮濫用情境 | ★★★ 速率限制（`limit_req`）補上「沒有設計防濫用」這一塊 |
| **A05** | **Security Misconfiguration（設定不當）** | 關掉除錯模式、移除範例檔 | ★★★★★ **這一項幾乎全部是維運的責任**：`server_tokens off`、關目錄列表、關 `display_errors`、移除預設頁與安裝程式、封鎖 `.git` 與備份檔 |
| **A06** | Vulnerable and Outdated Components（元件過舊） | 升級框架與函式庫 | ★★★★ 升級 OS 套件、PHP、Nginx；隱藏版本號降低被鎖定；用 `apt list --upgradable` 定期盤點 |
| **A07** | Identification and Authentication Failures（認證失效） | MFA、鎖定機制、安全的 session 管理 | ★★★★ 登入端點 `limit_req` 防暴力破解；★★★★ Fail2ban 封 IP（[[090-02-05-guide-防護-Fail2ban入侵防護]]）；Cookie 三屬性；接 AD／LDAP（[[090-03-05-svc-應用安全-自建服務接上AD與LDAP認證]]） |
| **A08** | Software and Data Integrity Failures（軟體與資料完整性） | 驗證更新來源、CI/CD 供應鏈防護 | ★★★ 部署來源固定為受控 git repo；檔案完整性監控（AIDE）；SRI 需要改 HTML 屬於開發端 |
| **A09** | **Security Logging and Monitoring Failures（日誌與監控不足）** | 應用內記錄安全事件 | ★★★★★ **這一項也幾乎全是維運的責任**：access／error log 保留、集中、告警。見 [[100-01-02-guide-日誌-日誌集中與輪替]] |
| **A10** | SSRF（伺服器端請求偽造） | 對外部請求做白名單 | ★★★ 從主機防火牆限制 Web 伺服器**對外**能連的目的地（egress filtering），特別是雲端 metadata 位址 |

> [!note] ★★★★ 兩個結論
> 1. **A05 與 A09 基本上是維運的事**，稽核報告上這兩類的紅字，你不能推給廠商。
> 2. 其餘各項維運都能**降低可利用性**，但不能根治。改善需求單還是要開。

### 安全標頭總覽 ★★★★★

安全標頭是「伺服器告訴瀏覽器：請幫我執行這些限制」。
特點是**成本極低、效果明確**，而且完全不需要改應用程式。

| 標頭 | 擋什麼 | 風險等級 | 弄壞網站的機率 |
| --- | --- | --- | --- |
| `Strict-Transport-Security` | SSL stripping 中間人 | ★★★★★ 不可逆 | 低（但壞了很難救） |
| `Content-Security-Policy` | XSS、資料外傳、點擊劫持 | ★★★★★ 效果最好也最容易搞砸 | ★★★★★ **高** |
| `X-Frame-Options` / CSP `frame-ancestors` | 點擊劫持（clickjacking） | ★★★★ | ★★★ 中（會擋掉合法的嵌入） |
| `X-Content-Type-Options: nosniff` | MIME 類型混淆攻擊 | ★★★ | ★★ 低（但伺服器 MIME 設錯時會顯現） |
| `Referrer-Policy` | Referer 洩漏內部 URL 與參數 | ★★★ | ★ 極低 |
| `Permissions-Policy` | 頁面（含被注入的腳本）濫用相機／麥克風／定位 | ★★ | ★★ 低（語法寫錯整條被忽略） |

★★★ 已經**不建議**再設的兩個（看到舊文件叫你設，別跟）：

| 標頭 | 為什麼不要 |
| --- | --- |
| `X-XSS-Protection` | 舊版瀏覽器的 XSS 過濾器本身曾造成漏洞，現代瀏覽器已移除該功能。要設就設 `X-XSS-Protection: 0`，或直接不設，改用 CSP |
| `Public-Key-Pins`（HPKP） | ★★★★★ 已被瀏覽器全面移除。它比 HSTS 更不可逆，設錯會讓網站永久無法存取。**絕對不要設** |

### CSP（Content-Security-Policy）★★★★★

CSP 是最有效的 XSS 緩解手段：它讓你**白名單化**「這個頁面可以從哪裡載入什麼」。
即使攻擊者成功把 `<script>` 塞進頁面，只要來源不在白名單裡，瀏覽器就不執行。

也因為它管得這麼細，**它是最容易把網站弄壞的標頭**。

常用指令：

| 指令 | 管什麼 |
| --- | --- |
| `default-src` | ★★★★ 其他 `*-src` 沒指定時的預設值 |
| `script-src` | JavaScript 從哪來 —— ★★★★★ 擋 XSS 的核心 |
| `style-src` | CSS 從哪來 |
| `img-src` | 圖片從哪來 |
| `connect-src` | `fetch`／`XMLHttpRequest`／WebSocket 可以連到哪 —— ★★★★ 擋資料外傳 |
| `font-src` | 字型從哪來 |
| `frame-src` | 頁面可以嵌入哪些來源的 iframe |
| **`frame-ancestors`** | ★★★★ **誰可以把我嵌進去** —— 取代 `X-Frame-Options` |
| `form-action` | ★★★★ 表單可以送到哪 —— 擋「表單被改成送到攻擊者網站」 |
| `base-uri` | ★★★ 限制 `<base>` 標籤，擋相對路徑劫持 |
| `object-src` | Flash／外掛物件，★★★ 現在一律設 `'none'` |
| `upgrade-insecure-requests` | 把頁內 `http://` 請求自動升級為 `https://` |
| `report-uri` / `report-to` | ★★★★★ 違規時回報到哪裡 —— 導入期的命脈 |

來源值的寫法：

| 值 | 意思 |
| --- | --- |
| `'self'` | 同源（同 scheme + host + port） |
| `'none'` | 完全禁止 |
| `https://cdn.example.tw` | 指定來源 |
| `'unsafe-inline'` | ★★★★ 允許行內 `<script>...</script>` 與 `onclick=` —— **等於放棄大半 XSS 防護** |
| `'unsafe-eval'` | ★★★★ 允許 `eval()` —— 同樣削弱防護 |
| `'nonce-<隨機值>'` | ★★★★ 只允許帶對應 nonce 的行內腳本（每次回應要換新值，需要應用程式配合） |
| `'sha256-<雜湊>'` | 只允許雜湊符合的行內腳本（適合固定不變的行內腳本） |

> [!danger] ★★★★★ CSP 一定要先跑 Report-Only
> 直接上強制模式的 CSP，結果幾乎必然是：**頁面看起來還在，但按鈕全部沒反應**。
> 因為廠商的系統裡到處是 `onclick="doSubmit()"` 這種行內事件與行內 `<script>`，
> 全部會被擋掉，而且**不會有任何錯誤畫面**，只有 Console 裡的紅字。
> 使用者只會回報「系統壞了」，你如果不知道是 CSP 造成的，會找很久。
>
> **正確流程**（三個階段，缺一不可）：
> 1. **Report-Only**：用 `Content-Security-Policy-Report-Only` 標頭。瀏覽器**照常執行**，
>    只把違規回報到你指定的端點。掛上去跑兩到四週。
> 2. **分析回報**：看看實際上載入了哪些來源，把它們加進白名單，或請廠商調整。
> 3. **切強制**：把標頭名稱改成 `Content-Security-Policy`。★★★★ 切換後盯 24～48 小時。

★★★ Report-Only 與強制模式**可以同時掛**：一個強制較寬鬆的政策，
一個 Report-Only 測試更嚴格的政策，這是逐步收緊的標準做法。

> [!warning] ★★★★ 兩個 CSP 的地雷
> 1. **`<meta http-equiv="Content-Security-Policy">` 裡的 `frame-ancestors`、`report-uri`、
>    `sandbox` 會被忽略。** 這三個**只有 HTTP 標頭形式有效**。
>    如果你看到有人說「CSP 設了但 clickjacking 還是擋不住」，多半是設在 meta 裡。
> 2. **設了兩個 CSP 標頭時，瀏覽器取「交集」不是「聯集」。** 兩份政策都要通過才放行，
>    所以多設一個只會更嚴格，不會互相覆蓋放寬。

### X-Frame-Options 與 frame-ancestors ★★★★

擋的是**點擊劫持**：攻擊者把你的網站放進一個透明 iframe，
蓋在他自己的頁面上誘導使用者點擊，使用者以為點的是 A，其實點到你網站的 B。

| 寫法 | 意思 |
| --- | --- |
| `X-Frame-Options: DENY` | ★★★★ 完全不准被嵌入 |
| `X-Frame-Options: SAMEORIGIN` | 只准同源嵌入 |
| `Content-Security-Policy: frame-ancestors 'none'` | 等同 DENY，★★★★ **現代寫法** |
| `Content-Security-Policy: frame-ancestors 'self'` | 等同 SAMEORIGIN |
| `Content-Security-Policy: frame-ancestors 'self' https://portal.example.gov.tw` | ★★★ 可以指定多個允許來源（`X-Frame-Options` 做不到） |

★★★ 兩個都設：`frame-ancestors` 給現代瀏覽器（它會優先），
`X-Frame-Options` 給極舊的瀏覽器。兩者衝突時以 CSP 為準。

> [!warning] ★★★★ 設 DENY 之前先確認沒有人在嵌入你
> 機關常見情境：某個入口網站或單一簽入平台，把你的系統用 iframe 嵌在框架裡。
> 你設了 `DENY`，那個平台當天就白畫面。
> **設之前先問**：有沒有其他系統嵌入我？搜尋一下自家其他站台的原始碼，
> 或看 access log 的 `Referer` 有沒有其他內部網域。

### X-Content-Type-Options: nosniff ★★★

瀏覽器有個「貼心」行為：伺服器回的 `Content-Type` 看起來不對時，
它會自己猜（MIME sniffing）。攻擊者可以利用這點 —— 上傳一個副檔名是 `.txt`
但內容是 JavaScript 的檔案，讓瀏覽器猜成腳本並執行。

`X-Content-Type-Options: nosniff` 就是告訴瀏覽器：**不准猜，照我說的 Content-Type 處理**。

> [!warning] ★★★ 這個標頭會「顯現」既有的 MIME 設定錯誤
> 設了 `nosniff` 之後偶爾會發生：**CSS 突然不生效、JS 突然不執行**。
> 這不是 `nosniff` 的錯，是伺服器本來就把 `.css` 回成 `text/plain`，
> 只是以前瀏覽器幫你猜對了。修法是修正 MIME 對應：
> ```bash
> grep -E "text/css|javascript" /etc/nginx/mime.types
> curl -sI https://host/css/app.css | grep -i content-type   # 應為 text/css
> ```
> 確認 `include mime.types;` 有在 `http` 區塊裡。

### Referrer-Policy ★★★

使用者從你的頁面點連結去外部網站時，瀏覽器會送 `Referer` 標頭告訴對方「我從哪來」。
問題：如果你的 URL 裡有 `?token=abc123` 或是內部系統路徑，就這樣洩漏出去了。

| 值 | 行為 | 建議 |
| --- | --- | --- |
| `no-referrer` | 完全不送 | ★★★ 最嚴，但有些分析工具與防盜連會壞 |
| `same-origin` | 只在同源送 | ★★★ 內部系統適用 |
| `strict-origin` | 只送 origin（不含路徑），且只在同等或更高安全等級 | ★★★ |
| **`strict-origin-when-cross-origin`** | 同源送完整、跨源只送 origin、降級不送 | ★★★★ **多數情況的正解**，也是現代瀏覽器的預設 |
| `unsafe-url` | 永遠送完整 URL | ★★★★ **不要用** |

### Permissions-Policy ★★

控制頁面（包含被注入的腳本、被嵌入的 iframe）可以使用哪些瀏覽器功能。
語法是結構化欄位，★★★ **寫錯的話整個標頭會被瀏覽器忽略**（不是部分忽略）。

```text
Permissions-Policy: geolocation=(), camera=(), microphone=(), payment=(), usb=()
```

- `()` 空清單 = **完全禁止**
- `(self)` = 只允許本頁面
- `(self "https://maps.example.tw")` = 本頁面加指定來源

★★★ 對一個純表單的公文系統，把相機、麥克風、定位全部關掉是零風險的正確做法。

### Cookie 的三個安全屬性 ★★★★

| 屬性 | 擋什麼 | 設錯的後果 |
| --- | --- | --- |
| **`Secure`** | ★★★★ Cookie 只在 HTTPS 送出。擋「HTTP 連線被竊聽而洩漏 session」 | 站台若還有 HTTP 頁面，那些頁面拿不到 cookie |
| **`HttpOnly`** | ★★★★★ JavaScript **讀不到**這個 cookie（`document.cookie` 看不見）。這是 XSS 偷 session 的最主要防線 | ★★★ 如果應用程式的前端 JS 真的要讀 cookie，會壞。但 session cookie 幾乎不該被 JS 讀 |
| **`SameSite`** | ★★★★ 擋 CSRF：控制 cookie 會不會在跨站請求時被送出 | ★★★★★ 設錯會造成**登入失效**，見下表 |

`SameSite` 三個值：

| 值 | 行為 | 適用 | 風險 |
| --- | --- | --- | --- |
| `Strict` | 任何跨站請求都不送 cookie（含從外部連結點進來） | 純內部、不從外部連結進入的系統 | ★★★★★ 使用者從 email 或入口網站點連結進來會**看起來像沒登入**，這是最常見的災情 |
| **`Lax`** | 跨站的**頂層導覽 GET** 會送，其他（POST、iframe、AJAX）不送 | ★★★★ **多數系統的正解**，也是現代瀏覽器的預設 | 低 |
| `None` | 一律送 | 需要被第三方嵌入的系統（SSO、金流回呼） | ★★★★★ **必須同時加 `Secure`**，否則瀏覽器直接丟棄整個 cookie |

> [!danger] ★★★★★ `SameSite=None` 沒加 `Secure` = cookie 消失
> 現代瀏覽器對 `SameSite=None` 且**沒有** `Secure` 的 cookie，會**直接拒絕儲存**。
> 症狀是「登入之後又跳回登入頁」，而且伺服器端日誌看起來一切正常。
> Console 會有警告：
> ```text
> Cookie "PHPSESSID" rejected because it has the "SameSite=None" attribute
> but is missing the "secure" attribute.
> ```

★★★★ **廠商程式沒設這些屬性時，維運端有兩條路**：

1. **PHP 應用**：改 `php.ini` 或 pool 設定，對 session cookie 全域生效（最乾淨）
2. **反向代理**：用 Nginx 的 `proxy_cookie_flags` 在回應經過時補上屬性（適用任何後端）

兩種做法在「安裝或基礎操作」都有完整範例。

### 資訊洩漏 ★★★★

攻擊的第一步是偵察。你洩漏的每一項資訊都在幫對方縮小攻擊面。

| 洩漏項目 | 怎麼被看到 | 危害 |
| --- | --- | --- |
| ★★★ Web 伺服器版本 | `Server: nginx/1.24.0 (Ubuntu)` | 對方直接查該版本的已知漏洞 |
| ★★★ PHP 版本 | `X-Powered-By: PHP/8.1.2` | 同上 |
| ★★★★ 目錄列表 | 存取沒有 index 的目錄，列出整包檔案 | 找到備份檔、設定檔、暫存檔 |
| ★★★★★ **`.git` 目錄可下載** | `https://host/.git/HEAD` 回 200 | ★★★★★ **可以還原出完整原始碼與提交歷史，包含裡面寫死的資料庫密碼** |
| ★★★★★ **備份檔可下載** | `config.php.bak`、`index.php~`、`db.sql`、`站台備份.zip` | ★★★★★ 同上，機關現場**極常見** |
| ★★★★ 錯誤頁洩漏絕對路徑 | `Fatal error: ... in /var/www/example/app/Db.php on line 42` | 得知目錄結構與框架，配合 LFI 更好利用 |
| ★★★ 錯誤頁洩漏 SQL | `SQLSTATE[42000]: Syntax error ... SELECT * FROM users WHERE ...` | ★★★★ 等於免費送上 SQL injection 的除錯訊息 |
| ★★★ `.env`、`composer.json`、`package.json` 可下載 | 直接存取 | 洩漏套件版本、環境變數、金鑰 |

> [!danger] ★★★★★ `.git` 被下載是機關現場最常見的重大缺失
> 發生原因幾乎都一樣：部署時直接在 `DocumentRoot` 底下 `git clone` 或 `git pull`，
> 於是 `/var/www/example/public/.git/` 就這樣對外可讀。
>
> 攻擊者用現成工具（`git-dumper` 之類）可以**完整還原整包原始碼**，
> 包含歷史提交裡曾經寫死、後來才拿掉的資料庫密碼與 API 金鑰。
>
> **立刻自我檢查**：
> ```bash
> curl -sI https://www.example.gov.tw/.git/HEAD | head -1
> ```
> 回 `HTTP/2 404` 或 `403` 才安全；回 `200` 就是**現在正在漏**。
> 治本是把 git 工作目錄移出 `DocumentRoot`（見 [[130-01-01-guide-部署-部署共通觀念]]）；
> 治標是立刻在 Nginx 封鎖，並且**假設密碼已外洩，全部輪換**。

### 上傳功能的風險 ★★★★

上傳是 Web 應用最危險的功能，沒有之一。三種攻擊：

| 攻擊 | 手法 | 後果 |
| --- | --- | --- |
| ★★★★★ **上傳可執行檔（webshell）** | 上傳 `shell.php`，然後直接存取 `https://host/uploads/shell.php` | ★★★★★ **完整的伺服器控制權** |
| ★★★★ 繞過副檔名檢查 | `shell.php.jpg`、`shell.pHp`、`shell.php%00.jpg`、`shell.phtml`、`.php5`、`.phar` | 同上 |
| ★★★★ 路徑穿越 | 檔名寫成 `../../../../var/www/html/x.php` | 把檔案寫到 DocumentRoot 或覆蓋既有檔案 |

**維運端最有效的一招 ★★★★★：讓上傳目錄無法執行任何動態腳本。**

即使廠商的副檔名檢查有漏洞、即使 webshell 成功上傳，只要那個目錄不會把 `.php`
交給 PHP-FPM，攻擊者拿到的就只是一個「可以下載的文字檔」。這一招不需要改程式碼，
而且是確定性的 —— 沒有繞過空間。

其他配套：

| 措施 | 做法 |
| --- | --- |
| ★★★★ 上傳目錄不在 DocumentRoot 內 | 存到 `/var/www/example/storage/`，用程式讀出來給使用者（治本，需開發配合） |
| ★★★ 限制大小 | Nginx `client_max_body_size`、PHP `upload_max_filesize` / `post_max_size` |
| ★★★ 檔案系統權限 | 上傳目錄 `chmod 750`、擁有者是 web user，且**不要有執行位元** |
| ★★★ 掃毒 | 上傳後用 ClamAV 掃（見 [[090-05-05-guide-資安設備-端點防護AV-EDR-XDR]]） |
| ★★ 正確的 Content-Type 與 nosniff | 避免瀏覽器把上傳的檔案當成腳本渲染 |

### 速率限制 ★★★

擋的不是「攻擊 payload」，而是「太多次」：暴力破解密碼、爬蟲抓資料、
掃描器狂打、單一 IP 打爆後端。

| Nginx 指令 | 限制什麼 |
| --- | --- |
| `limit_req_zone` / `limit_req` | ★★★★ **請求速率**（每秒／每分鐘幾個請求） |
| `limit_conn_zone` / `limit_conn` | ★★★ **同時連線數** |
| `limit_rate` | 每個連線的下載頻寬 |

> [!danger] ★★★★★ 在 NAT 後面的機關內網，用 IP 限流會誤擋一整個單位
> 一個單位一百人共用一個對外 IP，你設「每 IP 每分鐘 5 次登入」，
> 結果全單位每分鐘只能有 5 個人登入。這是限流最常見的災難。
>
> **對策**：
> 1. ★★★★ **只對特定端點限流**（登入、搜尋、匯出），不要對整站限流
> 2. ★★★★ **`limit_req_zone` 的 key 慎選**，並用 `geo` 把內部網段設成不限流
> 3. ★★★★ **先用 `limit_req_log_level` 觀察**，看日誌裡誰被擋、擋多少，再決定要不要真的擋
> 4. ★★★★ 站在代理後面時，一定要先用 `real_ip` 模組取回真實 IP，
>    否則所有請求的來源都是代理那一個 IP，一開限流就全站陣亡

## 安裝或基礎操作

### 先量測現況 ★★★★

改任何東西之前，先看看目前送出了什麼。

```bash
curl -sI https://www.example.gov.tw/
```

典型的「什麼都沒設」的樣子：

```text
HTTP/2 200
server: nginx/1.24.0 (Ubuntu)
date: Wed, 03 Sep 2026 01:22:41 GMT
content-type: text/html; charset=UTF-8
x-powered-by: PHP/8.1.2-1ubuntu2.14
set-cookie: PHPSESSID=8f3a...; path=/
```

四個問題一次看到：版本橫幅、PHP 版本、cookie 沒有任何安全屬性、沒有任何安全標頭。

寫成一個檢查腳本：

```bash
sudo tee /usr/local/sbin/header-check.sh > /dev/null <<'EOF'
#!/usr/bin/env bash
# 應用層安全標頭快檢
set -u
URL="${1:?用法: header-check.sh https://host/path}"
H=$(curl -sI -L "$URL")
echo "== $URL =="
chk() {
  local name="$1" want="$2"
  local line
  line=$(printf '%s' "$H" | grep -i "^${name}:" | tr -d '\r')
  if [ -n "$line" ]; then printf '  [ OK ] %s\n' "$line"
  else printf '  [MISS] %-32s <- %s\n' "$name" "$want"; fi
}
chk "strict-transport-security" "HSTS"
chk "content-security-policy"   "CSP（或 Report-Only）"
chk "x-frame-options"           "點擊劫持防護"
chk "x-content-type-options"    "應為 nosniff"
chk "referrer-policy"           "建議 strict-origin-when-cross-origin"
chk "permissions-policy"        "關閉不需要的瀏覽器功能"

echo "-- 洩漏檢查 --"
printf '%s' "$H" | grep -iE '^(server|x-powered-by|x-aspnet-version):' | tr -d '\r' \
  | sed 's/^/  [LEAK] /' || echo "  [ OK ] 無版本橫幅"

echo "-- Cookie 屬性 --"
printf '%s' "$H" | grep -i '^set-cookie:' | tr -d '\r' | while read -r c; do
  miss=""
  echo "$c" | grep -qi 'httponly'  || miss="$miss HttpOnly"
  echo "$c" | grep -qi 'secure'    || miss="$miss Secure"
  echo "$c" | grep -qi 'samesite'  || miss="$miss SameSite"
  if [ -n "$miss" ]; then printf '  [MISS]%s <- %s\n' "$miss" "${c:0:60}..."
  else printf '  [ OK ] %s\n' "${c:0:60}..."; fi
done
EOF
sudo chmod +x /usr/local/sbin/header-check.sh
sudo /usr/local/sbin/header-check.sh https://www.example.gov.tw/
```

預期輸出（改善前）：

```text
== https://www.example.gov.tw/ ==
  [ OK ] strict-transport-security: max-age=31536000
  [MISS] content-security-policy          <- CSP（或 Report-Only）
  [MISS] x-frame-options                  <- 點擊劫持防護
  [MISS] x-content-type-options           <- 應為 nosniff
  [MISS] referrer-policy                  <- 建議 strict-origin-when-cross-origin
  [MISS] permissions-policy                <- 關閉不需要的瀏覽器功能
-- 洩漏檢查 --
  [LEAK] server: nginx/1.24.0 (Ubuntu)
  [LEAK] x-powered-by: PHP/8.1.2-1ubuntu2.14
-- Cookie 屬性 --
  [MISS] HttpOnly Secure SameSite <- set-cookie: PHPSESSID=8f3a...; path=/...
```

> [!tip] ★★★ 也用線上工具交叉驗證
> <https://securityheaders.com>（給一個 A～F 等級，稽核愛引用）與
> Mozilla Observatory（<https://developer.mozilla.org/en-US/observatory>）。
> ★★★ 內網站台這兩個掃不到，就靠上面的腳本。

### 設定安全標頭（Nginx 主線）★★★★★

把標頭集中在一個檔案，各站台 `include` 進去。

```bash
sudo tee /etc/nginx/snippets/security-headers.conf > /dev/null <<'EOF'
# ── 應用層安全標頭 ─────────────────────────────────────────
# ★★★★ 每一行都要有 always，否則 4xx/5xx 錯誤頁不會帶標頭

# 點擊劫持：兩個都設，現代瀏覽器以 CSP frame-ancestors 為準
add_header X-Frame-Options "SAMEORIGIN" always;

# 禁止 MIME sniffing
add_header X-Content-Type-Options "nosniff" always;

# Referer 洩漏控制
add_header Referrer-Policy "strict-origin-when-cross-origin" always;

# 關閉用不到的瀏覽器功能（語法錯誤會讓整個標頭被忽略）
add_header Permissions-Policy "geolocation=(), camera=(), microphone=(), payment=(), usb=()" always;

# 明確關閉舊的 XSS 過濾器（不要設成 1）
add_header X-XSS-Protection "0" always;
EOF
```

在站台設定裡引用：

```nginx
server {
    listen 443 ssl;
    server_name www.example.gov.tw;
    # ... TLS 設定見 090-03-01 ...

    include snippets/security-headers.conf;
    add_header Strict-Transport-Security "max-age=31536000" always;

    root /var/www/example/public;
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
sudo /usr/local/sbin/header-check.sh https://www.example.gov.tw/
```

> [!danger] ★★★★★ Nginx `add_header` 不繼承 —— 最容易踩的坑
> **只要某個 `location` 裡出現任何一個 `add_header`，父層（`server`／`http`）的
> 所有 `add_header` 就全部失效。** 不是覆蓋同名的那一個，是**整組消失**。
>
> ```nginx
> server {
>     include snippets/security-headers.conf;      # 六個標頭
>
>     location ~ \.php$ {
>         add_header X-Debug "1" always;           # ★★★★★ PHP 頁面沒有任何安全標頭了
>         fastcgi_pass unix:/run/php/php8.1-fpm.sock;
>     }
> }
> ```
>
> **這一題最可怕的地方是：你的靜態首頁測起來完全正常。** 動態頁面（也就是真正有風險的頁面）
> 才是沒有標頭的那些。
>
> **兩個解法**：
> 1. 在每個有 `add_header` 的 `location` 裡**再 `include` 一次** `security-headers.conf`
> 2. ★★★★ 改用 `ngx_headers_more` 模組的 `more_set_headers`（**行為是累加的**）：
>    `sudo apt install nginx-extras`（Ubuntu 的 `nginx-extras` 套件含此模組）
>
> **驗證方式**：★★★★★ 不要只測首頁，要**逐路徑**測。
> ```bash
> for p in / /index.php /login.php /api/status /nonexistent-404; do
>   echo "--- $p"
>   curl -sI "https://www.example.gov.tw$p" | grep -icE '^(x-frame|x-content|referrer|permissions)'
> done
> ```
> 每一行都應該回 `4`（四個標頭都在）。回 `0` 的那個路徑就是有 `add_header` 覆蓋問題。

> [!info]- Apache 對照
> Apache 的 `Header` 指令**是繼承累加的**，沒有 Nginx 那個坑，但要先啟用 `mod_headers`。
> ```apache
> # /etc/apache2/conf-available/security-headers.conf
> <IfModule mod_headers.c>
>     Header always set X-Frame-Options "SAMEORIGIN"
>     Header always set X-Content-Type-Options "nosniff"
>     Header always set Referrer-Policy "strict-origin-when-cross-origin"
>     Header always set Permissions-Policy "geolocation=(), camera=(), microphone=()"
>     Header always set X-XSS-Protection "0"
>     Header always unset X-Powered-By
>     Header always unset Server
> </IfModule>
> ```
> ```bash
> sudo a2enmod headers
> sudo a2enconf security-headers
> sudo apachectl configtest    # 預期：Syntax OK
> sudo systemctl reload apache2
> ```
> ★★★ `Header always unset Server` 在 Apache 上**只能移除自己加的**，
> 要真正改掉 `Server` 橫幅得用 `ServerTokens Prod`（見下一節）。
> ★★ `.htaccess` 裡也能寫 `Header`，但要 `AllowOverride FileInfo` 才生效，
> 而且效能較差 —— 能寫在 vhost 就寫在 vhost。

## 進階應用

上一節的六個標頭是「設了就好、幾乎不會出事」的部分。
這一節開始的每一項，都**有機會把網站弄壞** —— CSP、Cookie 屬性、上傳目錄封鎖、速率限制。
共同的原則只有一條 ★★★★★：**先觀察、再強制，而且回滾方式要事先演練過。**

### CSP 導入：先 Report-Only ★★★★★

**階段一：掛上 Report-Only，什麼都不擋。**

```nginx
    # ★★★★★ 注意標頭名稱是 -Report-Only，瀏覽器只回報不阻擋
    add_header Content-Security-Policy-Report-Only
        "default-src 'self'; img-src 'self' data:; style-src 'self'; script-src 'self'; frame-ancestors 'self'; report-uri /csp-report" always;
```

建立一個收集端點。最省事的做法：讓 Nginx 直接把 POST 內容寫進日誌。

```nginx
    # CSP 違規回報收集
    location = /csp-report {
        access_log /var/log/nginx/csp-report.log csplog;
        # 回 204 讓瀏覽器不要重試
        return 204;
    }
```

在 `http` 區塊定義對應的日誌格式：

```nginx
log_format csplog escape=json '{"time":"$time_iso8601","ua":"$http_user_agent",'
                              '"referer":"$http_referer","body":$request_body}';
```

★★★★ 要記錄 POST body 必須加 `client_body_buffer_size` 並確保 body 被讀進來。
更穩妥的做法是用一個小端點接收：

```nginx
    location = /csp-report {
        client_body_buffer_size 32k;
        client_max_body_size    32k;
        access_log /var/log/nginx/csp-report.log csplog;
        proxy_pass http://127.0.0.1:9;   # 丟給 discard 埠，只為了讓 Nginx 讀取 body
        proxy_intercept_errors on;
        error_page 502 504 = @csp_ok;
    }
    location @csp_ok { return 204; }
```

> [!warning] ★★★ 這個 Nginx-only 的收集法有點取巧
> 更正統的做法是寫一支幾行的 PHP 或 Node 端點把 JSON 存起來，
> 或用外部的 CSP 回報服務。★★★ 重點不是收集手法多漂亮，
> 是**你真的有在看回報內容**。收集了三週沒人看，跟沒收集一樣。

**階段二：分析回報。** 跑兩到四週後：

```bash
# 看被擋到的指令與來源
jq -r '.body' /var/log/nginx/csp-report.log 2>/dev/null \
  | jq -r '."csp-report" | "\(."violated-directive")  \(."blocked-uri")"' \
  | sort | uniq -c | sort -rn | head -30
```

典型輸出（廠商系統的真實樣貌）：

```text
   4821 script-src-elem  inline
   1203 style-src-attr   inline
    612 img-src          https://www.google-analytics.com
    311 script-src-elem  https://cdn.jsdelivr.net
     47 connect-src      https://api.example-vendor.com
```

判讀 ★★★★：

| 回報內容 | 意思 | 怎麼處理 |
| --- | --- | --- |
| `blocked-uri: inline` + `script-src` | 頁面有行內 `<script>` 或 `onclick=` | ★★★★★ 這是最麻煩的。治本要請廠商改成外部 JS 或用 nonce；治標只能加 `'unsafe-inline'`（防護力大減） |
| `blocked-uri: <某個 CDN>` | 頁面從外部 CDN 載入資源 | ★★★ 確認是合法的就加進白名單 |
| `blocked-uri: <沒見過的網域>` | ★★★★★ 可能是**已經被植入的惡意腳本**，或第三方追蹤 | ★★★★★ 立刻查！這是 CSP 的意外收穫 —— 它會幫你抓到已存在的入侵 |
| `violated-directive: connect-src` | 有 AJAX 連到外部 | 確認是不是資料外傳 |

**階段三：切強制。**

```nginx
    # 依 Report-Only 觀察結果調整出來的政策
    add_header Content-Security-Policy
        "default-src 'self'; script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self' data:; connect-src 'self'; frame-ancestors 'self'; form-action 'self'; base-uri 'self'; object-src 'none'; upgrade-insecure-requests" always;
```

```bash
sudo nginx -t && sudo systemctl reload nginx
curl -sI https://www.example.gov.tw/ | grep -i content-security
```

> [!danger] ★★★★★ 切強制模式後的 48 小時
> - 準備好一鍵回滾：把整行改回 `-Report-Only` 再 reload，10 秒完成
> - 主動去點過系統的**每一個主要功能**（登入、查詢、送出表單、上傳、列印、匯出）
> - 開瀏覽器 Console 看有沒有 `Refused to ...` 的紅字
> - ★★★★ 告知服務台「今天有變更，接到『按鈕沒反應』的通報立刻找我」
>
> 症狀特徵：**頁面正常顯示，但互動功能失效，且沒有錯誤畫面。**
> 使用者不會說「CSP 擋住了」，他們會說「系統怪怪的」。

> [!tip] ★★★ 務實的目標
> 對一套廠商交付的舊系統，能做到
> `default-src 'self'` + `'unsafe-inline'` + `frame-ancestors 'self'` + `object-src 'none'`
> **就已經比原本好非常多**了 —— 至少擋掉了「載入外部惡意腳本」與「資料送到外部」。
> 追求完美的 nonce-based CSP 需要改程式碼，那是改善需求單的事，不是今天下午的事。

### Cookie 屬性補強 ★★★★

**做法一：PHP 全域設定（最乾淨，適用 PHP 應用）。**

```bash
# 找出目前生效的 php.ini
php -i | grep "Loaded Configuration File"
```
```text
Loaded Configuration File => /etc/php/8.1/fpm/php.ini
```

```bash
sudo tee /etc/php/8.1/fpm/conf.d/99-session-security.ini > /dev/null <<'EOF'
; session cookie 安全屬性
session.cookie_secure   = 1        ; 只在 HTTPS 送出
session.cookie_httponly = 1        ; JS 讀不到
session.cookie_samesite = Lax      ; 擋 CSRF；需要被第三方嵌入才改 None（並保持 Secure=1）
session.use_strict_mode = 1        ; 拒絕未經伺服器產生的 session id（擋 session fixation）
session.use_only_cookies = 1       ; 不接受 URL 帶 session id
EOF

sudo systemctl reload php8.1-fpm
php-fpm8.1 -i 2>/dev/null | grep -E "session.cookie_(secure|httponly|samesite)"
```

驗證：

```bash
curl -sI https://www.example.gov.tw/ | grep -i set-cookie
```
```text
set-cookie: PHPSESSID=9c1f...; path=/; secure; HttpOnly; SameSite=Lax
```

**做法二：Nginx 反向代理時補上（適用任何後端，Nginx ≥ 1.19.3）★★★★。**

```nginx
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 對所有 Set-Cookie 補上安全屬性
        proxy_cookie_flags ~ secure httponly samesite=lax;
    }
```

`~` 是「比對所有 cookie 名稱」的正規表示式。要只針對特定 cookie：

```nginx
        proxy_cookie_flags JSESSIONID secure httponly samesite=lax;
```

> [!info]- Apache 對照
> Apache 用 `mod_headers` 的 `edit` 直接改寫 `Set-Cookie`：
> ```apache
> Header always edit Set-Cookie ^(.*)$ "$1; HttpOnly; Secure; SameSite=Lax"
> ```
> ★★★ 這是純字串串接，**如果後端已經帶了 `HttpOnly`，會變成重複的屬性**。
> 瀏覽器通常容忍重複，但看起來很醜。要精確一點可以先判斷：
> ```apache
> Header always edit Set-Cookie "(?i)^((?:(?!;\s?HttpOnly).)+)$" "$1; HttpOnly"
> Header always edit Set-Cookie "(?i)^((?:(?!;\s?Secure).)+)$" "$1; Secure"
> ```
> PHP 應用一律優先用 `php.ini` 的做法，不要繞這一圈。

### 保護上傳目錄 ★★★★★

```nginx
server {
    root /var/www/example/public;

    # 一般 PHP 處理
    location ~ \.php$ {
        try_files $uri =404;                      # ★★★★ 防 path info 攻擊，不可省
        fastcgi_pass unix:/run/php/php8.1-fpm.sock;
        fastcgi_index index.php;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }

    # ★★★★★ 上傳目錄：任何動態腳本一律不執行
    # ^~ 讓這個前綴比對優先於上面的正規表示式 location
    location ^~ /uploads/ {
        # 巢狀 location：這裡的 .php 不會被送去 PHP-FPM
        location ~ \.(php|phtml|php[0-9]|phar|pl|py|cgi|asp|aspx|jsp|sh)$ {
            deny all;
            return 403;

        # 強制以附件下載，避免瀏覽器渲染
        add_header Content-Disposition "attachment" always;
        add_header X-Content-Type-Options "nosniff" always;
        # ★★★★ 這裡有 add_header，父層標頭會失效，所以要補回來
        include snippets/security-headers.conf;
        try_files $uri =404;
    }

    client_max_body_size 20m;                     # 與 PHP 的 upload_max_filesize 對齊
}
```

### 速率限制 ★★★

```nginx
# ── http 區塊 ────────────────────────────────────────────
# 先取回真實 IP（在代理／LB 後面時必做）
set_real_ip_from 10.0.0.0/24;        # ★★★★ 只列你的代理，不要 0.0.0.0/0
real_ip_header X-Forwarded-For;
real_ip_recursive on;

# 內部網段不限流
geo $limit_exempt {
    default        0;
    10.0.0.0/8     1;
    172.16.0.0/12  1;
    192.168.0.0/16 1;
}
map $limit_exempt $limit_key {
    0 $binary_remote_addr;
    1 "";                             # 空字串 = 不計入限流
}

limit_req_zone  $limit_key zone=general:10m rate=30r/s;
limit_req_zone  $limit_key zone=login:10m   rate=10r/m;
limit_conn_zone $limit_key zone=perip:10m;

limit_req_status  429;                # 預設是 503，429 語意更正確
limit_conn_status 429;
limit_req_log_level warn;             # ★★★★ 觀察期靠這個
```

```nginx
# ── server 區塊 ─────────────────────────────────────────
server {
    limit_conn perip 30;

    location / {
        limit_req zone=general burst=60 nodelay;
        # ...
    }

    # ★★★★ 只對登入端點嚴格限流
    location = /login.php {
        limit_req zone=login burst=5 nodelay;
        include snippets/security-headers.conf;   # 有 limit_req 沒關係，但別忘了 add_header 規則
        fastcgi_pass unix:/run/php/php8.1-fpm.sock;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }
}
```

`burst` 與 `nodelay` 的意思 ★★★★（這兩個最常被誤解）：

| 設定 | 行為 |
| --- | --- |
| `limit_req zone=login;`（無 burst） | 超過速率的請求**立刻**回 429。★★★ 太嚴格，正常使用者也會中 |
| `limit_req zone=login burst=5;` | 允許 5 個請求排隊**慢慢放行**（會有延遲） |
| `limit_req zone=login burst=5 nodelay;` | ★★★★ 允許 5 個請求**立刻**通過，之後才按速率限制。**通常是你要的** |

**觀察期做法 ★★★★★：先只記錄不阻擋。** Nginx 沒有 dry-run 模式，
但你可以把速率設得很寬鬆，先從日誌看誰會撞上：

```bash
# 誰被限流了
grep "limiting requests" /var/log/nginx/error.log \
  | grep -oE 'client: [0-9.]+' | sort | uniq -c | sort -rn | head -20
```

典型輸出：

```text
    412 client: 203.0.113.77      ← 掃描器或爬蟲，該擋
     38 client: 10.20.30.1        ← ★★★★ 這是某單位的 NAT 出口，誤擋了
```

看到內部 NAT 出口就要把它加進 `geo` 的豁免清單，或改用其他 key。

`error.log` 的原始訊息長這樣：

```text
2026/09/03 09:14:22 [warn] 1234#1234: *5678 limiting requests, excess: 5.320 by zone "login",
client: 203.0.113.77, server: www.example.gov.tw, request: "POST /login.php HTTP/2.0", host: "www.example.gov.tw"
```

★★★ 把它接給 Fail2ban，撞太多次就直接在防火牆層封掉 ——
見 [[090-02-05-guide-防護-Fail2ban入侵防護]]。

> [!tip] ★★★ 限流不是 DDoS 防護
> `limit_req` 擋的是「單一來源打太快」。真正的分散式攻擊來源成千上萬，
> 每個都不快，`limit_req` 完全擋不住。那是 CDN／清洗中心的工作，
> 見 [[090-05-11-guide-資安設備-DDoS防護與CDN]]。

### CORS 的正確設法 ★★★

只有在**真的需要**跨網域呼叫 API 時才開，不需要就不要設任何 CORS 標頭。

```nginx
    location /api/ {
        # ★★★★★ 絕對不要寫 add_header Access-Control-Allow-Origin "*";
        # 白名單比對
        set $cors_origin "";
        if ($http_origin ~* ^https://(portal|app)\.example\.gov\.tw$) {
            set $cors_origin $http_origin;
        }
        add_header Access-Control-Allow-Origin      $cors_origin always;
        add_header Access-Control-Allow-Credentials "true" always;
        add_header Access-Control-Allow-Methods     "GET, POST, OPTIONS" always;
        add_header Access-Control-Allow-Headers     "Content-Type, Authorization" always;
        add_header Vary "Origin" always;      # ★★★★ 沒有這行會造成快取污染
        include snippets/security-headers.conf;

        if ($request_method = OPTIONS) { return 204; }

        proxy_pass http://127.0.0.1:8080;
    }
```

三個重點 ★★★★：

1. **`Access-Control-Allow-Origin: *` 與 `Allow-Credentials: true` 不能並存** ——
   瀏覽器會直接拒絕。想帶 cookie 就必須回具體的 origin。
2. **`Vary: Origin` 不可省**。沒有它，CDN 或反向代理會把「給 A 網域的回應」
   快取起來發給 B 網域，等於白名單失效。
3. ★★★★ 不要用 `if ($http_origin ~ example)` 這種鬆散比對 ——
   `evil-example.gov.tw.attacker.com` 會通過。要錨定 `^...$`。

## 完整實戰範例

**情境**：機關委外開發的 PHP 線上申辦系統 `www.example.gov.tw`，
廠商維護合約已到期，原始碼在但沒人敢動。
資安健檢報告送來八項缺失。目標：**不改一行程式碼**，處理掉能處理的。

健檢報告摘要：

| # | 缺失 | 等級 |
| --- | --- | --- |
| 1 | 洩漏 Web 伺服器與 PHP 版本 | 低 |
| 2 | 缺少安全標頭（X-Frame-Options、nosniff、CSP 等） | 中 |
| 3 | Session Cookie 未設 HttpOnly／Secure／SameSite | 中 |
| 4 | `/.git/` 目錄可存取 | **高** |
| 5 | 存在可下載的備份檔 `config.php.bak` | **高** |
| 6 | 錯誤訊息洩漏系統絕對路徑 | 中 |
| 7 | 上傳目錄可執行 PHP | **高** |
| 8 | 登入頁無防暴力破解機制 | 中 |

### 步驟 0：建立基準與退路

```bash
# 記錄改善前的狀態

```

### 步驟 1：先處理三個「高」等級（★★★★★ 這三項今天就要做完）

**1-1 封鎖 `.git` 與備份檔。**

```bash
# 先確認嚴重程度
curl -s -o /dev/null -w '%{http_code}\n' https://www.example.gov.tw/.git/HEAD
curl -s -o /dev/null -w '%{http_code}\n' https://www.example.gov.tw/config.php.bak
```

★★★★★ 兩個都是 200 —— 原始碼與設定檔正在對外開放。

```bash
# 套用封鎖片段（內容見「隱藏資訊洩漏」一節）
sudo cp /etc/nginx/snippets/deny-sensitive.conf /etc/nginx/snippets/ 2>/dev/null || true
sudo sed -i '/include snippets\/security-headers.conf;/i\    include snippets/deny-sensitive.conf;' \
  /etc/nginx/sites-available/example.conf
sudo nginx -t && sudo systemctl reload nginx

for p in /.git/HEAD /config.php.bak /.env; do
  printf '%-20s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' https://www.example.gov.tw$p)"
done
```
```text

/config.php.bak      404
/.env                404
```

**1-2 追查外洩範圍並輪換密碼。★★★★★**

```bash
# 有沒有人下載過？

sudo grep "/\.git/" /var/log/nginx/*access*.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
```

有記錄就代表已經外洩。查出 `config.php` 裡的資料庫密碼，全部輪換：

```bash
sudo grep -iE "password|passwd|secret|key" /var/www/example/config.php
```
★★★★★ 找到的每一組憑證都要換。做法見 [[090-03-03-guide-應用安全-機密管理與金鑰保護]]。

**1-3 移出 git 目錄與備份檔（治本）。**

```bash
# 把 .git 搬到 DocumentRoot 之外
sudo mv /var/www/example/public/.git /var/lib/deploy/example.git
# 刪掉散落的備份檔
sudo find /var/www/example -maxdepth 3 \
  \( -name '*.bak' -o -name '*~' -o -name '*.orig' -o -name '*.sql' \) -ls
# 確認清單無誤後再刪
```

**1-4 鎖死上傳目錄。**

```bash
# 先確認現在真的可執行
echo '<?php echo "PWNED"; ?>' | sudo tee /var/www/example/public/uploads/t.php > /dev/null
curl -s https://www.example.gov.tw/uploads/t.php
```
```text
PWNED
```
★★★★★ 確認漏洞存在。套用設定：

```bash
# 把「保護上傳目錄」一節的 location ^~ /uploads/ 加進站台設定
sudo nginx -t && sudo systemctl reload nginx
curl -s -o /dev/null -w '%{http_code}\n' https://www.example.gov.tw/uploads/t.php
```
```text
403
```
```bash
sudo rm -f /var/www/example/public/uploads/t.php
```

### 步驟 2：安全標頭與版本隱藏

```bash
# 建立標頭片段（內容見前面）與引用
sudo nginx -t && sudo systemctl reload nginx

# 隱藏版本
sudo sed -i '/^http {/a\    server_tokens off;' /etc/nginx/nginx.conf
echo "expose_php = Off" | sudo tee /etc/php/8.1/fpm/conf.d/99-expose.ini
sudo nginx -t && sudo systemctl reload nginx && sudo systemctl reload php8.1-fpm
```

★★★★★ **逐路徑驗證**（不要只測首頁）：

```bash
for p in / /index.php /login.php /uploads/ /nope-404; do
  n=$(curl -sI "https://www.example.gov.tw$p" \
      | grep -icE '^(x-frame-options|x-content-type-options|referrer-policy|permissions-policy)')
  printf '%-16s 安全標頭數=%s\n' "$p" "$n"
done
```

預期輸出：

```text
/                安全標頭數=4
/index.php       安全標頭數=4
/login.php       安全標頭數=4
/uploads/        安全標頭數=4
/nope-404        安全標頭數=4
```

★★★★ 如果 `/index.php` 那行是 `0`，就是 `location ~ \.php$` 裡有 `add_header`
把父層蓋掉了 —— 回去在那個 location 裡補 `include snippets/security-headers.conf;`。

### 步驟 3：Cookie 屬性

```bash
sudo tee /etc/php/8.1/fpm/conf.d/99-session-security.ini > /dev/null <<'EOF'
session.cookie_secure   = 1
session.cookie_httponly = 1
session.cookie_samesite = Lax
session.use_strict_mode = 1
session.use_only_cookies = 1
EOF
sudo systemctl reload php8.1-fpm

# 驗證
curl -sI -c /dev/null https://www.example.gov.tw/login.php | grep -i set-cookie
```
```text
set-cookie: PHPSESSID=3b7e...; path=/; secure; HttpOnly; SameSite=Lax
```

★★★★ 改完**一定要親自登入一次**。如果系統從外部入口網站連進來，
`SameSite=Lax` 通常沒問題；若被 iframe 嵌入或有 SSO 回呼，可能需要 `None`（並保持 `Secure`）。

### 步驟 4：錯誤頁

```bash
sudo tee /etc/php/8.1/fpm/conf.d/99-errors.ini > /dev/null <<'EOF'
display_errors = Off
display_startup_errors = Off

error_log = /var/log/php/error.log
html_errors = Off
EOF
sudo mkdir -p /var/log/php && sudo chown www-data:www-data /var/log/php

# 加上 fastcgi_intercept_errors 與自訂錯誤頁（見前面）

# 驗證：故意打一個會出錯的參數，看回應裡有沒有路徑
curl -s "https://www.example.gov.tw/query.php?id=%27" | grep -iE "/var/www|Fatal error|SQLSTATE" \
  && echo "★★★★ 仍有洩漏" || echo "OK：無路徑或 SQL 洩漏"
```
```text
OK：無路徑或 SQL 洩漏
```

```bash
  curl -s -o /dev/null -w '%{http_code} ' -X POST https://www.example.gov.tw/login.php
```

★★★★ 觀察一週。若名單裡出現內部 NAT 出口，加進 `geo` 豁免。

### 步驟 6：CSP Report-Only（★★★★★ 這一項要跑最久）

## 常見錯誤與排錯

| # | 現象 | 原因 | 解法 |
| --- | --- | --- | --- |
| 1 | ★★★★★ 上了 CSP 之後，頁面看起來正常但**按鈕全部沒反應**，沒有錯誤畫面 | 系統有大量行內 `<script>` 與 `onclick=`，被 `script-src` 擋掉。Console 會有 `Refused to execute inline script because it violates the following Content Security Policy directive` | 立刻改回 `Content-Security-Policy-Report-Only` 回滾；重新走 Report-Only 觀察流程，把必要來源加進白名單或暫時加 `'unsafe-inline'` |
| 2 | ★★★★ CSP 設好了但**點擊劫持還是擋不住** | `frame-ancestors` 設在 `<meta>` 標籤裡 —— 該指令**只有 HTTP 標頭形式有效** | 改用 Nginx `add_header` 送出，或同時設 `X-Frame-Options` |
| 3 | ★★★★★ 首頁的安全標頭正常，但 `/index.php` 或 `/api/` **完全沒有標頭** | Nginx `add_header` 不繼承：子 `location` 有任何 `add_header` 就讓父層整組失效 | 在該 `location` 內 `include snippets/security-headers.conf;`，或改用 `ngx_headers_more` 的 `more_set_headers`。★★★★★ 一定要**逐路徑** `curl -sI` 驗證 |
| 4 | ★★★ 404／500 錯誤頁沒有安全標頭 | `add_header` 少了 `always` | 全部加上 `always` |
| 5 | ★★★★★ 設了 `SameSite=Strict` 後，使用者從入口網站或 email 連結點進來**看起來像沒登入** | `Strict` 連跨站的頂層導覽都不送 cookie | 改成 `Lax`（多數系統的正解） |
| 6 | ★★★★★ 改成 `SameSite=None` 後，**登入完立刻跳回登入頁**，伺服器日誌卻正常 | `SameSite=None` **必須**同時有 `Secure`，否則瀏覽器直接丟棄 cookie。Console 有 `rejected because it has the "SameSite=None" attribute but is missing the "secure" attribute` | 加上 `session.cookie_secure = 1`（且站台必須是 HTTPS） |
| 7 | ★★★ 設 `HttpOnly` 後某個前端功能壞掉 | 應用程式的 JS 真的在用 `document.cookie` 讀那個 cookie | 確認是不是 session cookie。若是非敏感的 UI 偏好 cookie，只對 session cookie 設 `HttpOnly`（用 `proxy_cookie_flags <名稱>` 精確指定） |
| 8 | ★★★ 設 `X-Content-Type-Options: nosniff` 後，**CSS 不生效或 JS 不執行** | 伺服器把 `.css`／`.js` 回成錯誤的 Content-Type（如 `text/plain`），以前靠瀏覽器猜對 | 檢查 `include mime.types;` 是否在 `http` 區塊；`curl -sI https://host/css/app.css \| grep -i content-type` 應為 `text/css` |
| 9 | ★★★★ 設 `X-Frame-Options: DENY` 後，某個入口平台的頁面變白畫面 | 那個平台用 iframe 嵌入你的系統 | 改用 `frame-ancestors 'self' https://portal.example.gov.tw`（`X-Frame-Options` 無法指定多來源） |
| 10 | ★★★ `Permissions-Policy` 設了但完全沒作用 | 語法錯誤（例如寫成 `geolocation 'none'` 而不是 `geolocation=()`），整個標頭被瀏覽器忽略 | 用 `名稱=()` 或 `名稱=(self)` 的結構化語法，用瀏覽器 Console 確認沒有 parse 警告 |
| 11 | ★★★★★ **限流上線後整個單位都連不上**，全部回 429 | 該單位在 NAT 後面共用一個對外 IP；或站台在代理後面沒設 `real_ip`，所有請求算同一個 IP | 用 `geo` 把內部網段設為豁免；設定 `set_real_ip_from` / `real_ip_header` 取回真實 IP；先看 `grep "limiting requests" error.log` 找出誰被擋 |
| 12 | ★★★ 限流設了但完全沒作用 | `limit_req_zone` 定義在 `http` 但站台的 `location` 沒有寫 `limit_req`；或 zone 名稱打錯 | `nginx -T \| grep -n limit_req` 確認兩邊都有；`nginx -t` 對不存在的 zone 會報 `unknown limit_req_zone` |
| 13 | ★★★★★ `curl https://host/.git/HEAD` 回 200 | 部署時直接在 DocumentRoot 底下 `git clone` | 立刻用 `location ~ /\.` 封鎖；把 `.git` 移出 DocumentRoot；★★★★★ **假設密碼已外洩，全部輪換** |
| 14 | ★★★★★ 上傳一個 `.php` 到 `/uploads/` 竟然執行了 | `location ^~ /uploads/` 沒設，或優先權被 `location ~ \.php$` 搶走 | 用 `^~` 前綴 + 巢狀 `location ~ \.php$ { deny all; }`；★★★★★ **實測**放一個 test.php 打打看，回 403 才算數 |
| 15 | ★★★★ 封鎖點開頭檔案後，**Certbot 續期失敗** | `location ~ /\.` 把 `/.well-known/acme-challenge/` 也擋了 | 用 `location ~ /\.(?!well-known/)` 排除，或另外加一個 `location ^~ /.well-known/acme-challenge/` |
| 16 | ★★★ `curl -sI` 看不到 `Server` 標頭消失 | `server_tokens off` 只拿掉版本號，`nginx` 字樣仍在 | 要完全移除需 `ngx_headers_more`（`apt install nginx-extras`）的 `more_clear_headers 'Server';` |
| 17 | ★★★ 錯誤頁還是顯示 PHP 的錯誤訊息 | 只設了 `display_errors=Off` 但沒設 `fastcgi_intercept_errors on;`，或應用程式框架自己有 debug 模式 | 兩邊都設；框架的 debug 開關（Laravel 的 `APP_DEBUG=false`）也要關 |
| 18 | ★★★★ CORS 白名單設了，但別的網域也能存取 | 正規表示式沒有錨定（`~ example` 會比對到 `evil-example.gov.tw.attacker.com`）；或少了 `Vary: Origin` 導致快取污染 | 用 `~* ^https://(a\|b)\.example\.gov\.tw$` 錨定；一定要加 `add_header Vary "Origin" always;` |
| 19 | ★★★ 瀏覽器 Console：`Access-Control-Allow-Origin cannot be * when credentials mode is include` | 同時設了 `Allow-Origin: *` 與 `Allow-Credentials: true` | 回傳具體的 origin，不要用 `*` |
| 20 | ★★★ `disable_functions` 設了之後匯出 PDF／寄信功能壞掉 | 應用程式真的在用 `exec()` 或 `proc_open()` 呼叫外部程式 | 先在測試環境驗證所有功能；必要時只關掉確定用不到的函式，或為該功能建獨立的 PHP-FPM pool |
| 21 | ★★★ `open_basedir` 設了之後系統報「無法讀取檔案」 | 應用程式讀取了 `open_basedir` 清單之外的路徑（常見：`/usr/share/zoneinfo`、暫存目錄） | 從 PHP error log 找出被擋的路徑（`open_basedir restriction in effect`），評估後加入清單 |

## 安全性注意事項

> [!danger] ★★★★★ 三件會把網站弄壞的變更 —— 一律先觀察再強制
> 1. **CSP 強制模式**：直接上線幾乎必然弄壞廠商系統的互動功能。
>    **先 `Content-Security-Policy-Report-Only` 跑兩到四週**，分析回報再切。
>    回滾方式（改回 Report-Only）要事先演練過。
> 2. **`SameSite=Strict`**：會讓從外部連結進入的使用者「看起來沒登入」。
>    ★★★★ 預設用 `Lax`，`Strict` 只給確定不會從外部連入的內部系統。
> 3. **速率限制**：NAT 後面的單位會被整批誤擋。
>    ★★★★ 先寬鬆上線 + 看 `error.log` 的 `limiting requests` 記錄，
>    確認沒有內部網段中招再收緊。

> [!danger] ★★★★★ 絕對不要設的標頭
> **`Public-Key-Pins`（HPKP）**。它會讓瀏覽器記住「這個網域只接受這幾把公鑰」，
> 一旦你換憑證換錯或私鑰遺失，網站就**永久無法存取**，比 HSTS 更不可逆。
> 瀏覽器已全面移除支援，但仍有舊文件在教。看到就是錯的。

其他要點：

| 項目 | 說明 |
| --- | --- |
| ★★★★★ `.git` 外洩要當成已入侵處理 | 封鎖只是止血。原始碼與歷史提交中的所有密碼、金鑰、token 全部視為外洩，必須輪換 |
| ★★★★★ 上傳目錄的設定要實測 | `location` 優先權很容易寫錯。**放一個 `.php` 上去打打看**，回 403 才算數 |
| ★★★★ 標頭要逐路徑驗證 | Nginx `add_header` 的繼承陷阱讓「首頁正常、動態頁沒標頭」變成常態。用迴圈測多個路徑 |
| ★★★★ 改 `php.ini` 後要跑完整功能測試 | `disable_functions`、`open_basedir` 會弄壞列印、匯出、寄信、影像處理 |
| ★★★★ 每次變更都要留 before／after 記錄 | 稽核佐證，也是出事時的回滾依據 |
| ★★★ 安全標頭不是萬靈丹 | 它們**緩解**攻擊的可利用性，不修復漏洞。輸入驗證與參數化查詢仍是廠商的責任 |
| ★★★ 內部系統也要做 | 「反正只有內網」不成立。內網橫向移動是目前最主要的攻擊路徑 |
| ★★★ 定期重新掃描 | 系統更新、廠商上版都可能把設定改掉。排進每週或每月例行檢查 |
| ★★ 改善需求單要留書面 | 需要改程式碼的項目要正式發文給廠商，這是責任分界的依據 |

> [!tip] ★★★★ 做完這篇之後才上 WAF
> 這篇的設定是**確定性**的（設了就是設了），WAF 是**機率性**的（會誤判、要調校）。
> 把基本功做完，WAF 才不用去補那些一行設定就能解決的洞，誤判調校也會單純很多。
> 接續閱讀：[[090-04-01-svc-WAF-WAF概念與ModSecurity安裝]] →
> [[090-04-02-guide-OWASP-CRS規則集]] → [[090-04-03-svc-ModSecurity-規則調校與誤判處理]]。

### 安全標頭一覽

| `Content-Security-Policy` | `default-src 'self'; frame-ancestors 'self'; object-src 'none'; base-uri 'self'; form-action 'self'` | XSS、資料外傳、點擊劫持 | ★★★★★ 高 |

| `X-Content-Type-Options` | `nosniff` | MIME 混淆 | ★★ 低 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Referer 洩漏 | ★ 極低 |

| `Public-Key-Pins` | ★★★★★ **絕對不要設** | — | ★★★★★ 極高 |

### Cookie 屬性

| 屬性 | 值 | 說明 |
| --- | --- | --- |
| `Secure` | — | 只在 HTTPS 送出 |

| `SameSite` | `Strict` | ★★★★★ 從外部連結進來會像沒登入 |
| `SameSite` | `None` | ★★★★★ **必須**同時有 `Secure`，否則 cookie 被丟棄 |

## 練習題

> [!question]- 練習 1：找出你的 `add_header` 繼承漏洞（★★★★★）
> 在一台有 PHP 站台的機器上：
> 1. 在 `server` 區塊 `include` 一組安全標頭
> 2. 在 `location ~ \.php$` 裡加一行 `add_header X-Test "1" always;`
> 3. reload 後，分別用 `curl -sI` 測 `/`（靜態）與 `/index.php`（動態）
> 4. 數一數兩者各有幾個安全標頭
> 5. 把 `include snippets/security-headers.conf;` 也加進 php 的 location，再測一次
>
> **解答方向**
> - 步驟 3：`/` 有四個安全標頭，`/index.php` **只有 `X-Test`**
> - ★★★★★ 重點體會：**動態頁面才是有風險的頁面**，而它正好是沒有標頭的那個
> - 步驟 5 之後兩者都恢復
> - 延伸：改用 `nginx-extras` 的 `more_set_headers` 再測一次，觀察它不受影響

> [!question]- 練習 2：CSP Report-Only 實測（★★★★★）
> 找一個內部測試站台：
> 1. 掛上 `Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report`
> 2. 建立收集端點（Nginx 日誌或簡單的 PHP 端點都行）
> 3. 用瀏覽器操作站台的主要功能，開 Console 觀察
> 4. 收集三天的回報，統計最常被擋的是哪些指令與來源
> 5. 依結果寫出一份**強制模式**的政策草稿
> 6. **不要真的切強制** —— 只寫出草稿並說明每一條白名單的理由
>
> **解答方向**
> - Console 會出現 `[Report Only] Refused to ...` 的訊息（注意有 `[Report Only]` 前綴，代表沒有真的擋）
> - 統計結果通常以 `script-src` + `inline` 佔最大宗
> - 第 5 步的重點是**每一條白名單都要說得出理由**。說不出理由的來源可能就是問題

> [!question]- 練習 3：上傳目錄防護實測（★★★★★）
> 1. 在站台的上傳目錄放一個 `test.php`，內容 `<?php echo "EXEC-OK"; ?>`
> 2. `curl` 存取它，記錄結果
> 3. 套用 `location ^~ /uploads/` 加巢狀拒絕規則
> 4. 再 `curl` 一次
> 5. 再測 `test.phtml`、`test.php5`、`test.PHP`（大寫）
> 6. 測完把檔案刪掉
>
> **解答方向**
> - 步驟 2 若回 `EXEC-OK`，代表你現在就是可被種 webshell 的狀態
> - 步驟 4／5 全部應回 `403`
> - ★★★★ 步驟 5 的大寫測試很重要：`location ~ \.php$` 是**區分大小寫**的，
>   要用 `~*` 才不分大小寫。這是真實存在的繞過手法

> [!question]- 練習 4：SameSite 的實際影響（★★★★）
> 1. 把測試站台的 `session.cookie_samesite` 設成 `Strict`
> 2. 登入系統，確認正常
> 3. 開一個**不同網域**的頁面（可以用本機另一個 port 的簡單 HTML），放一個連到系統的連結
> 4. 從那個頁面點連結進入系統，觀察是否還是登入狀態
> 5. 改成 `Lax`，重複步驟 3～4
>
> **解答方向**
> - `Strict` 時步驟 4 會**顯示為未登入**（cookie 沒被送出），但重新整理一次就恢復
> - `Lax` 時正常
> - ★★★★★ 這正是使用者回報「從公文系統點連結過來就要重新登入」的原因

> [!question]- 練習 5：限流誤擋演練（★★★★）
> 1. 設一個很嚴格的限流：`rate=2r/m`，套用在某個測試路徑
> 2. 用 `for i in $(seq 1 10); do curl -s -o /dev/null -w '%{http_code} ' https://host/測試路徑; done`
> 3. 觀察回應碼變化
> 4. 到 `error.log` 找 `limiting requests` 記錄，抄下 client IP
> 5. 用 `geo` 把你自己的 IP 加進豁免清單，重複步驟 2
> 6. 思考：如果整個單位共用一個 NAT 出口，這個限流會造成什麼後果
>
> **解答方向**
> - 步驟 3 會看到 `200 200 429 429 ...`（加 `burst` 的話前面會多幾個 200）
> - 步驟 5 之後全部 200
> - 步驟 6 的答案就是本篇 danger 區塊講的：整個單位每分鐘只有 2 個人能操作

> [!question]- 練習 6：資訊洩漏自我健檢（★★★★★）
> 對你負責的**每一個**對外站台跑一遍：
> ```bash
> for h in site1.example.gov.tw site2.example.gov.tw; do
>   echo "== $h"
>   for p in /.git/HEAD /.env /config.php.bak /backup.sql /composer.json /phpinfo.php /info.php; do
>     printf '  %-20s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' --max-time 5 https://$h$p)"
>   done
> done
> ```
> 把回 `200` 的項目整理成一張清單，逐項處理。
>
> **解答方向**
> - ★★★★★ 這不是練習，這是**你今天就該做的事**
> - 任何一個回 200 都是高風險缺失，`.git` 與 `.bak` 尤其
> - 處理順序：立刻封鎖 → 追查 access log 有沒有人下載過 → 輪換所有憑證 → 治本（移出 DocumentRoot）

## 小測驗

Q1.（選擇）你負責維運一套廠商開發的系統，稽核報告列出「未做輸入驗證，存在 SQL Injection 風險」。下列哪一項**不是**維運端能做的？
(A) 部署 ModSecurity + OWASP CRS 攔截常見 payload
(B) 把 `display_errors` 關掉，避免錯誤訊息幫助攻擊者
(C) 把應用程式的 SQL 查詢改成參數化查詢
(D) 對該端點加上速率限制，降低自動化探測的效率

Q2. OWASP Top 10 裡有兩項「幾乎完全是維運的責任」，是哪兩項？為什麼？

Q3.（是非）在 `<meta http-equiv="Content-Security-Policy">` 裡設 `frame-ancestors 'none'`，就能擋掉點擊劫持。

Q4. 這段設定有什麼問題？影響到哪些頁面？
```nginx
server {
    include snippets/security-headers.conf;
    location ~ \.php$ {
        add_header X-App "v3" always;
        fastcgi_pass unix:/run/php/php8.1-fpm.sock;
    }
}
```

Q5. 使用者回報「登入之後馬上又跳回登入頁」，伺服器日誌看起來一切正常，瀏覽器 Console 有 cookie 相關警告。最可能改了什麼設定？

Q6.（是非）`SameSite=Strict` 比 `Lax` 安全，所以應該優先選 `Strict`。

Q7. `curl -s -o /dev/null -w '%{http_code}\n' https://host/.git/HEAD` 回 `200`。除了立刻在 Nginx 封鎖之外，你**還必須**做哪兩件事？

Q8. 下面這段設定的用意是什麼？為什麼**一定要實際測試**才算完成？
```nginx
location ^~ /uploads/ {
    location ~ \.(php|phtml|phar)$ {
        deny all;
    }
}
```

Q9.（簡答）機關內網一個單位一百人共用一個對外 IP。你設定 `limit_req_zone $binary_remote_addr zone=login:10m rate=5r/m;` 並套用在登入頁。會發生什麼事？兩個對策是什麼？

Q10.（選擇）導入 CSP 的正確順序是：
(A) 直接上強制模式，出問題再調整
(B) 先掛 `Content-Security-Policy-Report-Only` 觀察兩到四週，分析回報後再切強制
(C) 先設 `default-src *` 再逐步縮小
(D) 設在 `<meta>` 標籤裡比較安全，因為可以隨時改 HTML

> [!question]- 測驗答案
> **Q1.** **(C)**。修改應用程式原始碼不是維運端能做的（也不該做 —— 動了廠商的程式碼，
> 出問題責任歸屬會很麻煩）。(A)(B)(D) 都是維運端當天就能做的緩解措施。
> ★★★★★ 這題就是本篇的核心立場，見「這篇的立場：你是維運，不是開發」。
>
> **Q2.** **A05 Security Misconfiguration（設定不當）** 與
> **A09 Security Logging and Monitoring Failures（日誌與監控不足）**。
> 前者的內容（版本橫幅、目錄列表、除錯模式、預設頁面、敏感檔案封鎖）全部在伺服器設定裡；
> 後者（日誌保留、集中、告警）是維運的例行工作。★★★★★ 這兩項在稽核報告上出現，
> **不能推給廠商**。見「OWASP Top 10 的維運視角」。
>
> **Q3.** ✗ 錯。★★★★ `frame-ancestors`、`report-uri`、`sandbox` 這三個指令
> **在 `<meta>` 標籤裡會被瀏覽器忽略**，只有 HTTP 標頭形式有效。
> 要擋點擊劫持必須用 `add_header` 送出，或設 `X-Frame-Options`。見排錯表第 2 列。
>
> **Q4.** ★★★★★ `location ~ \.php$` 裡出現了 `add_header`，會讓
> **父層 `server` 的所有 `add_header` 全部失效** —— 也就是**所有 PHP 頁面都沒有安全標頭**。
> 最可怕的是靜態首頁測起來完全正常，而動態頁面（真正有風險的那些）才是沒防護的。
> 解法：在該 location 裡也 `include snippets/security-headers.conf;`，
> 或改用 `ngx_headers_more` 的 `more_set_headers`。見排錯表第 3 列。
>
> **Q5.** ★★★★★ 最可能把 `session.cookie_samesite` 改成了 `None` **但沒有同時設
> `session.cookie_secure = 1`**（或站台不是 HTTPS）。瀏覽器會**直接丟棄**這個 cookie，
> 所以登入產生的 session 根本沒被保存。Console 訊息是
> `Cookie ... rejected because it has the "SameSite=None" attribute but is missing the "secure" attribute`。
> 見排錯表第 6 列。
>
> **Q6.** ✗ 錯。★★★★★ `Strict` 確實更嚴格，但它連**從外部連結點進來的頂層導覽**都不送 cookie，
> 使用者從 email 或入口網站點進來會顯示為未登入 —— 這是最常見的災情。
> **多數系統的正解是 `Lax`**，也是現代瀏覽器的預設。`Strict` 只適合確定不會從外部連入的內部系統。
>
> **Q7.** ★★★★★ (1) **追查 access log 有沒有人下載過**
> （`grep "/\.git/" /var/log/nginx/*access*.log`）；
> (2) **假設原始碼與歷史提交中的所有密碼、金鑰、token 已外洩，全部輪換**。
> 另外治本要把 `.git` 移出 DocumentRoot。封鎖只是止血，不是治療。見「資訊洩漏」的 danger 區塊。
>
> **Q8.** 用意是讓 `/uploads/` 目錄下的 `.php`／`.phtml`／`.phar` **不會被送去 PHP-FPM 執行**，
> 即使廠商的副檔名檢查有漏洞、webshell 成功上傳，也只是一個不能執行的檔案。
> ★★★★★ 必須實測的原因是 **`location` 的比對優先順序很容易寫錯**
> （`^~` 前綴比對與 `~` 正規表示式的優先權、巢狀 location 的行為）。
> 放一個 `test.php` 上去 `curl`，回 `403` 才算數；回出 PHP 執行結果就代表設定沒生效。
>
> **Q9.** ★★★★★ **整個單位的一百個人共用同一個限流配額**，每分鐘只有 5 次登入請求會通過，
> 其餘全部回 429 —— 等於整個單位被鎖在外面。
> 兩個對策：(1) 用 `geo` 把內部網段列入豁免（把 key 設成空字串就不計入限流）；
> (2) 只對真正需要的端點限流、並把速率設得寬鬆，先用 `limit_req_log_level warn`
> 從 `error.log` 觀察誰被擋，確認沒有內部 NAT 出口中招再收緊。
> 另外若站台在代理後面，還要先用 `set_real_ip_from`／`real_ip_header` 取回真實 IP。
> 見「速率限制」的 danger 區塊與排錯表第 11 列。
>
> **Q10.** **(B)**。★★★★★ CSP 是最容易把網站弄壞的標頭，症狀是
> 「頁面正常顯示但按鈕全部沒反應，且沒有錯誤畫面」。
> 必須先用 `Content-Security-Policy-Report-Only`（瀏覽器照常執行、只回報）觀察兩到四週，
> 分析出實際載入了哪些來源，調整白名單後才切強制，並準備好 10 秒回滾的方案。
> (A) 幾乎必然造成災情；(C) `default-src *` 等於沒設；
> (D) meta 形式會讓 `frame-ancestors` 與 `report-uri` 失效。
