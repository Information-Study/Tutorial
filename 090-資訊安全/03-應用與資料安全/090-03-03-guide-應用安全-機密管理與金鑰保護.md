# 機密管理與金鑰保護

## 這篇你會學到

> [!abstract] 學習目標
> - ★★★★★ 認清一件事：**機關現場的密碼幾乎都放在不該放的地方** —— 設定檔明文、程式碼裡、
>   Excel、便利貼、共用信箱，以及**已經推上 GitHub 的 git repo**。每一種的風險與補救方式
> - ★★★★ 把「機密」分成三類（**長期不變**／**會輪替**／**絕不可外流**），
>   不同類別用不同的保護強度，不要一套規則硬套全部
> - ★★★★★ 由淺到深的**四個成熟度層級**，機關可以照自己的能力選一層落地：
>   L1 檔案權限＋環境變數 → L2 檔案加密（`age`／`sops`）→ L3 系統整合（`systemd-creds`／KMS）
>   → L4 專用機密管理系統（Vault）
> - ★★★★★ **機密推上 git 之後怎麼辦**：怎麼掃、為什麼**改掉 commit 不等於沒外流**、
>   正確處置是**輪替憑據**而不是改歷史
> - ★★★★ **憑證私鑰**的特殊待遇：權限、備份、不可交給廠商、遺失的後果
> - ★★★ **輪替**的實務：什麼該定期換、換的時候怎麼不中斷服務（雙金鑰並行期）
> - ★★★★★ 完整實戰：把一個 Nginx ＋ MySQL ＋ Laravel 專案裡**散落各處的機密收攏**，
>   盤點 → 分級 → 用 `sops` ＋ `age` 加密進 git → 部署時解密 → 驗證，全程可跑

> [!tip] 這篇的立場
> 機密管理最容易失敗的原因不是工具不好，是**方案太重、沒有人願意用**。
> 一個所有人都遵守的 L1，遠勝過一套沒人會操作、掛掉就全公司停擺的 L4。
> 本篇每個層級都會寫「什麼時候該升上去」與「升上去要付的代價」。

## 觀念說明

### 先面對現實：機關的密碼現在都放在哪裡 ★★★★★

不用假設，這就是實際盤點的結果。幾乎每個機關都能在下表勾到四項以上：

| 存放位置 | 有多普遍 | 風險 | 一旦外洩的影響範圍 |
| --- | --- | --- | --- |
| **設定檔明文**（`.env`、`config.php`、`application.yml`） | 幾乎 100% | ★★★ 權限沒設好就全機可讀 | 該台主機上任何使用者、任何被入侵的服務 |
| **寫死在程式碼裡**（hard-code） | 很高 | ★★★★ 會跟著程式碼散布到每個人的筆電 | 所有拿過原始碼的人，含離職者、外包商 |
| **git repo 裡且已 push** | ★★★★★ 非常高 | ★★★★★ **等同公開** | 全世界（公開 repo）／全單位＋歷任外包（私有 repo） |
| **Excel／Word 密碼表**放共用磁碟 | 很高 | ★★★★ 檔案權限通常是「大家都能開」 | 全單位所有人，含臨時人員 |
| **便利貼、白板、螢幕邊框** | 高 | ★★★ 訪客、廠商、清潔人員都看得到 | 進得了機房或辦公室的任何人 |
| **共用信箱／LINE 群組／Teams 訊息** | 高 | ★★★★ 永久保存、可搜尋、無法回收 | 群組所有成員與未來加入的人 |
| **交接文件（Word）附在郵件** | 高 | ★★★★ 郵件會被轉寄、備份、留在離職者信箱 | 不可控 |
| **瀏覽器記住密碼** | 中 | ★★★ 換機／被入侵時整包被匯出 | 該使用者所有系統 |
| **廠商手上**（維護商保管） | 中 | ★★★★ 你完全無法稽核 | 廠商全體員工與其分包 |
| **沒有人知道**（原承辦已離職） | 中 | ★★★★★ 出事時無法登入處理 | 服務中斷且無法救援 |

> [!danger] 最後一列不是笑話 ★★★★★
> 「機密管理」失敗有兩個方向：**外流**與**遺失**。
> 機關常見的是後者 —— 承辦離職、交接沒交到、憑證私鑰只在他的筆電上，
> 憑證到期要換的時候誰都動不了。
> 一套機密管理方案如果只解決「不外流」卻讓「只有一個人拿得到」，那是把風險換了個方向而已。

### 「已經發生了怎麼辦」速查 ★★★★

| 你發現的狀況 | 第一步（今天就做） | 第二步 | 第三步 |
| --- | --- | --- | --- |
| 密碼在 **public git repo** | ★★★★★ **當作已外洩，立刻輪替該憑據** | 檢查該憑據近期的存取紀錄／登入紀錄 | 加 `.gitignore` ＋ pre-commit hook 防再犯 |
| 密碼在 **private git repo** | ★★★★ 同樣視為外洩（所有 clone 過的人都有） | 清點誰 clone 過 | 輪替＋改流程 |
| 密碼在**共用磁碟 Excel** | 收斂權限到最小群組 | 逐筆輪替高風險的（DB、雲端金鑰） | 移到 L2 加密檔或密碼管理器 |
| 密碼在 **LINE／郵件** | ★★★ 無法回收，直接輪替 | 宣導：憑據不走即時通訊 | 提供替代管道（加密檔／密碼管理器） |
| **憑證私鑰**外流 | ★★★★★ 立即向 CA 申請**撤銷（revoke）**並重新簽發 | 換掉所有部署該憑證的服務 | 檢討私鑰為何離開伺服器 |
| **沒人知道密碼** | 從能登入的路徑重設（本機 root、DB skip-grant） | 建立正式的機密存放位置 | 補交接文件與代理人 |

> [!warning] ★★★★★ 一條不能妥協的原則
> **只要憑據曾經離開你能控制的範圍（推上遠端、寄出去、貼到群組），就當作已經外洩。**
> 「我馬上刪掉了」「repo 是私有的」「群組只有我們三個」——
> 這些都不是「沒外洩」的證據，只是「還沒看到有人用它」而已。
> 正確的動作永遠是**輪替**，不是把痕跡擦掉。

### 機密的三種分類 ★★★★

不同的機密，處理原則完全不同。硬用同一套規則會導致「該換的沒換、不該動的亂動」。

| 類別 | 例子 | 特性 | 處理原則 |
| --- | --- | --- | --- |
| **A 長期不變** | 資料庫密碼、SMTP 帳密、內部服務間的固定密碼 | 換一次要協調多個元件、容易漏改 | ★★★ 重點在**存放安全**與**權限最小化**；輪替頻率低（年度或人員異動時），但**必須有可執行的輪替步驟文件** |
| **B 會輪替** | 第三方 API 金鑰、雲端存取金鑰、Webhook Token、CI/CD Token | 平台通常支援**同時存在兩把**、可個別撤銷 | ★★★★ 重點在**輪替流程自動化**與**雙金鑰並行期**；設到期提醒，離職／換廠商必換 |
| **C 絕不可外流** | 憑證私鑰、CA 私鑰、程式碼簽章金鑰、資料加密主金鑰、備份加密金鑰 | ★★★★★ **外洩後無法用「換一把」完全補救**（已簽的東西、已加密的資料都受影響） | ★★★★★ 產生後**不離開伺服器**；不進 git（即使加密也要多想一次）；離線保管一份；有撤銷程序 |

> [!note] 為什麼 C 類特別嚴重 ★★★★★
> - **憑證私鑰**外洩 → 任何人都能假冒你的網站。就算重簽新憑證，舊憑證在**撤銷資訊生效前**
>   仍可能被信任（CRL/OCSP 有快取、有些用戶端根本不查）。詳見 [[090-01-12-guide-PKI-憑證生命週期管理]]。
> - **簽章金鑰**外洩 → 攻擊者可以簽出「看起來是你發布的」程式或韌體，
>   已經流出去的惡意檔案**無法收回**。
> - **資料加密主金鑰**外洩 → 你過去所有的加密備份一次全裸。換金鑰只保護未來，**保護不了過去**。

### 四個成熟度層級 ★★★★★

這是本篇的主軸。**照自己的能力選一層，做到位，再談升級。**

| 層級 | 做法 | 機密放哪 | 適合誰 | 主要代價 |
| --- | --- | --- | --- | --- |
| **L1** | 檔案權限 ＋ 環境變數 | 主機上的 `600` 檔案 | ★★★★★ **所有人的起點**，1～10 台主機 | 幾乎零成本；缺點是**機密不能進版控**、多台主機要手動同步 |
| **L2** | 檔案加密（`age` / `sops`） | **加密後的檔案可以進 git** | ★★★★ 有 git 流程、多環境、2～3 人以上團隊 | 要管「解密金鑰」；金鑰派送與人員異動要有流程 |
| **L3** | 系統／平台整合（`systemd-creds`、雲端 KMS） | 由 OS 或雲平台保管 | ★★★ 已標準化的 Linux 機隊、或已上雲 | 綁定平台；`systemd-creds` 需要新版 systemd |
| **L4** | 專用機密管理系統（HashiCorp Vault 等） | 專屬服務，動態發放、可稽核 | ★★ 數十台以上、多團隊、需要稽核軌跡 | ★★★★ **它自己要高可用、要備份、要 unseal；它掛了所有服務跟著掛** |

> [!tip] 選型建議（給機關）★★★★★
> - **一般機關的資訊科**：把 **L1 做紮實**，再把「要進版控的設定」升到 **L2**。這已經解決 90% 的問題。
> - **有 CI/CD、多環境（dev/stage/prod）**：**L2 是甜蜜點**。`sops` ＋ `age` 檔案加密後直接進 git，
>   誰改了什麼在 commit 紀錄裡看得到，部署時才解密。
> - **L4 不要輕易自架**。下面「Vault 的代價」一節會講清楚為什麼。
>   如果真的需要 L4，優先考慮雲端託管的 KMS／Secret Manager，把高可用交給雲端業者。

## 安裝或基礎操作

### L1-1：檔案權限，最基本也最常做錯 ★★★★★

先看一個真實會發生的錯誤。

```bash
ls -l /var/www/myapp/.env
```

預期輸出（**錯誤示範**）：

```text
-rw-r--r-- 1 root root 812 Sep  3 09:12 /var/www/myapp/.env
```

`644` 代表**這台機器上任何使用者都讀得到**，包含被入侵的 `www-data`。
Web 服務一旦有任意檔案讀取（LFI）漏洞，資料庫密碼就直接被撈走。

正確做法：**擁有者是誰要跟「誰需要讀」對齊**。

```bash
# Laravel／PHP-FPM 情境：跑服務的是 www-data，所以群組給 www-data，其他人完全不可讀
sudo chown root:www-data /var/www/myapp/.env
sudo chmod 640 /var/www/myapp/.env
ls -l /var/www/myapp/.env
```

預期輸出：

```text
-rw-r----- 1 root www-data 812 Sep  3 09:12 /var/www/myapp/.env
```

| 情境 | 建議擁有者 | 建議權限 | 說明 |
| --- | --- | --- | --- |
| 只有 root 讀（systemd `EnvironmentFile`） | `root:root` | `600` | ★★★★ 最安全，服務由 root 啟動後降權 |
| 應用程式帳號要讀（PHP-FPM、Node） | `root:<服務群組>` | `640` | ★★★★ 檔案不可被服務帳號**寫入**，避免被入侵後竄改 |
| 應用程式自己產生的（Laravel `storage/`） | `www-data:www-data` | `750` 目錄 | ★★★ 目錄可寫、但別放機密 |
| **憑證私鑰** | `root:root` | ★★★★★ `600`，目錄 `/etc/ssl/private` 為 `700` | 見下面「憑證私鑰」一節 |

> [!warning] ★★★★ 三個常被忽略的權限漏洞
> 1. **目錄權限**。檔案是 `600`，但上層目錄是 `777` —— 別人雖然讀不到內容，卻能**改名或刪除**。
>    `ls -ld /var/www/myapp` 一起檢查。
> 2. **備份檔沒跟著保護**。`cp .env .env.bak` 產生的是預設 umask 權限（通常 `644`）。
>    ★★★★ `.env.bak`、`.env.old`、`.env~`（編輯器備份）是入侵者第一個試的檔名。
> 3. **Web root 底下的設定檔**。如果 `.env` 放在 `public/` 或 Web 根目錄，
>    設定一旦有誤就能被 `https://站台/.env` 直接下載。
>    ★★★★★ 設定檔一律放在 **document root 之外**，並在 Nginx 加保險：
>
> ```nginx
> location ~ /\.(env|git|svn|ht) {
>     deny all;
>     return 404;
> }
> ```
>
> 相關設定見 [[060-02-02-09-guide-Nginx-安全設定]]。

### L1-2：systemd 的 EnvironmentFile ★★★★

比起把密碼寫在 unit 檔的 `Environment=`，**一律用 `EnvironmentFile=`**。

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My App
After=network-online.target

[Service]
Type=simple
User=myapp
Group=myapp
WorkingDirectory=/opt/myapp
# 機密放在權限 600 的獨立檔案，不寫在 unit 裡
EnvironmentFile=/etc/myapp/env
ExecStart=/usr/bin/node /opt/myapp/server.js
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/myapp/env   ← chown root:root、chmod 600
DB_PASSWORD=Kx7#pQ2vLm9!zR4t
API_TOKEN=sk_live_9f3a2b7c1d8e
```

```bash
sudo install -o root -g root -m 600 /dev/null /etc/myapp/env
sudo nano /etc/myapp/env
sudo systemctl daemon-reload
sudo systemctl restart myapp
```

驗證 unit 檔本身沒有洩漏機密：

```bash
systemctl show myapp -p Environment -p EnvironmentFiles
```

預期輸出：

```text
Environment=
EnvironmentFiles=/etc/myapp/env (ignore_errors=no)
```

`Environment=` 是空的、只看得到**檔案路徑**而不是內容 —— 這就是我們要的。

> [!danger] ★★★★★ 絕對不要把密碼寫在 `Environment=`
> `systemctl show <unit>` **不需要 root** 就能執行，任何本機使用者都看得到 `Environment=` 的內容。
> 寫在 unit 檔裡的密碼等於公開在這台機器上。
>
> ```bash
> # 用低權限帳號測試，確認看不到內容
> sudo -u nobody systemctl show myapp -p Environment
> ```

### L1-3：★★★★★ 環境變數不是保險箱

很多人以為「改用環境變數就安全了」。**不是。** 環境變數只是「不在硬碟明文檔案裡」，
它有自己的一整組洩漏管道：

| 洩漏管道 | 說明 | 誰看得到 | 防法 |
| --- | --- | --- | --- |
| `/proc/<pid>/environ` | 程序的完整環境變數 | ★★★★ **同一個 UID 的任何程序**與 root | 服務用**專屬低權限帳號**跑，不要多個服務共用一個帳號 |
| **子程序繼承** | 應用程式 `exec` 出去的每個子程序（含 `sh -c`、image magick、ffmpeg、備份腳本）都繼承整包環境變數 | 任何被呼叫的外部程式 | ★★★★ 呼叫外部程式時**清空環境**（`env -i`）或只傳需要的變數 |
| **錯誤頁與 debug 畫面** | Laravel `APP_DEBUG=true` 的錯誤頁、`phpinfo()`、Node 的 stack trace | ★★★★★ **全世界** | 正式環境 `APP_DEBUG=false`；移除 `phpinfo.php` |
| **日誌與 APM** | 例外追蹤工具（Sentry 等）預設會上傳環境變數快照 | 第三方服務 | 設定敏感欄位遮蔽清單 |
| **crash dump / core dump** | core 檔含整個記憶體，環境變數在裡面 | 拿得到 core 檔的人 | 正式機關閉 core dump：`ulimit -c 0` |
| `ps` 與程序清單 | ★★★ 密碼**寫在命令列參數**時（`mysql -pXXXX`）全機可見 | 所有使用者 | 永遠不要把密碼放命令列，見下面 MySQL 範例 |
| **容器 inspect** | `docker inspect` 顯示容器的 `Env` | 能操作 docker 的人＝等同 root | ★★★ 用 secret 檔掛載而非 `-e` |

實測一下第一項：

```bash
# 找到服務的 PID
systemctl show myapp -p MainPID
```

```text
MainPID=2481
```

```bash
# 用 root 讀（同 UID 的使用者也讀得到）
sudo tr '\0' '\n' < /proc/2481/environ | grep -i pass
```

預期輸出：

```text
DB_PASSWORD=Kx7#pQ2vLm9!zR4t
```

> [!warning] ★★★★ 這代表什麼
> 如果你把 `myapp` 和另一個服務都用同一個帳號（例如都用 `www-data`）跑，
> 那**另一個服務被入侵就能讀到 `myapp` 的所有密碼**。
> 一個服務一個專屬系統帳號，是 L1 就該做到的隔離。

### L1-4：不要把密碼放進命令列 ★★★★

```bash
# ★★★★★ 錯誤示範：密碼會出現在 ps 與 shell history
mysqldump -u backup -pP@ssw0rd mydb > dump.sql
```

任何使用者執行 `ps aux | grep mysqldump` 都看得到密碼。正確做法用設定檔：

```ini
# /root/.my.cnf   ← chmod 600
[client]
user=backup
password=P@ssw0rd
```

```bash
sudo install -o root -g root -m 600 /dev/null /root/.my.cnf
sudo nano /root/.my.cnf
sudo mysqldump mydb > /var/backups/mydb.sql
```

或用 `--defaults-extra-file` 指定其他路徑：

```bash
sudo mysqldump --defaults-extra-file=/etc/mysql/backup.cnf mydb > /var/backups/mydb.sql
```

> [!tip] ★★★ shell history 也要顧
> 在互動 shell 打的 `export DB_PASSWORD=...` 會寫進 `~/.bash_history`。
> 臨時要輸入機密時，指令前面加**一個空白**（Bash 預設 `HISTCONTROL=ignorespace` 時生效），
> 或改用 `read -s`：
>
> ```bash
> read -rsp "DB password: " DB_PASSWORD; echo
> ```

### L2 起步：安裝 age 與 sops ★★★★

`age` 是簡單的檔案加密工具（取代 GPG 的複雜度），`sops` 是「只加密 YAML/JSON 的值、
保留鍵名」的設定檔加密工具。兩者搭配是目前最實用的 L2 組合。

```bash
# Ubuntu 22.04 / 24.04：age 在官方套件庫
```

```bash

```

若找不到套件，改用官方發布的二進位檔：

### 產生 age 金鑰對 ★★★★

```bash
mkdir -p ~/.config/sops/age
age-keygen -o ~/.config/sops/age/keys.txt
```

預期輸出：

```text
Public key: age1q9w8e7r6t5y4u3i2o1p0asdfghjklzxcvbnmqwertyuiop0asdfgh
```

檢查檔案內容與權限：

```bash
chmod 600 ~/.config/sops/age/keys.txt
cat ~/.config/sops/age/keys.txt
```

預期輸出：

```text
# created: 2026-09-03T09:40:11+08:00
# public key: age1q9w8e7r6t5y4u3i2o1p0asdfghjklzxcvbnmqwertyuiop0asdfgh
AGE-SECRET-KEY-1XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
```

| 這一行 | 是什麼 | 能給誰 |
| --- | --- | --- |
| `age1...`（public key） | ★ **公鑰**，用來加密 | 可以公開，寫進 `.sops.yaml` 進 git 沒問題 |
| `AGE-SECRET-KEY-1...` | ★★★★★ **私鑰**，用來解密 | **絕對不進 git**；只放在需要解密的機器與人員手上 |

單檔加解密的最小示範：

```bash
echo "這是機密" > secret.txt
age -r age1q9w8e7r6t5y4u3i2o1p0asdfghjklzxcvbnmqwertyuiop0asdfgh -o secret.txt.age secret.txt
file secret.txt.age
```

預期輸出：

```text

```

```bash
age -d -i ~/.config/sops/age/keys.txt secret.txt.age
```

預期輸出：

```text
這是機密
```

> [!tip] ★★★ `age -p`：不用金鑰對，用密碼加密
> 一次性傳檔（例如寄給廠商一份設定）用密碼模式最省事：
>
> ```bash
> age -p -o config.tar.gz.age config.tar.gz     # 加密，會提示輸入 passphrase
> age -d -o config.tar.gz config.tar.gz.age     # 解密
> ```
>
> 但**密碼本身怎麼給對方**又是同一個問題 —— 至少走不同管道（檔案用 email、密碼用電話）。

## 進階應用

### L2：用 sops 加密設定檔，然後放心地推進 git ★★★★★

`sops` 的關鍵優勢：**只加密「值」，鍵名維持明文**。所以：

- `git diff` 看得出「有人改了 `DB_PASSWORD`」，但看不到新值
- 合併衝突可以正常處理
- 誰在什麼時候改了哪個機密，commit 紀錄查得到

建立專案層級的設定檔 `.sops.yaml`（**這個檔要進 git**）：

```yaml
# .sops.yaml
creation_rules:
  # 正式環境：只有維運組的三把金鑰能解
  - path_regex: secrets/prod/.*\.ya?ml$
    age: >-
      age1q9w8e7r6t5y4u3i2o1p0asdfghjklzxcvbnmqwertyuiop0asdfgh,
      age1prodserver00000000000000000000000000000000000000000000,
      age1backupkey000000000000000000000000000000000000000000000
  # 測試環境：全開發團隊
  - path_regex: secrets/dev/.*\.ya?ml$
    age: >-
      age1q9w8e7r6t5y4u3i2o1p0asdfghjklzxcvbnmqwertyuiop0asdfgh,
      age1devteam00000000000000000000000000000000000000000000000
```

建立與加密：

```bash
mkdir -p secrets/prod
cat > secrets/prod/app.yaml <<'EOF'
db:
  host: 10.0.1.20
  name: myapp
  user: myapp
  password: Kx7#pQ2vLm9!zR4t
mail:
  host: smtp.example.gov.tw
  user: noreply@example.gov.tw
  password: S3nd!M4il2026
api:
  payment_key: sk_live_9f3a2b7c1d8e4f5a
EOF

sops --encrypt --in-place secrets/prod/app.yaml
head -12 secrets/prod/app.yaml
```

預期輸出（節錄，你會看到**鍵名還在、值被換成密文**）：

```yaml
db:
    host: ENC[AES256_GCM,data:mZ0kPQ==,iv:...,tag:...,type:str]
    name: ENC[AES256_GCM,data:9vTb,iv:...,tag:...,type:str]
    user: ENC[AES256_GCM,data:9vTb,iv:...,tag:...,type:str]
    password: ENC[AES256_GCM,data:xR2s7yQ1..,iv:...,tag:...,type:str]
mail:
    host: ENC[AES256_GCM,data:...,type:str]
```

檔案末端會多出 `sops:` 區塊，記錄用哪些 age 公鑰加密、什麼時候加密的。

日常編輯（**不要手動解密再加密**，用內建編輯器）：

```bash
sops secrets/prod/app.yaml
```

會用 `$EDITOR` 開啟**明文**，存檔離開時自動重新加密。

驗證解密：

```bash
sops --decrypt secrets/prod/app.yaml | head -6
```

預期輸出：

```yaml
db:
    host: 10.0.1.20
    name: myapp
    user: myapp
    password: Kx7#pQ2vLm9!zR4t
```

只取單一個值（部署腳本常用）：

```bash
sops --decrypt --extract '["db"]["password"]' secrets/prod/app.yaml
```

預期輸出：

```text
Kx7#pQ2vLm9!zR4t
```

> [!note] ★★★★ 解密金鑰怎麼管，才是 L2 的真正難題
> 加密很簡單，難的是「誰的機器上有私鑰」。實務上有三種放法：
>
> | 放法 | 說明 | 適用 |
> | --- | --- | --- |
> | **每個人一把個人金鑰** | 每位維運人員自己 `age-keygen`，把**公鑰**交給管理者加進 `.sops.yaml` | ★★★★ 最推薦。人員離職只要從 `.sops.yaml` 移除公鑰並 `sops updatekeys` |
> | **每台伺服器一把主機金鑰** | 部署時伺服器用自己的私鑰解密 | ★★★★ 搭配上面一起用；主機金鑰放 `/etc/sops/age/keys.txt`（`600 root:root`） |
> | **一把共用金鑰大家傳** | 省事 | ★★★★★ **不要**。一個人離職就要全部重加密，而且你不知道他有沒有留底 |
>
> 新增／移除人員之後，一定要更新既有檔案的收件者：
>
> ```bash
> sops updatekeys secrets/prod/app.yaml
> ```
>
> 它會依 `.sops.yaml` 目前的規則重新包裝資料金鑰（**不需要知道原本的明文**）。

> [!danger] ★★★★★ `sops updatekeys` 移除某人的公鑰 ≠ 他失去了資料
> 他手上如果留有舊版的加密檔（clone 過的 repo），舊檔案**永遠**可以用他的舊私鑰解開。
> 所以人員離職的正確流程是：
> 1. 從 `.sops.yaml` 移除他的公鑰、`sops updatekeys`
> 2. ★★★★★ **輪替他曾經解得開的所有機密**（改資料庫密碼、重發 API 金鑰）
> 3. 收回他的 git 存取權
>
> 只做第 1 步是自我安慰。

### L3-1：systemd-creds ★★★

`systemd-creds` 把機密用**綁定這台機器**的金鑰加密，服務啟動時由 systemd 解密後
以檔案形式放進一個只有該服務讀得到的 tmpfs 目錄。優點是機密**不以環境變數形式存在**，
所以 `/proc/<pid>/environ` 撈不到。

```bash
systemd-creds --version
```

> [!warning] ★★★★ 版本限制
> `LoadCredentialEncrypted=` 需要 **systemd 250 以上**。
> Ubuntu 22.04 LTS 內建 systemd 249，**沒有**這個功能；
> Ubuntu 24.04 LTS（systemd 255）與 Debian 12（systemd 252）可用。
> 先確認版本再決定要不要用：
>
> ```bash
> systemctl --version | head -1
> ```
>
> ```text
> systemd 255 (255.4-1ubuntu8.4)
> ```

加密一份機密：

```bash
printf 'Kx7#pQ2vLm9!zR4t' | sudo systemd-creds encrypt --name=db_password - /etc/credstore.encrypted/db_password
sudo ls -l /etc/credstore.encrypted/
```

預期輸出：

```text
-rw------- 1 root root 512 Sep  3 10:22 db_password
```

在 unit 檔載入：

```ini
[Service]
LoadCredentialEncrypted=db_password:/etc/credstore.encrypted/db_password
ExecStart=/opt/myapp/start.sh
```

程式在執行時，從 `$CREDENTIALS_DIRECTORY` 讀：

```bash
#!/bin/bash
# /opt/myapp/start.sh
DB_PASSWORD="$(cat "${CREDENTIALS_DIRECTORY}/db_password")"
exec /usr/bin/node /opt/myapp/server.js
```

> [!warning] ★★★★ systemd-creds 的加密金鑰在哪
> 主機金鑰預設在 `/var/lib/systemd/credential.secret`（有 TPM 的機器可綁 TPM2）。
> 這代表：
> - ★★★★★ **加密後的檔案換一台機器就解不開**（這是優點，也是陷阱）
> - ★★★★ **重灌／換硬體前一定要先把明文機密備份出來**，否則加密檔變成廢檔
> - 因此它**不適合**當作跨機共享機密的方案，只適合「這台機器自己用」

> [!warning] 未實機驗證
> `--name=` 的比對規則（載入時名稱不符會拒絕解密）與 TPM2 綁定選項（`--with-key=`）
> 在不同 systemd 版本行為略有差異，導入前請以你環境上的 `man systemd-creds` 為準。

### L3-2：雲端 KMS 的概念 ★★★

雲端的 Key Management Service（Azure Key Vault、GCP Cloud KMS、AWS KMS）解決的是同一件事，
但把「保管主金鑰」外包給雲端業者。

核心模式叫 **envelope encryption（信封加密）**：

```text
       ┌──────────────┐
       │  KMS 主金鑰   │  ← 永遠不離開 KMS，你只能請它「幫我加/解密」
       └──────┬───────┘
              │ 加密
              ▼
       ┌──────────────┐        ┌───────────────────┐
       │ 資料金鑰(DEK) │ ─────► │  你的機密／備份檔   │
       └──────────────┘  加密   └───────────────────┘
        （加密後的 DEK 跟資料放在一起）
```

- ★★★ 你的應用程式**沒有主金鑰**，只有「呼叫 KMS 解開 DEK」的權限
- ★★★★ 權限撤銷是即時的：把該身分的 KMS 權限拿掉，它手上的加密檔立刻變成廢檔
- ★★★★ 每次呼叫都有稽核紀錄 —— 這是自建 L1/L2 很難做到的

`sops` 也支援直接用 KMS 當金鑰來源（`.sops.yaml` 裡改寫 `azure_keyvault:` / `gcp_kms:` / `kms:`），
所以從 L2 升到 L3 不需要改工作流程，只要換金鑰來源。

> [!tip] ★★★ 機關上雲的常見組合
> 「應用跑在地端、金鑰放雲端 KMS」是可行的，但要想清楚：
> **雲端斷線時你的服務起得來嗎？** 如果不行，就要有本機快取或離線備援金鑰，
> 而那份備援金鑰又回到 L1/L2 的保管問題。沒有免費的午餐。

### L4：HashiCorp Vault 的價值與代價 ★★★★★

Vault 能做到 L1～L3 做不到的事：

| 能力 | 說明 |
| --- | --- |
| **動態憑據** | ★★★★ 應用程式跟 Vault 要一組資料庫帳密，Vault **當場建立**一組 TTL 1 小時的帳號，到期自動刪除。外洩的影響只有一小時 |
| **完整稽核軌跡** | 誰在什麼時候讀了哪個機密，全都有紀錄 |
| **集中輪替** | 一個地方改，所有取用端下次取用就是新的 |
| **細緻權限** | 以路徑為單位的 policy，服務 A 讀不到服務 B 的機密 |
| **加密即服務** | 應用不碰金鑰，把資料丟給 Vault 加密（Transit 引擎） |

聽起來很好。**然後看代價：**

> [!danger] ★★★★★ 自架 Vault 的真實成本
> 1. **它是新的單點故障，而且是最致命的那個。**
>    Vault 掛掉 → 所有服務拿不到憑據 → 重啟後起不來。
>    你等於把「全機關的服務可用性」壓在一個新服務上。
> 2. **它必須自己做高可用。** 單台 Vault 不能上正式環境，
>    你需要 3 或 5 節點的叢集（Raft storage 或外部 Consul），還要處理節點升級。
> 3. ★★★★★ **unseal（解封）是最容易被低估的坑。**
>    Vault 每次重新啟動都處於 sealed 狀態，**必須提供 unseal key 才能運作**。
>    預設是 Shamir 秘密分割：5 把鑰匙、要 3 把才能解封。
>    這代表**停電復電、機器重開、更新重啟，都要有人拿著鑰匙來解封**。
>    半夜三點誰來解？鑰匙保管人請假怎麼辦？
>    自動解封（auto-unseal）要靠雲端 KMS 或 TPM —— 又繞回 L3 的依賴。
> 4. **它自己也要備份。** Vault 的資料要備份，備份要加密，加密金鑰要保管……
>    **機密管理系統自己的機密該放哪** 是個沒有終點的問題。
> 5. **root token 與 recovery key 的保管**是新的 C 類機密，而且是全機關最重要的那一份。
> 6. **應用程式要改。** 現有系統都是讀 `.env`，要改成呼叫 Vault API 或跑 Vault Agent。
>    委外開發的系統你可能改不動。

> [!tip] ★★★★★ 什麼規模才值得上 L4
> 大致的門檻（滿足**三項以上**再考慮）：
> - 主機數量 **50 台以上**，或服務數量 30 個以上
> - 有 **3 個以上團隊**需要不同的機密存取權
> - 有**稽核要求**必須回答「誰在何時讀了哪個機密」
> - 有**專責人力**（至少 1 人可以負責這套系統的維運與救援）
> - 有 24 小時待命機制可以處理 unseal
>
> 一般機關的資訊科（3～8 人、10～30 台主機）**做好 L2 就夠了**，
> 硬上 Vault 通常的結局是：導入半年、沒人敢重開機、最後回頭用 `.env`。
>
> 如果確實需要 L4，**優先用雲端託管的 Secret Manager**（Azure Key Vault、GCP Secret Manager），
> 把高可用與備份交給雲端業者，你只管權限設定。

### ★★★★★ 機密進了 git，怎麼辦

這是本篇最重要的一節。

#### 第一步：先掃，知道有多嚴重

用 git 內建工具做初步掃描（不用裝任何東西）：

```bash
# 搜尋所有歷史 commit 的內容（含已刪除的檔案）
git grep -n -i -E 'password|passwd|secret|api[_-]?key|token|BEGIN (RSA|EC|OPENSSH|PRIVATE)' \
  $(git rev-list --all) -- ':!*.md' | head -40
```

預期輸出（每一行是「commit:檔案:行號:內容」）：

```text
a3f9c21:config/database.php:12:    'password' => 'P@ssw0rd2019',
a3f9c21:.env:8:DB_PASSWORD=P@ssw0rd2019
7b2e884:deploy/prod.env:4:API_TOKEN=sk_live_9f3a2b7c1d8e
```

追某個字串是什麼時候進來、什麼時候被刪的：

```bash
git log --oneline -S 'P@ssw0rd2019' --all
```

預期輸出：

```text
d91c4a7 chore: 移除設定檔中的密碼
a3f9c21 feat: 加入資料庫設定
```

★★★★ 注意上面這個輸出：`d91c4a7` 這個 commit **把密碼刪掉了**，
但 `a3f9c21` 還在歷史裡 —— 任何人 clone 之後都能還原出來：

```bash
git show a3f9c21:.env
```

專用掃描工具（規則庫比手寫 grep 完整很多，能認出 AWS key、Slack token 等特定格式）：

```bash
# gitleaks：掃整個 git 歷史
gitleaks detect --source . --redact -v
```

```bash
# trufflehog：會嘗試「驗證」找到的金鑰是否還有效
trufflehog git file://. --only-verified
```

> [!warning] 未實機驗證
> `gitleaks` 在 8.19 版之後把子指令改成 `gitleaks git`（掃歷史）與 `gitleaks dir`（掃工作目錄），
> `detect` 仍可用但已標示為 deprecated。`trufflehog` 的子指令與旗標在 v3 之後也有變動。
> 兩者請以你安裝版本的 `--help` 為準，本篇只保證概念正確。

#### 第二步：★★★★★ 改掉 commit 不等於沒外流

這是最多人做錯的地方。發現密碼在 git 裡，第一反應通常是：

```bash
# ★★★★★ 這不是「解決」，這只是「藏起來」
git rebase -i HEAD~5      # 改掉那個 commit
git push --force
```

**為什麼這無效：**

| 事實 | 說明 |
| --- | --- |
| ★★★★★ **已經 clone 的人手上還有** | 任何 clone 過這個 repo 的筆電、CI runner、備份，都保有完整歷史 |
| ★★★★ **GitHub 的 fork 與 PR ref 不會跟著消失** | force push 之後，舊 commit 常常還能用完整 SHA 直接存取 |
| ★★★★ **搜尋機器人是即時的** | 公開 repo 上的金鑰通常在 **push 後幾分鐘內**就被自動掃走並嘗試使用 |
| ★★★ **鏡像／備份／CI 快取** | 內部的 GitLab 鏡像、Jenkins 的 workspace、備份系統都留有副本 |
| ★★★ **私有 repo 也一樣** | 「只有我們單位看得到」= 全單位＋所有歷任外包＋所有離職者 |

> [!danger] ★★★★★ 正確的處置順序
> 1. **輪替憑據**（改密碼、重發金鑰、撤銷憑證）—— **這是唯一真正有效的動作**
> 2. **檢查是否已被利用**：看該憑據對應服務的存取紀錄、登入來源 IP、異常帳單
> 3. **確認新憑據沒有再進 git**（`.gitignore` ＋ pre-commit hook）
> 4. **最後**才考慮要不要清理歷史 —— 而且清理是為了「不要繼續散布」，**不是為了補救**

#### 第三步：真的要清理歷史時

> [!danger] ★★★★★ 這是不可逆操作，而且會影響所有協作者
> 重寫歷史會讓**所有 commit SHA 改變**，代表：
> - 所有人的本機 branch 都要重新對齊（`git reset --hard origin/<branch>`），
>   未推送的本機工作**可能遺失**
> - 開啟中的 PR／MR 可能全部失效
> - 所有 tag 與 release 的對應關係要重建
> - CI 的快取與部署紀錄可能對不上
>
> **執行前務必：① 完整備份整個 repo（`git clone --mirror`）② 通知所有協作者停止推送**
>
> ```bash
> # 備份，這一步不能省
> git clone --mirror https://github.com/例/repo.git repo-backup.git
> tar czf repo-backup-$(date +%F).tar.gz repo-backup.git
> ```

工具用 `git-filter-repo`（官方推薦，取代已棄用的 `filter-branch`）：

```bash
sudo apt install -y git-filter-repo
```

```bash
# 在一份「乾淨的 clone」上操作，不要在日常工作目錄做
git clone https://github.com/例/repo.git repo-clean
cd repo-clean

# 方式一：把某個檔案從所有歷史移除
git filter-repo --invert-paths --path .env --path deploy/prod.env

# 方式二：把特定字串換掉（保留檔案、只換內容）
cat > /tmp/replacements.txt <<'EOF'
P@ssw0rd2019==>***REMOVED***
sk_live_9f3a2b7c1d8e==>***REMOVED***
EOF
git filter-repo --replace-text /tmp/replacements.txt
```

```bash
# 驗證：舊字串應該找不到了
git grep -n 'P@ssw0rd2019' $(git rev-list --all) | wc -l
```

預期輸出：

```text
0
```

推回遠端（`git-filter-repo` 會移除 origin，要重新加）：

```bash
git remote add origin https://github.com/例/repo.git
git push --force --all
git push --force --tags
```

最後**通知 GitHub／GitLab 管理者清理殘留的 ref 與快取**（GitHub 需要開 support ticket 才會清 fork 網路裡的殘留物件）。

#### 第四步：事前預防 ★★★★★

**`.gitignore`** —— 專案一建立就先寫好：

```gitignore
# 機密與環境設定
.env
.env.*
!.env.example
*.local.php
secrets.yaml
!secrets.enc.yaml

# 憑證與金鑰
*.key
*.pem
*.p12
*.pfx
*.jks
id_rsa
id_ed25519
*.keystore

# 備份與編輯器暫存（★★★★ 最常被漏掉的）
*.bak
*.old
*.orig
*~
.*.swp
```

> [!warning] ★★★★ `.gitignore` 對已追蹤的檔案無效
> 如果 `.env` 已經被 `git add` 過，加進 `.gitignore` **不會**讓它停止被追蹤。
> 要先移出索引：
>
> ```bash
> git rm --cached .env
> git commit -m "chore: 停止追蹤 .env"
> ```
>
> 注意這只是「以後不追蹤」，**歷史裡的那份還在**，仍須輪替。

**pre-commit hook** —— 在 commit 之前就擋下來：

```bash
cat > .git/hooks/pre-commit <<'EOF'
#!/bin/bash
# 簡易機密檢查：擋住明顯的密碼與私鑰
set -e

PATTERN='(BEGIN (RSA |EC |OPENSSH |)PRIVATE KEY|AKIA[0-9A-Z]{16}|sk_live_[0-9a-zA-Z]{16,}|(password|passwd|secret|api_key|token)[[:space:]]*[:=][[:space:]]*["'"'"']?[^"'"'"'[:space:]]{8,})'

if git diff --cached --name-only --diff-filter=ACM | grep -qE '\.(env|pem|key|p12|pfx)$'; then
    echo "✗ 偵測到疑似機密檔案被加入 commit：" >&2
    git diff --cached --name-only --diff-filter=ACM | grep -E '\.(env|pem|key|p12|pfx)$' >&2
    echo "  若確定要提交，請用 git commit --no-verify" >&2
    exit 1
fi

if git diff --cached -U0 | grep -nE "^\+" | grep -qiE "$PATTERN"; then
    echo "✗ 偵測到疑似機密內容：" >&2
    git diff --cached -U0 | grep -nE "^\+" | grep -iE "$PATTERN" | head -5 >&2
    echo "  若為誤判，請用 git commit --no-verify" >&2
    exit 1
fi

exit 0
EOF
chmod +x .git/hooks/pre-commit
```

測試它有效：

```bash
echo "DB_PASSWORD=SuperSecret123" >> config.txt
git add config.txt
git commit -m "test"
```

預期輸出：

```text
✗ 偵測到疑似機密內容：
2:+DB_PASSWORD=SuperSecret123
  若為誤判，請用 git commit --no-verify
```

> [!warning] ★★★ hook 不會跟著 clone 走
> `.git/hooks/` 不在版控裡，所以新成員 clone 之後**不會**自動有這個 hook。
> 解法是把 hook 腳本放進 repo（例如 `.githooks/`），並在專案 README 要求執行一次：
>
> ```bash
> git config core.hooksPath .githooks
> ```
>
> 或使用 `pre-commit` 框架統一管理。**但無論如何，hook 都是本機的，可以被 `--no-verify` 繞過**
> —— 真正的防線是伺服器端的推送檢查（GitHub push protection、GitLab secret detection）。

**`_設定檔範例/` 只放範本** —— 本手冊的做法，也建議套用到你的專案：

```bash
# 進 git 的是 .env.example，值全部是佔位符
cat .env.example
```

```ini
APP_ENV=production
APP_DEBUG=false
DB_HOST=127.0.0.1
DB_DATABASE=CHANGE_ME
DB_USERNAME=CHANGE_ME
DB_PASSWORD=CHANGE_ME
MAIL_PASSWORD=CHANGE_ME
```

> [!tip] ★★★ 佔位符要「明顯是假的」
> 不要寫 `DB_PASSWORD=password123` 當範例 —— 有人會直接用。
> 用 `CHANGE_ME`、`<請填入>`、`REPLACE_WITH_REAL_VALUE` 這種**不可能是真值**的字樣，
> 部署腳本還可以據此檢查：
>
> ```bash
> grep -n 'CHANGE_ME' /var/www/myapp/.env && { echo "還有未填的設定！"; exit 1; }
> ```

### 憑證私鑰的保護 ★★★★★

私鑰是最典型的 C 類機密，值得單獨一節。

```bash
# 標準做法：私鑰放 /etc/ssl/private，目錄本身就要收好
sudo mkdir -p /etc/ssl/private
sudo chown root:root /etc/ssl/private
sudo chmod 700 /etc/ssl/private

sudo install -o root -g root -m 600 example.gov.tw.key /etc/ssl/private/
sudo install -o root -g root -m 644 example.gov.tw.crt /etc/ssl/certs/

ls -l /etc/ssl/private/ /etc/ssl/certs/example.gov.tw.crt
```

預期輸出：

```text
/etc/ssl/private/:
total 4
-rw------- 1 root root 1704 Sep  3 11:02 example.gov.tw.key

-rw-r--r-- 1 root root 1854 Sep  3 11:02 /etc/ssl/certs/example.gov.tw.crt
```

| 規則 | 說明 |
| --- | --- |
| ★★★★★ **私鑰在哪台伺服器產生，就留在哪台** | CSR 送出去、憑證拿回來，私鑰全程不移動。見 [[090-01-02-guide-PKI-CSR產生與req設定檔]] |
| ★★★★★ **不要把私鑰交給廠商** | 廠商說「私鑰給我我幫你裝」= 你的網站身分交給了廠商全體員工。正確做法是**廠商到你的機器上裝**，或**你自己裝** |
| ★★★★ **不要用郵件、LINE 傳私鑰** | 真的必須傳（例如負載平衡器要同一份），用 `age -p` 加密後傳，密碼走另一個管道 |
| ★★★★ **`.pfx`／`.p12` 一定要設密碼** | 這種格式把憑證與私鑰打包在一起，沒密碼等於裸奔。轉檔方式見 [[090-01-11-guide-PKI-憑證格式轉換與檢視工具]] |
| ★★★★ **備份，但要加密** | 私鑰遺失＝要重新簽發。備份一份加密的離線副本（見下方） |
| ★★★ **Nginx worker 不需要讀私鑰** | Nginx master 以 root 啟動時讀取私鑰後才降權，所以私鑰是 `600 root:root` 也能正常運作 |

私鑰的加密備份（放進安全的離線位置）：

```bash
sudo tar czf - -C /etc/ssl private certs/example.gov.tw.crt \
  | age -p -o ~/ssl-backup-$(date +%F).tar.gz.age
```

預期輸出：

```text
Enter passphrase (leave empty to autogenerate a secure one):
Confirm passphrase:
```

還原：

```bash
age -d ~/ssl-backup-2026-09-03.tar.gz.age | sudo tar xzf - -C /etc/ssl
sudo chmod 700 /etc/ssl/private
sudo chmod 600 /etc/ssl/private/*.key
```

> [!danger] ★★★★★ 私鑰遺失的後果
> - **伺服器憑證私鑰遺失** → 憑證作廢，必須重新產生 CSR、重新申請。
>   跟 GCA／TWCA 申請的憑證要走完整申請流程，**可能要好幾天**，期間網站沒有有效憑證。
>   申請流程見 [[090-01-14-guide-PKI-機關憑證來源GCA與TWCA]]。
> - ★★★★★ **自建 CA 的根私鑰遺失** → **無法再簽發任何新憑證、無法簽發 CRL**。
>   整條憑證鏈作廢，所有派送出去的根憑證都要重來一次。
>   自建 CA 的私鑰保管請看 [[090-01-06-guide-PKI-自建根CA]]。
> - **程式碼簽章金鑰遺失** → 舊版程式仍有效，但你再也發不出新版更新。

### 輪替：什麼該換、多久換、怎麼不中斷 ★★★★

#### 該不該定期換

| 機密類型 | 建議週期 | 觸發式輪替（**比定期更重要**） |
| --- | --- | --- |
| 資料庫密碼（A 類） | ★★ 12～24 個月 | ★★★★★ 人員異動、廠商更換、疑似外洩 |
| API 金鑰 / Token（B 類） | ★★★ 6～12 個月 | ★★★★★ 同上，加「進了 git」「貼到群組」 |
| CI/CD 部署 Token | ★★★ 6 個月 | ★★★★ CI 平台變更、pipeline 外洩日誌 |
| SSH 部署金鑰 | ★★ 12 個月 | ★★★★ 人員異動 |
| 伺服器憑證私鑰 | ★★★ 跟著憑證換發（1 年或 90 天） | ★★★★★ 私鑰外洩 → 立即撤銷 |
| 加密主金鑰（C 類） | ★ 不建議頻繁換（換了要重新加密所有資料） | ★★★★★ 確認外洩才換，且要有完整的重新加密計畫 |

> [!note] ★★★★ 「定期換密碼」在機器憑據上意義不大
> 對人用的密碼，強制 90 天換一次已經被證實**降低**安全性（大家會用 `Pass01!`→`Pass02!`）。
> 對機器憑據，重點也不是週期，而是：
> **① 出事時能快速換掉 ② 換的時候不會中斷服務 ③ 換完舊的真的失效。**
> 有這三個能力，週期長一點沒關係；沒有這三個能力，週期再短也沒用。

#### 雙金鑰並行期（zero-downtime rotation）★★★★★

換 API 金鑰時最怕的是「舊的關掉、新的還沒生效」。標準做法是留一段**兩把都有效**的重疊期：

```text
時間軸 ────────────────────────────────────────────►

  舊金鑰 ████████████████████████░░░░░░░░░░░
  新金鑰           ░░░░████████████████████████████
                   ↑    ↑              ↑        ↑
                   │    │              │        │
              ①建立新的 ②部署到所有  ③確認新的  ④撤銷舊的
                        取用端        有流量
```

實際步驟：

```bash
# ① 在服務商後台建立第二把金鑰（不要動舊的）
#    大多數平台支援同時存在多把，例如 Stripe、GitHub、雲端業者

# ② 更新機密檔並部署（用 sops 的話）
sops secrets/prod/app.yaml       # 把 payment_key 改成新值
git commit -am "chore: 輪替金流 API 金鑰"
git push
./deploy.sh                       # 部署到所有節點

# ③ 確認每個節點都在用新金鑰
for h in web01 web02 web03; do
  echo -n "$h: "
  ssh "$h" "sudo grep -c 'sk_live_NEWKEY' /var/www/myapp/.env"
done
```

預期輸出：

```text
web01: 1
web02: 1
web03: 1
```

```bash
# ④ 觀察 24～72 小時（確認排程工作、批次作業也都換過了），
#    到服務商後台看舊金鑰的「最後使用時間」，確定沒有流量後再撤銷
```

> [!warning] ★★★★ 最容易漏掉的取用端
> 換金鑰時常常漏掉這些地方，導致「換完隔天半夜批次掛掉」：
> - **cron／systemd timer** 裡的備份腳本、報表程式
> - **CI/CD 的環境變數**（GitHub Actions Secrets、GitLab CI Variables）
> - **另一台機器**上的同一個服務（負載平衡的第二節點）
> - **測試環境**（雖然不影響正式，但下次要用時才發現壞了）
> - **監控系統**用來檢查健康狀態的 Token
>
> ★★★★★ **輪替前先做一次「取用端盤點」，寫成清單。** 清單本身就是最有價值的產出。

#### 不支援雙金鑰時怎麼辦（例如資料庫密碼）★★★★

MySQL 一個帳號只有一個密碼，沒辦法雙密碼並行。做法是**建立新帳號而不是改密碼**：

```sql
-- ① 建立新帳號，權限與舊的相同
CREATE USER 'myapp_v2'@'10.0.1.%' IDENTIFIED BY '新的長亂密碼';
GRANT SELECT, INSERT, UPDATE, DELETE ON myapp.* TO 'myapp_v2'@'10.0.1.%';
FLUSH PRIVILEGES;
```

```bash
# ② 逐台切換設定並重啟服務（滾動更新，服務不中斷）
# ③ 確認沒有連線再用舊帳號
```

```sql
-- ③ 檢查舊帳號還有沒有連線
SELECT user, host, COUNT(*) FROM information_schema.processlist GROUP BY user, host;
```

預期輸出：

```text
+-----------+-------------+----------+
| user      | host        | COUNT(*) |
+-----------+-------------+----------+
| myapp_v2  | 10.0.1.11   |        8 |
| myapp_v2  | 10.0.1.12   |        7 |
+-----------+-------------+----------+
```

```sql
-- ④ 確定舊帳號沒有連線了，才刪除
DROP USER 'myapp'@'10.0.1.%';
```

> [!danger] ★★★★★ 不要用 `ALTER USER ... IDENTIFIED BY` 直接改密碼
> 改的瞬間，**所有還在用舊密碼的連線在重連時全部失敗**，
> 而你通常不會同時完成所有節點的設定更新。
> 「建新帳號 → 滾動切換 → 刪舊帳號」多花十分鐘，換來零停機。
> 帳號權限操作見 [[060-04-01-02-cmd-MySQL-使用者與權限]]。

## 完整實戰範例

**情境**：接手一套機關的公務系統，Nginx ＋ MySQL ＋ Laravel，跑在 Ubuntu 24.04。
原承辦已離職，機密散落各處，而且專案 repo 裡有 `.env`。
目標：**盤點 → 分級 → 收攏到 sops＋age → 部署時解密 → 驗證**。

環境假設：

| 項目 | 值 |
| --- | --- |
| 主機 | `web01`（Ubuntu 24.04），app 在 `/var/www/myapp` |
| 服務帳號 | `www-data`（PHP-FPM）、`myapp`（佇列 worker） |
| repo | `git@gitlab.example.gov.tw:it/myapp.git` |
| 你的工作機 | 一台 Ubuntu 桌機，已裝 `age`、`sops`、`git` |

### 步驟 1：盤點 —— 找出所有機密在哪裡 ★★★★★

```bash
cd /var/www/myapp

# 1-1 找出所有疑似機密的檔案
sudo find /var/www/myapp /etc/nginx /etc/mysql /etc/myapp \
  \( -name '*.env*' -o -name '*.key' -o -name '*.pem' -o -name 'my.cnf' -o -name '*.p12' \) \
  -type f -printf '%M %u:%g %p\n' 2>/dev/null
```

預期輸出（**問題一眼就看得出來**）：

```text
-rw-r--r-- root:root /var/www/myapp/.env
-rw-r--r-- root:root /var/www/myapp/.env.bak
-rw-r--r-- www-data:www-data /var/www/myapp/.env.old
-rw------- root:root /etc/ssl/private/example.gov.tw.key
-rw-rw-r-- root:root /etc/mysql/conf.d/backup.cnf
```


> [!danger] ★★★★ Laravel 的 `APP_KEY` 是特例，不要隨手換
> `APP_KEY` 用來加密 session、cookie，以及 `encrypted` 型別的資料庫欄位。
> **換掉之後：**
> - 所有使用者的 session 失效（會被登出）—— 可接受
> - ★★★★★ **資料庫裡用 `Crypt::encrypt()` 或 `encrypted` cast 存的欄位會全部解不開**
>
> 換之前一定要先確認有沒有加密欄位：
>
> ```bash
> grep -rn "encrypted\|Crypt::" /var/www/myapp/app/Models /var/www/myapp/app/Http | head
> ```
>
> 有的話，正確流程是：**用舊 key 讀出 → 換 key → 用新 key 寫回**，
> 要寫一支一次性的 migration 腳本，並在測試環境演練過。
> 沒有加密欄位的話，直接 `php artisan key:generate` 即可。

### 步驟 5：部署時解密 ★★★★★

在 `web01` 上寫一支部署腳本，把 sops 檔轉成 Laravel 要的 `.env`：

```bash
#!/bin/bash
# /usr/local/sbin/myapp-render-env.sh
# 用途：從 sops 加密檔產生 /var/www/myapp/.env
set -euo pipefail

REPO=/var/www/myapp
SECRET_FILE="${REPO}/secrets/prod/app.yaml"
TARGET="${REPO}/.env"
TMP="$(mktemp)"
export SOPS_AGE_KEY_FILE=/etc/sops/age/keys.txt

# ★★★★ mktemp 預設就是 600，但明確設一次比較安心
chmod 600 "$TMP"
trap 'rm -f "$TMP"' EXIT

get() { sops --decrypt --extract "$1" "$SECRET_FILE"; }

cat > "$TMP" <<EOF
APP_NAME=MyApp
APP_ENV=production
APP_DEBUG=false
APP_URL=https://myapp.example.gov.tw
APP_KEY=$(get '["app"]["key"]')

DB_CONNECTION=mysql
DB_HOST=$(get '["db"]["host"]')
DB_PORT=3306
DB_DATABASE=$(get '["db"]["database"]')
DB_USERNAME=$(get '["db"]["username"]')
DB_PASSWORD=$(get '["db"]["password"]')

MAIL_MAILER=smtp
MAIL_HOST=$(get '["mail"]["host"]')
MAIL_PORT=$(get '["mail"]["port"]')
MAIL_USERNAME=$(get '["mail"]["username"]')
MAIL_PASSWORD=$(get '["mail"]["password"]')

SMS_API_KEY=$(get '["services"]["sms_api_key"]')
PAYMENT_SECRET=$(get '["services"]["payment_secret"]')
EOF

# ★★★★ 檢查沒有空值（解密失敗時會產生空字串，比報錯更難查）
if grep -nE '=$' "$TMP"; then
    echo "✗ 有欄位是空的，解密可能失敗，中止部署" >&2
    exit 1
fi

install -o root -g www-data -m 640 "$TMP" "$TARGET"
echo "✓ 已產生 ${TARGET}"
```

## 常見錯誤與排錯

| # | 現象 | 原因 | 解法 |
| --- | --- | --- | --- |
| 1 | `sops --decrypt` 回 `Failed to get the data key required to decrypt the SOPS file.` | 本機找不到對應的 age 私鑰，或私鑰不在 `.sops.yaml` 列出的收件者裡 | 確認 `SOPS_AGE_KEY_FILE` 指到正確檔案；`grep 'public key' <keys.txt>` 比對 `.sops.yaml`；若確實沒被加入，請管理者 `sops updatekeys` |
| 2 | `sops` 開啟編輯器後存檔，卻出現 `Failed to compare document version` 或內容沒變 | ★★★ 編輯器是「另存新檔＋改名」型（如某些 vim 設定），sops 抓不到修改 | 用 `EDITOR='nano'` 或 `EDITOR='vim -c "set backupcopy=yes"' sops file.yaml` |
| 3 | 應用程式報 `SQLSTATE[HY000] [1045] Access denied for user 'myapp'@'localhost'` | ★★★★ `.env` 更新了但 Laravel 讀的是快取設定 | `php artisan config:clear && php artisan config:cache`，再 `systemctl reload php8.3-fpm` |
| 4 | 改了 `.env` 但服務完全沒反應 | ★★★★ `EnvironmentFile` 的內容只在**服務啟動時**讀取，`reload` 不會重讀 | `systemctl restart <unit>`（不是 `reload`）；確認 `systemctl show <unit> -p EnvironmentFiles` |
| 5 | `EnvironmentFile` 的值有引號、被當成字串的一部分 | ★★★ systemd 的 env 檔語法與 shell 不同，`FOO="bar"` 可能保留引號 | 值不要加引號；含空白時整行用 `FOO=bar baz`；含 `$` 要寫成 `$$` |
| 6 | 密碼裡有 `#`，讀進來被截斷 | ★★★ `#` 在 env 檔與 `.env` 裡是註解起始 | 密碼避開 `#`；或改用 `sops --extract` 直接取值而非經過 env 檔 |
| 7 | `nginx: [emerg] cannot load certificate key ... Permission denied` | 私鑰權限或目錄權限太緊／SELinux context 錯 | 私鑰 `600 root:root`、`/etc/ssl/private` 為 `700 root:root`；RHEL 系跑 `sudo restorecon -Rv /etc/ssl` |
| 8 | 加了 `.gitignore` 但 `.env` 還是被 commit | ★★★★ `.gitignore` 對**已追蹤**的檔案無效 | `git rm --cached .env` 後再 commit；並記得歷史裡那份仍須**輪替** |
| 9 | pre-commit hook 沒作用 | ★★★ hook 不在版控裡，新 clone 的 repo 沒有 | 把 hook 放 `.githooks/` 並 `git config core.hooksPath .githooks`；伺服器端另設 push protection |
| 10 | `git filter-repo` 回 `Refusing to destructively overwrite repo history` | ★★★★ 它要求在「乾淨的新 clone」上執行，避免誤刪本機工作 | 重新 `git clone` 一份再操作；真的要在原地執行才加 `--force`（**先備份**） |
| 11 | force push 之後，GitHub 上舊 commit 用完整 SHA 還是打得開 | ★★★★★ 平台保留 unreachable object 一段時間，fork 網路更是不會清 | ★★★★★ 這正是「改歷史不等於沒外流」的證據 —— **已輪替憑據才是解決方案**；另外開 support ticket 請平台清理 |
| 12 | `systemd-creds encrypt` 回 `Failed to determine host key` 或找不到指令 | systemd 版本低於 250（Ubuntu 22.04 是 249） | `systemctl --version` 確認；版本不足就改用 L2（sops）方案 |
| 13 | 換到新機器後 `systemd-creds decrypt` 全部失敗 | ★★★★★ 加密綁定 `/var/lib/systemd/credential.secret`，換機就失效 | 重灌／換機**前**先解密出明文並另存；或一開始就別用 systemd-creds 做跨機共用 |
| 14 | 部署腳本產生的 `.env` 有空值，網站白畫面 | ★★★★ `sops --extract` 路徑寫錯時回空字串而非報錯 | 腳本加上「檢查空值就中止」的判斷（見實戰範例步驟 5）；`set -o pipefail` 也要開 |
| 15 | 輪替 API 金鑰後隔天半夜批次失敗 | ★★★★★ 漏掉 cron／CI／第二節點等取用端 | 輪替前先做**取用端盤點**；保留雙金鑰重疊期，觀察舊金鑰「最後使用時間」為零才撤銷 |
| 16 | 換掉 Laravel `APP_KEY` 後，某些欄位讀出來是亂碼或拋 `DecryptException` | ★★★★★ 資料庫裡有用舊 key 加密的欄位 | 還原舊 `APP_KEY` 先救回服務；再寫「舊 key 解密→新 key 加密」的一次性腳本並在測試環境演練 |
| 17 | `age-keygen` 產生的檔案被同事看到 | 預設權限依 umask，可能是 `644` | ★★★★ 產生後立刻 `chmod 600`；並把這一步寫進 SOP |
| 18 | 掃描工具回報一堆誤判（測試資料、範例值） | 規則太寬 | 用 `.gitleaksignore` 或工具的 allowlist 標註；★★★ **不要因為誤判多就關掉掃描** |

## 安全性注意事項

> [!danger] ★★★★★ 五條不能違反的鐵律
> 1. **憑據一旦離開你的控制範圍，就當作已外洩，立刻輪替。** 不要花時間爭論「應該沒人看到」。
> 2. **改 git 歷史不是補救措施。** 它只防止繼續散布，救不回已經散出去的。
> 3. **私鑰不離開產生它的伺服器。** 不給廠商、不走郵件、不進即時通訊。
> 4. **不可逆操作前先備份。** 改歷史前 `git clone --mirror`；換 `APP_KEY` 前確認沒有加密欄位。
> 5. **一定要有備援金鑰（break-glass）並登記保管人。** 沒有它，人一走你就打不開自己的機密。

> [!warning] ★★★★ 常見的錯誤安全感
> | 你以為 | 實際上 |
> | --- | --- |
> | 「repo 是私有的，沒關係」 | 全單位＋所有歷任外包＋所有離職者的筆電上都有一份 |
> | 「我用 base64 編碼了」 | ★★★★★ base64 **不是加密**，`base64 -d` 一秒解開 |
> | 「密碼很長很亂，猜不到」 | 外洩的密碼不需要被猜，直接複製貼上就能用 |
> | 「改用環境變數就安全了」 | `/proc/<pid>/environ`、子程序繼承、debug 頁面、core dump 都會洩漏 |
> | 「檔案是 600 就安全了」 | root 與被入侵的同 UID 服務照樣讀得到；上層目錄權限也要看 |
> | 「有 Vault 就不用管權限了」 | Vault 的 policy 設錯，等於把全部機密開放給所有服務 |
> | 「加密後放雲端硬碟很安全」 | 解密金鑰如果也在同一個雲端硬碟，等於沒加密 |

> [!warning] ★★★★ 稽核與法遵面
> - **個資法**：機關系統若處理個人資料，資料庫憑據外洩導致個資外洩，
>   須依規定通報並通知當事人。相關要求見 [[090-07-07-guide-資安實踐-台灣資安法規與個資法]]。
> - **資安法**：公務機關的資安事件有通報時限，機密外洩屬於應通報事項。
>   流程見 [[090-07-04-guide-資安實踐-資安事件應變流程]]。
> - **委外管理**：把私鑰或系統帳密交給廠商，責任仍在機關。
>   契約應明訂憑據保管與返還規定，見 [[090-07-11-guide-資安實踐-委外與供應鏈資安]]。
> - **稽核**：稽核常見的缺失是「密碼表放共用磁碟」「無輪替紀錄」「離職未收回權限」。
>   本篇步驟 7 的三份文件正是用來應付這些問題的。

> [!tip] ★★★ 給主管的一句話版本
> 「我們現在的做法是：機密加密後才進版控，解密金鑰只有維運人員與伺服器有，
> 保險櫃裡有一把備援金鑰。誰改了哪個機密、什麼時候改的，git 紀錄查得到。
> 人員異動時走固定的移除與輪替程序。」
> —— 能講出這段話，就代表 L2 落地了。

### 檔案權限速查 ★★★★

| 對象 | 擁有者 | 權限 | 檢查指令 |
| --- | --- | --- | --- |
| `/etc/myapp/env`（systemd 用） | `root:root` | `600` | `stat -c '%A %U:%G %n' /etc/myapp/env` |
| `.env`（PHP-FPM 要讀） | `root:www-data` | `640` | 同上 |
| `/etc/ssl/private/` 目錄 | `root:root` | `700` | `ls -ld /etc/ssl/private` |
| 憑證私鑰 `*.key` | `root:root` | `600` | `ls -l /etc/ssl/private/` |
| 憑證 `*.crt` | `root:root` | `644` | 公開資訊，可讀 |
| `~/.my.cnf` | 該使用者 | `600` | `ls -l ~/.my.cnf` |
| age 私鑰 `keys.txt` | 該使用者／`root` | `600` | `ls -l ~/.config/sops/age/keys.txt` |

### age 常用指令 ★★★

| 指令 | 作用 |
| --- | --- |
| `age-keygen -o keys.txt` | 產生金鑰對，公鑰印在畫面上 |
| `age-keygen -y keys.txt` | 從私鑰檔反推公鑰 |
| `age -r <公鑰> -o out.age in` | 用公鑰加密 |
| `age -d -i keys.txt out.age` | 用私鑰解密到 stdout |
| `age -p -o out.age in` | 用密碼（passphrase）加密 |
| `age -d out.age` | 密碼模式解密（會提示輸入） |
| `age -R recipients.txt -o out.age in` | 收件者清單放檔案裡（多人共用） |

### sops 常用指令 ★★★★

| 指令 | 作用 |
| --- | --- |
| `sops --encrypt --in-place f.yaml` | 原地加密 |
| `sops --decrypt f.yaml` | 解密輸出到 stdout（**不改檔案**） |
| `sops f.yaml` | 開編輯器改明文，存檔後自動重新加密 |
| `sops --decrypt --extract '["db"]["password"]' f.yaml` | 只取一個值 |
| `sops updatekeys f.yaml` | 依 `.sops.yaml` 重新設定收件者 |
| `sops --rotate --in-place f.yaml` | 換一把新的資料金鑰重新加密 |
| `sops --encrypted-regex '^(password\|token)$' ...` | 只加密符合的鍵 |
| `SOPS_AGE_KEY_FILE=/path/keys.txt sops -d f.yaml` | 指定私鑰位置（腳本必用） |

### 機密分類與處理原則 ★★★★

| 類別 | 例子 | 輪替 | 存放 |
| --- | --- | --- | --- |
| A 長期不變 | DB 密碼、SMTP | 12～24 月／人員異動 | L1 檔案權限起，L2 更佳 |
| B 會輪替 | API 金鑰、Token | 6～12 月／異動即換 | L2 以上，要有雙金鑰程序 |
| C 絕不可外流 | 憑證私鑰、簽章金鑰、主金鑰 | 只在外洩時換 | 不離開伺服器 ＋ 加密離線備份 |

### 四個層級對照 ★★★★★

| 層級 | 工具 | 進 git？ | 主要風險 |
| --- | --- | --- | --- |
| L1 | `chmod 600` ＋ `EnvironmentFile` | ✗ | 多機同步靠人工、無稽核 |
| L2 | `sops` ＋ `age` | ✓（加密後） | 解密金鑰的派送與回收 |
| L3 | `systemd-creds` / 雲端 KMS | ✗ / ✓ | 綁定主機或雲端平台 |
| L4 | HashiCorp Vault | ✗ | ★★★★★ 新的單點故障、unseal、自身備份 |

### 輪替檢查清單 ★★★★

| 步驟 | 確認事項 |
| --- | --- |
| 1 | 已盤點**所有取用端**（app、cron、CI、第二節點、監控） |
| 2 | 新憑據已建立，**舊的還沒關** |
| 3 | 逐台部署並驗證（不是「應該有部署到」） |
| 4 | 服務商後台顯示舊憑據**最後使用時間**已停止 |

## 練習題

> [!example] 練習 1：把不安全的設定檔收好（★★）
> 在你的測試機上建立一個 `644` 的 `.env`，內含假密碼。
> 1. 用 `sudo -u nobody cat` 驗證「任何人都讀得到」
> 2. 改成 `root:www-data` `640`
> 3. 再驗證一次，確認 `nobody` 讀不到、`www-data` 讀得到
> 4. 額外檢查上層目錄權限
>
> > [!question]- 參考解答
> > ```bash
> > echo "DB_PASSWORD=test1234" | sudo tee /tmp/lab/.env >/dev/null
> > sudo chmod 644 /tmp/lab/.env
> > sudo -u nobody cat /tmp/lab/.env        # 讀得到 → 有問題
> >
> > sudo chown root:www-data /tmp/lab/.env
> > sudo chmod 640 /tmp/lab/.env
> > sudo -u nobody cat /tmp/lab/.env        # cat: Permission denied ✓
> > sudo -u www-data cat /tmp/lab/.env      # 讀得到 ✓
> > ls -ld /tmp/lab                          # 確認目錄不是 777
> > ```
> > 重點：**檔案權限與目錄權限要一起看**，而且要用「另一個帳號實際試一次」，
> > 不能只看 `ls -l` 的數字就當作沒事。

> [!example] 練習 2：sops ＋ age 完整走一遍（★★★）
> 1. 產生兩把 age 金鑰（模擬「你」與「伺服器」）
> 2. 寫 `.sops.yaml`，讓兩把都能解
> 3. 加密一個含三個密碼的 YAML
> 4. 用第二把私鑰解密成功
> 5. 從 `.sops.yaml` 移除第二把、跑 `sops updatekeys`，驗證第二把**再也解不開新檔**
> 6. 用步驟 4 存下來的**舊檔**再解一次 —— 觀察結果
>
> > [!question]- 參考解答
> > 步驟 6 的結果是**舊檔仍然解得開**。
> > 這正是本篇強調的重點：★★★★★ **`updatekeys` 只保護未來的檔案，
> > 保護不了已經被別人拿走的舊副本。** 所以移除人員之後，
> > 一定要接著**輪替他曾經解得開的所有機密**。

> [!example] 練習 3：模擬機密外洩並演練處置（★★★★）
> 建一個測試 repo：
> 1. commit 一個含假 API 金鑰的檔案，再 commit 一次把它刪掉
> 2. 用 `git log -S` 與 `git show <sha>:<path>` 證明「刪了還在」
> 3. 寫出完整的處置順序（不必真的改歷史）
>
> > [!question]- 參考解答
> > ```bash
> > git log --oneline -S 'sk_test_ABC123' --all
> > git show <第一個sha>:secret.txt      # 內容還在
> > ```
> > 處置順序：
> > 1. ★★★★★ **輪替**（重發 API 金鑰）—— 第一步、也是唯一有效的一步
> > 2. 檢查該金鑰的使用紀錄有無異常
> > 3. 加 `.gitignore` ＋ pre-commit hook
> > 4. 備份 repo（`git clone --mirror`）
> > 5. 通知協作者停止推送
> > 6. `git filter-repo` 清理歷史 ＋ force push
> > 7. 請平台管理者清理殘留 ref
> >
> > 順序不能顛倒 —— 先清歷史再輪替，等於在攻擊者已經拿到金鑰的期間什麼都沒做。

> [!example] 練習 4：無停機輪替資料庫密碼（★★★★）
> 在測試環境的 MySQL 上，用「建新帳號」的方式把應用的 DB 憑據換掉，
> 全程用 `curl` 監看網站，確認**沒有任何一次 5xx**。
>
> > [!question]- 參考解答
> > 監看用一個迴圈：
> > ```bash
> > while true; do
> >   printf '%s %s\n' "$(date +%T)" "$(curl -s -o /dev/null -w '%{http_code}' http://localhost/)"
> >   sleep 1
> > done
> > ```
> > 然後依序：`CREATE USER` → `GRANT` → 改 `.env` → `config:cache` → `reload php-fpm`
> > → 確認 `processlist` 沒有舊帳號 → `DROP USER`。
> > 用 `reload`（不是 `restart`）PHP-FPM 可以做到優雅重載，正在處理的請求會跑完。

> [!example] 練習 5：驗證環境變數會外洩（★★★）
> 寫一個會 sleep 的小腳本，用 `EnvironmentFile` 帶一個假密碼跑成 systemd 服務。
> 用同一個 UID 的另一個 shell 讀 `/proc/<pid>/environ`，證明讀得到。
> 然後改用 `LoadCredentialEncrypted`（systemd ≥ 250），再測一次。
>
> > [!question]- 參考解答
> > ```bash
> > sudo tr '\0' '\n' < /proc/$(systemctl show mylab -p MainPID --value)/environ | grep PASS
> > ```
> > 用 `EnvironmentFile` 時讀得到；改成 `LoadCredentialEncrypted` 之後，
> > 環境變數裡只有 `CREDENTIALS_DIRECTORY` 路徑，密碼在該目錄的 tmpfs 檔案中，
> > 且該目錄只有服務帳號能讀。★★★ 這就是 L3 相對 L1 的實質改善。

## 小測驗

Q1. （選擇）你發現三年前的 commit 裡有正式環境的資料庫密碼，該 commit 早就被後續 commit 刪掉了。
第一件該做的事是？
　A. `git filter-repo` 清掉那個 commit
　B. `git push --force` 覆蓋遠端
　C. 立刻更換資料庫密碼
　D. 把 repo 改成私有

Q2. （是非）把密碼寫在 systemd unit 檔的 `Environment=` 裡，因為 unit 檔是 `644 root:root`，
所以只有 root 看得到。

Q3. 「這行指令會發生什麼」
```bash
sudo tr '\0' '\n' < /proc/2481/environ | grep -i pass
```

Q4. （選擇）`sops` 加密後的 YAML 檔可以安全地推進 git，主要原因是？
　A. git 會自動加密所有檔案
　B. 只有「值」被加密，鍵名保留明文，所以可 diff、可 merge，而值是密文
　C. sops 會把檔案改成二進位，git 讀不懂
　D. 因為 `.gitignore` 會擋住它

Q5. （簡答）某同事離職，你從 `.sops.yaml` 移除他的公鑰並執行了 `sops updatekeys`。
這樣做**還不夠**，為什麼？還要做什麼？

Q6. （是非）`age` 的 `AGE-SECRET-KEY-1...` 開頭那一行可以放進 git，因為它已經是編碼過的格式。

Q7. （選擇）下列哪一項**不是**自架 HashiCorp Vault 的主要代價？
　A. 每次重啟都需要 unseal
　B. 它自己需要高可用叢集
　C. 它自己的資料也要備份
　D. 它不支援資料庫密碼的動態發放

Q8. （簡答）為什麼「換 Laravel 的 `APP_KEY`」不能像換 SMTP 密碼那樣隨手做？

Q9. 「這行指令會發生什麼」
```bash
mysqldump -u backup -pP@ssw0rd mydb > dump.sql
```

Q10. （選擇）輪替一把 API 金鑰時，正確的順序是？
　A. 撤銷舊的 → 建立新的 → 部署
　B. 建立新的 → 部署到所有取用端 → 確認舊的無流量 → 撤銷舊的
　C. 建立新的 → 撤銷舊的 → 部署
　D. 同時建立新的與撤銷舊的，再部署

> [!question]- 測驗答案
> **Q1: C。** ★★★★★ 一旦推上遠端就要當作已外洩，**輪替是唯一真正有效的動作**。
> A、B 只是把痕跡擦掉，所有 clone 過的人手上仍有完整歷史；D 更是毫無作用。
> 見「機密進了 git，怎麼辦 → 第二步」。
>
> **Q2: 錯。** ★★★★★ `systemctl show <unit> -p Environment` **不需要 root** 就能執行，
> 任何本機使用者都看得到 `Environment=` 的值。密碼一律用 `EnvironmentFile=` 指向 `600` 的檔案。
> 見「L1-2：systemd 的 EnvironmentFile」。
>
> **Q3:** 把 PID 2481 這個程序的完整環境變數（以 NUL 分隔）轉成換行分隔後印出，
> 並過濾出含 `pass` 的行 —— 也就是**把該服務的密碼撈出來**。
> ★★★★ 這說明環境變數不是保險箱：同 UID 的程序與 root 都讀得到。
> 見「L1-3：環境變數不是保險箱」。
>
> **Q4: B。** sops 的設計就是「加密值、保留結構」，所以 `git diff` 看得出誰改了哪個鍵，
> 但看不到新值；合併衝突也能正常處理。見「L2：用 sops 加密設定檔」。
>
> **Q5:** ★★★★★ 因為他手上**留有舊版的加密檔**（clone 過的 repo），
> 舊檔案永遠可以用他的舊私鑰解開。`updatekeys` 只保護未來的檔案。
> 必須接著**輪替他曾經解得開的所有機密**（改 DB 密碼、重發 API 金鑰），並收回 git 存取權。
> 見「解密金鑰怎麼管」下方的 `[!danger]`。
>
> **Q6: 錯。** ★★★★★ 那是**私鑰**，不是編碼格式的問題。
> 只有 `age1...` 開頭的**公鑰**可以公開（寫進 `.sops.yaml` 進 git 沒問題）。
> 私鑰進 git 等於整套加密方案失效。見「產生 age 金鑰對」的表格。
>
> **Q7: D。** 動態發放資料庫憑據（TTL 到期自動刪帳號）正是 Vault 的**強項之一**，不是代價。
> A、B、C 都是真實的自架代價，其中 unseal 最常被低估。見「L4：Vault 的價值與代價」。
>
> **Q8:** ★★★★★ 因為 `APP_KEY` 除了加密 session/cookie，還用來加密資料庫中
> `Crypt::encrypt()` 或 `encrypted` cast 的欄位。換掉之後這些欄位**會全部解不開**。
> 必須先確認有沒有加密欄位，有的話要寫「舊 key 解密 → 新 key 加密」的一次性腳本並先在測試環境演練。
> 見「完整實戰範例 → 步驟 1」的 `[!danger]`。
>
> **Q9:** 它會匯出資料庫，但★★★★ **密碼 `P@ssw0rd` 會出現在命令列參數裡**，
> 任何使用者跑 `ps auxww` 都看得到，而且會被寫進 shell history。
> 正確做法是用 `~/.my.cnf`（`600`）或 `--defaults-extra-file=`。
> 見「L1-4：不要把密碼放進命令列」。
>
> **Q10: B。** ★★★★★ 保留**雙金鑰重疊期**才能零停機：先建新的、部署到**所有**取用端
> （含 cron、CI、第二節點、監控），確認舊金鑰的「最後使用時間」不再更新，最後才撤銷。
> A、C、D 都會造成一段「新的還沒部署完、舊的已失效」的空窗。見「雙金鑰並行期」。
