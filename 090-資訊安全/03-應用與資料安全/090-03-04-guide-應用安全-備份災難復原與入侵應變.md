## 觀念說明

### ★★★★★ 三個層次：檔案、資料庫、整機

這是本篇最重要的觀念。很多機關「有備份」，出事時才發現備到的東西根本救不了服務。

```text
┌─────────────────────────────────────────────────────────────┐
│ ③ 整機備份（VM 快照 / PVE Backup / 磁碟影像）                 │
│   ┌───────────────────────────────────────────────────┐     │
│   │ OS + 套件 + 設定 + 使用者 + 排程 + 憑證             │     │
│   │  ┌─────────────────────────────────────────┐      │     │
│   │  │ ① 檔案備份（tar / rsync / restic）        │      │     │
│   │  │   /var/www、/etc、上傳目錄、日誌          │      │     │
│   │  └─────────────────────────────────────────┘      │     │
│   │  ┌─────────────────────────────────────────┐      │     │
│   │  │ ② 資料庫備份（mysqldump / pg_dump）       │      │     │
│   │  │   ★★★★★ 不能只靠 ① 複製 /var/lib/mysql   │      │     │
│   │  └─────────────────────────────────────────┘      │     │
│   └───────────────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────────────┘
```

| 層次 | 工具 | 能還原到什麼程度 | ★★★★★ **漏掉什麼** | 典型還原時間 |
| --- | --- | --- | --- | --- |
| ① **檔案備份** | `tar`、`rsync`、`restic` | 網站程式、上傳檔、設定檔 | ★★★★★ **資料庫內容**（直接複製資料檔會拿到不一致的快照）、系統套件、使用者與權限對應、cron、systemd unit（如果沒備到 `/etc`） | 分鐘～小時 |
| ② **資料庫備份** | `mysqldump`、`pg_dump` | 資料表結構與資料，可跨版本、可挑單一資料表 | ★★★★ **檔案系統上的東西**（使用者上傳的圖片、PDF）、資料庫使用者權限（除非另外備 `mysql` 系統庫） | 分鐘～數小時（大資料庫的匯入很慢） |
| ③ **整機備份** | PVE Backup、VM 快照、Veeam、`dd` | ★★★★ **整台機器原樣還原**，含 OS、套件、設定、排程 | ★★★★★ **一致性**（跑著的資料庫在快照裡可能是壞的）、還原顆粒度粗（不能只救一個資料表）、還原目標硬體要相容 | 小時 |

> [!danger] ★★★★★ 最常見的致命誤會
> **「我有整機快照，所以資料庫也備到了」** —— 這句話只有在**做快照時資料庫是靜止的**才成立。
>
> 對執行中的 MySQL 做 VM 快照，等於「拔掉電源再開機」：
> - InnoDB 有 crash recovery，**多數情況救得回來**，但不保證
> - 交易可能只寫了一半（redo log 有、資料檔沒有）
> - ★★★★★ **如果資料庫檔案跨多個磁碟或未啟用 barrier，可能還原成損毀狀態**
> - 就算資料庫本身沒壞，**檔案系統上的上傳檔與資料庫紀錄可能對不上**
>
> **正確的組合是「整機備份 ＋ 獨立的資料庫 dump」，不是二選一。**

> [!note] ★★★★ 三個層次的搭配建議
> | 情境 | 建議組合 |
> | --- | --- |
> | 單台網站主機 | ① 每日檔案備份 ＋ ② 每日（重要系統每小時）DB dump ＋ ③ 每週整機備份 |
> | 虛擬化環境（PVE/VMware） | ③ 每日整機備份（含快照）＋ ② 每日 DB dump（★★★★ **dump 一定要另外做**） |
> | 有測試環境可還原的 | 同上，另加**每季一次的完整還原演練**到測試環境 |
> | 只有一台、沒有預算 | ① ＋ ② 每日送到另一顆外接硬碟，★★★★ **平常拔線** |

### 應用層備份要備什麼 ★★★★

以一套典型的 LXMP（Linux ＋ Nginx ＋ MySQL ＋ PHP/Laravel）系統為例，
把「要備的東西」列成清單。**沒有清單，你一定會漏。**

| 類別 | 路徑（範例） | 一定要備？ | 說明 |
| --- | --- | --- | --- |
| **應用程式碼** | `/var/www/myapp` | ★★ 視情況 | 若已在 git 上，備份「版本號」就好；★★★★ 但**廠商沒給 git 的系統必須完整備** |
| ★★★★★ **使用者上傳檔** | `/var/www/myapp/storage/app/public`、`public/uploads` | ★★★★★ **必備** | 這是**唯一存在於此的資料**，弄丟就沒了 |
| **應用設定** | `.env`、`config/*.php`（本機覆寫） | ★★★★ 必備 | 含機密，★★★★ **備份要加密**，見 [[090-03-03-guide-應用安全-機密管理與金鑰保護]] |
| **Web 伺服器設定** | `/etc/nginx/`、`/etc/apache2/` | ★★★★ 必備 | 重建時省下大量時間 |
| **PHP 設定** | `/etc/php/8.3/fpm/` | ★★★ 建議 | pool 設定、`php.ini` 的調校值 |
| ★★★★★ **憑證與私鑰** | `/etc/ssl/private/`、`/etc/letsencrypt/` | ★★★★★ **必備且必須加密** | 私鑰遺失＝重新申請憑證 |
| **資料庫**（dump） | `/var/backups/db/*.sql.gz` | ★★★★★ **必備** | 見下一節 |
| **排程** | `/etc/cron.d/`、`/var/spool/cron/crontabs/`、`/etc/systemd/system/*.timer` | ★★★★ 必備 | ★★★★ 最常被漏掉，還原後才發現報表沒跑 |
| **systemd unit** | `/etc/systemd/system/*.service` | ★★★★ 必備 | 佇列 worker、自訂服務 |
| **系統使用者** | `/etc/passwd`、`/etc/group`、`/etc/shadow` | ★★★ 建議（加密） | ★★★ 還原檔案時 UID/GID 要對得上 |
| **套件清單** | `dpkg --get-selections` 的輸出 | ★★★ 建議 | 重建時快速裝回相同套件 |
| **日誌** | `/var/log/nginx/`、應用日誌 | ★★★★ 建議 | ★★★★★ **入侵調查時是關鍵證據**，見本篇後段 |

> [!tip] ★★★★ 一個實用的技巧：把「系統狀態」也 dump 成檔案
> 有些東西不是檔案，但重建時非常需要。把它們產生成文字檔一起備份：
>
> ```bash
> mkdir -p /var/backups/state
> dpkg --get-selections > /var/backups/state/packages.txt
> crontab -l > /var/backups/state/crontab-root.txt 2>/dev/null || true
> systemctl list-unit-files --state=enabled > /var/backups/state/enabled-units.txt
> ip addr show > /var/backups/state/ip.txt
> ip route show > /var/backups/state/route.txt
> mysql -e "SELECT user,host FROM mysql.user;" > /var/backups/state/db-users.txt
> ```
>
> 還原到新機時，這幾個檔案能省掉好幾小時的猜測。

### ★★★★★ 資料庫要 dump，不要直接複製資料檔

這是本篇必須講清楚的第二個重點。

```text
        直接複製 /var/lib/mysql              mysqldump
        ─────────────────────────           ──────────────────────
時間 T0  複製 table_a.ibd  ✓                 讀取一致性快照（MVCC）
時間 T1  ← 應用寫入一筆交易，                  ← 應用繼續寫入，
           同時改到 table_a 與 table_b          但 dump 看到的是 T0 的狀態
時間 T2  複製 table_b.ibd  ✓
                ↓                                    ↓
        ★★★★★ table_a 是舊的、                  ★★★★ 全部都是 T0 的一致狀態
        table_b 是新的 → 交易被撕裂
```

| 做法 | 一致性 | 可跨版本還原 | 顆粒度 | 還原速度 |
| --- | --- | --- | --- | --- |
| **直接複製 `/var/lib/mysql`（服務執行中）** | ★★★★★ **不保證，可能損毀** | ✗ 幾乎不行 | 全庫 | 快 |
| **停服務後複製（冷備份）** | ★★★★ 完全一致 | ✗ 版本要相同 | 全庫 | 快 |
| **`mysqldump --single-transaction`（熱備份）** | ★★★★ 一致（InnoDB） | ✓ 可以 | ✓ 可挑單庫／單表 | ★★★ 慢（要重跑 SQL） |
| **實體備份工具（XtraBackup / mariadb-backup）** | ★★★★ 一致 | 版本要相容 | 全庫 | 快 |

> [!warning] ★★★★ `--single-transaction` 的三個限制
> 1. ★★★★★ **只對 InnoDB 有效**。MyISAM 表不受交易保護，dump 到一半被改就不一致。
>    先確認沒有 MyISAM 表：
>    ```sql
>    SELECT table_schema, table_name, engine FROM information_schema.tables
>    WHERE engine <> 'InnoDB' AND table_schema NOT IN ('mysql','information_schema','performance_schema','sys');
>    ```
> 2. ★★★★ dump 期間如果有 **DDL**（`ALTER TABLE`、`CREATE TABLE`），一致性會被破壞。
>    排程備份時避開資料庫變更時段。
> 3. ★★★ 長時間的 dump 會讓 InnoDB 保留舊版本資料，**undo log 會膨脹**，
>    大資料庫要留意磁碟空間。

### ★★★★ 應用層一致性：檔案與資料庫要對得上

這是很多人沒想到的一層。假設使用者上傳一張圖片，系統會做兩件事：
把檔案寫到 `storage/app/public/`，並在資料表插入一筆紀錄。

```text
情況 A：先 dump DB，再備份檔案            情況 B：先備份檔案，再 dump DB
─────────────────────────────           ─────────────────────────────
T0  dump DB  ──────► 沒有這筆紀錄        T0  備份檔案 ──────► 沒有這個檔
T1  使用者上傳（檔案 + DB 紀錄）          T1  使用者上傳（檔案 + DB 紀錄）
T2  備份檔案 ──────► 有這個檔            T2  dump DB  ──────► 有這筆紀錄

還原後：檔案存在但 DB 沒紀錄              還原後：DB 有紀錄但檔案不存在
      ＝ 孤兒檔案（★★ 無害，佔空間）           ＝ ★★★★ 破圖／下載 404／程式拋例外
```

> [!tip] ★★★★★ 所以順序是：**先 dump 資料庫，再備份檔案**
> 這樣不一致的方向會落在「多出孤兒檔案」而不是「缺檔案」。
> 孤兒檔案只是佔空間，缺檔案會讓應用程式壞掉。
>
> 更嚴謹的做法（有停機空窗可用時）：
> ```bash
> php artisan down                      # 進入維護模式，停止新寫入
> mysqldump ... > db.sql
> tar czf files.tar.gz storage/app/public
> php artisan up
> ```
> ★★★ 這會有幾十秒到幾分鐘的停機，適合半夜的排程。

> [!note] ★★★ 熱備份與冷備份的取捨
> | | 冷備份（停服務） | 熱備份（不停服務） |
> | --- | --- | --- |
> | 一致性 | ★★★★★ 完全一致 | ★★★★ 需要工具支援（`--single-transaction`） |
> | 停機 | 有 | 無 |
> | 適用 | 每週／每月的完整備份、版本升級前 | ★★★★ 每日例行備份 |
> | 陷阱 | 忘記把服務起回來 | 誤以為「有備份就一致」 |

### 3-2-1 與不可變備份的最小理解 ★★★★★

方案選型與設備配置請看 [[090-05-14-guide-資安設備-備份與抗勒索防護]]，
這裡只講**你在寫備份腳本時必須記住的部分**。

```text
3 份資料  ─ 正式資料 1 份 + 備份 2 份
2 種媒體  ─ 例如：本機磁碟 + NAS，或 NAS + 磁帶/雲端
1 份異地  ─ 不在同一棟建築（火災、水災、竊盜）
─────────────────────────────────────────────
+1 份離線或不可變  ★★★★★ 這一份是抗勒索的關鍵
+0 個錯誤          ★★★★★ 還原演練必須全部成功
```

> [!danger] ★★★★★ 為什麼抗勒索一定要有一份離線或不可寫
> 勒索軟體的標準作業程序是：**先找備份、刪掉備份，才開始加密**。
> 它會用你的憑據去搜尋：
> - 掛載中的網路磁碟（`\\nas\backup`、`/mnt/nas`）
> - 備份軟體的管理介面（用你存在瀏覽器裡的密碼）
> - 有寫入權限的雲端儲存
> - ★★★★ **備份主機**（如果它能從被入侵的主機連過去）
>
> 所以：
> | 錯誤做法 | 為什麼會被一起加密 |
> | --- | --- |
> | 備份到常駐掛載的 NAS 目錄 | ★★★★★ 對勒索軟體來說就是另一個資料夾 |
> | 正式機用 `rsync` **推**到備份機 | ★★★★ 正式機被入侵＝有備份機的憑據＝能刪備份 |
> | 備份到同一台機器的另一個分割區 | 整機被加密時一起完蛋 |
>
> | 正確做法 | 說明 |
> | --- | --- |
> | ★★★★ **備份機主動「拉」**（pull） | 正式機沒有備份機的憑據，被入侵也刪不掉備份 |
> | ★★★★★ **物件儲存的 Object Lock** | 保留期內**連管理員都刪不掉**（WORM） |
> | ★★★★ **離線媒體**（外接硬碟／磁帶），平常拔線 | 最土法但最有效 |
> | ★★★ **快照式檔案系統**（ZFS/Btrfs）＋ 唯讀快照 | 見 [[020-01-24-guide-進階儲存-ZFS與Btrfs]] |

### ★★★★★ 還原演練：沒測過還原，等於沒有備份

這句話不是口號。實際遇到的失敗案例，幾乎都是「備份一直有在跑」但還原時才發現：

| 演練才會發現的問題 | 發生頻率 |
| --- | --- |
| 備份檔是空的／只有 0 bytes（腳本某天開始失敗，沒人看告警） | ★★★★★ 極常見 |
| 壓縮檔損毀（磁碟壞軌、寫入時空間不足被截斷） | ★★★★ 常見 |
| dump 缺了 stored procedure／trigger／event（沒加對應參數） | ★★★★ 常見 |
| 還原到新機時字元集變成 latin1，中文全變亂碼 | ★★★★ 常見 |
| 資料庫版本不相容（8.0 的 dump 還不進 5.7） | ★★★ |
| 忘了備份使用者上傳目錄，還原後全站破圖 | ★★★★ 常見 |
| 忘了備份 cron，還原後報表與通知都沒跑 | ★★★★ 常見 |
| 還原後應用起不來（`.env` 沒備、`APP_KEY` 不見） | ★★★★ |
| 沒有人知道還原步驟（唯一會的人離職了） | ★★★★★ |
| ★★★★★ 實際還原時間是 8 小時，但 SLA 承諾 2 小時 | ★★★★ |

> [!tip] 演練的三個層次 ★★★★
> | 層次 | 做什麼 | 頻率 | 耗時 |
> | --- | --- | --- | --- |
> | **L1 檔案抽驗** | 從備份取出幾個檔案，比對雜湊值；`gzip -t` 測壓縮檔完整性 | ★★★★ **每週（自動化）** | 分鐘 |
> | **L2 單項還原** | 把資料庫還原到一台測試機，跑幾個查詢驗證 | ★★★★ 每月或每季 | 1～2 小時 |
> | **L3 完整演練** | ★★★★★ 在乾淨的機器上**從零重建整套服務**並讓它跑起來，計時 | ★★★★★ **每年至少一次** | 半天～一天 |
>
> 演練的紀錄格式見本篇「完整實戰範例 → 步驟 7」。
> 演練屬於資安演練的一環，設計方式另見 [[090-07-17-guide-資安實踐-演練設計與演練紀錄]]。

### RPO 與 RTO：承諾值 vs 實測值 ★★★★

```text
        ← RPO →              事件         ← RTO →
   ─────┬──────────────────────╳──────────────────┬──────►
     最後一次成功備份                          服務恢復
     （會遺失這段期間的資料）              （這段期間服務中斷）
```

| | 定義 | 決定於 | 常見誤區 |
| --- | --- | --- | --- |
| **RPO**（Recovery Point Objective） | 可以接受**遺失多久的資料** | ★★★★ 備份**頻率** | 以為「每日備份」＝ RPO 24 小時，其實是「最多 24 小時＋備份執行時間」 |
| **RTO**（Recovery Time Objective） | 可以接受**停機多久** | ★★★★ 還原**速度**＋準備程度 | ★★★★★ 只算「解壓縮 + 匯入」的時間，忘了算「找備份、開機、裝套件、設定、驗證、公告」 |

> [!warning] ★★★★★ RTO 的實測值一定比你想的長
> 一次真實的還原包含這些階段，**每一段都要計時**：
>
> | 階段 | 常被低估的原因 |
> | --- | --- |
> | 察覺事件 | 沒有監控 → 使用者打電話來才知道，可能已經幾小時 |
> | 決策（要還原嗎？還原到哪個時間點？） | ★★★★★ 被入侵時這一段可能花掉數小時甚至數天 |
> | 準備目標機器 | 沒有備機就要先開 VM、裝 OS、裝套件 |
> | 取回備份 | ★★★★ 從異地／雲端下載 500 GB 要多久？網路頻寬算過嗎？ |
> | 還原資料 | 大資料庫的 `mysql < dump.sql` 可能跑好幾小時 |
> | 設定與接線 | DNS、防火牆規則、憑證 |
> | 驗證 | 沒驗證就上線，等於把問題留給使用者發現 |
> | 公告與復原確認 | |
>
> **只有實際演練過，你填在災難復原計畫裡的 RTO 才是可信的數字。**

## 安裝或基礎操作

### 檔案備份：tar 與 rsync ★★★

一次性完整封存（適合每週的完整備份）：

```bash
sudo mkdir -p /var/backups/files
sudo tar czf /var/backups/files/www-$(date +%F).tar.gz \
  --exclude='./storage/framework/cache' \
  --exclude='./node_modules' \
  --exclude='./vendor' \
  -C /var/www myapp
ls -lh /var/backups/files/
```

預期輸出：

```text
total 412M
-rw-r--r-- 1 root root 412M Sep  3 02:05 www-2026-09-03.tar.gz
```

驗證封存檔可讀（★★★★ **這一步不能省**）：

```bash
tar tzf /var/backups/files/www-2026-09-03.tar.gz | head -5
echo "exit=$?"
```

預期輸出：

```text
myapp/
myapp/artisan
myapp/composer.json
myapp/app/
myapp/app/Http/
exit=0
```

增量同步（適合每日）：

```bash
sudo rsync -aAX --delete \
  --exclude='node_modules' --exclude='vendor' \
  /var/www/myapp/ /var/backups/mirror/myapp/
```

| 參數 | 意義 | 為什麼重要 |
| --- | --- | --- |
| `-a` | archive（含 `-rlptgoD`） | ★★★★ 保留權限、時間、符號連結、擁有者 |
| `-A` | 保留 ACL | ★★★ 有設 ACL 的目錄不加會掉權限 |
| `-X` | 保留擴充屬性（xattr） | ★★★ SELinux context 靠這個 |
| `--delete` | 來源刪掉的，目的地也刪 | ★★★★★ **鏡像會跟著刪 —— 這代表它不是備份，是同步** |
| `-n` / `--dry-run` | 試跑 | ★★★★ 加 `--delete` 前先跑一次 |

> [!danger] ★★★★★ `rsync --delete` 的鏡像**不是備份**
> 檔案被勒索軟體加密或被誤刪之後，下一次同步就會把備份端的好檔案一起覆蓋／刪除。
> 鏡像只能防「硬碟壞掉」，**不能防「內容被破壞」**。
> 要當備份用，必須加上**版本保留**：
> - `rsync --backup --backup-dir=/var/backups/incr/$(date +%F)` 把被覆蓋的舊檔另存
> - 或改用有快照概念的工具（`restic`、`borg`）——見 [[090-05-14-guide-資安設備-備份與抗勒索防護]]

### 資料庫備份：mysqldump ★★★★★

最小可用的正確指令：

```bash
sudo mysqldump --defaults-extra-file=/etc/mysql/backup.cnf \
  --single-transaction --quick \
  --routines --triggers --events \
  --default-character-set=utf8mb4 \
  --no-tablespaces \
  myapp | gzip -9 > /var/backups/db/myapp-$(date +%F_%H%M).sql.gz
```

| 參數 | 作用 | 不加會怎樣 |
| --- | --- | --- |
| `--single-transaction` | ★★★★★ InnoDB 一致性快照，**不鎖表** | 資料可能跨表不一致 |
| `--quick` | 逐列取出、不先全部載入記憶體 | ★★★ 大表可能吃光記憶體 |
| `--routines` | 匯出 stored procedure / function | ★★★★ **還原後函式全不見**，程式報錯 |
| `--triggers` | 匯出 trigger（8.0 預設已含，明寫較保險） | 觸發器遺失 |
| `--events` | 匯出排程事件 | ★★★ 定時任務不見 |
| `--default-character-set=utf8mb4` | ★★★★ 固定連線字元集 | 中文可能變 `????` 或亂碼 |
| `--no-tablespaces` | 不匯出 tablespace 資訊 | ★★★ MySQL 8.0.21+ 沒有 `PROCESS` 權限時會報錯 |

驗證 dump 是完整的 —— ★★★★★ **這是本篇最實用的一招**：

```bash
zcat /var/backups/db/myapp-2026-09-03_0200.sql.gz | tail -1
```

預期輸出：

```text
-- Dump completed on 2026-09-03  2:01:44
```

> [!tip] ★★★★★ `-- Dump completed on` 是完整性的證據
> `mysqldump` **只有在成功跑完**才會寫出這一行。
> 如果磁碟寫滿、連線中斷、被 OOM killer 殺掉，檔案會被截斷、**沒有這一行**。
> 把這個檢查寫進備份腳本，是投報率最高的一個動作：
>
> ```bash
> if ! zcat "$OUT" | tail -1 | grep -q 'Dump completed'; then
>     echo "備份不完整！" >&2; exit 1
> fi
> ```

檢查壓縮檔本身沒有損毀：

```bash
gzip -t /var/backups/db/myapp-2026-09-03_0200.sql.gz && echo "gzip OK"
```

預期輸出：

```text
gzip OK
```

> [!info]- PostgreSQL 對照
> ```bash
> # 純文字格式（可讀、可 grep，但還原較慢、不能平行）
> sudo -u postgres pg_dump -Fp myapp | gzip -9 > myapp-$(date +%F).sql.gz
>
> # ★★★★ custom 格式（建議）：可壓縮、可平行還原、可挑單一資料表還原
> sudo -u postgres pg_dump -Fc -f /var/backups/db/myapp-$(date +%F).dump myapp
>
> # 全叢集（含角色與權限）
> sudo -u postgres pg_dumpall --globals-only > /var/backups/db/globals.sql
> ```
> 還原：
> ```bash
> sudo -u postgres pg_restore -d myapp_test -j 4 /var/backups/db/myapp-2026-09-03.dump
> ```
> ★★★★ `pg_dump` **不會**匯出角色（role）與資料庫層級的權限，
> 必須另外跑 `pg_dumpall --globals-only`，這是最常見的漏洞。
> 詳見 [[060-04-02-05-svc-PostgreSQL-備份與還原]]。

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> - 套件名：`mysql-server` 或 `mariadb-server`；`dnf install mariadb-server`
> - 資料目錄同樣是 `/var/lib/mysql`
> - ★★★★ **SELinux**：把備份放到非標準路徑（例如 `/backup`）時，
>   還原後檔案 context 不對會導致服務讀不到：
>   ```bash
>   sudo restorecon -Rv /var/www/myapp
>   sudo semanage fcontext -a -t httpd_sys_content_t "/srv/myapp(/.*)?"
>   ```
> - Web 服務帳號是 `apache`（不是 `www-data`），還原檔案後記得 `chown -R apache:apache`
> - 防火牆是 `firewalld`：還原到新機後要重開服務埠
>   ```bash
>   sudo firewall-cmd --permanent --add-service=https && sudo firewall-cmd --reload
>   ```

### 整機備份：Proxmox VE 的例子 ★★★

虛擬化環境下最省事的做法。詳細操作見 [[050-01-03-06-svc-PVE-備份與還原]]，這裡只講重點：

```bash
# 在 PVE 主機上手動備份一台 VM（vmid 101）
vzdump 101 --storage backup-nfs --mode snapshot --compress zstd --notes-template '{{guestname}}'
```

| `--mode` | 說明 | 一致性 |
| --- | --- | --- |
| `stop` | 關機後備份 | ★★★★★ 最一致，但有停機 |
| `suspend` | 暫停後備份 | ★★★★ 較一致，有短暫停頓 |
| `snapshot` | ★★★★ 線上快照備份（需儲存支援） | ★★★ **檔案系統層級一致，應用層未必** |

> [!warning] ★★★★★ `--mode snapshot` 仍然不能取代資料庫 dump
> 快照對資料庫來說等同「突然斷電」。InnoDB 通常救得回來，但：
> - 沒有保證
> - 還原顆粒度是整台 VM，**不能只救一個資料表**
> - 無法跨資料庫版本還原
>
> ★★★★ 安裝 **QEMU Guest Agent** 可以讓 PVE 在快照前呼叫 `fsfreeze`，
> 大幅改善檔案系統一致性（但仍不處理資料庫的交易一致性）：
> ```bash
> # 在 VM 內
> sudo apt install -y qemu-guest-agent
> sudo systemctl enable --now qemu-guest-agent
> ```
> 然後在 PVE 的 VM 選項中啟用 QEMU Guest Agent。

## 進階應用

### ★★★★★ 入侵之後：不要急著用備份還原

這是本篇最重要、也是其他兩篇沒有寫的部分。

發現主機被入侵時，第一個念頭通常是「用昨天的備份還原就好了」。
**這個念頭會讓你重複被入侵。**

```text
   入侵時間軸（你以為的）              入侵時間軸（真實的）
   ─────────────────────              ─────────────────────
                                       T-90d  攻擊者取得初始存取
                                       T-89d  植入 web shell
                                       T-80d  建立後門帳號、加 cron
                                       T-60d  ...潛伏、橫向移動...
   T-1d   一切正常                     T-1d   （備份把後門一起備走）
   T-0    發現異常 ← 開始              T-0    發現異常（可能是最後一步：
   T+1h   用 T-1d 的備份還原                    加密勒索、資料外洩被通報）
   T+2h   「修好了」                   T+2h   ★★★★★ 後門原封不動還原回去
   T+3d   ★★★★★ 又被入侵一次           T+3d   攻擊者用同一個後門回來
```

> [!danger] ★★★★★ 用備份還原前必須先回答的三個問題
> 1. **入侵是什麼時候開始的？**（不是「什麼時候被發現的」）
> 2. **我要還原的那份備份，是在入侵開始之前做的嗎？**
> 3. **備份本身有沒有被污染或被動過手腳？**
>
> 三個問題沒有答案就還原，等於把後門一起請回來。
>
> ★★★★★ **在還原之前，先做證據保全** ——
> 一旦覆蓋還原，所有跡證就永久消失了，你將永遠不知道對方怎麼進來的。
> 保全的具體步驟見 [[090-07-15-guide-資安實踐-被入侵主機的跡證檢查]]
> 與 [[090-07-04-guide-資安實踐-資安事件應變流程]]。

### 判斷「乾淨的還原點」的方法 ★★★★★

沒有一個指令能告訴你答案，要靠交叉比對。以下是實際可用的做法：

#### 方法一：從最早的異常跡證往前推

```bash
# 1. 找出最近被修改的 Web 檔案（web shell 通常是新增或修改的 .php）
sudo find /var/www/myapp -name '*.php' -newermt '2026-06-01' -printf '%TY-%Tm-%Td %TH:%TM  %p\n' | sort
```

預期輸出（**注意那些不該存在的檔案**）：

```text
2026-06-12 03:41  /var/www/myapp/public/uploads/img_2026.php
2026-06-12 03:42  /var/www/myapp/public/index.php
2026-08-30 14:20  /var/www/myapp/app/Http/Controllers/HomeController.php
```

★★★★★ `2026-06-12 03:41` 的那個 `uploads/*.php` 極可疑（上傳目錄不該有可執行的 PHP），
而且它比 `index.php` 的修改時間早一分鐘 —— 這暗示 **6 月 12 日凌晨就是初始入侵時間**。

```bash
# 2. 對照 Web 日誌，看那個檔案第一次被存取是什麼時候
sudo zgrep -h 'img_2026.php' /var/log/nginx/access.log* | head -3
```

預期輸出：

```text
203.0.113.45 - - [12/Jun/2026:03:43:02 +0800] "POST /uploads/img_2026.php HTTP/1.1" 200 512 "-" "python-requests/2.31.0"
203.0.113.45 - - [12/Jun/2026:03:45:11 +0800] "POST /uploads/img_2026.php HTTP/1.1" 200 8192 "-" "python-requests/2.31.0"
```

```bash
# 3. 再往前找上傳的那一刻（怎麼進來的）
sudo zgrep -h '12/Jun/2026:03:3' /var/log/nginx/access.log* | grep -iE 'POST|PUT' | head
```

> [!warning] ★★★★ mtime 可以被竄改
> 進階攻擊者會用 `touch -t` 或 `touch -r` 把時間戳改回去（timestomping）。
> 所以要交叉比對：
> - **ctime**（inode 變更時間，`touch -t` 改不到）：`find ... -newerct '2026-06-01'`
> - **日誌**（如果日誌沒被清）
> - ★★★★ **檔案完整性監控（FIM）的紀錄** —— 若有部署 AIDE 或 Wazuh，這是最可靠的來源

```bash
# ctime 比對：如果 mtime 很舊但 ctime 很新，就是被 touch 過的訊號
sudo find /var/www/myapp -name '*.php' -newerct '2026-06-01' \
  -printf 'mtime=%TY-%Tm-%Td ctime=%CY-%Cm-%Cd  %p\n' | head
```

預期輸出（**第一行就是竄改的證據**）：

```text
mtime=2019-03-14 ctime=2026-06-12  /var/www/myapp/public/uploads/img_2026.php
mtime=2026-08-30 ctime=2026-08-30  /var/www/myapp/app/Http/Controllers/HomeController.php
```

#### 方法二：檢查每一份備份裡有沒有惡意檔案

★★★★★ **不要只檢查最新的備份，要往回一份一份檢查，直到找到乾淨的那一份。**

```bash
#!/bin/bash
# 檢查每份備份裡有沒有已知的入侵指標（IoC）
IOC='img_2026\.php|eval\(base64_decode|passthru\(|/tmp/\.hidden|203\.0\.113\.45'

for f in /var/backups/files/www-*.tar.gz; do
    hit=$(tar tzf "$f" 2>/dev/null | grep -cE "$IOC" || true)
    printf '%-45s 可疑檔案數=%s\n' "$(basename "$f")" "$hit"
done
```

預期輸出：

```text
www-2026-06-08.tar.gz                         可疑檔案數=0
www-2026-06-09.tar.gz                         可疑檔案數=0
www-2026-06-10.tar.gz                         可疑檔案數=0
www-2026-06-11.tar.gz                         可疑檔案數=0
www-2026-06-12.tar.gz                         可疑檔案數=1     ← ★★★★★ 從這裡開始被污染
www-2026-06-13.tar.gz                         可疑檔案數=1
...
www-2026-09-02.tar.gz                         可疑檔案數=3
```

**結論：乾淨的還原點是 `www-2026-06-11.tar.gz`（或更早）。**

> [!danger] ★★★★★ 但這代表你要放棄 6/11 之後的所有資料
> 三個月的業務資料不可能直接丟掉。所以真實情境下的做法是：
>
> | 資料類型 | 處理方式 |
> | --- | --- |
> | **程式碼與設定** | ★★★★★ **用乾淨還原點（或直接從 git 重新部署）**，不要用污染後的備份 |
> | **資料庫內容** | ★★★★ 用**最新**的 dump，但**必須逐項檢查異常**（新增的管理員帳號、被竄改的資料、注入的內容） |
> | **使用者上傳檔** | ★★★★ 用最新的，但★★★★★ **必須掃過一遍**，移除所有可執行檔（`.php`、`.jsp`、`.sh`） |
> | **系統本體** | ★★★★★ **重灌，不要還原** —— 見下一節 |

檢查資料庫有沒有被動過手腳：

```sql
-- 檢查是否有非預期的管理員帳號（時間點在入侵之後建立的）
SELECT id, name, email, created_at, updated_at
FROM users WHERE is_admin = 1 ORDER BY created_at DESC LIMIT 20;

-- 檢查密碼被改過的帳號
SELECT id, email, updated_at FROM users
WHERE updated_at > '2026-06-12' ORDER BY updated_at DESC LIMIT 30;

-- 檢查內容欄位有沒有被注入 script（常見的黑帽 SEO / 掛馬）
SELECT id, title FROM posts WHERE content LIKE '%<script%' OR content LIKE '%eval(%' LIMIT 20;
```

> [!tip] ★★★★ 有部署 FIM 或 SIEM 的話會快很多
> Wazuh、AIDE 這類檔案完整性監控會告訴你「某個檔案在某年某月某日被新增／修改」，
> 直接就是入侵起始時間。這也是為什麼值得事先部署。
> 見 [[090-05-09-guide-資安設備-日誌集中與SIEM]]、
> [[090-07-14-guide-資安實踐-資安情資研判與IoC比對]]。

### 重建 vs 還原：怎麼選 ★★★★★

| | **還原**（restore） | **重建**（rebuild） |
| --- | --- | --- |
| 做法 | 把備份倒回原機或新機 | 裝一台全新的 OS，重新安裝套件、部署程式碼、只匯入資料 |
| 時間 | ★★★★ 快（小時） | ★★★ 慢（半天～數天） |
| 風險 | ★★★★★ **可能把後門一起還原** | ★★ 低 |
| 適用 | 硬體故障、誤刪、誤操作、單純的資料遺失 | ★★★★★ **確認被入侵、且不確定入侵範圍時** |

> [!danger] ★★★★★ 被入侵的系統，預設答案是「重建」
> 理由：
> - 你不知道攻擊者動了什麼（核心模組？systemd unit？SSH 授權金鑰？套件本體？）
> - Rootkit 可以讓你的檢查工具本身說謊
> - 「我全部檢查過了」在實務上幾乎不可能為真
>
> **例外**（可以考慮還原而非重建）：
> - 有可信的整機備份，且**能證明**該備份早於入侵起始時間
> - 入侵範圍明確且受限（例如只是 Web 應用層的 web shell，攻擊者沒有提權成功）
> - 有完整的 FIM 紀錄可以逐檔比對

重建的標準流程（配合本篇的備份清單）：

```text
① 準備乾淨的新機（新 VM 或重灌）
② 從 /var/backups/state/packages.txt 裝回套件
③ 從 git 重新部署程式碼（★★★★★ 不要用備份的程式碼目錄）
④ 從加密備份還原設定檔（.env、nginx conf），★★★★ 但要逐行 review
⑤ 匯入最新的資料庫 dump，★★★★ 並執行異常檢查
⑥ 還原使用者上傳檔，★★★★★ 掃描並移除所有可執行檔
⑦ ★★★★★ 輪替所有憑據（DB 密碼、API 金鑰、SSH 金鑰、憑證私鑰）
⑧ 修補當初被利用的漏洞（★★★★★ 沒修補就上線＝立刻再被入侵一次）
⑨ 加強監控後再開放對外
```

> [!warning] ★★★★★ 第 ⑦ 步不能省
> 攻擊者在你的機器上待了三個月，`.env` 裡的所有密碼都要當作已外洩。
> 輪替方法見 [[090-03-03-guide-應用安全-機密管理與金鑰保護]]。

## 完整實戰範例

**情境**：一台 Ubuntu 24.04 上的 LXMP 系統（Nginx ＋ MySQL 8 ＋ PHP-FPM 8.3 ＋ Laravel）。
目標：**建立備份腳本 → 排程 → 實際還原到測試機 → 驗證資料完整性 → 記錄 RTO/RPO**。

| 角色 | 主機 | 說明 |
| --- | --- | --- |
| 正式機 | `web01` (10.0.1.11) | 網站在 `/var/www/myapp`，DB 在本機 |
| 備份機 | `bak01` (10.0.1.50) | ★★★★ **主動拉取**，正式機沒有它的憑據 |
| 演練機 | `test01` (10.0.1.90) | 乾淨的 Ubuntu 24.04，用來做還原演練 |

### 步驟 1：建立備份專用的資料庫帳號 ★★★★

```sql
CREATE USER 'backup'@'localhost' IDENTIFIED BY '長且隨機的密碼';
GRANT SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER, RELOAD, PROCESS
  ON *.* TO 'backup'@'localhost';
FLUSH PRIVILEGES;
```

| 權限 | 為什麼需要 |
| --- | --- |
| `SELECT` | 讀資料 |
| `LOCK TABLES` | 沒用 `--single-transaction` 時需要 |
| `SHOW VIEW` | 匯出 view 定義 |
| `EVENT` / `TRIGGER` | ★★★ 搭配 `--events` / `--triggers` |
| `RELOAD` | `FLUSH TABLES` |
| `PROCESS` | ★★★ MySQL 8.0.21+ 匯出 tablespace 資訊需要；不給就要加 `--no-tablespaces` |

```ini
# /etc/mysql/backup.cnf   ← chmod 600 root:root
[client]
user=backup
password=長且隨機的密碼
```

```bash
sudo install -o root -g root -m 600 /dev/null /etc/mysql/backup.cnf
sudo nano /etc/mysql/backup.cnf
sudo mysql --defaults-extra-file=/etc/mysql/backup.cnf -e "SELECT 1;"
```

### 步驟 2：備份腳本 ★★★★★

```bash
#!/bin/bash
# /usr/local/sbin/myapp-backup.sh
# LXMP 應用層備份：先 DB 後檔案，含完整性檢查
set -euo pipefail

APP_DIR=/var/www/myapp
BACKUP_ROOT=/var/backups/myapp
DB_NAME=myapp
DB_CNF=/etc/mysql/backup.cnf
KEEP_DAYS=14
STAMP=$(date +%F_%H%M)
DEST="${BACKUP_ROOT}/${STAMP}"
LOG=/var/log/myapp-backup.log

log() { printf '%s  %s\n' "$(date '+%F %T')" "$*" | tee -a "$LOG"; }
fail() { log "✗ 失敗：$*"; exit 1; }

mkdir -p "$DEST"
chmod 700 "$BACKUP_ROOT" "$DEST"
log "=== 備份開始 ${STAMP} ==="

# ---------- 前置檢查：磁碟空間 ----------
# ★★★★ 沒空間時 dump 會被截斷，而且不一定報錯
NEED_MB=$(( $(du -sm "$APP_DIR" | cut -f1) + 2048 ))
FREE_MB=$(df -Pm "$BACKUP_ROOT" | awk 'NR==2 {print $4}')
[ "$FREE_MB" -gt "$NEED_MB" ] || fail "空間不足：需要約 ${NEED_MB}MB，只剩 ${FREE_MB}MB"
log "空間檢查通過（可用 ${FREE_MB}MB）"

# ---------- ① 資料庫（★★★★★ 先做 DB，見「應用層一致性」） ----------
DB_OUT="${DEST}/db-${DB_NAME}.sql.gz"
log "匯出資料庫 ${DB_NAME} ..."
mysqldump --defaults-extra-file="$DB_CNF" \
    --single-transaction --quick \
    --routines --triggers --events \
    --default-character-set=utf8mb4 \
    --no-tablespaces \
    "$DB_NAME" | gzip -9 > "$DB_OUT" || fail "mysqldump 執行失敗"

# ★★★★★ 完整性檢查：gzip 檔頭尾都要好，而且要有 Dump completed
gzip -t "$DB_OUT" || fail "gzip 檔損毀：$DB_OUT"
zcat "$DB_OUT" | tail -1 | grep -q 'Dump completed' \
    || fail "dump 不完整（缺少 'Dump completed' 結尾）"
log "資料庫 OK（$(du -h "$DB_OUT" | cut -f1)）"

# ---------- ② 應用檔案 ----------
log "封存應用檔案 ..."
tar czf "${DEST}/app.tar.gz" \
    --exclude='./storage/framework/cache/*' \
    --exclude='./storage/logs/*' \
    --exclude='./node_modules' \
    --exclude='./vendor' \
    -C "$(dirname "$APP_DIR")" "$(basename "$APP_DIR")" \
    || fail "tar 封存失敗"
tar tzf "${DEST}/app.tar.gz" >/dev/null || fail "app.tar.gz 無法讀取"
log "應用檔案 OK（$(du -h "${DEST}/app.tar.gz" | cut -f1)）"

# ---------- ③ 系統設定（★★★★ 最常被漏掉的部分） ----------
log "封存系統設定 ..."
tar czf "${DEST}/etc.tar.gz" \
    /etc/nginx /etc/php /etc/mysql \
    /etc/systemd/system/myapp*.service \
    /etc/cron.d /var/spool/cron/crontabs \
    2>/dev/null || true
tar tzf "${DEST}/etc.tar.gz" >/dev/null || fail "etc.tar.gz 無法讀取"

# ---------- ④ 憑證與私鑰（★★★★★ 一定要加密） ----------
if [ -d /etc/ssl/private ]; then
    log "封存憑證（加密）..."
    tar czf - /etc/ssl/private /etc/ssl/certs/myapp*.crt 2>/dev/null \
      | age -R /etc/backup/recipients.txt -o "${DEST}/ssl.tar.gz.age" \
      || fail "憑證加密備份失敗"
fi

# ---------- ⑤ 系統狀態 ----------
{
    echo "### packages"; dpkg --get-selections
    echo "### enabled units"; systemctl list-unit-files --state=enabled
    echo "### ip"; ip addr show
    echo "### php version"; php -v
    echo "### mysql version"; mysql --defaults-extra-file="$DB_CNF" -N -e "SELECT VERSION();"
} > "${DEST}/state.txt" 2>&1

# ---------- ⑥ 產生雜湊清單（還原時比對用） ----------
( cd "$DEST" && sha256sum ./* > SHA256SUMS )
log "雜湊清單已產生"

# ---------- ⑦ 清理過期備份 ----------
find "$BACKUP_ROOT" -maxdepth 1 -type d -name '20*' -mtime "+${KEEP_DAYS}" \
     -exec rm -rf {} + 2>/dev/null || true

log "=== 備份完成 ${STAMP}，總大小 $(du -sh "$DEST" | cut -f1) ==="
```

```bash
sudo install -o root -g root -m 750 myapp-backup.sh /usr/local/sbin/
sudo /usr/local/sbin/myapp-backup.sh
```

預期輸出：

```text
2026-09-03 02:00:01  === 備份開始 2026-09-03_0200 ===
2026-09-03 02:00:01  空間檢查通過（可用 184320MB）
2026-09-03 02:00:01  匯出資料庫 myapp ...
2026-09-03 02:01:44  資料庫 OK（86M）
2026-09-03 02:01:44  封存應用檔案 ...
2026-09-03 02:04:12  應用檔案 OK（412M）
2026-09-03 02:04:12  封存系統設定 ...
2026-09-03 02:04:14  封存憑證（加密）...
2026-09-03 02:04:15  雜湊清單已產生
2026-09-03 02:04:16  === 備份完成 2026-09-03_0200，總大小 499M ===
```

### 步驟 3：排程 ★★★★

用 systemd timer（比 cron 好追蹤，失敗會留在 journal 裡）：

```ini
# /etc/systemd/system/myapp-backup.service
[Unit]
Description=MyApp application-layer backup
After=mysql.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/myapp-backup.sh
# ★★★★ 失敗時寄信通知（需先設好 MTA 或改成呼叫其他通知方式）
OnFailure=myapp-backup-alert.service
```

```ini
# /etc/systemd/system/myapp-backup.timer
[Unit]
Description=Run MyApp backup daily at 02:00

[Timer]
OnCalendar=*-*-* 02:00:00
RandomizedDelaySec=300
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now myapp-backup.timer
systemctl list-timers myapp-backup.timer
```

預期輸出：

```text
NEXT                        LEFT       LAST                        PASSED  UNIT                 ACTIVATES
Thu 2026-09-04 02:00:00 CST 11h left   Wed 2026-09-03 02:00:01 CST 12h ago myapp-backup.timer   myapp-backup.service
```

> [!warning] ★★★★★ 排程建好之後，一定要建立「備份沒跑成功」的告警
> 備份失敗最可怕的地方是**它安靜地失敗**。最低限度的檢查：
>
> ```bash

> LATEST=$(ls -1d /var/backups/myapp/20* 2>/dev/null | tail -1)
> if [ -z "$LATEST" ] || [ "$(find "$LATEST" -maxdepth 0 -mmin -1440 | wc -l)" -eq 0 ]; then
>     echo "★★★★★ 24 小時內沒有成功的備份！" | mail -s "[告警] myapp 備份異常" it@example.gov.tw
> fi
> ```
>
> 監控與告警的完整做法見 [[100-01-03-guide-日誌-系統監控與告警]]。

### 步驟 4：備份機主動拉取 ★★★★

在 `bak01` 上設定（★★★★★ **方向很重要**：備份機拉，不是正式機推）：

```bash
# bak01 上：產生專用金鑰
sudo -u backup ssh-keygen -t ed25519 -f /home/backup/.ssh/id_ed25519_pull -N ''
sudo cat /home/backup/.ssh/id_ed25519_pull.pub
```

在 `web01` 的 `/root/.ssh/authorized_keys` 加入，並**限制只能執行 rsync**：

```text
command="rsync --server --sender -logDtpre.iLsfxCIvu . /var/backups/myapp/",no-agent-forwarding,no-port-forwarding,no-pty,no-user-rc,from="10.0.1.50" ssh-ed25519 AAAAC3Nz... backup@bak01
```

```bash
# bak01 上：拉取
sudo -u backup rsync -aH --delete-excluded \
  -e "ssh -i /home/backup/.ssh/id_ed25519_pull" \
  root@10.0.1.11:/var/backups/myapp/ /srv/backups/web01/myapp/
```

> [!tip] ★★★★★ 為什麼一定要「拉」不要「推」
> 如果是正式機推：正式機上必然有備份機的憑據。
> 攻擊者拿下正式機 → 拿到憑據 → 連到備份機 → **刪掉所有備份**再開始加密。
> 改成備份機拉，正式機上沒有任何指向備份機的憑據，攻擊者無從得知備份在哪。
> 進一步的不可變儲存做法見 [[090-05-14-guide-資安設備-備份與抗勒索防護]]。

> 很多人的演練紀錄只寫「演練成功」。真正有用的是這三欄：
> 1. **各階段的實際耗時**（沒有這個就無法改善 RTO）
> 2. **發現的問題**（沒發現問題通常代表演練做得不夠真）
> 3. **承諾值要不要調整**（誠實面對做不到的 SLA，比事後解釋好）

## 常見錯誤與排錯

| # | 現象 | 原因 | 解法 |
| --- | --- | --- | --- |
| 1 | 備份檔只有幾百 bytes 或 0 bytes | ★★★★★ `mysqldump` 失敗但 `gzip` 仍產生了檔案（管線中前段失敗被吃掉） | 腳本加 `set -o pipefail`；並檢查 `-- Dump completed on` 結尾；用 `${PIPESTATUS[0]}` 取 dump 的離開碼 |
| 2 | `gzip: unexpected end of file` / `tar: Unexpected EOF in archive` | ★★★★ 備份當時磁碟寫滿，檔案被截斷 | 備份前檢查可用空間（見實戰步驟 2）；改用前一份備份；設置容量告警 |
| 3 | `mysqldump: Error: 'Access denied; you need (at least one of) the PROCESS privilege(s)'` | MySQL 8.0.21+ 匯出 tablespace 需要 `PROCESS` | 加 `--no-tablespaces`，或授予 `PROCESS` 權限 |
| 4 | `mysqldump: Couldn't execute 'FLUSH TABLES': Access denied` | 備份帳號缺 `RELOAD` 權限 | `GRANT RELOAD ON *.* TO 'backup'@'localhost';` |
| 5 | 還原後 stored procedure / trigger 全部不見 | ★★★★ dump 時沒加 `--routines --triggers --events` | 重新 dump；★★★★★ **這種問題只有演練才會發現** |
| 6 | 還原時報 `ERROR 1273 (HY000): Unknown collation: 'utf8mb4_0900_ai_ci'` | ★★★★ 用 MySQL 8 的 dump 還原到 5.7 或 MariaDB | 還原到相同大版本；或在 dump 時加 `--compatible=`，或用 `sed` 批次置換 collation（★★ 有風險，要驗證） |
| 7 | 還原時報 `ERROR 1231 (42000): Variable 'sql_mode' can't be set to the value of 'NO_AUTO_CREATE_USER'` | 來源是 MySQL 5.7、目標是 8.0（該 sql_mode 已移除） | `sed -i "s/NO_AUTO_CREATE_USER,\?//g" dump.sql` 後再匯入 |
| 8 | 還原後中文變成 `????` 或 `æ¸¬è©¦` | ★★★★★ 匯出或匯入時連線字元集不是 utf8mb4 | 兩端都加 `--default-character-set=utf8mb4`；已經匯錯的要從原始備份重來（★★★★ 亂碼**無法可靠地事後修復**） |
| 9 | 匯入到一半停住不動、或 `ERROR 2006 (HY000): MySQL server has gone away` | ★★★★ 單筆 INSERT 超過 `max_allowed_packet`，或 `wait_timeout` 太短 | 目標端調大：`SET GLOBAL max_allowed_packet=256*1024*1024;`；dump 時加 `--net-buffer-length` 控制批次大小 |
| 10 | 還原後網站 500，日誌顯示 `Permission denied` on `storage/logs` | ★★★★ `tar` 還原後擁有者是 root，或 UID 對不上 | `chown -R www-data:www-data /var/www/myapp`；`chmod -R 775 storage bootstrap/cache`。RHEL 系另需 `restorecon -Rv` |
| 11 | 還原後網站白畫面，`.env` 存在但沒作用 | ★★★★ Laravel 的設定快取還是舊的 | `php artisan config:clear && php artisan config:cache`；`systemctl restart php8.3-fpm` |
| 12 | 還原後全站破圖、附件下載 404 | ★★★★★ 只備了程式碼與 DB，**漏了 `storage/app/public`**；或 symlink 沒重建 | 補備上傳目錄；`php artisan storage:link` 重建連結 |
| 13 | 還原後排程都沒跑（報表、通知全無） | ★★★★ 沒備份 `/etc/cron.d`、`crontabs`、systemd timer | 備份腳本加入這些路徑；還原後 `systemctl list-timers` 逐項確認 |
| 14 | 還原到新機後 HTTPS 起不來 | ★★★★ 憑證私鑰沒備份，或權限／SELinux context 不對 | 私鑰加密備份（見實戰步驟 2 第 ④ 段）；`chmod 600` 私鑰、`chmod 700 /etc/ssl/private` |
| 15 | 還原完成、服務正常，★★★★★ **三天後又被入侵** | ★★★★★ 用了被污染的備份，後門一起還原；或原漏洞未修補 | 見「入侵之後：不要急著用備份還原」；被入侵的系統預設應**重建**而非還原，並輪替所有憑據 |
| 16 | `rsync --delete` 之後備份端的舊檔案全沒了 | ★★★★★ 鏡像同步不是備份 | 改用有版本保留的工具（`restic`/`borg`），或加 `--backup --backup-dir=` |
| 17 | 備份目錄被勒索軟體一起加密 | ★★★★★ 備份掛載在本機、或正式機有備份機的憑據 | 改為備份機**主動拉取**；加一份離線或 Object Lock 的副本，見 [[090-05-14-guide-資安設備-備份與抗勒索防護]] |
| 18 | 演練時發現「沒有人知道還原步驟」 | ★★★★★ 唯一會的人離職，且沒有文件 | 演練紀錄與還原 SOP 寫進知識庫；見 [[100-02-11-guide-維運-維運文件與知識庫]] |

## 安全性注意事項

> [!danger] ★★★★★ 六條不能違反的鐵律
> 1. **備份檔含有全部的機密與個資，它的安全等級等同正式資料庫。**
>    備份儲存空間的權限要 `700`，異地／雲端的副本一定要加密。
> 2. **不要在正式機上直接做「覆蓋式還原」來測試。** 還原演練一律用另一台機器。
>    覆蓋還原是不可逆的 —— 你會同時失去「現況」與「跡證」。
> 3. **被入侵時，先保全跡證，再考慮還原。** 一旦覆蓋，永遠查不出對方怎麼進來的。
> 4. **確認被入侵的系統，預設答案是重建而非還原。**
> 5. **還原之後一定要輪替所有憑據。**
> 6. **刪除備份是不可逆的。** 清理保留期時務必確認保留策略正確，
>    並在腳本裡用 `-mtime +N` 而非手動 `rm -rf`。

> [!warning] ★★★★ 備份本身的安全問題
> | 風險 | 說明 | 對策 |
> | --- | --- | --- |
> | 備份檔權限太寬 | `644` 的 dump 檔＝全機可讀的資料庫 | `chmod 700` 備份目錄、`600` 備份檔 |
> | 備份含機密卻未加密 | `.env`、私鑰、`/etc/shadow` 都在裡面 | 異地副本一律加密（`age`／restic 內建加密） |
> | 備份帳號權限過大 | 用 root 或 `ALL PRIVILEGES` 的 DB 帳號 | 只給 `SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER, RELOAD, PROCESS` |
> | 備份機被當跳板 | 備份機能連到所有正式機 | ★★★★ 用受限的 `command=` SSH 授權；備份機自己也要加固 |
> | 演練機用了正式憑證與正式資料 | ★★★★ 演練機通常防護較弱，等於多一台含全部個資的機器 | 演練後**銷毀演練機**；或還原後立即遮蔽個資 |
> | 舊備份沒有安全銷毀 | 退役硬碟裡的備份 | 見 [[090-05-08-guide-資安設備-資料防護DLP與加密]] 的資料銷毀一節 |

> [!warning] ★★★★ 法遵面
> - **個資法**：備份檔含個人資料，同樣受個資法規範，安全維護義務一體適用。
>   演練機上的個資最好做**遮蔽（masking）**處理。
> - **資安法**：公務機關的核心系統應訂有災難復原計畫並定期演練，
>   演練紀錄是稽核時的必查文件。見 [[090-07-09-guide-資安實踐-資安稽核與符合性檢核]]。
> - **委外**：由廠商執行備份時，契約應載明備份保存位置、加密方式、
>   還原責任與時限，見 [[090-07-11-guide-資安實踐-委外與供應鏈資安]]。

### 三個層次對照 ★★★★★

### mysqldump 必備參數 ★★★★★

| 參數 | 作用 |
| --- | --- |
| `--single-transaction` | InnoDB 一致性快照，不鎖表 |
| `--quick` | 逐列取出，省記憶體 |
| `--routines` | 匯出 procedure / function |
| `--triggers` | 匯出 trigger |
| `--events` | 匯出排程事件 |
| `--default-character-set=utf8mb4` | 避免中文亂碼 |
| `--no-tablespaces` | 沒有 `PROCESS` 權限時必加 |
| `--defaults-extra-file=<檔>` | 密碼不進命令列 |
| `--databases db1 db2` | 匯出時含 `CREATE DATABASE` |
| `--source-data=2` | 記錄 binlog 位置（註解形式），做時間點復原用 |

### 備份完整性檢查 ★★★★★

| 檢查 | 指令 |
| --- | --- |
| gzip 完整 | `gzip -t file.sql.gz` |
| dump 跑完 | `zcat file.sql.gz \| tail -1 \| grep 'Dump completed'` |
| tar 可讀 | `tar tzf file.tar.gz > /dev/null` |
| 雜湊比對 | `sha256sum -c SHA256SUMS` |
| 檔案不是空的 | `[ "$(stat -c %s f)" -gt 1024 ]` |
| 備份有跑 | `find /var/backups -maxdepth 1 -mmin -1440` |

### 還原後驗證清單 ★★★★★

| # | 檢查 | 指令／方式 |
| --- | --- | --- |
| 1 | 資料表數量一致 | `SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='x';` |
| 2 | 關鍵表筆數一致 | `SELECT COUNT(*) FROM users;` 逐表比對 |
| 3 | routine/trigger/event 齊全 | 查 `information_schema.routines` / `.triggers` / `.events` |
| 4 | 中文沒亂碼 | `SELECT name FROM users WHERE name REGEXP '[^ -~]' LIMIT 5;` |
| 5 | 上傳檔數量一致 | `find storage/app/public -type f \| wc -l` |
| 6 | DB 紀錄對得上實體檔 | 隨機抽 5 筆 attachment 比對檔案是否存在 |
| 7 | 首頁與登入頁 200 | `curl -o /dev/null -w '%{http_code}'` |
| 8 | 健康檢查端點正常 | `curl /health` |
| 9 | 排程有註冊 | `systemctl list-timers`、`crontab -l` |
| 10 | HTTPS 正常 | `openssl s_client -connect host:443 -servername host` |

### 入侵後的判斷流程 ★★★★★

| 順序 | 動作 | 千萬不要 |
| --- | --- | --- |
| 1 | ★★★★★ **保全跡證**（記憶體、日誌、磁碟映像） | ✗ 直接重開機或覆蓋還原 |
| 2 | 判斷入侵起始時間（mtime/ctime、日誌、FIM） | ✗ 相信「發現時間＝入侵時間」 |
| 3 | 逐份檢查備份，找出第一份被污染的 | ✗ 只檢查最新的備份 |
| 4 | 決定重建 vs 還原（★★★★★ 預設重建） | ✗ 為了省時間直接還原 |
| 5 | 程式碼從 git 重新部署；資料用最新 dump 但要檢查 | ✗ 直接用污染後的程式碼備份 |
| 6 | ★★★★★ 輪替所有憑據 | ✗ 沿用舊密碼 |
| 7 | ★★★★★ 修補被利用的漏洞 | ✗ 沒修就上線 |
| 8 | 加強監控後再開放對外 | ✗ 直接對外並宣布結案 |

### 找出入侵起始時間的指令 ★★★★

| 目的 | 指令 |
| --- | --- |
| 近期被改的 PHP 檔 | `find /var/www -name '*.php' -newermt '2026-06-01' -printf '%TY-%Tm-%Td %p\n' \| sort` |
| ctime 比對（抓 timestomping） | `find /var/www -name '*.php' -newerct '2026-06-01' -printf 'm=%TY-%Tm-%Td c=%CY-%Cm-%Cd %p\n'` |
| 上傳目錄裡的可執行檔 | `find storage/app/public -name '*.php' -o -name '*.phtml'` |
| Web 日誌裡的可疑存取 | `zgrep -h '<檔名>' /var/log/nginx/access.log*` |
| 新增的系統帳號 | `awk -F: '$3>=1000 {print $1,$3}' /etc/passwd` |

| 檢查備份是否被污染 | `tar tzf backup.tar.gz \| grep -E '<IoC 樣式>'` |

### RPO / RTO 速查 ★★★★

| | 決定於 | 縮短的方法 |
| --- | --- | --- |
| **RPO** | 備份頻率 | 提高頻率；★★★ 加 binlog／WAL 備份做時間點復原 |
| **RTO** | 還原速度＋準備程度 | 備妥待命機；改用實體備份工具；★★★★★ **寫好 SOP 並演練** |

| 層次 | 內容 | 頻率 |
| --- | --- | --- |
| L1 抽驗 | 雜湊比對、`gzip -t`、檔案取出 | 每週（自動化） |

## 練習題

> [!example] 練習 1：證明「直接複製資料檔」不可靠（★★★）
> 在測試機上，一邊用迴圈持續寫入資料，一邊用 `cp -a` 複製 `/var/lib/mysql`，
> 然後把複製出來的目錄掛到另一個 MySQL 實例上啟動，觀察結果。
> 再用 `mysqldump --single-transaction` 做同樣的事，比較差別。
>
> > [!question]- 參考解答
> > 直接複製多半會在啟動時看到 InnoDB crash recovery 的訊息，
> > 例如 `InnoDB: Starting crash recovery`、`Database was not shut down normally!`。
> > 幸運的話能起來，但★★★★★ **無法保證跨表的交易一致性**。
> > `mysqldump --single-transaction` 則是用 MVCC 取得一致性快照，
> > 匯出的內容是同一個時間點的狀態。
> > 這個練習的目的是讓你親眼看到那行 crash recovery 訊息。

> [!example] 練習 2：寫出「備份沒跑成功就告警」的檢查（★★★）
> 寫一支腳本，每天早上檢查：
> 1. 最新備份是否在 24 小時內
> 2. `gzip -t` 通過
> 3. 有 `-- Dump completed on` 結尾
> 4. 檔案大小是否比前一天縮水超過 30%（★★★★ 可能是資料被刪或 dump 中斷）
>
> > [!question]- 參考解答
> > 第 4 點是很多人沒想到的：備份「有跑、有結尾、能解壓」，
> > 但如果昨天 86 MB、今天 3 MB，很可能是資料表被 drop 了或某個資料庫沒被匯出。
> > ```bash
> > cur=$(stat -c %s "$LATEST/db-myapp.sql.gz")
> > prev=$(stat -c %s "$PREV/db-myapp.sql.gz")
> > if [ "$cur" -lt $(( prev * 7 / 10 )) ]; then
> >     echo "★★★★ 備份大小異常縮水：${prev} → ${cur}"
> > fi
> > ```

> [!example] 練習 3：做一次完整的 L2 還原演練（★★★★）
> 把正式（或測試）資料庫還原到另一台機器，完成本篇「步驟 6」的十項驗證，
> 並記錄每個階段的耗時。
>
> > [!question]- 參考解答
> > 重點不是「還原成功」，而是**你會發現至少一個原本不知道的問題**。
> > 最常見的三個：① `--routines` 沒加 ② 上傳目錄沒備到 ③ 匯入時間比想像久很多。
> > 把耗時填進「RTO 實測值」，如果超過承諾值，就要做出選擇：
> > 改善還原速度，或誠實調整承諾值。

> [!example] 練習 4：找出乾淨的還原點（★★★★★）
> 模擬情境：在測試機的 `/var/www/lab/public/uploads/` 放一個假 web shell
> （內容寫 `<?php echo "lab"; ?>` 即可），連續做 7 天的備份（可以用 `date -s` 或直接改檔名模擬），
> 從第 4 天開始才有那個檔案。
> 寫一支腳本，掃過所有備份，找出**第一份被污染的備份**與**最後一份乾淨的備份**。
>
> > [!question]- 參考解答
> > ```bash
> > IOC='uploads/.*\.php$'
> > last_clean=""; first_dirty=""
> > for f in /var/backups/files/www-*.tar.gz; do
> >   if tar tzf "$f" | grep -qE "$IOC"; then
> >     [ -z "$first_dirty" ] && first_dirty="$f"
> >   else
> >     [ -z "$first_dirty" ] && last_clean="$f"
> >   fi
> > done
> > echo "最後一份乾淨：$last_clean"
> > echo "第一份被污染：$first_dirty"
> > ```
> > ★★★★★ 接著要思考的是：如果「最後一份乾淨」是三個月前的，
> > 你要怎麼處理這三個月的業務資料？答案是**分開處理**：
> > 程式碼用乾淨還原點或 git、資料用最新 dump 但逐項檢查、上傳檔掃過再用。

> [!example] 練習 5：驗證備份的方向性（★★★★）
> 在你的環境確認：正式機上有沒有任何指向備份儲存的憑據
> （SSH 金鑰、`/etc/fstab` 的網路掛載、rclone 設定、備份軟體的密碼）。
> 如果有，設計一個改成「備份機主動拉取」的方案。
>
> > [!question]- 參考解答
> > 檢查方式：
> > ```bash
> > sudo cat /etc/fstab | grep -E 'cifs|nfs'
> > sudo ls -la /root/.ssh/ /home/*/.ssh/
> > mount | grep -E 'cifs|nfs'
> > sudo find / -name 'rclone.conf' 2>/dev/null
> > ```
> > 只要正式機能寫到備份，勒索軟體也能。改成拉取的關鍵是：
> > **正式機上不存在任何備份端的憑據**，而備份機用受限的
> > `command="rsync --server --sender ..."` 授權金鑰連進來，只能讀不能寫。

## 小測驗

Q1. （選擇）你每晚都對整台 VM 做快照備份，資料庫跑在這台 VM 上。
下列敘述何者正確？
　A. 已經備到資料庫了，不需要另外 dump
　B. 快照對執行中的資料庫等同斷電，仍應另外做 dump
　C. 只要 VM 有裝 Guest Agent 就完全等同 dump
　D. 快照比 dump 更一致

Q2. （是非）`rsync -a --delete` 把網站同步到 NAS，就算是有備份了。

Q3. 「這行指令會發生什麼」
```bash
zcat /var/backups/db/myapp.sql.gz | tail -1
```

Q4. （簡答）備份時應該「先 dump 資料庫再備份檔案」還是「先備份檔案再 dump 資料庫」？為什麼？

Q5. （選擇）`mysqldump` 忘了加下列哪個參數，還原後 stored procedure 會不見？
　A. `--single-transaction`
　B. `--quick`
　C. `--routines`
　D. `--no-tablespaces`

Q6. （是非）發現主機被入侵後，最快的處理方式是立刻用昨天的備份還原，讓服務先恢復。

Q7. （簡答）你在 `/var/www/x/public/uploads/` 找到一個 `.php` 檔，
`mtime` 是 2019 年但 `ctime` 是上個月。這代表什麼？

Q8. （選擇）以下哪一種備份架構最能抵抗勒索軟體？
　A. 正式機用 cron `rsync` 推到 NAS 掛載點
　B. 正式機用 rclone 推到雲端
　C. 備份機主動 SSH 拉取，另有一份 Object Lock 的副本
　D. 備份到同一台機器的另一個分割區

Q9. （簡答）你的災難復原計畫寫著「RTO 4 小時」。要怎麼證明這個數字是真的？

Q10. 「這段情境會發生什麼」
一家機關被入侵，用了前一天的整機備份還原，服務恢復，宣布結案。
三天後同樣的攻擊再度發生。原因最可能是什麼？

> [!question]- 測驗答案
> **Q1: B。** ★★★★★ 快照對執行中的資料庫等同「拔電源」，InnoDB 通常救得回來但沒有保證，
> 且無法跨版本還原、無法只救單一資料表。
> Guest Agent 的 `fsfreeze` 改善的是**檔案系統**一致性，處理不了資料庫的交易一致性。
> 正確組合是「整機備份 ＋ 獨立 DB dump」。見「三個層次」的 `[!danger]`。
>
> **Q2: 錯。** ★★★★★ `--delete` 的鏡像**不是備份**，是同步。
> 檔案被勒索軟體加密或誤刪後，下一次同步會把備份端的好檔案一起覆蓋／刪除。
> 鏡像只防硬碟壞，不防內容被破壞。見「檔案備份：tar 與 rsync」的 `[!danger]`。
>
> **Q3:** 印出 dump 檔的最後一行。★★★★★ 如果看到 `-- Dump completed on ...`，
> 代表 `mysqldump` 成功跑完；沒有這一行就表示檔案被截斷（磁碟滿、被 OOM 殺掉、連線中斷）。
> 這是投報率最高的完整性檢查。見「資料庫備份：mysqldump」。
>
> **Q4:** ★★★★★ **先 dump 資料庫，再備份檔案。**
> 這樣不一致的方向會落在「多出孤兒檔案」（無害，只佔空間），
> 而不是「DB 有紀錄但檔案不存在」（破圖、下載 404、程式拋例外）。
> 見「應用層一致性」。
>
> **Q5: C。** `--routines` 才是匯出 stored procedure 與 function 的參數。
> ★★★★ 這類問題只有在實際做還原演練時才會被發現。見「mysqldump 必備參數」。
>
> **Q6: 錯。** ★★★★★ 兩個致命問題：① 覆蓋還原會**永久摧毀所有跡證**，
> 你將無法查出對方怎麼進來的；② 入侵通常早於發現數週甚至數月，
> 昨天的備份很可能**已經含有後門**，還原等於把攻擊者請回來。
> 見「入侵之後：不要急著用備份還原」。
>
> **Q7:** ★★★★★ 這是 **timestomping（時間戳竄改）**的訊號 ——
> 攻擊者用 `touch -t` 把 mtime 改成很久以前，想混在舊檔案裡。
> 但 `ctime`（inode 變更時間）改不掉，所以「mtime 很舊、ctime 很新」就是被動過手腳的證據。
> 而且上傳目錄本來就不該有 `.php` 檔。見「判斷乾淨的還原點 → 方法一」。
>
> **Q8: C。** ★★★★★ 關鍵在**方向**與**不可變**：
> 備份機主動拉取代表正式機上沒有任何備份端憑據，被入侵也刪不掉備份；
> Object Lock 的副本在保留期內連管理員都刪不掉。
> A、B 都是「正式機有寫入權限」，勒索軟體拿到憑據就能刪；D 整機被加密時一起完蛋。
> 見「3-2-1 與不可變備份的最小理解」。
>
> **Q9:** ★★★★★ **只有實際演練並計時才能證明。**
> 要記錄各階段耗時（取回備份、裝套件、還原檔案、匯入 DB、設定、驗證），
> 而且要把「察覺 + 決策」的時間也算進去。
> 沒演練過的 RTO 只是願望。見「RPO 與 RTO」與實戰步驟 7。
>
> **Q10:** ★★★★★ 最可能的原因是**還原了被污染的備份**：入侵早於備份時間點，
> 後門（web shell、後門帳號、惡意 cron）跟著被還原回去。
> 次要原因是**當初被利用的漏洞沒有修補**，以及**憑據沒有輪替**。
> 正確做法是：判斷入侵起始時間 → 找乾淨還原點 → **重建而非還原** →
> 輪替所有憑據 → 修補漏洞 → 加強監控後才開放。見「重建 vs 還原」。
