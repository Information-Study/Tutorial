# 系統與網路防護 常見故障排除

> [!abstract] 怎麼用這份手冊
> - 依「你看到什麼症狀」查，不是依「這屬於哪個工具」查。★★★★★ 出事的當下，
>   你通常**還不知道是防火牆、SSH、Fail2ban 還是 SELinux** —— 這份手冊就是為了那個當下寫的。
> - 找到症狀 → 看判斷分流 → 照編號步驟做 → 想懂原理再點進原文。
> - ★★★★★ 緊急時直接跳到下一節的「一頁式急救卡」，那是連不上主機的黃金 60 秒。
> - ★★★★★ 本手冊**不重講原理**，也**不重複本章八篇各自的排錯表**。
>   八篇裡已經有的（例如 ufw 的 17 條錯誤表、Fail2ban 的 18 條錯誤表），
>   這裡只給連結，篇幅留給**跨篇的症狀** —— 也就是你不知道是哪一層出問題的那種。
> - ★★★★★ 動手之前先問自己一句：**這台機器現在是「被我改壞了」還是「正在被攻擊」？**
>   兩者的第一動作完全相反 —— 前者要還原，後者要先保存現場。判斷不了就直接看
>   「什麼時候該停手求援」。

> [!danger] ★★★★★ 主機防護排錯的第一鐵律：**先確認你還有第二條路進得來**
> 這一章的每一個工具（ufw、nftables、firewalld、Fail2ban、sshd、SELinux）
> 都有能力**把你自己關在門外**，而且多半是在你按下 Enter 的那一瞬間。
> 動任何規則之前，先確認以下三者至少有一個成立：
> ① 另一個已經連上、而且**絕對不要關掉**的 SSH session；
> ② 可用的 console（PVE／iDRAC／iLO／雲端 Serial Console／VNC）；
> ③ 已經排好的自動還原（`at` 或 `systemd-run --on-active`）。
> 三個都沒有，就先停下來把其中一個做出來 —— 這一步省下來的十分鐘，
> 換來的是開車去機房的三小時。

## 一頁式急救卡

### ★★★★★ 情況 A：連不上主機了 —— 黃金 60 秒

**你手上還有一條活著的 SSH session**（哪怕它已經沒反應，也先不要關）：

```bash
# ─── 一、先讓機器活過來，再談對錯 ────────────────────────────
sudo ufw disable                                    # Debian 系：整個關掉 ufw
sudo systemctl stop firewalld                       # RHEL 系：先停 firewalld
sudo nft flush ruleset                              # 手寫 nftables：清空全部規則
sudo systemctl stop fail2ban                        # 懷疑被自己的 Fail2ban 鎖住
sudo setenforce 0                                   # RHEL：SELinux 轉 permissive（暫時）
sudo systemctl restart sshd                         # Ubuntu 舊版服務名是 ssh

# ─── 二、sshd 改壞了的最快還原 ──────────────────────────────
sudo sshd -t                                        # ★★★★★ 先驗語法，會直接印出錯誤行號
sudo mv /etc/ssh/sshd_config.d/*hardening*.conf /root/   # 把剛加的 drop-in 移走
sudo sshd -t && sudo systemctl restart sshd

# ─── 三、Fail2ban 把自己封了的最快解 ────────────────────────
sudo fail2ban-client unban --all                    # 解開所有 jail 的所有封鎖
sudo fail2ban-client set sshd unbanip 203.0.113.44  # 只解單一 IP

# ─── 四、確認 sshd 真的活著、真的在聽 ───────────────────────
systemctl is-active sshd; sudo ss -tlnp | grep -E ':(22|2222)\b'
```

**你手上已經沒有任何連線**：往下走「情況 B」。

### ★★★★★ 情況 B：完全連不上，要從外面救

★★★★★ **由上往下，找到第一個你手上真的有的途徑就用它**，不要跳。

| 順位 | 途徑 | 條件 | 進去之後第一件事 |
| --- | --- | --- | --- |
| ★★★★★ 1 | 已排好的 `at` 自動還原 | 動手前有排 | 等時間到（通常 5～10 分鐘），期間**不要再改任何東西** |
| ★★★★★ 2 | 虛擬化平台的 console（PVE `noVNC`、VMware Console） | VM | `ufw disable` ／ `nft flush ruleset` ／ `systemctl stop firewalld` |
| ★★★★★ 3 | 硬體帶外管理（iDRAC／iLO／IPMI 的遠端 KVM） | 實體機且 BMC 已設定 | 同上；順便看 `journalctl -u sshd -n 50` |
| ★★★★ 4 | 雲端主控台的 Serial Console／VNC | 雲端 VM | 同上；另檢查**雲端安全群組**（那一層不在本機） |
| ★★★★ 5 | 雲端安全群組／邊界防火牆規則 | 雲端或有前置設備 | 確認 22（或你的自訂埠）對你的來源 IP 是開的 |
| ★★★ 6 | 救援模式／Live 光碟掛載根分割 | 前面全沒有 | 改 `/etc/ufw/ufw.conf` 的 `ENABLED=no`、移走 sshd drop-in |
| ★★ 7 | 開機參數 `systemd.unit=emergency.target` | 實體接得到鍵盤螢幕 | `mount -o remount,rw /` 後改設定 |

> [!danger] ★★★★★ 沒有第 1～5 項的機器，就是「一旦鎖住就要進機房」的機器
> 這不是排錯技巧的問題，是**上架時就該做完的事**。
> 帶外管理的設定與網段規劃見 [[090-02-06-guide-防護-遠端存取安全]] 的
> 〈帶外管理（OOB）為什麼是最高等級〉與 [[040-02-09-guide-機房-伺服器上架與初始設定]]。

### ★★★★★ 情況 C：服務連不到 —— 五層速判

```bash
# 五個指令、五個層次，由內往外，第一個異常的地方就是答案
systemctl is-active <服務>                    # ① 程序活著嗎
sudo ss -tlnp | grep <埠>                     # ② 在聽嗎？聽在哪個位址？
curl -sv http://127.0.0.1:<埠>/ 2>&1 | head   # ③ 本機自己連得到嗎
sudo tcpdump -ni any port <埠> -c 10          # ④ 封包到得了這台機器嗎
sudo ausearch -m AVC -ts recent 2>/dev/null; sudo dmesg | grep -i 'apparmor.*DENIED' | tail
                                              # ⑤ MAC 擋了嗎
```

★★★★★ **④ 決定了問題在不在這台機器上**：
`tcpdump` 看得到封包卻沒回應 → 本機防火牆或服務；
`tcpdump` 什麼都看不到 → 問題在上游（雲端安全群組、邊界防火牆、交換器 ACL、路由），
**再怎麼調本機防火牆都沒用**。

### ★★★★ 情況 D：動手改防火牆之前的三道保命符

```bash
# ① 排一個自動還原（Debian 系；沒有 at 就 apt install at && systemctl enable --now atd）
echo "/usr/sbin/ufw --force disable" | sudo at now + 10 minutes
echo "/usr/bin/systemctl stop firewalld" | sudo at now + 10 minutes      # RHEL 系
echo "/usr/sbin/nft flush ruleset" | sudo at now + 10 minutes            # 手寫 nftables

# ② 先備份現況（規則、設定、整份 /etc）
sudo ufw status numbered | sudo tee /root/ufw-$(date +%F-%H%M).txt
sudo nft list ruleset | sudo tee /root/nft-$(date +%F-%H%M).nft
sudo firewall-cmd --permanent --list-all-zones | sudo tee /root/fw-$(date +%F-%H%M).txt
sudo tar czf /root/etc-$(date +%F-%H%M).tar.gz /etc

# ③ 開第二個終端連進來，然後【不要關它】
#    ★★★★★ 測試一律用「新開的第三個連線」，不要用手上這兩條判斷通不通
```

> [!warning] ★★★★★ 為什麼不能用手上這條連線判斷「通不通」
> 已建立的 TCP 連線走 conntrack 的 `ESTABLISHED`，**不受新規則影響**。
> 你把 22 埠關掉，手上這條照樣好好的，直到你關掉它才發現進不來了。
> 這是本章最常見、也最慘的一個誤判。
> 　→ 詳見 [[090-02-04-guide-防火牆-firewalld]] 的〈常見錯誤與排錯〉第 6 條。

## 依情境展開

### ★★★★★ 情境一：連不上主機了

**現象**：SSH 進不去。★★★★★ 這是本章最恐怖、也最常見的情境，
因為**這一章的每一個工具都有能力造成它**。

**★★★★★ 第一步不是修，是分類。** SSH 客戶端給你的訊息就是最好的分流器：

```text
ssh: connect to host 10.0.10.20 port 22: Connection timed out
  → ★★★★★ 封包被【靜默丟棄】。防火牆 DROP、Fail2ban、上游設備。       走【1】

ssh: connect to host 10.0.10.20 port 22: Connection refused
  → ★★★★★ 封包【到了】，但沒人在聽，或被明確 reject。sshd 掛了。      走【2】

ssh: connect to host 10.0.10.20 port 22: No route to host
  → 路由或 ARP 層問題，多半不是主機防護。先查網路。                     走【3】

Permission denied (publickey)．／ Permission denied (publickey,password)．
  → ★★★★★ TCP 通了、sshd 也活著，是【認證】被拒。sshd 設定改壞了。      走【4】

kex_exchange_identification: read: Connection reset by peer
  → 連上了又被踢掉。TCP wrapper、sshd 的 MaxStartups、或中間設備。       走【5】

（連線建立後幾秒才斷、或本來好好的突然斷）
  → ★★★★ Fail2ban 剛好在這時候把你封了。                              走情境五
```

> [!tip] ★★★★★ 三十秒判斷法：timeout 還是 refused
> **timeout（逾時）＝ 有人丟掉了你的封包** → 找防火牆（本機或上游）。
> **refused（拒絕）＝ 封包有到，但那個埠沒有服務在聽** → 找服務。
> 這一個字的差別，決定你接下來要查的是完全不同的兩邊。
> ★★★ 唯一的例外：把防火牆規則寫成 `reject` 而不是 `deny/drop` 時，
> 防火牆也會回 refused。所以看到 refused 也順手確認一下規則的動作是什麼。

#### 【1】逾時：找出是誰在丟包

★★★★★ 從**離你最遠的那一層**往回推，但先做一個成本最低的判斷：

```bash
# 在【你這邊】，先確認不是自己網路的問題
$ nc -zv -w3 10.0.10.20 22
nc: connect to 10.0.10.20 port 22 (tcp) failed: Connection timed out

$ nc -zv -w3 10.0.10.20 443        # ★★★★ 換一個「應該要開」的埠試
Connection to 10.0.10.20 443 port [tcp/https] succeeded!
#   443 通、22 不通 → 主機活著、網路通，就是【22 這條規則】的問題
#   兩個都不通    → 主機掛了、網段不通，或整台被封 → 先查網路與電源
```

進到主機（透過 console）之後，依序排除：

```bash
# ① 本機防火牆有沒有放行 22？三個工具各查各的
sudo ufw status numbered | grep -E '22|SSH'
sudo firewall-cmd --list-all | grep -E 'ssh|22'
sudo nft list ruleset | grep -n 'dport.*22'

# ② Fail2ban 有沒有把你封了？（★★★★★ 最容易被忽略的一層）
sudo fail2ban-client status sshd
sudo nft list ruleset | grep -A20 'f2b'
sudo ufw status numbered | grep -i 'REJECT\|DENY'

# ③ sshd 到底聽在哪個埠、哪個位址？
sudo ss -tlnp | grep sshd
#   看到 127.0.0.1:22 → ★★★★★ 只聽本機，外面永遠連不到（改 ListenAddress）
#   看到 0.0.0.0:2222 → 埠改過了，你的防火牆規則寫 22 當然沒用

# ④ 封包到底有沒有到這台機器？（決定問題在不在本機）
sudo tcpdump -ni any 'tcp port 22' -c 20
#   （同時從你的機器 nc -zv 10.0.10.20 22）
#   看得到 SYN 進來 → 問題在本機（防火牆或 sshd）
#   完全看不到      → ★★★★★ 問題在上游，本機再怎麼改都沒用
```

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| `tcpdump` 看得到 SYN，但沒有 SYN-ACK 回去 | 本機防火牆 DROP | 依工具放行：`ufw allow 22/tcp`／`firewall-cmd --add-service=ssh`／nft 加規則 | ★★★★★ |
| `tcpdump` 完全看不到封包 | 上游：雲端安全群組、邊界防火牆、交換器 ACL、路由 | 去那一層查。★★★★★ 雲端 VM 有**兩層**防火牆，很多人只記得本機那層 | ★★★★★ |
| `ss` 顯示 `127.0.0.1:22` | `sshd_config` 的 `ListenAddress` 被設成本機 | `sudo sshd -T \| grep -i listenaddress` 確認生效值後改回 `0.0.0.0` | ★★★★ |
| `ss` 完全沒有 sshd | sshd 沒起來（設定語法錯最常見） | `sudo sshd -t` 看錯誤行號；`journalctl -u sshd -n 50` | ★★★★★ |
| `fail2ban-client status sshd` 的 Banned IP list 有你的 IP | 你自己被封了 | `sudo fail2ban-client set sshd unbanip <你的IP>`，然後補 `ignoreip` | ★★★★★ |
| 防火牆規則存在但 `to` 寫了錯的來源網段 | 來源限制寫錯（打錯遮罩、寫成 `/32` 但你換了 IP） | `ufw status numbered` 逐條核對來源；★★★ 管理規則寫網段不要寫單一 IP | ★★★★ |
| 只有 IPv6 不通（或只有 IPv4 不通） | 規則只加了一邊 | `grep IPV6 /etc/default/ufw` 應為 `yes`；IPv6 要另外寫等效規則 | ★★★ |

> [!danger] ★★★★★ 逾時的時候，不要「多加幾條規則試試看」
> 每加一條你不確定的規則，都在把現場弄得更難判斷。
> 正確順序是：**先確認封包有沒有到（tcpdump）→ 再確認是誰擋的（規則與 counter）→ 才改**。
> 　→ ufw 的完整排查順序詳見 [[090-02-02-guide-防火牆-ufw基礎與實務]] 的〈排查順序〉；
> 　　nftables 版本見 [[090-02-03-guide-防火牆-nftables與iptables]] 的〈排查順序〉。

#### 【2】拒絕（refused）：沒人在聽

```bash
$ systemctl status sshd --no-pager -l
× ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/lib/systemd/system/ssh.service; enabled)
     Active: failed (Result: exit-code) since ...
      Process: 1234 ExecStartPre=/usr/sbin/sshd -t (code=exited, status=255)

$ sudo sshd -t
/etc/ssh/sshd_config.d/60-hardening.conf line 12: Bad configuration option: PermitRootlogin
```

★★★★★ `sshd -t` 會直接告訴你**哪個檔、哪一行、哪個字**錯了。
這是排 sshd 問題投報率最高的一步，而且**改設定前跑它就不會出這種事**。

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| `sshd -t` 報 `Bad configuration option` | 拼字錯（大小寫不影響，但字要對） | 照行號改；不確定就把整個 drop-in 移到 `/root/` 再重啟 | ★★★★★ |
| `sshd -t` 報 `Missing privilege separation directory` | `/run/sshd` 不存在 | `sudo mkdir -p /run/sshd`；正常情況 systemd 會建，出現代表有人動過 tmpfiles | ★★★ |
| `status=255` 但 `sshd -t` 沒問題 | 埠被別的程序佔用 | `sudo ss -tlnp \| grep :22`；`sudo lsof -i :22` | ★★★★ |
| 服務是 `inactive (dead)` 而不是 `failed` | 被 `disable` 或 `mask` 了（加固腳本誤傷） | `systemctl unmask sshd && systemctl enable --now sshd` | ★★★★ |
| 服務跑著，但只在某些來源被 refused | 防火牆規則動作寫成 `reject` 而不是 `drop` | ★★★ 對外網用 `deny`（靜默丟棄），`reject` 等於告訴掃描者「這台主機存在」 | ★★★ |

> [!tip] ★★★★ Ubuntu 的服務名稱
> Ubuntu 22.04 以前是 `ssh.service`，24.04 起 `sshd.service` 是它的別名，兩個都能用。
> RHEL 系一律 `sshd.service`。不確定就 `systemctl list-units '*ssh*'`。

#### 【3】`No route to host`

這通常**不是主機防護的問題**，但加固過程也可能造成：改了網路設定、
`rp_filter` 打壞不對稱路由、或防火牆把 ICMP 全擋了造成上游判斷錯誤。

```bash
ip -br addr; ip route get 10.0.10.20      # 你這邊的路由對嗎
arping -I ens192 10.0.10.20               # 同網段：ARP 回不回應
```

同網段連 ARP 都沒回應 → 機器真的掛了或網卡沒起來，走
[[020-01-98-trouble-Linux-常見故障排除]] 的網路分層排查。

#### 【4】`Permission denied (publickey)`：TCP 通了，認證被拒

★★★★★ 這代表**防火牆是通的、sshd 是活的** —— 別再去查防火牆了。
問題百分之百在 sshd 設定或金鑰。

```bash
# 【客戶端】先看它到底試了什麼
$ ssh -vvv ops@10.0.10.20 2>&1 | grep -E 'Offering|Authentications that can continue|Server accepts'
debug1: Authentications that can continue: publickey
debug1: Offering public key: /home/me/.ssh/id_ed25519 ED25519 SHA256:xxxx
debug1: Authentications that can continue: publickey
#   ★★★★ 「Offering 了但還是被拒」→ 伺服器端不認這把鑰匙

# 【伺服器端，透過 console】看 sshd 實際生效的設定，不要用 grep 猜
$ sudo sshd -T | grep -iE 'permitrootlogin|passwordauthentication|pubkeyauthentication|allowusers|allowgroups|authenticationmethods'
permitrootlogin no
passwordauthentication no
pubkeyauthentication yes
allowgroups sshusers
```

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| `allowgroups` 有值，你的帳號不在裡面 | 加固時設了 `AllowGroups` 但忘了把人加進群組 | `sudo usermod -aG sshusers <帳號>`（★★★★★ 一定要 `-aG`，漏了 `a` 會清掉原有群組） | ★★★★★ |
| `passwordauthentication no` 而你還沒放公鑰 | 停用密碼登入的順序做反了 | ★★★★★ **正確順序永遠是：先確認所有人都能用金鑰登入 → 才關密碼** | ★★★★★ |
| `authenticationmethods publickey,keyboard-interactive` | 加了 MFA，要求**兩者都過** | 先改回 `publickey`，確認每個帳號都有 `~/.google_authenticator` 再加回去 | ★★★★★ |
| 日誌有 `Authentication refused: bad ownership or modes for file` | `~/.ssh` 或 `authorized_keys` 權限太寬 | `chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys`，且家目錄不可群組可寫 | ★★★★ |
| 日誌有 `User ops not allowed because account is locked` | 帳號被 `usermod -L` 或 `chage -E 0` 鎖了 | `sudo usermod -U <帳號>`；廠商帳號的話這是**預期行為** | ★★★★ |
| 金鑰對得上，但登入後立刻退出 | shell 被改成 `/sbin/nologin`（受限帳號設計） | `getent passwd <帳號>`；SFTP 專用帳號本來就這樣 | ★★★ |
| RHEL 上一切正常卻仍被拒，`ls -lZ ~/.ssh` 標籤怪怪的 | SELinux：`authorized_keys` 標籤不是 `ssh_home_t` | `sudo restorecon -Rv ~/.ssh`（★★★★★ 手動 `cp` 進來的檔案最常犯） | ★★★★ |

　→ sshd 端的完整設定與強化順序詳見 [[020-02-01-07-svc-SSH-安全強化]]
　　與 [[020-02-01-98-trouble-SSH-常見故障排除]]。
　→ MFA 加在哪一層、為什麼會互斥，詳見 [[090-02-06-guide-防護-遠端存取安全]] 的
　　〈三、多因素驗證：加在哪一層〉。

#### 【5】連上了又被踢掉

```text
kex_exchange_identification: read: Connection reset by peer
Connection closed by 10.0.10.20 port 22
```

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| 大量連線同時進來時才發生 | `MaxStartups`（預設 `10:30:100`）開始隨機丟未認證連線 | 監控／自動化來源加進 `ignoreip` 或調高 `MaxStartups`；★★★ 先確認不是真的在被打 | ★★★ |
| 只有你會發生，別人正常 | Fail2ban 剛把你封在 `ESTABLISHED` 之外 | 走情境五 | ★★★★ |
| 每次都在同一秒斷 | 中間設備（NGFW／IPS）判定為攻擊而 reset | 查該設備的封鎖日誌；見 [[090-05-03-guide-資安設備-入侵偵測與防禦IDS-IPS]] | ★★★ |
| 日誌有 `error: Could not load host key` | 主機金鑰檔遺失或權限錯 | `sudo ssh-keygen -A` 重新產生；★★★★ 會改變主機指紋，要通知所有人 | ★★★ |

**預防**：
- ★★★★★ 改 sshd 前一律 `sudo sshd -t`，改完 **reload 不要 restart**（reload 不斷現有連線）
- ★★★★★ 開第二條連線當保命視窗，測試用第三條新連線
- ★★★★ 加固腳本永遠先寫 drop-in（`/etc/ssh/sshd_config.d/60-hardening.conf`），
  出事時整個檔案移走就還原了，不必去 diff 主設定檔
- ★★★★ 管理來源網段固定寫進 `ignoreip` 與防火牆白名單，並且**寫成網段不要寫單一 IP**

### ★★★★★ 情境二：服務起不來或連不到，但設定看起來都對

**現象**：「我什麼都設好了，就是連不到。」★★★★★ 這句話背後有五種完全不同的原因，
而**大部分人只查了其中一種（防火牆）**。

**★★★★★ 五層排查，由內往外，順序不可以跳**：

```text
  ① 程序有沒有起來？        systemctl is-active <服務>
        │ 沒有 → 不是防火牆問題，去看 journalctl -xeu
        ▼
  ② 有沒有在聽？聽在哪？    sudo ss -tlnp | grep <埠>
        │ 沒在聽      → 服務起來了但 bind 失敗（看日誌，可能是 MAC 埠標籤）→ ⑤
        │ 聽 127.0.0.1 → ★★★★★ 這不是防火牆問題！去改應用程式的 bind 設定
        ▼
  ③ 本機連得到嗎？          curl -sv http://127.0.0.1:<埠>/
        │ 本機也不通 → 服務本身的問題（後端、設定、權限）
        ▼
  ④ 防火牆放行了嗎？        ufw status numbered / firewall-cmd --list-all / nft list ruleset
        │ 規則在但沒作用 → 走情境三
        ▼
  ⑤ MAC 擋了嗎？            ausearch -m AVC -ts recent / dmesg | grep DENIED
        │ 有 AVC/DENIED → 走情境六
        ▼
  ⑥ 封包真的到得了嗎？      sudo tcpdump -ni any port <埠>
        │ 看不到 → 上游（雲端安全群組、邊界防火牆、交換器 ACL）
```

#### 【1】① 程序沒起來

```bash
$ systemctl status nginx --no-pager -l
$ sudo journalctl -xeu nginx --no-pager | tail -30
$ sudo nginx -t                      # ★★★★ 每個服務都有自己的語法檢查指令
```

| 服務 | 語法檢查指令 |
| --- | --- |
| nginx | `sudo nginx -t` |
| sshd | `sudo sshd -t` |
| sudoers | `sudo visudo -c` |
| fail2ban | `sudo fail2ban-client -t` |
| nftables | `sudo nft -c -f /etc/nftables.conf` |
| firewalld | `sudo firewall-offline-cmd --check-config` |
| auditd 規則 | `sudo augenrules --load` 後看 `auditctl -l` |
| apparmor profile | `sudo apparmor_parser -Q <profile>` |

★★★★★ 這張表值得背下來 —— **改完先驗語法再套用**，本章一半的災難都不會發生。

#### 【2】② 在聽，但聽錯位址

```bash
$ sudo ss -tlnp | grep 3306
LISTEN 0 151  127.0.0.1:3306  0.0.0.0:*  users:(("mariadbd",pid=1122,fd=21))
```

★★★★★ 看到 `127.0.0.1:` 就**停止調防火牆**。這條規則怎麼寫都沒用，
封包連進不了那個 socket。去改應用程式的綁定設定（MySQL 的 `bind-address`、
Node 的 `host`、Gunicorn 的 `--bind`）。

| `ss` 顯示 | 意思 |
| --- | --- |
| `0.0.0.0:80` | 所有 IPv4 位址，對外開放 |
| `*:80` 或 `[::]:80` | 所有位址（含 IPv6，多數情況也含 IPv4） |
| `127.0.0.1:3306` | ★★★★★ 只有本機連得到 |
| `10.0.10.20:9100` | 只綁在那張網卡的那個 IP（★★★★ 這其實是好習慣） |

#### 【3】③ 本機通、外部不通

到這一步，問題**確定在網路路徑上**（防火牆或上游）。往情境三走。
但先做一個五秒鐘的檢查：

```bash
# 從另一台同網段的機器測，排除「你的位置」的因素
$ nc -zv 10.0.10.20 8080
# 同網段通、你不通 → 問題在你到這個網段的路徑（VPN、跳板機、路由、上游 ACL）
# 同網段也不通    → 問題在這台機器
```

#### 【4】⑤ bind 失敗且訊息是 `Permission denied`

★★★★★ 以 root 執行卻拿到 `Permission denied`，這是 **SELinux 埠標籤**的招牌症狀：

```text
nginx: [emerg] bind() to 0.0.0.0:8081 failed (13: Permission denied)
```

走情境六【3】。★★★ 另一個可能是埠 < 1024 而服務不是 root 跑的
（這種訊息通常一樣，但 `ss` 會顯示沒有任何程序在聽）。

**原理**：「連不到」是一條路徑上任一環節斷掉的結果，而不是單一原因。
五層排查的價值在於**每一層都能用一個指令得到明確的是／否**，
不必猜。
　→ 詳見 [[090-02-02-guide-防火牆-ufw基礎與實務]] 的〈排查順序〉、
　　[[060-01-04-03-guide-ss-netstat-與lsof]] 與 [[060-01-04-01-guide-tcpdump-基礎抓包]]。

### ★★★★ 情境三：防火牆規則加了卻沒作用

**現象**：規則列表裡明明有那一條，`--list-all` 也看得到，就是不通（或該擋的沒擋）。

**判斷分流**：

```text
規則在列表裡，但重開機就不見        →【4】持久化問題
規則在列表裡，counter 永遠是 0      →【1】前面有規則先命中
規則寫了 accept，封包還是被丟        →【2】另一個 base chain 把它 drop 了
ufw 顯示沒開，但容器的埠通得到       →【3】Docker 繞過 ufw
runtime 改了但沒生效／改了但沒存     →【4】firewalld 的 runtime／permanent
規則在錯的 zone（沒綁任何介面或來源）→【5】zone 沒 active
```

#### 【1】★★★★ 順序：第一個匹配勝出

★★★★★ ufw、iptables、nftables 的 chain 都是**由上往下逐條比對，第一個匹配的動作立刻生效**，
後面的規則不會再看。所以**廣泛的 deny 放在前面，會把後面所有的特例都吃掉**。

```bash
$ sudo ufw status numbered
Status: active

     To                         Action      From
     --                         ------      ----
[ 1] 3306/tcp                   DENY IN     Anywhere            # ★★★★★ 先命中
[ 2] 3306/tcp                   ALLOW IN    192.168.10.0/24     # 永遠輪不到它
```

修法是把特例**插到前面**，不是在後面再加一條：

```bash
$ sudo ufw insert 1 allow from 192.168.10.0/24 to any port 3306 proto tcp comment 'app subnet'
$ sudo ufw status numbered           # ★★★★ 插完一定要重看一次確認位置對
```

**驗證規則到底有沒有被命中**（nftables 最直接）：

```bash
$ sudo nft reset counters                      # 歸零
#   （這時候從外面重打一次流量）
$ sudo nft list ruleset | grep -E 'counter packets [1-9]'
#   目標規則 packets 還是 0 → 確定被前面的規則攔走了，往上找
```

　→ 詳見 [[090-02-02-guide-防火牆-ufw基礎與實務]] 的〈規則順序：第一個匹配勝出〉
　　與 [[090-02-03-guide-防火牆-nftables與iptables]] 的〈★★★ counter 與除錯〉。

#### 【2】★★★★★ accept 不會覆蓋別人的 drop

★★★★★ 這是 nftables 最反直覺、也最常被踩的一點：
**多個 base chain 掛在同一個 hook 上時，全部都會執行**。
你的 chain 說 accept，另一個 chain（ufw 的、Docker 的、其他工具的）說 drop —— 封包還是被丟。

```bash
$ sudo nft list ruleset | grep -n 'type filter hook input'
 12:        type filter hook input priority filter; policy drop;
 89:        type filter hook input priority 0; policy drop;
#   ★★★★★ 出現兩個（以上）→ 這就是「accept 了還是不通」的答案
```

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| 有兩個以上 input base chain | 兩套防火牆並存（ufw ＋ 手寫 nftables，或 firewalld ＋ iptables 直寫） | ★★★★★ **一台機器只能有一個防火牆負責人**，二選一停掉另一個 | ★★★★★ |
| `nft list ruleset` 看不到規則，封包卻被擋 | 有 `iptables-legacy` 的規則存在（另一套後端） | `sudo iptables-legacy -S` 檢查；排維護時段清掉 | ★★★★ |
| `iptables -S` 與 `nft list ruleset` 對不起來 | 正常現象：相容層只看得到 iptables 建立的 table | ★★★★ 以 `nft list ruleset` 為準，那才是完整真相 | ★★★ |
| 主機「網路壞了」：DNS 不通、`apt` 卡住 | 漏了 `ct state established,related accept` —— 出得去回不來 | 補在 input chain 最前面（loopback 之後），排在所有 drop 之前 | ★★★★★ |

　→ 詳見 [[090-02-03-guide-防火牆-nftables與iptables]] 的
　　〈★★★★ 多個 base chain 掛同一個 hook：全部執行〉。

#### 【3】★★★★★ Docker 繞過 ufw

**現象**：`ufw status` 顯示只開了 22 與 80，但容器發布的 8080 從網際網路上通得到。

**原因**：★★★★★ Docker 直接往 `nat` 表與 `FORWARD` 鏈寫規則，
而 ufw 的使用者規則在 `INPUT` 鏈。**兩者根本不在同一條路徑上**，
ufw 管不到容器的發布埠。

```bash
$ sudo docker ps --format '{{.Names}}\t{{.Ports}}'
webapp    0.0.0.0:8080->80/tcp, :::8080->80/tcp     # ★★★★★ 對全世界開放
redis     127.0.0.1:6379->6379/tcp                  # ★ 只綁 loopback，安全
```

| 解法 | 做法 | 評價 |
| --- | --- | --- |
| ★★★★★ A：綁 loopback | `-p 127.0.0.1:8080:80`，對外一律走反向代理 | 最乾淨，優先用這個 |
| ★★★★ B：`DOCKER-USER` | 在 `/etc/ufw/after.rules` 加 `DOCKER-USER` 區塊後 `ufw reload` | 需要對外發布時用 |
| ★★★ C：`iptables: false` | 關掉 Docker 自己管 iptables | 會連容器出向都要自己處理，不建議新手用 |

★★★★★ **檢查方式（每台 Docker 主機都要做一次）**：

```bash
$ sudo ss -tlnp | grep -E '0\.0\.0\.0|\[::\]'      # 有哪些真的對外
$ sudo docker ps --format '{{.Names}}\t{{.Ports}}' | grep '0.0.0.0'
```

　→ 詳見 [[090-02-02-guide-防火牆-ufw基礎與實務]] 的〈★★★★ Docker 會繞過 ufw〉。

#### 【4】★★★★★ 沒生效 vs 沒存下來（firewalld 的兩份設定）

★★★★★ firewalld 有**兩份獨立的設定**：runtime（記憶體，立刻生效、重開就沒）
與 permanent（磁碟，重開才會讀）。這是 firewalld 排錯最大的坑：

| 你做了什麼 | 現在生效嗎 | 重開機後還在嗎 |
| --- | --- | --- |
| `firewall-cmd --add-service=http` | ★ 是 | ✗ 不在 |
| `firewall-cmd --permanent --add-service=http` | ✗ 否 | ★ 在 |
| `--permanent` 加完再 `--reload` | ★ 是 | ★ 在 |
| `--add-...` 後 `--runtime-to-permanent` | ★ 是 | ★ 在（但★★★ 會把 `--timeout` 的臨時規則一起存進去） |

```bash
# ★★★★★ 診斷：runtime 與 permanent 差在哪
$ diff <(sudo firewall-cmd --list-all-zones) <(sudo firewall-cmd --permanent --list-all-zones)
```

**其他兩個工具的持久化**：

```bash
# ufw：規則自動存，但服務要 enable，且 ufw.conf 要是 yes
systemctl is-enabled ufw                 # 應為 enabled
grep ENABLED /etc/ufw/ufw.conf           # 應為 ENABLED=yes

# nftables：★★★★★ nft add 下的規則【不會】自動存檔
systemctl is-enabled nftables            # 應為 enabled
sudo nft list ruleset | sudo tee /etc/nftables.conf     # 存檔
sudo nft -c -f /etc/nftables.conf        # ★★★★ 存完先驗語法
```

　→ 詳見 [[090-02-04-guide-防火牆-firewalld]] 的
　　〈★★★★★ 第一課：runtime 與 permanent 是兩份獨立的設定〉
　　與 [[090-02-03-guide-防火牆-nftables與iptables]] 的〈持久化與原子套用〉。

#### 【5】★★★★ 規則加在一個沒有 active 的 zone

firewalld 特有：規則加進 `internal`，但那個 zone **沒有綁任何介面或來源**，
所以永遠不會被使用。

```bash
$ sudo firewall-cmd --get-active-zones
public
  interfaces: ens192
#   ★★★★ internal 沒出現 → 它不是 active，加在裡面的規則等於沒加

# 綁上去（二選一）
$ sudo firewall-cmd --permanent --zone=internal --add-source=192.168.10.0/24
$ sudo firewall-cmd --permanent --zone=internal --change-interface=ens224
$ sudo firewall-cmd --reload
```

★★★★ zone 的判斷順序是「**來源綁定 → 介面綁定 → default zone**」，
來源綁定永遠優先。這也是 firewalld 最好用的一招：
把管理網段整段綁到一個高信任 zone，其餘走 public。

★★★★ 另一個相關陷阱：綁了介面到某個 zone，重開機或 `nmcli con up` 之後又跳回 `public` ——
因為 **NetworkManager 的 `connection.zone` 才是權威**：

```bash
$ sudo nmcli connection modify <連線名> connection.zone internal
$ sudo nmcli connection up <連線名>
```

　→ 詳見 [[090-02-04-guide-防火牆-firewalld]] 的
　　〈★★★★ 來源網段綁 zone —— firewalld 最好用的一招〉。

**預防**：
- ★★★★★ 規則一律加 `comment`（ufw）或寫進版本控管的規則檔（nftables），
  半年後你不會記得那條 8443 是給誰開的
- ★★★★★ nftables 規則**永遠寫成檔案**，`nft -c -f` 檢查後 `nft -f` 原子套用，
  不要在指令列一條一條下 —— 中途出錯會留下半套規則
- ★★★★ 改完一律**從外部實測**（`nc -zv`／`nmap`），不要只看規則列表
- ★★★★ 改完一律**重開機驗證一次**，這是唯一能確認持久化真的做對了的方法

### ★★★★ 情境四：Fail2ban 沒有擋

**現象**：Fail2ban 裝了、服務也在跑，但攻擊照樣進來，或者你故意打錯密碼十次也沒被封。

**★★★★★ 判斷分流：先用一個指令把問題切成兩半**

```bash
$ sudo fail2ban-client status sshd
Status for the jail: sshd
|- Filter
|  |- Currently failed: 0
|  |- Total failed:     0          ← ★★★★★ 這個數字決定往左還是往右
|  `- File list:        /var/log/auth.log
`- Actions
   |- Currently banned: 0
   |- Total banned:     0
   `- Banned IP list:
```

```text
Total failed = 0        → 問題在【前半段】：filter／日誌來源      走【1】【2】【3】
Total failed > 0 但沒 Ban → 問題在【門檻或白名單】                走【5】
有 Ban 但對方照樣連得進來 → ★★★★★ 問題在【後半段】：banaction    走【4】
```

★★★★★ 不先做這個切分，你會在錯的地方查一整個下午。

#### 【1】jail 根本沒 enabled

```bash
$ sudo fail2ban-client status
Status
|- Number of jail:      1
`- Jail list:   sshd
#   ★★★★ 你以為設好的 jail 不在這個清單裡 → 它沒 enabled
```

```ini
# /etc/fail2ban/jail.local
[nginx-limit-req]
enabled = true          # ★★★★★ 少了這一行，整個 section 等於沒寫
```

★★★★★ **只改 `jail.local`，永遠不要碰 `jail.conf`** ——
`jail.conf` 會被 `apt upgrade` 覆蓋，你的設定會在某個更新的凌晨無聲消失。

```bash
$ sudo fail2ban-client -t          # ★★★★★ 改完先驗語法再 restart
OK: configuration test is successful
```

　→ 詳見 [[090-02-05-guide-防護-Fail2ban入侵防護]] 的
　　〈★★★★★ 第一課：只改 `jail.local`，不要碰 `jail.conf`〉。

#### 【2】★★★★★ 日誌路徑不對，或根本沒有那個檔

**Ubuntu 24.04 預設不裝 rsyslog**，`/var/log/auth.log` 不存在，
於是 Fail2ban 起不來或抓不到任何東西：

```text
Have not found any log file for sshd jail
```

| 解法 | 做法 | 評價 |
| --- | --- | --- |
| ★★★★★ A | `jail.local` 加 `backend = systemd`，直接讀 journal | 建議做法 |
| ★★★★ B | `sudo apt install rsyslog`，把 `/var/log/auth.log` 生回來 | 想保留檔案式日誌時用 |

```bash
$ ls -l /var/log/auth.log /var/log/secure 2>&1      # 兩系統的路徑不同
$ journalctl -t sshd -n 20 --no-pager               # 確認 journal 裡有東西
```

★★★ RHEL 系是 `/var/log/secure`，不是 `auth.log`；抄別人的設定最常錯在這裡。

　→ 詳見 [[090-02-05-guide-防護-Fail2ban入侵防護]] 的
　　〈★★★★★ 步驟 0：先確認日誌到底在哪〉。

#### 【3】★★★★★ filter 沒匹配到

```bash
$ fail2ban-regex /var/log/auth.log /etc/fail2ban/filter.d/sshd.conf
...
Lines: 4213 lines, 0 ignored, 87 matched, 4126 missed
[Processed in 0.35 sec]
```

★★★★★ 要看**兩個數字**，缺一不可：

| 數字 | 是 0 的意思 | 解法 |
| --- | --- | --- |
| `Failregex` 匹配數 | 正則沒抓到任何行 | 檢查正則；自訂 filter 一定要有裸的 `<HOST>` |
| `Date template hits` | ★★★★★ Fail2ban 判斷不出事件時間，**有匹配也不會封鎖** | 在 filter 加正確的 `datepattern`；日期格式裡的 `%` 要寫成 `%%` |

其他常見錯：

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| `ERROR No failure-id group in ...` | 正則裡沒有 `<HOST>`，或被寫成 `(<HOST>)` | 加上**裸的** `<HOST>`，不要自己寫 IP 正則、不要加括號 | ★★★★ |
| 改了 `filter.d/sshd.local` 後原本會抓的不抓了 | ★★★★★ `.local` 的 `failregex` **整組取代**了 `.conf` 的 | 第一行加 `%(known/failregex)s` 把原規則接回來 | ★★★★ |
| logrotate 之後就不再偵測 | `backend` 用了不會偵測換檔的模式 | 用 `backend = auto`／`polling`；systemd backend 不受影響 | ★★★ |
| 反向代理後面，封鎖到的都是代理 IP | 日誌記的是代理 IP | Nginx 設 `set_real_ip_from` ＋ `real_ip_header`，見 [[060-02-02-09-guide-Nginx-安全設定]] | ★★★★ |

　→ 詳見 [[090-02-05-guide-防護-Fail2ban入侵防護]] 的〈★★★★ 自訂 filter：完整走一遍〉。

#### 【4】★★★★★ 有 Ban，但對方照樣連得進來 —— banaction 選錯的沉默失敗

★★★★★ **這是本章最陰險的一個坑**：`banaction` 選錯**不會有任何錯誤訊息**。
Fail2ban 開開心心地說「我封了」，`Currently banned: 37`，
但那個 action 對應的是你沒在用的防火牆，規則寫到了一個不存在的地方（或根本沒寫成功）。

```bash
# ★★★★★ 診斷：去【防火牆那一側】確認規則真的存在
$ sudo ufw status numbered | grep -i f2b        # ufw 環境
$ sudo nft list ruleset | grep -A10 f2b         # nftables 環境
$ sudo iptables -L -n --line-numbers | grep f2b # iptables 環境
$ sudo firewall-cmd --list-rich-rules           # firewalld 環境
#   ★★★★★ Currently banned 有數字、但這裡什麼都沒有 → 就是 banaction 選錯
```

| 你的防火牆 | 正確的 `banaction` |
| --- | --- |
| ufw | `ufw` |
| 手寫 nftables | `nftables-multiport`（★★★★ 封鎖量大時用 set，效能差很多） |
| firewalld | `firewallcmd-ipset` |
| iptables（傳統） | `iptables-multiport` |

```ini
# /etc/fail2ban/jail.local
[DEFAULT]
banaction = ufw              # ★★★★★ 改完一定要去防火牆那側驗證看得到規則
```

★★★★ 附帶的效能問題：`iptables-multiport` 每個 IP 一條規則、線性比對，
封鎖清單到幾千筆之後主機會吃 CPU、網路變慢。改用
`nftables-multiport`（set）或 `firewallcmd-ipset`。

　→ 詳見 [[090-02-05-guide-防護-Fail2ban入侵防護]] 的
　　〈★★★★★ `banaction`：選錯不會有任何錯誤訊息〉與
　　〈★★★★ 與 nftables set 的整合：封鎖量大時的唯一解〉。

#### 【5】★★★ 有 failed 但沒到門檻，或被白名單吃掉

```bash
$ sudo fail2ban-client get sshd ignoreip       # 來源是不是在白名單裡
$ sudo fail2ban-client get sshd maxretry
$ sudo fail2ban-client get sshd findtime
```

★★★★ 三個門檻參數的關係：**在 `findtime` 這段時間內，失敗達到 `maxretry` 次，
就封鎖 `bantime`**。測試時常見的誤會是「我打錯十次了為什麼沒封」——
因為那十次分散在超過 `findtime` 的時間裡。

```bash
# 觀察 Fail2ban 自己怎麼說（★★★★ 最直接的證據）
$ sudo journalctl -u fail2ban --since '15 min ago' --no-pager | grep -E 'Found|Ban|Unban|ERROR'
```

看得到 `Found` 但沒有 `Ban` → 門檻沒到或被 `ignoreip` 吃掉。

#### 【6】★★★★★ 就算全部設對了，Fail2ban 也擋不住的事

| 情況 | 為什麼擋不住 | 真正的解 |
| --- | --- | --- |
| 攻擊者被封後立刻換 IP 繼續打 | 分散式暴力破解，天生擋不住 | ★★★★★ **關掉密碼登入**（[[020-02-01-07-svc-SSH-安全強化]]）才是根本解 |
| 已建立的連線在封鎖後仍然活著 | conntrack 的 `ESTABLISHED` 不受新規則影響 | 正常現象；要立刻斷可搭配 `conntrack -D -s <IP>` |
| 重啟後封鎖名單全空 | `dbpurgeage`（預設 `1d`）小於 `bantime` | `fail2ban.local` 設 `dbpurgeage` ≥ 最大 `bantime` |
| `bantime.increment` 沒有遞增 | 同上，或忘了設 `bantime.increment = true` | 兩者一起檢查 |

★★★★★ **Fail2ban 是降噪工具，不是防護的主力。**
真正的防線是金鑰認證 ＋ 停用密碼登入 ＋ 管理埠限制來源網段。

### ★★★★ 情境五：Fail2ban 把自己或同事鎖了

**現象**：連線突然變成逾時。★★★★ 尤其是「本來好好的，我打錯幾次密碼之後」，
或「全機關的人同時連不上」。

#### 【1】怎麼確認是不是 Fail2ban

★★★★ 你已經連不進去了，所以這一步要**在別的網段**或 console 上做：

```bash
# 【方法 A】從另一個網段的機器連進去查
$ sudo fail2ban-client status sshd
   `- Banned IP list:   203.0.113.44 198.51.100.7
#   ★★★★★ 你的出口 IP 出現在這裡 → 確認就是它

# 【方法 B】在 console 上直接查防火牆那側
$ sudo nft list ruleset | grep -A20 f2b-sshd
$ sudo ufw status numbered | grep -i 'DENY\|REJECT'
$ sudo iptables -L f2b-sshd -n --line-numbers

# 【方法 C】看日誌裡的 Ban 事件
$ sudo journalctl -u fail2ban --since today | grep -E 'Ban 203\.0\.113\.'
2026-09-03 09:14:22 fail2ban.actions [812]: NOTICE [sshd] Ban 203.0.113.44
```

★★★★★ **先確認你的出口 IP 是什麼**。在機關內部，你看到的內網 IP
跟伺服器看到的來源 IP 常常不一樣（NAT）：

```bash
$ curl -s ifconfig.me; echo          # 從你的機器查對外出口 IP
$ sudo last -i -n 20                 # 在伺服器上看最近登入的來源 IP
$ sudo ss -tnp | grep :22            # 現有 SSH 連線的來源
```

#### 【2】怎麼解

```bash
# ★★★★★ 解單一 IP（最常用）
$ sudo fail2ban-client set sshd unbanip 203.0.113.44
1

# ★★★★ 解全部（緊急時用，會清掉所有 jail 的所有封鎖）
$ sudo fail2ban-client unban --all

# ★★★★★ 完全進不去、只有 console：直接把服務停掉
$ sudo systemctl stop fail2ban
#   ★★★ 停完記得處理完再啟動，不要就這樣放著
```

★★★ 解封之後**規則不會立刻讓既有連線恢復**，但新連線可以進來了。
如果解了還是不通，回情境一重新分流 —— 可能同時還有別的原因。

#### 【3】★★★★★ 怎麼避免：`ignoreip` 先寫，再開 jail

```ini
# /etc/fail2ban/jail.local
[DEFAULT]
# ★★★★★ 順序永遠是：先寫白名單 → 再開 jail
ignoreip = 127.0.0.1/8 ::1
           10.0.10.0/24            # 管理網段
           192.168.20.0/24         # 辦公室網段
           203.0.113.44            # 機關對外 NAT 出口
```

```bash
$ sudo fail2ban-client -t && sudo systemctl reload fail2ban
$ sudo fail2ban-client get sshd ignoreip        # ★★★★ 確認真的吃進去了
```

| 做法 | 為什麼重要 | ★ |
| --- | --- | --- |
| `ignoreip` 寫**網段**不要寫單一 IP | 你的 IP 會變（DHCP、換 VPN 出口、換辦公室） | ★★★★★ |
| 把**機關 NAT 出口**加進去 | ★★★★★ 否則一個人打錯密碼，全機關一起被鎖 | ★★★★★ |
| 監控主機、備份腳本、Ansible 的來源都加進去 | 自動化連線很密集，很容易誤觸門檻 | ★★★★ |
| 測試時先把 `bantime` 設短（如 `60`） | 測壞了一分鐘就自己解開 | ★★★★ |
| 開 jail 前先確認自己**有 console** | 這是唯一 100% 的退路 | ★★★★★ |

> [!danger] ★★★★★ `ignoreip` 不是萬能的，也不該無限擴大
> 把整個 `10.0.0.0/8` 塞進 `ignoreip` 等於在內網完全放棄 Fail2ban。
> 內網被打進來的橫向移動，正是它該擋的場景之一。
> 白名單只放**管理來源**與**已知的自動化來源**，其餘一律受管。

**原理**：Fail2ban 只認**日誌裡看到的來源 IP**，不認人。
你和攻擊者從同一個 NAT 出口出去，對它來說就是同一個來源。
　→ 詳見 [[090-02-05-guide-防護-Fail2ban入侵防護]] 的
　　〈★★★★★ `ignoreip`：先寫白名單，再開 jail〉與〈解封〉。

### ★★★★★ 情境六：SELinux／AppArmor 擋住，但錯誤訊息看不出來

**現象**：★★★★★ **`Permission denied`，但 `ls -l` 看起來完全正確**。
網頁 403、bind 失敗、反向代理 502、服務讀不到自己的設定檔 ——
權限查了三遍都對，就是不能動。

> [!tip] ★★★★★ 三十秒判斷法（背下來）
> 看到 `Permission denied` 時，先問自己：**「這個拒絕，用 `ls -l` 看起來合理嗎？」**
> - **不合理**（權限明明就對、甚至是 root 在跑）→ 八成是 MAC
> - **合理**（權限確實不對）→ 是 DAC，`chown`／`chmod` 就好

#### 【1】★★★★★ 確認是不是 MAC

```bash
# ── RHEL 系（SELinux）────────────────────────────────────
$ getenforce
Enforcing
$ sudo ausearch -m AVC -ts recent
type=AVC msg=audit(1756873421.123:456): avc:  denied  { read } for  pid=2211
  comm="nginx" name="index.html" dev="dm-0" ino=1049601
  scontext=system_u:system_r:httpd_t:s0
  tcontext=unconfined_u:object_r:default_t:s0 tclass=file permissive=0

# ── Debian 系（AppArmor）────────────────────────────────
$ sudo aa-status | head -3
$ sudo dmesg | grep -i 'apparmor.*DENIED' | tail
[12345.678] audit: type=1400 apparmor="DENIED" operation="open"
  profile="/usr/sbin/nginx" name="/data/www/index.html" pid=2211 comm="nginx"
  requested_mask="r" denied_mask="r"
$ journalctl -k --grep 'apparmor.*DENIED' -n 20 --no-pager
```

★★★★★ **更快的做法（但要立刻切回去）**：

```bash
$ sudo setenforce 0                     # SELinux 暫時轉 permissive
$ sudo aa-complain /usr/sbin/nginx      # AppArmor 該 profile 轉 complain
#   （測一下功能）
#   好了 → 確定是 MAC
$ sudo setenforce 1                     # ★★★★★ 立刻切回來，然後找正確解法
$ sudo aa-enforce /usr/sbin/nginx
```

> [!danger] ★★★★★ 「先關掉再說」是這一章最貴的壞習慣
> `setenforce 0` 是**診斷手段**，不是解法。
> 更嚴重的是 `/etc/selinux/config` 改成 `disabled` —— 那不只是關掉，
> 而是**停止維護檔案標籤**；哪天想開回來，會因為新產生的檔案全都沒有標籤而開不了機
> （救法：救援模式改回 `permissive`、`touch /.autorelabel`、重開機重貼標籤）。
> ★★★★★ 需要暫時放寬就用 `permissive`，不要用 `disabled`。

#### 【2】★★★★★ AVC 訊息怎麼讀

```text
scontext=system_u:system_r:httpd_t:s0             ← 誰（來源網域）：nginx
tcontext=unconfined_u:object_r:default_t:s0       ← 對什麼（目標型別）：那個檔案
tclass=file  { read }                             ← 想做什麼
```

★★★★ 關鍵在 `tcontext` 那一段的**型別**：

| 你看到的 tcontext 型別 | 意思 | 修法 |
| --- | --- | --- |
| `default_t` | ★★★★★ 這個檔案根本沒有被貼上正確標籤 | `semanage fcontext -a` ＋ `restorecon` |
| `user_home_t` | 在家目錄底下（把網站根目錄放家目錄的典型症狀） | 移到 `/var/www` 或加 fcontext 規則 |
| `httpd_sys_content_t` 而動作是 `write` | 標籤對，但那是「唯讀內容」的型別 | 可寫目錄要用 `httpd_sys_rw_content_t` |
| 動作是 `name_bind` | 埠標籤問題 | 走【3】 |
| 動作是 `name_connect` | ★★★★★ 布林值問題（服務要往外連） | 走【4】 |

#### 【3】★★★★★ 服務要聽非標準埠

```text
nginx: [emerg] bind() to 0.0.0.0:8081 failed (13: Permission denied)
```

```bash
$ sudo semanage port -l | grep http_port_t
http_port_t   tcp   80, 81, 443, 488, 8008, 8009, 8443, 9000
#   ★★★★ 8081 不在裡面 → 加進去

$ sudo semanage port -a -t http_port_t -p tcp 8081
$ sudo semanage port -l | grep 8081          # 確認
```

★★★★ 若回 `ValueError: Port tcp/8080 already defined` ——
該埠已屬於別的型別（如 `http_cache_port_t`），改用 `-m` 修改，
但要先評估對原服務的影響。

　→ 詳見 [[090-02-07-guide-防護-SELinux與AppArmor]] 的〈場景二：服務要聽非標準埠〉。

#### 【4】★★★★★ 反向代理 502：布林值

```text
connect() to 127.0.0.1:9000 failed (13: Permission denied) while connecting to upstream
```

```bash
$ getsebool -a | grep httpd_can_network
httpd_can_network_connect --> off              # ★★★★★ 就是它
httpd_can_network_connect_db --> off

$ sudo setsebool -P httpd_can_network_connect on
#   ★★★★ 只連本機資料庫的話用範圍更小的 httpd_can_network_connect_db
#   ★★★★★ -P 代表 permanent，漏了重開機就沒了
```

#### 【5】★★★★★ 修好了，一週後又壞掉

**原因**：用了 `chcon`。`chcon` 只改**當下**的標籤，
`restorecon`、系統重新標記、`cp` 覆蓋、套件更新都會把它還原。

```bash
# ✗ 錯誤做法（暫時的）
$ sudo chcon -t httpd_sys_content_t /data/www -R

# ★★★★★ 正確做法（永久的）：寫進政策 → 再套用
$ sudo semanage fcontext -a -t httpd_sys_content_t "/data/www(/.*)?"
$ sudo restorecon -Rv /data/www
$ matchpathcon /data/www/index.html          # ★★★★ 確認「應該是什麼」
```

#### 【6】AppArmor 那一側的對應坑

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| 改了主 profile，套件更新後規則消失 | 直接改 `/etc/apparmor.d/usr.sbin.nginx` 被覆蓋 | 規則寫在 `/etc/apparmor.d/local/usr.sbin.nginx` | ★★★★ |
| 加了 `/data/www/** r,` 但列目錄仍失敗 | ★★★★ `**` 不涵蓋目錄本身 | 同時加 `/data/www/ r,`（結尾斜線那一條） | ★★★★ |
| `aa-status` 說載入 enforce，行為卻沒變 | 服務在 profile 載入前就啟動了 | `systemctl restart <服務>` | ★★★★ |
| `aa-status` 載入很多，nginx 卻完全不受限 | ★★★★ Ubuntu 的 nginx 套件**沒有預設 profile** | `sudo aa-unconfined` 逐項確認；用 `aa-genprof` 自己產 | ★★★★ |
| `apparmor_parser -r` 回 `Found unexpected character` | 語法錯（少逗號、路徑沒引號） | 每條規則結尾要有 `,`；`apparmor_parser -Q` 只驗語法不載入 | ★★★ |

★★★★ 從實際日誌產生規則的正規流程：

```bash
$ sudo aa-complain /usr/sbin/nginx      # ① 轉 complain，只記錄不阻擋
#   （② 把功能完整操作一遍，讓該碰的路徑都碰過）
$ sudo aa-logprof                       # ③ 從日誌互動式產生規則
$ sudo aa-enforce /usr/sbin/nginx       # ④ 切回 enforce
```

#### 【7】★★★★★ 什麼時候該懷疑 `audit2allow` 的建議

`audit2allow` 很方便，但它是**照著你剛才那筆拒絕反推規則**，
很容易產生「放行整個 `default_t`」這種範圍過大的政策 —— 等於把 SELinux 挖個洞。

★★★★★ **正確的修法順位**：
① 標籤（`semanage fcontext` ＋ `restorecon`）→
② 布林值（`setsebool -P`）→
③ 埠（`semanage port`）→
④ 真的都不行，才考慮自訂模組，而且要逐條看它產生了什麼。

```bash
$ sudo semodule -l | grep <模組名>        # 查已載入的自訂模組
$ sudo semodule -r <模組名>               # 覺得不對就移除，回到三步法
```

★★★★ 另一個「什麼都查不到」的情況：`dontaudit` 規則把事件靜音了。

```bash
$ sudo semodule -DB          # 暫時停用 dontaudit，重測
#   （重現問題，再看 ausearch）
$ sudo semodule -B           # ★★★★ 測完一定要恢復
```

**原理**：DAC（rwx）問「你是誰」，MAC 問「這個程序被允許碰這類物件嗎」。
兩者是**串聯**的：DAC 過了，MAC 還要再過一次。
所以「權限明明對」和「被拒絕」可以同時成立，一點都不矛盾。
　→ 詳見 [[090-02-07-guide-防護-SELinux與AppArmor]] 的
　　〈DAC：傳統權限模型，以及它擋不住什麼〉與〈MAC：換一個問題來問〉。

### ★★★★ 情境七：強化之後某個功能壞了

**現象**：跑完加固腳本（或照 TWGCB／Lynis 建議改了一批設定）之後，
某個功能不能用了，但**改了幾十項，不知道是哪一項造成的**。

#### 【1】★★★★★ 先確認「壞掉」的時間點

```bash
# 什麼時候改的？（有 etckeeper 的話這一步是三秒鐘的事）
$ sudo git -C /etc log --oneline -20
$ sudo git -C /etc show <commit>            # 看那次改了什麼

# 沒有 etckeeper：用檔案時間找
$ sudo find /etc -newermt '2026-09-03 08:00' -type f 2>/dev/null | head -40
$ sudo ls -lt /etc/sysctl.d/ /etc/modprobe.d/ /etc/ssh/sshd_config.d/
```

★★★★★ 這就是為什麼加固之前要先 `etckeeper init` ——
**沒有基準就沒有 diff，沒有 diff 就只能猜**。
　→ 詳見 [[090-02-08-guide-防護-系統強化與稽核]] 的
　　〈一、用 etckeeper 把 /etc 納入版本控制〉。

#### 【2】★★★★ 二分法定位

★★★★★ 加固項目通常分成幾個**互相獨立的檔案**，這讓二分法很好做：

```bash
# 加固設定的典型落點（一次移走一整組，重測，逐步縮小範圍）
/etc/sysctl.d/60-hardening.conf          # 核心參數
/etc/modprobe.d/60-hardening.conf        # 模組黑名單
/etc/ssh/sshd_config.d/60-hardening.conf # SSH
/etc/security/limits.d/                  # 資源限制
/etc/fstab                               # 掛載選項（noexec/nosuid/nodev）
/etc/audit/rules.d/                      # auditd 規則
/etc/login.defs、/etc/profile.d/         # umask、密碼政策
```

```bash
# 第一輪：把最可疑的一整組移走，重測
$ sudo mv /etc/sysctl.d/60-hardening.conf /root/ && sudo sysctl --system
#   （測功能）好了 → 就在這個檔裡，進第二輪

# 第二輪：把該檔對半砍，一半留一半註解，重測
#   ★★★★ 二十行的設定，四輪就能定位到單一行
```

> [!warning] ★★★★ 模組黑名單與掛載選項要重開機才完全生效
> `sysctl` 可以 `sysctl --system` 立刻重載，但 `modprobe.d` 的黑名單
> 對**已載入的模組沒有效果**，`fstab` 的掛載選項也要重掛才算。
> 二分法時要把這一點考慮進去，否則你會以為「移走了還是壞的」而找錯方向。

#### 【3】★★★★★ 五個最常見的「加固副作用」

| 現象 | 元凶 | 解法 | ★ |
| --- | --- | --- | --- |
| 容器全部沒網路／VPN 通了但不能上網 | `net.ipv4.ip_forward = 0` 套在 Docker 宿主或 VPN 端點 | 該主機不設這一項（或設 1）：`sudo sysctl -w net.ipv4.ip_forward=1`，並從加固檔移除該行 | ★★★★★ |
| 重開機後 `snap` 全壞、`lxd`／`certbot` 起不來 | modprobe 黑名單停用了 `squashfs` | ★★★★★ **Ubuntu 上不要停用 squashfs**；從 `60-hardening.conf` 移除該行後重開 | ★★★★★ |
| 多網卡機器某些連線莫名逾時、單向不通 | `rp_filter = 1` 遇到不對稱路由，回程封包被丟 | 改 `net.ipv4.conf.all.rp_filter = 2`（loose）或 0，用防火牆補；`sysctl -a --pattern rp_filter` 確認生效值 | ★★★★ |
| `apt install` 某套件失敗，`Permission denied` 且路徑在 `/tmp` | `/tmp` 掛了 `noexec`，安裝腳本跑不動 | 暫時 `sudo mount -o remount,exec /tmp`，裝完改回 `noexec` | ★★★ |
| 網站上傳功能壞掉，檔案變成 `600` 其他程序讀不到 | 收緊 umask 時動到 `/etc/login.defs`，影響到服務 | ★★★★ 改成**只對互動式登入設 umask**（`/etc/profile.d/`），不要動全域 | ★★★★ |

★★★★ 另外兩個容易被忽略的：

| 現象 | 元凶 | 解法 |
| --- | --- | --- |
| 關掉某服務後，隔天備份／監控失效 | 關之前只看「當下有沒有連線」，沒查歷史 | 關服務前一定要 `journalctl -u <svc> --since "7 days ago"`；對照 `/root/baseline/` 復原 |
| `systemctl disable` 了服務，但埠還開著 | 有對應的 `.socket` 單元在監聽，被連時拉起 service | `systemctl list-units --type=socket --state=listening`，把 `.socket` 一起 `disable --now`，必要時 `mask` |

　→ 詳見 [[090-02-01-guide-防護-伺服器初始安全設定]] 的〈【六】核心層強化〉
　　與〈【三】★★★★★ 關閉不需要的服務與對外埠〉。

#### 【4】★★★★ 安全與可用之間怎麼取捨

★★★★★ 不是每一項建議都要照做。用**四問法**分桶：

| 問題 | 判斷 |
| --- | --- |
| ① 這項對**我這台機器的角色**有意義嗎？ | Web 伺服器不需要的 USB 儲存黑名單，套上去只是噪音 |
| ② 不做的話，**實際風險**是什麼？ | 說得出攻擊路徑才算真的有風險 |
| ③ 做了會**壞掉什麼**？ | 說不出來就代表你還沒驗證，先在測試機做 |
| ④ 有沒有**成本更低的等效控制**？ | 例如「限制來源網段」常常比「關掉整個功能」更實際 |

★★★★★ 分完之後只有三種結果：**照做**、**用等效控制替代**、
**接受風險並記錄理由**。第三種完全合法，但**一定要寫下來**，
否則下一次稽核你還要再解釋一次。

　→ 詳見 [[090-02-08-guide-防護-系統強化與稽核]] 的〈Step 3：用四問法分桶〉。

**預防**：
- ★★★★★ 加固前 `etckeeper init`，每一步都有 commit
- ★★★★★ **一次只改一類**，改完立刻驗證該類的功能，不要一次套二十項
- ★★★★ 在**測試機**跑完一輪再上正式機；正式機走變更流程
  （[[100-02-08-guide-維運-變更管理流程]]）
- ★★★★ 加固完成後**重開機驗證一次** —— 很多副作用只在重開機後出現

### ★★★ 情境八：稽核工具報一堆紅字

**現象**：跑完 Lynis／OpenSCAP／AIDE，畫面一片紅，
「這樣是不是代表我這台機器很危險？」

**★★★★★ 先建立一個觀念：檢核工具的輸出是【建議】不是【缺失】。**
它不知道你這台機器的角色、不知道你的補償控制、也不知道你的網路架構。

#### 【1】★★★★ Lynis：哪些要理、哪些不用理

```bash
$ sudo lynis audit system --quick
...
  Hardening index : 64 [############        ]
$ sudo grep -E '^(warning|suggestion)' /var/log/lynis-report.dat | head -30
```

| 類型 | 意思 | 怎麼處理 |
| --- | --- | --- |
| `warning` | ★★★★ Lynis 認為明確有問題 | **優先看這一類**，逐條走四問法 |
| `suggestion` | 建議 | 數量很多，挑跟角色相關的看 |
| 「未安裝某工具」類 | 只是它沒偵測到 | ★★★ 有等效方案就記錄理由，不必為了分數硬裝 |
| 「未設定某參數」但你有補償控制 | 例如它建議關某服務，你用防火牆限來源 | 記錄補償控制，這在稽核上是站得住的 |

★★★ **分數不是目的**。`Hardening index` 拿來看**趨勢**（這個月比上個月高嗎），
不要拿來跟別台機器比 —— 角色不同、基準不同，比了沒有意義。

★★★ 分數每次跑都不一樣，通常是因為用了不同來源的 Lynis（套件版 vs GitHub 版），
或有暫時性測試（如「可更新套件數」）。★★★ 固定用同一種來源，趨勢才有意義。

　→ 詳見 [[090-02-08-guide-防護-系統強化與稽核]] 的
　　〈二、讀懂 Lynis 並判斷該不該照做〉。

#### 【2】OpenSCAP 的常見誤讀

| 現象 | 意思 | 處理 |
| --- | --- | --- |
| 一大片 `notapplicable` | 該 profile 針對的版本或角色與本機不符 | ★★★ **不算 fail，不必處理**；換成對應版本的 datastream |
| `Profile ... was not found` | profile ID 抄錯，或該 datastream 沒有這個 ID | `oscap info <ds檔>` 看實際有哪些 ID，★★★★ 不要照抄文件 |
| `Could not open file ... ssg-*.xml` | 沒裝對應的 ssg 套件，或發行版版本對不上 | `ls /usr/share/xml/scap/ssg/content/` 看有哪些 |

★★★★ 台灣機關的基準對照見 [[090-06-07-guide-TWGCB-Linux檢測與符合性報告]]
與 [[090-06-08-guide-TWGCB-Linux誤判與服務衝突處理]] —— 後者專門處理
「基準說要關，但關了業務會壞」的情況。

#### 【3】★★★★★ auditd 報太多／把機器搞掛

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| `auditctl -s` 的 `lost` 一直增加 | 規則太寬（常見是無條件的 `-S execve` 或 `-S openat`） | 加 `-F` 條件收斂；調大 `-b`；`aureport -k --summary` 找出哪個 key 最吵 | ★★★★★ |
| 機器凌晨自己關機，audit.log 停在關機前 | `admin_space_left_action = halt`，`/var/log` 空間耗盡觸發 | ★★★★★ 改成 `SUSPEND` 或 `SYSLOG`，並把 `/var/log` 納入監控 | ★★★★★ |
| `ausearch -k <key>` 查不到東西 | 規則沒 `augenrules --load`，或 `auditctl -l` 顯示 `No rules` | `sudo augenrules --load && sudo auditctl -l` | ★★★★ |
| `augenrules --load` 後仍是 `No rules` | 規則檔語法錯被整份跳過；或已 `-e 2`（immutable） | 看 `journalctl -u auditd -n 30`；已 `-e 2` 必須**重開機**才能改 | ★★★★ |
| `systemctl restart auditd` 被拒 | auditd unit 有 `RefuseManualStop` 保護 | 用 `sudo service auditd restart`，或只重載規則 `sudo augenrules --load` | ★★★ |
| 稽核紀錄一堆 `uid=0` 分不清是誰 | 只看 `uid` 沒看 `auid`（原始登入者） | `ausearch -ua <auid>`；規則以 `-F auid>=1000` 過濾系統程序 | ★★★ |

　→ 詳見 [[090-02-08-guide-防護-系統強化與稽核]] 的〈四、auditd 實務〉。

#### 【4】★★★★ AIDE／漂移腳本每天報上千筆

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| 每次都報上千筆變動 | 監控範圍含 `/var/log`、`/proc`、`/tmp` 等本來就一直變的路徑 | 在 `/etc/aide/aide.conf.d/` 加排除規則，重建資料庫 |
| 跑到一半 OOM 或吃滿 I/O | 監控項目太多（含大量小檔的目錄，如 `node_modules`） | 排除該類目錄；排在離峰時段；必要時改用 Wazuh FIM |
| `Couldn't open file /var/lib/aide/aide.db` | `aideinit` 只產生了 `aide.db.new`，沒轉正 | `sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db` |
| 漂移報告每天都報套件清單變動 | 自動更新每天在裝東西（正常現象） | 套件清單改成**只在月檢比對**，或只比對套件名不比版本 |
| 漂移報告都是 `ss` 那一段在變 | 腳本沒濾掉 pid/fd，程序重啟就變 | 只留「協定＋位址＋程式名」 |

★★★★★ **一份每天都在響的警報，等於沒有警報。**
先把噪音調乾淨，剩下的每一筆才有人會看。

　→ 詳見 [[090-02-08-guide-防護-系統強化與稽核]] 的
　　〈五、AIDE 檔案完整性監控與 Wazuh 的分工〉，
　　集中化的做法見 [[090-08-04-guide-Wazuh-FIM檔案完整性監控]]。

#### 【5】★★★★★ 什麼時候該把「紅字」當成入侵事件

| 發現 | 判斷 | 動作 |
| --- | --- | --- |
| SUID 清單多了一支，`dpkg -S` 查得到來源套件 | 正常（裝了新套件） | 更新基準 |
| SUID 清單多了一支，`dpkg -S` **查不到** | ★★★★★ 高度可疑 | 當作入侵事件處理 |
| `/etc/passwd` 多了 UID=0 的帳號 | ★★★★★ 等於完整 root 權限 | 立刻升級為事件 |
| `authorized_keys` 多了不明公鑰 | ★★★★★ 後門 | 立刻升級為事件 |
| crontab 多了沒人承認的排程 | ★★★★★ 持久化手法 | 立刻升級為事件 |
| AIDE 報 `/usr/bin/` 底下的執行檔被改，且不在更新時段 | ★★★★★ | 立刻升級為事件 |

> [!danger] ★★★★★ 判定為入侵事件之後，第一件事不是「清理」
> **不要重開機、不要刪檔案、不要「順便清一清」** —— 記憶體內容與時間戳記都是證據。
> 保存現場並依 [[090-07-04-guide-資安實踐-資安事件應變流程]] 通報；
> 跡證怎麼採集見 [[090-07-15-guide-資安實踐-被入侵主機的跡證檢查]]。

### ★★★ 情境九：自動更新把服務重啟了

**現象**：凌晨服務莫名重啟、中斷幾秒；或早上發現某個服務跑的是新版本，
但沒有人做過部署。

#### 【1】怎麼發現

```bash
$ sudo journalctl -u unattended-upgrades --since '3 days ago' --no-pager | tail -40
$ sudo cat /var/log/unattended-upgrades/unattended-upgrades.log | tail -50
$ grep -E ' (install|upgrade) ' /var/log/dpkg.log | tail -20
$ sudo dnf history list | head            # RHEL 系
```

★★★ 對照服務的重啟時間：

```bash
$ systemctl show nginx -p ActiveEnterTimestamp
$ sudo journalctl -u nginx --since '3 days ago' | grep -iE 'stopping|starting|reload'
```

#### 【2】為什麼會重啟

★★★★ Debian 系的 `needrestart` 在套件更新後會檢查「有哪些服務還在用舊的函式庫」，
並依設定決定要不要自動重啟：

```bash
$ grep -rn 'nrconf{restart}' /etc/needrestart/
/etc/needrestart/needrestart.conf:$nrconf{restart} = 'a';
#   'a' = automatic（自動重啟，★★★★ 正式機不該用）
#   'i' = interactive（互動詢問，無人值守時等於不重啟）
#   'l' = list only（只列出，人來決定）★★★★ 正式機建議值
```

`libssl` 這類基礎函式庫一更新，幾乎所有服務都會被列進去 —— 這就是
「凌晨一次重啟一整排服務」的原因。

#### 【3】怎麼避免

| 做法 | 設定 | ★ |
| --- | --- | --- |
| 正式環境把自動重啟關掉 | `/etc/needrestart/needrestart.conf` 設 `$nrconf{restart} = 'l';` | ★★★★ |
| 把重啟排進維護時段 | 由人或變更流程決定，不要交給凌晨的排程 | ★★★★ |
| 關鍵服務加入黑名單 | `unattended-upgrades` 的 `Package-Blacklist` | ★★★ |
| 只自動裝安全性更新 | `Allowed-Origins` 只留 `${distro_id}:${distro_codename}-security` | ★★★★★ |
| 自動重開機要指定時間 | `Automatic-Reboot-Time "03:00";`，並確認業務允許 | ★★★★ |
| 更新後要有告警 | `Mail`／`MailReport` 設定，或送到集中日誌 | ★★★ |

★★★★★ **不要因為「怕它亂重啟」就整個關掉自動更新。**
沒有修補的主機，風險遠高於「凌晨中斷五秒」。
正確的做法是把**更新**留著、把**重啟**收回人手上。

★★★★ 另一個相關症狀：**`/var/log` 被 auditd 或防火牆日誌塞爆，
觸發 `admin_space_left_action` 讓機器停機**（見情境八【3】）——
自動更新與稽核設定共用同一塊磁碟，容量監控要一起做。

　→ 詳見 [[090-02-01-guide-防護-伺服器初始安全設定]] 的〈【五】★★★★ 自動更新與修補〉。

### ★★★★ 情境十：重開機後防火牆狀態不一樣

**現象**：規則昨天還在、今天不見了；或每次重開機的狀態都不同。

**★★★★★ 判斷分流：先看有幾套防火牆在跑**

```bash
$ systemctl is-enabled ufw firewalld nftables iptables 2>&1
enabled
enabled          # ★★★★★ 兩個都 enabled → 這就是答案
disabled
```

★★★★★ ufw 與 nftables／firewalld 開機時都會 `flush ruleset`，
**誰後啟動誰贏**，而啟動順序不保證每次一樣 —— 於是狀態變得隨機。

| 你的選擇 | 保留 | 停用 |
| --- | --- | --- |
| Debian 系、規則單純 | `ufw` | `sudo systemctl disable --now nftables` |
| Debian 系、需要 set／複雜規則 | 手寫 `nftables` | `sudo ufw disable` |
| RHEL 系 | `firewalld` | 不要同時跑 nftables.service |

```bash
# ★★★★ 確認只剩一個 base chain 掛在 input hook
$ sudo nft list ruleset | grep -c 'type filter hook input'
1
```

**其他讓規則「消失」的原因**：

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| firewalld `--reload` 之後所有規則都不見 | permanent XML 檔壞掉／被誤刪，reload 讀到空設定 | 從備份還原 `/etc/firewalld/`；改之前先 `firewall-offline-cmd --check-config` | ★★★★★ |
| 用 `nft` 手動加的規則，firewalld reload 後消失 | firewalld reload 會重建整個 ruleset | 不要混用；額外規則寫成 rich rule | ★★★★ |
| nftables 規則重開機沒了 | `nft add` 下的規則不會自動存檔 | 寫進 `/etc/nftables.conf` 並 `systemctl enable nftables` | ★★★★ |
| ufw 顯示 active 但 `iptables -S` 幾乎是空的 | 有別的工具把規則清掉了 | 查第二套防火牆；同一台只能有一個負責人 | ★★★★ |
| Fail2ban 的 f2b chain 在重啟後空了 | `dbpurgeage` < `bantime`，封鎖記錄被清 | `dbpurgeage` ≥ 最大 `bantime` | ★★★★ |

★★★★★ **驗證持久化的唯一可靠方法是重開機**。
「規則看起來都在」不等於「重開機後還在」。

　→ 詳見 [[090-02-03-guide-防火牆-nftables與iptables]] 的〈持久化與原子套用〉
　　與 [[090-02-04-guide-防火牆-firewalld]] 的〈標準工作流（本篇之後全部照這個做）〉。

### ★★★★ 情境十一：日誌爆量，或查不到防護日誌

#### 【1】★★★★ `/var` 被寫爆

```bash
$ df -h /var
$ sudo du -sh /var/log/* 2>/dev/null | sort -h | tail -10
```

| 元凶 | 症狀 | 解法 | ★ |
| --- | --- | --- | --- |
| `ufw logging full` 忘了關 | `/var/log/ufw.log` 幾 GB | `sudo ufw logging low`；`sudo truncate -s 0 /var/log/ufw.log`；檢查 `/etc/logrotate.d/ufw` | ★★★★ |
| firewalld `--set-log-denied=all` | journal 被塞爆 | 改 `unicast`；rich rule 的 `log` 一律加 `limit value="6/m"` | ★★★ |
| nftables `log` 沒搭配 `limit rate` | journal 被塞爆 | 補 `limit rate 5/minute burst 10 packets`；`journalctl --vacuum-size=200M` | ★★★★ |
| auditd 規則太寬 | `/var/log/audit` 幾十 GB | 收斂規則、調 `max_log_file`／`num_logs`（見情境八【3】） | ★★★★★ |
| 側錄檔沒有輪替 | 跳板機磁碟塞爆導致無法登入 | 獨立分割或 quota，加 logrotate，設磁碟使用率告警 | ★★★★ |

★★★★★ **磁碟寫爆本身就是一種阻斷服務**，而且它會連帶讓 auditd
觸發 `admin_space_left_action`（可能是 halt）把整台機器停掉。
`/var` 的用量一定要納入監控（[[100-01-03-guide-日誌-系統監控與告警]]）。

#### 【2】★★★ 查不到防火牆的日誌

```bash
# ufw：Ubuntu 24.04 預設沒有 rsyslog，日誌只在 journal
$ ls -l /var/log/ufw.log 2>&1
$ journalctl -k --grep 'UFW' -n 30 --no-pager

# nftables：看你自己 log 規則的 prefix
$ sudo journalctl -k --grep 'NFT-DROP' -n 20 --no-pager

# firewalld：先確認有沒有開
$ sudo firewall-cmd --get-log-denied
off                      # ★★★ off 就永遠不會有紀錄
$ sudo firewall-cmd --set-log-denied=unicast
```

| 日誌欄位 | 意思 |
| --- | --- |
| `[UFW BLOCK]` / `[UFW ALLOW]` / `[UFW LIMIT BLOCK]` | 動作結果 |
| `IN=` / `OUT=` | 進出的網卡 |
| `SRC=` / `DST=` | 來源／目的 IP |
| `SPT=` / `DPT=` | 來源埠／目的埠 |
| `SYN` | 新連線嘗試 |

★★★★★ **日誌只留在本機等於沒有留** —— 攻擊者拿到 root 就能刪。
送到集中式 log server（[[100-01-02-guide-日誌-日誌集中與輪替]]），
或接進 SIEM（[[090-08-05-guide-Wazuh-日誌蒐集與解析]]）。

　→ 詳見 [[090-02-02-guide-防火牆-ufw基礎與實務]] 的〈日誌〉。

### ★★★ 情境十二：跳板機與遠端存取出問題

#### 【1】`ssh -J` 失敗

| 訊息 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| `channel 0: open failed: administratively prohibited` | 跳板機 `PermitOpen` 白名單沒包含目標，或 `AllowTcpForwarding no` | 在對應的 `Match` 區塊加上目標 `IP:port` | ★★★★ |
| `Permission denied (publickey)`，但直連跳板機沒問題 | ★★★ `-J` 對兩段**各自認證**；目標主機沒有你的公鑰 | 把公鑰也放到目標主機的 `authorized_keys` | ★★★ |
| 跳板機重開機後 `jumponly` 帳號拿得到 shell 了 | drop-in 檔名或位置錯，沒被 `Include` 讀到 | 檔名必須是 `*.conf`；`sudo sshd -T \| grep -i permitopen` 確認生效值 | ★★★★ |
| VPN 連上了但連不到跳板機 | VPN 網段沒加進跳板機的防火牆允許清單 | `sudo ufw allow from <VPN 網段> to any port 22 proto tcp` | ★★★ |

★★★★ **`sshd -T` 是排錯神器**：它印出 sshd **實際生效**的完整設定
（把所有 include 與預設值展開）。懷疑設定沒吃到就用它，不要用 `grep` 猜設定檔。

```bash
$ sudo sshd -T | grep -i permitopen
$ sudo sshd -T -C user=vendor-acme-20260903,addr=203.0.113.44,host=x | grep -i forwarding
```

#### 【2】MFA 相關

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| TOTP 輸入正確也失敗 | 跳板機時間偏移超過容許視窗 | `chronyc tracking` 看 offset；`timedatectl` 確認 NTP 同步 | ★★★★ |
| 加了 MFA 之後改用金鑰就登不進去 | `AuthenticationMethods publickey,keyboard-interactive` 要求**兩者都過**，`nullok` 又被拿掉 | 先掛回 `nullok`，確認所有帳號都有 `~/.google_authenticator` 再移除 | ★★★★★ |

#### 【3】★★★★★ 廠商帳號到期後仍能登入

**原因**：只做了 `usermod -L`（鎖密碼），但**金鑰登入完全不受密碼鎖影響**。

```bash
# ★★★★★ 三件事一起做才算真的關掉
$ sudo chage -E 0 vendor-acme-20260903          # ① 帳號到期
$ sudo truncate -s 0 ~vendor-acme-20260903/.ssh/authorized_keys   # ② 清空公鑰
$ sudo pkill -KILL -u vendor-acme-20260903      # ③ 踢掉現有 session
$ sudo ss -tnp | grep vendor                    # 確認沒有殘留連線
```

★★★★ 順便檢查廠商工具有沒有留下無人值守存取：

```bash
$ systemctl list-unit-files | grep -iE 'teamviewer|anydesk|<工具名>'
$ sudo crontab -l -u vendor-acme-20260903
$ ls -la ~vendor-acme-20260903/.ssh/
```

#### 【4】★★★★ 掃描發現沒人記得的開放埠

```bash
# 本機的真相
$ sudo ss -tlnp | sort -k4
# 對照防火牆規則
$ sudo ufw status numbered
$ sudo firewall-cmd --list-all-zones | grep -E 'ports|services'
# 對照盤點表與申請紀錄
```

★★★★★ **找不到申請紀錄的一律先關再說**（走變更流程通知）。
「不知道是誰開的、不知道給誰用的」埠，就是最典型的攻擊面。

★★★ 這也是為什麼要有基準清單：`/root/baseline/02-listen.txt` 這種東西，
就是拿來回答「這個埠上禮拜就有嗎」的。
　→ 詳見 [[090-02-08-guide-防護-系統強化與稽核]] 的〈二、產出基準清單〉。

#### 【5】★★★★ 帶外管理（BMC／iDRAC／iLO）的兩個常見坑

| 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- |
| BMC 改到管理網段後收不到告警信、時間跑掉 | ★★★★ 管理網段**沒有預設路由**（這是刻意的） | 不要加預設路由；改由監控主機用 SNMP／Redfish 主動輪詢 | ★★★★ |
| 集中日誌主機沒收到跳板機的日誌 | rsyslog 轉送設定錯、防火牆擋 514、或收端沒開監聽 | 收端 `ss -lntp \| grep 514`；發端 `logger -p auth.info test` 後兩邊都查 | ★★★ |

> [!danger] ★★★★★ 帶外管理介面永遠不可以對網際網路開放
> BMC 的韌體更新頻率遠低於作業系統，歷史漏洞多，而且**繞過作業系統的所有防護** ——
> 它能開關機、能掛載虛擬光碟、能看你的主控台。
> 一律放在獨立管理網段，只能從跳板機到達。
> 　→ 詳見 [[090-02-06-guide-防護-遠端存取安全]] 的
> 　　〈帶外管理（OOB）為什麼是最高等級〉與〈第 4 步：處理帶外管理〉。

## 什麼時候該停手求援

> [!danger] ★★★★★ 以下情況請立刻停止操作 —— 繼續動手會讓證據消失或災情擴大

**【1】★★★★★ 懷疑不是故障而是入侵**：`/etc/passwd` 多了 UID=0 的帳號、
`authorized_keys` 多了不明公鑰、crontab 多了沒人承認的排程、
SUID 清單多了一支查不到來源的執行檔、日誌出現無法解釋的斷層、
`/tmp` 或 `/dev/shm` 裡有奇怪的執行檔。
★★★★★ **不要重開機、不要刪檔案、不要「順便清一清」。**
記憶體內容與時間戳記都是證據。保存現場並依
[[090-07-04-guide-資安實踐-資安事件應變流程]] 通報，
採證方法見 [[090-07-15-guide-資安實踐-被入侵主機的跡證檢查]]。

**【2】★★★★★ 你已經改壞了關鍵設定，但系統還開著**（防火牆、sshd、sudoers、
SELinux config、fstab）：★★★★★ **先不要重開機。**
系統還活著的時候你有 shell 可以修，重開之後可能就進不去了。
把當下的 shell 保留住，開第二個終端做驗證，確認新設定能用再考慮重開。

**【3】★★★★★ 你打算「先關掉防護看看」而且那是正式機**：
`setenforce 0`、`ufw disable`、`systemctl stop firewalld`、`systemctl stop fail2ban`
都是**診斷手段**，不是解法。
★★★★★ 關掉之後一定要有人負責關回去，而且要有時間上限 ——
不然它會在關閉狀態存活好幾年，直到出事那天。

**【4】★★★★★ 你手上沒有第二條路進得來，而下一步是防火牆或 sshd 的變更**：
停下來，先把 console／`at` 自動還原做出來。這一步沒有捷徑。

**【5】★★★★ 同一個問題試了超過三十分鐘，而且開始「隨便改改看」**：
★★★★★ 隨機修改會製造新問題，讓單一故障變成多重故障，而且沒人知道你動過什麼。
停下來，把做過的每一個動作寫下來，找第二個人一起看。
（方法論見 [[100-02-10-guide-維運-故障排除方法論]]）

**【6】★★★★ 災情比你以為的大**：不只一台機器有問題、多個服務同時異常、
或整個網段連不上。這時你面對的可能是網路、儲存、電力層級的事件，
繼續在單機上找答案只會浪費時間 —— 往上升級成事件處理流程
（[[100-02-09-svc-維運-事件處理與升級流程]]）。

**【7】★★★★ 要在正式環境做不可逆的變更，而且沒有走變更流程**：
即使技術上你做得到，制度上也應該先取得核准與備援計畫
（[[100-02-08-guide-維運-變更管理流程]]）。
半夜自己判斷「這個改一下應該沒差」是事故報告裡出現頻率最高的一句話。

**【8】★★★ 你發現這台機器的防護狀態跟你的認知完全不同**（例如以為有防火牆其實沒有、
以為 SELinux 是 enforcing 其實是 disabled）：先**盤點**再動手。
不知道現況就改設定，等於在黑暗中拆線。
　→ 盤點做法見 [[090-02-01-guide-防護-伺服器初始安全設定]] 的
　　〈【二】★★★★★ 盤點：先知道現在有什麼〉。
