# 遠端存取安全

> [!abstract] 這篇你會學到
> - 盤點一個機關「所有能從遠端進來的路」，而不只是 SSH
> - ★★★★★ 為什麼帶外管理介面（iDRAC／iLO／IPMI）絕對不可以直接對外
> - 用跳板機（bastion）＋ VPN 把管理平面收斂成單一入口，並設計備援與緊急通道
> - 廠商遠端支援的臨時帳號、時效、側錄與事後撤銷流程

## 觀念說明

### 為什麼「遠端存取」要單獨當成一個治理主題 ★★★★

多數機關的資安投資集中在「邊界」與「端點」，但實際被打進來的案例裡，
最常見的第一步不是零時差漏洞，而是**一條本來就不該存在的遠端通道**：

- 三年前為了讓廠商修東西開的 `3389`，忘了關
- 測試環境的 iLO 圖方便給了一個 public IP
- 某台舊主機的 SSH 用密碼登入，帳號是 `admin`，密碼是機關縮寫加年份
- 某人裝了 TeamViewer 方便在家連，帳號沿用私人 Email 且沒開兩步驟

這些都不是「技術漏洞」，是**治理漏洞**。技術上每一項都有解，
但沒有人負責回答「這條路現在還需要嗎？」

> [!note] ★★★★ 一句話定義
> 遠端存取安全 = **讓「能從外面進來的路」是一份可以逐條念出來的清單，
> 而且每一條都有負責人、有到期日、有紀錄。**

### 遠端存取的攻擊面全景 ★★★★

把「遠端」拆成六類，每一類的風險性質完全不同：

| # | 通道 | 典型埠／介面 | 風險特性 | 重要度 |
| --- | --- | --- | --- | --- |
| 1 | SSH | tcp/22 | 暴力破解、金鑰外流、被當跳板往內打 | ★★★ |
| 2 | RDP | tcp/3389 | 暴力破解、憑證竊取、勒索軟體最愛的入口 | ★★★★ |
| 3 | VPN | udp/500、udp/4500、udp/51820、tcp/443 | VPN 閘道本體的漏洞、帳號共用、進來就是內網 | ★★★★ |
| 4 | 廠商遠端支援工具 | TeamViewer／AnyDesk／VNC／專屬 client | 不受你控制、繞過防火牆（出向連線）、無稽核 | ★★★★ |
| 5 | 雲端主機 console | 雲端入口網站 | 雲端帳號被接管 = 繞過所有網路管控 | ★★★★ |
| 6 | 帶外管理 BMC | iDRAC／iLO／IPMI（tcp/443、udp/623） | ★★★★★ 拿到 = 拿到硬體，可掛 ISO 重灌 | ★★★★★ |

四個容易被忽略的性質：

1. **第 4 類是「出向」連線。**
   廠商工具通常由內部主機主動連到廠商雲端，防火牆的入向規則擋不到它。
   這是很多「我們防火牆很嚴」的機關實際上門戶洞開的原因。★★★★
2. **第 5 類完全繞過你的網路架構。**
   雲端 console 是走瀏覽器連到雲商，你的防火牆規則、跳板機、VPN 一個都沒用到。
   守它的方式只有「雲端帳號的 MFA ＋ 角色權限」。★★★★
3. **第 6 類即使主機關機也還在。** BMC 有獨立電源與獨立網路堆疊。
   你把 OS 加固到滿分，只要 BMC 對外，攻擊者可以直接掛遠端 ISO 重灌。★★★★★
4. **第 3 類進來的是「內網」。** VPN 帳號的價值等同一條實體網路線插進機房。
   把它當「一般帳號」管是錯的。★★★★

### 管理平面（management plane）與服務平面 ★★★★★

這是本篇最核心的一條原則：

> [!danger] ★★★★★ 管理埠不上公網
> **對外提供服務的埠**（80／443）與**管理用的埠**（22／3389／BMC／防火牆管理介面）
> 是兩個平面，必須用不同的路徑進入。
> 服務平面歡迎全世界；管理平面只歡迎「先通過身分驗證的內部路徑」。
>
> 一旦管理埠對 `0.0.0.0/0` 開放，你的第一道防線就只剩「密碼／金鑰」這一層。
> 全網掃描器在你開通後幾分鐘內就會找到它。

進管理平面的兩條合法路徑，二選一或並用：

| 路徑 | 做法 | 適合 |
| --- | --- | --- |
| VPN 優先 | 先建 VPN 進到管理網段，再直接連目標主機 | 人員多、需要用 GUI 工具（RDP、資料庫管理程式） |
| 跳板機優先 | 只開一台 bastion 對外，所有連線從它轉出去 | 以 CLI 為主、需要強稽核與側錄 |
| 兩者並用 ★★★★ | 先 VPN，VPN 網段只准連跳板機，跳板機再連目標 | 機關等級的標準做法 |

> [!tip] ★★★ 為什麼「並用」值得
> VPN 解決「你是不是我們的人」，跳板機解決「你做了什麼」。
> 只有 VPN，你知道誰進來但不知道他做了什麼；
> 只有跳板機，跳板機本身就是暴露在公網的單點。兩者互補。

### 跳板機（bastion / jump host）到底是什麼 ★★★★

一台**極度精簡、只做一件事**的機器：接受外部管理連線，再代理到內部目標。

它應該有的特性：

| 特性 | 說明 | 重要度 |
| --- | --- | --- |
| 單一入口 | 內部主機的防火牆只接受來自跳板機 IP 的 22 埠 | ★★★★★ |
| 極小攻擊面 | 只裝 sshd，不裝 Web、不裝資料庫、不當檔案伺服器 | ★★★★ |
| 不存資料 | 上面不該有專案原始碼、備份、私鑰 | ★★★★★ |
| 全程可稽核 | 誰連進來、從哪連、連去哪、做了什麼 | ★★★★ |
| 帳號獨立 | 每人一個實名帳號，不共用 | ★★★★ |
| 可以被重建 | 用 Ansible 十分鐘重建一台，因為它遲早要被重灌 | ★★★ |

> [!note] ★★★ 跳板機不是「多一台可以放東西的機器」
> 現場最常見的墮落過程：跳板機 → 順便放腳本 → 順便放備份 →
> 順便當測試機 → 上面有一堆私鑰 → 被打下來之後全機關一起完蛋。
> **跳板機被入侵時的損失，應該只有「跳板機本身」。**

### 零信任式的存取：從「網段信任」到「每次驗證」 ★★★

傳統模型：進了 VPN 就在內網，內網互通。
問題：一個被釣魚的員工筆電，等於一台在你機房裡的攻擊主機。

零信任的想法是**不因為來源網段就給信任**，每一次存取都要驗證身分、裝置狀態與授權，
並把可達範圍縮到「這個人此刻真的需要的那一台」。

在維運層面，你不必買一整套產品也能拿到大半好處：

- VPN 進來的網段**只准連跳板機**，不准直接連伺服器（微分段的最小版本）★★★★
- 跳板機上用 `Match User` 限制每個人能 `ProxyJump` 到哪些主機 ★★★
- 目標主機的防火牆只信任跳板機 IP，而不是整個管理網段 ★★★★
- 每次存取都留紀錄，不是「這個網段是安全的所以不用記」★★★

完整的零信任架構、身分感知代理與微分段產品面，看
[[090-05-12-guide-資安設備-零信任架構與微分段]]；
身分與 MFA 的產品層面看 [[090-05-07-guide-資安設備-身分存取管理IAM與MFA]]。

### 帶外管理（OOB）為什麼是最高等級 ★★★★★

BMC（Baseboard Management Controller，Dell 叫 iDRAC、HPE 叫 iLO、
Lenovo 叫 XCC、通用標準叫 IPMI／Redfish）是一顆**獨立於主機 CPU 的小電腦**。

它能做什麼：

- 遠端開關機、強制斷電
- 遠端 KVM（看到 BIOS 畫面）
- ★★★★★ **掛載遠端 ISO 開機** —— 等於你人在機房拿隨身碟插上去
- 讀取硬體感測器、更新韌體
- 有些機種可以直接讀寫主機記憶體

也就是說：**BMC 的權限 ≥ root。** 加固 OS 完全防不到它。

> [!danger] ★★★★★ BMC 三條鐵律
> 1. **BMC 網段絕不路由到網際網路。** 專用管理 VLAN，出口在防火牆上明確 deny。
> 2. **改掉出廠預設帳密。** `root/calvin`（Dell）、`Administrator/隨機標籤`（HPE）
>    這類預設值是掃描器的第一發子彈。
> 3. **關掉 IPMI over LAN（udp/623），只留 HTTPS／Redfish。**
>    IPMI 2.0 的認證設計有已知的結構性弱點（例如 cipher suite 0 可以用任意密碼通過驗證、
>    RAKP 交握會回傳密碼雜湊供離線破解），這些不是靠改密碼就能解決的。
>
> 上架時的 BMC 設定步驟見 [[040-02-09-guide-機房-伺服器上架與初始設定]]，
> 機房實體與管理網路的隔離見 [[040-02-13-guide-機房-機房實體安全]]。

## 安裝或基礎操作

以下用「一台跳板機 ＋ 一台目標主機」把最小可用的架構做出來。
主線 Ubuntu 24.04／Debian 12。

### 環境假設

```text
外部使用者 ──(公網)──> [跳板機 bastion]  10.10.99.10 / 對外 IP 203.0.113.10
                                │
                          管理網段 10.10.99.0/24
                                │
                        [目標主機 web01]   10.10.10.21
```

### 步驟 1：跳板機只開 SSH，其餘全關 ★★★★

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw limit 22/tcp comment 'SSH bastion'
sudo ufw enable
sudo ufw status verbose
```

預期輸出：

```text
狀態: 啟用
記錄: on (low)
預設: deny (incoming), allow (outgoing), disabled (routed)

至                         動作          來自
-                          --            --
22/tcp                     LIMIT IN      Anywhere                   # SSH bastion
22/tcp (v6)                LIMIT IN      Anywhere (v6)              # SSH bastion
```

> [!tip] ★★★ `ufw limit` 是什麼
> `limit` 會對同一來源 IP 在 30 秒內超過 6 次新連線做阻擋，
> 是最低成本的暴力破解緩解。更完整的封鎖交給 Fail2ban，
> 見 [[090-02-05-guide-防護-Fail2ban入侵防護]]。

### 步驟 2：跳板機關掉密碼登入，只收金鑰 ★★★★★

> [!danger] ★★★★★ 改 sshd 前先開第二條連線
> 在改 `sshd_config` 並 `systemctl restart ssh` 之前，
> **保留一個已經登入的 session 不要關**。設定寫錯時它是你唯一的救命通道。
> 沒有第二條連線又改壞，就只能請人去機房或用 BMC 進去。

```bash
sudo tee /etc/ssh/sshd_config.d/50-bastion.conf >/dev/null <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AllowGroups sshusers
X11Forwarding no
AllowAgentForwarding no
MaxAuthTries 3
LoginGraceTime 20
ClientAliveInterval 300
ClientAliveCountMax 2
EOF

sudo sshd -t && echo "設定語法 OK"
sudo systemctl reload ssh
```

`sshd -t` 沒有輸出代表語法正確；語法錯誤時會像這樣：

```text
/etc/ssh/sshd_config.d/50-bastion.conf: line 3: Bad configuration option: PasswordAuthentcation
```

> [!warning] ★★★ `AllowAgentForwarding no` 與 `ProxyJump` 不衝突
> 很多人以為跳板機一定要開 agent forwarding。**不需要。**
> `ProxyJump`（`-J`）是在**本機**做加密轉送，私鑰從頭到尾不離開你的電腦，
> 跳板機上也不會出現你的 agent socket。
> agent forwarding（`-A`）反而讓跳板機上的 root 可以盜用你的 agent —— 不要開。
> 兩者的差異在 [[020-02-01-05-cmd-SSH-隧道與埠轉發]] 有完整說明。

### 步驟 3：目標主機只信任跳板機 ★★★★★

在 `web01` 上：

```bash
sudo ufw default deny incoming
sudo ufw allow from 10.10.99.10 to any port 22 proto tcp comment 'SSH from bastion only'
sudo ufw allow 80,443/tcp comment 'web service'
sudo ufw enable
```

驗證（從外部直連應該逾時，從跳板機應該通）：

```bash
# 從你的筆電直連 web01：應該卡住然後 timeout
ssh -o ConnectTimeout=5 ops@10.10.10.21
```

```text
ssh: connect to host 10.10.10.21 port 22: Connection timed out
```

```bash
# 經跳板機：應該成功
ssh -J ops@203.0.113.10 ops@10.10.10.21 'hostname'
```

```text
web01
```

### 步驟 4：把 ProxyJump 寫進客戶端設定 ★★★

在**你自己的電腦**上編輯 `~/.ssh/config`：

```text
Host bastion
    HostName 203.0.113.10
    User ops
    Port 22
    IdentityFile ~/.ssh/id_ed25519_ops
    IdentitiesOnly yes

Host web01 db01 app01
    ProxyJump bastion
    User ops
    IdentityFile ~/.ssh/id_ed25519_ops
    IdentitiesOnly yes

Host web01
    HostName 10.10.10.21
Host db01
    HostName 10.10.10.31
Host app01
    HostName 10.10.10.41
```

之後一句 `ssh web01` 就會自動繞跳板機。`scp`、`rsync`、Ansible 全部沿用。

```bash
ssh web01 'uptime'
```

```text
 14:07:22 up 41 days,  3:12,  0 users,  load average: 0.08, 0.05, 0.01
```

客戶端設定檔的完整語法看 [[020-02-01-03-svc-SSH-客戶端設定檔]]。

### 步驟 5：確認「誰連進來」有被記錄 ★★★

```bash
sudo journalctl -u ssh --since "1 hour ago" | grep -E 'Accepted|Failed'
```

```text
Sep 03 14:07:19 bastion sshd[2311]: Accepted publickey for ops from 198.51.100.77 port 51422 ssh2: ED25519 SHA256:8Zr...q4
Sep 03 14:02:03 bastion sshd[2280]: Failed password for invalid user admin from 45.155.205.11 port 40122 ssh2
```

```bash
last -n 10 -F        # 成功登入紀錄（讀 /var/log/wtmp）
sudo lastb -n 10 -F  # 失敗登入紀錄（讀 /var/log/btmp）
```

> [!warning] ★★★★ 本機日誌會被清掉
> 攻擊者拿到 root 之後第一件事常常就是清 `/var/log`。
> **跳板機的日誌必須即時送到別台機器。** 做法看
> [[100-01-02-guide-日誌-日誌集中與輪替]]，接 SIEM 看
> [[090-05-09-guide-資安設備-日誌集中與SIEM]]。

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> - 防火牆用 firewalld，見 [[090-02-04-guide-防火牆-firewalld]]：
>   ```bash
>   sudo firewall-cmd --permanent --new-zone=mgmt
>   sudo firewall-cmd --permanent --zone=mgmt --add-source=10.10.99.10/32
>   sudo firewall-cmd --permanent --zone=mgmt --add-service=ssh
>   sudo firewall-cmd --permanent --zone=public --remove-service=ssh
>   sudo firewall-cmd --reload
>   sudo firewall-cmd --list-all-zones | head -40
>   ```
> - 服務名稱是 `sshd` 不是 `ssh`：`sudo systemctl reload sshd`、`journalctl -u sshd`。
> - RHEL 9 的 `/etc/ssh/sshd_config` 預設已經 `include /etc/ssh/sshd_config.d/*.conf`，
>   放 drop-in 的做法一樣。
> - 額外要注意 SELinux：改 SSH 埠號要用 `semanage port -a -t ssh_port_t -p tcp 2222`，
>   否則 sshd 起不來。見 [[090-02-07-guide-防護-SELinux與AppArmor]]。

## 進階應用

### 一、跳板機的權限收斂：誰能跳到哪 ★★★★

只讓「登入跳板機」還不夠，要限制每個人能跳去哪裡。

在跳板機的 `/etc/ssh/sshd_config.d/60-jump-policy.conf`：

```text
# 只做跳板用途的帳號：禁止取得 shell、禁止傳檔、只准 TCP 轉送
Match Group jumponly
    AllowTcpForwarding yes
    PermitOpen 10.10.10.21:22 10.10.10.31:22 10.10.10.41:22
    ForceCommand /usr/sbin/nologin
    AllowAgentForwarding no
    X11Forwarding no
    PermitTTY no
```

- `PermitOpen` 是白名單，把可轉送的目的地限制成明確的「IP:埠」清單。★★★★
- `ForceCommand /usr/sbin/nologin` ＋ `PermitTTY no` 讓這個帳號**不能在跳板機上開 shell**，
  但 `-J` 仍然可用（`ProxyJump` 走的是 `direct-tcpip` channel，不需要 shell）。★★★★

驗證：

```bash
ssh -J vendor@203.0.113.10 ops@10.10.10.21 'hostname'   # 允許
ssh vendor@203.0.113.10                                  # 應該被踢掉
```

```text
This account is currently not available.
Connection to 203.0.113.10 closed.
```

嘗試轉送到白名單外的主機：

```bash
ssh -J vendor@203.0.113.10 ops@10.10.10.99
```

```text
channel 0: open failed: administratively prohibited: open failed
stdio forwarding failed
```

> [!tip] ★★★ 分成兩種跳板帳號
> `jumponly`（只能穿透、不能落地）給大多數人與廠商；
> `sshusers`（可以登入跳板機本身）只留給少數需要在跳板機上跑東西的管理員。

### 二、全程側錄：把「做了什麼」留下來 ★★★★

側錄有三種層次，成本與可信度遞增：

| 層次 | 做法 | 可信度 | 成本 | 重要度 |
| --- | --- | --- | --- | --- |
| A. 只記連線 | sshd 日誌 ＋ `wtmp` | 低（只知道連了） | 極低 | ★★ |
| B. 記指令 | 目標主機上用 auditd 記 execve | 中（root 可繞過但留痕） | 低 | ★★★ |
| C. 記畫面 | 跳板機上 `tlog` 或 `script` 錄 session | 高（連輸出都有） | 中 | ★★★★ |

**層次 B：auditd 記錄執行過的指令**（裝在目標主機上）

```bash
sudo apt install -y auditd audispd-plugins
sudo tee /etc/audit/rules.d/50-exec.rules >/dev/null <<'EOF'
-a always,exit -F arch=b64 -S execve -F auid>=1000 -F auid!=unset -k cmdlog
-a always,exit -F arch=b32 -S execve -F auid>=1000 -F auid!=unset -k cmdlog
EOF
sudo augenrules --load
sudo auditctl -l
```

```text
-a always,exit -F arch=b64 -S execve -F auid>=1000 -F auid!=-1 -k cmdlog
-a always,exit -F arch=b32 -S execve -F auid>=1000 -F auid!=-1 -k cmdlog
```

查詢某個人做了什麼：

```bash
sudo ausearch -k cmdlog -ua 1001 -ts today -i | head -20
```

> [!note] ★★★★ `auid` 是稽核的關鍵
> `auid`（audit UID）在登入時被釘住，之後 `sudo su -` 變成 root 也**不會改變**。
> 這就是「這個 root 動作背後的真人是誰」的依據。
> 只記 `uid` 你會得到一堆分不清是誰的 `uid=0`。
> 完整的 auditd 規則設計見 [[090-02-08-guide-防護-系統強化與稽核]]。

**層次 C：跳板機 session 側錄**

最簡單、零額外套件的做法是用 `script`（`util-linux` 內建）：

```bash
sudo mkdir -p /var/log/sessions
sudo chmod 1733 /var/log/sessions          # 可寫入、不可列出、不可讀他人
```

在 `/etc/ssh/sshd_config.d/70-record.conf`：

```text
Match Group recorded
    ForceCommand /usr/local/sbin/rec-shell
```

`/usr/local/sbin/rec-shell`：

```bash
#!/bin/bash
# 跳板機 session 側錄包裝腳本
set -u
TS=$(date +%Y%m%d-%H%M%S)
OUT="/var/log/sessions/${USER}-${TS}-$$"
logger -t rec-shell "session start user=${USER} from=${SSH_CONNECTION:-unknown} file=${OUT}"
if [ -n "${SSH_ORIGINAL_COMMAND:-}" ]; then
    exec script -q -c "$SSH_ORIGINAL_COMMAND" -T "${OUT}.timing" "${OUT}.log"
else
    exec script -q -T "${OUT}.timing" "${OUT}.log"
fi
```

```bash
sudo chmod 0755 /usr/local/sbin/rec-shell
sudo sshd -t && sudo systemctl reload ssh
```

重播一段側錄：

```bash
scriptreplay -T /var/log/sessions/ops-20260903-140719-2311.timing \
             -t /var/log/sessions/ops-20260903-140719-2311.log
```

> [!warning] ★★★★ `script` 側錄擋不住有心人
> 使用者可以 `script -q /dev/null` 再開一層、可以用 `ssh host -- command` 直接下指令、
> 也可能在 shell 裡開出 `scp` 通道。
> `script` 適合「**留下正常作業的紀錄**」與「事後回溯」，
> **不是**用來對抗惡意內部人員的技術控制。
> 需要防繞過等級的側錄，要用專用的 PAM 產品（privileged access management），
> 例如 Teleport、Apache Guacamole 這類會把協定本身代理掉的閘道。
> 選型面向見 [[090-05-16-guide-資安設備-資安設備選型與導入實務]]。

> [!warning] 未實機驗證
> 上面 `rec-shell` 的 `SSH_ORIGINAL_COMMAND` 分支在不同 OpenSSH 版本下對
> `-T`（timing 檔）旗標的行為略有差異（部分較舊的 `util-linux` 用 `--timing=` 長格式）。
> 部署前請在測試機用 `script --version` 確認旗標，再放到正式環境。

### 三、多因素驗證：加在哪一層 ★★★★

MFA 不是「到處都加」，是「加在**單一入口**上」。加對地方一次就夠。

| 位置 | 做法 | 建議 | 重要度 |
| --- | --- | --- | --- |
| VPN 閘道 | 憑證 ＋ TOTP／推播 | ★★★★★ 最該加的地方 | ★★★★★ |
| 跳板機 SSH | 金鑰 ＋ TOTP（`pam_google_authenticator`） | ★★★★ 沒 VPN 時必加 | ★★★★ |
| 內部主機 SSH | 金鑰即可 | ★ 不必再加，已經在管理平面內 | ★ |
| 雲端 console | 帳號 MFA ＋ 硬體金鑰 | ★★★★★ 繞過所有網路管控，非加不可 | ★★★★★ |
| BMC | 若機種支援就開；不支援就靠網路隔離 | ★★★ | ★★★ |

**跳板機加 TOTP 的做法**（金鑰 ＋ 驗證碼，兩個都要過）：

```bash
sudo apt install -y libpam-google-authenticator
```

每位使用者自己跑一次產生 secret：

```bash
google-authenticator -t -d -f -r 3 -R 30 -W
```

會印出 QR code 與備援碼（**備援碼要離線保存**）。旗標意義：

| 旗標 | 意義 |
| --- | --- |
| `-t` | 使用時間型（TOTP），不是計次型 |
| `-d` | 不允許同一個驗證碼重複使用 |
| `-f` | 直接寫入 `~/.google_authenticator`，不再互動詢問 |
| `-r 3 -R 30` | 30 秒內最多 3 次嘗試 |
| `-W` | 縮小允許的時間視窗（比較嚴、但要求時間同步準確）|

接著 `/etc/pam.d/sshd` 最上方加：

```text
auth required pam_google_authenticator.so nullok
```

以及 `/etc/ssh/sshd_config.d/80-mfa.conf`：

```text
KbdInteractiveAuthentication yes
AuthenticationMethods publickey,keyboard-interactive
UsePAM yes
```

> [!danger] ★★★★★ `nullok` 是雙面刃
> 有 `nullok`：還沒設定 TOTP 的使用者可以只憑金鑰登入（導入期用，避免全機關被鎖在外面）。
> 沒有 `nullok`：沒設定的人**完全登不進來**。
> 導入流程是：先掛 `nullok` → 通知所有人在期限前完成設定 →
> 用 `sudo ls /home/*/.google_authenticator` 確認每個帳號都有 → 才拿掉 `nullok`。
> 順序反了就是全員被鎖在門外，只能去機房或走 BMC。

驗證登入流程：

```bash
ssh bastion
```

```text
Authenticated with partial success.
Verification code:
```

★★★ 時間不同步是 TOTP 最常見的失敗原因，跳板機務必跑 chrony：
見 [[020-01-28-cmd-Linux-時間同步NTP與chrony]]。

### 四、廠商遠端支援的管制 ★★★★

廠商要連進來修東西，是機關最常見也最難管的情境。不要用「相信廠商」來解決。

**五個必要控制點：**

| # | 控制 | 具體做法 | 重要度 |
| --- | --- | --- | --- |
| 1 | 臨時帳號 | 一案一帳號，不共用、不重複使用舊帳號 | ★★★★ |
| 2 | 時效 | 帳號自帶到期日，時間到自動失效 | ★★★★★ |
| 3 | 範圍 | 只能跳到本案相關的主機（`PermitOpen` 白名單） | ★★★★ |
| 4 | 側錄或陪同 | 高風險作業由我方人員全程線上陪同 | ★★★★ |
| 5 | 事後撤銷 | 結案後 24 小時內停用並驗證，留紀錄 | ★★★★★ |

**用 `chage` 讓帳號自動到期** ★★★★★：

```bash
sudo useradd -m -s /bin/bash -G jumponly vendor-acme-20260903
sudo mkdir -p /home/vendor-acme-20260903/.ssh
sudo tee /home/vendor-acme-20260903/.ssh/authorized_keys >/dev/null <<'EOF'
from="203.0.113.0/24",no-agent-forwarding,no-X11-forwarding,no-pty ssh-ed25519 AAAAC3Nza...ACME acme-support
EOF
sudo chown -R vendor-acme-20260903: /home/vendor-acme-20260903/.ssh
sudo chmod 700 /home/vendor-acme-20260903/.ssh
sudo chmod 600 /home/vendor-acme-20260903/.ssh/authorized_keys

# 帳號在 2026-09-05 之後自動失效
sudo chage -E 2026-09-05 vendor-acme-20260903
sudo chage -l vendor-acme-20260903
```

```text
Last password change                                    : Sep 03, 2026
Password expires                                        : never
Password inactive                                       : never
Account expires                                         : Sep 05, 2026
Minimum number of days between password change          : 0
Maximum number of days between password change          : 99999
Number of days of warning before password expires       : 7
```

`authorized_keys` 的選項是第二道鎖：

| 選項 | 作用 | 重要度 |
| --- | --- | --- |
| `from="203.0.113.0/24"` | 這把金鑰只能從廠商的來源網段使用 | ★★★★ |
| `no-agent-forwarding` | 防止廠商盜用你的 agent | ★★★ |
| `no-pty` | 不給互動 shell（純轉送用途） | ★★★ |
| `command="..."` | 強制只能執行指定指令 | ★★★★ |
| `expiry-time="20260905"` | ★★ OpenSSH 8.2+ 支援的金鑰到期時間 | ★★★ |

**結案撤銷** ★★★★★：

```bash
sudo usermod -L vendor-acme-20260903          # 鎖定密碼
sudo chage -E 0 vendor-acme-20260903          # 立即到期
sudo truncate -s 0 /home/vendor-acme-20260903/.ssh/authorized_keys   # 清掉金鑰
sudo pkill -KILL -u vendor-acme-20260903      # ★★★★ 踢掉還連著的 session
sudo who | grep vendor-acme                    # 應該無輸出
```

> [!danger] ★★★★★ 只 `usermod -L` 是無效的
> `usermod -L` 只鎖密碼，**對金鑰登入完全沒有效果**。
> 只做這一步的話廠商明天照樣連得進來。
> 撤銷一定要三件事一起做：**清 `authorized_keys` ＋ 設帳號到期 ＋ 踢掉現有連線**。

**關於廠商自己的工具（TeamViewer／AnyDesk／專屬 client）** ★★★★：

這類工具是「內部主機主動出向連到廠商雲端」，你的入向防火牆規則管不到。管制方式：

1. 政策上禁止常駐安裝，只允許「用時安裝、用完移除」
2. 在出向防火牆／Proxy 上預設阻擋這些服務的網域與埠，需要時開臨時例外
3. 一定要用時，**由我方人員在自己的機器上啟動、全程在旁**，作業結束立刻關閉
4. 絕不允許裝在伺服器上、絕不允許設成開機自動啟動、絕不允許設「無人值守存取」★★★★★

委外廠商的整體管理制度（合約條款、資安要求、稽核）看
[[090-07-11-guide-資安實踐-委外與供應鏈資安]]；
上線前的檢測看 [[090-03-06-guide-應用安全-委外系統上線前資安檢測]]。

### 五、Windows RDP：原則層 ★★★

> [!note] ★★★ 本篇只寫原則
> RDP 的細部操作、群組原則設定、AD 整合寫在
> [[030-01-00-idx-Windows系統管理-Windows管理]] 那一群組。
> 這裡只列「不管你怎麼設定都必須成立」的五條原則。

| # | 原則 | 說明 | 重要度 |
| --- | --- | --- | --- |
| 1 | 3389 絕不對公網開放 | RDP 是勒索軟體最主要的入口，沒有之一 | ★★★★★ |
| 2 | 一律先 VPN 或走 RD Gateway | RD Gateway 把 RDP 包在 TLS/443 裡並集中驗證 | ★★★★ |
| 3 | 開啟 NLA | Network Level Authentication，在建立完整 session 前先驗證身分，大幅降低未認證攻擊面 | ★★★★ |
| 4 | 帳號鎖定與 MFA | 有帳號鎖定原則，管理員帳號加 MFA | ★★★★ |
| 5 | 登入紀錄要集中 | 安全性事件記錄檔（登入 4624／失敗 4625）送到集中平台 | ★★★★ |

> [!danger] ★★★★★ 把 RDP 換個埠不算防護
> 「我們把 3389 改成 33890 了」不是防護。全埠掃描幾分鐘就找到。
> 改埠只降低雜訊，**不降低風險**。唯一有效的是「不對外開放」。

歷史上 RDP 有過可未認證遠端執行程式碼的重大漏洞（例如 CVE-2019-0708，俗稱 BlueKeep），
影響範圍是「只要 3389 對外就可能被打」。這類漏洞每隔幾年就會再出現一次，
所以正確的姿勢不是「等修補」，是「本來就不對外」。

## 完整實戰範例

**情境：** 某機關有 1 個機房、24 台實體伺服器、3 台網路交換器、1 台防火牆。
維運人員 4 人，另有 3 家系統廠商需要不定期遠端支援。
目前狀況：SSH 與 RDP 直接開在公網、iLO 有 3 台掛了 public IP、
廠商用 TeamViewer 連進來、沒有任何存取紀錄。

**目標：** 一個月內把遠端存取收斂成「單一入口 ＋ 全程稽核 ＋ 廠商有時效」。

### 第 0 步：盤點（不盤點就做設計一定會漏）★★★★★

### 第 1 步：網路分段設計 ★★★★

```text
                          ┌─────────────────────────┐
             網際網路 ────►│  防火牆（唯一對外設備）   │
                          └───┬──────────┬──────────┘
                              │          │
                 (A) 服務 DMZ │          │ (B) VPN 終端
                 203.0.113.x  │          │  udp/51820
                              │          │
        ┌─────────────────────▼──┐   ┌───▼────────────────────┐
        │ VLAN 20 服務網段         │   │ VLAN 99 管理網段        │
        │ 10.10.20.0/24           │   │ 10.10.99.0/24          │
        │  web01 / app01 / db01   │   │  bastion 10.10.99.10   │
        └──────────▲──────────────┘   └───┬────────────────────┘
                   │  只准 10.10.99.10:22  │
                   └──────────────────────┘
                                          │ 只准 bastion 連
                              ┌───────────▼────────────┐
                              │ VLAN 199 帶外管理網段    │
                              │ 10.10.199.0/24         │
                              │  iDRAC / iLO / 交換器   │
                              │  ★★★★★ 無預設路由     │
                              └────────────────────────┘
```

四條規則講完整個設計：

| # | 規則 | 重要度 |
| --- | --- | --- |
| 1 | 網際網路 → 只能到「服務 DMZ 的 80/443」與「VPN 的 udp/51820」 | ★★★★★ |
| 2 | VPN 網段 → **只能到 bastion 的 22**，不能直接到任何伺服器 | ★★★★★ |
| 3 | bastion → 可以到 VLAN 20 的 22、VLAN 199 的 443 | ★★★★ |
| 4 | VLAN 199（帶外）→ **沒有預設路由、不能主動出去、不能被 VPN 直接連** | ★★★★★ |

VLAN 規劃與交換器設定見 [[040-01-03-guide-網路設備-VLAN概念與規劃]] 與
[[040-01-06-guide-Juniper-VLAN與Trunk設定]]；
交換器自己的管理 IP 也要放在 VLAN 199，見 [[040-01-07-guide-Juniper-管理IP與遠端存取]]。

### 第 2 步：建跳板機 ★★★★

用最小安裝，不裝任何多餘套件：

```bash
# 在跳板機上
sudo apt update && sudo apt -y full-upgrade
sudo apt install -y auditd chrony ufw fail2ban
sudo systemctl enable --now auditd chrony fail2ban
```

### 第 3 步：帳號與權限流程 ★★★★

設計三種帳號類型：

| 類型 | 群組 | 能做什麼 | 有效期 | MFA |
| --- | --- | --- | --- | --- |
| 管理員 | `sshusers` ＋ `sudo` | 登入跳板機、跳所有主機、可 sudo | 常設，每季複查 | ★★★★ 必須 |
| 一般維運 | `jumponly` | 只能跳到指定主機清單 | 常設，每季複查 | ★★★★ 必須 |
| 廠商臨時 | `jumponly` | 只能跳到本案主機 | ★★★★★ 最長 7 天 | 依情況 |

申請流程（寫成表單，紀錄留檔）：

```text
1. 申請人填「遠端存取申請單」：對象主機、用途、需要期間、風險等級
2. 系統管理員審核 → 主管核准（廠商案件另需承辦單位會簽）
3. 建立帳號：useradd → 放 authorized_keys（含 from= 限制）→ chage -E 設到期日
4. 通知申請人；廠商案件同時約定作業時間窗與陪同人員
5. 作業中：跳板機側錄 + 目標主機 auditd 記錄
6. 結案：清 authorized_keys → chage -E 0 → pkill -u → 在申請單上簽註撤銷時間
7. 每季：列出所有帳號複查，超過 90 天未登入者停用
```

done

> [!danger] ★★★★★ BMC 沒有預設閘道是刻意的
> 很多人設定完發現 BMC 連不到 NTP、寄不出告警信，就順手加了預設閘道 ——

## 常見錯誤與排錯

| # | 現象 | 原因 | 解法 | 重要度 |
| --- | --- | --- | --- | --- |
| 1 | 改完 `sshd_config` reload 後所有人連不進來 | 設定語法錯或 `AllowGroups` 寫錯群組名 | 用保留的舊 session 執行 `sudo sshd -t` 看錯誤；沒有舊 session 只能走 BMC 遠端 KVM 進去改 | ★★★★★ |
| 2 | `ssh -J` 回 `channel 0: open failed: administratively prohibited` | 跳板機 `PermitOpen` 白名單沒包含目標，或 `AllowTcpForwarding no` | 在對應的 `Match` 區塊加上目標 `IP:port` | ★★★★ |
| 3 | `ssh -J` 回 `Permission denied (publickey)` 但直連跳板機沒問題 | 目標主機沒有你的公鑰；`-J` 對兩段各自認證 | 把公鑰也放到目標主機的 `authorized_keys` | ★★★ |
| 4 | 廠商帳號到期後仍能登入 | 只做了 `usermod -L`，金鑰登入不受密碼鎖影響 | `chage -E 0` ＋ 清空 `authorized_keys` ＋ `pkill -KILL -u` | ★★★★★ |
| 5 | TOTP 一直顯示 `Verification code:` 輸入正確也失敗 | 跳板機時間偏移超過容許視窗 | `chronyc tracking` 檢查 offset，`timedatectl` 確認時區與 NTP 同步 | ★★★★ |
| 6 | 加了 MFA 之後改用金鑰就登不進去 | `AuthenticationMethods publickey,keyboard-interactive` 要求**兩者都過**，`nullok` 又被拿掉 | 先掛回 `nullok`，確認所有帳號都有 `~/.google_authenticator` 再移除 | ★★★★★ |
| 7 | 側錄檔全是亂碼控制字元 | `script` 記錄的是原始終端輸出（含 ANSI 跳脫碼） | 用 `scriptreplay` 重播，或 `cat -v` 檢視；不要用一般編輯器直接讀 | ★★ |
| 8 | 側錄檔把跳板機磁碟塞爆導致無法登入 | `/var/log/sessions` 沒有輪替與容量上限 | 獨立 partition 或 quota，加 logrotate 規則，設磁碟使用率告警 | ★★★★ |
| 9 | BMC 改到管理網段後收不到告警信、時間跑掉 | 管理網段沒有預設路由（這是刻意的） | 不要加預設路由；改由監控主機用 SNMP／Redfish 主動輪詢 | ★★★★ |
| 10 | VPN 連上了但連不到跳板機 | VPN 網段沒有被加進跳板機的防火牆允許清單 | `ufw allow from <VPN 網段> to any port 22 proto tcp` | ★★★ |
| 11 | Fail2ban 把自己的管理 IP 封了 | `ignoreip` 沒設，或設了但 IP 變動 | `fail2ban-client set sshd unbanip <IP>`，並把管理來源網段加進 `ignoreip` | ★★★★ |
| 12 | 目標主機的 auditd 記錄一堆 `uid=0` 分不清是誰 | 只看 `uid` 沒看 `auid` | 用 `ausearch -ua <auid>` 查；規則裡以 `-F auid>=1000` 過濾系統程序 | ★★★ |
| 13 | 對外掃描發現一個沒人記得的開放埠 | 舊的 NAT 對映沒清、或設備上有臨時規則忘了撤 | 逐條對照防火牆規則與盤點表；找不到申請紀錄的一律先關再說 | ★★★★★ |
| 14 | 關掉廠商工具後廠商說「連不上」但流量還在 | 服務被設成開機自動啟動，或裝了無人值守存取 | `systemctl list-unit-files \| grep -i <工具名>` 找出並 `disable --now`，Windows 端查服務與排程 | ★★★★ |
| 15 | 集中日誌主機沒收到跳板機的日誌 | rsyslog 轉送設定錯、防火牆擋 514、或收端沒開監聽 | 收端 `ss -lntp \| grep 514`；發端 `logger -p auth.info test` 後兩邊都查 | ★★★ |
| 16 | 跳板機重開機後 `jumponly` 帳號可以拿到 shell 了 | drop-in 設定檔命名或位置錯誤，沒被 `Include` 讀到 | `sudo sshd -T \| grep -i permitopen` 確認生效值；檔名必須是 `*.conf` | ★★★★ |

> [!tip] ★★★★ `sshd -T` 是排錯神器
> `sudo sshd -T` 會印出「sshd 實際生效的完整設定」（把所有 include 與預設值展開）。
> 懷疑設定沒吃到就用它，不要用 `grep` 猜設定檔。
> 檢查特定使用者的生效設定：`sudo sshd -T -C user=vendor-acme-20260903,addr=203.0.113.44,host=x`。

更多 SSH 端的故障排除見 [[020-02-01-98-trouble-SSH-常見故障排除]]。

## 安全性注意事項

> [!danger] ★★★★★ 十條絕對不要
> 1. 不要把 SSH／RDP／BMC／防火牆管理介面直接開在公網
> 2. 不要用共用帳號（`admin`、`ops`、廠商共用一組）
> 3. 不要只做 `usermod -L` 就當成撤銷
> 4. 不要在跳板機上放私鑰、備份、原始碼
> 5. 不要開 SSH agent forwarding 到不完全信任的主機
> 6. 不要讓帶外管理網段有預設路由或對外的路
> 7. 不要在沒有第二條連線的情況下改 `sshd_config` 或防火牆規則
> 8. 不要允許廠商工具設定「無人值守存取」或開機自動啟動
> 9. 不要把「改埠號」當成防護措施
> 10. 不要讓日誌只留在本機

> [!warning] ★★★★ 跳板機掛掉怎麼辦：緊急通道
> 單一入口的代價是單點失效。必須事先準備，而不是出事才想。
>
> | 層次 | 準備 | 說明 |
> | --- | --- | --- |
> | 1. 備援跳板機 | ★★★★ 第二台 bastion，設定用 Ansible 同步，平時關機或低優先 DNS | 十分鐘內可切換 |
> | 2. VPN 直連例外 | ★★★ 防火牆上預留一條「緊急時啟用」的規則（平時 disabled），允許特定管理員 IP 直連 | 需雙人核可才啟用 |
> | 3. 帶外 KVM | ★★★★ 從管理網段內的另一台機器連 BMC 的遠端 KVM | 跳板機 OS 掛了也能救 |
> | 4. 實體到場 | ★★ 機房門禁名單、實體 KVM 或 console 線 | 最後手段 |
>
> ★★★★★ 緊急通道**必須定期演練**（建議半年一次）並留紀錄。
> 沒演練過的緊急通道，出事時十次有九次是不能用的
> （憑證過期、密碼沒人記得、規則被別人刪了）。
> 演練的設計與紀錄格式見 [[090-07-17-guide-資安實踐-演練設計與演練紀錄]]。

> [!warning] ★★★★ 跳板機本身就是高價值目標
> 它知道所有內部主機的位置，所有管理連線都經過它。
> 因此它需要**比一般伺服器更嚴格**的處理：
> - 修補優先度最高（安全性更新 24 小時內）
> - 開啟 FIM（檔案完整性監控），見 [[090-08-04-guide-Wazuh-FIM檔案完整性監控]]
> - 定期重建（例如每季用 Ansible 重灌一次）
> - 它的日誌是第一批送出去、也是第一批要監控告警的

> [!note] ★★★ 法規面
> 政府機關的遠端存取管制在《資通安全管理法》的技術構面與相關子法中有明確要求
> （存取控制、日誌留存、委外管理）。
> 對應關係見 [[090-07-07-guide-資安實踐-台灣資安法規與個資法]]；
> TWGCB 對 SSH 的具體組態要求見 [[090-06-03-guide-TWGCB-Linux項目分類詳解]]。

> [!tip] ★★★ 帳號生命週期要和人事流程綁在一起
> 最常見的殘留帳號來源是「人走了沒人通知資訊單位」。
> 和人事單位約定：離職／調職通知同步副本給資訊單位，
> 資訊單位在收到後 1 個工作天內停用所有存取。
> 沒有這條流程，靠季度複查只能事後補救。

## 練習題

1. **盤點練習**：對你負責的環境（或實驗環境）產出一張「對外開放清單」，
   欄位為：對外 IP:埠 / 內部目標 / 用途 / 開通日期 / 申請人 / 是否仍需要。
   至少要能對每一條回答「還需要嗎」。

2. **跳板機最小架構**：用兩台虛擬機建出 bastion ＋ target。
   要求：target 的 22 埠只接受 bastion 的來源 IP；
   在你的筆電上設好 `~/.ssh/config`，用 `ssh target` 一句話連上。
   最後從筆電直連 target 驗證是不通的。

3. **jumponly 帳號**：在 bastion 上建一個 `jumponly` 群組帳號，
   讓它可以 `-J` 到 `target:22`，但直接 `ssh bastion` 會被踢掉，
   而且 `-J` 到別的 IP 會被拒絕。附上三種情況的實際輸出。

4. **廠商臨時帳號全流程**：建立一個 3 天後到期的廠商帳號，
   `authorized_keys` 加上 `from=` 限制，
   然後執行完整撤銷（三個步驟）並驗證確實無法再登入。

5. **緊急通道演練**：假設 bastion 整台掛掉，寫出你的復原步驟
   （誰執行、用什麼通道、預估幾分鐘、需要誰核可），並實際走一次備援路徑。

> [!question]- 練習解答
>
> **第 1 題** — 重點不在格式而在「每一條都要找得到申請紀錄」。
> 找不到申請人或用途的規則，處理原則是：先在防火牆上停用（不是刪除）並公告，
> 觀察 2 週沒有人反映就正式移除。★★★★ 直接刪掉的風險是刪到還在用的服務。
>
> **第 2 題** — 關鍵三個指令：
> ```bash
> # target 上
> sudo ufw allow from <bastion IP> to any port 22 proto tcp
> sudo ufw deny 22/tcp        # 或 default deny incoming
> # 筆電上 ~/.ssh/config
> Host target
>     HostName <target 內網 IP>
>     ProxyJump bastion
> ```
> 驗證直連不通時要用 `-o ConnectTimeout=5`，否則會等很久。
> 如果直連仍然通，檢查 ufw 規則順序（`ufw status numbered`），
> allow 規則要在 deny 之前。
>
> **第 3 題** — `Match Group jumponly` 區塊裡三個關鍵：
> `ForceCommand /usr/sbin/nologin`（不給 shell）、
> `PermitTTY no`、`PermitOpen <target>:22`（白名單）。
> 三種輸出分別是：`-J` 成功印出 hostname；
> 直接 ssh 得到 `This account is currently not available.`；
> 跳到白名單外得到 `administratively prohibited: open failed`。
> ★★★ 常見錯誤是忘了 `AllowTcpForwarding yes`，那樣連合法目標也會被擋。
>
> **第 4 題** — 撤銷三步驟缺一不可：
> ```bash
> sudo truncate -s 0 /home/<vendor>/.ssh/authorized_keys
> sudo chage -E 0 <vendor>
> sudo pkill -KILL -u <vendor>
> ```
> 驗證方式：用廠商的私鑰再連一次，應該得到 `Permission denied (publickey).`；
> 若把金鑰放回去測試，也應該因為帳號到期而失敗
> （日誌會出現 `User <vendor> not allowed because account has expired`）。
> ★★★★★ 只做 `usermod -L` 的話，金鑰登入完全不受影響。
>
> **第 5 題** — 合格的答案要包含：
> ① 誰有權啟用緊急通道（至少雙人）；
> ② 用哪一條（備援 bastion / 防火牆臨時規則 / BMC KVM / 到場）；
> ③ 每一條的前置條件是否已備妥（備援機的金鑰有沒有同步？BMC 密碼誰有？）；
> ④ 事後要做什麼（關掉臨時規則、留紀錄、檢討為什麼會掛）。
> ★★★★ 最容易在演練中被抓包的是「備援機上沒有大家的公鑰」與
> 「BMC 密碼存在唯一那個人的腦子裡」。

## 小測驗

Q1. 一個機關說「我們的 SSH 已經改成金鑰登入、換了埠號、裝了 Fail2ban，所以直接開在公網沒關係」。
這個說法有什麼問題？請至少指出兩點。

Q2. （是非）`usermod -L vendor01` 可以有效阻止 vendor01 用 SSH 金鑰登入。

Q3. （選擇）下列哪一項如果對外暴露，風險等級最高？
(A) tcp/80 (B) tcp/22 (C) tcp/443 (D) BMC 的管理介面

Q4. 「這行指令會發生什麼」：
```bash
ssh -J vendor@bastion ops@10.10.10.99
```
已知 bastion 上 vendor 屬於 `jumponly` 群組，該群組設定為
`PermitOpen 10.10.10.21:22 10.10.10.31:22`。

Q5. （簡答）為什麼建議用 `ProxyJump`（`-J`）而不是 SSH agent forwarding（`-A`）來經過跳板機？

Q6. （是非）在跳板機上設 `ForceCommand /usr/sbin/nologin` 之後，該帳號就不能再當作 `-J` 的跳板了。

Q7. （選擇）VPN 網段的防火牆規則，下列哪一個設計最符合本篇的主張？
(A) VPN 網段可以連所有內部網段
(B) VPN 網段只能連跳板機的 22 埠
(C) VPN 網段可以連所有伺服器的 22 埠但不能連 BMC
(D) VPN 網段不設限，靠主機防火牆各自控管

Q8. （簡答）為什麼帶外管理網段（VLAN 199）刻意不設預設閘道？這樣做會帶來什麼副作用，怎麼解決？

Q9. 導入 SSH 的 TOTP MFA 時，`/etc/pam.d/sshd` 裡的 `nullok` 該在什麼時候拿掉？
提早拿掉會發生什麼事？

Q10. 「這行指令會發生什麼」：
```bash
sudo sshd -T -C user=vendor-acme-20260903,addr=203.0.113.44,host=bastion | grep -i permitopen
```

> [!question]- 測驗答案
>
> **Q1** — 至少兩點：
> ① 換埠號不是防護，全埠掃描幾分鐘就找到（見「Windows RDP：原則層」的 danger 區塊，
> 同樣的道理適用於 SSH）。
> ② 直接對外時，OpenSSH 本身的漏洞、金鑰外流、設定失誤都會直接變成入侵，
> 少了 VPN／跳板機這一層緩衝。
> ③ 沒有集中稽核，無法回答「誰在什麼時候從哪裡連進來」。
> 對應段落：「管理平面與服務平面」。★★★★
>
> **Q2** — **非**。`usermod -L` 只鎖密碼欄位，對公鑰認證完全無效。
> 撤銷必須同時做「清 `authorized_keys` ＋ `chage -E 0` ＋ `pkill -KILL -u`」。
> 對應段落：「廠商遠端支援的管制」的 danger 區塊。★★★★★
>
> **Q3** — **(D)**。BMC 的權限高於 root：可以遠端開關機、開 KVM、
> 掛遠端 ISO 重灌整台機器，而且主機關機時它還活著。
> 對應段落：「帶外管理（OOB）為什麼是最高等級」。★★★★★
>
> **Q4** — 連線會失敗，跳板機拒絕開啟到 `10.10.10.99:22` 的轉送通道，
> 用戶端看到 `channel 0: open failed: administratively prohibited: open failed`
> 接著 `stdio forwarding failed`。因為 `10.10.10.99` 不在 `PermitOpen` 白名單裡。
> 對應段落：「跳板機的權限收斂」。★★★★
>
> **Q5** — `ProxyJump` 在**本機**建立到最終目標的加密通道，
> 私鑰與 agent 都不出現在跳板機上；agent forwarding 則會在跳板機上留下 agent socket，
> 跳板機的 root（或被入侵後的攻擊者）可以盜用它去登入你有權限的所有主機。
> 對應段落：步驟 2 的 warning 區塊。★★★★
>
> **Q6** — **非**。`ForceCommand` 只影響「開啟 shell／執行指令」這個 channel；
> `-J` 用的是 `direct-tcpip` channel，不需要 shell，因此仍然可用。
> 這正是 `jumponly` 帳號設計的原理。對應段落：「跳板機的權限收斂」。★★★★
>
> **Q7** — **(B)**。VPN 解決「你是不是我們的人」，
> 但進來之後仍要經跳板機才拿得到「做了什麼」的紀錄，也才能收斂可達範圍。
> (A)(D) 等於把 VPN 帳號當成內網通行證；
> (C) 少了側錄與單一入口，且 BMC 的隔離只做了一半。
> 對應段落：「第 1 步：網路分段設計」。★★★★★
>
> **Q8** — 不設預設閘道是為了讓帶外網段**沒有任何對外的路**，
> 即使有人誤設規則也走不出去。副作用是 BMC 無法主動連 NTP、
> 無法自己寄告警信、無法連韌體更新伺服器。
> 解法是改成「拉」的模式：由管理網段內的監控主機用 SNMP／Redfish 主動輪詢，
> 韌體更新用手動或經跳板機代理。
> 對應段落：「第 4 步：處理帶外管理」的 danger 區塊。★★★★★
>
> **Q9** — 要等到「**確認每個需要登入的帳號都已經有 `~/.google_authenticator`**」之後才拿掉
> （用 `sudo ls /home/*/.google_authenticator` 逐一核對）。
> 提早拿掉的話，還沒設定 TOTP 的使用者會全部登不進來 ——
> 包含你自己，就變成整個機關被鎖在門外，只能靠 BMC 或到機房才能救。
> 對應段落：「多因素驗證」的 danger 區塊。★★★★★
>
> **Q10** — 它會印出「sshd 對 `vendor-acme-20260903` 這個使用者、
> 從 `203.0.113.44` 連進來時**實際生效**的 `PermitOpen` 值」，
> 例如 `permitopen 10.10.10.21:22` 與 `permitopen 10.10.10.31:22` 兩行。
> `-T` 展開所有 include 與預設值，`-C` 模擬特定連線條件以觸發對應的 `Match` 區塊。
> 這是驗證 `Match` 有沒有生效最可靠的方法，不要用 grep 設定檔去猜。
> 對應段落：「常見錯誤與排錯」下方的 tip。★★★★
