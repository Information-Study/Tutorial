# 系統強化與稽核

> [!abstract] 這篇你會學到
> - 說得清楚**設定漂移（configuration drift）**是什麼、為什麼一定會發生、怎麼被發現
> - 用 `etckeeper` ＋ git 把 `/etc` 的每一次改動變成有紀錄、可回溯的東西
> - 為服務、埠、帳號、sudo 授權、cron 建立**基準清單**，並用一支腳本產出「現況 vs 基準」差異報告
> - 跑 **Lynis**、讀懂 hardening index 與 suggestions，並用一套判斷準則決定**哪些建議該做、哪些在機關環境不能照做**
> - 用 **OpenSCAP** 對 CIS／TWGCB 類基準產出符合性報告，並分清楚它跟 Lynis 的定位差異
> - 寫得出堪用的 **auditd** 規則、用 `ausearch` / `aureport` 查得到人，並知道規則太多會怎麼拖垮效能
> - 用 **AIDE** 做檔案完整性監控（FIM），並知道什麼時候該交給 Wazuh
> - ★★★★★ 針對常見稽核問項（帳號覆核、修補率、日誌保存、權限最小化），**各給出一條能直接產出可交付證據的指令**

## 這篇你會學到

這篇處理的是一個很具體的場景：

> 三個月前照 [[090-02-01-guide-防護-伺服器初始安全設定]] 把一台新機設好了，
> 防火牆關好、root 登入停掉、帳號建好。三個月後的今天 ——

## 觀念說明

### 一、設定漂移是什麼 ★★★★

**設定漂移（configuration drift）**：系統的實際狀態，隨時間偏離當初設定好的基準狀態。

它不是「有人搞破壞」，絕大多數時候是**正常的維運行為累積出來的**。真實案例長這樣：

| 漂移來源 | 典型情境 | 三個月後留下什麼 |
| --- | --- | --- |
| 臨時開的埠沒關 ★★★★ | 廠商說「先開 3306 給我測一下」 | MySQL 對外全開，`ufw` 多一條 `ALLOW Anywhere` |
| 廠商施工改設定 ★★★★ | 系統商來裝新模組，順手改了 `php.ini` 與 `sshd_config` | `PermitRootLogin yes` 被改回來，沒人知道 |
| 緊急處理放寬權限 ★★★★★ | 半夜服務掛掉，`chmod 777` 先讓它動起來 | 上傳目錄變成 777，誰都能寫 |
| 測試帳號沒刪 ★★★ | 教育訓練建了 `test`、`demo` 帳號 | 弱密碼帳號長期存在，且從沒登入過 |
| 暫時停用的防護 ★★★★ | 「SELinux 先關掉，等有空再調」 | `SELINUX=permissive` 一放兩年 |
| 套件升級改回預設 ★★★ | `apt upgrade` 時選了「保留套件維護者版本」 | 自己改的設定檔被覆蓋回原廠值 |
| 排程殘留 ★★ | 一次性的資料轉檔 cron 忘了拿掉 | 每天凌晨跑一支已經沒人維護的腳本 |

> [!tip] 心態調整 ★★★
> 漂移**不可能杜絕**，只能**被發現**。
> 花力氣去「禁止任何人改設定」是徒勞的；真正有效的是**讓每一次改動都留下痕跡，並定期比對**。
> 這就是本篇兩個核心動作：**記錄改動**（etckeeper／auditd／AIDE）與**定期比對**（基準清單／Lynis／OpenSCAP）。

### 二、基準（baseline）的三種層次 ★★★

「基準」這個詞在資安圈被用得很鬆，實務上至少有三種，別混在一起講：

| 層次 | 名稱 | 內容 | 誰定的 | 本篇怎麼用 |
| --- | --- | --- | --- | --- |
| 1 | **組態基準文件** | TWGCB、CIS Benchmark、DISA STIG | 外部權威機構 | 用 OpenSCAP 對照它跑出符合性報告 |
| 2 | **機關內部標準** | 「我們的 Web 主機該長什麼樣」 | 你自己的單位 | 寫成 Ansible role 或檢核腳本 |
| 3 | **這台機器的現況快照** ★★★★ | 這台機器**上線當天**的服務／埠／帳號清單 | 上線時凍結 | 拿來做**漂移比對** |

本篇的漂移偵測操作的是**第 3 層**。第 1 層屬於 TWGCB 專章（[[090-06-02-guide-TWGCB-Linux基準文件解讀]]），第 2 層屬於 [[020-02-03-02-ref-標準化-基準設定與範本化]]。

> [!note] 為什麼第 3 層最實用 ★★★★
> 第 1 層告訴你「應該符合 200 條規範」，第 3 層告訴你「**這台機器上週多開了一個埠**」。
> 對現場維運來說，第 3 層的訊噪比高太多了 —— 它的每一筆差異都是**真的發生過的改動**，沒有理論值。

### 三、三種檢核工具的定位 ★★★★

新手最常見的困惑是「Lynis、OpenSCAP、Wazuh SCA 到底該用哪個」。答案是**用途不同，可以並存**：

| 工具 | 問的問題 | 產出 | 適合場合 | 不適合 |
| --- | --- | --- | --- | --- |
| **Lynis** | 「這台機器整體加固程度如何？有哪些可以再強化？」 | hardening index（0–100）＋ 一串 suggestion | 單機健檢、上線前體檢、找出被忽略的角落 | 拿去對稽核（它不對應任何官方基準編號） |
| **OpenSCAP** | 「這台機器符不符合 CIS Level 1 / TWGCB 的第幾條？」 | 逐條 pass/fail 的 XCCDF 報告（HTML／XML） | **符合性稽核**、要交報告給稽核員 | 找「規範沒寫但其實有問題」的東西 |
| **Wazuh SCA** | 同上，但**多機集中、持續、有歷史趨勢** | Dashboard 上的合規分數與逐機明細 | 有 Wazuh 的環境、幾十台以上 | 只有一兩台機器（架設成本不划算） |
| **自寫漂移腳本** | 「這台機器跟**它自己上個月**比，變了什麼？」 | diff 差異報告 | 每一種環境都該有 | 回答「符不符合外部規範」 |

> [!tip] 選型建議 ★★★★
> - 機器 **1～5 台**：Lynis ＋ 漂移腳本 ＋ AIDE，夠用而且零成本
> - 機器 **5～30 台**：加上 OpenSCAP，並用 Ansible 批次跑（[[020-02-03-07-guide-標準化-Ansible-role與日常批次作業]]）
> - 機器 **30 台以上**：導入 Wazuh，SCA ＋ FIM 一次解決（[[090-08-06-guide-Wazuh-SCA安全組態評估]]）
>
> ★★★ 不要因為導了 Wazuh 就把 Lynis 丟掉 —— 兩者找到的東西**重疊度沒有想像中高**。

### 四、稽核證據的三個要件 ★★★★★

制度面的稽核流程看 [[090-07-09-guide-資安實踐-資安稽核與符合性檢核]]。這裡只講技術面：**什麼樣的輸出才算得上「證據」**。

一份能交出去的證據，必須同時具備三件事：

| 要件 | 意思 | 技術上怎麼做到 |
| --- | --- | --- |
| **可重現** ★★★★ | 稽核員自己敲同一行指令，會得到同樣結果 | 證據旁邊要附**產生它的那行指令** |
| **有時間戳** ★★★★ | 看得出這是什麼時候的狀態 | 檔名帶日期、內文第一行寫 `date -Is` 的輸出 |
| **未被竄改** ★★★ | 從產生到交付之間沒被改過 | 打包後算 `sha256sum`，摘要另外記錄 |

> [!danger] 最常見的失分 ★★★★★
> 交出一份**沒有指令、沒有日期、Word 排版過的「檢核結果表」**。
> 稽核員無法驗證它，只能當成「聲明」而不是「證據」，等同於沒交。
> **原始輸出（raw output）永遠比整理過的表格有價值**，兩個都給最好。

## 安裝或基礎操作

這一段把四樣基礎建設裝起來：etckeeper、Lynis、auditd、AIDE。先裝、先跑起來，判讀留到下一段。

### 一、用 etckeeper 把 /etc 納入版本控制 ★★★★

這是投資報酬率最高的一步。裝好之後，**`/etc` 底下任何檔案的任何改動都查得到「誰、什麼時候、改了哪一行」**。

```bash
sudo apt update
sudo apt install -y etckeeper git
```

Ubuntu 的套件預設就用 git，確認一下：

```bash
grep -E '^VCS=' /etc/etckeeper/etckeeper.conf
```

預期輸出：

```text
VCS="git"
```

初始化（第一次會把整個 `/etc` 做成一個 commit）：

```bash
sudo etckeeper init
sudo etckeeper commit "baseline: 系統上線初始狀態 $(date +%F)"
```

預期輸出（節錄）：

```text
[master (root-commit) 3f9a1c2] baseline: 系統上線初始狀態 2026-09-03
 1284 files changed, 51203 insertions(+)
 create mode 100644 adduser.conf
 create mode 100644 apt/sources.list
 ...
```

之後查改動：

```bash
# 最近 10 次改動
sudo etckeeper vcs log --oneline -10

# 看某一次 commit 到底改了什麼
sudo etckeeper vcs show <commit-id>

# 現在有沒有還沒 commit 的改動（手改完設定檔還沒記錄的）
sudo etckeeper vcs status
```

`etckeeper vcs log` 的典型輸出：

```text
a71c4e8 committing changes in /etc after apt run
5d20f13 daily autocommit
3f9a1c2 baseline: 系統上線初始狀態 2026-09-03
```

> [!note] 它怎麼自動記錄 ★★★
> etckeeper 掛了兩個 hook：
> - **APT hook**：每次 `apt install` / `apt upgrade` 前後各 commit 一次，所以「套件升級改了哪個設定檔」一目了然
> - **每日 cron**：把當天手動改的東西 autocommit 起來（訊息是 `daily autocommit`）
>
> ★★★★ 但這代表**手改設定當下不會立刻 commit**。養成習慣：改完設定檔立刻自己下
> `sudo etckeeper commit "調整 nginx worker 數，變更單 CHG-2026-081"`，把變更單編號寫進去，
> 稽核時這一行就是最漂亮的證據。

> [!warning] 敏感檔案的處理 ★★★★
> `/etc` 裡有 `shadow`、`gshadow`，還可能有私鑰。etckeeper 會把它們一起納管。
> - git 目錄 `/etc/.git` 的權限必須是 **0700 且屬 root**，安裝時預設如此，**不要改**
> - ★★★★★ **絕對不要**把這個 repo push 到任何遠端（GitHub、內部 GitLab 都不行），
>   那等同於把整台機器的密碼雜湊與私鑰外送
> - 要異地備份就整份 `/etc/.git` 加密後放備份區

### 二、產出基準清單 ★★★★

`/etc` 只涵蓋設定檔。服務狀態、開放埠、帳號、sudo 授權、cron 這些**不在 `/etc` 裡或分散各處**，要另外抓快照。

先建目錄結構：

```bash
sudo mkdir -p /var/lib/baseline/{approved,current,reports}
sudo chmod 700 /var/lib/baseline
```

各項的抓法（先手動跑一次，看看輸出長什麼樣）：

```bash
# 1. 啟用的服務
systemctl list-unit-files --type=service --state=enabled --no-legend --no-pager \
  | awk '{print $1}' | sort
```

```text
apparmor.service
cron.service
nginx.service
ssh.service
systemd-journald.service
ufw.service
```

```bash
# 2. 監聽中的埠（含程式名）
sudo ss -tulpnH | awk '{print $1, $5, $7}' | sort -u
```

```text
tcp 0.0.0.0:22 users:(("sshd",pid=812,fd=3))
tcp 0.0.0.0:80 users:(("nginx",pid=1104,fd=6))
tcp 127.0.0.1:3306 users:(("mysqld",pid=990,fd=22))
udp 0.0.0.0:123 users:(("chronyd",pid=744,fd=5))
```

> [!tip] ★★★ `ss` 輸出裡的 pid 每次都不一樣，直接 diff 會滿江紅。
> 待會的腳本會把 pid 濾掉，只留「協定＋監聽位址＋程式名」。

```bash
# 3. 一般使用者帳號（UID >= 1000 且可登入）
awk -F: '$3>=1000 && $3<65534 {print $1":"$3":"$7}' /etc/passwd | sort
```

```text
deploy:1001:/bin/bash
sysadm:1000:/bin/bash
```

```bash
# 4. sudo 授權
getent group sudo
sudo grep -rhv -e '^#' -e '^$' /etc/sudoers /etc/sudoers.d/ 2>/dev/null | sort
```

```text
sudo:x:27:sysadm,deploy
Defaults env_reset
Defaults mail_badpass
%sudo ALL=(ALL:ALL) ALL
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart nginx
```

```bash
# 5. 排程
sudo ls -1 /etc/cron.d/ /etc/cron.daily/ /etc/cron.hourly/ /etc/cron.weekly/ /etc/cron.monthly/
for u in $(cut -d: -f1 /etc/passwd); do
  out=$(sudo crontab -u "$u" -l 2>/dev/null) && [ -n "$out" ] && echo "== $u ==" && echo "$out"
done
```

```bash
# 6. SUID / SGID 檔案（權限提升的主要來源）
sudo find / -xdev \( -perm -4000 -o -perm -2000 \) -type f -printf '%m %u %g %p\n' 2>/dev/null | sort -k4
```

```text
4755 root root /usr/bin/passwd
4755 root root /usr/bin/sudo
2755 root shadow /usr/bin/expiry
```

```bash
# 7. 已安裝套件與版本
dpkg-query -W -f='${Package} ${Version}\n' | sort
```

把上面七項各存成一個檔，就是這台機器的基準快照。下一段會給整合成一支腳本的版本。

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> - **etckeeper**：`sudo dnf install -y etckeeper git`，之後 `etckeeper init` 相同。
>   RHEL 系的 hook 掛在 dnf 上（`/etc/dnf/plugins/`），效果與 APT hook 相同。
> - **套件清單**改用 `rpm -qa --qf '%{NAME} %{VERSION}-%{RELEASE}\n' | sort`
> - **服務清單**指令完全相同（都是 systemd）
> - **sudo 群組**是 `wheel` 不是 `sudo`：`getent group wheel`
> - ★★★ RHEL 系多一項要抓：**SELinux 狀態與布林值**
>   ```bash
>   getenforce
>   sudo semanage boolean -l -C   # 只列出被改過（非預設）的布林值
>   ```
>   `-C` 會只顯示與原廠預設不同的項目，這正是漂移偵測要的。詳見 [[090-02-07-guide-防護-SELinux與AppArmor]]。

### 三、安裝 Lynis ★★★


## 進階應用

### 一、漂移偵測腳本 ★★★★★

把前面七項整合成一支可以每天跑的腳本。它做兩件事：**採集現況**、**跟核可基準比對**。

```bash
sudo tee /usr/local/sbin/drift-check.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# drift-check.sh — 設定漂移偵測
# 用法：
#   drift-check.sh collect   採集現況到 current/
#   drift-check.sh approve   把現況核可為新基準（覆蓋 approved/）
#   drift-check.sh diff      比對現況與基準，產出差異報告
set -uo pipefail

BASE=/var/lib/baseline
CUR="$BASE/current"
APV="$BASE/approved"
REP="$BASE/reports"
STAMP=$(date +%Y%m%d-%H%M%S)

mkdir -p "$CUR" "$APV" "$REP"
umask 077

collect() {
  # 1 啟用中的服務
  systemctl list-unit-files --type=service --state=enabled --no-legend --no-pager \
    | awk '{print $1}' | sort > "$CUR/01-services.txt"

  # 2 監聽埠（刻意濾掉 pid/fd，否則每次都不同）
  ss -tulpnH 2>/dev/null \
    | awk '{proto=$1; addr=$5; prog=""; if (match($0,/"[^"]+"/)) prog=substr($0,RSTART+1,RLENGTH-2); print proto, addr, prog}' \
    | sort -u > "$CUR/02-listen.txt"

  # 3 一般帳號（帳號:UID:shell）
  awk -F: '$3>=1000 && $3<65534 {print $1":"$3":"$7}' /etc/passwd | sort > "$CUR/03-users.txt"

  # 4 sudo 授權（含群組成員）
  { getent group sudo wheel 2>/dev/null
    grep -rhv -e '^#' -e '^$' /etc/sudoers /etc/sudoers.d/ 2>/dev/null
  } | sort > "$CUR/04-sudo.txt"

  # 5 排程
  { for d in /etc/cron.d /etc/cron.daily /etc/cron.hourly /etc/cron.weekly /etc/cron.monthly; do
      [ -d "$d" ] && find "$d" -maxdepth 1 -type f -printf "$d/%f\n"
    done
    for u in $(cut -d: -f1 /etc/passwd); do
      o=$(crontab -u "$u" -l 2>/dev/null | grep -v '^#') || continue
      [ -n "$o" ] && echo "$o" | sed "s|^|crontab:$u: |"
    done
  } | sort > "$CUR/05-cron.txt"

  # 6 SUID / SGID
  find / -xdev \( -perm -4000 -o -perm -2000 \) -type f -printf '%m %u %g %p\n' 2>/dev/null \
    | sort -k4 > "$CUR/06-suid.txt"

  # 7 套件清單
  if command -v dpkg-query >/dev/null; then
    dpkg-query -W -f='${Package} ${Version}\n' | sort > "$CUR/07-packages.txt"
  else
    rpm -qa --qf '%{NAME} %{VERSION}-%{RELEASE}\n' | sort > "$CUR/07-packages.txt"
  fi

  # 8 防火牆規則
  { command -v ufw     >/dev/null && ufw status verbose
    command -v nft     >/dev/null && nft list ruleset
  } 2>/dev/null | sort > "$CUR/08-firewall.txt"

  echo "採集完成：$CUR （$(date -Is)）"
}

approve() {
  collect
  cp -a "$CUR"/. "$APV"/
  date -Is > "$APV/.approved_at"
  echo "已將現況核可為新基準：$APV"
}

do_diff() {
  collect
  local out="$REP/drift-$STAMP.txt"
  local found=0
  {
    echo "設定漂移報告"
    echo "主機：$(hostname -f)"
    echo "產生時間：$(date -Is)"
    echo "基準核可時間：$(cat "$APV/.approved_at" 2>/dev/null || echo '（未建立）')"
    echo "產生指令：$0 diff"
    echo "======================================================"
  } > "$out"

  for f in "$CUR"/*.txt; do
    local n; n=$(basename "$f")
    if [ ! -f "$APV/$n" ]; then
      echo -e "\n### $n —— 基準不存在（新項目）" >> "$out"; found=1; continue
    fi
    if ! diff -q "$APV/$n" "$f" >/dev/null; then
      {
        echo ""
        echo "### $n"
        echo "--- 少了（基準有、現在沒有）"
        comm -23 "$APV/$n" "$f" | sed 's/^/  - /'
        echo "+++ 多了（基準沒有、現在有）"
        comm -13 "$APV/$n" "$f" | sed 's/^/  + /'
      } >> "$out"
      found=1
    fi
  done

  if [ "$found" -eq 0 ]; then
    echo -e "\n所有項目與基準一致，無漂移。" >> "$out"
  fi

  cat "$out"
  echo ""
  echo "報告已存於：$out"
  return "$found"
}

case "${1:-diff}" in
  collect) collect ;;
  approve) approve ;;
  diff)    do_diff ;;
  *) echo "用法：$0 {collect|approve|diff}" >&2; exit 2 ;;
esac
EOF

sudo chmod 700 /usr/local/sbin/drift-check.sh
```

首次使用 —— **先把當前狀態核可為基準**：

```bash
sudo /usr/local/sbin/drift-check.sh approve
```

```text
採集完成：/var/lib/baseline/current （2026-09-03T10:02:11+08:00）
已將現況核可為新基準：/var/lib/baseline/approved
```

之後任何時候比對：

```bash
sudo /usr/local/sbin/drift-check.sh diff
```

有漂移時的輸出長這樣（★★★★ 這就是你要的東西）：

```text
設定漂移報告
主機：web01.example.gov.tw
產生時間：2026-09-03T10:44:05+08:00
基準核可時間：2026-06-01T09:00:00+08:00
產生指令：/usr/local/sbin/drift-check.sh diff
======================================================

### 02-listen.txt
--- 少了（基準有、現在沒有）
+++ 多了（基準沒有、現在有）
  + tcp 0.0.0.0:3306 mysqld
  + tcp 0.0.0.0:8080 java

### 03-users.txt
--- 少了（基準有、現在沒有）
+++ 多了（基準沒有、現在有）
  + vendor:1005:/bin/bash

### 04-sudo.txt
--- 少了（基準有、現在沒有）
+++ 多了（基準沒有、現在有）
  + vendor ALL=(ALL) NOPASSWD: ALL

報告已存於：/var/lib/baseline/reports/drift-20260903-104405.txt
```

這份報告的三行差異就是一次完整的資安事件線索：廠商帳號、無密碼全權 sudo、MySQL 對外全開。

排成每日：

```bash
sudo tee /etc/cron.d/drift-check >/dev/null <<'EOF'
# 每天 06:30 檢查設定漂移，有差異時 cron 會把輸出寄給 root
30 6 * * * root /usr/local/sbin/drift-check.sh diff >/dev/null || /usr/local/sbin/drift-check.sh diff
EOF
```

> [!tip] 核可流程要有紀律 ★★★★
> `approve` 是**唯一會覆蓋基準的動作**，不能隨便下。實務規則：
> 1. 看到漂移 → 先判斷這是**核可過的變更**還是**未授權改動**
> 2. 是核可過的變更（有變更單）→ 才執行 `approve`，並在變更單記錄「已更新基準」
> 3. 是未授權改動 → **先復原，不要 approve** ★★★★★
>
> 最常見的錯誤是「報告太吵了，我 approve 一下讓它安靜」—— 這等於把漏洞正式收編進基準。

### 二、讀懂 Lynis 並判斷該不該照做 ★★★★★

Lynis 一跑就給你三、四十條建議。**照單全收會出事**。

先看單一建議的細節：

```bash
sudo lynis show details AUTH-9328
```

```text
[TEST]
  Id             : AUTH-9328
  Description    : Default umask values in /etc/login.defs
  ...
```

> [!warning] 測試編號會隨版本變動 ★★★
> 上面的 `AUTH-9328` 是常見的 umask 測試編號，但**不同 Lynis 版本的測試集合會增刪**。
> 一律以你機器上 `lynis show tests` 與 `/var/log/lynis-report.dat` 實際列出的為準，
> 不要照抄任何文件（包含本篇）裡的編號。

#### 判斷準則：四問法 ★★★★★

拿到一條建議，依序問四個問題，**任何一題答「是」就先不要做**：

| # | 問題 | 為什麼 | 典型例子 |
| --- | --- | --- | --- |
| 1 | 它會**改變現有服務的行為**嗎？ | 加固最常見的災難是服務靜默失效 | 收緊 `umask` 會讓 Web 應用寫出的檔案讀不到 |
| 2 | 它需要**重開機**或**重啟關鍵服務**才生效嗎？ | 要排維護時段，不能順手做 | sysctl 的部分項目、核心模組黑名單 |
| 3 | 它跟**既有基準（TWGCB／CIS）衝突**嗎？ | 兩邊都聽會打架 | 密碼複雜度、日誌保留天數的數值不同 |
| 4 | 這台機器的**角色**讓這條不適用嗎？ | 通用建議 vs 專用主機 | 對內部 DB 主機建議裝 malware scanner，效益低 |

#### 機關環境常見的「不該照做」清單 ★★★★

以下都是 Lynis 常給、但在機關環境要三思的建議：

| Lynis 常見建議 | 為什麼要三思 | 建議做法 |
| --- | --- | --- |
| 「把 `/var`、`/tmp`、`/home` 切成獨立分割區」 | 機器已上線，重分割等於重灌 ★★★★ | **記為例外**，下一批新機建置時採用；`/tmp` 可用 tmpfs 折衷 |
| 「安裝 malware scanner」 | ClamAV 在正式主機吃記憶體與 IO 明顯 | 有 Wazuh 的話交給它；否則只掃上傳目錄，不要全機常駐掃描 |
| 「停用未使用的核心模組（usb-storage、firewire）」 | ★★★ 機房主機通常該做，但**虛擬機或需要 USB 授權鎖的主機不能做** | 先確認有沒有 USB dongle、有沒有靠 USB 做救援 |
| 「啟用 `PermitRootLogin no`」 | 通常該做，但★★★★★**如果目前備份或監控系統是用 root SSH 進來的，改了會全斷** | 先查 `/var/log/auth.log` 有沒有 root 成功登入紀錄，改掉來源後再收 |
| 「設定密碼老化（`PASS_MAX_DAYS 90`）」 | 會影響服務帳號 —— 服務帳號密碼過期會導致排程失敗 | 只對「人用帳號」套用，服務帳號設為不過期並改用金鑰 |
| 「安裝 `debsums` 驗證套件完整性」 | 低風險，做了不會壞 ★ | 可以做，屬於「無腦照做」那一類 |
| 「啟用 process accounting（`acct`）」 | 會產生大量紀錄，磁碟空間要先算過 | 有 auditd 的話重疊度高，可略過 |
| 「調整多項 sysctl 網路參數」 | ★★★★ 部分項目（如 `rp_filter`、`accept_redirects`）在**多網卡或不對稱路由**環境會斷線 | 逐項評估，絕不整包套用 |

> [!danger] 絕對不要做的事 ★★★★★
> 網路上找得到「一鍵套用所有 Lynis 建議」的腳本。**不要在正式環境跑。**
> 這類腳本會一次改動 SSH、PAM、sysctl、掛載選項，出事時你**無法判斷是哪一項造成的**，
> 而且多半沒有回退機制。加固永遠是**一次一項、改完驗證、記錄變更**。

#### 把建議分成三桶 ★★★★

實務上把每次掃描結果分三類，寫進表格交給主管：

| 桶 | 定義 | 處理 |
| --- | --- | --- |
| **A：立刻做** | 不影響服務、可回退、風險明確 | 排在本週，改完重跑 Lynis 驗證 |
| **B：排期做** | 需要維護時段或重開機 | 排進下次維護窗，走變更流程 |
| **C：不做（例外）** ★★★★ | 與服務衝突或不適用 | **必須寫例外理由並留存**，格式見 [[090-07-09-guide-資安實踐-資安稽核與符合性檢核]] |

> [!tip] C 桶才是稽核的重點 ★★★★★
> 稽核員不在意你分數多少，在意的是「**沒做的那些，你知不知道自己沒做、為什麼不做**」。
> 一份寫得清楚的例外清單，比一個高分數更能通過稽核。

#### 只跑特定群組、跳過特定測試

```bash
# 只跑跟認證有關的測試（群組名以 lynis show groups 為準）
sudo lynis audit system --tests-from-group authentication

# 用自訂 profile 永久跳過某些測試
sudo tee /etc/lynis/custom.prf >/dev/null <<'EOF'
# 本機為虛擬機，無實體 USB，該測試不適用（例外編號 EX-2026-014）
skip-test=STRG-1846
# 分割區配置為既有環境限制，列為例外（EX-2026-015）
skip-test=FILE-6310
EOF

sudo lynis audit system
```

★★★★ 在 `custom.prf` 裡**每一行都寫上例外理由與例外編號** —— 這個檔案本身就是稽核證據。

#### 排成每月自動跑

```bash
sudo tee /etc/cron.monthly/lynis-audit >/dev/null <<'EOF'
#!/bin/sh
DATE=$(date +%Y%m)
/usr/sbin/lynis audit system --cronjob \
  --auditor "資訊室例行檢核" \
  --report-file "/var/log/lynis/report-${DATE}.dat" \
  --logfile "/var/log/lynis/lynis-${DATE}.log" >/dev/null 2>&1
EOF
sudo mkdir -p /var/log/lynis && sudo chmod 700 /var/log/lynis
sudo chmod 700 /etc/cron.monthly/lynis-audit
```

`--cronjob` 會關掉互動色彩與分頁，適合非互動執行。之後就能畫趨勢：

```bash
grep -H '^hardening_index=' /var/log/lynis/report-*.dat
```

```text
/var/log/lynis/report-202606.dat:hardening_index=64
/var/log/lynis/report-202607.dat:hardening_index=71
/var/log/lynis/report-202608.dat:hardening_index=73
```

★★★★★ **這三行就是「持續改善」的證據**，稽核時價值極高 —— 它證明的不是「你很安全」，而是「你有在管理」。

### 三、OpenSCAP：對照官方基準產出符合性報告 ★★★★

Lynis 給的是它自己的觀點；**OpenSCAP 給的是對照某一份正式基準的逐條結果**，這才是能交給稽核員的東西。

```bash
sudo apt install -y libopenscap8 ssg-base ssg-debderived ssg-debian ssg-applications
```

先看有哪些 datastream 檔與 profile：

```bash
ls /usr/share/xml/scap/ssg/content/
```

| 面向 | Lynis | OpenSCAP |
| --- | --- | --- |
| 依據 | 工具自己的最佳實務集合 | **正式發布的基準文件**（CIS / STIG / TWGCB 改寫） |
| 輸出 | 分數 ＋ 建議清單 | 逐條 pass/fail ＋ 標準化報告 |

| 誤判處理 | 用 `custom.prf` 的 `skip-test` | 用 tailoring 檔調整 profile |
| 部署難度 | 極低（一個套件、一行指令） | 中（要選對 datastream 與 profile） |
| 何時用 | 平時體檢、找盲點 | **稽核前、要交報告時** |

> 常見做法：**每月跑 Lynis 看趨勢，每季跑 OpenSCAP 產報告**，
> 對應到 [[100-02-05-guide-維運-每季維護作業]] 的季度作業裡。

### 四、auditd 實務 ★★★★

auditd 回答的是**「誰在什麼時候做了什麼」**，這是 syslog / journald 給不了的。

#### 規則的三種型態

規則放在 `/etc/audit/rules.d/*.rules`，用 `augenrules --load` 載入。三種寫法：

| 型態 | 語法 | 用途 |
| --- | --- | --- |
| **控制規則** | `-D`、`-b`、`-e` | 清空規則、設緩衝區、鎖定規則 |
| **檔案監控（watch）** | `-w <路徑> -p <權限> -k <標籤>` | 監控檔案／目錄的存取 |
| **系統呼叫（syscall）** | `-a always,exit -F arch=b64 -S <syscall> ...` | 監控特定系統呼叫，可加條件 |

`-p` 的四個旗標：`r` 讀、`w` 寫、`x` 執行、`a` 屬性變更（權限、擁有者）。

#### 一份夠用的規則集 ★★★★

```bash
sudo tee /etc/audit/rules.d/10-hardening.rules >/dev/null <<'EOF'
## 先清空既有規則，避免重複載入
-D

## 緩衝區：預設 8192，繁忙主機可調到 16384 或 32768
-b 16384

## 緩衝區滿時等待（毫秒），避免直接丟事件
--backlog_wait_time 60000

## ---- 1. 帳號與認證相關檔案異動 ----
-w /etc/passwd    -p wa -k identity
-w /etc/shadow    -p wa -k identity
-w /etc/group     -p wa -k identity
-w /etc/gshadow   -p wa -k identity
-w /etc/sudoers   -p wa -k scope
-w /etc/sudoers.d/ -p wa -k scope

## ---- 2. 關鍵服務設定 ----
-w /etc/ssh/sshd_config   -p wa -k sshd_conf
-w /etc/ssh/sshd_config.d/ -p wa -k sshd_conf
-w /etc/pam.d/            -p wa -k pam
-w /etc/crontab           -p wa -k cron
-w /etc/cron.d/           -p wa -k cron

## ---- 3. 稽核設定本身被動手（重要） ----
-w /etc/audit/    -p wa -k auditconfig
-w /sbin/auditctl -p x  -k audittools
-w /sbin/auditd   -p x  -k audittools

## ---- 4. 特權指令執行：以 root 身分執行、但發起者是一般使用者 ----
-a always,exit -F arch=b64 -S execve -C uid!=euid -F euid=0 -k privesc
-a always,exit -F arch=b32 -S execve -C uid!=euid -F euid=0 -k privesc

## ---- 5. 特定高風險執行檔 ----
-a always,exit -F path=/usr/bin/sudo   -F perm=x -F auid>=1000 -F auid!=unset -k sudo_exec
-a always,exit -F path=/usr/bin/su     -F perm=x -F auid>=1000 -F auid!=unset -k su_exec
-a always,exit -F path=/usr/bin/passwd -F perm=x -F auid>=1000 -F auid!=unset -k passwd_exec

## ---- 6. 模組載入 ----
-w /sbin/insmod  -p x -k modules
-w /sbin/rmmod   -p x -k modules
-w /sbin/modprobe -p x -k modules
EOF

sudo augenrules --load
sudo auditctl -l | head
```

```text
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
-w /etc/sudoers -p wa -k scope
-a always,exit -F arch=b64 -S execve -C uid!=euid -F euid=0 -k privesc
```

> [!note] `auid` 是關鍵欄位 ★★★★
> `auid`（audit UID / loginuid）記錄的是**最初登入的那個人**，即使他之後 `sudo su -` 變成 root，
> `auid` 仍然是他原本的 UID。這是 auditd 最有價值的地方 ——
> **`uid` 會變成 0，但 `auid` 不會**，所以查得到「是誰提權後做的」。
> `auid!=unset`（舊寫法 `auid!=4294967295`）用來排除系統程序（沒有登入來源者）。

#### 查詢：ausearch 與 aureport

```bash
# 依標籤查（最常用）
sudo ausearch -k identity -ts today -i
```

```text
type=SYSCALL msg=audit(2026-09-03 11:04:22.117:889) : arch=x86_64 syscall=openat
  success=yes exit=3 a0=0xffffff9c items=1 ppid=2210 pid=2377 auid=sysadm uid=root
  gid=root euid=root suid=root fsuid=root egid=root sgid=root fsgid=root
  tty=pts0 ses=12 comm=vim exe=/usr/bin/vim key=identity

  inode=131074 dev=fc:01 mode=file,644 ouid=root ogid=root
```

★★★ `-i` 會把數字翻成人看得懂的名字（`auid=sysadm` 而不是 `auid=1000`），一定要加。

```bash
# 查某個人今天做了什麼
sudo ausearch -ua sysadm -ts today -i | grep -E '^type=SYSCALL' | tail -5

# 查某段時間內失敗的登入
sudo ausearch -m USER_LOGIN --success no -ts 09/01/2026 -te 09/03/2026 -i

# 統計報表
sudo aureport --summary
sudo aureport -au -i --summary   # 認證嘗試統計
sudo aureport -k --summary       # 依標籤統計，最快看出哪類事件最多
```

`aureport -k --summary` 的輸出：

```text

===========================

===========================

```

★★★★ 這張表也是判斷「規則有沒有太吵」的依據 —— 某個 key 佔比異常高，通常代表那條規則寫太寬。

#### 效能取捨 ★★★★★

auditd 是**同步的核心層機制**，規則越多，每一次系統呼叫的成本越高。實務上的取捨：

| 做法 | 效能影響 | 建議 |
| --- | --- | --- |
| 監控 `/etc` 下幾十個特定檔案（`-w`） | 極低 ★ | 放心做 |
| 監控整個目錄遞迴（如 `-w /var/www/`） | **高** ★★★★ | 不要用 auditd 做，改用 AIDE 或 Wazuh FIM |
| `-S execve` 全記錄（不加條件） | **極高** ★★★★★ | 一定要加 `-F euid=0`、`-F auid>=1000` 之類的條件收斂 |
| `-S open`／`-S openat` 全記錄 | **災難級** ★★★★★ | 絕對不要，一台正常主機每秒數千次 |
| `-a always,exit -F dir=/` | 災難級 ★★★★★ | 同上 |

判斷有沒有過載，看兩個數字：

```bash
sudo auditctl -s
```

```text
enabled 1
failure 1
pid 1043
rate_limit 0
backlog_limit 16384
lost 0
backlog 34
```

| 欄位 | 意義 | 判定 |
| --- | --- | --- |
| `lost` | 已丟棄的事件數 | ★★★★★ **必須為 0**。不為 0 代表稽核紀錄有缺口，稽核時無法辯解 |
| `backlog` | 目前排隊中的事件 | 長期接近 `backlog_limit` 就要調大或減規則 |

以及磁碟成長速度：

```bash
sudo du -sh /var/log/audit/
sudo ls -lh /var/log/audit/
```

```text
412M    /var/log/audit/
-rw-r----- 1 root adm 8.0M Sep  3 11:20 audit.log
-rw-r----- 1 root adm 8.0M Sep  3 09:44 audit.log.1
```

日誌大小與保留在 `/etc/audit/auditd.conf` 調：

```ini
max_log_file = 32
num_logs = 10
max_log_file_action = ROTATE
space_left = 500
space_left_action = SYSLOG
admin_space_left = 200
admin_space_left_action = SINGLE
disk_full_action = SUSPEND
```

> [!danger] `disk_full_action` 與 `-f 2` 會讓主機停擺 ★★★★★
> - `disk_full_action = HALT` 或 `admin_space_left_action = HALT`：**磁碟滿時直接關機**
> - `-f 2`（failure mode = panic）：稽核子系統出錯時**核心 panic**
>
> 這兩個在高安全等級環境是「正確」設定（寧可停機也不能有稽核缺口），
> 但在一般機關的服務主機上，會把「日誌磁碟滿了」變成「服務全停」。
> **除非有明文要求，否則用 `SUSPEND` 或 `SYSLOG`**，並且把 `/var/log/audit` 的空間納入監控告警
> （見 [[100-01-03-guide-日誌-系統監控與告警]]）。

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> - 規則語法完全相同，路徑同為 `/etc/audit/rules.d/`
> - RHEL 系預設安裝時 `/etc/audit/rules.d/audit.rules` 已有基本內容，**新增規則另開檔案**（如 `10-hardening.rules`），不要直接改預設檔
> - RHEL 系有 `-w /etc/selinux/ -p wa -k MAC-policy` 這條額外的常見規則
> - ★★★ RHEL 的 `augenrules --load` 相同；查詢工具 `ausearch` / `aureport` 完全相同

### 五、AIDE 檔案完整性監控與 Wazuh 的分工 ★★★★

#### AIDE 的設定重點

Debian／Ubuntu 的 AIDE 設定是**組合出來的**：`/etc/aide/aide.conf` 加上 `/etc/aide/aide.conf.d/` 底下一堆片段，由 `update-aide.conf` 產生實際使用的 `/var/lib/aide/aide.conf.autogenerated`。

新增自己要監控的目錄：

```bash
sudo tee /etc/aide/aide.conf.d/99_local_www >/dev/null <<'EOF'
# 監控網站程式碼目錄（只看內容與權限，不追蹤 atime）
/var/www/html   ContentEx
# 上傳目錄變動頻繁，排除
!/var/www/html/uploads
EOF

sudo update-aide.conf
sudo aide.wrapper --update
```

★★★ `--update` 會同時**檢查並產生新資料庫**，輸出裡的差異就是這段期間的變動：

```text
Summary:
  Total number of entries:      182118
  Added entries:                12
  Removed entries:              0
  Changed entries:              3

---------------------------------------------------
Added entries:
---------------------------------------------------
f++++++++++++++++: /var/www/html/admin/tool.php

---------------------------------------------------
Changed entries:
---------------------------------------------------
f   ...    .C... : /etc/ssh/sshd_config
f   ...    .C... : /usr/bin/curl
```

確認這些變動都是預期的之後，才把新資料庫轉正：

```bash
sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db
```

> [!danger] AIDE 資料庫放在本機是有缺陷的 ★★★★★
> 攻擊者取得 root 後，可以**先改檔案、再重建 AIDE 資料庫**，你就完全查不出來。
> 緩解做法（依成本排序）：
> 1. 每次更新資料庫後，把 `sha256sum /var/lib/aide/aide.db` 的值**記錄到別的地方**（工單、另一台機器）
> 2. 把資料庫複製一份到**唯讀掛載或遠端**，比對時用遠端那份
> 3. 直接改用 Wazuh FIM —— 資料存在 manager 上，被入侵的那台機器改不到
>
> ★★★★ 這正是下面「跟 Wazuh 怎麼分工」的核心理由。

#### AIDE vs Wazuh FIM ★★★★

| 面向 | AIDE | Wazuh FIM |
| --- | --- | --- |
| 架構 | 單機、批次 | Agent ＋ 中央 manager |
| 偵測時機 | 你跑 `--check` 的那一刻 | 準即時（有 `whodata` 模式可即時） |
| 基準存放位置 | **本機** ★★★★（可被篡改） | **manager 上**（agent 改不到） |
| 誰改的 | ✗ 只知道檔案變了 | ✓ `whodata` 模式可記錄使用者與程序 |
| 多機管理 | 每台各自為政 | 集中設定、集中告警 |
| 導入成本 | 一個套件 | 要架 manager、部 agent |
| 適合 | 1～5 台、離線環境、無網路的 DMZ 主機 | 5 台以上、需要即時告警 |

> [!tip] 分工建議 ★★★★
> - **有 Wazuh 的環境**：主力用 Wazuh FIM（[[090-08-04-guide-Wazuh-FIM檔案完整性監控]]），
>   AIDE 保留在**最關鍵的一兩台**（如 CA 主機、跳板機）當第二道防線，因為它的資料庫格式完全不同，
>   攻擊者要同時騙過兩套的難度高很多
> - **沒有 Wazuh**：AIDE ＋ auditd 的 `-w` 規則互補 ——
>   auditd 告訴你「誰在什麼時候動了」，AIDE 告訴你「內容變成什麼樣」
> - ★★★ **不要兩套都監控同一批高頻變動目錄**，會製造大量重複告警而讓人麻痺

### 六、稽核證據的產出 ★★★★★

這一段是本篇的核心。稽核員要的**不是「我們有做」，而是「證明給我看」**。

以下針對四個最常被問到的問項，各給一條可直接執行的指令或腳本。

#### 問項 1：帳號覆核 —— 「離職人員的帳號都停用了嗎？」 ★★★★★

```bash
sudo tee /usr/local/sbin/evidence-accounts.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# 產出帳號覆核證據
set -u
echo "帳號覆核證據"
echo "主機：$(hostname -f)"
echo "產生時間：$(date -Is)"
echo "產生指令：$0"
echo "=============================================================="
echo ""
echo "## 一、所有可登入的一般帳號（UID>=1000）"
printf "%-14s %-6s %-18s %-12s %s\n" "帳號" "UID" "Shell" "密碼狀態" "最後登入"
awk -F: '$3>=1000 && $3<65534 {print $1, $3, $7}' /etc/passwd | while read -r u uid sh; do
  st=$(passwd -S "$u" 2>/dev/null | awk '{print $2}')
  case "$st" in
    L) st="鎖定" ;; P) st="有密碼" ;; NP) st="無密碼(危險)" ;; *) st="未知" ;;
  esac
  ll=$(lastlog -u "$u" 2>/dev/null | tail -1 | sed 's/  */ /g' | cut -d' ' -f4-)
  printf "%-14s %-6s %-18s %-12s %s\n" "$u" "$uid" "$sh" "$st" "$ll"
done
echo ""
echo "## 二、90 天以上未登入的帳號（應覆核是否仍需保留）"
lastlog -b 90 2>/dev/null | awk 'NR==1 || $0 !~ /Never logged in/' | head -40
echo ""
echo "## 三、從未登入過的帳號"
lastlog 2>/dev/null | awk '/Never logged in/ {print $1}' | while read -r u; do
  uid=$(id -u "$u" 2>/dev/null) || continue
  [ "$uid" -ge 1000 ] && [ "$uid" -lt 65534 ] && echo "  $u (UID=$uid)"
done
echo ""
echo "## 四、UID=0 的帳號（正常情況下只應有 root）"
awk -F: '$3==0 {print "  "$1}' /etc/passwd
echo ""
echo "## 五、密碼原則（chage）"
for u in $(awk -F: '$3>=1000 && $3<65534 {print $1}' /etc/passwd); do
  echo "--- $u"; chage -l "$u" 2>/dev/null | sed 's/^/    /'
done
EOF
sudo chmod 700 /usr/local/sbin/evidence-accounts.sh
sudo /usr/local/sbin/evidence-accounts.sh
```

輸出（節錄）：

```text
帳號覆核證據
主機：web01.example.gov.tw
產生時間：2026-09-03T13:20:41+08:00
產生指令：/usr/local/sbin/evidence-accounts.sh
==============================================================

## 一、所有可登入的一般帳號（UID>=1000）
帳號           UID    Shell              密碼狀態     最後登入
sysadm         1000   /bin/bash          有密碼       Wed Sep  3 09:02:11 +0800 2026
deploy         1001   /bin/bash          鎖定         Mon Jun 10 14:33:02 +0800 2026
vendor         1005   /bin/bash          有密碼       **Never logged in**

## 四、UID=0 的帳號（正常情況下只應有 root）
  root
```

★★★★★ 這份輸出**同時回答了三個稽核問項**：帳號清單、停用狀態、閒置帳號。而且它是原始輸出、有時間戳、有產生指令，符合證據三要件。

#### 問項 2：修補率 —— 「安全更新都套用了嗎？」 ★★★★

> [!tip] 修補率怎麼算 ★★★★
> 稽核常問「安全更新修補率」。單機的算法：
> **修補率 = 1 −（未套用安全更新數 ÷ 該期間釋出的安全更新總數）**
> 單機拿不到分母，所以實務上改用兩個更好取得的替代指標：
> - **當前未套用安全更新數**（上面第一條）—— 目標是 0
> - **最舊未套用安全更新的天數** —— 目標是不超過修補政策的時限
>
> 完整的修補管理循環與 SLA 定義在 [[090-07-03-guide-資安實踐-弱點與修補管理流程]]。

#### 問項 4：權限最小化 —— 「誰有 root 權限？有沒有超授權？」 ★★★★★

```bash
sudo tee /usr/local/sbin/evidence-privilege.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
set -u
echo "權限最小化證據"
echo "主機：$(hostname -f)"
echo "產生時間：$(date -Is)"
echo "產生指令：$0"
echo "=============================================================="
echo ""
echo "## 一、具備 sudo 權限的帳號"
getent group sudo wheel 2>/dev/null | sed 's/^/  /'
echo ""
echo "## 二、sudo 授權明細（含 NOPASSWD 標示）"
grep -rhv -e '^#' -e '^$' /etc/sudoers /etc/sudoers.d/ 2>/dev/null | sed 's/^/  /'
echo ""
echo "## 三、NOPASSWD 授權（高風險，應逐條說明理由）"
grep -rn 'NOPASSWD' /etc/sudoers /etc/sudoers.d/ 2>/dev/null | sed 's/^/  !! /' || echo "  （無）"
echo ""
echo "## 四、UID=0 帳號"
awk -F: '$3==0 {print "  "$1}' /etc/passwd
echo ""
echo "## 五、SUID / SGID 執行檔（非套件預設者需說明）"
find / -xdev \( -perm -4000 -o -perm -2000 \) -type f -printf '  %m %u:%g %p\n' 2>/dev/null | sort -k3
echo ""
echo "## 六、全域可寫檔案（world-writable，不含 sticky 目錄）"
find / -xdev -type f -perm -0002 -printf '  %m %u:%g %p\n' 2>/dev/null | head -50
echo ""
echo "## 七、無主檔案（帳號已刪但檔案還在）"
find / -xdev \( -nouser -o -nogroup \) -printf '  %u:%g %p\n' 2>/dev/null | head -30
echo ""
echo "## 八、最近 30 天的 sudo 使用紀錄"
if command -v ausearch >/dev/null && [ -r /var/log/audit/audit.log ]; then
  ausearch -k sudo_exec -ts recent -i 2>/dev/null | grep -c '^type=SYSCALL' \
    | xargs -I{} echo "  auditd 記錄的 sudo 執行次數（近期）：{}"
fi
grep -h 'sudo:' /var/log/auth.log 2>/dev/null | grep 'COMMAND=' | tail -20 | sed 's/^/  /'
EOF
sudo chmod 700 /usr/local/sbin/evidence-privilege.sh
sudo /usr/local/sbin/evidence-privilege.sh
```

## 常見錯誤與排錯

| # | 現象 | 原因 | 解法 |
| --- | --- | --- | --- |
| 1 | `etckeeper init` 後 `git` 報 `Please tell me who you are` | root 沒有設 git 身分 | `sudo git config --system user.email "root@$(hostname -f)"` 與 `user.name "etckeeper"`，再重跑 |
| 2 | 漂移報告每天都有差異，全都是 `ss` 那一段 | 腳本沒濾掉 pid/fd，程序重啟就變 | 用本篇腳本裡的 `awk` 版本，只留「協定＋位址＋程式名」 ★★★ |
| 3 | 漂移報告每天都報套件清單變動 | 自動更新每天在裝東西 | 正常現象。把 `07-packages.txt` 改成**只在月檢比對**，或改為只比較「新增／移除的套件名」而不比版本 |
| 4 | `lynis audit system` 卡在某個測試很久不動 | 通常是網路測試在等 timeout，或掃描大檔案系統 | 加 `--quick` 跳過等待較久的測試；或看 `/var/log/lynis.log` 最後一行判斷卡在哪一項 |
| 5 | Lynis 分數每次跑都不一樣 | 用了不同版本（套件版 vs GitHub 版），或有暫時性測試（如可更新套件數） | 固定用同一種來源；比較趨勢時看**同一版本**的資料 ★★★ |
| 6 | `oscap xccdf eval` 回 `Profile ... was not found` | profile ID 抄錯，或該 datastream 沒有這個 profile | 先跑 `oscap info <ds檔>` 看實際有哪些 ID，**不要照抄文件** ★★★★ |
| 7 | `oscap` 回 `Could not open file ... ssg-ubuntu2204-ds.xml` | 沒裝對應的 ssg 套件，或發行版版本對不上 | `ls /usr/share/xml/scap/ssg/content/` 看有哪些；裝 `ssg-debian ssg-debderived` 等 |
| 8 | OpenSCAP 報告一大片 `notapplicable` | 該 profile 針對的版本或角色與本機不符 | 換成對應本機發行版版本的 datastream；`notapplicable` 不算 fail，不必處理 |
| 9 | `systemctl restart auditd` 回 `Operation refused, unit auditd.service may be requested by dependency only` | auditd unit 有 `RefuseManualStop` 保護 | 改用 `sudo service auditd restart`，或只重載規則 `sudo augenrules --load` ★★★ |
| 10 | `augenrules --load` 後 `auditctl -l` 顯示 `No rules` | 規則檔語法錯誤被整份跳過，或前面有 `-e 2` 已鎖定 | 看 `sudo journalctl -u auditd -n 30`；若已 `-e 2` 必須**重開機**才能改規則 ★★★★ |

| 12 | `/var/log/audit` 塞爆，主機變得極慢或直接停 | `auditd.conf` 的 `disk_full_action`／`admin_space_left_action` 設成 HALT 或 SUSPEND | 緊急：清舊 log 檔並 `service auditd restart`；根本解：調 `max_log_file`／`num_logs`，並把該分割區納入監控告警 ★★★★★ |
| 13 | `aide.wrapper --check` 每次都報上千筆變動 | 監控範圍含 `/var/log`、`/proc`、`/tmp` 等本來就一直變的路徑 | 在 `/etc/aide/aide.conf.d/` 加排除規則，重跑 `update-aide.conf` 後重建資料庫 ★★★★ |
| 14 | AIDE 檢查跑到一半 OOM 或吃滿 IO | 監控項目太多（含大量小檔的目錄，如 node_modules） | 排除該類目錄；把 AIDE 排在離峰時段；必要時改用 Wazuh FIM |
| 15 | `aide --check` 回 `Couldn't open file /var/lib/aide/aide.db for reading` | `aideinit` 只產生了 `aide.db.new`，沒有轉正 | `sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db` ★★★ |
| 16 | 改完 `sshd_config` 後 reload，其他人連不進來 | 開了 `PasswordAuthentication no` 但有人還沒放公鑰 | ★★★★★ 用**還沒斷開的那條連線**改回來；預防：改之前先確認所有管理者都有金鑰，並保留一條 console／KVM 通道 |
| 17 | 收緊 umask 後網站上傳功能壞掉 | Web 應用寫出的檔案變成 `600`，其他程序讀不到 | 這是 Lynis 建議的典型副作用。改用**只對互動式登入設 umask**（`/etc/profile.d/`），不要動 `/etc/login.defs` 影響到服務 ★★★★ |
| 18 | 證據包解出來 `sha256sum -c` 全部 FAILED | 打包後又跑了一次腳本覆蓋檔案；或用文字模式傳輸壞了行尾 | 打包後不要再改動；傳輸一律用二進位（scp／sftp），不要複製貼上 |

## 安全性注意事項

### 一、加固本身就是高風險操作 ★★★★★

> [!danger] 三條鐵律
> 1. **一次只改一項**，改完立刻驗證服務仍正常。一次改十項，出事時你分不出是哪一項。
> 2. **改 SSH 之前，先另開一條連線並保留著。** 驗證新連線能進來之後，才關掉舊的那條。
> 3. **絕不在沒有 console／KVM／IPMI 退路的機器上動 SSH、PAM、防火牆預設政策。**
>    遠端主機把自己鎖在外面，等於要開機房或開遠端支援單。

### 二、檢核工具本身的權限風險 ★★★★

| 資產 | 風險 | 防護 |
| --- | --- | --- |
| `/etc/.git` | 含 shadow 雜湊與私鑰的完整歷史 | 權限 `0700 root:root`；★★★★★ **絕不 push 到任何遠端** |
| `/var/lib/aide/aide.db` | 被改掉就等於 FIM 失效 | 權限 `0600`；摘要值外部留存 |
| `/var/lib/baseline/` | 含完整的埠、帳號、sudo 清單 —— 對攻擊者是現成的地圖 | 目錄 `0700 root:root` |
| `/var/log/audit/` | 稽核紀錄本身 | 權限 `0600 root:root`；★★★★ 送一份到集中日誌 |
| 證據包 `.tar.gz` | 交付前存在本機，內含完整組態資訊 | 交付後從主機刪除；傳輸走加密通道 |

### 三、稽核紀錄的完整性 ★★★★★

auditd 最大的弱點是**紀錄存在被稽核的那台機器上**。root 被拿下之後，紀錄可以被刪、被改。

三層防護，依成本排序：

1. ★★★ **送到遠端**：透過 `audisp-remote`（在 `audispd-plugins` 套件裡）或 rsyslog 轉送到集中日誌主機
2. ★★★★ **規則鎖定**：在規則檔最後加 `-e 2`，讓規則變成不可修改，直到重開機為止

   ```bash
   # 加在 /etc/audit/rules.d/ 中排序最後的檔案結尾
   -e 2
   ```

   > [!warning] `-e 2` 的代價 ★★★★
   > 鎖定後**任何規則修改都必須重開機才生效**，包含你自己要調整的時候。
   > 建議：規則穩定運作一段時間後再啟用，並記錄在維運文件上，免得下一個人以為 `augenrules` 壞了。

3. ★★★★★ **集中式 SIEM**：把稽核事件即時送到 Wazuh／SIEM，被入侵的主機改不到 manager 上的資料

### 四、不要把稽核當成監控 ★★★

auditd 記錄「誰做了什麼」，但**它不會告訴你有事發生**。沒有人看的 audit.log 等於沒有。
必須搭配：

- 告警規則（[[100-01-05-guide-監控-監控策略與告警設計]]）
- 或送進 Wazuh 由規則引擎判讀（[[090-08-09-guide-Wazuh-自訂規則與解碼器]]）

### 五、檢核發現異常時的處置分界 ★★★★★

漂移報告或 AIDE 報出「系統執行檔被改動」時，**不要直接修復**。

> [!danger] 疑似入侵時不要動現場
> 看到以下任一種情況，**停止修復動作，改走事件應變流程**：
> - `/usr/bin`、`/usr/sbin` 下的執行檔被改動，但沒有對應的套件升級紀錄
> - 出現不明的 SUID 檔案
> - `auditd` 規則被清空、日誌出現斷層
> - 出現不明帳號，且 `lastlog` 顯示有登入
>
> 直接把檔案改回去會**銷毀跡證**，之後就查不出怎麼進來的、還有沒有其他後門。
> 正確流程見 [[090-07-15-guide-資安實踐-被入侵主機的跡證檢查]] 與 [[090-07-04-guide-資安實踐-資安事件應變流程]]。

### 六、分數不是目的 ★★★★

> [!tip] 給主管報告時的正確講法
> ✗ 「我們的 Lynis 分數是 72 分，業界平均 65 分」—— **沒有意義**，Lynis 官方也不建議把分數當 KPI。
> ✓ 「本季檢核發現 8 項偏差，已修復 6 項、2 項列為例外並附理由；
> 分數由 58 提升至 72，趨勢向上。」—— 這才是稽核與管理層要的。

> sudo etckeeper vcs log -p -1 -- motd
> ```
> 最後一行會印出這次的 commit 訊息、時間、作者，以及 `+本機為測試環境…` 這一行 diff。
> ★★ 重點在於：**commit 訊息要寫得讓半年後的自己看得懂**，最好帶變更單編號。

> [!question]- 練習 2：故意製造漂移並偵測出來 ★★★★
> **題目**：用本篇的 `drift-check.sh` 建立基準，然後刻意做三件事：
> 新增一個帳號、開一個埠、加一條 sudo 授權。跑漂移比對，確認三項都被抓到。
>
> **參考解答**
> ```bash
> # 1. 建立基準
> sudo /usr/local/sbin/drift-check.sh approve
>
> # 2. 製造漂移
> sudo useradd -m -s /bin/bash drifttest
> echo 'drifttest ALL=(ALL) NOPASSWD: /usr/bin/id' | sudo tee /etc/sudoers.d/99-drifttest
> sudo chmod 440 /etc/sudoers.d/99-drifttest
> nohup python3 -m http.server 18080 >/dev/null 2>&1 &
>
> # 3. 偵測
> sudo /usr/local/sbin/drift-check.sh diff
> ```
> 報告中應同時出現：
> ```text
> ### 02-listen.txt
>   + tcp 0.0.0.0:18080 python3
> ### 03-users.txt
>   + drifttest:1002:/bin/bash
> ### 04-sudo.txt
>   + drifttest ALL=(ALL) NOPASSWD: /usr/bin/id
> ```
> **清理**：
> ```bash
> sudo pkill -f 'http.server 18080'
> sudo rm -f /etc/sudoers.d/99-drifttest
> sudo userdel -r drifttest
> sudo /usr/local/sbin/drift-check.sh diff   # 應回到「無漂移」
> ```
> ★★★★★ 注意最後這一步：**修復後要再跑一次比對確認回到基準**，而不是直接 `approve`。

> [!question]- 練習 3：判讀 Lynis 建議並分桶 ★★★★
> **題目**：在測試機跑一次 `lynis audit system`，取出所有 suggestion，
> 挑其中 5 條用「四問法」判斷，寫成 A／B／C 三桶的表格，C 桶要寫例外理由。
>
> **參考解答（範例，實際結果依你的機器而異）**
> ```bash
> sudo lynis audit system
> sudo grep '^suggestion\[\]=' /var/log/lynis-report.dat | cut -d'|' -f1,2 | head -20
> ```
>
> | 建議 | Q1 影響服務 | Q2 需重啟 | Q3 衝突 | Q4 不適用 | 桶 | 理由 |
> | --- | --- | --- | --- | --- | --- | --- |
> | 安裝 debsums | 否 | 否 | 否 | 否 | A | 純檢查工具，零風險 |
> | 安裝 malware scanner | 否 | 否 | 否 | ★ 已有 Wazuh 反惡意 | C | 功能重疊，避免資源浪費（EX-xxx） |
> | 收緊 login.defs umask | ★★★★ 是 | 否 | 否 | 否 | B | 需先測 Web 寫檔權限 |
> | `/var` 獨立分割 | 是 | 是 | 否 | 否 | C | 既有機器無法重分割，列入新機標準（EX-xxx） |
> | 啟用 process accounting | 否 | 否 | 否 | ★ 與 auditd 重疊 | C | 已有 auditd 涵蓋（EX-xxx） |
>
> ★★★★★ 評分重點：**C 桶每一條都必須有理由與例外編號**，不能只寫「不做」。

> [!question]- 練習 4：寫 auditd 規則並查到自己 ★★★★
> **題目**：加一條規則監控 `/etc/hosts` 的寫入與屬性變更，標籤用 `hostsfile`。
> 然後修改該檔案，用 `ausearch` 查出「是哪個 auid 在什麼時候用什麼程式改的」。
>
> **參考解答**
> ```bash
> echo '-w /etc/hosts -p wa -k hostsfile' | sudo tee /etc/audit/rules.d/50-practice.rules
> sudo augenrules --load
> sudo auditctl -l | grep hostsfile
> ```
> ```text
> -w /etc/hosts -p wa -k hostsfile
> ```
> ```bash
> echo "127.0.1.5 practice.local" | sudo tee -a /etc/hosts
> sudo ausearch -k hostsfile -ts recent -i | grep -E 'auid=|comm=|exe='
> ```
> ```text
> ... auid=sysadm uid=root ... comm=tee exe=/usr/bin/tee key=hostsfile
> ```
> ★★★★ 觀察重點：`uid=root` 但 `auid=sysadm` —— 這正是 auditd 的價值，
> 即使提權成 root，仍然查得到原始登入者是誰。
>
> **清理**：
> ```bash
> sudo sed -i '/practice.local/d' /etc/hosts
> sudo rm -f /etc/audit/rules.d/50-practice.rules
> sudo augenrules --load
> ```

> [!question]- 練習 5：產出一份可交付的稽核證據包 ★★★★★
> **題目**：針對「權限最小化」這個稽核問項，產出一份符合證據三要件
> （可重現、有時間戳、未被竄改）的證據，並說明你會怎麼交給稽核員。
>
> **參考解答**
> ```bash
> sudo /usr/local/sbin/evidence-privilege.sh > /tmp/evi-priv-$(date +%Y%m%d).txt
> head -5 /tmp/evi-priv-$(date +%Y%m%d).txt
> sha256sum /tmp/evi-priv-$(date +%Y%m%d).txt
> ```
> 檢查是否符合三要件：
> - **可重現** ✓ —— 檔頭第 4 行寫著「產生指令：/usr/local/sbin/evidence-privilege.sh」，
>   稽核員可以自己跑一次
> - **有時間戳** ✓ —— 檔頭第 3 行的 `date -Is` 輸出，且檔名帶日期
> - **未被竄改** ✓ —— 產生 SHA-256 摘要
>
> **交付方式**：檔案走加密通道（scp／內部檔案系統）給稽核窗口，
> **SHA-256 摘要另外用電子郵件或工單傳送**，讓對方能獨立驗證。
> ★★★★★ 加分回答：同時附上一份「說明頁」，逐項對應到稽核問項編號，
> 但**原始輸出檔一定要保留**，不能只交整理過的說明頁。

> [!question]- 練習 6：AIDE 誤報收斂 ★★★
> **題目**：AIDE 每次檢查都報出 `/var/log` 下數百筆變動。設定排除，讓檢查結果乾淨。
>
> **參考解答**
> ```bash
> sudo tee /etc/aide/aide.conf.d/99_exclude_logs >/dev/null <<'EOF'
> # 日誌本來就一直變，交由 logrotate 與集中日誌管理，不納入 FIM
> !/var/log/.*
> # 但保留 auditd 目錄的「存在性」監控（不比對內容）
> /var/log/audit$ PERMS
> EOF
> sudo update-aide.conf
> sudo aide.wrapper --update
> sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db
> sudo aide.wrapper --check
> ```
> ```text
> AIDE found NO differences between database and filesystem. Looks okay!!
> ```
> ★★★★ 思考題：排除 `/var/log` 之後，「有人刪日誌」這件事誰來抓？
> 答案：**auditd 的 `-w /var/log/audit -p wa` 規則**，以及集中日誌主機上「該主機停止送 log」的告警。
> 排除一個監控手段時，一定要確認**另一個手段有補上**。

## 小測驗

**Q1.**（選擇）以下哪一項**最能**代表「設定漂移」的典型成因？
A. 攻擊者植入後門
B. 廠商施工時順手改了設定且沒有記錄
C. 硬碟出現壞軌
D. 套件庫伺服器離線

**Q2.**（是非）漂移偵測腳本報出差異時，如果確認是核可過的變更，應該立刻執行 `approve` 更新基準。

**Q3.**（簡答）Lynis 的 `hardening index` 適合當成資安 KPI 嗎？為什麼？

**Q4.**（這行指令會發生什麼）
```bash
sudo oscap xccdf generate fix --profile <某 profile> --fix-type bash \
  --output /root/fix.sh results.xml && sudo bash /root/fix.sh
```

**Q5.**（選擇）auditd 規則 `-a always,exit -F arch=b64 -S execve -C uid!=euid -F euid=0 -k privesc` 的用意是？
A. 記錄所有程式執行
B. 記錄所有 root 執行的程式
C. 記錄「執行時實際 UID 與有效 UID 不同、且有效 UID 為 0」的執行，也就是提權執行
D. 阻擋提權行為

**Q6.**（簡答）為什麼 auditd 的 `auid` 欄位比 `uid` 更有稽核價值？

**Q7.**（是非）`auditctl -s` 輸出中 `lost 143`，代表有 143 條規則載入失敗。

**Q8.**（選擇）Lynis 與 OpenSCAP 最主要的定位差異是？
A. Lynis 是商業軟體、OpenSCAP 免費
B. Lynis 給的是自訂最佳實務的分數與建議，OpenSCAP 給的是對照正式基準的逐條 pass/fail 報告
C. Lynis 只能跑 Ubuntu、OpenSCAP 只能跑 RHEL
D. 兩者完全相同，選一個用即可

**Q9.**（簡答）AIDE 的資料庫存在被檢查的那台機器上，這造成什麼安全弱點？至少寫出兩種緩解做法。

**Q10.**（簡答）一份「能交出去」的稽核證據，必須具備哪三個要件？各舉一個技術上的做法。

> [!question]- 測驗答案
> **A1. B。** 漂移絕大多數來自正常維運行為的累積（廠商施工、臨時開埠、緊急放權），
> 而不是惡意攻擊。A 是資安事件，C、D 與組態無關。
> → 見「觀念說明 → 一、設定漂移是什麼」的漂移來源表。
>
> **A2. ✗ 錯。** 順序反了。正確流程是：**先確認這是核可過的變更（有變更單）**，
> 才執行 `approve`；若是未授權改動，**要先復原，不要 approve**。
> 最危險的習慣是「報告太吵就 approve 讓它安靜」，那等於把漏洞收編進基準。
> → 見「進階應用 → 一、漂移偵測腳本」的核可流程 callout。
>
> **A3. 不適合。** 分數受 Lynis 版本、機器角色、暫時性因素（如當下可更新套件數）影響，
> 不同機器之間也不可比。★★★★ 有價值的用法是**看同一台機器、同一版本工具的趨勢**，
> 以及「發現幾項、修了幾項、幾項列例外」這種可驗證的數字。
> → 見「安全性注意事項 → 六、分數不是目的」。
>
> **A4. 極度危險，不要這樣做。** ★★★★★ `generate fix` 產出的腳本會一次套用該 profile 的**全部**項目，
> 包含改 PAM、SSH、掛載選項、停用服務，在有正式服務的機器上等於自殺，而且沒有回退機制。
> 正確用法是把它當「每一條該怎麼改」的參考手冊，人工挑出要做的段落，走變更流程逐項套用並驗證。
> → 見「進階應用 → 三、OpenSCAP」的 danger callout。
>
> **A5. C。** `-C uid!=euid` 比較兩個欄位是否不同，`-F euid=0` 限定有效 UID 為 root，
> 合起來就是「一般使用者透過 sudo/SUID 提權後執行程式」的情形。
> ★★★★ auditd **只記錄不阻擋**，所以 D 錯；A、B 的範圍太寬，不加條件會產生災難級的事件量。
> → 見「進階應用 → 四、auditd 實務」的規則集與效能取捨表。
>
> **A6. 因為 `auid` 記錄的是「最初登入的那個人」，而且 `sudo su -` 之後也不會改變。**
> `uid` 在提權後會變成 0，看不出是誰；`auid` 仍然是原本登入者的 UID，
> 所以能回答稽核最關心的問題：「是誰做的」。
> → 見「進階應用 → 四、auditd 實務」的 `auid` note。
>
> **A7. ✗ 錯。** `lost` 是**因為緩衝區滿而被丟棄的稽核事件數**，不是規則載入失敗。
> ★★★★★ 它不為 0 代表稽核紀錄有缺口，稽核時無法辯解，要靠加 `-F` 條件收斂規則、
> 調大 `-b`、或改善磁碟效能來解決。規則載入失敗要看 `journalctl -u auditd`。
> → 見「進階應用 → 四、auditd 實務」的效能取捨段落。
>
> **A8. B。** Lynis 依據自己整理的最佳實務，輸出分數與建議，找得比較廣但**沒有可對照的官方條號**；
> OpenSCAP 依據正式發布的基準（CIS／STIG／TWGCB 改寫），輸出逐條 pass/fail 的標準化報告，
> ★★★★ **對稽核的效力強得多**。兩者可以並存：平時 Lynis 看趨勢，稽核前 OpenSCAP 產報告。
> → 見「觀念說明 → 三、三種檢核工具的定位」與「進階應用 → 三」的對照表。
>
> **A9. 弱點：** 攻擊者取得 root 後可以「先改檔案、再用 `aide --update` 重建資料庫」，
> 讓後續檢查完全看不出異常，FIM 形同虛設。
> **緩解（任兩種即可）：**
> (1) 每次更新資料庫後把 `sha256sum` 記到別的地方（工單、另一台機器）；
> (2) 資料庫複製到唯讀掛載或遠端，比對時用遠端那份；
> (3) 改用 Wazuh FIM，基準資料存在 manager 上，被入侵的 agent 改不到。
> → 見「進階應用 → 五、AIDE」的 danger callout 與 AIDE vs Wazuh 對照表。
>
> **A10. 三要件：可重現、有時間戳、未被竄改。**
> - **可重現**：證據檔頭寫上「產生指令」，稽核員可自己跑一次得到相同結果
> - **有時間戳**：檔名帶日期，內文第一段輸出 `date -Is`
> - **未被竄改**：打包後算 `sha256sum`，摘要與檔案分開傳遞讓對方獨立驗證
>
> ★★★★★ 常見失分：交出沒有指令、沒有日期、Word 排版過的表格 ——
> 稽核員無法驗證，只能當成「聲明」而非證據。**原始輸出永遠比整理過的表格有價值。**
> → 見「觀念說明 → 四、稽核證據的三個要件」與「進階應用 → 六、稽核證據的產出」。
