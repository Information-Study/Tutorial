## 是非題（50 題）

Q1. 動防火牆或 sshd 設定之前，要保留一條已經連上、而且絕對不關閉的 SSH session；因為已建立的連線走 conntrack 的 `ESTABLISHED`，不受新規則影響，所以它在你改壞規則之後仍然活著。

Q2. 加固時設了 `AllowGroups sshusers`，要把管理者加進該群組必須用 `usermod -aG sshusers <帳號>`；漏掉 `a` 會把他原有的附加群組全部清掉。

Q3. `systemctl disable --now <服務>` 之後，那個埠仍然可能是開著的，因為有對應的 `.socket` 單元在監聽，被連線時會把 service 拉起來。

Q4. 「停用不需要的核心模組」是通用的加固建議，所以在 Ubuntu 上把 `squashfs` 加進 `/etc/modprobe.d/` 的黑名單是安全的做法。

Q5. `net.ipv4.ip_forward = 0` 是通用加固項目，任何伺服器都應該設，設了不會有副作用。

Q6. `auditd.conf` 的 `admin_space_left_action = halt` 意思是：當 `/var/log` 剩餘空間低於門檻時，主機會直接停機 —— 這會讓「日誌寫爆」變成「機器自己關機」。

Q7. Ubuntu 23.10 以後預設不安裝 rsyslog，`/var/log/auth.log` 可能根本不存在，這時要改用 `journalctl -t sshd` 之類的方式查登入紀錄。

Q8. `sudo ufw enable` 會立刻套用 `default deny incoming`，如果事前沒有放行 SSH，你手上這條連線之外的所有新連線都會被擋掉，等於把自己鎖在外面。

Q9. ufw 的規則是由上往下逐條比對、**第一個匹配的動作立刻生效**，所以前面若有一條廣泛的 `deny`，後面再加多少 `allow` 都不會被用到。

Q10. 承上題，發現特例規則被前面的 deny 吃掉時，正確做法是在後面再加一條更明確的 allow，ufw 會自動判斷哪一條比較精確。

Q11. Docker 發布的埠（`-p 8080:80`）會受到 ufw 使用者規則的管制，因為所有進入主機的封包都會經過 ufw 的 INPUT 鏈。

Q12. `ufw limit 22/tcp` 已經是完整的暴力破解防護，設了之後就不需要再裝 Fail2ban。

Q13. 對網際網路的規則建議用 `deny`（靜默丟棄）而不是 `reject`，因為 `reject` 會明確回應，等於告訴掃描者「這台主機存在」。

Q14. `sudo ufw status` 顯示 `Status: active`，就足以保證重開機之後規則還會在。

Q15. `sudo ufw --dry-run allow ...` 只會印出「這條指令會產生什麼規則」，不會真的套用，適合在正式機動手前先確認。

Q16. nftables 允許多個 base chain 掛在同一個 hook 上，而且**全部都會執行**；所以你的 chain 寫了 `accept`，另一個 chain（ufw 或 Docker 的）寫了 `drop`，封包一樣會被丟掉。

Q17. 用 `nft add rule ...` 在指令列加的規則，會自動寫進 `/etc/nftables.conf`，重開機後仍然存在。

Q18. input chain 漏掉 `ct state established,related accept` 的典型症狀是：主機「發得出去、收不回來」—— DNS 不通、`apt` 卡住、監控斷線。

Q19. `sudo nft -c -f /etc/nftables.conf` 只檢查語法、不會套用規則，是套用前必跑的一步。

Q20. nftables 的 set 若要放入 CIDR 網段，宣告時必須加上 `flags interval`，否則加入時會回 `Invalid argument`。

Q21. 在同時有 nftables 原生規則與 iptables 相容層規則的機器上，`iptables -S` 看到的就是完整的真相。

Q22. 一個 `policy drop` 的 base chain **從建立的那一刻就開始丟包**，所以規則要先寫完整份、檢查過，再一次原子套用，不能一條一條慢慢下。

Q23. firewalld 的 runtime 與 permanent 是兩份獨立的設定：runtime 在記憶體、立刻生效、重開就沒；permanent 在磁碟、要 reload 或重開才會生效。

Q24. `sudo firewall-cmd --permanent --add-service=http` 回了 `success`，就代表 http 服務現在已經可以連了。

Q25. 規則加在一個沒有綁定任何介面、也沒有綁定任何來源的 zone 裡，等於完全沒有加 —— 因為那個 zone 不在 active 清單中。

Q26. firewalld 判斷一個封包屬於哪個 zone 的順序是「來源綁定 → 介面綁定 → default zone」，來源綁定永遠優先。

Q27. `--timeout=1800` 可以搭配 `--permanent` 使用，用來建立一條「三十分鐘後自動從磁碟設定中消失」的規則。

Q28. 設定了埠轉發（forward-port）之後客戶端連線一直 hang 到 timeout，常見原因是少了 `--add-masquerade`，回程封包的來源 IP 不對而被丟棄。

Q29. Fail2ban 的 `banaction` 選錯時（例如環境是 ufw 卻用了 `iptables-multiport`），啟動會失敗並印出明確的錯誤訊息，所以不容易漏掉。

Q30. Fail2ban 的設定應該全部寫在 `/etc/fail2ban/jail.local`，不要去改 `jail.conf`，因為 `jail.conf` 會被套件更新覆蓋。

Q31. `ignoreip` 應該把管理網段與**機關對外的 NAT 出口 IP** 都寫進去；漏掉後者的典型災難是「一個同事打錯密碼，全機關一起連不上」。

Q32. Fail2ban 設定得夠嚴格的話，可以有效擋住從大量不同 IP 發起的分散式暴力破解。

Q33. `fail2ban-client status sshd` 的 `Total failed` 若是 0，代表問題在前半段（filter 沒匹配到、日誌路徑錯、backend 錯），而不是 action 那一側。

Q34. 在 `/etc/fail2ban/filter.d/sshd.local` 裡寫 `failregex`，內容會**附加**到 `sshd.conf` 原有的規則後面，原本抓得到的還是抓得到。

Q35. `dbpurgeage` 若小於最大的 `bantime`，重啟 Fail2ban 之後封鎖名單會變空，`bantime.increment` 的累犯計數也會歸零。

Q36. 管理平面（SSH、BMC、管理介面）與服務平面（對使用者提供服務的埠）應該在網路上分開，管理平面只從特定網段或跳板機可達。

Q37. 帶外管理介面（iDRAC／iLO／IPMI）只要設定夠強的密碼並開啟 HTTPS，就可以安全地開放到網際網路上供廠商遠端支援使用。

Q38. BMC 放在獨立管理網段、而且**不設預設路由**是刻意的設計；因此它收不到告警信、時間也同步不到是預期行為，要改由監控主機主動輪詢。

Q39. 廠商專案結束時執行 `usermod -L vendor01` 把密碼鎖起來，就足以確保該廠商再也登不進來。

Q40. `ssh -J bastion target` 會對跳板機與目標主機**各自認證一次**，所以目標主機上也必須有你的公鑰。

Q41. `sudo sshd -T` 會印出 sshd 實際生效的完整設定（把所有 include 與預設值展開），懷疑設定沒吃到時應該用它，而不是去 `grep` 設定檔猜。

Q42. 服務回報 `Permission denied`，但 `ls -l` 看起來權限完全正確、甚至程序是以 root 執行的 —— 這種情況八成是 SELinux 或 AppArmor 擋的，不是 DAC 權限問題。

Q43. 加固過程中如果 SELinux 造成困擾，把 `/etc/selinux/config` 改成 `disabled` 是一個安全的暫時做法，之後隨時可以改回 `enforcing`。

Q44. 用 `chcon -t httpd_sys_content_t /data/www -R` 把標籤改好之後，這個修正是永久的，不會被 `restorecon` 或套件更新還原。

Q45. AppArmor 的規則 `/data/www/** r,` 並不涵蓋 `/data/www/` 這個目錄本身，所以要能列目錄還必須另外加上結尾有斜線的那一條。

Q46. AppArmor 的自訂規則應該寫在 `/etc/apparmor.d/local/` 底下對應的檔案，而不是直接改主 profile，否則套件更新時會被覆蓋。

Q47. 服務要監聽一個非標準埠而在 SELinux 環境下 bind 失敗時，正確做法是用 `semanage port -a -t <型別> -p tcp <埠>` 把該埠加進對應的埠型別。

Q48. 設定漂移的主要來源是「有人手動改了但沒記錄」「緊急處置改完忘了回退」「自動更新換掉了設定檔」這三種，而不是有人惡意破壞。

Q49. Lynis 的 `Hardening index` 是絕對指標，分數越高代表越安全，因此應該以拿到滿分為目標，並拿自己的分數去和其他機器比較。

Q50. 稽核證據的要求是「證明給我看」：光說「我們有設定」不算數，要有**指令輸出、執行時間、執行者**三件齊備才構成證據。

## 選擇題（50 題）

Q51. 一台全新的對外 VPS 要開始做初始安全設定。下列哪一組是動手前最該完成的準備？
(A) 先把 `PermitRootLogin` 改成 yes 以免失聯 (B) 先把防火牆整個關掉，改完再開回來 (C) 確認自己會用該主機的 console／Serial Console、保留一條不關的 SSH session、並備份整份 `/etc` (D) 先把 SSH 改到高位埠，攻擊者就找不到管理埠了

Q52. 你已經 `systemctl disable --now cups.service`，但 `ss -tlnp` 顯示 631 埠還是有東西在聽。最可能的原因與處置是？
(A) 需要重開機才會生效 (B) 有對應的 `.socket` 單元在監聽，被連線時會拉起 service；要把 `.socket` 一起 `disable --now`，必要時 `mask` (C) `ss` 的輸出有快取，重跑一次就好 (D) 該服務被別的套件相依，無法停用

Q53. 一台 Docker 宿主套用加固腳本後，所有容器都連不出去。最可能的元凶是哪一項？
(A) `net.ipv4.conf.all.rp_filter = 1` (B) `/tmp` 掛了 `noexec` (C) `net.ipv4.ip_forward = 0` (D) `kernel.dmesg_restrict = 1`

Q54. 一台 Ubuntu 主機加固並重開機後，`snap` 指令全壞、`certbot` 起不來。最該檢查什麼？
(A) `/etc/sysctl.d/` 裡的網路參數 (B) `/etc/modprobe.d/` 裡有沒有把 `squashfs` 加進黑名單 (C) `/etc/fstab` 的 `nosuid` 選項 (D) AppArmor profile 是不是被切成 enforce

Q55. 一台有兩張網卡的機器，加固後某些連線莫名逾時、而且是單向不通。最可能的原因與處置是？
(A) `rp_filter = 1` 遇到不對稱路由把回程封包丟了；改成 `2`（loose）或 0，改用防火牆補 (B) MTU 設錯，改成 1500 (C) 兩張網卡的 IP 衝突 (D) 需要開啟 `ip_forward`

Q56. 某台機器凌晨自己關機，`/var/log/audit/audit.log` 停在關機前那一刻。最可能的原因是？
(A) 硬體過熱保護 (B) `unattended-upgrades` 的自動重開機 (C) `auditd.conf` 的 `admin_space_left_action = halt`，`/var/log` 空間耗盡而觸發 (D) OOM Killer 殺掉了 systemd

Q57. 加固時要關閉一個你不認識的服務。動手前最該做的一件事是？
(A) 直接關掉，壞了再開回來 (B) `journalctl -u <服務> --since "7 days ago"` 看它過去七天有沒有真的在工作，並對照基準清單 (C) 看它現在有沒有連線就好 (D) 先在 Google 查那個服務名稱

Q58. `sudo ufw status numbered` 顯示 `[1] 3306/tcp DENY IN Anywhere`、`[2] 3306/tcp ALLOW IN 192.168.10.0/24`。應用網段仍然連不到資料庫，正確處置是？
(A) 把第 2 條再加一次，讓它權重變高 (B) 重跑 `ufw reload` 讓 ufw 重新排序 (C) 刪掉第 2 條，用 `sudo ufw insert 1 allow from 192.168.10.0/24 to any port 3306 proto tcp` 把特例插到最前面 (D) 改用 `ufw limit` 取代 `allow`

Q59. `sudo ufw status` 只顯示允許 22 與 80，但同事回報從網際網路上連得到容器的 8080。最正確的解讀是？
(A) ufw 規則沒有 reload (B) Docker 直接往 `nat` 表與 `FORWARD` 鏈寫規則，ufw 的使用者規則在 `INPUT` 鏈，管不到容器發布埠 (C) `ufw status` 的輸出不完整，要看 `verbose` (D) 8080 是 ufw 的預設允許埠

Q60. 承上題，你要立刻降低風險。下列哪個做法最乾淨？
(A) `ufw deny 8080/tcp` (B) 把容器發布改成 `-p 127.0.0.1:8080:80`，對外一律走反向代理 (C) 把 Docker 服務停掉 (D) 在 `before.rules` 最前面加一條 drop

Q61. 從外部連某個埠得到的是 `Connection refused` 而不是逾時。這代表什麼？
(A) 封包被防火牆靜默丟棄了 (B) 封包**有到**這台機器，但那個埠沒有服務在聽（或規則動作是 reject）；要先查 `ss -tlnp` 而不是查防火牆 (C) 路由不通 (D) DNS 解析失敗

Q62. 服務在本機 `curl 127.0.0.1:3306` 通、從外部一律不通，防火牆規則看起來也正確。`ss -tlnp` 顯示 `127.0.0.1:3306`。正確判斷是？
(A) 防火牆規則順序錯了 (B) 需要開 IPv6 規則 (C) 這不是防火牆問題，服務綁在 loopback，要去改應用程式的 `bind-address` (D) conntrack 表滿了

Q63. 遠端主機要第一次啟用 ufw。下列哪一組步驟最不會把自己鎖在外面？
(A) `ufw default deny incoming` → `ufw enable` → 再補 SSH 規則 (B) 先排 `echo "/usr/sbin/ufw --force disable" | sudo at now + 10 minutes` → 確認 sshd 實際埠 → `ufw allow` 該埠 → `ufw show added` 確認 → 才 `ufw enable` (C) 直接 `ufw enable`，斷了再從 console 進去 (D) `ufw default allow incoming` → `ufw enable` → 之後再慢慢收

Q64. 要依號碼刪掉 ufw 的第 3、5、7 條規則。正確做法是？
(A) 依 3、5、7 的順序刪 (B) 從大號碼往小號碼刪（7 → 5 → 3），每刪一條重看一次 `numbered`，因為刪除會讓後面的號碼往前位移 (C) 一次寫 `ufw delete 3 5 7` (D) 先 `ufw reset` 再全部重加

Q65. 專案用 `sudo ufw allow 'Nginx Full'` 開了埠，某次 Nginx 升級後 HTTPS 突然不通。最合理的解釋與長期做法是？
(A) 升級把規則刪掉了，重新 enable 即可 (B) profile 的內容改了，但既有規則不會跟著變；正式環境建議直接寫埠號（`allow 80/tcp`、`allow 443/tcp`）不要依賴 profile (C) `ufw app update` 會自動同步，不必處理 (D) 這是 IPv6 規則沒加

Q66. 你在 nftables 裡明明寫了 `tcp dport 8080 accept`，封包還是不通。`sudo nft list ruleset | grep -c 'type filter hook input'` 回 `2`。最正確的判斷是？
(A) 規則寫在錯的 table，要換成 `ip` family (B) 有兩個 base chain 掛在同一個 input hook 上、兩個都會執行，另一個把封包 drop 了；一台機器只能有一個防火牆負責人 (C) counter 沒開所以規則沒生效 (D) 需要 `nft flush ruleset` 後重載

Q67. 要把一份新的 nftables 規則套到正式機。下列流程何者最安全？
(A) 用 `nft add rule` 一條一條下，邊下邊測 (B) 直接 `nft -f /etc/nftables.conf` (C) 排好 `at` 自動還原 → 規則寫成檔案 → `nft -c -f` 檢查語法 → `nft -f` 原子套用 → 從外部實測 → 重開機驗證 (D) 先 `nft flush ruleset` 清空，再慢慢加

Q68. 套用自寫的 nftables 規則後，主機「網路壞了」：DNS 不通、`apt update` 卡住、監控斷線，但 SSH 進得去。最可能漏了哪一條？
(A) `iif lo accept` (B) `ct state established,related accept`（放在 loopback 之後、所有 drop 之前） (C) `tcp dport 22 accept` (D) `policy accept`

Q69. 把一份威脅情資的 CIDR 清單加進 nftables set 時回 `Error: Could not process rule: Invalid argument`。原因是？
(A) set 的型別要用 `ipv4_addr` 以外的型別 (B) set 宣告時沒有加 `flags interval`，無法容納網段 (C) 清單裡有 IPv6 位址 (D) set 的元素數量超過上限

Q70. 你想確認某條 nftables 規則到底有沒有被命中。最直接的方法是？
(A) 看 `journalctl` 有沒有 drop 紀錄 (B) `sudo nft reset counters` 歸零後重打流量，再看 `nft list ruleset` 裡該規則的 `counter packets` 有沒有增加 (C) `iptables -L -v` (D) `tcpdump` 抓包就夠了

Q71. 一台手寫 nftables 的機器，規則昨天都在、今天重開機後全沒了。最該檢查哪兩件事？
(A) `systemctl is-enabled nftables` 是不是 enabled，以及規則有沒有真的寫進 `/etc/nftables.conf` (B) conntrack 表大小與 `net.netfilter` 參數 (C) 磁碟是不是滿了 (D) 是不是有人手動 `nft flush ruleset`

Q72. 封鎖清單累積到幾千筆之後主機開始吃 CPU、網路變慢。最正確的解讀與處置是？
(A) 主機硬體不夠力，該擴充 (B) 傳統 `iptables-multiport` 每個 IP 一條規則、線性比對；改用 nftables 的 set（`nftables-multiport`）或 `firewallcmd-ipset` 做集合比對 (C) 把 `bantime` 調短，讓清單不要太長就好 (D) 改用 `reject` 取代 `drop` 可以減少負擔

Q73. 你下了 `sudo firewall-cmd --permanent --add-service=http`，回 `success`，但服務仍然連不到。最該做的下一步是？
(A) 重開機 (B) `sudo firewall-cmd --reload`，讓 permanent 的內容載入 runtime (C) 再下一次不帶 `--permanent` 的版本，然後就不必管 permanent 了 (D) 檢查 `FirewallBackend` 設定

Q74. 你把資料庫的規則加進了 `internal` zone，`--permanent --list-all --zone=internal` 也看得到，但完全沒有作用。最可能的原因是？
(A) `internal` zone 的 target 設成了 `DROP` (B) 該 zone 沒有綁定任何介面或來源，不在 `--get-active-zones` 清單中，等於沒有被使用 (C) `internal` 是保留 zone 不能自訂 (D) 需要重啟 firewalld 才會讀 zone

Q75. 你用 `firewall-cmd --zone=internal --change-interface=ens224` 綁好了介面，重開機或 `nmcli con up` 之後又跳回 `public`。正確處置是？
(A) 加上 `--permanent` 再做一次就好 (B) NetworkManager 的 `connection.zone` 才是權威；用 `nmcli connection modify <連線> connection.zone internal` 並 `nmcli connection up` (C) 把 default zone 改成 internal (D) 停用 NetworkManager

Q76. 你剛把 `public` zone 的 ssh 服務移除，用**手上這條已連線的 SSH session** 測試發現「還是通的」，於是判定規則沒生效。這個判斷錯在哪？
(A) firewalld 需要 reload 才會生效，所以確實沒生效 (B) 已建立的連線走 conntrack 的 `ESTABLISHED`，不受新規則影響；一定要用**新開的連線**測試 (C) ssh 服務移除只影響 IPv6 (D) `--list-all` 的輸出有延遲

Q77. 設好埠轉發之後，客戶端連線一直 hang 到 timeout。最可能的原因是？
(A) 目標服務沒起來 (B) 少了 `--add-masquerade`，回程封包的來源 IP 不對而被丟棄；同時要確認 `net.ipv4.ip_forward=1` (C) rich rule 的順序寫錯 (D) zone 的 target 設成 `ACCEPT`

Q78. `firewall-cmd --runtime-to-permanent` 之後，permanent 設定裡多出一些你沒印象的規則。最正確的解讀是？
(A) 這是 bug，重新 reload 就會消失 (B) 它是**整包快照**，會把 `--timeout` 的臨時規則也一起存進去；存完應立刻 `--permanent --list-all-zones` 對一遍並刪掉不該存在的 (C) 那些是 firewalld 的內建規則，不用理 (D) 是別的服務（如 libvirt）加的，無法移除

Q79. `fail2ban-client status sshd` 顯示 `Currently banned: 37`，但被封的來源照樣連得進來。第一個該查什麼？
(A) `maxretry` 是不是設太高 (B) 去**防火牆那一側**確認規則真的存在（`nft list ruleset | grep f2b`／`ufw status numbered`／`iptables -L f2b-sshd`）；沒有規則就代表 `banaction` 選錯了 (C) 重啟 fail2ban 服務 (D) 把 `bantime` 調長

Q80. 一台 Ubuntu 24.04 上 Fail2ban 服務有在跑，但 `Total failed` 一直是 0，日誌裡有 `Have not found any log file for sshd jail`。最可能的原因與解法是？
(A) sshd 沒有在記錄失敗登入 (B) 系統沒裝 rsyslog，`/var/log/auth.log` 不存在；在 `jail.local` 加 `backend = systemd`，或安裝 rsyslog (C) filter 的正則寫錯 (D) `ignoreip` 把所有來源都吃掉了

Q81. 用 `fail2ban-regex` 測試自訂 filter 時，必須確認哪兩個數字都大於 0？
(A) `Lines` 與 `Ignored` (B) `Failregex` 匹配數與 `Date template hits` (C) `Missed` 與 `Matched` (D) `Total failed` 與 `Total banned`

Q82. 某天早上全機關的人（包括你）同時連不上某台主機，連線是逾時。最該優先確認的是？
(A) 主機是不是當機了 (B) 機關對外的 NAT 出口 IP 是不是被 Fail2ban 封了（`fail2ban-client status sshd` 的 Banned IP list）——因為所有人共用同一個來源 IP (C) 交換器是不是壞了 (D) DNS 是不是掛了

Q83. 你（透過 console）要把誤封的管理 IP 解開，並且避免再發生。正確的組合是？
(A) `systemctl restart fail2ban` 就會清空封鎖 (B) `fail2ban-client set sshd unbanip <IP>` 解封，並把**管理網段**（不是單一 IP）寫進 `ignoreip` 後 `fail2ban-client -t` 驗證再 reload (C) 把 `bantime` 設成 0 (D) 把 sshd jail 停用

Q84. 關於 Fail2ban 的設定檔，下列敘述何者正確？
(A) 直接改 `jail.conf` 最方便，反正 `jail.local` 只是備份 (B) 設定寫在 `jail.local`；`filter.d/*.local` 的 `failregex` 會**整組取代** `.conf` 的，要保留原規則必須在第一行加 `%(known/failregex)s` (C) `.local` 只能覆寫 `[DEFAULT]`，個別 jail 必須改 `.conf` (D) 改完不需要驗證，restart 失敗會自動回退

Q85. `maxretry = 5`、`findtime = 10m`、`bantime = 1h`。測試時你在半小時內打錯了八次密碼，卻沒有被封鎖。最合理的解釋是？
(A) `bantime` 太短 (B) 這八次沒有在任何一個 10 分鐘的窗口內累積到 5 次；門檻的意思是「在 `findtime` 內達到 `maxretry` 次」 (C) `maxretry` 要設成 8 才會觸發 (D) Fail2ban 只計算成功登入

Q86. `ssh -J bastion target` 回 `channel 0: open failed: administratively prohibited`。最可能的原因是？
(A) 目標主機沒有你的公鑰 (B) 跳板機的 `PermitOpen` 白名單沒包含這個目標，或 `AllowTcpForwarding no`；用 `sudo sshd -T | grep -i permitopen` 確認生效值 (C) 跳板機的防火牆擋了 22 埠 (D) 你的 SSH 客戶端版本太舊

Q87. 廠商專案結束，要確實關掉他的遠端存取。下列哪一組最完整？
(A) `usermod -L vendor01` (B) 改掉他的密碼 (C) `chage -E 0` 讓帳號到期 ＋ 清空 `~/.ssh/authorized_keys` ＋ `pkill -KILL -u` 踢掉現有 session，並檢查有沒有留下無人值守存取工具與排程 (D) 把他的帳號從 `sudoers` 移除

Q88. 跳板機加了 TOTP 之後，原本用金鑰登入的人全部進不去。最可能的原因是？
(A) TOTP 與金鑰互斥，只能二選一 (B) `AuthenticationMethods publickey,keyboard-interactive` 要求**兩者都要通過**，而部分帳號還沒有 `~/.google_authenticator`；先掛回 `nullok`，等所有人都設定好再移除 (C) 跳板機時間跑掉了 (D) `PubkeyAuthentication` 被自動關閉

Q89. 關於帶外管理（BMC／iDRAC／iLO）的放置，下列何者正確？
(A) 放在服務網段，方便廠商直接連 (B) 對網際網路開放但限制來源 IP 即可 (C) 放在獨立管理網段、不設預設路由、只能從跳板機到達；因為它繞過作業系統的所有防護，而且韌體更新頻率遠低於 OS (D) 與伺服器的業務網卡共用同一個 IP 即可

Q90. 跳板機啟用全程側錄之後，某天所有人都登不進去了。最可能的原因與預防是？
(A) 側錄程式當掉；改用別的工具 (B) `/var/log/sessions` 沒有輪替與容量上限，磁碟被塞爆導致無法登入；要獨立分割或設 quota、加 logrotate、設磁碟使用率告警 (C) 側錄檔權限設錯 (D) 側錄會讓 sshd 拒絕新連線，屬正常行為

Q91. 集中日誌主機收不到跳板機送來的日誌。最有效率的排查是？
(A) 重裝 rsyslog (B) 收端 `ss -lntp | grep 514` 確認有在監聽，發端 `logger -p auth.info test` 產生一筆測試訊息後兩邊都查，同時確認防火牆沒擋 514 (C) 直接看跳板機的 `/var/log/syslog` (D) 把日誌改成用 SCP 每小時拉一次

Q92. Rocky 9 上 nginx 以 root 執行卻回 `bind() to 0.0.0.0:8081 failed (13: Permission denied)`。最正確的處置是？
(A) `chmod 777 /usr/sbin/nginx` (B) 換到 80 埠就好 (C) `sudo semanage port -a -t http_port_t -p tcp 8081` 把該埠加進 SELinux 的 http 埠型別 (D) `setenforce 0` 然後就這樣放著

Q93. 反向代理回 502，錯誤日誌是 `connect() to 127.0.0.1:9000 failed (13: Permission denied) while connecting to upstream`。最正確的處置是？
(A) 檢查 PHP-FPM 的 socket 權限 (B) 這是 SELinux 布林值：`sudo setsebool -P httpd_can_network_connect on`（只連本機資料庫時可用範圍更小的 `httpd_can_network_connect_db`） (C) 把 nginx 改用 unix socket (D) 重啟 nginx

Q94. `ausearch -m AVC` 的輸出裡 `tcontext=unconfined_u:object_r:default_t:s0`。這代表什麼、該怎麼修？
(A) 目標檔案根本沒有被貼上正確標籤；用 `semanage fcontext -a -t <型別> "<路徑>(/.*)?"` 加規則後 `restorecon -Rv` 套用 (B) 來源程序的網域不對，要改 nginx 的執行使用者 (C) 這是正常的，不用處理 (D) 檔案權限不足，`chmod 755` 即可

Q95. 你用 `chcon` 把網站目錄的標籤改好了，一週後同樣的問題又出現。原因是？
(A) 有人改回去了 (B) `chcon` 只改當下的標籤，`restorecon`、系統重新標記、`cp` 覆蓋或套件更新都會把它還原；正確做法是 `semanage fcontext -a` ＋ `restorecon` (C) SELinux 的標籤有有效期限 (D) 需要重開機才會永久生效

Q96. 服務被 SELinux 擋住，`audit2allow` 產生了一個模組，載入後服務就好了。關於這個做法，下列敘述何者最正確？
(A) 這是標準解法，應該優先使用 (B) 它是照著剛才那筆拒絕反推規則，很容易放行整個 `default_t` 這種過大的範圍；正確的修法順位是「標籤 → 布林值 → 埠」，都不行才考慮自訂模組，而且要逐條看它產生了什麼 (C) 只要模組能載入就代表範圍是安全的 (D) 產生的模組會在重開機後失效，所以沒有風險

Q97. 服務明顯被擋住，但 `ausearch -m AVC -ts recent` 什麼都查不到。最可能的兩個原因是？
(A) `dontaudit` 規則把該事件靜音了（可用 `semodule -DB` 暫時停用、測完 `semodule -B` 恢復），或 auditd 根本沒在跑 (B) SELinux 已經是 disabled (C) 時間戳記格式不對 (D) 需要 root 才看得到，`sudo` 忘了加

Q98. 檢核工具給了一項建議，你不確定該不該照做。下列哪一組判斷方式最恰當？
(A) 全部照做，分數越高越好 (B) 只做不會影響服務的 (C) 用四問法：這對我這台機器的角色有意義嗎、不做的實際風險是什麼、做了會壞掉什麼、有沒有成本更低的等效控制；結果只有「照做／等效控制替代／接受風險並記錄理由」三種 (D) 看別人怎麼做就怎麼做

Q99. `auditctl -s` 顯示 `lost` 數字一直增加。最正確的處置是？
(A) 忽略，這是正常的 (B) 規則太寬（常見是無條件的 `-S execve` 或 `-S openat`）；用 `-F` 條件收斂、調大 `-b`，並用 `aureport -k --summary` 找出哪個 key 最吵 (C) 把 auditd 停用 (D) 擴充 `/var/log` 的容量就好

Q100. 稽核要求你提出「這台主機的防護設定確實有落實」的證據。下列哪一份最符合要求？
(A) 一份寫著「已依規定完成加固」的簽核文件 (B) 加固腳本的原始碼 (C) 具名的指令輸出（含執行時間與執行者）、對應的基準清單與差異比對結果，打包後附上 `sha256sum` 校驗檔 (D) 一張防火牆管理介面的截圖

| ★★★★ Q25、Q26、Q74、Q75 | **不懂 zone 的歸屬判斷** | 規則加在一個不 active 的 zone 裡，完全沒有作用 | [[090-02-04-guide-防火牆-firewalld]] 的〈★★★★ 來源網段綁 zone —— firewalld 最好用的一招〉 |

| ★★★★ Q33、Q80、Q81 | **不會切分 Fail2ban 的前後半段** | 在錯的地方查一整個下午 | [[090-02-05-guide-防護-Fail2ban入侵防護]] 的〈排查步驟（照順序，不要跳）〉 |
| ★★★★★ Q37、Q38、Q89 | **低估帶外管理的風險** | BMC 對外開放，繞過所有主機防護被拿下 | [[090-02-06-guide-防護-遠端存取安全]] 的〈帶外管理（OOB）為什麼是最高等級〉 |

## ★★★★★ 二十條必須記住的關鍵事實

★★★★ 這一章的內容很多，但真正會在半夜咬人的就是這二十條。
背不起全部，至少把有五顆星的那幾條記住。

| # | 事實 | ★ |
| --- | --- | --- |
| 1 | 已建立的連線走 conntrack 的 `ESTABLISHED`，**不受新規則影響** —— 它既是保命視窗，也是誤判的來源 | ★★★★★ |
| 2 | 測試防火牆規則**永遠用新開的連線**，不要用手上這條判斷 | ★★★★★ |
| 3 | `ufw enable` 是**立刻**生效，沒先放行 SSH 就會斷線 | ★★★★★ |
| 4 | 規則**第一個匹配勝出**，後面的 allow 不會覆蓋前面的 deny；用 `insert 1` 把特例插到前面 | ★★★★★ |
| 5 | Docker 走 `nat` 與 `FORWARD`，**繞過 ufw 的 INPUT 規則**；發布埠一律綁 `127.0.0.1` | ★★★★★ |
| 6 | nftables 的多個 base chain 掛同一個 hook 會**全部執行**，你的 accept 蓋不掉別人的 drop | ★★★★★ |
| 7 | 一台機器**只能有一個防火牆負責人**（ufw／firewalld／手寫 nftables 三選一） | ★★★★★ |
| 8 | nftables 規則**寫成檔案 → `nft -c -f` 檢查 → `nft -f` 原子套用**，不要一條一條下 | ★★★★★ |
| 9 | `ct state established,related accept` 漏掉，主機會「發得出去、收不回來」 | ★★★★★ |
| 10 | firewalld 的 runtime 與 permanent 是**兩份獨立設定**；`--permanent` 之後要 `--reload` | ★★★★★ |
| 11 | 沒有綁介面或來源的 zone **不是 active**，加在裡面的規則等於沒加 | ★★★★ |
| 12 | Fail2ban 的 `banaction` 選錯會**沉默失敗** —— 一定要去防火牆那側驗證規則存在 | ★★★★★ |
| 13 | `ignoreip` 要寫**網段**，而且一定要包含機關的 NAT 出口 | ★★★★★ |
| 14 | 只改 `jail.local`，永遠不要碰 `jail.conf` | ★★★★★ |
| 15 | Fail2ban 是**降噪工具**，擋不住分散式暴力破解；根本解是關掉密碼登入 | ★★★★★ |
| 16 | 帶外管理（BMC／iDRAC／iLO）**絕對不可對網際網路開放**，它繞過作業系統的所有防護 | ★★★★★ |
| 17 | `usermod -L` 只鎖密碼，**金鑰登入不受影響**；下線廠商要三件事一起做 | ★★★★★ |
| 18 | `Permission denied` 但 `ls -l` 權限正確 → 八成是 MAC，去看 `ausearch -m AVC` | ★★★★★ |
| 19 | 不要把 SELinux 設成 `disabled`，需要放寬用 `permissive`；`chcon` 不是永久修法 | ★★★★★ |
| 20 | 稽核證據要「證明給我看」：**可重現、有時間、可追溯**，三件缺一不可 | ★★★★★ |

## 考前十分鐘速記卡（八篇各一張）

★★★★ 每張只寫「**最容易考、也最容易在現場出事**」的那幾個指令與判準。
完整內容一律回原文，這裡只是提醒。

### 一、伺服器初始安全設定

```bash
# 盤點：先知道現在有什麼（改任何東西之前）
sudo ss -tlnp                                   # 誰在聽什麼埠
systemctl list-units --type=service --state=running
systemctl list-units --type=socket --state=listening   # ★★★★ 別漏了 socket
awk -F: '$3>=1000 && $7!~/nologin|false/' /etc/passwd  # 可登入的一般帳號
awk -F: '$3==0' /etc/passwd                     # ★★★★★ UID=0 只應該有 root
sudo find / -xdev -perm -4000 -type f 2>/dev/null | sort   # SUID 基準
```

| 判準 | 內容 | ★ |
| --- | --- | --- |
| 保命三件事 | console 可用、保留一條不關的 session、備份整份 `/etc` | ★★★★★ |
| 關服務前 | `journalctl -u <svc> --since "7 days ago"` 看七天歷史 | ★★★★ |
| socket | `.socket` 沒 disable，埠還是開的 | ★★★★ |
| 加固建議不能盲抄 | `ip_forward`、`squashfs`、`rp_filter`、`/tmp noexec` 都有副作用 | ★★★★★ |
| 改 sudoers | 一律 `visudo -f`，不要用一般編輯器 | ★★★★★ |

### 二、ufw

```bash
sudo ufw status verbose          # 稽核截這個（含預設政策與 logging）
sudo ufw status numbered         # ★★★★★ 排查與刪除必用
sudo ufw show added              # ★★★★★ enable 之前的最後檢查
sudo ufw --dry-run allow ...     # 只看會產生什麼，不套用
sudo ufw insert 1 <規則>          # 把特例插到最前面
sudo ufw delete <號碼>            # ★★★ 多條時由大到小刪
```

| 判準 | 內容 | ★ |
| --- | --- | --- |
| enable 順序 | 排 `at` → 確認 sshd 埠 → allow → `show added` → enable | ★★★★★ |
| 規則順序 | 第一個匹配勝出，特例要 `insert` 到前面 | ★★★★★ |
| Docker | 走 FORWARD 鏈，ufw 管不到；發布埠綁 `127.0.0.1` | ★★★★★ |
| 對外動作 | 用 `deny`（drop）不用 `reject` | ★★★★ |
| 持久化 | `is-enabled ufw` ＋ `ENABLED=yes`，重開機驗證 | ★★★★ |

### 三、nftables 與 iptables

```bash
sudo nft list ruleset                        # ★★★★★ 唯一的完整真相
sudo nft -c -f /etc/nftables.conf            # 語法檢查，不套用
sudo nft -f /etc/nftables.conf               # 原子套用
sudo nft reset counters                      # 歸零後重測，看哪條被命中
sudo nft list ruleset | grep -c 'hook input' # ★★★★★ 超過 1 就是災難來源
sudo nft flush ruleset                       # 緊急：清空全部規則
```

| 判準 | 內容 | ★ |
| --- | --- | --- |
| 多個 base chain | 全部執行，accept 蓋不掉別人的 drop | ★★★★★ |
| conntrack | `ct state established,related accept` 排在 loopback 之後、所有 drop 之前 | ★★★★★ |
| 持久化 | `nft add` 不會存檔，要寫進 `/etc/nftables.conf` ＋ enable 服務 | ★★★★ |
| set | 放 CIDR 要 `flags interval`；大量封鎖一定要用 set | ★★★ |
| 相容層 | `iptables -S` 看不到原生 `inet` table，別拿它當真相 | ★★★ |

### 四、firewalld

```bash
sudo firewall-cmd --state
sudo firewall-cmd --get-active-zones          # ★★★★ 規則沒作用先看這個
sudo firewall-cmd --zone=<zone> --list-all
diff <(sudo firewall-cmd --list-all-zones) \
     <(sudo firewall-cmd --permanent --list-all-zones)   # runtime vs permanent
sudo firewall-cmd --permanent --add-service=http && sudo firewall-cmd --reload
sudo firewall-cmd --panic-on                  # 緊急全斷（★★★ 會斷掉你自己）
```

| 判準 | 內容 | ★ |
| --- | --- | --- |
| 標準工作流 | runtime 先試 → 驗證 → `--permanent` ＋ `--reload` | ★★★★★ |
| zone 歸屬 | 來源綁定 → 介面綁定 → default zone | ★★★★ |
| NetworkManager | `connection.zone` 才是權威，會覆蓋 firewall-cmd | ★★★★ |
| `--timeout` | 只能用於 runtime，不能配 `--permanent` | ★★★★ |
| 埠轉發 | 一定要配 `--add-masquerade` ＋ `ip_forward=1` | ★★★★★ |

### 五、Fail2ban

```bash
sudo fail2ban-client -t                       # ★★★★★ 改完先驗語法
sudo fail2ban-client status                   # jail 有沒有起來
sudo fail2ban-client status sshd              # ★★★★★ Total failed 決定往哪查
fail2ban-regex <日誌> <filter>                 # Failregex 與 Date template hits
sudo fail2ban-client get sshd ignoreip
sudo fail2ban-client set sshd unbanip <IP>
sudo fail2ban-client unban --all              # 緊急全解
```

| 判準 | 內容 | ★ |
| --- | --- | --- |
| 設定位置 | 只改 `jail.local`；`filter.d/*.local` 的 failregex 是整組取代 | ★★★★★ |
| banaction | 選錯**沉默失敗**，一定要去防火牆那側驗證規則存在 | ★★★★★ |
| ignoreip | 寫網段、包含機關 NAT 出口，**先寫白名單再開 jail** | ★★★★★ |
| 門檻 | 在 `findtime` 內達到 `maxretry` 次，封鎖 `bantime` | ★★★★ |
| 定位 | Fail2ban 是降噪，根本解是關掉密碼登入 | ★★★★★ |

### 六、遠端存取安全

```bash
sudo sshd -T                                  # ★★★★ 實際生效的完整設定
sudo sshd -T -C user=<帳號>,addr=<IP>,host=x   # 特定使用者的生效設定
sudo sshd -t                                  # 語法檢查
sudo chage -E 0 <廠商帳號>                     # 帳號到期
sudo truncate -s 0 ~<廠商帳號>/.ssh/authorized_keys
sudo pkill -KILL -u <廠商帳號>
```

| 判準 | 內容 | ★ |
| --- | --- | --- |
| 管理平面 | 與服務平面分開，只從跳板機或特定網段可達 | ★★★★★ |
| 帶外管理 | 獨立網段、不設預設路由、絕不對外 | ★★★★★ |
| 廠商下線 | 到期 ＋ 清公鑰 ＋ 踢 session，三件缺一不可 | ★★★★★ |
| `ssh -J` | 兩段各自認證，目標主機也要有你的公鑰 | ★★★ |
| MFA | `AuthenticationMethods` 逗號代表「且」，導入要先掛 `nullok` | ★★★★★ |

### 七、SELinux 與 AppArmor

```bash
getenforce; sudo ausearch -m AVC -ts recent            # RHEL 系
sudo aa-status; sudo dmesg | grep -i 'apparmor.*DENIED' # Debian 系
sudo semanage fcontext -a -t <型別> "<路徑>(/.*)?" && sudo restorecon -Rv <路徑>
sudo semanage port -a -t http_port_t -p tcp 8081
sudo setsebool -P httpd_can_network_connect on
matchpathcon <路徑>                                     # 「應該是什麼標籤」
```

| 判準 | 內容 | ★ |
| --- | --- | --- |
| 三十秒判斷 | `Permission denied` 但 `ls -l` 合理 → 八成是 MAC | ★★★★★ |
| 修法順位 | 標籤 → 布林值 → 埠 → 才考慮自訂模組 | ★★★★★ |
| `chcon` | 只改當下標籤，會被 `restorecon` 還原，不是解法 | ★★★★★ |
| `disabled` | 不要用；需要放寬用 `permissive` | ★★★★★ |
| AppArmor | 規則寫 `local/`；`**` 不含目錄本身 | ★★★★ |

### 八、系統強化與稽核

sudo etckeeper init && sudo etckeeper commit "baseline"

## ★★★★ 實作驗收（在測試機做，不要在正式機）

★★★★★ 筆試 90 分不代表手會做。以下十項請在測試機（或快照過的 VM）上實際完成，
每一項都要能拿出**指令輸出**當作完成證明。

**【1】★★★★★ 把自己鎖在外面，然後救回來**
在測試 VM 上刻意跑 `sudo ufw default deny incoming && sudo ufw --force enable`
（不放行 SSH），確認連不上之後，用 console 進去 `sudo ufw disable` 救回來。
★★★★★ **驗收標準**：你要能說出「如果這是一台在外縣市機房的實體機，我剛才做了什麼？」

**【2】★★★★★ 排一次自動還原並讓它真的觸發**
`echo "/usr/sbin/ufw --force disable" | sudo at now + 3 minutes`，
然後故意把自己鎖住，等它救你。
**驗收標準**：`atq` 看得到排程、三分鐘後 `ufw status` 變成 inactive。

**【3】★★★★ 重現「規則順序」的陷阱**
先加一條 `ufw deny 3306/tcp`，再加 `ufw allow from <你的網段> to any port 3306`，
從外部測試會失敗；用 `ufw insert 1` 修好。
**驗收標準**：兩次 `ufw status numbered` 的輸出，以及兩次 `nc -zv` 的結果。

**【4】★★★★★ 重現 Docker 繞過 ufw**
起一個 `-p 8080:80` 的容器，確認 `ufw status` 沒有 8080、但從外部連得到；
改成 `-p 127.0.0.1:8080:80` 後再測一次。
**驗收標準**：兩次 `nc -zv <主機IP> 8080` 的結果不同。

**【5】★★★★ 寫一份 nftables 規則檔並原子套用**
含 loopback、`ct state established,related`、SSH、一個業務埠、`policy drop`。
先故意寫錯一個字，看 `nft -c -f` 怎麼報錯，改好再套用。
**驗收標準**：`nft -c -f` 的錯誤訊息（含行號）與套用後的 `nft list ruleset`。

**【6】★★★★★ 在 firewalld 上重現 runtime／permanent 的落差**
只下 runtime 規則 → 重開機驗證消失；只下 permanent → 驗證沒生效；
兩者都做 → 驗證都對。
**驗收標準**：三次 `diff <(firewall-cmd --list-all) <(firewall-cmd --permanent --list-all)`。

**【7】★★★★★ 讓 Fail2ban 真的封到一個 IP，並在防火牆那側看到規則**
從另一台機器故意打錯密碼觸發封鎖，然後在伺服器上**三層都看一次**：
`fail2ban-client status sshd`、防火牆規則、`journalctl -u fail2ban`。
**驗收標準**：三層輸出一致。★★★★★ 只看第一層不算通過。

**【8】★★★★ 驗證 `ignoreip` 真的有效**
把自己的網段加進 `ignoreip`，重新觸發同樣的失敗次數，確認**不會**被封。
**驗收標準**：`fail2ban-client get sshd ignoreip` 的輸出，以及觸發後仍連得上。

**【9】★★★★★ 重現一次 MAC 造成的 `Permission denied`**
在 Rocky／AlmaLinux 上把網站根目錄放到 `/data/www`，讓 nginx 讀不到；
用 `ausearch -m AVC` 找到原因，用 `semanage fcontext` ＋ `restorecon` 修好；
再跑一次 `restorecon -Rv` 驗證修正不會被還原。
**驗收標準**：AVC 原文、`matchpathcon` 的輸出、修好前後的頁面狀態。

**【10】★★★★ 建立一份可交付的稽核證據包**
用基準清單腳本產出 `01-*.txt` ～ `07-*.txt`，打包並附上 `sha256sum` 校驗檔，
在另一台機器上 `sha256sum -c` 驗證通過。
**驗收標準**：校驗全部 OK，而且每個檔案都看得出產出時間與執行者。
