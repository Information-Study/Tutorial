# 伺服器初始安全設定

## 這篇你會學到

> [!abstract] 這篇你會學到
> - 一台剛上線、有公網 IP 的 Linux 主機，**前十分鐘**會遇到什麼攻擊（附真實 log 片段）
> - 怎麼**盤點**這台機器現在跑了哪些服務、開了哪些埠，以及怎麼判斷「能不能關」
> - 帳號基準：root 登入、預設帳號、`pam_pwquality` 密碼政策、`sudo` 最小化與稽核軌跡
> - `unattended-upgrades` 自動修補怎麼設，以及**自動重啟服務**這個風險機關該怎麼取捨
> - 核心層強化：`sysctl` 網路參數、`noexec/nosuid/nodev` 掛載選項、核心模組黑名單
> - `auditd` 基本規則、journald 永久保存與日誌外送
> - 一台全新 Ubuntu Server 從裝好到通過自檢的**完整流程**，以及一支可以排進 cron 的自檢腳本
> - 加固過頭把自己鎖在門外時，怎麼救回來

## 觀念說明

### ★★★★★ 威脅模型：新機上線的前十分鐘

先看數字，不看理論。一台裝好 Ubuntu Server、給了公網 IP、開著 22 埠的機器，
**不需要被任何人知道它存在**，因為全世界的掃描器整天在掃整個 IPv4 空間：

| 時間 | 會發生的事 | 來源 |
| --- | --- | --- |
| **< 1 分鐘** | 第一次 TCP SYN 掃描抵達（22/80/443/3389/23） | Shodan、Censys 等測繪服務，以及殭屍網路 |
| **< 10 分鐘** | 第一次 SSH 登入嘗試（`root` / `admin` / `ubuntu`） | 自動化字典攻擊 |
| **< 1 小時** | 已知漏洞探測：`/.env`、`/phpinfo.php`、`/actuator/env`、`/.git/config` | Web 掃描 bot |
| **< 24 小時** | 每天數千至數萬次 SSH 嘗試；若有 Web，加上 Log4Shell、SQLi 探測 payload | 持續性掃描 |

> [!danger] 「這台只是測試機，沒人知道」是最常見的錯誤假設 ★★★★★
> 攻擊者不需要知道你是誰。他們掃的是**位址**，不是**單位**。
> 機關內最常見的入侵起點就是：一台「臨時開來測試、忘了關」的機器，
> root 密碼是 `Test1234`，開在公網上三個月。

### 這是真的 log，不是示意圖

在一台開放 22 埠對外的 Ubuntu 主機上，`/var/log/auth.log` 會長這樣：

```text
Sep  2 03:14:07 web-prd-01 sshd[10233]: Invalid user admin from 45.148.10.34 port 52344
Sep  2 03:14:07 web-prd-01 sshd[10233]: Failed password for invalid user admin from 45.148.10.34 port 52344 ssh2
Sep  2 03:14:08 web-prd-01 sshd[10233]: Connection closed by invalid user admin 45.148.10.34 port 52344 [preauth]
Sep  2 03:14:11 web-prd-01 sshd[10236]: Invalid user postgres from 45.148.10.34 port 52690
Sep  2 03:14:12 web-prd-01 sshd[10236]: Failed password for invalid user postgres from 45.148.10.34 port 52690 ssh2
Sep  2 03:14:19 web-prd-01 sshd[10241]: Failed password for root from 193.32.162.77 port 41022 ssh2
Sep  2 03:14:20 web-prd-01 sshd[10241]: Failed password for root from 193.32.162.77 port 41022 ssh2
Sep  2 03:14:22 web-prd-01 sshd[10241]: error: maximum authentication attempts exceeded for root from 193.32.162.77 port 41022 ssh2 [preauth]
Sep  2 03:14:22 web-prd-01 sshd[10241]: Disconnected from authenticating user root 193.32.162.77 port 41022 [preauth]
```

三個必須讀懂的細節：

| log 片段 | 意思 | ★ |
| --- | --- | --- |
| `Invalid user admin` | 這個帳號**不存在**。攻擊者在猜帳號名。 | ★★ |
| `Failed password for root` | 這個帳號**存在**，而且**允許密碼登入 root** —— 這是最危險的一行 | ★★★★★ |
| `maximum authentication attempts exceeded` | 單一連線內試了超過 `MaxAuthTries` 次 | ★★★ |

自己算一下今天被試了幾次：

```bash
sudo grep -c "Failed password" /var/log/auth.log
```

預期輸出（一台開在公網、沒做任何防護的機器，跑了一天）：

```text
8342
```

> [!warning] Ubuntu 23.10 之後預設沒有 `/var/log/auth.log` ★★★★
> Ubuntu 從 23.10 起**預設不安裝 `rsyslog`**，所有日誌只進 systemd journal。
> 在 Ubuntu 24.04 上，上面那個 `grep` 會回 `No such file or directory`。
> 正確的查法是：
>
> ```bash
> journalctl -t sshd --since "24 hours ago" | grep -c "Failed password"
> journalctl -u ssh.service -p warning --since today --no-pager | tail -20
> ```
>
> 這是新舊教材最常對不上的一點。做日誌外送前先確認這台到底有沒有 rsyslog：
> `dpkg -l rsyslog 2>/dev/null | grep ^ii`。細節見 [[020-01-19-guide-Linux-日誌系統]]。

### ★★★★ 攻擊者拿到一個 shell 之後會做什麼

理解這條鏈，才知道每一項加固擋的是哪一段：

```text
【1】掃描      → 找到開著的埠
【2】初始存取  → SSH 弱密碼 / Web 應用漏洞 / 未修補的服務
【3】站穩      → 加自己的 SSH 公鑰、開 cron、放 systemd timer
【4】提權      → 找 SUID 執行檔、可寫的 sudoers、舊核心的本機提權漏洞
【5】橫向移動  → 讀 ~/.ssh/known_hosts、config、內網掃描
【6】達成目的  → 挖礦 / 勒索加密 / 竊資 / 當跳板
```

對應的加固項：

| 階段 | 這篇的哪一節在擋 | ★ |
| --- | --- | --- |
| 【1】掃描 | 關閉多餘服務與埠、防火牆預設拒絕 | ★★★★★ |
| 【2】初始存取 | 帳號基準、密碼政策、SSH 強化、自動修補 | ★★★★★ |
| 【3】站穩 | auditd 監看 `~/.ssh/`、cron、systemd 單元 | ★★★★ |
| 【4】提權 | SUID 盤點、`noexec/nosuid` 掛載、sudo 最小化、核心修補 | ★★★★ |
| 【5】橫向移動 | 防火牆出向規則、金鑰不落地、分段網路 | ★★★ |
| 【6】達成目的 | 日誌外送（本機日誌會被刪）、監控告警 | ★★★★ |

> [!note] 為什麼「日誌外送」被歸在最後一階段 ★★★★
> 攻擊者站穩之後第一件事常常是清 log。**只存在本機的日誌，在真正的資安事件裡沒有證據力。**
> 這也是 [[090-07-15-guide-資安實踐-被入侵主機的跡證檢查]] 一開始就會問「有沒有外送」的原因。

### 最小安裝原則：不裝的東西不會有漏洞

這是整篇最省力、效益最高的一條原則。

> [!note] 攻擊面（Attack Surface）★★★★
> 攻擊面 = **所有攻擊者可以送資料進來的入口總和**。
> 每一個監聽中的服務、每一支 SUID 執行檔、每一個裝著但沒用的套件，都是一個入口。
> 減少攻擊面**不需要理解漏洞細節** —— 只要東西不存在，它的 CVE 就跟你無關。

實務上的三個層次：

| 層次 | 做法 | 效果 | ★ |
| --- | --- | --- | --- |
| **① 安裝時就不要裝** | 用 minimal / server 安裝選項，不要選 "Featured Server Snaps" | 最乾淨，事後不用清 | ★★★★★ |
| **② 裝了但停用** | `systemctl disable --now`，服務還在但不啟動 | 好回復，但套件的檔案仍在 | ★★★★ |
| **③ 移除套件** | `apt purge` | 最徹底，但可能扯出相依 | ★★★ |

★★★★ **順序一定是 ①→②→③**。已經上線的機器不要一上來就 purge，
先 disable 觀察一到兩週，確認沒有人抱怨再考慮移除。

>
> | 項目 | Ubuntu / Debian | Rocky / AlmaLinux |

### TWGCB 與這篇的關係

[[090-06-00-idx-TWGCB]]（台灣政府組態基準）由國家資通安全研究院發布，
Linux 部分是一份**逐項編號的檢核清單**（例如 TWGCB-01-014 對應 Ubuntu 22.04 LTS）。

| | 這篇 | TWGCB |
| --- | --- | --- |
| **性質** | 教學：為什麼做、怎麼做、怎麼驗證 | 法遵：做了沒、能不能出報告 |
| **範圍** | 挑最關鍵的三十幾項 | 數百項，含大量低風險項目 |
| **例外處理** | 用工程判斷 | 必須書面申請例外並留存 |
| **驗收** | 自檢腳本 | 官方檢測工具產出符合性報告 |

★★★★ **實務順序：先用這篇把機器弄到安全，再用 TWGCB 補齊法遵缺口。**
反過來做（先跑 TWGCB 工具、看報告修）會產生大量你不知道為什麼要改的設定，
上線後出問題無從判斷是不是加固造成的。

## 安裝或基礎操作

### 【一】動手之前：三個保命動作

> [!danger] 這一節不做，後面每一節都可能讓你進不去這台機器 ★★★★★
> 加固失手最常見的三種鎖門：改 SSH 設定後 sshd 起不來、防火牆規則寫錯、
> `/etc/fstab` 打錯字導致開不了機。三個保命動作缺一不可。

**① 開好第二條連線，而且不要關。**

```bash
# 終端機 A：你的工作視窗
ssh ops@10.20.30.51

# 終端機 B：保命視窗 —— 登進去之後放著，整場加固都不要關掉、不要 exit
ssh ops@10.20.30.51
```

★★★★★ 已經建立的 SSH 連線**不會**因為 `systemctl restart ssh` 或防火牆改規則而中斷
（既有連線走的是已建立的 TCP session）。這條保命線可以在你把自己鎖在外面時救你一次。

**② 確認 console 進得去。**

```bash
# 在 PVE 上：確認這台 VM 的 Console 按鈕點下去有畫面
# 在實體機上：確認 iDRAC / iLO / IPMI 的 IP、帳密是對的，而且能開 Virtual Console
```

**③ 拍快照 / 備份 `/etc`。**

```bash
# VM：先拍快照（PVE / VMware 都可以）
# 實體機：至少把 /etc 備一份
sudo tar -czf /root/etc-backup-$(date +%F).tar.gz /etc
ls -lh /root/etc-backup-*.tar.gz
```

預期輸出：

```text
-rw-r--r-- 1 root root 3.1M Sep  3 09:12 /root/etc-backup-2026-09-03.tar.gz
```

> [!tip] 更好的做法：etckeeper ★★★★
> `sudo apt install etckeeper` 之後，`/etc` 會被納入 git，**每次 apt 操作自動 commit**。
> 加固後想知道「我到底改了什麼」，`sudo git -C /etc log --stat` 一目瞭然。
> 見 [[020-02-03-02-ref-標準化-基準設定與範本化]]。

### 【二】★★★★★ 盤點：先知道現在有什麼

**不要憑印象關服務。** 順序永遠是「盤點 → 判斷 → 確認沒人用 → 關 → 驗證」。

#### 2-1 現在有哪些服務在跑

```bash
systemctl list-units --type=service --state=running --no-pager
```

```text

  dbus.service                loaded active running D-Bus System Message Bus
  getty@tty1.service          loaded active running Getty on tty1
```

#### 2-2 開機會自己起來的有哪些

`running` 只是「現在在跑」，`enabled` 才是「下次開機還會起來」。兩個都要看：

```bash
systemctl list-unit-files --type=service --state=enabled --no-pager
```

#### 2-3 ★★★★★ 誰在監聽哪個埠 —— 最重要的一條指令

```bash
sudo ss -tulpn
```

**看懂三個欄位就夠了：**

| 欄位 | 判讀 | ★ |
| --- | --- | --- |
| `Local Address` 是 `0.0.0.0` 或 `[::]` | ★★★★★ **對全世界開放**。這是要優先處理的 | ★★★★★ |
| `Local Address` 是 `127.0.0.1` / `127.0.0.53` | 只有本機連得到，風險低很多 | ★★ |
| `Process` 欄 | 是哪支程式開的。**沒有這欄就不知道要關誰**，所以一定要加 `-p` 且用 `sudo` | ★★★★ |

上面這台的問題一眼可見：**`rsync` 的 873 埠開在 `0.0.0.0`**。
`rsync` daemon 模式在很多情況下是不需要認證的，這是一個必須立刻處理的對外服務。

> [!tip] 只看對外開放的，不看 localhost ★★★★
> ```bash
> sudo ss -tulpn | grep -v '127\.0\.0\.\|\[::1\]'
> ```
> 這一行是每次交機驗收都要跑的。**輸出裡的每一行都要能說出「這是誰、為什麼要開」。**

```bash
# 全部（含相依）
dpkg-query -f '${binary:Package}\n' -W | wc -l

# 只看「人為手動裝的」—— 這才是你該檢視的清單
apt-mark showmanual | sort
```

預期輸出（節錄）：

```text

openssh-server
vim
curl
snapd
...
```

#### 2-5 有哪些帳號可以登入

```bash
awk -F: '$7 !~ /(nologin|false)$/ {print $1, $3, $7}' /etc/passwd
```

預期輸出：

```text

```

★★★★ `sync` 這種系統帳號有 shell 是正常的（歷史因素、無密碼），
但**除了 `root` 和你自己建的管理帳號以外，出現任何 UID ≥ 1000 的帳號都要查清楚是誰**。

#### 2-6 把盤點結果存起來 ★★★★

```bash
sudo mkdir -p /root/baseline
sudo sh -c '{
  echo "=== date ==="; date -Is
  echo "=== running services ==="; systemctl list-units --type=service --state=running --no-pager
  echo "=== enabled services ==="; systemctl list-unit-files --type=service --state=enabled --no-pager
```

沒有這份檔案，排錯時只能靠猜。

### 【三】★★★★★ 關閉不需要的服務與對外埠

#### 3-1 判斷流程

```text
發現一個監聽中的服務
   ↓
① 這是我裝的嗎？   → 不是 → 查是哪個套件帶進來的：dpkg -S $(which xxx)
   ↓ 是
② 有人在用嗎？     → 看連線數：ss -tnp state established '( sport = :873 )'
   ↓ 沒有
③ 有申請單寫要開嗎？→ 沒寫 → 關
   ↓ 有寫
④ 一定要對全世界開嗎？→ 不用 → 改綁 127.0.0.1，或用防火牆限來源
```

★★★★ 第 ② 步是最常被跳過、也是最常出事的一步。
關之前務必先確認沒有現行連線：

```bash
# 看 873 埠現在有沒有人連著
sudo ss -tnp state established '( sport = :873 )'
```

若輸出為空（只有表頭），代表當下沒人在用。**但「當下沒人用」不等於「沒人用」** ——
可能是每天凌晨才跑的備份。★★★★ 保守做法：先看歷史日誌。

```bash
journalctl -u rsync.service --since "7 days ago" --no-pager | tail -30
```

#### 3-2 disable / mask / purge 三種關法

| 做法 | 指令 | 效果 | 什麼時候用 | ★ |
| --- | --- | --- | --- | --- |
| **停用** | `systemctl disable --now foo` | 立刻停 + 開機不啟動；但**別的服務可以把它拉起來**（socket / 相依） | 大部分情況 | ★★★★ |
| **遮蔽** | `systemctl mask foo` | 連結到 `/dev/null`，**任何方式都啟不動** | 確定絕對不能跑（如 `apache2` 與 `nginx` 衝突時） | ★★★★★ |
| **移除** | `apt purge foo` | 套件與設定檔一併刪除 | 已觀察一段時間確認無用 | ★★★ |

```bash
# 停用並立刻停止 rsync daemon
sudo systemctl disable --now rsync.service
```

預期輸出：

```text
Synchronizing state of rsync.service with SysV service script with /usr/lib/systemd/systemd-sysv-install.
Executing: /usr/lib/systemd/systemd-sysv-install disable rsync
Removed "/etc/systemd/system/multi-user.target.wants/rsync.service".
```

驗證：

```bash
systemctl is-enabled rsync.service; systemctl is-active rsync.service
```

```text
disabled
inactive
```

★★★★ 再回頭確認埠真的關了：

```bash
sudo ss -tulpn | grep ':873' || echo "873 已無監聽 ✓"
```

```text
873 已無監聽 ✓
```

> [!danger] socket 啟動：disable 了還是會被拉起來 ★★★★
> 有些服務同時有 `foo.service` 和 `foo.socket`。你只 disable 了 `.service`，
> `.socket` 還在監聽，只要有人連進來 systemd 就會把 service 拉起來。
>
> ```bash
> systemctl list-units --type=socket --state=listening --no-pager
> sudo systemctl disable --now foo.socket foo.service
> ```
>
> 典型例子是 `cups.socket`、`docker.socket`。**只關 service 沒關 socket，等於沒關。**

#### 3-3 一台一般伺服器上「通常可以關」的清單

> [!warning] 「通常」不等於「一定」—— 每一項都要對照你的申請單 ★★★★
> 下表是機關環境常見的判斷，不是照抄清單。筆電、桌機、虛擬化宿主機的答案會不一樣。

| 服務 | 預設狀態 | 一般伺服器 | 理由 / 例外 | ★ |
| --- | --- | --- | --- | --- |
| `ModemManager` | 啟用 | ★★★ **可關** | 管 3G/4G 數據機，伺服器沒有 | ★★★ |
| `rsync`（daemon 模式） | 依安裝選項 | ★★★★★ **必關** | 873 埠常無認證；用 `rsync over ssh` 取代 | ★★★★★ |
| `avahi-daemon` | 部分安裝有 | ★★★★ **可關** | mDNS 服務探索，會對區網廣播 | ★★★★ |
| `cups` / `cups-browsed` | 桌面版有 | ★★★★ **必關** | 列印服務；歷史上多次 RCE | ★★★★ |
| `snapd` | 啟用 | ★★ 視情況 | Ubuntu 很多套件靠它；**貿然移除會連帶移除其他東西** | ★★ |
| `multipathd` | 啟用 | ★★ 視情況 | 有多路徑 SAN 才需要；VM 上通常可關 | ★★ |
| `bluetooth` | 部分機器 | ★★★★ **可關** | 伺服器不需要 | ★★★ |
| `systemd-resolved` | 啟用 | ★ **不要關** | 關掉 DNS 就壞了；它只綁 127.0.0.53，風險低 | ★★★★ |
| `cron` | 啟用 | ★ **不要關** | 大量維運作業靠它 | ★★★★ |
| `postfix`（local only） | 部分安裝有 | ★★★ 綁 localhost 即可 | 系統寄通知信要用；**確認 `inet_interfaces = loopback-only`** | ★★★★ |

檢查 postfix 有沒有對外開 25 埠：

```bash
sudo ss -tlnp | grep ':25 ' || echo "25 埠未對外監聽 ✓"
```

#### 3-4 ★★★★ 關不掉的，就把它綁回 localhost

很多服務你其實需要它，但**不需要它對全世界開放**。
比起關服務，「改綁 `127.0.0.1`」是更常用、風險更低的做法：

| 服務 | 設定檔 | 關鍵設定 |
| --- | --- | --- |
| MySQL / MariaDB | `/etc/mysql/mysql.conf.d/mysqld.cnf` | `bind-address = 127.0.0.1` |
| PostgreSQL | `postgresql.conf` | `listen_addresses = 'localhost'` |
| Redis | `/etc/redis/redis.conf` | `bind 127.0.0.1 -::1` |
| Node.js / PM2 應用 | 應用程式 | 監聽 `127.0.0.1:3000`，前面掛反向代理 |

改完一定要用 `ss` 驗證，不要相信設定檔：

```bash
sudo ss -tlnp | grep ':3306'
```

```text
tcp   LISTEN 0      151       127.0.0.1:3306      0.0.0.0:*    users:(("mysqld",pid=2210,fd=23))
```

`127.0.0.1:3306` 才是對的；看到 `0.0.0.0:3306` 就是還沒生效。

#### 3-5 防火牆：這篇只講兩個原則

> [!danger] 啟用防火牆前一定要先放行 SSH ★★★★★
> 順序寫反 —— 先 `ufw enable` 再加規則 —— 你會在按下 enter 的瞬間把自己踢出去。
> **先開好第二條連線**（見【一】），並且確認 console 進得去。

| 原則 | 說明 | ★ |
| --- | --- | --- |
| **① 一定要開** | 「反正前面有防火牆設備」不是理由。主機防火牆擋的是**已經進到內網之後的橫向移動** | ★★★★★ |
| **② 預設拒絕（default deny inbound）** | 白名單思維：沒明確允許的一律擋。黑名單永遠列不完 | ★★★★★ |

最小可用序列（**規則先加、enable 最後**）：

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 10.20.0.0/16 to any port 22 proto tcp comment 'ssh from mgmt'
sudo ufw enable
sudo ufw status verbose
```

預期輸出：

```text
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)
New profiles: skip

To                         Action      From
--                         ------      ----
22/tcp                     ALLOW IN    10.20.0.0/16               # ssh from mgmt
```

**規則怎麼寫、應用程式設定檔、記錄與除錯，全部在 [[090-02-02-guide-防火牆-ufw基礎與實務]]，這篇不重複。**
不用 ufw 的環境見 [[090-02-03-guide-防火牆-nftables與iptables]]；RHEL 系見 [[090-02-04-guide-防火牆-firewalld]]。

#### 3-6 SSH：在初始設定裡的位置

SSH 強化的完整內容在 [[020-02-01-07-svc-SSH-安全強化]]。這裡只講**順序**，因為順序錯會鎖門：

```text
① 建管理帳號 → ② 佈署公鑰 → ③ 用公鑰實測登入成功（★★★★★ 這一步不能跳）
   → ④ 才關 PermitRootLogin 與 PasswordAuthentication
   → ⑤ sshd -t 語法檢查 → ⑥ systemctl reload ssh → ⑦ 開新視窗實測
```

```bash
# ⑤ 改完設定，先語法檢查再套用 —— 這一行是保命符 ★★★★★
sudo sshd -t && echo "語法 OK" || echo "語法錯誤，不要 reload"

# 確認實際生效值（讀的是合併後的最終設定，比看設定檔可靠）
sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|pubkeyauthentication|maxauthtries'
```

預期輸出：

```text
permitrootlogin no
pubkeyauthentication yes
passwordauthentication no
maxauthtries 3
```

> [!danger] `restart` 與 `reload` 的差別 ★★★★
> `systemctl reload ssh` 只重讀設定，**不影響既有連線**。
> `systemctl restart ssh` 也不會砍掉既有 session（子行程獨立），
> 但如果設定檔有錯導致 sshd 起不來，**你就再也連不進去了**。
> 所以 `sshd -t` 必須先跑。

## 進階應用

### 【四】★★★★★ 帳號基準

#### 4-1 root 帳號的三件事

| 項目 | 指令 | 驗證 | ★ |
| --- | --- | --- | --- |
| ① 停用 root **遠端** SSH 登入 | 在 `sshd_config` 設 `PermitRootLogin no` | `sshd -T \| grep permitrootlogin` → `no` | ★★★★★ |
| ② 鎖定 root **密碼** | `sudo passwd -l root` | `sudo passwd -S root` → 第二欄為 `L` | ★★★★ |
| ③ 保留 console 救援途徑 | 不要動 `/etc/securetty`、不要刪 root | 從 PVE / iDRAC console 能進 | ★★★★★ |

```bash
sudo passwd -S root
```

鎖定前：

```text
root P 2026-08-20 0 99999 7 -1
```

鎖定後：

```text
root L 2026-09-03 0 99999 7 -1
```

> [!danger] 「鎖定 root 密碼」與「刪除 root 密碼」是兩件事 ★★★★★
> - `passwd -l root`：在雜湊前加 `!`，**密碼還在，只是不能用**。將來 `passwd -u root` 可解鎖。
> - `passwd -d root`：**刪掉密碼欄**。在某些 PAM 設定下這等於「空密碼可登入」，是災難。
>
> **永遠用 `-l`，不要用 `-d`。**
>
> 另外，鎖了 root 密碼之後**單人模式（single user）也會要密碼**，
> 屆時要靠 GRUB 開機參數救援，見 [[020-01-25-guide-Linux-開機流程與GRUB救援]]。

#### 4-2 ★★★★ 預設帳號與雲端映像帳號

用官方雲端映像 / OVA / cloud-init 佈建的機器，會自帶一個預設帳號：

| 來源 | 預設帳號 | 風險 |
| --- | --- | --- |
| Ubuntu Cloud Image | `ubuntu` | ★★★★ 帳號名全世界都知道，只要密碼認證沒關就是靶 |
| Debian Cloud Image | `debian` | ★★★★ 同上 |
| 各廠商 OVA / 樣板 | `admin` / `vagrant` / 廠商名 | ★★★★★ **樣板可能內建一把公開的私鑰** |

處理方式：

```bash
# 1) 檢查有沒有你不認識的授權金鑰 ★★★★★
sudo find /home /root -name authorized_keys -exec ls -l {} \; -exec cat {} \;
```

★★★★★ **樣板機最經典的災難**：Vagrant box 內建的 insecure key、
或前手工程師離職後留在 `authorized_keys` 裡的公鑰。**這一行一定要跑。**

```bash
# 2) 若不需要預設帳號，鎖起來（不要急著刪，先確認沒有服務用它跑）
sudo usermod -L -e 1 ubuntu     # -L 鎖密碼；-e 1 設定帳號到期日為 1970-01-02（即已到期）
sudo passwd -S ubuntu
```

```text
ubuntu L 2026-09-03 0 99999 7 -1
```

```bash
# 3) 確認到期日真的設進去了
sudo chage -l ubuntu | grep -i 'Account expires'
```

```text
Account expires						: Jan 02, 1970
```

> [!tip] cloud-init 會把帳號加回來 ★★★★
> 若這台是用 cloud-init 佈建的，重開機後 cloud-init 可能**重新建立**你剛鎖掉的帳號。
> 要根治得改 `/etc/cloud/cloud.cfg` 裡的 `users:` 區段，或直接
> `sudo touch /etc/cloud/cloud-init.disabled`（確定不再需要 cloud-init 時）。
> 鎖完帳號**一定要重開機再驗證一次**。

#### 4-3 管理帳號與 sudo 最小化

```bash
# 建立具名的管理帳號 —— ★★★★★ 一人一帳號，禁止共用
sudo adduser ops
sudo usermod -aG sudo ops
id ops
```

```text
uid=1000(ops) gid=1000(ops) groups=1000(ops),27(sudo)
```

> [!danger] 共用帳號＝沒有稽核軌跡 ★★★★★
> 全資訊室共用一個 `admin` 帳號，出事時 log 只會告訴你「admin 做的」。
> **稽核軌跡的價值等於帳號的唯一性。** 這是 [[090-07-01-guide-資安實踐-資安基本原則與實踐]]
> 講的職責分離在主機層的落實。

sudo 規則寫在 `/etc/sudoers.d/` 下的獨立檔案，**不要直接改 `/etc/sudoers`**：

```bash
sudo visudo -f /etc/sudoers.d/10-hardening
```

內容：

```text
# 所有 sudo 都要用 pty，避免被背景程式劫持（TTY hijacking）
Defaults    use_pty

# sudo 專屬日誌檔（獨立於 auth.log，比較好保存與外送）
Defaults    logfile="/var/log/sudo.log"

# 密碼快取縮短為 5 分鐘（預設 15），離開座位的風險窗口變小
Defaults    timestamp_timeout=5

# 打錯密碼時不要洩漏「這個帳號存不存在」
Defaults    !visiblepw
```

★★★★★ **`visudo` 一定要用，不要用 `vi` 直接編。**
`visudo` 存檔時會做語法檢查，語法錯的 sudoers 會讓**全機所有人都不能 sudo**。

驗證語法（改完的保險動作）：

```bash
sudo visudo -c -f /etc/sudoers.d/10-hardening
```

```text
/etc/sudoers.d/10-hardening: parsed OK
```

檢查某個人到底有哪些權限：

```bash
sudo -l -U ops
```

```text
User ops may run the following commands on tool-prd-02:
    (ALL : ALL) ALL
```

> [!warning] `NOPASSWD: ALL` 是最常見的自我毀滅設定 ★★★★★
> 為了讓腳本跑得順，很多人寫 `ops ALL=(ALL) NOPASSWD: ALL`。
> 這代表**只要拿到 ops 的 shell 就直接等於 root**，SSH 金鑰外洩＝全機淪陷。
>
> 正確做法是只對**特定指令**免密碼：
>
> ```text
> # 只讓監控帳號免密碼執行特定的檢查指令
> monitor ALL=(root) NOPASSWD: /usr/sbin/smartctl -a /dev/sda, /usr/bin/systemctl is-active *
> ```
>
> ★★★★ 免密碼的指令**不能是可以開 shell 的**（`vi`、`less`、`find -exec`、`tar --to-command`
> 都能逃逸成 root shell）。

進階：記錄 sudo 的完整輸入輸出（可用 `sudoreplay` 重播）：

```text
# 加在 /etc/sudoers.d/10-hardening
Defaults    log_input, log_output
Defaults    iolog_dir="/var/log/sudo-io"
```

★★★ 這會佔用磁碟空間，也可能錄到使用者輸入的密碼（例如 `sudo mysql -p`），
**啟用前要評估，並確保 `/var/log/sudo-io` 權限是 `0700 root:root`**。

#### 4-4 密碼政策：`pam_pwquality`

```bash
sudo apt install -y libpam-pwquality
```

編輯 `/etc/security/pwquality.conf`：

```ini
# 最短長度 ★★★★
minlen = 12

# 至少要用到幾種字元類別（大寫/小寫/數字/符號）★★★
minclass = 3

# 同一字元最多連續重複幾次
maxrepeat = 3

# 不允許包含使用者名稱
usercheck = 1

# 檢查字典（需要 cracklib 字典檔）
dictcheck = 1

# ★★★★ 連 root 改密碼也要遵守（預設 root 不受限）
enforce_for_root
```

在 Debian / Ubuntu 上，`libpam-pwquality` 會透過 `pam-auth-update` 掛進
`/etc/pam.d/common-password`。驗證有沒有真的掛上：

```bash
grep pam_pwquality /etc/pam.d/common-password
```

預期輸出（`retry=3` 由 pam-configs 帶入）：

```text
password	requisite			pam_pwquality.so retry=3
```

實測 —— 這一步才是驗證，看設定檔不算：

```bash
sudo passwd ops
```

輸入一個弱密碼，預期會被擋下：

```text
New password:
BAD PASSWORD: The password is shorter than 12 characters
New password:
BAD PASSWORD: The password fails the dictionary check - it is based on a dictionary word
```

> [!warning] `passwd` 對 root 執行時的行為 ★★★
> 沒有設 `enforce_for_root` 時，root 用 `passwd 某帳號` 設弱密碼，

> 或確認 `enforce_for_root` 已經寫進去。

#### 4-6 離職與異動帳號的處理

> [!danger] 「等等再刪」是資安事件的溫床 ★★★★★
> 離職帳號最危險的不是密碼，是**留在 `authorized_keys` 裡的公鑰** ——
> 改密碼、停 AD 帳號都擋不住金鑰登入。

標準處理順序（**不要第一步就刪**）：

| 步驟 | 指令 | 為什麼 |
| --- | --- | --- |
| ① 立刻鎖 | `sudo usermod -L -e 1 <user>` | 停止登入能力，秒級生效 |
| ② ★★★★★ 移除金鑰 | `sudo mv /home/<user>/.ssh/authorized_keys{,.revoked}` | 金鑰不受密碼政策管轄 |
| ③ 踢掉現有 session | `sudo pkill -KILL -u <user>` | 人已經登入中的話 ①② 都攔不到 |
| ④ 檢查殘留自動化 | `sudo crontab -l -u <user>`；`sudo ls /etc/sudoers.d/` | cron 與 sudo 規則會留著 |
| ⑤ 移出管理群組 | `sudo gpasswd -d <user> sudo` | 避免帳號被復用時繼承權限 |
| ⑥ 保留 30～90 天後再刪 | `sudo deluser --remove-home <user>` | 立刻刪會丟失稽核與交接資料 |

```bash
# ④ 一次查完殘留
sudo crontab -l -u alice 2>/dev/null; sudo grep -rl alice /etc/sudoers.d/ /etc/cron.d/ 2>/dev/null
```

### 【五】★★★★ 自動更新與修補

#### 5-1 為什麼一定要自動

弱點修補的實務數字：從 CVE 公布到出現公開 exploit，中位數是**幾天到兩週**；
機關的手動修補週期是**一個月到一季**。這中間就是暴露窗口。

| 做法 | 暴露窗口 | 服務中斷風險 | ★ |
| --- | --- | --- | --- |
| 完全手動 | 數週～數月 | 低（但都在維護時段外爆炸） | ★ |
| **只自動裝「安全性更新」** | 數小時～1 天 | 低 | ★★★★★ |
| 自動裝所有更新 | 數小時 | ★★★★ 中（功能更新可能改行為） | ★★ |
| 自動更新 + 自動重開機 | 最短 | ★★★★★ 高（沒人的時候重開） | ★★ |

**機關的建議取捨：自動裝安全性更新、自動重啟必要服務、但不自動重開機。**

#### 5-3 ★★★★★ 自動更新最大的風險：服務被自動重啟

Ubuntu 的 `needrestart` 套件會偵測「哪些服務用了已被更新的舊函式庫」。
在**互動式** `apt upgrade` 時它會跳出選單問你；在 `unattended-upgrades` 裡它會**依設定自動處理**。

```bash
grep -E '^\s*\$nrconf\{restart\}' /etc/needrestart/needrestart.conf
```

```text
$nrconf{restart} = 'i';
```

| 值 | 行為 | 建議 | ★ |
| --- | --- | --- | --- |
| `'i'` | interactive：跳選單問（無人環境等於不重啟） | 桌機 | ★★ |
| `'a'` | automatic：**自動重啟受影響的服務** | ★★★★★ 一般伺服器建議，但要知道會短暫中斷 | ★★★★★ |
| `'l'` | list only：只列出，不動作 | ★★★★ 有嚴格變更管理的正式環境 | ★★★★ |

> [!danger] `'a'` 會在凌晨自動 restart 你的 nginx / mysql ★★★★★
> `libssl` 一更新，用到它的服務幾乎全部在清單裡。自動重啟 = 數秒到數十秒的中斷。
> **對 24×7 服務或單點資料庫，設 `'l'` 並把重啟排進維護時段。**
> 對有負載平衡、可滾動重啟的服務，`'a'` 是比較安全的選擇。

還要重開機的判斷（核心更新後才需要）：

### 【六】核心層強化

#### 6-1 `sysctl` 網路參數

寫成獨立檔案，**不要改 `/etc/sysctl.conf`**（升級時會衝突）：

```bash
sudo tee /etc/sysctl.d/60-hardening.conf > /dev/null <<'EOF'
# ── 反向路徑過濾：擋來源位址偽造 ★★★★
net.ipv4.conf.all.rp_filter = 1
net.ipv4.conf.default.rp_filter = 1

# ── 不接受、不發送 ICMP 重導向（防中間人改路由）★★★★
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.default.accept_redirects = 0
net.ipv4.conf.all.secure_redirects = 0
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.default.send_redirects = 0

# ── 不接受來源路由封包 ★★★★
net.ipv4.conf.all.accept_source_route = 0
net.ipv4.conf.default.accept_source_route = 0

# ── SYN cookies：SYN flood 時仍能接受合法連線 ★★★★
net.ipv4.tcp_syncookies = 1

# ── 記錄來源位址不合理的封包（martian）★★★
net.ipv4.conf.all.log_martians = 1
net.ipv4.conf.default.log_martians = 1

# ── 不回應廣播 ping（避免被當 Smurf 放大器）★★★
net.ipv4.icmp_echo_ignore_broadcasts = 1
net.ipv4.icmp_ignore_bogus_error_responses = 1

# ── IPv6：不接受路由器通告與重導向 ★★★
net.ipv6.conf.all.accept_ra = 0
net.ipv6.conf.default.accept_ra = 0
net.ipv6.conf.all.accept_redirects = 0
net.ipv6.conf.default.accept_redirects = 0

# ── 非路由器就不要轉發封包 ★★★★★（見下方警告）
net.ipv4.ip_forward = 0

# ── 記憶體與程序保護 ★★★
kernel.randomize_va_space = 2      # ASLR 全開
fs.suid_dumpable = 0               # SUID 程式不產生 core dump
kernel.kptr_restrict = 2           # 不對外洩漏核心位址
kernel.dmesg_restrict = 1          # 一般使用者不能讀 dmesg
kernel.yama.ptrace_scope = 1       # 限制 ptrace（防記憶體竊讀）
EOF

sudo sysctl --system
```

預期輸出（節錄）：

```text
* Applying /etc/sysctl.d/60-hardening.conf ...
net.ipv4.conf.all.rp_filter = 1
net.ipv4.tcp_syncookies = 1
kernel.randomize_va_space = 2
...
* Applying /etc/sysctl.conf ...
```

驗證（★★★★ 要驗**執行中的值**，不是設定檔）：

```bash
sysctl net.ipv4.tcp_syncookies net.ipv4.conf.all.rp_filter kernel.randomize_va_space
```

```text
net.ipv4.tcp_syncookies = 1
net.ipv4.conf.all.rp_filter = 1
kernel.randomize_va_space = 2
```

> [!danger] 三個會把服務弄壞的 sysctl ★★★★★
>
> | 參數 | 什麼情況不能設 | 症狀 |
> | --- | --- | --- |
> | `net.ipv4.ip_forward = 0` | ★★★★★ **這台是路由器 / NAT 閘道 / Docker 宿主 / K8s node / VPN 端點** | 容器沒有網路、VPN 通了但不能上網 |
> | `net.ipv4.conf.all.rp_filter = 1` | ★★★★ **多網卡且路由不對稱**（如兩條 ISP、policy routing） | 封包進得來出不去，連線莫名逾時 |
> | `net.ipv6.conf.all.accept_ra = 0` | ★★★ 這台**靠 SLAAC 取得 IPv6 位址** | 重開後沒有 IPv6 位址 |
>
> Docker 啟動時會自己把 `ip_forward` 設回 `1`，你的設定會被覆蓋 —— 這不是 bug。
> **有 Docker 的機器就不要在這裡寫 `ip_forward = 0`**，會造成混淆。

> [!warning] `rp_filter` 的生效規則跟直覺不同 ★★★
> 核心取的是 `max(net.ipv4.conf.all.rp_filter, net.ipv4.conf.<介面>.rp_filter)`。
> 所以只設 `all` 就會影響所有介面，**不能**用個別介面設 0 來放寬。要放寬得把 `all` 也設 0：
> ```bash
> sysctl -a --pattern 'rp_filter'
> ```
> 更多核心參數調校見 [[020-01-26-guide-Linux-核心模組與sysctl調校]]。

#### 6-2 檔案系統掛載選項

三個選項，擋的是**攻擊者已經能寫檔之後的下一步**：

| 選項 | 意義 | 擋掉什麼 | ★ |
| --- | --- | --- | --- |
| `noexec` | 這個分割區上的檔案**不能被執行** | 攻擊者把 payload 丟進 `/tmp` 然後 `chmod +x` 執行 | ★★★★ |
| `nosuid` | 忽略 SUID / SGID 位元 | 使用者放一支 SUID root 的 shell 進去提權 | ★★★★★ |
| `nodev` | 忽略裝置檔 | 建立 `/tmp/mem` 這種裝置檔直接讀寫記憶體 / 磁碟 | ★★★★ |

★★★★★ **先看現況，不要照抄別人的 fstab：**

```bash
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS /tmp /var/log /home /dev/shm
```

一台預設 Ubuntu 24.04（`/tmp` 為 tmpfs、其餘未獨立分割）可能是：

```text
TARGET    SOURCE    FSTYPE OPTIONS
/tmp      tmpfs     tmpfs  rw,nosuid,nodev,relatime,size=1998952k,inode64
/dev/shm  tmpfs     tmpfs  rw,nosuid,nodev,inode64
```

`/var/log` 與 `/home` 沒有出現，代表它們在 `/` 上、沒有獨立分割 ——
**這種情況下不可能單獨給它們掛載選項**，只能在重建機器時處理（見
[[020-02-03-01-svc-標準化-新機建置標準流程]] 的磁碟分割一節）。

**情況 A：有獨立分割** —— 改 `/etc/fstab`：

```text
# <file system>            <mount point>  <type>  <options>                      <dump> <pass>
/dev/mapper/vg0-lv_tmp     /tmp           ext4    defaults,nosuid,nodev,noexec   0      2
/dev/mapper/vg0-lv_varlog  /var/log       ext4    defaults,nosuid,nodev,noexec   0      2
/dev/mapper/vg0-lv_home    /home          ext4    defaults,nosuid,nodev          0      2
tmpfs                      /dev/shm       tmpfs   defaults,nosuid,nodev,noexec   0      0
```

> [!danger] fstab 打錯字會讓機器開不了機 ★★★★★
> **存檔後、重開機前，一定要跑這兩行：**
>
> ```bash
> sudo findmnt --verify --verbose
> sudo mount -a && echo "mount -a 無錯誤 ✓"
> ```
>
> `findmnt --verify` 會檢查每一行的語法與裝置是否存在；`mount -a` 會實際掛一次。
> 兩者都過才可以重開機。
>
> 若真的開不了機：開機時在 GRUB 選單按 `e`，在 `linux` 那行結尾加
> `systemd.unit=emergency.target`，進去後 `mount -o remount,rw /` 再修 fstab。
> 完整救援見 [[020-01-25-guide-Linux-開機流程與GRUB救援]]。

不重開機直接套用（`remount` 只能改選項，不能改裝置）：

```bash
sudo mount -o remount /tmp
findmnt -no OPTIONS /tmp
```

```text
rw,nosuid,nodev,noexec,relatime
```

**情況 B：`/tmp` 是 tmpfs** —— 用 systemd drop-in 加選項：

```bash
sudo systemctl edit tmp.mount
```

輸入：

```ini
[Mount]
Options=mode=1777,strictatime,nosuid,nodev,noexec,size=2G
```

```bash
sudo systemctl daemon-reload
sudo systemctl restart tmp.mount     # ★★★★ 會清空 /tmp，確認沒有服務正在用
findmnt -no OPTIONS /tmp
```

> [!warning] `noexec` 的三個副作用 ★★★★
> 1. **`apt` / `dpkg` 的安裝腳本**有時會在 `/tmp` 產生並執行暫存檔。
>    Ubuntu 現行版本一般不受影響，但若遇到安裝失敗，可暫時
>    `sudo mount -o remount,exec /tmp`，裝完再改回來。
> 2. **某些商用軟體的安裝程式**（Java installer、廠牌驅動）會直接抱怨無法執行。
> 3. `/dev/shm` 掛 `noexec` 可能讓部分 JVM、瀏覽器、PostgreSQL 的舊版共享記憶體用法出問題。
>
> ★★★ 另外要有正確期待：`noexec` **不是牆，是減速丘**。
> 攻擊者仍可用 `/lib64/ld-linux-x86-64.so.2 ./payload` 繞過。
> 它的價值在於擋掉大量**自動化**攻擊腳本，而不是擋定向攻擊者。

#### 6-3 SUID 執行檔盤點

★★★★ **重點不是背這份清單，是「跟基準比對」**。把首次盤點的結果存檔，
之後每次自檢比對差異 —— **多出來的 SUID 檔案是入侵的強烈跡象**：

```bash
sudo find / -xdev -perm -4000 -type f 2>/dev/null | sort > /root/baseline/suid.txt
# 日後比對
sudo find / -xdev -perm -4000 -type f 2>/dev/null | sort | diff /root/baseline/suid.txt - && echo "SUID 無變動 ✓"
```

#### 6-4 核心模組黑名單

用不到的檔案系統與網路協定，直接讓它載不起來：

```bash
sudo tee /etc/modprobe.d/60-hardening.conf > /dev/null <<'EOF'
# 冷門檔案系統（歷史上多次有解析漏洞）
install cramfs /bin/false
install freevxfs /bin/false
install jffs2 /bin/false
install hfs /bin/false
install hfsplus /bin/false
install udf /bin/false

# 冷門網路協定
install dccp /bin/false
install sctp /bin/false
install rds /bin/false
install tipc /bin/false

# 停用 USB 隨身碟（僅限機房內、有實體風險考量的主機）
# install usb-storage /bin/false
EOF
```

驗證（要用 `--dry-run` 測，不要真的載）：

```bash
sudo modprobe -n -v dccp
```

```text
install /bin/false
```

看到 `install /bin/false` 就代表黑名單生效。

> [!danger] Ubuntu 上千萬不要停用 `squashfs` ★★★★★
> 很多 CIS / 基準範本會列 `install squashfs /bin/false`。
> **在 Ubuntu 上，snap 完全依賴 squashfs** —— 停用之後 `snapd` 會壞、
> 用 snap 安裝的東西（`lxd`、`certbot`、部分廠商工具）全部起不來。
> 確定這台不用 snap（且已 `apt purge snapd`）才考慮。
>
> 同理，`usb-storage` 停用之後，**用 USB 隨身碟做的現場救援也會失效**。

> [!info]- Rocky / AlmaLinux（RHEL 系）對照：核心層差異
> - `sysctl` 參數**完全相同**，檔案一樣放 `/etc/sysctl.d/`。
> - RHEL 系預設啟用 SELinux，**很多「攻擊者寫檔後執行」的路徑本來就被 SELinux 擋掉**，
>   `noexec` 的邊際效益較低，但仍建議設。
> - `modprobe` 黑名單語法相同，但 RHEL 不用 snap，**可以安全地停用 `squashfs`**。
> - `/tmp` 在 RHEL 9 預設是獨立的 tmpfs（`tmp.mount`），做法與 Ubuntu 的情況 B 相同。
> - 檢查 SELinux：`getenforce` → 應為 `Enforcing`；`sestatus`。

### 【七】稽核與日誌

#### 7-1 auditd：記錄「誰在什麼時候動了什麼」

`auditd` 與一般日誌的差別：一般日誌記的是**應用程式想告訴你的事**，
auditd 記的是**核心層真的發生的系統呼叫**。攻擊者可以讓應用程式不寫 log，
但很難讓核心不產生 audit 事件。

```bash
sudo apt install -y auditd audispd-plugins
systemctl is-active auditd
```

```text
active
```

基本規則檔 `/etc/audit/rules.d/60-hardening.rules`：

```text
# 先清空既有規則
-D

# 事件緩衝區（繁忙主機要調大，否則會掉事件）★★★★
-b 8192

# 緩衝區滿時的行為：1 = 寫 printk 到 kmsg（不中斷服務）
-f 1

# ── 身分與權限檔案的異動 ★★★★★
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
-w /etc/group -p wa -k identity
-w /etc/gshadow -p wa -k identity
-w /etc/sudoers -p wa -k scope
-w /etc/sudoers.d/ -p wa -k scope

# ── SSH 設定與授權金鑰 ★★★★★
-w /etc/ssh/sshd_config -p wa -k sshd_config
-w /root/.ssh/ -p wa -k root_ssh_keys

# ── 排程與 systemd 單元（常見的持久化手法）★★★★
-w /etc/crontab -p wa -k cron
-w /etc/cron.d/ -p wa -k cron
-w /etc/systemd/system/ -p wa -k systemd_units

# ── 時間被改動（掩蓋痕跡的典型動作）★★★★
-a always,exit -F arch=b64 -S adjtimex,settimeofday,clock_settime -k time_change
-w /etc/localtime -p wa -k time_change

# ── 提權：所有 setuid/setgid 程式的執行 ★★★
-a always,exit -F arch=b64 -F euid=0 -F auid>=1000 -F auid!=unset -S execve -k privileged_exec

# ── 模組載入 ★★★★
-w /sbin/insmod -p x -k modules
-w /sbin/rmmod -p x -k modules
-a always,exit -F arch=b64 -S init_module,delete_module -k modules

# ── 稽核設定本身的異動 ★★★★
-w /etc/audit/ -p wa -k auditconfig
-w /var/log/audit/ -p wa -k auditlog
```

```bash
sudo auditctl -l | head
```

```text

```

★★★★★ **`auid=ops` 這一欄是 auditd 最大的價值** ——
就算對方 `sudo su -` 變成 root，`auid`（audit UID，也叫 loginuid）仍然記著
**最初登入的是誰**。這是 root 共用時唯一還追得回人的線索。

日誌保存設定 `/etc/audit/auditd.conf` 的關鍵三行：

```ini
max_log_file = 50               # 單檔 MB
num_logs = 10                   # 保留幾份 → 總量約 500 MB
max_log_file_action = ROTATE    # 滿了輪替
space_left = 500                # 剩餘 MB 低於此值時觸發
space_left_action = EMAIL
admin_space_left = 100
admin_space_left_action = SUSPEND
```

> [!danger] `admin_space_left_action = halt` 會直接把機器關掉 ★★★★★
> 部分基準範本要求 `halt`（磁碟滿到記不了 log 就停機，確保稽核完整性）。
> 語意上正確，**但在一般業務主機上等於自己給自己一個 DoS 開關** ——
> 某天 `/var/log` 塞爆，機器凌晨三點自己 halt，全機關網站掛掉。
>
> 除非是**法遵要求稽核不可中斷**的主機，否則用 `SUSPEND`（暫停記錄但機器繼續跑）
> 或 `SYSLOG`，並且**一定要把 `/var/log` 的用量納入監控告警**。

> [!warning] 規則設成 immutable（`-e 2`）之前先想清楚 ★★★★★
> 在規則檔最後加 `-e 2`，稽核規則就變成**不可修改**，
> 連 root 也不能改，**只有重開機才能調整**。
> 這是稽核完整性的最高等級，但也代表你之後每次微調規則都要安排一次重開機。
> 上線初期建議先用 `-e 1`（啟用但可改），規則穩定後再改成 `-e 2`。

#### 7-2 journald 永久保存

Ubuntu 預設 `Storage=auto` —— **`/var/log/journal/` 目錄不存在時，日誌只留在記憶體，重開就沒了**。

```bash
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
```

明確設定 `/etc/systemd/journald.conf`：

```ini
[Journal]
Storage=persistent
Compress=yes
SystemMaxUse=2G          # ★★★★ 一定要設上限，否則日誌會吃光磁碟
SystemMaxFileSize=200M
MaxRetentionSec=90day    # 保存 90 天（配合機關的日誌保存政策）
ForwardToSyslog=no
```

```bash
sudo systemctl restart systemd-journald
journalctl --disk-usage
```

```text
Archived and active journals take up 384.0M in the file system.
```

驗證重開機後日誌還在：

```bash
journalctl --list-boots | head -5
```

```text
IDX BOOT ID                          FIRST ENTRY                 LAST ENTRY
```

#### 7-3 ★★★★★ 日誌外送

> [!danger] 只存在本機的日誌沒有證據力 ★★★★★
> 攻擊者拿到 root 之後 30 秒內就能 `journalctl --rotate --vacuum-time=1s`
> 或 `rm -rf /var/log/*`。**日誌必須在事發當下就已經離開這台機器。**

三種常見做法：

| 做法 | 適用 | ★ |
| --- | --- | --- |
| rsyslog 轉送到集中 log server | 傳統、簡單、機關最常見 | ★★★★ |
| `systemd-journal-remote` | 全 systemd 環境 | ★★★ |
| Wazuh / SIEM agent | 要做關聯分析與告警 | ★★★★★ |

設定細節在 [[100-01-02-guide-日誌-日誌集中與輪替]]，SIEM 面在 [[090-02-08-guide-防護-系統強化與稽核]]。

★★★★★ **時間對不上的日誌沒有辦法關聯。** 外送之前先確認時間同步：

```bash

```

```text
                 Time zone: Asia/Taipei (CST, +0800)
System clock synchronized: yes
              NTP service: active
```

`System clock synchronized: yes` 與 `NTP service: active` 兩行都要對。

把所有驗證濃縮成一支可以重複跑的腳本：

```bash
sudo tee /usr/local/sbin/host-hardening-check > /dev/null <<'SCRIPT'
#!/usr/bin/env bash
# host-hardening-check —— 伺服器初始安全設定自檢
# 用法： sudo host-hardening-check           人看的彩色輸出
#        sudo host-hardening-check --quiet   只輸出 FAIL，可排 cron
set -uo pipefail

QUIET=0
[ "${1:-}" = "--quiet" ] && QUIET=1
PASS=0; FAIL=0; WARN=0
G=$'\e[32m'; R=$'\e[31m'; Y=$'\e[33m'; N=$'\e[0m'
[ -t 1 ] || { G=""; R=""; Y=""; N=""; }

chk() {  # chk <說明> <期望值> <實際值>
  local desc="$1" want="$2" got="$3"
  if [ "$got" = "$want" ]; then
    PASS=$((PASS+1)); [ "$QUIET" -eq 1 ] || printf '%s[ PASS ]%s %-46s %s\n' "$G" "$N" "$desc" "$got"
  else
    FAIL=$((FAIL+1)); printf '%s[ FAIL ]%s %-46s 期望=%s 實際=%s\n' "$R" "$N" "$desc" "$want" "$got"
  fi
}
warn() { WARN=$((WARN+1)); printf '%s[ WARN ]%s %s\n' "$Y" "$N" "$1"; }

[ "$QUIET" -eq 1 ] || echo "=== $(hostname -f)  $(date -Is) ==="

# ── 1. SSH ────────────────────────────────────────────
chk "SSH 停用 root 登入"        "no"  "$(sshd -T 2>/dev/null | awk '/^permitrootlogin/{print $2}')"
chk "SSH 停用密碼認證"          "no"  "$(sshd -T 2>/dev/null | awk '/^passwordauthentication/{print $2}')"
chk "SSH 啟用公鑰認證"          "yes" "$(sshd -T 2>/dev/null | awk '/^pubkeyauthentication/{print $2}')"

# ── 2. 帳號 ───────────────────────────────────────────
chk "root 密碼已鎖定"           "L"   "$(passwd -S root 2>/dev/null | awk '{print $2}')"
EMPTY=$(awk -F: '($2==""){print $1}' /etc/shadow 2>/dev/null | wc -l)
chk "無空密碼帳號"              "0"   "$EMPTY"
UID0=$(awk -F: '($3==0){print $1}' /etc/passwd | grep -vc '^root$')
chk "無第二個 UID 0 帳號"       "0"   "$UID0"
chk "pam_pwquality 已掛載"      "yes" "$(grep -q pam_pwquality /etc/pam.d/common-password && echo yes || echo no)"

# ── 3. 防火牆 ─────────────────────────────────────────
if command -v ufw >/dev/null 2>&1; then
  chk "ufw 已啟用"              "active" "$(ufw status 2>/dev/null | awk '/^Status:/{print $2}')"
  chk "ufw 預設拒絕進入"        "yes"    "$(ufw status verbose 2>/dev/null | grep -q 'deny (incoming)' && echo yes || echo no)"
else
  warn "未安裝 ufw，請自行確認 nftables/firewalld 規則"
fi

# ── 4. 自動更新 ───────────────────────────────────────
chk "unattended-upgrades 啟用"  "enabled" "$(systemctl is-enabled unattended-upgrades 2>/dev/null)"
chk "不自動重開機"              "yes"     "$(apt-config dump 2>/dev/null | grep -qi 'Unattended-Upgrade::Automatic-Reboot "true"' && echo no || echo yes)"

# ── 5. 核心參數 ───────────────────────────────────────
for kv in "net.ipv4.tcp_syncookies=1" \
          "net.ipv4.conf.all.rp_filter=1" \
          "net.ipv4.conf.all.accept_redirects=0" \
          "kernel.randomize_va_space=2" \
          "fs.suid_dumpable=0" \
          "kernel.dmesg_restrict=1"; do
  k="${kv%%=*}"; want="${kv##*=}"
  chk "sysctl $k" "$want" "$(sysctl -n "$k" 2>/dev/null | tr -d '[:space:]')"
done

# ── 6. 掛載選項 ───────────────────────────────────────
for m in /tmp /dev/shm; do
  o=$(findmnt -no OPTIONS "$m" 2>/dev/null)
  if [ -z "$o" ]; then warn "$m 未獨立掛載，無法套用 noexec/nosuid"; continue; fi
  for opt in nosuid nodev noexec; do
    chk "$m 含 $opt" "yes" "$(echo "$o" | grep -qw "$opt" && echo yes || echo no)"
  done
done

# ── 7. 稽核與日誌 ─────────────────────────────────────
chk "auditd 執行中"             "active" "$(systemctl is-active auditd 2>/dev/null)"
RULES=$(auditctl -l 2>/dev/null | grep -vc '^No rules$')
[ "$RULES" -gt 5 ] && chk "auditd 規則已載入(>5)" "yes" "yes" || chk "auditd 規則已載入(>5)" "yes" "no"
chk "journald 永久保存"         "yes" "$([ -d /var/log/journal ] && echo yes || echo no)"
chk "時間已同步"                "yes" "$(timedatectl show -p NTPSynchronized --value 2>/dev/null | grep -q yes && echo yes || echo no)"

# ── 8. 對外監聽埠盤點（列出，不判定）─────────────────
if [ "$QUIET" -eq 0 ]; then
  echo
  echo "── 對外監聽中的埠（每一行都要說得出理由）──"
  ss -tulpnH 2>/dev/null | grep -v '127\.0\.0\.\|\[::1\]' | awk '{print "   ", $1, $5, $7}'
fi

# ── 9. SUID 基準比對 ──────────────────────────────────
if [ -f /root/baseline/suid.txt ]; then
  DIFF=$(find / -xdev -perm -4000 -type f 2>/dev/null | sort | diff -q /root/baseline/suid.txt - >/dev/null && echo same || echo changed)
  chk "SUID 清單與基準一致"     "same" "$DIFF"
else
  warn "無 /root/baseline/suid.txt，建議先建立 SUID 基準"
fi

# ── 10. 待重開機 ──────────────────────────────────────
[ -f /var/run/reboot-required ] && warn "有套件需要重開機才生效：$(tr '\n' ' ' < /var/run/reboot-required.pkgs 2>/dev/null)"

echo
printf '結果： %sPASS=%d%s  %sFAIL=%d%s  %sWARN=%d%s\n' "$G" "$PASS" "$N" "$R" "$FAIL" "$N" "$Y" "$WARN" "$N"
[ "$FAIL" -eq 0 ]
SCRIPT

sudo chmod 0750 /usr/local/sbin/host-hardening-check
sudo /usr/local/sbin/host-hardening-check
```

## 常見錯誤與排錯

| # | 現象 | 原因 | 解法 | ★ |
| --- | --- | --- | --- | --- |
| 1 | 改完 `sshd_config` 後 `systemctl reload ssh` 失敗，新連線被拒 | 設定檔語法錯誤，sshd 沒能重載或直接掛掉 | ★★★★★ 用**保命視窗**跑 `sudo sshd -t` 看錯誤行號並修正；已斷線就走 console。**永遠先 `sshd -t` 再 reload** | ★★★★★ |
| 2 | `ufw enable` 之後立刻斷線，再也連不上 | 沒有先加 `allow 22`，或來源網段寫錯 | 走 console → `sudo ufw disable` → 補規則 → 重新 enable。事前用 `systemd-run --on-active=10min ... ufw --force disable` 當保險 | ★★★★★ |
| 3 | 開機停在 `You are in emergency mode`，要求 root 密碼 | `/etc/fstab` 打錯字或 UUID 不存在 | ★★★★★ 若 root 密碼已鎖，需在 GRUB 按 `e`、加 `init=/bin/bash`、`mount -o remount,rw /` 後修 fstab。**事前一定要跑 `findmnt --verify` 與 `mount -a`** | ★★★★★ |
| 4 | `sudo` 全部壞掉，`sudo: /etc/sudoers.d/10-hardening: syntax error near line N` | 直接用編輯器改 sudoers，沒過語法檢查 | ★★★★★ 用 console 以 root 身分（或 `pkexec visudo`）刪掉該檔。**改 sudoers 一律用 `visudo -f`** | ★★★★★ |
| 5 | 關掉某服務後，隔天備份 / 監控失效 | 關之前只看「當下有沒有連線」，沒查歷史日誌與排程 | 對照 `/root/baseline/pre-hardening.txt` 復原：`systemctl enable --now <svc>`。關服務前一定要 `journalctl -u <svc> --since "7 days ago"` | ★★★★ |
| 6 | `systemctl disable` 了服務，但埠還是開著 | 有對應的 `.socket` 單元在監聽，被連線時會拉起 service | `systemctl list-units --type=socket --state=listening`，把 `.socket` 一起 `disable --now`；必要時 `mask` | ★★★★ |
| 7 | 容器全部沒網路 / VPN 通了但不能上網 | `net.ipv4.ip_forward = 0` 套在 Docker 宿主或 VPN 端點上 | 該主機不要設這一項（或設為 1）：`sudo sysctl -w net.ipv4.ip_forward=1` 並從 `60-hardening.conf` 移除該行 | ★★★★★ |
| 8 | 多網卡機器某些連線莫名逾時、單向不通 | `rp_filter = 1` 遇到不對稱路由，回程封包被丟 | 改 `net.ipv4.conf.all.rp_filter = 2`（loose mode）或 0，並用防火牆補；`sysctl -a --pattern rp_filter` 確認生效值取 `all` 與介面的最大值 | ★★★★ |
| 9 | `apt install` 某套件失敗，訊息含 `Permission denied` 且路徑在 `/tmp` | `/tmp` 掛了 `noexec`，安裝腳本無法執行暫存檔 | 暫時 `sudo mount -o remount,exec /tmp`，安裝完 `sudo mount -o remount,noexec /tmp` | ★★★ |
| 10 | 重開機後 `snap` 指令全壞、`lxd` / `certbot` 起不來 | modprobe 黑名單停用了 `squashfs` | ★★★★★ 從 `/etc/modprobe.d/60-hardening.conf` 移除 squashfs 那行後重開。**Ubuntu 上不要停用 squashfs** | ★★★★★ |
| 11 | 凌晨服務莫名重啟數秒中斷 | `unattended-upgrades` + `needrestart` 設 `'a'`，`libssl` 更新後自動重啟服務 | 正式環境改 `$nrconf{restart} = 'l';`，把重啟排進維護時段；或把該服務加入 `Package-Blacklist` | ★★★★ |
| 12 | 機器凌晨自己關機，`/var/log/audit/audit.log` 停在關機前 | `auditd.conf` 的 `admin_space_left_action = halt`，`/var/log` 空間耗盡觸發 | ★★★★★ 改成 `SUSPEND` 或 `SYSLOG`，並把 `/var/log` 用量納入監控。清空間：`journalctl --vacuum-size=500M` | ★★★★★ |
| 13 | `sudo ausearch -k identity` 查不到任何東西 | 規則寫進 `/etc/audit/rules.d/` 但沒 `augenrules --load`；或 `auditctl -l` 顯示 `No rules` | `sudo augenrules --load && sudo auditctl -l`。若規則已設 `-e 2`（immutable），只能重開機才會套用新規則 | ★★★★ |
| 14 | 重開機後 `journalctl` 只剩本次開機的日誌 | `Storage=auto` 且 `/var/log/journal/` 不存在 | `sudo mkdir -p /var/log/journal && sudo systemd-tmpfiles --create --prefix /var/log/journal`，並在 `journald.conf` 明寫 `Storage=persistent` | ★★★★ |
| 15 | 鎖掉的 `ubuntu` 帳號重開機後又活過來 | cloud-init 每次開機重建帳號 | 改 `/etc/cloud/cloud.cfg` 的 `users:` 區段，或確定不需要時 `sudo touch /etc/cloud/cloud-init.disabled` | ★★★★ |
| 16 | `grep -c "Failed password" /var/log/auth.log` 回 `No such file or directory` | Ubuntu 23.10+ 預設不裝 rsyslog，日誌只在 journal | 用 `journalctl -t sshd \| grep -c "Failed password"`；需要檔案就 `sudo apt install rsyslog` | ★★★ |
| 17 | 加固後某服務啟動失敗，日誌顯示 `Permission denied` 但檔案權限看起來正常 | AppArmor / SELinux 阻擋 | `sudo dmesg \| grep -i 'apparmor.*DENIED'`（RHEL：`sudo ausearch -m AVC -ts recent`）。見 [[090-02-07-guide-防護-SELinux與AppArmor]] | ★★★★ |
| 18 | 自檢腳本 `[ FAIL ] SUID 清單與基準一致` | 可能是裝了新套件（正常），也可能是被植入（嚴重） | ★★★★★ 先 `diff /root/baseline/suid.txt <(find / -xdev -perm -4000 -type f 2>/dev/null \| sort)` 看多了哪一支，用 `dpkg -S <路徑>` 查是否屬於合法套件。查不到來源就當作入侵事件處理，見 [[090-07-15-guide-資安實踐-被入侵主機的跡證檢查]] | ★★★★★ |

### ★★★★★ 把自己鎖在外面的三階段救援

**階段一：還有一條連線活著**（保命視窗）

```bash
# 立刻回復到可連狀態，先求活再求對

sudo systemctl restart ssh              # sshd 問題（先 sshd -t 確認語法）
sudo mv /etc/ssh/sshd_config.d/60-hardening.conf /root/ && sudo sshd -t && sudo systemctl restart ssh
```

**階段二：連線全斷，但 console 進得去**

```bash
# 在 PVE / iDRAC console 上，用未被鎖的管理帳號登入
sudo ufw disable
sudo systemctl status ssh --no-pager -l   # 看 sshd 為什麼起不來
sudo tar -xzf /root/etc-backup-2026-09-03.tar.gz -C /   # 最後手段：整份 /etc 還原
```

**階段三：連 console 都進不去（開機失敗 / 密碼全鎖）**

1. 開機時在 GRUB 選單按 `e`
2. 找到 `linux` 開頭那一行，結尾加上 `init=/bin/bash`（或 `systemd.unit=emergency.target`）
3. 按 `Ctrl+X` 開機
4. `mount -o remount,rw /`
5. 修正 `/etc/fstab` 或 `passwd -u root`
6. `exec /sbin/init` 或 `reboot -f`

完整程序見 [[020-01-25-guide-Linux-開機流程與GRUB救援]]。

> [!danger] 階段三代表你在機房 ★★★★★
> 遠端機房、外縣市機房、雲端 VM，階段三可能根本做不到。
> **這就是為什麼階段零（保命三件事）不能省。**

## 安全性注意事項

### ★★★★★ 加固不是一次性活動

| 迷思 | 事實 |
| --- | --- |
| 「上線前加固過了」 | 加固的狀態會**退步**：有人為了除錯開了埠、裝了套件、加了 NOPASSWD | 
| 「跑過基準檢測工具就合規」 | 工具檢的是**設定值**，不是**實際風險**。綁 `0.0.0.0` 的 Redis 沒有一條基準會抓到 |
| 「內網機器不用加固」 | ★★★★★ 入侵幾乎都是從一台外網機跳進來後**橫向移動**。內網機器往往完全不設防 |
| 「反正前面有防火牆設備」 | 邊界防火牆擋不了已經進到同一個 VLAN 的攻擊者 |

所以步驟 12 的**每日自檢 + 有 FAIL 就寄信**才是這篇真正的產出，
而不是那一次全綠的輸出。

### ★★★★ 加固與可用性的取捨

每一項加固都有可用性成本。做決定時問三個問題：

| 問題 | 說明 |
| --- | --- |
| **這台機器承載什麼？** | 24×7 對外服務 vs. 內部工具機，答案完全不同 |
| **失敗的代價是什麼？** | 服務中斷 30 秒 vs. 資料外洩，量級不同 |
| **有沒有補償控制？** | 不能關的服務，能不能用防火牆限來源、加 WAF、加監控？ |

具體的取捨建議：

| 加固項 | 24×7 對外服務 | 內部工具機 | 開發測試機 |
| --- | --- | --- | --- |
| 自動安裝安全更新 | ★★★★ 是 | ★★★★★ 是 | ★★★★★ 是 |
| `needrestart` 自動重啟服務 | ★★ 否（設 `'l'`） | ★★★★ 是 | ★★★★ 是 |
| 自動重開機 | ★ 否 | ★★ 可（限維護時段） | ★★★ 可 |
| `/tmp` `noexec` | ★★★★ 是 | ★★★★ 是 | ★★ 視情況（會擋工具鏈） |
| auditd `-e 2`（immutable） | ★★★ 穩定後可 | ★★ 否 | ★ 否 |
| `admin_space_left_action=halt` | ★ 否 | ★ 否 | ★ 否 |

### ★★★★★ 三個絕對不能做的事

1. **不要在沒有 console 的情況下動防火牆或 SSH。** 遠端機房 + 鎖門 = 一趟車程。
2. **不要 `passwd -d root`。** 用 `passwd -l root`。
3. **不要為了讓腳本跑得順而寫 `NOPASSWD: ALL`。** 這等於把 sudo 這層防護整個拿掉。

### ★★★★ 加固之後才會浮現的三個問題

| 問題 | 什麼時候發現 | 預防 |
| --- | --- | --- |
| 某個季度才跑一次的排程壞了 | 三個月後 | 關服務前查 `/etc/cron.*`、`systemctl list-timers --all` |
| 廠商來維護時進不來 | 下次維護 | 事先建立**具名的廠商帳號 + 限時 + 限來源**，不要臨時關防火牆 |
| 磁碟被 audit log 塞爆 | 數週後 | `max_log_file` × `num_logs` 算清楚總量，並納入監控 |

```bash
# 關服務前的排程檢查
systemctl list-timers --all --no-pager
sudo ls -l /etc/cron.d/ /etc/cron.daily/ /etc/cron.weekly/
for u in $(awk -F: '$3>=1000 && $3<65534 {print $1}' /etc/passwd); do
  echo "--- $u"; sudo crontab -l -u "$u" 2>/dev/null
done
```

### 稽核軌跡的完整性

> [!danger] 攻擊者的第一件事是清 log ★★★★★
> 本機日誌只是**方便你排錯**，不是**證據**。要有證據力必須滿足三件事：
> 1. **即時外送**到另一台機器（攻擊者拿不到的那台）
> 2. **時間同步**（沒有正確時間就無法關聯多台主機的事件）
> 3. **保存期限**符合機關規定（一般要求 6 個月以上）
>
> 三件事缺任何一件，事後鑑識就會卡住。見 [[100-01-02-guide-日誌-日誌集中與輪替]]。

## 練習題

> [!question]- 練習 1（★★★）盤點與判斷
> 在你的測試機上跑 `sudo ss -tulpn`，把輸出裡**每一個對外監聽的埠**列成一張表，
> 三欄：埠號、行程、「為什麼需要開」。
> 對於你答不出第三欄的每一個埠，追查它是哪個套件帶來的（`dpkg -S $(which <程式>)`），
> 並決定要 disable、mask 還是改綁 `127.0.0.1`。
>
> **解答方向**
> 一台 minimal 安裝的 Ubuntu 24.04，正常情況下對外只應該有 22 埠。
> 常見的意外訪客：`rsync`（873）、`postfix`（25，若沒設 `loopback-only`）、
> `cups`（631）、`avahi`（5353/udp）。
> ```bash
> sudo ss -tulpn | grep -v '127\.0\.0\.\|\[::1\]'
> dpkg -S /usr/bin/rsync            # → rsync: /usr/bin/rsync
> systemctl cat rsync.service | head # 看它是怎麼被啟動的
> sudo systemctl disable --now rsync.service
> sudo ss -tulpn | grep ':873' || echo OK
> ```
> ★★★★ 重點在於**你必須為每一個開著的埠負責**。說不出理由的埠就是不該開的埠。

> [!question]- 練習 2（★★★★）安全地關服務
> 挑一個你打算關掉的服務，在**關掉之前**完成三項確認並寫下結果：
> ① 現在有沒有連線？② 過去七天有沒有活動紀錄？③ 有沒有排程或其他服務依賴它？
>
> **解答方向**
> ```bash
> SVC=rsync
> # ① 現有連線
> sudo ss -tnp | grep "$SVC"
> # ② 歷史活動
> journalctl -u "$SVC" --since "7 days ago" --no-pager | tail -20
> # ③ 誰依賴它
> systemctl list-dependencies --reverse "$SVC.service"
> sudo grep -rl "$SVC" /etc/cron.d/ /etc/cron.daily/ /etc/systemd/system/ 2>/dev/null
> ```
> ★★★★★ 第 ③ 步最常被忽略。`list-dependencies --reverse` 會告訴你有沒有別的單元 `Requires` 它。

> [!question]- 練習 3（★★★★★）鎖門與救援演練
> **在可以隨時還原的測試 VM 上**（先拍快照）：
> 故意在 `/etc/fstab` 加一行指向不存在裝置的掛載，重開機，
> 然後從 console 用 emergency mode 把它救回來。
>
> **解答方向**
> ```bash
> # 製造問題
> echo '/dev/sdz9 /mnt/broken ext4 defaults 0 2' | sudo tee -a /etc/fstab
> sudo reboot
> ```
> 開機會停在 emergency mode。救援：
> ```bash
> # 若 root 密碼已鎖，需在 GRUB 按 e，於 linux 行尾加 init=/bin/bash
> mount -o remount,rw /
> sed -i '/sdz9/d' /etc/fstab
> findmnt --verify --verbose
> exec /sbin/init      # 或 reboot -f
> ```
> ★★★★★ 這個演練的目的不是學指令，是讓你在**真的出事時不會慌**。
> 演練過的人 5 分鐘救回來，沒演練過的人會先花 20 分鐘搜尋。
> 另外請留意：如果 `fstab` 那行加了 `nofail`，開機就不會卡住 —— 這也是一個值得學的技巧。

> [!question]- 練習 4（★★★★）驗證 auditd 真的在記
> 設定 auditd 監看 `/etc/sudoers.d/`，然後模擬「攻擊者偷偷加了一條 NOPASSWD 規則」，
> 確認你能從 audit log 追出**是誰**做的（即使他是用 `sudo su -` 變成 root）。
>
> **解答方向**
> ```bash
> echo '-w /etc/sudoers.d/ -p wa -k scope' | sudo tee /etc/audit/rules.d/99-test.rules
> sudo augenrules --load
>
> # 模擬：用一般帳號 sudo 提權後動手腳
> sudo su -
> echo '# test' >> /etc/sudoers.d/10-hardening
> exit
>
> sudo ausearch -k scope -i --start recent | grep -E 'auid|comm='
> ```
> 輸出裡的 `auid=ops` 就是答案 —— ★★★★★ **`auid` 記的是最初登入的身分，
> 不會因為 `su` / `sudo` 而改變**。這是 root 共用環境下唯一的追人線索。

> [!question]- 練習 5（★★★★）自檢腳本客製化
> 把本篇的 `host-hardening-check` 抄到你的環境，加上**兩項**適合你單位的檢查：
> 例如「檢查 `/etc/resolv.conf` 指向機關 DNS」、「檢查監控 agent 在跑」、
> 「檢查備份腳本最近 24 小時有執行過」。
>
> **解答方向**
> ```bash
> # 加在腳本的第 7 節之後
> chk "DNS 指向機關伺服器" "yes" \
>     "$(resolvectl status 2>/dev/null | grep -q '10.20.1.10' && echo yes || echo no)"
> chk "監控 agent 執行中"  "active" "$(systemctl is-active zabbix-agent2 2>/dev/null)"
> LASTBK=$(find /var/log/backup -name '*.log' -mtime -1 2>/dev/null | wc -l)
> [ "$LASTBK" -gt 0 ] && chk "24h 內有備份紀錄" "yes" "yes" || chk "24h 內有備份紀錄" "yes" "no"
> ```
> ★★★★ 自檢腳本的價值與**它涵蓋了多少你單位真正在乎的事**成正比。
> 照抄別人的腳本只能檢到通用項目。

> [!question]- 練習 6（★★★）加固前後對照報告
> 用步驟 1 的基準檔，做出一份「加固前 vs 加固後」的對照：
> 服務少了幾個、對外埠少了幾個、SUID 檔有無變動。
>
> **解答方向**
> ```bash
> sudo sh -c '{
>   echo "=== running ==="; systemctl list-units --type=service --state=running --no-pager
>   echo "=== listen ==="; ss -tulpn
> } > /root/baseline/post-hardening.txt'
>
> diff /root/baseline/pre-hardening.txt /root/baseline/post-hardening.txt | grep '^<' | head -20
>
> # 量化
> PRE=$(sudo grep -c 'LISTEN' /root/baseline/pre-hardening.txt)
> POST=$(sudo grep -c 'LISTEN' /root/baseline/post-hardening.txt)
> echo "監聽埠：$PRE → $POST"
> ```
> ★★★★ 這份對照就是交付驗收時最有說服力的文件，
> 也是 [[020-02-03-01-svc-標準化-新機建置標準流程]] 交付單的附件。

```bash
sudo passwd -l root
```

Q7. 下列哪一個 `sysctl` 設定在 **Docker 宿主機**上絕對不能設？
   (A) `net.ipv4.tcp_syncookies = 1`
   (B) `net.ipv4.ip_forward = 0`
   (C) `kernel.randomize_va_space = 2`
   (D) `fs.suid_dumpable = 0`

Q8. 是非題：把 `/tmp` 掛上 `noexec` 之後，攻擊者就完全無法在 `/tmp` 執行他丟進去的程式。

Q9. 為什麼在 Ubuntu 上不應該用 `install squashfs /bin/false` 停用 squashfs 模組？

Q10. 攻擊者用一般帳號登入後 `sudo su -` 變成 root，再修改 `/etc/sudoers.d/`。
   在 auditd 的事件裡，哪一個欄位仍然能追出「最初登入的是誰」？

> [!question]- 測驗答案
> **Q1. (A)** ★★★★★
> 全世界的掃描器持續在掃整個 IPv4 空間，通常**十分鐘內**就會有第一次 SSH 嘗試。
> 「沒人知道這台」是無效的假設 —— 攻擊者掃的是位址，不是單位。
> → 見〈觀念說明 · 威脅模型：新機上線的前十分鐘〉。
>
> **Q2. `Failed password for root` 更危險** ★★★★★
> `Invalid user admin` 代表這個帳號**不存在**，攻擊者在盲猜；
> 而 `Failed password for root` 代表 root 帳號**存在、而且允許密碼登入** ——
> 表示 `PermitRootLogin` 沒關好，攻擊者只需要猜對密碼就進來了。
> → 見〈觀念說明 · 這是真的 log，不是示意圖〉。
>
> **Q3. 錯** ★★★★
> 若同時存在 `foo.socket` 且仍在監聽，只要有人連進來 systemd 就會把 `foo.service` 拉起來。
> 要一起 `disable --now foo.socket`，或用 `systemctl mask` 徹底封死。
> → 見〈安裝或基礎操作 · 3-2〉的 danger 區塊。
>
> **Q4.** ★★★★★
> - `passwd -l root`：在密碼雜湊前加 `!` 前綴，**密碼還在但無法使用**，可用 `passwd -u` 解鎖。
> - `passwd -d root`：**刪除密碼欄位**，在某些 PAM 設定下等同「空密碼可登入」，是嚴重風險。
>
> **永遠用 `-l`，永遠不要用 `-d`。** 驗證用 `passwd -S root`，第二欄應顯示 `L`。
> → 見〈進階應用 · 4-1〉。
>
> **Q5.** ★★★★★
> `ufw` 的預設政策是 `deny incoming`。先 `enable` 再加規則的話，
> **enable 的瞬間 22 埠就被擋掉**，你的 SSH 連線建立不了新的，等於把自己鎖在門外。
> 正確順序是規則全部加完、`ufw show added` 確認過，最後才 enable，
> 並且事前開好第二條連線 + 設 `systemd-run --on-active=10min ... ufw --force disable` 當保險。
> → 見〈完整實戰範例 · 步驟 6〉。
>
> **Q6. `needrestart` 造成的** ★★★★
> `libssl` 等函式庫被自動更新後，`needrestart` 依 `$nrconf{restart}` 設定決定要不要重啟受影響的服務。
> 設為 `'a'` 就會自動重啟。正式環境改成 `'l'`（只列出不動作），
> 把重啟排進維護時段；或把該服務加入 `Unattended-Upgrade::Package-Blacklist`。
> → 見〈進階應用 · 5-3〉。
>
> **Q7. (B)** ★★★★★
> Docker 需要 `ip_forward = 1` 才能讓容器對外通訊（Docker 啟動時也會自己設回 1）。
> 把它硬設成 0 會造成容器完全沒有網路，而且因為 Docker 會覆蓋，
> 排錯時會出現「設定檔明明寫 0，實際卻是 1」的混淆。同理適用於 VPN 端點、NAT 閘道與 K8s node。
> → 見〈進階應用 · 6-1〉的 danger 區塊。
>
> **Q8. 錯** ★★★★
> `noexec` 只擋 `execve` 直接執行。攻擊者仍可用
> `/lib64/ld-linux-x86-64.so.2 /tmp/payload` 透過動態載入器繞過，
> 或改用 `bash /tmp/script.sh`（由 shell 解譯而非執行）。
> `noexec` 的價值在於**擋掉大量自動化攻擊腳本**，是減速丘不是牆。
> → 見〈進階應用 · 6-2〉的 warning 區塊。
>
> **Q9.** ★★★★★
> Ubuntu 的 snap 完全依賴 squashfs。停用之後 `snapd` 會壞掉，
> 所有用 snap 安裝的東西（`lxd`、`certbot`、部分廠商工具）都起不來。
> 很多 CIS / 基準範本列了這一項，是因為它們預設環境不用 snap ——
> **照抄基準範本而不理解環境，是加固最常見的翻車方式**。
> → 見〈進階應用 · 6-4〉的 danger 區塊。
>
> **Q10. `auid`（audit UID，又稱 loginuid）** ★★★★★
> `auid` 記錄的是**最初登入 session 的使用者**，不會因為 `su`、`sudo` 而改變。
> 所以即使事件的 `uid=root`、`euid=root`，`auid=ops` 仍然指出是誰做的。
> 這是共用 root 的環境下唯一還追得回人的線索，也是 auditd 相對於一般日誌的核心價值。
> → 見〈進階應用 · 7-1〉。
