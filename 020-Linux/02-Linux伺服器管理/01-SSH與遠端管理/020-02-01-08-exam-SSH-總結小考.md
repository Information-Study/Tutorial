## 是非題（50 題）

Q1. 客戶端看到 `Permission denied (publickey).`，代表 TCP 連通、協定版本協商、演算法協商、主機金鑰驗證這四關全部都過了，問題只剩使用者認證這一段。

Q2. 用 `ssh-keyscan -t ed25519 <IP> | ssh-keygen -lf -` 取回的指紋，拿去跟第一次連線畫面上顯示的指紋比對，兩者相符就足以確認沒有中間人。

Q3. 看到 `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!` 時，最快也最正確的處置是直接跑 `ssh-keygen -R <host>` 把舊記錄刪掉再重連。

Q4. 從 VM 範本 clone 出十台機器卻沒有重新產生 host key，這十台會共用同一把主機私鑰，攻破其中任何一台就能無警告地冒充其餘九台。

Q5. `ssh user@host '指令'` 回傳 exit code 255，代表遠端那條指令執行後回傳了 255。

Q6. OpenSSH 8.8 起預設停用的是 `ssh-rsa` 這個「RSA + SHA-1 簽章演算法」，不是 RSA 金鑰本身；同一把 RSA 金鑰改用 `rsa-sha2-256` / `rsa-sha2-512` 簽章仍可正常使用。

Q7. `StrictHostKeyChecking accept-new` 對「沒看過的新主機」與「已登記過卻換了金鑰」的主機都會自動接受，跟 `no` 的唯一差別是會多印一行警告。

Q8. 家目錄權限是 775（群組可寫）時，`StrictModes yes` 的 sshd 會直接忽略 `authorized_keys`，而客戶端就算加 `-vvv` 也只會看到 `Permission denied`，真正原因只在伺服器端日誌裡。

Q9. `ssh-keygen -y -P "" -f <私鑰>` 若成功印出公鑰，代表這把私鑰有設定 passphrase、保護良好。

Q10. `ssh -A`（agent forwarding）轉發到跳板機上的是私鑰檔本身，所以只要那個 socket 檔案權限是 600，別人就拿不走你的身分。

Q11. `authorized_keys` 的 `from=` 必須寫「伺服器實際看到的來源 IP」；走 NAT 或 ProxyJump 時，那不是你筆電的內網 IP。

Q12. 在命令列加上 `-i ~/.ssh/某把金鑰`，就足以讓 ssh 只送出這一把金鑰、不再嘗試 agent 裡的其他金鑰。

Q13. `authorized_keys` 的變更不需要 reload sshd，存檔後對新連線立刻生效 —— 這既方便，也代表貼錯會立刻生效。

Q14. `expiry-time=` 到期之後是靜默拒絕，客戶端只看得到 `Permission denied`，`Authentication refused: expired key` 這行只會出現在伺服器端日誌。

Q15. `~/.ssh/config` 的解析規則跟 Nginx 的 `conf.d` 一樣是「後面的蓋掉前面的」，所以 `Host *` 這種共用設定應該寫在檔案最前面。

Q16. `Host web01` 比對的是你在命令列打的字串（originalhost），跟這個別名的 `HostName` 解析成什麼 IP 完全無關。

Q17. `ssh -G web01` 印出的 `hostname` 如果等於 `web01`（別名本身），代表沒有任何 `Host` 區塊匹配到這個別名。

Q18. `ssh -G` 顯示的是新設定、實際 `ssh` 進去卻還是舊行為時，第一個該做的是 `ssh -O exit <別名>` 清掉 ControlMaster 的舊 socket。

Q19. `~/.ssh/config` 的權限是 644 時，ssh 會直接印 `Bad owner or permissions` 並拒絕連線。

Q20. 用 `ProxyJump` 連內網主機時，目標主機的 host key 驗證是在跳板機上完成的，所以目標的 known_hosts 要放在跳板機上。

Q21. `ProxyCommand ssh -W %h:%p bastion` 裡的 `%h` 展開成解析後的 HostName；若誤寫成 `%n` 會變成別名，跳板機上解析不到而失敗。

Q22. `sshd_config` 跟 `~/.ssh/config` 一樣是「第一個讀到的值勝出」，所以 `Include` 寫在主檔第 1 行時，`sshd_config.d/` 裡的設定一定贏過主檔。

Q23. `sshd_config.d/` 底下多個檔案設了同一個關鍵字時，檔名字典序**在後面**（數字大）的那個會勝出。

Q24. `sudo sshd -t` 沒有輸出、回傳 0，就代表這份設定不會把你自己鎖在外面。

Q25. 只寫 `PasswordAuthentication no` 而沒有一併把 `KbdInteractiveAuthentication` 設成 `no`，攻擊者仍可走 keyboard-interactive 經 PAM 的 `pam_unix` 撞同一組密碼。

Q26. Ubuntu 22.10 起預設走 systemd socket activation，此時 `sshd_config` 的 `Port` 與 `ListenAddress` 不會被使用，而 `systemctl status ssh` 顯示 `inactive (dead)` 是正常現象。

Q27. 在 `ssh.socket` 的 drop-in 裡只寫一行 `ListenStream=2222`（前面沒有空的 `ListenStream=`），22 埠就會被 2222 取代。

Q28. `Match` 區塊的效力會延伸到下一個 `Match` 或檔案結尾，所以寫在 `Match` 之後那些「以為是全域」的設定其實只對該條件生效，而 `sshd -t` 抓不出這個錯誤。

Q29. `MaxStartups 10:30:100` 的意思是「這台機器最多只接受 10 條 SSH 連線」。

Q30. `ssh -L 13306:127.0.0.1:3306 db01` 裡的 `127.0.0.1` 指的是你自己這台工作站的 loopback。

Q31. `-L` 是在客戶端 listen、由 SSH 伺服器發起最終連線；`-R` 是在伺服器 listen、由你的客戶端發起最終連線。

Q32. 本機埠已被占用時，ssh 預設仍會連線成功，只是印幾行警告然後把那條轉發丟掉 —— 這正是「隧道明明在跑、DBeaver 卻連到上週的舊隧道」的成因。

Q33. 設了 `ExitOnForwardFailure yes` 之後，後端服務（例如 MySQL）掛掉時 ssh 也會跟著結束，所以監控只要看 ssh 行程還在不在就夠了。

Q34. `curl --socks5 127.0.0.1:1080 http://intranet.example.gov.tw/` 的 DNS 查詢是在遠端 SSH 伺服器上解析的，不會外洩內部網域名稱。

Q35. `sshd_config` 的 `AllowTcpForwarding local`，這個 `local` 是站在 **ssh 客戶端**的角度看的，意思是只准客戶端的 `-L` 與 `-D`。

Q36. 客戶端看到 `channel 3: open failed: administratively prohibited: open failed`，代表目標主機那個埠上沒有服務在聽。

Q37. `ChrootDirectory` 指到的目錄，以及它往上的每一層目錄，都必須由 root 擁有且 group 與 other 不可寫。

Q38. chroot 環境下只要把 `/usr/lib/openssh/sftp-server` 連同依賴的函式庫複製進牢籠，效果就跟 `internal-sftp` 一樣，兩者可以互換。

Q39. 受限帳號的 `authorized_keys` 應該放在 chroot 之外（例如 `/etc/ssh/authorized_keys/%u`）並由 root 擁有，因為 sshd 是在 chroot **之前**用真實路徑讀這個檔案。

Q40. 由於 chroot 根目錄依規定不可被使用者寫入，受限帳號一定要另外建立可寫的子目錄，否則會出現「連得上，但 `put` 一律 Permission denied」。

Q41. 要停用一個委外廠商的 SFTP 帳號，執行 `usermod -L vendor01` 把密碼鎖起來就足夠了。

Q42. 只要 `ForceCommand internal-sftp -l INFO` 設好，chroot 帳號的傳輸紀錄就一定會出現在 syslog 裡。

Q43. `setfacl -m g:www-data:r-x upload/` 一下去，之後新上傳到該目錄的檔案也會自動繼承這條 ACL。

Q44. `AuthenticationMethods publickey,keyboard-interactive`（逗號分隔）表示兩種都要依序通過；改用空白分隔則變成任一種通過即可。

Q45. `Ciphers`、`MACs`、`KexAlgorithms` 可以寫在 `Match Address` 區塊裡，針對特定來源網段做演算法例外。

Q46. 把 SSH 從 22 改到 52222 之後，稽核報告可以寫「提升安全性」，因為攻擊者已經找不到管理埠。

Q47. SSH CA 的使用者 CA 與主機 CA 必須分開，而且 CA 私鑰不可以放在任何一台被該 CA 信任的伺服器上。

Q48. 憑證式認證能不能登入，取決於「憑證上 `-n` 指定的 principals」與「`AuthorizedPrincipalsFile` 對應該本機帳號的那個檔案內容」有沒有交集。

Q49. 簽發憑證時用了 `-O clear` 卻沒有補回 `-O permit-pty`，使用者會認證成功但拿不到終端機，出現 `PTY allocation request failed on channel 0`。

Q50. 加固完之後，用平常那條 `ssh web01` 重新連線成功，就足以證明新設定沒有把人鎖在外面。
