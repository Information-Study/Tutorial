## 是非題（50 題）

Q1. 一台伺服器只要裝好、服務跑得起來、使用者連得上，就算完成交付；簽核頁只是行政程序，缺了不影響。

Q2. 建置申請單的「資料分類等級」必須在開機前就決定，因為它決定磁碟要不要加密、日誌保留多久、以及除役時的抹除方式。

Q3. 要確認一個 IP 有沒有被佔用，最可靠的方法是先 ping 它，ping 不通就代表沒人在用、可以拿來配發。

Q4. 停用 SSH 密碼登入之前，必須另開一個**新的** session 實測公鑰登入與 sudo 成功，而且原本那條 session 全程不可以關掉。

Q5. 在 Ubuntu 24.04 上，只要把 `/etc/ssh/sshd_config` 裡的 `PasswordAuthentication` 改成 `no` 並 reload，密碼登入就一定關掉了。

Q6. 根目錄被暴增的日誌塞爆時，用 `truncate -s 0` 清空該檔比 `rm` 好，因為程式還開著那個檔案，`rm` 不會把空間釋放出來。

Q7. 監控 agent 的 `systemctl is-active` 顯示 `active`，就代表「監控納管」這一項驗收通過。

Q8. 「備份排程建好、而且已經跑過一次成功」還不算驗收通過，必須已經從那份備份還原過一個檔案到暫存目錄並比對內容一致。

Q9. 時區與 NTP 可以等機器上線、日誌開始送到集中平台之後再補設，因為已經送出去的日誌之後可以回溯校正時間。

Q10. 建置紀錄的三個載體（`script` 側錄 log、`build-record.md`、etckeeper）缺一不可，因為它們涵蓋的時間範圍互不重疊。

Q11. 在範本檔頭加上 render 的時間戳，可以讓人一眼看出這份設定是什麼時候產生的，是建議做法。

Q12. 裸跑 `envsubst`（不給白名單）會把範本裡 `$remote_addr`、`$NF` 這類**合法變數名**一併換成空字串，但 `$1` 因為不是合法變數名而不受影響。

Q13. `envsubst` 遇到白名單內但**未定義**的變數時，會把它換成空字串，而且退出碼仍然是 0。

Q14. 四層覆寫模型裡，下層的清單型變數會自動與上層合併，所以角色層只要寫新增的那幾條規則就好。

Q15. 從 `/run`（tmpfs）直接 `mv` 設定檔到 `/etc` 不是原子操作，因為跨檔案系統的 `mv` 實際上是「複製 + 刪除」。

Q16. `sshd -t` 回傳 0，就代表套用這份設定之後你一定連得進來。

Q17. 單機例外必須同時寫上原因、核准人與到期日；而且同一個例外出現在三台以上，就該升級成角色層或環境層。

Q18. 漂移偵測 timer 抓到差異時，應該讓排程自動把設定回填成基準值，這樣一致性才有保障。

Q19. 封裝 golden image 前只要清掉日誌與 bash history 就夠了；`machine-id` 與 SSH 主機金鑰保留下來反而方便統一管理。

Q20. 變數一律加 `BASELINE_` 前綴的實際理由，是讓 envsubst 的白名單能靠前綴自動、完整地產生，同時避免撞到 `TZ`、`LANG` 這類真實環境變數。

Q21. 用 https 從官網把金鑰檔抓下來，就已經完成金鑰驗證了。

Q22. 把第三方金鑰放進 `/etc/apt/trusted.gpg.d/` 等同於 `apt-key add` 的全域信任模型，它可以拿來驗證**任何**來源的 Release 檔。

Q23. 比對金鑰指紋時，比對前 8 碼與後 8 碼一致即可，因為 32-bit short ID 的碰撞在實務上不可能發生。

Q24. 只設了 `.sources` 與 keyring、卻沒有設 pinning 的第三方庫，會拿到和官方庫一樣的預設優先權 500，因此有權覆蓋你的 `libc6`。

Q25. 看到 `E: Release file for ... is expired`，最快也最正確的解法是設 `Acquire::Check-Valid-Until "false";` 讓 apt 不再檢查。

Q26. `Pin: origin "deb.myguard.nl"` 裡的 origin 比對的是**主機名稱**，而 `Pin: release o=MyGuard` 的 `o=` 才是 Release 檔的 `Origin` 欄位。

Q27. 裝了 `unattended-upgrades` 之後，第三方庫的套件也會被納入自動更新而收到安全修補。

Q28. 撤除第三方套件庫時，把 `/etc/apt/sources.list.d/` 底下那個來源檔 `rm` 掉，就算撤除完成了。

Q29. keyring 檔權限設成 `0600` 會讓 `_apt` 使用者讀不到而導致驗簽失敗，正確權限是 `0644 root:root`。

Q30. 一個 `.deb` 在安裝時會以 root 身分執行 maintainer script，所以「加一個第三方套件庫」等於把一個外部組織持續性地加進你的 root 信任清單。

Q31. 簽章私鑰不可以放在對外提供服務的發布機上；正確做法是 reprepro 與 GPG 私鑰只留在建置機，再用單向 rsync 把靜態檔推到發布機。

Q32. 套件升級時只會呼叫**新**套件的 `postinst`，舊套件的 `postrm` 不會被執行，所以 `postrm` 不需要做 `case "$1"` 分流。

Q33. `conffiles` 可以等到有人反映「我改的設定升級後不見了」再補進去；補上之後，使用者原有的修改就會受到保護。

Q34. `dpkg-deb --build` 沒有加 `--root-owner-group` 時，deb 內會記錄你當下的 uid/gid，裝到別台機器上檔案就變成某個不相干使用者所有。

Q35. 版本號 `1.2.3-1~noble1` 在排序上大於 `1.2.3-1`，所以移植版會贏過官方正式版。

Q36. 撤銷憑證必須在建立金鑰時就產生並離線保存，因為產生撤銷憑證需要私鑰，一旦私鑰遺失就再也產不出來了。

Q37. 套件庫改走 HTTPS 之後，客戶端就可以寫 `Trusted: yes` 省掉 GPG 簽章驗證，因為傳輸過程已經被保護了。

Q38. reprepro 每個 codename 只保留一個版本，所以要能回退就必須把**每一個發布過的 deb 都留檔**。

Q39. 內部庫的 pinning 用 `Package: *` 搭配 `Pin-Priority: 1001` 是最安全的做法，可以確保內部套件永遠優先。

Q40. 更換簽章金鑰時，必須先把「新舊兩把公鑰」派送到每一台客戶端並確認 100% 覆蓋，才可以切換 `SignWith`。

Q41. Ansible 是 agentless 的，所以可以直接用它完成「建立 VM → 裝 OS → 設定 IP」這整個 provision 階段。

Q42. playbook 寫完要連跑兩次，第二次必須是 `changed=0`；還有 `changed` 就代表有 task 不冪等。

Q43. `ansible.builtin.command` 模組會自己判斷有沒有真的改到東西，所以拿它寫 playbook 一樣能維持冪等。

Q44. `group_vars/web.yml` 的 `baseline_packages` 會**整個取代** `group_vars/all.yml` 的同名變數，而不是附加上去。

Q45. 遇到 `Host key verification failed` 時，最快也最正確的解法是在 `ansible.cfg` 設 `host_key_checking = False`。

Q46. playbook 裡 ufw 的 task 必須先 `allow 22` 再 `enable`；順序反過來會在 enable 那一刻把自己鎖在外面。

Q47. `cloud-init clean --logs --reboot` 是修正正式機設定的標準做法，因為它會讓 cloud-init 重新套用最新的 user-data。

Q48. `--check --diff` 乾跑時出現一堆紅字，不一定代表 playbook 有錯——因為 check 模式下前面的 task 沒有真的執行，後面依賴它的 task 會誤判失敗。

Q49. 導入自動化之後，因為工具本身會確保一致性，所以回滾方案可以等真的出事再設計。

Q50. 控制節點上那把能免密登入所有受管節點的私鑰，其保護等級必須高於任何一台受管伺服器。

> **Q1. ✗**
> 「裝好了」和「交付」是兩件事。★★★★★ 一台沒有簽核的機器，出事時沒有任何法律與稽核意義：
> 沒有人能說出它上線時是什麼狀態、誰核准的、當時的例外項是誰同意的。
> 交付單上「紅線項失敗數必須為 0」與「覆核人不得與建置人為同一人」這兩條，正是為此存在。
> 而且驗收必須在**交付當下**跑完——那是唯一一個所有資訊還在建置人腦子裡的時刻。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q2. ○**
> 資料分類等級（公開／內部／敏感／個資）是★★★★★級必填欄位，因為它一口氣決定四件事：
> 磁碟要不要加密、備份保存年限、日誌保留期、以及除役時要用實體銷毀還是密碼學抹除。
> 更關鍵的是時機：開機**之後**再去問業務單位，得到的答案永遠是「都可以、你決定就好」；
> 開機**之前**問，對方還需要你幫他開機，會認真回答。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q3. ✗**
> ★★★★「ping 不通就代表沒人用」是本章點名的典型誤解。至少四種情況會 ping 不通卻確實被佔用：
> 機器關機中（冷備）、防火牆擋 ICMP（多數加固過的主機都擋）、保留給 DHCP pool 或 VIP、
> 以及網路設備的管理介面（交換器、UPS、冷氣監控、門禁）。
> 唯一合法的取得方式是從盤點表的位址表配發並當場登記回去；配發後再用 `arping -c 3` 複驗，
> 收到任何 response 就代表已被佔用，停手回報。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q4. ○**
> ★★★★★ 帳號初始化的六步順序不可顛倒：建帳號 → 加 sudo → 部署公鑰 → **另開 session 實測**
> → 確認成功後才停用 root 與密碼登入 → reload 後開第三個 session 複驗。
> 把「停用密碼」做在「實測公鑰」之前，而公鑰剛好有問題（權限錯、多了換行、貼錯家目錄），
> 結果就是你和所有人都登不進去，遠端機房要開工單、雲端要開 console，少則兩小時多則隔天。
> 舊 session 是唯一的救命繩，全程不能關。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q5. ✗**
> ★★★★★ Ubuntu Server 24.04 從 ISO 安裝後會留下 `/etc/ssh/sshd_config.d/50-cloud-init.conf`，
> 裡面寫著 `PasswordAuthentication yes`。而 `sshd_config` 開頭就有 `Include sshd_config.d/*.conf`，
> 加上 sshd 的規則是「**第一個出現的設定值獲勝**」——所以 50 那個檔會贏，你改的完全不生效。
> 正確做法是改掉 50 那個檔或新增排序更前面的 `10-hardening.conf`，
> 並且★★★★ **一律以 `sshd -T` 的輸出為準**，不要 grep 設定檔。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q6. ○**
> 檔案被程式開著時，`rm` 只是移除目錄項目，inode 還被 fd 參照著，空間不會釋放；
> `truncate -s 0` 才會真的把空間交還檔案系統，而且程式可以繼續寫。
> 但這只是急救：★★★★ `rm` 還有第二個問題是**銷毀稽核軌跡**，屬於安全性注意事項裡明列的禁止行為。
> 根治方式是有 LVM 留白時 `lvextend` + `resize2fs` 線上擴充，並把 `/var/log` 獨立分割。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q7. ✗**
> ★★★ `active` 只代表 agent 這支程式在跑。真正的驗收是在**平台端**：
> 監控平台上看得到這台的最新資料點（時間差 < 5 分鐘），而且★★★★ 更實際的做法是
> **故意觸發一次告警**，確認通知真的送到申請單上填的那個人手上。
> 「沒有通知對象的監控等於沒有監控」——機器掛了三天沒人知道，多半就是這一項只驗了 `is-active`。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q8. ○**
> ★★★★★ 備份驗收有三個條件：① 排程存在且已啟用 ② 已經跑過至少一次且結果成功
> ③ **已經從那份備份還原過一個檔案並比對內容一致**。
> `systemctl list-timers` 的 `LAST` 欄位若是 `n/a` 代表從來沒跑過，
> `systemctl show backup.service -p ExecMainStatus --value` 必須是 `0`。
> 「硬碟壞掉才發現這台從沒被備份過」是本章列的六種典型災難之一，所以它是紅線項。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q9. ✗**
> ★★★★ 一旦機器開始把日誌送到集中平台，**時間戳就變成證據**，而已經送出去的日誌無法回溯修正——
> 那段期間等於沒有紀錄。時區沒設好會壞掉的東西包含：SIEM 事件關聯（登入事件比防火牆事件早 8 小時，
> 關聯規則永遠不觸發）、Kerberos／AD 加入網域（時間差超過 5 分鐘直接拒絕認證）、
> 憑證驗證（`certificate is not yet valid`），以及稽核軌跡的證據力。
> 所以時區、NTP、硬體時鐘 UTC 這三件事必須在階段【5】納管**之前**完成。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q10. ○**
> ★★★ 三個載體的時間範圍刻意錯開：`script` 側錄只涵蓋建置期間、記「打過哪些指令」；
> `build-record.md` 是建置當下的快照、記「為什麼這樣做」與例外是誰核准的；
> etckeeper 從交付之後持續、記「`/etc` 之後被誰改了什麼」。
> 少了 build-record，建置人離職後這台就變成「不敢動的黑盒子」。
> 注意 etckeeper 的 repo 含 `/etc/shadow` 與主機私鑰，權限必須 700 且★★★★★ 禁止外推。
> → 詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]
>
> **Q11. ✗**
> ★★★★★ 這是本篇明列的反面做法。加了時間戳之後，每天 06:00 的漂移偵測 render 出來的內容
> 一定跟線上檔不同 → 每天每台都報「有漂移」→ 三天後所有人開始忽略這份報告 →
> **真的漂移發生時沒有人看**。
> 檔頭只該放**會隨基準版本改變**的東西（`BASELINE_VERSION`、聯絡窗口）——
> 這樣某台還停在舊基準版本時，diff 會漂亮地在第一行告訴你，那才是有用的差異。
> → 詳見 [[020-02-03-02-ref-標準化-基準設定與範本化]]
>
> **Q12. ○**
> ★★★★★ 這正是 envsubst 三個坑裡最陰的一個：`$1` 活著、`$NF` 死了。
> 因為 envsubst 只取代符合 `[A-Za-z_][A-Za-z0-9_]*` 的名字，`$1` 不符合所以被留下。
> 危險在於：你在範本裡測了幾個 `$1`、`$2` 覺得沒事，結果 `$remote_addr`、`$host`、`$NF`、
> `$SERVER_NAME` 這些全部變成空字串，nginx 的 log_format 就這樣壞掉。

Q51. 你在一台剛裝好的 Ubuntu 24.04 上，把 `/etc/ssh/sshd_config` 的 `PasswordAuthentication` 改成 `no` 並 `systemctl reload ssh`，但 `sshd -T` 仍然回 `passwordauthentication yes`。最該先做什麼？

Q52. 為什麼「時區、NTP、硬體時鐘 UTC」這三件事必須在納管**之前**完成？
(A) 日誌一開始送到集中平台就變成證據，而已送出的時間戳無法回溯修正 (B) NTP 服務啟動後系統就不允許再更改時區 (C) 監控 agent 安裝時會把硬體時鐘設定鎖定 (D) chrony 只能在首次開機的初始化階段設定

Q53. 關於 `/var/log` 要不要獨立分割，下列敘述何者正確？
(A) 只有跑資料庫或郵件佇列的主機才需要分 (B) 分割之後就不必再設 logrotate (C) 分割會讓 journald 無法做持久化儲存 (D) 只要這台會產生日誌就該分，否則日誌暴增會塞爆 `/`，連 ssh 登入都會失敗

Q54. LVM 建議只配發 60～70% 的 VG 容量，主要理由是什麼？
(A) 檔案系統使用率超過 70% 之後會嚴重碎片化 (B) 留白讓事故當下能線上 `lvextend` + `resize2fs` 擴充，不必停機也不必刪日誌湮滅稽核軌跡 (C) LVM 的 metadata 本身需要保留 30% 的空間 (D) 為了讓快照有地方存放一份完整副本

Q73. 「有限度信任」的 preferences 設計中，把整個第三方庫壓到 `Pin-Priority: 100` 的實際效果是？

Q74. 你把放行清單寫成 `Package: nginx-* libnginx-mod-*`，結果 `apt install nginx` 裝到的仍是官方的 1.24 而不是第三方的 1.29。原因是？

Q75. 在 pinning 檔中「明確把 `libc6`、`openssl`、`systemd`、`openssh-*` 設成 `Pin-Priority: -1`」的用意是？
(A) 讓這些套件能夠從第三方版本降版回官方版本 (B) 減少 apt 的候選版本數量以加快相依解析 (C) 防呆 —— 即使將來有人把放行清單的萬用字元寫得太寬，這一段仍然擋得住 (D) 讓 `unattended-upgrades` 自動跳過這些套件

Q76. `apt-repo-audit` 稽核報告裡 `__ORPHAN__` 那一列不是 0，代表什麼？
(A) 有套件的 GPG 簽章驗證失敗 (B) 有來源檔缺少 `Signed-By` 綁定 (C) 有金鑰即將在 90 天內到期 (D) 有已安裝的套件已無任何來源提供，它永遠收不到安全更新，而且 apt 不會提醒你

Q77. 撤除第三方套件庫的七步流程中，為什麼要「先把 `Pin-Priority` 設成 -1，再處理已安裝的套件」？
(A) 先斷金流再處理存貨 —— 避免降版過程中 apt 又從該庫把新版抓回來 (B) 設成 -1 會讓 apt 自動把該庫的套件降回官方版本 (C) 這是移除 keyring 檔的必要前置條件 (D) -1 會讓 `apt update` 跳過該庫的索引下載，加快後續操作

Q78. `apt update` 報 `E: Conflicting values set for option Signed-By regarding source https://…`。最可能的原因是？

Q79. 關於 `unattended-upgrades` 與第三方庫的互動，下列何者是本手冊的建議做法？
(A) 完全不納入，第三方套件一律人工更新，也不必額外記錄 (B) 全部納入，讓所有漏洞都能自動補上 (C) 把第三方庫的 `Pin-Priority` 提高到 1001，確保自動更新一定拿得到新版 (D) 納入 `Allowed-Origins`，但配 `Package-Blacklist` 排除需要重啟服務的套件，並先在測試機跑滿 48 小時

Q80. 你在一台接手的舊機上看到 `/etc/apt/trusted.gpg` 裡有一把 Docker 金鑰，但來源清單裡已經沒有 `download.docker.com`。這代表什麼、該怎麼做？
(A) 這是 Ubuntu 官方預裝的 keyring，不要動它 (B) 來源檔被誤刪，應該把 Docker 來源重新加回來 (C) 這是一把沒有對應來源、且屬於全域信任的孤兒金鑰；先備份，再用完整指紋刪除，然後 `apt update` 確認沒有來源因此變成 `NO_PUBKEY` (D) 直接用短 ID `apt-key del` 即可，不需要額外驗證

Q81. 「誰拿到簽章私鑰，誰就能對全機關每一台機器推送任意套件」，這句話成立的根本原因是？
(A) 客戶端的信任鏈只驗 `InRelease` 的簽章，而 `.deb` 的 maintainer script 是以 root 執行的任意程式碼 (B) reprepro 的 `db/` 目錄可以被遠端讀取 (C) apt 在安裝時不會比對 `.deb` 的 SHA256 (D) HTTPS 憑證與 GPG 簽章共用同一份私鑰

Q82. 某次例行升級之後，全機關的內部 HTTPS 服務同時開始噴憑證錯誤。最可能的根因是？
(A) 機關根 CA 憑證剛好在那天到期 (B) 客戶端時鐘不同步導致憑證驗證失敗 (C) 套件的 `postrm` 沒有 `case "$1"` 分流，升級時舊版 postrm 以 `upgrade` 被呼叫，刪掉了新版剛解開的憑證 (D) `update-ca-certificates` 沒有被寫進 `Depends`

Q83. 你把根憑證放進 `/usr/local/share/ca-certificates/org-root-ca.pem`，套件裝成功、`postinst` 也回傳 0，但憑證就是沒生效。原因是？
(A) 該目錄需要 0700 權限才會被掃描 (B) `update-ca-certificates` 只處理副檔名為 `.crt` 且內容為 PEM 的檔案，其餘會被安靜忽略 (C) 憑證必須直接放在 `/etc/ssl/certs/` 才算數 (D) `Architecture: all` 的套件不會把檔案寫進 `/usr/local`

Q84. 關於 `conf/distributions` 的 `SignWith` 欄位，下列敘述何者正確？
(A) 它決定客戶端 `Suites:` 欄位要填什麼值 (B) 它只影響 `Release.gpg`，`InRelease` 不受它影響 (C) 省略它時 reprepro 會自動挑一把可用的金鑰來簽 (D) 有它才會產生 `InRelease`；沒有的話客戶端只能用 `[trusted=yes]`，而那等於關掉驗簽，是禁止的

Q85. `Architecture: all` 的套件匯入 reprepro 時被拒。最可能的原因是？
(A) `conf/distributions` 的 `Architectures` 沒有列出 `all` (B) `Components` 填了 `main` 以外的值 (C) 版本號沒有加上 `-1` 這樣的 Debian revision (D) control 檔沒有寫 `Depends` 欄位

Q86. 升級後發現某個套件把服務弄壞了，40 台受影響。用 aptly 的最佳止血順序是？
(A) 先逐台 `apt install pkg=舊版` 加 `apt-mark hold`，最後再 `publish switch` (B) 先 `aptly publish switch` 切回舊快照止血（避免更多機器踩到），再處理已升級的機器降版 (C) 直接 `aptly snapshot drop` 掉壞掉的快照，客戶端會自動回退 (D) 把該套件從 `pool/` 刪除，客戶端下次 `apt update` 就會自動降版

Q87. 為什麼 `/etc/apt/auth.conf.d/*` 的權限必須是 `0600 root:root`？
(A) 因為 apt 會拒絕讀取權限過寬的設定檔 (B) 因為它是二進位格式，權限過寬會被 apt 判定為損毀 (C) 因為 `_apt` 使用者需要對它有獨佔寫入權 (D) 因為它是明文密碼；預設 umask 022 產生的 0644 會讓任何本機使用者與 `www-data` 都讀得到，而這組密碼通常對所有機器都一樣

Q88. 內部庫的 pinning 用 `Package: *` 搭配 `Pin-Priority: 1001`，最嚴重的風險是？
(A) 內部套件反而會被官方版本蓋掉 (B) apt 會拒絕安裝任何官方庫的套件 (C) 只要有人不小心把一個舊版 `openssl` 匯進內部庫，全機關的 openssl 都會被降版並停住，官方安全更新永遠裝不上去，而且 apt 不會警告 (D) 1001 會讓 `unattended-upgrades` 完全失效

Q89. `apt upgrade` 完全不動你剛發布的新套件。最該先驗證什麼？
(A) 用 `dpkg --compare-versions` 確認新版本號真的大於舊版（例如誤加了 `~`，或在 `1.10` 之後發了 `1.9`） (B) 確認 `InRelease` 的簽章仍然有效 (C) 確認客戶端 `.sources` 的 `Architectures:` 有寫 amd64 (D) 確認 keyring 檔的權限是 644

Q90. 打包時漏了 `--root-owner-group`，`dpkg-deb -c` 顯示檔案擁有者是 `1000/1000`。正確處置是？
(A) 客戶端安裝後用 `chown` 改回來即可 (B) 重新打包 —— 這是 lintian 的 error 級問題，裝到別台機器上檔案會歸給不相干的使用者 (C) 在 `postinst` 裡加一行 `chown -R root:root` 補救 (D) 忽略它，內部套件本來就不必追求 lintian 零警告

Q91. `ansible all -m ping` 全部 UNREACHABLE，而這批機器是剛用 cloud-init 開起來的。最該先確認什麼？
(A) playbook 的 YAML 縮排有沒有用到 tab (B) 控制節點的 collection 有沒有裝齊 (C) 這是 provision 階段的問題 —— SSH 通不通、公鑰有沒有進去、python3 在不在 (D) `ansible.cfg` 的 `forks` 是不是設太高

Q92. 判斷「值不值得自動化」，本章提出的判準是？
(A) 台數 × 重做頻率 × 出錯代價，並用回收年數估算；回收年數超過 3 年就不要導入 (B) 台數超過 10 台就一定要導入 (C) 只要有對外服務就必須導入 (D) 看團隊裡有沒有人會寫 YAML

Q93. 一支 playbook 第二次執行仍有 `changed`，下列成因中**最危險**的是哪一種？

Q94. 為什麼「先寫 SOP → 再寫獨立驗收腳本 → 最後才寫 playbook」這個順序中，中間那一層不能跳過？

Q95. 關於 PVE 的 `--cicustom`，下列敘述何者正確？
(A) 它會與面板上填的 `ciuser` / `sshkeys` 合併使用 (B) `qm cloudinit dump <vmid> user` 可以印出 snippet 的完整內容 (C) snippet 檔放在任一節點的任一儲存區都可以 (D) 它會**完全取代**面板的 `ciuser`、`cipassword`、`sshkeys`，所以帳號與金鑰都要寫進 snippet 裡

(A) 目前目錄是不是 world-writable —— 是的話 Ansible 會為了安全忽略該目錄下的 `ansible.cfg` (B) `inventory.ini` 的副檔名對不對 (C) `ANSIBLE_CONFIG` 有沒有指到 `/etc/ansible/ansible.cfg` (D) `forks` 是不是被設成 0

Q99. 為什麼 `host_key_checking = False` 是紅線？

> 規模大時改用 SSH 憑證。
> (A) 錯：主機金鑰驗證與客戶端金鑰認證是兩件事，關掉不影響金鑰登入。
> (B) 錯：它只是不檢查，不會清空 `known_hosts`。
> (D) 錯：`--check` 與連線層設定無關。
> → 詳見 [[020-02-03-05-svc-標準化-自動化佈建入門]]
>
> **Q100. (D)**
> ★★★★★ 一台普通 web 伺服器被入侵，損失是一台；控制節點被入侵，損失是**全部**。
> 因為那把私鑰能免密登入所有受管節點，而那些帳號多半設了 `NOPASSWD: ALL` 的 sudo。
> 所以控制節點的保護等級必須高於任何一台伺服器：專用主機、私鑰**必須**設 passphrase、
> 限制管理網段、登入要 MFA 或走跳板機、私鑰不進雲端硬碟與 git、人員異動當天輪換金鑰、
> 並用 `rollout-history.log` 記錄誰在什麼時候用它跑了什麼。
> (A)(B) 錯：都是會讓 playbook 跑不起來的技術問題，屬於可見且可修的失敗，不是風險集中點。
> (C) 錯：Ansible 是 agentless，受管節點不需要裝 agent，這正是它被選為主線的理由之一。
> → 詳見 [[020-02-03-05-svc-標準化-自動化佈建入門]]
