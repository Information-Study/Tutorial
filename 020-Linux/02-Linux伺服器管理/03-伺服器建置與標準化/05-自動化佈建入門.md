# 自動化佈建入門

> [!abstract] 這篇你會學到
> - 用「台數 × 重做頻率 × 出錯代價」判斷**要不要自動化**，而不是憑感覺
> - 分清楚 **provision（機器從無到有）** 與 **configure（維持在期望狀態）** 是兩件事
> - 用 **cloud-init** 讓一台新 VM 開機就有 hostname、網路、管理帳號與公鑰
> - 用 **Ansible** 的四個核心概念（inventory / module / task / 冪等性）跑通一支 baseline playbook
> - ★★★★★ 正式環境的鐵律：**先 `--check --diff` 乾跑 → 再 `--limit` 單一台實跑 → 最後才全面套用**
> - ★★★★★ 為什麼**控制節點的 SSH 私鑰等同全機關 root**，保護等級必須高於任何一台伺服器
> - ★★★★ **先有 SOP 與檢查腳本，才寫 playbook** —— 順序反了就是自動化一份沒人驗證過的流程

## 觀念說明

### ★★★★ 第一個分界：provision 與 configure 不是同一件事

**維運人員導入自動化最常卡住的地方，是把這兩件事混為一談。**

```text
┌───────────────────────── 一台機器的生命週期 ─────────────────────────┐
│                                                                      │
│  【階段 A】provision（佈建）：機器【從無到有】                        │
│  ─────────────────────────────────────────────────                   │
│   建立 VM → 掛磁碟 → 裝 OS → 設 hostname/IP → 開 SSH → 放公鑰        │
│                                                                      │
│   工具： PVE clone + cloud-init                                      │
│          Ubuntu autoinstall（subiquity / preseed 的後繼）            │
│          裸機：PXE + autoinstall、廠商的 iDRAC/iLO 虛擬媒體          │
│                                                                      │
│   ★★★★ 這個階段【Ansible 幫不上忙】——                              │
│         因為此時「SSH 還沒通、公鑰還沒進去、Python 還沒裝」           │
│                                                                      │
│  ══════════════ 交界點：SSH 通了、管理帳號能免密登入 ══════════════   │
│                                                                      │
│  【階段 B】configure（組態管理）：機器【已存在】，維持在期望狀態      │
│  ─────────────────────────────────────────────────                   │
│   時區 / NTP / 套件 / 帳號 / 防火牆 / 服務設定 / 稽核設定            │
│   而且是【每次跑結果都一樣】、【機器飄移了會被拉回來】                │
│                                                                      │
│   工具： Ansible（本篇主線）、Puppet、Chef、Salt                     │
│                                                                      │
│   ★★★ 這個階段會【反覆執行】，不是一次性的                          │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

> [!danger] 最常見的第一次失敗 ★★★★
> ```
> 症狀：「我寫好 playbook 了，可是 ansible all -m ping 全部 UNREACHABLE」
>
> 原因：想用 Ansible 做【開機的第一步】。
>       但 Ansible 是 agentless，它的「agent」就是【SSH + 目標機的 Python】。
>       這兩樣東西必須在 Ansible 出場【之前】就準備好。
>
> ★★★★ 正確順序：
>   cloud-init（或 autoinstall）先把「SSH 通 + 公鑰進去 + python3 存在」做完
>   → 才輪到 Ansible。
>
> ★★ 換句話說：cloud-init 負責【讓 Ansible 進得來】，
>     其他所有事都留給 Ansible —— 不要把整套設定塞進 user-data。
>     理由見下方「為什麼 user-data 不該做太多」。
> ```

### ★★★★ 何時值得自動化：不是看「幾台」

大多數人問的是「幾台以上才需要 Ansible」。這是錯的問題。
**真正的判準是三個量的乘積：**

```text
自動化價值 ≈ 台數 × 重做頻率 × 出錯代價
             ↑      ↑            ↑
             │      │            └─ 一台設錯會怎樣？
             │      │               （純測試機 vs 對外服務 vs 個資系統）
             │      └─ 一年重做／改設定幾次？
             │         （建好就三年不動 vs 每季換版、每月加機器）
             └─ 現在管幾台？未來一年會變幾台？
```

**三台機器、但每個月因為專案改版要重建一次、而且是對外服務** ——
這比「三十台一次建好就三年不碰的內部測試機」更值得自動化。

#### ★★★★ 導入決策表

| 情境 | 台數 | 重做頻率 | 建議做法 | 為什麼 |
| --- | --- | --- | --- | --- |
| 小型內部服務 | 1～3 台 | 一年 1 次以下 | ★ **手動 SOP + 驗收檢查表就夠**（[[01-新機建置標準流程]]） | 導入成本回收不了；SOP 反而更容易交接 |
| 小型但常變動 | 1～3 台 | 一季 1 次以上 | ★★ **基準檔 repo + Ansible ad-hoc 指令** | 不必寫完整 playbook，`-m` 單一模組就有價值 |
| 中型 | 4～15 台 | 一年 2 次以上 | ★★★ **基準 repo + 簡單 playbook（本篇的程度）** | 效益最明顯的區間；不需要 role |
| 大型／有法遵稽核 | 15 台以上 | 任意 | ★★★★ **正式 Ansible + git 版本控管 + 變更管理** | 稽核要「證明所有機器設定一致」，只有程式碼能證明 |
| 有 TWGCB 符合性要求 | 任意台數 | 任意 | ★★★★ **一定要程式碼化**，見 [[06-TWGCB-Linux大量派送]] | 幾百個項目手動做不可能一致，且要能重複產出報告 |
| 純桌機／單機工作站 | 任意 | 任意 | ★ 不要用 Ansible，用映像檔或 GPO | 目標不是伺服器，工具選錯 |

#### ★★★ 導入工時回收的粗估算法

不要用感覺說服長官，用這個算：

```text
【手動成本】 T_manual = 單台手動工時 × 台數 × 年重做次數
【導入成本】 T_setup  = 學習與撰寫工時（第一次，含踩坑）
【自動成本】 T_auto   = 單次執行工時（含檢查與驗收） × 年執行次數
                       + 年維護工時（改 playbook、跟版本）

回收年數 = T_setup ÷ ( T_manual − T_auto )
```

實務上的參考值（機關環境，中等經驗的維運人員）：

| 項目 | 參考值 | 備註 |
| --- | --- | --- |
| 單台照 SOP 手動建置 | **2～4 小時** | ★★ 含網路、帳號、加固、驗收 |
| 第一次導入 Ansible（到本篇程度） | **16～24 小時** | ★★★ 含裝環境、寫 inventory、寫 baseline、踩坑 |
| Ansible 跑一批（含乾跑與驗收） | **20～40 分鐘** | ★ 不論 3 台還是 30 台，時間差不多 |
| 每年維護 playbook | **8～16 小時** | ★★ 跟 OS 版本、修 deprecated 模組 |

> [!tip] 用這組數字算一次 ★★
> 10 台、每年重建 2 次、單台 3 小時
> → `T_manual = 3 × 10 × 2 = 60 小時/年`
> → `T_auto = 0.5 × 2 + 12 = 13 小時/年`
> → 回收年數 `= 20 ÷ (60 − 13) ≈ 0.43 年`（約 5 個月）
>
> ★★★ **反例也要算**：3 台、三年不動、單台 3 小時 → `T_manual = 3 小時/年`。
> 導入成本 20 小時，回收要 **7 年以上** —— 這種情況**寫好 SOP 就好，不要導入**。
> 誠實地算出「不該導入」的結論，比硬導入後沒人維護的半套自動化有價值得多。

### ★★★ 工具選型比較表

比較維度刻意貼機關現實：**人員流動、離線環境、稽核時看不看得懂**，
而不是「哪個功能多」。

| | **★★★★ Ansible** | Puppet | Chef | Salt | cloud-init | 純 Shell + Git |
| --- | --- | --- | --- | --- | --- | --- |
| 定位 | configure | configure | configure | configure | **provision** | 兩者都能勉強 |
| **需要裝 agent** | **★★★★ 不需要**（走 SSH） | 需要（puppet agent） | 需要（chef-client） | 需要（minion，可 SSH 模式） | OS 內建 | 不需要 |
| 需要中央伺服器 | **不需要**（可純 CLI） | 通常需要 | 通常需要 | 通常需要 | 不需要 | 不需要 |
| 學習曲線 | **★★★ 低～中**（YAML） | 高（自有 DSL） | 高（Ruby DSL） | 中（YAML + Jinja） | ★ 低 | ★ 低但很快失控 |
| **人員流動後誰接得起來** | **★★★★ YAML 誰都讀得懂** | ✗ 要學 DSL | ✗ 要會 Ruby | 中等 | ★ 好接 | ✗✗ **最難接**（沒人敢改別人的腳本） |
| 離線／封閉環境可用 | **★★★ 可**（先下載 collection） | 可但佈署重 | 可但佈署重 | 可 | ★★★ 可 | ★★★ 可 |
| **與 Windows 端的搭配** | ★★ 可（WinRM／SSH，需另設） | ★★ 可 | ★★ 可 | ★★ 可 | ✗ 幾乎不用 | ✗ |
| 冪等性 | **★★★★ 模組內建** | ★★★★ 內建 | ★★★★ 內建 | ★★★★ 內建 | ✗ 只跑一次 | **✗✗ 要自己寫，最常出錯** |
| **稽核時看得懂嗎** | **★★★★ 看得懂**（一個 task 一個設定項） | 中 | ✗ | 中 | ★★ 看得懂 | ✗ 稽核員讀不了 300 行 bash |
| 中文資料與社群 | **★★★ 最多** | 少 | 少 | 少 | 中 | — |
| **本手冊建議** | **★★★★ 主線** | 大型既有環境才考慮 | 不建議新導入 | 有大量即時派送需求再看 | **★★★★ 搭配 Ansible 用** | 3 台以下或當作過渡 |

> [!note] 結論：機關環境選 Ansible ★★★★
> ```
> ① ★★★★ 無 agent —— 不必在 50 台機器上裝東西、不必開新的埠、
>    不必說服資安單位「這個 agent 是什麼」。走的是【本來就有的 SSH】。
>
> ② ★★★ YAML 可讀 —— 稽核時把 baseline.yml 印出來就是一份設定清單。
>    Puppet DSL 或 Chef 的 Ruby，稽核員看不懂、接手的同事也不敢改。
>
> ③ ★★★ 人員流動下接得起來 —— 這是機關最實際的考量。
>    離職的人留下 30 支互相呼叫的 bash 腳本，等同留下一顆地雷。
>
> ④ ★★ 離線可用 —— collection 可以先下載成 tar 帶進封閉環境。
>
> ★★ 唯一的代價：每次執行都要重新 SSH 連線並蒐集 facts，
>    上千台的規模會比 agent 型工具慢。機關規模通常碰不到這個天花板。
> ```

### ★★★★ 冪等性：這篇最重要的觀念

**冪等（idempotent）= 同一件事做一次和做十次，結果一樣。**

這是組態管理與「寫一支安裝腳本」最根本的差別。

```text
【壞味道】用 command 硬跑指令
  - name: 建立部署帳號
    ansible.builtin.command: useradd -m -s /bin/bash deploy
                             ↑
    第一次：帳號建好 → changed
    第二次：useradd 回傳 exit code 9（user already exists）
            → ★★★★ Ansible 判定 FAILED，整支 playbook 中斷
    就算加了 ignore_errors，也永遠報 changed，
    ★★★ 你【永遠不知道這台機器到底對不對】

【正確】用專門模組
  - name: 建立部署帳號
    ansible.builtin.user:
      name: deploy
      shell: /bin/bash
      create_home: true
                             ↑
    第一次：帳號不存在 → 建立 → changed
    第二次：帳號已存在且屬性相同 → ★★★★ 不動作 → ok
    第 N 次：有人手動改了 shell → ★★★ 改回來 → changed（偵測到飄移！）
```

#### ★★★★ changed 與 ok 的意義，以及自我檢驗標準

| 狀態 | 意義 | 你該有的反應 |
| --- | --- | --- |
| `ok` | 檢查過了，**已經是期望狀態，沒有動作** | ★ 正常 |
| `changed` | **實際改了東西** | ★★★ 第二次跑還出現 = 有問題 |
| `skipped` | `when:` 條件不成立 | ★ 確認條件寫對 |
| `failed` | 失敗 | ★★★★ 停下來查，不要 `ignore_errors` 蓋過去 |
| `unreachable` | **連不上**，跟 task 無關 | ★★★ 查 SSH，不是查 playbook |

> [!danger] ★★★★ 自我檢驗標準：第二次執行應該全部 ok
> ```
> 寫完 playbook 之後【一定要連跑兩次】：
>
>   第一次： changed=8  ok=3   ← 正常，它把機器改成期望狀態
>   第二次： changed=0  ok=11  ← ★★★★ 這才叫寫對了
>
> ★★★★ 如果第二次還有 changed，代表【那個 task 寫錯了】，常見原因：
>   ① 用了 command / shell 而不是專門模組
>   ② copy / template 的內容每次都不同（例如塞了時間戳記）
>   ③ file 模組的 mode 寫成 0644 但沒加引號 → YAML 讀成十進位 644
>   ④ lineinfile 的 regexp 匹配不到自己剛寫進去的那行 → 每次都再加一行
>      ★★★★ 這個最危險：設定檔會【無限膨脹】，跑 100 次就多 100 行
>
> ★★★ 為什麼這件事這麼重要：
>   一支不冪等的 playbook，你無法用它來【驗證】機器的狀態，
>   只能用它來【設定】。而組態管理真正的價值在前者 ——
>   「跑一次全部 ok」就等於一份自動產生的符合性報告。
> ```

### ★★★★ 從 SOP 到程式碼的正確順序

**很多單位的自動化失敗，是因為順序反了。**

```text
✗ 錯誤順序（最常見）
  ① 學 Ansible → ② 邊查文件邊寫 playbook → ③ 跑起來了 → ④ 上線
  結果：得到一份【沒人知道對不對】的自動化。
        因為從來沒有一份文件說「一台正確的機器長什麼樣」，
        playbook 寫的就是「當時那個人記得的樣子」。
        ★★★★ 一旦這份 playbook 派送到 50 台，錯誤也一起派送到 50 台。

✓ 正確順序
  ① 【先把 SOP 寫清楚】       → [[01-新機建置標準流程]]
     人可讀的步驟 + 每步的【驗收方式】
              ↓
  ② 【把可驗證的項目寫成檢查腳本】 → server-build-verify（01 篇產出）
     ★★★★ 這是關鍵中間層。它回答「怎樣算對」，
           而且【手動建的機器也能用它驗收】
              ↓
  ③ 【最後才把設定項寫成 playbook】 → 本篇的 baseline.yml
              ↓
  ④ playbook 跑完，用 ② 的檢查腳本驗收
     ★★★ 檢查腳本是【獨立的第三方】，不是 playbook 自己說自己對
```

> [!tip] 為什麼中間那層不能跳過 ★★★★
> 如果沒有獨立的檢查腳本，你驗證 playbook 的方式只剩下「再跑一次 playbook」。
> 那等於**拿考卷的答案去改同一份考卷**。
> 檢查腳本用不同的方式問同一個問題（例如 playbook 用 `ufw` 模組開 22 埠，
> 檢查腳本用 `ss -tlnp` 看真的有沒有在聽），才有驗證的意義。
> 詳見 [[07-自動化健康檢查實戰]]。

## 環境準備與安裝

### 第一部分：cloud-init（provision）

#### cloud-init 是什麼、在哪個時間點跑

cloud-init 是**雲端映像檔內建**的首次開機設定機制。Ubuntu / Rocky / Debian 的
官方 cloud image 都預裝它。它在開機時從「資料來源（datasource）」讀設定 ——
PVE 的資料來源是掛在 VM 上的那顆 **cloudinit 光碟（NoCloud）**。

```text
開機
 ├─ 【init-local】     偵測 datasource、設定網路（此時還沒有網路）
 ├─ 【init（network）】 掛載磁碟、產生 SSH host key、設定 hostname
 ├─ 【config】         users / groups / write_files / package 相關模組
 └─ 【final】          runcmd / scripts-user / final_message
                       ↑
                  ★★★★ runcmd 在【最後】跑，而且【只跑一次】
```

★★★★ **每個模組有「執行頻率」**：大多是 `once-per-instance`（一台 instance 只跑一次）。
`runcmd` 就是這種。**改了 user-data 再重開機，runcmd 不會重跑**，
必須 `cloud-init clean` 清掉狀態才會。這是 cloud-init 排錯第一名的坑。

#### 最小可用的 user-data

```yaml
#cloud-config
# ★★★★ 第一行必須是 #cloud-config，少了它整份被當成純文字忽略

hostname: web-tst-01
fqdn: web-tst-01.tst.example.gov.tw
manage_etc_hosts: true          # ★★★ 讓 /etc/hosts 跟著 hostname 走，避免 sudo 變慢
timezone: Asia/Taipei
locale: zh_TW.UTF-8

# ═══ ★★★★ 這一段是「讓 Ansible 進得來」的關鍵 ═══
users:
  - name: ansible
    gecos: "Ansible 控制節點專用帳號"
    groups: [sudo]
    shell: /bin/bash
    lock_passwd: true            # ★★★ 鎖住密碼登入，只能用金鑰
    sudo: "ALL=(ALL) NOPASSWD:ALL"
    ssh_authorized_keys:
      - "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...換成你控制節點的公鑰... ansible@ctl-01"

ssh_pwauth: false                # ★★★★ 關閉 SSH 密碼認證
disable_root: true               # ★★★ 禁止 root 直接 SSH

package_update: true             # ★★ 等同 apt update
package_upgrade: false           # ★★★ 建議 false，交給 Ansible 控制升級時機
packages:
  - python3                      # ★★★★ Ansible 需要，雖然 Ubuntu 預設有，明寫保險
  - qemu-guest-agent             # ★★ PVE 才看得到 VM 的 IP 與能正常關機
  - chrony                       # ★★ 時間同步

write_files:
  - path: /etc/ssh/sshd_config.d/60-baseline.conf
    permissions: '0644'          # ★★★ 一定要加引號，否則 YAML 讀成八進位以外的東西
    content: |
      PasswordAuthentication no
      PermitRootLogin no
  - path: /etc/motd
    content: |
      本機由 cloud-init 佈建、由 Ansible 管理組態。
      請勿手動修改 /etc 下的受管設定，變更請走變更管理流程。

runcmd:
  - [ systemctl, enable, --now, qemu-guest-agent ]
  - [ systemctl, restart, ssh ]
  - [ sh, -c, "echo provisioned $(date -Is) >> /var/log/provision.log" ]

final_message: "cloud-init 完成，開機耗時 $UPTIME 秒（$TIMESTAMP）"
```

> [!danger] ★★★★ 為什麼 user-data 不該做太多
> ```
> 看到 runcmd 能執行任意指令，很容易想「乾脆整套設定都寫在這裡」。不要。
>
> ★★★★ 三個理由：
>   ① runcmd【只跑一次】，不冪等。機器上線後設定飄移，它救不回來。
>   ② 出錯時只有 /var/log/cloud-init-output.log 一行紅字，
>      沒有 task 名稱、沒有 diff，排錯極痛苦。
>   ③ 改了要 cloud-init clean 才會重跑 → 等於【每次改設定都要重建機器】。
>
> ★★★★ 正確的界線：
>   user-data 只做【讓 Ansible 進得來】必要的事 ——
>   hostname、網路、管理帳號、公鑰、python3、關掉密碼登入。
>   通常 30 行以內。其他一律交給 Ansible。
>
> ★★★★★ 絕對不要在 user-data 裡寫明文密碼（cipassword、chpasswd）。
>   PVE 上的 cloudinit 磁碟【任何能讀該儲存區的人都看得到】，
>   而且 /var/lib/cloud/instance/user-data.txt 會【留在機器上】。
> ```

#### PVE cloud-init 面板欄位對應

PVE 的 VM → Cloud-Init 面板，其實就是幫你產生一份 user-data 與 network-config。
欄位與 `qm set` 參數、以及最終的 cloud-config 對應如下：

| PVE 面板欄位 | `qm set` 參數 | 對應的 cloud-init 概念 | 星級 |
| --- | --- | --- | --- |
| User | `--ciuser` | `users:` 的第一個帳號名 | ★★★ |
| Password | `--cipassword` | `chpasswd` ★★★★★ **不要用** | ★★★★★ |
| SSH public key | `--sshkeys <檔案>` | `ssh_authorized_keys` | ★★★★ |
| DNS domain | `--searchdomain` | network-config 的 search domain | ★★ |
| DNS servers | `--nameserver` | network-config 的 nameservers | ★★ |
| IP Config (netN) | `--ipconfig0 ip=…,gw=…` | network-config v1／v2 | ★★★★ |
| Upgrade packages | `--ciupgrade 0/1` | `package_upgrade` | ★★ |
| （面板沒有） | `--cicustom "user=local:snippets/x.yaml"` | **完整自訂 user-data** | ★★★★ |

> [!danger] ★★★★ cicustom 的兩個陷阱（官方文件明載）
> ```
> ① ★★★★ --cicustom user=… 會【完全取代】面板／設定檔裡的
>    ciuser、cipassword、sshkeys —— 【不是合併】。
>    很多人設了 cicustom 又在面板填 SSH key，結果面板那把【完全不生效】，
>    然後花半天查「為什麼公鑰沒進去」。
>    → 用 cicustom 就把所有帳號與金鑰都寫進 snippet 裡。
>
> ② ★★★ qm cloudinit dump <vmid> user 只會印出【PVE 原生產生的】設定，
>    【看不到】你的 cicustom snippet 內容。
>    → 要驗證 snippet，直接 cat /var/lib/vz/snippets/<檔名>，
>      或開機後在 VM 內 cat /var/lib/cloud/instance/user-data.txt。
>
> ★★★ snippet 檔案必須放在【啟用 Snippets 內容類型】的儲存區，
>    而且【每個可能遷移到的節點都要有】，否則 VM 開不起來。
>    路徑通常是 /var/lib/vz/snippets/（local 儲存區）。
> ```

啟用 snippets 內容類型：

```bash
# 在 PVE 節點上執行
sudo pvesm set local --content backup,iso,vztmpl,snippets
sudo pvesm status --storage local
```

預期輸出：

```text
Name             Type     Status           Total            Used       Available        %
local             dir     active        98559220        12034552        81462268   12.21%
```

> [!danger] ★★★★ 改了 user-data 卻沒生效？
> ```
> runcmd、users 這些模組的頻率是 once-per-instance。
> 同一台 VM 第二次開機【不會重跑】。
>
> 要重跑，在【測試機】上：
>   sudo cloud-init clean --logs        # 清狀態與日誌，不重開機
>   sudo cloud-init clean --logs --reboot   # 清完直接重開機重跑
>
> ★★★★★ 【絕對不要】在正式機上跑 cloud-init clean：
>   它會清掉 instance-id 與已產生的狀態，重開機後 cloud-init 會把這台
>   當成【全新的機器】重跑一次全部模組 ——
>   包含重設 hostname、重建帳號、重跑 runcmd。
>   若你的 user-data 已經過期（例如 IP 改過），會直接把機器打回舊設定。
>
> ★★★ 正確的心態：cloud-init 的設定改了，就【重建一台新 VM】，
>   不要試圖在既有機器上重跑。這也是「機器可拋棄」的實踐。
> ```

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> ```bash
> # ★★ 套件名一樣是 cloud-init，官方 GenericCloud 映像已預裝
> sudo dnf install -y cloud-init
> cloud-init status --wait --long
> ```
> ★★★ 差異點：
> - **預設帳號不同**：Ubuntu cloud image 是 `ubuntu`，Rocky／AlmaLinux 是 `rocky` / `almalinux`。
>   `--ciuser` 沒設時會落在這個預設帳號上。
> - **SSH 服務名是 `sshd` 不是 `ssh`**，`runcmd` 裡的 `systemctl restart ssh` 要改成 `sshd`。
> - **防火牆是 firewalld 不是 ufw**，`packages:` 不要裝 ufw，
>   Ansible 端也要換成 `ansible.posix.firewalld` 模組（見 [[04-防火牆-firewalld]]）。
> - **SELinux 預設 enforcing** ★★★★：`write_files` 寫到非預設路徑的檔案可能因為
>   context 不對而讓服務讀不到，必要時在 `runcmd` 加 `restorecon -Rv <路徑>`。
> - 套件管理模組在 Ansible 端要用 `ansible.builtin.dnf` 而不是 `apt`。

```text
【類型 3】UNREACHABLE + Host key verification failed
web-tst-01 | UNREACHABLE! => {
    "msg": "Failed to connect to the host via ssh: Host key verification failed.",
    "unreachable": true
}
→ ★★★★ known_hosts 裡的指紋跟現在對不上。
   重建過同一個 IP 的 VM 最常遇到。
   ★★★★★ 【不要】用 host_key_checking = False 蓋過去 —— 那等於永久接受中間人攻擊。
   正確：確認這台真的是你重建的那台，然後
        ssh-keygen -R 10.10.20.31
        ssh-keyscan -t ed25519 10.10.20.31 >> ~/.ssh/known_hosts
```

> [!warning] ★★★★ command 模組永遠報 CHANGED

> 臨時查東西用 ad-hoc 沒問題；**寫進 playbook 就是壞味道**。

### ★★★ 變數分層：對應 02 篇的四層覆寫

[[02-基準設定與範本化]] 講的「全域 → 角色 → 環境 → 單機」四層覆寫，
在 Ansible 裡就是這三個目錄（優先序由低到高）：

```text
        ↓ 被覆寫
```

## 進階應用：第一支 baseline.yml

### 不到 40 行、真的能跑的 baseline

```yaml
---
# ~/ops-baseline/baseline.yml
- name: 全機關基準組態
  hosts: all
  become: true
  gather_facts: true

  tasks:
    - name: 設定時區                                          # tags: time
      community.general.timezone: { name: "{{ baseline_timezone }}" }
      tags: [time]

    - name: 安裝基準套件                                       # tags: pkg
      ansible.builtin.apt:
        name: "{{ baseline_packages }}"
        state: present
        update_cache: true
        cache_valid_time: 3600      # ★★ 一小時內不重複 apt update
      tags: [pkg]

    - name: 部署 chrony 設定
      ansible.builtin.template:
        src: files/chrony.conf.j2
        dest: /etc/chrony/chrony.conf
        owner: root
        group: root
        mode: '0644'                # ★★★★ 一定要引號，否則 YAML 當成十進位
      notify: 重啟 chrony
      tags: [time]

    - name: 建立管理帳號                                       # tags: user
      ansible.builtin.user:
        name: "{{ baseline_admin_user }}"
        groups: sudo
        append: true                # ★★★★ 沒有 append 會【清掉】其他群組
        shell: /bin/bash
        state: present
      tags: [user]

    - name: 佈署管理帳號公鑰
      ansible.posix.authorized_key:
        user: "{{ baseline_admin_user }}"
        key: "{{ lookup('file', 'files/opsadmin.pub') }}"
        exclusive: false            # ★★★ true 會【刪掉】其他既有公鑰，想清楚再開
        state: present
      tags: [user]

    - name: 允許基準埠
      community.general.ufw:
        rule: allow
        port: "{{ item.split('/')[0] }}"
        proto: "{{ item.split('/')[1] }}"
      loop: "{{ baseline_ufw_allow }}"
      tags: [fw]

    - name: 啟用 ufw（預設拒絕入向）
      community.general.ufw:
        state: enabled
        policy: deny
        direction: incoming         # ★★★★★ 順序很重要：先開 22 再啟用，否則自己被鎖在外面
      tags: [fw]

  handlers:
    - name: 重啟 chrony
      ansible.builtin.service: { name: chrony, state: restarted }
```

`files/chrony.conf.j2`（**唯一用到的範本，故意保持最簡單**）：

```text
# 由 Ansible 管理，請勿手動修改
{% for s in baseline_ntp_servers %}
server {{ s }} iburst
{% endfor %}
driftfile /var/lib/chrony/chrony.drift
makestep 1.0 3
rtcsync
```

★★★ Jinja2 只用到 `{% for %}` 這一個結構，**本篇到此為止**。
需要 `if`、filter、巢狀資料時，去看 Ansible 官方的 templating 文件。

### ★★★★ 三個關鍵設計說明

| 設計 | 為什麼 | 星級 |
| --- | --- | --- |
| `handlers` + `notify` | ★★★★ **只有設定真的變了才重啟服務**。寫成一般 task 的 `state: restarted` 會**每次都重啟**，正式環境等於每次跑 playbook 都製造一次服務中斷 | ★★★★ |
| `tags` | ★★★ 分段執行。改了 NTP 只跑 `--tags time`，不必碰防火牆 | ★★★ |
| ufw **先開 22 再 enable** | ★★★★★ 反過來寫，`ufw enable` 那一刻你的 SSH 連線就斷了，**而且再也連不進去** | ★★★★★ |

| 你看到 | 意思 | 你該做什麼 |
| --- | --- | --- |
| `--- before / +++ after` 有 diff | ★★★★ **這就是它要改的東西** | 逐行看，不認得的變更**就是問題** |

> [!danger] ★★★★ --check 的三個限制（不能盲信）
> ```
> ① ★★★★ 【後面的 task 依賴前面的結果時，乾跑會誤判】。
>    例：task A 裝 nginx（check 模式沒真的裝）→ task B 改 nginx.conf
>    → B 會因為檔案不存在而 failed，但實跑其實不會。
>    → 症狀：乾跑一堆紅字，實跑卻沒事。★★ 不要因此就跳過乾跑，
>      而是要能看懂哪些紅字是 check 模式的假象。
>
> ② ★★★ command / shell 模組在 check 模式【預設不執行】，直接 skipped。
>    所以「乾跑全綠」不代表那些指令沒問題。
>
> ③ ★★ --diff 會把【檔案內容印在畫面上】。
>    ★★★★ 如果檔案裡有密碼或金鑰，就會出現在你的終端機與任何日誌裡。
>    → 這種 task 加 no_log: true，或改用 --check 不加 --diff。
> ```

### 【4】～【9】：一支腳本包起來

★★★★ 底下這支把「乾跑 → 備份 → 金絲雀 → 驗收 → 全面派送 → 冪等驗證」
整套包成一個可稽核的流程。**這才是機關環境該用的形狀**，
而不是直接手敲 `ansible-playbook baseline.yml`。

```bash
sudo tee /usr/local/bin/ansible-rollout >/dev/null <<'SCRIPT'
#!/usr/bin/env bash
# ansible-rollout —— 基準組態的受控派送流程
# 用法： ansible-rollout <playbook> <目標群組> <金絲雀主機>
# 例：   ansible-rollout baseline.yml all web-tst-01
set -euo pipefail

PLAYBOOK="${1:?用法: ansible-rollout <playbook> <目標> <金絲雀主機>}"
TARGET="${2:?缺少目標群組}"
CANARY="${3:?缺少金絲雀主機}"

TS="$(date +%Y%m%d-%H%M%S)"
LOGDIR="${HOME}/ops-baseline/rollout-logs/${TS}"
BACKUP_DIR="/var/backups/ansible-baseline"
VERIFY="/usr/local/bin/server-build-verify"    # ★★★ 由 01 篇提供的驗收腳本

mkdir -p "$LOGDIR"

section() { printf '\n\033[1;36m═══ %s ═══\033[0m\n' "$*"; }
die()     { printf '\033[1;31m[FAIL] %s\033[0m\n' "$*" >&2; exit 1; }
ok()      { printf '\033[1;32m[ OK ] %s\033[0m\n' "$*"; }

# ═══════════════ 【0】前置檢查 ═══════════════
section "【0】前置檢查"
command -v ansible-playbook >/dev/null || die "ansible-playbook 不存在"
[[ -f "$PLAYBOOK" ]]                   || die "找不到 playbook: $PLAYBOOK"
[[ -f ansible.cfg ]]                   || die "請在 ops-baseline 專案目錄下執行"

# ★★★★ 目錄權限若是 world-writable，Ansible 會忽略 ansible.cfg
perm="$(stat -c '%a' .)"
[[ "${perm: -1}" =~ [2367] ]] && die "目前目錄是 world-writable，ansible.cfg 會被忽略（權限 $perm）"

# ★★★★ repo 必須乾淨：派送的內容一定要對得上某個 commit（稽核要求）
if ! git diff --quiet || ! git diff --cached --quiet; then
    die "git 工作目錄不乾淨，請先 commit。派送內容必須可追溯到 commit"
fi
COMMIT="$(git rev-parse --short HEAD)"
ok "將派送 commit ${COMMIT} 的 ${PLAYBOOK} 到 ${TARGET}"

# ═══════════════ 【1】語法與清單 ═══════════════
section "【1】語法檢查與目標清單"
ansible-playbook "$PLAYBOOK" --syntax-check >/dev/null || die "語法檢查未通過"
ansible "$TARGET" --list-hosts | tee "$LOGDIR/hosts.txt"
HOST_COUNT="$(ansible "$TARGET" --list-hosts | grep -cE '^\s{4}\S')"
ok "語法通過，目標 ${HOST_COUNT} 台"

read -rp "  確認要對這 ${HOST_COUNT} 台派送？(輸入 yes 繼續) " ans
[[ "$ans" == "yes" ]] || die "使用者取消"

# ═══════════════ 【2】連線檢查 ═══════════════
section "【2】連線檢查"
ansible "$TARGET" -m ping 2>&1 | tee "$LOGDIR/ping.txt" | tail -5
grep -q 'UNREACHABLE' "$LOGDIR/ping.txt" && die "有主機連不上，先解決再派送（見 ${LOGDIR}/ping.txt）"
ok "全部主機可連線"

# ═══════════════ 【3】★★★★ 變更前備份（Ansible 沒有內建 undo）═══════════════
section "【3】變更前備份"
ansible "$TARGET" --become -m ansible.builtin.shell -a \
  "mkdir -p ${BACKUP_DIR} && tar czf ${BACKUP_DIR}/pre-${TS}.tar.gz \
   /etc/chrony /etc/ufw /etc/sudoers.d /etc/ssh 2>/dev/null; \
   ls -l ${BACKUP_DIR}/pre-${TS}.tar.gz" \
  2>&1 | tee "$LOGDIR/backup.txt" | tail -3
ok "備份完成：${BACKUP_DIR}/pre-${TS}.tar.gz"

# ═══════════════ 【4】★★★★★ 乾跑 ═══════════════
section "【4】乾跑 --check --diff"
set +e
ansible-playbook "$PLAYBOOK" --limit "$TARGET" --check --diff \
    2>&1 | tee "$LOGDIR/dryrun.txt"
set -e
echo
echo "★★★★ 請逐行看過上面的 diff。不認得的變更就是問題。"
read -rp "  乾跑結果可以接受？(輸入 yes 繼續) " ans
[[ "$ans" == "yes" ]] || die "乾跑未通過審查，流程中止"

# ═══════════════ 【5】★★★★★ 金絲雀：先跑一台 ═══════════════
section "【5】金絲雀實跑：${CANARY}"
ansible-playbook "$PLAYBOOK" --limit "$CANARY" --diff 2>&1 | tee "$LOGDIR/canary.txt"
grep -qE 'failed=[1-9]|unreachable=[1-9]' "$LOGDIR/canary.txt" \
    && die "金絲雀失敗，請看 ${LOGDIR}/canary.txt。其餘主機【未受影響】"
ok "金絲雀執行完成"

# ═══════════════ 【6】★★★★ 用 01 篇的驗收腳本驗證（獨立第三方）═══════════════
section "【6】驗收檢查：${CANARY}"
if ansible "$CANARY" --become -m ansible.builtin.script -a "$VERIFY" \
       2>&1 | tee "$LOGDIR/verify-canary.txt" | tail -20; then
    ok "驗收通過"
else
    echo "★★★★ 驗收未通過。回滾指令："
    echo "  ansible $CANARY --become -m ansible.builtin.shell \\"
    echo "    -a 'tar xzf ${BACKUP_DIR}/pre-${TS}.tar.gz -C / && systemctl restart chrony ssh'"
    die "驗收失敗，流程中止"
fi

# ═══════════════ 【7】全面派送（分批）═══════════════
section "【7】全面派送"
read -rp "  金絲雀通過。要對其餘主機派送？(輸入 yes 繼續) " ans
[[ "$ans" == "yes" ]] || die "使用者於全面派送前中止（金絲雀已變更，請自行決定是否回滾）"

ansible-playbook "$PLAYBOOK" --limit "$TARGET" --diff \
    -e "ansible_serial=3" 2>&1 | tee "$LOGDIR/rollout.txt"
grep -qE 'failed=[1-9]|unreachable=[1-9]' "$LOGDIR/rollout.txt" \
    && die "派送有失敗主機，請看 ${LOGDIR}/rollout.txt"
ok "全面派送完成"

# ═══════════════ 【8】★★★★ 冪等驗證：第二次應該全部 ok ═══════════════
section "【8】冪等驗證（第二次執行）"
ansible-playbook "$PLAYBOOK" --limit "$TARGET" 2>&1 | tee "$LOGDIR/idempotent.txt" | tail -8
if grep -qE 'changed=[1-9]' "$LOGDIR/idempotent.txt"; then
    echo "★★★★ 第二次執行仍有 changed —— 有 task 不冪等，請修正 playbook。"
    grep -E '^changed:' "$LOGDIR/idempotent.txt" | sort -u
    exit 2
fi
ok "冪等驗證通過（changed=0）"

# ═══════════════ 【9】稽核記錄 ═══════════════
section "【9】稽核記錄"
{
  echo "時間：$(date -Is)"
  echo "操作者：$(id -un)@$(hostname)"
  echo "commit：${COMMIT}"
  echo "playbook：${PLAYBOOK}"
  echo "目標：${TARGET}（${HOST_COUNT} 台）"
  echo "備份：${BACKUP_DIR}/pre-${TS}.tar.gz"
  echo "日誌：${LOGDIR}"
} | tee -a "${HOME}/ops-baseline/rollout-history.log"

ok "全部完成。回滾方式見 ${LOGDIR}/verify-canary.txt 上方說明。"
SCRIPT
sudo chmod 755 /usr/local/bin/ansible-rollout
```

>   ② 【次好】PVE 快照 → 派送前 qm snapshot，失敗就 rollback

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| **`UNREACHABLE! … Permission denied (publickey)`** ★★★★ | 公鑰沒進去、或 cloud-init user-data 貼錯（貼成私鑰、換行被吃掉） | 到 VM console `cat /home/ansible/.ssh/authorized_keys`；空的就是 cloud-init 沒生效，看 `/var/log/cloud-init-output.log` |
| **`UNREACHABLE! … Host key verification failed`** ★★★★ | 同 IP 重建過 VM，`known_hosts` 指紋對不上 | `ssh-keygen -R <IP>` 後重新 `ssh-keyscan`。★★★★★ **不要**設 `host_key_checking = False` |
| **改了 user-data 重開機卻沒生效** ★★★★ | `runcmd` 等模組是 `once-per-instance`，同一台不會重跑 | 測試機用 `cloud-init clean --logs --reboot`；★★★★★ 正式機**不要跑**，改成重建 VM |
| **`--cicustom` 設了但 SSH 公鑰沒進去** ★★★★ | cicustom 的 user 段**完全取代**面板的 `sshkeys`，不是合併 | 把公鑰寫進 snippet 裡；用 `cat /var/lib/cloud/instance/user-data.txt` 確認機器實際收到什麼 |
| **`couldn't resolve module/action 'community.general.ufw'`** ★★★ | 只裝了 `ansible-core`，沒有 collection | `ansible-galaxy collection install community.general ansible.posix`，或改用 `apt install ansible` |
| **第二次執行還有 `changed`** ★★★★ | task 不冪等：用了 `command`/`shell`、`lineinfile` 的 regexp 匹配不到、`mode` 沒加引號 | 換成專門模組；`mode: '0644'` 加引號；`lineinfile` 改用 `template` 管整個檔案 |
| **`ufw enable` 之後自己被鎖在外面** ★★★★★ | 先 enable 才開 22 埠 | task 順序改成「先 allow 22 → 再 enable」；★★★★ 補救只能走 PVE console 或 IPMI |
| **`sudo: a terminal is required to read the password`** ★★★ | 目標端 sudoers 有 `requiretty`，或 sudo 需要密碼 | 加 `-K` 提供密碼；或在 sudoers 設 NOPASSWD；`pipelining = True` 遇到 requiretty 會失敗，先關掉測試 |
| **`ansible.cfg` 裡的設定完全沒生效** ★★★ | 目前目錄是 world-writable，Ansible 為了安全會忽略該檔 | `ls -ld .` 檢查權限，`chmod o-w .`；`ansible --version \| grep 'config file'` 確認讀到哪一份 |
| **`group_vars` 的變數在某台上沒作用** ★★★ | 那台在 inventory 裡是 `ungrouped`，或被 `host_vars` 覆寫了 | `ansible-inventory --graph` 看分群；`ansible-inventory --host <主機>` 看最終值 |
| **`baseline_packages` 少裝了共通套件** ★★★★ | 變數覆寫是**整個取代**，`group_vars/web.yml` 蓋掉了 `all.yml` | 在角色層把共通項目重抄一次，或拆成 common + extra 再合併 |
| **`Failed to update apt cache`** ★★★ | 內網無法連 archive.ubuntu.com，或本地鏡像未設定 | 先確認 `/etc/apt/sources.list.d/` 指向內部鏡像；見 [[03-第三方APT套件庫實務]] |
| **playbook 跑很慢，每台要一分多鐘** ★★ | 沒開 `pipelining`、`forks` 太小、每個 play 都重新 `gather_facts` | `ansible.cfg` 設 `pipelining = True`、調高 `forks`；不需要 facts 的 play 設 `gather_facts: false` |
| **`--check` 大量紅字但實跑沒事** ★★★ | check 模式下前面的 task 沒真的執行，後面依賴它的 task 就失敗 | 認得這個假象即可；必要時對該 task 加 `check_mode: false`（★★★ 但那個 task 在乾跑時會真的執行，要想清楚） |
| **vault 密碼檔不小心進了 git** ★★★★★ | `.gitignore` 加得太晚 | ★★★★★ **視為已外洩**：立刻輪換 vault 密碼與所有被加密的機密，並清理 git 歷史 |

### 排查步驟

**【1】先分清楚是 provision 還是 configure 的問題 ★★★★**

```bash
ansible all -m ping
```

預期輸出（正常）：

```text
web-tst-01 | SUCCESS => { "changed": false, "ping": "pong" }
```

**看到 `UNREACHABLE` → 問題在 provision（cloud-init／SSH／網路），
往【2】走，不要去改 playbook。
看到 `SUCCESS` 但 playbook 跑起來失敗 → 問題在 configure，跳到【5】。**

**【2】確認機器本身活著 ★★★**

```bash
ping -c 2 10.10.20.31
nc -vz 10.10.20.31 22
```

預期輸出：

```text
2 packets transmitted, 2 received, 0% packet loss
Connection to 10.10.20.31 22 port [tcp/ssh] succeeded!
```

**ping 不通 → 網路或 VM 沒開，去 PVE console 看。
ping 通但 22 拒絕 → cloud-init 還沒跑完，或 SSH 服務掛了，往【3】。**

**【3】在 VM console 上看 cloud-init ★★★★**

```bash
cloud-init status --long
```

預期輸出（失敗時）：

```text
status: error
extended_status: error - done
errors:
        - Cloud-init 26.1 failed in stage modules-config
```

**`error` 或 `degraded done` → 往【4】看 log。
`disabled` → 檢查 `/etc/cloud/cloud-init.disabled` 或核心參數 `cloud-init=disabled`。
`done` 但 SSH 還是連不上 → 往【6】查金鑰。**

**【4】看 cloud-init 到底錯在哪 ★★★★**

```bash
sudo grep -iE 'error|warn|traceback' /var/log/cloud-init.log | tail -20
sudo tail -30 /var/log/cloud-init-output.log
sudo cat /var/lib/cloud/instance/user-data.txt | head -20
```

預期輸出（典型錯誤）：

```text
2026-08-28 09:14:03,441 - util.py[WARNING]: Failed loading yaml blob.
Invalid format at line 12 column 7: "mapping values are not allowed in this context"
```

**看到 `Failed loading yaml blob` → user-data 語法錯，整份被丟掉，
所以帳號、公鑰全都沒建。回到 PVE 修 snippet，`cloud-init schema` 驗過再重建 VM。
看到 `user-data.txt` 是空的或不是你寫的內容 → `--cicustom` 路徑錯或 snippets 沒啟用。**

**【5】playbook 執行失敗：先加 `-vvv` 看真正的錯誤 ★★★**

```bash
ansible-playbook baseline.yml --limit web-tst-01 -vvv 2>&1 | tail -40
```

預期輸出（節錄）：

```text
fatal: [web-tst-01]: FAILED! => {
    "changed": false,
    "msg": "No package matching 'chronyd' is available"
}
```

**`No package matching` → 套件名寫錯或鏡像沒有（Ubuntu 是 `chrony` 不是 `chronyd`）。
`couldn't resolve module/action` → collection 沒裝，往【7】。
`Permission denied` 且不是 SSH 階段 → sudo 問題，往【8】。**

**【6】金鑰與 SSH 逐層排除 ★★★★**

```bash
ssh -vv -i ~/.ssh/id_ed25519_ansible ansible@10.10.20.31 'id -un' 2>&1 \
  | grep -iE 'offering|accepted|denied|authentication'
```

預期輸出（成功）：

```text
debug1: Offering public key: /home/ops/.ssh/id_ed25519_ansible ED25519 SHA256:8xK...
debug1: Server accepts key: /home/ops/.ssh/id_ed25519_ansible ED25519 SHA256:8xK...
debug1: Authentication succeeded (publickey).
```

**看到 `Offering` 但沒有 `Server accepts` → 公鑰不在目標的 authorized_keys 裡。
連 `Offering` 都沒有 → 本機這把私鑰權限錯（必須 600）或路徑寫錯。
看到 `Authentications that can continue: password` → 目標的 authorized_keys 空的，
回到【3】確認 cloud-init 有跑到 users 模組。**

**【7】確認 collection 與模組真的找得到 ★★★**

```bash
ansible-galaxy collection list | grep -E 'community.general|ansible.posix'
ansible-doc -l 2>/dev/null | grep -c .
ansible-doc community.general.ufw | head -5
```

預期輸出：

```text
community.general             11.3.0
ansible.posix                 2.0.0
> COMMUNITY.GENERAL.UFW    (…/ufw.py)
        Manage firewall with UFW.
```

**`ansible-doc` 找不到模組 → collection 沒裝或裝在別的路徑。
`ansible-galaxy collection list` 會印出搜尋路徑，對照
`ansible --version` 的 `ansible collection location`。**

**【8】sudo 提權問題 ★★★**

```bash
ansible web-tst-01 -m command -a 'sudo -n -l' 
```

預期輸出（NOPASSWD 正常時）：

```text
web-tst-01 | CHANGED | rc=0 >>
User ansible may run the following commands on web-tst-01:
    (ALL) NOPASSWD: ALL
```

**看到 `sudo: a password is required` → NOPASSWD 沒設好，
執行時改用 `-K`，或修 `/etc/sudoers.d/90-cloud-init-users`。
看到 `a terminal is required` → sudoers 有 `requiretty`，
先在 `ansible.cfg` 把 `pipelining` 關掉測試。**

**【9】冪等性問題：找出哪個 task 每次都 changed ★★★★**

```bash
ansible-playbook baseline.yml --limit web-tst-01 --diff 2>&1 | grep -B12 '^changed:'
```

預期輸出（找到元凶）：

```text
TASK [部署 chrony 設定] ********************************************************
--- before: /etc/chrony/chrony.conf
+++ after: …/source
@@ -1,2 +1,2 @@
-# 由 Ansible 管理，產生於 2026-08-28T10:15:33
+# 由 Ansible 管理，產生於 2026-08-28T10:22:07
changed: [web-tst-01]
```

**diff 只差一個時間戳 → 範本裡塞了 `ansible_date_time`，拿掉就好。
diff 顯示同一行被反覆新增 → `lineinfile` 的 `regexp` 匹配不到自己寫的內容，
★★★★ 這種會讓設定檔無限膨脹，改成用 `template` 管整個檔案。**

**【10】確認派送前後的實際狀態差異（驗收用）★★★**

```bash
ansible all --become -m ansible.builtin.shell -a \
  'timedatectl show -p Timezone --value; ufw status | head -1; id opsadmin' \
  -o
```

預期輸出：

```text
web-tst-01 | CHANGED | rc=0 | (stdout) Asia/Taipei\nStatus: active\nuid=1001(opsadmin) gid=1001 groups=1001,27(sudo)
web-tst-02 | CHANGED | rc=0 | (stdout) Asia/Taipei\nStatus: active\nuid=1001(opsadmin) gid=1001 groups=1001,27(sudo)
db-tst-01  | CHANGED | rc=0 | (stdout) Asia/Taipei\nStatus: active\nuid=1001(opsadmin) gid=1001 groups=1001,27(sudo)
```

★★★ 三行輸出**一模一樣**就是標準化成功。有任何一台不同，
那台就是「特例機」，要嘛補進 playbook，要嘛在 `host_vars` 裡**明確記錄例外原因**。

## 安全性注意事項

> [!danger] ★★★★★ 控制節點的私鑰 = 全機關的 root
> ```
> ★★★★★ 這是自動化導入後【風險最集中的一點】，很多單位完全沒有意識到：
>
>   控制節點上那把 ~/.ssh/id_ed25519_ansible
>     → 能免密登入所有受管節點
>     → 而且那些帳號多半設了 NOPASSWD sudo
>     → 拿到這把私鑰 = 【瞬間拿到全機關伺服器的 root】
>
>   一台普通的 web 伺服器被入侵，損失是一台。
>   控制節點被入侵，損失是【全部】。
>
> ★★★★★ 所以控制節點的保護等級必須【高於任何一台伺服器】：
>   ① 專用主機，不要跟開發、瀏覽網頁、收信混用
>   ② 私鑰【必須】設 passphrase，搭配 ssh-agent 使用（見 [[02-SSH-金鑰認證與ssh-agent]]）
>      ★★★★ 「反正是自動化，設 passphrase 很麻煩」是最常見的致命妥協
>   ③ 只允許特定管理網段 SSH 進控制節點
>   ④ 控制節點的登入本身要 MFA 或跳板機
>   ⑤ 私鑰【不要】備份到雲端硬碟、不要放在共用資料夾、不要進 git
>   ⑥ 人員異動【當天】就要輪換這把金鑰並重新佈署公鑰
>   ⑦ 記錄誰在什麼時候用它跑了什麼（rollout-history.log 就是為此）
> ```

> [!danger] ★★★★★ 一個寫錯的 playbook 能在 90 秒內弄壞 50 台
> ```
> 手動作業有一個被低估的優點：【慢】。
> 你在第 3 台就會發現不對勁，還有 47 台是好的。
>
> ★★★★★ 自動化把這個保護拿掉了：
>   forks = 10 的情況下，一個錯的 ufw 規則、一個錯的 sshd_config、
>   一個手滑寫成 /etc 的 file 模組 path ——
>   【90 秒內同時發生在 50 台上】，而且你連不進去修。
>
> ★★★★★ 五道防線（缺一不可）：
>   ① --check --diff 乾跑，逐行看過 diff
>   ② --limit 一台金絲雀，跑完用【獨立的驗收腳本】檢查
>   ③ serial: 3 分批 + max_fail_percentage: 0（失敗就整批停）
>   ④ 先在測試環境跑過完整流程（tst 群組存在的理由）
>   ⑤ 變更走變更管理，有人複核、有時間窗、有回滾方案
>      → [[08-變更管理流程]]、[[03-風險與變更管理]]
>
> ★★★★ 特別危險的模組（用之前多想三秒）：
>   ansible.builtin.file  state: absent   → path 寫錯就刪掉整個目錄
>   ansible.builtin.shell / command       → 不冪等且無 --check 保護
>   community.general.ufw state: enabled  → 順序錯就把自己鎖在外面
>   ansible.builtin.user  state: absent   → 連家目錄一起消失（remove: true）
>   ansible.builtin.apt   state: absent   → 可能連帶移除一堆相依套件
> ```

> [!danger] ★★★★ 機密與稽核軌跡
> ```
> ★★★★★ 【絕對禁止】把密碼、token、憑證私鑰明文寫進 playbook 或 group_vars。
>   → repo 一旦推到內部 GitLab，全單位有讀權限的人都看得到。
>   → 用 ansible-vault；已經 commit 過的視為【已外洩】，必須輪換。
>
> ★★★★ 【絕對禁止】在 PVE 的 cipassword 欄位放正式環境密碼。
>   → cloudinit 磁碟任何能讀該儲存區的人都拿得到，
>     而且 /var/lib/cloud/instance/user-data.txt 【永久留在機器上】。
>
> ★★★★ 【絕對禁止】設 host_key_checking = False。
>   → 等於宣告「任何冒充成我的伺服器的機器，我都把 sudo 密碼與設定送過去」。
>   → 正確做法是維護 known_hosts，或用 SSH 憑證（見 [[07-SSH-安全強化]]）。
>
> ★★★ 個資法與稽核（機關特別注意）：
>   ① playbook 的執行日誌可能含【使用者帳號、IP、路徑】→ 屬於稽核軌跡，
>      保存期限依機關規定，且【不得任意刪除】。
>   ② --diff 會把檔案內容印出來 → 若檔案含個資，日誌就是個資外洩點。
>      這種 task 加 no_log: true。
>   ③ 每次派送要能回答「誰、何時、依據哪個 commit、改了什麼、誰複核」——
>      這正是 rollout-history.log 與 git commit 的用途。
>   ④ 最小權限：不要為了方便給 NOPASSWD: ALL。
>      ★★★ 進階做法是把 sudoers 限縮到 playbook 實際用到的指令，
>      但這會大幅增加維護成本，機關環境需權衡後在資安文件中說明。
> ```

| `/etc/sudoers.d/90-cloud-init-users` | cloud-init 產生的 sudo 設定 | ★★★ |

## 練習題

> [!question]- 練習 1：算出你自己環境的回收年數，並誠實接受結論
> **題目**
> 用本篇「導入工時回收的粗估算法」，套上你單位真實的數字，
> 算出回收年數。如果算出來大於 3 年，寫出「不導入」的理由與替代方案。
>
> **參考解答**
>
> 假設情境：某機關 6 台 Linux 伺服器，每年因為系統改版重建 1 次，
> 單台照 SOP 手動建置 3 小時。
>
> ```text
> T_manual = 3 小時 × 6 台 × 1 次 = 18 小時/年
> T_auto   = 0.5 小時 × 1 次 + 12 小時（年維護） = 12.5 小時/年
> T_setup  = 20 小時
>
> 回收年數 = 20 ÷ (18 − 12.5) = 20 ÷ 5.5 ≈ 3.6 年
> ```
>
> ★★★★ **結論是「不值得為了省工時而導入」**。誠實面對這個結果很重要。
>
> 但★★★ 還有兩個「省工時以外」的理由可能翻轉決策：
> ① **稽核需求** —— 如果單位要求證明 6 台設定一致，手動做不到；
> ② **人員風險** —— 只有一個人會建這 6 台，那個人請假就沒人能重建。
>
> 替代方案（不導入 Ansible 時）：
> 把 SOP 寫紮實（[[01-新機建置標準流程]]）+ 基準檔進 git（[[02-基準設定與範本化]]）
> + 寫一支**唯讀的驗收腳本**（[[07-自動化健康檢查實戰]]）。
> ★★★ 這三樣的成本大約 8 小時，卻拿到自動化八成的價值。

> [!question]- 練習 2：找出這支 playbook 的四個問題
> **題目**
> 底下這段 playbook 有四個問題，每個都會在正式環境造成實際傷害。找出來並改正。
>
> ```yaml
> - hosts: all
>   become: true
>   tasks:
>     - name: 建立部署帳號
>       ansible.builtin.command: useradd -m -s /bin/bash deploy
>       ignore_errors: true
>
>     - name: 寫入 nginx 設定
>       ansible.builtin.copy:
>         dest: /etc/nginx/conf.d/app.conf
>         content: "# generated {{ ansible_date_time.iso8601 }}\nserver { listen 80; }"
>         mode: 0644
>
>     - name: 重啟 nginx
>       ansible.builtin.service: { name: nginx, state: restarted }
>
>     - name: 啟用防火牆
>       community.general.ufw: { state: enabled, policy: deny }
> ```
>
> **參考解答**
>
> **問題 1（★★★★ 不冪等 + 掩蓋錯誤）**：`command: useradd` 第二次跑會失敗，
> 用 `ignore_errors: true` 蓋掉 —— 這會**連同真正的錯誤一起吞掉**。
> 改成：
> ```yaml
> - ansible.builtin.user: { name: deploy, shell: /bin/bash, create_home: true }
> ```
>
> **問題 2（★★★★ 內容含時間戳 → 永遠 changed）**：`ansible_date_time.iso8601`
> 每次都不同，檔案每次都被改寫、nginx 每次都被重啟。拿掉時間戳；
> 需要標記來源就寫固定字串「由 Ansible 管理，請勿手動修改」。
>
> **問題 3（★★★ mode 沒加引號）**：`mode: 0644` 在 YAML 裡是**十進位 644**，
> 換算成八進位是 `1204`，權限會變成非預期的值。必須寫 `mode: '0644'`。
>
> **問題 4（★★★★★ 順序 + 無條件重啟）**：兩個問題疊在一起 ——
> ① `state: restarted` 讓 nginx **每次跑 playbook 都中斷一次**，
> 應改成 `notify:` + `handlers:`；
> ② `ufw enable` 前**沒有 allow 22**，執行的當下所有 SSH 連線被切斷，
> 而且**再也連不進去**，只能走 PVE console 救。
> 必須先 `ufw: {rule: allow, port: '22', proto: tcp}` 再 enable。

> [!question]- 練習 3：設計一個你能在 30 分鐘內完成的回滾方案
> **題目**
> 假設你要對 8 台正式 web 伺服器派送一份改動 `sshd_config` 的 playbook。
> 寫出完整的回滾方案，包含：備份什麼、怎麼備份、失敗時怎麼還原、
> 以及「還原不了」的情況怎麼辦。
>
> **參考解答**
>
> **【備份】派送前，用同一支 playbook 的第一個 task 做：**
> ```yaml
> - name: 變更前備份 SSH 設定
>   ansible.builtin.copy:
>     src: /etc/ssh/sshd_config
>     dest: "/etc/ssh/sshd_config.bak-{{ ansible_date_time.epoch }}"
>     remote_src: true
>   # ★★★ 這個 task 本身不冪等（epoch 每次不同），
>   #     所以要放在獨立的「備份 play」裡，不要混進 baseline
> ```
> ★★★★ 更穩的做法是**在 PVE 上做快照**：`qm snapshot <vmid> pre-ssh-change`。
>
> **【驗證】改完 SSH 設定，★★★★★ 絕對不要直接重啟就走人：**
> ```yaml
> - name: 驗證設定檔語法
>   ansible.builtin.command: sshd -t
>   changed_when: false        # ★★★ 純檢查，不算變更
> ```
> `sshd -t` 失敗就不要 reload。★★★★★ 而且**保留一個已登入的 session 不要關**，
> 用另一個視窗測試新連線能不能進來 —— 這是 SSH 變更的鐵律。
>
> **【還原】**
> ```bash
> ansible web --become -m ansible.builtin.shell -a \
>   'cp /etc/ssh/sshd_config.bak-* /etc/ssh/sshd_config && sshd -t && systemctl reload ssh'
> ```
>
> **【還原不了怎麼辦】★★★★ 這才是重點：**
> 如果 SSH 已經連不進去，上面的 ansible 指令**也連不進去**。所以：
> ① **事先確認 PVE console（或 IPMI／iDRAC）可用**，並知道 console 的登入密碼
> （★★★ 這是唯一不依賴 SSH 的管道，平常就要驗證它能用）；
> ② 用 `serial: 1` 一台一台做，壞一台停下來，其餘 7 台還是好的；
> ③ 派送時間選在**有人在機房或能到機房**的時段，不要半夜遠端做 SSH 變更。
>
> ★★★★★ **沒有演練過的回滾方案不算方案。** 在測試機上實際故意弄壞一次、
> 走完整個還原流程並計時，才知道 30 分鐘夠不夠。

Q10. 看到 `web-tst-02 | UNREACHABLE! … Host key verification failed`，

> [!question]- 測驗答案
> **Q1.** 因為 Ansible 是 **agentless**，它依賴的「agent」其實是
> **目標機上的 SSH 服務 + Python 直譯器 + 已佈署的公鑰**。
> 一台剛建立的 VM 這三樣**都還不存在**，所以 `ansible all -m ping` 只會得到
> 一整片 `UNREACHABLE`。
> ★★★★ 正確的分工是把生命週期切成兩段：
> **provision（機器從無到有）** 用 cloud-init／autoinstall／PVE clone，
> 它的唯一任務是「讓 Ansible 進得來」—— hostname、網路、管理帳號、
> 公鑰、python3、關掉密碼登入，通常 30 行 user-data 以內；
> **configure（維持在期望狀態）** 才交給 Ansible，而且會反覆執行。
> 交界點就是「SSH 通了、管理帳號能免密登入」這一刻。
> ★★★ 詳見「觀念說明 → 第一個分界」。
>
> **Q2.** 因為「幾台」只是三個變因之一。真正的判準是
> **台數 × 重做頻率 × 出錯代價**。
> 三台但每個月重建一次的對外服務，比三十台建好三年不動的內部測試機
> 更值得自動化 —— 前者一年要做 36 次且錯了會出事，後者一年做 0 次。
> ★★★★ 而且要用回收年數把它算成數字：
> `回收年數 = T_setup ÷ (T_manual − T_auto)`。
> 算出來大於 3 年就**誠實地不要導入**，改成「SOP + 基準檔進 git + 唯讀驗收腳本」，
> 用約八小時拿到八成價值。
> ★★★ 例外：有 TWGCB 或稽核符合性需求時，不論台數都應該程式碼化，
> 因為稽核要求的是「能證明所有機器一致」，這件事手動做不到。
> 見「觀念說明 → 何時值得自動化」與「導入決策表」。
>
> **Q3.** 三個問題，一個比一個嚴重：
> ① **第二次執行會 FAILED** —— `useradd` 在帳號已存在時回傳 exit code 9，
> Ansible 判定失敗，整支 playbook 中斷在半路（機器停在中間狀態）。
> ② **就算加了 `ignore_errors: true`，它永遠報 `changed`** ——
> 你**永遠無法用這支 playbook 驗證機器的狀態**，只能用來設定。
> 而且 `ignore_errors` 會連同**真正的錯誤**一起吞掉。
> ③ **偵測不到飄移** —— 有人手動把 deploy 的 shell 改成 `/sbin/nologin`，
> `command: useradd` 不會察覺也不會修正。
> ★★★★ 正確寫法：
> ```yaml
> ansible.builtin.user: { name: deploy, shell: /bin/bash, create_home: true }
> ```
> 它會在不存在時建立（changed）、屬性相同時不動作（ok）、
> 被改過時改回來（changed，這就是偵測到飄移）。見「冪等性」那節。
>
> **Q4.** 因為冪等的 playbook 具有**雙重身分**：它既是「設定工具」，
> 也是「驗證工具」。第一次跑把機器改成期望狀態（`changed=8`），
> 第二次跑如果全部 `ok`（`changed=0`），就同時證明了兩件事 ——
> **playbook 本身寫對了**，以及**這批機器現在的狀態與程式碼一致**。
> ★★★★ 這一行 `changed=0` 等於一份自動產生的符合性報告。
> 第二次還有 `changed` 的三種常見原因：
> ① 用了 `command` / `shell` 而不是專門模組（它們永遠報 changed）；
> ② `copy` / `template` 的內容每次不同（最常見是塞了 `ansible_date_time` 時間戳）；
> ③ ★★★★ `lineinfile` 的 `regexp` 匹配不到自己剛寫進去的那行 ——
> 這個最危險，設定檔會**無限膨脹**，跑 100 次就多 100 行，
> 解法是改用 `template` 管理整個檔案。
> 另外 `mode: 0644` 沒加引號被 YAML 讀成十進位，也會造成每次都改權限。
>
> **Q5.** 因為 ★★★★ **`--cicustom` 的 user 段會「完全取代」面板／設定檔裡的
> `ciuser`、`cipassword`、`sshkeys`，不是合併**。
> 這是 Proxmox 官方文件明載的行為：一旦指定了自訂 user snippet，
> PVE 就完全不產生它原生的那份 user-data，面板上填的公鑰**完全不生效**。
> **解法**：把所有帳號與公鑰都寫進 snippet 的 `users:` → `ssh_authorized_keys:` 裡。
> ★★★ **驗證方式**要注意：`qm cloudinit dump <vmid> user` **看不到** cicustom 的內容
> （它只印 PVE 原生產生的設定），所以要驗證得用
> `cat /var/lib/vz/snippets/x.yaml`（PVE 端）或
> `cat /var/lib/cloud/instance/user-data.txt`（VM 內，這是機器**實際收到**的）。
> ★★★ 另外 snippet 檔必須放在啟用了 Snippets 內容類型的儲存區，
> 而且每個可能遷移到的節點都要有，否則 VM 開不起來。
>
> **Q6.** 這行會**刪除 cloud-init 的所有狀態與日誌，然後重開機**。
> 重開機後 cloud-init 會把這台當成**全新的 instance**，
> **重跑一次全部模組**（包含 `once-per-instance` 的 `runcmd`、`users`、`hostname`）。
> ★★★★ 在**測試機**上這正是你要的 —— 改了 user-data 想重新驗證就用它。
> ★★★★★ 但在**正式機**上跑的後果是災難級的：
> ① 它會依據**那份可能早已過期的 user-data** 重新設定機器 ——
> IP 改過、hostname 改過、帳號改過的，全部**打回舊設定**；
> ② `runcmd` 會再跑一次，如果裡面有「初始化資料庫」「產生憑證」這類操作，
> 可能**覆蓋現有資料**；
> ③ SSH host key 可能被重新產生，導致所有人的 `known_hosts` 全部對不上。
> ★★★ 正確心態：cloud-init 設定改了就**重建一台新 VM**，
> 不要在既有機器上重跑。見速查表「cloud-init 指令」該列的 ★★★★★ 標記。
>
> **Q7.** ★★★★★ 順序是 **`--check --diff` 乾跑 → `--limit` 單一台實跑 → 全面套用**。
> **① 乾跑不做的後果**：你不知道它要改什麼。
> `--diff` 會印出 before/after，**每一行你都應該認得**；
> 出現不認得的變更就是問題（例如範本會整份覆蓋掉原本的 chrony pool 設定）。
> ★★★ 但要知道 `--check` 的限制：後面的 task 依賴前面結果時會誤判紅字，
> `command`/`shell` 在 check 模式預設 skipped，`--diff` 會把檔案內容印在畫面上
> （含機密時要加 `no_log: true`）。
> **② 金絲雀不做的後果**：★★★★★ **一次弄壞全部**。
> `forks=10` 下，一個錯的 ufw 規則能在 90 秒內同時發生在 50 台上。
> 跑完金絲雀還要用**獨立的驗收腳本**檢查，不能用 playbook 自己驗自己。
> **③ 全面套用時**要配 `serial: 3` 與 `max_fail_percentage: 0`，
> 失敗就整批停，不要讓錯誤擴散。最後再跑一次確認 `changed=0`。
>
> **Q8.** web 群組的機器**只會裝 nginx**，`chrony` 與 `vim` **都不會裝**。
> 這叫 ★★★★ **「變數覆寫是整個取代，不是合併」** 的陷阱。
> Ansible 的變數優先序是 `host_vars` > 特定 `group_vars` > `group_vars/all`，
> 而覆寫的單位是**整個變數**，不是逐項合併 ——
> 清單型變數尤其容易讓人誤以為會 append。
> **症狀**很難察覺：「基準套件明明寫了，web 這幾台就是沒裝」。
> ★★★ **兩種解法**：
> ① 入門建議：在 `group_vars/web.yml` 把共通項目**重抄一次**。
> 笨，但一目了然、稽核好讀、接手的人不會誤解。
> ② 進階：拆成 `baseline_packages_common` + `baseline_packages_extra`，
> 在 playbook 裡用 `union` 合併（已接近本篇邊界，需要時再查文件）。
> ★★★ **隨時可驗證**：`ansible-inventory --host web-tst-01` 印出該台最終拿到的值。
>
> **Q9.** 因為 ★★★★★ **控制節點上的 SSH 私鑰等同全機關的 root**。
> 那把 `~/.ssh/id_ed25519_ansible` 能免密登入所有受管節點，
> 而那些帳號多半設了 `NOPASSWD: ALL` 的 sudo ——
> **拿到這把私鑰就等於瞬間拿到全機關伺服器的 root**。
> 一台普通 web 伺服器被入侵，損失是一台；**控制節點被入侵，損失是全部**。
> 具體措施（至少四項）：
> ① **專用主機** —— 不跟開發、瀏覽網頁、收信混用；
> ② ★★★★ **私鑰必須設 passphrase**，搭配 ssh-agent
> （「反正是自動化，設 passphrase 很麻煩」是最常見的致命妥協）；
> ③ **只允許特定管理網段** SSH 進控制節點，登入本身要 MFA 或走跳板機；
> ④ **私鑰不得備份到雲端硬碟、共用資料夾或 git**；
> ⑤ **人員異動當天輪換金鑰**並重新佈署公鑰；
> ⑥ **記錄誰在何時用它跑了什麼**（`rollout-history.log` + git commit）。
> 見「安全性注意事項」第一個 danger callout。
>
> **Q10.** ★★★★ 這個錯誤代表 **`~/.ssh/known_hosts` 裡記的主機指紋，
> 跟目標機現在提供的指紋不一致**。最常見的無害原因是
> **同一個 IP 重建過 VM**（新 VM 產生了新的 SSH host key）。
> **該先查的**：確認這台真的是你重建的那台（去 PVE 看 VMID 與建立時間，
> 或在 console 上比對 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` 的指紋）。
> 確認無誤後：
> ```bash
> ssh-keygen -R 10.10.20.32
> ssh-keyscan -t ed25519 10.10.20.32 >> ~/.ssh/known_hosts
> ```
> ★★★★★ **為什麼不能用 `host_key_checking = False`**：
> 那不是「跳過一個煩人的提示」，而是**永久宣告「任何冒充成我的伺服器的機器，
> 我都願意把 sudo 密碼、設定檔、甚至 vault 解密後的機密送過去」**。
> 中間人只要在網路上冒充該 IP，就能收下你整批派送的內容並回傳假結果。
> ★★★ 正確做法是維護 `known_hosts`（用 `ssh-keyscan` 自動化），
> 規模大時改用 SSH 憑證（CA 簽發 host key），見 [[07-SSH-安全強化]]。
