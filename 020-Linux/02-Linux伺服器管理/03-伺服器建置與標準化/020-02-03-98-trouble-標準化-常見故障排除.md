## 依情境展開

### ★★★★★ 情境一：apt update 跳出一片紅字，什麼都裝不了

**現象**：任何 `apt update` / `apt install` 都先吐出這幾行其中之一。

```text
W: GPG error: https://deb.myguard.nl/apt noble InRelease: The following signatures
   couldn't be verified because the public key is not available: NO_PUBKEY A1B2C3D4E5F60718
E: The repository 'https://deb.myguard.nl/apt noble InRelease' is not signed.
E: Release file for https://deb.myguard.nl/apt/dists/noble/InRelease is expired
   (invalid since 32d 4h 12min).
E: Conflicting values set for option Signed-By regarding source https://deb.myguard.nl/apt/ noble:
   /etc/apt/keyrings/a.gpg != /etc/apt/keyrings/b.gpg
```

**判斷分流**：

```bash
sudo apt update 2>&1 | grep -E '^(W:|E:)' || echo "無警告"
```

- `NO_PUBKEY` → 金鑰問題，往下走第【1】步
- `is expired` → 分清楚「庫死了」還是「時鐘壞了」，第【3】步
- `is not valid yet` → ★★★★ 幾乎一定是**本機時鐘**，跳情境十第【3】步
- `Conflicting values … Signed-By` → 重複定義，第【4】步
- `does not have a Release file` / `Unable to locate package` → 來源沒被讀到，第【5】步
- 完全無警告卻裝到錯版本 → 跳情境四

**處置步驟**：

【1】金鑰三連查（路徑、權限、指紋）：

```bash
KR=/etc/apt/keyrings/myguard.gpg
stat -c '%a %U:%G %n' "$KR"                                    # 應為 644 root:root
sudo -u _apt test -r "$KR" && echo "_apt 可讀" || echo "★★★★ _apt 讀不到"
gpg --show-keys --with-fingerprint --with-colons "$KR" | awk -F: '/^fpr:/{print $10}'
```

- 權限不對 → `sudo chmod 644 "$KR"; sudo chown root:root "$KR"`（`/etc/apt/keyrings` 應為 `755`）
- 檔案不存在 → `.sources` 的 `Signed-By:` 路徑打錯：`grep -n Signed-By /etc/apt/sources.list.d/*.sources`
- `gpg: no valid OpenPGP data found` → 對已是二進位的 `.gpg` 又跑了一次 `--dearmor`，
  或抓到 HTML 錯誤頁：`file "$KR"` 確認，下載一律用 `curl -f`

【2】★★★★★ 指紋和登錄表對不上時**不要直接換金鑰**。走第二管道（官方公告頁、
另一台已驗證主機、廠商窗口）取得新指紋，比對一致後才更換並補變更單 ——
上游被打下來時，「照著網頁指示更新金鑰」正是攻擊者要你做的事。

【3】過期：先看時鐘，再看庫。

```bash
timedatectl status | grep -E 'Local time|System clock|NTP service'
grep -m1 '^Valid-Until:' /var/lib/apt/lists/*_InRelease
# Valid-Until: Wed, 02 Sep 2026 03:00:12 UTC     ← 這行在未來才正常
```

- `System clock synchronized: no` 且時間明顯錯 → 修時間即可（情境十第【3】步）
- 時鐘正確、`Valid-Until` 在過去 → ★★★★ **這個庫沒人維護了**，啟動撤除評估（情境十二）
- ★★★★★ **絕對不要**用 `Acquire::Check-Valid-Until "false";` 掩蓋，那等於關掉重放攻擊防護

【4】重複定義：把提到這個主機名的檔案一次找齊，只保留一份。

```bash
grep -rn 'deb.myguard.nl' /etc/apt/sources.list /etc/apt/sources.list.d/ 2>/dev/null
# myguard.list:1:deb https://deb.myguard.nl/apt noble main     ← ★★★★ 舊 .list 沒刪，就是它
# myguard.sources:2:URIs: https://deb.myguard.nl/apt
```

刪掉 `.list`，只留 `.sources`，再 `sudo apt update`。

【5】來源根本沒被讀進去：

```bash
apt-get indextargets --no-release-info --format '$(URI) $(SUITE) $(COMPONENT)' | sort -u
```

看不到你的來源，依序檢查：副檔名是不是 `.sources`（寫成 `.list`／`.conf` 會被完全忽略）、
`Enabled:` 是不是 `no`、欄位有沒有拼錯（★★★ 正確是 `URIs:` 不是 `URI:`）、該庫支不支援這個 codename。

**原理**：apt 的信任模型已從全域信任池（`apt-key`）改成**每個來源綁一把金鑰**（`Signed-By`），
`InRelease` 的 `Valid-Until` 則是庫的心跳訊號。
→ 原理詳見 [[020-02-03-03-cmd-標準化-第三方APT套件庫實務]]

**預防**：加庫一律走 `apt-repo-add` 腳本（內建指紋雙管道驗證與 `signed-by` 綁定）；
每季跑 `apt-repo-audit` 盤點；把 `Valid-Until` 剩餘天數納入監控告警。

### ★★★★★ 情境二：套件裝到一半卡住，之後每個 apt 指令都先叫你跑 dpkg --configure -a

**現象**：

```text
E: dpkg was interrupted, you must manually run 'sudo dpkg --configure -a' to correct the problem.
E: Could not get lock /var/lib/dpkg/lock-frontend. It is held by process 3271 (unattended-upgr)
dpkg: error processing package org-ca-certificates (--configure):
 installed post-installation script returned error exit status 1
```

**判斷分流**：

```bash
ps aux | grep -E '[a]pt|[d]pkg'; sudo fuser -v /var/lib/dpkg/lock-frontend; sudo dpkg --audit
```

- **有程序在跑** → 不要動，等它結束（`unattended-upgrades` 可能跑好幾分鐘），第【1】步
- 沒有程序但仍報 interrupted → 第【2】步
- 訊息裡有 `post-installation script returned error` → 套件的 postinst 壞了，第【4】步

**處置步驟**：

【1】★★★★★ 先確認真的沒有東西在跑，這一步不能跳：
`systemctl status unattended-upgrades --no-pager | head -5`，
`sudo fuser -v /var/lib/dpkg/lock-frontend`（沒人佔用時完全沒有輸出）。
★★★★★ **在 apt 執行中刪鎖檔會造成套件資料庫損壞**，那是比原本問題大十倍的災難。

【2】確認無程序後才移除鎖檔並收尾：

```bash
sudo rm -f /var/lib/dpkg/lock-frontend /var/lib/dpkg/lock /var/cache/apt/archives/lock
sudo dpkg --configure -a
sudo apt --fix-broken install
```

【3】看它卡在哪個套件、哪個狀態：

```bash
grep -E 'half-configured|half-installed|unpacked' /var/log/dpkg.log | tail -20
dpkg -l | awk '$1 !~ /^ii$/ {print}' | tail
# 2026-08-29 11:07:31 status half-configured org-ca-certificates:all 1.0.0
```

- 停在 `half-configured` / `half-installed` → postinst 失敗，第【4】步
- 停在 `unpacked` 就沒了 → 相依沒滿足，`sudo apt --fix-broken install`

【4】不必安裝就能檢查維護腳本：

```bash
DEB=/var/cache/apt/archives/org-ca-certificates_1.1.0_all.deb
dpkg-deb --ctrl-tarfile "$DEB" | tar -tv          # ★★★ 檔名前沒有 x 權限 = 忘了 chmod 0755
dpkg-deb --ctrl-tarfile "$DEB" | tar -xO ./postinst
sudo journalctl -t org-ca-certificates -n 20
```

常見元兇：postinst 非冪等（`mkdir` 已存在、`useradd` 重複建立）、`Depends:` 漏宣告、
維護腳本沒有執行位元。
★★★ `trying to overwrite '/etc/x.conf', which is also in package Y` 是缺 `Conflicts:` + `Replaces:`，
補進 control 重新打包，**不要**用 `--force-overwrite` 硬幹。

**原理**：dpkg 是一個有狀態機的資料庫（unpacked → half-configured → installed），
中斷會停在中間狀態；維護腳本必須冪等才禁得起重跑。
→ 原理詳見 [[020-02-03-04-svc-標準化-自建APT套件庫]]

**預防**：內部套件的 `postinst`／`postrm` 一律寫 `case "$1" in` 分流，
並在測試機做「裝 → 升 → 降 → 移除 → 重裝」五連測；
正式機的 `unattended-upgrades` 設維護時間窗，不要和人工作業撞在一起。

### ★★★★ 情境三：磁碟或 /boot 滿了，升級失敗、服務同時開始回 500

**現象**：

```text
E: You don't have enough free space in /boot.
nginx: [emerg] open() "/var/log/nginx/error.log" failed (28: No space left on device)
-bash: cannot create temp file for here-document: No space left on device
```

★★★★ 典型伴隨症狀：**SSH 登得進去但一登入就被踢掉**（家目錄寫不進去）。

**判斷分流**：

```bash
df -h  | awk 'NR==1 || $5+0 > 80'
df -i  | awk 'NR==1 || $5+0 > 80'
```

- 只有 `/boot` 滿 → 舊核心堆積，第【1】步
- `/` 或 `/var` 滿 → 找大檔，第【2】步
- **容量還有但 inode 用完** → 大量小檔（session 檔、佇列），照第【2】步找目錄再清

**處置步驟**：

【1】`/boot` 用官方方式清：

```bash
uname -r                                  # ★★★★ 先記住「現在在跑的」是哪一版
dpkg -l 'linux-image-*' | grep ^ii
sudo apt autoremove --purge
```

★★★★★ **不要手動 `rm /boot/vmlinuz-*`** —— dpkg 狀態會與實際檔案不一致，
下次 `update-initramfs` 直接失敗，而且可能刪掉正在跑的那一版，重開機就進不去系統
（救援見 [[020-01-25-guide-Linux-開機流程與GRUB救援]]）。

【2】找出誰吃掉空間：

```bash
sudo du -xh / 2>/dev/null | sort -h | tail -15
sudo journalctl --disk-usage
sudo apt clean && sudo apt autoclean
```

【3】★★★★ 日誌暴增時**不要 `rm`**，要 `truncate`：

```bash
sudo lsof +L1 | head                      # 已刪除但仍被開著的檔（空間不會釋放）
sudo truncate -s 0 /var/log/nginx/access.log
sudo journalctl --vacuum-size=500M
```

★★★ `rm` 掉程式還開著的 log，空間**不會**釋放（inode 還在），`df` 依然 100%，而且檔案救不回來。

【4】有 LVM 留白就直接擴，這是最乾淨的解：

```bash
sudo vgs                                  # 先看 VFree 還有沒有空間
sudo lvextend -L +10G /dev/mapper/vg0-var && sudo resize2fs /dev/mapper/vg0-var
```

**原理**：分割規劃階段就該把 `/var/log` 獨立出來並在 VG 留白，
讓「日誌寫爆」不會升級成「整台機器掛掉」。
→ 原理詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]、[[020-01-15-cmd-Linux-磁碟分割與掛載]]

**預防**：「`/var/log` 獨立分割」與「VG 留白 ≥20%」列進建置驗收表；
`logrotate` 與 journald 的 `SystemMaxUse=` 進基準範本；磁碟使用率 80% 進監控告警。

### ★★★★★ 情境四：服務突然起不來，一查發現套件被換成沒見過的版本

**現象**：

```text
nginx: [emerg] unknown directive "autocert" in /etc/nginx/nginx.conf:14
$ openssl version
OpenSSL 3.5.0 1~noble            # ★★★★★ 官方 noble 明明是 3.0.13
php-fpm[1123]: symbol lookup error: … undefined symbol: EVP_…
```

或者：**半夜服務自己重啟了，早上才發現版本變了，沒人知道是誰做的**。

**判斷分流**：

```bash
apt policy openssl nginx
grep -E 'install |upgrade ' /var/log/dpkg.log* | tail -30
sudo tail -40 /var/log/unattended-upgrades/unattended-upgrades.log
```

- `apt policy` 顯示套件來自第三方庫 → pinning 沒設或設錯，第【1】步
- dpkg.log 的時間對得上半夜 → 是 `unattended-upgrades` 幹的，第【4】步
- 套件只顯示 `/var/lib/dpkg/status`、查不到來源 → ★★★★ 孤兒套件，第【5】步

**處置步驟**：

【1】確認「誰贏了」：

```bash
apt policy openssl
```

預期輸出（問題現場）：

```text
openssl:
  Installed: 3.5.0-1~noble
 *** 3.5.0-1~noble 500
        500 https://deb.myguard.nl/apt noble/main amd64 Packages    # ★★★★★ 第三方也拿到 500
     3.0.13-0ubuntu3.4 500
        500 http://archive.ubuntu.com/ubuntu noble-updates/main amd64 Packages
```

★★★★★ 兩邊都是 500 時**版本號大的贏** —— 這就是第三方庫悄悄接管系統套件的方式。

【2】先止血，換回官方版本：

```bash
sudo apt install openssl=3.0.13-0ubuntu3.4 --allow-downgrades
sudo systemctl restart nginx php8.3-fpm      # ★★★★ 舊行程還跑在舊 ABI 上，一定要重啟
apt policy openssl | head -3
```

【3】再治本，把整個庫壓到 100，只放行真正要的：

```bash
sudo tee /etc/apt/preferences.d/myguard <<'EOF'
Package: *
Pin: release o=MyGuard
Pin-Priority: 100

Package: nginx nginx-* libnginx-*
Pin: release o=MyGuard
Pin-Priority: 700

Package: openssl libssl3 libc6 systemd
Pin: release o=MyGuard
Pin-Priority: -1
EOF
apt policy nginx openssl | grep -E '^\S+:$|[0-9-]+ http'
```

- 庫仍顯示 `500` → ★★★ 多半是 `Pin: origin "…"` 寫成 Release 的 Origin 欄位而不是主機名，
  改用 `Pin: release o=MyGuard` 精準比對
- 放行套件仍是 `100` → 萬用字元沒涵蓋（★★★ `nginx-*` **不含** `nginx` 本身）
- 封鎖套件不是 `-1` → `preferences.d/` 裡字典序更後面的檔覆蓋了它
- ★★★ 出現 `held broken packages` → 放行清單漏了相依（放行 `nginx` 卻沒放行 `nginx-common`）

【4】半夜自動升級：`grep -rn 'Allowed-Origins\|Package-Blacklist\|Automatic-Reboot'
/etc/apt/apt.conf.d/50unattended-upgrades`。把第三方庫從 `Allowed-Origins` 拿掉，
或把關鍵套件加進 `Package-Blacklist`；★★★★ 正式機的 `Automatic-Reboot` 一律關掉。

【5】孤兒套件（掃描報高風險但 `apt upgrade` 說沒得升）：
`sudo /usr/local/sbin/apt-repo-audit | sed -n '/## 3/,/## 4/p'`，
看 `__ORPHAN__` 那一列。★★★★ 不是 0 就代表這些套件永遠收不到安全更新，
逐一決定「移除」或「找回官方替代品」，不能放著。

**原理**：apt 預設給每個來源 500 優先權，第三方庫因此和官方平起平坐；
pinning 是把「有限度信任」寫成設定的唯一方式。
→ 原理詳見 [[020-02-03-03-cmd-標準化-第三方APT套件庫實務]]

**預防**：第三方庫**加入的同時**就放 `preferences.d/` 檔；
核心函式庫（`libc6`、`openssl`、`systemd`）一律 `-1` 封鎖；
第三方套件不在發行版 CVE 追蹤範圍，要自己納管（[[090-07-03-guide-資安實踐-弱點與修補管理流程]]）。

### ★★★★★ 情境五：SSH 連不進去 —— 你和所有人都被鎖在門外

**現象**：

```text
Permission denied (publickey).
ssh: connect to host web-prd-01 port 22: Connection refused
ssh: connect to host web-prd-01 port 22: Connection timed out
```

★★★★★ **先確認你手上還有沒有一個活著的舊 session** —— 有的話那是你最寶貴的資產，
**在問題解決前絕對不要關掉它**。

**判斷分流**（在還能連的地方跑）：

```bash
nc -vz web-prd-01 22
```

- `Connection refused` → sshd 沒在跑，或埠變了 → 第【2】步
- `Connection timed out` → 防火牆／路由／機器沒開 → 第【3】步
- 連得上但 `Permission denied (publickey)` → 認證問題 → 第【4】步
- 以上都不通且沒有活著的 session → 直接走 console，第【1】步

**處置步驟**：

【1】走帶外通道：PVE 用 `qm terminal <VMID>` 或 Web VNC，實體機用 IPMI／iDRAC／iLO。
★★★★ 這條路必須**平時就測過**，出事當天才發現 IPMI 密碼沒人知道是常見的二次災難。

【2】埠變了，或 socket 活化沒重生成（Ubuntu 24.04 常見）：

```bash
sudo ss -lntp | grep sshd
sudo sshd -T | grep -i '^port'
sudo systemctl daemon-reload && sudo systemctl restart ssh.socket
```

★★★★ `sshd -T` 說 22 但 `ss` 顯示 2222 → 埠由 systemd generator 從設定檔產生，
`systemctl reload ssh` **不會**重新生成，一定要 `restart ssh.socket`。

【3】防火牆把自己關在外面：

```bash
sudo ufw status numbered
sudo ufw allow 22/tcp
```

★★★★★ `ufw enable` 前一定要先 `allow 22`。
★★★★ 基準範本的角色層覆蓋也會造成同樣結果 —— 清單型變數是**整個取代不是合併**，
角色層若只寫 `80/tcp 443/tcp`，`22/tcp` 就消失了。

【4】公鑰認證失敗的逐層排除（從你的工作站跑）：

```bash
ssh -vv -i ~/.ssh/id_ed25519_ops ops@web-prd-01 'id -un' 2>&1 \
  | grep -iE 'offering|accepts|denied|authentications that can continue'
```

- 有 `Offering` 沒有 `Server accepts` → 公鑰不在目標的 `authorized_keys` 裡
- 連 `Offering` 都沒有 → 本機私鑰權限錯（必須 600）或路徑寫錯
- `Authentications that can continue: password` → 目標的 `authorized_keys` 是空的

【5】在 console 上修權限 —— ★★★ sshd 對權限錯誤是**靜默拒絕**，不會告訴你原因：

```bash
sudo chown -R sysadm:sysadm /home/sysadm/.ssh
sudo chmod 700 /home/sysadm/.ssh; sudo chmod 600 /home/sysadm/.ssh/authorized_keys
sudo tail -20 /var/log/auth.log
# Authentication refused: bad ownership or modes for directory /home/sysadm/.ssh
```

【6】確認到底是哪個設定檔贏了：

```bash
sudo grep -rn -iE 'passwordauthentication|kbdinteractive|allowgroups' \
  /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
sudo sshd -T | grep -iE 'passwordauth|kbdinter|allowgroups|permitrootlogin'
```

★★★★★ sshd 是**先出現者勝**（`Include` 在 `sshd_config` 最開頭），
所以 `sshd_config.d/50-cloud-init.conf` 會贏過 `sshd_config` 本體。
★★★★ 一律用 `sshd -T` 判斷生效值，**不要 grep 設定檔**。
★★★ `AllowGroups` 打錯字或群組不存在 → 所有人都不符合 → 全部被拒；用 `getent group <名稱>` 對照。

【7】固定收尾動作：

```bash
sudo sshd -t && sudo systemctl reload ssh      # ★★★★ 先驗語法再 reload，不要 restart
sudo sshd -T | grep -iE 'passwordauth|port'
```

★★★★★ **另開一個新視窗實測登入成功**，才可以關掉手上的舊 session。

**原理**：帳號初始化有不可顛倒的六步（建帳號 → 加 sudo → 部署公鑰 →
**另開 session 實測** → 才停用密碼登入 → reload 後再複驗），顛倒就是鎖門事故。
→ 原理詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]、[[020-02-01-07-svc-SSH-安全強化]]

**預防**：把「另開 session 實測」列為 SOP 紅線項；sshd 範本一律先在 tst 環境套用；
任何改 sshd 的變更單都要求「保留一條既有連線」。

### ★★★★★ 情境六：設定檔明明改了，服務卻完全照舊

**現象**：檔案內容你確認過三次沒錯，但

```text
$ sudo sshd -T | grep -i permitrootlogin
permitrootlogin yes                    # ★★★★ 檔案裡明明寫 no
$ sysctl -n net.core.somaxconn
4096                                   # ★★★★ 你剛才改成 8192
$ grep SystemMaxUse /etc/systemd/journald.conf.d/50-baseline.conf
SystemMaxUse=                          # ★★★★★ 值是空的，而且完全沒有錯誤訊息
```

**判斷分流**：

```bash
sudo sshd -T | grep -iE 'permitrootlogin|^port'
sudo systemd-analyze cat-config systemd/journald.conf | tail -8
sysctl -n net.core.somaxconn
```

- **生效值 ≠ 你的檔案內容** → 有別的檔蓋過你，第【1】步
- **產出檔裡的值是空的** → 範本變數沒定義，第【3】步
- 生效值就是你寫的但服務行為沒變 → 沒 reload，或 socket 活化（情境五第【2】步）

**處置步驟**：

【1】★★★★★ 兩個方向相反的規則，排查時千萬別記反：

| 設定系統 | 誰贏 | 怎麼確認生效值 |
| --- | --- | --- |
| ★★★★★ `sshd_config` | **先出現者勝**（找數字更**小**的檔） | `sshd -T` |
| ★★★★★ `sysctl.d` | **後讀者勝**（找數字更**大**的檔） | `sysctl -n <key>` |
| ★★★★ systemd drop-in | 後讀者勝 | `systemd-analyze cat-config <路徑>` |
| ★★★★ `apt preferences.d` | 字典序在後的覆蓋 | `apt policy <套件>` |

```bash
ls -1 /etc/ssh/sshd_config.d/ /etc/sysctl.d/
```

【2】RHEL 系的兩個專屬陷阱：`head -5 /etc/ssh/sshd_config` ——
RHEL 8 可能**沒有 `Include` 那行**，drop-in 根本不會被讀，自己補在最前面；
檔案從別處 `mv` 進 `/etc` 會帶錯 SELinux context（症狀是 sshd 啟動失敗 `Permission denied`），
用 `sudo restorecon -Fv <檔>` 修。

【3】範本 render 的三個坑，一組指令篩出來：

```bash
sudo /usr/local/sbin/baseline-render
grep -nE '\$\{|=[[:space:]]*$' /run/baseline-staging/* || echo "clean"
```

- 輸出 `SystemMaxUse=` 這種空值行 → ★★★★★ **變數未定義被 render 成空字串**，
  語法合法、語意全錯、`envsubst` 還回傳 0。回第【4】步查變數
- 輸出 `${BASELINE_XXX}` → 變數拼錯或沒加前綴，沒進白名單
- ★★★★★ nginx 範本 render 後 `$remote_addr` 全空 → **裸跑 `envsubst`** 把合法變數名一起吃掉了，
  必須用白名單 `envsubst "$WL" < tpl`，`WL` 由 `compgen -v | grep '^BASELINE_'` 產生

【4】查四層變數的最終值與覆寫者：

```bash
sudo /usr/local/sbin/baseline-render --dump-vars | grep BASELINE_UFW_ALLOW
grep -n 'BASELINE_UFW_ALLOW' /srv/baseline/vars/*.env
# global.env:31:BASELINE_UFW_ALLOW="22/tcp"
# role-web.env:4:BASELINE_UFW_ALLOW="22/tcp 80/tcp 443/tcp"
```

★★★★ 載入順序 global → role → env → host，**最後一層獲勝，而且是整個取代不是合併**。
角色層漏抄共通項就是常見事故源頭。

【5】升級把你的設定蓋掉了（或把新選項擋在門外）：
`sudo find /etc \( -name '*.dpkg-dist' -o -name '*.dpkg-new' -o -name '*.ucf-dist' \)`，
再 `diff -u` 現行檔與 `.dpkg-dist`。
★★★★ 正確處置：diff 兩者 → 把新版帶來的**新選項補進 repo 範本** → 重新 render 套用 →
刪掉 `.dpkg-dist`。★★★ **不要直接 `mv` 覆蓋**，那等於繞過真值來源，下次 render 又被推回去。

**原理**：`/etc` 底下每個設定系統的合併規則不同，「檔案內容」與「生效值」是兩件事；
範本化的價值就是把生效值收斂到單一真值來源。
→ 原理詳見 [[020-02-03-02-ref-標準化-基準設定與範本化]]

**預防**：所有基準檔走 `render → validate → 才寫入`；必填變數加 `: "${VAR:?}"`；
驗收一律看 `sshd -T` / `sysctl -n` 而不是 grep 設定檔。

### ★★★★ 情境七：每天早上的漂移報告都有紅字，大家開始忽略它

**現象**：`/var/log/baseline-drift.log` 每天長這樣，久了沒人看。

```text
=== baseline-apply (check)  host=web-prd-02  版本=baseline-2026.08  2026-08-29 06:00:07 CST ===
--- repo:/etc/ssh/sshd_config.d/50-baseline.conf
+++ live:/etc/ssh/sshd_config.d/50-baseline.conf
-Port 22
+Port 2222
[DRIFT] 未納管檔案 /etc/ssh/sshd_config.d/99-debug.conf —— 可能是有人手動新增的（漂移）
=== 結果：偵測到漂移（退出碼 2）===
```

**判斷分流**：

```bash
sudo journalctl -u baseline-drift.service --since '-7d' | grep -c DRIFT
sudo etckeeper vcs log --oneline -- /etc/ssh/sshd_config.d/ | head -10
```

- **每台都有、而且是同一行** → 多半是報告本身的雜訊，第【1】步
- **每天固定時間出現** → 有另一個排程在改同一個檔，第【2】步
- **只有一兩台、內容各異** → 真的有人手改，第【3】步
- 日誌出現 `committing changes in /etc after apt run` → 升級改的（情境六第【5】步）

**處置步驟**：

【1】先消除假漂移，否則真漂移會被淹掉：`head -3 /srv/baseline/templates/*.tpl`。
★★★★ 範本檔頭**只能放 `BASELINE_VERSION`，不可以放 render 時間戳**；
timer 要先 `git pull --ff-only` 再 render，否則 repo 版本與各機不同步也會製造差異。

【2】確認是不是別的工具在管同一個檔：
`systemctl list-timers --all | grep -iE 'baseline|twgcb|ansible|puppet'`。
★★★★ 本篇範本、TWGCB 派送（[[090-06-06-guide-TWGCB-Linux大量派送]]）、Ansible 同時管同一個檔，
就會「今天符合基準、明天又不符合」鬼打牆。解法只有一個：
**劃檔案歸屬表，一個檔只能有一個擁有者。**

【3】★★★★★ 分類，不要先動手。每一筆漂移只有三種歸屬：

| 類別 | 例子 | 處置 |
| --- | --- | --- |
| ★★★ 立刻回填 | `sysctl` 安全參數、`issue.net` 警語、檔案權限 | 可腳本自動修，仍要分批 |
| ★★★★★ 先告警等人工確認 | `sshd`、防火牆規則、服務設定 | ★ 自動改會斷線，一律人工判斷 |
| ★★★ 納入例外白名單 | 合理的單機差異 | 補 `host-*.env`（原因／核准／到期）+ 變更單 |

先查 [[100-02-08-guide-維運-變更管理流程]] 有沒有對應 CHG 單號 ——
**沒有單號就是漂移，有單號才可能是合理例外**。

【4】以 `Port 2222` 這個真實案例為例：

```bash
# ★★★★★ 先確認 22 是通的！防火牆此刻若只開 2222，自動改回 22 會當場斷掉所有管理連線
ssh web-prd-02 'sudo ufw status | grep -E "22|2222"'
ssh web-tst-01 'sudo baseline-apply --apply --file sshd_config.d'   # ★★★ 先在 tst 驗
```

tst 新連線進得來之後，才對正式機單台套用：

```bash
sudo /usr/local/sbin/baseline-render
sudo /usr/local/sbin/baseline-apply --apply --file sshd_config.d
# ★★★★★ 保留這條 session，另開視窗驗證 22 埠可登入
```

【5】收尾三件事，缺一件下個月會再抓到同一筆：

```bash
sudo rm /etc/ssh/sshd_config.d/99-debug.conf     # 未納管檔案一併清掉
sudo ufw delete allow 2222/tcp                   # 收回臨時規則
sudo /usr/local/sbin/baseline-apply --check      # 差異必須收斂到 0
```

再到 `docs/CHANGELOG.md` 記一行（什麼時候、誰、為什麼、怎麼收斂）並補一張事後變更單。
★★★★★ 回滾機器之後**一定要把 repo 也改回去或修正**，
否則下次 `--apply` 又把壞設定推一次 —— 這是最常見的二次事故。

**原理**：漂移偵測的價值不在「抓到」，在「每一筆都被分類與結案」；
diff 法知道「對不對」、etckeeper 知道「誰改的」、FIM 知道「正在被改」，三者互補。
→ 原理詳見 [[020-02-03-02-ref-標準化-基準設定與範本化]]

**預防**：排查用的臨時設定一律放**另一個檔**並在變更單裡寫回填期限；
「漂移報告歸零」列進月維護檢查（[[100-02-07-ref-維運-維護檢查表範本]]）；
關鍵路徑加 FIM 即時告警（[[090-08-04-guide-Wazuh-FIM檔案完整性監控]]）。

### ★★★★★ 情境八：內部套件庫發了新版，客戶端拿不到或裝錯版本

**現象**：

```text
E: The repository 'https://apt.example.gov.tw noble InRelease' is not signed.
   NO_PUBKEY 9F8E7D6C5B4A3928                     # ★★★★★ 全機關同時發生
org-ca-certificates: Candidate: 1.0.0             # ★★★★ 明明已經發布 1.1.0
E: Conflicting distribution: … (expected stable but got noble)
Hash Sum mismatch
```

**判斷分流**：★★★★ 一律**由外而內**依序走，不要跳。

```bash
sudo reprepro -b /srv/apt list noble org-ca-certificates      # 在建置機上
```

- 有看到期待的版本 → 問題在**發布或客戶端**，第【2】步
- 沒有輸出 → 問題在**匯入**，看 `/var/log/repo-publish.log`
- 一開始就是全機關 `NO_PUBKEY` → **金鑰輪替出事**，直接跳第【5】步

**處置步驟**：

【2】從外部抓索引，確認 rsync 真的推出去了：

```bash
curl -s https://apt.example.gov.tw/dists/noble/InRelease | head -12
# Date: Sat, 29 Aug 2026 11:05:12 UTC        ← 舊的代表 rsync 沒跑
# Valid-Until: Sat, 12 Sep 2026 11:05:12 UTC ← ★★★★ 過期就重新 export
```

- `Valid-Until` 已過 → `sudo reprepro -b /srv/apt export noble` 後重新同步
- `404` → Nginx 的 `root` 或 `location` 設錯，看 `/var/log/nginx/apt.error.log`
- `Hash Sum mismatch` → ★★★ 透明代理／CDN 快取了舊索引，或 rsync 傳到一半。
  對 `dists/` 加 `Cache-Control: no-cache`、rsync 改用 `--delay-updates`，
  客戶端 `sudo rm -rf /var/lib/apt/lists/*`

【3】確認外部拿到的 `Packages` 真的含目標版本：
`curl -s https://<庫>/dists/noble/main/binary-amd64/Packages.gz | gunzip | grep -A3 '^Package: org-ca-certificates$'`。
完全找不到 → `Components` 或 `Architectures` 與 `conf/distributions` 不符。

【4】用**客戶端手上的那把公鑰**驗簽（不是用建置機的）：

```bash
curl -s https://apt.example.gov.tw/dists/noble/InRelease -o /tmp/InRelease
gpgv --keyring <(gpg --dearmor < /etc/apt/keyrings/org-apt.asc) /tmp/InRelease
```

- `Good signature from …` → 簽章沒問題，往第【6】步
- `Can't check signature: No public key` → 客戶端公鑰不是最新的，第【5】步
- `BAD signature` → 檔案傳輸中被改動或 rsync 傳到一半，重新同步

【5】★★★★★ 金鑰輪替造成的全機關停擺 —— 先止血，再走正確流程：

```bash
sudo sed -i "s/^SignWith: .*/SignWith: $OLD_FPR/" /srv/apt/conf/distributions
sudo reprepro -b /srv/apt export noble        # 先改回舊金鑰，讓大家能更新
```

之後照四階段輪替（T0 產新金鑰 → +2 週派送**含新舊兩把**的 keyring →
+4 週才切 `SignWith` → +6 週移除舊公鑰）。第二階段有個硬閘門：

```bash
for h in $(cat /etc/org/hosts.txt); do
  printf '%-24s ' "$h"
  ssh "$h" 'dpkg-query -W -f="${Version}\n" org-apt-keyring 2>/dev/null || echo MISSING'
done | grep -v ' 2\.0\.0$'          # ★★★★★ 這裡必須沒有任何輸出才能切
```

【6】客戶端側：`Candidate` 不對或看不到這個庫 ——
`sudo rm -rf /var/lib/apt/lists/* && sudo apt update; apt-cache policy org-ca-certificates`。
★★★ `.sources` 的副檔名寫成 `.list` 或 `.conf` 會被**完全忽略**，這是最常見的低級錯誤。
★★★ `Conflicting distribution` 是客戶端 `Suites:` 與 `conf/distributions` 的
`Codename`/`Suite` 不符，兩邊統一即可。
★★★ `apt upgrade` 完全不動新套件 → 新版本號**不大於**舊版，用 `dpkg --compare-versions` 驗。

【7】★★★★ 檢查 pinning 有沒有反效果，這一步不能省：`apt-cache policy | grep -B2 -A2 '1001'`。
若 `1001` 那行出現的是 `archive.ubuntu.com`，代表 pin 的比對條件寫錯，
**官方安全更新可能已經被壓住** —— 內部庫的 pin 一律縮到 `Package: org-*`，
再跑 `apt list --upgradable` 確認沒有漏掉的更新。

【8】套件裝了（`ii`）但東西沒生效：
`openssl x509 -in /usr/local/share/ca-certificates/org-root.crt -noout -subject`。
★★★★ `update-ca-certificates` 對**副檔名不是 `.crt`** 或**內容是 DER 不是 PEM** 的檔案
會靜默忽略，用 `-inform DER` 轉檔後重新打包。
★★★★★ 若症狀是「升級後全機關內部 HTTPS 全部憑證錯誤」，元兇是 `postrm` 沒寫
`case "$1"` 分流，升級時舊版 postrm 以 `upgrade` 被呼叫、刪掉了新版剛解開的憑證 ——
修 postrm 發新版，受影響機器 `apt install --reinstall org-ca-certificates`。

**原理**：一個 APT 套件庫就是「一堆檔案 + 一個簽章」，整條信任鏈只靠簽章私鑰，
所以簽章機與發布機必須分離、金鑰輪替必須新舊並存。
→ 原理詳見 [[020-02-03-04-svc-標準化-自建APT套件庫]]

**預防**：`Valid-Until` 到期前自動重新 `export` 並納入監控；金鑰輪替寫成六週標準變更單；
發布腳本每一步都留 log 到 `/var/log/repo-publish.log`。

### ★★★★★ 情境九：Ansible 跑不動，或每次跑完都一堆 changed

**現象**：

```text
fatal: [web-tst-01]: UNREACHABLE! => {"msg": "Failed to connect … Permission denied (publickey)"}
fatal: [web-tst-01]: UNREACHABLE! => {"msg": "Host key verification failed."}
ERROR! couldn't resolve module/action 'community.general.ufw'
changed: [web-tst-01]                      # ★★★★★ 第二次、第三次跑還是 changed
```

**判斷分流**：★★★★ 第一件事永遠是分清楚 provision 還是 configure。

```bash
ansible all -m ping
```

- `UNREACHABLE` → 問題在 **provision**（cloud-init／SSH／網路），第【1】步。
  ★★★★ **不要去改 playbook**，那裡沒有問題
- `SUCCESS` 但 playbook 失敗 → 問題在 **configure**，第【5】步
- 全部成功但每次都 `changed` → 冪等性問題，第【6】步

**處置步驟**：

【1】機器活著嗎、SSH 起來了嗎：`ping -c 2 10.10.20.31; nc -vz 10.10.20.31 22`。
ping 不通 → VM 沒開或網路錯，去 console。ping 通但 22 拒絕 → cloud-init 還沒跑完，第【2】步。

【2】在 VM console 上看 cloud-init：

```bash
cloud-init status --long
sudo grep -iE 'error|warn|traceback' /var/log/cloud-init.log | tail -20
sudo head -20 /var/lib/cloud/instance/user-data.txt
```

預期輸出（失敗時）：

```text
status: error
errors: - Cloud-init 26.1 failed in stage modules-config
util.py[WARNING]: Failed loading yaml blob. Invalid format at line 12 column 7
```

★★★★★ `Failed loading yaml blob` → **user-data 整份被丟掉**，帳號、公鑰、套件全都沒建。
回 PVE 修 snippet，用 `cloud-init schema --config-file` 驗過再重建 VM。
★★★★ `user-data.txt` 是空的或不是你寫的 → `--cicustom` 路徑錯或 snippets 沒啟用；
注意 **cicustom 的 user 段完全取代面板的 `sshkeys`，不是合併**。

【3】改了 user-data 重開機卻沒生效：`runcmd` 等模組是 once-per-instance，同一台不會重跑。
測試機用 `sudo cloud-init clean --logs --reboot`；
★★★★★ **正式機不要跑 `cloud-init clean`**，改成重建 VM。

【4】host key 對不上：`ssh-keygen -R 10.10.20.31 && ssh-keyscan -H 10.10.20.31 >> ~/.ssh/known_hosts`。
★★★★★ **不要**設 `host_key_checking = False`，那等於永久放棄中間人攻擊防護。

【5】playbook 失敗：先 `-vvv` 看真正的錯誤，再對症下藥。

```bash
ansible-playbook baseline.yml --limit web-tst-01 -vvv 2>&1 | tail -40
```

| 錯誤訊息 | 處置 |
| --- | --- |
| `No package matching 'chronyd'` | 套件名寫錯（Ubuntu 是 `chrony`）或鏡像沒有 |
| `couldn't resolve module/action` | `ansible-galaxy collection install community.general ansible.posix` |
| `sudo: a password is required` | NOPASSWD 沒設好，改用 `-K` 或修 `/etc/sudoers.d/` |
| `sudo: a terminal is required` | sudoers 有 `requiretty`，先在 `ansible.cfg` 關掉 `pipelining` |
| `Failed to update apt cache` | 內網連不到上游，確認來源指向內部鏡像（情境八） |
| `ansible.cfg` 完全沒生效 | ★★★ 目錄 world-writable 會被忽略：`chmod o-w .` |
| `group_vars` 變數在某台沒作用 | `ansible-inventory --graph` 看它是不是在 `ungrouped` |
| `baseline_packages` 少裝共通套件 | ★★★★ 變數覆寫是整個取代，角色層要把共通項重抄一次 |

【6】★★★★★ 找出哪個 task 每次都 changed（非冪等的副作用）：

```bash
ansible-playbook baseline.yml --limit web-tst-01 --diff 2>&1 | grep -B12 '^changed:'
# -# 由 Ansible 管理，產生於 2026-08-28T10:15:33
# +# 由 Ansible 管理，產生於 2026-08-29T10:22:07     ← 只差時間戳
```

- 只差時間戳 → 範本裡塞了 `ansible_date_time`，拿掉就好
- ★★★★★ **同一行被反覆新增** → `lineinfile` 的 `regexp` 匹配不到自己寫的內容，
  設定檔會**無限膨脹**，最後撐爆磁碟或讓服務讀到上千行重複設定。改用 `template` 管整個檔案
- 用了 `command` / `shell` 卻沒有 `creates:` / `changed_when:` → 永遠 changed
- `mode: 0644` 沒加引號 → 被當成十進位整數誤判，每次都 changed

【7】驗收：`ansible all --become -m shell -a 'timedatectl show -p Timezone --value; ufw status | head -1' -o`
的三台輸出必須**一模一樣**。★★★ 有任何一台不同，那台就是「特例機」，
要嘛補進 playbook，要嘛在 `host_vars` 裡明確記錄例外原因與到期日。

**原理**：provision（把機器變出來）與 configure（把機器設定成該有的樣子）是兩件事，
分不清就會在錯的地方找問題；冪等性是「同一支 playbook 跑一百次結果相同」的保證。
→ 原理詳見 [[020-02-03-05-svc-標準化-自動化佈建入門]]

**預防**：`ansible-lint` 進 CI；派送前一律 `--check --diff` 乾跑；用 `--limit` + `serial` 分批；
★★★★★ 派送前先回答「這支 playbook 出事，我怎麼在 30 分鐘內恢復？」，
答不出來就不要送 —— 沒演練過的回滾方案等於沒有回滾方案。

### ★★★★ 情境十：新機一上線就出事 —— IP 衝突、時間錯亂、sudo 變慢

**現象**（多半是別人先來跟你講）：

```text
「新機一開起來，隔壁那台印表機伺服器就斷線了」
「SIEM 上這台的日誌時間差 8 小時，關聯規則都不觸發」
「加入 AD 網域失敗：Clock skew too great while getting initial credentials」
「每次 sudo 都要等 5 到 10 秒才有反應」
```

**判斷分流**：

```bash
ip -br a; timedatectl status; hostname -f
```

- 有別的設備同時斷線 → IP 衝突，第【1】步
- `Time zone` 不是 `Asia/Taipei` 或 `RTC in local TZ: yes` → 第【2】步
- `System clock synchronized: no` → 第【3】步
- `hostname -f` 只回短名，或 `sudo` 變慢 → 第【4】步

**處置步驟**：

【1】★★★★★ IP 衝突：先斷網，再查表。

```bash
sudo ip link set ens18 down
sudo arping -D -I ens18 -c 3 10.20.30.41; echo "rc=$?"      # rc 非 0 = 位址已被占用
```

回頭查資產盤點表重新配發。★★★★ **不要用 ping 判斷位址空閒** ——
對方可能擋 ICMP 或剛好關機中。

【2】時區與硬體時鐘：

```bash
sudo timedatectl set-timezone Asia/Taipei
sudo timedatectl set-local-rtc 0     # ★★★★ 硬體時鐘一律 UTC，改完用 timedatectl status 複驗
```

★★★★★ **已經送出去的日誌無法回溯修正** —— 該區間必須在事件報告中註記，不要假裝沒發生。

【3】對時：`chronyc sources -v` 看來源，`sudo chronyc makestep` 強制對時，
`chronyc tracking` 複驗。Kerberos 預設只容忍 5 分鐘偏差，對完時再 `realm join`。
★★★★ 確認 NTP 來源與網域控制站一致，否則過幾小時又會漂開。

【4】hostname 與 `/etc/hosts` 沒同步：

```bash
grep 127.0.1.1 /etc/hosts; hostname -f
# 127.0.1.1   web-prd-01.example.gov.tw   web-prd-01     ← ★★★ FQDN 在前、短名在後
```

順序寫反 → `hostname -f` 只回短名，憑證與郵件通知的來源名稱會錯。
完全沒有這行 → `sudo` 解析主機名時等 DNS timeout，那 5～10 秒就是這樣來的。

**原理**：基準設定的六件事（hostname、時區、NTP 來源、RTC、locale、套件來源）
之所以排在納管之前，是因為後面每一件事都依賴它們。
→ 原理詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]、[[020-01-28-cmd-Linux-時間同步NTP與chrony]]

**預防**：IP 一律從盤點表配發（[[040-02-11-guide-機房-資訊設備盤點]]）；
六件事寫進 cloud-init 範本與基準範本，不靠人工記憶；驗收表逐條驗過才簽核。

### ★★★★ 情境十一：驗收腳本退出碼不是 0，卡在紅線項

**現象**：

```text
$ sudo /usr/local/sbin/server-build-verify | grep FAIL
  FAIL 13 密碼登入已關閉      實際=pwd=yes kbd=no 預期=password=no 且 kbdint=no
  FAIL 20 監控 agent 已納管   實際=服務在跑但平台查無此主機
  FAIL 21 日誌轉送已設定      實際=缺轉送設定或寫入失敗
  FAIL 22 備份首次成功        實際=查無備份紀錄
退出碼：2
```

**判斷分流**：★★★ 同時出現多項通常是**不同原因**，要分開查。

| FAIL 項 | 往哪裡走 |
| --- | --- |
| 13 密碼登入 | 情境六第【1】步：確認誰贏了 |
| 20 監控 | 第【2】步 |
| 21 日誌轉送 | 第【3】步 |
| 22 備份 | ★★★★★ 第【5】步，紅線中的紅線 |
| 腳本整支中斷 | 第【6】步 |

**處置步驟**：

【2】監控裝了但「沒有通知對象」是最常見的假納管：

```bash
systemctl is-active wazuh-agent
sudo /var/ossec/bin/agent_control -l 2>/dev/null | head
```

★★★★ agent 在跑**不等於**納管完成，必須到平台確認：有資料點、有加進群組、有告警路由到人。
★★★★★ 驗收時要**實際觸發一次告警**確認收得到，否則就會出現「機器掛了三天沒人知道」。

【3】日誌轉送：先確認本機寫得進 journal，再確認送得出去。

```bash
logger -p local0.notice "PROBE-$$"; sleep 1; journalctl --since '-1 min' | grep "PROBE-$$"
```

有輸出 → 本機正常，往下。沒輸出 → journald 有問題，
先查 `systemctl status systemd-journald` 與 `/var/log` 是否寫滿（情境三）。

```bash
grep -rn '@' /etc/rsyslog.d/; sudo ss -tnp | grep 6514
```

看到 `ESTAB` → 連線已建立，問題在對端沒收到或沒索引，找日誌平台管理員。沒有連線 → 第【4】步。

【4】從這台實測對端的埠：
`timeout 5 bash -c 'cat </dev/null >/dev/tcp/log.example.gov.tw/6514' && echo OPEN || echo BLOCKED`。
★★★★ `BLOCKED` 代表防火牆規則沒開 —— 通常是資源配發階段的「VLAN／防火牆開通單」漏了一條。
**回去補開通單，不要自己在主機上繞路**（開隧道之類的做法會變成沒人知道的技術債）。

【5】★★★★★ 「這台從沒被備份」是不能簽核的紅線。到備份平台確認三件事：
有這台的任務、最近一次成功、**還原測試紀錄**。立即納入備份並實際做一次還原測試
（[[060-01-06-03-guide-傳輸-備份策略與還原演練]]）—— 沒做過還原測試的備份等同沒有備份。

【6】腳本自己在某一項就整支中斷：`sudo bash -x /usr/local/sbin/server-build-verify 2>&1 | tail -20`。
★★★ `set -e` 下某個取值指令回傳非零（例如沒有 LVM 時 `vgs` 失敗）就會整支死掉；
用 `safe()` 包裝取值、用 `if` 取代 `cond && x`。

【7】全部修完重跑，退出碼必須是 0：

```bash
sudo /usr/local/sbin/server-build-verify --table > /root/verify-final.md; echo "退出碼：$?"
```

★★★★★ **退出碼不是 0 就不要拿去簽核。** 確實無法修正的項目，
必須填進交付單的「例外項目與核准依據」並取得核准人簽名 ——
**而不是把那一行從表格裡刪掉**。

**原理**：驗收腳本把 SOP 的 22 項檢查變成可執行的證據，
紅線項（密碼登入、日誌轉送、備份）不通過就不算交付完成。
→ 原理詳見 [[020-02-03-01-svc-標準化-新機建置標準流程]]

**預防**：驗收腳本納入基準 repo 隨基準一起改版；每季對既有機器重跑一次；
例外項一律有到期日與複查人（[[100-01-03-guide-日誌-系統監控與告警]] 負責「告警送得到人」那一半）。

### ★★★★ 情境十二：撤掉的套件庫過幾天自己又回來了

**現象**：

```text
# 上週已經撤掉的來源，今天 apt update 又出現：
Get:5 https://deb.myguard.nl/apt noble InRelease
W: … Key is stored in legacy trusted.gpg keyring (/etc/apt/trusted.gpg)
```

或者：弱點掃描報出一批「來源不明」的套件，`apt-cache policy` 查不到出處。

**判斷分流**：

```bash
HOST=deb.myguard.nl
grep -rn "$HOST" /etc/apt/ 2>/dev/null
grep -rn "$HOST" /srv/baseline ~/ansible 2>/dev/null | head
```

- 只有 `/etc/apt` 有殘留 → 撤除沒做乾淨，第【1】步
- **組態管理的程式碼裡還有** → ★★★★★ 這才是真正原因，第【2】步
- 兩邊都乾淨但套件還在 → 孤兒套件，回情境四第【5】步

**處置步驟**：

【1】完整殘留掃描（撤除後一定要跑）：

```bash
HOST=deb.myguard.nl
grep -rn "$HOST" /etc/apt/ 2>/dev/null      # sources.list.d 與 preferences.d 都要
ls -l /etc/apt/keyrings/ | grep -i myguard
apt-cache policy | grep -c "$HOST"          # 撤乾淨時是 0
ls -l /etc/apt/trusted.gpg /etc/apt/trusted.gpg.d/ 2>/dev/null
```

【2】★★★★★ 改組態管理的程式碼，否則下次派送又寫回來：
在 `/srv/baseline` 與 Ansible repo 各跑一次 `git grep -n 'myguard'`，
把 `.sources`、`preferences.d/`、keyring 三處都拿掉，commit、走 PR、重新派送。
★★★ 只改機器不改 repo，就是「回滾了機器沒回滾真值來源」的二次事故。

【3】孤兒金鑰盤點（接手舊機一定要做）：

```bash
gpg --no-default-keyring --keyring /etc/apt/trusted.gpg \
    --list-keys --with-fingerprint --with-colons \
  | awk -F: '/^fpr/{print $10} /^uid/{print "   uid:", $10}'
grep -rhoE 'https?://[^ ]+' /etc/apt/sources.list /etc/apt/sources.list.d/ 2>/dev/null \
  | awk -F/ '{print $3}' | sort -u
```

上面列出的金鑰在下面找不到對應來源 → ★★★★ 那是**孤兒金鑰**，該移除。

【4】移除前先備份，並用完整指紋（★★★★ 不要用短 ID）：

```bash
sudo install -d -m 0700 /root/apt-key-backup
sudo cp -a /etc/apt/trusted.gpg /etc/apt/trusted.gpg.d/ /root/apt-key-backup/
sudo gpg --no-default-keyring --keyring /etc/apt/trusted.gpg \
        --batch --yes --delete-key 9DC858229FC7DD38854AE2D88D81803C0EBFCD88
sudo apt update           # ★★★★ 一定要跑，確認沒有來源因此變成 NO_PUBKEY
```

★★★ `trusted.gpg` 清空後直接把整個檔案刪掉，空檔仍會讓工具誤判「有 legacy keyring」。

【5】撤除前的必要前置（很多人漏掉這步才搞出災情）：
`sudo nginx -T | grep -nE 'autocert|http_shield|zstd'` 找出用到第三方模組的指令，
★★★★ 先註解掉再降回官方版本。順序反過來就會看到
`nginx: [emerg] unknown directive "autocert"`，服務直接起不來。

**原理**：套件庫是供應鏈上的一道門，「加入」與「撤除」都要有程序、有紀錄、有稽核佐證；
組態管理工具才是真值來源，機器只是它的投影。
→ 原理詳見 [[020-02-03-03-cmd-標準化-第三方APT套件庫實務]]、[[020-02-03-05-svc-標準化-自動化佈建入門]]

**預防**：撤除走 `apt-repo-remove --mode purge` 並同步改 repo；
每季 `apt-repo-audit` 產出稽核報告；加庫時就把「撤除計畫」寫進風險評估表
（[[060-02-05-01-guide-MyGuard-MyGuard套件庫介紹]] 是本手冊唯一長期使用的第三方庫實例）。

## 一頁式急救卡

出事時來不及讀長文，先照順序跑這幾個指令，每個都會直接告訴你往哪個方向查。

```bash
# ① 系統還活著嗎、容量夠不夠
uptime; df -h | awk 'NR==1||$5+0>80'; df -i | awk 'NR==1||$5+0>80'; free -h
#   → load 高但 CPU 閒 = IO 卡住；任何 use% >80 = 跳情境三（容量／inode）

# ② 有沒有服務掛了
systemctl --failed --no-pager; systemctl is-system-running
#   → 有 failed unit = 看 journalctl -u <unit> -n 50
#   → degraded 但沒 failed = 開機時有 unit 沒起來，看 journalctl -b -p err

# ③ 套件系統是不是壞在半路
sudo dpkg --audit; sudo fuser -v /var/lib/dpkg/lock-frontend
#   → dpkg --audit 有輸出 = 跳情境二；fuser 有輸出 = 有人在跑 apt，等它跑完

# ④ 來源與金鑰是不是出事（最常見的一類）
sudo apt update 2>&1 | grep -E '^(W:|E:)' || echo "來源正常"
#   → NO_PUBKEY / expired / Signed-By 衝突 = 跳情境一

# ⑤ 我還進得去嗎（改 sshd 前後必跑）
sudo sshd -T | grep -iE '^(port|permitrootlogin|passwordauthentication|allowgroups)'
sudo ss -lntp | grep sshd; sudo ufw status | head -3
#   → sshd -T 的值 ≠ 檔案內容 = 有別的檔蓋過你（情境六）
#   → ss 的埠 ≠ sshd -T 的埠 = socket 活化沒重生成（情境五第 2 步）

# ⑥ 時間對不對（影響簽章驗證、Kerberos、日誌關聯）
timedatectl status | grep -E 'Local time|Time zone|System clock|RTC in local TZ'
#   → synchronized: no 或時區不是 Asia/Taipei = 跳情境十

# ⑦ 設定被誰改過、什麼時候
sudo etckeeper vcs log --oneline -10 2>/dev/null
sudo baseline-apply --check 2>/dev/null | tail -5
#   → 有 DRIFT = 跳情境七；出現 "after apt run" = 升級改的（情境六第 5 步）

# ⑧ 有沒有人動過帳號或提權（懷疑入侵時先跑這個，跑完就停手）
sudo last -n 20; sudo lastb -n 10
grep -E 'session opened for user root|COMMAND=' /var/log/auth.log | tail -20
#   → 有不認識的登入或 sudo 紀錄 = ★★★★★ 停手，看下一節
```

> [!tip] ★★★★ 三個永遠要先做的動作
> 1. **保留現有的 SSH session** —— 問題解決前不要關掉，它是你唯一的後門
> 2. **先讀，再寫** —— `--check`、`-T`、`--diff`、`policy`、`--audit` 都是唯讀的，先用它們定位
> 3. **記下時間與每一個指令** —— 事後報告與變更單都要，`script -a /root/incident.log` 最省事

## 什麼時候該停手求援

> [!danger] ★★★★★ 以下情況立刻停手，繼續操作會讓證據消失或災情擴大
> | 狀況 | 為什麼不能自己動 | 先做什麼 |
> | --- | --- | --- |
> | ★★★★★ **懷疑遭入侵**（不明帳號、不認識的 sudo 紀錄、不明外連） | 你的每個指令都在覆寫記憶體與時間戳，證據會消失 | 保持**開機**、**斷網不斷電**，通報資安窗口；不要重開機、不要 `rm`、不要重裝 |
> | ★★★★★ **資料庫檔案損毀**（`InnoDB: Database page corruption`） | 錯誤的修復指令會讓可救的資料變成不可救 | 立刻停止寫入，對檔案層做**完整副本**（複製不是搬移），聯絡 DBA |
> | ★★★★★ **RAID 降級中或正在 rebuild** | 拔錯一顆盤就是全滅；rebuild 的 IO 壓力最容易誘發第二顆故障 | 先確認備份可用，聯絡硬體廠商，rebuild 期間不做任何非必要操作 |
> | ★★★★★ **簽章私鑰疑似外洩** | 攻擊者能簽出任意套件推給全機關，每台都會驗簽通過並以 root 執行 postinst | 立刻停掉發布主機的 Nginx，走**帶外通道**派送新 keyring，通報資安 |
> | ★★★★ **檔案系統報 `Input/output error`** | 每一次讀寫都可能讓壞軌擴散 | `dmesg -T \| grep -i error` 存證後，先做整碟映像再談修復 |
> | ★★★★ **不知道這台在跑什麼、也找不到 build-record** | 停錯服務會影響你不知道的下游系統 | 先查資產盤點表與交接文件，找到負責人再動手 |
> | ★★★★ **正式環境、上班時間、影響範圍不明** | 補救動作本身可能造成第二次中斷 | 先開事故單，確認回滾方案，約時間窗再動 |
> | ★★★★ **回滾方案沒演練過** | 沒演練過的回滾方案 = 沒有回滾方案 | 先在測試機演練，或改走「砍掉重建 + 還原備份」路線 |

> [!warning] ★★★★ 三個「看起來能救、其實會擴大災情」的動作
> - `rm` 掉正在被程式開著的大 log —— 空間不會釋放，檔案也救不回來（要用 `truncate -s 0`）
> - 手動刪 `/boot/vmlinuz-*` 或 `/lib/modules/*` —— dpkg 狀態不一致，下次開機直接進不去
> - 在 apt 執行中刪 `lock` 檔 —— 套件資料庫損毀，比原本的問題大十倍
