# MySQL 設定檔與調校

> [!abstract] 這篇你會學到
> - 說得出 MySQL **實際讀了哪些設定檔、哪一份贏**，並用 `SHOW GLOBAL VARIABLES` 確認**實際值**而不是你以為的值
> - ★★★★ 為一台 8GB／16GB 的 LXMP 共存主機**算出一張記憶體預算表**，把 PHP-FPM 的 `pm.max_children` 與 MySQL 的 `max_connections` 放進同一個算式，**在 OOM killer 殺掉 mysqld 之前先看到徵兆**
> - 依「專用機／共存機」決定 `innodb_buffer_pool_size`，並用**命中率**驗證這個數字夠不夠
> - ★★★★ 對主管解釋 `innodb_flush_log_at_trx_commit` / `sync_binlog` 的取捨：**「我們選這一組，最壞情況會掉多少資料」**
> - 開對慢查詢日誌（`long_query_time=1`）並用 `mysqldumpslow` / `sys` schema 撈出 Top 10 慢語句，**而不會把磁碟寫爆**
> - 用一支 `mysql-tune-check.sh` 驗收調校結果，**改壞了能在 3 步內救回來**

## 觀念說明

### 調校不是抄參數，是編預算

網路上「MySQL 最佳化參數大全」的最大問題是：**它不知道你這台機器上還跑了什麼**。

```
機關最常見的 LXMP 單機（8 GB RAM）：

  ┌──────────────────────── 8 GB 實體記憶體 ───────────────────────┐
  │                                                                │
  │  OS + page cache   Nginx    PHP-FPM×N    Redis      MySQL      │
  │  ████████          ██       ██████████   ███        ██████████ │
  │   ~1.6 G          80 M        960 M      320 M        ~3.0 G   │
  │                                                                │
  └────────────────────────────────────────────────────────────────┘
                                      ↑
        ★★★★ 每一格都會「長大」。長到總和超過 8 G 那一刻，
              Linux 的 OOM killer 會挑【RSS 最大的那個】殺掉 ——
              那幾乎一定是 mysqld。凌晨批次跑一跑就當機，就是這樣來的。
```

> [!danger] ★★★★★ OOM killer 殺 mysqld 的後果不只是「服務中斷」
> ```
> mysqld 被 SIGKILL → 沒有 graceful shutdown
>   → 重啟時 InnoDB crash recovery（資料量大時可能數分鐘到數十分鐘）
>   → 這段時間 Laravel 全站 500
>   → 若 innodb_flush_log_at_trx_commit ≠ 1，最後約 1 秒的交易【真的會不見】
> ```
> 所以調校的第一個產出**不是設定檔，是一張加得起來的預算表**。

### MySQL 的記憶體分成兩塊，只有一塊會隨連線數放大

```
┌─────────────────────────────────────────────────────────────┐
│ 全域區（Global）—— 啟動時配置一次，與連線數【無關】          │
│   innodb_buffer_pool_size          ← 佔九成以上，最重要      │
│   InnoDB 額外結構（約 buffer pool 的 5~10%）                 │
│   innodb_log_buffer_size                                     │
│   key_buffer_size（只有 MyISAM 用得到）                      │
│   performance_schema 的記憶體                                │
└─────────────────────────────────────────────────────────────┘
                            ＋
┌─────────────────────────────────────────────────────────────┐
│ 每連線區（Per-connection）—— 【每一條連線各配一份】★★★★    │
│   sort_buffer_size / join_buffer_size                        │
│   read_buffer_size / read_rnd_buffer_size                    │
│   thread_stack / binlog_cache_size / net_buffer_length       │
│   tmp_table_size（需要記憶體暫存表時才配）                    │
│                     × 實際並發連線數                          │
└─────────────────────────────────────────────────────────────┘

  最壞情況記憶體 = 全域區 + 每連線區 × max_connections
```

> [!note] 為什麼「把 sort_buffer_size 調成 8M」是新手最常犯的錯
> `sort_buffer_size` 預設只有 256 KB 是**故意的**。
> 它是**每連線**參數 —— 調成 8 MB、`max_connections` 又設 500，
> 最壞情況就是 **8 M × 500 = 4 GB** 憑空長出來。
> ★★★ **每連線參數要調，先問「乘以 max_connections 之後是多少」。**

### 調校的三個階段（順序不能顛倒）

| 階段 | 做什麼 | 為什麼是這個順序 |
| --- | --- | --- |
| **【1】不要死掉** ★★★★ | 編記憶體預算、限制 `max_connections`、確認不會 OOM | 穩定 > 快。會當機的快沒有意義 |
| **【2】不要慢** ★★★ | buffer pool 吃得下熱資料、redo log 夠大、I/O 參數對得上 SSD | 這是「整台機器」層級的調整 |
| **【3】找出爛查詢** ★★★★ | 慢查詢日誌 + `sys` schema，把 Top 10 交給開發 | **一條沒有索引的查詢，比任何參數都傷** |

> [!tip] ★★★ 90% 的「資料庫很慢」最後是階段【3】
> 參數調校最多帶來數倍的改善；一條全表掃描的 SQL 加上索引，常常是**數百倍**。
> 先做【1】保命，再直接跳去【3】找爛查詢，通常 CP 值最高。
> 索引怎麼設計、`EXPLAIN` 怎麼讀，見 [[060-04-01-03-cmd-MySQL-SQL基礎操作]]。

## 基礎設定

### 設定檔在哪裡、誰贏

Ubuntu / Debian 的 MySQL 8.0 套件：

```bash
tree -L 2 /etc/mysql/
```

預期輸出：

```text
/etc/mysql/
├── conf.d/
│   ├── mysql.cnf                 # [mysql] 用戶端區段
│   └── mysqldump.cnf
├── debian.cnf                    # ★ 維護帳號 debian-sys-maint 的密碼（0600）
├── debian-start
├── my.cnf -> /etc/alternatives/my.cnf
├── my.cnf.fallback
└── mysql.conf.d/
    ├── mysql.cnf
    └── mysqld.cnf                # ★ 發行版的伺服器設定，【不要改這一份】
```

`/etc/mysql/my.cnf` 本身幾乎沒有內容，它只做兩件事：

```ini
# /etc/mysql/my.cnf
!includedir /etc/mysql/conf.d/
!includedir /etc/mysql/mysql.conf.d/
```

用 `mysqld` 自己說的為準：

```bash
mysqld --verbose --help 2>/dev/null | head -n 12
```

預期輸出：

```text
mysqld  Ver 8.0.42-0ubuntu0.24.04.1 for Linux on x86_64 ((Ubuntu))
...
Default options are read from the following files in the given order:
/etc/my.cnf /etc/mysql/my.cnf ~/.my.cnf          # ★★★ 順序 = 優先順序
```

> [!warning] ★★★★ 三個必須記住的規則
> **【規則一】同一個參數出現多次，最後讀到的那個生效。**
> 所以 `/etc/mysql/my.cnf` 贏過 `/etc/my.cnf`。
>
> **【規則二】`!includedir` 的檔案讀取順序，官方文件明講「不保證」。**
> 實務上 Debian/Ubuntu 是**依檔名字典序**（所以 `zz-tuning.cnf` 會最後讀到），
> 但**不要依賴它** —— ★★★ **同一個參數絕對不要寫在兩個檔案裡**。
>
> **【規則三】`mysqld-auto.cnf` 讀在最後，它贏過所有設定檔。** ★★★★
> 這是 `SET PERSIST` 寫出來的檔案（在資料目錄 `/var/lib/mysql/`）。
> **「設定檔明明改了卻沒生效」有一半是它。** 查法見下方。

### 為什麼要自建 `zz-tuning.cnf`

```bash
# ★★★ 不要改 /etc/mysql/mysql.conf.d/mysqld.cnf
#     apt upgrade 時 dpkg 會問你要不要覆蓋，選錯就整份沒了；
#     選保留又會一直卡住未來的套件更新。
sudo install -o root -g root -m 0644 /dev/null \
  /etc/mysql/mysql.conf.d/zz-tuning.cnf
```

```
命名為什麼是 zz-：
  · 讀取順序在 mysqld.cnf 之後（字典序），確保我們的值贏
  · 一眼看得出「這是人為調整」，不是發行版原檔
  · 升級時 dpkg 不會碰它（不屬於任何套件）
```

### 確認「實際值」——這是本篇最重要的習慣 ★★★★

**你寫進設定檔的值，跟 MySQL 實際採用的值，是兩件事。**

```bash
mysql -e "SHOW GLOBAL VARIABLES LIKE 'innodb_buffer_pool%';"
```

預期輸出：

```text
+-------------------------------------+----------------+
| Variable_name                       | Value          |
+-------------------------------------+----------------+
| innodb_buffer_pool_chunk_size       | 134217728      |   # 128 MB
| innodb_buffer_pool_dump_at_shutdown | ON             |
| innodb_buffer_pool_instances        | 1              |
| innodb_buffer_pool_load_at_startup  | ON             |
| innodb_buffer_pool_size             | 2147483648     |   # ★ 2 GB，這才是實際值
+-------------------------------------+----------------+
```

一次看全部關鍵參數（人類看得懂的單位）：

```bash
mysql -e "
SELECT VARIABLE_NAME AS name,
       VARIABLE_VALUE AS raw,
       ROUND(VARIABLE_VALUE/1024/1024, 1) AS MB
FROM performance_schema.global_variables
WHERE VARIABLE_NAME IN (
  'innodb_buffer_pool_size','innodb_log_buffer_size','key_buffer_size',
  'sort_buffer_size','join_buffer_size','read_buffer_size',
  'read_rnd_buffer_size','tmp_table_size','max_heap_table_size',
  'binlog_cache_size','thread_stack','max_allowed_packet')
ORDER BY VARIABLE_NAME;"
```

預期輸出（節錄）：

```text
+--------------------------+-----------+---------+
| name                     | raw       | MB      |
+--------------------------+-----------+---------+
| innodb_buffer_pool_size  | 2147483648| 2048.0  |   # ★ 全域，配一次
| join_buffer_size         | 262144    |    0.3  |   # ★ 每連線
| max_allowed_packet       | 67108864  |   64.0  |
| sort_buffer_size         | 262144    |    0.3  |   # ★ 每連線
| tmp_table_size           | 16777216  |   16.0  |   # ★ 每連線（需要時）
+--------------------------+-----------+---------+
```

> [!danger] ★★★★ 「上週明明修好了」——`SET GLOBAL` 與 `SET PERSIST` 的陷阱
> ```sql
> SET GLOBAL max_connections = 300;   -- 立即生效，【重啟就沒了】★★★
> SET PERSIST max_connections = 300;  -- 立即生效，且寫入 mysqld-auto.cnf
> ```
> `SET PERSIST` 寫出的 `/var/lib/mysql/mysqld-auto.cnf` **讀在所有設定檔之後**，
> 於是你在 `zz-tuning.cnf` 改的值**永遠不會生效**，而且沒有任何警告。
>
> 查有沒有被 persist 過：
> ```sql
> SELECT * FROM performance_schema.persisted_variables;
> ```
> 清掉單一項或全部：
> ```sql
> RESET PERSIST max_connections;   -- 清一項
> RESET PERSIST;                   -- 全部清掉（會刪 mysqld-auto.cnf 的內容）
> ```
> **本手冊的建議：正式環境一律用設定檔 + 重啟，`SET GLOBAL` 只用於救火，
> 救完當下就同步改檔。**

### 區分「重啟前後」的值

```sql
SHOW VARIABLES LIKE 'max_connections';         -- ★ 目前 session 看到的
SHOW GLOBAL VARIABLES LIKE 'max_connections';  -- ★★ 伺服器層級，看這個
```

```bash
# ★★★ 設定檔裡寫了什麼（不管有沒有生效）
sudo my_print_defaults mysqld | grep -E 'buffer_pool|max_connections'
```

預期輸出：

```text
--innodb_buffer_pool_size=2G
--max_connections=60
```

**兩者不一致 = 有東西覆蓋了你**（多半是 `mysqld-auto.cnf`，或參數被寫在兩個檔案裡）。

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> ```bash
> # 設定檔位置完全不同
> /etc/my.cnf                    # 主檔，內含 !includedir /etc/my.cnf.d
> /etc/my.cnf.d/                 # ★ 放自訂檔的地方
> /var/log/mysql/mysqld.log      # ★★★ 錯誤日誌路徑不同（Ubuntu 是 /var/log/mysql/error.log）
> /var/lib/mysql/                # 資料目錄（相同）
>
> # 自建調校檔
> $ sudo vi /etc/my.cnf.d/zz-tuning.cnf
> $ sudo systemctl restart mysqld          # ★★★ 服務名是 mysqld，不是 mysql
>
> # ★★★★ SELinux：改 datadir、log 路徑、tmpdir 到非預設位置一定要一起改 context
> $ sudo semanage fcontext -a -t mysqld_db_t "/data/mysql(/.*)?"
> $ sudo restorecon -Rv /data/mysql
> $ sudo ausearch -m avc -ts recent | grep mysqld     # 起不來先查這個
>
> # ★★ RHEL 8/9 的 mysql-server 走 module
> $ sudo dnf module list mysql
> $ sudo dnf module enable mysql:8.0 -y && sudo dnf install -y mysql-server
> ```

> [!info]- MariaDB 對照（★★★ 機關的 RHEL 主機預設常常是 MariaDB，不是 MySQL）
> 先確認你到底裝了什麼：
> ```bash
> $ mysql -V
> mysql  Ver 15.1 Distrib 10.11.9-MariaDB, for Linux (x86_64)   # ★ 這是 MariaDB
> ```
> 主要差異：
>
> | 項目 | MySQL 8.0 | MariaDB 10.6~11.x |
> | --- | --- | --- |
> | 服務名 | `mysql`（Ubuntu）／`mysqld`（RHEL） | `mariadb`（`mysqld` 為別名） |
> | redo log 參數 | `innodb_redo_log_capacity`（8.0.30+） | ★★★ **沒有**，仍用 `innodb_log_file_size` |
> | `SET PERSIST` | 支援 | ★★★ **不支援**（沒有 `mysqld-auto.cnf`，反而少一個坑） |
> | `--validate-config` | 8.0.16+ 支援 | ★★★ **不支援**，只能用 `--help --verbose` 硬驗 |
> | 預設引擎與執行緒池 | InnoDB／無內建 thread pool | InnoDB／★★ 內建 `thread_handling=pool-of-threads` |
> | `sys` schema | 內建完整 | 10.6+ 內建，但**部分 view 名稱與欄位不同** |
> | `performance_schema` | 預設 ON | ★★★ **預設 OFF**，要調校得先開並重啟 |
> | `utf8mb4` 預設定序 | `utf8mb4_0900_ai_ci` | `utf8mb4_general_ci` / `uca1400_ai_ci` |
>
> ★★★★ **本篇的記憶體預算算式在 MariaDB 完全通用**，只是 redo log 與 `sys` 查詢要換寫法。
> `innodb_buffer_pool_size`、`innodb_flush_log_at_trx_commit`、`sync_binlog`、
> `max_connections`、`slow_query_log` 這些核心參數名稱與語意都相同。

## 進階設定與調校

> [!warning] 參數預設值會隨版本改變
> 下面標出的預設值以 **Ubuntu 24.04 + MySQL 8.0.4x** 為準。
> ★★★ **動手前一律先用 `SHOW GLOBAL VARIABLES` 查你這台的實際值**，
> 不要拿本篇的數字當事實。這正是上一節反覆強調的習慣。

### 一、★★★★ 記憶體預算表（本篇的核心產出）

先量現況，不要猜：

```bash
free -m
```

預期輸出：

```text
               total        used        free      shared  buff/cache   available
Mem:            7900        5820         210          12        1870        1740
Swap:           2047         860        1187
```

```text
★★★★ available 只剩 1740 M，而 Swap 已經用掉 860 M
      → 這台已經在超賣邊緣，凌晨批次一跑就會被 OOM killer 收掉
```

各服務實際佔用（**用最大 RSS，不要用平均**）：

```bash
ps -eo rss,comm --sort=-rss | awk '
  $2 ~ /mysqld|php-fpm|nginx|redis-server|node/ {s[$2]+=$1; if($1>m[$2])m[$2]=$1; c[$2]++}
  END{printf "%-16s %6s %10s %10s\n","程序","數量","合計MB","最大MB";
      for(k in s) printf "%-16s %6d %10.0f %10.0f\n", k, c[k], s[k]/1024, m[k]/1024}'
```

預期輸出：

```text
程序                 數量     合計MB     最大MB
mysqld                  1       3120       3120
php-fpm8.3             12        912         96   # ★ 最大 96 MB，不是平均 76
nginx                   5         84         22
redis-server            1        318        318
```

**填這張表**（把 [[060-03-01-02-guide-PHP-FPM設定與Pool調校]] 的結論搬進來一起算）：

| # | 項目 | 算法 | 8 GB 機 (MB) | ★ |
| --- | --- | --- | ---: | --- |
| 1 | 實體記憶體（`free -m` 的 total） | 量測 | 7900 | |
| 2 | OS + page cache 保留 | 1 × 20% | **1580** | ★★★★ **不留這 20% 就等著 OOM** |
| 3 | Nginx | 5 worker × 22 MB | 110 | ★ |
| 4 | PHP-FPM | `pm.max_children` 12 × **最大 RSS** 96 MB | **1152** | ★★★★ 用最大值算，見 [[060-03-01-02-guide-PHP-FPM設定與Pool調校]] |
| 5 | Redis | `maxmemory` 256 MB × 1.25 | 320 | ★★ 沒設 `maxmemory` 就是無上限 |
| 6 | 其他（sshd／cron／journald／監控 agent） | 量測 | 200 | ★ |
| 7 | **可分配給 MySQL** | 1 −(2+3+4+5+6) | **4538** | ★★★★ |

MySQL 內部再切一次：

| # | MySQL 項目 | 算法 | (MB) | ★ |
| --- | --- | --- | ---: | --- |
| A | `innodb_buffer_pool_size` | 決策變數 | **2048** | ★★★★ 最重要的一個數字 |
| B | InnoDB 額外結構 | A × 10% | 205 | ★★★ 常被忘記 |
| C | `innodb_log_buffer_size` | 設定值 | 16 | ★ |
| D | `key_buffer_size` | 沒有 MyISAM 就設 16 M | 16 | ★★ 別留 8M 以上除非真的用 MyISAM |
| E | `performance_schema` | **實測**（下方指令） | 260 | ★★★ 別用猜的 |
| F | **全域小計** | A+B+C+D+E | **2545** | |
| G | 每連線基本量 | 約 2 MB × `max_connections` 60 | 120 | ★★ |
| H | 尖峰暫存表 | 20% 連線 × `tmp_table_size` 32 M ＝ 12 × 32 | 384 | ★★★ 排序／GROUP BY 才會吃 |
| I | **每連線小計（最壞）** | G+H | **504** | ★★★★ 乘數是 `max_connections` |
| J | **MySQL 最壞合計** | F+I | **3049** | |
| K | **餘裕** | 4538 − J | **+1489** | ★★★★ 為正才安全 |

`performance_schema` 的**實測**方法：

```bash
mysql -e "SHOW ENGINE PERFORMANCE_SCHEMA STATUS\G" | tail -n 4
```

預期輸出：

```text
*************************** 264. row ***************************
  Type: performance_schema
  Name: memory
Status: 272629760            # ★ 260 MB，這才是實際開銷
```

> [!danger] ★★★★ 把 buffer pool 拉到 4 GB 會發生什麼
> ```
> A=4096 → B=410 → F=4798 → J=5302
> K = 4538 − 5302 = 【−764 MB】
>
> 平常看起來好好的（因為連線數沒滿、暫存表沒用到），
> 但凌晨報表批次一跑：連線衝到 40、每個都在排序
>   → 實際用量越過 8 GB
>   → dmesg: "Out of memory: Killed process 1234 (mysqld)"
> ```
> 檢查是不是被殺過：
> ```bash
> $ sudo dmesg -T | grep -i -E 'killed process|out of memory'
> [Thu Aug 27 03:14:22 2026] Out of memory: Killed process 1234 (mysqld) total-vm:...
> $ sudo journalctl -u mysql --since '-7 days' | grep -c 'Starting MySQL'
> 3                     # ★★★★ 一週重啟 3 次 = 一定有事
> ```

> [!tip] ★★★ `max_connections` 不是設越大越好
> 它是**每連線區的乘數**。反過來算 MySQL 需要的連線數：
> ```
> PHP-FPM pm.max_children              12
> Laravel queue worker（Supervisor）    4
> 排程／Artisan cron                    2
> 監控 exporter / 備份腳本              2
> ★★★★ 保留給 root 的緊急連線          （max_connections 之外，MySQL 自動保留 1 條）
> ─────────────────────────────────────────
> 實際需要                              20
> 設 60 = 3 倍餘裕，足夠且不會爆記憶體
> ```
> ★★★★ **`max_connections` 應該略大於「所有應用端連線上限的總和」，
> 而不是「使用者人數」。** 使用者人數與連線數沒有直接關係 ——
> 決定連線數的是 PHP-FPM 的 worker 數。

### 二、`innodb_buffer_pool_size`：唯一真正重要的記憶體參數

| 機器角色 | 建議比例 | 8 GB | 16 GB | ★ |
| --- | --- | --- | --- | --- |
| **專用資料庫機**（只跑 MySQL） | 50~70% | 4~5.5 G | 8~11 G | ★★★ |
| **LXMP 共存單機**（Nginx+PHP+Redis+MySQL） | **25~35%** | **2~2.5 G** | **4~5 G** | ★★★★ 本手冊主線 |
| 開發／測試機 | 資料集大小即可 | 512 M~1 G | 1 G | ★ |

> [!tip] ★★★ 有一個上限：資料量
> ```sql
> SELECT ROUND(SUM(data_length+index_length)/1024/1024) AS 'InnoDB 總量(MB)'
> FROM information_schema.tables WHERE engine='InnoDB';
> ```
> 預期輸出：
> ```text
> +-----------------+
> | InnoDB 總量(MB) |
> +-----------------+
> |            1350 |
> +-----------------+
> ```
> **資料總量只有 1.35 GB，buffer pool 設 4 GB 是純浪費** ——
> 設 2 GB 就已經「整個資料庫都在記憶體裡」了。
> ★★★★ 把那 2 GB 留給 PHP-FPM 或 page cache 更有價值。

#### chunk 對齊規則 ★★★

```ini
innodb_buffer_pool_size = 2G
innodb_buffer_pool_instances = 1        # ★ buffer pool < 1G 時自動為 1
innodb_buffer_pool_chunk_size = 128M    # 預設
```

```
規則：實際 buffer pool 會被【向上調整】成
      chunk_size × instances 的整數倍

例：想設 9 G，instances=16，chunk=128M
    16 × 128M = 2G
    9G 不是 2G 的倍數 → 實際變成 【10 G】★★★
    → 你以為省了 1 G，其實多吃了 1 G，預算表就對不起來了
```

驗證有沒有被往上調：

```bash
mysql -e "SELECT @@innodb_buffer_pool_size/1024/1024/1024 AS GB,
                 @@innodb_buffer_pool_instances AS inst,
                 @@innodb_buffer_pool_chunk_size/1024/1024 AS chunk_MB;"
```

預期輸出：

```text
+--------+------+----------+
| GB     | inst | chunk_MB |
+--------+------+----------+
| 2.0000 |    1 |      128 |
+--------+------+----------+
```

> [!tip] instances 怎麼設
> - buffer pool **< 1 GB** → `instances = 1`（MySQL 會強制成 1）
> - buffer pool ≥ 1 GB → 讓**每個 instance 至少 1 GB**
>   - 2 G → 1 或 2；8 G → 8；★ 8 GB 共存機設 1 就好，切太細沒有意義

#### 命中率：判斷夠不夠的唯一指標 ★★★★

```bash
mysql -e "
SELECT ROUND(100 - (r.v / rr.v * 100), 4) AS 'buffer pool 命中率(%)'
FROM
 (SELECT VARIABLE_VALUE v FROM performance_schema.global_status
   WHERE VARIABLE_NAME='Innodb_buffer_pool_reads') r,
 (SELECT VARIABLE_VALUE v FROM performance_schema.global_status
   WHERE VARIABLE_NAME='Innodb_buffer_pool_read_requests') rr;"
```

預期輸出：

```text
+-----------------------+
| buffer pool 命中率(%) |
+-----------------------+
|               99.9412 |
+-----------------------+
```

| 命中率 | 判讀 | 動作 | ★ |
| --- | --- | --- | --- |
| **≥ 99.9%** | 熱資料完全在記憶體 | 不用動，去查慢查詢 | ★ |
| 99.0 ~ 99.9% | 可接受 | 觀察即可 | ★★ |
| 95 ~ 99% | 開始從磁碟撈 | 考慮加 buffer pool | ★★★ |
| **< 95%** | **明顯不足** | 加記憶體或減資料 | ★★★★ |

> [!warning] ★★★ 命中率要看「一段時間的差值」，不是開機至今的累計
> `Innodb_buffer_pool_reads` 是**累計值**。剛重啟時分母小、數字難看；
> 跑了 30 天的累計又會被歷史稀釋。**正確做法是取兩次差值**：
> ```bash
> $ mysqladmin extended-status -i 60 -c 2 \
>     | grep -E 'Innodb_buffer_pool_read(s|_requests) '
> ```
> 這會每 60 秒印一次，用**第二次減第一次**才是這一分鐘的真實命中率。

#### 線上調整（MySQL 8.0）

```sql
SET GLOBAL innodb_buffer_pool_size = 3221225472;   -- 3G，★ 不用重啟
SELECT * FROM performance_schema.global_status
 WHERE VARIABLE_NAME='Innodb_buffer_pool_resize_status';
```

預期輸出：`Innodb_buffer_pool_resize_status | Completed resizing buffer pool at ...`（進行中會顯示目前進度）。

> [!warning] ★★★ 線上調整不是免費的
> 調整期間 InnoDB 要重新配置 chunk，**會有數秒到數十秒的抖動**，
> 縮小時尤其明顯（要把頁面刷出去）。
> **正式環境請在離峰做，而且做完一定要同步寫進 `zz-tuning.cnf`** ——
> 否則重啟後又回到舊值（見前面 `SET GLOBAL` 的陷阱）。

> [!tip] 重啟後的暖機
> ```sql
> SHOW GLOBAL VARIABLES LIKE 'innodb_buffer_pool_%_at_%';
> ```
> ```text
> | innodb_buffer_pool_dump_at_shutdown | ON |   # ★★ 保持 ON
> | innodb_buffer_pool_load_at_startup  | ON |   # ★★ 重啟後自動載回熱頁面
> ```
> 這兩個預設 ON。**關掉的話每次重啟後前 10 分鐘都會特別慢**。

### 三、★★★★ 耐久性 vs 效能：要能對主管解釋的取捨

```
一筆 UPDATE 走完的路：

  交易 COMMIT
      │
      ├─► redo log buffer ──► redo log 檔案（ib_redo*）
      │        ↑ innodb_flush_log_at_trx_commit 決定「什麼時候真的落地」
      │
      └─► binlog cache ─────► binary log（複寫與 PITR 用）
               ↑ sync_binlog 決定「幾個交易 fsync 一次」
```

| `flush_log_at_trx_commit` / `sync_binlog` | 斷電最壞損失 | 相對寫入效能 | 適用 | ★ |
| --- | --- | --- | --- | --- |
| **`1` / `1`** | **0 筆**（ACID 完整） | 基準 1× | ★★★★ **有金流、公文、個資異動的機關系統** | ★★★★ |
| `2` / `0` | **約最後 1 秒的交易**（OS crash 或斷電才會掉；mysqld 自己 crash 不會） | 2~5× | 內部查詢系統、可重跑的報表 | ★★★ |
| `0` / `0` | 約最後 1 秒（連 mysqld crash 都會掉） | 最快 | ★★★★ **只用於可重建的資料**（快取、匯入暫存） | ★★★★ |

```ini
# ★★★★ 機關正式系統的預設選擇，不要改
innodb_flush_log_at_trx_commit = 1
sync_binlog                    = 1
```

> [!danger] ★★★★★ 這個決定要寫進系統文件，不能是工程師私下改的
> 對主管的說法應該是這樣的一句話：
> > 「我們選 `1/1`，代表**機房斷電時已回應成功的交易一筆都不會掉**，
> > 代價是寫入吞吐量約為最快設定的 1/3。
> > 若改成 `2/0`，寫入快 2~5 倍，但**斷電時可能損失最後約 1 秒內的交易**。」
>
> ★★★★ 這個「最壞損失」必須與 [[060-04-01-05-svc-MySQL-備份與還原]] 訂的 **RPO** 對齊：
> ```
> RPO = 0（不可掉資料）  → 必須 1/1，而且要有 binlog + 即時複寫
> RPO = 1 小時           → 1/1 或 2/0 都行，重點在備份頻率
> ```
> 掉的那一秒**備份救不回來** —— 備份只能把你帶回上一個還原點。

> [!tip] 只在這種情況用 `0/0`
> 一次性大量匯入（`mysqldump` 還原、資料遷移）時**臨時**調低，做完立刻改回：
> ```sql
> SET GLOBAL innodb_flush_log_at_trx_commit = 2;
> SET GLOBAL sync_binlog = 0;
> -- ...匯入...
> SET GLOBAL innodb_flush_log_at_trx_commit = 1;   -- ★★★★ 一定要改回來
> SET GLOBAL sync_binlog = 1;
> ```
> ★★★ 因為是 `SET GLOBAL`，**萬一忘了改回來，重啟時會自動回到設定檔的 1/1** ——
> 這次這個「重啟就沒了」的特性反而救了你。

### 四、redo log 與磁碟 I/O

```ini
# ★★★ MySQL 8.0.30 以後用這個（單一參數，可線上調整）
innodb_redo_log_capacity = 1G          # 預設只有 100 M，對寫入型負載太小

# ★★ 8.0.30 之前（含 MariaDB）用舊參數，兩者相乘等於 capacity
# innodb_log_file_size       = 512M
# innodb_log_files_in_group  = 2
```

```
redo log 太小的症狀：
  · 寫入偶發卡頓（checkpoint 一來全部等）
  · SHOW ENGINE INNODB STATUS 的 LOG 段
    "Log sequence number" 與 "Last checkpoint at" 差距長期接近容量上限
  · Innodb_log_waits 持續增加   ← ★★★ 最直接的指標
```

```bash
mysql -e "SHOW GLOBAL STATUS LIKE 'Innodb_log_waits';"
```

預期輸出：`| Innodb_log_waits | 0 |` —— ★★★ 持續為 0 才正常；一直漲代表 redo／log buffer 太小。

```ini
# ★★★ I/O 相關
innodb_flush_method       = O_DIRECT   # 避免 OS page cache 與 buffer pool 雙重快取
innodb_file_per_table     = ON         # 預設 ON，★★★★ 千萬不要關
innodb_io_capacity        = 1000       # SATA SSD；NVMe 可到 2000~4000
innodb_io_capacity_max    = 2000       # 建議 = io_capacity × 2
```

| 儲存 | `innodb_io_capacity` | `innodb_io_capacity_max` | ★ |
| --- | ---: | ---: | --- |
| 傳統硬碟 / RAID1 HDD | 100~200 | 400 | ★★ |
| SATA SSD | 1000 | 2000 | ★★★ |
| NVMe SSD | 2000~4000 | 4000~8000 | ★★★ |
| 虛擬機掛網路儲存（iSCSI/NFS） | ★★★ **先量再說** | — | ★★★★ 不要照抄實體機數字 |

> [!danger] ★★★★ `innodb_file_per_table = OFF` 是不可逆的坑
> 關掉之後所有資料都塞進共用的 `ibdata1`：
> ```
> · DROP TABLE 之後 ibdata1 【不會縮小】，空間永遠拿不回來
> · 想縮回去只能：全量 mysqldump → 停機 → 刪 datadir → 重建 → 匯入
> · 單一大檔也讓表層級的備份／搬移變得不可能
> ```
> ★★★★ 預設就是 `ON`，**沒有任何理由關掉它**。
> 檢查：
> ```bash
> $ mysql -e "SELECT @@innodb_file_per_table;"
> $ ls -lh /var/lib/mysql/ibdata1
> -rw-r----- 1 mysql mysql 12M Aug 28 09:10 /var/lib/mysql/ibdata1   # ★ 應該一直很小
> ```

> [!warning] ★★★★ 不要在 LXMP 共存機開 `innodb_dedicated_server`
> ```ini
> innodb_dedicated_server = ON     # ★★★★ 只有【整台機器只跑 MySQL】才可以開
> ```
> 它會依「**整台機器的實體記憶體**」自動決定 buffer pool（約 50~75%）與 redo log 容量。
> 在同時跑 Nginx + PHP-FPM + Redis 的機器上開它，
> **等於直接宣告要 OOM**。共存機請一律手動指定數字。

### 五、連線數與逾時

```ini
max_connections        = 60      # ★★★★ 記憶體預算的乘數
max_user_connections   = 40      # ★★★ 單一帳號上限，防一個 App 吃光
thread_cache_size      = 16      # ★★ 快取執行緒，減少建連線成本
back_log               = 128     # ★ TCP 未完成連線佇列
wait_timeout           = 600     # ★★★ 非互動連線閒置多久斷（預設 28800 = 8 小時）
interactive_timeout    = 600     # 互動用戶端（mysql CLI）
max_allowed_packet     = 64M     # ★★★ 預設 64M，處理 BLOB／大 SQL 要調大
```

> [!tip] ★★★ `wait_timeout` 為什麼要從 8 小時改成 10 分鐘
> PHP-FPM 每個請求結束會關連線，通常沒問題；
> 但 **Laravel queue worker、Supervisor 常駐程序、連線池**會長期持有連線。
> 預設 8 小時代表**一個當掉的 worker 會佔住連線 8 小時**，
> 慢慢累積就是 `Too many connections`。
> ★★★ 但**不要設太短**（< 60 秒），否則常駐程序會不停遇到
> `MySQL server has gone away` 而必須重連。

#### `Too many connections` 當下怎麼辦 ★★★★

MySQL 會**額外保留一條**連線給有 `CONNECTION_ADMIN`（或 `SUPER`）權限的帳號——就是為了這一刻。

**【1】用 root 從本機 socket 進去**

```bash
sudo mysql
```

預期輸出：

```text
Welcome to the MySQL monitor.  Commands end with ; or \g.
mysql>
```

看到 `ERROR 1040 (HY000): Too many connections` 代表**連保留連線都用掉了**，
直接跳到【4】。

**【2】看是誰佔住**

```sql
SELECT user, host, db, command, time, state,
       LEFT(info, 60) AS query
FROM information_schema.processlist
ORDER BY time DESC LIMIT 15;
```

預期輸出：

```text
+---------+----------------+--------+---------+------+---------------+--------------------------+
| user    | host           | db     | command | time | state         | query                    |
+---------+----------------+--------+---------+------+---------------+--------------------------+
| laravel | localhost:5512 | app    | Query   | 1842 | Sending data  | SELECT * FROM audit_log  |  ★★★★ 跑了 30 分鐘
| laravel | localhost:5513 | app    | Sleep   | 3600 |               | NULL                     |  ★★★ 閒置一小時沒斷
| laravel | localhost:5514 | app    | Sleep   | 3598 |               | NULL                     |
+---------+----------------+--------+---------+------+---------------+--------------------------+
```

```
判讀：
  · 一堆 Sleep 且 time 很大   → ★★★ wait_timeout 太長，或應用沒關連線
  · Query 且 time 很大        → ★★★★ 有爛查詢卡住，去看慢查詢日誌
  · state = 'Waiting for table metadata lock' → ★★★★ 有人開了交易沒 commit
```

**【3】殺掉元凶（只殺確定的那一條）**

```sql
KILL 5512;                 -- ★★★ 只殺那條卡住的 Query
```

```sql
-- ★★★★ 危險：批次殺掉所有閒置超過 5 分鐘的連線，執行前先看清楚 SELECT 的結果
SELECT CONCAT('KILL ', id, ';') FROM information_schema.processlist
WHERE command='Sleep' AND time > 300 AND user <> 'root';
```

**【4】臨時放大（治標）**

```sql
SET GLOBAL max_connections = 150;   -- ★★★★ 立即生效，【重啟就沒了】
```

```bash
# ★★★★ 同一分鐘內就把設定檔改掉，否則下次重啟又爆一次
sudo sed -i 's/^max_connections.*/max_connections = 150/' \
  /etc/mysql/mysql.conf.d/zz-tuning.cnf
grep max_connections /etc/mysql/mysql.conf.d/zz-tuning.cnf
```

> [!danger] ★★★★ 放大 `max_connections` 之前先回頭看預算表
> 60 → 150 代表每連線區從 504 MB 變成 **1260 MB**，
> 餘裕 K 從 +1489 掉到 **+733**。
> **`Too many connections` 的真正解法通常是往上游走** ——
> 減少 PHP-FPM 的 `pm.max_children`、修掉那條跑 30 分鐘的查詢，
> 而不是無腦放大連線數。

#### `MySQL server has gone away` 的三種成因 ★★★

| 成因 | 判斷方式 | 解法 |
| --- | --- | --- |
| `max_allowed_packet` 太小 ★★★ | 錯誤發生在寫入大 BLOB／長 SQL 時 | 調大到 64M~256M，**用戶端也要調** |
| `wait_timeout` 到期 ★★ | 長閒置後的第一個查詢就失敗 | 應用端開 `PDO::ATTR_PERSISTENT` 要小心；或縮短連線閒置 |
| **mysqld 真的重啟／被殺** ★★★★ | `SHOW GLOBAL STATUS LIKE 'Uptime'` 很小 | 查 OOM、查 error log |

```bash
mysql -e "SHOW GLOBAL STATUS LIKE 'Uptime';"
```

預期輸出：`| Uptime | 1832 |` —— ★★★★ 只有 30 分鐘？**它悄悄重啟過**，去查 error log 與 OOM 紀錄。

### 六、★★★★ 慢查詢日誌：找出效能問題的唯一入口

```ini
slow_query_log                  = ON
slow_query_log_file             = /var/log/mysql/slow.log
long_query_time                 = 1        # ★★★★ 預設 10 秒太寬鬆，什麼都抓不到
min_examined_row_limit          = 100      # ★★ 過濾掉掃描列數很少的雜訊
log_slow_admin_statements       = ON       # ★★ ALTER TABLE 這類也記
log_queries_not_using_indexes   = ON       # ★★★★ 威力最大，也最危險
log_throttle_queries_not_using_indexes = 10   # ★★★★★ 上一行開了，這行【一定要】跟著開
```

> [!danger] ★★★★★ `log_queries_not_using_indexes` 沒限流會在幾小時內把磁碟寫爆
> ```
> log_throttle_queries_not_using_indexes 預設是 0 = 【不限流】
>
> 一個 Laravel 的 admin 列表頁沒加索引，每秒被打 50 次
>   → 每秒寫 50 筆慢查詢紀錄，每筆約 300 bytes
>   → 15 KB/s → 一天 1.3 GB → 三天磁碟滿
>   → ★★★★★ /var 滿了 MySQL 直接停止寫入，全站白畫面
> ```
> 設成 10 之後：**每 60 秒最多記 10 筆同類查詢**，
> 結束時再補一行摘要「這段時間還有 N 筆被抑制」。
> ★★★★ **本手冊的規定：這兩行永遠成對出現。**

驗證有沒有生效：

### 七、`performance_schema` 與 `sys` schema

`sys` schema 是把 `performance_schema` 的原始表包成人看得懂的 view。

```sql
-- ★★★★ 最耗時的語句 Top 10（不需要慢查詢日誌就能看）
SELECT query, exec_count, total_latency, avg_latency,
       rows_examined_avg, rows_sent_avg
FROM sys.statement_analysis
ORDER BY total_latency DESC LIMIT 10;
```

預期輸出（節錄）：

```text
+--------------------------------+------------+---------------+-------------+
| query                          | exec_count | total_latency | avg_latency |
+--------------------------------+------------+---------------+-------------+
| SELECT * FROM `audit_log` ...  |        312 | 43.78 m       | 8.42 s      |  ★★★★
| SELECT COUNT ( * ) FROM `doc.. |       1180 | 37.55 m       | 1.91 s      |  ★★★
+--------------------------------+------------+---------------+-------------+
```

```sql
-- ★★★ 從來沒被用過的索引（可以刪，省寫入成本與空間）
SELECT * FROM sys.schema_unused_indexes;

-- ★★★★ 會全表掃描的表
SELECT * FROM sys.schema_tables_with_full_table_scans ORDER BY rows_full_scanned DESC;

-- ★★ 哪張表佔了 buffer pool
SELECT object_schema, object_name, allocated, data, pages
FROM sys.innodb_buffer_stats_by_table ORDER BY pages DESC LIMIT 10;

-- ★★ 目前的連線在做什麼（比 SHOW PROCESSLIST 好讀）
SELECT thd_id, conn_id, user, db, command, state, current_statement
FROM sys.session WHERE command <> 'Sleep';
```

> [!warning] ★★★ `sys.schema_unused_indexes` 的判讀要小心
> 它只統計**伺服器啟動到現在**的使用情形。
> 剛重啟兩小時就拿它去刪索引，**會把每月才跑一次的報表索引刪掉**。
> ★★★★ **至少觀察一個完整的業務週期（通常一個月）再決定。**
> 而且刪索引前務必先在測試環境驗證，見 [[060-04-01-03-cmd-MySQL-SQL基礎操作]]。

預期輸出：

```text

+------------------------------+--------+

| 狀態值 | 建議門檻 | 超標代表什麼 | ★ |
| --- | --- | --- | --- |
| `Threads_connected` | > `max_connections` × 80% | ★★★★ 快要 `Too many connections` 了 | ★★★★ |
| `Threads_running` | 持續 > CPU 核心數 × 2 | ★★★★ 真正在跑的太多，CPU 或鎖是瓶頸 | ★★★★ |

| `Slow_queries` | 每分鐘增量 > 10 | ★★★★ 有爛查詢在跑，去撈慢查詢日誌 | ★★★★ |
| `Aborted_connects` | 每小時增量 > 5 | ★★★ 密碼錯／防火牆擋／SSL 交握失敗，**也可能是暴力破解** | ★★★★ |
| `Created_tmp_disk_tables` / `Created_tmp_tables` | 比值 > 25% | ★★★ 排序落地到磁碟，`tmp_table_size` 太小或查詢有 BLOB | ★★★ |
| `Innodb_row_lock_waits` | 每分鐘增量 > 1 | ★★★★ 交易互鎖，應用端交易範圍太大 | ★★★★ |
| `Innodb_buffer_pool_wait_free` | 任何非 0 的成長 | ★★★★ buffer pool 已經完全不夠用 | ★★★★ |
| `Uptime` | 突然變小 | ★★★★ **它悄悄重啟過**，去查 OOM 與 error log | ★★★★ |

> [!tip] ★★★ `Aborted_connects` 是資安訊號，不只是效能訊號
> 短時間內暴增通常是**帳號密碼暴力嘗試**。
> 對應處置與稽核見 [[060-04-01-07-svc-MySQL-安全強化]] 與 [[100-01-03-guide-日誌-系統監控與告警]]。

> 有兩種情況**無論設多大都會落地到磁碟**：

> [!danger] ★★★★ `/tmp` 是 tmpfs 時，磁碟暫存表會吃掉「記憶體」
> 很多雲端映像把 `/tmp` 掛成 `tmpfs`（記憶體檔案系統）。
> 這時 `Created_tmp_disk_tables` 增加**不是寫磁碟，是吃 RAM** ——
> 你的記憶體預算表會完全失準，而且 `/tmp` 滿了會直接讓查詢失敗：
> ```text
> ERROR 1021 (HY000): Disk full (/tmp/#sql_xxxx.MAI); waiting for someone to free some space...
> ```
> 解法：指定一個**真的在磁碟上**的目錄。
> ```bash
> $ sudo install -d -o mysql -g mysql -m 0750 /var/lib/mysql-tmp
> # zz-tuning.cnf 加入： tmpdir = /var/lib/mysql-tmp
> ```
> ★★★ RHEL 系記得補 SELinux context（見前面的對照 callout）。

```bash
# ★★ 資料庫機的 swap 傾向要壓低，但【不要設 0】
cat /proc/sys/vm/swappiness
```

預期輸出：

```text
60          # ★★★ 桌面預設值，資料庫機建議 1~10
```

```
★★★ vm.swappiness = 1  → 幾乎不換出，但保留最後手段（比 0 安全）
★★★ vm.swappiness = 0  → 完全不換出，記憶體壓力大時【更容易觸發 OOM killer】
★★  NUMA 多插槽機器：mysqld 可能只用到單一節點的記憶體而提早換出
      → 這屬於核心參數範疇，設定方式見 [[020-01-26-guide-Linux-核心模組與sysctl調校]]
```

### 十、★★★★ 改設定的安全流程（六步，一步都不能跳）

```
【1】備份原檔（含時間戳）
      sudo cp -a zz-tuning.cnf zz-tuning.cnf.$(date +%F-%H%M)

【2】一次只改【一組相關參數】
      ★★★★ 一次改五個，出事你不知道是哪一個造成的

【3】語法驗證（不啟動伺服器）
      sudo -u mysql /usr/sbin/mysqld --validate-config

【4】重啟並確認起得來
      sudo systemctl restart mysql && sudo systemctl is-active mysql

【5】觀察 15 分鐘（不是 15 秒）
      看 Threads_running、Slow_queries 增量、error log、應用端 5xx

【6】不對就回滾（把備份檔換回來 → restart）
```

**【3】的實際操作**：

```bash
sudo -u mysql /usr/sbin/mysqld --validate-config
echo "exit=$?"
```

正常時的預期輸出：

```text
exit=0          # ★ 沒有任何訊息 + exit 0 = 語法沒問題
```

有錯時：

```text
2026-08-28T02:11:44.120Z 0 [ERROR] [MY-000067] [Server] unknown variable 'innodb_buffer_pool_sizee=2G'.
2026-08-28T02:11:44.120Z 0 [ERROR] [MY-010119] [Server] Aborting
exit=1          # ★★★★ 這一步就攔下來，不要等到 restart 才發現
```

> [!danger] ★★★★ MySQL 起不來時，`systemctl status` 的訊息會誤導你
> ```bash
> $ sudo systemctl status mysql
> ● mysql.service - MySQL Community Server
>      Active: failed (Result: exit-code) since Fri 2026-08-28 02:12:03 CST
>     Process: 8821 ExecStart=/usr/sbin/mysqld (code=exited, status=1/FAILURE)
> ```
> **這裡只會告訴你「失敗了」，不會告訴你為什麼。**
> 真正的原因永遠在這兩個地方：
> ```bash
> $ sudo tail -n 40 /var/log/mysql/error.log      # ★★★★ 第一順位
> $ sudo journalctl -u mysql -n 60 --no-pager     # ★★★ 第二順位（error log 還沒寫出時）
> ```
> ★★★ RHEL 系的錯誤日誌在 `/var/log/mysql/mysqld.log`，路徑不同。

## 完整實戰範例

### 情境

```
機關「公文附件管理系統」正式主機
  · 硬體：VM，4 vCPU / 8 GB RAM / 200 GB SATA SSD
  · Ubuntu 24.04 + Nginx + PHP-FPM 8.3 + MySQL 8.0 + Redis
  · 應用：Laravel 11 + Filament 後台，資料約 1.3 GB
  · 症狀：
      ① 上班尖峰（09:00-10:00）Nginx 回 502，Laravel log 出現
         SQLSTATE[HY000] [1040] Too many connections
      ② 8/27 03:14 mysqld 被 OOM killer 殺掉一次，早上才被發現
      ③ 後台「附件清單」頁面要轉 15 秒
```

### 第一步：蒐證（不要急著改設定）

```bash
sudo mkdir -p /root/db-tuning && cd /root/db-tuning
{
  echo "=== date ==="; date
  echo "=== free ==="; free -m
  echo "=== OOM ==="; sudo dmesg -T | grep -i -E 'killed process|out of memory' | tail -5
  echo "=== RSS ==="; ps -eo rss,comm --sort=-rss | head -15
  echo "=== mysql vars ==="; sudo mysql -e "SHOW GLOBAL VARIABLES;" 
  echo "=== mysql status ==="; sudo mysql -e "SHOW GLOBAL STATUS;"
  echo "=== persisted ==="; sudo mysql -e "SELECT * FROM performance_schema.persisted_variables;"
} > baseline-$(date +%F).txt 2>&1
wc -l baseline-$(date +%F).txt
```

預期輸出：

```text
1284 baseline-2026-08-28.txt      # ★★★ 這份是回滾與事後檢討的依據，先存起來
```

關鍵發現：

```text
Out of memory: Killed process 1234 (mysqld)                  ← ②的證據 ★★★★
innodb_buffer_pool_size  4294967296   （4 GB）               ← ★★★★ 共存機設 4G，超賣
max_connections          151          （預設值沒動）          ← ★★★★ 乘數太大
long_query_time          10.000000                            ← ★★★★ 難怪抓不到慢查詢
performance_schema.persisted_variables → Empty set            ← ★ 至少沒有 SET PERSIST 的坑
php-fpm pm.max_children  25           （來自 www.conf）        ← ★★★ 對 8 GB 機太多
```

### 第二步：填預算表並決定新值

| 項目 | 舊值 | 新值 | 理由 | ★ |
| --- | --- | --- | --- | --- |
| `pm.max_children`（PHP-FPM） | 25 | **12** | 25×96 MB = 2.4 G 太多，見 [[060-03-01-02-guide-PHP-FPM設定與Pool調校]] | ★★★★ |
| `innodb_buffer_pool_size` | 4 G | **2 G** | 資料才 1.3 G，2 G 已能全部裝下 | ★★★★ |
| `max_connections` | 151 | **60** | 實際需求 20，3 倍餘裕 | ★★★★ |
| `tmp_table_size` / `max_heap_table_size` | 16 M | **32 M** | 落地比例 40% | ★★★ |
| `long_query_time` | 10 | **1** | 才抓得到那個 15 秒的頁面 | ★★★★ |
| `innodb_redo_log_capacity` | 100 M | **1 G** | 減少 checkpoint 卡頓 | ★★★ |
| `innodb_flush_log_at_trx_commit` / `sync_binlog` | 1 / 1 | **1 / 1（不動）** | 公文系統 RPO = 0 | ★★★★ |
| `wait_timeout` | 28800 | **600** | 避免死掉的 worker 佔住連線 8 小時 | ★★★ |

**新預算表合計 3049 MB，餘裕 +1489 MB**（就是本篇第一節那張表）。

### 第三步：產出 `zz-tuning.cnf`

```bash
sudo cp -a /etc/mysql/mysql.conf.d/zz-tuning.cnf \
  /root/db-tuning/zz-tuning.cnf.$(date +%F-%H%M) 2>/dev/null || \
  echo "（原本沒有這個檔，第一次建立）"

sudo tee /etc/mysql/mysql.conf.d/zz-tuning.cnf >/dev/null <<'EOF'

# /etc/mysql/mysql.conf.d/zz-tuning.cnf
# 公文附件管理系統 — 8 GB LXMP 共存主機
# 依據：/root/db-tuning/baseline-2026-08-28.txt 的記憶體預算表
# 最後修改：2026-08-28
# ★★★★ 改任何一行前，先重新算一次預算表
# ============================================================
[mysqld]

# ───── 記憶體：全域區（合計約 2545 MB）─────
innodb_buffer_pool_size        = 2G      # ★★★★ 資料量 1.3G，2G 已足夠全裝
innodb_buffer_pool_instances   = 1       # ★★ 2G 切一份就好
innodb_log_buffer_size         = 16M
key_buffer_size                = 16M     # ★★ 沒有 MyISAM，設小

# ───── 記憶體：每連線區（× max_connections）─────
sort_buffer_size               = 512K    # ★★★ 每連線，別亂調大
join_buffer_size               = 512K    # ★★★ 同上

### 第五步：驗收腳本

```bash
sudo tee /usr/local/bin/mysql-tune-check.sh >/dev/null <<'SCRIPT'
#!/usr/bin/env bash
# =====================================================================
# mysql-tune-check.sh —— MySQL 調校驗收
#   1) 比對關鍵參數的【實際值】與【預期值】
#   2) 計算 buffer pool 命中率與暫存表落地比例
#   3) 列出 Top 5 慢語句
#   4) 估算最壞情況記憶體用量並與實體記憶體比較
# 用法： sudo mysql-tune-check.sh [期望值檔]
# 離開碼： 0=全過  1=有警告  2=有嚴重問題  3=無法連線
# =====================================================================
set -euo pipefail

EXPECT_FILE="${1:-/etc/mysql/tune-expect.conf}"
MYSQL_OPTS=(--defaults-file=/etc/mysql/debian.cnf)
WARN=0; CRIT=0

c_ok()   { printf '  \033[32m[ OK ]\033[0m %s\n' "$*"; }
c_warn() { printf '  \033[33m[WARN]\033[0m %s\n' "$*"; WARN=$((WARN+1)); }
c_crit() { printf '  \033[31m[CRIT]\033[0m %s\n' "$*"; CRIT=$((CRIT+1)); }
title()  { printf '\n\033[1m═══ %s ═══\033[0m\n' "$*"; }

q() { mysql "${MYSQL_OPTS[@]}" -N -B -e "$1" 2>/dev/null; }

# ── 前置檢查 ────────────────────────────────────────────────
if ! command -v mysql >/dev/null 2>&1; then
    echo "錯誤：找不到 mysql 用戶端" >&2; exit 3
fi
if ! q "SELECT 1" >/dev/null 2>&1; then
    echo "錯誤：無法連線到 MySQL。請確認服務已啟動，且 /etc/mysql/debian.cnf 可讀（需 root）。" >&2
    echo "      sudo systemctl status mysql" >&2
    exit 3
fi

var() { q "SELECT @@GLOBAL.$1"; }
sts() { q "SELECT VARIABLE_VALUE FROM performance_schema.global_status
           WHERE VARIABLE_NAME='$1'"; }

# ── 1. 參數比對 ─────────────────────────────────────────────
title "1. 關鍵參數實際值比對"
if [[ ! -f "$EXPECT_FILE" ]]; then
    cat > "$EXPECT_FILE" <<'EXP'
# 參數名 期望值(bytes 或原始值)  嚴重度(crit|warn)
innodb_buffer_pool_size 2147483648 crit
max_connections 60 crit
long_query_time 1.000000 crit
log_throttle_queries_not_using_indexes 10 crit
innodb_flush_log_at_trx_commit 1 crit
sync_binlog 1 crit
innodb_file_per_table 1 crit
innodb_redo_log_capacity 1073741824 warn
tmp_table_size 33554432 warn
max_heap_table_size 33554432 warn
wait_timeout 600 warn
EXP
    echo "  （已建立預期值檔 $EXPECT_FILE，請依實際規劃調整）"
fi

while read -r name want sev; do
    [[ -z "${name:-}" || "$name" == \#* ]] && continue
    got="$(var "$name" || echo '?')"
    if [[ "$got" == "$want" ]]; then
        c_ok "$name = $got"
    elif [[ "$sev" == "crit" ]]; then
        c_crit "$name 實際 $got ≠ 預期 $want   ★★★★ 檢查 mysqld-auto.cnf 與重複設定"
    else
        c_warn "$name 實際 $got ≠ 預期 $want"
    fi
done < "$EXPECT_FILE"

# ★★★★ SET PERSIST 覆蓋檢查
PCNT="$(q "SELECT COUNT(*) FROM performance_schema.persisted_variables")"
if [[ "${PCNT:-0}" -gt 0 ]]; then
    c_crit "有 $PCNT 個參數被 SET PERSIST 覆蓋（mysqld-auto.cnf 贏過設定檔）"
    q "SELECT CONCAT('        ', VARIABLE_NAME,' = ',VARIABLE_VALUE)
       FROM performance_schema.persisted_variables"
else
    c_ok "沒有 SET PERSIST 覆蓋"
fi

# ── 2. 效率指標 ─────────────────────────────────────────────
title "2. 效率指標"
RR="$(sts Innodb_buffer_pool_read_requests)"; RD="$(sts Innodb_buffer_pool_reads)"
HIT="$(awk -v a="$RD" -v b="$RR" 'BEGIN{if(b==0){print "0.0000"}else{printf "%.4f",100-(a/b*100)}}')"
printf '  buffer pool 命中率： %s %%\n' "$HIT"
awk -v h="$HIT" 'BEGIN{exit !(h<95)}' && c_crit "命中率 < 95%%  ★★★★ buffer pool 明顯不足" \
  || { awk -v h="$HIT" 'BEGIN{exit !(h<99)}' && c_warn "命中率 < 99%%" || c_ok "命中率良好"; }

TT="$(sts Created_tmp_tables)"; TD="$(sts Created_tmp_disk_tables)"
RATIO="$(awk -v a="$TD" -v b="$TT" 'BEGIN{if(b==0){print 0}else{printf "%.1f",a/b*100}}')"
printf '  暫存表落地比例：  %s %%\n' "$RATIO"
awk -v r="$RATIO" 'BEGIN{exit !(r>25)}' && c_warn "落地比例 > 25%%  ★★★ 查詢需要優化" || c_ok "落地比例正常"

UP="$(sts Uptime)"
if [[ "${UP:-0}" -lt 3600 ]]; then
    c_warn "Uptime 只有 ${UP}s  ★★★★ 最近重啟過，確認是否被 OOM killer 殺掉"
else
    c_ok "Uptime = $((UP/86400)) 天"
fi

TC="$(sts Threads_connected)"; MC="$(var max_connections)"
PCT="$(awk -v a="$TC" -v b="$MC" 'BEGIN{printf "%.0f",a/b*100}')"
printf '  連線使用率：      %s / %s = %s %%\n' "$TC" "$MC" "$PCT"
[[ "$PCT" -ge 80 ]] && c_crit "連線使用率 ≥ 80%%  ★★★★ 逼近 Too many connections" || c_ok "連線水位安全"

# ── 3. Top 5 慢語句 ────────────────────────────────────────
title "3. Top 5 最耗時語句（sys.statement_analysis）"
mysql "${MYSQL_OPTS[@]}" -e "
SELECT LEFT(query,70) AS query, exec_count, total_latency, avg_latency,
       rows_examined_avg AS examined
FROM sys.statement_analysis
WHERE db IS NOT NULL AND db NOT IN ('mysql','sys','performance_schema')
ORDER BY total_latency DESC LIMIT 5;" 2>/dev/null \
  || c_warn "無法查詢 sys.statement_analysis（performance_schema 是否開啟？）"

# ── 4. 記憶體預算 ──────────────────────────────────────────
title "4. 最壞情況記憶體估算"
TOTAL_MB="$(free -m | awk '/^Mem:/{print $2}')"
BP="$(( $(var innodb_buffer_pool_size) / 1048576 ))"
LB="$(( $(var innodb_log_buffer_size) / 1048576 ))"
KB="$(( $(var key_buffer_size) / 1048576 ))"
PS_BYTES="$(mysql "${MYSQL_OPTS[@]}" -e "SHOW ENGINE PERFORMANCE_SCHEMA STATUS" 2>/dev/null \
            | awk '$2=="memory"{print $3}' | tail -1)"
PS_MB="$(( ${PS_BYTES:-0} / 1048576 ))"
EXTRA=$(( BP / 10 ))
GLOBAL=$(( BP + EXTRA + LB + KB + PS_MB ))

PER_CONN_KB=$(( ( $(var sort_buffer_size) + $(var join_buffer_size) \
               + $(var read_buffer_size) + $(var read_rnd_buffer_size) \
               + $(var thread_stack) + $(var binlog_cache_size) ) / 1024 ))
CONNS="$(var max_connections)"
PER_TOTAL=$(( PER_CONN_KB * CONNS / 1024 ))
TMP_MB="$(( $(var tmp_table_size) / 1048576 ))"
TMP_WORST=$(( TMP_MB * CONNS / 5 ))          # 假設 20% 連線同時用暫存表
MYSQL_WORST=$(( GLOBAL + PER_TOTAL + TMP_WORST ))

OTHER_MB="$(ps -eo rss,comm | awk '$2 !~ /mysqld/ {s+=$1} END{printf "%d", s/1024}')"
RESERVE=$(( TOTAL_MB / 5 ))
BUDGET=$(( TOTAL_MB - RESERVE - OTHER_MB ))

printf '  實體記憶體            %6d MB\n' "$TOTAL_MB"
printf '  OS/page cache 保留20%%  %6d MB\n' "$RESERVE"
printf '  其他程序實測          %6d MB\n' "$OTHER_MB"
printf '  ────────────────────────────────\n'
printf '  可分配給 MySQL        %6d MB\n' "$BUDGET"
printf '  MySQL 全域區          %6d MB  (buffer pool %d + 額外 %d + log %d + key %d + P_S %d)\n' \
       "$GLOBAL" "$BP" "$EXTRA" "$LB" "$KB" "$PS_MB"
printf '  每連線 %d KB × %d      %6d MB\n' "$PER_CONN_KB" "$CONNS" "$PER_TOTAL"
printf '  尖峰暫存表(20%%連線)    %6d MB\n' "$TMP_WORST"
printf '  MySQL 最壞合計        %6d MB\n' "$MYSQL_WORST"
MARGIN=$(( BUDGET - MYSQL_WORST ))
printf '  餘裕                  %+6d MB\n' "$MARGIN"

if   [[ "$MARGIN" -lt 0 ]];   then c_crit "★★★★ 記憶體超賣！尖峰時會被 OOM killer 殺掉 mysqld"
elif [[ "$MARGIN" -lt 300 ]]; then c_warn "★★★ 餘裕不足 300 MB，建議調降 buffer pool 或 max_connections"
else c_ok "記憶體預算安全"
fi

# ── 結論 ───────────────────────────────────────────────────
title "結論"
printf '  警告 %d 項 / 嚴重 %d 項\n' "$WARN" "$CRIT"
if   [[ "$CRIT" -gt 0 ]]; then echo "  ★★★★ 有嚴重問題，請依上方訊息處理"; exit 2
elif [[ "$WARN" -gt 0 ]]; then echo "  ★★ 有警告，建議排入檢討"; exit 1
else echo "  ★ 全部通過"; exit 0
fi
SCRIPT

sudo chmod 0750 /usr/local/bin/mysql-tune-check.sh
sudo /usr/local/bin/mysql-tune-check.sh
```

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 凌晨 mysqld 消失，`dmesg` 有 `Out of memory: Killed process (mysqld)` | 記憶體超賣：buffer pool + 每連線 × `max_connections` 超過實體記憶體 | 重算預算表，調降 `innodb_buffer_pool_size` 與 `max_connections`；用 `mysql-tune-check.sh` 驗收 |
| ★★★★ `ERROR 1040 (HY000): Too many connections` | `max_connections` 不足，或有連線被卡住不釋放 | `sudo mysql` 用保留連線進去 → `information_schema.processlist` 找元凶 → `KILL` → 再考慮調大；同時檢查 `wait_timeout` |
| ★★★★ 改了設定檔重啟後值沒變 | 被 `mysqld-auto.cnf`（`SET PERSIST`）覆蓋，或同一參數寫在兩個檔案 | `SELECT * FROM performance_schema.persisted_variables;` → `RESET PERSIST <name>;`；`my_print_defaults mysqld` 比對 |
| ★★★★ `systemctl restart mysql` 失敗，`systemctl status` 只說 `exit-code=1` | 設定檔語法錯／參數名拼錯／目錄權限不足 | 看 `/var/log/mysql/error.log` 與 `journalctl -u mysql`；事前用 `mysqld --validate-config` 攔下來 |
| ★★★★ `/var` 磁碟在幾小時內被寫滿，全站白畫面 | `log_queries_not_using_indexes=ON` 但 `log_throttle_queries_not_using_indexes=0` | 立刻 `SET GLOBAL log_throttle_queries_not_using_indexes=10;`，清舊日誌，同步改設定檔 |
| ★★★★ 斷電復電後少了幾筆交易 | `innodb_flush_log_at_trx_commit` 或 `sync_binlog` 不是 1 | 改回 `1/1`；若必須用 `2/0`，把「最壞損失約 1 秒」寫進系統文件並與 RPO 對齊 |
| ★★★ `innodb_buffer_pool_size` 設 3 G，`SHOW VARIABLES` 顯示 3.125 G | 被 `chunk_size × instances` 向上對齊 | 把值設成 `chunk_size × instances` 的整數倍；或調整 `instances` |
| ★★★ 「上週明明修好了」，重啟後問題重現 | 當時只做了 `SET GLOBAL`，沒有寫進設定檔 | 每次 `SET GLOBAL` 後**當下**同步改 `zz-tuning.cnf`，並用檢查表確認 |
| ★★★ `MySQL server has gone away` | `max_allowed_packet` 太小／`wait_timeout` 到期／mysqld 重啟過 | 依 `Uptime` 判斷是不是重啟；調大 `max_allowed_packet`（**用戶端也要調**） |
| ★★★ 查詢突然報 `Disk full (/tmp/#sql...)` | `tmpdir` 指向 tmpfs 的 `/tmp` 且空間用盡 | 建 `/var/lib/mysql-tmp` 並設 `tmpdir`；同時處理造成大量暫存表的查詢 |
| ★★★ `Created_tmp_disk_tables` 佔比 40%，CPU iowait 高 | `tmp_table_size` 太小，或查詢含 BLOB／大量 `GROUP BY` | 先調大到 32 M（與 `max_heap_table_size` 同值）；根本解是加索引，見 [[060-04-01-03-cmd-MySQL-SQL基礎操作]] |
| ★★★ 開了慢查詢日誌卻一筆都沒有 | `long_query_time` 還是預設的 10 秒；或檔案權限不對 | `SELECT @@long_query_time;` 應為 1；`ls -l /var/log/mysql/slow.log` 應為 `mysql:adm` |
| ★★★ 重啟後前 10 分鐘特別慢 | buffer pool 是冷的 | 確認 `innodb_buffer_pool_dump_at_shutdown` 與 `load_at_startup` 都是 `ON` |
| ★★ 命中率算出來是 0% 或很難看 | 用開機至今的累計值，且剛重啟不久 | 用 `mysqladmin extended-status -i 60 -c 2` 取兩次差值 |
| ★★ `mysqld --validate-config` 報 `Permission denied` | 用一般使用者跑，讀不到資料目錄 | `sudo -u mysql /usr/sbin/mysqld --validate-config` |
| ★★ `dnf` 主機上找不到 `mysqld --validate-config` | 那台是 MariaDB，不支援此旗標 | `mysql -V` 確認版本；MariaDB 改用 `mysqld --help --verbose` 硬驗 |

沒有紀錄但 Uptime 很小        → ★★★ 查 /var/log/mysql/error.log，可能是設定或磁碟問題
Uptime 正常（數天以上）        → 跳【3】
```

**【3】看連線水位與誰在跑**

```bash
mysql -e "SHOW GLOBAL STATUS WHERE Variable_name IN
  ('Threads_connected','Threads_running','Max_used_connections','Aborted_connects');"
mysql -e "SELECT id,user,command,time,state,LEFT(info,50) info
          FROM information_schema.processlist WHERE command<>'Sleep' ORDER BY time DESC LIMIT 10;"
```

預期輸出：

```text

| Threads_running      | 21   |     # ★★★★ 4 核機器有 21 條在跑 = 嚴重塞車
| Max_used_connections | 60   |
| Aborted_connects     | 12   |
```

```
Threads_running 遠大於核心數  → ★★★★ 有慢查詢塞住，跳【5】
Threads_connected 高但 running 低 → ★★★ 連線沒關（wait_timeout / 應用端），跳【6】
Aborted_connects 快速成長     → ★★★ 密碼錯或被掃描，見 [[060-04-01-07-svc-MySQL-安全強化]]
```

**【4】I/O 與 redo log**

```bash
mysql -e "SHOW GLOBAL STATUS LIKE 'Innodb_log_waits';
          SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_wait_free';
          SELECT @@innodb_redo_log_capacity/1024/1024 AS redo_MB;"

預期輸出：

```text

| redo_MB                      | 100  |    # ★★★ 還是預設值，寫入型負載會卡
```

```
Innodb_log_waits 成長      → 調大 innodb_redo_log_capacity（1G）與 innodb_log_buffer_size
buffer_pool_wait_free 成長 → ★★★★ 先確認記憶體預算還有空間，才能加 buffer pool
兩者都是 0                 → I/O 不是瓶頸，跳【5】
```

**【5】撈慢查詢**

## 安全性注意事項

> [!danger] ★★★★★ 絕對禁止
> - **不要把 `debian.cnf` 或含密碼的 `.my.cnf` 設成 0644。**
>   `/etc/mysql/debian.cnf` 裡是 `debian-sys-maint` 的明文密碼，
>   權限放寬等於**任何本機使用者都能完整存取整個資料庫**（含個資表）。
>   ```bash
>   $ sudo chmod 0600 /etc/mysql/debian.cnf && sudo chown root:root /etc/mysql/debian.cnf
>   $ sudo ls -l /etc/mysql/debian.cnf
>   -rw------- 1 root root 316 Aug 28 09:12 /etc/mysql/debian.cnf
>   ```
> - **不要在腳本或 cron 裡寫 `mysql -u root -pXXXX`。**
>   密碼會出現在 `ps aux`、shell history、以及 `/proc/<pid>/cmdline`，
>   ★★★★★ 同機的任何帳號都看得到。改用 `--defaults-file` 或 `mysql_config_editor`。
> - **不要把 `general_log` 開在正式環境。**
>   它會逐字記錄**所有 SQL，包含 `INSERT` 進去的身分證字號、地址、`WHERE` 條件裡的個資**。
>   一旦開啟，`/var/log` 就變成一份沒有加密、沒有存取控管的個資副本。
>   除錯完**當下**關掉並刪檔。
> - **不要在慢查詢日誌開啟後忽略它的內容敏感性。** ★★★★
>   慢查詢日誌會完整記錄 SQL 文字，**其中的 `WHERE id_no = 'A123456789'` 就是個資**。
>   `/var/log/mysql/` 應維持 `mysql:adm 0640`，並納入日誌保存與清理政策。
> - **不要為了「解 `Too many connections`」把 `max_connections` 設成 5000。**
>   ★★★★ 這只會把「連線不足」換成「OOM 全服務中斷」，而且中斷得更難查。

> [!warning] ★★★ 機關情境的四個對應點
> | 情境 | 本篇對應的做法 | 相關篇章 |

> | **最小權限** | 驗收腳本用 `--defaults-file` 而非 root 明文密碼；監控帳號只給 `PROCESS`、`REPLICATION CLIENT`、`SELECT ON performance_schema.*` | [[060-04-01-02-cmd-MySQL-使用者與權限]] |

## 練習題

> [!question]- 練習 1：為一台 16 GB 的機器編預算表
> **題目**：一台 16 GB 的機關主機，跑 Nginx（6 worker × 25 MB）、
> PHP-FPM（`pm.max_children` = 24，最大 RSS 110 MB）、Redis（`maxmemory` 512 M）、
> 其他系統程序 250 MB。InnoDB 資料總量 6 GB。
> 請算出 `innodb_buffer_pool_size` 與 `max_connections` 該設多少。
>
> **參考解答**：
> ```
> 【1】實體 16384 MB（free -m 實測約 16050）
> 【2】OS + page cache 保留 20%      = 3210 MB
> 【3】Nginx  6 × 25                 =  150 MB
> 【4】PHP-FPM 24 × 110              = 2640 MB   ★★★★ 用最大 RSS
> 【5】Redis  512 × 1.25             =  640 MB
> 【6】其他                          =  250 MB
> 【7】可分配給 MySQL = 16050 − (3210+150+2640+640+250) = 9160 MB
>
> 【8】決定 buffer pool：
>      共存機 25~35% → 16050 × 0.30 ≈ 4800 MB
>      但資料只有 6 GB，設 5 G（5120 MB）就能裝下絕大部分熱資料 ★★★
>      取 5 G，instances = 4（每份 1.25 G）
>      → 5120 必須是 128M × 4 = 512M 的倍數：5120 / 512 = 10 ✓ 不會被上調
>
> 【9】全域區 = 5120 + 512(額外10%) + 16 + 16 + 300(P_S 實測) ≈ 5964 MB
> 【10】可用於每連線區 = 9160 − 5964 = 3196 MB
>       每連線基本約 2.3 MB，尖峰暫存表 20% × 32 M
>       設 max_connections = C：
>         2.3C + (0.2C × 32) = 2.3C + 6.4C = 8.7C ≤ 3196
>         C ≤ 367
>       ★★★★ 但實際需求只有 24(FPM) + 6(queue) + 4(其他) = 34
>       → 設 max_connections = 100（3 倍餘裕，且遠低於上限）
>
> 結論：innodb_buffer_pool_size = 5G，max_connections = 100
>       最壞合計 ≈ 5964 + 870 = 6834 MB，餘裕 +2326 MB ✓
> ```

> [!question]- 練習 2：讀懂一筆慢查詢並決定下一步
> **題目**：慢查詢日誌出現這一筆，你要怎麼判斷、下一步做什麼？
> ```text
> # Query_time: 3.882914  Lock_time: 2.914003  Rows_sent: 1  Rows_examined: 1
> SELECT * FROM documents WHERE id = 88213 FOR UPDATE;
> ```
>
> **參考解答**：
> ```
> 【1】Rows_examined = 1，Rows_sent = 1 → 比值 1:1
>      ★★★★ 這【不是】缺索引的問題，主鍵查詢已經是最佳路徑
>
> 【2】關鍵在 Lock_time = 2.914 秒，佔了 Query_time 的 75%
>      → 這條查詢本身只花了約 0.97 秒，其餘時間都在【等鎖】
>
> 【3】所以問題在別的交易佔住了這一列：
>      mysql> SHOW ENGINE INNODB STATUS\G     ← 看 TRANSACTIONS 段 ★★★
>      找 "---TRANSACTION ... ACTIVE N sec" 且 N 很大的那一筆
>      mysql> SELECT * FROM sys.innodb_lock_waits;   ← 誰在等誰
>
> 【4】常見成因：應用端在交易裡做了外部 API 呼叫或檔案上傳，
>      交易開著卻在等網路，一等就是好幾秒
>
> 【5】對應處置：
>      · 短期：監控 Innodb_row_lock_waits，超標告警
>      · 根本：請開發把交易範圍縮到只包住 DB 操作 ★★★★
>      · 這是應用層問題，【調任何 MySQL 參數都不會改善】
> ```

> [!question]- 練習 3：設定改了卻沒生效
> **題目**：你在 `zz-tuning.cnf` 把 `max_connections` 改成 60 並重啟，
> 但 `SHOW GLOBAL VARIABLES` 顯示 300。列出你的排查順序。
>
> **參考解答**：
> ```
> 【1】確認設定檔真的有那一行、也真的被讀到
>      $ sudo my_print_defaults mysqld | grep max_connections
>      --max_connections=60
>      → 有讀到 60，代表不是檔案位置或語法問題
>
> 【2】★★★★ 第一嫌疑：SET PERSIST
>      mysql> SELECT * FROM performance_schema.persisted_variables;
>      +-----------------+----------------+
>      | max_connections | 300            |
>      +-----------------+----------------+
>      → 找到了。mysqld-auto.cnf 讀在所有設定檔之後，它贏
>      mysql> RESET PERSIST max_connections;
>      $ sudo systemctl restart mysql
>      mysql> SELECT @@max_connections;     → 60 ✓
>
> 【3】若 persisted_variables 是空的，第二嫌疑是【參數寫在兩個地方】
>      $ sudo grep -rn 'max_connections' /etc/mysql/ /etc/my.cnf 2>/dev/null
>      → 若 conf.d/ 與 mysql.conf.d/ 各有一份，讀取順序不保證，刪到只剩一處 ★★★
>
> 【4】第三嫌疑：值被自動調整或有上限
>      $ sudo tail -n 30 /var/log/mysql/error.log | grep -i 'adjust\|changed'
>      → 例如 open_files_limit 不足時，MySQL 會自動下修 max_connections 並記在 error log
>      $ systemctl show mysql -p LimitNOFILE
>
> 【5】結論寫進變更單，並用 mysql-tune-check.sh 的參數比對段做例行驗收 ★★★
> ```

## 小測驗

Q1. MySQL 在 Ubuntu 上會依序讀哪些設定檔？**同一個參數出現在兩個檔案時哪一個生效**？為什麼建議自建 `zz-tuning.cnf` 而不是改 `mysqld.cnf`？

Q2. 「這行指令會發生什麼」：`SET GLOBAL innodb_buffer_pool_size = 4294967296;` 在一台 8 GB 的 LXMP 共存機上執行。

Q3. **是非題**：`sort_buffer_size` 從 256 K 調成 8 M 可以讓排序變快，是划算的調整。請說明理由。

Q4. 你把 `innodb_buffer_pool_size` 設成 `3G`，重啟後 `SHOW GLOBAL VARIABLES` 顯示 `3355443200`（3.125 G）。發生了什麼事？

Q5. **選擇題**：主管問「斷電時我們會掉多少資料？」在 `innodb_flush_log_at_trx_commit = 2` 且 `sync_binlog = 0` 的設定下，正確答案是？
(A) 一筆都不會掉 (B) 最壞情況約最後 1 秒內已提交的交易 (C) 全部未備份的資料 (D) 取決於 buffer pool 大小

Q6. `log_queries_not_using_indexes = ON` 是找出缺索引查詢的利器，**但為什麼一定要同時設 `log_throttle_queries_not_using_indexes`**？不設會發生什麼？

Q7. 「看到這個錯誤該先查哪裡」：`systemctl restart mysql` 之後 `systemctl status mysql` 顯示 `Active: failed (Result: exit-code)`。你的前三個動作是什麼？

Q8. 現場出現 `ERROR 1040 (HY000): Too many connections`，你手上沒有任何連線。請說明你能怎麼進去、進去之後看什麼、以及**為什麼「直接調大 max_connections」通常不是正解**。

Q9. `Created_tmp_disk_tables / Created_tmp_tables = 45%`。這代表什麼？調大 `tmp_table_size` 一定有用嗎？有哪兩種情況調多大都沒用？

Q10. 你上週處理過 `Too many connections`，當時執行了 `SET GLOBAL max_connections = 300;`，今天問題又出現了。**成因是什麼？正確的做法應該是什麼？**

> [!question]- 測驗答案
> **Q1.** 順序是 `/etc/my.cnf` → `/etc/mysql/my.cnf` → `~/.my.cnf`，
> 而 `/etc/mysql/my.cnf` 內以 `!includedir` 再拉進 `/etc/mysql/conf.d/` 與
> `/etc/mysql/mysql.conf.d/`；最後還會讀資料目錄下的 `mysqld-auto.cnf`。
> ★★★★ **同一參數出現多次時，最後讀到的那一個生效**（`--user` 是唯一例外，取第一個）。
> 用 `mysqld --verbose --help | head -12` 可以看到 mysqld 自己宣告的順序。
> 建議自建 `zz-tuning.cnf` 的理由有三個：
> ① `apt upgrade` 時 dpkg 不會碰不屬於套件的檔案，**改 `mysqld.cnf` 會遇到覆蓋詢問**；
> ② `zz-` 開頭在字典序最後，我們的值比較容易贏；
> ③ 一眼區分「人為調整」與「發行版預設」，交接與稽核都方便。
> ★★★ 但要注意官方文件明講 `!includedir` 的**讀取順序不保證**，
> 所以**同一個參數絕對不要寫在兩個檔案裡**。見〈基礎設定〉。
>
> **Q2.** 它會**立即把 buffer pool 從目前值線上調整成 4 GB，不需要重啟**，
> 但會造成三個後果：
> ① 調整期間 InnoDB 重新配置 chunk，**有數秒到數十秒的效能抖動**；
> ② ★★★★ 在 8 GB 共存機上，全域區會膨脹到約 4.5 GB，加上每連線區與
> PHP-FPM／Redis／Nginx，**最壞情況總和超過實體記憶體 → OOM killer 會殺掉 mysqld**；
> ③ ★★★ 因為是 `SET GLOBAL` 而非寫入設定檔，**重啟後就回到舊值**，
> 造成「昨天測試沒問題、今天重開又不一樣」的假象。
> 正確做法是先算預算表，確認餘裕為正，再同時改 `zz-tuning.cnf` 並排程重啟。
> 見〈進階設定與調校〉第一、二節。
>
> **Q3.** **錯誤（是非題答「非」）**。
> `sort_buffer_size` 是 ★★★★ **每連線參數**，不是全域參數。
> ```
> 8 M × max_connections 300 = 【2.4 GB】憑空長出來
> ```
> 而且 MySQL 對排序有分段配置的最佳化，**多數查詢根本用不到 8 M**，
> 調大只是讓最壞情況變恐怖，實際收益極小。
> ★★★ 判斷準則：**每連線參數要調，先乘以 `max_connections` 再決定**。
> 真正該做的是把那條需要大量排序的查詢加上索引（見 [[060-04-01-03-cmd-MySQL-SQL基礎操作]]），
> 讓它根本不需要排序。見〈觀念說明〉與〈速查表：記憶體相關參數〉。
>
> **Q4.** 這是 ★★★ **chunk 對齊**。
> 規則是：`innodb_buffer_pool_size` 會被**向上調整**成
> `innodb_buffer_pool_chunk_size × innodb_buffer_pool_instances` 的整數倍。
> ```
> chunk_size 預設 128 M，若 instances = 8 → 對齊單位 = 1 G... 但此例是：
> 3 G 不是對齊單位的倍數 → 往上補到 3.125 G
> ```
> 後果不是「壞掉」，而是 ★★★★ **你的記憶體預算表對不起來** ——
> 多吃的 128 MB 在尖峰時可能就是壓垮駱駝的那一根。
> 用 `SELECT @@innodb_buffer_pool_size, @@innodb_buffer_pool_instances,
> @@innodb_buffer_pool_chunk_size;` 驗證，
> 解法是把值設成對齊單位的整數倍，或調整 `instances`。見〈進階設定與調校〉第二節。
>
> **Q5.** **(B) 最壞情況約最後 1 秒內已提交的交易**。
> `innodb_flush_log_at_trx_commit = 2` 代表 redo log 每次 commit 會寫進 OS 的檔案快取，
> 但**每秒才 fsync 一次**；`sync_binlog = 0` 代表 binlog 交給 OS 決定何時落地。
> ```
> mysqld 自己 crash        → 資料還在 OS 快取，【不會掉】
> ★★★★ 主機斷電 / OS panic → 最後約 1 秒的交易【真的不見】
> ```
> ★★★★ 這句話必須寫進系統文件，並與 [[060-04-01-05-svc-MySQL-備份與還原]] 訂的 **RPO** 對齊 ——
> 若 RPO = 0（公文、金流、個資異動），就**必須用 `1/1`**，
> 因為備份只能把你帶回上一個還原點，掉的那一秒備份救不回來。
> 見〈進階設定與調校〉第三節。
>
> **Q6.** 因為 `log_throttle_queries_not_using_indexes` ★★★★★ **預設是 0 = 完全不限流**。
> ```
> 一個沒加索引的列表頁每秒被打 50 次
>   → 每秒 50 筆慢查詢紀錄 × 約 300 bytes ≈ 15 KB/s
>   → 一天 1.3 GB → 三天把 /var 寫滿
>   → /var 滿了 MySQL 無法寫日誌與暫存 → 全站白畫面
> ```
> 設成 10 之後，**每 60 秒最多記 10 筆同類查詢**，
> 視窗結束時再補一行摘要說明被抑制了幾筆與累計耗時 —— 資訊沒有損失，磁碟卻保住了。
> ★★★★ 本手冊的規定是**這兩行永遠成對出現**。
> 額外提醒：慢查詢日誌會完整記錄 SQL 文字，其中的 `WHERE id_no = '...'` 就是個資，
> 檔案權限必須維持 `mysql:adm 0640`。見〈進階設定與調校〉第六節與〈安全性注意事項〉。
>
> **Q7.** ★★★★ **不要停在 `systemctl status`，它只會告訴你「失敗了」，不會說原因。**
> 前三個動作：
> ```bash
> 【1】sudo tail -n 40 /var/log/mysql/error.log     # ★★★★ 真正的錯誤在這裡
>      典型： [ERROR] [MY-000067] unknown variable 'innodb_bufer_pool_size=2G'
> 【2】sudo journalctl -u mysql -n 60 --no-pager    # error log 還沒生出來時看這個
> 【3】sudo -u mysql /usr/sbin/mysqld --validate-config   # 純語法驗證
> ```
> 確認是設定問題後的救援：**把 `zz-tuning.cnf` 移走 → `systemctl start mysql`
> → 確認 `active` → 再逐段加回去，每加一段跑一次 `--validate-config`**。
> ★★★ 這一整套的預防方法是：改設定的六步流程裡，
> **第【3】步就先 `--validate-config`**，根本不會走到重啟失敗。
> RHEL 系記得錯誤日誌在 `/var/log/mysql/mysqld.log`。見〈進階設定與調校〉第十節。
>
> **Q8.** ★★★★ **MySQL 會額外保留一條連線給具 `CONNECTION_ADMIN`／`SUPER` 權限的帳號**，
> 就是為了這一刻 —— 用 `sudo mysql` 走本機 socket 進去。進去之後看：
> ```sql
> SELECT user,host,db,command,time,state,LEFT(info,60)
> FROM information_schema.processlist ORDER BY time DESC LIMIT 15;
> ```
> ① 一堆 `Sleep` 且 `time` 很大 → 連線沒關，`wait_timeout` 太長；
> ② 有 `Query` 跑了幾百上千秒 → 爛查詢卡住，去撈慢查詢日誌；
> ③ `Waiting for table metadata lock` → 有人開了交易忘了 commit。
> **為什麼調大不是正解**：★★★★ `max_connections` 是每連線區的**乘數**，
> 60 → 150 會讓最壞記憶體多吃約 750 MB，
> **把「連線不足」換成「OOM 全服務中斷」**，而且中斷得更難查。
> 正解是往上游走：修掉那條卡住的查詢、縮短 `wait_timeout`、
> 或調降 PHP-FPM 的 `pm.max_children`（見 [[060-03-01-02-guide-PHP-FPM設定與Pool調校]]）。
> 見〈進階設定與調校〉第五節。
>
> **Q9.** 代表 ★★★ **有 45% 的暫存表放不進記憶體，落到磁碟去了** ——
> 通常伴隨 CPU iowait 升高與查詢變慢。門檻建議是 25%。
> 第一步確實是把 `tmp_table_size` 與 `max_heap_table_size` **設成相同值**
> （取兩者中較小的生效，只調一個等於沒調），例如 32 M。
> **但有兩種情況調多大都沒用**：
> ```
> 【1】結果集含 BLOB / TEXT 欄位 —— 這類暫存表容易直接落地
> 【2】單一暫存表本身就超過設定值，例如 GROUP BY 一張百萬列的表
> ```
> ★★★★ 這兩種情況的正解是**改查詢與加索引**（見 [[060-04-01-03-cmd-MySQL-SQL基礎操作]]），
> 或改用彙總表。另外要注意 ★★★★ 如果 `tmpdir` 指向 tmpfs 的 `/tmp`，
> 「落到磁碟」其實是**落到記憶體**，會讓你的預算表整個失準。
> 見〈進階設定與調校〉第八、九節。
>
> **Q10.** 成因是 ★★★ **`SET GLOBAL` 只改執行期的值，重啟就回到設定檔的值**。
> 中間主機重開過（`apt upgrade`，或被 OOM killer 殺掉後自動重啟），
> `max_connections` 悄悄回到 151，「上週明明修好了」的問題就重現。
> 佐證：`SHOW GLOBAL STATUS LIKE 'Uptime';`（值很小＝重啟過）
> 加上 `SELECT @@max_connections;`（已經不是 300）。
> 正確做法：
> ```
> 【1】救火用 SET GLOBAL 讓服務先活過來（這正是它的用途）
> 【2】★★★★ 同一分鐘內把值寫進 /etc/mysql/mysql.conf.d/zz-tuning.cnf
> 【3】用 my_print_defaults mysqld 確認檔案內容一致
> 【4】把「參數實際值比對」納入例行驗收（mysql-tune-check.sh 第 1 段）
> ```
> ★★★ 反方向的陷阱是 `SET PERSIST`：它寫進 `mysqld-auto.cnf` 且**贏過所有設定檔**，
> 造成「設定檔改了卻沒生效」。兩個坑要一起記。見〈基礎設定〉與第十節。
