# btop 操作與設定

## 觀念說明：btop vs htop ★★

| | **htop** | **btop** |
| --- | --- | --- |
| 主要用途 | **★★★ 程序管理** | **★★ 整體系統概覽** |
| CPU | ★★ 每核心的條 | ★★ 條 + **歷史曲線圖** |
| 記憶體 | ★★ 一條 | ★★ 條 + 曲線 + **各程序明細** |
| **磁碟 I/O** | ✗ | **★★★ 有**（每個掛載點的讀寫速度） |
| **網路流量** | ✗ | **★★★ 有**（即時上下行 + 曲線） |
| 程序管理 | **★★★ 完整**（kill/nice/樹狀/過濾） | ★★ 基本 |
| 滑鼠支援 | ★ 有 | **★★ 很好** |
| 資源占用 | **★ 極小**（~5MB） | ★★ 中（~30-60MB，**★ C++ 版還好**） |
| 在最小環境 | **★★★ 幾乎都有** | ★ 常常要自己裝 |
| 遠端 SSH | **★★★ 輕快** | ★★ 需要好一點的終端機 |
| 相依 | ★ 極少 | ★★ 需要 UTF-8、真彩色終端機 |

```
★★★ 實務建議：

  【日常排查、找程序、kill】     → ★★★ htop
  【看整體趨勢、含磁碟與網路】   → ★★ btop
  【伺服器只裝一個】             → ★★★ htop（★ 輕、通用、一定有）
  【自己的工作機】               → ★ 兩個都裝

★★ btop 的真正價值：
  一個畫面同時看到【CPU + 記憶體 + 磁碟 I/O + 網路】
  → ★★★ 排查「網站變慢」時，一眼就能看出是哪一類瓶頸
  → ★ 用 htop 的話要另外開 iostat 和 iftop
```

## 安裝

```bash
# ★★ Ubuntu 22.04+ / Debian 12+（★ 官方套件庫已有）
$ sudo apt update && sudo apt install -y btop
$ btop --version
btop version: 1.3.2

# ★ Ubuntu 20.04 用 snap
$ sudo snap install btop
```

> [!info]- Rocky / AlmaLinux（RHEL 系）對照
> ```bash
> $ sudo dnf install -y epel-release
> $ sudo dnf install -y btop
>
> # ★★ RHEL 8 的 EPEL 可能沒有 → 用官方 binary
> $ curl -fsSL -o /tmp/btop.tbz \
>     https://github.com/aristocratos/btop/releases/latest/download/btop-x86_64-linux-musl.tbz
> $ sudo tar xjf /tmp/btop.tbz -C /opt
> $ sudo ln -sf /opt/btop/bin/btop /usr/local/bin/btop
> ```

```bash
# ★★ 檢查終端機能力（★ btop 需要真彩色與 UTF-8）
$ echo "$TERM"
xterm-256color                       # ★ 或 screen-256color / tmux-256color

$ echo "$COLORTERM"
truecolor                            # ★★ 有這個最好

$ locale | grep -E 'LANG|LC_ALL'
LANG=zh_TW.UTF-8                     # ★★ 一定要 UTF-8

# ★★★ 顯示成亂碼時的處理
$ btop --utf-force                   # ★ 強制 UTF-8
$ TERM=xterm-256color btop
$ sudo locale-gen en_US.UTF-8 zh_TW.UTF-8 && sudo update-locale
```

## 畫面組成 ★★

```
┌─ cpu ────────────────────────────────────────────────────────────┐
│ CPU  32%  ▁▂▄▆█▆▄▂▁▂▄▆█  ← ★★ 歷史曲線（htop 沒有）             │
│ 0 [|||||||||    45%]  4 [||||           18%]                     │
│ 1 [||||         12%]  5 [||||||||||||   62%]                     │
│ Load: 1.24 0.98 0.87    Uptime: 12d 04:33   Temp: 52°C           │
└──────────────────────────────────────────────────────────────────┘
┌─ mem ──────────────────┐┌─ net ────────────────────────────────┐
│ Used   5.82G ████████  ││ ↓ 12.4 MiB/s  ▂▄▆█▆▄▂  ★★ 即時流量  │
│ Cache  2.10G ███       ││ ↑  3.2 MiB/s  ▁▂▃▂▁                  │
│ Free   0.41G █         ││ eth0  Total: ↓ 842GB  ↑ 210GB        │
│ Swap   128M  ▏         │└──────────────────────────────────────┘
│                        │┌─ disks ─ ★★★ htop 沒有 ─────────────┐
│ ★★ /     45G/100G  45% ││ /       Read  2.1 MiB/s ▁▂▁          │
│ ★★ /var  82G/200G  41% ││         Write 48.2 MiB/s ▄▆█▆  ★★★  │
└────────────────────────┘└──────────────────────────────────────┘
┌─ proc ───────────────────────────────────────────────────────────┐
│  Pid   Program      Command              Threads User  Mem   Cpu%│
│ 5678   mysqld       /usr/sbin/mysqld          42 mysql 2.0G  8.1 │
│ 1234   php-fpm      php-fpm: pool www          1 www-d 156M 12.3 │
└──────────────────────────────────────────────────────────────────┘
```

> [!tip] btop 最有價值的兩個面板 ★★★
> ```
> ★★★ ① disks 面板 —— 即時的讀寫速度
>      → 「網站變慢」時一眼看出是不是 I/O
>      → ★★ 而且是【每個掛載點分開】
>        · / 正常，/var 寫爆 → ★ 大概是日誌或資料庫
>      → ★ 等同於 iostat -x 1 但不用另開視窗
>
> ★★★ ② net 面板 —— 即時的上下行
>      → ★★ 「頻寬被誰吃掉了」的第一步
>      → ★ 突然的大量下行 = 可能在被爬 / 被攻擊
>      → ★ 大量上行 = 可能在被下載大檔 / 資料外洩
>
> ★★ 加上 CPU 與記憶體，四大資源一個畫面看完
>   → ★★★ 這就是 btop 存在的理由
> ```

## 操作 ★★

| 鍵 | 作用 |
| --- | --- |
| **`Esc` / `m`** | **★★ 主選單** |
| **`f`** | **★★★ 過濾程序** |
| **`+` / `-`** | 展開 / 收合程序樹 |
| **`e`** | **★★ 切換樹狀檢視** |
| **`↑↓`** | 選擇程序 |
| **`Enter`** | **★★ 程序詳細資訊**（含開啟的檔案、記憶體明細） |
| **`t`** | **★★ 送 SIGTERM** |
| **`k`** | 送 SIGKILL |
| `s` | 送任意訊號 |
| **`1` `2` `3` `4`** | **★★ 開/關 CPU/記憶體/網路/程序面板** |
| `p` | 切換 CPU 顯示模式（總和 / 每核心） |
| **`c`** | **★ 切換每核心的顯示** |
| `d` | ★ 切換磁碟的顯示模式 |
| `h` | 說明 |
| `q` / `Ctrl+C` | 離開 |

```
★★★ 排序（在 proc 面板）：
  滑鼠點欄位標題，或用選單
  → ★★ 預設依 CPU 排序
  → ★ 按 Enter 看程序詳情最有用：
     · 完整指令列
     · ★★ 開啟的檔案（等於 lsof -p）
     · ★★ 記憶體明細
     · 執行緒數
     · ★ CPU 與記憶體的歷史曲線
```

```bash
# ★★ 命令列選項
$ btop --preset 0            # ★ 使用預設版面 0
$ btop --utf-force           # ★★ 強制 UTF-8
$ btop --low-color           # ★ 終端機色彩支援不佳時
$ btop --tty                 # ★★ 純文字模式（★ 實體 console 用）
$ btop --debug               # 除錯
```

## 設定 ★★

```bash
$ btop            # ★ 第一次執行會自動產生設定檔
$ ls ~/.config/btop/
btop.conf  btop.log  themes/

$ vim ~/.config/btop/btop.conf
```

```ini
# ~/.config/btop/btop.conf

# ═══ ★★ 外觀 ═══
color_theme = "Default"        # ★ 或 "gruvbox_dark" / "nord" / "dracula"
theme_background = False       # ★★ 用終端機的背景色（★ 建議 False）
truecolor = True               # ★★ 真彩色（★ 終端機不支援就設 False）
force_tty = False              # ★ 實體 console 設 True
vim_keys = False               # ★ hjkl 移動

# ═══ ★★★ 版面 ═══
# ★ 面板組合：可以只留你要的
shown_boxes = "cpu mem net proc"
#   ★★ 只看程序：shown_boxes = "proc"
#   ★★ 伺服器排查：shown_boxes = "cpu mem net proc"

presets = "cpu:1:default,proc:0:default cpu:0:default,mem:0:default,net:0:default"
#   ★ 用 p 鍵切換預設版面

update_ms = 2000               # ★★★ 更新間隔（★ 見下方說明）

# ═══ ★★ 程序面板 ═══
proc_sorting = "cpu lazy"      # ★ cpu lazy / cpu direct / memory / pid / name
proc_reversed = False
proc_tree = False              # ★★ 樹狀檢視
proc_colors = True
proc_gradient = True
proc_per_core = False          # ★★ CPU% 是否除以核心數
proc_mem_bytes = True          # ★★ 顯示 MB 而不是百分比
proc_cpu_graphs = True         # ★ 每個程序的迷你曲線
proc_info_smaps = False        # ★★★ 見下方警告
proc_filter_kernel = True      # ★★ 隱藏核心執行緒（★ 建議 True）
proc_aggregate = False         # ★★ 子程序合併到父程序（★ php-fpm 很有用）

# ═══ ★★ CPU ═══
cpu_graph_upper = "total"
cpu_graph_lower = "total"
cpu_invert_lower = True
cpu_single_graph = False
check_temp = True              # ★ 顯示溫度（★ 需要 lm-sensors）
show_coretemp = True
show_cpu_freq = True
custom_cpu_name = ""

# ═══ ★★★ 磁碟 ═══
show_disks = True
disks_filter = "exclude=/boot /snap /var/lib/docker/overlay2"
#   ★★★ 很重要！否則 snap 和 docker 的每一層都會列出來
#   ★★ 或用白名單：disks_filter = "/ /var /home"
only_physical = True           # ★★★ 只顯示實體磁碟（★ 排除 tmpfs/overlay）
use_fstab = True               # ★★ 依 /etc/fstab
zfs_arc_cached = True          # ★ ZFS 的 ARC 算進 cache
disk_free_priv = False
show_io_stat = True            # ★★★ 顯示 I/O 統計
io_mode = False                # ★ 磁碟條顯示 I/O 而不是使用量
io_graph_combined = False
io_graph_speeds = ""           # ★ 例如 "sda:100,sdb:50"（MiB/s 的刻度上限）

# ═══ ★★ 網路 ═══
net_download = 100             # ★ 下行的圖表上限（Mbit）
net_upload = 100
net_auto = True                # ★★ 自動調整刻度
net_sync = True                # ★ 上下行用同一個刻度
net_iface = ""                 # ★★ 指定網卡（空 = 自動選流量最大的）

# ═══ ★ 其他 ═══
show_battery = False           # ★ 伺服器關掉
show_uptime = True
show_swap = True
swap_disk = True
mem_graphs = True
temp_scale = "celsius"
base_10_sizes = False          # ★ False = 1024 進位（KiB/MiB）
background_update = True
clock_format = "%X"
log_level = "WARNING"
```

> [!danger] `proc_info_smaps` 會拖垮系統 ★★★
> ```
> ★★★ proc_info_smaps = True 讓 btop 讀取每個程序的
>      /proc/PID/smaps 來算精確的記憶體
>
> ★★★★ 問題：
>   · smaps 的讀取【非常昂貴】（★ 核心要遍歷整個位址空間）
>   · 程序多的時候（★ 幾百個）→ btop 自己吃掉一顆 CPU
>   · ★★★ 在正式伺服器上這是【自己製造效能問題】
>
> ★★ 建議：保持 False
>   → 需要精確的記憶體時，手動查單一程序：
>     $ grep ^Pss: /proc/PID/smaps_rollup
> ```

> [!warning] `update_ms` 的取捨 ★★
> ```
> update_ms = 500     ★ 很即時，但 btop 自己吃 CPU
> update_ms = 2000    ★★ 預設，平衡
> update_ms = 5000    ★★★ 伺服器上長時間開著（★ 建議）
>
> ★★★ 注意：
>   · btop 每次更新都要讀 /proc 下的幾百個檔案
>   · ★★ SSH 連線時，更新越頻繁 = 網路流量越多
>   · ★★★ 掛在 tmux 裡長時間跑的話一定要調大
>
> ★★ 檢查 btop 自己吃多少：
>   $ ps -o pid,rss,pcpu,cmd -C btop
> ```

```bash
# ★★ 主題
$ ls /usr/share/btop/themes/
adapta.theme  dracula.theme  gruvbox_dark.theme  nord.theme  solarized_dark.theme ...

# ★ 下載更多
$ mkdir -p ~/.config/btop/themes
$ curl -fsSL -o ~/.config/btop/themes/catppuccin_mocha.theme \
    https://raw.githubusercontent.com/catppuccin/btop/main/themes/catppuccin_mocha.theme

# ★★ 伺服器上的最小設定（★ 省資源）
$ mkdir -p ~/.config/btop
$ cat > ~/.config/btop/btop.conf <<'EOF'
color_theme = "Default"
theme_background = False
update_ms = 5000
shown_boxes = "cpu mem net proc"
proc_info_smaps = False
proc_filter_kernel = True
proc_aggregate = True
only_physical = True
disks_filter = "exclude=/boot /snap /var/lib/docker"
show_battery = False
log_level = "ERROR"
EOF
```

## 完整實戰範例：用 btop 定位瓶頸

```bash
# ═══ 情境：使用者回報「網站有時候很慢」 ═══
$ btop
```

```
★★★ 觀察順序（★ 四個面板一次看完）：

【① CPU 面板】
  CPU 18%  ▂▂▃▂▂▃▂▂          ← ★ 不高，曲線平穩
  Load: 8.42 6.21 4.15         ← ★★★ 但 load 8.4（4 核）→ 有東西在排隊
  → ★★★★ CPU 低但 load 高 = 【不是 CPU 瓶頸】

【② mem 面板】
  Used   6.90G ████████████    ← ★★ 快滿
  Cache  0.70G █               ← ★★★ cache 被擠光了！
  Free   0.20G ▏
  Swap   1.40G ████            ← ★★★★ swap 用了 1.4G → 【記憶體不夠】

【③ disks 面板】★★★ 關鍵
  /       Read   8.2 MiB/s  ▄▆█▆▄
  /var    Write 68.4 MiB/s  ██████    ← ★★★★ /var 一直在寫
  → ★★ /var 是資料庫和日誌的位置

【④ net 面板】
  ↓ 2.1 MiB/s   ↑ 8.4 MiB/s   ← ★ 不算高，排除頻寬問題

★★★★ 三十秒的結論：
  記憶體不夠 → page cache 被擠光 → 資料庫一直讀寫磁碟 → I/O 塞住 → load 爆高
  ★ 不是 CPU 問題，也不是網路問題
```

#                                                          ↑
#                                            ★★★★ 磁碟 100% 滿載

$ ps -eo pid,rss,comm --sort=-rss | head -6

$ grep innodb_buffer_pool_size /etc/mysql/mysql.conf.d/mysqld.cnf
innodb_buffer_pool_size = 3G       # ★★★ 加上 MySQL 就超過實體記憶體了

# ═══ ★★★【處置】═══
#   ① 立即：降低 pm.max_children
$ sudo sed -i 's/^pm.max_children = 20/pm.max_children = 8/' \
    /etc/php/8.3/fpm/pool.d/www.conf
$ sudo php-fpm8.3 -t && sudo systemctl reload php8.3-fpm

#   ② 調整 MySQL
$ sudo sed -i 's/^innodb_buffer_pool_size.*/innodb_buffer_pool_size = 2G/' \
    /etc/mysql/mysql.conf.d/mysqld.cnf
$ sudo systemctl restart mysql

#   ③ ★★ 再看一次 btop
$ btop
#   → Cache 回到 2.5G、Swap 停止增加、disks 的 write 降下來、load 回到 1.x

#   ④ ★★★ 長期：加記憶體，或把資料庫分離出去
```

## 替代方案 ★★

### glances ★

```bash
$ sudo apt install -y glances          # 或 pip install glances
$ glances

# ★★ 特色：
#   · Python 寫的，★ 幾乎在哪都能裝
#   · ★★★ 有【web 模式】與 API
#   · ★★ 內建告警（★ 數值超標會變色）
#   · ★ 支援 Docker 容器統計

# ★★★ web 模式（★ 遠端看很方便）
$ glances -w --bind 127.0.0.1 --port 61208
#   → ★★ 一定要綁 127.0.0.1，再用 SSH 埠轉發連
$ ssh -L 61208:127.0.0.1:61208 server
#   → 本機瀏覽器開 http://localhost:61208

# ★ 匯出成 JSON / CSV（★ 可以做簡單的記錄）
$ glances --export csv --export-csv-file /var/log/glances.csv -t 60
$ glances --stdout cpu.user,mem.used,load.min1 -t 5

# ★★ 用戶端/伺服器模式
$ glances -s -B 127.0.0.1              # 伺服器端
$ glances -c 127.0.0.1                 # 用戶端
```

> [!warning] glances 的 web 模式不要對外開 ★★★
> ```
> ★★★★ glances -w 預設綁 0.0.0.0:61208，【沒有認證】
>   → 任何人連得到就看得到你的完整系統資訊
>     · 跑了什麼服務

## 小測驗

Q1. **btop 比 htop 多了哪兩個關鍵面板**？為什麼重要？

Q2. **`proc_info_smaps = True` 為什麼不建議在伺服器上開**？

Q3. **btop 的 disks 面板列出一堆 `overlay` 和 `/dev/loop`，怎麼處理**？

Q4. **`update_ms` 該設多少**？考量是什麼？

Q5. **CPU 面板顯示 18% 但 load 是 8.4（4 核），從 btop 的哪個面板找答案**？

Q6. **`glances -w` 有什麼安全風險**？正確用法？

Q7. **在容器內跑 btop，記憶體數字可以相信嗎**？

Q8. **伺服器上如果只能裝一個監控工具，該裝哪個**？為什麼？

Q9. **`sysstat` 為什麼建議每台伺服器都裝**？

Q10. **從 GitHub 下載 btop binary 時該做什麼驗證**？

> [!question]- 測驗答案
> **Q1.** **★★★ disks（磁碟 I/O）與 net（網路流量）** —— htop 完全沒有這兩個。
> **為什麼重要**：排查「網站變慢」時，四大資源
> （CPU、記憶體、磁碟 I/O、網路）**必須一起看才能定位瓶頸**。
> 用 htop 的話，你看到 CPU 不高、記憶體看起來還好，
> 就得**另外開 `iostat -x 1` 和 `iftop`** 才知道是不是 I/O 或頻寬問題。
> btop 一個畫面就能判斷：
> **CPU 低 + load 高 + disks 面板某個掛載點狂寫 = I/O 瓶頸**；
> **net 面板突然大量下行 = 可能被爬蟲或攻擊**。
> disks 面板還會**分掛載點顯示**，
> 「`/` 正常但 `/var` 寫爆」直接指向日誌或資料庫。
>
> **Q2.** 因為 **讀取 `/proc/PID/smaps` 對核心來說非常昂貴** ——
> 核心必須**遍歷該程序的整個虛擬位址空間**並逐段統計，
> 一個大程序的 smaps 可能有幾千行。
> btop 每次更新都對**每一個程序**做這件事，
> 程序數量一多（幾百個很常見）**btop 自己就吃掉一整顆 CPU**。
> **在正式伺服器上這等於用監控工具製造效能問題** ——
> 你為了看效能而讓系統變慢，觀察行為本身干擾了被觀察的對象。
> **建議保持 `False`**；真的需要精確的記憶體數字時，
> **手動查單一程序**就好：
> ```bash
> grep ^Pss: /proc/<PID>/smaps_rollup
> ```
> （`smaps_rollup` 是核心預先彙總好的，比讀完整 `smaps` 便宜很多。）
>
> **Q3.** 那些是 **Docker 的 overlay 檔案系統層和 snap 的 loop 裝置掛載**，
> 一台跑 Docker 的機器可能有幾十個，把畫面完全洗版。
> **兩個設定**：
> ```ini
> only_physical = True                                    # ★★★ 只顯示實體磁碟
> disks_filter = "exclude=/boot /snap /var/lib/docker/overlay2"
> ```
> `only_physical` 直接排除 tmpfs、overlay、squashfs 等虛擬檔案系統，
> 通常這一個就夠了。
> `disks_filter` 也支援**白名單**寫法：`disks_filter = "/ /var /home"`。
> 另外 `use_fstab = True` 讓 btop 只顯示 `/etc/fstab` 裡定義的掛載點，
> 也是一個乾淨的做法。
> 驗證用 `findmnt -t ext4,xfs,btrfs -o TARGET,SOURCE` 看真正該顯示的有哪些。
>
> **Q4.** **伺服器上建議 5000（5 秒）**，工作機用預設的 2000 就好。
> **考量有三個**：
> ①**★★ btop 自己的 CPU 消耗** —— 每次更新都要讀 `/proc` 下的**幾百個檔案**，
> 500ms 的更新頻率會讓 btop 明顯吃 CPU；
> ②**★★ SSH 的網路流量** —— 遠端連線時，更新越頻繁，
> 傳送的畫面更新資料越多，慢速連線下會很卡；
> ③**★★★ 長時間掛在 tmux 裡** —— 這是最常見的用法，
> 一個開著好幾天的 btop 如果 500ms 更新一次，累積的資源消耗很可觀。
> **檢查方式**：`ps -o pid,rss,pcpu,cmd -C btop`，
> **`%CPU` 超過 5 就該調大 `update_ms`**。
>
> **Q5.** **★★★ disks 面板** —— **CPU 低但 load 高，幾乎一定是 I/O 問題**。
> load average 統計的是 **R（執行/等 CPU）+ D（等 I/O）**狀態的程序，
> CPU 只有 18% 表示沒什麼東西在算，
> 那 load 8.4 就是**一堆程序卡在 D 狀態等磁碟**。
> **在 disks 面板看**：哪個掛載點的 Read/Write 速度異常高、
> 或是速度不高但一直有活動（表示磁碟已經到極限）。
> **接著用專門工具確認**：
> ```bash
> mpstat -P ALL 1 3     # ★★★ %iowait 高就確認了
> iostat -x 1 3         # ★★ %util 接近 100%、w_await 高
> ps -eo state,pid,cmd | awk '$1~/^D/'     # ★★★ 誰卡住
> sudo iotop -oPa       # ★★ 誰在讀寫
> ```
> **也要看 mem 面板** —— 記憶體不夠導致 page cache 被擠光，
> 是造成 I/O 暴增最常見的根因。
>
> **Q6.** **★★★★ `glances -w` 預設綁 `0.0.0.0:61208` 而且沒有任何認證** ——
> 任何連得到那個 port 的人都能看到你的**完整系統資訊**：
> 跑了什麼服務與版本、**完整的程序指令列（可能含密碼）**、
> 檔案系統配置、網路介面與 IP、資源使用狀況。
> 這對攻擊者是**現成的偵察報告**。
> **正確用法**：
> ```bash
> glances -w --bind 127.0.0.1 --port 61208   # ★★★ 只綁本機
> ssh -L 61208:127.0.0.1:61208 server        # ★★ SSH 埠轉發存取
> # 本機瀏覽器開 http://localhost:61208
> ```
> 真的需要對外提供的話，必須放在**反向代理後面 + Basic Auth + HTTPS + IP 白名單**，
> 而且 `--password` 只是最低限度的補強，不能取代前面的措施。
>
> **Q7.** **★★★★ 不能** —— 和 htop 完全一樣的問題。
> btop 讀的是 **`/proc/meminfo`，那是主機的資料**，
> 不是容器的 cgroup 限制。
> 容器限制 512MB 但 btop 顯示「5.8G/7.75G」，
> 你以為還很寬裕，其實**隨時會被 cgroup OOM killer 砍掉**。
> **該看的地方**（容器內，cgroup v2）：
> ```bash
> cat /sys/fs/cgroup/memory.max        # ★★★ 真正的上限
> cat /sys/fs/cgroup/memory.current    # 目前用量
> cat /sys/fs/cgroup/cpu.max
> ```
> **從主機看**：`docker stats --no-stream`、`systemd-cgtop`、
> `docker inspect <id> --format '{{.State.OOMKilled}}'`。
> 例外是裝了 **lxcfs** 的環境（常見於 LXC/Proxmox 容器），
> 它會讓容器內的 `/proc` 反映 cgroup 限制。
>
> **Q8.** **★★★ htop**。理由：
> ①**幾乎所有發行版的套件庫都有**，而且很多系統預裝
> （btop 在 Ubuntu 22.04 之前、RHEL 8 都要另外處理）；
> ②**資源占用極小**（~5MB vs btop 的 30-60MB），
> 在資源吃緊的機器上不會火上加油；
> ③**程序管理功能完整** —— 過濾、樹狀、送訊號、看開啟的檔案，
> 這是排查時真正需要的；
> ④**在慢速 SSH 連線下依然輕快**；
> ⑤**對終端機的要求低**，實體 console、序列埠、老舊終端機都能用。
> btop 缺少的磁碟與網路資訊，
> 可以用 **`sysstat` 套件的 `iostat`/`mpstat`/`sar`** 補上 ——
> 而那些工具**更精確、可以寫進腳本、還有歷史資料**。
>
> **Q9.** 因為 **`sysstat` 提供「歷史資料」，這是所有互動式工具都沒有的**。
> htop 和 btop 只能看**現在**；
> 但事故通常是**事後才被回報**的：
> 「昨天下午三點網站很慢」「上禮拜三半夜服務掛過」——
> 沒有歷史資料就完全無從查起。
> **啟用方式**：
> ```bash
> sudo apt install -y sysstat
> sudo sed -i 's/^ENABLED="false"/ENABLED="true"/' /etc/default/sysstat
> sudo systemctl enable --now sysstat
> ```
> 之後每 10 分鐘自動記錄到 `/var/log/sysstat/sa<日期>`，預設保留 28 天。
> **查詢**：
> ```bash
> sar -u -f /var/log/sysstat/sa27          # ★★★ 27 號的 CPU
> sar -r -f /var/log/sysstat/sa27          # 記憶體
> sar -d -p -f /var/log/sysstat/sa27       # 磁碟
> sar -n DEV -f /var/log/sysstat/sa27      # 網路
> sar -q -s 14:00:00 -e 16:00:00           # ★★ 指定時段的 load
> ```
> 同時 `mpstat`/`iostat`/`pidstat` 也是這個套件提供的。
>
> **Q10.** **★★ 驗證 SHA256 checksum**：
> ```bash
> curl -fsSL -O .../btop-x86_64-linux-musl.tbz
> curl -fsSL -O .../btop-x86_64-linux-musl.tbz.sha256
> sha256sum -c btop-x86_64-linux-musl.tbz.sha256
> # btop-x86_64-linux-musl.tbz: OK        ★★ 一定要看到 OK
> ```
> **但更重要的原則是：★★★ 正式環境優先用套件庫的版本**。
> 理由：
> ①套件庫的版本**會隨著系統更新拿到安全修補**，
> 手動下載的 binary **沒有人會提醒你有漏洞**，通常一放就是好幾年；
> ②套件庫的內容經過發行版維護者的**簽章驗證**（APT/DNF 自動檢查 GPG 簽章），
> 比你手動比對一個 checksum 更可靠；
> ③`dpkg -S $(command -v btop)` 能追溯來源，符合稽核要求。
> **監控工具本身也是攻擊面** —— 它有讀取 `/proc` 的權限、
> 常常被以 root 執行、而且是維運人員每天都會跑的東西，
> 是供應鏈攻擊的理想目標。
