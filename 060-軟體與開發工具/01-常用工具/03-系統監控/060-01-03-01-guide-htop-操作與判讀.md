# htop 操作與判讀

> [!abstract] 這篇你會學到
> - htop 的畫面組成與**每一個欄位的意義**
> - **★★★ CPU 條的顏色**代表什麼（很多人只看百分比）
> - **★★★★ 記憶體條的綠/藍/黃/橘**與「記憶體用光了嗎」的正確判讀

> - 排序、過濾、樹狀檢視、送訊號

### ★★★ CPU 條的顏色

```
★★★★ 每一條 CPU 的【顏色】比百分比更重要：

  ▌綠色（藍色系統依主題而定）  low priority   ★ nice > 0 的程序
  ▌綠色                        normal        ★★ 使用者空間的一般程序
  ▌紅色                        kernel        ★★★ 核心空間（system time）
  ▌藍色                        virtualization ★ 虛擬化的 guest time
  ▌灰／青                      IO-wait       ★★★★ 等待磁碟（★ 見下）
  ▌橘                          IRQ           硬體中斷
  ▌洋紅                        soft IRQ      ★★ 軟體中斷（★ 網路封包處理）
  ▌灰                          steal         ★★★★ 被 hypervisor 搶走（★ 雲端主機）

★★★ 怎麼判讀：

  綠色為主      → ★ 正常，應用程式在做事
  紅色很多      → ★★★ 核心在忙
                  · 大量 syscall（★ 檔案 I/O、網路）
                  · context switch 太多
                  · ★★ 可能是程式寫法問題（例如每次迴圈都 open/close）
  IO-wait 高    → ★★★★ CPU 在【等磁碟】，不是在算
                  · ★ 加 CPU 沒用，要換 SSD / 調 I/O
                  · ★★ 用 iostat -x 1 確認
  steal 高      → ★★★★ 【雲端主機被超賣】
                  · 你的 vCPU 被 hypervisor 分給別人了
                  · ★★★ 這不是你的問題，要換機型或找供應商
  soft IRQ 高   → ★★ 網路流量大（★ 用 ethtool -S 看網卡）
```

```bash
# ★★ 用 mpstat 看更精確的分類
$ sudo apt install -y sysstat
$ mpstat -P ALL 1 3

  0  45.2  0.00  8.1    2.10 0.00  0.50   0.00   0.00  44.1
  2  88.7  0.00 45.2   12.40 0.00  3.20   0.00   0.00   0.5   # ★★ 這顆很忙
#   ★★★ %iowait 8.2 → 有 I/O 壓力
#   ★★★★ %steal > 5 → 雲端超賣
```

### ★★★★ 記憶體條的顏色

```
★★★★ 這是最多人誤判的地方：

  Mem[|||||||||||||||||||  5.82G/7.75G]
      ▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌
      綠  藍  黃  橘

  ▌綠色  used          ★★★ 【真正被程式用掉的】
  ▌藍色  buffers       ★★ 區塊裝置的緩衝
  ▌黃色  page cache    ★★★★ 【檔案快取】← ★ 關鍵！
  ▌橘色  shared        ★ 共享記憶體（tmpfs、/dev/shm）

★★★★ 最重要的觀念：
  【黃色（cache）不是「用掉」，是「借用」】
  → 核心把閒置的記憶體拿來快取檔案，加速讀取
  → ★★★ 程式需要記憶體時，核心會【立刻釋放 cache】
  → ★★★★ 所以「記憶體用了 90%」不代表記憶體不夠！

★★★ 正確的判斷方式：
  ① 看 free -h 的【available】欄（★ 不是 free）
  ② 看 htop 的 Swp（swap）有沒有在用
  ③ ★★ 看 vmstat 的 si/so（swap in/out）
```

```bash
# ★★★ free -h 的正確讀法
$ free -h
               total   used   free  shared  buff/cache  available
Mem:            7.8Gi  2.1Gi  0.4Gi   210Mi       5.3Gi       5.4Gi
Swap:           2.0Gi  128Mi  1.9Gi
#                              ↑              ↑             ↑
#                     ★ free 只有 0.4G       ★★ cache 5.3G
#                     → 看起來快滿了？        ★★★★ available 5.4G
#                                              → 【還有 5.4G 可用】！

★★★ available 的意義：
  「不需要 swap，程式現在可以拿到多少記憶體」
  → ★ 已經扣掉不可回收的部分
  → ★★★ 這才是判斷「記憶體夠不夠」的欄位

★★★★ 什麼時候才是真的不夠：
  ① available < 總量的 10%
  ② ★★ Swp 一直在增加
  ③ ★★★ vmstat 的 si/so 持續 > 0（★ 真的在換頁）
  ④ ★★★★ dmesg 出現 Out of memory: Killed process
```

```bash
# ★★★ 確認是否真的有記憶體壓力
$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1  0 131072 412000 210000 5300000  0    0     0    12  890 1420 32 12 48  8  0
 0  0 131072 408000 210000 5310000  0    0     0     8  850 1380 28 10 54  8  0
#                                    ↑    ↑
#                            ★★★ si/so 都是 0 → 沒有在換頁 → ★ 記憶體夠

# ★★★★ 有壓力時會長這樣：
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 3  2 1843200  48000  12000  180000 1240  890  4200  3100 5600 8900 45 32  5 18 0
#                                    ↑    ↑  ★★★★ 持續換頁 = 真的不夠

# ★★ 檢查 OOM killer
$ dmesg -T | grep -i 'out of memory\|killed process'
$ journalctl -k --since '1 day ago' | grep -i oom
$ grep -i oom /var/log/syslog | tail
```

### Load average ★★★

```
★★★ Load average: 1.24 0.98 0.87
                    ↑     ↑     ↑
                  1分鐘  5分鐘  15分鐘

★★★★ 最大的誤解：「load average 是 CPU 使用率」→ 不是！

★★★ 正確定義（Linux 特有）：
  「處於 R（running）或 D（uninterruptible sleep）狀態的程序平均數量」

  R = 正在跑或等 CPU
  ★★★ D = 【等待 I/O】（不可中斷睡眠）
      → ★★★★ 這是 Linux 與其他 Unix 最大的不同
      → ★ 所以磁碟很慢時 load 會爆高，但 CPU 可能是閒的

★★★ 怎麼判讀（假設 4 核心）：
  load < 4        ★ 沒有等待，正常
  load ≈ 4        ★★ 剛好滿載
  load > 4        ★★★ 有程序在排隊
  load = 40       ★★★★ 嚴重壅塞（★ 但要先看是 CPU 還是 I/O）

★★★★ load 高但 CPU 閒 = 【I/O 問題】
  → ★ 看 htop 的 IO-wait（灰/青色）
  → ★★ 用 iostat -x 1 找出哪個磁碟
  → ★★★ 用 ps 找出 D 狀態的程序
```

```bash
# ★★ 核心數
$ nproc
4
$ grep -c ^processor /proc/cpuinfo
4

# ★★★ 找出卡在 D 狀態（等 I/O）的程序
$ ps -eo state,pid,user,cmd | awk '$1 ~ /^D/'
D  12345 mysql    /usr/sbin/mysqld
D  12890 www-data php-fpm: pool www
#   ★★★ 這些程序在等磁碟

# ★★ 看它們在等什麼
$ sudo cat /proc/12345/stack 2>/dev/null | head
$ sudo cat /proc/12345/wchan; echo

# ★★★ 磁碟壓力
$ iostat -x 1 3
Device  r/s   w/s  rkB/s  wkB/s  ...  %util  aqu-sz  r_await w_await
sda    12.0  340.0  480.0 42000.0 ...  98.4    12.3    2.10   35.40
#                                        ↑              ↑
#                              ★★★★ %util 98% 磁碟滿載
#                                            ★★★ w_await 35ms 很慢
```

> [!tip] load average 的正常範圍 ★★
> ```
> ★★ 沒有絕對標準，但可以這樣抓：
>
>   load / 核心數 < 0.7    ★ 很健康
>   load / 核心數 ≈ 1.0    ★★ 滿載但還撐得住
>   load / 核心數 > 2.0    ★★★ 需要處理
>   load / 核心數 > 5.0    ★★★★ 使用者已經有感
>
> ★★★ 但一定要搭配：
>   · CPU 條的顏色（★ 是 user、system 還是 iowait？）
>   · free 的 available
>   · iostat 的 %util
>   → ★★★★ 單看 load 會誤判
> ```

## ★★★ 程序列表的欄位

| 欄位 | 意義 | 判讀重點 |
| --- | --- | --- |
| `PID` | 程序 ID | |
| `USER` | 執行者 | **★★ 服務跑在對的使用者嗎** |
| `PRI` | 核心的優先權 | 一般 20 |
| **`NI`** | **nice 值**（-20~19） | ★ 數字越小優先權越高 |
| **`VIRT`** | **虛擬記憶體** | **★★★ 通常不用管**（見下） |
| **`RES`** | **★★★ 實體記憶體**（RSS） | **★ 這才是真正吃掉的** |
| **`SHR`** | 共享記憶體 | ★★ 多個程序共用的部分 |
| `S` | 狀態 | **★★★ R/S/D/Z/T** |
| `CPU%` | CPU 使用率 | ★ 可以 > 100%（多執行緒） |
| `MEM%` | 記憶體百分比 | = RES / 總記憶體 |
| `TIME+` | 累計 CPU 時間 | **★★ 找長期吃 CPU 的程序** |
| `Command` | 指令 | ★ 按 `Shift+H` 可顯示完整路徑 |

### ★★★ VIRT / RES / SHR

```
★★★★ 最常見的誤判：「這個程序吃了 8GB！」（看 VIRT）

  PID  USER   VIRT   RES   SHR  Command
 5678  mysql 8192M 2048M   64M  /usr/sbin/mysqld
                ↑      ↑
      ★★★ VIRT 8G   ★ RES 2G

★★★ VIRT（virtual）= 程序【要求】的位址空間總和
  包含：
    · 實際使用的記憶體
    · ★★ mmap 但沒真正讀寫的檔案（★ 例如 MySQL 的 buffer pool 預留）
    · ★★ 共享函式庫（★ 每個程序都算一次，但實際只有一份）
    · ★ 已經 swap 出去的
  → ★★★★ VIRT 大【完全不代表】吃記憶體
  → ★ 一個 JVM 常常 VIRT 幾十 GB，RES 只有幾百 MB

★★★ RES（resident）= 【實際在實體記憶體中】的部分
  → ★★★ 這才是要看的
  → ★★ 但 RES 也會【重複計算共享的部分】

★★ SHR = RES 中【與其他程序共享】的部分
  → 主要是共享函式庫和 shared memory

★★★★ 所以「所有程序的 RES 加起來 > 總記憶體」是正常的
  → ★ 因為共享的部分被算了很多次
  → ★★★ 要精確算單一程序的獨占記憶體，用 PSS：
```

```bash
# ★★★ PSS（Proportional Set Size）—— 共享的部分按比例分攤
$ sudo grep -H '^Pss:' /proc/5678/smaps_rollup
/proc/5678/smaps_rollup:Pss:  1893204 kB      # ★★ ~1.85G（比 RES 準）

# ★★ 一次看多個
$ sudo smem -k -s pss -r | head -10          # ★ apt install smem
  PID User   Command                    Swap    USS    PSS    RSS
 5678 mysql  /usr/sbin/mysqld              0   1.7G   1.8G   2.0G
 1234 www-d  php-fpm: pool www             0  98.2M  156M   198M

# ★★★ php-fpm 這種 fork 出來的程序，PSS 差異很大
$ ps -eo pid,rss,comm --sort=-rss | head -10
$ sudo bash -c 'for p in $(pgrep php-fpm); do
    printf "%s %s\n" "$p" "$(grep ^Pss: /proc/$p/smaps_rollup|awk "{print \$2}")"
  done' | awk '{s+=$2} END {print "php-fpm PSS 總計: " s/1024 " MB"}'
php-fpm PSS 總計: 612 MB
#   ★★★ 這才是 php-fpm 真正吃的記憶體（★ 用來算 pm.max_children）
```

### 程序狀態 `S` ★★★

```
  R  Running        ★ 正在跑或等 CPU
  S  Sleeping       ★★ 可中斷睡眠（★ 絕大多數程序都是這個，正常）
  D  ★★★ Uninterruptible sleep  → 【等 I/O】
                    ★★★★ 很多 D = 磁碟或網路儲存有問題
                    ★ kill -9 也殺不掉
  Z  ★★ Zombie      → 子程序結束但父程序沒回收
                    ★ 少量正常；★★★ 大量 = 父程序有 bug
  T  Stopped        ★ 被 Ctrl+Z 或 SIGSTOP 暫停
  I  Idle           ★ 核心執行緒閒置（★ 正常）
```

```bash
# ★★ 統計各狀態
$ ps -eo state | sort | uniq -c | sort -rn
    285 S
     18 I
      3 R
      2 D                    # ★★★ 兩個在等 I/O
      1 Z                    # ★★ 一個殭屍

# ★★★ 找殭屍程序的父程序
$ ps -eo pid,ppid,state,cmd | awk '$3=="Z"'
  9876   1234 Z  [php] <defunct>
$ ps -p 1234 -o pid,cmd
  1234 /usr/bin/supervisord         # ★★ 這個父程序沒回收子程序
#   ★★★ 解法：重啟父程序（★ 殭屍本身殺不掉）
```

| **`H`** | **★★★ 顯示/隱藏使用者執行緒** |
| `K` | 顯示/隱藏核心執行緒 |

### 送訊號 ★★

```
★★ F9 之後選訊號：

  SIGTERM (15)   ★★★ 【預設，優雅結束】→ 程式可以清理後退出
  SIGKILL  (9)   ★★★★ 強制殺掉 → ★ 不會清理，可能損毀資料
  SIGHUP   (1)   ★★ 重新讀取設定（★ nginx/sshd 常用）
  SIGSTOP (19)   暫停
  SIGCONT (18)   繼續
  SIGUSR1/2      ★ 應用自訂（★ nginx 用 USR1 重開日誌）

★★★★ 順序原則：
  ① 先 SIGTERM，等 5~10 秒
  ② 還在 → 再 SIGTERM 一次
  ③ ★★ 真的不行才 SIGKILL
  ④ ★★★★ D 狀態的程序【SIGKILL 也殺不掉】
     → 要等 I/O 完成，或處理底層的儲存問題
```

```bash
# ★★ 命令列的等價操作
$ pkill -TERM -f 'php-fpm: pool www'
$ pkill -u www-data nginx
$ kill -HUP $(cat /run/nginx.pid)      # ★★ nginx 重讀設定

# ★★★ 服務請用 systemctl（★ 不要直接 kill）
$ sudo systemctl reload nginx           # ★ 優雅重載
$ sudo systemctl restart php8.3-fpm
#   → ★★★ 直接 kill 會讓 systemd 以為服務異常退出
```

## ★★ 容器與 cgroup 的陷阱

> [!danger] 在容器裡看到的是【主機的】資料 ★★★★
> ```
> ★★★★ htop 在容器內執行時：
>   · CPU 條 = 【主機的】所有核心
>   · Mem 條 = 【主機的】總記憶體
>   · ★★★ 不是容器的 limit！
>
> 情境：容器限制 512MB，htop 顯示 Mem 5.8G/7.75G
>   → ★★★ 你以為還有很多，其實容器隨時會 OOM
>
> ★★ 原因：htop 讀 /proc/meminfo，而 /proc 是主機的
>   → ★ 除非用了 lxcfs（LXC）或 --pid=host 之外的處理
> ```

```bash
# ★★★ 在容器裡看【真正的】限制（cgroup v2）
$ cat /sys/fs/cgroup/memory.max
536870912                              # ★★ 512MB
$ cat /sys/fs/cgroup/memory.current
487325696                              # ★★★ 已用 465MB → 快滿了！

$ cat /sys/fs/cgroup/cpu.max
200000 100000                          # ★★ = 2 個 CPU

# ★ cgroup v1（舊系統）
$ cat /sys/fs/cgroup/memory/memory.limit_in_bytes
$ cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us

# ★★ 從主機看容器
$ docker stats --no-stream
CONTAINER   CPU %   MEM USAGE / LIMIT    MEM %   NET I/O
app         12.3%   465MiB / 512MiB      90.8%   1.2GB / 890MB
#                          ↑
#                  ★★★★ 90.8% → 快 OOM 了

$ systemd-cgtop                          # ★★ systemd 的 cgroup 檢視
$ systemctl status php8.3-fpm | grep -E 'Memory|Tasks|CPU'
     Tasks: 12 (limit: 9445)
    Memory: 487.2M (peak: 612.1M)
       CPU: 1h 23min 45s
```

```bash

## 小測驗

Q1. **htop 顯示記憶體用了 90%，是不是快沒記憶體了**？怎麼正確判斷？

Q2. **load average 是什麼**？跟 CPU 使用率的關係是什麼？

Q3. **load average 是 20 但 CPU 幾乎閒著，最可能是什麼問題**？怎麼確認？

Q4. **VIRT、RES、SHR、PSS 分別是什麼**？算 `pm.max_children` 該用哪個？

Q5. **CPU 條出現大量 `steal`（灰色）代表什麼**？該怎麼處理？

Q6. **程序狀態 `D` 是什麼**？為什麼 `kill -9` 殺不掉？

Q7. **在容器裡跑 htop 看到 8GB 記憶體，可以相信嗎**？該看哪裡？

Q8. **htop 按 `H` 做什麼**？什麼時候需要？

Q9. **殭屍程序（`Z`）怎麼處理**？

Q10. **為什麼 `mysql -u root -pMyPass` 這樣下指令是資安問題**？

> [!question]- 測驗答案
> **Q1.** **不一定** —— 這是最常見的誤判。
> htop 的記憶體條裡，**黃色的 page cache 不是「被用掉」而是「被借用」** ——
> 核心把閒置的記憶體拿來快取檔案加速讀取，
> **程式需要時核心會立刻釋放**。
> **正確判斷方式**：看 **`free -h` 的 `available` 欄**（不是 `free`）：
> ```
>                total   used   free  shared  buff/cache  available
> Mem:            7.8Gi  2.1Gi  0.4Gi   210Mi       5.3Gi       5.4Gi
> ```
> `free` 只剩 0.4G 看起來很嚇人，但 **`available` 有 5.4G** —— 記憶體其實很夠。
> **真的不夠的四個徵兆**：
> ①`available` < 總量的 10%；
> ②swap 持續增加；
> ③**`vmstat` 的 `si`/`so` 持續 > 0**（真的在換頁）；
> ④`dmesg` 出現 `Out of memory: Killed process`。
>
> **Q2.** **★★★★ load average 是「處於 R（執行/等 CPU）或 D（等 I/O）狀態的程序平均數量」**，
> 分別統計 1 分鐘、5 分鐘、15 分鐘。
> **★★★ 它不是 CPU 使用率** —— 這是 Linux 與其他 Unix 最大的不同：
> **Linux 把 D 狀態（等待 I/O 的不可中斷睡眠）也算進去**。
> 所以磁碟很慢時 load 會爆高，但 CPU 可能完全是閒的。
> **判讀要對照核心數**（`nproc`）：
> ```
> load / 核心數 < 0.7   ★ 健康
> load / 核心數 ≈ 1.0   ★★ 滿載
> load / 核心數 > 2.0   ★★★ 需要處理
> ```
> 4 核心的機器 load 4 是滿載，8 核心的機器 load 4 只是一半。
> **單看 load 會誤判**，一定要搭配 CPU 條的顏色、`available`、`iostat` 一起看。
>
> **Q3.** **★★★★ I/O 問題** —— 大量程序卡在 **D 狀態（等待磁碟）**，
> 這些程序算進 load 但不消耗 CPU。
> **確認方式**：
> ```bash
> mpstat -P ALL 1 3            # ★★★ 看 %iowait（高就是 I/O 瓶頸）
> iostat -x 1 3                # ★★ 看 %util（接近 100% = 磁碟滿載）
>                              #    看 aqu-sz（佇列長度）、w_await（延遲 ms）
> ps -eo state,pid,user,cmd | awk '$1 ~ /^D/'   # ★★★ 列出卡住的程序
> sudo iotop -oPa              # ★★ 誰在讀寫
> ```
> **常見成因**：磁碟真的太慢（機械硬碟）、
> **記憶體不夠導致 page cache 被擠光而反覆讀磁碟**、
> 資料庫的慢查詢做全表掃描、NFS/iSCSI 網路儲存有問題、磁碟即將故障。
> **★★★ 加 CPU 完全沒用**，要解決 I/O 或記憶體。
>
> **Q4.** **`VIRT`（虛擬記憶體）** = 程序**要求的位址空間總和**，
> 包含 mmap 但沒真正讀寫的部分、共享函式庫（每個程序都算一次）、已 swap 出去的 ——
> **★★★ VIRT 大完全不代表吃記憶體**，JVM 常常 VIRT 幾十 GB 但 RES 只有幾百 MB。
> **`RES`（RSS，常駐記憶體）** = **實際在實體記憶體中的部分** ——
> 這才是要看的，但**會重複計算共享的部分**。
> **`SHR`** = RES 中與其他程序共享的部分（主要是共享函式庫）。
> **`PSS`（Proportional Set Size）** = **共享部分按使用者數量比例分攤後的值** ——
> **最準確**：`grep ^Pss: /proc/PID/smaps_rollup`。
> **算 `pm.max_children` 要用 PSS** ——
> php-fpm 的 worker 是 fork 出來的，共享大量記憶體，
> 用 RES 相加會**嚴重高估**（可能高估 2-3 倍），導致 max_children 設得太保守。
>
> **Q5.** **★★★★ 你的雲端主機被超賣了** ——
> `steal` 是「你的 vCPU 想執行，但被 hypervisor 分配給同一台實體機上的其他租戶」的時間。
> **這不是你的系統的問題，是你買不到你付錢的 CPU**。
> **判斷標準**：
> ```
> %steal < 1%    ★ 正常
> %steal 5~10%   ★★ 有影響，開始注意
> %steal > 10%   ★★★★ 嚴重，服務明顯變慢
> ```
> **確認**：`mpstat -P ALL 1` 或 `vmstat 1` 的 `st` 欄。
> **處理方式**：
> ①**換機型**（通常「共享型/突發型」實例最容易 steal，換成「專用型/獨享 CPU」）；
> ②**換可用區或重建實例**（可能被排到比較空的實體機）；
> ③**向供應商反映**（附上 `mpstat` 的數據）。
> **調你自己的應用程式完全沒有用**。
>
> **Q6.** **`D` = Uninterruptible Sleep（不可中斷睡眠）**，
> 意思是程序**正在等待一個不能被打斷的核心操作完成**，
> 絕大多數情況是**等待磁碟或網路儲存的 I/O**。
> **`kill -9` 殺不掉的原因**：
> 訊號要送給程序，程序必須**回到使用者空間才能處理訊號** ——
> 但 D 狀態的程序卡在核心裡等 I/O，**根本沒有機會處理任何訊號**，
> 包括 SIGKILL。訊號會被記錄下來，等 I/O 完成回到使用者空間時才生效。
> **所以真正的解法是處理 I/O 本身**：
> 磁碟壞了？NFS server 掛了？iSCSI 斷線？磁碟佇列塞爆？
> ```bash
> sudo cat /proc/<PID>/stack     # ★ 看卡在核心的哪個函式
> cat /proc/<PID>/wchan          # ★ 等待通道
> dmesg -T | tail -30            # ★★ I/O 錯誤、NFS timeout
> ```
> **大量 D 狀態程序 = 儲存層出事了**，這是要立刻處理的訊號。
>
> **Q7.** **★★★★ 不能相信** —— htop 讀的是 **`/proc/meminfo`，那是主機的**，
> **不是容器的 cgroup 限制**。
> 容器限制 512MB 但 htop 顯示「5.8G/7.75G」，
> 你以為還很寬裕，其實**隨時會被 cgroup OOM killer 砍掉**。
> **該看哪裡**（容器內，cgroup v2）：
> ```bash
> cat /sys/fs/cgroup/memory.max        # ★★★ 真正的上限
> cat /sys/fs/cgroup/memory.current    # ★★★ 目前用量
> cat /sys/fs/cgroup/cpu.max           # ★ CPU 配額
> ```
> **從主機看**：
> ```bash
> docker stats --no-stream             # ★★ MEM USAGE / LIMIT
> systemd-cgtop                        # ★ systemd 服務的 cgroup
> docker inspect <id> --format '{{.State.OOMKilled}}'   # ★★★ 是不是被 OOM 殺的
> dmesg -T | grep -i 'memory cgroup'
> ```
> 有些環境裝了 **lxcfs** 可以讓容器內的 `/proc` 反映 cgroup 限制，但預設沒有。
>
> **Q8.** **`H` 切換「顯示/隱藏使用者執行緒」**。
> 預設 htop 會把**每一個執行緒都列成一行** ——
> nginx、mysqld、Java 應用可能有幾十甚至上百個執行緒，
> 畫面被洗版，**看不出到底有幾個真正的程序、各吃多少資源**。
> **按 `H` 隱藏後**，每個程序只顯示一行，CPU% 和 RES 是該程序的總和 ——
> 這才是判斷「誰在吃資源」的正確視角。
> **什麼時候要打開**：
> 想知道**某個多執行緒程式是哪個執行緒在忙**時
> （例如 Java 應用的某個 GC 執行緒吃滿一顆 CPU）。
> 相關的還有 **`K`**（顯示/隱藏核心執行緒，那些方括號 `[kworker/0:1]` 之類的）。
> 命令列等價：`top -H`、`ps -eLf`。
>
> **Q9.** **殭屍程序本身殺不掉，也不需要殺** ——
> 它已經是死掉的程序，只剩一個 process table 項目，
> **不占用 CPU 也不占用記憶體**，等著父程序呼叫 `wait()` 來回收退出狀態。
> **正確處理：重啟或修正「父程序」**。
> ```bash
> ps -eo pid,ppid,state,cmd | awk '$3=="Z"'    # ★ 找殭屍
>   9876   1234 Z  [php] <defunct>
> ps -p 1234 -o pid,cmd                         # ★★ 找它的父程序
>   1234 /usr/bin/supervisord
> sudo systemctl restart supervisor             # ★★★ 重啟父程序
> ```
> 父程序死掉後殭屍會被 **init/systemd（PID 1）接管並回收**。
> **少量殭屍是正常的**（父程序還沒來得及 `wait()`）；
> **大量且持續增加 = 父程序有 bug**，
> 累積到 PID 用盡時系統就 fork 不出新程序了。
> 容器內的 PID 1 問題也是同一類（需要 `dumb-init`/`tini`）。
>
> **Q10.** 因為 **程序的完整指令列是所有使用者都讀得到的** ——
> `/proc/<PID>/cmdline` 預設權限是 `r--r--r--`，
> **任何在這台機器上的使用者跑 `ps aux` 或 htop 都看得到密碼**。
> ```bash
> $ ps aux | grep mysql
> root  5678  ... mysql -u root -pMyPassword123      ★★★★ 明文
> ```
> 而且密碼還會進入 **shell history**、**auditd 日誌**、**監控系統的程序快照**。
> **三個正確做法**（安全性由高到低）：
> ①**`mysql -u root -p`** 互動輸入（最安全）；
> ②**`--defaults-file=~/.my.cnf`** 放在權限 600 的檔案裡；
> ③`MYSQL_PWD="$pass" mysql -u root`（環境變數，但仍會出現在 `/proc/PID/environ`，
> 只是那個檔案預設只有同一個使用者和 root 讀得到，比 cmdline 好一些）。
> **多租戶環境的額外防護**：
> `mount -o remount,hidepid=2,gid=adm /proc` 讓使用者只看得到自己的程序。
