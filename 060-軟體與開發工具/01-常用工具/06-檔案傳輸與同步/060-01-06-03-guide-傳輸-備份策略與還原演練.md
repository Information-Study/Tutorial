## ★★★★ 3-2-1 原則

```
★★★★ 3-2-1 是備份的基本法則：

  ★★★ 3 份資料
    → 正式資料 + 2 份備份

  ★★★ 2 種不同的媒體/儲存
    → 例如：本機磁碟 + NAS；或 磁碟 + 磁帶；或 本地 + 雲端物件儲存
    → ★★ 目的：避免同一種媒體的共同故障模式

  ★★★★ 1 份異地
    → 火災、水災、竊盜、★★★ 整棟樓斷電
    → ★★★ 「異地」不是同一個機房的另一個機櫃

★★★★ 現代的延伸：3-2-1-1-0

  ★★★★ +1  一份【離線或不可變】的備份
    → 勒索軟體會【主動搜尋並加密網路上的備份】
    → ★★★★ 連得到 = 可能被加密
    → 離線磁帶、WORM 物件儲存、有 immutability 的快照

  ★★★★ +0  零錯誤
    → ★★★ 【定期驗證】備份可以還原
    → ★★★★ 沒有驗證過的備份 = 沒有備份
```

```
★★★ 實務上的三層架構：

  ┌────────────────────────────────────────────────────┐
  │ ★★★ 第一層：本機快照（RPO 1 小時，RTO 5 分鐘）      │
  │   · rsync --link-dest 硬連結快照 / ZFS snapshot     │
  │   · 保留 7~30 天                                    │
  │   · ★★★★ 用途：誤刪、誤改的【快速】復原              │
  │   · ★★★ 限制：磁碟壞了就沒了                        │
  └────────────────────────────────────────────────────┘
                        ↓
  ┌────────────────────────────────────────────────────┐
  │ ★★★ 第二層：內網備份機（RPO 24 小時，RTO 1 小時）   │
  │   · 不同的實體機器 + 不同的磁碟                      │
  │   · 保留 30~90 天                                   │
  │   · ★★★ 用途：主機故障、磁碟損毀                     │
  │   · ★★★★ 限制：同一個機房 → 火災就一起沒            │
  └────────────────────────────────────────────────────┘
                        ↓
  ┌────────────────────────────────────────────────────┐
  │ ★★★★ 第三層：異地 + 不可變（RPO 24h，RTO 4~24h）    │
  │   · 另一個機房 / 雲端物件儲存 / 離線磁帶              │
  │   · ★★★★ 加密 + WORM / 版本鎖定                     │
  │   · 保留 90 天 ~ 7 年（★ 依法規）                    │
  │   · ★★★★ 用途：災難、勒索軟體、法規稽核             │
  └────────────────────────────────────────────────────┘
```

## ★★★★ RPO 與 RTO

```
★★★★ 這兩個名詞決定你的備份策略：

  ★★★★ RPO（Recovery Point Objective，復原點目標）
    → 「可以接受【損失多久】的資料？」
    → ★★★ 決定【備份頻率】

    RPO = 24 小時  →  每天備份一次（★ 最多損失一天的資料）
    RPO = 1 小時   →  每小時備份 / 或用資料庫的 binlog
    RPO ≈ 0        →  ★★★ 同步複寫 / 資料庫主從即時複製

  ★★★★ RTO（Recovery Time Objective，復原時間目標）
    → 「服務中斷【多久】之內必須恢復？」
    → ★★★ 決定【還原方式與備援架構】

    RTO = 24 小時  →  從備份還原就好
    RTO = 1 小時   →  ★★ 要有熱備機或現成的還原環境
    RTO = 5 分鐘   →  ★★★ 要有高可用架構（★ 備份救不了你）
```

```
★★★★ 不同系統的建議值（機關環境）：

  ┌──────────────────┬─────────┬─────────┬──────────────────────┐
  │ 系統             │ RPO     │ RTO     │ ★ 做法               │
  ├──────────────────┼─────────┼─────────┼──────────────────────┤
  │ ★★★ 對外服務網站  │ 1 小時  │ 1 小時  │ 資料庫主從 + 每小時快照│
  │ ★★★ 內部業務系統  │ 24 小時 │ 4 小時  │ 每日備份 + 熱備機      │
  │ ★★ 檔案伺服器     │ 24 小時 │ 8 小時  │ 每日快照              │
  │ ★★ 開發/測試環境  │ 1 週    │ 1 天    │ 每週備份（★ 或不備份） │
  │ ★★★★ 憑證/金鑰    │ 立即    │ 立即    │ ★★★ 多份離線副本      │
  │ ★★★★ 設定檔       │ 每次變更│ 5 分鐘  │ ★★★ Git 版控          │
  └──────────────────┴─────────┴─────────┴──────────────────────┘

★★★★ 關鍵觀念：
  RTO 很短（分鐘級）→ 【備份解決不了】，需要 HA 架構
  → ★★★ 備份是為了「資料不遺失」，不是為了「服務不中斷」
```

```bash
# ★★★ 實測你的 RTO（★ 很多人從來沒測過）
$ time sudo restore-drill /srv/backup/app/latest
real    12m34.567s                    # ★★★ 這就是你的實際 RTO 下限
#   → ★★★★ 加上「發現問題 + 決策 + 準備環境」的時間才是真正的 RTO

# ★★ 分解各階段
$ time rsync -aAXH /srv/backup/app/latest/ /restore/      # 檔案還原
real    8m12.334s
$ time zcat /backup/db/app-2026-08-28.sql.gz | mysql app  # ★★★ 資料庫還原
real    24m18.902s                    # ★★★★ 通常這個最久！
```

## ★★★ 該備份什麼

```
★★★★ 「全部備份」是錯的 —— 會讓備份太大、太慢、太貴

  ┌─────────────────────────────────────────────────────┐
  │ ★★★★ 一定要備份                                      │
  ├─────────────────────────────────────────────────────┤
  │ · ★★★★ 資料庫（★ 用 dump 或一致性快照，不是複製檔案）│
  │ · ★★★★ 使用者上傳的檔案（storage/app、uploads）      │
  │ · ★★★★ 憑證與私鑰（★ 但要加密！）                    │
  │ · ★★★ 設定檔（/etc 的相關部分）                      │
  │ · ★★★ 應用程式的 .env（★ 加密保存）                  │
  │ · ★★ crontab、systemd unit                          │
  │ · ★★★ 資料庫的 binlog（★ 做 PITR 時）                │
  └─────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────┐
  │ ★★★ 不需要備份（★ 可以重建）                          │
  ├─────────────────────────────────────────────────────┤
  │ · ★★★★ 程式碼 → 【在 Git 裡】                        │
  │ · ★★★★ vendor/ node_modules/ → composer/npm 重裝     │
  │ · ★★★ 建置產物 dist/ public/build/ → 重新 build       │
  │ · ★★★ 快取 storage/framework/cache、OPcache          │
  │ · ★★ 日誌（★ 除非有稽核需求 → 送到集中式日誌）        │
  │ · ★★ 系統套件 → 用 Ansible 重建                      │
  │ · session 檔案                                       │
  └─────────────────────────────────────────────────────┘

★★★★ 判斷準則：
  「這個東西能不能用一個指令重建？」
    能  → 不用備份（★ 但要備份【重建的方法】= Ansible/Dockerfile）
    不能 → ★★★★ 一定要備份
```

```bash
# ★★★ 檢查你的備份涵蓋率
$ sudo tee /usr/local/bin/backup-coverage >/dev/null <<'EOF'
#!/usr/bin/env bash
# ★★★ 檢查關鍵資料是否都在備份中
BACKUP="${1:?用法: backup-coverage <備份目錄>}"
echo "═══ 備份涵蓋率檢查 ═══"

check() {
    local desc="$1" pattern="$2"
    if find "$BACKUP" -path "*$pattern*" -print -quit 2>/dev/null | grep -q .; then
        printf "  ✓ %-40s\n" "$desc"
    else
        printf "  ★★★★ 缺少: %-32s (%s)\n" "$desc" "$pattern"
    fi
}

check "資料庫 dump"        "*.sql.gz"
check "使用者上傳"          "storage/app"
check "應用設定 .env"       ".env"
check "Nginx 設定"          "nginx"
check "TLS 憑證"            "letsencrypt"
check "crontab"             "crontabs"
check "systemd units"       "systemd/system"

echo -e "\n★★★ 不該出現在備份中的："
for bad in node_modules vendor 'storage/framework/cache' 'public/build'; do
    n=$(find "$BACKUP" -path "*$bad*" -type f 2>/dev/null | wc -l)
    [ "$n" -gt 0 ] && printf "  ★★★ %s: %s 個檔案（★ 浪費空間）\n" "$bad" "$n"
done
EOF
$ sudo chmod +x /usr/local/bin/backup-coverage
$ sudo backup-coverage /srv/backup/app/latest
```

## ★★★★ 資料庫的一致性備份

```
★★★★ 最常見的錯誤：直接 rsync 資料庫的資料目錄

  $ rsync -av /var/lib/mysql/ /backup/mysql/     ← ★★★★ 錯！

  ★★★ 為什麼不行：
    · 資料庫在寫入時，檔案處於【不一致的中間狀態】
    · InnoDB 的資料分散在 ibdata、.ibd、redo log 中
    · ★★★★ 複製到的可能是「A 表已更新、B 表還沒」的狀態
    · → 還原後【資料庫損毀或資料不一致】

  ★★★★ 三種正確做法：
    ① 邏輯備份（mysqldump / pg_dump）  ★★★ 最通用
    ② 一致性快照（LVM/ZFS + FLUSH TABLES WITH READ LOCK）
    ③ ★★★ 物理備份工具（XtraBackup / pg_basebackup）
```

```bash
# ═══ ★★★★【MySQL】邏輯備份 ═══
$ mysqldump \
    --single-transaction \        # ★★★★ InnoDB 的一致性快照（不鎖表）
    --routines \                  # ★★★ 預存程序與函式
    --triggers \                  # ★★★ 觸發器
    --events \                    # ★★ 排程事件
    --no-tablespaces \            # ★★ 避免需要 PROCESS 權限
    --hex-blob \                  # ★★ 二進位資料正確編碼
    --default-character-set=utf8mb4 \
    --master-data=2 \             # ★★★★ 記錄 binlog 位置（★ 做 PITR 用）
    --databases app \
    | gzip -6 > "/backup/db/app-$(date +%F-%H%M%S).sql.gz"

#   ★★★★ --single-transaction 的限制：
#     · 只對 InnoDB 有效（★ MyISAM 仍會不一致）
#     · ★★★ 過程中不能有 DDL（ALTER TABLE 等）

# ★★★ 驗證 dump 完整
$ gzip -t /backup/db/app-2026-08-28.sql.gz && echo "★ 壓縮完整"
$ zcat /backup/db/app-2026-08-28.sql.gz | tail -1
-- Dump completed on 2026-08-28 18:30:11
#   ★★★★ 一定要看到 "Dump completed"（★ 沒有就是中斷了）

$ zcat /backup/db/app-2026-08-28.sql.gz | head -30 | grep -E 'MySQL dump|CHANGE MASTER'
-- MySQL dump 10.13  Distrib 8.0.39
-- CHANGE MASTER TO MASTER_LOG_FILE='binlog.000142', MASTER_LOG_POS=48210;
#   ★★★★ 這個位置是 PITR 的起點

# ═══ ★★★ PITR（Point-In-Time Recovery）═══
#   ★★★ 開啟 binlog
$ sudo tee -a /etc/mysql/mysql.conf.d/mysqld.cnf <<'EOF'
log_bin = /var/log/mysql/binlog
binlog_expire_logs_seconds = 604800     # ★★ 保留 7 天
binlog_format = ROW                     # ★★★ ROW 最安全
sync_binlog = 1                         # ★★★ 每次交易都寫入磁碟
EOF
$ sudo systemctl restart mysql

#   ★★★ 備份 binlog
$ sudo rsync -av /var/log/mysql/binlog.* /backup/binlog/

#   ★★★★ 還原到特定時間點
$ zcat /backup/db/app-2026-08-28.sql.gz | mysql
$ sudo mysqlbinlog \
    --start-position=48210 \
    --stop-datetime='2026-08-28 14:23:00' \
    /backup/binlog/binlog.000142 /backup/binlog/binlog.000143 | mysql
#   ★★★★ 這樣可以還原到「誤刪資料的前一秒」

# ═══ ★★★【PostgreSQL】═══
$ pg_dump -Fc -Z6 -f "/backup/db/app-$(date +%F).dump" app
#   -Fc  ★★★ custom 格式（★ 可以平行還原、可以選擇性還原）
$ pg_dump -Fd -j 4 -f "/backup/db/app-$(date +%F)" app    # ★★ 平行 dump

#   ★★★ 全部（含角色與表空間）
$ pg_dumpall --globals-only > /backup/db/globals.sql
$ pg_dumpall | gzip > "/backup/db/all-$(date +%F).sql.gz"

#   ★★★★ 物理備份 + WAL 歸檔（★ 支援 PITR）
$ sudo -u postgres pg_basebackup -D /backup/pgbase -Ft -z -P -Xs
#   postgresql.conf:
#     archive_mode = on
#     archive_command = 'test ! -f /backup/wal/%f && cp %p /backup/wal/%f'

# ═══ ★★★ 一致性快照（LVM / ZFS）═══
$ mysql -e "FLUSH TABLES WITH READ LOCK; FLUSH LOGS;" &
$ sleep 1
$ sudo lvcreate -L 10G -s -n mysql-snap /dev/vg0/mysql
$ mysql -e "UNLOCK TABLES;"
$ sudo mount -o ro /dev/vg0/mysql-snap /mnt/snap
$ sudo rsync -av /mnt/snap/ /backup/mysql-files/
$ sudo umount /mnt/snap && sudo lvremove -f /dev/vg0/mysql-snap

# ★★★ ZFS 更簡單
$ mysql -e "FLUSH TABLES WITH READ LOCK;" &
$ sudo zfs snapshot tank/mysql@$(date +%F-%H%M)
$ mysql -e "UNLOCK TABLES;"
$ sudo zfs send tank/mysql@2026-08-28 | ssh backup 'zfs recv tank/mysql-backup'
```

> [!danger] 資料庫備份的五個常見失誤 ★★★★
> ```
> ① ★★★★ 直接 rsync 資料目錄 → 還原後資料庫損毀
> ② ★★★★ 沒驗證 dump 完整 → 檔案只有 2KB（★ 權限錯誤的錯誤訊息）
>    → ★★★ 一定要 gzip -t + 檢查 "Dump completed"
> ③ ★★★ 忘記 --routines --triggers → 還原後預存程序全沒了
> ④ ★★★★ 密碼寫在指令列 → ps aux 看得到
>    → ★★★ 用 ~/.my.cnf（chmod 600）或 MYSQL_PWD
> ⑤ ★★★★ 從來沒試過還原 → 需要時才發現格式不對/版本不相容
> ```

```bash
# ★★★ 安全的憑證處理
$ sudo tee /root/.my.cnf >/dev/null <<'EOF'
[client]
user=backup
password=很長的隨機密碼
EOF
$ sudo chmod 600 /root/.my.cnf

$ sudo mysqldump --single-transaction --routines --triggers app | gzip > backup.sql.gz
#   ★★★ 不用在指令列打密碼

# ★★★ 備份專用的最小權限帳號
$ sudo mysql <<'EOF'
CREATE USER 'backup'@'localhost' IDENTIFIED BY '很長的隨機密碼';
GRANT SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER, RELOAD,
      REPLICATION CLIENT ON *.* TO 'backup'@'localhost';
FLUSH PRIVILEGES;
EOF
#   ★★★★ 不要用 root 做備份
```

## ★★★★ 不可變備份與勒索軟體

```
★★★★ 勒索軟體的行為模式：

  ① 入侵 → 潛伏（★★ 平均 30~90 天）
  ② ★★★★ 【主動搜尋並加密/刪除備份】
     · 掃描網路芳鄰、掛載的磁碟
     · ★★★ 用竊取的憑證登入備份伺服器
     · ★★★★ 刪除 VSS 快照、雲端備份的舊版本
  ③ 加密正式資料 → 勒索

★★★★ 結論：
  【連得到的備份 = 可能被加密的備份】

★★★★ 四種防護：

  ① ★★★★ 【離線備份】（air-gapped）
     → 磁帶、外接硬碟（★ 備份完就拔掉）
     → ★★★ 最可靠，但 RTO 長

  ② ★★★★ 【不可變儲存】（WORM / immutability）
     → S3 Object Lock、MinIO 的 retention
     → ★★★ 設定期間內【任何人都刪不掉】（含 root）

  ③ ★★★★ 【拉取式備份】（pull-based）
     → ★★★ 備份伺服器【主動去拉】，來源機沒有備份機的憑證
     → ★★★★ 來源被入侵時，攻擊者【沒有路徑】到備份機

  ④ ★★★ 【只能寫入的憑證】
     → rrsync -wo（write-only）
     → ★★ 即使憑證外洩也只能新增，不能刪改
```

```bash
# ═══ ★★★★ 拉取式備份（★ 最實用的防護）═══

# ★★★ 在【備份伺服器】上設定（★ 不是在來源機）
$ sudo -u backup ssh-keygen -t ed25519 -f /home/backup/.ssh/id_pull -N ''

# ★★★ 在【來源機】上放公鑰，限制成唯讀
$ cat >> /home/backupsrc/.ssh/authorized_keys <<'EOF'
command="/usr/local/bin/rrsync -ro /",restrict,from="10.10.20.50" ssh-ed25519 AAAA... backup@backup01
EOF
#   ★★★★ -ro = read-only（★ 備份機只能【讀】來源）
#   ★★★★ from= 限制只有備份機能用這把金鑰

# ★★★ 備份伺服器主動拉
$ sudo -u backup rsync -aAXH --numeric-ids \
    --link-dest="/srv/backup/app/$(ls -1t /srv/backup/app | head -1)" \
    -e 'ssh -i /home/backup/.ssh/id_pull' \
    backupsrc@10.10.20.31:/var/www/app/ \
    "/srv/backup/app/$(date +%F-%H%M%S)/"

#   ★★★★ 關鍵：來源機【沒有】任何能寫入備份機的憑證
#     → 來源被勒索軟體入侵，攻擊者也【找不到路徑】到備份

# ═══ ★★★★ 不可變的物件儲存（MinIO / S3）═══
$ mc alias set backup https://s3.internal.example.gov.tw ACCESS SECRET
$ mc mb backup/app-backup --with-lock                 # ★★★★ 建立時就要啟用
$ mc retention set --default GOVERNANCE 90d backup/app-backup
#   ★★★ GOVERNANCE：有特殊權限的人可以覆寫

## ★★★★ 還原演練

```
★★★★ 「沒有驗證過的備份 = 沒有備份」

★★★ 常見的失敗（★ 都是在真正需要時才發現）：
  · 備份任務「成功」但檔案是空的
  · 資料庫 dump 只有一行錯誤訊息（★ 權限問題）
  · 加密的備份沒有金鑰
  · 備份的版本和現在的系統不相容
  · ★★★ 排除規則太寬，關鍵資料沒備到
  · ★★★★ 還原要 8 小時，但 RTO 是 4 小時
  · 還原程序沒有人知道怎麼跑（★ 寫程序的人離職了）
```

```bash
#!/usr/bin/env bash
# ★★★★ /usr/local/bin/restore-drill —— 完整的還原演練
set -uo pipefail

SNAP="${1:?用法: restore-drill <備份快照路徑>}"
DRILL_DIR=$(mktemp -d /srv/drill/drill.XXXXXX)
DRILL_DB="drill_$(date +%s)"
LOG=/var/log/restore-drill.log
START=$(date +%s)
FAIL=0

log() { printf '%s %s\n' "$(date '+%F %T')" "$*" | tee -a "$LOG"; }
cleanup() {
    log "【清理】"
    rm -rf "$DRILL_DIR"
    mysql -e "DROP DATABASE IF EXISTS \`$DRILL_DB\`" 2>/dev/null || true
}
trap cleanup EXIT

log "═══ 還原演練開始: $SNAP ═══"

# ═══ ★★★【1】檔案還原 ═══
log "【1】檔案還原"
T0=$(date +%s)
if rsync -aAXH --numeric-ids "$SNAP/" "$DRILL_DIR/" >>"$LOG" 2>&1; then
    T_FILES=$(( $(date +%s) - T0 ))
    log "  ★ 完成，耗時 ${T_FILES}s"
else
    log "  ★★★★ 檔案還原失敗"
    exit 1
fi

# ═══ ★★★【2】檔案完整性 ═══
log "【2】檔案完整性"
FILES=$(find "$DRILL_DIR" -type f | wc -l)
SIZE=$(du -sh "$DRILL_DIR" | cut -f1)
log "  檔案數: $FILES，大小: $SIZE"
[ "$FILES" -gt 100 ] || { log "  ★★★★ 檔案數異常偏低"; FAIL=$((FAIL+1)); }

#   ★★★ 關鍵檔案存在嗎
for f in current/artisan current/composer.json current/public/index.php; do
    if [ -e "$DRILL_DIR/$f" ]; then
        log "  ✓ $f"
    else
        log "  ★★★★ 缺少關鍵檔案: $f"
        FAIL=$((FAIL+1))
    fi
done

# ═══ ★★★★【3】資料庫還原 ═══
log "【3】★★★★ 資料庫還原"
DUMP=$(find "$SNAP" -name '*.sql.gz' -type f 2>/dev/null | sort | tail -1)
if [ -z "$DUMP" ]; then
    log "  ★★★★ 找不到資料庫 dump！"
    FAIL=$((FAIL+1))
else
    log "  dump: $(basename "$DUMP") ($(du -h "$DUMP" | cut -f1))"

    #   ★★★ 壓縮完整性
    if gzip -t "$DUMP" 2>/dev/null; then
        log "  ✓ 壓縮完整"
    else
        log "  ★★★★ 壓縮損毀！"
        FAIL=$((FAIL+1))
    fi

    #   ★★★★ dump 是否完整結束
    if zcat "$DUMP" | tail -3 | grep -q 'Dump completed'; then
        log "  ✓ dump 完整結束"
    else
        log "  ★★★★ dump 沒有正常結束（可能中斷）"
        FAIL=$((FAIL+1))
    fi

    #   ★★★★ 實際還原
    T0=$(date +%s)
    mysql -e "CREATE DATABASE \`$DRILL_DB\` CHARACTER SET utf8mb4"
    if zcat "$DUMP" | sed "s/^USE \`[^\`]*\`;/USE \`$DRILL_DB\`;/" | \
         mysql "$DRILL_DB" 2>>"$LOG"; then
        T_DB=$(( $(date +%s) - T0 ))
        log "  ★ 資料庫還原完成，耗時 ${T_DB}s"

        #   ★★★★ 資料驗證
        TABLES=$(mysql -N -e "SELECT COUNT(*) FROM information_schema.tables
                              WHERE table_schema='$DRILL_DB'")
        log "  資料表數: $TABLES"
        [ "$TABLES" -gt 0 ] || { log "  ★★★★ 沒有任何資料表！"; FAIL=$((FAIL+1)); }

        #   ★★★ 抽查關鍵表的筆數
        for t in users orders; do
            n=$(mysql -N -e "SELECT COUNT(*) FROM \`$DRILL_DB\`.\`$t\`" 2>/dev/null || echo "N/A")
            log "  $t: $n 筆"
            [ "$n" = "N/A" ] && { log "  ★★★ 表 $t 不存在"; FAIL=$((FAIL+1)); }
        done

        #   ★★★ 預存程序與觸發器
        R=$(mysql -N -e "SELECT COUNT(*) FROM information_schema.routines
                         WHERE routine_schema='$DRILL_DB'")
        T=$(mysql -N -e "SELECT COUNT(*) FROM information_schema.triggers
                         WHERE trigger_schema='$DRILL_DB'")
        log "  預存程序: $R，觸發器: $T"
    else
        log "  ★★★★ 資料庫還原失敗！"
        FAIL=$((FAIL+1))
    fi
fi

# ═══ ★★★【4】應用程式層驗證 ═══
log "【4】應用程式驗證"
if [ -f "$DRILL_DIR/current/artisan" ]; then
    #   ★★ 需要 .env 才能跑
    if [ -f "$DRILL_DIR/shared/.env" ]; then
        log "  ✓ .env 存在"
    else
        log "  ★★★★ 缺少 .env（★ 可能被 exclude 了，但還原時需要）"
        FAIL=$((FAIL+1))
    fi

    if php "$DRILL_DIR/current/artisan" --version >/dev/null 2>&1; then
        log "  ✓ artisan 可執行"
    else
        log "  ★★★ artisan 執行失敗（★ 可能缺 vendor/）"
    fi
fi

[ -f "$DRILL_DIR/current/composer.json" ] && {
    jq -e . "$DRILL_DIR/current/composer.json" >/dev/null 2>&1 \
      && log "  ✓ composer.json 有效" \
      || { log "  ★★★ composer.json 損毀"; FAIL=$((FAIL+1)); }
}

# ═══ ★★★【5】上傳檔案抽樣 ═══
log "【5】使用者上傳檔案"
UPLOAD_DIR="$DRILL_DIR/shared/storage/app"
if [ -d "$UPLOAD_DIR" ]; then
    N=$(find "$UPLOAD_DIR" -type f | wc -l)
    log "  上傳檔案數: $N"
    #   ★★★ 抽樣檢查檔案沒有損毀
    find "$UPLOAD_DIR" -type f -size +1k 2>/dev/null | shuf -n 5 | while read -r f; do
        if file "$f" | grep -qE 'empty|data$'; then
            log "  ★★★ 可疑檔案: $(basename "$f")"
        fi
    done
else
    log "  ★★★★ 沒有 storage/app！使用者上傳的檔案沒備份到"
    FAIL=$((FAIL+1))
fi

# ═══ ★★★★【6】RTO 評估 ═══
TOTAL=$(( $(date +%s) - START ))
log "【6】★★★★ RTO 評估"
log "  總耗時: ${TOTAL}s ($((TOTAL/60)) 分鐘)"
log "  · 檔案還原: ${T_FILES:-?}s"
log "  · 資料庫還原: ${T_DB:-?}s"
log "  ★★★ 實際 RTO 還要加上：發現問題 + 決策 + 準備環境 + 切換 DNS"
log "  ★★★★ 建議以 $((TOTAL/60 * 3)) 分鐘作為 RTO 的規劃基準"

# ═══ 【7】結論 ═══
if [ "$FAIL" -eq 0 ]; then
    log "═══ ★ 還原演練通過 ═══"
    echo "$(date -Is)|PASS|$SNAP|${TOTAL}s|$FILES 檔案|$TABLES 表" >> /var/log/restore-drill-history.log
else
    log "═══ ★★★★ 還原演練發現 $FAIL 項問題 ═══"
    echo "$(date -Is)|FAIL($FAIL)|$SNAP|${TOTAL}s" >> /var/log/restore-drill-history.log
fi
exit "$FAIL"
```

## 安全性注意事項

> [!danger] 六個要點 ★★★★
> ```
> ① ★★★★ 備份含【所有】資料 = 最高機密
>      → 備份目錄 700、加密異地備份
>      → ★★★ 備份伺服器的安全等級要【等同或高於】正式機
>
> ② ★★★★ 勒索軟體會攻擊備份
>      → 拉取式 + 不可變儲存 + 離線副本
>      → ★★★ 來源機不應該有寫入備份的憑證
>
> ③ ★★★★ 金鑰異地保存
>      → 至少 2 份，其中一份離線（紙本/保險箱）
>      → ★★★ 每季驗證能不能用
>
> ④ ★★★ 備份帳號最小權限
>      → 資料庫用專用帳號（SELECT/LOCK TABLES/RELOAD）
>      → ★★★ SSH 用 rrsync 限制
>
> ⑤ ★★★ 保留期限與銷毀
>      → 個資有保存期限（★ 個資法）
>      → ★★ 過期的備份要【安全銷毀】（shred / 加密磁碟直接毀金鑰）
>
> ⑥ ★★★ 備份的存取要有稽核記錄
>      → 誰在什麼時候還原了什麼
> ```

```bash
# ★★★★ 備份伺服器的加固檢查
$ sudo tee /usr/local/bin/backup-security-audit >/dev/null <<'EOF'
#!/usr/bin/env bash
echo "═══ 備份安全稽核 $(date '+%F %T') ═══"
FAIL=0

chk() { printf '  %-46s ' "$1"; shift
        if eval "$@" >/dev/null 2>&1; then echo "✓"; else echo "★★★★ 失敗"; FAIL=$((FAIL+1)); fi; }

echo -e "\n【權限】"
chk "備份目錄權限 700" '[ "$(stat -c %a /srv/backup)" = "700" ]'
chk "備份目錄由 root 擁有" '[ "$(stat -c %U /srv/backup)" = "root" ]'
chk "金鑰檔權限 600" '[ "$(stat -c %a /etc/backup-age.key)" = "600" ]'

echo -e "\n【★★★★ 機密外洩】"
chk "備份中沒有未加密的 .env" \
    '! find /srv/backup -name ".env" -type f | grep -q .'
chk "備份中沒有未加密的私鑰" \
    '! find /srv/backup \( -name "*.pem" -o -name "id_rsa" -o -name "id_ed25519" \) -type f | grep -q .'

echo -e "\n【★★★★ 勒索軟體防護】"
chk "來源機沒有備份機的寫入金鑰" \
    '! grep -rl "backup01" /home/*/.ssh/id_* 2>/dev/null | grep -q .'
chk "備份用的 authorized_keys 有 command 限制" \
    'grep -q "command=" /home/backup/.ssh/authorized_keys'
chk "備份用的 authorized_keys 有 restrict" \
    'grep -q "restrict" /home/backup/.ssh/authorized_keys'

echo -e "\n【新鮮度】"
chk "今天有新的備份" \
    'find /srv/backup/app -maxdepth 1 -type d -name "2*" -mtime -1 | grep -q .'
chk "遠端今天有新的備份" \
    'ssh -o BatchMode=yes backup01 "find /srv/backup/app -maxdepth 1 -mtime -1 | grep -q ." '

echo -e "\n【★★★★ 演練】"
LAST=$(tail -1 /var/log/restore-drill-history.log 2>/dev/null | cut -d'|' -f1)
if [ -n "$LAST" ]; then
    DAYS=$(( ($(date +%s) - $(date -d "$LAST" +%s)) / 86400 ))
    printf '  %-46s ' "最後一次演練距今 $DAYS 天"
    [ "$DAYS" -lt 100 ] && echo "✓" || { echo "★★★★ 超過一季未演練"; FAIL=$((FAIL+1)); }
else
    echo "  ★★★★ 從來沒有做過還原演練！"
    FAIL=$((FAIL+1))
fi

echo -e "\n【空間】"
U=$(df --output=pcent /srv/backup | tail -1 | tr -dc '0-9')
I=$(df -i --output=ipcent /srv/backup | tail -1 | tr -dc '0-9')
printf '  磁碟使用率 %s%%  inode 使用率 %s%%  ' "$U" "$I"
{ [ "$U" -lt 85 ] && [ "$I" -lt 85 ]; } && echo "✓" || { echo "★★★★ 偏高"; FAIL=$((FAIL+1)); }

echo ""
[ "$FAIL" -eq 0 ] && echo "★ 全部通過" || echo "★★★★ $FAIL 項需要處理"
exit "$FAIL"
EOF

EOF

Q4. **`mysqldump` 之後要做哪兩個完整性驗證**？

Q5. **勒索軟體怎麼攻擊備份**？四種防護？

Q6. **「拉取式備份」為什麼比推送式安全**？

Q7. **加密備份最大的風險是什麼**？怎麼防護？

Q8. **哪些東西不需要備份**？判斷準則是什麼？

Q9. **還原演練有哪四個層級**？該多久做一次？

Q10. **「備份成功」的訊息為什麼不能信**？該檢查什麼？

> [!question]- 測驗答案
> **Q1.** **3-2-1 = 3 份資料、2 種不同的媒體/儲存、1 份異地**。
> **3 份** = 正式資料 + 2 份備份；
> **2 種媒體** = 避免同一種媒體的共同故障模式（同批磁碟同時壞掉）；
> **1 份異地** = 防火災、水災、竊盜、整棟樓斷電
> （「異地」不是同一機房的另一個機櫃）。
> **★★★★ 現代延伸為 3-2-1-1-0**：
> **`+1` = 一份離線或不可變的備份** ——
> 因為**勒索軟體會主動搜尋並加密網路上的備份**，
> **連得到的備份就是可能被加密的備份**；
> **`+0` = 零錯誤** —— **定期驗證備份可以還原**，
> **沒有驗證過的備份等於沒有備份**。
> 這兩個延伸都是從真實的災難案例學來的。
>
> **Q2.** **RPO（Recovery Point Objective）= 「可以接受損失多久的資料」→ 決定備份頻率**。
> RPO 24 小時就每天備份一次；RPO 1 小時就每小時備份或用 binlog；
> RPO 接近 0 就需要同步複寫或資料庫主從即時複製。
> **RTO（Recovery Time Objective）= 「服務中斷多久之內必須恢復」→ 決定還原方式與架構**。
> **★★★★ RTO 5 分鐘的話，備份完全解決不了** ——
> 光是還原資料庫可能就要 20 分鐘。
> **必須用高可用架構**：資料庫主從自動切換、
> 多台應用伺服器 + 負載平衡、健康檢查自動移除故障節點。
> **關鍵觀念：備份是為了「資料不遺失」，不是為了「服務不中斷」** ——
> 這兩件事需要不同的方案。
> **實測方式**：演練時計時，那才是真正的 RTO 下限。
>
> **Q3.** 因為 **資料庫在執行時，磁碟上的檔案處於「不一致的中間狀態」**。
> InnoDB 的資料分散在 `ibdata`、各表的 `.ibd`、**redo log**、undo log 中，
> 一筆交易可能「已經寫進 redo log 但還沒 flush 到資料檔」。
> **rsync 掃描檔案需要時間** —— 掃到 A 表時是 10:00 的狀態，
> 掃到 B 表時已經是 10:05 了，**中間發生的交易讓兩者對不上**。
> **還原後的結果是資料庫損毀或資料不一致**（外鍵指向不存在的紀錄）。
> **三種正確做法**：
> ①**邏輯備份**：`mysqldump --single-transaction`（InnoDB 的一致性快照，不鎖表）；
> ②**一致性快照**：`FLUSH TABLES WITH READ LOCK` + LVM/ZFS 快照；
> ③**物理備份工具**：Percona XtraBackup、`pg_basebackup`。
>
> **Q4.** ①**★★★ 壓縮完整性**：
> ```bash
> gzip -t /backup/db/app-2026-08-28.sql.gz && echo "壓縮完整"
> ```
> 這能抓到「傳輸中斷」「磁碟寫滿」造成的截斷。
> ②**★★★★ dump 是否正常結束**：
> ```bash
> zcat app.sql.gz | tail -3 | grep -q 'Dump completed' || echo "★★★★ 中斷了"
> ```
> **mysqldump 正常結束時最後一行一定是 `-- Dump completed on ...`**。
> **為什麼這個特別重要**：
> **權限不足時 mysqldump 會產生一個「只有錯誤訊息」的小檔案**，
> 而 shell 的 exit code 可能因為管線（`| gzip`）而看不出來，
> 備份腳本會回報「成功」——
> 直到需要還原時才發現那是一個 2KB 的垃圾檔。
> **加碼檢查**：檔案大小是否在合理範圍（和昨天比對）。
>
> **Q5.** **勒索軟體的行為模式**：
> 入侵後**潛伏 30~90 天**，這期間**主動搜尋並破壞備份** ——
> 掃描網路芳鄰與掛載的磁碟、
> **用竊取的憑證登入備份伺服器刪除備份**、
> 刪除 Windows 的 VSS 快照、刪除雲端備份的舊版本 ——
> **確認你無法還原之後**，才開始加密正式資料並勒索。
> **四種防護**：
> ①**★★★★ 離線備份**（air-gapped）—— 磁帶、備份完就拔掉的外接硬碟；
> ②**★★★★ 不可變儲存** —— S3 Object Lock（COMPLIANCE 模式連 root 都刪不掉）、
> ZFS 的 `zfs hold`、MinIO retention；
> ③**★★★★ 拉取式備份** —— 備份機主動去拉，
> **來源機沒有任何能寫入備份機的憑證**；
> ④**★★★ 只能寫入的憑證** —— `rrsync -wo`，即使外洩也只能新增不能刪改。
>
> **Q6.** 因為 **來源機上沒有任何能存取備份機的憑證**。
> **推送式**（來源機 → 備份機）：來源機必須持有備份機的 SSH 金鑰。
> **來源機被入侵時，攻擊者可以直接拿那把金鑰登入備份機，把備份全部刪掉**。
> **拉取式**（備份機 → 來源機）：
> 金鑰放在**備份機**上，而且在來源機的 `authorized_keys` 中限制成唯讀：
> ```
> command="/usr/local/bin/rrsync -ro /",restrict,from="10.10.20.50" ssh-ed25519 ...
> ```
> **來源機被入侵時，攻擊者在來源機上找不到任何通往備份機的路徑** ——
> 他甚至不知道備份存在哪裡。
> **額外的加固**：`from=` 限制來源 IP、`restrict` 停用所有轉發、
> 備份機本身不對外提供服務、備份機的安全等級要**等同或高於**正式機。
>
> **Q7.** **★★★★ 最大的風險不是被破解，是自己弄丟金鑰**。
> **典型災難**：機房失火 → 主機全毀 → 準備從異地備份還原 →
> **發現金鑰只放在已經燒掉的那台機器上** →
> **備份完好無損，但永遠打不開**。
> **三個防護原則**：
> ①**★★★★ 異地保存至少兩份** —— 保險箱、另一個機房、企業密碼管理器；
> ②**★★★ 紙本也是一種備援** ——
> 印出來封存（適合 root CA 私鑰、restic/borg 的主密碼、age 私鑰），
> 紙不怕勒索軟體也不怕磁碟損毀；
> ③**★★★ 定期驗證** ——
> **還原演練時要用「異地保存的那份金鑰」**，
> 而不是本機的那份，才能確認異地副本真的可用。
> borg 的 `repokey` 模式要記得 `borg key export` 匯出後異地保存。
>
> **Q8.** **不需要備份的**：
> **程式碼**（在 Git 裡）、**`vendor/` 與 `node_modules/`**（composer/npm 重裝）、
> **建置產物**（`dist/`、`public/build/`，重新 build）、
> **快取**（`storage/framework/cache`、OPcache、session）、
> **日誌**（除非有稽核需求 → 送到集中式日誌）、
> **系統套件**（用 Ansible 重建）。
> **★★★★ 判斷準則：「這個東西能不能用一個指令重建？」**
> 能重建就不用備份 —— **但要備份「重建的方法」**
> （Ansible playbook、Dockerfile、`composer.lock`、`package-lock.json`）。
> **不能重建的一定要備份**：資料庫、使用者上傳的檔案、
> 憑證與私鑰（加密）、設定檔、`.env`（加密）。
> 備份 `node_modules` 會讓備份大好幾倍、慢好幾倍，卻毫無價值。
>
> **Q9.** **四個層級**：
> **L1 檔案級** —— 能不能把檔案還原出來？（檔案數、大小、關鍵檔案存在）；
> **L2 資料級** —— 資料庫能不能還原、資料完整嗎？
> （實際 `zcat | mysql`，檢查表數、筆數、預存程序）；
> **L3 服務級** —— **還原後服務能不能正常運作？**
> 在隔離環境啟動完整服務並測試 API；
> **L4 演練級** —— **模擬真實災難的完整流程**：
> 發現 → 通報 → 決策 → 還原 → 驗證 → 切換，**全程計時**。
> **頻率建議**：**L2 每季一次、L4 每年至少一次**。
> **每次演練都要記錄**：耗時（這是你真正的 RTO）、
> 發現的問題、改進事項與負責人、下次演練日期。
> L4 特別重要的是**找出流程中的人為瓶頸**（誰有權限決策、誰知道金鑰在哪）。
>
> **Q10.** 因為 **「備份任務執行完畢沒有報錯」不等於「備份內容可用」**。
> **常見的假成功**：
> ①`mysqldump` 因權限不足只產生一個含錯誤訊息的 2KB 檔案，
> 但因為接了 `| gzip`，**shell 看到的 exit code 是 gzip 的 0**；
> ②rsync 的來源目錄沒掛載，**同步了一個空目錄**（配合 `--delete` 更慘）；
> ③排除規則寫太寬，**關鍵資料整個沒備到**；
> ④磁碟寫滿，備份**截斷在一半**。
> **該檢查的五項**：
> ```bash
> find /srv/backup/latest -type f | wc -l        # ★★ 檔案數合理嗎
> du -sh /srv/backup/latest                       # ★★ 大小和昨天比
> gzip -t /backup/db/*.sql.gz                     # ★★★ 壓縮完整
> zcat dump.sql.gz | tail | grep 'Dump completed' # ★★★★ 正常結束
> backup-coverage /srv/backup/latest              # ★★★ 關鍵檔案都在
> ```
> **最終還是要靠還原演練** —— 只有真的還原出來並跑起來，才算數。
