# 資訊設備維運手冊 — 升級規劃

> [!abstract] 這份文件是什麼
> 把現有的「Linux 系列教學」（197 篇骨架）升級為涵蓋 **資訊設備安裝、部署、設定、優化、維護** 全生命週期的維運手冊。
> 本文件先定案結構與篇章清單，經確認後再執行搬遷與骨架建立。

---

## 一、定位轉變

| | 升級前 | 升級後 |
| --- | --- | --- |
| 定位 | Linux 系列教學 | 資訊設備全生命週期維運手冊 |
| 範圍 | 單機 Linux + Web/DB/容器/部署 | 再加上網路設備、Windows/AD、虛擬化、軟路由、機房硬體、憑證 PKI、維運制度 |
| 讀者 | 想學 Linux 的人 | 負責機關／企業資訊設備的維運人員 |
| 主軸 | 由淺至深學會工具 | **安裝 → 部署 → 設定 → 優化 → 維護** 的循環 |
| 規模 | 197 篇教學 + 40 索引 | 約 **348 篇教學**（新增約 151 篇）+ 約 60 索引 |

不變的部分：Ubuntu/Debian 主線 + RHEL 對照、每篇 12 段章節骨架、frontmatter 規格、
`[[wikilink]]` 交叉引用、`_工具/` 自動化維護腳本。

新增的橫向慣例：

- **網路設備**：Cisco IOS 為主線，Juniper JunOS 以 `> [!info]- Juniper JunOS 對照` 摺疊區塊並列（與現有 RHEL 對照相同寫法）。
- **Windows 主題**：以 GUI 操作步驟為主、PowerShell 指令為輔，兩者並陳。
- **實務表單**：巡檢表、盤點表、變更單等可直接取用的表格，統一放 `_表單範本/`。

## 十二、後續規劃：全 vault 檔名改制（**工作告一段落後才執行**）

> 2026-08-29 使用者指定。**現階段不動**，等內容撰寫告一段落再做。
> 這是全 vault 規模的破壞性操作，必須一次做完、當天驗收完畢。

### 目標命名格式

```
<大章節編號>-<小章節編號>-<文件編號>-<文件類型>-<文件標題>.md
```

目的：在 Obsidian 的檔案總管、快速切換（Ctrl+O）、搜尋結果與 `.base` 表格中，
**光看檔名就知道它屬於哪一章、排第幾、是什麼性質的文件**，且排序天然正確。

### ★★★★ 先解決一個規劃沒涵蓋的問題：目錄有三層也有四層

實測目前 635 個內容檔的層數分布：

| 層數 | 檔數 | 範例 |
| ---: | ---: | --- |
| 2 | 27 | `000-索引/00-首頁.md` |
| 3 | 400 | `010-基礎概論/01-計算機概論/00-計算機概論-索引.md` |
| **4** | **208** | `020-Linux/02-Linux伺服器管理/01-SSH與遠端管理/01-SSH-原理與第一次連線.md` |

**32% 的檔案有第三層資料夾**（子章節），而使用者給的格式只有「大章節-小章節-文件編號」三段。
建議做法：**數字段數跟著資料夾深度走**，四層目錄就多一段編號。

| 深度 | 格式 | 範例（改制後） |
| --- | --- | --- |
| 2 層 | `群組-序-類型-標題` | `000-02-ref-指令速查表.md` |
| 3 層 | `群組-章-序-類型-標題` | `010-02-03-guide-網路分層模型.md` |
| 4 層 | `群組-章-子章-序-類型-標題` | `020-02-01-01-guide-SSH原理與第一次連線.md` |

索引頁一律 `序 = 00`、`類型 = idx`：
`010-01-00-idx-計算機概論.md`、`020-02-01-00-idx-SSH與遠端管理.md`

### 文件類型代碼

沿用 `_工具/新增筆記.py` 既有的 `--kind` 詞彙，另加 `idx`：

| 代碼 | 意義 | 骨架 |
| --- | --- | --- |
| `idx` | 索引／MOC | 導覽 + 篇章列表 |
| `cmd` | 指令教學 | 觀念 → 基礎操作 → 進階用法 |
| `svc` | 服務教學 | 觀念 → 安裝 → 基礎設定 → 調校 |
| `guide` | 觀念與實戰 | 觀念 → 逐步說明 → 實戰 |
| `ref` | 速查頁 | 純速查表 + 小測驗 |

用小寫英文而非中文：長度短、排序穩定、不受 CJK 字寬影響。

### ★★★★★ 這件事的最大風險：wikilink 全斷

**前車之鑑**：上次架構重整只改了群組資料夾編號，就斷了 **166 個** wikilink。
這次要改的是**全部 635 個檔名**，牽動：

1. 內文所有 `[[檔名]]`（約 3000+ 處）
2. **frontmatter `prerequisites` 裡的 wikilink（305 個檔案有）** ← 最容易漏
3. 各層索引頁「篇章列表」表格裡的連結（`重建索引.py` 會重生，但要重跑）
4. `.obsidian/bookmarks.json` 的書籤路徑
5. `_規劃/`、`README.md`、`CLAUDE.md` 裡引用到的路徑字串

**不受影響**：`000-索引/索引查詢資料庫.base` 用的是 `file.name` / `file.folder` 這類泛用欄位，
沒有寫死檔名 —— 改制後它的「依檔名排序」反而會變得更有意義。

### 執行步驟（必須照順序，全程在一個 commit 內完成）

```bash
# 0. 前置：確認乾淨的起點
git status --short          # 必須為空
python3 _工具/檢查連結.py    # 必須 0 個斷連結
python3 _工具/健檢.py        # 必須無問題
git checkout -b rename-scheme   # ★★★★ 開分支做，不要直接動 main

# 1. 產生 舊檔名 → 新檔名 對照表（先只輸出，人工檢查過再執行）
python3 _工具/改制檔名.py --dry-run > /tmp/rename-map.tsv
#    檢查重點：新檔名是否全 vault 唯一、類型判定是否正確、標題是否被截斷

# 2. 實際搬移（用 git mv 保留歷史）
python3 _工具/改制檔名.py --apply

# 3. 依對照表批次改寫所有 wikilink（含 frontmatter 的 prerequisites）
python3 _工具/改制檔名.py --fix-links

# 4. 驗收 —— 三個都要乾淨才算完成
python3 _工具/檢查連結.py    # 必須 0
python3 _工具/重建索引.py
python3 _工具/健檢.py

# 5. 修 bookmarks 與文件中的路徑字串
#    .obsidian/bookmarks.json、README.md、CLAUDE.md、_規劃/手冊升級規劃.md
```

`_工具/改制檔名.py` 尚未撰寫，是本次改制的**第一項工作**。
它要能從路徑推導新檔名、從 frontmatter 的 `type`／骨架特徵推導文件類型、
並產出可人工複核的對照表。

### ★★★ 要先讓使用者知道的代價

改制後 wikilink 會**變長且變難讀**：

```
改制前：[[01-SSH-原理與第一次連線]]
改制後：[[020-02-01-01-guide-SSH原理與第一次連線]]
```

**緩解方式**：本手冊每篇 frontmatter 都有 `aliases`，Obsidian 的 wikilink
可以直接用別名解析。所以日後交叉引用建議寫成：

```
[[SSH 原理與第一次連線]]        ← 用 aliases 裡的名稱，短又好讀
[[020-02-01-01-guide-SSH原理與第一次連線|SSH 原理]]   ← 或用管線指定顯示文字
```

★★★★ 這代表**改制的同時必須確保每篇的 `aliases` 都有一個好用的自然語言名稱**，
否則寫作體驗會明顯變差。這一項要併進改制腳本一起檢查。

### 待使用者確認

   等前綴，在新制下已由編號保證唯一，可以拿掉讓標題更乾淨
