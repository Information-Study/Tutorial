# 資訊設備維運手冊 — 升級規劃

> [!abstract] 這份文件是什麼
> 把現有的「Linux 系列教學」（197 篇骨架）升級為涵蓋 **資訊設備安裝、部署、設定、優化、維護** 全生命週期的維運手冊。
> 本文件先定案結構與篇章清單，經確認後再執行搬遷與骨架建立。

---

## 一、定位轉變

| | 升級前 | 升級後 |
| --- | --- | --- |
| 定位 | Linux 系列教學 | 資訊設備全生命週期維運手冊 |
| 範圍 | 單機 Linux + Web/DB/容器/部署 | 再加上網路設備、Windows/AD、虛擬化、軟路由、機房硬體、憑證 PKI、維運制度 |
| 讀者 | 想學 Linux 的人 | 負責機關／企業資訊設備的維運人員 |
| 主軸 | 由淺至深學會工具 | **安裝 → 部署 → 設定 → 優化 → 維護** 的循環 |
| 規模 | 197 篇教學 + 40 索引 | 約 **348 篇教學**（新增約 151 篇）+ 約 60 索引 |

不變的部分：Ubuntu/Debian 主線 + RHEL 對照、每篇 12 段章節骨架、frontmatter 規格、
`[[wikilink]]` 交叉引用、`_工具/` 自動化維護腳本。

新增的橫向慣例：

- **網路設備**：★★★★ **Juniper JunOS 為主線**（2026-08-29 使用者改定），Cisco IOS 以 `> [!info]- Cisco IOS 對照` 摺疊區塊並列（與現有 RHEL 對照相同寫法）。
- **Windows 主題**：以 GUI 操作步驟為主、PowerShell 指令為輔，兩者並陳。
- **實務表單**：巡檢表、盤點表、變更單等可直接取用的表格，統一放 `_表單範本/`。

### ★★★★ 「依建議學習順序及邏輯順序編號」的可行性與限制

使用者要求**依建議學習順序「及邏輯順序」排序編號**。
實測 85 個索引頁都有 `## 建議閱讀順序`，但它們是**敘述性文字，且多半給出好幾條路線**，例如：

  - 效率向：Bash/Zsh 效率設定 → 現代 CLI 工具集
```

★★★★ **一組線性編號只能表達一種順序，無法同時表達三條路線。**
因此改制時必須為每章**挑一條正規順序（canonical order）**當作編號依據。
使用者指定的兩個排序依據，實務上這樣結合：

1. **建議學習順序優先** —— 以索引頁「必修／主線」那條路線為準

2. **邏輯順序作為決勝與補位** —— 學習路線沒點名、或多條路線互相衝突的篇章，
   改用邏輯順序決定：
   - **依賴在前**：被別篇當作 `prerequisites` 的，排在依賴它的篇章之前
   - **生命週期順序**：概念 → 安裝 → 設定 → 調校 → 備份 → 監控 → 安全強化 → 疑難排解
   - **由淺入深**：`difficulty` 入門 → 進階 → 專家
3. 其餘路線**仍以文字保留在索引頁的「建議閱讀順序」**，用 wikilink 指過去 ——
   讀者照樣能跳著讀，只是檔名順序反映主線。
4. ★★★ 每章的正規順序**改制前要逐章人工確認**，這是本次改制最需要判斷、

### 98 常見故障排除手冊的寫法

**定位**：這不是新的教學，是**查詢用的索引**。維運人員出事時第一個打開的就是它。

結構建議：

```

> [!abstract] 怎麼用這份手冊
> 依「症狀」找，不是依「技術」找。找到症狀 → 看判斷分流 → 點進原文看原理。

## 快速索引（依症狀）
| 症狀 | 最可能的原因 | 先查什麼 | 原理詳見 |
| --- | --- | --- | --- |
| 連不上 SSH，Connection refused | 服務沒起來／埠改了／防火牆 | `ss -ltnp \| grep sshd` | [[…原文…]] |

## 依情境展開
### ★★★★ 情境一：<症狀>
- **現象**：實際會看到的錯誤訊息（逐字）
- **判斷分流**：看到 X 代表 A、看到 Y 代表 B
- **處置步驟**：【1】【2】【3】，附指令與預期輸出
- **原理**：一句話帶過 + `→ 原理詳見 [[原文檔名]]`
- **預防**：怎麼避免再發生

## 一頁式急救卡
出事時先跑的五個指令與判讀

## 延伸閱讀
```

**硬性要求**：

2. 症狀要用**使用者實際會說的話**與**逐字的錯誤訊息**，不要用技術術語當索引

### 4-3 每篇重點大綱

**`110-06-01` LLM 心智模型與提示六大構件（入門）**
1. 用維運人員聽得懂的比喻：一個讀很多手冊、打字很快、記性只到這段對話為止、而且**不會說「我不知道」**的實習生。附「同一問題連問三次得到三種答案」的實測示範
2. 六大構件逐項拆解：角色／任務／脈絡／限制／輸出格式／範例
3. ★★★★★ **脈絡**（發行版、版本、已做過什麼）與**限制**（不可重啟服務、不可動防火牆）是維運提示最常缺、後果最嚴重的兩項
4. 完整走查：拿「這台 Nginx 502 了」，先給爛提示與它的爛回答，再逐項加構件，展示回答如何從泛泛變成可直接執行
5. 附一份可複製的空白骨架與一份填好的範例
6. **這招什麼時候不該用**：能 `man` 查到的、有標準答案的、需要即時系統狀態的

**`110-06-02` 情境工程與何時該重開對話（進階）**
1. 情境污染的三個可辨識徵兆：開始重複已被否決的建議、忘記前面設過的限制、回答變短變泛
2. 明確的重開判準，以及「重開前先請它總結現況」的交棒手法
3. 長文件與大量資料的決策樹：直接貼／先過濾／附檔／建知識庫
4. ★★★★ 核心觀念：**先用 `grep`／`awk`／`journalctl` 把 200MB 縮到 200 行再餵** —— 這是維運人員本來就會的技能，只是沒想到可以接在 AI 前面
5. 與 `110-05-05` 的分界：那篇寫 Claude Code 的 `/clear` 操作，本篇寫通用原理

**`110-06-03` 結構化輸出與自動化串接（進階）**
1. 為什麼這是分水嶺：能穩定產出合格 JSON 才能接進既有維運流程
2. 三段式：怎麼要（給 schema、明講不要任何額外說明文字）→ 怎麼驗（`jq -e`、`json.loads`、欄位必填）→ 不合格怎麼辦（回饋錯誤重試、剝除 ``` 包裹、設重試上限後轉人工）
3. 完整範例：把 Fail2ban 日誌轉成 JSON 陣列再餵進報表腳本
4. 任務拆解與人工檢查點：**不可逆步驟前一定要有人工閘門**、每一步都要有可驗證的中間產物
5. 接進 shell 腳本與 n8n 流程（連 `070-07-11`）
6. **這招什麼時候不該用**：一次性的探索性問題、輸出本來就是散文的任務

**`110-06-04` 迭代除錯提示與使用反模式（進階）**
1. 四種失敗病因診斷表：回答泛泛→任務描述不清；具體但與環境不符→脈絡不足；內容對但格式亂→輸出格式沒指定；多次重試都在同一處崩→模型層級不對
2. 「把失敗輸出貼回去並說明哪裡不對」比重問一次有效
3. 一次只改一個變因；改了五次還不行通常是任務本身不適合
4. 八種反模式與改法對照：當搜尋引擎用、一次丟太多、不給驗收條件、盲目相信沒驗證就上正式機、在小模型上硬做複雜任務、把長對話當文件保存、把機敏資料貼進雲端模型、**把 AI 產出的指令直接貼進正式機終端機**（每條標後果嚴重度）
5. 長對話的成本陷阱：每一輪都重送全部歷史；能用一支 `sort`／`awk` 解決就不要叫 AI

**`110-06-05` 維運提示樣板庫（ref／進階）**
1. 每個樣板固定四段：適用情境／提示全文（可直接複製）／示範輸入與輸出／已知會失敗的情況
2. **診斷類**：日誌異常分析、systemd 與 Java 錯誤堆疊翻成人話、兩份 `nginx.conf` 或 `sshd_config` 的**實質差異**（不是 diff 而是「這些差異各自的影響」）、解讀前人留下沒註解的腳本
3. **產出類**：產設定檔、寫巡檢腳本、產交接文件、寫變更申請單、寫事故報告
4. ★★★★★ **每個產出型樣板都必須內建驗收要求** —— 產設定檔的樣板要求同時給出 `nginx -t` 驗證指令與回滾步驟
5. 變更申請單與事故報告兩項連回 `100-02-08`、`100-02-09` 的既有制度與 `_表單範本/` 的 docx

**`110-06-06` 生成式 AI 使用規範與資料紅線（進階）**
1. 一張資料分級表：哪些絕不可上雲（憑證私鑰、個資、未公開標案、內網拓撲）、哪些去識別化後可以

3. 技術管控與其極限：網頁閘道網域阻擋、DLP 關鍵字、瀏覽器政策 —— 手機不受控
4. 地端 7B 模型接不住原提示時的補償手法：拆更細、多給範例、一次只要求一件事、放寬格式要求改用人工整理（連 `110-02`、`110-03`）
