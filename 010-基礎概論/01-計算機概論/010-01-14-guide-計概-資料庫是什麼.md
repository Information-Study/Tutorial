## 觀念說明

### ★★★ 為什麼不能一直用 Excel 就好

先看一個真實會發生的情境。

> [!example] 用 Excel 管理客戶訂單
> 你有一張 Excel，每一列是一筆訂單：
>
> | 訂單編號 | 客戶姓名 | 客戶電話 | 客戶地址 | 產品 | 金額 |
> | --- | --- | --- | --- | --- | --- |
> | 1 | 張三 | 0912-345-678 | 台北市信義路一段 | 筆電 | 30000 |
> | 2 | 張三 | 0912-345-678 | 台北市信義路一段 | 滑鼠 | 800 |
> | 3 | 李四 | 0922-111-222 | 新北市板橋區 | 螢幕 | 6000 |
> | 4 | 張三 | 0912-345-679 | 台北市信義路一段 | 鍵盤 | 1500 |
>
> **問題來了**：
> 1. ★★ 張三的資料**重複了三次**（浪費空間，這叫**冗餘**）
> 2. ★★★ 第 4 列的電話是 `...679`，跟前面不一樣 —— **到底哪個是對的？**
> 3. ★★★ 張三搬家了，你要**改三個地方**，漏掉一個資料就不一致
> 4. ★★★ 想刪掉訂單 3，李四的聯絡資料就**跟著消失了**
> 5. ★ 十萬列的時候，找「張三買過什麼」會很慢
> 6. ★★★★ 兩個同事同時開這個檔案編輯 → **一定會有人的修改被蓋掉**

這六個問題，正是資料庫要解決的。

### ★★ 核心比喻：檔案櫃 vs 圖書館系統

| | **Excel／單一檔案** | **資料庫** |
| --- | --- | --- |
| ★ 比喻 | 一個**資料夾**，你自己記得東西放哪 | **有編目系統的圖書館** |
| ★★★ 誰能同時用 | 一個人（多人會衝突） | **上千人同時讀寫** |
| ★★★ 找資料 | 從頭翻到尾 | **用索引直接跳到位置** |
| ★★★★ 資料一致性 | 靠你自己小心 | **系統強制檢查** |
| ★★ 資料量上限 | 百萬列就會卡 | 億級以上 |
| ★★★ 誰改了什麼 | 不知道 | **有交易紀錄，可回溯** |
| ★★ 權限 | 整個檔案給不給 | **可以細到某一欄** |

> [!tip] ★★★ 什麼時候該從 Excel 升級到資料庫
> 出現以下任一情況就該考慮：
> - ★★ 資料超過幾萬列，開檔要等很久
> - ★★★★ **多人需要同時編輯**
> - ★★★ 同一份資料在多個地方重複出現
> - ★★★ 需要控制「誰能看哪些欄位」
> - ★★★ 需要知道「誰在什麼時候改了什麼」
> - ★★ 需要跟其他系統（網站、App）串接
>
> 這正是機關把 Excel 表單升級成資訊系統的時機。

## ★★★ 關聯式資料庫的基本結構

### ★★ 表格、欄位、記錄

**關聯式資料庫（Relational Database）** 把資料組織成一張張**表格（table）**。

```
顧客表（customers）
┌────────┬────────┬──────────────────┬──────────────────┐
│ 顧客ID  │  姓名   │      電子郵件      │       地址        │  ← 欄位（column／attribute）
├────────┼────────┼──────────────────┼──────────────────┤
│   1    │  張三   │ zhang@example.com│ 台北市信義路一段    │  ← 記錄（row／record）
│   2    │  李四   │ li@example.com   │ 新北市板橋區       │
└────────┴────────┴──────────────────┴──────────────────┘
```

| 名詞 | 別名 | 比喻 |
| --- | --- | --- |
| ★★ **表格 Table** | 關聯 Relation | 一本冊子 |
| ★★ **欄位 Column** | 屬性 Attribute、Field | 冊子上的一個欄目 |
| ★★ **記錄 Row** | 元組 Tuple、Record | 冊子上的一列 |
| ★★★★ **主鍵 Primary Key** | PK | **身分證字號** |
| ★★★★ **外鍵 Foreign Key** | FK | **指向另一本冊子的參照** |

### ★★★★ 主鍵：每一列的身分證

**主鍵（Primary Key）** 是能**唯一識別一筆記錄**的欄位。

它必須：
- ★★★★ **唯一**（不能有兩個人身分證字號一樣）
- ★★★ **不能是空的**（每個人都必須有）
- ★★★ **最好不會變**（改身分證字號很麻煩）

> [!warning] ★★★★ 不要用「姓名」當主鍵
> 因為會有同名同姓的人。同理：
> - ★★★ 不要用電話（會換號碼、會共用）
> - ★★★ 不要用 Email（會換）
> - ★★ 不要用「姓名 + 出生日期」（仍可能重複）
>
> ★★★★ **最安全的做法是用一個沒有意義的流水號**（如 `id`），
> 這叫 **surrogate key（代理鍵）**。
> 它唯一的用途就是識別，永遠不會因為現實世界的變化而需要修改。

### ★★★★ 外鍵：把兩張表連起來

現在我們把剛才那張 Excel **拆成兩張表**：

```
顧客表（customers）
┌────────┬────────┬─────────────────┐
│顧客ID★ │  姓名   │      電話        │
├────────┼────────┼─────────────────┤
│   1    │  張三   │ 0912-345-678    │   ← 張三的資料只存一次！
│   2    │  李四   │ 0922-111-222    │
└────────┴────────┴─────────────────┘
     ↑
     │ 外鍵參照
     │
訂單表（orders）
┌────────┬────────┬────────┬───────┬────────────┐
│訂單ID★ │顧客ID◆ │  產品   │ 金額  │    日期     │
├────────┼────────┼────────┼───────┼────────────┤
│   1    │   1    │  筆電   │ 30000 │ 2026-01-15 │
│   2    │   1    │  滑鼠   │   800 │ 2026-01-15 │
│   3    │   2    │  螢幕   │  6000 │ 2026-02-03 │
│   4    │   1    │  鍵盤   │  1500 │ 2026-03-11 │
└────────┴────────┴────────┴───────┴────────────┘
                              ★ = 主鍵    ◆ = 外鍵
```

**六個問題全部解決了**：

| 原本的問題 | 現在 |
| --- | --- |
| ★★ 張三資料重複三次 | ✅ 只存一次 |
| ★★★ 電話不一致 | ✅ 只有一個地方可以改，不可能不一致 |
| ★★★ 搬家要改三個地方 | ✅ **只改一個地方**，所有訂單自動看到新資料 |
| ★★★ 刪訂單會連帶刪掉客戶資料 | ✅ 兩張表獨立 |
| ★★ 查詢很慢 | ✅ 主鍵自動有索引 |
| ★★★★ 多人編輯會衝突 | ✅ 資料庫用交易機制處理 |

> [!note] ★★★★ 外鍵還會幫你「擋錯」
> 資料庫可以設定**參照完整性（referential integrity）**：
> - ★★★★ 不能新增一筆「顧客ID = 99」的訂單，因為顧客表裡沒有 99 這個人
> - ★★★ 不能刪除「顧客ID = 1」，因為還有訂單指著他（除非設定連動刪除）
>
> **這是資料庫幫你把關，而不是靠寫程式的人記得檢查。**
> 這正是資料庫比「用檔案自己存」可靠的核心理由。

### ★★★ 正規化：拆表的原則

把一張大表拆成多張小表，讓每份資料**只存在一個地方**，
這個過程叫 **正規化（Normalization）**。

> [!tip] ★★★ 一句話記住正規化的目的
> ★★★★ **「同一件事實，只記錄一次。」**
>
> 因為只要記錄兩次以上，就可能不一致；
> 而不一致的資料，比沒有資料更危險 —— 你不知道該相信哪一個。

| 情況 | 該不該拆表 |
| --- | --- |
| ★★★ 同一組資料在多列重複出現 | **拆** |
| ★★★ 一個欄位裡塞了多個值（如「產品A,產品B」） | **拆** |
| ★★ 某些欄位只跟部分列有關（大量空白） | 考慮拆 |
| ★★★ 拆完之後每次查詢都要 join 五張表 | 可能**拆太細**了 |

> [!warning] ★★★ 正規化不是越多越好
> 拆太細會讓查詢變複雜、變慢。
> 實務上常見的做法是**先正規化，需要時再刻意「反正規化」**
> （在特定欄位保留冗餘）來換取查詢效能。
>
> 這是設計上的取捨，沒有標準答案。

## ★★★ SQL：跟資料庫講話的語言

**SQL**（Structured Query Language）是操作關聯式資料庫的標準語言。

它的設計目標是「**接近英文**」，所以其實比想像中好讀。

### ★★ 最基本的查詢

```sql
-- ★★ 選出顧客表的所有欄位、所有記錄
SELECT * FROM customers;

-- ★ 只要姓名和電話
SELECT 姓名, 電話 FROM customers;

-- ★★★ 加上條件
SELECT 姓名, 電話 FROM customers WHERE 顧客ID = 1;

-- ★★ 模糊搜尋（找姓張的）
SELECT * FROM customers WHERE 姓名 LIKE '張%';

-- ★★ 排序（金額由大到小）
SELECT * FROM orders ORDER BY 金額 DESC;

-- ★★★ 只要前 10 筆
SELECT * FROM orders ORDER BY 日期 DESC LIMIT 10;
```

> [!tip] ★★ 把 SQL 唸出來就懂了
> `SELECT 姓名 FROM customers WHERE 顧客ID = 1;`
> → 「**選出** 姓名 **從** 顧客表 **在哪裡** 顧客ID 等於 1」
>
> SQL 刻意設計得像英文句子。理解它的關鍵是**照順序讀**：
> 選什麼 → 從哪張表 → 什麼條件 → 怎麼排序。

### ★★★ JOIN：把分開的表接回來

這是關聯式資料庫最強大的地方。

> [!example] 「誰買了電腦？什麼時候買的？」
> 這個問題需要**同時用到兩張表**：
> 姓名在顧客表，產品與日期在訂單表。
>
> ```sql
> SELECT
>     customers.姓名,
>     orders.產品,
>     orders.日期
> FROM orders
> JOIN customers ON orders.顧客ID = customers.顧客ID
> WHERE orders.產品 = '筆電';
> ```
>
> 結果：
> | 姓名 | 產品 | 日期 |
> | --- | --- | --- |
> | 張三 | 筆電 | 2026-01-15 |
>
> ★★★★ **關鍵在 `ON orders.顧客ID = customers.顧客ID`** ——
> 這就是外鍵發揮作用的地方：告訴資料庫「這兩張表怎麼對應」。

> [!note] ★★ JOIN 的比喻
> 想像你有兩疊卡片：一疊寫客戶資料、一疊寫訂單。
> 每張訂單卡上寫著客戶編號。
>
> **JOIN 就是把訂單卡拿去對應的客戶卡旁邊排好**，
> 讓你可以同時看到兩邊的資訊。

### ★★★ 常見的 JOIN 類型

| 類型 | 意思 | 白話 |
| --- | --- | --- |
| ★★★ `INNER JOIN` | 只留**兩邊都有**的 | 「有下訂單的客戶」 |
| ★★★ `LEFT JOIN` | 左表全留，右表沒有就補空 | 「所有客戶，順便看有沒有訂單」 |
| ★ `RIGHT JOIN` | 右表全留 | 較少用 |
| ★★ `FULL OUTER JOIN` | 兩邊都全留 | MySQL 不直接支援 |

```sql
-- ★★★ 列出所有客戶，以及他們的訂單數（沒下單的顯示 0）
SELECT
    c.姓名,
    COUNT(o.訂單ID) AS 訂單數
FROM customers c
LEFT JOIN orders o ON c.顧客ID = o.顧客ID
GROUP BY c.顧客ID, c.姓名;
```

### ★★★★ 增刪改

```sql
-- ★★ 新增
INSERT INTO customers (姓名, 電話) VALUES ('王五', '0933-444-555');

-- ★★★★ 修改（張三搬家了 —— 只要改這一個地方）
UPDATE customers SET 地址 = '台中市西區' WHERE 顧客ID = 1;

-- ★★★★ 刪除
DELETE FROM orders WHERE 訂單ID = 4;
```

> [!danger] ★★★★★ `UPDATE` 和 `DELETE` 忘了寫 `WHERE` 是災難
> ```sql
> UPDATE customers SET 地址 = '台中市西區';   -- ★★★★★ 沒有 WHERE！
> ```
> ★★★★★ 這會把**所有客戶的地址**都改成台中市西區。
>
> **防護習慣**：
> 1. ★★★★ 先用 `SELECT` 確認 `WHERE` 條件抓到的是哪幾筆
> 2. ★★★★ 確認筆數對了，才把 `SELECT *` 換成 `UPDATE ... SET`
> 3. ★★★★ 在正式環境操作前**先備份**
> 4. ★★★ 開啟資料庫用戶端的「安全更新模式」
>    （MySQL Workbench 預設就會擋沒有 WHERE 的 UPDATE）
> 5. ★★★★ 包在**交易（transaction）**裡，錯了可以 `ROLLBACK`
>
> ```sql
> START TRANSACTION;
> UPDATE customers SET 地址 = '台中市西區' WHERE 顧客ID = 1;
> SELECT * FROM customers WHERE 顧客ID = 1;   -- ★★★★ 確認結果
> COMMIT;      -- ★★★★ 對了就提交
> -- ROLLBACK;  -- ★★★★ 錯了就回滾
> ```

## ★★★★ 交易（Transaction）：全部成功或全部不做

> [!example] ★★★★ 轉帳的經典例子
> 甲要轉 1000 元給乙。這需要兩個動作：
> 1. 甲的餘額 −1000
> 2. 乙的餘額 +1000
>
> ★★★★ **如果第 1 步做完，系統就當機了呢？**
> 錢就這樣憑空消失了。
>
> **交易**保證這兩個動作是「**一整包**」：
> 要嘛兩個都成功（`COMMIT`），要嘛兩個都不算（`ROLLBACK`）。
> 絕不會停在中間。

資料庫交易有四個特性，合稱 **ACID**：

| 特性 | 英文 | 白話 |
| --- | --- | --- |
| ★★★★ **原子性** | **A**tomicity | 一整包，全部成功或全部不做 |
| ★★★ **一致性** | **C**onsistency | 交易前後，資料都符合所有規則 |
| ★★★ **隔離性** | **I**solation | 多人同時操作時互不干擾 |
| ★★★★ **持久性** | **D**urability | 一旦說成功了，**就算馬上斷電也不會丟** |

> [!tip] ★★★★ 持久性靠的是 WAL
> **WAL（Write-Ahead Log，預寫式日誌）**：
> 資料庫在真正修改資料之前，**先把「我要做什麼」寫進日誌並強制寫入磁碟**。
>
> 這樣就算修改到一半斷電，重開機後也能照著日誌把事情做完或還原。
>
> 這也是資料庫**備份與時間點還原（PITR）**的基礎 ——
> ★★★★ 有完整備份 + 之後的所有日誌，就能還原到任意一個時間點。
> 詳見 `53-資料庫與資料儲存` 的備份章節。

## ★★ 關聯式 vs NoSQL

| | **關聯式（SQL）** | **NoSQL** |
| --- | --- | --- |
| ★★ 結構 | 固定的表格與欄位 | 彈性，每筆資料結構可以不同 |
| ★ 比喻 | **制式表單** | **一疊自由書寫的便條紙** |
| ★★ 語言 | SQL（標準化） | 各家不同 |
| ★★★★ 交易 | **強 ACID 保證** | 通常較弱（但也有支援的） |
| ★★ 擴充 | 垂直為主（加大機器） | 水平為主（加機器數量） |
| ★★ 代表 | **MySQL、PostgreSQL**、SQL Server、Oracle | MongoDB、Redis、Elasticsearch、**Qdrant** |
| ★★★ 適合 | 財務、訂單、人事、**任何不能出錯的資料** | 日誌、快取、全文檢索、向量搜尋 |

> [!tip] ★★★ 該選哪一種？
> ★★★★ **預設用關聯式資料庫。** 除非你有明確的理由不用。
>
> 大部分機關與企業的業務系統（人事、財產、公文、報名）
> 都是結構明確、不能出錯的資料，關聯式是正確答案。
>
> NoSQL 適合特定用途：
> - ★★★ **Redis** — 快取、Session、排行榜（極快，但資料在記憶體）
> - ★★ **Elasticsearch** — 全文搜尋、日誌分析（見 [[090-05-09-guide-資安設備-日誌集中與SIEM]]）
> - ★★ **Qdrant** — 向量搜尋、AI 的 RAG 知識庫（見 `80-AI服務`）
> - ★ **MongoDB** — 結構常變動的資料
>
> 實務上常常是**混用**：關聯式存核心業務資料，
> Redis 做快取，Elasticsearch 做搜尋。

## ★★★ 完整實戰範例：親手建一個小資料庫

用 **SQLite** 練習最方便 —— 它不需要安裝伺服器，一個檔案就是一個資料庫。

```bash
$ sudo apt install sqlite3
$ sqlite3 練習.db
```

```sql
-- ★★ 1. 建立顧客表
CREATE TABLE customers (
    顧客ID   INTEGER PRIMARY KEY,        -- ★★★★ 主鍵，自動遞增
    姓名     TEXT NOT NULL,              -- ★★★ 不能空白
    電話     TEXT,
    email    TEXT UNIQUE,                -- ★★★ 不能重複
    建立時間  TEXT DEFAULT CURRENT_TIMESTAMP
);

-- ★★★★ 2. 建立訂單表，並設定外鍵
CREATE TABLE orders (
    訂單ID  INTEGER PRIMARY KEY,
    顧客ID  INTEGER NOT NULL,
    產品    TEXT NOT NULL,
    金額    INTEGER NOT NULL CHECK (金額 >= 0),   -- ★★★ 金額不能是負的
    日期    TEXT NOT NULL,
    FOREIGN KEY (顧客ID) REFERENCES customers(顧客ID)   -- ★★★★ 這行讓資料庫替你擋掉孤兒資料
);

-- ★ 3. 塞資料
INSERT INTO customers (姓名, 電話, email) VALUES
    ('張三', '0912-345-678', 'zhang@example.com'),
    ('李四', '0922-111-222', 'li@example.com');

INSERT INTO orders (顧客ID, 產品, 金額, 日期) VALUES
    (1, '筆電', 30000, '2026-01-15'),
    (1, '滑鼠',   800, '2026-01-15'),
    (2, '螢幕',  6000, '2026-02-03'),
    (1, '鍵盤',  1500, '2026-03-11');
```

**現在來試試資料庫怎麼幫你擋錯**：

```sql
-- ★★★ 試著新增一筆不存在的顧客的訂單
sqlite> PRAGMA foreign_keys = ON;   -- ★★★★ SQLite 要手動開啟外鍵檢查
sqlite> INSERT INTO orders (顧客ID, 產品, 金額, 日期)
   ...> VALUES (99, '印表機', 5000, '2026-04-01');
Error: FOREIGN KEY constraint failed        ← ★★★★ 資料庫擋下來了！

-- ★★ 試著新增負數金額
sqlite> INSERT INTO orders (顧客ID, 產品, 金額, 日期)
   ...> VALUES (1, '退貨', -100, '2026-04-01');
Error: CHECK constraint failed: 金額 >= 0   ← ★★★ 也擋下來了

-- ★★ 試著新增重複的 email
sqlite> INSERT INTO customers (姓名, email) VALUES ('假張三', 'zhang@example.com');
Error: UNIQUE constraint failed: customers.email
```

> [!tip] ★★★★ 這就是資料庫的價值
> ★★★★ 這三個錯誤，如果是用 Excel 或自己寫檔案，**全部都會成功寫進去**，
> 然後在幾個月後變成一堆難以追查的髒資料。
>
> 資料庫把「規則」寫在**資料的定義裡**，而不是散落在各個程式中。
> 不管是網站、App、還是有人直接下 SQL，規則都會被強制執行。

**查詢練習**：

```sql
-- ★★ 每位顧客的總消費
SELECT c.姓名, SUM(o.金額) AS 總消費, COUNT(*) AS 訂單數
FROM customers c
JOIN orders o ON c.顧客ID = o.顧客ID
GROUP BY c.顧客ID, c.姓名
ORDER BY 總消費 DESC;

-- 結果：
-- 張三 | 32300 | 3
-- 李四 |  6000 | 1

-- ★★ 三月份的所有訂單，含顧客姓名
SELECT o.日期, c.姓名, o.產品, o.金額
FROM orders o
JOIN customers c ON o.顧客ID = c.顧客ID
WHERE o.日期 LIKE '2026-03%';
```

**體驗索引的威力**：

```sql
-- ★★★ 沒有索引時，查詢要掃描整張表
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE 產品 = '筆電';
-- SCAN orders                    ← ★★★ 全表掃描

-- ★★★ 建立索引
CREATE INDEX idx_orders_產品 ON orders(產品);

EXPLAIN QUERY PLAN SELECT * FROM orders WHERE 產品 = '筆電';
-- SEARCH orders USING INDEX ...  ← ★★★ 直接跳到位置
```

> [!note] ★★★ 索引就是書後面的索引頁
> 想在一本 500 頁的書裡找「資料庫」這個詞：
> - **沒有索引**：從第 1 頁翻到第 500 頁（全表掃描）
> - **有索引**：翻到書末的索引頁，看到「資料庫……第 87, 203 頁」，直接翻過去
>
> ★★★ **代價**：索引本身佔空間，而且每次新增/修改資料時，
> 索引也要跟著更新（所以寫入會變慢一點）。
>
> ★★★ **原則**：常用來查詢與 JOIN 的欄位建索引，不要每個欄位都建。

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★ 同一個客戶資料在系統裡有三份不同的電話 | 沒有正規化，資料重複儲存 | 拆表，讓每份資料只存一個地方 |
| ★★★★★ `UPDATE` 忘了 `WHERE`，全表都被改了 | — | **從備份還原**；日後養成先 `SELECT` 確認的習慣；用交易包起來 |
| ★★★ 查詢越來越慢 | 缺少索引；或資料量成長 | `EXPLAIN` 看執行計畫；為 WHERE/JOIN 的欄位建索引 |
| ★★ 建了很多索引但寫入變超慢 | 索引過多 | 移除用不到的索引；索引不是越多越好 |
| ★★★ 中文存進去變成 `???` | 字元集不是 UTF-8 | MySQL 用 **`utf8mb4`**（不是 `utf8`）；連線也要指定 |
| ★★★★ 交易一直卡住不動 | **鎖等待**或死結 | `SHOW ENGINE INNODB STATUS`；縮短交易；統一鎖定順序 |
| ★★★★ 兩人同時改同一筆，其中一人的修改不見了 | 沒有適當的鎖或版本控制 | 用交易；或用樂觀鎖（版本欄位） |
| ★★★ 用姓名當主鍵，遇到同名同姓就爆炸 | 主鍵選錯 | 改用無意義的流水號（surrogate key） |
| ★★★ 刪了客戶，訂單資料變成孤兒 | 沒設外鍵約束 | 加上 `FOREIGN KEY`，並決定 `ON DELETE` 行為 |
| ★★★★★ 網站被 SQL Injection 攻擊 | 把使用者輸入直接拼進 SQL | **一律用參數化查詢**，見下方資安段落 |
| ★★★★★ 資料庫掛掉才發現沒有備份 | 沒有備份機制或沒驗證過 | 設定自動備份，並**定期演練還原** |

## 安全性注意事項

> [!danger] ★★★★★ SQL Injection：最經典也最致命的網站漏洞
> ★★★★★ **問題出在把使用者輸入直接拼進 SQL 字串。**
>
> ```php
> // ★★★★ ❌ 危險寫法
> $sql = "SELECT * FROM users WHERE name = '" . $_POST['name'] . "'";
> ```
>
> 如果使用者輸入 `' OR '1'='1`，組出來的 SQL 變成：
> ```sql
> SELECT * FROM users WHERE name = '' OR '1'='1'
> ```
> ★★★★ `'1'='1'` 永遠成立 → **回傳所有使用者資料**。
>
> 更糟的輸入：`'; DROP TABLE users; --`
> → 整張表被刪掉。
>
> ★★★★★ **唯一正確的解法：參數化查詢（prepared statement）**
> ```php
> // ★★★★ ✅ 安全寫法
> $stmt = $pdo->prepare("SELECT * FROM users WHERE name = ?");
> $stmt->execute([$_POST['name']]);
> ```
> 參數化查詢把「SQL 指令」與「資料」**分開傳送**，
> 資料庫不會把資料當成指令執行 —— 從根本上杜絕這個問題。
>
> ★★★★ **不要試圖用「過濾特殊字元」來解決**，永遠會有繞過的方法。
> 見 [[090-03-02-guide-應用安全-應用層安全]] 與 [[090-05-04-guide-資安設備-Web應用防火牆WAF]]。

> [!warning] ★★★★ 資料庫帳號的最小權限原則
> ★★★★ 網站程式用的資料庫帳號**不應該是 root**。
>
> | 帳號 | 該有的權限 |
> | --- | --- |
> | ★★★★ 網站程式 | 只對需要的表格有 `SELECT/INSERT/UPDATE/DELETE` |
> | ★★★ 報表程式 | **只有 `SELECT`** |
> | ★★★ 備份程式 | 只有 `SELECT` + `LOCK TABLES` |
> | ★★★★ 管理員 | 全部（但只在需要時使用） |
>
> 這樣就算網站被 SQL Injection 攻破，
> 攻擊者也**不能 `DROP TABLE`、不能建立新帳號、不能讀取其他資料庫**。
>
> ```sql
> -- ★★★★ 建立一個受限的網站帳號
> CREATE USER 'webapp'@'localhost' IDENTIFIED BY '強密碼';
> GRANT SELECT, INSERT, UPDATE, DELETE ON myapp.* TO 'webapp'@'localhost';
> -- ★★★★ 注意：沒有給 DROP、CREATE、GRANT
> ```

> [!danger] ★★★★★ 資料庫絕對不要對外網開放
> 常見的災難：把 MySQL 的 3306 埠開放到網際網路，
> 加上弱密碼或預設帳號 → **幾小時內就會被掃到並攻破**。
>
> **正確做法**：
> 1. ★★★★ 資料庫**只監聽 127.0.0.1**（`bind-address = 127.0.0.1`）
> 2. ★★★★ 如果要跨機器，走**內網 IP + 防火牆白名單**
> 3. ★★★★ 遠端管理走 **SSH 隧道**或 VPN，不要直接開埠
> 4. ★★★ 移除預設的匿名帳號與測試資料庫
>    （MySQL 執行 `mysql_secure_installation`）
> 5. ★★★★ 敏感欄位（身分證、密碼）要**加密或雜湊**儲存
>
> 見 `53-資料庫與資料儲存` 的安全強化章節。

> [!warning] ★★★★ 密碼絕對不能明文存
> 資料庫裡的密碼欄位**永遠不該存明文，也不該用可逆加密**。
>
> 正確做法是用**專為密碼設計的雜湊函式**：
> ★★★★ **bcrypt、argon2、scrypt**（不要用 MD5 或 SHA1）。
>
> 這樣即使資料庫外洩，攻擊者也無法直接得到密碼。
> 見 [[090-07-02-guide-資安實踐-密碼與帳號管理實務]]。

> [!tip] ★★★★ 個資保護
> 依《個人資料保護法》，機關持有的個資有保護義務。
> 資料庫層面應做到：
> - ★★★★ 敏感欄位加密（身分證字號、健保卡號、金融帳號）
> - ★★★ **存取記錄**：誰在什麼時候查了誰的資料
> - ★★★★ 測試環境使用**去識別化**的假資料，不要拷貝正式資料
> - ★★★ 備份檔案同樣要加密
>
> 見 [[090-07-07-guide-資安實踐-台灣資安法規與個資法]] 與 [[090-05-08-guide-資安設備-資料防護DLP與加密]]。

## 小測驗

Q1. 用 Excel 管理訂單資料會遇到哪六個問題？

Q2. 主鍵（Primary Key）必須符合哪三個條件？為什麼不建議用「姓名」或「Email」當主鍵？

Q3. 外鍵（Foreign Key）的作用是什麼？除了「連接兩張表」，它還能幫你做什麼？

Q4. 用一句話說出「正規化」的目的。為什麼「不一致的資料比沒有資料更危險」？

Q5. 把 `SELECT 姓名 FROM customers WHERE 顧客ID = 1;` 用中文唸出來。

Q6. JOIN 在做什麼？請用「兩疊卡片」的比喻說明。

Q7. 什麼是交易（Transaction）？用轉帳的例子說明「原子性」。ACID 分別代表什麼？

Q8. 索引像什麼？它的代價是什麼？

Q9. SQL Injection 是怎麼發生的？唯一正確的解法是什麼？為什麼「過濾特殊字元」不夠？

Q10. 網站程式用的資料庫帳號為什麼不該是 root？這麼做能在被攻破時擋下什麼？

> [!question]- 測驗答案
> **Q1.** ★★★ ①同一客戶資料**重複出現多次**（冗餘）；
> ②重複的資料可能**不一致**（不知道哪個對）；
> ③修改時要**改很多地方**，漏一個就出錯；
> ④刪除訂單可能**連帶失去客戶資料**；
> ⑤資料量大時**查詢很慢**；
> ⑥**多人同時編輯會互相覆蓋**。
>
> **Q2.** ★★★★ 三個條件：①**唯一**（不能重複）；②**不能為空**；③**最好不會變動**。
> 不用姓名是因為**會有同名同姓**；不用 Email 是因為**會換**。
> 最安全的做法是用**無意義的流水號**（surrogate key／代理鍵），
> 它唯一的用途就是識別，不會因現實世界的變化而需要修改。
>
> **Q3.** ★★★★ 外鍵是「指向另一張表主鍵的參照」，讓兩張表能夠關聯查詢（JOIN）。
> 它還能提供**參照完整性檢查** —— 資料庫會**主動擋錯**：
> 不能新增指向不存在客戶的訂單、不能刪除還有訂單指著的客戶。
> **這是資料庫幫你把關，而不是靠寫程式的人記得檢查。**
>
> **Q4.** ★★★ 目的是：「**同一件事實，只記錄一次。**」
> 不一致的資料比沒有資料更危險，是因為**你不知道該相信哪一個** ——
> 沒有資料時你知道要去查證，但看到兩個互相矛盾的值時，
> 可能就直接用了錯的那個。
>
> **Q5.** ★★ 「**選出** 姓名 **從** 顧客表 **在哪裡** 顧客ID **等於** 1」。
> SQL 刻意設計得接近英文，照順序讀就是：
> 選什麼 → 從哪張表 → 什麼條件。
>
> **Q6.** ★★★ JOIN 是把分散在多張表的資料**依照對應關係接回來**一起查詢。
> 比喻：你有兩疊卡片，一疊寫客戶資料、一疊寫訂單，
> 每張訂單卡上寫著客戶編號。
> **JOIN 就是把訂單卡拿去對應的客戶卡旁邊排好**，讓你同時看到兩邊的資訊。
>
> **Q7.** ★★★★ **交易**是一組必須「全部成功或全部不做」的操作。
> 轉帳需要「甲 −1000」與「乙 +1000」兩個動作，
> 若第一步做完就當機，錢會憑空消失 —— **原子性**保證這兩步是一整包，
> 要嘛都成功（COMMIT），要嘛都不算（ROLLBACK），絕不停在中間。
> **ACID**：**A**tomicity 原子性、**C**onsistency 一致性、
> **I**solation 隔離性、**D**urability 持久性。
>
> **Q8.** ★★★ 索引像**書末的索引頁** —— 不用從第 1 頁翻到第 500 頁，
> 查索引就能直接翻到目標頁。
> **代價**：①索引本身**佔儲存空間**；
> ②每次新增或修改資料時**索引也要更新，所以寫入變慢**。
> 因此應該只為常用於 WHERE 與 JOIN 的欄位建索引，不是越多越好。
>
> **Q9.** ★★★★★ 發生原因是**把使用者輸入直接拼接進 SQL 字串**。
> 使用者輸入 `' OR '1'='1` 就能讓條件永遠成立而取得全部資料，
> 輸入 `'; DROP TABLE users; --` 甚至能刪表。
> **唯一正確的解法是「參數化查詢（prepared statement）」** ——
> 它把「SQL 指令」與「資料」**分開傳送**，資料庫不會把資料當指令執行。
> 「過濾特殊字元」不夠，是因為編碼變形與各種繞過手法層出不窮，
> **黑名單式的過濾永遠有漏網之魚**。
>
> **Q10.** ★★★★ 因為要落實**最小權限原則**。
> 網站帳號只需要對特定表格的 `SELECT/INSERT/UPDATE/DELETE`，
> 不需要 `DROP`、`CREATE`、`GRANT`。
> 這樣即使網站被 SQL Injection 攻破，攻擊者也**不能刪除資料表、
> 不能建立新的資料庫帳號、不能讀取其他資料庫**，
> 損害被限制在該應用自己的資料範圍內。
