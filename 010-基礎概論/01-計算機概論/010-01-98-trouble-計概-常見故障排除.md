# 計算機概論 常見故障排除

> [!abstract] 怎麼用這份手冊
> - 依「你看到什麼症狀」查，不是依「這屬於什麼技術」查
> - 找到症狀 → 看判斷分流 → 照處置步驟做 → 想懂原理再點進原文
> - ★★★★ 緊急時直接跳到最下面的「一頁式急救卡」

> [!warning] ★★★★★ 這份文件不教原理
> 每個情境最後都有 `→ 原理詳見` 的連結。
> **出事當下照著做，事後回去把原文讀完** —— 只照做不讀原理，下次還是會再犯一次。

## 依情境展開

### ★★★★★ 情境一：使用者說「這台電腦超慢」

**現象**：

> 「開機要三分鐘」「點一下要等好久」「Word 打字會延遲」
> —— 使用者不會給你錯誤訊息，只會給你這三句話。

★★★★ 「慢」不是一種故障，是**四種故障的共同症狀**。先分類，再處理。

**判斷分流**：

```bash
lsblk -d -o NAME,MODEL,SIZE,ROTA     # 系統碟是不是機械硬碟
free -h                               # 記憶體夠不夠（看 available，不是 free）
uptime; nproc                         # load 除以核心數
vmstat 1 3                            # CPU 時間花在哪
```

```text
NAME    MODEL                  SIZE ROTA
sda     ST1000DM010-2EP102   931.5G    1     ← ROTA=1 就是機械硬碟

 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 3  2 1677721 163840  20480 471040  480  620  1840  2100  910 4200 12  8 20 60  0
                                    ^^^  ^^^                              ^^
                        si/so 持續有數字 = 正在 thrashing        wa 60 = 卡在磁碟
```

- `ROTA=1` 且系統裝在上面 → **就是它，後面不用查了**，換 SSD（約 1,500 元，效果最大）
- `available` 低於總量 10% 且 `si`/`so` 持續有數字 → 記憶體不足 → 【1】
- `wa` 持續高於 20 → CPU 在空等磁碟，換 CPU 完全沒用 → 查磁碟（情境七）
- `us` 高且 `r` 大於核心數 → 真的是 CPU 不夠 → 【2】
- `st` 持續大於 10 → 這是虛擬機，實體主機超賣，你調不動，要找供應商

**處置步驟**：

**【1】找出是誰在吃** ★★★

```bash
ps aux --sort=-%mem | head -6                       # 依記憶體
ps -eo pcpu,pid,user,comm --sort=-pcpu | head -6    # 依 CPU
```

- 前幾名是你預期會吃資源的服務（資料庫、JVM）→ 容量規劃問題
- ★★★★★ 前幾名出現**你不認得的程序名** → 先當成資安事件，跳到情境十六

★★★★ 看 `RSS` 不要看 `VSZ`；`vmstat` 的**第一行是開機以來的平均值**，要看第二行之後。

**【2】確認不是被溫度或電源策略壓住** ★★★★

```bash
sensors | grep -E 'Package|crit'
grep MHz /proc/cpuinfo | sort -u | head -3
```

```text
Package id 0:  +94.0°C  (high = +90.0°C, crit = +100.0°C)
cpu MHz         : 1197.000        ← 遠低於基礎時脈 = 被壓住了
```

- 溫度貼著 `high` **且**時脈掉到零頭 → **過熱降頻**，清灰塵、重塗散熱膏，當天就要處理
- 時脈低**但**溫度很低 → 電源策略在省電：`sudo cpupower frequency-set -g performance`

★★★★ 另一個常見的「花錢卻沒效果」：`top -H -p <PID>` 底下只有一條執行緒 100%、
其他接近 0 → **單執行緒瓶頸**，加核心、加機器完全沒有用。

**【3】前兩步都正常 → 問題在軟體** ★★★

```bash
systemd-analyze
systemd-analyze blame | head -5
```

```text
Startup finished in 4.102s (firmware) + 3.821s (kernel) + 1min 42.443s (userspace)
1min 30.114s  snapd.seeded.service          ← 元兇通常就是第一行
```

★★★ Windows 上看工作管理員的「啟動」分頁，以及**防毒的全碟掃描排程** ——
排在上班時間是機關電腦「早上特別慢」的標準答案。

**原理**：慢的來源是**瓶頸**，不是「電腦老了」。CPU、記憶體、磁碟三者只要有一個吃緊，
其他兩個再強也沒用；而 Linux 的 load 把「卡在 I/O」的程序也算進去，
所以 **load 很高但 CPU 很閒**通常是磁碟的問題。
→ 原理詳見 [[010-01-19-guide-計概-電腦規格與選購]]、[[010-01-06-guide-計概-記憶體與儲存階層]]、
[[010-01-05-guide-計概-CPU如何工作]]、[[010-01-11-guide-計概-程式程序與多工]]

**預防**：採購規格書寫明「SSD > 記憶體 > CPU > 顯卡」與雙通道配置；
把 CPU 溫度與 `available` 記憶體納入長期監控，不要等使用者抱怨才去看。

### ★★★★★ 情境二：磁碟寫滿，服務全部倒了

**現象**：

```text
nginx: 502 Bad Gateway
ERROR 1114 (HY000): The table 'orders' is full
bash: cannot create temp file for here-document: No space left on device
sudo: unable to open /var/lib/sudo/ts/ops: No space left on device
```

★★★★★ 最後一行是最恐怖的：**磁碟滿到連 `sudo` 都不能用**。

**判斷分流**：

```bash
df -h        # 空間
df -i        # inode
```

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p3   20G   20G     0  100% /var        ← 是 /var 滿了，不是根目錄
```

- 某個掛載點 `Use% 100%`、`Avail 0` → 真的是空間滿 → 【1】
- 空間都很低卻仍報 no space → 看 `df -i`，`IUse% 100%` 就是 **inode 用完** → 【3】
- `du` 加總遠小於 `df` 顯示的用量 → **已刪除但仍被程序握著的檔案** → 【4】

**處置步驟**：

**【1】逐層下鑽，找出吃空間的目錄** ★★★

```bash
sudo du -x -h --max-depth=1 /var | sort -rh | head -6
sudo du -x -h --max-depth=1 /var/log | sort -rh | head -5
```

```text
19G     /var
14G     /var/log
11G     /var/log/nginx          ← 就是它，日誌沒有輪替
```

★★★ `-x` 是「不跨掛載點」，少了它會把別的檔案系統也算進來。

**【2】止血：清日誌，但不要用 `rm`** ★★★★

```bash
sudo journalctl --vacuum-size=500M
sudo truncate -s 0 /var/log/nginx/access.log     # 清空但保留 inode
```

> [!danger] ★★★★★ 不要對正在被寫入的日誌下 `rm`
> `rm access.log` 之後空間**不會釋放**，而且 nginx 會繼續往一個看不見的檔案寫 ——
> 等於在事故當下把稽核紀錄關掉。用 `truncate -s 0`，或交給 logrotate 處理。

**【3】inode 用完：找出檔案「數量」最多的目錄** ★★★★

```bash
sudo find /var -xdev -type f -printf '%h\n' | sort | uniq -c | sort -rn | head -5
```

```text
 982341 /var/lib/php/sessions        ← 98 萬個 session 檔，清理排程壞了
```

★★★★ 這是**檔案「數量」爆了，不是「大小」爆了**，空間再多也沒用。
處理方式是**修好清理排程**，不是無腦 `rm -rf` —— 那個目錄下週會再長回來。

**【4】幽靈檔案：已刪除卻仍被佔用** ★★★★

```bash
sudo lsof +L1 | head -5
```

```text
COMMAND   PID USER  FD  TYPE DEVICE   SIZE/OFF NLINK NODE NAME
nginx    1287 www-d  5w  REG   259,3 15032385536   0  418 /var/log/nginx/access.log (deleted)
                                                    ^ NLINK=0 就是幽靈檔案
```

```bash
sudo systemctl reload nginx      # reload 比 restart 安全，服務不中斷
df -h /var
```

```text
/dev/nvme0n1p3   20G  5.1G   14G  27% /var        ← 15G 回來了
```

**【5】收尾：把門檻補上** ★★★★

```bash
df -h /var && df -i /var      # 空間與 inode 是兩回事，兩個都要看
```

事後一定要補三件事：①80% 告警與 90% 緊急告警；②該目錄的輪替／清理排程；
③把這次的原因寫進交接文件。少了第三件，下次換人值班會從頭再查一遍。

**原理**：磁碟滿了會同時造成服務中斷、**日誌停止記錄**（攻擊發生時沒有證據），
有些系統甚至會在磁碟滿時停止稽核 —— 這可能被攻擊者利用來湮滅痕跡。
不只是可用性問題，也是資安問題。
→ 原理詳見 [[010-01-03-cmd-計概-0與1和資料單位]]、[[010-01-09-guide-計概-檔案與檔案系統]]

**預防**：`/var/log` 單獨切一個分割區（撐爆也不會拖垮根目錄）；
設定 `SystemMaxUse=` 與 logrotate 上限；
日誌保存天數要**先算「每日量 × 保存天數」再設 `rotate`**，不然稽核要 6 個月、兩週就被刪光。

### ★★★★ 情境三：「我不能上網」

**現象**：

> 「網頁打不開」「連不上共用資料夾」「LINE 可以但網頁不行」
> 這五個字可能是**七種完全不同的故障**。

**判斷分流**：★★★★ 第一件事不是碰鍵盤，是問「範圍多大」。

| 使用者的回答 | 直接跳到 |
| --- | --- |
| 只有這一台，其他人正常 | 【1】 |
| 整層樓都不能上 | 【4】（問題在交換器／上聯，不在這台電腦） |
| 剛換過位置／剛接了新設備 | 【1】，並特別留意 IP 衝突與線材 |

**處置步驟**：

**【1】實體層與 IP：兩個指令一次看完** ★★★★

```bash
ip -br link show
ip -4 addr show scope global
```

```text
enp1s0     UP     52:54:00:a1:b2:c3 <BROADCAST,MULTICAST,UP,LOWER_UP>
           ^^                                              ^^^^^^^^^
        要 UP                                 要有 LOWER_UP＝線真的通
```

| 看到什麼 | 代表 | 下一步 |
| --- | --- | --- |
| 沒有 `LOWER_UP` | ★★★ 線沒插好／線壞了／交換器埠沒開 | 換線換孔。**重灌驅動、重開機都不會有幫助** |
| `169.254.x.x` | ★★★★ DHCP 完全沒回應 | 【2】 |
| 正常的私有 IP | 拿到了 | 【3】 |
| 完全沒有 `inet` 那行 | 網卡被停用 | `sudo ip link set enp1s0 up` |

**【2】重新跟 DHCP 要一次** ★★★

```bash
sudo dhclient -r enp1s0 && sudo dhclient -v enp1s0
```

```text
DHCPDISCOVER on enp1s0 to 255.255.255.255 port 67
DHCPOFFER of 192.168.1.37 from 192.168.1.1       ← 有 OFFER 才代表 DHCP 活著
DHCPACK of 192.168.1.37 from 192.168.1.1
```

★★★ 只看到 DISCOVER 沒有 OFFER → 問題在交換器、VLAN 或 DHCP 服務本身 → 【4】。

**【3】由內而外跑一次五步驟 ping** ★★★★

```bash
ping -c 2 127.0.0.1
ping -c 2 $(hostname -I | awk '{print $1}')
ping -c 2 $(ip route show default | awk '{print $3}')     # 閘道
ping -c 2 8.8.8.8
ping -c 2 www.google.com
```

★★★★ **這是整個情境最實用的一段**：

- 停在**第 3 步（閘道）** → 問題在你和分享器之間：線材、交換器埠、遮罩設錯、IP 衝突 → 【5】
- 停在**第 4 步（8.8.8.8）** → 你到分享器沒事，**分享器對外有事** → 【4】
- **只停在第 5 步** → 網路完全正常，**純 DNS 問題** → 【6】
- 五步全過但仍說不能上網 → 是某個應用的問題，用 `curl -sI https://目標 | head -1` 直接驗

**【4】確認問題在不在你這端之外** ★★★★

用手機開熱點，讓同一台電腦連上去，重跑【3】。
熱點上一切正常 → 問題在辦公室網路，不是這台電腦。
**這一步能省掉半天的無效重灌。**

**【5】查 IP 衝突** ★★★★

```bash
sudo arping -D -I enp1s0 -c 3 192.168.1.37
```

```text
Unicast reply from 192.168.1.37 [00:11:22:33:44:55]    ← 有人回應＝這個 IP 已經有人在用
```

★★★ **沒有任何回應才是正常的**。IP 衝突的症狀是「時通時不通」，而且兩邊都受害。

**【6】DNS 壞在哪一層** ★★★

```bash
nslookup www.gov.tw                # 目前設定的 DNS
nslookup www.gov.tw 1.1.1.1        # 公用 DNS 對照
```

| 結果組合 | 結論 |
| --- | --- |
| 兩個都失敗 | 對外根本不通，回【3】第 4 步 |
| 本地失敗、公用成功 | ★★★★ 你設定的那台 DNS 掛了或設錯 |
| 兩個都成功但**回傳 IP 不一樣** | ★★★★★ 高度懷疑 **DNS 被竄改／劫持** → 跳到情境十六 |
| 本地成功、公用失敗 | 對方擋外部遞迴查詢，機關內網常見，正常 |

**原理**：上網要同時具備四樣東西 —— 實體連線、IP、閘道、DNS。
五步驟 ping 就是把這四樣**由內往外**一層一層驗過去，每一步都把嫌疑範圍砍一半。
→ 原理詳見 [[010-01-16-guide-計概-網路初體驗]]、[[010-02-17-guide-網概-網路排錯入門]]

**預防**：固定 IP 一律在 DHCP 伺服器上做**位址保留**，不要在用戶端手設；
每一步的實際輸出貼進工單，換人接手時不必從頭再猜一輪。

### ★★★★★ 情境四：按下電源鍵完全沒反應

**現象**：

> 風扇不轉、燈不亮、聽不到任何聲音，按幾次都一樣。

★★★★★ 這一節的順序是刻意的 —— **從零成本、零風險的動作開始**，
把最貴、最容易弄壞東西的動作放最後。八段照做，八成的案例會停在【1】或【2】。

**判斷分流**：先看主機板上那顆待機指示燈（絲印多為 `SB_PWR` 或 `PWR_LED`）。

```text
插上電源、打開 PSU 開關後：
  待機燈會亮  → 電已經進到主機板，問題在「啟動訊號」→ 從【2】開始
  待機燈不亮  → 電根本沒進來，問題在插座、電源線或 PSU → 從【1】開始
```

**處置步驟**：

**【1】確認它真的有吃到電** ★★★★

不要相信「插頭有插」。用另一個確定有電的插座、另一條確定好的電源線各試一次。

```text
牆上插座        → 插一盞檯燈，會亮嗎
電源線          → 換一條已知良品（螢幕的電源線多半可以互換）
PSU 背後 I/O 開關 → 有些型號預設在 O（關）
115/230 電壓開關 → ★★★★ 台灣一律 115，撥到 230 會完全不開機
```

**【2】排除機殼電源鍵與 F_PANEL 接線** ★★★

機殼電源鍵是最便宜也最常壞的零件，接線鬆脫更常見。

```text
把 F_PANEL 上 PWR_SW 那兩根針腳，用螺絲起子輕碰一下短接：
  短接後會開機   → 機殼電源鍵或它的接線壞了，跟主機板無關
  短接後仍沒反應 → 問題在 PSU 或主機板，繼續【3】
```

**【3】兩組電源接頭都要插到底** ★★★

24-pin 主電源與 **8-pin CPU 電源**都要卡榫「喀」一聲扣上。
★★★ **只插 24-pin 忘了插 8-pin** 是自行組裝最常見的失誤 ——
風扇會轉、燈會亮，看起來像有電，但永遠不會有畫面。

**【4】洩掉殘電後再試一次，觀察反應** ★★★★

拔掉電源線，按住機殼電源鍵 5 秒，再插上電、按一次電源鍵：

| 觀察到 | 判讀 | 下一步 |
| --- | --- | --- |
| CPU 風扇抖一下就停 | PSU 有出力但保護跳掉 | 多半是短路，檢查主機板背面有沒有多餘銅柱 |
| 完全靜止、待機燈不亮 | PSU 或供電路徑 | 【5】 |
| 風扇正常轉但無畫面 | 電源沒問題，是 POST | 跳到情境五 |

**【5】換一顆已知良品 PSU 交換測試** ★★★★

> [!danger] ★★★★★ 別用「迴紋針短接法」測 PSU
> 在**沒有負載**的情況下短接綠線與黑線，有些型號會直接保護或損壞，
> 而且你的手正對著高壓輸入側。
> ★★★★★ 唯一能得到明確結論的做法是**換一顆已知良品的 PSU**。
> 而且風扇會轉**不代表輸出穩定** —— 電源有 12V／5V／3.3V／+5VSB 多組電壓，
> 其中一組虛掉一樣開不了機，但風扇照轉。

**【6】清 CMOS，回到出廠設定** ★★★

拔電源線 → 取下 CR2032 電池等 5 分鐘（或短接主機板上的 `CLR_CMOS` 針腳）→ 裝回開機。
超頻設定錯誤、記憶體 XMP 設過頭、BIOS 設定損毀都會導致完全不開機。

★★★ 順帶一提：**每次開機都要重設時間、BIOS 設定跑掉** 就是 CR2032 沒電，換一顆幾十元。

**【7】降到最小系統** ★★★

保留 **主機板 + CPU + 散熱器 + 一條記憶體 + 電源**，其餘全部拔掉，螢幕接內顯。

```text
有畫面 → 一次裝回一個零件，裝到哪個掛掉就是哪個有問題
沒畫面 → 兇手就在這四樣裡面，用替換法逐一換掉測試
```

**【8】定不出來：準備送修** ★★★

★★★ 一份寫清楚的紀錄可以省掉維修廠一半的時間，也避免「送回來說沒問題」——
要帶哪些資訊見最下面的「什麼時候該停手求援」。

**原理**：開機分四步 —— 通電自檢（POST）→ 找到開機裝置 → 載入作業系統 → 啟動服務。
「完全沒反應」代表**連第一步都沒到**，所以先查電，不是先查系統。
→ 原理詳見 [[010-01-01-cmd-計概-電腦到底是什麼]]、[[010-01-02-guide-計概-主機裡面有什麼]]

**預防**：搬機器後開蓋把記憶體、顯卡、排線逐一重插（運送震動很會弄鬆）；
拆機前一律**拔電源線 + 按住電源鍵 5 秒放殘電**，帶電插拔會燒插槽。

### ★★★★ 情境五：風扇會轉、燈會亮，但螢幕永遠沒訊號

**現象**：

> 主機聽起來有在跑，螢幕卻一直顯示「無訊號」或直接黑畫面，也沒有任何嗶聲。

**判斷分流**：先看主機板的四顆 Q-LED，它直接指出卡在哪一段。

| 恆亮的燈 | 代表 | 先做什麼 |
| --- | --- | --- |
| `CPU` | CPU 或 CPU 供電有問題 | ★★★ 檢查 8-pin 供電、散熱器有沒有壓歪 |
| `DRAM` | 記憶體沒被認出來 | ★★★ 走【2】記憶體逐槽測試 |
| `VGA` | 顯示裝置有問題 | ★★ 重插顯卡與 PCIe 供電，或先拔顯卡用內顯 |
| `BOOT` | 找不到可開機的裝置 | ★★ 跳到情境六 |

**處置步驟**：

**【1】先排除「不是主機的問題」** ★★★

★★★ 「螢幕沒畫面」不等於「顯示卡壞了」，整條鏈都要查：

```text
螢幕自己的電源有沒有開？
螢幕的輸入源選對了嗎（HDMI-1 / HDMI-2 / DP）？
訊號線接在顯示卡上，還是接到主機板的內顯孔？ ← ★★★ 有獨顯時一定要接顯卡
換一條確定好的訊號線試？
```

**【2】記憶體逐條、逐槽測試** ★★★★

★★★ 這是「風扇轉但沒畫面」機率最高的原因，優先做。

```text
【2-1】只留一條記憶體，插在主機板標示的 A2（或手冊指定的第一優先）槽
【2-2】不通 → 同一條換到 B2 槽
【2-3】仍不通 → 換另一條記憶體，重複 2-1
```

> [!danger] ★★★★ 每次插拔前都要斷電並洩掉殘電
> 帶電插拔記憶體會**當場燒掉插槽與那條記憶體**，通常是插到一半瞬間短路。

**【3】8-pin CPU 輔助電源有沒有插** ★★★

★★★ 「風扇會轉、燈會亮、螢幕永遠沒訊號、也沒有嗶聲」的典型答案就是
**只插了 24-pin、忘了 8-pin（或 4+4）CPU 供電**。

**【4】進得了系統之後，把記憶體測滿一輪** ★★★★

```bash
sudo apt-get install -y memtest86+     # 之後從 GRUB 選單進入
```

```text
Memtest86+ v6.20  |  Pass 1  |  Errors: 0     ← Errors 必須是 0
```

> [!info]- Windows 的對應工具
> `Win` + `R` 輸入 `mdsched.exe` → 「立即重新啟動並檢查問題」。結果寫進事件檢視器：
> ```powershell
> Get-WinEvent -LogName System | Where-Object Id -in 1201,1101 | Select-Object -First 3 TimeCreated, Message
> ```

★★★★★ 只要 `Errors` 不是 0，那條記憶體**立刻換掉，不要「再觀察看看」**。
記憶體錯誤造成的不只是當機，還會**默默把錯誤的資料寫進檔案** ——
那種損壞是備份也救不回來的（備份會忠實地備份錯誤資料）。

★★★ 完整一輪至少 4 小時，只跑十分鐘看到 PASS 沒有意義；
多條記憶體時**一次只插一條測**，才分得出是哪一條壞。

**【5】只認到一半的記憶體** ★★★

```bash
sudo dmidecode -t memory | grep -E 'Size:|Locator:|Speed:'
```

```text
	Size: 8192 MB
	Locator: DIMM_A2
	Size: No Module Installed
	Locator: DIMM_B2          ← 這條沒被認出來
```

★★★ 交換插槽測試，就能分辨是「條壞」還是「槽壞」。

**原理**：POST（開機自我檢查）在畫面亮起**之前**執行，所以 POST 失敗時你看不到任何錯誤訊息 ——
主機板只能用 Q-LED 與嗶聲告訴你。記憶體是 POST 最早檢查、也最常出問題的一項。
→ 原理詳見 [[010-01-02-guide-計概-主機裡面有什麼]]、[[010-01-06-guide-計概-記憶體與儲存階層]]

**預防**：加記憶體一律買**同品牌同型號**（混插會統一降到最慢那條，甚至開不了機）；
伺服器用 ECC 記憶體，它會自動修正單位元錯誤並記進日誌。

### ★★★★ 情境六：開機到一半掉進 initramfs 或找不到開機裝置

**現象**：

```text
Gave up waiting for root file system device.
ALERT!  UUID=8f3c... does not exist.  Dropping to a shell!

BusyBox v1.30.1 (Ubuntu 1:1.30.1-7ubuntu3) built-in shell (ash)
(initramfs)
```

或是廠商 Logo 之後：

```text
No bootable device -- insert boot disk and press any key
```

**判斷分流**：

```text
掉進 (initramfs)          → 開機載入器有跑，但找不到／掛不動根檔案系統 → 【1】
No bootable device        → 連開機載入器都找不到 → 【3】
UEFI 看得到硬碟卻沒有開機項目 → EFI 分割區或 NVRAM 開機項目遺失 → 【4】
```

**處置步驟**：

**【1】在 initramfs 裡先確認硬碟看不看得到**

```text
(initramfs) cat /proc/partitions
(initramfs) blkid
```

- 完全看不到那顆碟 → **是硬體問題**，跳到情境七（不要繼續在這裡試指令）
- 看得到碟、但 UUID 對不上 → 是 `/etc/fstab` 或 GRUB 的 `root=` 寫錯，往【2】

**【2】檔案系統壞了：先檢查再掛載**

```text
(initramfs) fsck -y /dev/nvme0n1p2
(initramfs) exit
```

> [!danger] ★★★★★ 對懷疑正在壞的碟跑 `fsck` 之前先想清楚
> `fsck -y` 會**直接改寫檔案系統結構**。如果這顆碟是實體故障（見情境七），
> 修復動作本身可能讓資料更難救。
> ★★★★★ **重要資料先整碟複製出來（`ddrescue`）再修**，不要先修再哭。

**【3】UEFI 裡看不看得到硬碟**

開機時按 `Del` 或 `F2` 進 UEFI，看 Boot 或 Storage 頁面。

```text
看得到硬碟、開機順序也對 → 是 bootloader 壞了，用安裝媒體開機救援 GRUB
看不到硬碟               → 換 SATA 排線、換 SATA 埠、換電源線分支
換線換埠都看不到          → ★★★★ 硬碟本身故障，準備資料救援而不是繼續重試
```

**【4】常見的兩個「不是壞掉」的原因** ★★★

```text
新裝的 M.2 SSD 在 BIOS 裡看不到
  → 該 M.2 槽與某幾個 SATA 埠共用通道，插了 M.2 就會關掉 SATA（或反過來）
  → 查主機板手冊的通道共用表，換一個 M.2 槽

虛擬機停在 UEFI Shell 或 No bootable device
  → 磁碟控制器類型（IDE/SATA/SCSI/VirtIO）或 BIOS/UEFI 模式與當初安裝時不一致
  → 改回原本的設定就會開起來，磁碟根本沒壞
```

**原理**：開機第三步是「載入作業系統」—— 韌體先讀 EFI 分割區裡的開機載入器，
載入器再掛載根檔案系統。這兩段任一段斷掉，都會停在黑底文字畫面。
→ 原理詳見 [[010-01-01-cmd-計概-電腦到底是什麼]]、[[010-01-08-guide-計概-作業系統是什麼]]、
[[020-01-25-guide-Linux-開機流程與GRUB救援]]

**預防**：改 `/etc/fstab` 之後**不要直接重開**，先跑 `sudo mount -a` 確認沒有錯誤；
新增的掛載點加 `nofail` 選項，這樣裝置不在時系統仍開得起來。

### ★★★★★ 情境七：懷疑硬碟正在壞

**現象**：

```text
[Fri Aug 29 09:14:22 2026] ata1.00: failed command: READ FPDMA QUEUED
[Fri Aug 29 09:14:25 2026] blk_update_request: I/O error, dev sda, sector 148372480
```

或是**規律的喀喀聲**、開檔案要等十幾秒、複製到一半整台凍住。

> [!danger] ★★★★★ 這個情境的第一步永遠是「備份」，不是「診斷」
> 診斷可以晚點做，資料沒了就沒了。
> **每一次重試都在消耗這顆碟剩下的壽命。**
> 聽到喀喀聲就**立刻斷電**，那是磁頭在敲碟片，繼續通電只會刮掉更多資料。

**判斷分流**：

```bash
sudo dmesg -T | grep -iE 'I/O error|medium error|ata[0-9]|nvme.*(reset|timeout)' | tail -5
```

- 有 `I/O error` 或 `medium error` → ★★★★★ **應用程式已經讀不到資料了**，
  停止一切非必要寫入，先把資料抄出來，才做【2】以後的診斷
- 沒有這些訊息但很慢 → 走【2】看 SMART 屬性

**處置步驟**：

**【1】先確認裝置名稱與序號，避免對錯磁碟下手** ★★★★

```bash
lsblk -o NAME,SIZE,TYPE,MODEL,SERIAL,MOUNTPOINTS
```

```text
NAME        SIZE TYPE MODEL                SERIAL          MOUNTPOINTS
sda       931.5G disk WDC WD10EZEX-08WN4A0 WD-WCC6Y1ZK5V8P /data
```

★★★★★ **`SERIAL` 這一欄一定要抄下來。** 真的要拔磁碟時，靠的是序號跟磁碟標籤**逐字比對**，
不是「它應該是左邊數來第二顆」。拔錯一顆還在服役的磁碟，等於自己製造一次資料事故。

**【2】SMART 總評只是第一眼，不能只看它** ★★★★

```bash
sudo smartctl -H /dev/sda
sudo smartctl -A /dev/sda | grep -E 'Reallocated|Pending|Uncorrect|Power_On_Hours'
```

```text
SMART overall-health self-assessment test result: PASSED
  5 Reallocated_Sector_Ct  ...  -  0
  9 Power_On_Hours         ...  -  49312
197 Current_Pending_Sector ...  -  8      ← 非 0，但總評仍是 PASSED
198 Offline_Uncorrectable  ...  -  8
```

| 屬性 | 判讀 | 重要度 |
| --- | --- | --- |
| `Reallocated_Sector_Ct` | 從 0 開始長就是警訊，持續增加＝換 | ★★★ |
| `Current_Pending_Sector` | **非 0 就開始安排更換** | ★★★★ |
| `Offline_Uncorrectable` | 非 0 代表已經有資料讀不出來了 | ★★★★★ |
| `Power_On_Hours` | 49312 小時 ≈ 5.6 年，已屆退役年限 | ★★ |

★★★★ **PASSED 不等於健康** —— 總評只有跨過廠商門檻才會轉成 FAILED，
很多已經在掉磁區的硬碟總評仍是 PASSED。這就是「只看 `-H` 會漏掉」的典型例子。

**【3】SSD 改看壽命百分比** ★★★

```bash
sudo smartctl -A /dev/nvme0n1 | grep -Ei 'Percentage Used|Available Spare|Media and Data'
```

```text
Available Spare:                    100%
Percentage Used:                    7%
Media and Data Integrity Errors:    0
```

★★★ `Available Spare` 掉到廠商門檻（多為 10%），或 `Media and Data Integrity Errors` 非 0，
就要準備換。

**【4】換之前先點亮定位燈** ★★★

```bash
sudo dd if=/dev/sda of=/dev/null bs=1M count=20000 status=progress
```

★★★ 讓那顆持續讀取，靠硬碟燈閃爍確認實體位置。
**序號比對 +（可行的話）定位燈亮起，兩個條件都成立才動手拔。**

**原理**：磁碟不是「好」或「壞」兩種狀態，而是一條**逐漸劣化**的曲線。
壞磁區會先被搬走（Reallocated），搬不動的排隊等處理（Pending），
完全救不回的就是 Uncorrectable —— 到那一步資料已經丟了。
→ 原理詳見 [[010-01-07-guide-計概-磁碟格式化與RAID入門]]、[[010-01-02-guide-計概-主機裡面有什麼]]

**預防**：把 SMART 那三個屬性納入每日巡檢與告警；
HDD 通電滿五年就排定汰換，不要等它壞；重要資料照 **3-2-1-1-0** 原則備份。

### ★★★★★ 情境八：RAID 陣列亮紅燈／顯示 degraded

**現象**：

```text
$ cat /proc/mdstat
md0 : active raid5 sdc[0] sdd[1](F) sde[2] sdf[3]
      15628052480 blocks super 1.2 level 5, 512k chunk, algorithm 2 [4/3] [U_UU]
                                                                    ^^^^^ ^^^^^^
                                                          4 顆中只剩 3 顆  中間那顆掛了
```

或伺服器面板某一格亮紅燈、廠商工具顯示 `Degraded` / `Rebuilding`。

> [!danger] ★★★★★ 停手三原則，先讀完再動任何一顆碟
> 1. ★★★★★ **重建（rebuild）進行中，絕對不可以再拔任何一顆碟。**
>    重建期間所有硬碟都在滿載讀取，這是整組陣列一生中壓力最大的時刻。
> 2. ★★★★★ **不確定是哪一顆壞就不要拔。** 拔錯一顆，RAID 5 當場全毀。
> 3. ★★★★★ **降級狀態下先做備份，再換碟。** 此時你已經沒有容錯了。

**判斷分流**：

```bash
cat /proc/mdstat
sudo mdadm --detail /dev/md0
```

```text
[U_UU]  且沒有 recovery 那一行  → 降級中、還沒開始重建 → 【1】
recovery = 42.1% (…) finish=318.2min  → ★★★★★ 正在重建 → 【4】：什麼都不要做，等它跑完
[U__U]（RAID 5 少兩顆）        → ★★★★★ 陣列已經掛了 → 直接跳「什麼時候該停手求援」
```

> [!info]- 硬體 RAID 卡與 Windows 儲存空間
> 硬體 RAID 用廠商工具看（`storcli` / `perccli` / `ssacli`）；
> Windows 用 `Get-VirtualDisk | Select FriendlyName, HealthStatus, OperationalStatus`。
> 判讀邏輯完全一樣：先確認是「降級」還是「重建中」。

**處置步驟**：

**【1】先確認是哪一顆，用序號不用位置** ★★★★

```bash
sudo mdadm --detail /dev/md0 | grep -A6 'Number'
sudo smartctl -i /dev/sdd | grep -i serial
```

**【2】立刻做一次完整備份** ★★★★★

★★★★★ 降級狀態＝**沒有容錯**。RAID 5 再壞一顆就全毀。
先備份，再換碟 —— 順序反過來是很多資料事故的起點。

**【3】換上同容量（或更大）的碟，加回陣列**

```bash
sudo mdadm --manage /dev/md0 --add /dev/sdd
watch -n 30 cat /proc/mdstat
```

**【4】重建期間的紀律** ★★★★★

```text
不要再拔任何碟
不要重開機
不要跑大量 I/O 的批次作業（備份、報表）
4TB 的碟重建約 8～15 小時，8TB 可能數十小時 —— 就是要等
```

**原理**：★★★★★ **RAID 不是備份。** 它只防一件事：硬碟實體故障。
誤刪、勒索軟體加密、下錯 `DELETE`、機房淹水 —— RAID 會忠實地把災難同步到每一顆碟。
→ 原理詳見 [[010-01-07-guide-計概-磁碟格式化與RAID入門]]、[[020-01-29-guide-Linux-網路儲存與軟體RAID]]

**預防**：★★★★★ **RAID 壞一顆通常沒有任何症狀** —— 沒有主動監控，
你會在壞第二顆、資料全毀的那天才發現第一顆早就壞了。

```bash
# 最陽春的告警：發現非全 U 就寄信（放進 cron）
grep -q '_' /proc/mdstat && echo "RAID 異常" | mail -s "RAID Alert" admin@example.com
```

★★★ 大容量陣列改用 **RAID 6**（能容忍兩顆），並準備熱備援（hot spare）。

### ★★★★ 情境九：一跑重的工作就整台無預警斷電重開

**現象**：

> 平常好好的，一開始跑編譯／轉檔／備份／遊戲，畫面直接黑掉重開，
> 事件檢視器只有一句「非預期關機」。

**判斷分流**：兩種原因，處置完全不同。

```bash
sensors | grep -E 'Package|crit'
sudo dmesg -T | grep -iE 'mce|thermal|hardware error' | tail -5
```

```text
Package id 0:  +99.0°C  (high = +90.0°C, crit = +100.0°C)   ← 溫度貼著 crit ＝過熱保護
```

- 溫度接近 `crit` → **過熱保護**，往【1】
- 溫度正常，但**最近加裝過獨顯或硬碟** → ★★★★ **電源瓦數不足**，往【2】
- 有 `MCE`（Machine Check Exception）訊息 → ★★★★ CPU 或記憶體硬體錯誤，
  存證後報修，**不要只是重開了事**

**處置步驟**：

**【1】過熱：清灰塵、重塗散熱膏**

★★★★★ 「換完散熱器一開機就自動關機」的典型原因是**散熱膏沒塗、或扣具只壓到一邊**，
CPU 瞬間過熱觸發保護。**立刻斷電重裝散熱器**，反覆高溫開機會永久縮短 CPU 壽命。

**【2】電源瓦數：重新算一次峰值**

```text
CPU     TDP × 1.5     i5-14400   65W  →  約 100W    （Turbo 時遠超過標示 TDP）
獨顯    TGP × 1.2     RTX 4060  115W  →  約 140W    （瞬時尖峰可達標示兩倍）
主機板 + 記憶體 + 風扇                →  約  60W
NVMe ×1 / HDD ×2                      →  約  20W
────────────────────────────────────────────
峰值合計 ≈ 320W  →  再留 30～40% 餘裕  →  450W ～ 550W
```

★★★ 另外兩個常被忽略的細節：

- **只看總瓦數不看 +12V 那一路的安培數** —— 標示 500W 但 +12V 只給 30A（360W）的電源，
  帶不動 CPU + 獨顯
- **PCIe 供電接頭數量不對** —— 顯卡要 2×8-pin，電源只有 1 個，用轉接線硬接是走火風險

> [!danger] ★★★★ 電源是「自己壞掉還會拖死別人」的零件
> 其他零件壞掉通常只有自己壞；電源不是。
> 輸出電壓不穩時會把不穩的電壓灌進主機板、記憶體與硬碟 ——
> 實際發生過的結果是**主機板與系統碟一起燒掉，資料全失**。

**【3】斷電之後一定要檢查資料**

★★★★ 無預警斷電的當下，正在寫入的檔案可能已經損毀。
資料庫要看啟動日誌有沒有 crash recovery，檔案系統要跑一次檢查。

**原理**：電源供應器的標示瓦數是**持續輸出能力**，而 CPU Turbo 與顯卡的**瞬時尖峰**
可以是標示值的兩倍。撐不住時保護電路會直接切斷輸出，表現就是「無預警斷電」。
→ 原理詳見 [[010-01-19-guide-計概-電腦規格與選購]]、[[010-01-15-guide-計概-電力基礎與用電安全]]

**預防**：加裝任何耗電零件（獨顯、額外硬碟）後**重算一次瓦數**；
把 CPU 溫度納入長期監控 —— 長期貼著 `high` 跑不會馬上壞，但會提早壞，
典型結果是「機器用兩三年後開始隨機當機，查不出原因」。

### ★★★★★ 情境十：一直跳電、延長線發燙、摸機殼會麻、聞到燒焦味

**現象**：

> 「插上那台印表機就跳電」「延長線摸起來燙燙的」
> 「摸機殼有麻麻的感覺」「機櫃有一股燒焦味」

> [!danger] ★★★★★ 這四種現象裡有兩種要立刻停手
> - **摸機殼會麻** → 漏電且接地不良，**立即停用該設備**，請電匠處理
> - **聞到燒焦味** → ★★★★★ **立刻斷電，不要通電測試、不要「再開一次看看」**。
>   燒焦味代表某個零件已經在冒煙，再通電可能起火
>
> 這兩種都不是你該自己排錯的範圍，見最下面的「什麼時候該停手求援」。

**判斷分流**：跳電與發燙先算數字，不要憑感覺。

```text
台灣一般插座迴路的無熔絲開關（NFB）多為 15A 或 20A：
  15A × 110V = 1650 W   →  安全持續負載 = 15 × 0.8 = 1320 W
  20A × 110V = 2200 W   →  安全持續負載 = 20 × 0.8 = 1760 W
                                          ^^^^^^^^^^^^^^^ 這兩個數字請背起來
```

把這條迴路上**所有設備的瓦數加總**，超過上面的數字就是原因。

**處置步驟**：

**【1】把高功率設備分散到不同迴路** ★★★

雷射印表機（列印瞬間 800～1200W）、電暖器、除濕機不要跟電腦共用一條迴路。

**【2】不要串接延長線、不要用三孔轉兩孔** ★★★★

串接會累積壓降並過載；三孔轉兩孔等於**拿掉接地保護**，
這正是「摸機殼會麻」的常見成因。

**【3】真的不夠用 → 請合格電匠增設專用迴路** ★★★★

> [!danger] ★★★★★ 絕對不要「因為一直跳電就換大一號的 NFB」
> NFB 保護的是**牆內的電線**，規格是依電線粗細決定的。
> 把 15A 換成 30A，電線並沒有變粗 ——
> 你只是拿掉了那個會在電線起火前先跳掉的保護裝置。
> **一直跳電代表負載真的太重**，正確做法是分散負載或增設專用迴路（連電線一起換粗）。

**【4】停電相關的三個常見誤判** ★★★★

| 現象 | 真正的原因 | 處置 |
| --- | --- | --- |
| UPS 買 1000VA 卻帶不動 800W 設備 | ★★★ **VA ≠ W**，功率因數可能只有 0.6 | 看 **W** 的標示，不要看 VA |
| 停電時 UPS 只撐了 30 秒 | ★★★★ **電池老化**（超過 3～5 年） | 定期放電測試、記錄安裝日期、到期更換 |
| 停電後伺服器沒有正常關機 | ★★★★ **沒接 UPS 訊號線**（USB／網路） | 接上訊號線並設定 NUT 或廠商軟體 |

**原理**：`P = V × I`。一條迴路能吃多少電，取決於牆內電線的粗細，
NFB 只是那條電線的保險絲。超過的後果輕則跳電，重則**電線在牆壁裡持續發熱起火**。
→ 原理詳見 [[010-01-15-guide-計概-電力基礎與用電安全]]、[[040-02-07-guide-機房-UPS電池維護與更換]]

**預防**：機櫃用電照「1 機櫃 ≈ 1 冷凍噸」評估空調；
伺服器雙電源的**兩條線要插在不同 PDU／不同迴路**，插同一條排插等於白買；
維修斷電時落實 LOTO（掛牌上鎖）並**用電表確認真的沒電**。

### ★★★★ 情境十一：服務半夜自己消失，或整個卡住不動

**現象**：

```text
$ systemctl status php8.3-fpm
   Active: failed (Result: signal) since Wed 2026-08-27 03:14:23 CST
```

應用程式自己的 log 什麼錯誤都沒寫，就這樣斷在半夜。

**判斷分流**：

```bash
sudo dmesg -T | grep -iE 'out of memory|killed process'
```

```text
[Wed Aug 27 03:14:22 2026] Out of memory: Killed process 3312 (php-fpm) total-vm:2298765kB
```

- 有這一行 → ★★★★★ 服務不是「自己掛掉」，是**被系統殺掉的** → 【1】
- 沒有這一行但服務仍消失 → 查 `journalctl -u <服務名> --since '-1h'` 與應用自己的日誌
- 服務還活著但**所有查詢都卡住不動** → 資料庫鎖等待或死結 → 【4】

**處置步驟**：

**【1】對照時間點，找出導火線** ★★★★

★★★ 記下 OOM 的時間，去比對那個時段的流量或排程作業 ——
**備份、報表、批次匯入**最常是導火線。

**【2】判斷是「用量大」還是「記憶體洩漏」** ★★★★

```bash
for i in $(seq 1 10); do
  printf '%s  RSS=%s KB\n' "$(date +%T)" "$(ps -o rss= -p 1234 | tr -d ' ')"
  sleep 60
done
```

```text
09:00:01  RSS=1465000 KB
09:01:01  RSS=1489200 KB
09:02:01  RSS=1512800 KB        ← 像樓梯一路往上、從不回落 ＝ 洩漏
```

★★★★ 看 `RSS`（實際佔用的實體記憶體）**不要看 `VSZ`** —— `VSZ` 只是保留的位址空間。

**【3】止血與根治** ★★★

```ini
# /etc/systemd/system/<服務>.service.d/override.conf
[Service]
MemoryMax=2G
RuntimeMaxSec=86400      # 洩漏的服務先每天自動重啟止血
```

★★★ 止血完把觀測記錄交給開發者，根治要修程式。

**【4】資料庫全部卡住不動** ★★★★

```sql
SHOW ENGINE INNODB STATUS\G
```

★★★ 現代資料庫會自動偵測死結並選一個犧牲者回滾。
若是**長交易鎖住不放**，就要找出那條連線。統一鎖定順序、縮短交易、應用層要能重試。

**原理**：Linux 允許程式「超額申請」記憶體，真的不夠用時由 OOM Killer 選一個程序殺掉。
被殺的**不一定是兇手**，常常是「最胖的那個」。
→ 原理詳見 [[010-01-06-guide-計概-記憶體與儲存階層]]、[[010-01-11-guide-計概-程式程序與多工]]、
[[010-01-14-guide-計概-資料庫是什麼]]

**預防**：`dmesg` 的環形緩衝區會被覆蓋、重開機後全空 ——
要保留證據就開啟 journal 持久化或把日誌送到集中平台。

### ★★★ 情境十二：插上去沒反應（隨身碟／螢幕／網路孔）

**現象**：

> 「隨身碟插了沒反應」「外接硬碟複製到一半就斷」「螢幕沒訊號」「網路只跑到 100M」

★★★★ 週邊問題有一條固定的分流順序：**實體層 → 供電 → 驅動 → 裝置節點 → 應用層**。
順序顛倒（一開始就重裝驅動）是最常見的浪費時間方式。

**判斷分流**：開一個終端機常駐監看，然後**當場插拔一次**。

```bash
sudo dmesg -w
```

```text
[12345.678] usb 2-2: new SuperSpeed USB device number 5 using xhci_hcd
[12345.689] usb-storage 2-2:1.0: USB Mass Storage device detected
```

- 兩行都有 → 實體層沒問題，跳【3】
- ★★★★ **插拔完全沒有任何新訊息** → 問題在**實體層**（線、孔、裝置本身）→ 【1】。
  此時重裝驅動、重開機、換作業系統**都不會有幫助**
- 只有 `new ... device` 沒有 `detected` → 驅動沒接手 → 【3】

**處置步驟**：

**【1】實體層有三個變因，一次只換一個** ★★★

```text
換另一個孔（優先用主機背面直接焊在主機板上的，不要用前面板或延長 Hub）
換另一條線（Type-C 尤其要換，充電專用線沒有資料腳位）
換另一台電腦試同一個裝置
```

```bash
lsusb -t     # 最後一欄 480M 代表只協商到 USB 2.0
```

**【2】供電不足：時斷時續、大檔複製到一半失敗** ★★★★

```bash
dmesg | grep -iE 'error -71|error -32|over-current|reset high-speed'
```

★★★★ 看到 `error -71` 或反覆 `reset` → **供電或線材品質**，不是檔案系統壞掉。
換有外接電源的 USB Hub、換短一點的線；2.5 吋外接硬碟用 Y 型雙頭線供電。

★★★★ 這種狀況**不要繼續寫入資料** —— 傳到一半斷線會讓檔案系統進入不一致狀態。

**【3】裝置在、驅動不在** ★★★

```bash
sudo lspci -k -s 01:00.0
```

★★★★ **沒有 `Kernel driver in use:` 這一行** → 系統認得這個裝置，但沒有任何驅動接手，
所以它在使用者眼中等於不存在。有 `Kernel modules:` 就 `sudo modprobe <模組名>`。

**【4】螢幕與網路的專屬分流** ★★★

```bash
for f in /sys/class/drm/*/status; do echo "$f: $(cat "$f")"; done
sudo ethtool "$(ip route | awk '/default/{print $5; exit}')" | grep -E 'Speed|Duplex|Auto-neg'
```

```text
/sys/class/drm/card0-HDMI-A-1/status: disconnected   ← 訊號根本沒進來：線、孔、或 Type-C 不支援 DP Alt Mode
        Speed: 100Mb/s                                ← 協商只到 100M
```

★★★★ `Auto-negotiation: on` 卻只有 100Mb/s → **先換線（Cat5e 以上）再換交換器**，
順序反了會白花一整天。`Duplex: Half` 在 Gigabit 環境是異常，會伴隨大量重傳。

**原理**：一個週邊要能用，必須同時具備「實體連線 → 足夠供電 → 驅動程式 → 裝置節點」。
驅動程式就是翻譯官，缺了它作業系統看得到裝置卻不知道怎麼跟它說話。
→ 原理詳見 [[010-01-12-guide-計概-輸入輸出與週邊設備]]、[[020-01-27-cmd-Linux-硬體資訊與裝置管理]]

**預防**：採購時線材寫明規格（Cat5e 以上、支援資料傳輸的 Type-C）；
機關的 USB 埠政策與惡意隨身碟風險見 [[010-01-18-guide-計概-資訊安全初步]]。

### ★★★ 情境十三：程式／容器／虛擬機跑不起來

**現象**：

```text
./myapp: error while loading shared libraries: libssl.so.1.1: cannot open shared object file
-bash: ./deploy.sh: /bin/bash^M: bad interpreter: No such file or directory
exec /usr/local/bin/entrypoint: exec format error
docker: Error response from daemon: driver failed ... address already in use
```

**判斷分流**：★★★ 這四行錯誤訊息各自對應一個明確的原因，**照字面查就好，不要猜**。

| 錯誤訊息 | 原因 | 一行處置 |
| --- | --- | --- |
| `error while loading shared libraries` | 缺共用函式庫 | `ldd 執行檔 \| grep 'not found'` |
| `bad interpreter` 且結尾有 `^M` | 檔案是 Windows CRLF 換行 | `dos2unix deploy.sh` |
| `exec format error` | ★★★★ 映像／執行檔架構不符（arm64 vs amd64） | `docker pull --platform linux/amd64 …` |
| `address already in use` | 埠被別的服務或舊容器占著 | `ss -ltnp \| grep 8080` |

**處置步驟**：

**【1】容器：死因幾乎都寫在日誌的最後三行** ★★★★

```bash
docker ps -a --filter name=mysite
docker logs --tail 20 mysite
```

★★★ 看到 `Exited (…)` 就是死了；**完全沒有輸出**代表主程式跑完就結束 ——
容器需要一個**前景程式**才會活著。

**【2】容器「我明明改了檔案，網頁卻沒變」** ★★★★

```bash
docker inspect -f '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}' mysite
```

★★★★ Docker 遇到**不存在的主機路徑不會報錯**，它會安靜地幫你建一個空目錄。
用 `docker inspect` 印出實際生效的來源路徑，比對是不是你想的那一個。

**【3】虛擬機開不起來** ★★★★

```bash
kvm-ok
```

```text
INFO: Your CPU supports KVM extensions
INFO: KVM is disabled by your BIOS       ← 進 BIOS 打開 VT-x / AMD SVM
```

★★★★ 另外兩個常見原因：**同一時間只有一個 Hypervisor 能拿走硬體虛擬化**
（Windows 開了 Hyper-V／WSL2 之後 VirtualBox 就會極慢或失敗）；
以及**記憶體超賣**到開不動（判斷準則：記憶體不要超賣，CPU 可以適度超賣）。

**【4】修補完漏洞掃描還在報同一個 CVE** ★★★★★

```bash
sudo needrestart -r l
sudo systemctl restart nginx
sudo lsof +c 0 2>/dev/null | grep -c 'DEL.*lib'
```

```text
0        ← 這個 0 才是「已修補」的證據
```

★★★★ 磁碟上的檔案換掉了，**記憶體裡的服務還載著舊版函式庫**。
把這個 `0` 的輸出存證，稽核要的是這個，不是 `apt upgrade` 的畫面。

**原理**：程式要跑起來需要「對的架構 + 對的直譯器 + 對的函式庫」三者齊備，
缺一個就是上面那幾行錯誤訊息之一。
→ 原理詳見 [[010-01-10-guide-計概-軟體授權與程式怎麼跑起來]]、[[010-01-17-guide-計概-雲端虛擬化與容器]]

**預防**：`.gitattributes` 寫 `*.sh text eol=lf`，讓 Windows 同事 commit 時自動轉換；
容器資料一律用 volume 掛出來；
★★★★★ `docker system prune -a --volumes` **會連沒掛在執行中容器上的 volume 一起刪掉**，
執行前先 `docker system df` 看清楚。

### ★★★ 情境十四：中文變亂碼、存進資料庫變問號

**現象**：

```text
CSV 用 Excel 開：  ¯¶«È¦W ºÙ
資料庫查出來：      ???
PHP 頁面：          Warning: Cannot modify header information - headers already sent
```

**判斷分流**：

```bash
file -i data.csv
```

```text
data.csv: text/plain; charset=iso-8859-1      ← 多半其實是 Big5
data.csv: text/plain; charset=utf-8           ← 是 UTF-8，那就是開啟方式的問題
```

**處置步驟**：

```bash
iconv -f BIG5 -t UTF-8 data.csv > data-utf8.csv        # Big5 轉 UTF-8
sed -i '1s/^\xEF\xBB\xBF//' deploy.sh                   # 移除 BOM（腳本／PHP 用）
convmv -f BIG5 -t UTF-8 -r .                            # 檔名亂碼
```

| 場合 | 正確設定 |
| --- | --- |
| ★★★ Excel 要開 UTF-8 CSV | **加上 BOM**（`EF BB BF`），這是 BOM 少數有用的場合 |
| ★★★★ MySQL | 用 `utf8mb4`（**不是 `utf8`**，那只支援 3 位元組，存不了 emoji），連線也要指定 |
| ★★★ 網頁 | `<meta charset="utf-8">` 放在 `<head>` 最前面，HTTP 標頭也要帶 |
| ★★★★ Shell 腳本／PHP | UTF-8 **無 BOM**（有 BOM 會讓 `#!` 失效、讓 PHP 提前輸出） |

> [!danger] ★★★★★ 最危險的動作：用錯誤的編碼開啟，然後按下儲存
> ★★★★ **亂碼幾乎不會弄壞檔案** —— 只要沒有用錯誤編碼重新存檔，原始位元組都還在。
> 但一旦存下去，就真的把資料轉壞了，而且通常救不回來。

**原理**：編碼就是一本「號碼簿」。同一串位元組用不同號碼簿去查，就會查出不同的字。
→ 原理詳見 [[010-01-04-cmd-計概-數字系統與文字編碼]]

**預防**：★★★★ **從輸入到儲存到輸出，全程統一用 UTF-8。**
每多一個轉換點，就多一個出錯與被攻擊的機會。

### ★★★★★ 情境十五：檔案不見了、誤刪、誤格式化

**現象**：

> 「我按了 Enter 才發現 `rm` 打錯路徑」「格式化完才想起來資料還沒備份」
> 「共用資料夾整個目錄消失了」

> [!danger] ★★★★★ 第一步不是「找救援軟體」，是「停止寫入」
> 刪除只是把索引標成**可覆寫**，資料本體還在磁碟上。
> **每多寫一次，就少一分機會。**
> - 立刻停止使用該磁碟：卸載（`umount`）或直接關機
> - ★★★★★ **不要**把救援軟體安裝到同一顆碟上
> - ★★★★★ **不要**繼續在那顆碟上「找找看」—— 瀏覽也會產生寫入

**處置步驟**：

**【1】確認範圍與時間**：刪了什麼、幾點刪的、那顆碟有沒有備份或快照。

**【2】先看有沒有更省事的來源** ★★★★

```text
有備份 / 快照 / ZFS snapshot / VSS 陰影複製  → 從那裡還原，不要碰原碟
有 Windows 回收筒 / trash-cli                → 直接還原
以上皆無                                      → 【3】
```

**【3】整碟做一份唯讀映像，在映像上救** ★★★★★

```bash
sudo ddrescue /dev/sdb /mnt/rescue/sdb.img /mnt/rescue/sdb.log
```

★★★★★ **所有救援動作都在映像上做**，原碟從此不再寫入。
之後用 TestDisk（救分割表）或 PhotoRec（依檔案特徵撈檔）處理那份映像。

**【4】判斷值不值得送專業救援**：如果是「唯一一份」的公務資料或資料庫檔案，
不要自己試 —— 見「什麼時候該停手求援」。

**原理**：刪除有三個層次 —— 移到回收筒、清掉索引（資料還在）、真正覆寫。
一般的「刪除」只做到第二層，所以救得回來；也正因如此，
★★★★ **報廢硬碟必須另外做資料銷毀**，快速格式化完全無法保護資料。
→ 原理詳見 [[010-01-09-guide-計概-檔案與檔案系統]]、[[010-01-07-guide-計概-磁碟格式化與RAID入門]]

**預防**：`alias rm='rm -i'` 或裝 `trash-cli`；
★★★★★ 落實 **3-2-1-1-0**（3 份副本、2 種媒體、1 份異地、1 份離線不可變、0 個還原錯誤）——
**沒演練過的備份等於沒有**。

### ★★★★★ 情境十六：懷疑中招（勒索、釣魚、被入侵）

**現象**：

```text
桌面出現 README_FOR_DECRYPT.txt，所有檔案副檔名變成 .locked
top 最上面是一個沒看過的程序名，CPU 100%
nslookup 同一個網域，本地 DNS 與 1.1.1.1 回傳的 IP 不一樣
```

> [!danger] ★★★★★ 順序很重要，做錯就毀掉證據
> 1. ★★★★★ **立刻拔掉網路線／關閉 Wi-Fi**（阻止擴散與資料外傳）
> 2. ★★★★ **不要關機** —— 記憶體中的證據會消失，可能還救得回檔案
> 3. ★★★★★ **立刻通報資訊人員／資安窗口**，說明你做了什麼
> 4. ★★★ **不要自己嘗試清除**，那會破壞跡證
> 5. ★★★★ 從**另一台乾淨的裝置**改掉所有密碼

**判斷分流**：

```bash
ps aux --sort=-%cpu | head -6
sudo ls -l /proc/<PID>/exe          # 這支程式的執行檔到底在哪裡
nslookup 目標網域; nslookup 目標網域 1.1.1.1
```

- ★★★★★ 高 CPU 的程序名**你不認得**、執行檔在 `/tmp` 或 `/dev/shm` → 高度可疑（挖礦程式很常見）
- ★★★★★ 兩台 DNS 回傳的 IP **不一樣** → 高度懷疑 DNS 被竄改／分享器被入侵：
  立刻改分享器管理密碼、關閉 WAN 遠端管理、更新韌體、通報

**處置步驟**：★★★★★ 到這一步，你的工作是**保全現場並通報**，不是自己修。

```text
【1】隔離：拔網路線（不關機）
【2】記錄：拍下畫面、記下時間點與當事人做過的動作
【3】通報：依機關的資安事件通報流程走
【4】評估：這台機器碰得到哪些系統、哪些帳號要立刻停用
【5】復原：從已知乾淨的備份重建，不是「清乾淨繼續用」
```

**原理**：勒索軟體是**雙重勒索**（加密 + 竊取後公開），而且會刻意破壞備份；
釣魚不需要你點連結，「只是輸入帳密看看」就已經被騙了。
→ 原理詳見 [[010-01-18-guide-計概-資訊安全初步]]、[[090-07-04-guide-資安實踐-資安事件應變流程]]

**預防**：★★★★★ **MFA 比密碼更重要**；離線或不可變備份；
★★★★★ 建立**不責備的通報文化** —— 延遲通報會讓損害擴大好幾倍。

## ★★★★ 一頁式急救卡

出事時來不及讀長文，先跑這幾個指令。**每一行後面就是「看到什麼代表什麼」。**

```bash
df -h && df -i
# 有 Use% 100% 或 IUse% 100% → 磁碟／inode 滿了，服務全倒的頭號原因（情境二）

free -h && vmstat 1 3
# available 低於總量 10% 且 si/so 持續有數字 → 記憶體不足在 thrashing（情境一、十一）
# wa 持續高於 20 → CPU 在空等磁碟，換 CPU 沒有用

sudo dmesg -T | grep -iE 'I/O error|medium error|killed process|mce|thermal'
# I/O error / medium error → ★★★★★ 磁碟已經讀不出資料，停手先備份（情境七）
# killed process           → 服務是被 OOM Killer 殺的，不是自己掛的（情境十一）
# mce / thermal            → CPU 或記憶體硬體錯誤、過熱，存證後報修（情境九）

cat /proc/mdstat
# 出現 _ 或 [4/3] → ★★★★★ RAID 降級，已經沒有容錯（情境八）
# 有 recovery = xx% → 正在重建，什麼碟都不要拔

uptime; nproc; ps -eo pcpu,pid,user,comm --sort=-pcpu | head -5
# load ÷ nproc 大於 2 → 嚴重排隊；最上面出現不認得的程序名 → 當資安事件處理（情境十六）

ip -br link show; ip -4 addr show scope global
# 沒有 LOWER_UP → 線根本沒通，別再查軟體（情境三）
# 169.254.x.x   → DHCP 完全沒回應

sensors | grep -E 'Package|crit'
# 溫度貼著 high/crit → 過熱降頻或即將保護關機，當天就要處理（情境九）

sudo smartctl -A /dev/sda | grep -E 'Reallocated|Pending|Uncorrect'
# 三個數字任一非 0 且在增加 → 這顆碟要換了，先備份（情境七）
```

> [!tip] ★★★★ 排錯的三條通則
> 1. **從最便宜的開始試** —— 換一條線成本是零，換一張主機板是幾千塊
> 2. **不要一開始就重開機** —— 重開會沖掉 `free`、`vmstat`、`dmesg` 裡的現場證據，
>    事後只會得到一句「重開就好了」，然後下週再壞一次
> 3. **每一步的實際輸出都貼進工單** —— 排錯最貴的成本是重複做同一件事

## 什麼時候該停手求援

> [!danger] ★★★★★ 下面這幾種情況，繼續自己動手會讓災情擴大或證據消失
> | 情況 | 為什麼要停 | 立刻該做的 |
> | --- | --- | --- |
> | ★★★★★ **聞到燒焦味、看到冒煙** | 零件正在燒，再通電可能起火 | **斷電**，不要「再開一次看看」，不要通電測試 |
> | ★★★★★ **摸機殼會麻** | 漏電且接地不良，有觸電風險 | 停用該設備，請**合格電匠**處理，不要自行改配電 |
> | ★★★★★ **硬碟發出規律喀喀聲** | 磁頭在敲碟片，每一秒都在刮掉更多資料 | 立刻斷電，評估送專業資料救援 |
> | ★★★★★ **`dmesg` 出現 `I/O error` / `medium error`** | 這顆碟已經讀不出資料 | 停止一切非必要讀寫，先整碟複製（`ddrescue`）出來 |
> | ★★★★★ **RAID 正在重建（rebuild）** | 全部硬碟滿載，是陣列壓力最大的時刻 | **不要拔碟、不要重開機、不要跑大量 I/O**，就是等 |
> | ★★★★★ **RAID 降級且不確定是哪一顆壞** | 拔錯一顆，RAID 5 當場全毀 | 用**序號**比對確認，比對不出來就先備份再說 |
> | ★★★★★ **資料庫檔案疑似損毀** | 錯誤的修復動作會讓還救得回的部分也毀掉 | 先整份複製一份再動任何工具，通知 DBA／原廠 |
> | ★★★★★ **懷疑遭入侵、看到勒索信** | 關機與清除都會湮滅證據 | **拔網路線但不要關機**，通報資安窗口 |
> | ★★★★★ **誤刪／誤格式化了唯一一份資料** | 每一次寫入都在降低救回機率 | 立刻卸載或關機，在**映像檔**上救，不要碰原碟 |
> | ★★★★ **UPS 已在電池供電且快沒電** | 硬斷電會造成檔案損毀 | 依序**優雅關機**，不要等它自己斷 |
> | ★★★★ **拆機前發現裡面有敏感資料** | 送修等於把資料交給第三方 | 先取出或加密該碟，並留紀錄 |

★★★★ 求援時要帶的資訊（帶齊可以省掉維修廠一半的時間）：
發生的**確切時間**、當時在做什麼、卡在哪一步、**已經試過什麼**、
Debug LED 停在哪一顆或嗶聲幾長幾短、這台機器裡有沒有敏感資料。

升級與通報的正式流程見 [[100-02-09-svc-維運-事件處理與升級流程]]
與 [[100-02-10-guide-維運-故障排除方法論]]。
