# 計算機網路 常見故障排除

> [!abstract] 怎麼用這份手冊
> - 依「你看到什麼症狀」查，不是依「這屬於什麼技術」查
> - 找到症狀 → 看判斷分流 → 照處置步驟做 → 想懂原理再點進原文
> - ★★★★ 緊急時直接跳到最下面的「一頁式急救卡」
> - ★★★★ 本章的核心是**分層**：先回答「這是第幾層的問題」，層定位錯了後面全是白做工

| ★★★★ 一整層樓斷網、燈號正常 | 上行線斷、上聯埠設定被改、DHCP 掛了 | `show interfaces status`（交換器） | [[010-02-16-guide-網概-VLAN與網路分段]] |
| ★★★★ 電腦搬個位置就上不了網 | **那個網路孔在別的 VLAN** | `show ethernet-switching interfaces` | [[010-02-16-guide-網概-VLAN與網路分段]] |
| ★★★ 同 VLAN 內通、跨 VLAN 不通 | 沒有第 3 層介面，或沒開路由 | `ip route show default` + 交換器 `show vlans` | [[010-02-16-guide-網概-VLAN與網路分段]] |
| ★★★ 同網段 ping 不到、`ip neigh` 是 `<incomplete>` | ARP 沒解析成功（對方不在、VLAN 不同） | `ip neigh show 對方IP` | [[010-02-05-guide-網概-MAC位址與交換器]] |
| ★★★★ 系統跳「偵測到 IP 位址衝突」 | 靜態 IP 撞進 DHCP 池 | `arp -a \| grep IP` 看幾個 MAC | [[010-02-06-guide-網概-IP位址與子網路]] |
| ★★★ 同網段可通、跨網段全不通 | 沒有預設閘道，或閘道設錯 | `ip route show default` | [[010-02-07-guide-網概-路由與封包旅程]] |
| ★★★★ 小檔案傳得過去、大檔案就卡住 | MTU／PMTU 黑洞 | `ping -M do -s 1472 目標` | [[010-02-07-guide-網概-路由與封包旅程]] |
| ★★★★ 網頁很慢但不是不通 | 分不清是 DNS、延遲、TTFB 還是下載 | `curl -w` 看五段耗時 | [[010-02-14-guide-網概-一個網頁請求的完整旅程]] |
| ★★★★ Gigabit 只跑 100M；或慢到不可思議＋`errors` 暴增 | 線材是 Cat5／協商失敗；或 **Duplex Mismatch** | `sudo ethtool eth0 \| grep -E 'Speed\|Duplex'` | [[010-02-04-guide-網概-線材與實體層]] |
| ★★★ Wi-Fi 連得上但沒有網路 | 拿到 APIPA、閘道／DNS 錯、Portal 沒過 | `nmcli device show wlp2s0` | [[010-02-15-guide-網概-無線網路與WiFi]] |
| ★★★ Wi-Fi 訊號滿格卻很慢 | 通道壅塞、AP 上行只有 100M、舊裝置拖累 | `nmcli -f CHAN device wifi list` | [[010-02-15-guide-網概-無線網路與WiFi]] |
| ★★★★ Wi-Fi 每隔幾分鐘斷一次又自己好 | 5GHz DFS 通道偵測到雷達 | 看 AP 日誌的 `radar detected` | [[010-02-15-guide-網概-無線網路與WiFi]] |
| ★★★ 紅字 `ERR_CERT_DATE_INVALID`；或電腦正常、手機憑證錯誤 | 憑證過期；或缺中繼憑證（沒用 fullchain） | `openssl s_client -connect 主機:443` | [[010-02-13-guide-網概-HTTP與HTTPS]] |
| ★★★ **502 Bad Gateway** | 反向代理連不到後端 | `systemctl status 後端服務` | [[010-02-13-guide-網概-HTTP與HTTPS]] |
| ★★★ **504 Gateway Timeout** | 後端太慢（不是網路） | `curl -w "TTFB:%{time_starttransfer}"` | [[010-02-13-guide-網概-HTTP與HTTPS]] |
| ★★★★ 埠轉發設好了外面還是連不進來 | 在 CGNAT 後面／防火牆／服務只聽本機 | `curl -s ifconfig.me` 比對 WAN IP | [[010-02-08-guide-網概-NAT與私有位址]] |
| ★★★★ 全機關同時斷網、ping 閘道卻通 | 對外線路斷、或 NAT conntrack 表爆滿 | `dmesg \| grep -i conntrack` | [[010-02-08-guide-網概-NAT與私有位址]] |
| ★★★★ `CLOSE_WAIT` 持續累積、`Too many open files` | 應用程式沒關閉連線（程式 bug） | `ss -tanp state close-wait` | [[010-02-09-guide-網概-TCP與UDP]] |
| ★★★ 只有某個網站特別慢，其他正常 | ISP 之間互連不良（路由不佳） | `mtr -n 那個網站` | [[010-02-02-guide-網概-ISP與上網方式]] |
| ★★★★★ 被導到奇怪的網站、網銀出現憑證警告 | **DNS 被竄改（資安事件）** | `cat /etc/resolv.conf` + `cat /etc/hosts` | [[010-02-18-guide-網概-網路安全基礎]] |
| ★★★★ traceroute 從某一跳開始全是 `* * *` | 那一段真的斷了（中間偶爾 `*` 是正常的） | `traceroute -n 目標` | [[010-02-17-guide-網概-網路排錯入門]] |

## 依情境展開

> [!tip] ★★★ 動手前先問這兩題
> **① 什麼時候開始的？② 在此之前有什麼變動？**
> 九成的突發故障來自一個變動 —— 搬位置、裝軟體、廠商來過、有人動了機櫃。
> 第 ② 題常常直接給你答案，比跑十個指令都快。
> → 原理詳見 [[010-02-17-guide-網概-網路排錯入門]]

### ★★★★★ 情境一：一個人「完全不能上網」，旁邊的人都正常

**現象**：使用者說「網路壞掉了」。瀏覽器顯示
`ERR_INTERNET_DISCONNECTED` 或 `無法連上這個網站`，
Windows 工作列的網路圖示可能有一個黃色驚嘆號或紅色叉叉。

**判斷分流**：★★★★ 這是全章的總入口，**跑五步驟 ping，第一個失敗的那一步就是問題所在的層**。

```bash
ping -c2 127.0.0.1        # ① 本機 TCP/IP 堆疊
ping -c2 192.168.1.10     # ② 自己的網卡（換成自己的 IP）
ping -c2 192.168.1.1      # ③ 預設閘道
ping -c2 8.8.8.8          # ④ 對外網路（純 IP，避開 DNS）
ping -c2 www.google.com   # ⑤ DNS 解析
```

- 看到 ① 就失敗 → 作業系統的網路堆疊壞了（**極罕見**）。Windows `netsh int ip reset` 後重開機
- 看到 ② 失敗 → **網卡或驅動程式**。裝置管理員／`ip link`；換一張網卡對照
- 看到 ③ 失敗 → **第 1／2／3 層**：線、交換器埠、VLAN、IP 遮罩。往下走第 1 步
- 看到 IP 是 `169.254.x.x` → 跳到情境二
- 看到 ④ 失敗但 ③ 通 → 問題在閘道之外：路由、NAT、對外線路。跳到情境十三
- 看到 ⑤ 失敗但 ④ 通 → **純 DNS 問題**，跳到情境三
- 看到 ①～⑤ 全通 → 網路是好的，問題在應用層。跳到情境五

**處置步驟**（卡在 ③ 的走這條，這是最常見的）：

【1】確認實體層真的通了。

```bash
ip -br link show
```

預期輸出：

```text
enp3s0    UP    00:1a:2b:3c:4d:5e <BROADCAST,MULTICAST,UP,LOWER_UP>
                                                          ^^^^^^^^ ★★★★ 有 LOWER_UP 才代表線是通的
```

只有 `UP` 沒有 `LOWER_UP`，或 `ethtool` 顯示 `Link detected: no` → 線／埠的問題，跳到【2】。

【2】★★★ **換線、換孔、換機**，一次只換一個。

```bash
# 換一條確定是好的成品跳線
# 換牆上另一個網路孔
# 把同一條線接到另一台確定正常的電腦
```

三者之中哪一個換了就好，問題就在哪。★★★ 這比看設定快得多，也便宜得多。

【3】確認自己的 IP 與遮罩跟閘道是同一個網段。

```bash
ip -br addr show enp3s0
ip route show default
```

```text
enp3s0    UP    192.168.1.10/24
default via 192.168.1.1 dev enp3s0        # ★★★★ 沒有這行就永遠出不了自己的網段
```

★★★★ `192.168.1.10/24` 配 `10.0.0.1` 的閘道是**永遠不會通**的 —— 這是設定錯誤，不是故障。

【4】確認 ARP 有解析到閘道。

```bash
ip neigh show 192.168.1.1
```

```text
192.168.1.1 dev enp3s0 lladdr 00:aa:bb:cc:dd:ee REACHABLE   # ★★★ REACHABLE 才算通
192.168.1.1 dev enp3s0  INCOMPLETE                          # ★★★★ 沒人回應 → 多半是 VLAN 錯了
```

`INCOMPLETE` → 你跟閘道**不在同一個廣播網域**，跳到情境八。

【5】前面都正常還是不通 → 到交換器上看那個埠。

```bash
# JunOS
show interfaces ge-0/0/12 extensive | match "error|drop|Link"
show ethernet-switching interfaces ge-0/0/12
```

★★★★ 特別確認該埠有沒有被埠安全機制關掉（JunOS 顯示為 `disabled`／Cisco 顯示 `err-disabled`）。

**原理**：五步驟 ping 是把 OSI 由下而上走一遍，每一步通過就永久排除一整層。
　→ 原理詳見 [[010-02-17-guide-網概-網路排錯入門]]、[[010-02-03-guide-網概-網路分層模型]]

**預防**：★★★ 每一條線兩端貼標籤（寫明對端位置），配線圖保持更新；
使用者座位異動一律當成「網路異動」處理，先確認新孔的 VLAN。
→ [[040-02-08-guide-機房-結構化佈線與標籤規範]]

### ★★★★★ 情境二：IP 變成 `169.254.x.x`，重開機也一樣

**現象**：

```text
C:\> ipconfig
   自動設定 IPv4 位址 . . . . . . . : 169.254.183.44
   子網路遮罩 . . . . . . . . . . . : 255.255.0.0
   預設閘道 . . . . . . . . . . . . :                  ← ★★★★ 空的
```

Windows 網路圖示顯示「無法辨識的網路」／「沒有網際網路存取」。

**判斷分流**：★★★★ `169.254.x.x` 是 **APIPA**，意思是「我喊了 DHCP，但沒有任何人回我」。
它等同於沒有 IP。先分辨是「喊不出去」還是「沒人回」。

```bash
sudo ethtool enp3s0 | grep -E 'Link detected'
sudo dhclient -v enp3s0 2>&1 | tail -10
```

- 看到 `Link detected: no` → **實體層**問題，回情境一【2】
- 看到 `DHCPDISCOVER` 一直重送、完全沒有 `DHCPOFFER` → 廣播沒到達伺服器，往下走第 1 步
- 看到 `DHCPOFFER` 但沒有 `DHCPACK` → 位址衝突或伺服器拒絕，看 DHCP 伺服器日誌
- 看到拿到 IP 但**網段跟同事不一樣** → 接到錯的 VLAN，跳到情境八

**處置步驟**：

【1】★★★★ 依這五個原因逐一排除（依現場發生機率排序）：

| # | 原因 | 怎麼確認 |
| --- | --- | --- |
| 1 | ★★★ **接到錯誤的 VLAN**（那個 VLAN 沒有 DHCP） | 交換器 `show ethernet-switching interfaces ge-0/0/x` |
| 2 | ★★ 網路線沒插好／埠被停用 | `ethtool` 看 `Link detected` |
| 3 | ★★★ **位址池發完了** | DHCP 伺服器日誌出現 `no free leases` |
| 4 | ★★★★ **DHCP 伺服器掛了** | 伺服器上 `systemctl status isc-dhcp-server` |
| 5 | ★★★ **跨網段但沒設 Relay** | 交換器 `show configuration forwarding-options dhcp-relay`（Cisco 為 `ip helper-address`） |

【2】臨時止血：手動給一個確定沒被使用的 IP，先讓人能上班。

```bash
# ★★★ 先確認這個 IP 沒人在用，再設下去
ping -c2 192.168.1.211        # 要「不通」才可以用
sudo ip addr add 192.168.1.211/24 dev enp3s0
sudo ip route add default via 192.168.1.1
```

★★★★ 這只是止血。**一定要記錄下來並在修好 DHCP 後撤掉**，
否則下次 DHCP 把這個 IP 發給別人就變成情境十一（IP 衝突）。

【3】在網段內抓 DHCP 封包，確認伺服器到底有沒有回應。

```bash
sudo tcpdump -i enp3s0 -n port 67 or port 68
```

```text
IP 0.0.0.0.68 > 255.255.255.255.67: BOOTP/DHCP, Request from 00:1a:2b:...   # 只有這行 = 沒人回你
IP 192.168.1.1.67 > 192.168.1.10.68: BOOTP/DHCP, Reply                       # ★★★ 有 Reply 才算有伺服器
```

【4】★★★★★ 如果抓到的 `Reply` 來源**不是你認識的那台 DHCP** ——
有人在網路上接了自己的分享器（Rogue DHCP）。這已經是資安事件，跳到「什麼時候該停手求援」。

**原理**：DHCP 靠廣播運作，廣播不跨網段；拿不到就退回 APIPA 自己挑一個 link-local 位址。
　→ 原理詳見 [[010-02-12-guide-網概-DHCP自動取得設定]]

**預防**：★★★★ 伺服器與網路設備一律**手動固定 IP**，不要靠 DHCP；
DHCP 池必須排除靜態區段；部署第二台 DHCP（分割位址池或 failover）；
使用者埠啟用 DHCP Snooping 擋掉假 DHCP。

### ★★★★★ 情境三：「網頁打不開，但 LINE 還能用」

**現象**：瀏覽器顯示 `DNS_PROBE_FINISHED_NXDOMAIN` 或
`無法連上這個網站　找不到 www.example.gov.tw 的伺服器 IP 位址`，
但通訊軟體、已經連線中的 VPN、遠端桌面都正常。

**判斷分流**：★★★★ 這個組合幾乎可以直接斷定是 **DNS**。用兩行確認：

```bash
ping -c2 8.8.8.8              # 純 IP
dig +short www.example.gov.tw # 名稱解析
```

- 看到 ping 通、`dig` 沒有輸出 → **確定是 DNS**，往下走
- 看到 ping 也不通 → 不是 DNS，回情境一
- 看到 `dig` 有回 IP、網頁還是打不開 → DNS 沒問題，跳到情境四

**處置步驟**：

【1】★★★★ 換一台 DNS 對照，一行就分清楚是「自家 DNS 壞了」還是「記錄本身有問題」。

```bash
dig @8.8.8.8 +short www.example.gov.tw
dig @1.1.1.1 +short www.example.gov.tw
```

| 你看到 | 判斷 |
| --- | --- |
| ★★★★ 公用 DNS 查得到、系統 DNS 查不到 | **自家 DNS 伺服器的問題** |
| ★★★ 兩邊都查不到，但問權威查得到 | **快取還沒更新**，等 TTL |
| ★★ 連權威都查不到 | 記錄根本沒設，或網域過期 |
| ★★★★ 查得到但 **IP 不是你認識的** | **DNS 被劫持**，跳到求援段落 |

【2】確認你實際在用哪一台 DNS。

```bash
resolvectl status | grep -A2 'DNS Servers'
cat /etc/resolv.conf
```

```text
nameserver 192.168.1.1        # ★★★ 這台就是實際在幫你查的
```

【3】清快取後重試（三層快取都要清）。

```bash
sudo resolvectl flush-caches     # ★★ 系統
# 瀏覽器：Ctrl+F5，或開無痕視窗
```

```powershell
ipconfig /flushdns
```

【4】看錯誤碼決定往哪修。

| 回應 | 意義 | 往哪修 |
| --- | --- | --- |
| ★★★ `NXDOMAIN` | 網域真的不存在 | 檢查拼字；`dig NS 網域` 看網域是否還有效 |
| ★★★ `SERVFAIL` | 伺服器內部錯誤或 DNSSEC 驗證失敗 | 換一台 DNS 測；檢查 DNSSEC 設定 |
| ★★★★ 有時通有時不通 | **只開了 UDP 53、沒開 TCP 53** | 防火牆兩個都要放行（大回應會改走 TCP） |
| ★★ 查詢超過 500ms | DNS 太遠或負載高 | 換近的解析器；查 DNS 伺服器負載 |

【5】內部主機名稱解析不到（`server01` 打不到但 `server01.local.gov.tw` 可以）
→ `search` domain 沒設。檢查 DHCP 的 option 15／`/etc/resolv.conf` 的 `search` 行。

**原理**：DNS 是網頁請求的第 ③ 步，它壞掉時第 ①～② 步（實體、路由）完全正常，
所以症狀跟斷網一模一樣，但 IP 直連的服務不受影響。
　→ 原理詳見 [[010-02-11-guide-網概-DNS網域名稱系統]]、[[010-02-14-guide-網概-一個網頁請求的完整旅程]]

**預防**：★★★ 內部至少兩台 DNS，DHCP 同時發下去；
對 DNS 做健康檢查監控（查一筆固定記錄，失敗就告警）；
網站搬遷前先把 TTL 降到 300 秒。→ [[100-01-04-guide-日誌-健康檢查與可用性監控]]

### ★★★★ 情境四：DNS 查得到 IP，網頁還是打不開

**現象**：`dig` 有回 IP，`ping` 那個 IP 也通，但瀏覽器顯示紅字憑證警告、
`502 Bad Gateway`、`504 Gateway Timeout`，或轉圈到逾時。

**判斷分流**：★★★★ 網路層已經清白，用 `curl -v` 一次看到卡在哪一段。

```bash
curl -sv https://www.example.gov.tw -o /dev/null 2>&1 | head -25
```

- 看到 `Connection refused` → 那個埠沒有服務在聽，跳到情境五
- 看到卡在 `Trying 203.66.x.x...` 到逾時 → 封包被靜默丟棄，跳到情境五
- 看到 `SSL certificate problem` → 憑證問題，往下走第 1 步
- 看到 `HTTP/2 502` 或 `504` → 連到了，但後端有問題，往下走第 2 步
- 看到 `HTTP/2 200` 但畫面破版 → 前端資源或混合內容問題，看瀏覽器 F12 Console

**處置步驟**：

【1】憑證問題：先看到期日與 SAN。

```bash
echo | openssl s_client -connect www.example.gov.tw:443 -servername www.example.gov.tw 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

```text
notAfter=Aug 20 08:00:00 2026 GMT        # ★★★★ 已經過期就是這裡
X509v3 Subject Alternative Name:
    DNS:example.gov.tw, DNS:www.example.gov.tw   # ★★★ 你打的網域必須列在這裡
```

| 瀏覽器訊息 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ `NET::ERR_CERT_DATE_INVALID` | 憑證過期 | 立刻續期；**補上自動續期與到期監控** |
| ★★★ `ERR_CERT_COMMON_NAME_INVALID` | SAN 不含這個網域 | 重簽含正確 SAN 的憑證 |
| ★★★ `ERR_CERT_AUTHORITY_INVALID` | 自簽或缺中繼憑證 | 部署 `fullchain.pem`，不是 `cert.pem` |
| ★★★★ **電腦正常、手機紅字** | 缺中繼憑證（電腦有快取、手機沒有） | 同上，一定要用 fullchain |

【2】5xx：★★★★ **看對日誌**。502／504 是反向代理在講後端的狀況，
500 是應用程式自己的錯誤。

```bash
sudo tail -50 /var/log/nginx/error.log      # 502 / 504 看這裡
sudo journalctl -u 你的後端服務 -n 50       # 500 的真正原因在這裡
```

| 狀態碼 | 意義 | 先看哪裡 |
| --- | --- | --- |
| ★★★ **502** | 反向代理**連不到**後端 | 後端服務有沒有起來、socket 路徑、埠、權限 |
| ★★★ **504** | 後端**太慢**（不是網路） | 後端日誌找慢查詢；調 `proxy_read_timeout` 只是遮住問題 |
| ★★ 503 | 後端過載或維護中 | worker 數、CPU／記憶體 |
| ★★★ 500 | 應用程式錯誤 | ★★★★ **應用程式日誌**，不是 Nginx 日誌 |
| ★★ 404 但檔案存在 | 路徑大小寫、rewrite、`root` 設錯 | Linux 區分大小寫 |

【3】確認不是被中間設備擋掉（機關常見）：
`curl -v https://網址 2>&1 | grep -iE 'blocked|forbidden|proxy|policy'`。
★★★ 回了一頁「本站已被封鎖」代表是內容過濾設備，不是網站壞了。

**原理**：DNS 只是第 ③ 步，後面還有 TCP 交握、TLS 交握、伺服器處理三大關卡，
任何一關失敗看到的都是「網頁打不開」。
　→ 原理詳見 [[010-02-13-guide-網概-HTTP與HTTPS]]、[[010-02-14-guide-網概-一個網頁請求的完整旅程]]

**預防**：★★★★ 憑證到期監控是必做項目（提前 30 天告警）；
自動續期後一定要驗證真的換上去了，不要只看 cron 有沒有跑。

### ★★★★★ 情境五：ping 得通，服務就是連不上

**現象**：`ping 192.168.1.50` 回應正常，但

```text
$ mysql -h 192.168.1.50 -u app -p
ERROR 2003 (HY000): Can't connect to MySQL server on '192.168.1.50' (111)
```

或瀏覽器一直轉圈到 `ERR_CONNECTION_TIMED_OUT`。

**判斷分流**：★★★★ ping 走 ICMP（第 3 層），只證明**主機活著**，
完全不證明那個服務有人在聽。用 `nc` 測第 4 層才是真答案，
而且**失敗的方式**就直接告訴你問題在哪。

```bash
nc -zv 192.168.1.50 3306
```

- 看到 `succeeded!` → 網路全程沒問題，問題在應用層（帳密、設定、憑證）
- 看到 **立刻** `Connection refused` → 封包**有到對方**，但那個埠沒有程序在聽。往下走第 1 步
- 看到 **卡住到逾時** → 封包被**靜默丟棄**，通常是防火牆 drop。往下走第 3 步
- 看到 `No route to host` → 路由問題，回情境一【3】

★★★★ **記住這個對照**，它能省掉一半的排錯時間：

| 失敗方式 | 對方回了什麼 | 意義 |
| --- | --- | --- |
| ★★★★ **立刻** `Connection refused` | TCP RST | 主機在、**服務沒起來或聽在別的埠** |
| ★★★★ **等到逾時** | 什麼都沒回 | **防火牆 drop**，或路由不通 |
| ★★ `Connection reset by peer` | 連上後被切 | 通常是應用層拒絕（來源 IP 白名單、TLS 版本） |

**處置步驟**：

【1】★★★★ 到伺服器上看它到底聽在哪個位址 —— 這是這個情境的頭號原因。

```bash
sudo ss -tulpn | grep 3306
```

```text
tcp LISTEN 0 151 127.0.0.1:3306  0.0.0.0:*  users:(("mysqld",pid=812,fd=22))
                ^^^^^^^^^ ★★★★ 只監聽 127.0.0.1，外面永遠連不到
tcp LISTEN 0 151 0.0.0.0:3306    0.0.0.0:*  users:(("mysqld",pid=812,fd=22))
                ^^^^^^^ 所有介面都聽
```

改設定檔的 `bind-address`（MySQL）／`listen`（Nginx）／`ListenAddress`（sshd）。

> [!danger] ★★★★★ 改成 `0.0.0.0` 之前先想清楚
> 把資料庫從 `127.0.0.1` 改成 `0.0.0.0` 等於**把它開放給所有網路介面**。
> ★★★★★ 一定要**同時**用防火牆限制來源 IP，否則 3306／5432／6379 會在數小時內被掃到。
> 更安全的做法是綁內網 IP，或走 SSH 隧道。
> → [[090-02-02-guide-防火牆-ufw基礎與實務]]

【2】服務根本沒起來。

```bash
systemctl status mysql
sudo journalctl -u mysql -n 30 --no-pager
```

【3】逾時 → 找出是哪一段擋掉。★★★ 用 TCP 版 traceroute 直接看斷在第幾跳。

```bash
sudo traceroute -T -p 3306 -n 192.168.1.50
```

最後成功到達的那一跳的**下一台設備**，就是擋掉的地方。

【4】兩端的防火牆都要看，不要只看伺服器那端。

```bash
sudo ufw status verbose
sudo nft list ruleset | head -40
```

【5】★★ UDP 服務（DNS、NTP、SNMP、syslog）**不能用 `nc -zu` 判斷** ——
UDP 沒有交握，測不出來。改用該服務自己的協定測：

```bash
dig @192.168.1.53 example.com     # 測 DNS
ntpdate -q 192.168.1.53           # 測 NTP
```

**原理**：ping 在第 3 層、服務在第 4／7 層；`Connection refused` 與逾時的差別
來自對方是「回了 RST」還是「什麼都沒回」。
　→ 原理詳見 [[010-02-09-guide-網概-TCP與UDP]]、[[010-02-10-guide-網概-連接埠與應用層協定]]

**預防**：★★★ 服務上線檢查表固定加兩項：`ss -tulpn` 確認監聽位址、
從**另一台機器**測一次埠。只在本機 `curl localhost` 測是最常見的漏檢。

### ★★★★★ 情境六：整層樓的人同時說「網路斷了」

**現象**：同一層樓、同一個網段的人幾乎同時申告。有人完全不能上網，
有人拿到 `169.254.x.x`，有人說「內部系統可以、外面不行」。

**判斷分流**：★★★★ 先分「這一層自己壞了」還是「上面壞了」。**先去現場看燈**。

```text
到樓層機櫃看該層交換器：
  ① 電源燈不亮            → 停電／電源供應器壞／被拔掉
  ② 所有埠燈同步狂閃      → ★★★★★ 廣播風暴，跳到情境七
  ③ 上聯埠（Uplink）燈不亮 → 上行線斷，往下走第 1 步
  ④ 燈號一切正常          → 設定或上層問題，往下走第 2 步
```

**處置步驟**：

【1】上行線：先用最便宜的方法確認。

```bash
# 在交換器上
show interfaces ge-0/0/47 extensive | match "Link|error|drop"
```

★★★ 把上行線換到交換器另一個埠測 —— 兩分鐘就能分辨是「線斷」還是「埠壞」。

【2】燈正常卻不通：從一台受影響的電腦跑五步驟 ping，看斷在哪一層。

```bash
ping -c2 192.168.30.1     # 該網段閘道
ping -c2 8.8.8.8
```

| 現象 | 判斷 | 往哪查 |
| --- | --- | --- |
| ★★★★ 整層都拿不到 IP | DHCP 掛了、或 Relay 設定被改 | 情境二 |
| ★★★★ 拿得到 IP、ping 不到閘道 | 上聯埠的 Trunk 掉了那個 VLAN | 情境八 |
| ★★★ ping 得到閘道、出不去 | 上層路由／防火牆／對外線路 | 情境十三 |
| ★★★ 內部通、外部不通 | DNS 或對外線路 | 情境三、情境十三 |

【3】★★★★ 問「最近有沒有人動過機櫃或接線」。這一題常常直接結案 ——
廠商換設備沒還原設定、清潔人員碰掉線、有人把兩個網孔接在一起（跳情境七）。

【4】★★★ 如果是**全機關**而不只一層樓 → 跳到情境十三。
判斷方法：問另一層樓的同事，或從伺服器機房的機器測一次。

**原理**：故障範圍就是最好的定位工具 —— 一個人是終端問題、一層樓是該層交換器、
全機關是對外線路或核心設備。
　→ 原理詳見 [[010-02-17-guide-網概-網路排錯入門]]、[[040-01-17-guide-網路設備-交換器故障排除]]

**預防**：★★★★ 核心與樓層交換器之間做鏈路聚合（LAG）並走**不同實體路徑**；
交換器接 UPS；設定檔每次異動後備份。
→ [[040-01-16-guide-網路設備-鏈路聚合與STP]]、[[040-01-09-svc-Juniper-設定備份與韌體升級]]

### ★★★★★ 情境七：交換器所有燈同步狂閃、整個網段癱瘓

**現象**：★★★★★ 網路不是「不通」而是「時通時斷、慢到不能用」，
交換器面板上**所有埠的燈同時、同節奏地狂閃**。
`ping` 閘道會看到大量逾時夾雜幾個回應。這通常發生在有人剛動過接線之後。

**判斷分流**：★★★★★ 這幾乎可以直接斷定是**網路迴圈造成的廣播風暴**。

```bash
# 在任何一台還能操作的機器上
sudo tcpdump -i enp3s0 -n -c 200 broadcast
```

- 看到每秒數千筆廣播、同一個來源不斷重複 → **確定是廣播風暴**
- 在交換器上看到同一個 MAC 在多個埠之間跳動 → 確定有迴圈

```text
# JunOS
show ethernet-switching table | match 00:1a:2b:3c:4d:5e
show spanning-tree interface        # ★★★★ 埠狀態一直在 Learning/Forwarding 之間變化 = 拓樸不穩
```

**處置步驟**：★★★★★ 目標是**先止血**，不要先追究責任。

【1】★★★★★ 找出迴圈並拔掉。最快的做法是**依現場線索**，不是逐埠測試。

```text
① 問：剛剛誰動了線？哪個房間？   ← ★★★★ 九成在這裡就找到了
② 看：哪一區的網孔最近有施工／搬桌子
③ 看交換器：哪兩個埠的流量與燈號完全同步
```

【2】止血：★★★★ 從**上聯埠往下**逐段拔線，把網路切成兩半，
哪一半安靜下來，迴圈就在另一半。二分法最多幾次就能定位。

【3】找到後**拔掉重複的那條線**，網路通常在數秒內恢復。

【4】恢復後補上防護（★★★★ 這一步不做，下次還會發生）。

```junos
# ★★ 把所有使用者埠收成一個 interface-range
set interfaces interface-range access-ports member-range ge-0/0/1 to ge-0/0/24

# ★★★★ 廣播／群播／未知單播超過 5% 埠頻寬就抑制
set forwarding-options storm-control-profiles sc-5 all bandwidth-percentage 5
set interfaces interface-range access-ports unit 0 family ethernet-switching storm-control sc-5

# ★★★★ 使用者埠宣告為 edge，並讓 edge 埠一收到 BPDU 就關閉
set protocols rstp interface ge-0/0/1.0 edge
set protocols rstp bpdu-block-on-edge

# ★★★★★ 送出前先比對；10 分鐘內沒再 commit 一次就自動回滾
show | compare
commit confirmed 10
```

被 BPDU 保護關掉的埠，排除問題後手動解除：

```junos
clear ethernet-switching bpdu-error interface ge-0/0/1.0
```

> [!info]- Cisco IOS 對照 ★★★★
> ```cisco
> interface range Gi0/1 - 24
>  spanning-tree portfast
>  spanning-tree bpduguard enable     ! 收到 BPDU 就關閉該埠
>  storm-control broadcast level 5    ! 廣播超過 5% 頻寬就抑制
> ```
> ★★★ IOS 打完立即生效，沒有 `commit confirmed` 的自動回滾可以救 ——
> 遠端操作時特別小心。

> [!warning] 未實機驗證
> 本段 JunOS／IOS 設定依官方文件撰寫，未在實機驗證。實作前請對照你手上設備的版本。

**原理**：第 2 層沒有 TTL，廣播封包在迴圈裡會無限循環並不斷倍增，
瞬間吃光交換器的轉送能力與所有埠的頻寬。
　→ 原理詳見 [[010-02-05-guide-網概-MAC位址與交換器]]、[[010-02-16-guide-網概-VLAN與網路分段]]

**預防**：★★★★ 所有使用者埠一律開 BPDU 保護＋storm-control；
未使用的網孔**停用**並丟到黑洞 VLAN；牆上網孔不要成對開放給使用者自行接線。
→ [[040-01-08-guide-Juniper-埠設定與安全]]、[[040-01-13-guide-Cisco-埠設定與安全]]

### ★★★★ 情境八：電腦搬個位置就上不了網（VLAN 相關）

**現象**：使用者說「我只是把電腦搬到隔壁座位／換了一個網孔」，
然後拿到 `169.254.x.x`，或拿到 IP 但**網段跟同事不一樣**，
或者同網段互通但跨部門的伺服器完全連不到。

**判斷分流**：★★★★ 先看拿到的 IP 屬於哪個網段。

```bash
ip -br addr show enp3s0
```

- 看到 `169.254.x.x` → 那個孔在一個**沒有 DHCP 的 VLAN**（或是黑洞 VLAN）
- 看到 IP 網段跟同事不同（例如同事 `10.10.30.x`、你 `10.10.99.x`）→ **接到錯的 VLAN**
- 看到 IP 正確、同 VLAN 通、跨 VLAN 不通 → 第 3 層路由問題，往下走第 3 步
- 看到某個 VLAN 在**這台交換器**通、跨到另一台就不通 → Trunk 沒帶那個 VLAN，往下走第 4 步

**處置步驟**：★★★ VLAN 排錯就四步，照順序走。

【1】★★★★（JunOS 專屬）**我到底 commit 了沒？**

```junos
show | compare
```

在設定模式下有輸出 → 設定**還沒生效**。這是 JunOS 的頭號陷阱：
「設定打完了卻完全沒作用」十次有八次是這個。

【2】這個埠是 access 還是 trunk？屬於哪個 VLAN？

```junos
show ethernet-switching interfaces ge-0/0/12
```

【3】跨 VLAN 不通 → 要有第 3 層介面才會路由。

```junos
show vlans
show interfaces terse | match irb
```

- ★★★ `irb` 介面存在但是 `down` → **那個 VLAN 裡沒有任何 up 的成員埠**，先讓一個埠接上
- ★★★ 沒有 `irb` → 建立並用 `set vlans <名稱> l3-interface irb.N` 綁定
- ★★★ 三層交換器上做過了還是不通（Cisco）→ **忘了 `ip routing`**，這是 IOS 最常見的疏漏

【4】VLAN 跨不到另一台交換器 → Trunk 沒帶。

```junos
show configuration interfaces ge-0/0/23 | display set
```

```text
set interfaces ge-0/0/23 unit 0 family ethernet-switching vlan members [ v10 v20 v30 ]
                                                                                  ^^^ ★★★ 缺哪個就補哪個
```

★★★ 另外確認 `native-vlan-id` 有沒有同時列進 `vlan members` ——
沒列進去的話 Trunk 上的 untagged 封包會全部消失。

【5】★★ 虛擬機拿不到正確 VLAN 的 IP → 問題在 hypervisor 的 port group VLAN ID，
不在實體交換器。

**原理**：VLAN 是把一台交換器切成多個獨立的廣播網域；
不同 VLAN 之間**天生不通**，要靠第 3 層設備才能互通。
　→ 原理詳見 [[010-02-16-guide-網概-VLAN與網路分段]]、[[040-01-03-guide-網路設備-VLAN概念與規劃]]

**預防**：★★★★ 每個網孔的 VLAN 對照表要文件化並貼在機櫃上；
埠描述（`description`）寫清楚對應的房間與用途；
座位異動流程納入「確認網孔 VLAN」這一項。
→ [[040-01-18-guide-網路設備-網路設備盤點與文件化]]

### ★★★★ 情境九：網頁很慢，但不是不通

**現象**：網頁最後會開，只是要等三、五秒甚至更久。使用者說「網路很慢」。
★★★★ 這是最容易被誤判的一種 —— 使用者說的「網路慢」有一半根本不是網路的問題。

**判斷分流**：★★★★ 一行指令把「慢」拆成五段，看哪一段大。

```bash
curl -w "DNS:%{time_namelookup}s TCP:%{time_connect}s TLS:%{time_appconnect}s TTFB:%{time_starttransfer}s 總計:%{time_total}s\n" \
     -o /dev/null -s https://www.example.gov.tw
```

```text
DNS:0.021s TCP:0.045s TLS:0.098s TTFB:1.842s 總計:2.130s
                                  ^^^^^^^^^ ★★★★ TTFB 這麼大 = 伺服器慢，不是網路慢
```

| 哪一段大 | 問題在 | 往哪走 |
| --- | --- | --- |
| ★★ `time_namelookup` | **DNS 查詢慢** | 換近一點的解析器；查 DNS 負載 |
| ★★★ `time_connect` − `namelookup` | **網路延遲**（RTT） | 往下走第 1 步 |
| ★★ `time_appconnect` − `connect` | TLS 交握 | 開 TLS 1.3、Session Resumption |
| ★★★★ **`time_starttransfer` − `appconnect`** | **伺服器處理（TTFB）** | ★★★★ 這不是網路問題，去查應用程式與資料庫 |
| ★★★ `time_total` − `starttransfer` | **下載時間／頻寬** | 往下走第 2 步 |

★★★ 健康門檻：DNS < 20ms、TCP（國內）< 20ms、TLS < 50ms、**TTFB < 200ms**、完整載入 < 2s。

**處置步驟**：

【1】延遲高或掉包 → 用 `mtr` 找出是哪一跳。

```bash
mtr -n -c 50 8.8.8.8
```

```text
HOST              Loss%   Snt   Last   Avg  Best  Wrst StDev
 1. 192.168.1.1    0.0%    50    1.2   1.3   1.0   2.1   0.2
 3. 168.95.98.254 12.0%    50   12.3  13.1  11.9  45.2   4.8    # ★★★ 從這跳開始掉
 4. 8.8.8.8       12.0%    50   25.8  26.5  25.1  58.9   5.2    # ★★★ 後面也掉 → 真的有問題
```

- ★★★ **從某一跳開始持續掉包、後面也都掉** → 那一跳有問題
- ★★★ 只有中間某一跳掉、**後面都正常** → 那台設備對 ICMP 限速，**這是正常的**

【2】★★★★ 先排除實體層 —— 這是「假故障」的最大來源。

```bash
sudo ethtool enp3s0 | grep -E 'Speed|Duplex|Link detected'
ip -s link show enp3s0
```

```text
Speed: 100Mb/s        # ★★★★ Gigabit 網卡只協商到 100M → 線材是 Cat5 或壓接不良
Duplex: Half          # ★★★★ 雙工不符：網路「會通但慢到不可思議」，errors 不斷增加
RX: bytes packets errors dropped
    ...     ...    1234      56       # ★★★ errors 持續增加就是實體層問題
```

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ Gigabit 只跑 100M | 線材是 Cat5、水晶頭壓接不良、面板品質差 | 換 Cat5e/Cat6 成品跳線對照測試 |
| ★★★★ **慢到不可思議＋errors 暴增** | **Duplex Mismatch** | ★★★★ 兩端都設**自動協商**；不要一端自動一端手動 |
| ★★★ 新裝 10G 網卡只跑 1G | 線材是 Cat6（10G 限 55m）或 Cat5e | 換 Cat6a 或改光纖 |
| ★★★ 時通時不通、封包錯誤 | 壓接不良、接觸不良 | 換成品跳線；用測線器測 |
| ★★★ 光纖接收功率過低 | 端面髒、彎折、接頭沒插到底 | `ethtool -m` 讀 DOM；清潔並重插 |

【3】分辨是內網慢還是對外慢。

```bash
iperf3 -c 內部伺服器IP      # 內網速度
speedtest-cli              # 對外速度
```

- 內網快、對外慢 → 對外頻寬或 ISP 問題（跳情境十三）
- 內網也慢 → 內部網路問題（回【2】）

**原理**：「慢」有五個完全不同的來源（DNS、延遲、TLS、伺服器處理、頻寬），
用 `curl -w` 拆解才知道該找誰修。
　→ 原理詳見 [[010-02-14-guide-網概-一個網頁請求的完整旅程]]、[[010-02-04-guide-網概-線材與實體層]]

**預防**：★★★ 上線時就記錄一次正常值（TTFB、RTT、協商速度）當基準線；
沒有基準線就永遠只能靠感覺判斷「慢」。
→ [[100-01-03-guide-日誌-系統監控與告警]]

### ★★★★ 情境十：Wi-Fi 連得上，卻沒有網路

**現象**：手機／筆電顯示已連線到 SSID，但出現「已連線，無網際網路」，
或連上後什麼網頁都開不了。旁邊的人用同一個 SSID 卻正常。

**判斷分流**：★★★★ 「連得上」只代表**第 2 層認證過了**，
第 3 層（IP／閘道／DNS）完全是另一回事。

```bash
nmcli device show wlp2s0 | grep -E 'IP4.ADDRESS|IP4.GATEWAY|IP4.DNS'
```

- 看到 `169.254.x.x` 或完全沒有位址 → **DHCP 沒回應**，跳到情境二
- 看到有 IP 但**沒有 GATEWAY** → DHCP 的 option 3 沒發，或 AP 的 DHCP 設定錯
- 看到 IP／閘道都有、ping 閘道通、上不了網 → DNS 或訪客網路策略，跳到情境三
- 看到需要先開瀏覽器登入卻沒跳出來 → Captive Portal，手動開 `http://neverssl.com` 觸發
- 看到訊號很強但速度極慢 → 往下走第 3 步

**處置步驟**：

【1】確認連到的是**你以為的那個 SSID**（★★★ 機關常有 `GOV`／`GOV-Guest` 這種相似名稱）。

```bash
iw dev wlp2s0 link
```

```text
Connected to 00:11:22:33:44:55 (on wlp2s0)
        SSID: OFFICE-Guest          # ★★★★ 連到訪客網路，當然存取不到內部資源
        signal: -47 dBm             # ★★★ -50 ～ -65 為良好
```

【2】訪客網路連得上但存取不到內部系統 → ★★★ **這是設計如此，不是故障**。
訪客 VLAN 應該與內網隔離。請使用者改用內部 SSID 或 VPN。

【3】訊號滿格卻很慢，依這張表查：

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★ **AP 標 1200M 但只跑 90M** | AP 上行是 100M 埠或 Cat5 線 | 換 Gigabit 埠與 Cat6 線（回情境九【2】） |
| ★★★ 整個 Wi-Fi 都很慢 | 一台舊裝置（802.11b/g）拖累全體 | 停用低速率；舊裝置隔離到專用 SSID |
| ★★★ 公寓／密集辦公室極慢 | 2.4GHz 通道壅塞 | 改 5GHz；2.4GHz **只用 1／6／11** |
| ★★★ 10 台 AP 效能反而更差 | 通道寬度設 80/160MHz，通道不夠分 | 改成 20 或 40MHz |
| ★★★ 微波爐一開就斷 | 2.4GHz 被干擾 | 改用 5GHz |
| ★★★ 開會時大家連不上 | AP 連線數上限、通道壅塞 | 增設 AP；啟用 OFDMA（Wi-Fi 6） |

【4】★★★★ **每隔幾分鐘斷 1～10 分鐘又自己好** → 幾乎確定是 **DFS**。
5GHz 的 52～144 通道偵測到雷達訊號時，AP 必須立刻淨空該通道。

```text
在 AP 日誌搜尋：radar detected / DFS / channel change
解法：★★★★ 固定使用非 DFS 通道（36～48 或 149～165）
```

【5】走到另一個房間就斷線（漫遊不順）→ ★★★ **降低 AP 發射功率**並啟用 802.11k/v/r
（功率開太大，裝置會「捨不得」切換到更近的 AP）。

**原理**：Wi-Fi 只取代第 1／2 層，上面的 IP、閘道、DNS 全部照舊；
「訊號強」與「速度快」是兩件事。
　→ 原理詳見 [[010-02-15-guide-網概-無線網路與WiFi]]

**預防**：★★★★ 訪客 SSID 一律獨立 VLAN ＋ Client Isolation ＋ 防火牆規則；
企業內部 SSID 改用 802.1X，不要用共用 PSK（離職員工照樣連得上）。
→ [[090-05-13-guide-資安設備-網路存取控制NAC與802.1X]]

### ★★★★ 情境十一：同一個 IP 被兩台機器搶走（IP 衝突）

**現象**：

```text
Windows：偵測到 IP 位址衝突　—　此網路上的另一部系統與這部電腦有相同的 IP 位址
Linux：  kernel: IPv4: martian source / arp: 192.168.1.50 moved from aa:bb:.. to 11:22:..
```

症狀是**時通時不通**、遠端桌面連上去發現「不是那台機器」、
印表機列印出別人的文件。

**判斷分流**：★★★★ 一個 IP 對到兩個 MAC 就是鐵證。

```bash
sudo arping -c 4 -D -I enp3s0 192.168.1.50
```

```text
ARPING 192.168.1.50 from 0.0.0.0 enp3s0
Unicast reply from 192.168.1.50 [00:1A:2B:3C:4D:5E]  0.712ms
Unicast reply from 192.168.1.50 [52:54:00:AA:BB:CC]  0.804ms   # ★★★★ 兩個不同 MAC = 確定衝突
```

- 看到兩個以上不同 MAC 回應 → **確定 IP 衝突**，往下走
- 看到只有一個 MAC → 不是衝突，回情境一
- 看到 ARP 表裡**一個 MAC 對應多個 IP** → ★★★★ 這是 **ARP 欺騙**，不是衝突，跳到求援段落

**處置步驟**：

【1】用 MAC 的 OUI 前綴猜出是什麼設備，縮小搜尋範圍。

```bash
ip neigh show | grep 192.168.1.50
```

| OUI | 通常是 |
| --- | --- |
| ★★★ `00:50:56`、`00:0C:29` | VMware 虛擬機 |
| ★★★ `52:54:00` | KVM/QEMU 虛擬機 |
| ★★★ `08:00:27` | VirtualBox |

★★★ 是虛擬化的 OUI → 十之八九是有人複製了 VM 或還原了快照。

【2】在交換器上查那個 MAC 接在哪個埠，直接找到實體位置。

```junos
show ethernet-switching table address 52:54:00:aa:bb:cc
show interfaces descriptions
```

【3】★★★★ 判斷誰才是「合法」的那一台：查 DHCP 租約與 IP 台帳。
**先確認再改**，不要直接把伺服器的 IP 改掉。

```bash
grep -A5 "192.168.1.50" /var/lib/dhcp/dhcpd.leases | tail -20
```

【4】把違規那台改成 DHCP 或另一個未使用的 IP，然後清 ARP 快取。

```bash
sudo ip neigh flush all
```

【5】★★★★ **修正根因**：DHCP 池必須排除靜態區段。

```text
.1        閘道                    ★★★ 全機關一致
.2 - .20  網路設備（交換器、AP）
.21 - .50 伺服器（靜態）
.51 - .99 印表機（靜態或 DHCP 保留）
.100-.250 DHCP 動態池            ★★★★ 動態池絕不能跟上面重疊
```

**原理**：ARP 沒有驗證機制，同一個 IP 有兩台回應時，
交換器與其他主機會依「最後聽到誰」不斷改寫對應，造成流量在兩台之間亂跳。
　→ 原理詳見 [[010-02-06-guide-網概-IP位址與子網路]]、[[010-02-05-guide-網概-MAC位址與交換器]]

**預防**：★★★★ 維護一份 IP 台帳；靜態 IP 一律用 **DHCP 保留**發放而不是手動設定 ——
這樣衝突在伺服器端就被擋掉了。
→ [[040-01-02-guide-網路設備-IP位址規劃與子網切分]]

### ★★★ 情境十二：小檔案傳得過去，大檔案就卡住

**現象**：SSH 登入得進去但 `ls` 一個大目錄就當住；網頁標題出現但圖片載不完；
複製小檔案正常、複製大檔案傳到一半停住不動；VPN 連上後某些網站永遠轉圈。

**判斷分流**：★★★★ 這個組合幾乎只有一個原因：**MTU／PMTU 黑洞**。
用「不允許分片」的 ping 逐步縮小封包，找出路徑真正的 MTU。

```bash
ping -M do -s 1472 -c 2 目標IP      # 1472 + 28 位元組標頭 = 1500
```

- 看到正常回應 → 這條路徑的 MTU 至少 1500，**不是 MTU 問題**，回情境九
- 看到 `message too long, mtu=1400` → ★★★ 路徑 MTU 只有 1400，往下走
- 看到完全沒有回應（逾時）→ ★★★★ **典型的 PMTU 黑洞**：中間設備把大封包丟掉，
  又把「封包太大」的 ICMP 通知也擋掉了，兩端都不知道發生什麼事

```powershell
ping -f -l 1472 目標IP
```

**處置步驟**：

【1】二分法找出實際可通過的最大值。

```bash
for s in 1472 1400 1372 1300 1200; do
  printf "%s: " "$s"
  ping -M do -s "$s" -c1 -W2 目標IP >/dev/null 2>&1 && echo OK || echo FAIL
done
```

實際 MTU = 最後一個 OK 的數值 + 28。

【2】★★★★ **正解**是放行必要的 ICMP，讓 PMTU 探索能運作。

```text
必須放行：ICMP Type 3 Code 4（Fragmentation Needed）
順便放行：ICMP Type 11（Time Exceeded，traceroute 需要）
★★★★ 把 ICMP 整包擋掉是製造 PMTU 黑洞最常見的原因
```

【3】無法改中間設備時的替代解：夾住 TCP MSS。

```bash
# 在自己這端的介面上調 MTU
sudo ip link set enp3s0 mtu 1400

# ★★★ 或在防火牆／路由器上做 MSS clamping，讓 TCP 自己協商小一點的分段
sudo iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
     -j TCPMSS --clamp-mss-to-pmtu
```

【4】★★ Jumbo Frame（MTU 9000）環境出這個症狀 → **路徑上每一台設備都要設相同 MTU**。

**原理**：TCP 交握用的封包很小、一定過得去，所以連線「建立得起來」；
真正傳資料的大封包才會被丟掉，看起來就是「連得上但傳不動」。
　→ 原理詳見 [[010-02-07-guide-網概-路由與封包旅程]]、[[010-02-09-guide-網概-TCP與UDP]]

**預防**：★★★ 防火牆規則裡永遠不要寫「drop all ICMP」；
VPN 上線時就實測一次 PMTU 並記錄下來。

### ★★★★ 情境十三：全機關同時斷網，或埠轉發外面連不進來

**現象**：兩種都是「對外」的問題 ——
① 所有人都上不了外網，但內部系統正常；
② 埠轉發／DDNS 設好了，從外面就是連不進來。

**判斷分流**：

```bash
ping -c2 192.168.1.1          # 內部閘道
ping -c2 8.8.8.8              # 對外
curl -s --max-time 5 ifconfig.me   # 網際網路實際看到的來源 IP
```

- 看到閘道通、`8.8.8.8` 不通 → 對外線路或邊界設備，往下走第 1 步
- 看到閘道也不通 → 不是對外問題，回情境六
- 看到 `ifconfig.me` 回的 IP 跟分享器 WAN 口顯示的 **不一樣** → ★★★★ 你在 **CGNAT** 後面，跳到第 4 步
- 看到 `ifconfig.me` 落在 `100.64.0.0/10` → ★★★★ 確定是 CGNAT

**處置步驟**：

【1】看邊界設備的燈與 ISP 側狀態。

```bash
traceroute -n 8.8.8.8
```

```text
 1  192.168.1.1     1.2 ms          # 自家閘道
 2  * * *                            # ★★★ 第 2 跳就不通 → 打電話給 ISP
```

★★★ 中間偶爾出現 `* * *` **是正常的**（設備不回 ICMP）；
判斷準則永遠是「**最後一跳有沒有到達**」。

【2】★★★★ 內部通、對外全斷、ping 閘道卻正常 → 檢查 NAT 設備的 conntrack 表。

```bash
dmesg | grep -i conntrack
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
```

```text
nf_conntrack: table full, dropping packet     # ★★★★ 就是它
```

臨時解：加大上限並縮短逾時；根因通常是有機器在狂開連線（P2P、掃描、被入侵）。

【3】對外頻寬被吃滿也會表現成「全機關斷網」。看流量圖，或在邊界抓一次排行。

```bash
sudo iftop -i 對外介面
```

★★★★ 如果是**單一內部 IP** 佔滿上行 → 高度懷疑資料外洩或被當跳板，跳到求援段落。

【4】埠轉發連不進來，依這個順序排除：

| # | 檢查 | 指令／做法 |
| --- | --- | --- |
| 1 | ★★★★ **是不是在 CGNAT 後面** | `curl ifconfig.me` 比對 WAN IP；落在 `100.64/10` 就是 |
| 2 | ★★★ 內部服務真的起來了嗎 | 在伺服器上 `sudo ss -tulpn \| grep :埠` |
| 3 | ★★★ 服務只聽 `127.0.0.1` 嗎 | 同上，見情境五【1】 |
| 4 | ★★★ 伺服器本機防火牆 | `sudo ufw status` |
| 5 | ★★★ NAT 規則的內部 IP 對不對 | 分享器／防火牆的埠轉發設定 |
| 6 | ★★ 從**外部網路**測，不要在內網測 | 用手機行動網路測 `nc -zv 對外IP 埠` |

★★★★ **DDNS 不能解決 CGNAT**。DDNS 只處理「IP 會變」，
CGNAT 是「你根本沒有對外 IP」—— 解法只有向 ISP 申請真實／固定 IP。

【5】★★★ 只有某個網站特別慢或不通、其他都正常 → 通常是 ISP 之間互連不良。
跑 `mtr -n -c 50 那個網站`，把輸出附在申告單裡，比講十句「就是不通」有用得多。

**原理**：NAT 讓多台內部機器共用一個對外 IP，代價是「外面主動連進來」需要額外設定；
CGNAT 則是連 ISP 那層也做了一次 NAT，你在自家設備上做什麼都沒用。
　→ 原理詳見 [[010-02-08-guide-網概-NAT與私有位址]]、[[010-02-02-guide-網概-ISP與上網方式]]

**預防**：★★★★ 需要對外服務的機關，採購線路時就要寫明「固定公有 IP」；
雙線備援要求**不同實體路徑**，並定期**實際演練切換**（沒演練過的備援等於沒有）。
★★★★★ 遠端桌面（3389）與 SMB（445）**永遠不要對外開埠**，一律走 VPN。

## 一頁式急救卡

出事時來不及讀長文，先跑這幾個指令。★★★★ **由上往下跑，第一個「✗」出現的地方就是問題所在的層。**

```bash
# ═══ ① 實體層：線通了嗎 ═══════════════════════════════════
ip -br link show
# 有 LOWER_UP → 線是通的｜只有 UP 沒 LOWER_UP → 線沒插好／線壞／對面埠被關（★★★★ 這層不過，下面全部免看）

# ═══ ② 我有 IP 嗎 ═══════════════════════════════════════
ip -br addr show
# 有 192.168.x.x/24 → 過關｜169.254.x.x → DHCP 沒回應（情境二）｜完全沒有 inet → 同上

# ═══ ③ 出得了自己的網段嗎 ═════════════════════════════════
ip route show default && ping -c2 -W2 $(ip route | awk '/default/{print $3;exit}')
# 有 default via 且 ping 得通 → 問題不在這段 LAN｜ping 不通 → 交換器埠／VLAN／遮罩設錯（★★★★）

# ═══ ④ 出得去外面嗎（純 IP，避開 DNS）══════════════════════
ping -c2 -W2 8.8.8.8
# 通 → 路由與 NAT 正常，剩下只可能是 DNS 或服務｜不通但③通 → 對外線路／NAT／防火牆（情境十三）

# ═══ ⑤ 名字查得到嗎 ═══════════════════════════════════════
dig +short www.google.com ; dig @8.8.8.8 +short www.google.com
# 上行空、下行有 → ★★★★ 自家 DNS 壞了（情境三）｜兩行都有 → DNS 沒問題，往下走

# ═══ ⑥ 那個服務真的有人在聽嗎 ═════════════════════════════
nc -zv 目標主機 443
# succeeded → 網路全程清白，問題在應用層｜立刻 refused → 服務沒起（情境五）｜卡到逾時 → 防火牆 drop

# ═══ ⑦ 慢不慢？慢在哪一段 ═════════════════════════════════
curl -w "DNS:%{time_namelookup} TCP:%{time_connect} TLS:%{time_appconnect} TTFB:%{time_starttransfer} 總計:%{time_total}\n" -o /dev/null -s https://目標網址
# ★★★★ TTFB 大 = 伺服器慢，不是網路慢（情境九）｜總計−TTFB 大 = 頻寬／下載量問題

# ═══ ⑧ 都看不出來就抓封包，至少能講清楚責任在誰 ═══════════
sudo tcpdump -i any -n host 目標IP and port 443 -c 20
# 只看到自己重送 [S]、對方沒回 → 出得去回不來，問題在對方或中間設備｜連出向都沒有 → 問題在本機
```

★★★★ **五步驟 ping 的判讀，背這一張就夠**：

| 從哪一步開始失敗 | 問題在哪 | 去哪個情境 |
| --- | --- | --- |
| ★ ① `127.0.0.1` | 作業系統網路堆疊（極罕見） | 情境一 |
| ★★ ② 自己的 IP | 網路卡或驅動 | 情境一 |
| ★★★★ ③ 閘道 | **實體層／VLAN／IP 遮罩** | 情境一、情境八 |
| ★★★ ④ `8.8.8.8` | 對外路由、NAT、ISP | 情境十三 |
| ★★★★ ⑤ 只有網域名稱失敗 | **DNS**（網路完全是通的） | 情境三 |
| ★★★ 全部成功 | 網路正常，問題在應用層 | 情境四、情境五 |

> [!tip] ★★★★ 三個永遠適用的判斷準則
> - **`Connection refused` = 服務沒起；逾時 = 防火牆 drop。** 這兩個差別能省掉一半時間。
> - **traceroute 中間的 `* * *` 通常是正常的**，只看最後一跳有沒有到達。
> - **一次只改一項，改完就測。** 一次改三個地方，修好了你也不知道是哪一個。

## 什麼時候該停手求援

★★★★ 下面這些情況，**繼續自己動手會讓證據消失或災情擴大**。
停手、保留現場、依通報流程往上報。

| 你看到 | 為什麼要停手 | 先做什麼 |
| --- | --- | --- |
| ★★★★★ **DNS 指向你不認識的 IP**、網銀出現憑證警告 | **DNS 劫持**：分享器或端點已被入侵，你重設設定就毀掉證據 | 拍照／截圖存證，**不要重設**設備，斷開對外連線後通報 |
| ★★★★★ **`/etc/hosts` 或 `resolv.conf` 有陌生項目** | 惡意程式竄改，機器已失守 | 保留檔案原樣（先複製一份），不要直接編輯 |
| ★★★★★ **ARP 表裡一個 MAC 對應多個 IP** | **ARP 欺騙（中間人）**，正在被監聽 | 保留 `ip neigh` 輸出，通報後由資安人員處理 |
| ★★★★★ 出現**不認識的 DHCP 伺服器**在發位址 | Rogue DHCP：有人接了設備進內網，可能是刻意的 | 記下該設備的 MAC 與所在埠，先隔離該埠再通報 |
| ★★★★★ 單一內部 IP **在深夜佔滿對外上行** | 資料外洩或被當跳板 | 保留流量紀錄與防火牆日誌，**不要重開那台機器** |
| ★★★★★ 大量連往陌生 IP 的高位埠 | 惡意程式回連 C&C | 同上；重開機會清掉記憶體中的證據 |
| ★★★★ 交換器 **MAC 表暴增到接近上限** | MAC 洪泛攻擊 | 保留 `show ethernet-switching table` 統計後通報 |
| ★★★★ 大量 `SYN_RECV` 連線堆積 | SYN Flood；需要上游一起處理 | 通知 ISP 與資安，不要只在本機調參數 |
| ★★★★★ 你**不確定手上這台是不是還在服務中**的核心設備 | 一個 `commit` 打錯就整棟樓斷網 | 先確認影響範圍與變更窗口，用 `commit confirmed` |
| ★★★★★ 要在**營運時間**改核心交換器／防火牆規則 | 改錯會把自己鎖在外面 | 排變更窗口、先備份設定、留一條頻外（out-of-band）管理路徑 |

> [!danger] ★★★★★ 懷疑是資安事件時的三不
> **不重開機**（記憶體證據會消失）、
> **不重設設備**（設定與日誌會被清掉）、
> **不自行清除惡意程式**（會破壞鑑識軌跡）。
>
> 排錯時發現的異常，★★★★ **不要只把它當網路問題修掉就算了** ——
> 要循資安事件應變流程處理並保全證據。
> → [[090-07-04-guide-資安實踐-資安事件應變流程]]、[[090-05-09-guide-資安設備-日誌集中與SIEM]]

> [!warning] ★★★★ 也該求援的三種「不是資安」的情況
> - **同一個症狀你已經查了 30 分鐘還沒有方向** —— 換個人看常常五分鐘就找到
> - **要動的設備你沒有備份、也沒有回滾方法** —— 先取得備份再說
> - **問題明確落在 ISP 或機房那一段**（traceroute 第 2 跳就斷）——
>   附上 `mtr` 與 `tcpdump` 輸出去申告，不要自己在內網繼續試
