## 觀念說明

### 排錯的第一原則：先問清楚，再動手

> [!warning] 「網路壞了」是沒有意義的描述
> 使用者說「網路不能用」時，實際可能是：
> - 完全沒有網路
> - 只有某個網站不能開
> - 網路很慢
> - 只有 Wi-Fi 不行，有線可以
> - 印表機找不到
> - 內部系統打不開但可以上 Google
>
> **這六種問題的排查方向完全不同。**

**必問的六個問題**：

| # | 問題 | 為什麼問 |
| --- | --- | --- |
| **1** | **什麼時候開始的？** | 剛剛？今天早上？一直都這樣？ |
| **2** | **在此之前有什麼變動？** | 換位置、裝了軟體、更新、有人動了機櫃 |
| **3** | **是全部不能用，還是只有某些？** | 全部 → 底層；部分 → 上層或特定服務 |
| **4** | **只有你一個人，還是大家都這樣？** | 一個人 → 終端問題；一整層 → 交換器；全機關 → 對外線路 |
| **5** | **有線與無線都一樣嗎？** | 縮小到實體層 |
| **6** | **確切的錯誤訊息是什麼？** | **請對方截圖**，不要靠轉述 |

> [!tip] 第 2 題常常直接給你答案
> **「網路突然壞掉」的背後，九成有一個變動。**
>
> 常見的：
> - 「我只是把電腦搬到另一個位置」→ **那個網路孔在不同的 VLAN**
> - 「我裝了一個 VPN 軟體」→ **它改了路由表或 DNS**
> - 「昨天有廠商來換交換器」→ **設定沒還原**
> - 「我把一條線插到牆上另一個孔」→ **形成迴圈，廣播風暴**

### 核心方法：由下而上，逐層排除

> [!note] 為什麼要「由下而上」
> 因為**上層依賴下層**。
>
> 如果第 1 層（線）就沒通，你花再多時間檢查 DNS 設定也沒用。
>
> **從最底層開始，每確認一層就排除一大塊可能性。**

```mermaid
graph TD
    A["使用者說：連不上"] --> L1{"L1 實體<br/>燈亮嗎？"}
    L1 -->|否| F1["線、網卡、交換器埠"]
    L1 -->|是| L2{"L2 鏈路<br/>有 IP 嗎？<br/>同網段通嗎？"}
    L2 -->|否| F2["DHCP、VLAN、ARP"]
    L2 -->|是| L3{"L3 網路<br/>ping 得到閘道<br/>與 8.8.8.8 嗎？"}
    L3 -->|否| F3["閘道、路由表、防火牆"]
    L3 -->|是| L4{"L7-DNS<br/>解析得到嗎？"}
    L4 -->|否| F4["DNS 伺服器、快取、hosts"]
    L4 -->|是| L5{"L4 傳輸<br/>目標埠通嗎？"}
    L5 -->|否| F5["防火牆、服務沒起、監聽位址"]
    L5 -->|是| L7["L7 應用<br/>憑證、認證、程式錯誤"]
```

## 第一把刀：ping 的五步驟診斷法

> [!tip] **這是最重要的一節，請把這五步背起來**
> 一分鐘之內就能把問題範圍縮到很小。

```bash
ping 127.0.0.1          # ① 測自己的 TCP/IP 軟體
ping <自己的IP>          # ② 測自己的網路卡
ping <閘道IP>            # ③ 測到分享器/交換器通不通
ping 8.8.8.8            # ④ 測對外網路（用 IP，避開 DNS）
ping www.google.com     # ⑤ 測 DNS 解析
```

### 判讀表

| 從哪一步開始失敗 | 問題在哪 | 該檢查什麼 |
| --- | --- | --- |
| **① 127.0.0.1 就失敗** | 作業系統的 TCP/IP 堆疊 | **極罕見**。重裝網路元件；Windows 用 `netsh int ip reset` |
| **② 自己的 IP 失敗** | **網路卡或驅動程式** | 裝置管理員；`ip link`；換一張網卡測 |
| **③ 閘道失敗** | **實體層或第 2/3 層** | 線材、交換器埠、**VLAN**、IP/遮罩設錯、ARP |
| **④ 8.8.8.8 失敗** | **對外連線** | 路由表、防火牆、ISP、NAT |
| **⑤ 只有網域名稱失敗** | **DNS**（網路完全是通的！） | DNS 伺服器設定、快取、hosts |
| 全部成功 | 網路正常 | **問題在應用層** → 往第 4/7 層查 |

> [!example] 最經典的案例：「網頁打不開但 LINE 可以用」
> ```bash
> $ ping -c 2 8.8.8.8
> 64 bytes from 8.8.8.8: icmp_seq=1 ttl=113 time=8.4 ms   ← 通
>
> $ ping -c 2 www.google.com
> ping: www.google.com: Name or service not known           ← 不通
> ```
>
> **診斷**：第 ④ 步通、第 ⑤ 步失敗 → **確定是 DNS 問題**。
>
> **處置**：
> ```bash
> # 換成公用 DNS 測試
> $ dig @8.8.8.8 +short www.google.com
> 142.250.196.132        ← 公用 DNS 查得到 → 是自家 DNS 的問題
>
> # 清快取
> $ sudo resolvectl flush-caches       # Linux
> > ipconfig /flushdns                 # Windows
>
> # 檢查 DNS 設定
> $ resolvectl status | grep -A2 'DNS Servers'
> $ cat /etc/resolv.conf
> ```

### 讀懂 ping 的輸出

```bash
$ ping -c 5 8.8.8.8
PING 8.8.8.8 (8.8.8.8) 56(84) bytes of data.
64 bytes from 8.8.8.8: icmp_seq=1 ttl=113 time=8.42 ms
64 bytes from 8.8.8.8: icmp_seq=2 ttl=113 time=8.31 ms
64 bytes from 8.8.8.8: icmp_seq=3 ttl=113 time=9.15 ms

--- 8.8.8.8 ping statistics ---
5 packets transmitted, 5 received, 0% packet loss, time 4006ms
rtt min/avg/max/mdev = 8.310/8.628/9.150/0.331 ms
                                          ^^^^^ 抖動（jitter）
```

| 看什麼 | 意義 | 健康值 |
| --- | --- | --- |
| **`packet loss`** | **掉封包率** | **0%**；超過 1% 就有問題 |
| `time=` | **往返延遲（RTT）** | 同網段 < 1ms；國內 < 30ms；美國 100～200ms |
| `mdev` | **抖動** | 越小越穩定；VoIP 要求 < 30ms |
| `ttl=` | 剩餘存活次數 | 可推算經過幾跳與對方 OS |

### ping 的錯誤訊息對照

| 訊息 | 意義 | 檢查 |
| --- | --- | --- |
| `Destination Host Unreachable` | **同網段內找不到那台機器**（ARP 失敗） | 對方開機嗎？IP 對嗎？VLAN？ |
| `Destination Net Unreachable` | **路由器找不到往那個網段的路** | 路由表、閘道 |
| `Request timeout` / 沒有回應 | 完全沒回應 | 對方關機、**防火牆 drop**、路由不通 |
| `Name or service not known` | **DNS 解析失敗** | DNS 設定 |
| `Network is unreachable` | **本機沒有路由**（通常是沒有預設閘道） | `ip route` |
| `Operation not permitted` | 本機防火牆擋掉了送出 | 檢查本機防火牆規則 |

> [!warning] ping 不通不一定代表壞掉
> **很多伺服器與防火牆刻意封鎖 ICMP** —— 這是常見的資安設定。
>
> 所以「ping 不通」可能是：
> - 真的不通
> - **對方故意不回應**
>
> **這時改測「服務本身」**：
> ```bash
> $ nc -zv example.com 443        # 測 TCP 埠
> $ curl -sI https://example.com  # 測 HTTP 服務
> ```

> [!tip] 進階：用 ping 找出 MTU 問題
> 「小檔案通、大檔案卡住」的經典排查：
> ```bash
> # -M do = 不允許分片；-s = 封包大小（不含 28 位元組標頭）
> $ ping -M do -s 1472 -c 2 8.8.8.8      # 1472 + 28 = 1500
> # 成功 → MTU 至少 1500
>
> $ ping -M do -s 1472 -c 2 <VPN對端>
> ping: local error: message too long, mtu=1400
> #                                    ^^^^^^^^ 這條路徑的 MTU 只有 1400
> ```
> ```powershell
> # Windows
> ping -f -l 1472 8.8.8.8
> ```
> 找出實際 MTU 後，可以調整介面 MTU 或 TCP MSS。

## 第二把刀：traceroute 找出斷在哪一跳

```bash
# Linux（預設用 UDP）
$ traceroute -n 8.8.8.8

# 用 ICMP（與 Windows 的 tracert 一致）
$ traceroute -I -n 8.8.8.8

# 用 TCP 443（能穿過只擋 ICMP/UDP 的防火牆）
$ sudo traceroute -T -p 443 -n example.com
```

```powershell
# Windows
tracert 8.8.8.8
```

**輸出解讀**：

```
 1  192.168.1.1      1.234 ms  1.100 ms  1.050 ms    ← 你家分享器
 2  10.20.30.1       8.512 ms  8.400 ms  8.300 ms    ← ISP 第一跳
 3  * * *                                             ← 這台不回應（可能正常）
 4  168.95.98.254   12.334 ms 12.200 ms 12.100 ms
 5  220.128.1.1     13.001 ms 13.100 ms 12.900 ms
 8  8.8.8.8         25.882 ms 25.700 ms 25.600 ms    ← 到達
```

| 觀察 | 判斷 |
| --- | --- |
| **第 1 跳就不通** | 你到分享器的問題（線、網卡、IP 設定） |
| **第 2 跳不通** | 分享器到 ISP 的問題（**打電話給 ISP**） |
| 某跳延遲突然 **+100ms 以上** | 通常是**跨海**（正常現象） |
| 中間幾跳 `* * *` **但最後有到達** | **正常**（那些設備不回 ICMP） |
| **從某一跳開始全部 `* * *` 到結束** | **那裡真的斷了** |
| 同一跳的三個時間差很多 | 該節點負載高或有限速 |
| 路徑一直變來變去 | 有負載平衡（正常）或路由不穩 |

> [!warning] `* * *` 大多數時候是正常的
> 這是最常被誤判的地方。
>
> 很多路由器基於安全考量**不回應 ICMP Time Exceeded**，
> 或對它做了嚴格限速。
>
> **判斷原則**：
> **看最後一跳有沒有到達目的地** ——
> 有到達就是正常，中間的 `*` 可以忽略。

> [!tip] mtr：traceroute + ping 的結合（強烈推薦）
> ```bash
> $ sudo apt install mtr
> $ mtr -n 8.8.8.8
>
> HOST                    Loss%   Snt   Last   Avg  Best  Wrst StDev
>  1. 192.168.1.1          0.0%    50    1.2   1.3   1.0   2.1   0.2
>  2. 10.20.30.1           0.0%    50    8.5   8.7   8.2  12.3   0.6
>  3. 168.95.98.254       12.0%    50   12.3  13.1  11.9  45.2   4.8
>                         ^^^^^^                          ^^^^
>                      這一跳開始掉包                   延遲不穩
>  4. 8.8.8.8             12.0%    50   25.8  26.5  25.1  58.9   5.2
> ```
>
> **mtr 持續測試並統計**，能找出「間歇性」的問題 ——
> 這是單次 traceroute 看不出來的。
>
> **判讀重點**：
> - **從某一跳開始持續掉包，且後面都掉** → **那一跳有問題**
> - 只有中間某一跳掉包但後面正常 → **那台設備對 ICMP 限速**（正常）

## 第三把刀：DNS 排查

```bash
# 快速查
$ dig +short www.example.com
$ nslookup www.example.com

# 指定 DNS 伺服器（判斷是不是自家 DNS 的問題）
$ dig @8.8.8.8 +short www.example.com
$ dig @1.1.1.1 +short www.example.com

# 看完整查詢路徑
$ dig +trace www.example.com

# 直接問權威伺服器（繞過所有快取）
$ dig @$(dig +short example.com NS | head -1) +short www.example.com

# 反解
$ dig -x 8.8.8.8 +short
```

**診斷邏輯**：

| 情況 | 判斷 |
| --- | --- |
| 系統 DNS 查不到，公用 DNS 查得到 | **你的 DNS 伺服器有問題** |
| 兩者都查不到，權威查得到 | **快取尚未更新**（等 TTL） |
| 連權威都查不到 | **記錄根本沒設定**或設錯 |
| 查得到但 IP 不對 | **快取舊資料**，或 **DNS 被劫持** |
| 查詢很慢（> 500ms） | DNS 伺服器太遠或負載高 |

> [!danger] DNS 被劫持的檢查
> ```bash
> # 1. 檢查你實際在用哪台 DNS
> $ resolvectl status | grep -A3 'DNS Servers'
> $ cat /etc/resolv.conf
> ```
> ```powershell
> ipconfig /all | findstr "DNS Servers"
> ```
>
> **如果出現你不認識的 IP**（不是分享器、不是 ISP、不是公用 DNS），
> 高度懷疑：
> - **分享器被入侵**（DNS 設定被改）
> - **本機有惡意程式**
>
> ```bash
> # 2. 檢查 hosts 檔案有沒有被竄改
> $ cat /etc/hosts
> ```
> ```
> C:\Windows\System32\drivers\etc\hosts
> ```
>
> 症狀：網銀導向奇怪的頁面、大量廣告、憑證警告。

## 第四層與第七層的檢查

### 第 4 層：埠通不通

```bash
# 測 TCP 埠
$ nc -zv example.com 443
Connection to example.com 443 port [tcp/https] succeeded!

# 測多個埠
$ nc -zv 192.168.1.50 22 80 443 3306

# 沒有 nc 時用 bash 內建
$ timeout 3 bash -c '</dev/tcp/example.com/443' && echo OPEN || echo CLOSED

# 看本機開了哪些埠、誰在監聽
$ sudo ss -tulpn
```

```powershell
Test-NetConnection example.com -Port 443
```

> [!warning] 第 4 層最常見的兩個問題
> **一、服務只監聽 `127.0.0.1`**
> ```bash
> $ sudo ss -tulpn | grep 3306
> tcp LISTEN 127.0.0.1:3306    ← 只有本機連得到！
> ```
> **解法**：改設定檔的 `bind-address` 為 `0.0.0.0` 或內網 IP。
>
> **二、防火牆擋掉了**
> ```bash
> $ sudo ufw status verbose
> $ sudo iptables -L -n -v
> ```
>
> **怎麼分辨**：
> | 症狀 | 意義 |
> | --- | --- |
> | **立刻 `Connection refused`** | 那個埠**沒有服務在聽**（收到 RST） |
> | **一直等到逾時** | **防火牆 drop** 或路由不通 |

### 第 7 層：應用層

```bash
# HTTP 服務
$ curl -I https://example.com
$ curl -v https://example.com 2>&1 | head -30

# 各階段耗時（判斷慢在哪）
$ curl -w "DNS:%{time_namelookup} TCP:%{time_connect} TLS:%{time_appconnect} TTFB:%{time_starttransfer} 總計:%{time_total}\n" \
       -o /dev/null -s https://example.com

# 憑證
$ echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates

# 看伺服器日誌
$ sudo tail -f /var/log/nginx/error.log
$ sudo journalctl -u nginx -f
```

## 完整實戰範例：一鍵診斷腳本

```bash
#!/usr/bin/env bash
# 網路分層診斷腳本
# 用法：./netdiag.sh [目標網域]
TARGET="${1:-www.google.com}"
IFACE=$(ip route 2>/dev/null | awk '/default/{print $5; exit}')
GW=$(ip route 2>/dev/null | awk '/default/{print $3; exit}')
MYIP=$(ip -4 addr show "$IFACE" 2>/dev/null | awk '/inet /{print $2}' | cut -d/ -f1)

ok(){ echo "  ✓ $*"; }
ng(){ echo "  ✗ $*"; }

echo "════════════════════════════════════════"
echo " 網路診斷  介面=$IFACE  IP=$MYIP  閘道=$GW"
echo "════════════════════════════════════════"

echo -e "\n【L1】實體層"
if [ -n "$IFACE" ]; then
  sudo ethtool "$IFACE" 2>/dev/null | grep -E 'Speed|Duplex|Link detected' | sed 's/^/  /'
  ip -s link show "$IFACE" | awk '/RX:|TX:/{getline; print "  errors/dropped: "$3" "$4}'
else
  ng "找不到預設路由介面"
fi

echo -e "\n【L2/L3】位址與路由"
if [ -z "$MYIP" ]; then
  ng "沒有 IPv4 位址"
elif [[ "$MYIP" == 169.254.* ]]; then
  ng "IP 是 $MYIP （APIPA → DHCP 失敗！）"
else
  ok "IP = $MYIP"
fi
[ -n "$GW" ] && ok "預設閘道 = $GW" || ng "沒有預設閘道"
ip neigh show 2>/dev/null | head -3 | sed 's/^/  /'

echo -e "\n【ping 五步驟】"
step(){ ping -c2 -W2 "$2" &>/dev/null && ok "$1 ($2)" || ng "$1 ($2)  ← 問題可能在這裡"; }
step "① 本機 TCP/IP" 127.0.0.1
[ -n "$MYIP" ] && step "② 自己的網卡" "$MYIP"
[ -n "$GW" ]   && step "③ 預設閘道"   "$GW"
step "④ 對外網路" 8.8.8.8

echo -n "  ⑤ DNS 解析 ($TARGET) ... "
if getent hosts "$TARGET" >/dev/null 2>&1; then
  echo "✓ $(dig +short "$TARGET" 2>/dev/null | head -1)"
else
  echo "✗  ← DNS 問題（網路本身可能是通的）"
fi

echo -e "\n【DNS】"
echo -n "  目前使用的 DNS: "
(resolvectl status 2>/dev/null | awk '/DNS Servers/{print $3; exit}' \
  || awk '/^nameserver/{print $2; exit}' /etc/resolv.conf) 2>/dev/null
echo "  系統 DNS 查詢:  $(dig +short "$TARGET" 2>/dev/null | head -1)"
echo "  8.8.8.8 查詢:   $(dig @8.8.8.8 +short "$TARGET" 2>/dev/null | head -1)"

echo -e "\n【L4】埠連通性"
for p in 80 443; do
  nc -z -w3 "$TARGET" "$p" 2>/dev/null && ok "TCP $p 通" || ng "TCP $p 不通"
done

echo -e "\n【L7】HTTP 與效能"
curl -sI --max-time 10 "https://$TARGET" 2>/dev/null | head -1 | sed 's/^/  /'
curl -w "  DNS:%{time_namelookup}s TCP:%{time_connect}s TLS:%{time_appconnect}s TTFB:%{time_starttransfer}s 總計:%{time_total}s\n" \
     -o /dev/null -s --max-time 10 "https://$TARGET" 2>/dev/null

echo -e "\n【路徑】"
command -v traceroute >/dev/null && traceroute -n -w1 -q1 -m8 "$TARGET" 2>/dev/null | sed 's/^/  /'

echo -e "\n════════════════════════════════════════"
```

**使用方式**：

```bash
$ chmod +x netdiag.sh
$ ./netdiag.sh
$ ./netdiag.sh www.gov.tw
```

> [!tip] 把這個腳本放進你的工具箱
> 建議放在 `/usr/local/bin/netdiag`，
> 遇到問題時第一件事就是跑它，**30 秒內得到完整的分層報告**。
>
> 也可以把輸出存起來附在工單裡，方便交接與後續追查。

## 常見情境的排查流程

### 情境一：一個人不能上網，其他人正常

```
1. ping 五步驟 → 找出卡在哪一層
2. 若卡在 ③（閘道）：
   - 換一條網路線測試
   - 換一個網路孔測試
   - 檢查交換器該埠的 VLAN
   - 看該埠有沒有被 port-security 關掉（err-disabled）
3. 若 IP 是 169.254.x.x → DHCP 問題
4. 若卡在 ⑤ → DNS 問題
```

### 情境二：一整層樓不能上網

```
1. 這一層的交換器有電嗎？燈號正常嗎？
2. 交換器到核心的上行線正常嗎？
   → show interfaces status
3. 有沒有廣播風暴？
   → 燈號同步狂閃 = 有迴圈
   → show spanning-tree 看有沒有埠不斷變化
4. 核心交換器上該 VLAN 的 SVI 正常嗎？
5. 最近有沒有人動過機櫃或接線？
```

### 情境三：全機關不能上網

```
1. 對外線路正常嗎？
   → ping ISP 的閘道
   → 看數據機/路由器的燈號
2. 防火牆正常嗎？
   → 有沒有當機、規則有沒有被改
   → conntrack 表滿了嗎？
3. 對外頻寬是不是被吃滿？
   → 看流量圖；有沒有人在下載大檔或遭 DDoS
4. DNS 伺服器掛了嗎？
   → 內部服務通但外部網站不通 = DNS
5. 打電話問 ISP（記得先自己排除內部問題）
```

### 情境四：網路很慢（不是不通）

```bash
# 1. 是延遲高還是頻寬不足？
$ mtr -n 8.8.8.8              # 看延遲與掉包
$ speedtest-cli               # 看實際頻寬

# 2. 是不是實體層問題？
$ sudo ethtool eth0 | grep -E 'Speed|Duplex'
#   Speed 只有 100Mb/s？ → 線材或協商問題
#   Duplex: Half？       → 雙工不符（會極慢）
$ ip -s link show eth0        # errors 一直增加？

# 3. 是不是內部還是對外的問題？
$ iperf3 -c 內部伺服器          # 內網速度正常嗎？
#   內網快、對外慢 → 對外頻寬或 ISP 問題
#   內網也慢       → 內部網路問題

# 4. 是不是伺服器慢而不是網路慢？
$ curl -w "TTFB:%{time_starttransfer}s 總計:%{time_total}s\n" -o /dev/null -s https://網站
#   TTFB 很大 → 伺服器端問題，不是網路

# 5. 有沒有人佔用大量頻寬？
$ sudo iftop -i eth0          # 即時流量排行
$ sudo nethogs eth0           # 依程序看流量
```

### 情境五：只有某個網站打不開

```bash
# 1. 別人也打不開嗎？（用手機行動網路測試）
#    → 大家都不行 = 對方網站的問題

# 2. DNS 解析正常嗎？
$ dig +short 那個網站
$ dig @8.8.8.8 +short 那個網站

# 3. 埠通嗎？
$ nc -zv 那個網站 443

# 4. 憑證有問題嗎？
$ echo | openssl s_client -connect 那個網站:443 -servername 那個網站 2>&1 | grep -E 'verify|expire'

# 5. 是不是被防火牆/內容過濾擋了？
$ curl -v https://那個網站 2>&1 | head -20
#    看是連不上、被 RST、還是回了封鎖頁面

# 6. 清快取試試
$ sudo resolvectl flush-caches
#    瀏覽器：Ctrl+F5、無痕視窗
```

## 常見錯誤與排錯

| 錯誤的做法 | 為什麼不好 | 應該怎麼做 |
| --- | --- | --- |
| **一有問題就重開機** | 沒有診斷，問題會再發生，也學不到東西 | **先跑五步驟 ping**，30 秒就有方向 |
| 從應用層開始查 | 上層依賴下層，可能白忙 | **由下而上** |
| 只憑使用者轉述 | 描述常常不精確 | **請對方截圖**、自己到現場確認 |
| 一次改很多設定 | **不知道是哪一個修好的**（或改壞的） | **一次只改一項**，改完就測 |
| 沒有記錄就開始動手 | 改壞了無法還原 | **先備份設定**、記下原本的值 |
| 看到 `* * *` 就說路由斷了 | 多數是設備不回 ICMP | 看**最後一跳有沒有到達** |
| ping 不通就說對方掛了 | 可能只是擋 ICMP | 改用 `nc -zv` 測埠 |
| 忽略「最近改了什麼」 | 九成的突發故障來自變動 | **一定要問第 2 題** |
| 沒有留下處理紀錄 | 下次同樣的問題又要重來 | **建立知識庫**，記錄症狀與解法 |

> [!tip] 排錯的四個心法
> **一、二分法。**
> 不確定問題在 A 還是 B 之間時，**從中間切一刀** ——
> 例如「電腦到網站不通」，先測「電腦到閘道」，
> 一次就排除一半的可能性。
>
> **二、換一個測試。**
> 換一條線、換一個埠、換一台電腦、換一個網站 ——
> **對照組是最快的診斷方法**。
>
> **三、從最便宜的開始。**
> 換線兩分鐘、換設定二十分鐘、換設備兩小時。
> **先做便宜的。**
>
> **四、記錄一切。**
> 你改了什麼、什麼時候改的、結果如何。
> 這既是為了能還原，也是為了下次。

## 安全性注意事項

> [!warning] 排錯工具也是攻擊工具
> `ping`、`traceroute`、`nmap`、`tcpdump` 這些工具
> 在**別人的網路上使用可能構成違法行為**。
>
> **在台灣**，未經授權對他人系統進行掃描或探測，
> 可能觸犯《刑法》第三十六章「妨害電腦使用罪」。
>
> **即使在自己管理的網路上**：
> - **大規模掃描前應知會相關人員**（否則會觸發資安告警）
> - **留下操作紀錄**（誰、何時、為什麼）
> - 在正式環境操作前走**變更管理流程**

> [!danger] 抓封包可能抓到敏感資料
> `tcpdump` 會抓到**所有經過的流量**，包含：
> - 未加密協定的**帳號密碼**（HTTP、FTP、Telnet）
> - Session Cookie
> - 個人資料
>
> **注意事項**：
> 1. **只在必要時抓，抓完立刻刪除**
> 2. **不要把封包檔案隨意外傳**（給廠商前要評估）
> 3. **加上過濾條件**縮小範圍：
>    ```bash
>    # ❌ 抓全部
>    sudo tcpdump -i any -w all.pcap
>
>    # ✅ 只抓需要的
>    sudo tcpdump -i any -w trace.pcap 'host 192.168.1.50 and port 443'
>    ```
> 4. 抓封包本身可能屬於**個資法**規範的行為，
>    機關應有明確的作業程序

> [!tip] 排錯時的資安警訊
> 排查網路問題時，如果發現以下狀況，**要往資安方向想**：
>
> | 發現 | 可能是 |
> | --- | --- |
> | DNS 設定指向不認識的 IP | **DNS 劫持**（分享器被入侵或惡意程式） |
> | `hosts` 檔案有奇怪的項目 | **惡意程式竄改** |
> | ARP 表中一個 MAC 對應多個 IP | **ARP 欺騙（中間人）** |
> | 對外流量異常大 | **資料外洩**或機器被當跳板 |
> | 網路上出現不認識的 DHCP 伺服器 | **Rogue DHCP** |
> | 大量連到陌生 IP 的高位埠 | **惡意程式回連 C&C** |
> | 交換器 MAC 表暴增 | **MAC 洪泛攻擊** |
>
> **不要只把它當成「網路問題」修掉就算了** ——
> 要循資安事件應變流程處理。
> 見 [[090-07-04-guide-資安實踐-資安事件應變流程]]。

## 速查表

### **ping 五步驟（背起來）**

```bash
ping 127.0.0.1        # ① 本機 TCP/IP
ping <自己IP>          # ② 網路卡
ping <閘道>            # ③ 到交換器/分享器
ping 8.8.8.8          # ④ 對外網路
ping www.google.com   # ⑤ DNS
```

| 從哪步失敗 | 問題在 |
| --- | --- |
| ① | 作業系統網路堆疊（罕見） |
| ② | **網路卡／驅動** |
| ③ | **線材／交換器／VLAN／IP 設定** |
| ④ | **路由／防火牆／ISP** |
| ⑤ | **DNS**（網路是通的！） |

### 分層排錯順序

| 層 | 檢查 | 指令 |
| --- | --- | --- |
| **L1** | 燈亮嗎、速度對嗎 | `ethtool eth0`、`ip -s link` |
| **L2** | 有 IP 嗎、同網段通嗎 | `ip addr`、`ip neigh` |
| **L3** | 閘道、路由、對外 | `ip route`、`ping`、`traceroute` |
| **DNS** | 解析得到嗎 | `dig`、`nslookup` |
| **L4** | 埠通嗎、有在聽嗎 | `nc -zv`、`ss -tulpn` |
| **L7** | 應用正常嗎 | `curl -v`、`openssl s_client`、看日誌 |

### ping 錯誤訊息

| 訊息 | 意義 |
| --- | --- |
| Destination Host Unreachable | 同網段找不到（ARP 失敗） |
| Destination Net Unreachable | 路由器找不到路 |
| Request timeout | 沒回應（關機／防火牆 drop） |
| Name or service not known | **DNS 失敗** |
| Network is unreachable | **本機沒有路由** |

### 關鍵指標

| 指標 | 健康值 |
| --- | --- |
| **掉封包率** | **0%** |
| 延遲（同網段） | < 1 ms |
| 延遲（國內） | < 30 ms |
| 延遲（美國） | 100～200 ms |
| 抖動 mdev | < 30 ms（VoIP） |
| **TTFB** | **< 200 ms** |

### 必備工具

| 工具 | 用途 | 安裝 |
| --- | --- | --- |
| `ping` | 連通性 | 內建 |
| `traceroute` / `tracert` | 路徑 | `apt install traceroute` |
| **`mtr`** | **traceroute + ping 統計** | `apt install mtr` |
| `dig` / `nslookup` | DNS | `apt install dnsutils` |
| `nc` | 測埠 | `apt install netcat-openbsd` |
| `ss` | 連線與監聽 | 內建 |
| `curl` | HTTP 測試與計時 | 內建 |
| `tcpdump` | 抓封包 | `apt install tcpdump` |
| `iperf3` | 吞吐量 | `apt install iperf3` |
| `iftop` / `nethogs` | 即時流量 | `apt install iftop nethogs` |
| `ethtool` | 網卡狀態 | `apt install ethtool` |

### 排錯四心法

1. **二分法** —— 從中間切，一次排除一半
2. **換一個測試** —— 換線、換埠、換機器、換網站
3. **從最便宜的開始** —— 換線 2 分鐘 vs 換設備 2 小時
4. **記錄一切** —— 改了什麼、結果如何

## 練習題

> [!question]- 練習 1：跑一次五步驟
> 依序執行五個 ping，記下每一步的結果與延遲。
>
> 然後**故意製造問題**：
> ```bash
> # 把 DNS 改成不存在的位址
> sudo resolvectl dns eth0 192.168.99.99
>
> # 再跑一次五步驟
> # → 你會看到只有第 ⑤ 步失敗
>
> # 改回來
> sudo resolvectl revert eth0
> ```
> 接著試試刪掉預設閘道（記得復原）：
> ```bash
> GW=$(ip route | awk '/default/{print $3}')
> sudo ip route del default
> # 跑五步驟 → 第 ③④ 步會失敗
> sudo ip route add default via $GW
> ```

> [!question]- 練習 2：用 mtr 找出網路品質問題
> ```bash
> sudo apt install mtr
> mtr -n -c 100 8.8.8.8      # 送 100 個封包後結束
> ```
> 回答：
> 1. 有沒有哪一跳開始持續掉包？
> 2. 平均延遲是多少？最差呢？
> 3. StDev（標準差）大不大？（大 = 不穩定）
> 4. 換 `mtr -n 一個國外網站` 再測一次，比較差異

> ```
>
> 然後**加上你環境專屬的檢查項目**，例如：
> - ping 你機關的內部伺服器
> - 檢查 VPN 是否連線
> - 測試特定的內部服務埠
> - 檢查代理伺服器設定
>
> **這份腳本會是你日後最常用的工具。**

## 小測驗

Q1. 使用者說「網路壞了」時，你該問哪六個問題？其中哪一題常常直接給你答案？

Q2. 為什麼排錯要「由下而上」而不是從應用層開始？

Q3. 請寫出 ping 五步驟，並說明每一步失敗各代表什麼。

Q4. 「網頁打不開但 LINE 可以用」時，五步驟會在哪一步失敗？代表什麼？

Q5. ping 的輸出中，最該注意的指標是什麼？健康值是多少？

Q6. ping 不通就一定代表對方壞了嗎？該怎麼改測？

Q7. traceroute 中間出現 `* * *`，什麼情況下是正常的？什麼情況下才是真的斷了？

Q8. `mtr` 比 `traceroute` 好在哪裡？

Q9. 第 4 層排查時，「立刻 Connection refused」與「一直等到逾時」分別代表什麼？

Q10. 排錯的四個心法是什麼？排錯時發現哪些現象要往「資安事件」方向想（至少舉三個）？

> [!question]- 測驗答案
> **Q1.** ①**什麼時候開始的**？②**在此之前有什麼變動**？
> ③是全部不能用還是只有某些？④只有你一個人還是大家都這樣？
> ⑤有線與無線都一樣嗎？⑥**確切的錯誤訊息是什麼**（請截圖）。
> **第 2 題常常直接給你答案** —— 「網路突然壞掉」的背後九成有一個變動
> （搬位置導致 VLAN 不同、裝了 VPN 軟體改了路由/DNS、廠商動過設定、接錯線形成迴圈）。
>
> **Q2.** 因為**上層依賴下層**。
> 如果第 1 層（線）就沒通，你花再多時間檢查 DNS 設定也沒用。
> 從最底層開始，**每確認一層就排除一大塊可能性**，效率高得多。
>
> **Q3.** ①`ping 127.0.0.1`（本機 TCP/IP 堆疊，失敗極罕見）；
> ②`ping 自己的 IP`（**網路卡／驅動程式**）；
> ③`ping 閘道`（**線材、交換器埠、VLAN、IP/遮罩設定**）；
> ④`ping 8.8.8.8`（**對外連線：路由、防火牆、ISP、NAT**）；
> ⑤`ping www.google.com`（**DNS**）。
>
> **Q4.** 會在**第 ⑤ 步**失敗（前四步都通）。
> 這代表**網路本身完全是通的，問題純粹在 DNS**。
> LINE 能用是因為它可能有自己的連線機制或快取。
> 處置：用 `dig @8.8.8.8` 比對、清 DNS 快取、檢查 DNS 伺服器設定。
>
> **Q5.** 最該注意的是 **`packet loss`（掉封包率）**，
> **健康值是 0%**，超過 1% 就有問題。
> 其次是 `time=`（延遲：同網段 < 1ms、國內 < 30ms、美國 100～200ms）
> 與 `mdev`（抖動，VoIP 要求 < 30ms）。
>
> **Q6.** **不一定。** 很多伺服器與防火牆**刻意封鎖 ICMP**，這是常見的資安設定。
> 所以 ping 不通可能是「真的不通」也可能是「對方故意不回應」。
> **改測服務本身**：`nc -zv 主機 443`（測 TCP 埠）
> 或 `curl -sI https://網址`（測 HTTP 服務）。
>
> **Q7.** **中間幾跳 `* * *` 但最後有到達目的地 → 正常**
> （那些路由器基於安全考量不回應 ICMP Time Exceeded，或對它限速）。
> **從某一跳開始全部都是 `* * *` 直到結束 → 那裡真的斷了**。
> 判斷原則就是：**看最後一跳有沒有到達**。
>
> **Q8.** `mtr` 是 **traceroute + ping 的結合，會持續測試並統計** ——
> 顯示每一跳的**掉包率、平均/最佳/最差延遲、標準差**。
> 這能找出「**間歇性**」的問題（例如某一跳偶爾掉包），
> 而單次 traceroute 只是一個快照，看不出來。
>
> **Q9.** **立刻 `Connection refused`** = 收到 **RST**，
> 代表**那個埠沒有服務在監聽**（主機是活的，但服務沒起來或埠錯）；
> **一直等到逾時** = 完全沒有回應，
> 代表**防火牆 drop 掉了**、路由不通、或主機關機。
>
> **Q10.** **四個心法**：①**二分法**（從中間切，一次排除一半）；
> ②**換一個測試**（換線、換埠、換機器、換網站，對照組最快）；
> ③**從最便宜的開始**（換線 2 分鐘 vs 換設備 2 小時）；
> ④**記錄一切**（改了什麼、結果如何）。
> **要往資安方向想的現象**（任三個）：
> **DNS 設定指向不認識的 IP**（DNS 劫持）、
> **hosts 檔案有奇怪項目**（惡意程式竄改）、
> **ARP 表中一個 MAC 對應多個 IP**（ARP 欺騙／中間人）、
> **對外流量異常大**（資料外洩或被當跳板）、
> **出現不認識的 DHCP 伺服器**（Rogue DHCP）、
> **大量連到陌生 IP 的高位埠**（惡意程式回連 C&C）、
> **交換器 MAC 表暴增**（MAC 洪泛攻擊）。
