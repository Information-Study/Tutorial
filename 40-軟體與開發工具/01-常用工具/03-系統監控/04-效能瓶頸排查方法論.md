## ★★★★ 為什麼需要方法論

```
★★★★ 沒有方法論的排查長這樣：

  「網站很慢」
    → 「應該是資料庫吧」→ 調 innodb_buffer_pool → 沒好
    → 「那是 PHP 吧」  → 調 max_children     → 更糟
    → 「加記憶體好了」  → 花錢 → 還是慢
    → 「重開機看看」    → 好了一小時 → 又慢了

  ★★★ 問題：
    ① 憑印象猜，不是憑數據
    ② ★★★★ 一次改多個地方 → 不知道哪個有效
    ③ ★★★ 沒有記錄 → 下次再發生時從頭來過
    ④ ★★ 治標不治本（重開機）

★★★★ 有方法論的排查：
  ① 60 秒內取得【全貌】
  ② ★★★ 用 USE 對每個資源系統化檢查 → 不會漏
  ③ ★★ 由外而內分層 → 縮小範圍
  ④ ★★★ 一次只改一個變數 → 知道是什麼有效
  ⑤ ★★ 記錄下來 → 建立知識庫
```

> [!tip] 三個核心原則 ★★★★
> ```
> ★★★★ ① 【先量測，不要猜】
>      → 「我覺得是資料庫」不是證據
>      → ★★★ 數據才是（iowait 62%、available 0.6G）
>
> ★★★★ ② 【一次只改一個變數】
>      → 同時改三個設定 → 就算好了也不知道是哪個
>      → ★★ 而且不知道另外兩個是不是變糟了
>
> ★★★★ ③ 【找到根因，不要只解症狀】
>      → 重開機 = 症狀消失，根因還在
>      → ★★★ 問「為什麼」至少三次
>        「網站慢」→ 為什麼？→「iowait 高」→ 為什麼？
>        →「記憶體不夠 cache 被擠光」→ 為什麼？
>        →「php-fpm max_children 設 50 但只有 8G 記憶體」← ★★★ 根因
> ```

## ★★★★ 60 秒檢查清單

```
★★★★ 這是 Netflix 效能團隊的標準流程
    —— 登入一台有問題的機器後，先跑這十個指令
```

```bash
#!/usr/bin/env bash
# ★★★★ /usr/local/bin/first60 —— 60 秒取得系統全貌
echo "═══ $(hostname) $(date '+%F %T') ═══"

echo -e "\n【1】uptime —— ★★ load 的趨勢"
uptime
#   ★★★ 看三個數字的【趨勢】：
#     1分 > 5分 > 15分  → ★★ 問題正在【惡化】
#     1分 < 5分 < 15分  → ★ 問題正在【緩解】
#     三個都高          → ★★ 持續性的問題

echo -e "\n【2】dmesg | tail —— ★★★ 核心層的錯誤"
dmesg -T 2>/dev/null | tail -10
#   ★★★★ 找：OOM killer、I/O error、網卡 reset、
#            TCP: drop open request、硬體錯誤

echo -e "\n【3】vmstat 1 —— ★★★★ 最重要的一個"
vmstat -w 1 5 | tail -4
#   ★★★ r（等CPU）b（等I/O）si/so（換頁）wa（iowait）st（steal）

echo -e "\n【4】mpstat -P ALL 1 —— ★★★ CPU 是否平均"
mpstat -P ALL 1 2 2>/dev/null | tail -6
#   ★★★ 只有一顆滿載 = 單執行緒 或 中斷集中

echo -e "\n【5】pidstat 1 —— ★★ 誰在吃 CPU（含短命程序）"
pidstat 1 2 2>/dev/null | tail -8
#   ★★ 比 top 好：會顯示【取樣期間出現又消失】的程序

echo -e "\n【6】iostat -xz 1 —— ★★★ 磁碟"
iostat -xz 1 2 2>/dev/null | tail -8
#   ★★★ aqu-sz > 2 排隊；w_await > 50ms 慢；%util（HDD）

echo -e "\n【7】free -m —— ★★★ available 才是重點"
free -m
#   ★★★★ 看 available 不是 free

echo -e "\n【8】sar -n DEV 1 —— ★★ 網路吞吐"
sar -n DEV 1 2 2>/dev/null | grep -vE 'lo|IFACE' | tail -4
#   ★★ 對照網卡上限（1Gb = 125 MB/s）

echo -e "\n【9】sar -n TCP,ETCP 1 —— ★★★ TCP 層的問題"
sar -n TCP,ETCP 1 2 2>/dev/null | tail -5
#   ★★★ retrans/s 高 = 網路品質差
#   ★★★ passive/s 突增 = 連線暴增

echo -e "\n【10】top —— ★ 最後才看"
top -b -n1 2>/dev/null | head -15
```

```bash
$ sudo install -m755 first60.sh /usr/local/bin/first60
$ sudo first60 | tee /tmp/diag-$(date +%F-%H%M).txt
```

> [!tip] 十個指令的排列邏輯 ★★★
> ```
> ★★★ 順序不是隨便的：
>
>   1  uptime        → ★★ 有沒有問題？多嚴重？在惡化還是緩解？
>   2  dmesg         → ★★★ 有沒有【硬性錯誤】（OOM、硬體、I/O error）
>   3  vmstat        → ★★★★ 【一個指令涵蓋四大資源】
>   4  mpstat        → CPU 的細部（平均嗎？哪一類？）
>   5  pidstat       → CPU 是誰用的
>   6  iostat        → 磁碟的細部
>   7  free          → 記憶體的細部
>   8  sar -n DEV    → 網路吞吐
>   9  sar -n TCP    → 網路品質
>   10 top           → ★ 最後才看（★ 前面已經知道方向了）
>
> ★★★ 邏輯：【先全貌，再細部；先資源，再程序】
>   → ★★★★ top 放最後是因為它只給你「現在最忙的程序」，
>     不告訴你「系統的瓶頸在哪一類資源」
> ```

## ★★★ USE method

```
★★★★ USE = Utilization / Saturation / Errors
      對【每一個資源】問這三個問題：

  ★★★ Utilization（使用率）
    → 這個資源有多忙？（★ 時間比例或容量比例）

  ★★★★ Saturation（飽和度）← ★ 最容易被忽略但最重要
    → 有多少工作在【排隊等待】？
    → ★★★ 使用率 100% 不一定是問題，但排隊一定是

  ★★★ Errors（錯誤）
    → 有沒有錯誤事件？（★ 常常最先出現症狀）
```

### 五大資源的 USE 檢查表

| 資源 | **Utilization** | **★★ Saturation** | **Errors** |
| --- | --- | --- | --- |
| **CPU** | `mpstat` 的 `100-%idle` | **`vmstat` 的 `r` > 核心數**；`pidstat -w` 的 `nvcswch` | `mcelog`；`dmesg` |
| **記憶體** | `free` 的 `used/total` | **`vmstat` 的 `si`/`so`**；OOM killer | `dmesg \| grep -i oom` |
| **磁碟** | `iostat` 的 `%util` | **`iostat` 的 `aqu-sz`**；`vmstat` 的 `b` | `dmesg \| grep -i 'i/o error'`；`smartctl` |
| **網路** | `sar -n DEV` 的 `rxkB/txkB` | **`ss -s` 的 overflow**；`netstat -s` 的 drop | `ip -s link` 的 `errors`/`dropped` |
| **檔案描述符** | `lsof \| wc -l` vs `ulimit -n` | — | `dmesg \| grep 'too many open files'` |

```bash
#!/usr/bin/env bash
# ★★★ /usr/local/bin/use-check —— USE method 自動檢查
CORES=$(nproc)
echo "═══ USE Method Check ═══  ($CORES cores)"

# ═══ ★★★ CPU ═══
echo -e "\n【CPU】"
U=$(mpstat 1 2 2>/dev/null | tail -1 | awk '{print 100-$NF}')
R=$(vmstat 1 2 | tail -1 | awk '{print $1}')
printf "  Utilization: %.1f%%\n" "$U"
printf "  ★★ Saturation: r=%s (核心數=%s)" "$R" "$CORES"
[ "$R" -gt "$CORES" ] && echo "  ★★★ 排隊！" || echo "  ★ 正常"
echo "  Errors: $(dmesg 2>/dev/null | grep -ci 'mce\|machine check' || echo 0)"

# ═══ ★★★ 記憶體 ═══
echo -e "\n【記憶體】"
free | awk '/^Mem:/{printf "  Utilization: %.1f%%  (available %.1f%%)\n",
  ($2-$7)/$2*100, $7/$2*100}'
vmstat 1 2 | tail -1 | awk '{printf "  ★★★★ Saturation: si=%s so=%s", $7,$8
  if($7>0||$8>0) print "  ★★★★ 正在換頁 = 記憶體真的不夠"; else print "  ★ 沒有換頁"}'
OOM=$(dmesg 2>/dev/null | grep -ci 'out of memory\|oom-kill' || echo 0)
echo "  ★★★ Errors: OOM 事件 $OOM 次"

# ═══ ★★★ 磁碟 ═══
echo -e "\n【磁碟】"
iostat -xdz 1 2 2>/dev/null | awk '/^Device/{h=1;next} h&&NF>8 {
  printf "  %-10s util=%5.1f%%  ★★ aqu-sz=%5.2f  w_await=%6.1fms",$1,$NF,$(NF-1),$(NF-3)
  if($(NF-1)>2) printf "   ★★★ 排隊"
  if($(NF-3)>50) printf "   ★★★ 延遲高"
  print ""}' | tail -5
echo "  ★★★ Errors: $(dmesg 2>/dev/null | grep -ci 'i/o error\|ata.*failed' || echo 0) 次"

# ═══ ★★ 網路 ═══
echo -e "\n【網路】"
for i in $(ls /sys/class/net | grep -v lo); do
  ip -s link show "$i" | awk -v n="$i" '
    /RX:/{getline; rxe=$3; rxd=$4}
    /TX:/{getline; txe=$3; txd=$4;
      printf "  %-8s ★★ Errors: rx_err=%s rx_drop=%s tx_err=%s tx_drop=%s\n",n,rxe,rxd,txe,txd}'
done
echo "  ★★ Saturation:"
ss -s | grep -E 'TCP:' | sed 's/^/    /'
netstat -s 2>/dev/null | grep -iE 'overflow|listen.*drop|retransmit' | head -3 | sed 's/^/    ★★★ /'

# ═══ ★★ 檔案描述符 ═══
echo -e "\n【檔案描述符】"
CUR=$(cat /proc/sys/fs/file-nr | awk '{print $1}')
MAX=$(cat /proc/sys/fs/file-max)
awk -v c="$CUR" -v m="$MAX" 'BEGIN{printf "  Utilization: %s / %s (%.2f%%)\n", c, m, c/m*100}'
echo "  ★★ Errors: $(dmesg 2>/dev/null | grep -ci 'too many open files' || echo 0) 次"
```

> [!danger] Saturation 比 Utilization 重要 ★★★★
> ```
> ★★★★ 這是 USE method 最有價值的洞見：
>
>   【使用率 100% 不一定是問題】
>     · SSD 的 %util 100% 但 await < 1ms → ★ 完全沒問題
>     · CPU 100% 但 r = 核心數 → ★★ 剛好用滿，很有效率
>
>   【★★★★ 但只要有排隊，一定是問題】
>     · r > 核心數        → ★★★ 程序在等 CPU
>     · aqu-sz > 2        → ★★★ I/O 請求在排隊
>     · si/so > 0         → ★★★★ 記憶體在換頁
>     · listen overflow   → ★★★ 連線被丟棄
>
> ★★★ 實務意義：
>   → ★★ 監控告警應該設在【Saturation】而不是 Utilization
>   → 「CPU > 80% 告警」會一直誤報
>   → ★★★★ 「r > 核心數 持續 5 分鐘」才是真的有問題
> ```

## ★★★ RED method

```
★★★ USE 是【資源導向】（由內而外）
    RED 是【服務導向】（由外而內）
    → ★★★★ 兩個要一起用

★★★ RED = Rate / Errors / Duration
  對【每一個服務】問：

  ★★ Rate      每秒處理多少請求？
  ★★★ Errors    有多少失敗？（★ 5xx、逾時、例外）
  ★★★★ Duration  處理一個請求要多久？（★ 尤其是 P95/P99）
```

```bash
# ═══ ★★★ 從 Nginx access log 算 RED ═══

# ★★ Rate（每秒請求數）
$ awk '{print $4}' /var/log/nginx/access.log | \
    sed 's/\[//' | cut -d: -f1-3 | uniq -c | tail -10
   1240 28/Aug/2026:14:20
   1856 28/Aug/2026:14:21          # ★★ 每分鐘 1856 = 31 req/s

# ★★★ Errors（依狀態碼）
$ awk '{c[$9]++} END {for(s in c) printf "%s: %d\n", s, c[s]}' \
    /var/log/nginx/access.log | sort -rn -k2
200: 84210
404: 1240
500: 892                            # ★★★ 892 個 500！
502: 124                            # ★★★★ 上游掛了

# ★★★★ Duration（★ 需要在 log_format 加 $request_time）
$ awk '{print $NF}' /var/log/nginx/access.log | sort -n | \
    awk '{a[NR]=$1} END {
      printf "  P50: %.3fs\n  P90: %.3fs\n  ★★★ P95: %.3fs\n  ★★★★ P99: %.3fs\n  max: %.3fs\n",
      a[int(NR*0.50)], a[int(NR*0.90)], a[int(NR*0.95)], a[int(NR*0.99)], a[NR]}'
  P50: 0.082s
  P90: 0.341s
  ★★★ P95: 2.104s                   # ★★★ 5% 的請求超過 2 秒
  ★★★★ P99: 8.920s                  # ★★★★ 1% 超過 8 秒！
  max: 30.001s                       # ★★ 撞到 timeout
```

```nginx
# ★★★ 讓 access log 能算 Duration（★ 一定要加）
log_format timed '$remote_addr - $remote_user [$time_local] '
                 '"$request" $status $body_bytes_sent '
                 '"$http_referer" "$http_user_agent" '
                 'rt=$request_time uct=$upstream_connect_time '
                 'uht=$upstream_header_time urt=$upstream_response_time';
#                    ↑ ★★★★ 這四個是關鍵
access_log /var/log/nginx/access.log timed;
```

```bash
# ★★★★ 用 upstream 時間拆解瓶頸在哪一層
$ awk 'match($0,/rt=([0-9.]+).*urt=([0-9.]+)/,m) {
    nginx_time = m[1] - m[2]
    if (m[1] > 1) printf "總=%.3f 上游=%.3f nginx=%.3f  %s\n", m[1], m[2], nginx_time, $7
  }' /var/log/nginx/access.log | tail -10
總=2.104 上游=2.089 nginx=0.015  /api/reports
#         ↑ ★★★★ 幾乎全部時間在上游（PHP/後端）→ 不是 nginx 的問題

總=3.201 上游=0.042 nginx=3.159  /download/big.zip
#                     ↑ ★★★ 時間在 nginx（★ 傳輸大檔案，正常）

# ★★★ 找出最慢的 URL
$ awk 'match($0,/rt=([0-9.]+)/,m) {sum[$7]+=m[1]; cnt[$7]++}
  END {for(u in sum) printf "%.3f  %5d  %s\n", sum[u]/cnt[u], cnt[u], u}' \
    /var/log/nginx/access.log | sort -rn | head -10
8.240    124  /api/reports/export     # ★★★★ 平均 8 秒，被叫了 124 次
2.104   1820  /api/dashboard          # ★★★ 2 秒 × 1820 次 = 主要負載
0.082  42104  /api/users              # ★ 快
```

> [!tip] 為什麼要看 P95/P99 而不是平均 ★★★★
> ```
> ★★★★ 平均值會騙人：
>
>   1000 個請求：
>     990 個  0.05 秒
>      10 個  10 秒
>   → 平均 = 0.149 秒  ★★ 看起來很好！
>   → ★★★★ 但有 10 個使用者等了 10 秒
>
>   P50 = 0.05s     ★ 一半的人很快
>   P95 = 0.05s     ★ 95% 的人很快
>   ★★★★ P99 = 10s  ← ★ 這才是問題所在
>
> ★★★ 實務意義：
>   · 平均值適合看【趨勢】
>   · ★★★★ P95/P99 才反映【使用者的實際體驗】
>   · ★★ 一個使用者一天發 100 個請求
>     → P99 = 1% → ★★★ 平均每天遇到 1 次超慢
> ```

## ★★★ 由外而內的分層定位

```
★★★★ 「網站很慢」的六層排查（★ 由外而內縮小範圍）

  ┌─────────────────────────────────────────────────┐
  │ ① ★★ 使用者端／網路                              │
  │    · 是所有人都慢，還是只有他？                    │
  │    · ★★★ 從不同網路測（手機 4G / 外網 / 內網）     │
  │    · curl -w 看 DNS / 連線 / TTFB 的時間拆解       │
  └────────────────────┬────────────────────────────┘
  ┌────────────────────▼────────────────────────────┐
  │ ② ★★ TLS / CDN / 反向代理                        │
  │    · 憑證鏈完整？OCSP stapling？                  │
  │    · ★★ CDN 快取命中率                            │
  └────────────────────┬────────────────────────────┘
  ┌────────────────────▼────────────────────────────┐
  │ ③ ★★★ Web 伺服器（Nginx）                        │
  │    · ★★★ $request_time vs $upstream_response_time │
  │    · worker 數、連線數、error.log                  │
  └────────────────────┬────────────────────────────┘
  ┌────────────────────▼────────────────────────────┐
  │ ④ ★★★ 應用層（PHP-FPM / Node）                   │
  │    · ★★★★ pm.max_children 夠嗎？佇列多長？        │
  │    · 慢日誌、OPcache 命中率                        │
  └────────────────────┬────────────────────────────┘
  ┌────────────────────▼────────────────────────────┐
  │ ⑤ ★★★★ 資料庫                                    │
  │    · ★★★ 慢查詢、鎖等待、連線數                    │
  │    · ★★ 索引、buffer pool 命中率                   │
  └────────────────────┬────────────────────────────┘
  ┌────────────────────▼────────────────────────────┐
  │ ⑥ ★★★ 系統資源（CPU / 記憶體 / 磁碟 / 網路）      │
  │    · ★★★★ USE method                             │
  └─────────────────────────────────────────────────┘
```

```bash
# ═══ ★★★★【層 1】curl 的時間拆解（★ 最有效的第一步）═══
$ cat > /tmp/curl-format.txt <<'EOF'
     DNS 解析:  %{time_namelookup}s
     TCP 連線:  %{time_connect}s
   TLS 交握:    %{time_appconnect}s
   ★★★ TTFB:   %{time_starttransfer}s
   ★★ 總時間:   %{time_total}s
   ─────────────────────────────
   下載大小:    %{size_download} bytes
   下載速度:    %{speed_download} B/s
   HTTP 狀態:   %{http_code}
EOF

$ curl -w "@/tmp/curl-format.txt" -o /dev/null -s https://app.example.gov.tw/api/dashboard
     DNS 解析:  0.004s
     TCP 連線:  0.012s
   TLS 交握:    0.089s
   ★★★ TTFB:   2.104s          # ★★★★ 伺服器思考了 2 秒
   ★★ 總時間:   2.118s
   下載大小:    4820 bytes

#   ★★★★ 判讀：

## 常見瓶頸的特徵表 ★★★★

| 瓶頸 | **★ 特徵** | 確認 | 處置 |
| --- | --- | --- | --- |
| **CPU 不足** | `r` > 核心數；`us`+`sy` ≈ 100；**`wa` 低** | `mpstat`；`pidstat` | 優化程式／加 CPU／快取 |
| **★★★★ 記憶體不足** | **`si`/`so` > 0**；`available` < 10%；cache 被擠光 | `vmstat`；`free -h` | 降 `max_children`／調 buffer pool／加記憶體 |
| **★★★★ I/O 瓶頸** | **`b` > 0**；`wa` > 20%；`aqu-sz` > 2 | `iostat -x`；`iotop` | 加索引／換 SSD／調日誌 |
| **★★ 單執行緒** | 只有一顆 CPU 100% | `mpstat -P ALL` | 改用多程序／多執行緒 |
| **★★★ 中斷集中** | 某顆的 `%soft` 高 | `/proc/interrupts` | RSS/RPS／`irqbalance` |
| **★★★★ 雲端超賣** | **`st` > 5%** | `mpstat` | **換機型**（不是你的問題） |
| **★★★★ FPM worker 不足** | `listen queue` > 0；`max children reached` > 0 | `/status?full` | 調 `pm.max_children`（**★ 用 PSS 算**） |
| **★★★ 慢查詢** | 上游時間長；`Slow queries` 增加 | 慢日誌；`sys.session` | **加索引**／改寫查詢／快取 |
| **★★★ 連線數上限** | `Too many open files`；`accept4() failed` | `error.log`；`ss -s` | 調 `worker_rlimit_nofile`／`LimitNOFILE` |
| **★★★ TCP backlog 滿** | `listen overflow`；連線被丟 | `netstat -s`；`ss -lnt` | 調 `somaxconn`／`backlog` |
| **★★ 網路飽和** | `rxkB/txkB` 接近網卡上限 | `sar -n DEV` | 加頻寬／壓縮／CDN |
| **★★ 磁碟空間/inode** | 寫入失敗 | `df -h`；`df -i` | 清理／`lsof +L1` |
| **★★★ 快取失效** | 命中率驟降 | OPcache/Redis 統計 | 檢查快取設定與 TTL |

## 速查表

### ★★★★ 60 秒檢查清單

```bash
uptime                    # ① ★★ load 趨勢（1分>15分 = 惡化中）
dmesg -T | tail           # ② ★★★ OOM / I/O error / 硬體
vmstat -w 1 5             # ③ ★★★★ r b si so wa st（最重要）
mpstat -P ALL 1 3         # ④ CPU 平均嗎？哪一類？
pidstat 1 3               # ⑤ 誰在吃 CPU
iostat -xdz 1 3           # ⑥ ★★★ aqu-sz / await
free -m                   # ⑦ ★★★ available
sar -n DEV 1 3            # ⑧ 網路吞吐
sar -n TCP,ETCP 1 3       # ⑨ ★★ retrans / overflow
top -b -n1 | head -15     # ⑩ ★ 最後才看
```

### ★★★★ USE method

```
對每個資源問三個問題：
  Utilization  有多忙？
  ★★★★ Saturation  有多少在【排隊】？ ← 最重要
  Errors       有錯誤嗎？

CPU:    100-%idle  |  ★★★ r > 核心數      |  mcelog
記憶體:  used/total |  ★★★★ si/so > 0     |  OOM killer
磁碟:   %util      |  ★★★★ aqu-sz > 2    |  i/o error
網路:   rx/txkB    |  ★★★ overflow/drop  |  ip -s link
fd:     file-nr    |  —                   |  too many open files

★★★★ 告警設在 Saturation，不要設在 Utilization
```

### ★★★ RED method

```
Rate      每秒請求數
Errors    ★★★ 5xx / 逾時
Duration  ★★★★ P95 / P99（不要看平均）

log_format 一定要加：
  rt=$request_time urt=$upstream_response_time
  → ★★★★ rt - urt = nginx 花的時間；urt = 後端花的時間
```

### ★★★★ curl 時間拆解

```bash
curl -w "@/tmp/curl-format.txt" -o /dev/null -s https://host/path
# DNS > 0.1s      → DNS 問題
# connect > 0.1s  → 網路 / 防火牆
# appconnect>0.3s → TLS / 憑證鏈
# ★★★★ TTFB 慢   → 伺服器端處理 ← 往下查
# total-TTFB 大   → 傳輸慢
```

### ★★★★ 三種「慢」的快速區分

```
r > 核心數, wa 低          → ★★★ CPU 不足
si/so > 0, available < 10% → ★★★★ 記憶體不足
b > 0, wa > 20%, aqu-sz>2  → ★★★★ I/O 瓶頸
st > 5%                    → ★★★★ 雲端超賣（換機型）
以上都正常                  → ★★★ 往應用層查（FPM/DB）
```

### 分層定位

```
① curl 時間拆解      ② TLS/CDN
③ nginx error.log + rt vs urt
④ ★★★★ FPM /status?full（listen queue、max children reached）
⑤ ★★★★ 慢查詢 + EXPLAIN + sys.statements_with_full_table_scans
⑥ ★★★★ USE method
```

### ★★★ 三個原則

```
① 先量測，不要猜
② 一次只改一個變數
③ 問三次「為什麼」找根因
★★★ 事後寫 incident 記錄
```

## 小測驗

Q1. **排查效能問題的三個核心原則**？

Q2. **60 秒清單為什麼把 `top` 放在最後**？

Q3. **USE method 是什麼**？為什麼 Saturation 比 Utilization 重要？

Q4. **監控告警該設在 Utilization 還是 Saturation**？各舉一個例子。

Q5. **為什麼要看 P99 而不是平均回應時間**？

Q6. **`$request_time` 和 `$upstream_response_time` 的差值代表什麼**？

Q7. **`curl -w` 顯示 TTFB 2 秒但 DNS/connect/TLS 都很快，往哪個方向查**？

Q8. **PHP-FPM 的 `listen queue > 0` 和 `max children reached > 0` 代表什麼**？

Q9. **所有系統指標都正常但使用者說慢，五個排查方向**？

Q10. **「重開機就好了」為什麼是糟糕的處置**？該怎麼做？

> [!question]- 測驗答案
> **Q1.** ①**★★★★ 先量測，不要猜** ——
> 「我覺得是資料庫」不是證據，「iowait 62%、available 0.6G」才是。
> 憑印象猜通常會猜錯，而且會浪費時間在錯的方向上；
> ②**★★★★ 一次只改一個變數** ——
> 同時調 `max_children`、`buffer_pool`、加索引，
> 就算問題解決了也**不知道是哪一個有效**，
> 更糟的是不知道另外兩個是不是讓情況變糟了（只是被第三個蓋過去）；
> ③**★★★★ 找到根因，不要只解症狀** ——
> 重開機讓症狀消失，但根因還在，明天會再發生。
> **問「為什麼」至少三次**：
> 「網站慢」→「iowait 高」→「記憶體不夠 cache 被擠光」→
> 「`pm.max_children` 設 50 但只有 8G 記憶體」← **這才是根因**。
>
> **Q2.** 因為 **`top` 只告訴你「現在最忙的程序」，不告訴你「瓶頸在哪一類資源」**。
> 60 秒清單的邏輯是**先全貌、再細部；先資源、再程序**：
> `uptime` 判斷嚴重程度與趨勢 →
> `dmesg` 找硬性錯誤（OOM、I/O error、硬體）→
> **`vmstat` 一個指令涵蓋四大資源** →
> 然後才依 vmstat 指出的方向去看細部（`mpstat`/`iostat`/`free`）。
> **如果一開始就看 `top`**，你會看到「mysqld 佔 8% CPU」，
> 然後開始懷疑資料庫 —— 但真正的問題可能是
> **磁碟排隊**（mysqld 只是受害者，它在等 I/O 所以 CPU 才低）。
> 先看資源層才不會被表面現象誤導。
>
> **Q3.** **USE = Utilization（使用率）/ Saturation（飽和度）/ Errors（錯誤）**，
> **對每一個資源都問這三個問題**，
> 這樣就**不會漏掉任何一類資源**（CPU、記憶體、磁碟、網路、檔案描述符）。
> **★★★★ Saturation 比 Utilization 重要的原因**：
> **使用率 100% 不一定是問題，但只要有排隊就一定是問題**。
> SSD 的 `%util` 100% 但 `await` < 1ms 完全正常（它能平行處理）；
> CPU 100% 但 `r` = 核心數表示剛好用滿，很有效率。
> 反之：
> `r` > 核心數 = 程序在等 CPU；
> `aqu-sz` > 2 = I/O 請求在排隊；
> **`si`/`so` > 0 = 記憶體在換頁**；
> `listen overflow` = 連線被丟棄 —— **這些每一個都直接對應到使用者感受到的延遲**。
>
> **Q4.** **★★★ 設在 Saturation**。
> **Utilization 告警的問題**：
> 「CPU > 80% 告警」會**一直誤報** ——
> 一台把 CPU 用滿的機器可能只是很有效率地在工作，
> 而且深夜的批次作業本來就會把 CPU 拉滿。
> 久了就變成「狼來了」，真的有事時沒人看。
> **Saturation 告警的例子**：
> ```
> ★★★ CPU：   vmstat 的 r > 核心數，持續 5 分鐘
> ★★★★ 記憶體：vmstat 的 si 或 so > 0，持續 3 分鐘
> ★★★★ 磁碟：  iostat 的 aqu-sz > 4，持續 5 分鐘
> ★★★ 應用：  PHP-FPM 的 listen queue > 0
> ★★★ 網路：  netstat -s 的 listen overflow 增加
> ```
> 這些**每一條都直接對應到「有人在等」**，誤報率低很多。
> Errors 類（OOM、I/O error、5xx 率）也該告警。
>
> **Q5.** 因為**平均值會騙人**。
> ```
> 1000 個請求：990 個 0.05 秒，10 個 10 秒
> → 平均 = 0.149 秒     ★★ 看起來很好
> → ★★★★ 但有 10 個使用者等了 10 秒
> ```
> **P50 = 0.05s、P95 = 0.05s、P99 = 10s** ——
> **只有 P99 反映出問題**。
> **實務意義更嚴重**：一個使用者一天可能發 100 個請求，
> P99 = 1% 表示**他平均每天會遇到一次超慢的體驗**，
> 而那次體驗就是他對系統的印象。
> **平均值適合看趨勢**（今天比昨天慢了嗎），
> **P95/P99 才反映使用者的實際體驗**。
> Nginx 要能算這個，`log_format` 必須加 **`$request_time`**。
>
> **Q6.** **`$request_time` = nginx 收到請求到送完回應的總時間**；
> **`$upstream_response_time` = 上游（PHP-FPM/Node/後端）處理的時間**。
> **★★★★ 兩者的差值 = nginx 自己花的時間**（含網路傳輸給客戶端）。
> **判讀**：
> ```
> rt=2.104 urt=2.089  → 差 0.015  ★★★★ 幾乎全在後端 → 查 PHP/DB
> rt=3.201 urt=0.042  → 差 3.159  ★★★ 時間在 nginx
> ```
> 後者的常見原因：**傳輸大檔案**（正常）、
> **客戶端網路很慢**（nginx 要慢慢餵資料給它）、
> **`proxy_buffering off`** 導致 nginx 被慢客戶端拖住、
> 或 nginx 本身的 worker 不足。
> 這一個差值就能**把問題切成「前面」和「後面」兩半**，
> 是分層定位最有效的一刀。
>
> **Q7.** **★★★★ 伺服器端的處理** —— 往下查應用層與資料庫。
> TTFB（time to first byte）涵蓋的是
> 「連線建立完成之後，到收到第一個位元組」的時間，
> DNS、TCP、TLS 都已經排除了，**剩下的就是伺服器在思考**。
> **往下的順序**：
> ①**nginx**：`error.log` 有沒有 `upstream timed out`；
> 比對 `rt` 與 `urt` 確認是不是後端；
> ②**PHP-FPM**：`/status?full` 看 **`listen queue`** 和 **`max children reached`**；
> `php-fpm-slow.log` 看卡在哪一行程式碼；
> ③**資料庫**：慢查詢日誌、`sys.session`、
> **`sys.statements_with_full_table_scans`**（找缺索引的查詢）；
> ④**系統資源**：`first60` + USE method。
> 反之如果是 **`total - TTFB` 很大**，那是傳輸階段慢（內容太大或頻寬不足）。
>
> **Q8.** **`listen queue > 0`** = **有請求在 socket 佇列裡等待**，
> 因為**所有 FPM worker 都在忙，沒有人能接手**。
> **`max children reached > 0`** = **曾經達到 `pm.max_children` 上限**
> （這是一個累計計數器，不會歸零）。
> **兩者一起出現 = worker 數量不足**，使用者正在排隊等待。
> **但★★★ 不能直接把 `max_children` 調大** ——
> 要先確認**記憶體夠不夠**：
> ```bash
> # ★★★ 用 PSS 算單一 worker 的真實用量（RES 會高估近兩倍）
> for p in $(pgrep -x php-fpm); do
>   grep ^Pss: /proc/$p/smaps_rollup | awk '{print $2}'
> done | awk '{s+=$1;n++} END {printf "平均 PSS: %.0f MB\n", s/n/1024}'
> ```
> `max_children = (可用記憶體 - 資料庫 - 系統) / 單一 worker 的 PSS`。
> **也要同時查「為什麼每個請求那麼慢」** ——
> worker 不夠常常是**慢查詢**造成的（worker 都卡在等資料庫），
> 加索引比調大 `max_children` 有效得多。
>
> **Q9.** ①**★★★ 間歇性問題** —— 你看的時候剛好正常。
> 用 **`sar` 查歷史**（`sar -u -s 14:00 -e 16:00 -f .../sa27`），
> 或部署 watchdog 在異常時自動蒐證；
> ②**★★★ 問題不在這台機器** —— 資料庫、快取、外部 API 在別台。
> 用 **`curl` 時間拆解 + 分層測試**（本機/內網/外網）；
> ③**★★★ 只有特定使用者或請求慢** ——
> 看整體平均會完全看不到。從 access log **找出最慢的 URL**、
> 看 **P99 而不是 P50**、注意特定大客戶的資料量；
> ④**★★ 前端問題** —— **TTFB 很快但頁面很慢** 就是前端，
> 資源太多、JS 阻塞、圖片沒壓縮，用 DevTools Network 和 Lighthouse 查；
> ⑤**★★ 使用者的網路** —— 從不同網路測、`mtr` 看路徑、
> 檢查分公司專線或 VPN。
>
> **Q10.** 因為**重開機只是讓症狀消失，根因原封不動** ——
> 它清掉了累積的狀態（記憶體洩漏、卡住的連線、滿的佇列），
> 所以「好了一小時」，然後**同樣的累積過程再跑一遍，問題必然重現**。
> 更糟的是：**重開機把證據也清掉了** ——
> 記憶體狀態、程序清單、開啟的檔案描述符、`/proc` 下的統計，
> 全部歸零，下次再發生時你還是從頭開始猜。
> **該怎麼做**：
> ①**★★★ 重開機前先蒐證** ——
> `first60 > /tmp/diag-$(date +%F-%H%M).txt`，
> 加上 `ps aux`、`ss -s`、`lsof`、應用的 status 頁；
> ②**如果服務中斷必須立刻恢復**，那就先重啟服務（不是整台機器），
> 但**證據一定要先存下來**；
> ③**★★★★ 事後用那份證據做根因分析**，問三次為什麼；
> ④**寫 incident 記錄**（影響/偵測/根因/處置/效果/預防），
> 並把預防措施（監控告警、CI 檢查）真的做掉 ——
> 否則下次還是同一個問題。
