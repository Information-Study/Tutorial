# 前端建置工具與套件管理

> [!abstract] 這篇你會學到
> - `package.json` / lock 檔 / `node_modules` 三者的分工，以及**為什麼 lock 檔一定要進版控**
> - ★★★★ **部署腳本用 `npm ci` 而不是 `npm install`** —— 這是最重要的一條
> - Vite 的開發伺服器與建置產物，以及 dev 與 build 行為不同造成的「本機好好的」問題
> - ★★★★★ 前端環境變數**沒有秘密可言**：`VITE_` 開頭的變數會原封不動出現在打包產物裡
> - 建置產物的部署方式（含 Nginx 快取設定）與 CI 上常見的建置失敗排查
> - 供應鏈安全：`npm audit`、鎖版本、postinstall 腳本的風險

## 觀念說明

### 三個檔案的分工

```
package.json          ← 你「宣告」要哪些套件（範圍版本，如 ^5.4.0）
package-lock.json     ← 記錄「實際裝了」哪個版本（精確版本 + 雜湊）
node_modules/         ← 實際的套件檔案（★★★★ 絕不進版控，體積上百 MB）
```

```json
// package.json
{
  "name": "dashboard",
  "type": "module",
  "scripts": {
    "dev":       "vite",
    "build":     "vite build",
    "preview":   "vite preview",
    "typecheck": "tsc --noEmit"
  },
  "dependencies":    { "vue": "^3.5.13" },
  "devDependencies": { "vite": "^6.0.7", "typescript": "^5.7.2" }
}
```

| 欄位 | 意義 | 星級 |
| --- | --- | --- |
| `dependencies` | **執行期**需要的套件（會被打包進產物） | ★★★★ |
| `devDependencies` | **只有建置時**需要（Vite、TS、ESLint） | ★★★★ |
| `scripts` | 用 `npm run <名稱>` 執行 | ★★★★ |
| `type: "module"` | 這個專案用 ESM（`import` 而非 `require`） | ★★★ |

★★★ 前端專案裡這兩者的分界常被搞混。判斷法：**建置完的 `dist/` 還需要它嗎？**
需要 → `dependencies`；只在 `npm run build` 期間用到 → `devDependencies`。
（純靜態前端其實兩者都不會被安裝到伺服器上，但分清楚有助於 CI 加速與稽核。）

### 版本範圍符號 ★★★★

```
"vue": "^3.5.13"    → 允許 3.x.x（次版本與修訂可升，主版本不可）  ← 預設
"vue": "~3.5.13"    → 允許 3.5.x（只有修訂可升）
"vue": "3.5.13"     → 精確鎖死
"vue": "*"          → ★★★★ 任何版本，絕對不要用
```

★★★★ **這就是 lock 檔存在的理由**：`^3.5.13` 在今天裝到 3.5.13，
三個月後在 CI 上可能裝到 3.9.2，於是「我這邊好好的，CI 就是建不起來」。
Lock 檔把每個套件（含相依套件的相依套件）都釘到精確版本與雜湊。

> [!danger] lock 檔一定要進版控
> ★★★★★ `package-lock.json`（npm）／`pnpm-lock.yaml`（pnpm）／`yarn.lock`（yarn）
> **必須 commit 進 git**。把它加進 `.gitignore` 是嚴重錯誤 ——
> 等於放棄了「每次建置結果一致」的保證，也放棄了套件版本的稽核軌跡。

### `npm install` vs `npm ci` ★★★★★

| | `npm install` | `npm ci` |
| --- | --- | --- |
| 依據 | `package.json` | ★★★★ **只看 lock 檔** |
| 會不會改 lock 檔 | ★★★★ **會**（可能悄悄升版） | 不會，lock 與 package.json 不符就直接失敗 |
| `node_modules` | 增量更新 | ★★★ 先整個刪掉再裝 |
| 速度 | 較慢 | 較快 |
| 用在 | 本機開發、要新增套件時 | ★★★★★ **CI、部署腳本** |

```bash
# 本機開發
npm install                 # 首次或新增套件後
npm install axios           # 新增套件（會改 package.json 與 lock 檔）
npm install -D vitest       # 新增開發用套件

# ★★★★★ CI 與部署腳本一律用這個
npm ci
```

> [!warning] 部署腳本用 `npm install` 的後果
> 每次部署都可能裝到不同版本 —— 上週部署好好的，這週同一份程式碼建置失敗，
> 或者建置成功但線上行為改變。因為某個相依套件在這期間發了新的修訂版。
> ★★★★ **部署腳本裡看到 `npm install` 就該改成 `npm ci`。**

### npm / pnpm / yarn 怎麼選

| | npm | pnpm | yarn |
| --- | --- | --- | --- |
| 是否內建 | ★★★ 隨 Node 附帶 | 要另裝 | 要另裝 |
| 磁碟用量 | 每個專案一份完整 `node_modules` | ★★★★ 全域硬連結，省 60~80% | 中等 |
| 安裝速度 | 中 | ★★★★ 最快 | 快 |
| 嚴格度 | 寬鬆（幽靈相依可用） | ★★★★ 嚴格（沒宣告就不能 import） | 中 |
| 多專案 monorepo | 可 | ★★★ 最好 | 可 |

**選擇原則**：
- 接手既有專案 → ★★★★ **看它有哪個 lock 檔就用哪個**，不要混用
- 新專案、單一專案 → npm 就夠（少一個要裝的東西）
- 伺服器上跑很多前端專案、磁碟吃緊 → pnpm

```bash
# ★★★★ 混用 lock 檔是常見災難
ls -1 *.lock* package-lock.json pnpm-lock.yaml yarn.lock 2>/dev/null
# 出現兩個以上 → 團隊沒有共識，先開會決定留哪個，其餘刪掉
```

## 環境準備與安裝

### Node.js 版本管理

```bash
# 確認版本
node --version      # v22.x.x
npm --version       # 10.x.x

# ★★★★ 專案宣告需要的版本
cat package.json | grep -A3 '"engines"'
```

```json
{
  "engines": { "node": ">=20.19.0" },
  "packageManager": "pnpm@9.15.0"
}
```

★★★★ Node 版本不符是 CI 建置失敗的第一名成因。用 `.nvmrc` 統一：

```bash
echo "22" > .nvmrc          # 進版控
nvm use                     # 開發者切到正確版本
```

```yaml
# GitHub Actions 讀同一份
- uses: actions/setup-node@v4
  with:
    node-version-file: '.nvmrc'
    cache: 'npm'
```

> [!info]- 伺服器上安裝 Node（Ubuntu / RHEL）
> ```bash
> # Ubuntu / Debian —— NodeSource
> curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
> sudo apt install -y nodejs
> ```
> ```bash
> # Rocky / AlmaLinux
> sudo dnf module reset nodejs
> sudo dnf module enable nodejs:22
> sudo dnf install -y nodejs
> ```
> ★★★ 發行版內建的 Node 通常太舊（Ubuntu 24.04 是 18.x），
> 建置現代前端專案會失敗。詳見 [[060-03-02-03-guide-PM2-程序管理入門]] 所在章節。

## 基礎設定

### `vite.config.ts` 的關鍵設定

```typescript
import { defineConfig, loadEnv } from 'vite';

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '');

  return {
    // ★★★★ 部署在子路徑時必改，否則資源全部 404
    base: env.VITE_BASE_PATH || '/',

    server: {
      host: '0.0.0.0',
      port: 5173,
      // ★★★ 開發用代理，解決 CORS（見 04 篇）
      proxy: {
        '/api': {
          target: env.VITE_API_TARGET || 'http://localhost:8000',
          changeOrigin: true,
        },
      },
    },

    build: {
      outDir: 'dist',
      // ★★★★ 正式環境不要輸出 source map（會洩漏原始碼）
      sourcemap: mode !== 'production',
      // ★★★ 超過這個大小（KB）就警告，提醒你做分割
      chunkSizeWarningLimit: 600,
      rollupOptions: {
        output: {
          // 把大型套件拆出來，讓它們的快取不被業務程式碼的改動打掉
          manualChunks: {
            vendor: ['vue', 'vue-router'],
          },
        },
      },
    },
  };
});
```

### ★★★★★ 環境變數：前端沒有秘密

```bash
# .env                 所有環境共用（★★★ 進版控）
# .env.development     npm run dev 時
# .env.production      npm run build 時
# .env.local           ★★★★ 本機覆寫，一定要進 .gitignore
```

```bash
# .env.production
VITE_API_BASE=/api
VITE_APP_TITLE=機房監控儀表板

# ✗✗✗ 絕對不可以
VITE_DB_PASSWORD=P@ssw0rd
VITE_API_SECRET=sk-xxxxxxxx
```

```typescript
// 讀取
const 標題 = import.meta.env.VITE_APP_TITLE;
const 是正式 = import.meta.env.PROD;    // Vite 內建
```

> [!danger] 這是本篇最重要的一條
> ★★★★★ **只有 `VITE_` 開頭的變數會被注入，而注入的方式是「在建置時把文字直接替換進 JS 檔」。**
> 也就是說，`VITE_API_SECRET=sk-abc123` 會變成 `dist/assets/index-xxx.js` 裡的一段明文字串。
> 任何人下載你的網頁、按 F12、或直接 `curl` 那支 JS 檔都看得到。
>
> **前端不存在「隱藏的環境變數」這種東西。** 需要保密的一律放伺服器端。

**驗證方式**（★★★★ 每次上線前都該跑）：

```bash
npm run build

# 檢查產物裡有沒有可疑字串
grep -rEi 'password|secret|api[_-]?key|token|sk-[a-zA-Z0-9]{20}' dist/ \
  && echo "★★★★★ 發現疑似機密，停止部署！" \
  || echo "✓ 未發現明顯機密"
```

## 進階設定與調校

### 讀懂建置產物

```bash
npm run build
```

```
vite v6.0.7 building for production...
✓ 47 modules transformed.
dist/index.html                   0.62 kB │ gzip:  0.38 kB
dist/assets/index-BvK2xQ8p.css   12.44 kB │ gzip:  3.02 kB
dist/assets/vendor-Dp3nQz1a.js   98.71 kB │ gzip: 38.15 kB
dist/assets/index-C7mR9tYb.js    24.03 kB │ gzip:  9.44 kB
✓ built in 1.24s
```

| 觀察點 | 說明 |
| --- | --- |
| ★★★★ 檔名裡的 `BvK2xQ8p` | **內容雜湊**。內容改變 → 檔名改變 → 瀏覽器一定重新下載 |
| ★★★★ 看 gzip 欄，不是原始大小 | 使用者實際下載的是壓縮後的量 |
| `vendor-*.js` | 第三方套件，通常不常變，快取效益最高 |
| ★★★ 單檔 > 500 kB | 該考慮動態 import 做分割 |

```
dist/
├── index.html          ← ★★★★ 絕不能長期快取
└── assets/
    ├── index-*.css     ← ★★★★ 可以快取一年（檔名有雜湊）
    ├── index-*.js
    └── vendor-*.js
```

### 部署到 Nginx ★★★★

```nginx
server {
    listen 443 ssl http2;
    server_name dash.example.tw;

    root /var/www/dashboard/dist;
    index index.html;

    # ★★★★ SPA 路由：找不到檔案就回 index.html，交給前端路由處理
    location / {
        try_files $uri $uri/ /index.html;
    }

    # ★★★★★ index.html 絕不快取 —— 它記載了目前該載哪些帶雜湊的資源
    location = /index.html {
        add_header Cache-Control "no-cache, must-revalidate" always;
        expires -1;
    }

    # ★★★★ 帶雜湊的資源可以快取一年（immutable 表示「內容永遠不會變」）
    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable" always;
        access_log off;
    }

    # API 反向代理 —— 同源，不需要 CORS（見 04 篇）
    location /api/ {
        proxy_pass http://127.0.0.1:8000/;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;
}
```

> [!danger] 快取設反的後果
> ★★★★★ 如果把 `index.html` 也設成 `max-age=31536000`，使用者的瀏覽器會
> **永遠拿舊的 index.html**，而它指向的 `index-舊雜湊.js` 已經被新版部署刪掉 →
> 整個網站白畫面，而且**清不掉**（除非使用者自己清快取）。
> 這是前端部署最嚴重也最常見的事故。規則只有一句：
> **有雜湊的長快取，沒雜湊的不快取。**

### 部署在子路徑

```bash
# 要部署到 https://example.tw/dashboard/
VITE_BASE_PATH=/dashboard/ npm run build
```

```nginx
location /dashboard/ {
    alias /var/www/dashboard/dist/;
    try_files $uri $uri/ /dashboard/index.html;

```

★★★★ 忘記設 `base` 是子路徑部署最常見的錯 —— 症狀是頁面空白、
Console 一堆 404，路徑都是 `/assets/...` 而不是 `/dashboard/assets/...`。

## 完整實戰範例

### 從 GitHub 專案到上線的完整部署腳本

**`/usr/local/bin/deploy-frontend`**

```bash
#!/usr/bin/env bash
# 前端專案建置與部署 —— 原子切換、保留舊版可回滾
set -euo pipefail

# ── 設定 ────────────────────────────────────────────────────
專案="${1:?用法：deploy-frontend <專案名> [git分支]}"
分支="${2:-main}"

原始碼="/srv/src/${專案}"
發布根="/var/www/${專案}"
版本目錄="${發布根}/releases/$(date +%Y%m%d-%H%M%S)"
現行連結="${發布根}/current"
保留版本數=5

紅=$'\e[31m'; 綠=$'\e[32m'; 黃=$'\e[33m'; 無=$'\e[0m'
步驟() { printf '%s▶ %s%s\n' "$黃" "$*" "$無"; }
成功() { printf '%s✓ %s%s\n' "$綠" "$*" "$無"; }
失敗() { printf '%s✗ %s%s\n' "$紅" "$*" "$無" >&2; exit 1; }

# ── 1. 取得原始碼 ────────────────────────────────────────────
步驟 "取得原始碼（${分支}）"
if [[ -d "${原始碼}/.git" ]]; then
  git -C "$原始碼" fetch --prune origin
  git -C "$原始碼" checkout "$分支"
  git -C "$原始碼" reset --hard "origin/${分支}"    # ★★★ 丟棄本機改動，確保與遠端一致
else
  失敗 "找不到 ${原始碼}/.git"
fi
提交=$(git -C "$原始碼" rev-parse --short HEAD)
成功 "已更新到 ${提交}"

cd "$原始碼"

# ── 2. 檢查 Node 版本 ────────────────────────────────────────
if [[ -f .nvmrc ]]; then
  需要=$(tr -dc '0-9.' < .nvmrc)
  現有=$(node --version | tr -dc '0-9.')
  [[ "${現有%%.*}" == "${需要%%.*}" ]] \
    || 失敗 "Node 版本不符：需要 ${需要}，目前 ${現有}"
fi
成功 "Node $(node --version)"

# ── 3. 安裝相依（★★★★ 一定用 ci，不用 install） ────────────────
步驟 "安裝相依套件"
[[ -f package-lock.json ]] || 失敗 "缺少 package-lock.json —— lock 檔必須進版控"
npm ci --no-audit --no-fund || 失敗 "npm ci 失敗（lock 檔與 package.json 是否同步？）"
成功 "相依安裝完成"

# ── 4. 型別檢查與 lint（有設定才跑） ──────────────────────────
if npm run | grep -q '^  typecheck'; then
  步驟 "型別檢查"
  npm run --silent typecheck || 失敗 "型別檢查未通過"
  成功 "型別檢查通過"
fi

# ── 5. 建置 ─────────────────────────────────────────────────
步驟 "建置正式版"
rm -rf dist
NODE_ENV=production npm run build || 失敗 "建置失敗"
[[ -f dist/index.html ]] || 失敗 "建置產物缺少 index.html"
成功 "建置完成（$(du -sh dist | cut -f1)）"

# ── 6. ★★★★★ 機密掃描：擋住把金鑰打包進去的意外 ───────────────
步驟 "掃描產物中的機密"
if grep -rEiq 'sk-[A-Za-z0-9]{20,}|BEGIN [A-Z ]*PRIVATE KEY|["'\'']password["'\'']\s*:\s*["'\''][^"'\'']{4,}' dist/; then
  grep -rEin 'sk-[A-Za-z0-9]{20,}|BEGIN [A-Z ]*PRIVATE KEY' dist/ | head -5
  失敗 "產物中發現疑似機密，部署中止"
fi
成功 "未發現機密"

# ── 7. 原子切換 ─────────────────────────────────────────────
步驟 "發布"
mkdir -p "${發布根}/releases"
cp -a dist "$版本目錄"
echo "$提交" > "${版本目錄}/.commit"
chown -R www-data:www-data "$版本目錄"
find "$版本目錄" -type d -exec chmod 755 {} +
find "$版本目錄" -type f -exec chmod 644 {} +

# ★★★★ ln -sfn + mv 才是原子操作，直接 rm 再 ln 中間會有幾毫秒的 404
ln -sfn "$版本目錄" "${發布根}/current.new"
mv -Tf "${發布根}/current.new" "$現行連結"
成功 "已切換到 $(basename "$版本目錄")"

# ── 8. 驗證 ─────────────────────────────────────────────────
步驟 "驗證"
nginx -t || 失敗 "Nginx 設定有誤"
systemctl reload nginx
sleep 1
碼=$(curl -s -o /dev/null -w '%{http_code}' "https://${專案}.example.tw/")
[[ "$碼" == "200" ]] || 失敗 "首頁回應 ${碼}，請檢查（可用下方指令回滾）"
成功 "首頁回應 200"

# ── 9. 清理舊版本 ───────────────────────────────────────────
cd "${發布根}/releases"
```

## 常見錯誤與排錯

| 現象 | 原因 | 解法 |
| --- | --- | --- |
| ★★★★★ 部署後使用者看到白畫面、Console 一堆 404 | `index.html` 被長期快取，指向已刪除的舊雜湊檔 | Nginx 對 `index.html` 設 `no-cache`；已發生時只能請使用者強制重整 |
| ★★★★ 本機建置成功、CI 失敗 | Node 版本不同、或用了 `npm install` 裝到新版套件 | `.nvmrc` + `setup-node` + `npm ci` |
| ★★★★ `npm ci` 報 `lock file does not satisfy package.json` | 有人改了 `package.json` 卻沒更新 lock 檔 | 本機跑 `npm install` 產生新 lock 並 commit |
| ★★★★ 子路徑部署後資源全 404 | 沒設 `base` | `VITE_BASE_PATH=/子路徑/ npm run build` |
| ★★★★ 重新整理 SPA 深層網址回 404 | Nginx 沒設 `try_files` | 加 `try_files $uri $uri/ /index.html;` |
| ★★★★ 開發時 API 正常、上線後 CORS 錯誤 | Vite 代理**只在 dev 有效** | 正式環境用 Nginx 反向代理，見 [[070-01-04-cmd-前端-JavaScript非同步與API]] |
| ★★★ `EACCES: permission denied` | 用 sudo 跑過 npm，`node_modules` 變 root 所有 | `sudo chown -R $USER ~/.npm node_modules`；★★★ 不要用 sudo 跑 npm |
| ★★★ `ERR_OSSL_EVP_UNSUPPORTED` | 舊版 webpack 專案 + 新版 Node 的 OpenSSL 3 | `NODE_OPTIONS=--openssl-legacy-provider`，或升級建置工具 |
| ★★★ 建置時 `JavaScript heap out of memory` | 專案大、記憶體不足 | `NODE_OPTIONS=--max-old-space-size=4096 npm run build` |
| ★★★ 產物有 `.map` 檔對外可下載 | `sourcemap: true` 上了正式環境 | 設 `sourcemap: false`，或 Nginx 擋 `location ~ \.map$ { return 404; }` |
| ★★ `dist/` 被 commit 進 git | `.gitignore` 沒寫 | `git rm -r --cached dist` 並補進 `.gitignore` |
| ★★ 同時存在兩種 lock 檔 | 團隊混用 npm 與 pnpm | 決定一種，刪掉另一種，寫進 README |

### 排查步驟

**【1】確認環境一致**

```bash
node --version && npm --version
cat .nvmrc 2>/dev/null
grep -E '"(engines|packageManager)"' -A3 package.json
```

★★★★ 三者對不上就先修這個，不要往下查。

**【2】乾淨重裝，排除 `node_modules` 髒掉的可能**

```bash
rm -rf node_modules
npm ci
```

★★★ 「本機好好的」問題有一半是 `node_modules` 累積了舊狀態。
`npm ci` 會先整個刪掉再裝，正好處理這件事。

**【3】看完整的建置錯誤**

```bash
npm run build 2>&1 | tee /tmp/build.log
grep -nE 'error|Error|ERR!' /tmp/build.log | head -20
```

**【4】建置成功但畫面不對 —— 用 preview 排除伺服器因素**

```bash
npm run preview      # 用建置產物起一個本機伺服器（不是 dev server）
```

★★★★ 這一步很關鍵：`npm run dev` 與 `npm run build` 的行為**不一樣**
（dev 不打包、不壓縮、環境變數也不同）。
「dev 正常但上線壞掉」的問題，`npm run preview` 通常就能重現。

**【5】確認伺服器上的檔案真的是新的**

```bash
ls -la /var/www/dashboard/current            # 看 symlink 指向哪個版本
cat /var/www/dashboard/current/.commit       # 看是哪個提交
curl -s https://dash.example.tw/ | grep -o 'assets/[^"]*\.js'
# 把這個檔名跟 dist/assets/ 裡的對照，不一致就是快取或 symlink 沒切換
```

**【6】確認快取標頭正確**

```bash
for u in / /assets/$(ls /var/www/dashboard/current/assets/*.js | head -1 | xargs basename); do
  echo "── $u"
  curl -sI "https://dash.example.tw$u" | grep -iE 'HTTP/|cache-control|etag'
done
```

```

HTTP/2 200
```

## 安全性注意事項

### ★★★★★ 前端環境變數不是秘密

已在上方詳述，這裡再列一次判斷法：

```
這個值放進 VITE_ 變數，會被任何人看到 —— 我能接受嗎？
   能 → 可以放（API 網址、應用標題、功能開關）
   不能 → ★★★★★ 放伺服器端，前端透過自家後端代理存取
```

### 供應鏈安全 ★★★★

前端專案動輒安裝上千個間接相依套件，每一個都是潛在入口。

```bash
# 檢查已知漏洞
npm audit
npm audit --audit-level=high        # ★★★ CI 用這個，只擋高風險以上

# 自動修（★★★ 只修不改主版本的部分）
npm audit fix

# 看某個套件為什麼被裝進來
npm ls lodash
```

**postinstall 腳本的風險 ★★★★**

```bash
# 安裝時完全不執行套件的生命週期腳本
npm ci --ignore-scripts
```

★★★★ 惡意套件最常見的手法就是在 `postinstall` 裡執行程式（竊取 `.env`、SSH 金鑰、雲端憑證）。
但有些套件（如需要編譯原生模組的）確實需要 `postinstall`，
所以 `--ignore-scripts` 不能無腦全開 —— 建議做法是**在 CI 上開啟**，
並對確實需要的套件用 allowlist 個別處理。

**其他控管手段**：

| 措施 | 做法 | 星級 |
| --- | --- | --- |
| 鎖定版本 | lock 檔進版控 + `npm ci` | ★★★★★ |
| 新套件審查 | 看週下載量、最後更新、維護者數、有無混淆程式碼 | ★★★★ |
| 私有 registry | 機關內部架 Verdaccio／Nexus，只放審過的套件 | ★★★ |
| 定期掃描 | Dependabot / Renovate 自動開 PR | ★★★ |
| 減少相依 | 一行的功能不要為它裝一個套件 | ★★★ |

> [!warning] typosquatting
> ★★★★ 攻擊者會註冊與熱門套件相似的名稱（`crossenv` vs `cross-env`、
> `lodahs` vs `lodash`）。安裝新套件前**逐字確認名稱**，
> 並用 `npm view <套件名>` 看週下載量與最後發布時間。

### 產物與伺服器

- ★★★★ **關閉正式環境的 source map**（`build.sourcemap: false`）——
  否則原始碼、註解、甚至內部 API 結構全部可下載

  正式主機不該有 npm 與編譯工具鏈
- ★★ **設定安全標頭**（CSP、X-Content-Type-Options、Referrer-Policy），

> [!question]- 練習 2：診斷白畫面

## 小測驗

Q1. `package-lock.json` 該不該進版控？為什麼？

Q2. 部署腳本裡該用 `npm install` 還是 `npm ci`？差別是什麼？

Q3. `dependencies` 與 `devDependencies` 怎麼分？

Q4. `VITE_API_KEY=sk-xxx` 寫在 `.env.production` 裡，安全嗎？

Q5. 為什麼 `dist/assets/index-BvK2xQ8p.js` 的檔名裡有一串亂碼？

Q6. Nginx 對 `index.html` 和 `assets/*` 的快取設定該分別怎麼設？設反會怎樣？

Q7. 重新整理 `https://dash.example.tw/hosts/web01` 得到 404，但從首頁點進去正常。原因是什麼？

Q8. 開發時 `/api` 呼叫都正常，部署後全部 CORS 錯誤。為什麼？

Q9. `npm run dev` 一切正常，但建置後畫面壞掉。怎麼在本機重現這個問題？

Q10. `npm ci --ignore-scripts` 是在防什麼？可以無條件全開嗎？

> [!question]- 測驗答案
> **Q1.** ★★★★★ **一定要進版控。** `package.json` 裡寫的是**版本範圍**
> （`^3.5.13` 代表任何 3.x.x），lock 檔才記錄**實際安裝的精確版本與雜湊**，
> 而且涵蓋所有間接相依（相依的相依）。
> 沒有 lock 檔，同一份程式碼在不同時間、不同機器上會裝到不同版本，
> 於是出現「我這邊好好的，CI 就是建不起來」，或更糟的「上線後行為變了但沒人改過程式碼」。
> 它同時也是**套件版本的稽核軌跡** —— 出資安事件時要靠它回答「當時我們用的是哪個版本」。
>
> **Q2.** ★★★★★ **用 `npm ci`。**
> `npm install` 依 `package.json` 解析，**可能悄悄升級套件並改寫 lock 檔**，
> 而且是增量更新 `node_modules`（會殘留舊狀態）。
> `npm ci` **只看 lock 檔**、先把 `node_modules` 整個刪掉再裝、
> 且 lock 檔與 `package.json` 不同步時直接失敗（而不是自作主張修正）。
> 這正是部署要的性質：**可重現、不會偷偷變動、有問題早點失敗**。
> 順帶一提它也比較快。本機開發或要新增套件時才用 `npm install`。
>
> **Q3.** 判斷法：**建置完的 `dist/` 還需要它嗎？**
> 需要（會被打包進產物）→ `dependencies`，如 Vue、axios；
> 只在建置期間用到 → `devDependencies`，如 Vite、TypeScript、ESLint、測試框架。
> ★★★ 純靜態前端最後上線的只有 `dist/`，兩者都不會出現在正式主機上，
> 但分清楚仍有意義：CI 可以用 `npm ci --omit=dev` 加速、
> 資安稽核時能區分「真正跑在使用者瀏覽器裡的程式碼」與「只在建置機器上跑的工具」。
>
> **Q4.** ★★★★★ **極度不安全。** Vite 對 `VITE_` 開頭的變數做的是
> **建置期的文字替換** —— 那串 `sk-xxx` 會原封不動變成 `dist/assets/index-*.js`
> 裡的一段明文字串。任何人按 F12、或直接 `curl` 那支 JS 檔都看得到，
> 搜尋引擎與爬蟲也會抓到。
> **前端不存在「隱藏的環境變數」。** 需要保密的一律放伺服器端，
> 前端呼叫自家後端的代理端點，由後端帶著金鑰去打外部 API。
> 建議在部署腳本裡加一道 `grep -rEi 'sk-|secret|password' dist/` 的自動檢查。
>
> **Q5.** 那是**內容雜湊（content hash）**，由檔案內容計算而來。
> ★★★★ 它讓「快取失效」變成自動的：內容一改，雜湊就變，檔名就變，
> 瀏覽器看到沒見過的網址一定會重新下載；內容沒改則檔名不變，
> 使用者繼續用快取，完全不必發請求。
> 這就是為什麼帶雜湊的 `assets/*` 可以放心設 `max-age=31536000, immutable`
> —— 那個網址對應的內容永遠不會改變。
>
> **Q6.** `index.html` 設 `no-cache, must-revalidate`（不快取）；
> `assets/*` 設 `public, max-age=31536000, immutable`（快取一年）。
> 邏輯是：`index.html` **沒有雜湊**、且它記載了目前該載哪些帶雜湊的資源，
> 所以必須每次都拿最新的；`assets/*` **有雜湊**，內容永不改變，快取越久越好。
> ★★★★★ **設反的後果非常嚴重**：使用者的瀏覽器永遠拿到舊的 `index.html`，
> 而它指向的舊雜湊 JS 檔已被新版部署刪除 → **整站白畫面，而且使用者自己清不掉**，
> 只能請他們強制重整。這是前端部署最常見的重大事故。
> 一句話記法：**有雜湊的長快取，沒雜湊的不快取。**
>
> **Q7.** ★★★★ SPA 的路由是**前端 JS 在瀏覽器裡處理的**，
> 伺服器上根本沒有 `/hosts/web01` 這個檔案或目錄。
> 從首頁點進去時沒有發請求（JS 直接換畫面）所以正常；
> 但重新整理會真的向伺服器要 `/hosts/web01`，Nginx 找不到就回 404。
> 解法是 `try_files $uri $uri/ /index.html;` ——
> 先找實體檔案，找不到就回 `index.html`，讓前端路由接手處理。
>
> **Q8.** 因為 `vite.config.ts` 的 `server.proxy` **只在開發伺服器（`npm run dev`）生效**。
> 開發時瀏覽器連的是 Vite dev server，它幫你把 `/api` 轉發到後端，所以同源、沒有 CORS。
> ★★★★ 建置後的 `dist/` 是一堆靜態檔案，**沒有任何代理能力**。
> 正式環境必須由 Nginx 承擔同樣的角色：`location /api/ { proxy_pass ...; }`。
> 這是「開發正常、上線壞掉」的經典成因，也提醒我們
> **開發環境與正式環境的架構差異本身就是一種風險**。
>
> **Q9.** 用 **`npm run preview`**。
> ★★★★ 它會建置後用一個本機靜態伺服器提供 `dist/`，行為接近正式環境。
> `npm run dev` 與 `npm run build` 差異很大：dev 不打包、不壓縮、不做 tree-shaking、
> 環境變數用 `.env.development`、且有 HMR 與代理。
> 所以「dev 好好的、build 壞掉」多半是壓縮／打包／環境變數／代理其中之一造成的，
> `preview` 通常一次就能重現。
> 排查順序建議：`npm run preview` 重現 → 若重現不了，才往伺服器設定（快取、路由、代理）查。
>
> **Q10.** ★★★★ 在防**惡意套件的安裝時程式碼執行**。
> npm 套件可以宣告 `preinstall` / `postinstall` 腳本，在 `npm install` 期間自動執行任意程式。
> 這是供應鏈攻擊最常見的落地手法 —— 竊取 `.env`、SSH 私鑰、雲端憑證，
> 或在 CI 環境裡橫向移動。`--ignore-scripts` 讓這些腳本完全不執行。
> **不能無條件全開**：有些套件（需要編譯原生模組的，如 `sharp`、`node-sass`、
> 部分資料庫驅動）確實依賴 `postinstall` 才能正常運作，全禁會導致安裝出來的套件不能用。
> 實務做法是**在 CI 上預設開啟**，對確實需要的套件用 allowlist
> （npm 的 `onlyBuiltDependencies` 或 pnpm 的對應設定）個別放行。
